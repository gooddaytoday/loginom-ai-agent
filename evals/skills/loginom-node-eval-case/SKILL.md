# Eval отдельного узла Loginom

Нужны совместимый checkout loginom-ai-agent, Bun, Python 3 и подготовленный CLI/стенд.
Live требует Linux bubblewrap и браузерного управления для cold rerun.

Один кейс проверяет конкретное поведение принятого узла. Вспомогательные импорт,
сортировка и экспорт допустимы, если не подменяют вычисление узла. Для большого
многоузлового сценария выбрать `loginom-eval-case`.

Skill описывает методику и артефакты; назначение и действующие AGENTS.md определяют
границы работы. В Multica оперативные роли, lease, recovery и передача результатов
определены текущим контрактом Evaler. Локально Multica не требуется.

## Выбрать роль и источники

- **Автор:** задание, входы, принятый узел/режим, checkout и критерии → собственный
  oracle → reference и проверки → комплект на точном SHA.
- **Независимый приёмщик:** сначала сохранить расчёт по исходному prompt и CSV,
  **до открытия** авторских checklist/SPEC/oracle/reference/results. После этого
  проверить точный SHA, cold, негативы и свежий product eval. Авторский код не исправлять.

Контракт файлов и проектирование кейса — [case-contract](references/case-contract.md).
Подготовка попытки — [execution](references/execution.md).
Критерий готовности и проверка происхождения — [verification](references/verification.md).
Окружение и роли — [integrations](references/integrations.md), открыть для выбранной среды.

## Порядок автора

1. Проверить полноту назначения и поддержку узла/режима в назначенном checkout.
   Маленький CSV должен различать правильное поведение и вероятные ошибки.
   Новая поддержка валидатора требует отдельного согласованного изменения внутри evals/.
2. Сделать независимый воспроизводимый расчёт. Зафиксировать исходные prompt,
   inputs и все oracle с хэшами; черновик держать вне загружаемой коллекции.
3. Подготовить `task.json`, `acceptance.json`, черновик SPEC. Модели передаются
   только prompt и inputs. Oracle, эталон и код harness внутри sandbox недоступны.
4. Выполнить один вызов `scripts/reference-attempt.ts` на одну попытку. На кейс
   максимум три авторские попытки, включая предыдущие продолжения; сохранять
   подсказки и не менять исходное задание/ожидаемое значение ради результата.
   Промежуточная ошибка потока не является терминальным итогом.
5. Проверить обязательные свойства существующим node validator и независимый
   результат; для состояний/перенастройки нужна история событий. Затем cold rerun
   точного пакета и негативные проверки обязательных доказательств.
6. Пройти последовательный gate из verification, перенести проверенный пакет,
   зафиксировать provenance и проверить итоговую коллекцию. Автор выполняет один
   fresh product eval каждого назначенного кейса; приёмщик делает свой свежий прогон.

Node eval использует code-only runner (`--skip-judge`, repeat=1). Авторитетный
результат — `code-verdict`, не общий exit 0/summary. Качество кейса
ACCEPT/REJECT/BLOCKED и измеренный product PASS/FAIL/ERROR учитывать отдельно.
Неизвестная очистка или инфраструктурный ERROR прекращают дальнейшие исполнения;
диагностика и восстановление идут по существующему operational-контракту.
