# Eval отдельного узла Loginom

Нужны совместимый checkout loginom-ai-agent, Bun, Python 3 и подготовленный CLI/стенд.
Live требует Linux bubblewrap и браузерного управления для cold rerun.

Один кейс проверяет конкретное поведение принятого узла. Вспомогательные импорт,
сортировка и экспорт допустимы, если не подменяют вычисление узла. Для большого
многоузлового сценария выбрать `loginom-eval-case`.

Skill описывает методику и артефакты; назначение и действующие AGENTS.md определяют
границы работы. В Multica оперативные роли, lease, recovery и передача результатов
определены текущим контрактом Evaler. Локально Multica не требуется.

## Выбрать роль и источники

- **Автор:** задание, входы, принятый узел/режим, checkout и критерии → собственный
  oracle → reference и проверки → комплект на точном SHA.
- **Независимый приёмщик:** сначала сохранить расчёт по исходному prompt и CSV,
  **до открытия** авторских checklist/SPEC/oracle/reference/results. После этого
  проверить точный SHA, cold, негативы и свежий product eval. Авторский код не исправлять.

Контракт файлов и проектирование кейса — [case-contract](references/case-contract.md).
Подготовка попытки — [execution](references/execution.md).
Критерий готовности и проверка происхождения — [verification](references/verification.md).
Окружение и роли — [integrations](references/integrations.md), открыть для выбранной среды.

## Порядок автора

1. Проверить полноту назначения и поддержку узла/режима в назначенном checkout.
   Маленький CSV должен различать правильное поведение и вероятные ошибки.
   Новая поддержка валидатора требует отдельного согласованного изменения внутри evals/.
2. Сделать независимый воспроизводимый расчёт. Зафиксировать исходные prompt,
   inputs и все oracle с хэшами; черновик держать вне загружаемой коллекции.
3. Подготовить `task.json`, `acceptance.json`, черновик SPEC. Модели передаются
   только prompt и inputs. Oracle, эталон и код harness внутри sandbox недоступны.
4. Выполнить один вызов `scripts/reference-attempt.ts` на одну попытку. На кейс
   максимум три авторские попытки, включая предыдущие продолжения; сохранять
   подсказки и не менять исходное задание/ожидаемое значение ради результата.
   Промежуточная ошибка потока не является терминальным итогом.
5. Проверить обязательные свойства существующим node validator и независимый
   результат; для состояний/перенастройки нужна история событий. Затем cold rerun
   точного пакета и негативные проверки обязательных доказательств.
6. Пройти последовательный gate из verification, перенести проверенный пакет,
   зафиксировать provenance и проверить итоговую коллекцию. Автор выполняет один
   fresh product eval каждого назначенного кейса; приёмщик делает свой свежий прогон.

Node eval использует code-only runner (`--skip-judge`, repeat=1). Авторитетный
результат — `code-verdict`, не общий exit 0/summary. Качество кейса
ACCEPT/REJECT/BLOCKED и измеренный product PASS/FAIL/ERROR учитывать отдельно.
Неизвестная очистка или инфраструктурный ERROR прекращают дальнейшие исполнения;
диагностика и восстановление идут по существующему operational-контракту.

## Допуск после устранённого авторского инцидента

Исторический `product=ERROR` сохраняется. Evaler может добавить к **своему проверенному** handoff evidence необязательное поле `review_admission: {kind: "recovered_author", resolution_sha256: "<SHA256 отдельного resolution receipt>"}`. Это разрешает только первоначально предусмотренный независимый Rich → Ben прогон на exact clean frozen SHA; не разрешает повтор Rich, смену модели, увеличение recovery/quality budget или ACCEPT при ERROR Ben.

До выдачи допуска Evaler offline проверяет доступность exact SHA, доставленный архив и manifest/SHA256, готовность reference/cold/обязательных позитивов и негативов всех назначенных case IDs. Отдельный resolution receipt связывает issue/task/SHA/manifest, перечисляет **каждый** назначенный кейс и каждую попытку (включая ERROR и not_started), содержит hashes источников инцидентов и подтверждённые recovery completion, архивы истории, cleanup и stand release. Непроверенные заявления автора не становятся confirmed. Receipt и его hash входят в доставленный manifest; исходные ERROR/summary не переписываются. Неполное evidence, stale SHA, незавершённая очистка и ERROR Ben блокируют передачу. Receipt не заменяет offline verification.

## Диагностика перед следующей попыткой

Повторяемый технический отказ reference требует сначала минимальной немодельной диагностики того же отказа. Оставшиеся три попытки не расходуются на неизменившуюся известную причину. Исправление проверяется адресно; требования reference/cold/oracle не ослабляются, специальное переименование узла для F3 не требуется.

После подтверждённого provider headers timeout 300 секунд с нулевыми tokens выполняется один ограниченный немодельный HEAD probe через назначенное приватное окружение. Оператор проверяет исходный неизменный `result.json` и включает его SHA256 в обязательное поле `attempt_sha256` classified receipt вместе с `kind=provider_headers_timeout`, `tokens=0`, `timeout_ms=300000`. Это идентичность исходной попытки; SHA256 самого classified receipt сохраняется отдельно как `source_sha256`. Старый receipt без идентичности попытки отклоняется.

`script/provider-route-probe.ts <classified.json> <new-private-probe.json>` требует назначенные provider base URL/key и `EVAL_PROVIDER_PROBE_LEDGER_DIR`. Ledger — один постоянный canonical directory с текущим UID и mode 0700, общий для ролей и всех доставок receipt, вне каталогов evidence. Оператор назначает его до первого probe и сохраняет между заданиями и перезапусками; другой каталог не является способом получить новый допуск. Перед будущим назначением уже израсходованные исторические probes должны быть учтены в этом ledger по проверенному исходному attempt SHA; отсутствие старой записи не разрешает повтор. Старые результаты и probes не перезапускать и не переписывать.

Helper атомарно создаёт закрытую запись `<attempt_sha256>.json` mode 0600 до HEAD. Расходование сохраняется после NO_HEADERS и ошибки записи результата; копия/переформатирование classified receipt, новый путь результата, смена URL или конкурентный вызов не дают второй запрос. Выходной receipt версии 2 содержит оба SHA и hash маршрута, без секретов. HEAD сохраняет timeout 5 секунд, без redirects/генерации/fallback/retry. Любые полученные headers (в том числе HTTP 401/405) подтверждают ответ маршрута, но не авторизацию или успешную генерацию. Исходная ошибка остаётся самостоятельным результатом.
