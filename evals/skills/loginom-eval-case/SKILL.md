# Эталонные eval-кейсы Loginom

Skill строит проверенный reference, итоговый CSV и независимый oracle для действующего eval-harness. Содержание задачи задаёт карточка, процесс — [согласованный дизайн](../../../docs/superpowers/specs/2026-10-28-analytics-expansion-design.md), очередность и pins — [план реализации](../../../docs/superpowers/plans/2026-10-28-analytics-expansion-implementation.md). Исходный текст, каталог или пакет и целевые case/collection задаются явно; отдельный репозиторий источников не нужен.

Нужны Loginom в Docker, установленный `loginom-ai-agent-cli`, Bun, Python 3, Docker и проверенный браузерный UI-путь. Функции действующего harness импортируются из `AGENT_REPO`.

Пока нет `reference.lgp` и `SPEC.md`, кейс живёт вне runnable-коллекции, например в `$WORK_ROOT/drafts/<набор>/<id>/`: загрузчик требует эти файлы при наличии `task.json`. Новые пары размещаются в `evals/tasks/analytic-detailed/<slug>-detailed/` и `evals/tasks/analytic-business/<slug>-business/`; прежние 65 кейсов не меняются. Смысл и статус пары ведутся только в [её карточке](../../../docs/superpowers/specs/2026-10-28-analytics-expansion-pairs.md), README коллекции описывает запуск.

## Когда открывать файлы

- Контракт кейса, чеклист и шаблоны — [references/case-contract.md](references/case-contract.md).
- Готовый профиль Authoring, модель, стенд и коды выхода — [references/environment.md](references/environment.md).
- Проверка пакета, браузер и калибровка — [references/verification.md](references/verification.md).

## Порядок

До live-работы установить источник, ID, среду, модель и бюджет по поручению владельца и плану. Уже данное разрешение на авторинг, cold rerun, калибровку и измерения не запрашивать повторно. Команда владельца от 28.10.2026 разрешает эту реализацию: бюджет выбирает исполнитель до запуска, измерения — по одной попытке формы, последовательно (`parallel=1`), с одинаковыми D/B pins Benchmark и judge. Коммит, push, merge и выпуск не разрешены.

1. Прочитать существующий файл `LOGINOM_EVAL_CASE_ENV` (по умолчанию `~/.config/loginom-eval-case/env`) и актуальные handoff по [environment.md](references/environment.md). Сохранить готовый Authoring; setup/OAuth/smoke и очистку runtime не повторять. Выбранные авторские pins и бюджет фиксируются в плане до запуска.
2. Прочитать карточку пары и её источник. Проверить фактические native-контракты из раздела [границ возможностей](../../../docs/superpowers/specs/2026-10-28-analytics-expansion-design.md#граница-доступных-возможностей), а не только исторический реестр узлов. Подтверждённо неподдержанный режим записать в backlog; не заменять его JavaScript. Ошибка автора сама по себе не доказывает отсутствие поддержки и не разрешает сузить задачу.
3. Подготовить обе формы по [общему D/B-контракту](references/case-contract.md#две-формы-задачи). Дословно включить общие определения, входы, выходную схему и правила формата. Только detailed раскрывает способ решения. Входы называются уникальными basename; итоговый CSV ровно один. До авторинга проверить, что ловушки меняют ответ сильнее выбранного допуска.
4. Независимо от Loginom рассчитать `oracle.csv` через закрытый `oracle.py`, читающий `data/`. Передавать модели только входы и её prompt; oracle, SPEC, reference и указатель на черновик остаются вне `--dir`. Написать `task.json`, `acceptance.json` и черновик `SPEC.md` по [контракту](references/case-contract.md).
5. Из каталога skill запустить авторскую попытку в готовом Authoring и проверить её:

```sh
bash scripts/run_attempt.sh <черновик> <номер> [файл_подсказки]
bun scripts/summarize_attempt.ts <попытка>
python3 scripts/collect_artifacts.py <попытка>
python3 scripts/check_reference.py <черновик> <попытка>
```

Повторять авторинг только по конкретной причине в заранее записанном бюджете. Помощь и подсказка фиксируются в provenance; task не меняется ради успеха автора. Код 0 без пакета — неудача. При занятости/восстановлении действовать по [environment.md](references/environment.md), без удаления lock. `check_reference.py` сверяет результат функцией `compareCsv` harness; oracle под выгрузку не подгоняется.

Для analytics expansion действуют [правила откладывания](../../../docs/superpowers/plans/2026-10-28-analytics-expansion-implementation.md#откладывание-пары-и-завершение-кампании): бюджет общий для пары и не обнуляется; без конкретного нового исправления не повторять. При исчерпании бюджета или отсутствии доступного исправления оставить обе формы как deferred вне принятого набора, указав в карточке этап/причину, попытки, evidence и условие возврата. После подтверждённой пригодности среды продолжить независимую пару. Кампания допускает меньше 100 готовых evals после разбора всех карточек; требования к принятому eval сохраняются. Измерительный FAIL не является основанием отложить корректный eval.

6. Выполнить [cold rerun D1](references/verification.md#cold-rerun-d1) через проверенный браузерный путь: прежний результат припаркован, пакет не перенастроен, SHA256 серверного LGP неизменен, все ветви исполнены, новый полный CSV совпадает с oracle. Если UI-путь недоступен, сохранить блокер до ручного исполнения владельцем; новый runner не строить.
7. Описать фактический пакет в `SPEC.md`, финализировать CLI-reference и перенести готовые формы в свои self-contained каталоги. Для [внешнего reference](references/case-contract.md#внешний-reference) использовать честный provenance без фиктивной авторской сессии. Сверить `cmp` всех входов и oracle D/B, проверить обе коллекции через `validate_collection.ts`.
8. Подготовить содержательные near-miss и выполнить [калибровку](references/verification.md#калибровка-и-измерения). Foreign negative берётся из другой аналитической задачи своей коллекции; D/B одной пары не являются отрицательными примерами друг для друга. Выполнить разрешённые независимые измерения в Benchmark, не в Authoring; не повторять ради лучшего балла.
9. В карточке пары и итоговом отчёте указать фактические reference/rerun/oracle/calibration/measurement результаты и ограничения, ссылку `Сценарий: <url>`. Профиль, историю и сценарии Authoring сохранить.
