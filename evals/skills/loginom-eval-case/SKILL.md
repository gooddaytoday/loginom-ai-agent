# Эталонные eval-кейсы Loginom

Skill строит кейс, который загружает eval-harness и который можно калибровать без выполнения пакета. Формулы, колонки, узлы, модель и адрес стенда в skill не заданы: их определяют задание, реестр узлов и файл настроек.

Готовый кейс лежит в `sources/<набор>/<id>/` репозитория agent-validation. Набор выбирает пользователь: существующий набор формата harness или новый. Не писать кейсы в каталог другого формата. Пока у кейса нет `reference.lgp` и `SPEC.md`, он живёт в черновике `$WORK_ROOT/drafts/<набор>/<id>/`: harness падает на подкаталоге с `task.json` без этих файлов, и незаконченный кейс сломал бы прогон всего набора.

## Когда открывать файлы

- Контракт кейса, чеклист и шаблоны — [references/case-contract.md](references/case-contract.md).
- Профиль, модель, стенд и коды выхода — [references/environment.md](references/environment.md).
- Проверка пакета, браузер и калибровка — [references/verification.md](references/verification.md).
- Повторное выполнение пакета — `$VALIDATION_REPO/.agents/skills/loginom-automation/SKILL.md`. Из другого репозитория этот skill сам не находится, открыть его по пути.

## Порядок

Не начинать прогон и не писать в хранилище Loginom, пока пользователь не подтвердил источник задания, набор и id кейсов.

1. Прочитать `~/.config/loginom-eval-case/env`. Если нет `MODEL`, спросить пользователя; `VARIANT` указывается, если у модели есть варианты. Не выбирать их самостоятельно.
2. Узнать источник задания: каталог в `sources/`, текст пользователя или уже проверенный пакет. Зафиксировать набор и id.
3. Прочитать реестр узлов `docs/node-development/registry.json` и карточки `docs/node-development/nodes/*/README.md` в репозитории агента. Задачу, которой нужен неподдержанный узел или режим, сузить или отклонить и объяснить почему. Имена компонентов в промпт не писать.
4. Сформулировать промпт так, чтобы два независимых расчёта дали одно значение. Промпт задаёт:
   - формулы, условия и округление;
   - полный порядок строк с разрешением равенств;
   - судьбу готовых производных колонок;
   - точные имена колонок выгрузки;
   - разделитель выгрузки — запятую или точку с запятой.

   Входы называть по basename; basename входов не повторяются. Выгрузка — не больше одной. До прогона проверить данные на равенства, пороги и смешанные типы.
5. Положить в черновик `oracle.py` на стандартной библиотеке. Он читает `data/`; модели этот файл не передавать.
   - Если кейс выгружает результат, `oracle.py` пишет `oracle.csv`. harness сам сверяет с ним каждую попытку: колонки по именам, строки и их порядок, текст точно, числа с допуском.
   - Без выгрузки `oracle.csv` не создавать, а ожидаемый граф описать в файле с другим именем.
6. Написать `task.json`, `acceptance.json` и черновик `SPEC.md` по контракту. Обязательные пункты графа и пункт результата отметить `required: true`. Пункт результата содержит `oracle.csv` целиком, потому что судья видит только текст пункта.
7. Подготовить отдельный профиль CLI по [references/environment.md](references/environment.md) и запустить `bash scripts/smoke.sh`: он должен подтвердить модель и вариант по БД сессии.
8. Из каталога skill запустить попытку и проверить её:

```sh
bash scripts/run_attempt.sh <черновик> <номер> [файл_подсказки]
bun scripts/summarize_attempt.ts <попытка>
python3 scripts/collect_artifacts.py <попытка>
python3 scripts/check_reference.py <черновик> <попытка>
```

Не больше трёх попыток. Третья может получить подсказку; `task.json` при этом не менять. Код 0 без пакета — неудача. Коды 3 и 4 и оставшийся `.writer` — остановиться и спросить пользователя. `check_reference.py` сверяет результат функцией `compareCsv` harness. Расхождение не исправлять правкой oracle под выгрузку.

9. Заново выполнить принятый пакет в Loginom по [references/verification.md](references/verification.md): `collect_artifacts.py --park`, выполнение в браузере, `collect_artifacts.py --rerun`, `check_reference.py <черновик> <попытка> --rerun`. Без браузерного MCP кейс не готов. Если повторное выполнение не совпало с oracle, пакет не принимать.
10. Переписать `SPEC.md` по фактическому `Unit.xml`, выполнить `scripts/finalize_case.py`, перенести черновик в `sources/<набор>/<id>/` и добавить строку кейса в README набора. Затем `bun scripts/prune_runtime.ts` убирает диагностику runtime из профиля.
11. `bun scripts/validate_collection.ts <набор>`, перепечатать хэши в README набора и, после предупреждения о стоимости, калибровка новых id. При одном новом id добавить в `--only` уже принятый кейс, иначе negative не считается. Живой `--repeat` не запускать и не коммитить.
12. В отчёте по каждому кейсу указать попытки, подсказку, граф, время и строку `Сценарий: <url>`.
