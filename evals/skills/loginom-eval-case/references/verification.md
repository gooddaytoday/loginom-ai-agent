# Проверка эталона

> Сведения о локальном окружении обезличены. Приватные подтверждения, упомянутые в документе, не включены в репозиторий.

Открывать после прогона CLI и перед тем, как объявить кейс готовым.

## Попытка

Из каталога skill, с файлом настроек:

1. `bun scripts/summarize_attempt.ts <попытка>` — пишет `summary.json`. Ненулевой код значит, что модель или вариант в БД сессии не совпали с настройками.
2. `python3 scripts/collect_artifacts.py <попытка>` — выбирает пакет теми же правилами, что `evals/src/artifact.ts`. Порядок выбора:
   1. последняя существующая квитанция сохранения;
   2. имя из промпта;
   3. самый новый `.lgp` после начала попытки, но только с именем `<name>.*` или `<name>-*`.

   Скрипт копирует файлы результата `<name>.*` из корня хранилища и сверяет байты загруженных входов с `data/`. Всё записывается в `storage.json`.
3. `python3 scripts/check_reference.py <черновик> <попытка>` — проверяет граф по `acceptance.json`. Если в кейсе есть `oracle.csv`, сверяет с ним ровно один `*.result.csv` функцией `compareCsv` harness с допуском `oracle_tolerance` из `task.json`. Отчёт пишется в `check.json`.

Явный режим без записи отчёта: `check_reference.py <кейс> <пакет.lgp> [файл результата]`.

Сверка такая же, как в eval: колонки сопоставляются по именам без учёта порядка; число и порядок строк и нечисловые значения сверяются точно, числа — с допуском. Расхождение не ослаблять правкой oracle под выгрузку: oracle считается из данных и задания.

## Cold rerun D1

Каноническая процедура — [cold rerun принятого reference](../../../../docs/superpowers/specs/2026-10-28-analytics-expansion-design.md#cold-rerun-принятого-reference). Использовать проверенный браузерный путь готового Authoring из handoff (приватный архив; не опубликован). Служебный инфраструктурный rerun не заменяет проверку нового пакета.

1. Завершить авторскую CLI-сессию; сохранить точные входы, принятый LGP и SHA256 фактического серверного LGP. Проверить, что CLI больше не удерживает профиль/пакет.
2. `python3 scripts/collect_artifacts.py <попытка> --park` — переименовывает результат этой попытки в `<name>-cli.*`. Подтвердить отсутствие прежнего файла по пути экспорта; новый результат должен появиться после этой парковки.
3. В отдельной браузерной сессии открыть точный сохранённый пакет через «Пакеты → Открыть». Повторный переход по hash на уже открытой домашней странице пакет не открывает. Выполнить все узлы с графа, включая независимые ветви, без открытия мастеров, применения настроек, изменения связей/путей и сохранения пакета. Активные рамки и отсутствие ошибки подтвердить UI-свидетельством; один успешный экспорт не доказывает исполнение всех ветвей. Закрыть пакет без сохранения.
4. Повторно прочитать серверный LGP и сравнить SHA256 до/после; повторный hash одной локальной копии этого не доказывает. Сохранить свидетельство отсутствия изменений настроек и появления нового результата.
5. `python3 scripts/collect_artifacts.py <попытка> --rerun` — забирает новый файл результата.
6. `python3 scripts/check_reference.py <черновик> <попытка> --rerun` — полный CSV сверяется с закрытым oracle, отчёт пишется в `check-rerun.json`.

Принимается только совокупность: неизменный серверный LGP, выполненный без перенастройки полный граф, новый CSV и `check-rerun.json:pass`. Readback или повторное применение настроек через handler не заменяют D1. Закрытый oracle не передаётся исполнителю rerun. Если проверенный UI-путь недоступен, сохранить конкретный блокер до ручного исполнения владельцем; не объявлять кейс готовым и не разрабатывать новый execution API.

Порядок колонок повторной выгрузки может отличаться от выгрузки CLI. Это известное свойство автосинхронизации Loginom: при повторном открытии пакета синхронизируемые колонки встают после сохранённых определений. Сверка по именам это допускает.

Строка отчёта для пакета в хранилище:

```
Сценарий: <URL стенда>?testable=true#packages/<пользователь>/<имя пакета>/Unit1/workflow
```

URL и пользователь берутся из настроек, имя пакета — из `storage.json`.

## Оформление и набор

`SPEC.md` описывает фактические узлы эталона. Затем:

```sh
python3 scripts/finalize_case.py <черновик> <попытка> --scenario-url <url>
mv <черновик> <collection_dir>/<id>
bun scripts/validate_collection.ts <collection_dir>
```

`finalize_case.py` ничего не пишет, если не пройдены ворота: модель подтверждена, входы совпали, `check.json` и `check-rerun.json` с `pass: true`.

Соседний `<attempt>.case` должен ссылаться на этот черновик и оставаться вне `--dir`. Для внешнего готового reference применять явный `check_reference.py <case> <package.lgp> <result.csv>` и [честный provenance](case-contract.md#внешний-reference) вместо фиктивной CLI-финализации. Перед переносом обеих форм сверить `cmp` всех входов и `oracle.csv`; обе runnable-коллекции проверить отдельно.

`validate_collection.ts` загружает набор так же, как harness с `--tasks`, и печатает `agent_inputs_hash` и `rubric_hash`. Секретные значения он не печатает.

Ошибкой считаются:

- повторяющиеся basename входов;
- больше одного пункта `requires_result_file`;
- `oracle.csv` без пункта результата или пункт результата без `oracle.csv`;
- `oracle.csv`, который не разбирает harness;
- устаревший блок `result` в `acceptance.json`;
- пустые каталоги;
- секреты из `evals/.env`.

Отклонения от соглашений skill выводятся как предупреждения:

- пункт результата без полного `oracle.csv`;
- нет пунктов `required`;
- больше 50 строк в oracle — предупреждение о размере текста для judge, без требования сузить задачу;
- размер чеклиста вне диапазона 5–8.

## Калибровка и измерения

Авторизация текущей реализации включает калибровку, cold rerun и одну измерительную попытку каждой новой формы; повторное согласие перед ними не требуется. Использовать принятые Benchmark/judge pins из [environment.md](environment.md), одинаковые D/B. Калибровку выполнять только для новых ID из конкретной коллекции:

```sh
cd <AGENT_REPO>/evals
bun run src/run.ts --calibrate --tasks <collection_dir> --only <id,id>
```

До judge проверить recipes существующим `python3 script/check-calibration-corpus.py --tasks <collection_dir> --only <id,id>` из `evals/`. Manifests находятся в общем `evals/calibration/<task.id>/cases.json`, hashes точны для каждой формы; смысловые мутации используют существующие виды `sort/aggregate/threshold/filter/column`. Ожидания `expected_failed` включают предметный пункт, `expected_oracle_pass` проверяется отдельно. Не ослаблять их ради PASS.

Positive требует ≥90 и oracle=true; near-miss — всех ожидаемых предметных провалов и точного oracle-исхода; foreign negative — ≤40. Калибровка не исполняет пакет; positive с oracle и near-miss с синтетическим CSV включают полную result-проверку, foreign negative исключает её, `requires_run` исключается всегда.

Negative — reference следующей выбранной задачи. Использовать минимум две **различные аналитические задачи внутри своей коллекции**. D/B одной пары не являются отрицательными примерами друг другу. У первой одиночной P01 foreign negative штатно отсутствует: отметить это в карточке до следующей принятой пары, затем закрыть проверку на двух задачах каждой коллекции.

Измерения — независимые чистые D/B попытки в Benchmark, по одной на форму, `--parallel 1 --repeat 1`. Не запускать runner на Authoring и не повторять измерения ради лучшего балла. До первой серии и после неё получить полный закрытый read-back разрешённой User/Peer memory, а между формами проверить журнал на запись/неожиданные инструменты по [проверке сопоставимости](../../../../docs/superpowers/specs/2026-10-28-analytics-expansion-design.md#сравнение-формулировок). Нулевой `memory_tool_calls` сам по себе не доказывает отсутствия переноса решения. При изменении памяти или неполном read-back сохранить исходы, но не объявлять сравнение свободным от переноса; не удалять память для исправления отчёта.

Хэши loader/validator фиксировать в предусмотренном отчёте/доказательствах: baseline с другими хэшами несравним. README содержит команды запуска, статусы и причины ограничений — только карточки. История и runtime Authoring сохраняются; prune не является частью принятия кейса. Коммит/push/merge/выпуск требуют отдельной команды владельца.
