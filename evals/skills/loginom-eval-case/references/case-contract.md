# Контракт кейса

Открывать при создании `task.json`, `SPEC.md`, `oracle.py`, `acceptance.json` и `provenance.json`.

Кейс собирается в явном черновом каталоге вне runnable-коллекций, например `$WORK_ROOT/drafts/<набор>/<id>/`. В целевую коллекцию переносятся готовые `task.json`, `reference.lgp`, `SPEC.md`, `acceptance.json`, `oracle.py`, `oracle.csv`, `provenance.json` и `data/*`. Загрузчик `evals/src/task.ts` пропускает с предупреждением подкаталоги без `task.json`, но падает, если при `task.json` отсутствуют reference/SPEC. Скрипты и вспомогательные каталоги в корень коллекции не класть.

## Две формы задачи

Канонические определения и статусы находятся в [карточках пар](../../../../docs/superpowers/specs/2026-10-28-analytics-expansion-pairs.md), правила — в [D/B-контракте дизайна](../../../../docs/superpowers/specs/2026-10-28-analytics-expansion-design.md#две-формулировки-одной-задачи). Detailed/business — две self-contained формы одной аналитической задачи:

- `evals/tasks/analytic-detailed/<slug>-detailed/` и `evals/tasks/analytic-business/<slug>-business/` имеют разные task ID.
- Входы, «Общий контракт», схема результата и общие правила формата дословно одинаковы в обоих prompt. Одинаковы oracle, tolerance и rubric; все входы и `oracle.csv` сверяются через `cmp`.
- Detailed раскрывает вычисления и последовательность. Business содержит цель и точные определения показателей, но не native-путь, промежуточные таблицы и алгоритмические подсказки. Необходимое для однозначного ответа бизнес-правило доступно обеим формам.
- Reference показывает один корректный путь, rubric принимает эквивалентные native-композиции. Не требовать одинаковых имён/числа узлов или внутреннего графа, если это не содержательный контракт метода.

Фактическую поддержку проверять по [runtime-контрактам](../../../../docs/superpowers/specs/2026-10-28-analytics-expansion-design.md#граница-доступных-возможностей). Неподдержанный специальный узел не заменяется JS; подтверждённое ограничение фиксируется в backlog. Неудача авторинга не разрешает упрощать задачу: допустимы помощь автору или пригодный внешний reference с теми же проверками.

## task.json

Поля, которые проверяет загрузчик:

- `id` совпадает с именем каталога.
- `title` и `prompt` — непустые строки. Входы названы по basename; общий контракт фиксирует определения, условия, округление, NULL, единицы, полный порядок строк, точные имена колонок и разделитель CSV — запятую или точку с запятой. Способ расчёта раскрывает только detailed. Названия узлов не подставлять вместо предметной постановки.
- `inputs` — пути относительно кейса, обычно `data/<файл>`. Пустой массив допустим. harness копирует входы в рабочую папку агента по basename, поэтому basename не должны совпадать.
- `reference` — `reference.lgp`, `spec` — `SPEC.md`; оба файла обязаны существовать.
- `expected_output` — текст ожидаемого результата для судьи.
- `checklist` — пункты `{id, text, weight?, required?, requires_result_file?, requires_run?}` с уникальными `id`. `required` — строго boolean, по умолчанию false.
- `timeout_ms` — положительный предел попытки. По умолчанию harness берёт `EVAL_TASK_TIMEOUT_MS`. Если эталон строился дольше, задать предел с запасом от фактического времени из `provenance.json`.
- `oracle_tolerance` — абсолютный допуск сверки чисел с `oracle.csv`, неотрицательное число, по умолчанию 0.01. Задавать, только если другой допуск следует из задания.

Хвост промпта harness хранит шаблоном `agentPromptTail` в `evals/src/task.ts` и подставляет функцией `buildAgentPrompt`. `run_attempt.sh` строит промпт той же функцией, поэтому эталон и eval получают одинаковый текст:

```
Сохрани готовый пакет как `/<username>/<name>.lgp`. Если задача требует выгрузку в файл, назови его `<name>.result.csv`. Уточняющих вопросов не задавай — принимай разумные решения самостоятельно и доведи задачу до конца.
```

harness отдаёт судье все файлы корня хранилища с именем `<name>.*`, кроме пакетов, а с `oracle.csv` сверяет ровно один `*.result.csv`. Поэтому у кейса не больше одной выгрузки.

## Оценка попытки

`pass` в eval требует трёх условий: балл судьи не ниже порога; пройдены все пункты с `required: true` или `requires_result_file: true`; выгрузка совпала с `oracle.csv`, если он есть в кейсе.

Сверку выполняет `compareCsv` из `evals/src/oracle.ts`:

- колонки сопоставляются по точным именам, регистр и пробелы значимы; порядок колонок не проверяется, а недостающая, лишняя или повторяющаяся колонка — провал;
- число и порядок строк совпадают;
- нечисловые значения совпадают точно;
- числа сравниваются с абсолютным допуском `oracle_tolerance`.

Разделитель — запятая или точка с запятой; табуляцию harness не распознаёт. `check_reference.py` вызывает ту же функцию.

## Чеклист

- Одинаковая rubric D/B: 3–5 обязательных предметных пунктов, один полный результат и один пункт честности. Предметные пункты описывают зерно, ключи, знаменатели, бизнес-правила и NULL этой задачи; общая связность графа не заменяет проверку расчёта.
- Структурный пункт проверяется по `Unit.xml`, принимает эквивалентную native-композицию и имеет `required: true`. Пункты о лишних узлах и о честности ответа обязательными не делать.
- Калибровка не исполняет пакет. Positive с `oracle.csv` и near-miss с синтетическим CSV включают результат и oracle-сверку; foreign negative исключает result-пункт. `requires_run` исключается во всех калибровочных видах.
- Содержимое файла результата проверяет ровно один пункт с `requires_result_file: true`, `required: true` и обычно `weight: 2`. Если выгрузки нет, такого пункта нет.
- Судья не видит `oracle.csv`. Пункт результата содержит его целиком и правила сверки harness, иначе балл судьи расходится с oracle. Шаблон:

  ```
  Файл результата содержит ровно <N> строк данных и <M> колонок, без лишних или пропущенных строк и колонок. Имена колонок, порядок строк и все значения каждой строки соответствуют приведённому эталонному CSV; колонки сопоставляются по именам, их порядок не проверяется. Текстовые значения совпадают точно; числовые — с абсолютным допуском ±<oracle_tolerance>. Проверяются все строки и все колонки, а не отдельные якорные значения. Эталонный CSV:
  <содержимое oracle.csv>
  ```

- Выбирать компактный информативный fixture, сохраняя смысл задачи. Таблица больше 50 строк может увеличить текст для judge, но не отменяет полного oracle и не требует сокращать корректную задачу.
- Честность финального ответа — пункт с `requires_run: true`.
- Пункт об экспорте прямо говорит, что содержимое файла им не проверяется, чтобы судья не принял его за пункт о результате при пустом `results/`.
- Пункты привязаны к ключам, колонкам и условиям этого кейса. Иначе подмена эталона на калибровке не будет замечена.
- Содержательный near-miss должен провалить свой предметный пункт в `expected_failed`; `expected_oracle_pass` проверяется отдельно. Плохой CSV сам по себе не доказывает, что judge распознал ошибку расчёта.

## acceptance.json

Параметры графа для `scripts/check_reference.py`. Фрагменты — подстроки атрибута `xsi:type` в `Unit.xml`. Их берут из `Unit.xml` пакета, где нужный узел уже есть, и не путают с названиями компонентов в промпте. Пустые строки запрещены: скрипт отклоняет такой файл.

```json
{
  "required_type_fragments": ["<фрагмент типа узла>"],
  "linked_nodes": true,
  "path": {"from": "<фрагмент источника>", "to": "<фрагмент приёмника>"},
  "inputs": {"type_fragment": "<фрагмент узла, читающего файл>", "suffixes": ["<basename входа>"]},
  "forbidden_literals": ["<значение, которое должно считаться из данных>"]
}
```

Обязателен только `required_type_fragments`. `linked_nodes: false` разрешает узлы без связей. `path`, `inputs` и `forbidden_literals` можно опустить. Блока `result` нет: файл результата сверяется с `oracle.csv` кейса, допуск берётся из `oracle_tolerance`.

## oracle.py и oracle.csv

`oracle.py` читает `data/` и пишет результат рядом с собой до вызова модели. Для таблиц использовать стандартную библиотеку; проверенную численную библиотеку для моделей — только по принятому дизайну. Oracle рассчитывается независимо от сценария и его экспорта, модели не передаётся. До авторинга проверить ловушки карточки: правдоподобное неверное решение должно отличаться сильнее допуска.

- Если кейс выгружает результат, oracle пишет ровно `oracle.csv`. harness находит файл по имени, сверяет с ним каждую попытку и включает его в `rubric_hash`.
- Заголовок `oracle.csv` — точные имена колонок из промпта. Имена непустые и не повторяются, во всех строках одинаковое число полей.
- Нечисловые значения сравниваются точно. Формат дат, логических и пустых значений должен совпадать с выгрузкой Loginom и общим контрактом D/B. Неподтверждённый формат обязательной колонки — причина проверить native-настройку либо записать ограничение, а не удалить колонку из результата.
- Numeric-looking строки могут сравниваться как числа: generic oracle не доказывает сохранность ведущих нулей. Применять существующую предметную проверку типа/графа либо ключи с буквенным префиксом, если формат ID не является смыслом задачи. Допуск выбирать по всем колонкам, одинаково для D/B; не расширять ради PASS.
- Без выгрузки `oracle.csv` не создавать, иначе harness потребует файл результата и провалит каждую попытку. Ожидаемый граф тогда описывает файл с другим именем, например `oracle.json`.

## SPEC.md

Пишется после принятия пакета по фактическому `Unit.xml`: назначение, таблица «узел / компонент / настройка», связи, входы, ожидаемый результат. Имена файла пакета и результата задаёт harness, в оценке они не учитываются.

## provenance.json

Пишет `scripts/finalize_case.py`, и только если пройдены все ворота:

- модель и вариант подтверждены по БД сессии;
- загруженные входы совпали с `data/`;
- проверка результата CLI прошла;
- проверка повторного выполнения прошла.

Содержимое: хэши входов, oracle и эталона, версия CLI, модель, путь пакета и способ его выбора, номер и число попыток, подсказка, ревизия Dock-skill из квитанции, время, счётчики, `scenario_url`. Секретов нет.

При перестройке кейса `source_task` прежнего файла сохраняется. Хэш и номер попытки заменённого эталона записываются в `supersedes`. Номер новой попытки продолжает прежнюю нумерацию.

## Внешний reference

Для готового пакета выполнить [проверки дизайна](../../../../docs/superpowers/specs/2026-10-28-analytics-expansion-design.md#готовые-пакеты-loginom): прочитать все вложенные Unit.xml, проверить используемые узлы/режимы, входы и права, полное выполнение и D1 с новым CSV, независимый oracle и near-miss. Адаптация путей/экспорта допустима; удаление специального алгоритма ради поддержки — нет.

`check_reference.py <case> <package.lgp> <result.csv>` проверяет явные файлы. Provenance внешнего пакета оформляется без CLI-финализатора: URL страницы/архива, дата получения, права, версия, хэши исходного и принятого пакетов, существенные изменения и реальные проверки. Не приписывать ему вымышленные model/session/CLI attempts. Оригинал и адаптация различаются; готовое решение и его ссылка не передаются измеряемому агенту. Обе формы исполняются независимо даже при общем reference.

## README набора

README описывает запуск коллекции и калибровку. Смысл, состав и статусы пар остаются в карточках; pins и результаты — в каноническом плане/отчёте. `scripts/validate_collection.ts` печатает актуальные хэши после изменений:

- `agent_inputs_hash` включает промпты, входы и шаблон хвоста harness;
- `rubric_hash` включает чеклист с флагами, `expected_output`, `SPEC.md`, `reference.lgp`, `oracle.csv` и `oracle_tolerance`.
