# Правка пакета по локальному пути

Кейс `local-lgp-edit` использует `input_mode: paths`: исходный пакет передаётся локальным путём `{{INPUT_ROOT}}/data/Пакет #1/sales.lgp`, без вложения. Нужно исправить существующий расчёт `amount_double` с `amount*2` на `amount*3`, сохранить остальные исходные узлы и связи, выполнить сценарий и выгрузить CSV с запятой в исходном порядке строк.

## Вход и независимый результат

`data/Пакет #1/sales.lgp`: 9873 байта, SHA256 `4313b47f09cc875993e8acc42ef2d35baec7d7dc61589af817d413b37261e7bf`. Пакет автономный, внешних файлов данных не требует. Исходный источник выдаёт строки `Alpha/10`, `Beta/20`, `Alpha/25`.

`oracle.py` использует только стандартную библиотеку Python, сначала проверяет SHA исходного пакета и затем независимо умножает известные исходные значения на 3. Он не передаётся модели. Ожидаемый `oracle.csv`:

```csv
Category,amount,amount_double
Alpha,10,30
Beta,20,60
Alpha,25,75
```

Имена колонок, число и порядок строк точны; числовой допуск равен 0. Общая сверка harness сопоставляет колонки по именам. Отдельное требование выгрузки фиксирует порядок `Category,amount,amount_double`.

## Фактический reference

Пакет содержит модуль `Unit1` / «Модуль1» (`Unit_0/Unit.xml`) и следующий рабочий граф:

1. `JS: Category, amount` — `TBGJavaScriptEngine`, GUID `bee595ca-d654-4594-b941-c50a69511e0f`. Автономный JavaScript создаёт три исходные строки с полями `Category` и `amount`. Код источника совпадает с исходным пакетом.
2. `amount_double` — `TBGCalcData`, GUID `9cfc49f4-987a-43bf-920f-5f2b81f0b893`. Существующее поле `amount_double` типа `dtFloat` вычисляется выражением `amount*3` из входного `amount`.
3. `Порядок колонок CSV` — `TBGReformColumnsEngine`, GUID `0f91bd91-3fcd-4d41-b78c-a6efb06e0381`. Выходные поля расположены как `Category` (`dtString`), `amount` (`dtInteger`), `amount_double` (`dtFloat`).
4. `ExportCSV` — `TBGExportTextFile`, GUID `ad0bf199-e30c-4e2f-a280-da9cdc957462`. Фактическая выгрузка reference — `/user/local-path-scenarios-local-lgp-edit-1.result.csv`: UTF-8 (`CodePage=65001`), заголовки из имён полей, запятая, десятичная точка.

Три исходные рабочие связи сохранены с прежними узлами и портами:

- JavaScript `58f7e6c3-511e-39d7-8853-036e0a1a7612` → Calculator `9dc72a3f-56bf-3bfc-84ec-f979daf4da6b`.
- Calculator `4ba0e2c2-69ad-3a32-bbdc-75714efe7a51` → перестройка колонок `9dc72a3f-56bf-3bfc-84ec-f979daf4da6b`.
- Перестройка колонок `4ba0e2c2-69ad-3a32-bbdc-75714efe7a51` → экспорт `9dc72a3f-56bf-3bfc-84ec-f979daf4da6b`.

В reference фактически четыре рабочих узла и три связи. Критерий сохранения требует исходные GUID и endpoints; дополнительные узлы сами по себе не являются ошибкой. Данные источника не заменены готовыми результатами, порядок строк сохранён.

## Проверка reference

Reference построен с попытки 1 без подсказки установленным prod CLI `0.3.2-localpaths74.9f7233ce71` из чистого source `9f7233ce71fbac34959b5ba64e24e730929aa077`, модель `openai/gpt-6.1-sol/xhigh` подтверждена по БД сессии. CLI вернул 1 (`CLI_TOOL_FAILED`): после активации `loginom-automation` модель один раз попыталась прочитать бинарный `.lgp` инструментом `read`, получила штатный отказ и продолжила через Loginom. Это отражено в provenance; успешный выход CLI с кодом 0 не заявляется.

`check_reference.py` подтвердил граф и CSV. Дополнительная физическая проверка через `extractPackage` и `verifyPreservedGraph` подтвердила исходные GUID/связи/порты; XML — формулу и неизменный источник. Native Close/logout завершились успешно, runtime подтвердил ACK и exit 0, `.writer` и оставшихся процессов собственного payload нет.

Независимый холодный прогон через browser MCP открыл сохранённый пакет командой «Пакеты → Открыть», выполнил все узлы, подтвердил их активное состояние без ошибок и закрыл пакет с явным отказом от сохранения, затем выполнил выход из Loginom. Повторная выгрузка прошла ту же сверку с oracle. Сохранённые байты reference и исходного пакета на сервере после Close без сохранения не изменились.
