# Выручка на открытый магазинодень — фактический эталон P24

> Сведения о локальном окружении обезличены. Приватные подтверждения, упомянутые в документе, не включены в репозиторий.

## Контракт и источник
Обе формы используют один полностью synthetic календарь открытых магазинодней и пять строк продаж.
PK календаря — (store_id,date), PK продаж — sale_id; каждая продажа относится к календарному store/day.
Локальные даты Europe/Moscow читаются как ISO-строки без преобразования часового пояса.
Опубликованный day_type имеет приоритет перед weekday: 2026-02-02 намеренно HOLIDAY.
Результат — полный реестр region/month/day_type из календаря, включая дни и группы без продаж.
Числитель — сумма amount, знаменатель — полное число календарных магазинодней; причинный эффект не заявляется.
Общий контракт, рубрика, исходные данные и oracle одинаковы D/B; подробный метод дан только в D prompt.
Нативная композиция может быть эквивалентной; имена, число узлов, GUID и расположение не являются критериями приёмки.

## Фактическая композиция Unit_0/Unit.xml
Принятый A1 содержит 12 штатных узлов и 11 связей, без JavaScript или подстановки готового результата.
1. Два TBGImportTextFile читают operating_calendar.csv и sales_lines.csv: UTF-8, «;», заголовок, десятичная точка.
2. Калькулятор получает локальную date выражением Left(timestamp,10).
3. TBGGroupDataEngine сворачивает продажи по store_id/date, gdSum(amount) → daily_revenue.
Две продажи S01/2026-02-02 дают одну дневную запись с выручкой 80, не два магазинодня.
4. TBGJoinDataEngine соединяет полный календарь слева с дневной выручкой по store_id/date.
Отсутствие JoinType=jtJoin в фактическом engine означает левое основание; шесть календарных строк сохраняются.
5. Калькулятор получает month=Left(date,7), заменяет daily_revenue через NVLF(daily_revenue,0).
Без продаж S02/2026-02-02 и S03/2026-02-02 остаются в основании с нулём.
6. Группировка region/month/day_type считает store_id (gdCount → open_store_days), суммирует daily_revenue (gdSum → revenue).
7. Калькулятор получает revenue_per_store_day выражением revenue / open_store_days без промежуточного округления.
8. Сортировка region/month/day_type ASC с LocaleAware=false задаёт ASCII-порядок строк.
9. Финальный калькулятор форматирует уже рассчитанные значения: Round(revenue*100,0), Round(ratio*1000,0), Str/StrZero/Concat.
Выручка получает две цифры после точки, нормированная метрика — три; это форматирование готовых итогов.
10. ReformColumns исключает числовые служебные поля и передаёт текстовые значения под revenue/revenue_per_store_day.
11. Текстовый экспорт сохраняет ровно шесть заданных колонок: UTF-8, «;», заголовок, кавычка, точка, LF, без BOM.
Три open_store_days остаются целочисленными; пустых итоговых ячеек нет.

## Полный ожидаемый CSV
Колонки сопоставляются по именам; порядок колонок при проверке не ограничивается.
Все 18 ячеек проверяются, строки идут по region/month/day_type, абсолютный числовой допуск ±0.001.
Все три count — целые неотрицательные тексты без дробной части; все шесть денежных текстов имеют минимум две цифры после точки.
```csv
region;month;day_type;open_store_days;revenue;revenue_per_store_day
R_A;2026-02;HOLIDAY;2;80.000000;40.000000
R_A;2026-02;WORKDAY;3;90.000000;30.000000
R_B;2026-02;HOLIDAY;1;0.000000;0.000000
```
Независимые ручной расчёт и stdlib Decimal oracle получены после заморозки raw, до нативной попытки; gold не входит в agent prompt.
