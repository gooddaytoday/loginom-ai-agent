# Node evals: общий порядок работы

Действующий контракт будущих серий. Лидер — Evaler, автор — Rich, независимая приёмка — Ben. Одна карточка содержит назначенные кейсы одного узла/режима; её не объединяют с соседними. На одном стенде живые этапы выполняются последовательно. Принятый результат возвращается в общую ветку до следующего назначения.

## Маршрут и реквизиты

Сначала применимые AGENTS.md, [checkpoint](evaler/checkpoint.md) до 20 строк, этот runbook и шапка карточки. Документы — из checkout на SHA шапки. [Методика](../skills/loginom-node-eval-case/SKILL.md) читается один раз на серию и после изменения, нужный reference — для особенностей узла. Формат результата и кодовые проверки — в [node-evals.md](node-evals.md); команды — в [operations.md](evaler/operations.md).

В шапке фиксируются проверенный SHA назначения, узел, case IDs, входы, ссылка на активный runbook серии и разрешённый этап. SHA в state.base_sha — машинная копия шапки; авторский frozen SHA при приёмке записывается отдельно. В runbook серии единожды задаются установленные CLI/helper/config, checkout/профили, endpoint/container и модели сценарного агента. Для текущего импорта это [активный раздел интеграции](2026-10-16-text-import-integration.md#действующий-маршрут).

Установленный helper исполняет операторские команды; текущие документы и handoff читаются из назначенного checkout. Отдельная доставка support ради текста не нужна. Датированные отчёты, старые support и комментарии — история, не действующие поручения. Они нужны лишь для адресного расследования.

Модели Evaler/Rich/Ben и их runtime/MCP/параллелизм сохраняются. Evaler имеет shell/Git, Multica и OpenViking, но не CLI-профили и Playwright. Живые действия выполняют Rich/Ben в собственных профилях. OpenViking выводит Peer из текущего checkout; глобальный Peer не задаётся. Generated task CODEX_HOME не подменяется общей home. Память — справка, не доказательство текущей очереди или готовности.

Процедура очистки и сброса: [node-eval-cleanup.md](node-eval-cleanup.md). C квалифицирован на eval-tests 16.10.2026: рецепт включает допуск нового экземпляра через READY → COMPLETE → RELEASED → FREE без модели. Применять весь рецепт в его границах; фактические config/container pins — только в активном runbook серии.

## Самостоятельность и пределы решений

Rich сам исследует и исправляет технические проблемы своей области. BLOCKED для Evaler нужен, когда нет новой проверяемой гипотезы; отсутствуют права/ресурсы; меняется смысл кейса, критерии, oracle, тестируемая модель/CLI либо ослабляются проверки; нужен общий защитный/операторский код с независимой проверкой до установки; затрагиваются материалы Ben/другая серия; состояние стенда неизвестно. Промежуточный прогресс лидеру не пересылается.

Evaler решает такие блокеры сам в пределах делегирования. Владелец или его уполномоченный координатор нужен только для смысла/критериев кейса, нового бюджета/платного ресурса, отсутствующих учётных данных, действий вне выделенной среды либо уничтожения невосстановимых данных. Отсутствие sudo у работника решается через уже назначенного оператора, если действие разрешено. Изменение общего защитного/операторского executable требует TDD и независимой проверки точного чистого исходника до установки. Принятые критерии не ослабляются.

Deadlines и Rich 10/card отменены, исторические файлы о них не переписываются. Не повторять неизменённую попытку без новой проверяемой гипотезы или доказанного изменения внешнего условия. Технические тайм-ауты команд и ограниченное завершение процессов сохраняются. Максимум три reference-попытки на кейс, один физический продуктовый вызов кейса каждым исполнителем, одно штатное восстановление на захват. Переделка, новый SHA и сброс не пополняют бюджеты.

Технические cold/admission/wrapper без модели не ограничиваются историческими счётчиками. Cold 8/7/5 — факты вызовов/запусков/завершений, а admission 3/3 был расходом модельных проб; старый расход не стирается. Любая новая модельная проба требует разрешённого бюджета. Привязки владения, целостность и независимость остаются обязательными.

## Состояние и нативные передачи

Только Evaler пишет metadata evaler.state и статусы назначенной этому squad карточки. Сверять metadata с фактическими comments/tasks, родителем ответа, исполнителем, этапом и SHA. Локальный файл — только cache. Нельзя передать пустой pending_tasks без чтения настоящей очереди. Не создавать карточки, расписания или новые назначения узлов по собственной инициативе.

`script/evaler-handoff.ts <input.json>` — чистая функция проверки перехода: она не пишет Multica и не запускает модель. Вход — state, событие dispatch/receipt/report и наблюдаемые pending_tasks; в gate передаётся вложенный state из metadata. Evidence получает confirmed только после реальной проверки Evaler. Схема и текущее поведение — [исходник](../src/evaler-handoff.ts); supplementary metadata не меняет код. Существующие review_cycle, reject_count, processed_report_ids и last_dispatch не обнуляются.

Перед routed поручением сохранить стабильный intent ID и ambiguous last_dispatch; после отправки — реальные comment/task ID и trigger_outcomes, без повторного комментария. queued/coalesced/deferred означают принятую передачу; после неё Evaler завершает ход и освобождает слот. Неоднозначный ответ требует чтения опубликованных comments/tasks, а не повторного назначения. no_action заканчивает ход без дополнительных комментариев. Не менять assignee и не редактировать активное поручение: это может отменить задачу.

Поручение использует нативный mention реального агента; обычный текст @Rich не маршрутизирует работу. ID Evaler — de4ba430-2182-4085-a148-fa4a3fc8a6f5, Rich — edc52e36-a965-4f93-9118-6fa5640840b4, Ben — 99804e93-d241-45f2-872d-8a1e16ec7f3d, squad — 1ea03453-9bbb-4229-adb5-2e301896240e. Перед использованием сверить roster.

```sh
multica issue comment add <current-issue-id> \
  --content-file <nonsecret-comment-file> --parent <current-trigger-comment-id> --output json
```

Если у assignment-trigger нет комментария, parent опустить. Работник публикует ровно один обычный итоговый parent comment без /note и routed mentions, затем завершает ход. Он автоматически будит Evaler; финальный текст Codex комментарий не заменяет. Rich возвращает READY_FOR_BEN либо BLOCKED с SHA, сделанным, доказательствами и нужным решением. Ben возвращает VERDICT_BEN: ACCEPT|REJECT|BLOCKED с независимым расчётом, всеми воспроизводимыми замечаниями, командами, evidence и состоянием стенда. Прямых Rich↔Ben поручений нет.

## Проверка и переделки

Ben фиксирует собственное ожидание по заданию и входам до авторских checklist/SPEC/oracle/reference/results и до любой живой работы по карточке. Затем проверяет exact frozen SHA, reference, полные типы/значения, реальные native-события, холодное открытие, отрицательные проверки и первоначально предусмотренную продуктовую попытку. Авторский код он не исправляет; мутации проверяет на своих копиях. Весь набор воспроизводимых замечаний возвращается одной проверкой, Rich исправляет его одним заходом.

Новый авторский SHA требует независимой проверки; новых модельных попыток это не даёт. Повтор замечания, объявленного исправленным, требует новой гипотезы либо BLOCKED для Evaler. Запасные кейсы не подбирать. Качество eval ACCEPT/REJECT/BLOCKED и результат продукта PASS/FAIL/ERROR учитывать раздельно. Product FAIL при достоверном измерении и очистке совместим с ACCEPT; ERROR Ben — нет. Generic summary/exit 0 не заменяют code-verdict.

**Пакет B реализован:** необязательный `state.rework_limit` задаёт число автоматических переделок (по умолчанию 1). Для текстового импорта Evaler при допуске назначает 3, сохраняя существующий state. Четвёртый свежий REJECT даёт `phase=blocked`, `executor=null`, `EVALER_DECISION_REQUIRED`; только ACCEPT переводит в in_review. Повторный REJECT с тем же ID счётчик не расходует. Повторная неполная доставка также адресуется Evaler.

Каждая остановка по worker report сохраняет `blocked_context`: reason, report_id, фактический sha и cleanup_required. Единственное событие продолжения — `continue_after_evaler` с новым ID решения, issue_id, report_id остановки, sha и target Rich/Ben. Несовпадение или фаза вне blocked дают no_action; после ACCEPT продолжения нет. При cleanup_required=true нужен stand_ready=true, который Evaler выставляет только после проверки доказательств свободы и исправности стенда. Отсутствующий cleanup считается неизвестным. Старый blocked без контекста этим событием не продолжается.

Успешное решение не запускает работника: оно возвращает ready_to_dispatch, сохраняет счётчики/лимит/историю, переносит SHA в resume_sha и очищает старый dispatch. Далее обычный dispatch проверяет очередь и не повторяет принятое назначение. Resume SHA сохраняется до следующего относящегося к текущей задаче отчёта; затем очищается. Ben допускается только к имеющемуся frozen_sha; новый результат Rich идёт через обычный READY. Новых reference/product попыток решение не даёт. Счётчик review_cycle по прежнему правилу растёт при принятом назначении Ben; это учёт передач, не бюджет вызовов.

Решение Evaler — обычный комментарий карточки с проверяемым основанием. Input gate содержит уже проверенные признаки; сама чистая функция не проверяет физическое состояние стенда. Пример события и порядок записи — [операторская инструкция](evaler/operations.md#продолжение-после-решения-evaler). Handoff исполняется из нового проверенного checkout на SHA назначения, а не из старой копии установленного операторского helper.

**Один физический вызов:** `script/run-node-evals.ts` принудительно задаёт `repeat=1` и `--no-infra-retry`. Общий harness по умолчанию сохраняет один инфраструктурный повтор; явный флаг его отключает. После вызова ERROR и его история сохраняются, штатная очистка обязательна. Ограничение действует внутри одного запуска runner; повторный вызов runner не даёт нового бюджета: перед ним исполнитель сверяет уже потраченные попытки по карточке и сохранённым результатам. При новом SHA, переделке или сбросе расход не обнуляется.

## Очистка и завершение

Каждый исполнитель завершает и очищает собственные живые запуски. Один захват стенда (lease) охватывает его последовательные инструменты; передача незавершённого живого запуска Rich к Ben запрещена. Перед карточкой status → acquire → preflight без модели выполняются на том же захвате, который Rich использует для первого разрешённого этапа. Preflight не создаёт completion: освобождение — после настоящего completion этапа.

Обычная очистка → закрытый архив истории и БД с WAL/SHM → подтверждённое completion → release → FREE. Проверяются профили, процессы и изолированное хранилище; неизвестное не считается чистым, PID/возраст/завершённая задача ресурс не освобождают. Одно штатное восстановление принадлежит исходному захвату, новое имя инцидента не даёт ещё одно.

Ben отвечает за итоговую исправность и свободу стенда. После неуспеха обычной очистки и одного восстановления допустим только заранее одобренный, проверенный рецепт сброса вместе с допуском нового экземпляра. Ben выполняет его сам либо привлекает указанного оператора к недоступному шагу. До удаления — проверенный архив и границы широкой очистки из AGENTS.md. Ben не исследует причину и не пишет операторский код внутри карточки. Старый ERROR и lease сохраняются; новый FREE не исправляет исходное измерение. Квалифицированная процедура C доступна в своих границах; неизвестное состояние остаётся BLOCKED.

Исторический recovered_author допускает только первоначальную независимую проверку Ben после offline-проверки Evaler отдельного resolution evidence по существующему коду. Это не новая попытка Rich и не право ACCEPT при ERROR Ben; original summary/evidence не переписываются. Обязательные машинные доказательства сохраняются, новых квитанций на каждый административный шаг не требуется.

После независимого ACCEPT и проверки доказательств плюс свободного исправного стенда Evaler передаёт результат в in_review. Done, merge и release — владельцу либо явно уполномоченному им координатору. Инфраструктурный сбой или неизвестная очистка — BLOCKED. Правила координатора — в AGENTS.md: без разработки новой инфраструктуры внутри карточки, без таймера с растущим заданием, без присвоения очистки; результат или один конкретный вопрос в конце хода.
