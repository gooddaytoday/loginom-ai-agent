# Автономные eval-кампании: runbook

Текущие правила завершения — [контракт](../../docs/superpowers/specs/2026-09-18-evals-design.md#завершение-автономной-кампании--2026-10-27).
Этот runbook заменяет операционные инструкции старого
[плана 23.10](../../docs/plans/2026-10-23-autonomous-evals-plan.md).
План и датированные evidence остаются историей; незавершённый LAB-170 этим
изменением не закрывается. Локальная проверка кода не подтверждает установку
на runner, применение инструкций Multica или живую приёмку.

## Постановка и запуск

Кампанию назначать прямо EvalOps. С учётом поручения он выбирает свободный
совместимый сервер по unit, процессам и native reservations, затем закрепляет manifest с
исполнителем, pins, ключами измерений, пределами и ID собственных wakeups.
Manifest и server config хранятся в защищённом каталоге вне Git; секреты
остаются в предусмотренном `tokenFile`/env, а не в комментариях или results.

Команды выполнять из `harnessRoot` принятой поставки (`evals/`). Значения
путей и имя экземпляра брать из действующего server config и manifest;
не переносить их из чужой кампании. В примерах переменные указывают на эти
проверенные абсолютные пути, `campaign_id` равен `manifest.id`.

```sh
bun --no-env-file run script/run-campaign.ts --manifest "$campaign_manifest" --server "$campaign_server" --operation reserve
sudo systemctl enable --now "loginom-eval-campaign@$campaign_id.service"
sudo systemctl status "loginom-eval-campaign@$campaign_id.service"
sudo journalctl -u "loginom-eval-campaign@$campaign_id.service" -n 100 --no-pager
```

Используется существующий [systemd template](../ops/loginom-eval-campaign@.service.in),
настроенный на тот же server config и `stateRoot`. Служба ведёт обычные batches
без LLM: учитывает сохранённые результаты и продолжает только missing.
Quality FAIL не повторяется ради PASS; модели, критерии, pins, бюджет и
исходный срок без прогресса сохраняются. Результаты и cleanup — разные факты:
завершённый batch сам по себе не подтверждает освобождение ресурсов.

## Запуск из одной карточки

Владелец создаёт карточку в `in_progress` с версией CLI, кейсами, раундами,
моделями, параллелизмом и лимитами, затем назначает EvalOps.
EvalOps сам готовит request из этих условий
и принятой конфигурации runner, создаёт wakeup, резервирует стенд, выполняет
native prepare/verify и включает собственную службу. Техническую проверку
после ремонта можно повторять в пределах исходного срока. EvalOps сохраняет
ответственность до проверенного финала.

В Multica v0.8.0 назначение карточки в `backlog` само по себе не запускает
агента. Перед назначением проверить trigger-preview: ожидается одна задача
EvalOps. При неизвестном ответе назначения перечитать карточку и задачи.

```sh
bun --no-env-file run script/launch-campaign.ts --request "$campaign_request" --server "$campaign_server"
```

Request содержит `issueId`, `executor`, `parallel`, `batchSize`, `keys`, `pins`
и `limits` существующего manifest. ID выводится из UUID карточки как
`issue-UUID`. Launcher сохраняет request, manifest и два scoped wakeup в
`stateRoot/issue-UUID`, исходный clock получает из `issue.created_at`.
Повтор с изменённым request отклоняется. Перед повтором после неизвестного
ответа перечитываются квитанции и фактическое состояние.

Установленный private server config дополнительно содержит `launch` с
`campaignUnit` (например `loginom-eval-autonomy@{campaign}.service`),
`prepareCommand` и `verifyCommand`. В массивах команд отдельный аргумент
`{outputDir}` заменяется новым private evidence-каталогом. Его родитель должен
иметь режим `0700`; сам каталог создаёт CLI при запуске. По умолчанию
используются принятый `script/run-campaign.ts` и `sudo -n systemctl`.
Для узкого установленного sudo helper задаётся `serviceCommand`.
Native подготовка получает окружение из `launch.environmentFile`.
При отсутствии настройки используется `batchEnvFile`. При раздельных
EnvironmentFiles указать постоянный controller env, поскольку batch env
переписывается контроллером перед каждой партией.
Live `launch.prepareCommand`, `launch.verifyCommand` и верхний `verifyCommand`
для финальной очистки запускать в собственном systemd unit
с `Delegate=no`: журнал подготовки сохраняет фактическую привязку к нему.
Для transient user unit использовать `systemd-run --user --wait` без
`--collect`; постоянный env должен давать доступ к user bus также из службы
кампании. После выхода пользователя доступ обеспечивает `linger`.
Не сбрасывать failed unit до штатной сверки retained reservations: его
invocation и завершение нужны существующему механизму cleanup.
Команды ремонта выполняются с постоянным controller env этой поставки.
При ошибке launcher сохраняет `launch-error.json` и одну запись в карточке.
Неподтверждённую подготовку EvalOps сначала разбирает по сохранённому receipt.

Launcher вызывается из native задачи EvalOps. Права human originator
и publisher проверяются при установке runner. Адресные поручения review
создаются штатными агентскими инструментами из задачи EvalOps с сохранённой
delegation. Набор прав проверяется реальным немодельным заданием.

## Сетевая и модельная готовность

Для новой среды или службы EvalOps проверяет фактическую конфигурацию стенда,
а не переносит proxy и пути из истории. До измерений сверить передачу нужных
настроек по всей цепочке: systemd EnvironmentFiles → controller → batch →
изолированный CLI. Проверять только необходимые ключи; полный env, токены и
proxy credentials не выводить. Диагностика `run.json` показывает признаки
proxy/bypass в эффективном окружении дочернего процесса. Эти признаки сами
по себе не доказывают выбранный сетевой маршрут или доступность API.

Если стенду нужен proxy, согласовать `HTTP_PROXY`/`HTTPS_PROXY` и нижний
регистр. `NO_PROXY`/`no_proxy` должны обходить loopback и фактические локальные
Loginom endpoints; имена брать из текущего server/slots config без схемы и
пути. Не добавлять `*` или домены провайдера для обхода proxy. Стенд с принятым
и работающим direct-доступом не требует proxy. Автоматического подбора адреса
или переключения маршрута нет.

Различать три результата: native verify подтверждает Loginom/browser и
cleanup; HTTP-проверка без авторизации подтверждает только доступность пути;
штатный `requestPreflight` подтверждает реальный модельный вызов каждого
назначенного слота. HEAD 405, успешный TLS или локальный verify не заменяют
модельный READY. Исполнитель проверяет сохранённые события, историю и cleanup;
при техническом отказе передаёт доказательства EvalOps. Дополнительных
модельных запросов и отдельной smoke-кампании не требуется.

Heartbeat Multica подтверждает соединение daemon с сервером. После ремонта
native OAuth доступ агента проверить одним коротким реальным заданием Multica:
прочитать HEAD установленного checkout и проверить доступ к slots config.
Такой readiness не запускает eval-измерения и не меняет модель агента.
Авторизация native агентов и отдельный cache судьи обновляются разными
входами; копирование активного refresh token между ними не требуется.

Авторизация судьи относится к подготовке подключённого runner. Для неё
использовать собственный постоянный OAuth cache; сохранять обновлённый файл,
не копировать при каждом запуске старый seed или кэш работающего агента.
Существующие lease на judge-home и judge gate сериализуют доступ, в том
числе внутри N2; отдельный механизм блокировки не нужен.
`login status` и срок из JWT не доказывают доступность судейства. При
`refresh_token_reused` требуется свежий вход в назначенный владельцем аккаунт. Отказ
авторизации не является transport failure и не открывает третий вызов;
сохранённые terminal unscored не пересуживаются после обновления доступа.
Порядок обновления кэша — в [официальной документации Codex](https://learn.chatgpt.com/docs/auth/ci-cd-auth).

Новая политика harness ограничивает исполнение requestPreflight 180 секундами
независимо от task timeout 15/30/60 минут; обязательный cleanup выполняется
после остановки запроса. Меньший timeout в fixtures сохраняется. До первых
измерений закрепить принятый transport, несекретные настройки bypass и hash
проверенной конфигурации в существующих pins/evidence кампании. Не сохранять
секретные значения окружения. Local/model readiness остаются отдельными
доказательствами; при неизвестном результате повтор вслепую запрещён.

Действующие кампании сохраняют свои acceptedHarness, pins, таймауты, бюджет,
исходный clock и scoped wakeups. Изменение исходников или standing instructions
не устанавливает новую политику на runner. Поставка требует отдельного решения
по существующему repair/freeze-протоколу после проверок и свежего live state;
здоровый batch ради неё не останавливается.

## Standing и wakeup инструкции EvalOps

- Штатный прогресс ведёт служба. Не запускать агента и не писать snapshot
  после каждого batch. Для новой кампании достаточно существующих событий
  `blocked`, native failure порученной задачи и periodic fallback **7200 с**.
  Нового scheduler или дополнительного `task.failed`-правила нет. Изменение
  уже действующих правил — отдельная операция установки с read-back.
- При пробуждении сначала сверить journal, unit, процессы и running/queued
  repair/review tasks. Pending retry или действующий ремонт не дублировать.
  Если действий нет, periodic завершить штатным check-in без комментария;
  event — пустым ответом без промежуточных сообщений.
- Если доступен следующий разрешённый шаг, выполнить его. Один `repairing=true`
  или неизменный `blocked` не доказывает, что кто-то продолжает ремонт.
  Технический ремонт не меняет срок без прогресса и не разрешает новые
  измерения после terminal outcome.

Для изменяющего ремонта принять владение штатной командой и сохранить его
до проверки. Не править journal вручную и не обходить cleanup guards:

```sh
bun --no-env-file run script/run-campaign.ts --manifest "$campaign_manifest" --server "$campaign_server" --operation repair --repairer EvalOps
# Диагностика и разрешённое исправление; дождаться завершения своего batch.
bun --no-env-file run script/run-campaign.ts --manifest "$campaign_manifest" --server "$campaign_server" --operation resume --repairer EvalOps
```

`repair` допускает active batch: долговечно запрещает новые measurement
admissions и следующий batch, не отменяя preflights текущего batch. Изменение окружения
или harness и `resume` выполняются после terminal batch и подтверждённого
cleanup. Если нужно перечитать EnvironmentFile, остановить только свой idle
campaign-controller, выполнить исправление и resume из нового окружения,
затем снова запустить controller. Batch и чужие службы не останавливать.

После reboot при подтверждённой необходимости новой generation между этими
командами используется `--operation prepare-generation --repairer EvalOps`.
Resume повторно проверяет cleanup и preflight; освобождает только matching
owner. Неизвестное владение или активные чужие ресурсы запрещают takeover.

## Итог и обязательный отдельный ответ исполнителя

После terminal outcome служба публикует итог **до архива** и читает его
обратно. Полный итог требует всех ключей и подтверждённой очистки;
частичный явно указывает пропуски, причину и неподтверждённые ресурсы.
Этот машинный итог одновременно служит единственным адресным поручением:
`manifest.executor` разрешается через `GET /api/agents` нужного workspace,
единственный ID сохраняется в `journal.executorAgentId` до POST.
Неоднозначное назначение требует ремонта, а не выбора первого агента.
В новых пилотах назначен EvalBaseline. Исторические manifest с EvalRunner
сохраняют своего исполнителя.

Поручение содержит `<!-- eval-handoff:CAMPAIGN -->`, его ID хранится в
`reportCommentId`. Trigger-preview оставляет вызов только назначенного
исполнителя. После read-back итога служба отключает periodic этой кампании;
событийное правило сохраняется для ремонта доставки и финального ответа.

**Инструкция назначенному исполнителю:** прочитать итог и фактическое состояние доставки;
проверить, не опубликован ли уже собственный ответ, и ответить отдельным
комментарием в ветке поручения (`parent_id=reportCommentId`). Указать число
учтённых/недостающих измерений, PASS/FAIL, cleanup, полный/частичный исход
и доставлен ли архив. Добавить отдельной строкой
`<!-- eval-executor-final:CAMPAIGN -->`, подставив точный ID кампании.
Если архив ещё не доставлен, сообщить это; финальный ответ не должен его
ждать. Не повторять измерения и не создавать второе поручение.

Служба принимает ответ только с `author_type=agent`,
`author_id=executorAgentId`, нужным `parent_id` и точным marker; прочитанный
ID сохраняет в `executorResponseCommentId`. Машинный отчёт ответом исполнителя
не считается. Повторный tick/restart сначала сверяет marker и сохранённые ID;
потерянный HTTP-ответ не разрешает слепую повторную публикацию.

Архив доставляется независимо существующей службой с download/hash-проверкой.
Ошибка загрузки сохраняет готовый итог и запускает повтор только доставки.
`published=true` и `in_review` выставляются после read-back **обоих** фактов:
проверенного архива и отдельного ответа исполнителя. Тогда отключаются
остальные собственные wakeups из manifest; чужие правила не затрагиваются.
Ошибка отключения повторяется идемпотентно, результат не теряется.
Ошибка доставки переводит карточку в `blocked` для существующего вызова
EvalOps. Если исполнитель не ответил до исходного no-progress предела,
служба сообщает `CAMPAIGN_EXECUTOR_RESPONSE_MISSING` тем же способом,
сохраняя полный итог измерений. Отдельного таймера ожидания ответа нет.

Для одного прохода сверки и незавершённой доставки используется та же команда:

```sh
bun --no-env-file run script/run-campaign.ts --manifest "$campaign_manifest" --server "$campaign_server" --once
```

Старый `published=true` остаётся no-op без требования новых полей.
Исторический внешний partial без нового handoff-marker сохраняет старый
terminal path: admission/наблюдение прекращаются без требования архива с
недоступного хоста. Новые snapshot partial используют сохранённые данные,
локальный snapshot-архив и обычное поручение с обязательным ответом.
Возврат хоста усваивает partial, не возобновляет измерения и не объявляет
очистку подтверждённой без проверки.


## Дополнения готовности и завершения

Немодельная готовность запускает и закрывает установленный Chromium в границе
изоляции CLI с его Node, sandbox и downloads options. Явный browser failure
при Help ready отклоняется. Диагностика исходной ошибки очищается от секретов
и сохраняется вне mounts агента. Campaign preflight сверяет
`pins.dockSkillRevision` и наблюдаемые bytes/inodes файловых систем с
закреплёнными порогами до допуска следующей партии.

Для новых кампаний `EVAL_JUDGE_TRANSPORT_RESERVE=1` в pins разрешает одну
третью попытку только после подтверждённого транспортного отказа без вердикта
и с подтверждённой очисткой. Отсутствие pin сохраняет лимит два. Повтор
использует прежний артефакт, модель и рубрику. Счётчик сохраняется до вызова.
Исчерпание нового бюджета записывается как `unscored`, сохраняет генерацию
и исключает повтор ключа из обычного цикла и resume. После остальных ключей
публикуется partial с отдельными числами оценённых, исполненных без оценки
и вовсе не исполненных результатов.

Для принятого private способа сдачи установить `multica.archiveMode=private`
в server config. Служба хранит архив вне cleanup слотов, читает его полностью,
публикует host/path/bytes/SHA256 ответом к отчёту и проверяет read-back.
При отсутствии настройки действует историческая доставка вложения. Проверки
ответа исполнителя и выключения своих wakeup обязательны в обоих случаях.

## Постоянные инструкции Eval Operations

EvalOps ведёт кампанию от назначения до in_review. Сам подготавливает launch,
устраняет технические блокеры выделенной среды, проверяет исправление и делает
resume. Новый многошаговый ремонт перед поставкой независимо проверяет
EvalRunner по exact SHA/diff; verdict сохраняется в карточке. Повтор принятой
процедуры требует проверки её исходных условий.

EvalRunner выполняет адресное независимое чтение назначенного ремонта,
возвращает verdict и воспроизводимые findings в исходную ветку обсуждения.
В ответе явно упоминает EvalOps и проверяет trigger-preview: успешное
завершение поручения без упоминания само по себе не возвращает руководителю
новую задачу. EvalOps включает это требование в поручение. Связь делегирования
проверяется по `delegated_from_task_id`; повторное поручение не создаётся,
пока исходное queued/running.
EvalBaseline вызывается единственным машинным финальным поручением и
подтверждает результаты, очистку и архив отдельным адресным ответом.
Оба исполняют конкретное действующее назначение.

Briefing squad и три agent description соответствуют этим ролям. Установленные
инструкции ссылаются на этот файл в принятой поставке runner. Параметры
кампании остаются в request/manifest. Обновление инструкций проверяется
read-back, фактические модели агентов берутся из конфигурации Multica.

## Проверка исходников

Выполнять `bun run test` и `bun typecheck` из `evals/`. Проверка финализации
читает ISO-время с `Z` через Python `datetime.fromisoformat`, поэтому в
тестовом PATH используется Python 3.11. Для shared Docker с исчерпанными
автоматическими пулами network fixture принимает `EVAL_TEST_DOCKER_SUBNET`.
Перед запуском проверить отсутствие пересечения выбранной подсети с Docker
IPAM и маршрутами хоста. Например, свободный искусственный диапазон
`192.0.2.0/29` позволяет проверить собственный bridge и все прежние gates.
Удаление исторических сетей для этого не требуется.
