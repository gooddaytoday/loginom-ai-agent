# Контракт параллельных evals по пользователям

Редакция 2026-10-16. Нормативны решения владельца от этой даты и
[дизайн](../../docs/plans/2026-10-11-evals-parallel-design.md).
[План](../../docs/superpowers/plans/2026-10-16-evals-parallel.md) отслеживает работу;
[runbook](../../docs/testing/loginom-ai-agent/parallel-evals.md) содержит команды.
История перенесена в [архив](../../docs/archive/2026-10-16-evals-parallel-history.md).
Этот контракт задаёт правила, а не свидетельствует о готовности реализации.

## Конфигурация и граница режимов

1. Новый путь включается через `EVAL_SLOTS_FILE` и `--parallel N`.
   Без slots file сохраняется отдельный legacy exclusive путь.
   Legacy broad cleanup не используется в режиме пользовательских слотов.
2. Один run использует выделенные Server/Studio. Идентичность контейнеров,
   canonical roots и marker kind `loginom-evals-users`, version 2 проверяются
   до dispatch и перед удалением. Изменение identity прекращает admission.
3. Каждый слот имеет уникальные username, CLI-profile, browser runtime,
   workspace, history и закрытый archive. Canonical пути не пересекаются
   друг с другом, controller state, judge home, credentials или корпусом задач.
4. Агент видит только свои prompt/inputs/workspace, подготовленный runtime
   продукта и необходимые данные своего пользователя. История и результаты
   остальных попыток, судья, controller и исходники корпуса не монтируются.
5. Значения acceptance: агент `openai/gpt-6-luna/high`, судья
   `gpt-6-sol/xhigh`, задачи `filter-active-rows`, `calc-data-double`,
   `group-sum-qty`, один repeat. CLI, задачи, rubrics и настройки закрепляются
   для N=1 замера и N=2. Исторические результаты не переписываются.

## Владение и подготовка

6. На run удерживается одна OS-блокировка сервера с долговечной бронью,
   блокировки выбранных профилей и home судьи. Отдельного user lock нет;
   слот выбирается только при удерживаемой server lock.
7. Завершение процесса controller освобождает OS guard, но не снимает бронь.
   Неизвестная или чужая reservation не перезаписывается. Маркер v2 отвергается
   прежними исполнителями широкой очистки.
8. До dispatch выполняется одна повторяемая процедура согласования остатков
   предыдущего run. Доказанно свои остатки на новом стенде harness очищает
   автоматически после обязательных проверок; неизвестность сохраняет карантин. Внутри run
   восстановления слота нет, адресного recover и цепочки эпох не требуется.
9. `prepare` создаёт недостающих пользователей, roots и профили и проверяет
   права. Повторная подготовка сохраняет существующие данные и credentials.
   `verify` и обычный run проверяют подготовку без создания и исправления
   пользователей, ACL или Pool. Неподготовленное окружение не допускается.
10. Пользователь имеет нужные права проектирования, без административных прав,
    доступа к root другого слота и общим записываемым местам. Учитываются
    Everyone и возможности серверных компонентов, а не только файловый UI.
11. `PackagePoolSize=0` настроен и перечитан до работы пользователя.
    Ненулевое значение, неподтверждённый readback или drift останавливают admission.
12. Одно admin-соединение открыто до старта слотов и обслуживает весь run.
    Исследовательские backup/pool/progress/component-пробы исключены из рабочих
    операций драйвера. Проверка/настройка обязательного Pool=0 остаётся рабочей.

## Сессии, архив и очистка

13. Пользователей слотов использует исключительно harness. Все серверные
    сессии конкретного пользователя принадлежат этому слоту. Выбор пользователя
    точный; полное native имя каждой его сессии передаётся адресному закрытию
    через заранее открытое admin-соединение. Wildcard/prefix-close запрещён.
14. После закрытия перечитывается список сессий. Только подтверждённое отсутствие
    всех сессий своего пользователя допускает следующий шаг. Сессии другого
    слота и admin не затрагиваются. Ошибка закрытия или чтения — карантин без delete.
15. До повторного использования профиля свои процессы должны завершиться,
    а история каждой попытки, БД/WAL/SHM и inputs сохраниться в закрытом архиве
    своего слота. Артефакты для судьи и результаты сохраняются вне workspace.
    Архив не является механизмом архивирования всего серверного хранилища.
16. Перед удалением нужна непосредственная проверка сервера: нет открытых файлов
    в canonical root слота. Она выполняется после закрытия и перечитывания сессий,
    без цепочки FD/kernel receipts. Нечитаемая проверка или активный файл запрещает
    delete. Опасная topology/подмена root запрещает delete.
17. Удаляется только подтверждённый root своего пользователя и свои рабочие
    файлы. Архивы и результаты сохраняются. Неизвестное владение запрещает любые
    удаления; пустой каталог или исчезнувший PID сами по себе не доказывают владение.
18. `SessionBackup` только читается до dispatch и перед очисткой. Непустой каталог
    или невозможность прочитать его останавливает весь run без удаления данных.
    Backup не создаётся для пробы, не присваивается слоту и не очищается harness.
19. Для исправления одного слота общий сервер не перезапускается. Широкая очистка
    UserStorage/SessionBackup и удаление root соседа запрещены.
20. Harness автоматически удаляет свои файлы и доказанно свои остатки прежнего
    run на новом стенде после всех обязательных проверок. Разрешение владельца
    нужно для старых стендов, инцидентов и созданного не этим harness на этом
    стенде; старое не трогается до успешного N=2 и решения одним списком.
    Ограничение «кроме собственных временных файлов текущего хода» относится
    к работе исполнителя, а не штатному поведению harness.

## Очередь, процессы и отказы

21. Существующая общая очередь выдаёт `(task, attempt)` свободному слоту.
    Слот занят до завершения агента, судьи и cleanup; здоровые слоты продолжают
    очередь независимо. Отдельная очередь судей не нужна; home защищён lock/gate.
22. Упавший слот получает карантин, сохраняет результаты и не восстанавливается
    внутри run. Здоровый продолжает очередь. После SIGINT новые jobs не допускаются,
    собственные активные цепочки завершаются безопасно, сводка сохраняется.
23. Отказ лицензии останавливает весь run. Общая ошибка прекращает новые
    admissions; неопределённый cleanup сохраняет данные и бронь. Доказанно чистые
    профили освобождаются независимо, общая server reservation — только когда
    весь run завершён без неразрешённых остатков.
24. Subreaper и проверка pid+starttime перед каждым сигналом обязательны.
    Цепочка родителей прочитана полностью и не ведёт в свой launcher — процесс
    чужой: без сигнала и без карантина. Невозможно прочитать цепочку — отказ.
    Исход попытки решает подтверждённый cleanup supervisor-а. Описи/census только
    диагностические: их отказ не меняет status/exit. Writer owner unavailable при
    подтверждённом дереве и пустом unknown не проваливает попытку; `.writer`
    снимает существующий releaseStaleWriter. Непроверенное дерево остаётся отказом.
25. Все секреты, включая пароли пользователей, авторизацию модели/судьи и admin,
    остаются вне env агента/судьи и вне results/prompts/диагностики. Runtime-auth
    и подготовленные подключения используются без передачи секретов через env.
    Секретные файлы не становятся произвольными mounts агента.
26. Home судьи — `/home/kiselev/.local/state/loginom-evals/parallel/judge-codex`.
    Разрешено снять только его удержанную бронь команды
    `585940be-5c1b-4bff-a7c6-00459a4f7fa3`, сохраняя incident A00yuH.
    VPN launcher сохраняет caller home только при том же разобранном TOML lockdown-конфиге;
    исключаются лишь корневые строковые defaults model/model_reasoning_effort,
    заданные явно в judge command. Все остальные/вложенные настройки сравниваются
    строго; ошибка разбора — отказ. Canonical path проверяется,
    symlink/выход за разрешённый root не допускается.
    VPN и ограничения сети сохраняются, глобальный home не подменяет выделенный.
    Проверяется login status через исправленный launcher без model calls; нет
    действительного входа — остановка с просьбой владельцу выполнить вход.
    Граница владения VPN-судьи — валидированный именованный systemd-юнит с лимитом
    времени. Harness ждёт wrapper с timeout и проверяет завершение этого юнита
    после выхода; root-процессы sudo/systemd-run не ошибка владения и не получают
    сигналов от harness. Неизвестный/незавершённый юнит запрещает reuse home.

## Результаты и приёмка

27. До dispatch записываются бюджет, модели/настройки и условия измерений.
    Обязательны CPU/RAM хоста и контейнеров, диск, OOM, лицензия, ошибки провайдера.
    Процессная телеметрия диагностическая и не является обязательным gate.
    Run сам запускает sample-parallel-resources.ts перед dispatch N=1/N=2 и
    завершает/дожидается collector в finally с чистым env. Перед N=1 MemAvailable
    хоста проверяется против бюджета; недостаток — остановка и сообщение владельцу.
    Отсутствие обязательного замера не превращается в PASS.
28. N=1 на тех же трёх задачах даёт замер для предложения порогов владельцу.
    Числовые пороги N=2 утверждает владелец до запуска. Нельзя менять бюджет
    после получения результата. OOM/ENOSPC, отказ лицензии, rate/quota ошибки
    исключают успешную инфраструктурную приёмку, включая скрытые retries.
29. Четыре обязательных live A/B сценария: взаимная невидимость файлов;
    закрытие A не затрагивает B; удаление A только после закрытия своих сессий;
    неизвестное владение оставляет файлы неизменными. Остальные live-тесты
    запускаются только по явному флагу и не блокируют первый полезный путь.
30. Готово после одного реального N=2 с общей сводкой, указанными моделями,
    обязательными гарантиями и очисткой только своего. Ошибки качества задач
    отражаются честно. N=1/N=2 сравнение качества — следующая задача.
31. Существующие статусы результатов/сводки сохраняются. До dispatch ошибка
    окружения возвращает exit 2 без measured summary; после dispatch ошибки
    и карантин видны в summary/exit 1. `slot_id` связывает попытку с её архивом.
32. После успешного N=2 одним проходом удаляются неиспользуемые механизмы и
    их тесты по согласованному перечню, затем выполняются unit checks/typecheck.
    До этого заморожены эпохи, user-lock, process inventories/telemetry,
    FD/kernel receipts и server storage archives. Хроники здесь не ведутся,
    новые протоколы, описи и разделы контракта не добавляются.
33. План после независимого ревью и перечень утверждены владельцем
    с поправками; повторное согласование не требуется. Технические блокеры
    решаются самостоятельно. Вопрос владельцу нужен только когда необходимы
    его данные, полномочия или изменение требований. Обязательные гарантии,
    ограничения удаления и отдельное утверждение бюджета N=2 сохраняются.
