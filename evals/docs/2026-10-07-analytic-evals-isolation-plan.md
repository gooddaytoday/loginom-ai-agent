## Граница запуска и обоснование мер

### 1. Явный набор файлов через bubblewrap

В `src/sandbox.ts` сформировать одну команду для текущего binary-режима: `bwrap --unshare-user --unshare-pid --unshare-ipc --die-with-parent --new-session … -- <реальный CLI> …`. Использовать пустой корень, собственные `/proc`, `/dev`, `/dev/shm`, `/tmp` и HOME. Сеть оставить общей для Loginom, Dock и провайдера. Это соответствует [модели bubblewrap](https://github.com/containers/bubblewrap): границу задают mounts и аргументы вызывающей программы.

Доступные mounts:

- read-only: реальный installation root выбранного CLI с Node, Chromium, runtime, skills и manifest; системные `/usr` и `/bin`/`lib` aliases; конкретные файлы DNS/NSS, CA certificates, шрифтов и загрузчика;
- read-write: **только текущий** workspace и подготовленный eval-профиль целиком, по прежним абсолютным путям; рабочий каталог внутри namespace — workspace. Постоянные файлы профиля также доступны на запись, включая OAuth refresh;
- без mounts родительского репозитория, `.git`, исходного `agent-validation`, `results`, calibration, исторических профилей, host `/tmp`, `/run`, Docker/desktop sockets. Не использовать `--ro-bind / /`: read-only не запрещает чтение ответов.

Передавать минимальное окружение запуска: PATH/locale, чистые HOME/temp, существующие обязательные переменные продукта и реально нужные proxy/TLS settings. Авторизация продукта остаётся в подготовленном профиле. Harness, судья, Docker extraction и их файловые дескрипторы не входят в namespace; ребёнку остаются stdin/stdout/stderr pipes. Shell, `rg`, `python3`, `curl` из `/usr/bin` и инструменты Loginom сохраняются. Отдельный mount Bun не нужен: в наблюдавшихся попытках агент его не использовал.

**Что закрывает:** все локальные копии ответов, включая оставшуюся `agent-validation`, Git-историю, результаты и `/proc/<внешний pid>/root|fd`. Tool permissions этого не обеспечивают; запрет отдельных имён/путей пропустит другие копии. Контейнер агента и сетевой proxy здесь не нужны. Установленный `bwrap 0.6.1` успешно выполнил probe с пустым корнем и PID namespace; host смог наблюдать потомков через `/proc`. Затем реальный CLI `0.1.17-prod` выполнил внутри этой границы `loginom check --format json`: exit 0, `LOGINOM_CONNECTION_VALID`; в дереве процессов наблюдались Node host, Chromium и crashpad. Chromium sandbox не отключался. Это подтверждает осуществимость запуска, но ещё не отрицательные проверки чтения ответов, OAuth refresh и штатный shutdown по сигналам.

Оборачивать только model-bearing `runAgent`; management-команды остаются доверенной частью harness. Сохранять исходную команду для `selectedCli`/`browserIdentity` в `process-supervisor.ts`, а `bwrap` учитывать отдельно: механическая замена `cmd[0]` ломает manifest lookup и identity. Launcher/supervisor остаются снаружи и используют host PID. При timeout/Ctrl+C SIGINT/SIGTERM направлять проверенному CLI и его потомкам, давая штатному shutdown время закрыть пакеты и выйти из Loginom (`package-cleanup.mjs`); процессы `bwrap` завершать последними, launcher — после них. Сохранить identity checks, grace periods и общий deadline. Исходный обход ledger по порядку обнаружения убивал бы внешний `bwrap` первым; с `--die-with-parent` внутренний CLI не выполняет cleanup — это подтверждено опытом пользователя на данном хосте.

Preflight отказывает до модели при отсутствии bwrap, отказе namespace/mounts, неподготовленном профиле или небезопасном стенде. Ошибка самой обёртки при dispatch/во время попытки должна явно давать **`harness_error`, `stop: true`, без судьи и повторного dispatch**, через существующие поля ошибки/`stopped_reason`; это правило имеет приоритет и при одновременном timeout/Ctrl+C. Отличать её от exit 1 самого CLI и штатного завершения обёртки supervisor по служебному результату запуска обёртки, а не только по отсутствию токенов или произвольному stderr. В исходной классификации exit 1 bwrap превращался в `failed`, а исключение до measured checkpoint могло вернуть `stop: false`: нужны оба перехода и проверка получения ошибки, а не только `statusFor`. Само сообщение `child-pid` ещё не подтверждает успешные mounts/exec. Никакого fallback без изоляции. Live `source` отклоняется с указанием существующих `EVAL_CLI_MODE=binary`/`EVAL_CLI_BIN`; fake/dry-run и judge-only/calibrate сохраняются. Изменение контракта относительно default `source` заранее записать в `evals/AGENTS.md` как явное отклонение от внешней спеки, не меняя файлы вне `evals/`.

### 2. Убрать историю из существующего eval-профиля

В существующих `prepareProfile`/`afterAttempt`, под lease и после подтверждения idle, архива диагностики и recovery, переносить историю из рабочей области. Белый список сохраняемых данных: **`cli-profile.json`**, `data/auth.json`, config, connection, model catalogue и настройки модели. Архивировать БД вместе с WAL/SHM, `data/tool-output`, `data/log`, `data/repos`, старые runtime/diagnostics/artifacts, `loginom/inputs`, `cache/tmp` и остальные файлы вне белого списка. При pending recovery/connection или неподтверждённом завершении — остановка, без переноса и новой попытки.

Первую историю **и историю каждой следующей попытки, включая infra retry**, сохранять в закрытом sibling под gitignored `.profile/`, `0700`, вне mounts агента, с привязкой к run/task/attempt/session. Перенос выполняется только при остановленной БД; проверить сохранность и возможность прочитать её из архива. Профиль и актуальные OAuth-токены переиспользуются на запись; read-only bind настроек исключён. Секретные browser/config файлы не помещать в `results`: там остаётся только прежний очищенный архив диагностики. Перед admission проверить белый список и пустые области истории. Это меняет решение `profile.test.ts`, считающее БД/inputs долговечными **в рабочем профиле**: данные теперь долговечны в закрытом архиве. Сам адресный `pruneRuntimeAttempts` можно сохранить; перенос добавить на границе попытки, обновить тесты и описание в `AGENTS.md`.

**Что закрывает:** чтение готового результата предыдущей попытки через БД/журналы/downloads внутри разрешённого mount. Новый workspace и нынешний pruning не очищают эти места. Полный `--reset-profile` или новый профиль на попытку избыточны; простое сохранение всего профиля снова открыло бы ответы.

### 3. Один чистый Loginom и эксклюзивное окно локального стенда

Один раз подготовить переиспользуемый eval-контейнер из того же образа Loginom **без монтирования `/workdir`**: сохранить `Settings.cfg`, `Users.cfg` и прочие конфиги образа, но не копировать исходный writable layer, UserStorage, SessionBackup, testdata mounts или общий socket volume. Пустой host bind скрыл бы конфиги и потому не подходит. Подключить контейнер к `loginom-net` с alias **`loginom-server-7.4.2-test`**: Studio проксирует на `ws://loginom-server-7.4.2-test:8080/ws/`. Создать при подготовке маркер выделенного стенда вне UserStorage, связанный с container ID и разрешёнными корнями очистки. Использовать существующие `LOGINOM_URL`, `LOGINOM_CONTAINER`, `LOGINOM_STORAGE_DIR`; новых пользовательских флагов и профилей на попытку нет. Инструкции подготовки — в `README.md`.

Текущий image digest: `sha256:5e3c79877de937aae168ecdcaf70c837bbbcf04e8f4262c2a976ac283ea394c2`, entrypoint `/app/loginomd --run -workdir=/workdir`. Воспроизвести необходимые runtime-библиотеки `/app/libxml2.so.16*` и проверить версию/работоспособность без пользовательских данных. Проверить Python в `Components.cfg` чистого сервера; **если включён — явно выключить**, не полагаться на default. Иначе ответы могут оставаться вне очищаемого storage, например в `/tmp`. Публичный каталог `user-v1` Python/ExecCmd не предоставляет; необходимые аналитические узлы и локальный Python сохраняются.

На всё окно eval исходный сервер остановлен. У него **`restart=always`**: при подготовке окна сохранить политику, временно отключить автоперезапуск и остановить контейнер; после остановки eval-контейнера восстановить политику и исходный сервер с прежними данными. Проверить, что alias ведёт только на чистый сервер. Внешние Desktop inspector/CDP выключены. Пользователь наблюдал случайные 33001/39783 — это примеры, не константы. При недоступности проверки или обнаружении внешнего debugger/активного исходного сервера — отказ. Harness не закрывает чужие приложения автоматически; оператор не запускает их параллельно. Сетевой proxy не нужен при таком режиме доверенного стенда.

Между попытками завершить собственную серверную сессию, извлечь результаты и подтвердить завершение работы. **Широкую очистку разрешать только после проверки маркера, container ID/корней очистки и отсутствия host bind mounts; проверять повторно непосредственно перед удалением и обращаться по проверенному ID.** Маркер `/workdir/.loginom-evals-isolated.json` создаётся только при подготовке нового чистого контейнера; он фиксирует ID, выбранный storage и корни `/workdir/UserStorage` и `/workdir/SessionBackup`. Нестандартное имя файла не должно обходить очистку. Default `LOGINOM_CONTAINER=loginom-server-master` и текущий `.env` с пользовательским сервером сами по себе никогда не разрешают такую очистку. ## Последовательность реализации

Последовательность сохраняется; выполненная часть и оставшаяся работа отмечены в checkpoint ниже. Реализация — TDD из `evals/`: один падающий тест поведения → минимальное изменение → зелёный тест. Продуктовые пакеты, форматы задач и оценки не менять.

1. **Проверка точных mounts до переноса и разработки.** Выполнен запуск без модели: установленный CLI со штатным `loginom check --format json`, read-only installation root и `/usr`, aliases `/bin`, `/sbin`, `/lib`, `/lib64`, отдельные DNS/NSS/CA/font/loader файлы; read-write только eval-профиль и workspace; собственные HOME, `/tmp`, `/proc`, `/dev`, `/dev/shm`, user/PID/IPC namespaces. Получен exit 0, `LOGINOM_CONNECTION_VALID`, реально стартовали host/Chromium. Runtime использует `chromiumSandbox: true`; Chromium нужны **вложенные user namespaces**, их доступность входит в эту проверку, sandbox не отключается. Перезапись OAuth и обработка сигналов этим check не проверены — они входят в пункты 3–4. Это проверка осуществимости, не приёмка защиты ответов. Если при реализации изменится набор mounts, повторить проверку до следующих изменений; при отказе остановиться и уточнить этот же дизайн. Простого `/bin/sh` probe недостаточно.

## Калибровка и сравнимость

Перенос неизменных файлов не меняет `agent_inputs_hash`, `rubric_hash` и corpus hash: абсолютный `task.dir` в них не входит. Исторические пути в provenance/XML — доказательства прежней приёмки, а не обязательная зависимость harness; их сохранить. Повторная полная калибровка и baseline 35 автоматически не назначаются.

Изоляция, скрытие межпопыточной истории и чистый Loginom меняют условия агента. **В README явно запретить использовать старый неизолированный и новый изолированный прогоны как контролируемое сравнение**, даже если `compare` признаёт их сравнимыми: он не проверяет harness SHA/режим изоляции. Существующие `label` и harness SHA служат ручной идентификации, не автоматической защитой; формат отчётов не менять. Один smoke подтверждает работоспособность, не качество на 35 задачах. Полный новый baseline нужен только для количественного сравнения в новых условиях; обе стороны должны работать в одинаковой изоляции.

Изменение промпта судьи требует пересуживания всего корпуса по `AGENTS.md`. Изменение рубрик/oracle/мутаций требует проверки затронутых ожиданий и обновления соответствующих доказательств; изменения протокола/версии судьи, делающие прежнюю калибровку неприменимой, требуют новой калибровки. Этот перенос таких изменений не предусматривает.

## Существенные ограничения и checkpoint

- Linux и установленный binary CLI; полноценный live source требует отдельной упаковки runtime и не входит в минимальное решение.
- Нужно эксклюзивное окно локального Loginom endpoint без внешних debugger, включая приёмки LAB-16; при невозможности запуск запрещён.
- Узкий поиск доступного Dock не является доказательством отсутствия любых материалов на удалённом сервере. Проверенные доступные ресурсы не содержат ответов; эталонный корпус и результаты не должны публиковаться в разрешённые агенту ресурсы продукта.
