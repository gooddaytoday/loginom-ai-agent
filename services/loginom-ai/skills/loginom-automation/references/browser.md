# Браузер, подключение и восстановление

Схемы браузерных tools получены из закреплённого Playwright MCP. Для обычных
действий используй snapshot/locators. Для поллинга, геометрии и настоящей мыши
доступен `browser_run_code_unsafe` с асинхронной функцией `(page) => ...`.
Работа идёт в основном документе Loginom; наличие iframe сначала проверяй по DOM.

Зависимые браузерные действия выполняй строго последовательно: получи результат
клика, затем исследуй новое состояние, затем выбирай следующее действие. Не отправляй
click и проверку его результата параллельными tool calls в одном ответе. При открытом
file chooser следующим браузерным действием должен быть file-upload, при другом
native dialog — его адресная обработка; обычный DOM tool не обслуживает modal state.

Форма Loginom, если она показана: input внутри
`LoginForm;Login;edtUsername` и `LoginForm;Login;edtPassword`, кнопка
`LoginForm;Login;btnLogin`. Не предполагается общий пароль или автоматический логин.
После авторизации ожидай аватар и снятие маски, а не только завершение навигации.
При Keycloak/другой форме используй её фактическое состояние или ввод пользователем.

## Ожидания

Ориентиры из helpers: до 70 секунд на data-tid, 60 секунд на стартовую маску,
300 секунд на открытие пакета, 120 секунд на таблицу preview. Обычные переходы
проверяются по исчезновению маски и появлению ожидаемого контейнера. Для длительного
выполнения сообщай пользователю, что процесс продолжается, и проверяй статус.
Не объявляй успех по отсутствию маски: дополнительно нужен ожидаемый результат.

Проверь `.x-message-box-error`, видимый toast и `WizrdMCF;btnError`.
При ошибке мастера открой подробности и прочти текст. Консоль может содержать
посторонние предупреждения: соотнеси сообщение с выполняемым действием.

## Диалоги и файлы

Native alert/confirm/beforeunload не входят в DOM ExtJS. Используй browser dialog
tool при появлении диалога. Если навигация ожидает beforeunload, сначала выясни,
сохранены ли изменения; затем адресно обработай этот диалог. Не принимай будущие
диалоги постоянно и без проверки. ExtJS msgBox требует обычного действия по DOM.

Для загрузки файла приготовь разрешённый пользователем локальный fixture внутри
каталога артефактов Dock. Прочти актуальный `filestorage.ts`, выбери нужную папку,
активируй Upload и используй file-upload tool либо `setInputFiles` на найденном
input. Проверь строку файла в хранилище и её имя/размер. Клик Upload без появления
файла не доказывает загрузку. Не перезаписывай одноимённый пользовательский файл
в рамках проверки; используй свободное имя.

Браузер принимает файлы только из разрешённых каталогов своей сессии. Если исходный
файл находится снаружи, это не отсутствие доступа агента к файлу: обычным файловым
инструментом агента скопируй разрешённый пользователем файл без изменения содержимого
в `artifacts` текущей сессии. Для небольшого текстового fixture доступны read/write;
для двоичного файла нужен инструмент копирования байтов. Путь бери из диагностики
или сообщения allowed roots. После копирования используй новый абсолютный путь
в browser upload. Не расширяй разрешённые корни браузера и не передавай файл через
внутренние методы Loginom.

Скриншоты сохраняй в собственном каталоге сессии, указанном диагностикой. Перед
показом проверь, что изображение содержит нужный результат и не раскрывает секреты.
Двоичные файлы и изображения не отправляются в общий архив автоматически.
В отчёте используй фактический путь из ответа screenshot tool, а не предполагаемый
подкаталог. Проверь существование файла перед передачей ссылки пользователю.

## Неудачное действие

Сначала обнови DOM и состояние процесса. При таймауте проверь, произошло ли
действие; при частичном результате продолжи с него. Меняй подход только по новой
улике: неверная вкладка, маска, readonly, отсутствующий порт или другой selector.
Несколько одинаковых неудач без нового сигнала требуют объяснения пользователю,
а не бесконечного цикла. Перезапуск браузера закрывает собственное окно и может
потерять несохранённое; используй его только после проверки этой ситуации.
