## Результат и зависимости

Один вызов `node.apply` создаёт/изменяет «Фильтр строк», настраивает, выполняет и читает оба выхода.
Новый узел создаёт внутренний драйвер добавления; существующий задаётся точной ссылкой.
Настройка условий — отдельный обработчик типа внутри общей локальной операции,
без отдельных модельных команд на открытие мастера, клики или чтение портов.

## Вход и выход обработчика

Использовать общий контракт `node.apply`; новые MCP-ключи здесь не объявляются.
Параметры типа задают полный упорядоченный набор условий: точное поле либо номер
строки, оператор, типизированное значение/границы/список, регистр строк и И/ИЛИ.
Поддержать сравнения `=`, `<>`, `<`, `<=`, `>`, `>=`, Null/не Null, в/вне интервала,
в/вне списка, содержит/начинается/заканчивается и их отрицания; отбор по номеру строки.
Семантику И/ИЛИ задавать группами условий И, разделёнными ИЛИ; произвольные скобки
не подменять плоской последовательностью. Совместимость оператора проверять по типу.
При изменении существующего узла набор условий заменяется целиком по запросу;
остальные настройки и посторонние объекты сохраняются. Пустой набор не означает
неявное «пропустить всё»: вернуть требование явно задать поддержанное условие.
Управляющие переменные и переменный тип — вне первого режима, выявлять до изменения UI.

Выход: отдельные refs, число строк и схема для «Соответствуют условию» и
«Не соответствуют условию», общая execution identity и до десяти строк выборки
с указанием порта каждой строки, полноты и ограничений точности.
Пустой порт — допустимый результат; ошибка/непрочитанный порт не равны нулю строк.
По умолчанию «Выполнить» с ожиданием обоих выходов. При «Готово» вернуть
`execution=not_requested`, `output=not_refreshed`; прежние данные не доказывают новые условия.

## Этапы реализации и ожидания

1. Codex исследует отдельную live-сессию: добавление/удаление условий, ИЛИ,
   типовые редакторы, списки, диапазоны, регистр и оба выходных порта.
2. Зафиксировать допустимые операторы и нормализованное описание условий;
   проверить весь запрос и входную схему до создания/редактирования узла.
3. Добавить ограниченное чтение страницы фильтра и её редакторов, с owner-контекстом;
   общий lifecycle открывает мастер нужного узла и обеспечивает готовность входа.
4. Применить полный набор условий, не смешивая его с прежними строками;
   после каждой правки проверять нужную строку, её оператор, значения и позицию.
5. Перед завершением сверить весь логический набор, затем передать управление
   общему finish/execute/result. Не использовать предпросмотр мастера вместо выполнения.
6. Дождаться нового выполнения, прочитать оба конкретных порта и проверить полноту
   доступных счётчиков. При адресном дополнительном чтении не запускать узел повторно.

Именованные ожидания: мастер нужного узла, строка условия, связанный редактор,
применённый список/интервал, отсутствие ошибки, завершение и свежие выходы.
Ожидание прекращается при достижении условия; `settle: 0`, контекст/epoch и deadline сохранены.
До двух обновлений наблюдения разрешены только при `NOT_APPLIED` до жеста,
`effect_possible=false`, той же цели и исходном deadline. Каждая попытка журналируется.
После возможного добавления условия сверить строки; не добавлять дубль вслепую.
После возможного «Выполнить» продолжать status/reconciliation исходной операции.
Отмена и cleanup общие; частичная настройка и неизвестный исход не становятся SUCCEEDED.

## Проверки и критерий готовности

- Табличные поведенческие проверки всех заявленных операторов на совместимых типах,
  границы интервалов, регистр, список, И/ИЛИ с различающимися результатами при иной группировке.
- Проверить Null против пустой строки, дроби более двух знаков, даты с секундами,
  номер строки после изменённого порядка, все/ни одной подходящей записи и пустой вход.
- На малом golden-наборе проверить оба полных выхода: каждая входная запись попала
  ровно в один выход, значения/дубли сохранены, сумма чисел строк равна входу.
- Проверить изменение существующего фильтра, сохранность чужих объектов, stale до клика,
  потерянный ответ после добавления строки/выполнения, отмену и повтор operation ID.
- В QA отдельно проверить «Готово»/«Выполнить»/«Закрыть» и roundtrip мастера;
  штатный проход должен обходиться без повторного открытия его настроек.
- Предпросмотр мастера ограничен первыми 1000 входных и 25 подходящими строками;
  тест с совпадением за этой границей должен проверять выполненный выход.
  Для точных значений использовать подтверждённый полноточный режим «Таблица».
- После Codex-отладки через настоящий MCP провести goal-only Hermes-приёмку:
  `openai-codex` / `gpt-5.6-sol` / `low`, существующая подписка, без fallback.
  Задача включает CSV-очистку, изменение отбора, оба выхода и save/reopen/reexecute пакета.
- Независимый аудитор проверяет полный ожидаемый результат и граф на закреплённых
  runtime/harness; записать времена фаз, все попытки, токены и компактность ответов.

Готовность: заявленные операторы и оба выхода прошли source/live/QA и самостоятельную
приёмку без модельных UI-шагов внутри `node.apply`; coverage обновлён по доказательствам.
