## Подтверждённый дефект

### N11-R1 — P2: проверять коллизии по итоговым правилам и режиму существующего узла

Основное место: `unavailable:artifact-2d5d49d5c6d67019`.
Связанный порядок действий: `unavailable:artifact-dfe2a5ceaef3d975,46–53`;
сбор сохранённых правил: `unavailable:artifact-49216f767852c94a`.

**Сценарий.** Во входе существуют строковые поля `A` и `A_Replace`. В уже
настроенном узле включена замена для `A`, режим выхода — `replace`. Это допустимая
конфигурация с полями выхода `A`, `A_Replaced`, `A_Replace`. Пользователь передаёт
только `parameters={"output_mode":"add"}`, сохраняя существующие правила.
После переключения потребуются два поля `A_Replace`: сохранённое входное и новое
производное. Контракт подплана требует отказа до изменения настроек.

**Причина.** `changed` строится только из `p.rules`. При отсутствии `rules` он
пуст, поэтому проверка коллизий не выполняется. Сохранённые правила читаются
позднее, но итоговая конфигурация повторно не проверяется на коллизии перед
`setMode`. Эта функция сначала посылает действие `dptSupplement`, и только
после неё вызывается `validateReplacementSources`. Следовательно, отказ по
известной заранее коллизии переносится за действие изменения политики выхода.
Это нарушает обещание раннего отказа и оставляет необходимость восстановления
после уже начатой настройки. Успешное сохранение ошибочного пакета не утверждается.

Вторая форма той же ошибки: в существующем `add`-узле правило было только для `B`,
во входе есть `A`, `A_Replace`, `B`. Запрос добавляет правило `A`, опуская режим.
Resolver считает только суффикс `_Replaced`, хотя сохраняемый режим требует
также `_Replace`. Проверка должна учитывать объединение сохранённых и новых
правил и фактический режим при отсутствии нового значения.

**Доказательство ревью.** На закреплённом Node 24.19.0 вызовы актуальных функций
дали следующие результаты:

| Проверка | Результат |
|---|---|
| `resolveReplacementParameters({rules:[ruleA],output_mode:'add'}, fields)` | Отказ `Replacement output collision: A_Replace` |
| Тот же resolver с `{output_mode:'add'}` | Пропустил запрос |
| Тот же resolver с `{rules:[ruleA]}` | Пропустил запрос, не имея фактического режима |
| `replacementSources({rules:[ruleA],input_fields:fields},'add')` | `A, A_Replace, A_Replaced, A_Replace` |
| `configureReplacementInlineMapping` с сохранённым `ruleA` и requested mode `add` | Дошёл до действия `btnProduceType;mn;dptSupplement` |

Последняя проверка использовала подставленный канал: исходное состояние выхода
`produce_mode='replace'`, реальные функции кандидата, запись действий и остановка
исключением непосредственно перед действием смены политики. Полученная
последовательность: Table → Links → Produce menu → Supplement. Проверка
не имитирует серверную реакцию Loginom на коллизию и не доказывает конкретный
финальный статус операции на стенде. Подтверждён именно пропуск ранней проверки.

**Требуемое исправление и проверка.** До изменения таблиц/выходной политики
проверить полную эффективную конфигурацию: сохранённые правила плюс частичный
запрос, действительный сохранённый режим либо явно запрошенный. Добавить целевые
проверки обеих форм запроса выше, отказа без изменения правил/режима, и контрольные
неконфликтующие смены `replace ↔ add` с сохранением неперечисленных правил.
В назначенном раунде воспроизвести через публичный `node.apply` на отдельной
диагностической копии пакета, проверить исходные настройки после отказа и успешный
полный результат неконфликтующего запроса. Оригинал
`/test-2/Node11-Handler-90de4e18.lgp` сохранить.
