## N12-R1 — P2: схема пустого выхода берётся из проверяемого результата

**Место:** `tools/loginom-acceptance/duplicates_output_evidence.py:28`;
передача этой схемы как expected в `verify_calculator_output` — строка 63.
Вызовы из полного сценарного аудитора — `duplicates_node_acceptance.py:101`.

**Триггер:** узел возвращает 0 строк, а схема таблицы отличается от сохранённой
конфигурации/исходной fixture. Например, таблица содержит `WrongId` вместо `Id`,
хотя импорт и настройка узла по-прежнему определяют `Id`.

**Наблюдаемое поведение:** `verify_duplicates_output` создаёт `columns` из
`node_checkpoint.result.output.ports[0].schema` и использует их как независимый
expected для проверки сырых таблиц. При `source_rows=[]` построчная проверка
`verify_marking` не проверяет имена/полноту столбцов. Поэтому согласованная между
сырым чтением и результатом неверная схема проходит. Отдельный конфигурационный
аудитор проверяет настройки мастера, но не связывает их со схемой прочитанной
таблицы; он также проходит при неизменённой правильной конфигурации.

**Подтверждение:** на копии реального журнала сессии
`343124f4-1fef-41e0-bc4f-e9a988339b2d`, операция `node12-qa2-empty-mark`:

1. Исходный журнал: output PASS, configuration PASS.
2. Только в read-части доказательств заменено точное значение `Id` на `WrongId`.
   Конфигурация checkpoint восстановлена из оригинала; предыдущие настройки и
   входной mapping оставлены неизменными. Для согласованного тестового журнала
   пересчитаны локальные digest/signature шагов относительно изменённых наблюдений.
3. Результат: output PASS, configuration PASS; execution ID сохранился `:455:11`.

Воспроизводящий приватный скрипт:
`.dock/node12-review/schema-probe.py` (запуск из корня worktree через Python 3).
SHA-256: `09c60e8ab150880b3a3f2fe9b7645f8608f71cd5c83a01e1712fb0d8d2ff9743`.
Результат: `.dock/node12-review/schema-probe-result.json`.
Оригинальный журнал не изменялся; преобразование сделано только в памяти процесса.

Это **подтверждённый дефект проверяющей функции на согласованных тестовых
доказательствах**, а не наблюдавшаяся ошибка Loginom и не утверждение об обходе
аутентификации журнала. Полный автономный auditor на подменённом сценарии не
запускался. Source-инференс: его проверки initial/persisted output используют ту
же функцию без независимого expected schema, поэтому этот пробел остаётся и там.

**Ожидается:** схема должна независимо определяться исходной fixture и четырьмя
служебными полями, сверяться с реальной таблицей и конфигурацией даже при 0 строк.
Допустимый порядок можно проверять отдельно от состава. Нужен отрицательный тест
на согласованную неверную схему пустого вывода (переименование, потеря служебного
поля, неверный тип) при неизменённой правильной конфигурации; исходная fixture
должна продолжать проходить. Выполнить в назначенном раунде доработок.

## Границы покрытия и следующего этапа

Живой вывод покрывает integer/string, составные ключи, несколько выходных ролей,
NULL/пустую строку/текст `null` в сравниваемом поле, обе группы одновременно,
key-only и пустую таблицу. Булевы, real и datetime принимаются scalar-контрактом,
но отдельной живой матрицей не подтверждены; NULL именно в ключе тоже не покрыт
этими fixtures. Это границы проверки, а не автоматически найденные дефекты:
подплан требует строковые/числовые поля и явное обозначение неизвестной семантики.

Повтор завершённого operation ID подтверждён исторической source-сессией
`ae2d9d34-e86c-4508-a2b1-a4f657efcb5a`; отдельного node12 live fault-injection
потери ответа в итоговом журнале нет. Общие проверки lost reply присутствуют,
но их нельзя называть полной живой проверкой этого случая для нового handler.
При доработках следует явно сохранить эту границу или закрыть её адресной проверкой.
