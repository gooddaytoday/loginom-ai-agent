# Node17: сохранение ответа download до проверок

Задание `node17:download-evidence-fix:1:921c5340`.
Исправлен только acceptance observer. Новая live-сессия, браузерный вызов,
прогон компонента и Hermes в этой фазе не запускались.

## Изменение и проверка

Отдельный `observer-responses.jsonl` теперь получает durable `received` до
вызова parser: тип/размер/число блоков и SHA256 текстов, без самого текста.
После успешного разбора записывается `decoded` с ограниченной проекцией
native ответа; только после этой записи выполняются status/success assertions.
Разрешены статусы, фазы и фиксированный список DOWNLOAD-кодов, булевы
`effect_possible`/`cleanup_complete`, явно сообщённые pending/download counts
и фиксированные булевы context checks. Сообщения ошибок, URL, пути, содержимое
файла, полное UI и произвольные trace-поля не копируются в новые receipts.
Отсутствующие поля остаются null; завершение host promise не означает
отсутствия незавершённого UI-действия.

Сохраняются run/session/read/seq/step, hash браузерного запроса и code hash,
монотонное время, исходный deadline и признак отмены. Текст не больше 1 MiB
на блок и не больше 8 блоков допускается к разбору. Больший ответ получает
ограниченный fingerprint и отказ. Успешный ответ всё ещё проверяется прежними
проверками графа, навигации, байтов и причинной связи. Существующий журнал
успешных шагов не заменён проекцией: он нужен независимому аудиту.

Received-negative, parse failure, transport throw и cancellation имеют разные
записи. Транспортный throw не создаёт received. Поздний полученный ответ после
отмены сохраняется, но не разрешает dispatch. В журнале действий после
prepared записывается completed только при успехе либо failure при отказе;
failure не подделывает cleanup. Отмена после prepared и до вызова браузера
также фиксируется. Отмена исходного MCP-вызова передаётся observer.
Ошибка записи receipts блокирует дальнейшее выполнение; при недоступном диске
сама запись failure тоже может оказаться невозможной — гарантировать её нельзя.

**28 Node-проверок PASS**, включая реальные SDK in-memory проверки и все пять
ветвей (negative/parse/transport/cancel/success) через настоящий observer gate:
при incomplete dispatch=0, при полном синтетическом успехе dispatch=1.
Проверены отсутствие секретного текста, ограничения ответа, отказ записи,
порядок received→decoded→validated/failure и отмена после prepared.
**20 Python-проверок PASS.** Это локальные тесты, не native acceptance.

## Предлагаемая одна диагностическая проверка — ещё не разрешена к запуску

Старая сессия `3b238204-8e1e-42c3-91f6-45e28900ff02` закрыта. Предложение:
одна новая изолированная actual stdio user-v1 сессия, без смены browser/client/
profile/document внутри попытки. Восстановление старого браузерного профиля
и повторное использование старых runtime receipts исключены.

1. После одобрения scope подготовить отдельную private цель `download-diagnosis`
   в acceptance entry с точными новыми pins и one-shot marker. Она должна
   проверять runtime/harness/goal/catalog/account и разрешать только приведённый
   ниже набор действий. Проверки обычного component/full admission остаются
   закрытыми. Диагностический вход ещё не реализован; обычный runner сейчас
   не может запуститься с новым observer из-за protected check.
2. Пинованный Node24.19.0; URL
   `http://logi-test-plan.bg.local/app/?testable=true`, Loginom7.4.2,
   аккаунт test-2, каталог node11.2-candidate с SHA
   `bb2fe2207e01d594108efb591d1c25036adc12f67168ef895dfde755d391ac2a`.
   Изолированный user-v1 config, видимый maximized browser, viewport=null.
   Сначала native account/owner probe, один Avatar close, подтверждённое
   исчезновение меню и отсутствие pending. При отказе — закрытие и остановка.
3. В этой же сессии одна доставка неизменённого Main CSV, затем три
   node.apply: source, исходный export, ожидаемый reject. Новый уникальный
   `/test-2/Dock-export-<run>-csv.csv`. Независимо проверить полные 124 байта,
   SHA `9f9972ed174053d02745df8df0c3c2d44697b33f7fb6da2ce8463eb58cc5d13a`,
   5×3 и terminal reject с cleanup и без execution. Это необходимый контекст
   для воспроизведения прежней границы; старый файл не подставляется.
4. Один публичный replace-intent поступает в тот же stdio interceptor, чтобы
   связать исходный request с observer. **Продуктовый replace не отправляется
   ни при каком исходе диагностики.** В diagnostic-purpose должен быть
   отдельный безусловный запрет actual-dispatch после observer; сначала
   подтвердить локально, что даже успешный observer не вызывает product handler.
   Это диагностическая остановка, а не component PASS.
5. Один интервал максимум 60 секунд со сквозным исходным deadline: исходный
   граф → Файлы → `/test-2` → точный видимый CSV → одна попытка download.
   Никаких повторных жестов, scroll/reveal fallback, новой браузерной вкладки/браузера,
   конфигурации или исполнения внутри observer. Если скачивание успешно,
   один возврат в исходный граф и контроль владельца; если неуспешно — никаких
   дополнительных диагностических UI-жестов. Полученный отрицательный ответ
   анализируется только по новым receipts. Отсутствие файла не доказывает
   отсутствие жеста.
6. Закрыть только собственный browser/stdio; проверить PID и неизменность
   global config. Независимый audit должен связать receipts с prepared seq,
   code/request hashes, run/session/read/deadline и actual wire; проверить
   отказ actual-dispatch и отсутствие любых product replace events. При успехе
   download сверить свежие байты, при отказе назвать только реально сообщённый
   status/code/checks, сохранив неизвестные эффекты как unknown. Без повторного
   запуска, автоматического исправления на лету или Hermes.

Владелец следующего решения — координатор. Конкретный триггер: одобрение этого
scope и отдельное назначение на подготовку/проверку diagnostic-purpose entry
и ровно одну попытку. Новые entry pins потребуется заморозить после такой
подготовки; текущий manifest не является разрешением запуска.
