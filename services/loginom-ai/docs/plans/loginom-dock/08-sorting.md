## Результат, исходное состояние и источники

Обработчик «Сортировка» внутри `node.apply` упорядочивает выход по нескольким ключам
с независимыми ASC/DESC. Сортировка отображения «Таблица» не заменяет узел.
После этого принимается весь сценарий продаж с двумя ветвями.
На исходной ревизии capability registry обработчика Сортировки не было; существующие операции
графа и чтение таблиц являются основанием для разработки, а не готовым результатом.

Проверенные при составлении источники:

- Help: [Сортировка](https://help.loginom.ru/userguide/processors/transformation/sorting.html),
  локальный файл `data/processors/transformation/sorting.md`.
- E2E: `tests/toreview/acceptance/wizards/sorting.ts`; содержит SortingWizard,
  SortingColumnCollection, добавление/перестановку полей, направление и регистр.
- E2E fixtures: `testdata/wizards/sorting/Sorting.lgp`,
  `testdata/wizards/sorting/AllTypesSorting.lgd`.
- Общие источники исполнения/выхода: `bg/helpers/wizard.ts`,
  `bg/helpers/workflow/previewTable.ts`; не запускать эти helpers как runtime.

Sorting E2E расположен в `toreview`, часть cases пропущена. Это подсказки для
UI-исследования, не доказательство корректности селекторов или успешной приёмки.
Перед реализацией закрепить SHA/ревизии и проверить поведение целевого Loginom.

## Зависимости и контракт

Основа — [01](01-open-loginom-draft.md), [02](02-add-nodes.md), [03](03-text-import.md).
Для продаж нужны [Калькулятор 04](04-calculator.md) и [Группировка 07](07-grouping.md).
Не откладывать эту цепочку до 05/06/09/10: она завершает первый сквозной этап V3.

- Общая цель `node.apply`: новый узел через внутреннее добавление 02 либо точная
  ссылка на существующий; один табличный вход и актуальная идентичность его схемы.
- `keys`: непустой упорядоченный список «идентичность поля, ASC/DESC» без повторов.
  Направление обязательно для каждого ключа; порядок массива задаёт приоритет.
- Для строковых/переменных полей — явное `case_sensitive`; для узла —
  `compare_with_locale`. Фактическая локаль входит в контекст проверки результата.
- При создании значение сравнения с локалью по умолчанию — `true`, согласно Help;
  у существующего узла незапрошенное значение сохранять и сообщать в результате.
- Кэширование и число потоков не оптимизировать этим обработчиком: для нового
  узла сохранить наблюдённые defaults, для существующего — прежние настройки.
- Список ключей заменяет настройку сортировки целиком; mappings и остальные
  параметры применяются по общему контракту 03 без изменения чужих объектов.
- По умолчанию «Выполнить» и подтверждённый новый выход; при «Готово» без запуска
  вернуть `execution=not_requested`, `output=not_refreshed`, не читать старый кэш
  как результат новой конфигурации.
- Выход по 03: refs, квитанции, execution identity, schema/types/row count,
  ограниченная выборка с полнотой и точностью; сортировка сохраняет состав строк.

При одинаковых всех ключах не обещать стабильность неописанного порядка строк.
Если задаче нужен однозначный порядок, агент добавляет подходящий следующий ключ.
Правила Null и сравнения разных значений variant сначала сверить с Help/live;
не вводить собственную SQL-политику NULLS FIRST/LAST, отсутствующую в мастере.

## Конкретные этапы реализации

1. В живом UI проверить списки доступных/выбранных полей, изменение приоритета,
   ASC/DESC, регистр и локаль, переходы input/node/output и признаки исполнения.
2. Описать параметры и привязку keys к входной схеме, отказ неоднозначным полям.
   Внешний запрос агента не содержит селекторов, координат или кликов.
3. Через `node.apply` создать/найти и подключить узел, впервые открыть мастер.
   Привести список ключей к точному порядку и значениям; не полагаться на defaults
   направления и не переключать флаги вслепую повторным toggle.
4. Проверить настройки и выходной mapping, завершить выбранным способом,
   получить новый результат и записать checkpoint общими средствами 03.
5. Добавить независимую проверку упорядоченности и сохранения полного мультимножества
   строк для малого fixture; затем выполнить сквозную приёмку продаж ниже.

## Ожидания, восстановление и проверки

Именованные условия: мастер нужного узла, список выбранных ключей в требуемом
порядке, применённое направление/регистр, сохранение и завершение нового запуска.
Использовать deadline/`settle: 0`, ownership/epoch и до двух обновлений только
после доказанного NOT_APPLIED до жеста. Не дублировать запуск при потере ответа.
Отмена/частичный эффект сохраняются в квитанциях; штатный wizard reopen исключён.

- Проверить числовую ASC/DESC, несколько ключей со смешанными направлениями,
  одинаковые первые ключи, отрицательные/точные дробные значения, даты и строки.
- Проверить дубли, Null, пустой вход, регистр/локаль на закреплённом профиле;
  не терять строки и не объявлять выборку доказательством всей таблицы.
- Проверить переупорядочение существующих ключей и изменение upstream;
  недоступное поле/неоднозначная метка отклоняются до изменения узла.
- Отдельные QA: отмена, «Готово» без запуска, «Выполнить», settings roundtrip,
  гонка до клика, потеря ответа после запуска и отсутствие повторного эффекта.

## Сквозная приёмка продаж и готовность

Подготовить отдельный версионированный CSV с товарами, регионами, количеством и ценой;
старый `fixtures/data-pipeline/sales.csv` без товара и исторические audits не изменять.
До запуска зафиксировать SHA входа и независимый полный ожидаемый результат:
выручка каждой строки, суммы по двум разрезам, убывающий порядок и лидеры.
Добавить дроби, возврат/ноль и равные суммы; не зашивать формулу/имена в обработчики.

После Codex-отладки запустить goal-only Hermes на существующей подписке:
`openai-codex / gpt-5.6-sol / low`, без fallback, с замороженными runtime/audit.
Агент строит импорт → Калькулятор → две ветви «Группировка → Сортировка»,
но его пользовательское задание не подсказывает инструменты или UI-последовательность.
Общими операциями 03 сохранить после импорта, каждой завершённой ветви и финала;
показать лидеров, закрыть/открыть точный пакет, проверить граф и повторно выполнить
обе ветви. Независимо сопоставить все значения и порядок, а не только первую строку.
Проверить продолжение из сохранённого этапа без дублей; мастер каждого узла
в обычном проходе не открывать повторно. Раздельно измерить все участки и recovery.

Готовность: независимый PASS Сортировки и всей задачи продаж, правильные данные
после reopen/reexecute, подтверждённые checkpoints/pins, один `node.apply` на узел
без внутренних модельных кликов. Это завершает V3, но не приёмку остальных типов v1.
