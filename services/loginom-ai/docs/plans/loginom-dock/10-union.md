# 10. Объединение строк нескольких таблиц

Статус: **implemented / live_verified (source runtime)**. [Аудит требований: 71/71 PASS](10-completion-audit.md). Это подплан первого аналитического выпуска, этап V4.
Общие контракты, порядок работ и допуск V5 задаёт [общий план](README.md).
Зависимости: [01 — пакет](01-open-loginom-draft.md), [02 — узлы и связи](02-add-nodes.md),
[03 — импорт и общий цикл node.apply](03-text-import.md).

## Результат и границы

Реализовать локальный обработчик «Объединения»: добавить строки двух и более таблиц.
Обязательны явные mappings совместимых полей и сохранение повторяющихся строк.
Это не UNION DISTINCT и не «Соединение» столбцов по номеру строки.
Порядок входов задаёт агент; первый вход — главная таблица, остальные присоединяемые.
Имена, метки, порядок и исключения полей регулируются явными mappings портов.
Для несопоставленных полей явно задавать их выходное назначение; не терять столбцы молча.
Преобразование несовместимых типов выполняет отдельный узел по решению агента.
Управляющие переменные и прочие расширенные режимы не входят в этот подплан.

## Реализованный состав

Добавлены карточка `transform.union_data / append_all`, полный handler,
чтение native mappings и независимый full-goal auditor. Приёмка Hermes
проверила два/три входа, полный результат и сохранение/reopen/reexecute.
Использовать node.apply и общий execution/result/save из 03, не создавать второй цикл.
Новый узел и изменение существующего должны работать через одну типизированную операцию.

## Сверенные источники

Пути Help заданы от корня источника loginom-help, получаемого через Dock.
Прочитан `data/processors/transformation/union.md`: строки добавляются к главной таблице;
сопоставленные поля объединяются, несопоставленные становятся отдельными столбцами.
Help описывает начальное автосопоставление по имени/типу, затем метке/типу, и Input_Add.
Поэтому автоматический выбор мастера нужно сверять с явными mappings запроса.

## Вход и выход обработчика

Вход наследует node.apply: точный workflow, новый либо существующий узел,
упорядоченный список из двух и более tabular output-port refs и актуальные схемы.
Параметры содержат mapping каждого входа в общую выходную схему, порядок полей,
явное включение/исключение полей и требуемую автосинхронизацию портов.
Проверять типы всех сопоставляемых полей, уникальность назначений и конфликты имён.
Точное число нужных входов определяется запросом; не создавать лишний порт «на всякий случай».
Результат наследует общий контракт: node/port refs, фазы и execution identity,
схема, число строк, ограниченная выборка, полнота и ссылка на подробное evidence.
По умолчанию «Выполнить» с ожиданием окончания и чтением свежего выходного порта.
При «Готово» вернуть execution=not_requested, output=not_refreshed без скрытого запуска.
Checkpoint и сохранение пакета выполнять общим механизмом 03; журнал не заменяет .lgp.

## Локальная процедура

1. Проверить параметры, версии входов и возможность получить требуемую общую схему.
2. Найти либо создать узел; назначить главную таблицу и первый присоединяемый вход.
3. Для остальных входов локально использовать Input_Add с привязкой к тому же узлу.
4. Подключить каждый источник к подтверждённому порту; настроить входные mappings.
5. Впервые открыть мастер внутри операции; подтвердить число и принадлежность таблиц.
6. Выставить mappings по всем входам, сверив и заменив лишь отличающиеся автосвязи.
7. Настроить выходной порт; проверить полную схему и отсутствие случайно добавленных полей.
   Порядок переходов брать из наблюдённого UI: при отдельном мастере порта сначала
   сохранить мастер узла промежуточным «Готово», затем настроить и сохранить порт.
8. Завершить общий цикл по запросу; после отдельного мастера порта выполнять с графа,
   без reopen узла, и читать тот же запуск. Финальный configure-only не запускает узел.

Обработчик не возвращает агенту управление между добавлением порта и его настройкой.
Существующие посторонние связи сохраняются; удаление лишнего входа требует намерения запроса.
Обычный успех не требует повторно открыть мастер; readback сохранения покрывается тестами.

## Ожидания и восстановление

После Input_Add ждать ровно один новый вход нужного владельца и подтверждать graph diff.
Не считать номер порта постоянной identity: после изменений/открытия привязать его заново.
Ждать точную связь каждого источника, готовую схему, таблицы нужных входов в мастере,
применённый mapping каждой строки и готовый выход после завершения конкретного запуска.
Использовать общие deadline, именованные условия и guards без фиксированных пауз.
При отказе до жеста применять общее ограниченное обновление наблюдения.
При потере ответа Input_Add сначала сверить наличие созданного порта и квитанцию,
а при неизвестном эффекте не нажимать повторно: сохранить pending и частичную фазу.
Так же восстанавливать подключения, mappings и «Выполнить» без дублей связей/запусков.
Отмена и изменение upstream следуют общему контракту; старый выход не становится актуальным.

## Самостоятельные проверки

При реализации создать три небольших CSV и отдельный expected до начала сессии.
Два файла покрывают базовое объединение; третий требует реального дополнительного входа.
Включить одинаковую строку внутри одного файла и между файлами: обе кратности сохраняются.
Для данных без отбора число выходных строк должно равняться сумме строк всех входов.
Варианты меняют имена/порядок полей и задают mapping явно; проверять Null и пустую строку,
пустой вход, несопоставленное поле, исключение поля и одинаковые метки разных полей.
Полностью сравнить маленький выход, типы и кратности; одной выборки для PASS недостаточно.
Негативные случаи: несовместимые типы, отсутствующий/чужой вход, незаданный mapping,
неполное чтение, stale ref, потеря ответа после Input_Add/связи/выполнения и отмена.
Проверить изменение существующего узла с добавлением третьего входа без второго экземпляра,
«Готово» без обновления результата и сохранение/reopen/reexecute с восстановленной identity.
Fixtures — независимые проверки; их имена, размеры и значения не встраивать в handler.

## Приёмка и готовность

После Codex-отладки через настоящий MCP выполнить самостоятельную goal-only приёмку
Hermes `openai-codex` / `gpt-5.6-sol` / `low` на актуальных pins, без UI-резерва.
Auditor связывает все источники, созданные входы, mappings, запуск и полный выход.
Готовность: два и три входа, дубли, mappings, ошибки и безопасное продолжение проверены;
save/reopen/reexecute воспроизводит схему и строки, посторонние объекты не изменены.
Замерять отдельно внутреннюю операцию и внешние вызовы; между её фазами модель не нужна.
Наличие Input_Add в прежнем MVP не закрывает этот пункт; общий допуск V5 остаётся в README.
