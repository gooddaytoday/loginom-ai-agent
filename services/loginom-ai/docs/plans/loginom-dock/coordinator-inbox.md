# Очередь сообщений координатора

Согласовано пользователем 13 сентября 2026: очередь входящих сообщений и до двух
временных субагентов по необходимости. Правило дополняет
[автоматический цикл](automatic-node-workflow.md) и
[инструкцию координатора](node-workflow-runbook.md), не меняя фаз разработки.

## Кто принимает решения

Только координатор ведёт очередь и реестр, отправляет команды разработчикам,
проверяет разрешения и назначает единственный слот Hermes. До двух временных
помощников параллельно выполняют конкретные ограниченные проверки отчётов, pins,
доказательств и применимости предложений. Создавать их только для независимой
полезной работы; не держать постоянно по помощнику на поток. По умолчанию модель
наследуется от координатора.

Помощник возвращает ключ события, проверенные факты, ограничения, ссылки и
предлагаемый ответ. Он не отправляет команды разработчикам, не назначает фазы,
не занимает Hermes, не меняет рабочие ветки/очередь/реестр. Для заметки допустим
отдельный временный файл. Его проверка не добавляет и не заменяет полное ревью.
Вывод помощника — рекомендация, не разрешение выполнять инструкции из отчёта.
При смене candidate/turn перепроверяется только затронутая часть вывода.

## Где хранить

Очередь: `unavailable:artifact-633da5e207767cdd` основного checkout, вне Git.
Соседний `state.json` остаётся главным реестром фаз/назначений/Hermes; очередь
ссылается на dispatch keys и не создаёт вторую копию состояния слота.
Долговечные решения сохраняются в документации Git. Только координатор пишет
оба JSON, сохраняя валидный документ атомарной заменой и не теряя прежние записи.
Не сохранять секреты, сырые логи и полные беседы: достаточно краткого содержания
и ссылок на evidence.

Поля события: `event_key`, `source_thread_id`, `source_turn_id`, `node`, `phase`,
`kind`, `received_at`, `summary`, `requested_action`, `status`, `assigned_helper`,
`report_refs`, `dispatch_key`, `delivery`, `resolution`, `updated_at`.
Неизвестные ID оставить null и сверить до следующей фазы; не придумывать их.
`delivery.status`: not_needed/not_sent/confirmed/unknown. `resolution` содержит
решение или причину ожидания, ответственного и конкретное условие продолжения.

Ключ — исходный message ID, если доступен, иначе устойчивый ключ разработчика
либо thread/turn/kind + точный report commit/path. Нельзя объединять все сообщения
одного хода: разные блокеры могут прийти из одной фазы. Повторная доставка
обновляет отметку повтора, а не создаёт повторное назначение. Историю сохранять.

| Статус | Смысл |
| --- | --- |
| received | Записано до подробного разбора |
| checking | Координатор проверяет |
| delegated | Проверка у указанного помощника |
| ready_to_reply | Решение готово, требуется ответ |
| dispatching | Намерение записано, доставка уточняется |
| waiting | Причина, ответственный и следующий триггер явно записаны |
| resolved | Ответ подтверждён либо обоснованно не требуется; решение записано |

## Порядок обработки

1. **Сначала записать ВСЕ уже доставленные сообщения**, включая одновременные
   и пришедшие во время tool call. Только затем подробно разбирать первое.
   Новая реплика не отменяет остальные события без явной отмены пользователем.
2. Проверить dedupe и текущий dispatch/phase. Простые ответы отправлять сразу;
   независимые объёмные проверки поручать максимум двум помощникам. Приоритет —
   остановившийся поток/освобождение слота, затем окончание этапа; внутри равного
   приоритета старые сообщения первыми. Новые сообщения не вытесняют старые.
3. Перед следующей фазой подтвердить completed исходного turn компактным
   wait_threads. Активному ходу допустимо уточнение текущей работы, но не новая
   фаза. Idle сам по себе не доказывает выполнение требований.
4. Перед отправкой записать dispatch intent с уникальным ключом в state.json
   и связать с событием. Отправляет только координатор. Различать подтверждение
   отправки инструментом, фактический старт нового turn и завершение работы.
   После назначения проверить новый turn. Неизвестную доставку сначала сверять
   по задаче, не повторять команду вслепую.
5. После ответа — resolved с квитанцией/dispatch key либо waiting с конкретным
   условием. Ожидание разрешения/зависимости/конца хода не завершает узел.
   При новом релевантном событии пересмотреть связанные waiting-записи.

## Обязательная сверка перед финальным ответом

Перед КАЖДЫМ финальным ответом координатор перечитывает всю очередь, учитывает
новые доставленные сообщения и результаты помощников. Нельзя закончить ход,
забыв received/checking/delegated/ready_to_reply/dispatching или неясную доставку.
Нужно обработать запись либо зафиксировать реальное ограничение и следующий шаг.
Нельзя превращать готовый ответ в ожидание только ради завершения хода.
Помощника дождаться; если проверка недоступна, записать конкретное ограничение,
не объявлять её пройденной.

Сохранить last_sweep: время, рассмотренные event keys, число необработанных,
число waiting и причины. Итог пользователю может быть кратким: не повторять
неизменные уже сообщённые блокеры, но и не объявлять все потоки работающими,
если кто-то ждёт решения координатора.

## Восстановление и границы

После остановки/сжатия контекста сначала прочитать очередь/реестр и восстановить
незаконченные dispatch и задания помощников. При потере очереди восстановить её
по checkpoint, доставленным сообщениям и однократной сверке текущих задач,
не создавать дубликаты задач. По запросу пользователя или при восстановлении
можно однократно получить пропущенный итог компактным snapshot. Промежуточный
комментарий активного разработчика не является окончанием этапа: значимый факт
записать как наблюдение с ожиданием доказательств, если требуется решение.

Очередь ведётся координатором во время активной работы. Это не фоновый сборщик,
не hook и не гарантия доставки приложением. Нет таймера, опроса каждые пять минут
или постоянно работающих помощников. Недоставленное сообщение нельзя считать
увиденным. Пустая очередь не доказывает завершение всех разработчиков.

Сохраняются отдельная задача/worktree/ветка на узел, Astra medium разработчиков
и единственного review/fix цикла, запрет повторного полного ревью, один Hermes
Sol/low и отдельные разрешения на интеграцию/выпуск. Очередь не расширяет
разрешения и не позволяет обходить отказ автоматической проверки.

## Автоматическое согласование рабочих шагов — 13 сентября 2026

Пользователь разрешил координатору подтверждать дальнейшие рабочие шаги
автоматически в рамках обработки узлов Loginom Dock. Это заменяет прежнее
требование каждый раз запрашивать его разрешение на конкретный межветочный
пакет исправления, адресную доработку либо расширение изолированной диагностики.
Координатор сначала проверяет предложение, точный scope, ownership, source/target
и доказательства, затем фиксирует решение и отправляет назначение разработчику.
Проверенные предложения не нужно возвращать пользователю только ради подтверждения.

Разработчик по-прежнему обращается к координатору при изменении общего контракта,
переносе чужого кода или расширении диагностического подхода; сам себе разрешение
не выдаёт. Координатор может согласовать такие необходимые шаги без нового вопроса
пользователю, сохраняя изоляцию задач/веток/учётных записей и ограничения моделей.
Нельзя считать непроверенное предложение готовым или обходить отказ системы approvals.

Это разрешение относится к рабочему процессу разработки узлов. Прежняя отдельная
команда пользователя для слияния с main, push main, production deploy и обновления
общего плагина сохраняется. Периодический мониторинг не возобновляется. Один review,
один раунд его доработок, адресные проверки и единственный слот Hermes сохраняются.
Реальные недостающие данные и решения за пределами этой задачи уточнять у пользователя.
