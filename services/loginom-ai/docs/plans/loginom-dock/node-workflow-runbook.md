## 3. Подготовка ветки, задачи и runtime

1. Записать точный принятый base SHA из main. Новый узел не наследует неслитый
   предыдущий узел; текущий HEAD сам по себе не является принятой базой. Проверить
   чистоту/чужие изменения и наличие нужных зависимостей в выбранном commit.
2. Создать постоянный `.worktrees/node-<номер>-<slug>` и ветку
   `codex/node-<номер>-<slug>` с проверкой коллизий. Для новых узлов выбрать номер
   из реестра, не перенумеровывать11–16. Существующие чужие изменения сохранить.
3. Зарегистрировать папку как самостоятельный сохранённый проект штатной командой
   `codex app <абсолютный-путь-worktree>`, затем получить реальный project ID через
   `list_projects` и сверить exact path/isGitRepository. Так были добавлены узлы16
   и17. Отсутствие отдельного add-project MCP и запрет CUA управлять Codex не
   означают отсутствия этого CLI способа; прежде чем просить пользователя о
   ручном шаге, проверить `codex app --help` и результат `list_projects`.
   Не использовать иной GUI-драйвер или правку внутреннего состояния приложения.
   На этом шаге задачу ещё не создавать:
   создание немедленно запускает её первый ход.
4. До первого хода подготовить локальную `.codex/config.toml`: source MCP из этой
   ветки, явный Dock config/stateDir и свой `LOGINOM_DOCK_HOME`. Установленный
   `loginom-dock@loginom-dock` отключён только в рабочем проекте. Worktree сам
   по себе не изолирует глобальный Dock HOME и hooks.
5. Сверить Node с требованиями репозитория, зависимости, runtime/skill/adapter и
   manifest знаний. Общие бинарники браузера и зависимости допустимы только для
   чтения; не устанавливать пакеты через symlink в общую папку `node_modules`.
6. Поместить свежие AGENTS.md и эту инструкцию в рабочую папку, даже если принятая
   база их ещё не содержит. Подготовить проверенный pending-маршрут памяти по
   разделу4 установленным helper-ом поколения `20260913.5`; старый v1 registry
   не расширять. Зафиксировать успешную подготовку до следующего шага.
7. Теперь создать обычную задачу с **local execution в подготовленном worktree**,
   `gpt-6-astra`, `medium` и коротким подготовительным запросом из раздела4.
   Это явно выбранная схема, а не ещё один временный worktree приложения.
   Внутри задачи проверить фактические cwd, branch/base/head, writable roots,
   модель и source pins. Сводка приложения с cwd `/` не заменяет runtime-проверку:
   такое расхождение уже наблюдалось у узла14.
8. После окончания подготовительного хода завершить регистрацию памяти, проверить
   actor-доступ по разделу4. Рабочее задание выдать следующим ходом в эту же задачу
   только после полного допуска; первоначальный ход не начинает разработку.
9. Сохранить `.dock/stream-preflight.json` и запись назначения: component ID,
   поток, task/project ID, worktree, ветка/base, модель, Dock session/profile,
   аккаунт/хранилище, memory registration, pins и ограничения. Приватные файлы —
   с ограниченными правами, без секретов в коммитах.

Не архивировать задачу ради reload: приложение уже удаляло временный worktree
при архивировании, несмотря на Git lock. Сохранять задачи, ветки, постоянные папки
и доказательства до отдельного решения о слиянии/очистке. После правки JS проверять
новый код свежим source harness из своей ветки с новым pin. Уже работающий MCP
не считается обновлённым от изменения файлов. Общий reload MCP и переустановка
общего клиента во время потоков не разрешены.

## 5. Живой Loginom и отсутствие конфликтов

- У каждого узла свои Dock session ID, profile, state, config, артефакты,
  `.lgp` и workflow. Разные вкладки одного браузерного профиля не изолируют вход;
  разные workflow одного пакета не защищают от перезаписи всего пакета.
- Выполнить `dock_prepare`, проверить доступ к закреплённым знаниям и реальному
  Loginom. Не выводить готовность памяти из health Dock или наоборот.
- Проверить собственный аккаунт и storage root в UI. Видимое окно запускать
  с `--start-maximized`, `viewport:null`; проверить фактическую геометрию.
  Диагностика, ревью и приёмка используют отдельные пакеты/профили. При запрете
  второго входа передавать аккаунт последовательно, сохранив состояние.
- Clipboard общий для Mac: использовать существующий `dock_clipboard_transfer`
  и единый порт блокировки **46419** до подтверждённой вставки. Таймаут не разрешает
  обход. Не выполнять глобальные copy/paste/клавиатурные жесты параллельно.
- Закрывать только собственный браузер/процесс. Не использовать общие `pkill`,
  массовые перезапуски, глобальную смену current/previous, плагинов или gateway.
  При перегрузке координатор ограничивает одновременные живые проверки.
- Native-архив Dock у source-запусков остаётся непринятым. `archiveActive=false`
  не доказывает изоляцию hooks. Это отдельный механизм от работающей общей памяти
  OpenViking; её успех не закрывает native-интеграцию Dock.

При потере связи/ответа сначала сохранить checkpoint, проверить UI, точные receipt,
pending operation и execution ID. `AMBIGUOUS`/effect_possible не разрешают повторять
действие вслепую. После изменения handler или controlled lost-reply восстановить
проверенный runtime; не продолжать новые операции на заведомо устаревшем harness.
После перезапуска приложения проверить реальные процессы/профили, а не старые PID.

Если потоки блокирует Dock, координатор уже уполномочен диагностировать VPS
`82.22.23.10` через существующий SSH: сеть/TLS, Caddy, сервисы, ресурсы и
обезличенные журналы. Сначала определить неисправный слой. Для проверки связи
использовать `/health`; `/ready` и verify-server могут обращаться к embeddings.
Разрешение на диагностику не означает произвольную смену credentials или моделей.

## 6. Разработка и критерии завершения

Сначала изучить реальный мастер Loginom, затем сверить Help/E2E и сформировать
реализацию. Сохранить границы наблюдения и неподдержанные режимы. Подход проекта:
Hermes задаёт граф/параметры, локальная операция узла выполняет поиск/добавление,
соединение, настройку, завершение мастера, выполнение и чтение результата.
Не вводить общий интерпретатор сценария как обязательную часть выпуска.

Объём задают подплан и gates roadmap: все заявленные входы/выходы, схема/типы/
значения, Null/пустые данные, порядок, изменение настроек, Done/Close/preserve,
ошибки и восстановление — где применимо. Ожидаемые результаты независимы от
проверяемого ответа; отрицательные подмены проверяют сам аудитор. Для обучаемых
узлов отдельно train/apply/retrain и применение сохранённой модели к новым данным.
Наличие UI-пункта не подтверждает доступность внешней БД/runtime/подключения.

Сначала Codex заканчивает прямую диагностику и независимые verifiers. Тесты
выполняются по изменению и обязательным требованиям; уже успешные проверки не
повторять без новой причины. Общие UI/readers/API исправления делать минимально,
отдельными коммитами, с описанием затронутых потоков для будущего слияния.

В обычном продуктовом ходе не открывать каждый мастер повторно. Настройки
проверять во время конфигурации, output — после выполнения; отдельные roundtrip
и reopen оставлять диагностике и приёмке. Нормальный Hermes сохраняет пакет в
конце через `package.save_checkpoint`; промежуточные сохранения нужны по запросу
или конкретному риску потери. Локальный receipt не доказывает сохранность `.lgp`.

Завершение разработки: весь заявленный scope реализован, проверки и live evidence
сохранены, commit/dirty state и pins известны, ограничения названы. Это ещё не
приёмка и не выпуск. Текст «готово», WIP, idle или exit0 этого не заменяют.

## 7. Ревью, один раунд доработок, автономная приёмка

| Фаза | Исполнитель | Что разрешает переход |
| --- | --- | --- |
| Разработка | Astra medium, задача узла | Завершённый scope и checkpoint |
| Одно ревью | Astra medium, та же задача | Полный diff от base до фиксированного SHA, требования и доказательства; конкретные findings |
| Один раунд доработок при замечаниях | Astra medium, та же задача | Живое подтверждение/снятие каждого дефекта, исправления и затронутые проверки |
| Автономная приёмка | Hermes `openai-codex / gpt-5.6-sol / low` | Закреплённый candidate, единственный слот, полный независимый аудит |
| Принят в ветке | Координатор | Проверены scope, SHA/pins, отчёты, persistence и освобождение ресурсов |

Фазы одного узла последовательны; ревью начинается только после завершения
предыдущего turn. Ревью в том же чате — отдельный анализ, а не независимый агент
с новым контекстом. В ревью код не исправлять. Доработка получает формулировку:
«Перепроверь найденные дефекты на живом Loginom и после подтверждения исправь
то, что реально недоработано». Неподтверждённые замечания снять с доказательствами.
После одного раунда **повторного полного ревью нет**; нельзя назвать его проверкой
исправлений. Незакрытое обязательное требование остаётся блокером для диагностики.

Hermes запускается через существующую подписку ChatGPT на Mac, только Sol/low.
Один слот выдаёт координатор после прямой QA/ревью; до выдачи проверить процесс
предыдущего владельца. Остальные разработчики могут продолжать собственную работу.
Не заменять модель/провайдера после ошибки и не использовать серию Hermes-прогонов
вместо диагностики Codex.

Перед приёмкой закрепить immutable candidate URI/SHA, knowledge/catalog revision,
source/runtime/skill/adapter pins, scope/fixtures и независимый audit. Сборка
поставляемых артефактов — на VPS. Нужные новые карточки и разрешённый storage root
должны быть в проверенном candidate; недостаточный старый allowlist не обходить.
Подготовка отдельного candidate не переключает production/current/общий клиент.

Успех требует независимого аудита полного заявленного результата, свежего
выполнения, правильных владельцев входов/выходов и отдельного сохранения/переоткрытия.
Отчёт Hermes, код выхода и ручной успех Codex недостаточны. При провале вернуться
к живой диагностике в той же задаче. Новый код/harness меняет candidate: прежняя
приёмка автоматически не переносится. Повторное ревью не требуется; необходимая
повторная приёмка исправленного результата от этого не отменяется.

## 8. Сообщения, восстановление и переход к следующему узлу

Координатор: `01a096e6-a321-7df2-99db-2cae02a305ee`. Разработчик перед окончанием

| Поле | Содержание |
| --- | --- |
| Идентичность | Узел/component ID, поток, задача, phase/turn, worktree/ветка/base |
| Код | HEAD, reviewed/fixed/candidate SHA, незакоммиченные изменения |

## Автоматическое согласование рабочих шагов — 13 сентября 2026

Пользователь разрешил координатору подтверждать дальнейшие рабочие шаги
автоматически в рамках обработки узлов Loginom Dock. Это заменяет прежнее
требование каждый раз запрашивать его разрешение на конкретный межветочный
пакет исправления, адресную доработку либо расширение изолированной диагностики.
Координатор сначала проверяет предложение, точный scope, ownership, source/target
и доказательства, затем фиксирует решение и отправляет назначение разработчику.
Проверенные предложения не нужно возвращать пользователю только ради подтверждения.

Разработчик по-прежнему обращается к координатору при изменении общего контракта,
переносе чужого кода или расширении диагностического подхода; сам себе разрешение
не выдаёт. Координатор может согласовать такие необходимые шаги без нового вопроса
пользователю, сохраняя изоляцию задач/веток/учётных записей и ограничения моделей.
Нельзя считать непроверенное предложение готовым или обходить отказ системы approvals.

Это разрешение относится к рабочему процессу разработки узлов. Прежняя отдельная
команда пользователя для слияния с main, push main, production deploy и обновления
общего плагина сохраняется. Периодический мониторинг не возобновляется. Один review,
один раунд его доработок, адресные проверки и единственный слот Hermes сохраняются.
Реальные недостающие данные и решения за пределами этой задачи уточнять у пользователя.
