# Живая перепроверка ревью «Параметров полей» — 11 сентября 2026

Два замечания ревью подтверждены на Loginom 7.4.2 и исправлены в исходниках.
Расширенная проверка выявила и закрыла связанный отказ при обновлении метки
через условное выходное соответствие. Самостоятельная финальная приёмка
Hermes завершилась **49/49 PASS**, все **9 отрицательных подмен отклонены**.
Новый runtime принят для исходного полного сценария; отдельные смешанные
запросы и управляемая смена выбранного элемента проверены прямой Codex-диагностикой
и независимым аудитом сырых наблюдений.

## Подтверждённые условия и исправления

### Ошибочный запрос сохранял часть входных настроек

У существующего узла «Очистка» поле `RawAmount` уже преобразовано в
`NetAmount`; другое поле имеет имя `Id`. Запрос одновременно выключал autosync
входного порта и переименовывал `RawAmount` в `Id`. Прежний обработчик завершал
мастер входного порта, затем обнаруживал коллизию в основном мастере.
Результат — `AMBIGUOUS`, незакрытый черновик и **autosync false** после нового
открытия входного порта, хотя до запроса было **true**.

Для existing-запросов с непустым `changes` и явно заданным input mapping
добавлена предварительная проверка полной сохранённой конфигурации. Входной
порт и мастер узла читаются и закрываются с отменой, затем проверяется весь
результат преобразования. Учитываются стабильные ID, новый порядок входа,
наследование исходных имён и меток. Обычные изменения без input mapping,
новые узлы и `changes:[]` этого дополнительного прохода не получают.

Отмена входного мастера теперь привязана к native port GUID, его открытию,
узлу, документу и сценарию; вопрос закрытия проверяется до подтверждения.
Завершённый отказ имеет `FAILED`, `cleanup_complete:true`, без pending phase;
повтор того же публичного operation ID возвращает прежний ответ. Открытие
настроек может деактивировать узел, поэтому `effect_possible:true` сохраняется.
Это проверка до фиксации настроек, не обещание транзакционного отката Loginom.

После исправления оба сценария отклонены с неизменным **autosync true** и
прежними именами входа: прямая коллизия `RawAmount → Id` и коллизия
`RawAmount → NewInputId` вместе с input mapping `Id → NewInputId`.

### Обновление графа оставляло узел без выбранного корпуса

Между исходным наблюдением и действием диагностический код выполнял настоящий
клик по корпусу узла. Loginom показывал панель над корпусом и менял DOM epoch.
Старая попытка корректно получала `UI_EPOCH_CHANGED`; после обновления
обработчик нажимал подпись, но решение о втором клике было вычислено ещё по
старому наблюдению. Панель настройки после возврата функции отсутствовала.
Простое движение мыши само по себе этот сценарий в данной проверке не вызвало.

Решение о дополнительном клике теперь принимается по фактически разрешённому
действию после обновления. В живом повторе выполнены клики по подписи и корпусу;
панель настройки появилась. Независимый проверяющий разрешает такой переход
только между корпусом и подписью того же подготовленного native-узла.

### Синхронизация метки ошибочно считалась повреждением

В успешном смешанном запросе вход `Id` переименовывался в `InputId` и
переставлялся, а метка `NetAmount` менялась с «Сумма» на «Сумма проверено».
При добавлении нового выходного поля Loginom синхронизировал также метку
сохранившегося поля. Общая строгая проверка останавливала обработчик с
`Calculator inline synchronization changed a retained field`.

Reform сохраняет исходную конфигурацию и допускает ровно обновление метки
от прежнего значения источника к новому подтверждённому значению. Отличная
пользовательская метка остаётся под строгой проверкой, как тип, ID, порядок
и остальные свойства. Проверки остальных обработчиков не ослаблены.
Повтор на живом Loginom завершился `SUCCEEDED`, выполнением и чтением всех
**6 строк × 4 поля**: Timestamp, NetAmount, Enabled, InputId.

пакет не изменялся. Браузеры использовали видимое развёрнутое окно и

existing-запросов. Обязательного повторного открытия мастера после каждой
конфигурации не добавлено. Неизвестный транспортный результат по-прежнему
сохраняет pending phase и требует разбирательства.
