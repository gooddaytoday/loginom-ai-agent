Актуализация 12 сентября: подготовлен [новый план управляемых потоков](../plans/loginom-dock/three-stream-workflow.md),
без запуска разработки. Ниже сохранена история остановленного пилота; Слияние
и общее исправление панели процесса были завершены позднее отдельными запросами.

Старт и остановка: 11 сентября 2026. Статус: **пилот остановлен пользователем**.
Пользователь вернул последовательную работу: один узел за раз, без параллельных
разработчиков и проверяющего. Это решение заменяет разрешение на запуск пилота.
Все четыре субагента остановлены; повторный запуск требует нового указания.
Последнее уточнение пользователя: **разработку не продолжать, завершить только
документацию**. Очередь ниже справочная, автоматического продолжения нет.

## Изоляция и передача результата

Каждый разработчик меняет только собственный worktree. Общие зависимости клиента
используются только для чтения; установка зависимостей в общем каталоге запрещена.
Каждый поток запускает отдельный локальный source MCP/диагностический браузер,
имеет собственные config/state/artifacts и уникальные CSV/пакеты в явно выбранном
хранилище. Пользовательский браузер, config, gateway, плагины и global current
не меняются разработчиками. Сервер Dock остаётся единым сервером знаний.

Для пилота на VPS собран и размещён отдельный неизменяемый каталог
`2026.09.11-parallel-pilot.1-candidate`, с обратным чтением через настоящий Dock MCP.
Manifest SHA: `4ac827fc9e0cefa609bf2cb8fd7d3d79318dd3fe92999decc7e385fae51fc6e2`.
Он разрешает `save_as` и `save_checkpoint` только внутри трёх подтверждённых
тестовых каталогов, использует профиль Loginom 7.4.2 и не активирован в production.
Чистые сборочные исходники: `7da6f1f8`; архив SHA
`7ce4fc21ab64bf70926af467927cf6bc3ddbfa78a7e2cf777f0c96ad05aafad2`.
Серверный каталог: `/opt/loginom-dock/releases/20260911-catalog-parallel-pilot1-7da6f1f8`.
Приватные профили разработчиков закреплены на этот manifest. Уже запущенные
диагностические сессии сохраняют собственные исходные pins; переносить на них
новый pin задним числом нельзя. Это подготовка приёмки, а не её успешный результат.

Подготовка источников — через dock_prepare; реализация начинается с наблюдения
реального UI. Целевой стенд берётся из установленного профиля приёмки 7.4.2,
не из Codex config с 7.5. Пользователь создал отдельные аккаунты для пилота:
`test-1` — Слияние, `test-2` — Замена, `test-3` — Дата и время.
В каждом аккаунте проверены вход без пароля, личный каталог через «Файлы»
(`/test-1`, `/test-2`, `/test-3` соответственно) и независимый новый черновик.
Пути подтверждены наблюдением UI, а не выведены из имён аккаунтов.
Каждый поток использует уникальные имена `ParallelJoin-20260911*`,
`ParallelReplacement-20260911*`, `ParallelDateTime-20260911*` в своём каталоге.
Приватные профили потоков обновлены; основной профиль не менялся.
Проверяющий получает аккаунт и пакет по очереди после передачи владельцем.
Начальные запуски с профилем `user`, отклонённые автоматическим допуском,
не обходились; разрешённая диагностическая сессия `user` закрыта без работы
с данными. Неуспешные попытки с общим `test` заменены новыми аккаунтами.
Видимый браузер:
`--start-maximized`, `viewport:null`, проверка фактической геометрии.
Буфер обмена использует одну host-wide блокировку без обхода.

Реестр владельцев ведёт только координатор в `.dock/parallel-pilot-20260911/state.json`.
Рабочие документы, журналы и configs отдельных потоков лежат в их собственных
каталогах; секреты и сырые журналы не попадают в Git. Память остаётся в actor scope
текущей задачи; никаких глобальных Peer overrides или чтения чужих проектов.
Во всех четырёх сессиях субагентов подтверждены `health`, поиск с точным URI памяти
исходного проекта и чтение найденной записи через OpenViking. Автоматический
захват каждой сессии субагента пока не проверен. Передача работы не зависит
от извлечения памяти: используются сообщения и фиксированные артефакты в Git.

Разработчик сдаёт commit, scope, точные pins, проверенные режимы, тесты, live
evidence, независимый oracle и ограничения. Ревью привязано к конкретному commit.
Замечания передаются разработчику: «Перепроверь найденные дефекты на живом Loginom
и после подтверждения исправь то, что реально недоработано». Неподтверждённое
замечание снимается с доказательством; пересмотренный кандидат проверяется снова.

Изменения общих API/registry/readers передаются отдельными коммитами, когда это
помогает интеграции. Разработчик Слияния владеет первым кандидатом расширения
нескольких входов; остальные не зависят от него и не меняют эту область параллельно.
Координатор объединяет кандидаты последовательно. Проверка отдельной ветки не
подменяет проверку объединённой версии; на время приёмки её файлы заморожены.

## Допуск и наблюдение за пилотом

Переходы: подготовлен → live-исследование → реализация → Codex QA → ревью →
исправления → интеграция → Hermes → независимый аудит → main → сборка/установка.
Ни разработчик, ни проверяющий не запускает Hermes без выделенного координатором
окна и не выполняет push, установку или обновление сервера.

Сначала подтвердить три одновременно независимых браузера/черновика/схемы и
отсутствие пересечения файлов. Следить за ожиданиями UI, блокировками пакетов,
ошибками подготовки, ресурсами и сохранностью конфигурации. При конфликте
ограничить только конфликтующий ресурс; не останавливать чужие процессы массово.

Приёмка обычного Hermes: естественная задача и данные, финальный save_checkpoint;
Codex отдельно открывает сохранённый пакет и выполняет его без перенастройки.
Перед push нужны ревью итогового кода и проверки затронутых старых узлов.
Производственные комплекты собираются только на VPS. Установка выполняется
координатором в безопасной точке с сохранением предыдущего комплекта и настроек.
Публичный GitHub Release и landing не создаются автоматически из внутреннего пилота.

Планировалось измерять время работы/ожидания, циклы ревью, конфликты интеграции,
модельные вызовы, токены, приёмку и поставку. До завершённых узлов пилот не дошёл,
поэтому ускорение не измерено. Прежняя автоматическая выдача следующего узла
освободившемуся потоку отменена. Дальнейшие действия определяет только новый
запрос пользователя и последовательная очередь в реестре подпланов.
