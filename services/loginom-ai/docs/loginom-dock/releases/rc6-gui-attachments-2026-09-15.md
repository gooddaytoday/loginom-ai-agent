# Вложения GUI после RC6 — 15 сентября 2026

Исправления этого отчёта затем вошли в установленный RC7 вместе с изоляцией
сессий Hermes. [Текущий выпуск и ограничения](rc7-release-2026-09-15.md).

Два внешне похожих сообщения имели разные причины. Содержимое банковского
датасета не читалось; проверялись metadata, native references и квитанции Dock.

## Codex

Задача «Создать анализ кредитного риска», thread
`01a0a1c4-1b4b-7041-90f6-e3d2bd7b919f`, cwd `/Users/kartamyshev/Git/temp`.
Оба сообщения с файлом штатно распознаются установленным парсером. Но native
hook не запускался: ticket отсутствует, три prepare без host_context_token,
input_artifacts пуст. Штатный hooks/list подтвердил для всех шести Dock hooks
`enabled=true`, `trustStatus=modified`: hashes остались от предыдущего выпуска.

Пользователь отдельно разрешил подтвердить доверие к шести проверенным RC6
командам. Выполнен штатный config/batchWrite только для их hooks.state, затем
hooks/list подтвердил все шесть `trusted`. Команды/манифесты других плагинов,
модель, credentials и рабочие каталоги не изменялись. Приложение и активные
MCP-процессы принудительно не перезапускались.

Нативные события прошлого сообщения не переигрываются. Проверка исправления
в реальном GUI требует нового сообщения с вложением после восстановления
доверия; отдельная задача только ради этого не создавалась. Native current-turn
и session identity проверки не ослаблены.

## Hermes

Задача «Создать сценарий кредитного риска в Loginom», session
`20260915_000029_1318f6`, Dock `42157136-c1af-4820-93a9-435abcd7afe1`.
Первый prepare, ещё LOGIN_REQUIRED, уже вернул CSV12959байт; после входа тот же
artifact сохранился. Повторное вложение также породило host_context_token.
Producer Hermes исправен; сообщение «файл не поступил» не соответствовало
первым квитанциям.

Вошедший аккаунт — test-1, а все три выбранных каталога —
`/orcestrator/RC public 20260914`. В Files `/` видны семь папок, в том числе test-1;
orcestrator не виден. Доставка остановилась до upload на первом сегменте пути,
`upload_submitted_or_unknown=false`. Сообщение `no scroll owner` описывало
короткий список без прокрутки и скрывало недоступность выбранного каталога.

Затем после переавторизации старый workflow стал недоступен. Prepare вернул
WORKFLOW_LOST без эффекта; следующие новые запросы попали в preparation conflict.
Пользователь выбрал **входить в Hermes как orcestrator**. Каталоги поэтому
сохранены. Последующее сообщение пользователя показало, что новая задача сама
по себе не решает проблему: Hermes использует общее MCP подключение, уже
принадлежащее предыдущему чату. Прежняя рекомендация открыть новую задачу
отменена. [Причина и проверенное исправление маршрутизации](hermes-session-routing-2026-09-15.md).

## Подготовленные изменения исходников

- Недоступная запись хранилища сообщает имя/родительский каталог и причину;
  доставка возвращает ARTIFACT_DESTINATION_UNAVAILABLE, identity уже принятого
  artifact и выбранный inputs root. Не утверждается глобальное отсутствие папки.
- Новый явный запрос подготовки разрешён после подтверждённого WORKFLOW_LOST
  без создания и эффекта. Отмена, неопределённый эффект, неизвестный ответ и
  повторное использование ID для другого запроса сохраняют прежний запрет.
- Инструкции Codex/Hermes и user-v1 различают получение файла и доступ к каталогу;
  setup явно сообщает зависимость вложений от доверия к hooks после обновления.

Это локальные изменения исходников поверх main024408f1. Публичный RC6,
установленные runtime/skills и сайт ими **не заменялись**. Из применённых к
установке исправлений — только отдельно разрешённое восстановление доверия.
