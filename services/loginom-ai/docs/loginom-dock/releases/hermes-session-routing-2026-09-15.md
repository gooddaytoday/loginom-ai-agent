# Изоляция задач Hermes после RC6 — 15 сентября 2026

**Продолжение:** исправление опубликовано и установлено в RC7 после разрешения
пользователя. Ниже сохранён исходный этап диагностики; его ожидание публикации
заменено [итоговым отчётом RC7](rc7-release-2026-09-15.md).

## Причина повторного отказа

Пользователь сообщил `Host ticket belongs to another native session`, затем
Hermes назвал MCP недоступным. Исследованы только исходники, технические metadata,
native attachment references и квитанции точных задач; содержимое банковского
датасета, системные сообщения и рассуждения модели не читались.

Новая задача «Создать сценарий анализа рисков в Loginom #2», native session
`20260915_005848_0de8ac`, получила правильно выпущенный билет. Но общий менеджер
Hermes использовал прежний named MCP `loginom-dock`: Dock session
`42157136-c1af-4820-93a9-435abcd7afe1` уже принадлежала
`20260915_000029_1318f6`. Отказ произошёл до claim файла. Проверка владельца
работала правильно; повторное вложение не могло исправить маршрутизацию.

В Hermes 0.21.0, core `693641aa8b4359c602283bdbbc14041e03bc47bc`,
`tools/mcp_tool.py::_servers[name]` общий для чатов одного процесса.
`mcp_tool_discovery.py` повторно использует здоровое подключение;
`mcp_tool_handlers.py` не передаёт native session/turn в MCP metadata.
Штатный pre-tool hook может дополнить аргументы без модификации Hermes core.

После четырёх накопленных ошибок Hermes circuit breaker отказал в следующем
вызове до RPC. Сообщение «unreachable» не доказывало остановку Dock или сетевой
сбой. Исправляется исходная привязка задачи; выключать circuit breaker не нужно.
Прежняя рекомендация просто открыть новый чат в RC6 была недостаточной.

## Реализация в исходниках

- `dispatch.mjs` запускает для Hermes `hermes-mcp.mjs`. Codex сохраняет прежний
  прямой MCP. Публичные операции и обработчики узлов не менялись.
- Нативный hook выдаёт приватный непрозрачный билет текущих session/turn через
  `context hermes`. На **каждый** вызов Dock hook подставляет этот билет, заменяя
  значение модели. Это действует и для сообщений без вложения. При отсутствии
  текущего native события вызов блокируется до RPC.
- `hermes-router.mjs` направляет вызов в отдельные bridge, artifact store,
  runtime pins и браузер данной беседы. В одном внешнем процессе используется
  SDK InMemoryTransport. Возврат в беседу сохраняет её прежнюю сессию.
- Владелец `hostInputOwner` задан до первого вызова, даже без файла. Прежние
  проверки билетов вложений сохранены. Нет выбора «последнего активного чата».
- Билет маршрутизации хранится приватно, проверяется его формат, возраст,
  отсутствие symlink и приватность файла; путь и содержимое датасета в нём
  отсутствуют. Служебное поле удаляется перед вызовом bridge.
- Ошибки маршрутизации возвращаются как структурированный результат операции.
  Потерянный ответ остаётся AMBIGUOUS с возможным эффектом; маршрут сохраняется,
  новая сессия или повтор мутации автоматически не создаются. Обычные ошибки
  дочернего MCP не маскируются и механизм Hermes circuit breaker не меняется.
- При закрытии менеджер ожидает cleanup каждого bridge. Неподтверждённое закрытие
  любого браузера не превращается в успешное завершение всего процесса.
- Журнал происхождения различает прямой `official_stdio_transport` и внутренний
  `native_hermes_router`; внутренний вызов не выдаётся за прямое stdio-доказательство.

Это локальный кандидат поверх main `024408f1`, **не установленное исправление**.
Runtime, оба общих плагина, сайт, GitHub и конфигурация пользователя не изменены.
Новые узлы, модельные задачи и мониторинг не запускались.

## Применение и эксплуатационные границы

Одно подключение удерживает до16 маршрутов до завершения внешнего MCP процесса.
Даже бездействующая задача не вытесняется: это защищает несохранённые пакеты.
При лимите новый чат получает DOCK_SESSION_LIMIT, существующие продолжают работу.
Автоматический eviction или отдельное завершение чата пока не реализованы.
Количество одновременно открытых браузеров влияет на память компьютера.

Для применения нужен согласованный новый выпуск runtime и Hermes adapter,
обновление общего плагина и контролируемый перезапуск Hermes MCP/gateway после
сохранения пользовательских пакетов. Установка runtime отдельно от native hook
недостаточна. Старые процессы не переключаются на новый код автоматически;
потерянный workflow не восстанавливается из старого билета.

По правилу проекта публикация/main push/обновление общего плагина требуют отдельной
команды пользователя. Следующий этап после разрешения: построить артефакты на VPS,
проверить состав и согласованность версий, опубликовать исправление и обновить
клиенты штатно, проверить доверие hooks Codex после изменения их файлов.
Затем подтвердить прикрепление новым сообщением в реальном GUI. Исходные
пользовательские задачи и пакеты до этого не перезапускать принудительно.
