## N13-R1 — P1: потерянный ответ настройки блокирует исходную операцию без recovery

Места: `client/lib/date-time-procedure.mjs:48–50` — новый вызов переключения;
`client/lib/executor.mjs:1421–1473` — общий `inspectApply`;
`client/lib/executor.mjs:2022–2024` — запрет resume при unresolved phase;
`client/lib/calculator-node.mjs:207–213` — продолжение только от принятого finish.

**Условие:** существующий узел, фаза configure; native click DateB/quarter
успешно выполнился, ответ потерян. Браузер и черновик ещё существуют; доступна
квитанция выполненного внутреннего действия. Требуется сверить исходную
операцию и продолжить либо безопасно завершить её, сохранив известные эффекты.

Реальное доказательство: сессия `1e796919-a7f3-4966-8339-b93a0f309734`, операция
`node13-lost-flag`, внутренний ID `node13-lost-flag:n44`, `browser-968.json`.
Квитанция click — SUCCEEDED/cleanup_complete=true; публичный результат —
AMBIGUOUS/configure/cleanup_complete=false. Независимые снимки подтверждают
ровно quarter false→true. SAME apply и resume не вызывают браузер повторно
(969→969→969), resume отвергнут как unresolved phase. Это доказывает отсутствие
повторного переключения, но **не восстановление исходной операции**.

В `inspectApply` есть сверка workflow и target, но нет сверки configure,
внутреннего n44 и ожидаемой матрицы. Поэтому дополнительный inspect эту
неопределённость также не снимает. Проверка общего runtime без браузера
подтвердила: inspect → state=pending, recovery_options=[],
internal_resume_available=false; resume запрещён; другой operation_id запрещён
с `Another Dock operation remains pending`. Configure вызван один раз.
Артефакт: `.dock/node13-review/recovery-repro.json`; воспроизводящий скрипт рядом.
Это модель общей границы runtime, не новая живая попытка.

**Влияние:** одна потеря ответа после уже исполненного флага блокирует дальнейшую
работу в этой сессии. Ручная отмена через операторский harness и новый браузер
теряют исходный continuation и не выполняют recovery-контракт next-wave.

**Нужное исправление:** фазовая сверка исходной квитанции и живой полной матрицы,
точного узла/пакета и cleanup; затем разрешённое продолжение того же ID либо
доказуемое безопасное завершение. Нельзя повторять click или просто сбрасывать
pending. Отдельно проверить отказ при изменившемся черновике/чужом владельце.

Общий пробел существовал в базе; node13 его использует, это не новая регрессия
алгоритма дат. Координатор уже ведёт общую recovery-работу в ветке14. Владельца
configure-варианта необходимо согласовать с ним: input_mapping recovery сам по
себе этот случай не закрывает. Код ветки14 в кандидате не учитывался.

## N13-R2 — P1: подтверждённая ошибка исполнения остаётся неопределённым pending

Места: `client/lib/node-execution-procedure.mjs:247–248`,
`client/lib/node-apply.mjs:162–188`, `client/lib/executor.mjs:1421–1473`.
Это **существующий общий дефект**, уже обозначенный координатором как
terminal-failure работа ветки14; отдельную реализацию здесь не начинать.

**Условие:** выполнение узла идентифицировано; наблюдение того же native process
имеет verified=true, terminal=true и состояние failed. Драйвер выбрасывает
обычный Error `Node execution ended without success: failed`. Общий обработчик
не превращает это подтверждение в terminal failure receipt: нет соответствующей
ветки очистки pending, а inspect обрабатывает только workflow/target.

Проверка общего runtime с воспроизведением именно этой ошибки драйвера вернула
AMBIGUOUS, pending_phase=execute, execution.status=pending при сохранённом
execution_id; inspect/resume не разрешили продолжение. Артефакт:
`.dock/node13-review/terminal-failure-repro.json` и одноимённый скрипт.
Реальную ошибку процесса Date/time в этом ревью **не вызывали**; вывод основан
на коде реального драйвера и проверке общей границы обработки. Успешные
0×7/4×27 эту ветку не проверяют.

**Влияние:** известная ошибка исполнения представляется как неизвестный эффект,
удерживает gate и блокирует исправленный запрос в той же сессии. Это нарушает
требование next-wave проверить ошибку исполнения и продолжение.

**Нужное исправление:** принять доказательство terminal failure для того же
execution/node/document с подтверждённым cleanup, честно завершить неуспешную
операцию и обеспечить согласованный дальнейший путь без повторного запуска.
Интеграцию и целевую проверку общего исправления координировать с владельцем14.

## N13-R3 — P2: аудитор не проверяет запрошенные метки сквозных выходов

Место: `tools/loginom-acceptance/date_time_configuration_evidence.py:127–139`,
особенно условие на `origin.get('configured_label')` в строке134.

**Воспроизведение без изменения журналов:** взять оригинальный запрос
`node13-layout-fixed` сессии `fcccbde6-d697-465d-8b2c-603d7d51d037`.
Исходный audit PASS. В копии запроса задать для output mapping источника `Id`
`label="Unfulfilled requested label"`, оставив все реальные observations,
квитанции и результат без изменений. Audit снова PASS. То же воспроизведено
для `Amount`. Артефакт: `.dock/node13-review/auditor-label-repro.json`.

У сквозного столбца нет configured_label, поэтому сравнение с запросом
пропускается, а projection копирует фактическую метку. Последующие проверки
схемы/значений используют эту projection и также не проверяют намерение.
Аналогичная ветка требует внимания при output mapping сохранённого вычисленного
поля с parameters={}: его configured_label тоже отсутствует.

**Влияние:** независимый PASS возможен при невыполненной пользовательской
настройке метки. Проверки input labels и порядка этого не компенсируют.
Это новый дефект аудитора, а не доказанный дефект записи меток обработчиком.

**Нужное исправление:** независимо связать каждый output override с исходной
конфигурацией и проверить имя/метку/excluded для всех полей, включая сквозные и
сохранённые вычисленные. Добавить отрицательные проверки изменения только
запроса для обоих видов полей. Expected не должен брать запрошенную метку из
фактического результата. Это локальная работа узла13.
