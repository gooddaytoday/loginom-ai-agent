Проверено 5 сентября 2026 года при подготовке [продолжения плана](../plans/2026-09-02-loginom-dock-implementation-plan.md#post-mvp-phases).
Это карта исходников и ограничений, а не отчёт о запуске E2E или готовности функций.

доступной области; вместо этого проверены конкретные файлы без Git-фильтров.

На другой машине сначала найти этот репозиторий или импортированные оригиналы
через существующий Dock importer. Для каждого используемого файла проверить
commit и SHA; абсолютный путь на машине автора не является настройкой продукта.
Локальная `.dock/executor-mvp-acceptance/e2e` содержит только пять старых
нормализованных retrieval-копий и не заменяет полный исходник.

## Что не переносить буквально

1. **TestCafe runtime и retries.** `t`, `Selector`, `ClientFunction`, callback helpers (`fn()`), `t.expect` и TestCafe smart waits не являются data-only definitions и не должны доставляться с сервера как исполняемый код. Переносить доказанный UI pattern в версионированную локальную capability, а параметры и provenance — в каталог. `links.ts:45` прямо описывает workaround TestCafe dragToElement; нужна собственная проверка координат и final graph.
2. **Глобальные selectors, индексы и скрытые допущения.** `S` и `AddTabIndexToSelector` — зависимая пара; `OnlyVisible`, AltAttrs, label normalization, текущая вкладка/подмодель нельзя терять. nth/count-before, дефолтное имя «Подмодель» и fixed-offset drag заменить наблюдаемой идентичностью/diff и явным владельцем.
3. **Неявные составные эффекты.** OpenPackage по умолчанию запускает все узлы (`packages.ts:83,102`); MakeNodeSettings по умолчанию Execute (`wizard.ts:224`). У CloseNodeSettings разные ветви: при `finalAction != Close` helper жмёт Next до последней страницы (`:109`); при `Close` подтверждает discard (`:128`), без этого прохода страниц. Будущий cancel driver не должен выполнять ветвь завершения мастера. В продукте каждый значимый эффект должен быть отдельно виден агенту и иметь postcondition.
4. **Тестовые поблажки.** Exceptions/ShouldCheckErrorAbsent, excludeCheck, игнорирование errors и управление цветом ожидаемого статуса — инструменты отрицательных тестов, не полномочие агента объявить ошибку успехом. `LaunchAllNodes(excludeCheck)` всё равно запускает исключённые узлы; исключение относится только к проверке.
5. **Обходы пользовательского UI.** `bg/lib.ts:758` вызывает DOM element.click; `BeforeTest` меняет окно, прячет tooltips, безусловно принимает native dialogs (`main.ts:297–312`), может перезапускать сервер (`:327`); `AfterTest` закрывает пакеты через serverApi (`:447`). Эти функции не являются допустимым production execution path Dock.
6. **Данные/credential/test environment.** Не копировать testdata URL/autologin, hardcoded credentials, path rewrite user…→testdata, cleanup чужих пакетов, LFS/bootstrap/submodule install. Требуется отдельный контракт доставки разрешённых файлов и секретов; destructive cleanup ограничен созданными артефактами.
7. **Проверки результата имеют границы.** `CheckPreviewDataShowing` ждёт строку1; `CheckPreviewTable` проверяет переданный sample видимых ячеек; `progressForm` читает отображаемую ограниченную историю, не весь журнал. Для полного функционала нужны empty/schema/count/truncation, matching current execution и semantic output assertions. `.skip`, quarantine и TODO учитывать в coverage matrix, не выдавать за пройденную acceptance.

Рекомендованная последовательность для плана (вывод из зависимостей, не существующая реализация): scoped read-only settings/schema/process observations → wizard lifecycle + file import + explicit execute/inspect + result sample → transform/field mappings и variables → connection lifecycle/upload → nested workflows и compose/expand → прочие семейства узлов по той же coverage matrix. Каждую семью принимать отдельным реальным сценарием с проверкой результата, save/reopen, ошибкой/частичным эффектом и продолжением агента, а не только успешной последовательностью кликов.
