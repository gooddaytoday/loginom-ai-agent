## Подтверждённые замечания

### R16-1 · P2 · Старое доказательство загрузки принимается после замены файла

Место: [collapse-native-source.mjs:18](../../client/lib/collapse-native-source.mjs#L18),
строки 18–21; связанный существующий gate — `text-import-node.mjs:40–61`.

Условие: в одной сессии загрузить и проверить A по пути `/test/data.csv`, затем
заменить этот путь другим проверенным файлом B. После этого выполнить импорт,
оставив ссылку на старый upload A. Текущий import preflight выбирает квитанцию
по operation ID и проверяет её внутреннюю согласованность и путь, не актуальность
содержимого пути. Новый `completedStaticImports` повторяет эту проверку и допускает
источник с SHA A, хотя более поздняя успешная загрузка подтверждает SHA B.
Проверка последнего execution узла не исправляет неверную связь execution с файлом.

Контролируемая offline-проверка настоящих `verifyTextImportSource` и
`completedStaticImports` с двумя приватными завершёнными uploads по одному пути
подтвердила: обе функции приняли старый SHA `aaaa…`, при новом SHA `bbbb…`.
Пользовательский флаг provenance в воспроизведении не использовался.

Следствие: профиль `owned_static_completed_fixture` может быть заявлен для
других байтов, чем подтверждает сохранённая source proof. Значения native могут
быть точно прочитаны из результата B, но происхождение этого результата
не соответствует доказательству A. Это не требование server atomic snapshot.

В correction-фазе нужно связать проверенную версию содержимого пути с выполнением
импорта либо отклонять superseded/неопределённые загрузки того же пути. Учесть,
что текущий executor передаёт только successful uploads: одной проверки последнего
успешного SHA недостаточно для поздней неопределённой перезаписи. Контрольный случай
— новая подтверждённая загрузка с теми же байтами; её нельзя ошибочно считать
изменением данных. Живой end-to-end случай замены в ревью не запускался: дефект
подтверждён на host admission functions, его live-проверка относится к correction.

### R16-2 · P2 · Frontend pins подтверждают повторную загрузку, а не код документа

Место: [collapse-native-output.mjs:22](../../client/lib/collapse-native-output.mjs#L22),
строки 22–33.

`verifyFrontends` получает из страницы только `document.scripts[].src`, затем
отдельным host fetch скачивает файлы и хеширует новые ответы. Эти ответы не связаны
с телами scripts, которые браузер ранее загрузил и исполнил. Например, документ
может использовать ранее закешированный `rpc.js` с тем же URL и номером Loginom,
а свежий host fetch уже возвращает закреплённую ревизию. Gate пропустит документ.
Три последующие проверки count-loader functions не проверяют используемые
`GetDynamicData`/`InitializeMethodCallMessage`/`DispatchMessageAsync` из RPC runtime.

Offline-проба исполнила извлечённую без изменений функцию gate: браузер вернул
только пять src, host fetch получил пять реальных закреплённых файлов из локальных
артефактов. Gate завершился успешно, не запросив исполняемую RPC-реализацию.
Это воспроизведение пробела проверки, **не утверждение, что RPC текущего живого
Loginom был подменён**. Сохранённые успешные live-результаты остаются действительными.

Следствие: private fixed321/interface116 может быть допущен на runtime, для которого
совместимость с закреплённым transport не установлена. Нужен документно-привязанный
контроль действительно загруженных scripts или проверяемых критических функций
реального RPC объекта до native dispatch; несовпадение должно отказывать.
Повторный fetch сам по себе не заменяет такую привязку.

### R16-3 · P3 · TypeScript-контракт не отражает exact-full API

Место: [node-contracts.d.ts:26](../../client/lib/node-contracts.d.ts#L26),
также `TableCell` и `NodeOutputPort` того же файла.

В JSON API и runtime добавлены `read.coverage`, `cell_type`, `native`, `exact_table`
и метаданные чтения, а экспортируемый `NodeApplyRequest.read` по-прежнему содержит
только три старых поля. Декларации результата также не содержат новых полей.
Типизированный клиент не может описать новый object literal запроса и прочитать
exact_table через объявленный `NodeOutputPort` без обхода типов.

Подтверждено чтением итоговых деклараций и сравнением с JSON schema; TypeScript
compiler не запускался. Следует синхронизировать декларации, сохранив совместимость
старого sample-контракта и различие legacy/native ячеек.
