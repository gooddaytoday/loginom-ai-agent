# Подключение задач к общей памяти Loginom Dock

## Новый узел: регистрация поколения 20260913.5

Механизм реализован и установлен 13 сентября 2026 по указанию пользователя.
Он применяется **перед каждым новым узлом**. Повторная разработка механизма,
перезапуск приложения и изменение настроек соседних задач не требуются.
Четыре текущих MCP11–14 продолжают использовать неизменённое поколение
`20260913.3`. Новые MCP используют `20260913.5` и требуют точной активной
регистрации; отсутствие записи не разрешает fallback к памяти своего worktree.

Координатор работает из основного checkout. Сначала выбирает узел по обычным
phase gates, фиксирует принятую main base и создаёт новый постоянный worktree,
ветку и самостоятельный сохранённый проект приложения. Задачу пока не создавать:
это немедленно запустит первый ход. Не использовать следующую разработку как
тест памяти до завершения обязательной приёмки предыдущего узла.

### 1. Подготовка точной рабочей папки

После подготовки собственного Dock source MCP, HOME и отключения установленного
Dock-плагина выполнить сначала preview, затем установку. Значения ниже —
заполнители: взять настоящий путь, именованную ветку и полный принятый base SHA.

```sh
python3 tools/project-memory/prepare_task_memory.py --cwd <worktree> --branch <branch> --base <SHA>
python3 tools/project-memory/prepare_task_memory.py --cwd <worktree> --branch <branch> --base <SHA> --install
```

Helper проверяет linked Git worktree именно этого репозитория, ветку/base,
неизменную сборку и установленные корневые hooks. Сохраняет существующий Dock
config побайтно и дописывает только проектный MCP памяти и локальное отключение
`openviking-memory@openviking`. При существующей чужой memory config отказывает.
Настройки самого подключения и ключи не меняются.

Независимая запись:
`~/.openviking/project-memory-enrollments/loginom-dock/<sha256(cwd)>.json`.
Права каталога0700, файлов0600; рядом резервная копия исходного project config.
В routeSpec входит только один cwd, его hash не зависит от следующих регистраций.
Начальный статус `pending`; session state и cursor ещё не создаются. Старый
`~/.openviking/project-memory-routing.json` и его список11–14 **не менять**.

### 2. Один подготовительный ход новой задачи

Получить подготовленный project ID через `list_projects`. Создать обычную задачу
с local execution именно в этом permanent worktree, `gpt-6-astra / medium`.
Первый запрос должен ограничиваться проверкой окружения, например:

> Это подготовительный ход нового узла до включения общей памяти. Подтверди
> фактический cwd, branch/base/head, собственные writable roots и source pins.
> Разработку и обращения к OpenViking пока не начинай; подключение ожидает
> регистрации координатором. Настройки, hooks и память не меняй. Верни проверенные
> метаданные и заверши ход; следующее задание придёт в эту же задачу.

Реальный SessionStart записывает `<sha256(cwd)>.bootstrap.json`: только task ID,
cwd, registrationId, routeHash и время. Остальные события pending-фазы не вызывают
официальные hooks. Другая задача в той же папке не может присвоить эту запись.
До активации MCP отклоняет вызовы. Не отправлять ему подставные host metadata и
не создавать регистрацию из придуманного thread ID.

### 3. Проверка границы и включение

После завершения подготовительного хода координатор получает свежий app snapshot:
реальный task ID, turn ID, `completed` и `idle`. Сохранить только эти метаданные
в приватный JSON0600, например `.dock/shared-project-memory/<node>-bootstrap-evidence.json`:

```json
{
  "threadId": "<actual app task ID>",
  "cwd": "<exact prepared worktree>",
  "registrationId": "<ID returned by preparation>",
  "turnStatus": "completed",
  "threadStatus": "idle",
  "developmentStarted": false,
  "turnId": "<actual completed bootstrap turn ID>",
  "checkedAt": "<UTC time of the app check>"
}
```

Файл является подтверждением координатора, не независимым источником истины:
сначала проверить приложение и ответ задачи. Helper дополнительно сверяет его
с реальным SessionStart observation; допускаются receipts не старше10 минут.
Если проверка устарела — перечитать состояние, а не поменять дату вслепую.

```sh
node tools/project-memory/review_hooks.mjs --generation 20260913.5 --workspace <worktree> --trust --output <hooks-receipt.json>
node tools/project-memory/enroll_task.mjs --cwd <worktree> --thread <actual-task-ID> --evidence <bootstrap-evidence.json> --hooks-receipt <hooks-receipt.json>
```

`review_hooks` читает штатный `hooks/list`, сверяет точные команды и сохраняет
возвращённые currentHash через обычный `config/batchWrite`, без runtime reload.
Новая папка должна видеть10 trusted project hooks и0 original memory hooks.
Это две группы пяти событий: v3 обслуживает11–14, v5 с `--enrollments-only`
обслуживает только независимые регистрации. Координатор сохраняет свой обычный
плагин; обе проектные группы его пропускают. Две группы не означают двойной capture.

`enroll_task` резервирует только свою запись (`.json.lock`), проверяет prepared
config/hooks, отсутствие legacy/shared state и writer, переводит запись в
`enrolling`. Затем вызывает неизменённый официальный SessionStart с `source:resume`:
он не запускает sweeper чужих сессий. Штатный новый state с cursor0 и совпадающие
activation/route receipts позволяют установить `active`. Нулевой cursor допустим
только для новой сессии; после запуска он не редактируется. Подготовительный ход
может войти в последующий штатный capture уже в общем Peer.

### 4. Проверка доступа и первой записи

Следующий короткий ход **той же задачи** должен вызвать её зарегистрированный
MCP: health, адресный find общего project root в actor, `read_content:false`,
малый limit, затем точный read одной релевантной записи. Зафиксировать URI и
результат. Только после успешного допуска выдавать разработку следующему ходу.
Helper возвращает `actorAccessVerified:false` и `newCaptureVerified:false`:
одна установка файлов не подтверждает эти свойства.

После первого законченного этапа проверить общий Peer новых сообщений и
extraction подтверждённого знания; выполнить exact read-back и scoped retrieval.
Проверка конкретного знания обязательна: успешный commit extractor не гарантирует
каждый фрагмент. Далее чтение по потребности, события по окончании фаз; таймера нет.

### Повторный запуск и восстановление

- Повторная подготовка той же свежей папки с неизменным config возвращает
  `already-prepared`. Не использовать её для переезда или обновления работающей задачи.
- Повторный `enroll_task` для active сессии возвращает `already-enrolled` с прежним
  cursor, если приложены свежие достоверные receipts и исходное наблюдение bootstrap.
- При частичном сбое состояние `enrolling` сохраняется. Повтор возможен только
  для той же задачи с новым подтверждённым idle snapshot и нулевым неиспользованным
  state. Захваченные данные, чужой ID, writer или оставшаяся coordinator lock
  требуют разбора; helper не удаляет lock и не сбрасывает cursor вслепую.
- При расхождении config/runtime/receipts сохранить всё и остановить запуск этой
  задачи. Старые потоки продолжают свой маршрут. Не включать второй capture и
  не возвращать резервную копию поверх уже продвинувшегося состояния.
- До создания новой задачи и появления capture можно отдельно восстановить её
  project config из сохранённой копии после проверки отсутствия иных изменений.
  Регистрации/истории не удалять без согласованного решения. После начала capture
  обратный переход — отдельная миграция на границе этапа, а не удаление записи.

## Обязательный порядок включения

1. Дождаться окончания текущего этапа либо явной остановки пользователем;
   сохранить ID, checkpoint, commit и незавершённые изменения. Проверить
   отсутствие активной работы/harness/Hermes. Остановку не считать завершением разработки.
2. После перезапуска открыть только координатор, оставив рабочие задачи незагруженными.
   Проверить исходные SHA конфигурации и pinned runtime. Проверить фактические
   настройки hooks этой задачи. Подтвердить новые определения через штатный
   интерфейс Codex; не записывать выдуманный `trusted_hash`, не применять
   флаги обхода hook trust. Определения должны соответствовать подготовленным
   `hooks.json.pending` и текущему проверенному коду обёртки.
3. `flush_legacy_capture.mjs N`: дозаписать и завершить прежнюю партию capture штатным кодом OpenViking под
   прежним Peer. Успех проверить по состоянию и ответу сервера: не должно остаться
   неотправленного хвоста, активной блокировки или незавершённого `ovSessionId`.
   Один лишь код выхода hook этого не доказывает.
4. `install_task_config.py N` устанавливает подготовленный MCP override и
   `plugins."openviking-memory@openviking".enabled=false` только в данной рабочей
   папке. Это отключает исходные plugin hooks; глобальные настройки плагина
   не меняются. Поскольку bundled skills также исчезнут из каталога задачи,
   ссылки на официальные SKILL.md сохранены в AGENTS.md. Снова вызвать
   `review_hooks.mjs --trust`: для этой папки originalMemoryHooks должны быть пусты.
   Подтвердить завершение возможных async workers. Не отправлять задаче новый
   запрос до окончания следующего шага.
5. `migrate_task_state.mjs N --phase-boundary-verified` требует свежие receipts
   после установки и verified idle boundary. Он берёт официальный legacy lock,
   проверяет transcript tail, сохраняет внешний backup, переносит cursor с
   chmod 0600 и запускает SessionStart с `source:"resume"`. Флаг не заменяет
   проверку координатором. При сбое после переноса не восстанавливать старый backup.
   Helper сохраняет activation record после переноса; обёртка создаёт routing
   receipt только после проверки состояния официального hook. Две активные копии
   состояния и обнуление курсора запрещены.
6. Обновить подключение MCP этой задачи и проверить реальный `find/read` в actor
   scope. До этого старый процесс не считается обновлённым от изменения файлов.
   Не архивировать задачу и не удалять worktree ради перечитывания настроек.
7. Зафиксировать один реальный подтверждённый нюанс Loginom. Проверить фактический
   Peer нового capture, извлечение нужного знания в общий раздел, точное read-back
   и адресный поиск из другой задачи. Повторить первоначальный доступ для каждого
   потока; затем обращаться к памяти по потребности, без таймера.

по прежним правилам, отдельно от проектных событий Peer.

Для точной проверки extraction: GET `/api/v1/tasks` с `task_type=session_commit`
и точным `resource_id=cx-<threadId>`; сопоставить created_at с текущим commit,
проверить status completed, затем memory_diff_uri. Из diff сохранять только
URI/типы операций и summary, без before/after и сырых сообщений. Точный read-back
и адресный find выполняются через зарегистрированный MCP. Это разовая диагностика,
не периодический опрос и не альтернативный путь записи.

## Существующая память и конкуренция

Старые worktree-записи не удаляются и не переписываются. Автоматическая смена
маршрута не переносит их. После переключения разработчик может сформулировать
подтверждённые прежние выводы в своей текущей задаче для общего capture; полные
старые журналы не переотправляются.

В исходниках сервера есть раздельные сессии, очереди по Peer и блокировки записи;
соответствие этих деталей живой версии не проверено этим набором локальных тестов.
Файловая блокировка не предотвращает смысловые противоречия. Новые знания должны
содержать версию Loginom, узел, условия, ветку/SHA и статус проверки. Незавершённая
ветка не меняет автоматически знания о принятом main или установленном плагине.

## Обратный переход

Остановить выдачу новых этапов и завершить текущий capture. Сверить, что нет
неотправленного хвоста. Вернуть исходные конфигурации только если их SHA совпадают
с планом и нет новых чужих изменений; включить штатные hooks и обычный MCP.
Перенести актуальный cursor, а не старую резервную копию. Не удалять полученные
знания и не переотправлять историю. Снова проверить фактическую маршрутизацию.
