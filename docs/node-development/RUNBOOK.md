# Обработка узлов — рабочий маршрут

Актуальная инструкция для агента, который берёт узел из задачи Paperclip и доводит его до PR.
Остальные документы каталога `docs/node-development/` справочные: они не запускают очередь
и не добавляют проверок сверх этого файла.

Ветка `lab-preparation` в `loginom-swarm` заморожена. Её код, роли и задачи не использовать
и не продолжать.

## Принципы

- Цель — принятый узел, а не новая инфраструктура. Новые проверки, барьеры и сервисы
  добавлять только с согласия владельца.
- Блокер дольше 30 минут — остановиться и написать владельцу в задаче Paperclip.
- Состояние хранится в задаче Paperclip. Checkpoint — не больше 20 строк, комментарием к задаче.
- Прерванная попытка (нет `result.json`) не засчитывается как результат узла и не блокирует слот:
  порядок восстановления описан в разделе «Прерванная попытка». Владельцу пишут только в случаях, перечисленных там.
- База — ветка `loginom` репозитория `gooddaytoday/loginom-ai-agent`. PR открывать в `loginom`.
  Закрытые PR прежнего Lab не использовать.

## Слот

Слот — это агент-разработчик и его ресурсы: аккаунт Loginom, CLI-профиль, номер DISPLAY
и каталог `/opt/loginom-worker/slots/<slot>/`. Сейчас слоты `a`, `b` и `c`. Переменная
`NODE_SLOT` задаёт слот агента. Чужой слот не занимать.

Стенд: `http://logi-test-plan.bg.local/app/?testable=true`.
Paperclip: `http://10.200.4.106`.

## Как взять задачу

1. Взять назначенную задачу (Issue) со статусом, который Paperclip отдал в работу.
   В описании указаны component ID, slug, режимы и критерии приёмки.
2. Работать в worktree, который Paperclip создал для этой задачи, от базовой ветки
   проекта (сейчас она указана в [PAPERCLIP.md](PAPERCLIP.md)). Имя ветки — не больше трёх слов через дефис, без `/` и префикса типа.
3. Если обработчика ещё нет, написать подплан
   `docs/node-development/nodes/<slug>/plan.md` по [шаблону](templates/node-plan.md).
   Готовый режим не переписывать: задача тогда явно про доработку или проверку.

## Живое исследование

На стенде, в аккаунте своего слота, открыть мастер узла штатными скриптами runtime
и сверить его с Help и существующими E2E. Computer Use не применять. Зафиксировать
в подплане только то, что увидено: режимы, поля, типы портов, порядок строк.
Ожидаемые числа для приёмки записать в `expected.json` до запуска модели.

## Где писать код

Обработчик — в `packages/loginom-runtime`, рядом с уже существующими узлами
(`client/lib/*-node.mjs` и процедура параметров). Общий контракт Host или Agent
менять только если без этого узел не работает, и сначала согласовать с владельцем.
Адресные тесты запускать из каталога пакета, не из корня репозитория.

## Сборка и приёмка

Из worktree, закреплёнными Bun 1.3.14 и источниками Node/Chromium:

```sh
scripts/node-acceptance/build-candidate.sh "$PWD" /opt/loginom-worker/slots/$NODE_SLOT/candidates/<issue>
scripts/node-acceptance/accept-node.sh \
  --node <slug> \
  --slot "$NODE_SLOT" \
  --cli /opt/loginom-worker/slots/$NODE_SLOT/candidates/<issue>/bin/loginom-ai-agent-cli \
  --out /opt/loginom-worker/slots/$NODE_SLOT/attempts/<issue>
```

Кандидат запускается из своего каталога и не устанавливается глобально.
`build-candidate.sh` собирает не в worktree задачи, а в постоянной копии слота
`/opt/loginom-worker/slots/$NODE_SLOT/build/repo` (`NODE_SLOT` должен быть задан): там один раз ставятся зависимости
(`bun install --frozen-lockfile --ignore-scripts`), а сборка берёт `HEAD` worktree и переносит незакоммиченные
изменения (тогда кандидат получает `sourceDirty=true`). Не запускать `bun install` в корне worktree:
`node_modules` на 2,3 ГБ Paperclip копирует на хост и обратно при каждом запуске агента. Для тестов пакета
`packages/loginom-runtime/client` его собственные зависимости (около 50 МБ) ставятся в его каталоге.
`accept-node.sh` поднимает Xvfb и Openbox слота, запускает
`openai/gpt-6-sol` / `low` с лимитом 2 часа, сверяет сохранённый пакет
с `docs/node-development/nodes/<slug>/acceptance/expected.json` и закрывает сессию.
Перед холодным открытием скрипт закрывает только серверные сессии своего слота:
иначе пакет, оставленный CLI, открывается как «только чтение». Данные администратора
берутся из `LOGINOM_ACCOUNTS_FILE`, по умолчанию `/opt/loginom-worker/slots/accounts.json`.
Каждая попытка сохраняет свой пакет `/<аккаунт слота>/node-pipeline-<slug>-<имя --out>.lgp`,
поэтому повтор в том же слоте не упирается в запрет перезаписи.
Модели не передаются ожидаемые числа, история разработки и oracle.

### Время запуска

У разработчиков лимита времени запуска нет (`timeoutSec` = 0 в Paperclip): работа может идти несколько часов.
Запуск всё равно может оборваться снаружи (остановка или пауза агента, перезапуск Paperclip, сбой SSH). Одна
приёмка обычно занимает 15–25 минут, лимит работы CLI 2 часа, в худшем случае вся попытка около 2 часов 15 минут. Поэтому:

1. Молчание Codex дольше 150 минут (`outputInactivityTimeoutMs` у разработчиков) завершает запуск. Приёмка в худшем
   случае идёт около 2 часов 15 минут: если она может молчать дольше 150 минут, запускай её в фоне и опрашивай
   `result.json` и `attempts/.lock` с паузами.
2. Перед долгими шагами (сборка кандидата, приёмка) оставлять checkpoint: что готово, имя попытки, из какого HEAD.

### Прерванная попытка

Попытка прервана, если `result.json` нет, pid в `attempts/.lock/pid` не существует, а процессов слота нет
(`pgrep -u "$(id -un)" -f 'Xvfb|chrome|bwrap'` пуст). Обычная причина — оборванный запуск (остановка агента, сбой среды).
Это не ошибка узла и не повод останавливаться.

1. Проверить слот: `scripts/node-acceptance/slot-status.sh` (блокировка `устарел` — норма).
2. Написать checkpoint: «попытка X прервана, исход не засчитан, слот проверен».
3. Запустить новую попытку с новым именем из текущего HEAD. `accept-node.sh` сам снимает устаревшую блокировку
   и закрывает серверные сессии слота: данные администратора недоступны агенту, вручную `release-slot-sessions.mjs`
   не запускать напрямую. Для диагностики вне приёмки использовать порядок ниже.

Владельцу писать только если: процесс слота жив, но не ваш; `accept-node.sh` вернул `BLOCKED` при `slot locked by live pid`
и ожидание дольше 30 минут; две попытки подряд прерваны. `BLOCKED` из-за живого pid значит «ждать», а не «остановиться».

В задачу приложить `result.json` и короткий отчёт как work product.
`status` бывает `PASS`, `FAIL` или `BLOCKED`. `PASS` требует совпадения графа
и строк выхода, а также `package_closed` и `logged_out`.

### Диагностика вне приёмки и восстановление сессий

Диагностику и адресные живые проверки запускать в своём `NODE_SLOT` через общий wrapper,
а не из отдельного процесса без блокировки. Приёмка и диагностика используют одну `attempts/.lock`;
`.lock-guard` сериализует захват и восстановление устаревшей блокировки. Все новые запуски слота
должны соблюдать этот порядок. Исторические запуски без wrapper автоматически не считаются своими.

```sh
python3 scripts/node-acceptance/diagnostic-slot.py run \
  --slot "$NODE_SLOT" \
  --resources /opt/loginom-worker/slots/$NODE_SLOT/candidates/<candidate>/resources/loginom \
  --out /opt/loginom-worker/slots/$NODE_SLOT/attempts/<issue>-diagnostic-1 \
  -- <команда диагностического скрипта>
```

Wrapper проверяет соответствие `--slot` назначенному `NODE_SLOT`, сохраняет `owner.json` до запуска,
держит блокировку до окончания очистки и не выдаёт агенту административные данные в выводе.
В `owner.json` PID относится к локальному процессу, а не к серверной сессии Loginom.
Вывод диагностической команды хранится в приватных файлах; не публиковать его без проверки на секреты.
`lifecycle.json` отделяет результат команды от подтверждения освобождения сессий: `COMPLETED` — команда
завершилась с кодом 0 и очистка подтверждена, `FAILED` — команда не удалась, но очистка подтверждена,
`BLOCKED` — освобождение не подтверждено. Эти статусы не означают PASS узла или исправление дефекта.

Для штатного завершения скрипт использует `withDiagnosticSession` из
`scripts/node-acceptance/diagnostic-session.mjs`. Передать свой authenticated context, `execute`,
каталог доказательств, `makePackageCleanupCode` из проверяемого SHA и identity:
`sessionId`, `account`, `packagePath`, `loginomUrl`, обязательный `loginomBuild`,
а также явный `diagnosticDiscard`, если разрешено отбросить собственные диагностические изменения.
В callback сразу после workspace prepare вызвать `await bindPrepared(prepared)` до следующих действий:
helper сохраняет `session.json` с document/package/workflow refs и в `finally` выполняет штатный cleanup,
проверяет привязку квитанции, записывает `cleanup.json` и закрывает браузер. Не передавать пароли в identity.
Закрытие браузера само по себе не означает освобождение серверной сессии. Если prepare не завершён,
helper не угадывает пакет; административное восстановление выполняет wrapper.

При аварии всего wrapper (включая SIGKILL) `finally` не гарантирован. После проверки завершения процессов
запустить восстановление с новым именем каталога:

```sh
python3 scripts/node-acceptance/diagnostic-slot.py recover \
  --slot "$NODE_SLOT" \
  --resources /opt/loginom-worker/slots/$NODE_SLOT/candidates/<candidate>/resources/loginom \
  --out /opt/loginom-worker/slots/$NODE_SLOT/attempts/<issue>-recovery-1
```

Это разрешённый служебный путь вне приёмки; запускать постороннюю приёмку ради cleanup не требуется.
Восстановление захватывает ту же блокировку, сверяет аккаунт `lab-slot-<slot>` и URL профиля с настройкой
слота, проверяет отсутствие живых процессов профиля/дисплея и вызывает штатную административную очистку
в квалифицированном bwrap/Xvfb/Openbox, с лимитом 180 секунд. Сейчас серверная очистка закрывает **все сессии
аккаунта своего слота**, а не точечный server session ID. Поэтому она разрешена только при исключительном
владении свободным слотом; чужие аккаунты и активные процессы не затрагиваются. После refresh проверяется,
что сессий аккаунта не осталось, и подтверждается выход администратора. Повтор с новым каталогом безопасен:
нулевое число оставшихся сессий допустимо. Временный файл административных данных удаляется в `finally`;
после SIGKILL до публикации артефактов оператор проверяет приватный каталог на оставшийся
`.release-accounts.json` и удаляет его, не загружая в Paperclip.

При `BLOCKED` не обходить проверки и не запускать `release-slot-sessions.mjs` напрямую.
Сохранять исходный FAIL. Если владелец процесса/сессии неизвестен, слот использует чужой запуск,
невозможно прочитать состояние процессов или восстановление завершилось ошибкой — сообщить оператору
конкретный слот и пути собственных пакетов. Для исторических сессий без подтверждённого исключительного
владения требуется оператор. Общий код слотов обновлять перед использованием; одновременно запускать
старую копию приёмки без `.lock-guard` и новый wrapper нельзя.

## Сдача

1. Обновить запись узла в `docs/node-development/registry.json` и выполнить
   `python3 docs/node-development/tools/validate.py --render`.
2. Открыть PR в `loginom`. В описании — ссылка на задачу Paperclip и на `result.json`.
3. Перевести задачу в `in_review` с финальным комментарием (итог, ссылки на PR и `result.json`). Стадия review сама
   назначит «Ревьюера узлов» и разбудит его; ревьюера в комментарии не упоминать: упоминание затирает пробуждение
   стадии, и ревьюер получит обычное «вас упомянули» без контекста ревью. Пробуждение может прийти с задержкой
   до нескольких минут, пока освобождается аренда среды вашего запуска, это нормально.
4. Не сливать PR и не выпускать релиз. Это делает владелец на стадии approval.

Раскладка приёмки узла: `docs/node-development/nodes/<slug>/acceptance/task.md`,
`data/*.csv` и `expected.json`. В `task.md` и `expected.json` путь пакета пишется
как `{{PACKAGE_PATH}}`: скрипт подставит путь попытки. `expected.json` в рабочую папку
модели не копируется.

## Ревью

«Ревьюер узлов» проверяет PR и `result.json`, но не переписывает узел за разработчика.

1. Прочитать diff PR, подплан, исходные данные и `expected.json`. Для всего обязательного scope составить
   матрицу: требование/режим → сценарий → публичный путь API → SHA → доказательство → PASS/FAIL/NOT_RUN.
   Ожидаемые числа независимо пересчитать из данных, не из вывода модели. Непроверенный сценарий не является PASS.
2. Проверить свежесть `result.json`: `status` `PASS`, `cli_exit` `0`, `oracle.status` `PASS`,
   `package_closed` и `logged_out` равны `true`; SHA результата, кандидата и вердикта совпадает с головой PR.
   Проверить все поля/метки/типы, строки, NULL, числовую точность, отсутствие фильтра и свежесть выполнения.
3. Живые проверки выбирать по рискам в собственном слоте `r`. Самостоятельно проверять затронутую динамику
   схемы, повторное выполнение после изменения входа, восстановление и изменения общего runtime.
   Адресные скрипты штатного runtime и публичные Dock-вызовы разрешены; новые сервисы и Computer Use не нужны.
   Проверять скрипт перед запуском, использовать точный SHA PR и отдельный каталог доказательств.
4. Для динамического узла сохранить IDs импорта и узла, заменить источник и повторить публичный
   `loginom_dock_node_read` с исходным `source_operation_id`. Проверить изменение числа полей и смену
   категории/метки при прежнем числе полей. Пересоздание или повторная настройка узла не подтверждают этот путь.
   Первоначальный PASS, fixture oracle, видимая таблица и низкоуровневый cold reader не заменяют публичного чтения.
5. Подтвердить граф, сохранение после последнего успешного чтения, независимое открытие и выполнение пакета
   без повторной настройки, полный результат и очистку своих сессий. Исторические FAIL сохранять.
   Для агрегатов использовать группы с различающимися значениями, чтобы различить Sum/Min/Max/Avg.
6. Различать «не воспроизвелось» и «не удалось проверить». Недоступный стенд, таймаут или другой SHA дают
   NOT_RUN/BLOCKED; подтверждённые внешние доказательства учитывать. В отчёте назвать покрытие и ограничения.
7. На native стадии решение и комментарий передавать единым `PATCH /api/issues/:id`.
   Одобрить: `status: done` с выводом — Paperclip передаст следующему участнику, если стадия approval ещё впереди.
   Вернуть: `status: in_progress` с конкретными правками — Paperclip запишет `changes_requested` и назначит
   `returnAssignee`. Два отказа эскалируются владельцу; лимит кругов не означает одобрения.
   При оставшихся дефектах или обязательных непроверенных рисках вердикт «НЕ ПРИНЯТО».

Лимит запуска Ловца Галлюцинаций — 3 часа (`timeoutSec=10800`). Перед долгой проверкой оставлять checkpoint,
сохранять время на закрытие пакета, выход и отчёт. Новый SHA требует перепроверки затронутых сценариев.

### Возврат с approval и независимая проверка

Возврат владельцем с approval выполняется единым PATCH `status: in_progress` с комментарием.
Он сохраняет предыдущие стадии и возвращает исполнителю; повторная сдача идёт на ту же approval,
уже завершённый native review автоматически не повторяется. Первым запросом не ставить `todo` или `blocked`:
board override может сбросить executionState.

Если владелец требует дополнительную независимую проверку, после исправления исполнитель:

1. Закрепляет запушенный SHA PR и свежие серверные доказательства. Публикует verification packet и результат
   на своей исходной задаче штатным artifact helper: загрузка разрешена только в свою задачу, в задачу другого
   агента API вернёт 403 `Agent cannot mutate another agent's issue`, поэтому файлы туда не переносятся.
2. Одним запросом создаёт дочернюю verification-задачу Ловцу и ставит родителю блокер:

   ```sh
   POST /api/issues/<родитель>/children
   {
     "title": "Независимая проверка <узел> — раунд N",
     "assigneeAgentId": "<id Ловца Галлюцинаций>",
     "status": "todo",
     "blockParentUntilDone": true,
     "executionWorkspacePreference": "isolated_workspace",
     "executionWorkspaceSettings": {"mode": "isolated_workspace"},
     "description": "<самодостаточное описание>"
   }
   ```

   - `blockParentUntilDone` добавляет child к существующим blockers родителя в той же операции, поэтому
     промежуточный `backlog` не нужен и проверка не может завершиться раньше зависимости.
   - `isolated_workspace` даёт Ловцу собственную рабочую копию. Без этого child наследует рабочую копию
     родителя, и Ловец правит ветку разработчика (так в ветку PR попал чужой merge-коммит).
   - Копия Ловца создаётся от `node-pipeline`. Точный SHA он берёт сам: `git fetch origin <ветка PR>` и
     `git checkout --detach <SHA>`, затем собирает кандидата `build-candidate.sh` из этой копии.
   - В description: полный scope, критерии, команды, точный SHA, пути входных файлов в репозитории на этом SHA
     и ссылки `/api/attachments/<id>/content` на материалы исходной задачи: имя файла, размер, SHA-256 и
     идентификатор исходной задачи.

   Затем переводит родителя в `blocked`, оставаясь исполнителем. Владелец ничего не копирует.
3. Первым шагом Ловец своим текущим run-token скачивает материалы по ссылкам в собственный каталог,
   сверяет размер, SHA-256, manifest и SHA кода и оставляет короткий receipt чтения на своей задаче.
   Доступ оператора не доказывает доступ run-token; родительские документы могут быть недоступны, поэтому
   description должен быть самодостаточным. При 401 обновляет штатные credentials; при 403/404 не повторяет
   загрузку разработчиком в чужую задачу, не меняет trust preset и не принимает результат: сохраняет запрос
   владельцу через штатную interaction и `in_review`, называя недоступный attachment. Владелец обеспечивает
   разрешённый источник или один раз копирует файл в child, после чего проверка продолжается там же.
   Ловец самостоятельно рассчитывает expected и выполняет проверку; PASS разработчика не заменяет её.
   Публикует отчёт и артефакты на своей задаче. Завершённая проверка — `done` с PASS или FAIL;
   недоступный стенд или незавершённая обязательная проверка остаётся блокером с явным действием владельцу.
4. После разрешения зависимости исполнитель читает вердикт. PASS на текущем SHA позволяет сдачу родителя
   в `in_review` владельцу. FAIL требует исправления и нового раунда на новом SHA. Для доработки LOG-29
   разрешены два раунда; после второго FAIL сдача владельцу с явным «НЕ ПРИНЯТО» и обоими отчётами.

Это дополнительный verification work product, не замена native review/approval. Native `maxReviewRounds`
не считает такие дочерние проверки. Прежние отчёты и история стадий сохраняются, финальное approval — владелец.

## Руководитель

«Руководитель узлов» раскладывает партию, код не пишет и слоты не запускает.

1. Список узлов берёт из задачи партии; если он не назван, из `python3 docs/node-development/tools/queue.py next --count N`
   (Sampling — только по решению владельца).
2. Для каждого узла создаёт подзадачу в проекте «Узлы Loginom» по образцу «Образец: задача узла»:
   метка `узел` и метка режима, `executionPolicy` со стадиями `review` («Ревьюер узлов») и `approval` (владелец),
   `commentRequired`, `maxReviewRounds` = 2.
3. Порядок задают исполнители и блокировки. Последовательно: цепочка через `blockedByIssueIds`.
   Параллельно: разработчики A, B, C по кругу; лишние узлы встают в цепочку за задачей того же разработчика.
   У одного разработчика не бывает двух задач одновременно: слот один.
4. В задаче партии оставляет таблицу «узел → исполнитель → зависимость».
5. Следит за `blocked`: причину пишет одной строкой, при ожидании владельца ставит метку `нужен владелец`.
6. Утренняя сводка по расписанию — не больше 20 строк: в работе, заблокировано, ждёт владельца, слоты, что взять следующим.
