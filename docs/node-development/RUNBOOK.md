# Обработка узлов — рабочий маршрут

Актуальная инструкция для агента, который берёт узел из задачи Paperclip и доводит его до PR.
Остальные документы каталога `docs/node-development/` справочные: они не запускают очередь
и не добавляют проверок сверх этого файла.

Ветка `lab-preparation` в `loginom-swarm` заморожена. Её код, роли и задачи не использовать
и не продолжать.

## Принципы

- Цель — принятый узел, а не новая инфраструктура. Новые проверки, барьеры и сервисы
  добавлять только с согласия владельца.
- Блокер дольше 30 минут — остановиться и написать владельцу в задаче Paperclip.
- Состояние хранится в задаче Paperclip. Checkpoint — не больше 20 строк, комментарием к задаче.
- Неизвестный результат одной попытки помечает слот как грязный и сообщается владельцу.
  Второй слот продолжает работу.
- База — ветка `loginom` репозитория `gooddaytoday/loginom-ai-agent`. PR открывать в `loginom`.
  Не использовать продуктовые PR #3, #6, #7 и #12. PR #8 допустим.

## Слот

Слот — это агент-разработчик и его ресурсы: аккаунт Loginom, CLI-профиль, номер DISPLAY
и каталог `/opt/loginom-worker/slots/<slot>/`. Сейчас слоты `a` и `b`. Переменная
`NODE_SLOT` задаёт слот агента. Чужой слот не занимать.

Стенд: `http://logi-test-plan.bg.local/app/?testable=true`.
Paperclip: `http://10.200.4.106`.

## Как взять задачу

1. Взять назначенную задачу (Issue) со статусом, который Paperclip отдал в работу.
   В описании указаны component ID, slug, режимы и критерии приёмки.
2. Работать в worktree, который Paperclip создал для этой задачи, от базовой ветки
   проекта (сейчас она указана в [PAPERCLIP.md](PAPERCLIP.md)). Имя ветки — не больше трёх слов через дефис, без `/` и префикса типа.
3. Если обработчика ещё нет, написать подплан
   `docs/node-development/nodes/<slug>/plan.md` по [шаблону](templates/node-plan.md).
   Готовый режим не переписывать: задача тогда явно про доработку или проверку.

## Живое исследование

На стенде, в аккаунте своего слота, открыть мастер узла штатными скриптами runtime
и сверить его с Help и существующими E2E. Computer Use не применять. Зафиксировать
в подплане только то, что увидено: режимы, поля, типы портов, порядок строк.
Ожидаемые числа для приёмки записать в `expected.json` до запуска модели.

## Где писать код

Обработчик — в `packages/loginom-runtime`, рядом с уже существующими узлами
(`client/lib/*-node.mjs` и процедура параметров). Общий контракт Host или Agent
менять только если без этого узел не работает, и сначала согласовать с владельцем.
Адресные тесты запускать из каталога пакета, не из корня репозитория.

## Сборка и приёмка

Из worktree, закреплёнными Bun 1.3.14 и источниками Node/Chromium:

```sh
scripts/node-acceptance/build-candidate.sh "$PWD" /opt/loginom-worker/slots/$NODE_SLOT/candidates/<issue>
scripts/node-acceptance/accept-node.sh \
  --node <slug> \
  --slot "$NODE_SLOT" \
  --cli /opt/loginom-worker/slots/$NODE_SLOT/candidates/<issue>/bin/loginom-ai-agent-cli \
  --out /opt/loginom-worker/slots/$NODE_SLOT/attempts/<issue>
```

Кандидат запускается из своего каталога и не устанавливается глобально.
`accept-node.sh` поднимает Xvfb и Openbox слота, запускает
`openai/gpt-6-sol` / `low` с лимитом 30 минут, сверяет сохранённый пакет
с `docs/node-development/nodes/<slug>/acceptance/expected.json` и закрывает сессию.
Перед холодным открытием скрипт закрывает только серверные сессии своего слота:
иначе пакет, оставленный CLI, открывается как «только чтение». Данные администратора
берутся из `LOGINOM_ACCOUNTS_FILE`, по умолчанию `/opt/loginom-worker/slots/accounts.json`.
Каждая попытка сохраняет свой пакет `/<аккаунт слота>/node-pipeline-<slug>-<имя --out>.lgp`,
поэтому повтор в том же слоте не упирается в запрет перезаписи.
Модели не передаются ожидаемые числа, история разработки и oracle.

В задачу приложить `result.json` и короткий отчёт как work product.
`status` бывает `PASS`, `FAIL` или `BLOCKED`. `PASS` требует совпадения графа
и строк выхода, а также `package_closed` и `logged_out`.

## Сдача

1. Обновить запись узла в `docs/node-development/registry.json` и выполнить
   `python3 docs/node-development/tools/validate.py --render`.
2. Открыть PR в `loginom`. В описании — ссылка на задачу Paperclip и на `result.json`.
3. Перевести задачу в `in_review` и назначить `Node Reviewer`. Если у задачи уже есть
   стадия review, Paperclip передаст её ревьюеру сам.
4. Не сливать PR и не выпускать релиз. Это делает владелец на стадии approval.

Раскладка приёмки узла: `docs/node-development/nodes/<slug>/acceptance/task.md`,
`data/*.csv` и `expected.json`. В `task.md` и `expected.json` путь пакета пишется
как `{{PACKAGE_PATH}}`: скрипт подставит путь попытки. `expected.json` в рабочую папку
модели не копируется.

## Ревью

`Node Reviewer` проверяет PR и `result.json`, но не переписывает узел за разработчика.

1. Прочитать diff PR, подплан и `expected.json`. Ожидаемые числа должны следовать из данных,
   а не из вывода модели.
2. Проверить, что `result.json` свежий: `status` `PASS`, `cli_exit` `0`, `oracle.status` `PASS`,
   `package_closed` и `logged_out` равны `true`, `source_sha` совпадает с головой PR.
3. Одобрить: комментарий с выводом, задачу перевести в `in_review` на владельца.
   Вернуть: комментарий со списком конкретных правок, задачу — на разработчика в `todo`.
   Не больше двух кругов, дальше решает владелец.
