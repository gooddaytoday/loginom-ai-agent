# Обработка одного узла отдельным агентом

Начать с [README](../README.md), [inventory](../inventory.md), [registry](../registry.json)
и конкретного подплана. Общие критерии фаз — [lifecycle](lifecycle.md), проверка
через модель — [acceptance-cli](acceptance-cli.md). Этот маршрут не требует
запуска четырёх потоков или отдельной задачи оркестратора.

## Назначение

Пользователь либо оркестратор передаёт [assignment](../templates/assignment.md):
тип/режимы, ссылку на подплан, границы, pinned base SHA ветки `loginom`, собственные
ресурсы и критерии результата. Если подробного подплана нет, сначала подготовить
его по [new-node-plan](new-node-plan.md) и [шаблону](../templates/node-plan.md).
Не расширять задачу до следующего узла или всей категории.

Один узел — отдельные задача разработчика, постоянный worktree и ветка; название
ветки не длиннее трёх слов через дефис, без `/`. Проверить ветку/base/HEAD,
исходные незавершённые изменения, Loginom-аккаунт, изолированный browser/runtime
profile и уникальные имена пакетов. Работать в `loginom-ai-agent`; старые Dock
checkout и installed plugins не являются местом правки обработчика.

Проверенный доступ к общей памяти нового проекта обязателен до разработки.
Применять [текущую регистрацию](../../../services/loginom-ai/tools/project-memory/CURRENT.md)
поколения `20260924.1`: подготовить новый `<repo>/.worktrees/<короткая-ветка>` до
создания задачи, завершить отдельный bootstrap без разработки, проверить фактические
metadata/доверие hooks, активировать и проверить actor health/find/read в этой задаче.
**[Установка и полный цикл записи проверены](shared-memory.md).** При отсутствии допуска
сохранить checkpoint «подготовка заблокирована» с владельцем и точным условием
продолжения. После первого содержательного этапа проверить capture/extraction и
прочитать сохранённое знание из основного checkout. В одиночном режиме эти шаги
выполняет сам агент в роли координатора; это не независимое ревью или уже выданный
допуск. Старые helpers Dock, глобальный Peer и сброс cursor не использовать.

## Выполнение

1. На Astra / medium создать Goal до готовности к первому ревью, без собственного
   token_budget. Исследовать живой Loginom через Dock/runtime scripts, Help/E2E
   и текущую реализацию; не использовать Computer Use.
2. Автономно выполнить подплан и подходящие тесты, сохранить доказательства,
   ограничения и source SHA. Задавать вопросы только о недоступном существенном
   решении; обычные probes, правки и адресные проверки не требуют подтверждения.
3. Выполнить один отдельный проход ревью в этой же задаче на Astra / medium.
   Затем один раунд исправлений подтверждённых в живом Loginom замечаний, если
   они есть. Проверить исправления адресно; повторное полное ревью не запускать.
4. Подготовить из своих исходников отдельный candidate и входы приёмки. Проверить
   происхождение candidate и неизменность параметров; не заменять рабочую
   пользовательскую установку ради проверки.
5. Проверить общий журнал ресурсов хоста и CLI-слот по
   [правилам оркестратора](orchestrator.md). Путь и владелец журнала обязательны
   в назначении; новый локальный lease не заменяет общий `acceptance.lock`.
   Если слот занят другой кампанией, сообщить готовность
   и ждать его освобождения. Если отдельного оркестратора нет, самому записать
   минимальную campaign/lease по [шаблону](../templates/campaign.json): mode=single,
   только этот узел, один developer и один acceptance slot. Не начинать
   конкурирующий прогон лишь потому, что задача называется single.
6. Выполнить автономную приёмку штатным standalone CLI на GPT-6 Sol (`openai/gpt-6-sol`) / low с существующей
   ChatGPT OAuth-подпиской. Самостоятельно проверить результат по oracle подплана;
   итог модели и успешный exit не заменяют проверку. При FAIL следовать lifecycle:
   сохранить попытку, диагностировать, исправить и выполнить обоснованный повтор.

Если агент получил назначение от оркестратора, он не присваивает себе общие
полномочия: выдачу ревью/приёмки и lease выполняет оркестратор. Агент сообщает
один результат на границе фазы по [event](../templates/event.json). При прямом
single-запросе одного пользователя агент последовательно выполняет эти же фазы
сам и отмечает их границы в checkpoint; это не означает независимое контекстное
ревью другим агентом.

## Отчёт и продолжение

После каждой завершённой фазы и перед остановкой сохранить
[checkpoint](../templates/checkpoint.md). В нём нужны текущая фаза, HEAD, результаты,
активные/неопределённые операции, занятые ресурсы и конкретный следующий шаг.
При возобновлении сначала сверить реальные процессы, задачу и receipts, затем
продолжать ту же фазу; не повторять действие с неизвестным эффектом.

Итог по [completion](../templates/completion.md) перечисляет поддержанные режимы,
фактические проверки, независимый результат, кандидат/commit и оставшиеся
ограничения. Освободить только собственные подтверждённо завершённые ресурсы.
Не удалять доказательства неуспешных попыток и чужие данные.

После одного узла остановить назначения. Принятый узел не означает автоматическое
слияние, push ветки `loginom`, релиз или обновление пользовательского клиента:
для этого нужна отдельная команда. Для последовательной обработки очереди
использовать [orchestrator](orchestrator.md) с mode=sequential, а не скрыто
превращать single-задачу в кампанию.
