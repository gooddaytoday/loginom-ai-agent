# Техническая приёмка CLI

Итоговый прогон исполнителя и независимый модельный прогон ревьюера выполняются в Loginom AI Agent CLI на модели и с уровнем рассуждения, заданными действующими инструкциями сквада Multica для внутреннего CLI-прогона. Multica — единственный источник выбора этих настроек; подпланы, документация и карточки не закрепляют их конкретные значения. Модель native Codex агента и модель внутреннего Loginom CLI — отдельные настройки. Исполнитель фиксирует выбранные значения в доказательствах попытки; ревьюер проверяет тот же SHA с теми же моделью и уровнем рассуждения. Смена настройки Multica требует новой итоговой попытки, прежние результаты сохраняются. Промежуточные диагностические прогоны могут использовать другие модели; их результаты не заменяют итоговую приёмку. Перед запуском проверить доступность модели и варианта в установленном CLI; при недоступности зафиксировать нехватку доступа, не подменять модель. Доказательства фиксируют фактические модель, вариант, исходный SHA и сборку CLI.

Критерий приёмки — самостоятельное выполнение агентом согласованной задачи через рабочие инструменты Loginom, включая создание, настройку, выполнение, сохранение и проверку результата. Отдельные тесты хелперов не заменяют этот прогон. Oracle и ожидаемые результаты остаются вне контекста модели; ревьюер выполняет независимую проверку под своим аккаунтом на том же опубликованном SHA.

Если целевой прогон выявляет ошибки, исполнитель устанавливает причину и самостоятельно исправляет хелперы и инструкции узла в разрешённом объёме. Исправления должны обеспечивать корректную работу целевой модели без ослабления проверок, раскрытия oracle или подмены результата заранее подготовленным ответом. Изменения общих контрактов и критериев приёмки согласовываются с владельцем; общие изменения оформляются отдельной задачей. После исправления выполняется новый итоговый прогон на назначенной через Multica модели с новым профилем и идентификатором попытки; исходная попытка и неизвестные эффекты сохраняются. Это осознанный прогон после исправления, а не автоматический повтор сбоя или переключение модели. Применяются штатные правила cleanup и ограничение трёх последовательных попыток без прогресса.

Stage 0 принимается по критериям исследования: это правило не добавляет модельную или полную приёмку обработчика к согласованному объёму Stage 0. Исторические проверки и техническая квалификация параллельности сохраняются как история; их PASS не переносится на другую модель или уровень рассуждения.

Задание и входы находятся в `nodes/<slug>/acceptance/task.md` и `data/`. Ожидания — в `expected.json`; они не передаются модели. Предельное время модельного прогона — 7200 секунд. Проверяется новый пакет в собственном аккаунте, без перезаписи существующего.

После CLI независимый `scripts/node-acceptance/cold-check.mjs` из проверяемого checkout открывает пакет в новом профиле, выполняет узел, сверяет граф, значения, типы и порядок строк. PASS требует exit 0, совпадения ожиданий, подтверждённого закрытия пакета и выхода. Durable journal и его fsync-подтверждения не ослаблять. Прерывание или убийство не считается успешным закрытием.

Проверяющий работает с тем же чистым опубликованным SHA и отдельным аккаунтом. Отрицательный вердикт содержит точный дефект и предел проверки. Установку runtime, авторизацию, запуск и публикацию материалов описывает операционное руководство.
