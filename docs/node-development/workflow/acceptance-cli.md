# Техническая приёмка CLI

Задание и входы находятся в `nodes/<slug>/acceptance/task.md` и `data/`. Ожидания — в `expected.json`; они не передаются модели. Модель — `openai/gpt-6.1-sol` (medium), предельное время прогона — 1800 секунд. Проверяется новый пакет в собственном аккаунте, без перезаписи существующего.

После CLI независимый `scripts/node-acceptance/cold-check.mjs` из проверяемого checkout открывает пакет в новом профиле, заново выполняет узлы, сверяет граф, значения, типы и порядок полей. PASS требует exit 0, совпадения ожиданий, подтверждённого закрытия пакета и выхода. Повторное выполнение в новом профиле само исключает результат прежнего запуска, поэтому квитанции и доказательства происхождения не требуются. Прерывание или убийство не считается успешным закрытием.

Для `output_node_type: export_input` с `column_order: exact` передайте `--csv <фактически скачанный CSV>` из штатного файлового reader. Перед cold файл целиком сверяется с oracle сценария. Cold проверяет порядок заголовка CSV, а значения, типы и полный состав колонок — независимо после переоткрытия пакета. Без CSV такой Export получает `COLD_EXPORT_CSV_REQUIRED`. Наблюдаемый cold mapping и порядок CSV печатаются в `export_observation` отчёта; порядок mapping не определяет порядок пользовательского файла.

По умолчанию CSV — UTF-8, разделитель запятая, заголовок из технических имён. Для штатного экспорта с другим форматом укажите `--csv-delimiter` (`;` или символ табуляции) и `--csv-header labels` для меток. Неоднозначные повторяющиеся метки не доказывают порядок. Для таблицы без Export прежняя строгая проверка `exact` сохраняется.

Порядок строк (`ordered`), несколько выходов узла (`outputs` с `output_port`) и допуск для вещественных (`tolerance` колонки: `abs`/`rel`) cold-check уже поддерживает; формат полей `expected.json` — в `scripts/node-acceptance/expected-outputs.mjs`. Выход переменных cold-check не проверяет. В ветке узла новые возможности проверки не реализуются.

Проверяющий работает с тем же чистым опубликованным SHA и отдельным аккаунтом. Отрицательный вердикт содержит точный дефект и предел проверки.

## Задание модели

`task.md` проверяет один узел, а не цепочку узлов:

- не больше ~15 строк на бизнес-языке, с `{{PACKAGE_PATH}}`;
- сценарий: импорт входов → целевой узел → при необходимости одна перенастройка того же узла → сохранение пакета;
- другие обрабатываемые узлы (Калькулятор, Группировка, экспорт и т.п.) включаются, только если без них целевой узел невозможно получить на вход или выход;
- без промежуточных `.draft`-сохранений, экспортов «для проверки», квитанций и проверок SHA файлов;
- без указаний модели, как работать: инструменты, сессии, «сохраняй идентичность операции» и т.п. не пишутся;
- `expected.json` описывает только выходы целевого узла.

Всё, что cold-check не умеет проверить, — либо за пределами этапа, либо задача общего кода приёмки (решение владельца), а не повод расширять задание или строить проверку в ветке узла.
