# Автономная приёмка узла через standalone CLI

Этот документ применяется после разработки, одного ревью и необходимых
исправлений по [lifecycle](lifecycle.md). Вход — назначение, подплан и
[registry](../registry.json); порядок чтения — [README](../README.md). Во всей кампании
одновременно занят только **один слот модельной приёмки**, в том числе при
[отдельной обработке узла](single-node.md).

Модель — `openai/gpt-5.6-sol`, вариант `low`, существующая ChatGPT OAuth-подписка.
Разработчик Astra / medium и модель CLI имеют разные задачи и истории.
Computer Use, Hermes и плагины ChatGPT/Codex в этом маршруте не используются.

## Условия начала

В [assignment](../templates/assignment.md) и checkpoint должны быть заполнены:

- Узел/режимы, source commit, pinned base `loginom`, точный CLI-кандидат, его
  версия и hashes; источники и bundled runtime действительно совпадают.
- Отдельный абсолютный CLI profile, аккаунт Loginom, чистая рабочая папка с
  пользовательскими входами, уникальные пути пакета/экспорта и evidence directory.
- Исходное ТЗ и hashes данных; ожидаемые схемы/значения и независимый аудитор
  находятся вне папки и контекста модели.
- Конкретные команды проверок подплана, включая сохранение и независимое переоткрытие;
  допустимая точность, граничные случаи и критерий полного результата.
- Владелец и попытка CLI-слота, предел времени. По умолчанию — 30 минут от
  отправки задания. Подплан может заранее задавать обоснованный другой предел,
  например для широких точных чтений; зафиксировать его до запуска.

Нужны закреплённые Node/Chromium и соответствующий платформе action catalog из
кандидата. Не запускать source checkout поверх старого установленного bundle
под видом нового кандидата. Проверки источников допустимы отдельно и так
обозначаются. Сборка/установка кандидата выполняется по платформенному runbook
репозитория в своей среде, без замены пользовательского клиента.

До запуска получить host lease и `acceptance.lock` по
[правилам оркестратора](orchestrator.md); локальная запись кампании не создаёт
дополнительный слот. Убедиться, что профиль и аккаунт не заняты другим владельцем,
`.writer` не остался от неподтверждённого завершения, ресурсов хватает и доступна
графическая сессия для видимого браузера. Не снимать lock по возрасту/PID
вместо сверки владельца и cleanup. Не запускать тяжёлые общие suites одновременно
с приёмкой без причины.

## Штатные команды

Ниже реальные команды текущего standalone CLI. Подставить абсолютные пути из
назначения. Значения в угловых скобках — заполнители, не готовые адреса.
Эти команды выполняются при приёмке, а не автоматически при чтении документа.

```sh
export LOGINOM_AI_AGENT_CLI_PROFILE="<абсолютный приватный CLI profile>"
NODE_ACCEPTANCE_CLI="<абсолютный путь к проверенному loginom-ai-agent-cli>"

"$NODE_ACCEPTANCE_CLI" --version
"$NODE_ACCEPTANCE_CLI" providers list
"$NODE_ACCEPTANCE_CLI" models openai
"$NODE_ACCEPTANCE_CLI" loginom status --format json
```

Проверить, что нужный профиль использует OpenAI OAuth и видит Sol. Модель,
вариант и провайдер фиксируются также по фактическому запуску. CLI profile не
наследует авторизацию Desktop автоматически. Если существующая подписка ещё
не подключена к этому профилю, применяется штатный
`providers login --provider openai` с выбором ChatGPT OAuth. Не подменять её
API-ключом, другим провайдером или fallback-моделью. Недоступный пользовательский
OAuth-шаг — настоящий блокер подготовки, а не неуспех обработчика.

Для нового разрешённого тестового подключения:

```sh
"$NODE_ACCEPTANCE_CLI" loginom setup --stdin-json --format json \
  < "<приватный JSON подключения>"
"$NODE_ACCEPTANCE_CLI" loginom check --format json
"$NODE_ACCEPTANCE_CLI" loginom status --format json
```

JSON содержит `url`, `username`, `apiKey`, `password`. Секреты поступают только
через приватный stdin; не вставлять значения в команду, Git, отчёт или prompt.
У файла права 0600, у приватного каталога 0700. Пустой `password` означает явно
выбранный вход без пароля; отсутствующее поле сохраняет прежнее значение.
Рабочая папка Loginom определяется как `/<username>`; выбирать реальную
разрешённую учётную запись, не предполагать, что она называется `user`.
Для уже подготовленного неизменного профиля достаточно check/status, повторный
setup не нужен. Перед запуском должны быть подтверждены готовность соединения
и отсутствие конфликтующей работы.

Автономная попытка:

```sh
"$NODE_ACCEPTANCE_CLI" run --no-headless --format json \
  --model openai/gpt-5.6-sol --variant low \
  --dir "<чистая рабочая папка задачи>" \
  --file "<абсолютный путь task.md>" \
  --file "<абсолютный путь dataset.csv>" \
  -- "Создай и выполни сценарий по приложенному заданию и данным. Покажи результат и сохрани пакет по пути <уникальный путь .lgp>."
```

Потоки stdout/stderr перехватывает средство запуска агента. **До записи в
evidence** отобрать публичные события и ошибки и применить существующий
`createRedactor` из `packages/loginom-runtime/client/lib/redact.mjs`: метод
`redact` для структурированных событий, `text` для сообщений об ошибках.
Известные секретные значения передавать ему только в памяти. Если JSON или
очистка не удались, записать факт пропуска; исходную строку не сохранять.
Сохранять очищенные события как `events.jsonl`, ошибки как `stderr.txt`.
Не делать предварительный raw dump; это сбор evidence конкретной попытки,
а не готовый универсальный приёмочный runner.

Набор вложений определяется подпланом; использовать отдельный `--file` для
каждого входа, не архив или каталог вместо подтверждённо поддержанного формата.
CLI снимает байты пользовательского вложения; текстовый локальный путь в prompt
не заменяет файл. Проверять фактическую admission/delivery и SHA по receipts.
Путь пакета выбирается до запуска, не должен перезаписывать чужой файл.

Не добавлять модели готовые tool calls, граф, формулы решения, ожидаемые числа,
аудитор, историю исправлений или секреты. ТЗ должно однозначно требовать
проверяемое поведение, но оставлять построение модели. Если она решает задачу
обходным путём без проверяемого обработчика, это не приёмка данного узла.
Не включать `--thinking`; скрытые рассуждения не входят в evidence.

Оператор сохраняет код выхода, время старта/финиша и ID процесса рядом с
manifest попытки. Предел времени контролирует владелец запуска: у `run` нет
специального аргумента приёмочного deadline. По истечении отправить SIGINT
**своему** CLI, дождаться его штатного завершения и cleanup. Ожидание cleanup
не продлевает время решения. Принудительное завершение, если понадобилось,
фиксируется как неподтверждённый cleanup, а не PASS. `killall` запрещён.

Исходники интерфейса: `packages/agent/src/cli/cmd/run.ts`,
`packages/agent/src/cli/loginom-management.ts` и
`packages/product/src/cli-profile.ts`. Проверять их при изменении CLI-контракта;
не заменять этот маршрут несуществующей командой `evals/src/run.ts`.

## Наблюдение и продолжение

`events.jsonl` содержит `sessionID`, timestamp, `tool_use`, `text`, `step_finish`
и `error`. Сохранить все завершённые вызовы и реальные исходы; одинаковый wait
не означает повтор мутации. Минутный timeout `dock_node_wait` не означает,
что сама операция закончилась. Не запускать вторую команду управления на
профиле, пока его CLI владеет `.writer`.

При настоящем необходимом уточнении ответить только по данным/бизнес-правилу,
записать точный ответ и отметить участие человека. Техническая подсказка,
ручная настройка узла или готовый вызов переводят попытку в DEBUG_ONLY.
Для нового сообщения в точно известной сессии после завершения её CLI:

```sh
"$NODE_ACCEPTANCE_CLI" run --no-headless --format json \
  --model openai/gpt-5.6-sol --variant low \
  --dir "<та же папка>" --session "<точный sessionID>" \
  -- "<ответ на необходимое уточнение>"
```

Для продолжения использовать тот же отбор и очистку до записи, с отдельными
именами `followup-events.jsonl` и `followup-stderr.txt`.

Это продолжение диалога, а не восстановление старого браузерного контекста.
Перед продолжением сверить receipts и фактическое состояние; runtime новой
CLI-команды может быть новым. Не использовать неоднозначный `--continue`, не
продлевать истёкшую node operation и не повторять неизвестную мутацию.

По умолчанию новый Host использует мягкий режим восстановления: снятие замка
не доказывает, что старая операция не изменила пакет. Старые инструкции о
безусловном `loginom recover --acknowledge` не применять. Strict recovery
существует как явный CLI opt-in и проверяется только когда это требует подплан.
Не удалять журналы или `.writer`, чтобы скрыть исход либо начать следующий тест.

Отдельной команды `history/export` standalone сейчас нет. При необходимости
читать `session`/`message`/`part` из `<profile>/data/loginom-ai-agent.db` только
read-only и только для своей сессии; учитывать актуальную схему. Пример чтения
есть в `packages/loginom-host/script/tui-multichat-acceptance.ts`. В отчёт
переносятся проверенные факты и необходимые публичные сообщения user/assistant
и результаты инструментов. До записи отфильтровать reasoning, system/developer,
секреты и бинарные данные, затем применить redactor. Не копировать базу и не
сохранять все raw parts из неё. Runtime receipts находятся в
`<profile>/loginom/runtime/generations/<generation>/chats/<chat>/attempts/<uuid>`.

## Независимая проверка и результат

После завершения модели разработчик или координатор проверяет результат
**по отдельному oracle подплана**, не доверяя тексту «готово»:

1. Совпали исходные файлы, модель, candidate/source и фактический Loginom build.
2. Исполнен именно проверяемый тип/режим; узлы и связи соответствуют требуемой
   задаче, нет замены вычислением вне Loginom или неподдержанным обходом.
3. Схемы, роли, строки и значения совпали с ожидаемыми результатами; точность и
   полнота чтения достаточны. Для больших результатов выборка не доказывает
   полный набор. Oracle не строится из ответа проверяемой модели.
4. Сохранение подтверждено после последних изменений, путь точный; dirty-state,
   исполнение и независимое переоткрытие проверены по подплану. Для экспортного
   узла также проверены сам выходной файл и его содержимое.
5. Завершены собственные операции и процессы, cleanup имеет доказательство.
   Выход CLI, закрытие Chromium и закрытие пакета/Loginom logout — разные факты.

Применимый узловой аудитор и команда задаются подпланом до готовности к приёмке.
Существующие Python-аудиторы находятся в
`packages/loginom-runtime/tools/loginom-acceptance`; проверить их входы и пути
нового репозитория. `packages/desktop/test/loginom/cold-readback.mjs` — конкретный
CSV/Grouping oracle с ограниченными именами пакетов и Alpha/Beta, **не**
универсальная проверка любого узла. Для другого режима нужен соответствующий
проверочный путь через существующие Dock/runtime scripts.

`runtime-acceptance.ts`, `desktop-oracle.mjs` и `oracle-provider.ts` подают
заранее заданные вызовы и проверяют технический pipeline. Их успех — DEBUG_ONLY
или отдельная регрессия, не автономная Sol-приёмка. `acceptanceCleanupPackage`
существует только у специального managed acceptance старта; обычный CLI run
не принимает этот параметр и не обещает такой receipt. Пакет закрывать только
с проверенным сохранением, точной собственной identity и применимым узловым
проверочным сценарием; чужие сессии не закрывать.

Записать PASS только при полном выполнении критериев подплана. Иначе FAIL —
наблюдаемый дефект, BLOCKED — недоступное обязательное условие, либо DEBUG_ONLY —
вмешательство/скриптовая подстановка. Отдельно фиксировать provider/network,
host/runtime, Loginom, данные и oracle: отказ сети не доказывает дефект узла.
Прошлый PASS на другом SHA сохраняется как историческое доказательство.

Сохранить [completion](../templates/completion.md) и
[checkpoint](../templates/checkpoint.md), передать событие по
[шаблону](../templates/event.json). Освободить CLI-слот только после проверки
завершения своего процесса и принадлежащих ему browser/runtime ресурсов.
Неясность cleanup — ожидание с владельцем и триггером, не разрешение тихо
выполнить следующий прогон. Публикация и изменение общей установки не входят
в эту приёмку.
