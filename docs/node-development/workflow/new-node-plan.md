# Как создать подплан нового узла

Вход: component ID из [реестра](../registry.json), пользовательская задача, требуемые
режимы, версия Loginom и разрешённая среда. Выход: самостоятельный Markdown-подплан
по [шаблону](../templates/node-plan.md), набор маленьких fixtures и спецификация oracle.
Создание подплана не разрешает реализацию, если назначена только подготовка плана.

## 1. Определить объём

Проверить запись [обзора](../inventory.md) и текущий диспетчер runtime. Для готового
обработчика уточнить, исправляется дефект или добавляется режим; не начинать его
повторную разработку по устаревшему подплану. Сохранить прежние номера 03–17,
component ID и runtime type. Новый номер назначать после проверки отсутствия
коллизий; имя каталога — устойчивый slug, номер не используется как ID компонента.
Не превращать место узла в старой очереди в техническую зависимость.

## 2. Исследовать до проектирования

В собственной изолированной среде исследовать живой Loginom штатными Dock-скриптами,
затем сопоставить UI с Help/E2E и актуальным runtime нового repo. Не использовать
Computer Use и не выполнять действия в пользовательском браузере. Фиксировать
версию, component/fulltype, доступность в данной редакции, страницы мастера,
табличные/переменные/деревья портов, изменение схемы и необходимость train/apply.
Наличие узла в палитре не доказывает работоспособность обработчика.

До выдачи на разработку план должен отделять наблюдённое от гипотез. Если стенд,
БД, формат или режим недоступны, результат — `discovery_required` с конкретным
условием продолжения. Нельзя описывать вымышленные controls/API как готовую реализацию.

## 3. Задать контракт и зависимости

Описать бизнес-результат, поддержанные режимы/типы, исключения, входы и выходы,
порядок полей, NULL/пустую строку, точность чисел/дат и семантику изменения числа строк.
Выбрать существующие компоненты `packages/loginom-runtime/client`; расширять
контракт только если имеющегося недостаточно. Указать владельца общего изменения,
принятый SHA зависимости и независимый fixture, позволяющий не ждать соседний узел.
Не добавлять общий интерпретатор сценариев как условие разработки одного узла.

Описать границы configure/execute/read/save, идемпотентность, ошибки до эффекта,
возможный частичный эффект, отмену, допустимое продолжение и проверку фактического
состояния. Автоматическое исправление формулы/агрегации моделью или скриптом без
доказательства исходного намерения не является техническим восстановлением.

## 4. Подготовить доказательства

Составить небольшие явные fixtures и независимо рассчитанные expected. Проверки
должны обнаруживать неверные результаты и связи, а не повторять реализацию.
Выбрать по риску: нормальный случай, пустой вход, NULL/пустые строки, границы типов,
дубликаты/порядок, динамическая схема, неверные параметры и частичное выполнение.
Для trainable-узла добавить сохранение/повторное применение модели и разделение
обучающей/проверочной выборок. Не вводить искусственный train для обычных преобразований.

Бизнес-задание для CLI содержит только задачу, входные файлы и уникальное место
сохранения. Эталон, исходники oracle и ожидаемые значения не помещать в его workspace.
Где нужны допуски/погрешность — задать их до прогона и объяснить причину.

## 5. Сделать план исполнимым

Указать точные точки кода и существующие команды адресных проверок (из каталога
пакета); команды, ещё требующие реализации, обозначить явно. Составить критерии
готовности к ревью, исправлений и [CLI-приёмки](acceptance-cli.md), включая
настройки/связи/выходы/сохранение/независимое повторное открытие. Указать допустимое
время попытки: по умолчанию 30 минут, обоснованное другое значение закрепить в подплане.

Завершить таблицей «требование → проверка → ожидаемый результат → доказательство»
и инструкцией продолжения. Если остались технические решения, которые должен
угадывать разработчик, план ещё не ready. Обычные шаги внутри выданного объёма
не требуют дополнительных согласований; существенное расширение — координатору
или пользователю в single-режиме.

## Сохранение

Рабочий план хранить в `docs/node-development/nodes/<slug>/plan.md`,
карточку с границами и доказательствами — рядом в `README.md`. В карточке
сослаться на план, в плане — на карточку и общий регламент; не копировать
жизненный цикл и команды CLI в каждый узел. Обновить `plan`/ссылку записи реестра.
Перенос или адаптация плана не повышает готовность реализации и не отменяет
прежнюю подтверждённую готовность: новые проверки отмечаются отдельно.
[Пример применения шаблона к Кросс-таблице](../templates/cross-table-plan-example.md)
— документальная проверка, не запуск нового узла и не подтверждение live discovery.
