# Проверка комплекта документации

Снимок: 2026-09-24, исходная ревизия нового клиента
`8b7ea1225d0ed095ea48b8816a6c80b04f0d0cdf`, Dock
`43dad2dbeaa130c5cc264ad560b5da978a4b676a`. Это проверка документации и
согласованности с исходниками. Новые разработки, Loginom UI, модельные прогоны
и повторная аналитическая приёмка обработчиков не выполнялись.

## Воспроизводимые проверки

Из корня нового репозитория, с Python 3.10 или новее:

```sh
python3 docs/node-development/tools/validate.py --render
python3 docs/node-development/tools/validate.py --source-archive "<исходный ZIP>"
python3 docs/node-development/tools/package.py
```

Первый вызов обновляет только [inventory.md](inventory.md) из
[registry.json](registry.json). Второй проверяет каталог, типы текущего runtime,
карточки и подпланы, обязательные поля и доказательства, SHA256 оригиналов и
адаптированных документов, сохранение readiness, JSON и локальные ссылки
рабочей и включённой исторической документации. Третий повторяет проверки,
создаёт новый архив в `~/Backups/loginom-node-development/`, распаковывает его
в отдельный каталог и сравнивает перечень файлов и SHA256. Повторный вызов создаёт
отдельный архив и не перезаписывает прежний.

Исторические ссылки на неперенесённые материалы
не считаются существующими: они перечислены в [каталоге](history/unavailable.json).
Для JSON-доказательств [исходные идентичности](history/references.json) отделены
от текущих путей навигации. Исторический SHA не приписывается новому файлу.
В архиве есть отдельный `external-dependencies.json`. Документы, которые ссылаются
на сайт Help, сервер, отсутствующие raw evidence либо приватные артефакты,
не становятся самодостаточным доказательством live-приёмки после упаковки.

Проверены совпадение каталога с историческим источником, отсутствие дублирующих
component IDs и однозначное соответствие каждого зарегистрированного runtime
type одной карточке. Числовая сводка находится только в формируемом обзоре.
В актуальных границах учтены отличия кода от прежних экспериментальных режимов;
исторические результаты не переписаны.

## Разбор инструкций на контрольных ситуациях

Проверка выполнена чтением регламента и заполнителей журналов; это не запуск
автоматического оркестратора. Сценарии должны оставаться выполнимыми после
изменений [orchestrator.md](workflow/orchestrator.md) и шаблонов.

| Ситуация | Применяемое правило | Проверяемый итог |
| --- | --- | --- |
| Два разработчика одновременно закончили фазу | Сначала занести оба события; затем сверить task/turn/attempt, применить каждый переход один раз | Оба события получили решение; повтор доставки не создаёт второй review |
| Один поток заблокирован | Отдельно `execution_status=blocked`, причина, владелец и следующий триггер; остальные назначения независимы | Общая очередь не останавливается; заблокированный узел не становится принятым |
| Два узла требуют изменения общего контракта | Один владелец изменения, явная зависимость и принятый результат с SHA | Второй агент не правит контракт параллельно; перенос не подразумевает merge в `loginom` |
| Задача прервана либо получен AMBIGUOUS | Сохранить checkpoint, operation/session ID, проверить процесс, receipts и реальный эффект до retry | Не повторяется неизвестная мутация, занятый ресурс не объявляется свободным |
| Переход parallel → sequential | Прекратить новые параллельные назначения; текущим дойти до безопасной точки и сохранить состояние | После освобождения ресурсов работает один разработчик, разрешённая очередь сохраняется |
| Один узел или остановка после текущего | Зафиксировать новую границу кампании; не выдавать следующий узел | Завершение назначенного узла не запускает остаток исторического каталога |
| Два узла готовы к CLI-приёмке | Один lease приёмки; второй ждёт освобождения после подтверждённого cleanup | Не конкурируют браузеры/профили и подписка; код выхода не заменяет аудит |
| Исправления после первого ревью | Один раунд исправлений и адресная проверка; сбой приёмки возвращает к диагностике | Не создаётся автоматическое повторное полное ревью |
| Новый worktree без общей памяти | Подготовка actor-доступа нового проекта с проверкой фактического маршрута | Старый Dock Peer не подставляется; установка старого enrollment не считается допуском |

## Проверка шаблона подплана

[Пример Кросс-таблицы](templates/cross-table-plan-example.md) сопоставлен с
`component.transform.CrossTable` и сохранённым историческим подпланом 15.
В примере есть вход, самостоятельно рассчитанные суммы, границы неизвестного,
зависимости и критерии приёмки. Он явно имеет состояние `discovery_required`:
схема выходных полей, пустые комбинации и доступные операции требуют наблюдения
актуального Loginom. Пример показывает применение шаблона, не разрешает разработку
и не меняет готовность Кросс-таблицы в реестре.

## Границы результата

Общая память нового проекта для будущих worktrees ещё не настроена. CLI-приёмка
по новому регламенту в этой работе не запускалась. Архив — документация и
проверяемые исходные приложения, а не установочный пакет клиента. Коммиты,
слияние, push и публикация не выполнялись.
