# 15. Кросс-таблица: исследование, реализация и приёмка

[Карточка](README.md) · [реестр](../../registry.json) · [создание нового подплана](../../workflow/new-node-plan.md) · [один узел](../../workflow/single-node.md).

Подготовительный статус: **discovery_required**. Текущий runtime не содержит обработчика CrossTable; название будущего runtime type, публичная schema и native bindings ещё не закреплены. План адаптирован из [исторического подплана 15](../../../../services/loginom-ai/docs/plans/loginom-dock/15-cross-table.md). Новых живых наблюдений не было; ни один пункт ниже не выполнен этим документом и readiness не меняется.

## Предметная цель и ограниченный scope

Один `dock_node_apply` должен создать или настроить компонент Кросс-таблица, подключить одну таблицу, выставить роли, факты, колонки и mappings, выполнить и вернуть свежую сводную таблицу. Модель задаёт аналитический смысл; внутренние настройки выполняет локальный обработчик общей оболочки.

Исходный scope для исследования:

- Один или несколько ключей строк, одно дискретное измерение колонок, один или несколько числовых фактов.
- Sum/avg/min/max; число исходных строк — через явно подготовленный числовой факт «Количество» со значением 1. Не переносить семантику SQL COUNT без проверки.
- Фиксированный набор категорий: полный явный список и политика новых/пропущенных значений, включая выбранное поведение «Прочие» и «Пропущенные».
- Скользящие уникальные значения: добавление и исчезновение категорий изменяет выходную схему. Должно сохраняться подтверждённое соответствие категория + факт → выходное поле.
- Пустые пересечения и NULL остаются согласно подтверждённой нативной семантике; нули не подставляются неявно. Предел ширины завершает операцию явным ограничением, без обрезания категорий.

Два режима колонок несовместимы и настраиваются явно. Многомерные колонки, новые агрегаты, управление переменными и автоматическое усечение остаются вне этой задачи. Если исследование требует сузить обязательный scope, согласовать изменение назначения и не закрывать исходный подплан одним статическим снимком.

## Источники и существующая общая основа

В новом репозитории существуют:

- [node-api.mjs](../../../../packages/loginom-runtime/client/lib/node-api.mjs) и [node-apply.mjs](../../../../packages/loginom-runtime/client/lib/node-apply.mjs) — публичная валидация и общий цикл. CrossTable отсутствует в enum; будущая регистрация должна быть согласована во всех слоях.
- [grouping-node.mjs](../../../../packages/loginom-runtime/client/lib/grouping-node.mjs), [grouping-parameters.mjs](../../../../packages/loginom-runtime/client/lib/grouping-parameters.mjs), [grouping-context.mjs](../../../../packages/loginom-runtime/client/lib/grouping-context.mjs) — образец scalar ролей/агрегатов; переиспользовать общие механизмы, но не утверждать, что сводка эквивалентна GroupDataWizard.
- [grouping-parameters.test.mjs](../../../../packages/loginom-runtime/client/test/grouping-parameters.test.mjs), [grouping-output-sources.test.mjs](../../../../packages/loginom-runtime/client/test/grouping-output-sources.test.mjs), [node-api.test.mjs](../../../../packages/loginom-runtime/client/test/node-api.test.mjs) — существующие примеры проверки контракта/связи полей, не тесты готового CrossTable.
- [grouping_output_evidence.py](../../../../packages/loginom-runtime/tools/loginom-acceptance/grouping_output_evidence.py) — пример независимого чтения результатов. Собственные CrossTable fixture/oracle/auditor предстоит разработать; готового entrypoint здесь нет.

Исторические source-root указатели: Help `data/processors/transformation/cross-table.md`; E2E `tests/toreview/acceptance/wizards/cross_table/` — `cross_table_helpers.ts`, `sliding_uniq_values.ts`, `agregation.ts`, `edit_facts.ts`, `move_fields.ts`, `delete_fields.ts`. Они указаны в прежнем подплане; наличие или пропуск E2E не доказывает работоспособность. Получить актуальные версии штатным доступом к источникам и закрепить SHA при выполнении discovery, без догадок о локальном пути и live-версии.

## Что установить исследованием

1. В назначенной изоляции штатными скриптами runtime изучить палитру, input port, мастер ролей, редактор измерения и фактов, переключение режимов, выходной mapping и завершение. Записать только наблюдённые owner identities, доступные параметры и версию Loginom; не переносить старые selectors без проверки.
2. Для каждого режима подтвердить native значения, политику новых/NULL категорий, порядок категорий, имя/метку факта, правила образования технических имён и коллизий. Проверить одинаковые метки и кириллицу.
3. Установить типы всех агрегатов и пустых пересечений, правило all-null, наличие синтетического счётчика и предел ширины полного безопасного чтения. Не назначать непрерывное число колонкой через скрытую смену data_kind.
4. Отдельно воспроизвести смену входа: новая категория и исчезновение прежней. Установить поддержанный способ обновления downstream mapping без потери новых полей. Не копировать `autosync=false` статического отчёта в динамический режим без проверки.
5. Сохранить маленький пакет и заново открыть для проверки обеих конфигураций. Закрепить подтверждённую матрицу scope/ограничений и ожидаемые результаты до автономной попытки.

Выход discovery — проверенная спецификация контракта, UI-переходов, ограничений и oracle. Состояние `discovery_required` снимается по подтверждённым данным, не по существованию этого текста.

## Изменения после discovery

1. Спроектировать ограниченный валидатор параметров: полные роли, список фактов/функций, ровно один column mode, фиксированные категории/политики либо явное принятие изменения схемы. Проверять уникальность identities и выходных имён до мутации. Изменения общего контракта согласовать с оркестратором, который владеет shared files.
2. Добавить handler в существующую регистрацию и публичное описание. Переиспользовать add/find/connect, ожидания, ownership, execution и readback; не создавать второй браузер, сценарный интерпретатор либо модельные UI-клики.
3. Реализовать наблюдение полных списков и связанных редакторов. После Apply проверить функцию каждого факта и режим, включая удаление лишних функций по умолчанию. Existing запрос должен согласованно заменить зависимые настройки при смене режима.
4. Сформировать/проверить полный output mapping. Возвращать наблюдённое соответствие категория + факт → поле и новую schema identity. Не угадывать транслитерацию и не переиспользовать прежний ref категории после изменения данных.
5. Добавить адресные contract/procedure/output/recovery tests и независимый typed oracle. Аудитор читает полный малый результат и source identities, без импорта handler и без записи ожидаемых значений в пакет.
6. Выполнить адресную диагностику и source tests, затем единственный назначенный автономный CLI-проход по [приёмке](../../workflow/acceptance-cli.md). Для следующего автономного повтора после FAIL сначала устранить подтверждённую причину прямой диагностикой.

## Независимые fixtures и ожидаемые инварианты

Fixtures и expected создаются как версионированные материалы до автономного запуска. Каждая строка содержит независимый RowID; пропуски представлены явным NULL-маркером.

| Случай | Данные | Проверка |
| --- | --- | --- |
| Основная сводка | Region/Category/Amount: North,A,10; North,A,20; North,B,5; South,A,7; South,C,11; South,C,NULL. Quantity=1 в каждой строке. | North/A sum=30,avg=15, min=10, max=20, count=2; North/B sum=5, count=1; South/A sum=7, count=1; South/C sum=11, count=2. Count проверяется суммой Quantity; поведение avg/min/max с NULL фиксируется до автономного запуска. |
| Фиксированные колонки | Категории A/B с явно выбранной политикой для C и NULL. | Колонки сохраняют заданный состав; C не теряется: отдельные «Прочие» либо другое явно предусмотренное поведение. Никаких нулей в пустых пересечениях без отдельного решения. |
| Динамические колонки | Первый источник A/B/C; второй заменяет B на D и меняет значения. | После свежего выполнения A/C/D: новая D добавлена, исчезнувшая B удалена согласно подтверждённому режиму, A/C остаются связанными с прежним смыслом. Суммы совпадают с изменённым источником, downstream видит новую схему. |
| Несколько ключей и фактов | Region+Month, Amount+Quantity; календарный Month заранее задан во входе. | Все ячейки вычисляются независимой группировкой по ключам и категории. Дата и время не являются зависимостью разработки этого узла. |
| Неоднозначные имена | Категории A-1/A1, кириллица, одинаковые метки разных фактов, empty/NULL/literal null. | Каждая категория + факт имеет уникальное подтверждённое поле; нет транслитерационного слияния или потери категории. |
| Пустота и ширина | Header-only источник, all-null факт; категории за пределом видимой области и сверх установленного discovery лимита. | Полная схема либо явное объявленное ограничение; нельзя принять обрезанный отчёт за полный. Значения без строк/наблюдений не выдумываются. |
| Редактирование и persistence | Fixed→dynamic→fixed существующего узла, изменение порядка upstream, сохранение и новое открытие. | Нет остатков несовместимого режима; schema/category mapping и значения воспроизводятся без повторной настройки из expected. |

Oracle должен независимо строить сводку по тройке row keys/category/fact и сравнивать все ячейки, типы и полноту соответствий. Представление пустых пересечений и именование колонок связывать с отдельно утверждённой спецификацией, а не копировать из результата проверяемого прогона.

## Негативные случаи

- Неизвестное поле/функция, неверный тип факта, непрерывное измерение без разрешённого режима, повтор категории/имени, одновременно два режима — отказ до мутации.
- Неполное чтение списка категорий, коллизия технических имён, усечение ширины, ложная неизменность схемы после нового источника — отсутствие полного PASS.
- Lost reply после переключения режима, настройки факта, Finish или Execute: сначала сверить тот же owner/режим/квитанцию, без повторного добавления колонки или запуска при неизвестном эффекте.
- Отмена вложенного редактора, Done без Execute, Close, stale ref и changed document: не применять черновик к чужому узлу; исходные данные и посторонний граф не меняются.
- Аудитор обязан отклонять подмену функции, перестановку связи категория→поле, отсутствующую категорию, неправильную NULL-семантику и старый execution, даже если итоговая общая сумма совпала.

## Автономная цель и завершение

Задача CLI: построить месячную сводку продаж по регионам и категориям с суммой и количеством, явно выбрать фиксированный/динамический отчёт и сохранить пакет. Малые отдельные диагностические случаи проверяют изменение категорий и сохранённые настройки; обе заявленные конфигурации должны пройти самостоятельный oracle.

До разработки пройти [жизненный цикл](../../workflow/lifecycle.md). Первая обработка узла выполняется на Astra medium с Goal до готовности изменения к первому ревью, без собственного token_budget. Финальная автономная приёмка — standalone CLI Loginom AI Agent, Sol low и назначенный слот, по общему регламенту. Предоставлять бизнес-цель/входы, не пошаговые инструкции мастера. После сохранения отдельная независимая проверка открывает .lgp и воспроизводит полные выходы.

Передать подтверждённый контракт, новый code SHA, input/oracle/runtime pins, результаты обоих режимов, исходные FAIL и оставшиеся ограничения. Реализация, техническая проверка, аналитика, integration и release фиксируются отдельно. Один статический пример, ручной успех или только source tests не закрывают этот подплан. После выполнения single-задачи новый узел самостоятельно не назначается; слияние требует отдельной команды.
