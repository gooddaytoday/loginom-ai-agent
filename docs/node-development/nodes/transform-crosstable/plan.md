### Этап 2 — агрегаты, типы и несколько измерений (отдельная карточка)

- Native «Количество» и функции по подтверждённой матрице типов (число, строка, Boolean, DateTime, Variant).
- Количество уникальных и пропусков, первый и последний (зависят от порядка входа), стандартное отклонение с делителем из этапа 0.

- Несколько измерений колонок и строк, несколько фактов и функций. Конфигурации без строк или колонок — только подтверждённые.

Формат наборов этапа 1:

- Схема: `RowID`, `Region` и `Category` (строки, дискретные), `Amount` (вещественный: для целого справка разрешает только «Количество»), `Quantity` (=1, тип — по этапу 0).

Пример арифметики: значения `10` и `30` дают сумму 40, минимум 10, максимум 30, среднее 20, сумму Quantity 2. Значения `−5` и `5` дают настоящий ноль, который нельзя спутать с пустым пересечением.

Manifest каждого набора фиксирует байты и SHA256, кодировку, разделитель, кавычки, NULL-маркер, технические имена, метки, типы, виды данных, локаль и порядок строк, если он важен. Ожидаемая структура хранится только в `expected.json` и `oracle.py`; модели она не передаётся.

Независимый oracle:

- не импортирует код обработчика и runtime;
- считает по CSV в разрезе «ключи строк, категория, факт, функция»;
- проверяет все ячейки, размерность, типы и соответствие категорий полям;
- пустое пересечение и all-null считает null, а не 0;
- не использует целые за пределами ±(2^53−1) и не берёт ожидания из результата прогона;
- отклоняет старое исполнение, чужой узел, неверную функцию, потерянное поле, переставленные категории, NULL→0 и совпадение одних итогов.

- Оба сценария смены источника пропущены и проверяют только число колонок `C_n`.
- `CheckPreviewTable` сравнивает только заданный прямоугольник (`bg/helpers/workflow/previewTable.ts:160-202`).
- Агрегатные ожидания — UI-снимки на пакетах 6.5.0-alpha и 7.1.5 (`agregation.ts:29-36`) при пустых строках и колонках. Для 7.4.2 это не oracle.

Задание на бизнес-языке. Прежний `task.md` был пошаговым техническим сценарием с именами инструментов и параметрами; новое задание должно доказать самостоятельную работу.

Нужен отчёт продаж по регионам и категориям: сумма, минимум, максимум и среднее суммы продажи и количество продаж по колонке Quantity. Отчётов два:

- с фиксированным набором категорий, где новые категории попадают в «Прочие», а пропуски — в отдельную колонку;
- динамический, который перестраивает колонки по данным.

После построения модель заменяет данные в источнике файлом `sales-update.csv` и пересчитывает оба отчёта, не меняя их настроек и связей. Она показывает все строки и колонки до и после замены и сохраняет пакет `{{PACKAGE_PATH}}`.

Указывается формат данных, включая `?` как пропуск. Запрещены runtime type, имена инструментов, значения enum, ожидаемые числа и сведения об oracle.

Требования к входам:

- оба CSV больше 1 KiB (W2), например 50–60 строк;
- в обновлённом файле одна категория исчезает, одна появляется, NULL-категория остаётся, значения меняются;
- отчёты — не больше 5 строк-регионов и около 26 колонок, чтобы таблица целиком укладывалась в умолчания и 46 000 байт;
- значения подобраны с точно представимыми средними.

### Приёмка исполнителя

```sh

~/.local/share/loginom-multica/scripts/accept-node.sh --worktree "$PWD" \

  --node transform-crosstable --cli "$PWD/.multica-node/current/bin/loginom-ai-agent-cli" \
  --out "$PWD/.multica-node/attempts/<новая-попытка>"
node scripts/node-acceptance/crosstable-transcript-audit.mjs \
  "$PWD/.multica-node/attempts/<попытка>/evidence/events.jsonl"
```

Модельный прогон засчитывается только через `accept-node.sh`. Ручной запуск CLI — диагностика.

Обвязка выполняет:

- профиль с каналом из манифеста и каталогом моделей;
- `loginom setup` из конфига роли;
- `run --no-headless --format json --model openai/gpt-6.1-sol --variant low` с пределом 7200 с;
- освобождение собственных сессий;
- `cold-check.mjs` из checkout;
- отредактированные `events.jsonl` и `stderr.txt`, `evidence/result.json`.

PASS исполнителя требует одновременно:

- PASS `accept.py`: `cli_exit=0`, `oracle_exit=0`, oracle PASS, нет timeout, `package_closed=true`, `logged_out=true`;
- PASS аудита протокола;
- PASS адресной матрицы.

Код выхода 0 сам по себе ничего не доказывает: ошибки `loginom_*` на него не влияют (`packages/agent/AGENTS.md:161`).

При сбое сначала прочитать `result.json`, `events.jsonl` и `stderr.txt` и сверить SHA клиента, исходников и обвязки.

- `CLI_SETUP_FAILED` — проблема подготовки соединения.
- `UND_ERR_CONNECT_TIMEOUT` к `mcp.loginom.ai` — сетевой путь (LAB-7), а не узел.
- После устранения причины — новая попытка и новый профиль под той же парой аккаунтов и тем же SHA. Изменённый код — новый SHA и новая полная приёмка. Oracle не ослаблять, неизменный неуспешный запуск не повторять.

### Публикация и независимая приёмка

1. Исполнитель публикует чистый SHA: `LOGINOM_NODE_WORKFLOW=cli git -c core.hooksPath=.husky push`. Затем создаёт PR в ветку задания и публикует доказательства: `scripts/publish-evidence.py` с комментарием. В комментарий входят result, отредактированные события и stderr, результат oracle и cleanup, результат аудита. Профили, клиент, сырые журналы и секреты не публикуются. После проверки receipt — статус Review и упоминание Ловца: точный SHA, PR, подплан, результат.
2. Ловец берёт точный опубликованный SHA, собирает своего кандидата и проводит `accept-node.sh` с `reviewer.json` под другим аккаунтом. Затем запускает аудит протокола своей попытки и проверяет PR, доказательства и критерии подплана.
3. При PASS Ловец публикует доказательства, проверяет receipt и скачанное содержимое и ставит Done.
4. При дефекте Ловец публикует конкретные замечания с SHA, ставит In progress и передаёт исполнителю. Исправление даёт новый SHA и повторную приёмку. После второго отрицательного вердикта — Blocked и эскалация владельцу через Генератора.
5. Done означает принятие результата карточки. Merge и релиз выполняет владелец.

### Отражение результатов

- Адресная матрица, приёмка исполнителя и приёмка Ловца отражаются раздельно; W1–W3 — отдельными пунктами.
- Принятый объём — только политики колонок и функции, прошедшие матрицу и обе приёмки. Если подтвердилась одна политика, вторая отклоняется обработчиком до мутации и записывается в `limitations`.
- Слои реестра обновляются в PR по доказательствам; `integration` и `release` не трогаются.

### Негативные случаи

- Неизвестное поле/функция, неверный тип факта, непрерывное измерение без разрешённого режима, повтор категории/имени, одновременно два режима — отказ до мутации.
- Неполное чтение списка категорий, коллизия технических имён, усечение ширины, ложная неизменность схемы после нового источника — отсутствие полного PASS.
- Lost reply после переключения режима, настройки факта, Finish или Execute: сначала сверить тот же owner/режим/квитанцию, без повторного добавления колонки или запуска при неизвестном эффекте.
- Отмена вложенного редактора, Done без Execute, Close, stale ref и changed document: не применять черновик к чужому узлу; исходные данные и посторонний граф не меняются.
- Аудитор обязан отклонять подмену функции, перестановку связи категория→поле, отсутствующую категорию, неправильную NULL-семантику и старый execution, даже если итоговая общая сумма совпала.
