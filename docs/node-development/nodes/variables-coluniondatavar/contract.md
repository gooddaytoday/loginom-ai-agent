# Контракт этапа 1 — предложение

LAB-838, база `v040@5d3860bfd542c44a2875ae61d03dab6ecdb64ec6`.
Критерии предлагаются для утверждения до назначения реализации. Здесь нет
регистрации обработчика или изменений общего W1.

## Идентичность и границы

Component ID `component.variables.ColunionDataVar`, runtime type
`variables.column_union`, режим `append_variables`. Только два исходных
входа variables 0/1, выход variables 0; табличных портов нет. Родной
`Input_Add` виден, но не используется. Служебные порты не считать данными.

Новый узел: два разных источника одного подготовленного workflow;
`variable_inputs` с `kind:variables`, input 0/1 и фактическим output каждого
источника из inventory W1. Контрольный порт вместо обычного variables
отвергается. Не переносить имена/GUID/operation IDs из другого документа.
Для existing при повторном выполнении `variable_inputs:[]` сохраняет связи
согласно W1; для нового отсутствие одного из двух входов — объяснимый отказ
до мутации. Необязательность native портов не расширяет срез обработчика.

Настройки [карточки типа](node-card-proposal.json): `parameters:{}` либо
`column_union.mapping:"automatic"`. Поле строковое, enum из одного значения.
В новом узле сохраняется native автоматическая синхронизация и полное
соответствие выхода. Existing пустой patch не сбрасывает настройки;
существующее ручное соответствие, третий вход или неподдержанный тип
отвергаются до мутации с причиной. Не удалять такие настройки автоматически.

## Семантика

Конкатенация наборов: все переменные входа 0 в исходном порядке, затем
входа 1. Не соединение по ключам и не добавление строк таблицы.
В fixture 6 + 6 = 12 переменных. Метки, исходные типы и значения сохраняются.
При совпадении технического имени native создаёт уникальное: числовое
окончание увеличивается, для имени без цифр добавляется `_1`.
Выделение последовательное: a0 слева, затем a0/a1 справа → a0/a1/a2.
Совпавшие метки остаются одинаковыми. Обработчик читает фактические имена,
а не подставляет вычисленные имена вместо native readback.
Регистр, Unicode-коллизии и ведущие нули в суффиксе не проверены; их
не включать в утверждаемый набор коллизий этого этапа.

Простые типы `integer|real|string|boolean`; NULL сохраняет объявленный тип.
NULL не равен отсутствующей переменной, пустой строке, false либо 0.
Типов не выводить из отображаемого текста и не преобразовывать. Верхняя
граница — 128 переменных суммарно по границе reader W1, не лимит Loginom.
При превышении — отказ до мутации, без обрезания результата.
Целые приёмочного комплекта безопасны для IEEE754: `abs(v) <= 2^53-1`.
Неподтверждённая точность больших Int64 — отказ, не округление.

Строки/boolean/integer/NULL, имена, метки, типы, число и порядок — точно.
Вещественные: `abs(actual-expected) <= max(1e-12,1e-12*abs(expected))`;
NaN/Infinity отвергаются. Это допуск сравнения, не округление результата.
Наблюдены 0.125 и 0.1 в typed store, даже если DOM показывает меньше знаков.

Execute вычисляет текущие входы; train и отдельного apply обученной модели
нет. После patch правого a0 с 29 на 41 повторное выполнение без настройки
соединения меняет только выходной a1; a0=11, a2=37 сохраняются.
Save — отдельная операция после чтения.

## Компактное подтверждение

Переиспользовать выданные W1 NodeRef и typed endpoints, schema/value envelope
и freshness нового выполнения. Не добавлять свою квитанцию или origin-proof.
Configuration readback: `mode`, `mapping:automatic`, число входов, две
фактические связи и упорядоченное соответствие `input/source_name/output_name`;
метки/типы/значения — в единственном полном output.variable_ports[0].
Проверить ID каждого порта и native reciprocal edge через W1. Не повторять
полную схему, справку или все значения в configuration readback.
Пустой или неподключённый набор не выдавать за NULL-переменную.

## Что нужно сверх W1

W1 владеет `variable_inputs` kinds, портами/связями/ownership, scalar reader,
read.variable_ports и typed cold. Их повторная реализация не нужна.
Узлу нужны только аддитивная регистрация, свой обработчик lifecycle
`DerivedVariablesMappingEngineOutputPortWizard` → `DoneWizard`, проверка
поддержанного automatic mapping и компактный узловой readback, раздел навыка
и сценарий run-check. Динамические входы W2 не нужны.
Real должен приходить через принятый typed scalar envelope W1; узел его
только сохраняет, новый codec/преобразование типов не предлагается.
Если фактический W1 не покрывает real или output mapping lifecycle, этап 1
сначала фиксирует пробел и запрашивает решение, не расширяет общий контракт.

В базе нет собственного обработчика и typed cold W1, поэтому комплект —
проект ожиданий, а не запускаемый stock-сценарий. Этап 1 добавляет scenario
`variables-column-union` в существующий run-check после W1; модели передавать
только task и inputs.json. Oracle/expected/manifest модели не передаются.
Для источников подготовлен собственный `fixtures/source.lgp` только с двумя
Калькуляторами и исходными значениями; перед каждым прогоном загружать свежую
копию по acceptance/README. Чтение и patch значений источника используют
принятый W1 и обработчик Калькулятора; JavaScript fallback не нужен.

## Предлагаемые критерии и оценка

1. Два fixed inputs → 12 переменных, полный порядок, типы, метки и значения
   [expected.json](acceptance/expected.json), числовые и обычные коллизии.
2. После изменения источника только a1 меняется 29→41, связи/порядок/остальное
   неизменны; повторное чтение нового выполнения без перенастройки соединения.
3. Save → новый профиль → open/Execute без повторной настройки: полный
   updated набор на native variables output 0, настройки и обе связи;
   `package_closed=true`, `logged_out=true`. Typed cold W1 обязателен.
4. Неверный kind/owner/port, третий input, custom mapping и unsupported types
   дают адресный отказ до мутации. Нет маскирования через таблицу.
5. Обязательные проверки изменённых путей; ≥2/3 PASS исполнителя и 2/3
   независимой проверки на том же опубликованном SHA по регламенту.

Утверждение критериев — условие назначения этапа 1; `ready_for_development`
обозначает готовый исследовательский комплект, не разрешение менять W1.
После принятого W1: **1–2 цикла** (регистрация/lifecycle/live, затем
readback/cold/регрессия по наблюдённому отказу), независимая приёмка отдельно.
Новые общие механизмы, публичный Host/Agent контракт, budgets/deadline,
новые преобразования типов и W2 не предлагаются.
