# Предложение приёмки двух наборов

Утвердить [контракт](../contract.md) и критерии до реализации. На базе нет
зарегистрированного обработчика и typed cold W1. Комплект не является stock
сценарием run-check и не заявляет модельный PASS.

## Входной пакет

`../fixtures/source.lgp` — штатно сохранённый Loginom 7.4.2 пакет размером
несколько КБ: два Калькулятора переменных с константами и служебный узел
сценария. Соединения, готового результата, пользовательских переменных
пакета, внешних ссылок, JavaScript и связей нет. По шесть переменных в каждом
источнике. Входные значения, порядок и типы заданы в `inputs.json`.
Manifest фиксирует байты, SHA256 и исходные node IDs/выходы. GUID порта
сам по себе не глобальный идентификатор: он одинаков у обоих источников;
всегда нужны NodeRef + kind + ordinal.

До каждого будущего прогона оператор загружает через Files → Upload свежую
копию source.lgp **в каталог своей роли назначенной пары**, под новым именем
пакета сценария. Предыдущие попытки не заменять. Для предлагаемого сценария
`variables-column-union` путь —
`<package_directory>/<out.name>-variables-column-union.lgp`.
Прямая передача модели приватного пути source.lgp или импорт LGD не нужны.
Независимая проверка загружает свою копию под своим аккаунтом.

В контекст модели — только `task.md` и `fixtures/inputs.json` как входное
вложение. Oracle, expected и manifest остаются у проверяющего.
Исходные числа в inputs — данные пользователя; в task нет выходных имён,
результатов oracle, названий инструментов или технического плана решения.

## Oracle и ожидания

```sh
python3 docs/node-development/nodes/variables-coluniondatavar/acceptance/oracle.py
python3 docs/node-development/nodes/variables-coluniondatavar/acceptance/oracle.py --check
```

Первый вызов пишет expected.json; `--check` сверяет его и входной бинарный
fixture с JSON/manifest. Используется только Python stdlib: последовательное
выделение уникальных имён и конкатенация входов, без runtime или Loginom.
XML читается только для контроля **входа**, не для определения результата.
Нет новых общих механизмов проверки.

Результат на native variables output 0: 12 элементов, `ordered:true`, типы
и значения каждого; в updated выходной a1=41 вместо 29, остальные прежние.
Integer/boolean/string/NULL точны; для real `abs=1e-12,rel=1e-12`, правило
сравнения — в контракте. Пустая строка, отсутствующая переменная и NULL
не взаимозаменяемы. Свободную метку узла сопоставлять через `label_any`;
метки переменных фиксированы входными данными и проверяются точно.

Expected — **проект данных для W1**, не совместимый с табличным matcher базы
без принятого typed variable пути. CSV здесь не предлагается: таблица или
CSV не заменяют проверку исходного порта переменных. Save/cold/cleanup
проверяются отдельно от oracle арифметики и имён.

## Этап 1

После W1 в существующий run-check добавить только запись
`variables-column-union`: task из этого каталога, входное вложение inputs.json,
заранее загруженная копия пакета, ожидания initial/updated, typed cold updated.
Структуру записи согласовать с принятым W1; не подавать весь этот каталог
как `data`, чтобы expected/oracle не попали в контекст модели.

Штатный `run-check start`, затем `wait` одним foreground-вызовом; модель
`openai/gpt-6.1-sol`, medium, 1800 с и регламент нагрузки сквада. На одном
SHA ≥2/3 PASS исполнителя, typed cold PASS и независимые 2/3 по назначению.
Открытие/повторное Execute в новом профиле не восстанавливает настройки.
Обязательны обе реальные связи, полный updated выход и cleanup true/true.
Упавший пакет/профиль не переиспользовать. До этапа 1 эти прогоны не запускались.
