## 2. Этапы

### Этап 0 — перепроверка принятого объёма

Подготовка: проверить SHA, собрать кандидата из закоммиченных исходников, получить `loginom status` = `ready` на назначенном стенде.

1. Собрать `acceptance/` из прежнего контракта (раздел 3): независимые ожидания и значения сохранить; транспорт, pins и receipts прежнего формата не переносить. Прежний launcher Hermes не запускать.
2. Адресные тесты `client/test/duplicates-*.test.mjs` (3 файлов), затем весь `client/test`: `bun run test:upstream` в `packages/loginom-runtime`.
3. CLI-сценарий и независимое холодное открытие по RUNBOOK; generic cold-check и адресные дополнения — в разделах 3–4.
4. При расхождении — живая сверка мастера с `?testable=true`; прочитать причину из кнопки ошибки, записать в `discovery.md`; наблюдение не подменять E2E-снимком.
5. Исправить дефект с адресным тестом; правка общего кода — минимальная и только под наблюдённый отказ сценария; расширение объёма — вопрос владельцу.

Выход: PASS исполнителя и независимая приёмка того же SHA; `client_technical_validation` и `analytical_validation` отражаются только по новому результату.

### Адресные действия при FAIL

1. Подтвердить семантику ролей и служебных полей для действующего scope на целевой версии; проверить, что разметка включает все экземпляры повторной записи.
2. В resolveDuplicatesParameters валидировать полную схему, непересекающиеся роли и отсутствие конфликтов служебных имён/меток до назначения usage.
3. Настроить полные роли полей; неперечисленные поля оставить вне сравнения. Не скрывать выбор первой строки или фильтрацию внутри handler.
4. Прочитать весь малый output и сравнить по уникальному RowID. Проверить принадлежность к группам как отношение эквивалентности, не требуя конкретных номеров без основания.
5. Поддержать сохранение роли и исходной схемы после reopen. Адаптируя аудит, сохранить проверки identity import, не удаляя неудобные события из журнала.

### Этап 1 и далее — непокрытые режимы Help 7.4 (отдельные карточки владельца)

- Boolean/real/datetime, NULL, пустые строки, несколько входных/выходных и отсутствие выходных полей.
- Смена ролей, empty/singleton, номера групп с 1 и сохранение исходных полей.
- Уточнить применимость роли для variable и способ сравнения неоднородных ячеек; неподдержанное явно зафиксировать.

Перечень будущей полноты сохраняет прежний подплан: частично принятые действия перепроверяются на этапе 0, дополнительные controls/типы/режимы назначаются отдельно; совпавшее название режима не расширяет scope.

## 3. Данные и независимые проверки

Комплект `nodes/duplicates/acceptance/` собирает будущая карточка:

- `task.md` на бизнес-языке с `{{PACKAGE_PATH}}`; без имён инструментов и ожидаемых чисел;
- `data/Node12-main10.csv` и остальные указанные ниже CSV — точные копии прежних входов; только входы передаются модели; положительные наборы и header-only — из duplicates_test_fixtures.py;
- `expected.json` из независимого `oracle.py` до прогона; адресные наборы — `fixtures/` с manifest (байты, SHA, формат, типы, порядок).

Прежние входы: `fixtures/duplicates/Node12-main10.csv`: 136 байт, 10 записей, колонки `Id, Key, Sub, Value, Amount`, разделитель `;`; `fixtures/duplicates/Node12-null8.csv`: 81 байт, 8 записей, колонки `Id, Key, Value`, разделитель `;`; кодировка UTF-8, NULL-маркер `__NULL__`. Размеры и SHA сохранить в manifest до прогона.

Ожидания прежнего контракта: Из `duplicates_oracle.py`: проверить флаги всех копий, состав групп как отношение эквивалентности, неизменные исходные строки. Служебные поля `Duplicate, DuplicateGroup, Contradiction, ContradictionGroup`; непомеченный номер группы — NULL, помеченный — положительный integer. Номера группы не фиксируют бизнес-идентичность.

Матрица сохранена из прежнего подплана; ожидания и неоднозначные правила переподтвердить до модельного прогона:

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| Группы | RowID 1..6; Key=A,A,B,B,C,C; Value=x,x,y,z,w,w; плюс уникальный RowID=7/Key=D/Value=q. | A/C имеют повторные полные записи, B — разные Value при одном Key, D уникален. Независимо проверить все флаги и эквивалентность групп для каждой строки. |
| NULL только в Value | Для отдельных ключей значения NULL,NULL; empty,empty; literal null,literal null; NULL и empty. | Не сливать разные представления. Ожидаемые группы/флаги взять из независимого duplicates_oracle и проверить полнотой всех RowID. |
| Только ключ | output_fields пуст, повторные Key и исходное неучаствующее поле с различными значениями. | Разметка следует выбранным ролям; неучаствующие значения и все строки сохранены. |
| Редактирование/пустота | Поменять набор input/output ролей; header-only вход; отдельный save/reopen. | Служебная схема остаётся полной; новая роль влияет только на семантику групп, а не состав исходных строк. |

Oracle не импортирует handler/runtime, рассчитывает по исходным байтам, сверяет все ячейки и схему, отличает NULL/пустую строку/0, отвергает неполное чтение.

Cold-check: схема проверяется позиционно (имена, метки, типы), строки — как мультимножество, до 100 строк/выход и 32 выходов (`scripts/node-acceptance/expected-outputs.mjs:14,29-39,72-81`). Числа сравниваются точно (`cold-check.mjs:232`); большие Int64 — десятичные строки. Каждый ожидаемый выход однозначно связан с типом и меткой узла. E2E-снимки мастера не являются oracle.

Числовые номера групп могут измениться после reopen; отдельный независимый аудит сравнивает группы по составу RowID. Cold-check сравнивает числа точно: до прогона переподтвердить детерминированность нумерации на fixture; не снимать её проверку и не подгонять expected по текущему output.

Свежесть результата обеспечивает сам cold-check: он заново выполняет узлы сохранённого пакета в новом профиле. Отдельные доказательства происхождения, квитанции и receipts не требуются. Порядок строк, несколько портов одного узла, допуск для вещественных и выход переменных в cold-check добавляет общая карточка LAB-78 (ветка `acceptance-tools`); в ветке узла эти возможности не реализуются.

### Предложение приёмки

`acceptance/task-typed-keys.md`, `task-empty.md`, `task-singleton.md` и три CSV

У основного fixture ровно по одной группе дубликатов и противоречий: предложен

полную схему, singleton с NULL-ключом получает false/NULL, а не группу.
