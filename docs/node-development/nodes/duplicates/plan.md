# 12. Дубликаты и противоречия: подплан сопровождения и приёмки

[Карточка и принятые границы](README.md) · [реестр](../../registry.json) · [работа с одним узлом](../../workflow/single-node.md).

Обработчик `research.duplicates` уже реализован в режиме `mark`. Этот подплан адаптирует исторический 12 к текущему runtime и standalone CLI: это маршрут адресного исправления, проверки переноса или отдельно назначенного расширения, не повторная разработка с нуля. Историческое принятие сохраняется в своём scope; технические Desktop проверки не являются аналитической CLI-приёмкой. Новых живых наблюдений и прогонов при составлении документа не было, readiness не повышается.

До начала выбрать точное изменение и пройти [подготовку/жизненный цикл](../../workflow/lifecycle.md). Разработчик работает в Astra medium в своей задаче, ветке и worktree. Первичная разработка получает Goal до готовности изменения к первому ревью, без собственного token_budget. Этот документ не назначает следующий узел и не разрешает слияние.

## Узловые требования

Режим mark размечает исходные строки; не удаляет дубли и не выбирает «лучшую» запись. Явные непересекающиеся input_fields/output_fields задают поля ключа и сравниваемых значений, остальные остаются без роли. Mapping overrides запрещены; все исходные колонки сохраняются.

Выход добавляет Duplicate, DuplicateGroup, Contradiction, ContradictionGroup. Validator принимает scalar-типы, но исторически приняты integer/string и NULL/empty/literal null в Value. Boolean/real/datetime и NULL keys не считать принятыми автоматически: расширение требует отдельного scope. Номера групп не являются стабильным бизнес-идентификатором.

## Шаги изменения

1. Подтвердить семантику ролей и служебных полей для действующего scope на целевой версии; проверить, что разметка включает все экземпляры повторной записи.
2. В resolveDuplicatesParameters валидировать полную схему, непересекающиеся роли и отсутствие конфликтов служебных имён/меток до назначения usage.
3. Настроить полные роли полей; неперечисленные поля оставить вне сравнения. Не скрывать выбор первой строки или фильтрацию внутри handler.
4. Прочитать весь малый output и сравнить по уникальному RowID. Проверить принадлежность к группам как отношение эквивалентности, не требуя конкретных номеров без основания.
5. Поддержать сохранение роли и исходной схемы после reopen. Адаптируя аудит, сохранить проверки identity import, не удаляя неудобные события из журнала.

## Независимые fixtures и oracle

Ниже — обязательная узловая матрица для объявленного полного scope. При адресном исправлении выбрать затронутые строки и обосновать выбор; расширение режима добавляет новые строки. До автономной попытки сохранить входы и expected отдельно от handler, с версиями и SHA. Ожидания не вычислять импортом реализации и не подгонять по её приёмочному выводу.

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| Группы | RowID 1..6; Key=A,A,B,B,C,C; Value=x,x,y,z,w,w; плюс уникальный RowID=7/Key=D/Value=q. | A/C имеют повторные полные записи, B — разные Value при одном Key, D уникален. Независимо проверить все флаги и эквивалентность групп для каждой строки. |
| NULL только в Value | Для отдельных ключей значения NULL,NULL; empty,empty; literal null,literal null; NULL и empty. | Не сливать разные представления. Ожидаемые группы/флаги взять из независимого duplicates_oracle и проверить полнотой всех RowID. |
| Только ключ | output_fields пуст, повторные Key и исходное неучаствующее поле с различными значениями. | Разметка следует выбранным ролям; неучаствующие значения и все строки сохранены. |
| Редактирование/пустота | Поменять набор input/output ролей; header-only вход; отдельный save/reopen. | Служебная схема остаётся полной; новая роль влияет только на семантику групп, а не состав исходных строк. |

## Негативные случаи

- Пересечение/дубли ролей, пустой список ключей, неизвестное поле, конфликт имени/метки служебных колонок, mappings: отказ до настройки.
- Непринятые типы/NULL keys не выдавать за покрытые по одному успешному запуску; отдельная диагностика и oracle обязательны при расширении.
- Аудит отвергает удаление повторной строки, неверную принадлежность группе, флаг только у второй копии и старый output; номера групп сравнивает семантически.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.

## Автономная проверка и передача

Разметить повторные и противоречивые записи по согласованным ключам и значениям, сохранить все исходные строки и пакет, независимо объяснить каждую полученную группу.

Первичная отладка — штатными скриптами текущего runtime в назначенной изоляции. После неё выполнить адресные source tests и проверить независимый oracle, включая его отказ на подменённых значениях/схеме/идентичности. Только затем подготовить неизменный candidate и получить слот по [CLI-регламенту](../../workflow/acceptance-cli.md): standalone CLI Loginom AI Agent, Sol low, согласованная подписка, бизнес-цель и входные файлы без пошаговых UI-команд.

Критерий аналитического PASS — полный малый output/артефакт, проверенная схема и настройки, новый execution и сохранённый пакет, которые независимо воспроизводятся после отдельного открытия. Configure-only и Close проверяются отдельно; обычный продуктовый путь не переоткрывает мастер ради повторной проверки. Непроверенные платформы, большие наборы и дополнительные режимы остаются явно ограниченными.

Передать checkpoint с точными source/runtime/client/model/platform pins, заявленным scope, результатами и неизменёнными исходными FAIL. Техническое завершение, аналитическая проверка, integration и release — отдельные состояния реестра. Один этап ревью и один раунд исправлений выполняются по общему жизненному циклу; этот подплан не добавляет повторного полного ревью.
