Оркестрация — Multica, сквад «Обработчики узлов»: Генератор тасок готовит назначение, Тест-Манки #1 перепроверяет и исправляет, Ловец Галюцинаций независимо принимает опубликованный SHA.

Карточка:

```text

Узел: union
Обработать узел по его подплану до независимой приёмки. Объём — этап 0 подплана (перепроверка).
```

В ветке задания должны быть RUNBOOK, этот подплан, `scripts/node-acceptance/cold-check.mjs` и сборка `--no-archive`. При отсутствии передать проблему Генератору, сохранив in_progress.

### Объём назначения

Разрешено: собрать `acceptance/` из прежнего oracle; выполнить адресные тесты, CLI и независимую приёмку; при расхождении сверить мастер штатными средствами runtime; исправить дефекты в `union-*.mjs` и их тестах в принятом объёме; подготовить PR и доказательства.

Не разрешено: merge и релиз; следующие этапы; изменение общей оболочки (`calculator-node.mjs`, `node-read-*`, `workspace-ui.mjs`, `node-procedure.mjs`, `collapse-native-*`) или `cold-check.mjs` без согласования Генератора в рамках исходной цели; несогласованное изменение конфигураций обвязки. Технические настройки запуска согласует Генератор.

Общие исправления в исходной цели согласует Генератор и назначает одного исполнителя в существующей карточке; изменение критериев или публичных контрактов остаётся за владельцем.

### Препятствия и эскалация

Порядок — [координация сквада](../../../testing/loginom-ai-agent/multica-mas.md). Обычные ошибки исполнитель исправляет сам; вопросы о пределах технического исправления решает Генератор. При неизвестном исходе остановить опасные действия и сохранить попытку, но продолжить анализ через Генератора. Критерии приёмки ниже не меняются.

## 2. Этапы

### Этап 0 — перепроверка принятого объёма

Подготовка: проверить SHA, собрать кандидата из закоммиченных исходников, получить `loginom status` = `ready` на назначенном стенде.

1. Собрать `acceptance/` из прежнего контракта (раздел 3): независимые ожидания, значения, freshness и отказы сохранить; адаптировать транспорт, pins и receipts к CLI. Прежний launcher Hermes не запускать.
2. Адресные тесты `client/test/union-*.test.mjs` (6 файлов), затем весь `client/test`: `bun run test:upstream` в `packages/loginom-runtime`.
3. CLI-сценарий и независимое холодное открытие по RUNBOOK; generic cold-check и адресные дополнения — в разделах 3–4.
4. При расхождении — живая сверка мастера с `?testable=true`; прочитать причину из кнопки ошибки, записать в `discovery.md`; наблюдение не подменять E2E-снимком.
5. Исправить дефект в принятом объёме с адресным тестом; общую оболочку или расширение объёма передать Генератору; расширение цели и критериев согласует владелец.

Выход: PASS исполнителя и независимая приёмка того же SHA; `client_technical_validation` и `analytical_validation` отражаются только по новому результату.

### Адресные действия при FAIL

1. Зафиксировать порядок и полные схемы всех источников. В resolveUnionTables проверить каждое поле и требуемую общую схему до изменения UI.
2. При необходимости добавить ровно недостающие Input_Add порты, каждый раз проверяя graph diff и владельца. Номер UI-порта после reopen не считать прежней identity.
3. Проверить привязку всех входов, заменить неверные автоматические соответствия явными mappings. Несопоставленные поля отразить в выходе с согласованными префиксами.
4. Сверить полный output mapping и отсутствие коллизий; выполнить с графа после всех мастеров, без дополнительного открытия узла в нормальном пути.
5. Независимый аудитор связывает каждый input digest, динамический порт и mapping с полным мультимножеством результата. Добавление третьего входа existing не должно создавать второй узел.

### Этап 1 и далее — непокрытые режимы Help 7.4 (отдельные карточки владельца)

- Два шага name+type→label+type; fallback совместимого свободного поля при отдельном выборе.
- Связать все/удалить все, фильтр свободных полей, sort представления, несвязанные поля и префиксы.
- Автоматическая/пользовательская метка и Markdown описание.

Перечень будущей полноты сохраняет прежний подплан: частично принятые действия перепроверяются на этапе 0, дополнительные controls/типы/режимы назначаются отдельно; совпавшее название режима не расширяет scope.

## 3. Данные и независимые проверки

Комплект `nodes/union/acceptance/` собирает будущая карточка:

- `task.md` на бизнес-языке с `{{PACKAGE_PATH}}`; без имён инструментов и ожидаемых чисел;
- `data/main.csv` и остальные указанные ниже CSV — точные копии прежних входов; только входы передаются модели;
- `expected.json` из независимого `oracle.py` до прогона; адресные наборы — `fixtures/` с manifest (байты, SHA, формат, типы, порядок).

Прежние входы: `fixtures/union/main.csv`: 51 байт, 3 записей, колонки `Code, Amount, Note`, разделитель `;`; `fixtures/union/second.csv`: 35 байт, 2 записей, колонки `Memo, Value, Key`, разделитель `;`; `fixtures/union/third.csv`: 55 байт, 2 записей, колонки `Item, Total, Text, Extra`, разделитель `;`; кодировка UTF-8, NULL-маркер `NULL`. Размеры и SHA сохранить в manifest до прогона.

Ожидания прежнего контракта: Из `union_oracle.py` и `fixtures/union/expected.json`: после двух входов 5 строк и 3 копии A; после третьего — 7 строк и 4 копии A. Выход `Code, Amount, Note, Extra`; Extra — отдельное поле, NULL у других источников. Сохраняются все повторения.

Матрица сохранена из прежнего подплана; ожидания и неоднозначные правила переподтвердить до модельного прогона:

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| Два/три входа | A: ID1,2,2; B: ID2,3; C: ID4. Значения строки ID2 одинаковы. | После A+B — 5 строк, ID2 встречается 3 раза; после добавления C — 6 строк. Считать кратности независимо. |
| Явный mapping | Во втором CSV колонки переставлены и переименованы; есть Extra с main:null. | Полное совпадение типов и значений общей схемы, отдельный Extra с ожидаемыми NULL у других источников; отсутствие неявной потери столбца. |
| Пустой и широкий вход | Один header-only CSV и один с NULL/empty; вариант 8 входов и широких таблиц. | Число строк равно сумме входов; NULL/empty различимы. Для 15 входов нужна самостоятельная проверка, не вывод из validator. |
| Сохранение | Изменить mapping и префикс в existing, сохранить, заново открыть и выполнить. | Все динамические порты, связи, порядок входов и типы восстановлены; сравнение результата по мультимножеству без необещанного порядка. |

Oracle не импортирует handler/runtime, рассчитывает по исходным байтам, сверяет все ячейки и схему, отличает NULL/пустую строку/0, отвергает чужой узел, старое исполнение, неполное чтение и подмену данных. Freshness, происхождение и настройки доказываются отдельно от правильных значений.

Cold-check: схема проверяется позиционно (имена, метки, типы), строки — как мультимножество, до 100 строк/выход и 32 выходов (`scripts/node-acceptance/expected-outputs.mjs:14,29-39,72-81`). Числа сравниваются точно (`cold-check.mjs:232`); большие Int64 — десятичные строки. Каждый ожидаемый выход однозначно связан с типом и меткой узла. E2E-снимки мастера не являются oracle.

## 5. Ловушки — переподтвердить, не копировать

- Несовместимые типы, неполное fields, повторный target, пропущенный номер порта, незаданный источник: отказ без автоконверсии.
- Коллизии несопоставленных имён, main:null скрыт без явного output exclusion, чужой вход: аудит/валидация должны отвергать.
- Потеря ответа Input_Add/connect/Execute, отмена после создания порта: сверить фактическое наличие, не создавать второй порт при неизвестном эффекте.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.
- Исторический аудит 10: Input_Add создаёт динамический порт, номер после reopen не заменяет identity. Исторически проверены 8 входов; validator на 15 не доказывает 15 живых связей.
- Приёмки текущего CLI нет; неподтверждено: граница 15 входов, динамические порты и полный mapping текущего CLI. Исторические замеры/локаль/платформа не являются гарантией текущего стенда.
