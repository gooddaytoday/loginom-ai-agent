# 10. Объединение: подплан сопровождения и приёмки

[Карточка и принятые границы](README.md) · [реестр](../../registry.json) · [работа с одним узлом](../../workflow/single-node.md).

Обработчик `transform.union_data` уже реализован в режиме `append_all`. Этот подплан адаптирует исторический 10 к текущему runtime и standalone CLI: это маршрут адресного исправления, проверки переноса или отдельно назначенного расширения, не повторная разработка с нуля. Историческое принятие сохраняется в своём scope; технические Desktop проверки не являются аналитической CLI-приёмкой. Новых живых наблюдений и прогонов при составлении документа не было, readiness не повышается.

До начала выбрать точное изменение и пройти [подготовку/жизненный цикл](../../workflow/lifecycle.md). Разработчик работает в Astra medium в своей задаче, ветке и worktree. Первичная разработка получает Goal до готовности изменения к первому ревью, без собственного token_budget. Этот документ не назначает следующий узел и не разрешает слияние.

## Узловые требования

Append_all объединяет строки 2–15 входов с сохранением дублей. Вход 0 — главная таблица, дополнительные таблицы перечислены по портам 1..N без пропусков. Для каждого поля каждого дополнительного входа требуется явное main либо null; совпадающие поля имеют одинаковые типы.

main:null означает отдельный выходной столбец, а не автоматическое исключение данных. Префиксы name/label заданы явно; коллизии требуют явного исправления. Полный output mapping может исключить поле по запросу. Историческая проверка 8 входов не доказывает live-проверку всех 15.

## Шаги изменения

1. Зафиксировать порядок и полные схемы всех источников. В resolveUnionTables проверить каждое поле и требуемую общую схему до изменения UI.
2. При необходимости добавить ровно недостающие Input_Add порты, каждый раз проверяя graph diff и владельца. Номер UI-порта после reopen не считать прежней identity.
3. Проверить привязку всех входов, заменить неверные автоматические соответствия явными mappings. Несопоставленные поля отразить в выходе с согласованными префиксами.
4. Сверить полный output mapping и отсутствие коллизий; выполнить с графа после всех мастеров, без дополнительного открытия узла в нормальном пути.
5. Независимый аудитор связывает каждый input digest, динамический порт и mapping с полным мультимножеством результата. Добавление третьего входа existing не должно создавать второй узел.

## Независимые fixtures и oracle

Ниже — обязательная узловая матрица для объявленного полного scope. При адресном исправлении выбрать затронутые строки и обосновать выбор; расширение режима добавляет новые строки. До автономной попытки сохранить входы и expected отдельно от handler, с версиями и SHA. Ожидания не вычислять импортом реализации и не подгонять по её приёмочному выводу.

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| Два/три входа | A: ID1,2,2; B: ID2,3; C: ID4. Значения строки ID2 одинаковы. | После A+B — 5 строк, ID2 встречается 3 раза; после добавления C — 6 строк. Считать кратности независимо. |
| Явный mapping | Во втором CSV колонки переставлены и переименованы; есть Extra с main:null. | Полное совпадение типов и значений общей схемы, отдельный Extra с ожидаемыми NULL у других источников; отсутствие неявной потери столбца. |
| Пустой и широкий вход | Один header-only CSV и один с NULL/empty; вариант 8 входов и широких таблиц. | Число строк равно сумме входов; NULL/empty различимы. Для 15 входов нужна самостоятельная проверка, не вывод из validator. |
| Сохранение | Изменить mapping и префикс в existing, сохранить, заново открыть и выполнить. | Все динамические порты, связи, порядок входов и типы восстановлены; сравнение результата по мультимножеству без необещанного порядка. |

## Негативные случаи

- Несовместимые типы, неполное fields, повторный target, пропущенный номер порта, незаданный источник: отказ без автоконверсии.
- Коллизии несопоставленных имён, main:null скрыт без явного output exclusion, чужой вход: аудит/валидация должны отвергать.
- Потеря ответа Input_Add/connect/Execute, отмена после создания порта: сверить фактическое наличие, не создавать второй порт при неизвестном эффекте.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.

## Автономная проверка и передача

Объединить три предоставленные таблицы с разными именами/порядком полей в согласованную схему, сохранить все повторы и явно несопоставленные столбцы, затем сохранить пакет.

Первичная отладка — штатными скриптами текущего runtime в назначенной изоляции. После неё выполнить адресные source tests и проверить независимый oracle, включая его отказ на подменённых значениях/схеме/идентичности. Только затем подготовить неизменный candidate и получить слот по [CLI-регламенту](../../workflow/acceptance-cli.md): standalone CLI Loginom AI Agent, Sol low, согласованная подписка, бизнес-цель и входные файлы без пошаговых UI-команд.

Критерий аналитического PASS — полный малый output/артефакт, проверенная схема и настройки, новый execution и сохранённый пакет, которые независимо воспроизводятся после отдельного открытия. Configure-only и Close проверяются отдельно; обычный продуктовый путь не переоткрывает мастер ради повторной проверки. Непроверенные платформы, большие наборы и дополнительные режимы остаются явно ограниченными.

Передать checkpoint с точными source/runtime/client/model/platform pins, заявленным scope, результатами и неизменёнными исходными FAIL. Техническое завершение, аналитическая проверка, integration и release — отдельные состояния реестра. Один этап ревью и один раунд исправлений выполняются по общему жизненному циклу; этот подплан не добавляет повторного полного ревью.
