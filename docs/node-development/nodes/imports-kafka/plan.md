## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Checkout/SHA и сборка из закоммиченных исходников, `loginom status` = `ready`; квалифицировать внешнюю среду отдельно. Каждый отказ мастера читать из кнопки ошибки.

1. Палитру «Импорт > Kafka», edition/license, корень мастера, подключение/переменные и табличный выход.
2. Topic/group.id/client.id, лимит и timeout одного сообщения; умолчания, последнюю неполную пачку.
3. Имена/метки/типы полей сообщений, ключа, partition/offset и timestamp; schema до/после Execute.
4. Пять типов offset, когда group commit меняется; порядок только в каждой партиции.
5. Повтор того же узла после нового producer input, пустой topic, ACL/неверное свойство Consumer; частичный consume, отмену/потерю ответа.

Результат — `discovery.md`: observed/hypothesis, exact значения/типы/имена, границы источника и side effects, решения по W. Выход — `ready_for_development` только после снятия блокеров; закреплённые type/mode, `fixtures/` и `acceptance/` до кода обработчика.

Неподдержанные формат/порт/режим/тип/параметр отклоняются до мутации с понятным объяснением исправления.

## 3. Данные и независимые проверки

Комплект `nodes/imports-kafka/acceptance/` (для следующих этапов `acceptance/stageN/`): `task.md` с `{{PACKAGE_PATH}}`, `data/` только для входов модели, `expected.json` из независимого `oracle.py` до обработчика. Внешние manifests, oracle и ожидания модели не передаются; секреты — только во внешнем окружении.

CSV-спецификации: UTF-8, разделитель `,`, decimal `.`, header, NULL-маркер `\N`; empty string отличается от NULL. `fixtures/manifest.json`: фактические байты/SHA256, типы/метки/порядок и происхождение каждого бинарного файла/внешнего объекта; размер фиксируется при генерации, а не угадывается.

| Набор | Содержание и назначение |
|---|---|
| `messages.csv / producer-manifest.json` | Id,Partition,Key,Payload: две партиции × три сообщения с уникальными ключами/номерами; независимый producer фиксирует фактические bytes и offsets. |
| `offsets-before.json / offsets-after.json` | Admin-клиент фиксирует позиции группы; эталонный consumer читает без изменения группы под проверкой. Лимит основного case — 4 сообщения. |
| `empty-topic / replace.csv` | Своя пустая очередь для timeout без строк; новые Id/payload на том же узле, исходная позиция задаётся manifest. |

Правило producer fixture: для Partition p=0,1 и j=0..2 создать Id=3p+j+1, Key=`p:j`, Payload=`Привет:p:j`; admin/producer фиксируют фактический offset, а не предполагают, что он равен j. Дополнительный аудит проверяет порядок внутри каждой партиции.

Oracle не импортирует handler/runtime, считает по входам, сверяет все ячейки/объекты/байты, имена/метки/типы/порядок полей, NULL/empty/0. Отклоняет старое исполнение, чужой destination/узел и подмену данных; E2E preview/обратный импорт не является независимым эталоном.

Для табличного выхода cold-check сверяет имена/метки/типы и порядок колонок, строки без учёта порядка (`expected-outputs.mjs:14,29-39`), до 100 строк/выход и 32 выходов. Числа точны (`cold-check.mjs:232`); использовать точно представимые значения или отдельно согласованный допуск до прогона. Метаданные видов/назначений и порядок строк требуют отдельного аудита. Выходы связываются по type/label с уникальным node_id (`expected-outputs.mjs:72-81`), port index отсутствует: переменные статуса не покрыты.

## 4. Проверки, приёмка и завершение

Непроведённая проверка — `not_checked`; ожидания/границы фиксируются до модельного прогона.

| Требование / проверка | Независимое условие успеха |
|---|---|
| `imports-kafka:r01` | При лимите 4 прочитано ровно 4 доступных сообщения; пустой топик завершается по timeout без вымышленных строк. Проверить реальные ключи/значения/metadata. |
| `imports-kafka:r02` | Для каждой партиции заранее записать offsets; сверить фактические message IDs и конечные offsets новым клиентом, не только row count. |
| `imports-kafka:r03` | Менять одно допустимое свойство и topic через переменную; неверное свойство/ACL даёт отказ. Конфликт wizard и дополнительного свойства — discovery. |
| `imports-kafka:r04` | Повтор не обязан вернуть прежние строки: expected определяется сохранённой позицией группы. Проверить отсутствие повторного потребления после lost reply. |
| Контракт и отказы | Неверные настройки/типы отклонены до эффекта; исходная ошибка мастера сохранена |
| Изменение существующего | Настройки/связи readback подтверждены; новый источник не даёт старый результат; незапрошенные свойства сохранены |
| Persistence | Сохранить после всех чтений; открыть новым профилем без восстановления настроек; внешние эффекты и происхождение проверить по согласованному W |
| Recovery | Потерянный ответ не повторяет неизвестный эффект; результат сверяется независимо перед продолжением |
| Регрессия | Адресные тесты нового узла и полный `client/test`; прежние контракты не ослаблены |

Задание модели: Прочитать ограниченную порцию сообщений из выделенной очереди, показать содержимое и положение чтения, проверить результат и сохранить пакет в {{PACKAGE_PATH}}.

PASS исполнителя: CLI и применимый cold-check/согласованный независимый аудит результата, адресная матрица, `package_closed=true`, `logged_out=true`. Файловый/внешний/переменный результат нельзя объявить принятым неподходящим oracle. Публикация и Ловец принимают тот же чистый SHA по RUNBOOK; `integration` и `release` не меняются.

## 5. Ловушки — переподтвердить, не копировать

Ниже документальные ограничения и требования прежнего черновика; точные controls и runtime-семантика для стенда остаются гипотезами до этапа 0.

Подключение Kafka + необязательные управляющие переменные → таблица сообщений. Чтение может изменять сохранённые offsets группы; схему выходных полей выяснить в discovery.

Подключение Kafka: PLAINTEXT, SASL_Plaintext, SSL, SASL_SSL; SASL PLAIN/SCRAM-SHA-256/SCRAM-SHA-512. Каждый доступный профиль проверяется отдельно; секреты поступают из окружения и не сохраняются в evidence.

В изолированном топике 2 партиции, в каждой 3 сообщения с уникальными ключами и порядковыми номерами. Независимый producer готовит байты; эталонный consumer читает без изменения группы под проверкой. Начальные group offsets фиксируются административным клиентом.

Не сбрасывать offsets общей группы. Отмена и потеря ответа требуют независимой сверки offsets; слепой retry может пропустить сообщения или прочитать другой набор.
