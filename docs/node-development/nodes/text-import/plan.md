# 03. Текстовый импорт: подплан сопровождения и приёмки

[Карточка и принятые границы](README.md) · [реестр](../../registry.json) · [работа с одним узлом](../../workflow/single-node.md).

Обработчик `imports.text` уже реализован в режиме `delimited`. Этот подплан адаптирует исторический 03 к текущему runtime и standalone CLI: это маршрут адресного исправления, проверки переноса или отдельно назначенного расширения, не повторная разработка с нуля. Историческое принятие сохраняется в своём scope; технические Desktop проверки не являются аналитической CLI-приёмкой. Новых живых наблюдений и прогонов при составлении документа не было, readiness не повышается.

До начала выбрать точное изменение и пройти [подготовку/жизненный цикл](../../workflow/lifecycle.md). Разработчик работает в Astra medium в своей задаче, ветке и worktree. Первичная разработка получает Goal до готовности изменения к первому ревью, без собственного token_budget. Этот документ не назначает следующий узел и не разрешает слияние.

## Узловые требования

Источник должен поступить через подтверждённый артефакт текущей сессии: совпадение storage path не доказывает совпадение файла. Параметры задают источник, кодировку, пропуск строк, заголовок, разделитель, кавычки, десятичный разделитель и NULL-маркер. Настроить все поля, их типы, виды, использование, технические имена и метки.

Текущий полный путь поддерживает 1–1000 явно настроенных полей; старый draft-reader на восемь видимых полей не задаёт лимит полного обработчика. Однако прежняя проверка настройки 1000 полей не доказывает полное точное чтение и сохранение такой ширины. ASCII используется для технического имени; кириллица сохраняется в source_name/label. Имя источника разрешается только однозначным совпадением наблюдённого имени или метки, без транслитерации и привязки по позиции.

## Шаги изменения

1. Проверить admission файла и native источник на закреплённой версии: owner, encoding, rows_to_skip, first_line_as_title; отделить ошибку доставки от ошибки CSV-парсера.
2. Изменять binding/patch в text-import-parameters и адресное чтение import-definition-pages. При смене парсера сопоставить старую и новую схемы по подтверждённым именам; для появившихся полей требовать полный набор свойств.
3. Применить формат до настройки столбцов; проверить всю полную схему страницами, затем выходной mapping. Для editor recovery сохранить связь с тем же полем/свойством; исчезнувший или чужой редактор не выбирать по похожей метке.
4. Сохранить различие нового импорта, patch существующего и повторного выполнения сохранённой конфигурации. После известного binding refusal закрывать только собственный черновик с подтверждённым cleanup; при неизвестном эффекте не создавать второй узел.
5. Связать output с новым execution и исходными байтами. Отдельно проверить сохранённый source path/format/columns после открытия .lgp; не вставлять данные напрямую в результат вместо исполнения Loginom.

## Независимые fixtures и oracle

Ниже — обязательная узловая матрица для объявленного полного scope. При адресном исправлении выбрать затронутые строки и обосновать выбор; расширение режима добавляет новые строки. До автономной попытки сохранить входы и expected отдельно от handler, с версиями и SHA. Ожидания не вычислять импортом реализации и не подгонять по её приёмочному выводу.

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| CSV с разделителями | 5 строк: кириллица; значение с «;» внутри кавычек; удвоенная кавычка; перенос внутри строкового поля; пустая строка и отдельный NULL-маркер. | Независимый CSV parser читает зафиксированные исходные байты. Сравнить все строки, различение NULL/empty и SHA входа; число физических строк файла не считать числом записей. |
| Типы и точность | Поля ID, Amount, Active, EventAt, Label; integer за безопасной границей JavaScript хранить в oracle как десятичный текст, real с >2 знаками, datetime с секундами. | Типы, метки, порядок и каждое значение; не принимать форматированный экранный округлённый текст за точный результат. |
| Смена источника | Второй CSV меняет порядок A/B, добавляет C; header-only вариант сохраняет схему без строк. | Неизменённые имена сохраняют свои настройки; новое C требует явных свойств. Пустой результат имеет полную ожидаемую схему. |
| Ширина | Отдельные 40 и 1000 полей; изменение последнего невидимого поля. | Проверить конфигурационную полноту отдельно от полноты output/persistence; незавершённый широкий прогон не обозначать полным PASS. |

## Негативные случаи

- Чужой artifact/session, неизвестный verified ID, неверный digest, исчезнувший файл: отказ без подмены локальным путём.
- Повторные или неоднозначные заголовки, кириллическое техническое имя, неописанное новое поле после смены парсера: отсутствие угадывания и частичного успеха.
- Скрытый/неверный owner поля, смена document или execution во время чтения, потеря ответа Execute: никаких повторных запусков по старому результату.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.

## Автономная проверка и передача

Импортировать предоставленный CSV со всеми указанными типами и метками, затем заменить его вторым согласованным источником в том же узле и сохранить пакет. Независимо проверить каждый выход и воспроизведение сохранённых настроек.

Первичная отладка — штатными скриптами текущего runtime в назначенной изоляции. После неё выполнить адресные source tests и проверить независимый oracle, включая его отказ на подменённых значениях/схеме/идентичности. Только затем подготовить неизменный candidate и получить слот по [CLI-регламенту](../../workflow/acceptance-cli.md): standalone CLI Loginom AI Agent, Sol low, согласованная подписка, бизнес-цель и входные файлы без пошаговых UI-команд.

Критерий аналитического PASS — полный малый output/артефакт, проверенная схема и настройки, новый execution и сохранённый пакет, которые независимо воспроизводятся после отдельного открытия. Configure-only и Close проверяются отдельно; обычный продуктовый путь не переоткрывает мастер ради повторной проверки. Непроверенные платформы, большие наборы и дополнительные режимы остаются явно ограниченными.

Передать checkpoint с точными source/runtime/client/model/platform pins, заявленным scope, результатами и неизменёнными исходными FAIL. Техническое завершение, аналитическая проверка, integration и release — отдельные состояния реестра. Один этап ревью и один раунд исправлений выполняются по общему жизненному циклу; этот подплан не добавляет повторного полного ревью.
