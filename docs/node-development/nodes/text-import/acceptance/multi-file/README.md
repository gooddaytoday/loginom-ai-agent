# Приёмочный комплект: несколько текстовых файлов

**Предложение этапа 0, ожидает утверждения владельцем.** Runtime базы этот режим
не поддерживает. Здесь нет регистрации сценария, нового runner или изменения
общей верификации. Модельная приёмка: NOT_RUN.

- [Маска](../task-multi-file.md): один каталог, `sales_*.csv`, последовательная обработка, FileName.
- [Явный список](../task-multi-file-list.md): февраль, затем январь, тот же выход.
- [Исходные байты](../../fixtures/multi-file/README.md).
- [Независимый oracle](../oracle-multi-file.py), [его проверки](../test-oracle-multi-file.py).
- [expected.json](expected.json): пять записей, один output 0 узла imports.text.
- [expected-new-month.json](expected-new-month.json): шесть записей после отдельной доставки марта.

Модели передаются только бизнес-задание и три первичных CSV. Oracle, expected,
диагностические варианты и мартовская выгрузка при первом выполнении не передаются.
Нужно сохранить исходные basename при доставке: маска `sales_*.csv` не должна
подменяться маской случайных имён с префиксом digest. Каталог — отдельный внутри
назначенной пары. Утверждённый набор текущих файлов фиксируется до прогона.

Все имена, типы, порядок полей, каждое значение, NULL/пустой текст и кратности
проверяются; метки, не заданные пользователем, — через `label_any`. Порядок строк
свободный (`ordered:false`): порядок перечисления маски нативно не сортирован.
Ожидаемая последовательность списка проверяется чтением настройки; наблюдение
порядка строк не превращается в гарантию планировщика.

Для ручной проверки oracle из корня репозитория:

```sh
python3 -B docs/node-development/nodes/text-import/acceptance/oracle-multi-file.py --check-expected docs/node-development/nodes/text-import/acceptance/multi-file/expected.json
python3 -B docs/node-development/nodes/text-import/acceptance/oracle-multi-file.py --include-new-month --check-expected docs/node-development/nodes/text-import/acceptance/multi-file/expected-new-month.json
python3 -B docs/node-development/nodes/text-import/acceptance/test-oracle-multi-file.py
```

Дополнительный `--csv <скачанный CSV>` проверяет экспорт с `;` и явным маркером
NULL `\N`. Это отдельная проверка исходных значений; штатный runner после
утверждения по-прежнему проверяет свой CSV, Save, cold и cleanup. В `expected.json`
маркер не зафиксирован: stock использует явный маркер соответствующего экспорта.
Нельзя выдавать совпадение экранного округлённого текста за точный CSV PASS.

После утверждения — использовать существующий `run-check start`, затем `wait`
одной командой, точный SHA, новую основу/профиль для каждой попытки. До реализации
и регистрации multi-file сценария команда с вымышленным именем не приводится.
Для положительного сценария требуется ≥2/3 PASS исполнителя и независимые 2/3
на том же SHA, cold пакета, полный набор затронутых пакетов. Cold Export — только
с реально скачанным `--csv`. Oracle не передаётся модели.

Два холодных опыта различаются: обычный cold сравнивает неизменные пять строк;
после контролируемого добавления марта отдельный опыт сравнивает шесть строк
без изменения мастера. Добавление файла — подготовка испытания, не восстановление
настроек из expected. Список после добавления марта должен остаться прежним.
FileTime пока диагностический: независимого эталона серверной точности времени
этот комплект не задаёт. Подробная матрица и границы — [multi-file.md](../../multi-file.md).
