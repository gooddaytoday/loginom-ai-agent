### Порты, таблица и сохранение

Импорт имеет `Input_Connection-0`, `Input_Var-1` и `Output_Data-0`;
экспорт — `Input_Connection-0`, `Input_Data-1`, `Input_Var-2`, без табличного
выхода. У файловых узлов переменный вход имеет subtype **3**, не скрытый
subtype 4. В W1 это `variable_inputs.kind="variables", input=0`; у экспорта
табличный input также имеет отдельный публичный ordinal 0. Нативные суффиксы
1/2 нельзя переносить в эти ordinal. Новый переключатель меняет редактор поля;
он не создаёт новый выход или новую схему таблицы. При одинаковом файле,
формате и колонках импорт даёт ту же таблицу; экспорт остаётся файловым выходом.

В штатно скачанном пакете полная привязка сохраняется у каждого Component:

```xml
<PropBinder>
  <PropertyBindSavers>
    <Item Name="FileName.Engine.Root." PropertyPath="FileName.Engine.Root."
          VariableName="FileCsv"/>
  </PropertyBindSavers>
</PropBinder>
```

`Engine/@FileName` при этом тоже содержит строку пути. Она не доказывает режим:
при переключении в VariableControl скрытая ValueControl ещё показывала старый
шаблон (`:32`). Нужно читать активный режим, точное имя переменной, mapping
входа и актуальное значение. XML — доказательство сериализации, не способ записи.

Шаблон `%ReportDate%` — **другой механизм**: он введён в ValueControl,
`Engine.FileName` сохраняет строку с `%ReportDate%`; у этого импорта в промежуточном
скачанном пакете нет соответствующего FileName PropertyBindSaver. Подстановка
внутри пути подтверждена для ASCII имени ReportDate. Кириллическое имя,
несколько/вложенные подстановки, экранирование `%`, неизвестное имя и NULL внутри
шаблона не проверены. Автометка `%FileCsv%` сама по себе не доказывает шаблон.
В первый срез предлагается только полный путь из одной переменной; дату и путь
пользователь вычисляет в Калькуляторе переменных. Шаблоны остаются отдельным
расширением, несмотря на наличие native UI.

## Предлагаемые границы и критерии владельцу

Предлагается сохранить `mode=delimited` и добавить только необязательный
`parameters.file_name_variable={kind:"variable",name:"InputFile"}` либо ReportFile.
Его отсутствие оставляет прежний literal-контракт. Это проект публичного
добавления, не разрешение менять контракт сейчас.

`settings.source.source_path` импорта и `destination` экспорта остаются явным
**свидетелем текущего разрешённого пути** операции. Значение наблюдённой
строковой переменной обязано совпасть с ним. Writer переключает поле на
переменную, а не фиксирует в нём строковую копию. При следующей дате меняется
источник значений и свидетель операции, но сохраняется binding и node_id.
Для import по-прежнему требуется подтверждённый файл текущей операции, для
export — прежняя проверка конфликта и явная политика overwrite.

Для первого среза источник — уже выполненный Калькулятор переменных W1,
один однозначный строковый output. Native discovery использует встроенный
источник пользователя; это не обещание автоматически расширить все ограничения
W1 для builtin. Фактическую доступность прямого builtin→file handler нужно
принимать отдельно. Техническое имя берётся из observed mapping, не из caption.

1. **Два запуска.** На одном SHA один импорт и один экспорт, два значения даты;
   тот же node_id и binding; оба результата и оба скачанных CSV совпадают
   с независимым oracle по всем полям/строкам. Первый файл остаётся прежним.
2. **Сохранение.** Save, новая сессия/профиль, исходный сохранённый пакет;
   прочитать source values, W1 links/mapping, оба FileName binding и формат;
   выполнить сохранённые узлы без повторной настройки. Cold Export — только
   со скачанным CSV через штатный `--csv`. Не считать потерей binding отсутствие
   ещё не активированной схемы переменного источника.
3. **Разрешённый путь до эффекта.** Перед create/link/mapping/wizard/Execute
   получить типизированное текущее значение из подтверждённого W1 output и
   пропустить его через существующую storage policy: inputs для импорта,
   exports для экспорта. Не выводить разрешённую папку из username. Проверка
   `root + '/'`, а не общего строкового префикса. Конфликт файла — reject,
   replace только с явным разрешённым witness destination каждой операции.
4. **Отказы.** NULL, пустое/пробельное значение, не строка, неизвестная либо
   неоднозначная переменная, относительный путь, `..`, backslash, URL, маска,
   `%`, control chars, sibling-папка и путь вне выбранной папки → отказ до
   мутации. Без fallback на сохранённый FileName, автоматического приведения
   NULL к строке, обхода «Всё равно далее» и изменения пути ради успеха.
   Отрицательный путь нельзя проверять реальным доступом к чужой папке.
5. **Текущее значение.** До finish/Execute повторно сверить source execution,
   тип, значение, mapping и разрешённый путь. Изменение/недоступность source
   после preflight → отказ; после неизвестного эффекта не повторять запись.
   Холодный запуск сначала выполняет переменный источник, проверяет путь,
   затем допускает файловую операцию. Формулы, меняющие путь при каждом
   неявном перевыполнении upstream, в этот срез не входят.

Пункты 3–5 — предложение применения существующих правил source identity,
путей, отказа до мутации и неизвестного эффекта к новому binding. Native UI
сам такой гарантии не даёт: пустые/NULL значения обнаружены уже внутри мастера,
есть продолжение после ошибки. Отсутствие побочных эффектов должен доказывать
production preflight red→green и журнал этапа 1, а не этот документ.

## Приёмочный комплект и нарезка

Задания на языке пользователя: `acceptance/task-file-variable-import.md`,
`acceptance/task-file-variable-export.md`, общий срез —
`acceptance/task-file-variable.md`. Входы — два маленьких CSV в
`fixtures/file-variable/`; схема и порядок совпадают, количество строк и значения
различаются, есть кириллица, кавычка CSV для запятой, 0, отрицательное число
и пустая строка. Пустое Item не является пустым именем файла.

Независимый `acceptance/file-variable/oracle.py` использует только Python csv,
исходные байты и int; `expected.json` вычислен до будущих прогонов. Верхний
outputs описывает финальный импорт; секция `file_variable_proposal` хранит обе
стадии и отрицательные случаи. Это **не зарегистрированный run-check scenario**
и не новый механизм верификации. На этапе 1 нужны каталог/привязка к существующему
runner, последовательные стадии и штатные CSV/Save/cold/cleanup проверки.
Oracle и expected модели не передаются; только task и исходные CSV.
`canonical_export_bytes` — размер независимой канонической сериализации,
не требование идентичного native quoting при совпадении таблиц.

| Пакет работ v0.4.1 | Циклы реализация → проверки → живой сценарий | Оценка diff без тестов и generated snapshots |

Цикл 1: минимальный guarded read/write FileName, resolved witness и отказы,
один импорт и один экспорт до живого сценария. Цикл 2: смена даты/сохранение/
cold/скачанные файлы. Цикл 3 — резерв на наблюдённый отказ, не отдельная
архитектура. Независимая проверка 2/3 на том же SHA — отдельно; общие требования
сквада, модель и deadline не меняются. Циклы здесь не означают узел «Цикл».

Адресные файлы: `text-import-node.mjs`, `text-import-procedure.mjs`,
`text-export-node.mjs`, `text-export-parameters.mjs`, `text-export-procedure.mjs`,
`text-export-context.mjs`, `text-export-output.mjs`. Import source proof и
Export artifact destination должны сравниваться с разрешённым актуальным
значением, а не со старым literal. Потребуется аддитивное чтение активного
редактора в `workspace-ui.mjs`, параметр/описание в `node-api.mjs`, точный
readback в `node-result-schema.mjs` и сохранение связи W1; старые поля не удалять.

Общий код уже содержит `storagePath`, `requireStorageDestination`,
`requireExportDestination` (`storage-policy.mjs`), W1 variable refs/links/mapping
и источники точных значений. Для двух узлов нужен общий по смыслу property
binding; сначала использовать существующие guards и адресные hooks, без
нового универсального фреймворка. Если гарантия до мутации требует неаддитивной
правки W1, host/agent или публичного контракта сверх утверждённого добавления,
остановить этап 1 и вынести один вопрос владельцу. W1 в эту docs-ветку не перенесён.

Проверки этапа 1 по фактическим путям определяет `required-checks.py`;
ожидаются полный client suite с pinned Chromium под nice, schema-budget,
acceptance-tests при изменении runner, run-check start+wait, CSV/Save/cold и
независимая приёмка. Изменения runtime/src дополнительно требуют host bun test.
Сейчас применимы только docs/fixture/oracle проверки; их результаты — в PR.

Проект полных карточек и замеры бюджетов: [file-variable/budgets.md](acceptance/file-variable/budgets.md).
Прежде чем менять handler, владелец утверждает именно этот ограниченный
полный путь и предложенные критерии. Отдельные даты, новые форматы, Excel,
HTTP/REST и подстановки `%Name%` не принимаются этим этапом 0.
