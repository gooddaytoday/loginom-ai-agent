# 09. Слияние: подплан сопровождения и приёмки

[Карточка и принятые границы](README.md) · [реестр](../../registry.json) · [работа с одним узлом](../../workflow/single-node.md).

Обработчик `transform.join_data` уже реализован в режиме `inner`, `left`. Этот подплан адаптирует исторический 09 к текущему runtime и standalone CLI: это маршрут адресного исправления, проверки переноса или отдельно назначенного расширения, не повторная разработка с нуля. Историческое принятие сохраняется в своём scope; технические Desktop проверки не являются аналитической CLI-приёмкой. Новых живых наблюдений и прогонов при составлении документа не было, readiness не повышается.

До начала выбрать точное изменение и пройти [подготовку/жизненный цикл](../../workflow/lifecycle.md). Разработчик работает в Astra medium в своей задаче, ветке и worktree. Первичная разработка получает Goal до готовности изменения к первому ревью, без собственного token_budget. Этот документ не назначает следующий узел и не разрешает слияние.

## Узловые требования

Два табличных входа: 0 левый, 1 правый. Только inner/left; явные пары ключей, case_sensitive и include_joined_keys. Типы ключей должны совпадать; преобразование выбирается отдельным узлом. Повторяющиеся ключи сохраняют все пары совпадений.

Пустой parameters для existing допустим только при сохранении прежних входов и input mappings. Общие имена/метки не являются идентичностью поля. Нет right/full/cross либо соединения по номеру строки. Порядок результата без отдельной Сортировки не гарантирован.

## Шаги изменения

1. Проверить обе схемы и source versions до настройки. Выписать роль каждого входа и эффективные имена после input mapping; не менять left/right для удобства редактора.
2. В resolveJoinKeys проверить каждую пару и одинаковые типы. Для нового узла обязательны оба источника; для смены источников existing требовать полный набор ключей и опций.
3. Настроить режим и весь набор связей ключей, затем прочитать каждую пару. Открытие правой таблицы или одна нарисованная линия не доказывают целый составной ключ.
4. Согласовать include_joined_keys и выходной mapping; проверить collisions/исключения и поля обоих источников, включая поля за пределом видимой области.
5. Независимо проверить кратность и заполнение правых полей NULL для left без пары. После сохранения сверить обе входные связи и повторить из сохранённых настроек.

## Независимые fixtures и oracle

Ниже — обязательная узловая матрица для объявленного полного scope. При адресном исправлении выбрать затронутые строки и обосновать выбор; расширение режима добавляет новые строки. До автономной попытки сохранить входы и expected отдельно от handler, с версиями и SHA. Ожидания не вычислять импортом реализации и не подгонять по её приёмочному выводу.

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| Многие ко многим | Слева (LID,K)=(1,A),(2,A),(3,B); справа (RID,K)=(10,A),(11,A). | Inner даёт пары (1,10),(1,11),(2,10),(2,11); left дополнительно (3, NULL). Сравнивать мультимножество, не порядок. |
| Составной ключ | K+Date: часть строк совпадает только по K; отдельный вариант A/a с обоими флагами регистра. | Пары рассчитывать независимо по полному ключу. Включение правых ключей меняет схему, но не множество соответствий. |
| NULL и пустота | NULL key, пустая строка, текст null; пустой правый/левый вход. | Правило NULL-ключей закрепить отдельно по целевой семантике Loginom, не копировать SQL NULL. Проверить полные схемы пустых выходов. |
| Wide и existing | 40 полей с каждой стороны, сходные метки; изменить ключ/режим существующего узла. | Ни одно поле не теряется при прокрутке; новая связь и режим сохраняются после отдельного reopen, посторонние связи не затронуты. |

## Негативные случаи

- Разные типы ключей, неизвестное имя, повтор поля в парах, чужой port/workflow, коллизия output: предсказуемый отказ до незапрошенного изменения.
- Потеря ответа после создания связи либо Execute: не проводить связь/запуск повторно при неизвестном эффекте.
- Аудит отклоняет переставленные входы, потерянное совпадение, ошибочную кратность, старую схему после upstream change и неполное чтение.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.

## Автономная проверка и передача

Соединить операции с деталями по согласованным ключам, получить внутренний и левый варианты без потери повторных совпадений, сохранить и независимо проверить пакет.

Первичная отладка — штатными скриптами текущего runtime в назначенной изоляции. После неё выполнить адресные source tests и проверить независимый oracle, включая его отказ на подменённых значениях/схеме/идентичности. Только затем подготовить неизменный candidate и получить слот по [CLI-регламенту](../../workflow/acceptance-cli.md): standalone CLI Loginom AI Agent, Sol low, согласованная подписка, бизнес-цель и входные файлы без пошаговых UI-команд.

Критерий аналитического PASS — полный малый output/артефакт, проверенная схема и настройки, новый execution и сохранённый пакет, которые независимо воспроизводятся после отдельного открытия. Configure-only и Close проверяются отдельно; обычный продуктовый путь не переоткрывает мастер ради повторной проверки. Непроверенные платформы, большие наборы и дополнительные режимы остаются явно ограниченными.

Передать checkpoint с точными source/runtime/client/model/platform pins, заявленным scope, результатами и неизменёнными исходными FAIL. Техническое завершение, аналитическая проверка, integration и release — отдельные состояния реестра. Один этап ревью и один раунд исправлений выполняются по общему жизненному циклу; этот подплан не добавляет повторного полного ревью.
