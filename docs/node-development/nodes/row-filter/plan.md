## 1. Цель и проверенная основа

Цель этапа 0 — подтвердить принятый объём текущим standalone CLI и исправить адресные дефекты. Кросс-таблица изменила общую оболочку, `node-read-*`, `workspace-ui.mjs`, `node-procedure.mjs` и `collapse-native-*`; CLI-регрессии прежних обработчиков не было, unit-тесты её не заменяют.

Принятый объём из реестра: OR между группами, AND внутри; scalar-условия и два выхода true/false.
Ограничения: Нет переменных и variant. Строковые сравнения требуют явного case_sensitive. Execute допускает чтение хотя бы одного выбранного выхода 0/1; при приёмке обоих заявленных выходов проверить оба. Исторический новый узел на 1000 полях встречал UI_SCAN_LIMIT; текущая максимальная live-ширина этой инвентаризацией не подтверждена.

Логика — И между условиями внутри группы, ИЛИ между группами. Поддержаны явные scalar-типы, строковый регистр, row_number, сравнения/интервалы/списки, NULL и boolean-предикаты из действующего FILTER_OPERATORS. Пустой groups не означает пропустить все строки.

Действующий handler при Execute допускает чтение хотя бы одного из портов 0/1, хотя текстовое описание API ещё упоминает оба. Для независимой проверки разделения читать оба: каждый RowID должен встретиться ровно один раз в объединении выходов. Preview мастера с ограничением строк не служит полным oracle. Лимиты: 64 группы и 128 строк условий вместе с разделителями ИЛИ.

## 2. Этапы

### Этап 0 — перепроверка принятого объёма

Подготовка: проверить SHA, собрать кандидата из закоммиченных исходников, получить `loginom status` = `ready` на назначенном стенде.

1. Собрать `acceptance/` из прежнего контракта (раздел 3): независимые ожидания, значения, freshness и отказы сохранить; адаптировать транспорт, pins и receipts к CLI. Прежний launcher Hermes не запускать.
2. Адресные тесты `client/test/filter-*.test.mjs` (3 файлов), затем весь `client/test`: `bun run test:upstream` в `packages/loginom-runtime`.
3. CLI-сценарий и независимое холодное открытие по RUNBOOK; generic cold-check и адресные дополнения — в разделах 3–4.
4. При расхождении — живая сверка мастера с `?testable=true`; прочитать причину из кнопки ошибки, записать в `discovery.md`; наблюдение не подменять E2E-снимком.
5. Исправить дефект в принятом объёме с адресным тестом; общая оболочка или расширение объёма — стоп-условие.

Выход: PASS исполнителя и независимая приёмка того же SHA; `client_technical_validation` и `analytical_validation` отражаются только по новому результату.

### Адресные действия при FAIL

1. Закрепить таблицу оператор × тип × арность по filter-parameters и живому редактору. Устранение несоответствия описания API реальному validator оформлять как адресное изменение, не расширяя режим.
2. Привязать условия к актуальным техническим именам входа; boolean использовать через is_true/is_false, datetime через локальное ISO со секундами без timezone.
3. При полной настройке заменить весь набор условий, проверить ИЛИ-разделители, операнды и case_sensitive после применения редакторов; existing без groups должен выполнять подтверждённую сохранённую конфигурацию.
4. Связать оба выхода с одним свежим execution. Смена условия аннулирует старые результаты обоих портов; не принимать preview мастера за выполненный output.
5. Сохранить независимый row_filter_oracle и негативные подмены: неверный порт, утраченная/повторная строка, старый запуск должны проваливать аудит.

### Этап 1 и далее — непокрытые режимы Help 7.4 (отдельные карточки владельца)

- Все применимые сравнения, NULL, интервалы/списки, contains/prefix/suffix, first/last, true/false для scalar типов.
- Клонирование, перемещение/удаление условий и OR, списки уникальных, ручное добавление/редактирование и clipboard.
- Динамический scalar и CSV-подобные списки из строковой переменной для integer/string.
- Variable поля: документированная матрица predicates и строковая вставка clipboard без автоопределения типа.

Перечень будущей полноты сохраняет прежний подплан: частично принятые действия перепроверяются на этапе 0, дополнительные controls/типы/режимы назначаются отдельно; совпавшее название режима не расширяет scope.

## 3. Данные и независимые проверки

Комплект `nodes/row-filter/acceptance/` собирает будущая карточка:

- `task.md` на бизнес-языке с `{{PACKAGE_PATH}}`; без имён инструментов и ожидаемых чисел;
- `data/golden.csv` и остальные указанные ниже CSV — точные копии прежних входов; только входы передаются модели;
- `expected.json` из независимого `oracle.py` до прогона; адресные наборы — `fixtures/` с manifest (байты, SHA, формат, типы, порядок).

Прежние входы: `fixtures/row-filter/golden.csv`: 413 байт, 10 записей, колонки `Id, Amount, Flag, When, Text`, разделитель `;`; кодировка UTF-8, NULL-маркер `NULL`. Размеры и SHA сохранить в manifest до прогона.

Ожидания прежнего контракта: Из `filter_goal_contract.py`: начальный отбор — непустые Amount/Text и непустая строка Text; финальный — (Amount ≥ 1.23456 И When ≤ 2024-01-02T12:30:01 И Flag=true) ИЛИ Text содержит Tail без учёта регистра. Оба выхода сверить по RowID, их объединение равно входу без потерь и повторов.

Матрица сохранена из прежнего подплана; ожидания и неоднозначные правила переподтвердить до модельного прогона:

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| И/ИЛИ | RowID 1..6: (Age,Income)=(20,10),(30,10),(40,50),(NULL,60),(18,30),(70,5); условие (Age≥30 И Income<20) ИЛИ Income≥50. | Порт подходящих: RowID 2, 3, 4, 6; противоположный:1,5. Проверить мультимножества, непересечение и суммарные 6 строк. |
| Строки и NULL | A, a, пустая строка, NULL, текст null, строка с кавычкой. | Отдельные case-sensitive/insensitive, is_null и contains; empty/null/literal сохраняют различие. Ожидаемые ID зафиксировать до прогона. |
| Типизированная матрица | Integer/real с дробями, boolean true/false/NULL, datetime границы интервала, row_number. | Включённость границ, отрицание и арность каждого заявленного оператора; нумерацию строк брать из документированной/подтверждённой семантики Loginom. |
| Изменение/пустота | Сменить условия того же узла так, чтобы один выход стал пустым; отдельный header-only вход. | Оба выхода сохраняют правильную схему; сохранённые условия воспроизводят точные наборы ID после reopen. |

Oracle не импортирует handler/runtime, рассчитывает по исходным байтам, сверяет все ячейки и схему, отличает NULL/пустую строку/0, отвергает чужой узел, старое исполнение, неполное чтение и подмену данных. Freshness, происхождение и настройки доказываются отдельно от правильных значений.

Cold-check: схема проверяется позиционно (имена, метки, типы), строки — как мультимножество, до 100 строк/выход и 32 выходов (`scripts/node-acceptance/expected-outputs.mjs:14,29-39,72-81`). Числа сравниваются точно (`cold-check.mjs:232`); большие Int64 — десятичные строки. Каждый ожидаемый выход однозначно связан с типом и меткой узла. E2E-снимки мастера не являются oracle.

Cold-check открывает только порт 0 (`cold-check.mjs:221`); `expected.json` не принимает индекс порта (`expected-outputs.mjs:10-14`). Порт 1, полнота разделения и принадлежность обоих результатов одному исполнению проверяются отдельным независимым аудитом после нового открытия. Если нужен общий cold-check обоих портов — W1 (порт в ожидании и адресное чтение), только после решения владельца.

## 5. Ловушки — переподтвердить, не копировать

- Отсутствующее поле, несовместимый тип, числовое сравнение boolean, невалидная дата/интервал, дубликаты списка, лишний операнд: отказ до редактирования.
- Две одинаковые метки разных полей, недостающий порт, неполное чтение широкой схемы: не принимать сокращённый результат за полный.
- Потерянный ответ после применения условия, stale ref до жеста, отмена: не добавлять второе условие или лишний ИЛИ, сохранить pending при неопределённости.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.
- Исторический аудит 06: полная матрица операторов и автономный аудит были разными проверками. У нового узла на 1000 полях встречался UI_SCAN_LIMIT; это ограничение не объявлять снятым без нового наблюдения.
- Приёмки текущего CLI нет; неподтверждено: полная ширина, правила row_number и precision datetime в текущем мастере. Исторические замеры/локаль/платформа не являются гарантией текущего стенда.
