# 06. Фильтр строк: подплан сопровождения и приёмки

[Карточка и принятые границы](README.md) · [реестр](../../registry.json) · [работа с одним узлом](../../workflow/single-node.md).

Обработчик `transform.filter_data` уже реализован в режиме `conditions`. Этот подплан адаптирует исторический 06 к текущему runtime и standalone CLI: это маршрут адресного исправления, проверки переноса или отдельно назначенного расширения, не повторная разработка с нуля. Историческое принятие сохраняется в своём scope; технические Desktop проверки не являются аналитической CLI-приёмкой. Новых живых наблюдений и прогонов при составлении документа не было, readiness не повышается.

До начала выбрать точное изменение и пройти [подготовку/жизненный цикл](../../workflow/lifecycle.md). Разработчик работает в Astra medium в своей задаче, ветке и worktree. Первичная разработка получает Goal до готовности изменения к первому ревью, без собственного token_budget. Этот документ не назначает следующий узел и не разрешает слияние.

## Узловые требования

Логика — И между условиями внутри группы, ИЛИ между группами. Поддержаны явные scalar-типы, строковый регистр, row_number, сравнения/интервалы/списки, NULL и boolean-предикаты из действующего FILTER_OPERATORS. Пустой groups не означает пропустить все строки.

Действующий handler при Execute допускает чтение хотя бы одного из портов 0/1, хотя текстовое описание API ещё упоминает оба. Для независимой проверки разделения читать оба: каждый RowID должен встретиться ровно один раз в объединении выходов. Preview мастера с ограничением строк не служит полным oracle. Лимиты: 64 группы и 128 строк условий вместе с разделителями ИЛИ.

## Шаги изменения

1. Закрепить таблицу оператор × тип × арность по filter-parameters и живому редактору. Устранение несоответствия описания API реальному validator оформлять как адресное изменение, не расширяя режим.
2. Привязать условия к актуальным техническим именам входа; boolean использовать через is_true/is_false, datetime через локальное ISO со секундами без timezone.
3. При полной настройке заменить весь набор условий, проверить ИЛИ-разделители, операнды и case_sensitive после применения редакторов; existing без groups должен выполнять подтверждённую сохранённую конфигурацию.
4. Связать оба выхода с одним свежим execution. Смена условия аннулирует старые результаты обоих портов; не принимать preview мастера за выполненный output.
5. Сохранить независимый row_filter_oracle и негативные подмены: неверный порт, утраченная/повторная строка, старый запуск должны проваливать аудит.

## Независимые fixtures и oracle

Ниже — обязательная узловая матрица для объявленного полного scope. При адресном исправлении выбрать затронутые строки и обосновать выбор; расширение режима добавляет новые строки. До автономной попытки сохранить входы и expected отдельно от handler, с версиями и SHA. Ожидания не вычислять импортом реализации и не подгонять по её приёмочному выводу.

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| И/ИЛИ | RowID 1..6: (Age,Income)=(20,10),(30,10),(40,50),(NULL,60),(18,30),(70,5); условие (Age≥30 И Income<20) ИЛИ Income≥50. | Порт подходящих: RowID 2, 3, 4, 6; противоположный:1,5. Проверить мультимножества, непересечение и суммарные 6 строк. |
| Строки и NULL | A, a, пустая строка, NULL, текст null, строка с кавычкой. | Отдельные case-sensitive/insensitive, is_null и contains; empty/null/literal сохраняют различие. Ожидаемые ID зафиксировать до прогона. |
| Типизированная матрица | Integer/real с дробями, boolean true/false/NULL, datetime границы интервала, row_number. | Включённость границ, отрицание и арность каждого заявленного оператора; нумерацию строк брать из документированной/подтверждённой семантики Loginom. |
| Изменение/пустота | Сменить условия того же узла так, чтобы один выход стал пустым; отдельный header-only вход. | Оба выхода сохраняют правильную схему; сохранённые условия воспроизводят точные наборы ID после reopen. |

## Негативные случаи

- Отсутствующее поле, несовместимый тип, числовое сравнение boolean, невалидная дата/интервал, дубликаты списка, лишний операнд: отказ до редактирования.
- Две одинаковые метки разных полей, недостающий порт, неполное чтение широкой схемы: не принимать сокращённый результат за полный.
- Потерянный ответ после применения условия, stale ref до жеста, отмена: не добавлять второе условие или лишний ИЛИ, сохранить pending при неопределённости.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.

## Автономная проверка и передача

Разделить таблицу на соответствующие бизнес-условию и остальные строки, сохранить оба выхода в одном пакете и независимо подтвердить отсутствие потерь и дублирования.

Первичная отладка — штатными скриптами текущего runtime в назначенной изоляции. После неё выполнить адресные source tests и проверить независимый oracle, включая его отказ на подменённых значениях/схеме/идентичности. Только затем подготовить неизменный candidate и получить слот по [CLI-регламенту](../../workflow/acceptance-cli.md): standalone CLI Loginom AI Agent, Sol low, согласованная подписка, бизнес-цель и входные файлы без пошаговых UI-команд.

Критерий аналитического PASS — полный малый output/артефакт, проверенная схема и настройки, новый execution и сохранённый пакет, которые независимо воспроизводятся после отдельного открытия. Configure-only и Close проверяются отдельно; обычный продуктовый путь не переоткрывает мастер ради повторной проверки. Непроверенные платформы, большие наборы и дополнительные режимы остаются явно ограниченными.

Передать checkpoint с точными source/runtime/client/model/platform pins, заявленным scope, результатами и неизменёнными исходными FAIL. Техническое завершение, аналитическая проверка, integration и release — отдельные состояния реестра. Один этап ревью и один раунд исправлений выполняются по общему жизненному циклу; этот подплан не добавляет повторного полного ревью.
