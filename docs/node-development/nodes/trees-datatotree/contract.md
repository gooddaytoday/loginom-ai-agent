## Первый срез

| Runtime type / mode | Native component | Вход 0 → выход 0 |
|---|---|---|
| `trees.from_table` / `manual_structure` | `component.trees.DataToTree` | table → tree |
| `trees.to_json` / `serialize` | `component.trees.TreeToJSON` | tree → table с одной JSON-строкой |

DataToTree: непустая таблица, root object Root, одна повторяющаяся ветвь объектов,
не более одного вложенного object в её элементе. Схема задаётся явным упорядоченным
списком path/name/label/type/is_array/source_field. Контейнерам source_field
запрещён; скалярам обязателен. Тип равен исходному, label=name. Родитель раньше
ребёнка; путь однозначен, имена sibling уникальны. Ограничения ≤64 узлов схемы,
не больше лимитов принятого tree_io: 256 экземпляров, depth16, 1 MiB ответа.
Это подмножество существующих пределов, не изменение общего бюджета.

Утверждённое требование к экземплярам: **одна строка → один элемент, порядок исходный**.
Повторные OrderID сохраняются, агрегации нет. Это пока не наблюдение платформы;
до регистрации нужна проверка native на fixture, без подстройки oracle под результат.
Если native не реализует правило в этом профиле mapping — остановка с вопросом,
а не незаметная замена на группировку.

TreeToJSON: один root object, одна ветвь items, технические имена, исключение
служебного Root, compact JSON, один документ. Root arrays, multi-row splitting,
pretty, labels-as-keys, даты, Variant, управляющие переменные, XSD/JSON-импорт схем,
пустой вход, произвольная глубина и несколько sibling arrays вне этого среза.
Запросы этих режимов отклоняются до мутации; их native наличие не означает поддержку.
ISO8601 остаётся настройкой, но datetime-поля preflight отклоняет.

Полные `semantics` для NODE_TYPES и `description` каждого поля parameter_schema:
[schema-proposal.json](acceptance/schema-proposal.json). Enum строковые.
На новом узле обязательны все настройки. На существующем `parameters:{}`
сохраняет проверенные настройки; явный nodes заменяет структуру целиком,
patch сериализации сохраняет пропущенные поля. Не изменять настроенный вход,
схему или значения ради совпадения ожиданий.

## NULL, порядок, типы, точность

- Схема и значения проверяются раздельно на tree output 0. Тип NULL-ячейки
  остаётся типом leaf в схеме; не превращать его в строку или новый тип поля.
  NULL, пустая строка, ноль и false различны.
- DataToTree должен сохранять NULL существующего поля. Missing scalar в JSON
  нормализуется в NULL принятым `trees.from_json`; четвёртая note появится как null.
  Исходное отсутствие уже не восстановить. Правило не распространяется на контейнеры.
- В дереве точный порядок схемы, детей и экземпляров. В JSON точный порядок массива,
  порядок ключей object семантически несущественен. Перестановка schema недопустима,
  даже если JSON AST равен.
- Int64 проверяется Python int / точным десятичным текстом tree reader, без Number.
  В JSON это число, не quoted string. Boolean не 0/1. Real — binary64, fixture
  использует двоично точные 1.25, 0.5, 2.0; **abs=rel=0**. Числовые JSON записи
  2 и 2.0 эквивалентны, но тип real исходного tree leaf проверяется отдельно.
- JSON сравнивается после строгого декодирования, с запретом duplicate keys,
  NaN и Infinity. Escape spelling Unicode, кавычек и LF может отличаться;
  декодированная строка обязана совпасть. Нет округления или усечения ради PASS.
- Полное чтение источника до настройки, затем исходного tree-порта и итогового
  JSON-порта. Совпадения финального JSON недостаточно для приёмки DataToTree.

Компактный readback содержит только mode, точные настройки, упорядоченные
paths/types/links, node/workflow identity, input/output 0 и отдельный статус
исполнения. Полное дерево/JSON не дублируется в configuration. Done доказывает
commit настроек, Execute — новое завершённое выполнение и полное чтение;
Save/reopen отдельно. Не добавлять receipts/квитанции как бизнес-критерий.
ML-обучение и отдельный saved-model apply не обещаются: наличие Train в меню
ещё не доказательство их семантики.

## Разрешённые общие правки этапа 1 и их условия

| Предложение | Наблюдаемая причина / точка базы | Минимальная общая правка этапа 1 |
|---|---|---|
| W040-UI | Live `DataToTreeWizard`, `TreeToJSONWizard`, `EditDataTreeNodeDefForm`; `workspace-ui.mjs:39,335,347` их не знает | Две стадии мастера и ограниченный редактор node-def: наблюдение, разрешённые жесты, значения/порядок/связи, native ошибка Next, безопасные Cancel/Done; hook в существующую procedure, без обхода ownership/deadline |
| W040-JSON | `expected-outputs.mjs` сравнивает string values; разные корректные escape spelling не равны | Явный узловой JSON AST comparator в существующем cold-check/run-check для JSON-ячейки; без нового диспетчера/системы верификации, с exact integer parsing |
| W040-tree-audit | `run-check.py:616` check_tree жёстко знает `/items` и один уровень leaves; `:1081` применяет одно ожидание ко всем tree reads | Адресный выбор ожидаемого tree-порта по type/label/port и проверка nested object в существующем audit; cold-read исходного tree output в сохранённом пакете |

Tree refs, DataTree links, typed tree reader и лимиты из v0.3.9 **переиспользовать**,
не реализовывать заново. `node-result-schema.mjs` допускает tree output, но новый
configuration readback потребуется зарегистрировать аддитивно. Собственные
handler/parameters/readback и ветвь диспетчеризации — код новых узлов; регистрации
в схемах/типах, собственный skill и два сценария run-check также аддитивны.
Всё, что расширяет существующие guard/validator/observation, остаётся W040-UI.
Нет разрешения менять packages/agent, общий публичный wire shape, deadline,
общие бюджеты или другие обработчики. Если это понадобится — новая остановка.

W040-UI/W040-JSON/W040-tree-audit разрешены на этапе 1 **только аддитивно**,
для новых типов либо явно помеченных ожиданий. Поведение существующих типов,
стадий мастеров и проверок не меняется. JSON AST comparator включается явным
полем expected; строковое сравнение остаётся поведением по умолчанию.
check_tree параметризуется с прежним поведением по умолчанию; обязательны
red→green на старых и новых ожиданиях. Регрессия: по одному живому прогону
деревьев v0.3.9 с повтором и без, REST GET и s1. Публичный wire shape,
packages/agent, бюджеты и deadline не меняются.

Первый шаг отдельного этапа 1 — native-подтверждение правила «строка → элемент
без группировки» и исключения Root. При расхождении — остановка с вопросом;
критерии и oracle не подстраивать. Этап 0 готов к разработке; это не разрешение
начать этап 1 в текущей карточке и не доказательство native семантики.

## Утверждённые критерии и ожидаемые числа

Два отдельных новых чата/профиля/пакета, до исполнения — fixtures/task/oracle/expected.
Ни один expected не является измерением Loginom.

| Сценарий | Независимое ожидание |
|---|---|
| `table-tree-json` | 3 входные строки × 8 полей; Root→items[3]→details; 11 schema nodes, 32 tree instances; OrderID 10,10,20; ExternalID 9007199254740993,9007199254740993,9007199254740994; Qty 2,0,NULL, сумма 2; Price сумма 3.75; Note NULL, пустая строка, Unicode/кавычки/LF; один JSON документ |
| `json-tree-json` | 1 JSON document→typed tree→1 JSON document; items A/B/C/D, 4 элемента, 24 tree instances; id 9007199254740993; qty сумма 6; note NULL/пустая строка/x/NULL после нормализации отсутствующего scalar |

Все проверки ordered=true, output_port=0, column_order=exact; labels не заданных
бизнес-task выходных полей — label_any. Имя JSON-колонки пока not_checked,
используется один string column с name_any, без догадки о native имени.
Собственные ожидаемые labels терминальных узлов закрепляются runner при подготовке,
task не содержит имён инструментов, oracle или ожидаемых контрольных сумм.

Утверждённые критерии: (1) полные schema/instances DataToTree по oracle;
(2) JSON AST пары table→tree→JSON и JSON→tree→JSON;
(3) точные Int64/NULL/empty/Boolean/real и порядок;
(4) сохраняемые настройки и cold reopen/reexecute с чтением собственных портов;
(5) Execute актуального входа, отказ неподдержанных режимов до мутации;
(6) 2/3 PASS на одном SHA у исполнителя и 2/3 независимых под reviewer своей пары,
cold PASS и проверки затронутых пакетов. Критерии утверждены решением v040-scope.

Приёмочный комплект не запускается текущим run-check: новые типы/сценарии не
зарегистрированы, raw string comparison не реализует proposed_json_comparison,
nested tree требует указанного audit. JSON AST oracle — независимая функция
ожиданий, не замена живому reader/cold.

9765 Б. Это пункт отчёта, не причина менять общий skill или бюджет здесь.
Черновики ссылок/файлов skill лежат в acceptance и не установлены в продукт.

references/nodes/<тип>.md. Превышение общего SKILL.md решает LAB-768.

Оценка отдельного этапа 1: **4–6 циклов с новым бизнес-прогоном**:
W040-UI + DataToTree; TreeToJSON; существующий audit/cold + semantic comparison;
основная приёмка двух сценариев; до двух циклов под наблюдённые отказы и регрессию.
Независимая проверка того же SHA — отдельно. Это оценка, не изменение лимитов
карточки: каждый следующий пакет работы назначается самостоятельно.
