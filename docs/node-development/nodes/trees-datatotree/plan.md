этапа 0 снят. Этап 1 начнётся только по отдельной карточке; его первый шаг —

## 2. Этапы

### Этап 0 — исследование и приёмочный комплект

Наблюдения и предложение оформлены. До прогонов записаны fixtures, task,
независимый stdlib Python oracle, expected, schema/semantics и draft skill.
Никакого модельного или cold PASS. Native mapping/массив/Root/значения пока
not_checked; первым шагом отдельного этапа 1 подтвердить на закреплённых входах без изменения
ожиданий ради PASS. Несовпадение семантики — вопрос.

### Этап 1 — Ручная структура и табличные связи

Один табличный вход 0, один tree output 0. Явно заданные Root→items[] и
один вложенный object; schema fields/source links в точном порядке. Предложение:
каждая исходная строка — отдельный элемент, без группировки одинаковых OrderID.
r01 — построение container/array/leaf и связи; r02 — исходные типы, порядок,
NULL против empty. Пустой вход/исчезнувшие контейнеры требуют отдельного критерия.

Реализация — отдельным назначением; W040 и критерии утверждены с условиями.
Узловые handler/parameters/readback, аддитивные регистрации типов/схем,
свой reference-файл skill и два run-check сценария. Общие guard/validator,
UI observation и существующий comparator — только по утверждённому W040.
Неподдержанный режим отказывать до мутации. Подробная схема всех параметров
и текста NODE_TYPES.semantics — в общем контракте.

### Последующие этапы — отдельно

r03: полный редактор/загрузка JSON и XSD, namespace, mapping и исключения; r04: глубина и рекурсивные схемы; r05: переменные/сохранённые дополнительные свойства.
Вне первого среза также sibling arrays, Variant, произвольная глубина,
пустой вход, missing container/empty array, смена источника и schema import.
Они не являются обещанием поддержки или критериями первого назначения.

## 3. Данные и oracle

Собственный [task](acceptance/task.md), [expected](acceptance/expected.json),
[описание комплекта](acceptance/README.md), fixtures/manifest.json.
Общий oracle — `../trees-datatotree/acceptance/oracle.py`, без Loginom/runtime.
Модели только business task и входной CSV; oracle/schema/expected/manifest ей
не передаются. Новый owned пакет и профиль для каждого сценария.

Ожидания: table→tree→JSON — 3 строки, 8 исходных полей, 32 tree instances,
1 JSON document; JSON→tree→JSON — 4 items, 24 tree instances, 1 document.
ordered=true, output_port=0, нулевой допуск; точный Int64 и NULL/empty отдельно.
JSON AST сравнивает объекты без порядка ключей, массивы с порядком;
порядок и типы tree schema проверяются на исходном порте.

Текущий run-check этот комплект не исполняет: типы/сценарии и адресный JSON
comparator не зарегистрированы. Полнота таблицы со строкой не доказывает дерево.
Разделение схемы/значений, правила NULL, точности, порты и числа — в contract.md.

## 4. Утверждённая приёмка

2/3 PASS двух сценариев на одном SHA, cold reopen/reexecute и полное чтение
исходного tree и конечного JSON output 0. Затем независимые 2/3 на том же SHA
под другим аккаунтом. Save после чтений, package_closed/logged_out, соответствующие
изменённым пакетам проверки. Unknown эффект не повторять; native ошибку читать.
Критерии утверждены. Квитанции/receipts не входят в бизнес-приёмку.
Регрессия этапа 1: по одному прогону trees v0.3.9 с повтором и без, REST GET
и s1. JSON comparator включается явным полем expected; строковое сравнение
по умолчанию сохраняется. check_tree параметризуется с прежним поведением
по умолчанию; red→green на старых и новых ожиданиях.
