Статус: `discovery_required`. Редакция 1 от 2026-10-05, автор — переработка подпланов в ветке `node-coverage-plans`.
Component ID: `component.exports.DataBase`, slug `exports-database`. Runtime type и режим: `exports.database` / `append` — предложение до конца этапа 0.
База назначения: ветка задания из карточки; исследованы исходники `loginom@dada8010e`. Loginom: ожидается 7.4.2, фактические версию/редакцию и ОС сервера записать на этапе 0; платформа исполнителя — Linux x64.

## 0. Как выполняется назначение

Оркестрация — Multica, сквад «Обработчики узлов»: Генератор тасок готовит назначение, Тест-Манки #1 разрабатывает и проходит приёмку, Ловец Галюцинаций независимо принимает опубликованный SHA.

Карточка:

```text
Ветка: <ветка задания>
Узел: exports-database
Обработать узел по его подплану до независимой приёмки. Объём — этап <N> подплана.
```

Первая карточка — этап 0 отдельно. Этап 1 назначается после решения владельца по W1 и W2; следующие W — перед соответствующим этапом. Общие исправления, подплан, RUNBOOK и инструменты приёмки должны быть в ветке задания до старта.

Разрешено:

1. Живое исследование штатными средствами runtime в собственном аккаунте.
2. Реализация назначенного этапа и только согласованных общих изменений (W1; W2; W3).
3. Приёмочный комплект, PR в ветку задания, публикация доказательств и независимая приёмка.

Не разрешено: merge/релиз; следующие этапы; новые общие контракты без решения владельца; изменение конфигурации обвязки. Внешние объекты и файлы — только собственные объекты из задания.

### Стоп-условия

Каждое — Blocked с конкретным вопросом Генератору:

- нет RUNBOOK, подплана, обязательных исправлений/инструментов; аккаунты или CLI не `ready`;
- компонента нет в палитре или внешняя среда недоступна (включая reader/драйвер/лицензию);
- нет решения владельца по W, требуемому назначенным этапом;
- неизвестный исход операции/частичный эффект: попытку сохранить, writer marker не удалять, перед повтором независимо сверить фактическое состояние;
- нужны новые режимы/общие изменения вне назначения или нельзя независимо проверить полный результат.

## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Checkout/SHA и сборка из закоммиченных исходников, `loginom status` = `ready`; квалифицировать внешнюю среду отдельно. Каждый отказ мастера читать из кнопки ошибки.

1. Палитру «Экспорт > База данных», заголовки мастера, обязательные подключение/таблицу и выход переменных; табличный выход не предполагать.
2. Дополнение и точные ключевые/обычные связи; auto-link имя→метка, типы, autosync и перестановку полей.
3. Шесть операций, disabled по SQL-диалекту, умолчания пачки/commit/ignore-errors; COPY на границах 99/100/499/500/501.
4. Когда появляется target schema и можно ли выполнить без предварительного создания; до/после частичной пачки читать статус и БД.
5. Смену источника того же узла, NULL/NOT NULL, overflow, дубликат ключа, недоступное подключение и потерю ответа.

Результат — `discovery.md`: observed/hypothesis, exact значения/типы/имена, границы источника и side effects, решения по W. Выход — `ready_for_development` только после снятия блокеров; закреплённые type/mode, `fixtures/` и `acceptance/` до кода обработчика.

### Этап 1 — самостоятельный первый срез

Scope: PostgreSQL, существующая Target, только дополнение, ручные связи совместимых полей; создание и изменение того же узла, явный новый объект для повторной приёмки. Создание и настройка существующего узла; readback фактически наблюдённых настроек и свежести результата. Неподдержанные формат/порт/режим/тип/параметр отклоняются до мутации с понятным объяснением исправления.

Требования этапа 1 (частичные режимы явно ограничены разделом 1):

- `exports-database:r01` — Дополнение, очистка+заполнение, TRUNCATE+заполнение, удаление по ключу, удаление+дополнение, обновление.
- `exports-database:r02` — Явное соответствие/ключевые поля, auto-link по имени затем метке, обновление полей и автоматическая синхронизация.

Источник и подключение выбираются по наблюдённой identity, не по похожей метке. Для внешней БД/Kafka/DW/1С `artifact_id` и `upload_operation_id` не описывают подключение и не заменяют проверку внешнего объекта. Табличные входы экспорта можно доставить принятым текстовым импортом с проверенным upload receipt; загрузка не подтверждает экспортированный результат.

Файлы: новые `packages/loginom-runtime/client/lib/exports-database-{node,parameters,procedure,readback}.mjs`, тесты `client/test/exports-database-*.test.mjs`; регистрация `node-contracts.mjs`/`.d.ts`, `node-support.mjs`, `node-api.mjs`, `node-result-schema.mjs`, `user-results.mjs`. Образец — [Текстовый экспорт](../../../../packages/loginom-runtime/client/lib/text-export-node.mjs), не переносить его семантику/формат. Общие `node-procedure.mjs`/`workspace-ui.mjs` меняются только в согласованных W.

Общие изменения, каждый отдельным коммитом с адресными тестами:

- **W1** — контракт подключения и порта Подключение: identity, readback и отказ недоступного объекта; node-contracts/node-api/node-procedure/workspace-ui, отдельный коммит и тесты.
- **W2** — приёмка внешнего эффекта без слепого повторного Execute: отдельное SQL-соединение, before/after, execution identity, частичные commit и закрытие пакета; scripts/node-acceptance и тесты.
- **W3** — этап 3: чтение выходных переменных статуса и управляющие bindings 0–5; node-read-*/node-api и независимый oracle переменных.

Видимость для модели: `NODE_TYPES.semantics` объясняет бизнес-результат и побочные эффекты; `description` у каждого параметра, строковые enum, компактный readback. Наблюдённые значения отличать от запроса модели.

Тесты из `packages/loginom-runtime`: `bun run test:upstream`; при изменении приёмки — из того же каталога `node --test ../../scripts/node-acceptance/tests/*.test.mjs`. Команды новых адресных тестов закрепить после появления файлов; сейчас они не существуют.

### Этап 2 и далее — отдельные карточки

Этап 2 — остальные операции r01, автоматические связи r02 и DDL r03; этап 3 — r04 и r05, переменные/статус W3, пачки, fast loader и отдельные SQL-провайдеры.

- Завершить частично принятые требования этапа 1: r01: этап 1 принимает только дополнение; r02: только ручные связи. Остальные операции и автоматические связи принимаются этапом 2, сохранность полной спецификации — ниже.

- `exports-database:r03` — Создание таблицы: поля/порядок/тип/размер/NOT NULL/PK; удаление существующей; просмотр или редактирование DDL.
- `exports-database:r04` — Режим через integer-переменную 0–5; ignore-errors и статус, число строк пачки, период фиксации.
- `exports-database:r05` — Матрица SQL-диалектов и PostgreSQL fast loader Авто/Да/Нет.

Полный текст каждого требования сохранён в его этапе; проверки в разделе 4 относятся к соответствующей карточке, не являются PASS первого среза.

## 3. Данные и независимые проверки

Комплект `nodes/exports-database/acceptance/` (для следующих этапов `acceptance/stageN/`): `task.md` с `{{PACKAGE_PATH}}`, `data/` только для входов модели, `expected.json` из независимого `oracle.py` до обработчика. Внешние manifests, oracle и ожидания модели не передаются; секреты — только во внешнем окружении.

CSV-спецификации: UTF-8, разделитель `,`, decimal `.`, header, NULL-маркер `\N`; empty string отличается от NULL. `fixtures/manifest.json`: фактические байты/SHA256, типы/метки/порядок и происхождение каждого бинарного файла/внешнего объекта; размер фиксируется при генерации, а не угадывается.

| Набор | Содержание и назначение |
|---|---|
| `base.csv` | Id,Label,Amount; строки (2,B2,25),(3,C,30). Независимый SQL создаёт Target=(1,A,10),(2,B,20),(9,Z,90). |
| `constraints.csv / batches.csv` | NULL в NOT NULL, переполнение и повтор ключа; генерация Id=1..n при n=99,100,499,500,501 и отдельно нарушение во второй пачке. |
| `empty.csv / replace.csv` | Та же схема без строк; новый источник (4,Г,40), переставленный порядок колонок и совпадающие метки. |

Oracle не импортирует handler/runtime, считает по входам, сверяет все ячейки/объекты/байты, имена/метки/типы/порядок полей, NULL/empty/0. Отклоняет старое исполнение, чужой destination/узел и подмену данных; E2E preview/обратный импорт не является независимым эталоном.

Нынешний cold-check принимает только таблицы: `expected-outputs.mjs:2-23`, нет файлов, sink или переменных. `expected.json` этого узла — **предлагаемая** схема external_effects[] с объектом/before/after/operation identity, до W она не принимается обвязкой. Нельзя добавлять фиктивный табличный output или объявлять PASS лишь по входной таблице. W приёмки обязателен перед этапом 1; после cold-open сверять настройки/граф и уже произошедший эффект, не повторять внешнюю запись вслепую.

## 4. Проверки, приёмка и завершение

Непроведённая проверка — `not_checked`; ожидания/границы фиксируются до модельного прогона.

| Требование / проверка | Независимое условие успеха |
|---|---|
| `exports-database:r01` | Для каждого из 6 режимов сравнить Target после выполнения независимым SQL-клиентом; удаление не вставляет строки, обновление не вставляет новый ключ. |
| `exports-database:r02` | Переставить исходные поля и совпадающие метки: проверить связи по identity/type, существующие связи сохраняются; schema change не подменяет ключ. |
| `exports-database:r03` | Сверить DDL каталога БД. Длина строки сверх лимита/NULL в NOT NULL дают отказ; удаление допустимо только в своей fixture-схеме. Обновление DDL назначения проверяется внешним oracle и не требует relaxed output-schema policy. |
| `exports-database:r04` | Перебрать 0–5 и недопустимые значения; провоцировать ошибку во второй пачке и сравнить реально committed строки со статусом, не считать activation успехом. |
| `exports-database:r05` | На PostgreSQL проверить размеры 99/100/499/500/501 и batch; VIEW/RULE/неподдержанный тип проверяют ограничения fast loader. Провайдерный лог подтверждает COPY/INSERT, числа — oracle. |
| Контракт и отказы | Неверные настройки/типы отклонены до эффекта; исходная ошибка мастера сохранена |
| Изменение существующего | Настройки/связи readback подтверждены; новый источник не даёт старый результат; незапрошенные свойства сохранены |
| Persistence | Сохранить после всех чтений; открыть новым профилем без восстановления настроек; внешние эффекты и происхождение проверить по согласованному W |
| Recovery | Потерянный ответ не повторяет неизвестный эффект; результат сверяется независимо перед продолжением |
| Регрессия | Адресные тесты нового узла и полный `client/test`; прежние контракты не ослаблены |

Задание модели: Дополнить выделенную таблицу сведениями из приложенного файла, сопоставить поля по их смыслу, показать настройки и результат записи, затем сохранить новый пакет в {{PACKAGE_PATH}}.

Файловый/внешний/переменный результат нельзя объявить принятым неподходящим oracle. Публикация и Ловец принимают тот же чистый SHA по RUNBOOK; `integration` и `release` не меняются.

## 5. Ловушки — переподтвердить, не копировать

Ниже документальные ограничения и требования прежнего черновика; точные controls и runtime-семантика для стенда остаются гипотезами до этапа 0.

Подключение БД + исходная таблица + необязательные управляющие переменные → переменные статуса (0/1, ошибка); табличного результата экспорта нет.

Ограничения Help: TRUNCATE недоступен SQLite/Firebird/Access; ODBC разрешает выбор, но драйвер может отказать. ClickHouse использует TRUNCATE вместо очистки DELETE и ALTER DELETE для ключевого удаления; UPDATE отсутствует в ClickHouse/BigQuery. MS Excel допускает только добавление/обновление. Пачки настраиваются для ClickHouse/Oracle/PostgreSQL/ODBC (1–1000000); fast loader — только PostgreSQL и три вставляющих режима. Транзакции READ COMMITTED лишь при поддержке СУБД; transaction commit interval проверяется отдельно.

Независимый SQL-клиент создаёт Target с начальными (1,A,10),(2,B,20),(9,Z,90). Вход (2,B2,25),(3,C,30), отдельные NULL/overflow/дубликат ключа. Каждый destructive case получает новую схему; ожидаемое состояние БД рассчитывается до запуска.

DDL и автоматическая синхронизация связей назначения меняют внешнюю таблицу/настройки sink, но не разрешают relaxed policy чтения результата Loginom. Поэтому CrossTable dynamic-schema не является prerequisite. Сверять target DDL и bindings отдельным DB oracle; неизвестное изменение входной схемы не принимается без наблюдённого mapping и строгой проверки.

До Execute фиксировать целевой объект, режим и исходное состояние; DDL/TRUNCATE/частичные commit могут быть необратимы. Потерянный ответ не допускает повтор INSERT/DELETE. Проверить БД другим соединением; rollback только своей активной транзакции.
