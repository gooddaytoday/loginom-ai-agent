## 1. Подтверждённая основа

Палитра Data Mining → Ассоциативные правила, иконка `bg-vendor-icon-assnrules`.
Два табличных входа, три табличных выхода. Корень мастера `WizrdMCF`:
настройка основного входа → вспомогательный вход → `AssnRulesWizard` →
три страницы output mapping (обычный Next пропускает) → `DoneWizard`.
Роли основного входа: «Транзакция», «Элемент», оба поля дискретные строковые.
Пустой вспомогательный вход не препятствовал обучению.

Наблюдены отдельное Обучить узел, обычное выполнение, повторное обучение,
смена файла существующего импорта без пересоздания целевого узла,
полное точное чтение всех трёх портов и сохранение собственного пакета.
Параметры UI — проценты, Support/Confidence на выходах — доли 0..1.
Невалидная поддержка 101: причина из `btnError` — «Значение этого поля не
может быть больше 100». Подробности, границы и ограничения — в discovery.

## 2. Предлагаемый этап 1 — подготовленные транзакции, наборы и правила

Предлагается согласовать **порты 0/1**. Порт 2 имеет дополнительный native
отбор рекомендаций, не установленный общим контрактом этого среза; он
исследован, но не нужен для точных правил/поддержки/достоверности. Его
поддержка и критерии назначаются отдельно. Это предложение набора портов
в пределах разрешения LAB-777, не понижение уже утверждённой приёмки.

| Требование | Контракт | Приёмочные данные |
|---|---|---|
| `datamining-assnrules:r01` | один основной вход Transaction/Item, string/discrete; явное обучение перед выполнением | `transactions.csv`: 4 набора и 2 правила; `length.csv`: 6 наборов и 6 правил |
| `datamining-assnrules:r02` | min support=50%, min confidence=60%, max_items=2; min lift=0, одиночные наборы включены, native лимит следствий=1 | включение поддержки ровно 50%, доли 1/2, 2/3, 3/4, 1; ABC с поддержкой 50% исключена длиной 2 |

Пять полей `parameter_schema`: `transaction_field`, `item_field`,
`min_support_pct`, `min_confidence_pct`, `max_items`. Описание есть у каждого
поля; mode — строковый `fp_growth`. Max_items в предложении ограничен 2,
хотя UI допускает 1..1024. Другие длины требуют другой схемы выходов.
Оба порога описываются в процентах 0..100. Новый узел требует все пять полей;
у существующего пропуск сохраняет настройку. Execute — явный Train текущего
связанного входа, затем Execute и чтение обоих результатов. Переобучение не
должно скрываться за отдельным режимом apply.

Исходные CSV — без NULL и пустых ID/товаров. Пустой вход, NULL-обработка,
native дубли, вспомогательные элементы, расширенные фильтры, несколько
следствий и holdout без retrain не входят в приёмку этапа 1. Не заменять
NULL нулём/пустым текстом и не обещать непроверенные режимы.

| Выход | Порядок полей при max_items=2 |
|---|---|
| 0 | ItemsetID integer, Width integer, Support real, Item_0 string, Item_1 string |
| 1 | RuleID integer, Support real, Confidence real, Lift real, Item_0_A string, Item_0_C string |

Padding Item_1 — NULL. Физический порядок строк не фиксируется:
`ordered:false`; порядок полей — `column_order:exact`. Native метки —
`label_any`, т.к. пользователь их не задавал. IDs для этих fixtures закреплены
discovery-привязкой, без обобщения на произвольные входы. Все real —
`tolerance:{abs:1e-10,rel:1e-10}`, остальное точно. Лифт присутствует в native
схеме и проверяется как confidence/support(следствия); пользовательский
параметр фильтра лифта не добавляется.

## 3. Приёмочный комплект и проверки

- `fixtures/*.csv`, `manifest.json` — самостоятельные подготовленные данные,
  UTF-8 CSV с заголовком, запятой и маркером NULL `?`; порядок Transaction, Item.
- `acceptance/task.md`, `acceptance/data/transactions.csv`, `expected.json` —
  основной пример AB, AB, AC, BC. Правила A→B и B→A: support=1/2,
  confidence=2/3, lift=8/9.
- `acceptance/length/task.md`, `data/length.csv`, `expected.json` —
  ABC, ABC, AB, AC. Выходы 0/1 имеют 6/6 строк. Тройка ABC частая, но
  запрещена пределом длины 2. Это отличает проверку длины от пустой декларации.
- `acceptance/oracle.py` — Apriori, множества, Fraction, Python stdlib;
  не импортирует runtime, не читает фактические результаты. Численные ожидания
  рассчитаны до проверки соответствующего примера. `--write` регенерирует,
  `--check` проверяет оба expected, аналитические границы, дубли и байты входов.
- `fixtures/node-type.json`, `parameter-schema.json`, `skill-routing.txt`,
  `skill-node.md` — предложения для регистрации на этапе 1, не активный handler.
  `schema-size.mjs` измеряет их через существующие serializers без мутации runtime.

Модель получает только пользовательский task и соответствующий `data/`.
Oracle, expected и discovery ей не передавать. Добавить два сценария run-check
на этапе 1. Stock oracle уже умеет output_port, ordered, tolerance и несколько
выходов: старые W2/W3 из редакции 1 больше не нужны.

После реализации: red→green на production-ветке; полный client test с pinned
Chromium, тесты оснастки при её изменении; `required-checks.py list/verify`.
Живые прогоны только run-check start + wait одной командой, модель
`openai/gpt-6.1-sol`, medium, 1800 с. На одном SHA ≥2/3 PASS исполнителя и
2/3 независимой проверки, CSV обоих выходов, Save, stock cold по скачанному
CSV, закрытие пакета/logout. Это будущие критерии, здесь не выполнены.

## 4. Общие изменения и бюджеты

Новых общих механизмов на предложенном срезе не выявлено. Использовать
обучение как у Кластеризации/Логистической регрессии, существующий reader
портов и matcher. Только аддитивная регистрация собственного handler,
wizard/roles/readback, своего файла навыка и двух сценариев. `packages/agent`,
публичные общие контракты, сроки и лимиты не менять.

Compact dock_node_apply и карточка типа укладываются в 20 000/12 000 Б;
строка маршрутизации — 148 Б, файл узла <6 000 Б. **Общий SKILL.md в базе
49 525 Б >40 000 Б**; плюс строка — 49 673 Б. Это внешняя зависимость
соблюдения бюджета этапа 1. Полная схема измеряется без лимита. Точные
байты и способ расчёта — в discovery; общая переработка skill сюда не входит.

Оценка реализации — 2–3 цикла. Если потребуется новый общий механизм,
остановиться с конкретным вопросом, не расширять срез молча.

## 5. Последующие этапы и точка продолжения

Отдельные назначения: расширенный диапазон длины с динамической схемой,
дубли и NULL/пустые транзакции, вспомогательный вход, фильтры, рекомендации
порта 2 с независимо согласованным отбором, holdout/apply сохранённой модели,
инвалидация/повторное обучение после смены источника, cold жизненного цикла.
Они не наследуют PASS математического базового примера.

Этап 0 подготовлен: native discovery и численные проверки 0/1 есть; handler
не реализован, модельные прогоны, cold, интеграция и релиз не заявлены.
После завершённых чтений `length.csv` стенд разорвал связь; cleanup вернул
`CONNECTION_DISCONNECTED`, package_closed/logout не подтверждены. Сессия не
восстанавливалась, диалог закрыт и браузер завершён. До разрыва был сохранён
пакет базового примера; последнее изменение источника не объявляется сохранённым.

Следующий шаг — утверждение предложенных портов 0/1, чисел, допуска,
порядка и ограничений; затем отдельная карточка этапа 1 от назначенной базы.
