## Обучение, применение, точность

Штатное меню `mn;mniTeachNode` — «Обучить узел» — отдельно от
`mn;mniActivateNode` — «Выполнить узел». Обучение завершалось как процесс
собственного узла без ошибки. Повторное обучение того же GUID и чтение трёх
портов выполнены штатными процедурами подтверждения завершённого процесса.
Все три native чтения вернули полное содержимое, `numbers_verified=true`,
binary64 с 17 значащими цифрами, точные integer/string/NULL.

Поддержка и достоверность **в параметрах — проценты, на выходах — доли**.
Первый вывод Таблицы округлял confidence до `0,6666666667`; oracle использует
2/3, а не этот текст. Native reader вернул `0.6666666666666666` и lift
`0.8888888888888888`. Padding `Item_1` у одноэлементных наборов подтверждён
как `exact_null`, не пустая строка. Support=0.5 при min support=50 включён.

Третий выход — рекомендации недостающих элементов. На основном примере
выданы T3→B и T4→A; покупки с уже имеющимся следствием строк не дали.
На `length.csv` имеются четыре подходящих правила, но native выдал только
две строки: T3/A→C по RuleID=3 и T4/A→B по RuleID=1 (confidence=0.75).
Альтернативные B→C и C→B с confidence=2/3 отсутствуют. **Это наблюдение,
а общий алгоритм ранжирования/ограничения рекомендаций не установлен.**
Гипотеза — отбор более достоверного правила при лимите следствий 1; её не
превращаем в oracle. Поэтому порт 2 предлагается отложить: владелец ограничил
срез точными наборами/правилами, поддержкой и достоверностью и разрешил
предложить набор портов. Для завершения этого среза новый критерий отбора
рекомендаций не нужен. Пользовательские task и expected требуют только 0/1.
Это применение к текущему основному входу, не holdout без переобучения.
Наблюдался отдельный процесс «Применение модели ассоциативных правил».

После смены файла существующего импорта на `length.csv` тот же GUID
ассоциативного узла явно переобучен; параметры и связь сохранены. Отсутствие
скрытого retrain при отдельном holdout, инвалидирование модели без явного
обучения и cold-восстановление модели остаются `not_checked`. Этап 1
предлагает Execute=явное обучение текущего входа + выполнение; отдельный
режим saved-model apply не регистрировать.

## Схема и независимый приёмочный комплект

Порядок технических полей для max_items=2:

| Порт | Поля в native порядке |
|---|---|
| 0 | `ItemsetID` integer, `Width` integer, `Support` real, `Item_0` string, `Item_1` string |
| 1 | `RuleID` integer, `Support` real, `Confidence` real, `Lift` real, `Item_0_A` string, `Item_0_C` string |
| 2 | `RuleID` integer, `Support` real, `Confidence` real, `Lift` real, `Transaction` string, `Item_0_A` string, `Item_0_C` string |

Исходные поля: **Transaction, Item**, UTF-8 CSV, запятая, заголовок,
оба string/discrete; `?` — NULL. CSV для модели лежат только в `acceptance/data`
или `acceptance/length/data`. `task.md` — пользовательская просьба; oracle,
expected, manifest и discovery модели не передаются. Числа Apriori рассчитаны
до проверок соответствующего примера. Привязка native схемы/IDs установлена
в discovery, а `expected.json` подготовлены до будущих run-check.

`acceptance/oracle.py` — независимый Apriori на stdlib: послойное объединение
кандидатов, отсечение по частым подмножествам, точный счёт присутствий через
множества и `Fraction`. Он не читает Loginom, журналы или runtime и не
реализует FP-Growth. Вероятности вычисляются только из CSV.
Порядок native ID для данных этих fixtures — отдельная явно выделенная
привязка, не формула вероятности и не гарантия для иных входов.

| Пример | Ожидаемые числа |
|---|---|
| `transactions.csv`: AB, AB, AC, BC | 4 набора: A=3/4, B=3/4, AB=1/2, C=1/2; 2 правила A→B, B→A, support=1/2, confidence=2/3, lift=8/9; рекомендации T3→B и T4→A |
| `length.csv`: ABC, ABC, AB, AC | 6 наборов: A=1, B=C=AB=AC=3/4, BC=1/2; 6 правил. Частая ABC имеет support=1/2, но исключена max_items=2. Порт 2 не входит в oracle |

Второй пример нужен потому, что первый сам по себе не доказывает отсечение
троек. Oracle отдельно подтверждает: при max_items=3 на втором входе
появляется седьмой набор ABC. У первого примера min support=50.1,
min confidence=67 или max_items=1 дают ноль правил; это независимые
аналитические проверки, не заявленные native/модельные PASS этих режимов.

Предлагается утвердить до этапа 1:

- Один основной вход, поддержка/достоверность и max_items=2,
  фиксированные политики из таблицы; оба примера, **порты 0 и 1**,
  каждая ячейка и точная последовательность полей. Рекомендации порта 2 отложить.
- `ordered:false`: физический порядок строк не является требованием задачи.
  Имена и типы полей точные; native метки — `label_any`, пользователь их не задавал.
  IDs на этих fixtures закреплены discovery-привязкой; произвольные IDs для
  иных данных не обобщаются. Правила сверяются вместе с содержимым и метриками.
- Для real `tolerance:{abs:1e-10,rel:1e-10}`; integer, string и NULL — точно.
  Никакого допуска для ID или замены NULL пустым текстом. Маркер CSV NULL
  берётся stock runner из явных настроек соответствующего экспорта; `?`
  в manifest относится к исходным CSV. Значения `""` в выходах этих примеров отсутствуют.
- Сохранение, два экспорта, stock cold-check по скачанному CSV, повторное
  исполнение в новом профиле; ≥2/3 PASS исполнителя и 2/3 независимой проверки
  на одном SHA по регламенту. Здесь эти проверки не выполнялись.
- Входы подготовлены без NULL и пустых ID/товаров. `null.csv` и `empty.csv`
  — адресные данные для последующего исследования; native поведение на них
  не установлено, обработчик не должен обещать их поддержку или подменять значения.
  `duplicates.csv` проверяет set-семантику oracle; native дубль отдельно не проверен.

Воспроизведение oracle: `python3 .../acceptance/oracle.py --write`, затем
`--check`. Manifest содержит байты/SHA входов и типы, не квитанции исполнения.
Текущий `expected-outputs.mjs` уже поддерживает `ordered`, `column_order`,
`output_port`, `tolerance`, `label_any` и несколько портов; W2/W3 не нужны.
