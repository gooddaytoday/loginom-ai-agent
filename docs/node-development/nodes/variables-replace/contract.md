# Предложение контракта этапа 1

LAB-840, база `origin/v040@5d3860bfd542c44a2875ae61d03dab6ecdb64ec6`.
Объём владельца `v040-extras-0411`: точная замена простых переменных без
regex и смены типа. Все критерии ниже — предложение к утверждению
оркестратором перед этапом 1 (`v040-scope`). Регистрации схемы здесь нет.

## Вход, операция и выход

`component.variables.Replace`, runtime `variables.replace`, mode `exact`.
Один обязательный вход variables и выход variables 0. Отдельный control-вход
не подменяет вход значений. W1 уже определяет `variable_inputs` с kind
`variables|control`, `read.variable_ports` и typed cold. Эти контракты здесь
не дублируются; точные refs, связи и ожидаемый формат берутся из принятого W1.

Для 1–32 выбранных переменных: точное техническое имя из входного inventory,
тип `integer|real|string|boolean`, 1–32 пары from/to и политика `other:keep`.
Обе стороны пары имеют тип переменной либо JSON null. Для string обязательно
`case_sensitive:true`; для integer/real `precision:0`. Boolean не является
числом; строки не преобразуются в числа/формулы. Целые — безопасный диапазон
`[-(2^53-1), 2^53-1]`. Вещественные — только конечные. Строки — до 2048
символов без NUL/CR/LF; эти пределы — предложенный лимит handler, не Loginom.

Один поиск по исходному значению: red→blue и blue→green дают для red ровно
blue. Неуказанная переменная и значение без совпадения сохраняются.
При обновлении полностью заменяются пары только перечисленных переменных;
сохранённые правила остальных и выходное соответствие не меняются.
Обновление не добавляет повторную таблицу правил к прежней.

Сохраняются технические имена, метки, типы, число переменных и порядок входа.
**Native по умолчанию добавляет к меткам изменяемых переменных «Замена».**
Поэтому handler должен явно установить прежние метки на странице
`DerivedVariablesMappingEngineOutputPortWizard`. Это узловая обязанность,
а не обещание автоматического сохранения native-меток.

NULL — отсутствие значения с прежним типом. Оно отлично от `""`, false, 0
и отсутствия самой переменной в наборе. Допустимы пары NULL→константа,
константа→NULL и NULL→NULL с тем же типом. Последний случай семантически
предлагается; в discovery отдельно не выполнялся.

## Отказы и компактный readback

До мутации: неизвестное имя/параметр/режим, повторная переменная, дубликаты
ключей, неверный тип пары, несовместимый вход, небезопасное целое, NaN/Infinity,
смена типа, datetime/Variant, regex, импорт/экспорт правил, approximate matching,
case-insensitive и другие политики остальных. Нельзя обходить native-ошибку
кнопкой «Всё равно далее». Причину брать из `WizrdMCF;btnError`.

[node-card-proposal.json](node-card-proposal.json) содержит `semantics` и
`description` каждого поля; enum только строковые. Кросс-полевые проверки
`type`↔from/to, обязательность precision/case_sensitive и правил при создании
выполняются handler до открытия UI. JSON Schema сама их все не выражает.

Configuration readback: `mode`, ordered `rules` с variable.name/type/pairs/
other/case_sensitive/precision и ordered `output_variables` с name/label/type.
Не повторять весь входной inventory, UI-координаты и подписи кнопок.
Identity и фактические typed-связи подтверждает W1. Чтение результата отдельно
возвращает полный ordered-набор name/label/type/value с port kind и индексом.
Done, Execute и успешное чтение не объединяются в один признак.
Обученная модель для этих замен не нужна; отдельный train/apply не заявляется.

## Приёмка, допуски и независимость

До любых модельных прогонов подготовлены `fixtures/`, пользовательский
`acceptance/task.md`, Python oracle и `expected.json`. Oracle — независимый
типизированный словарь Python с Decimal для чисел, без Loginom/runtime.
Он вычисляет каждую замену один раз и выдаёт три полных состояния.
Модели доступны только task и два fixture JSON; oracle/expected ей не передают.

Предлагаются `output_port:0`, `port_kind:variables`, `ordered:true` и точная
сверка имён, меток, типов, количества, NULL, строк, Boolean и integer.
Для real: `|a-e| <= max(1e-12, 1e-12*|e|)`. Это допуск чтения результата,
**не** numeric matching precision: поиск правил остаётся с точностью 0.
DOM округляет real; сравнивать typed-значение W1, а не текст клетки.

1. Создать источник из 10 переменных, соединить его пользовательский выход 4
   с variables-входом узла, задать 8 таблиц (9 пар), получить initial.
2. На том же GUID изменить только Count: 2→8; получить updated, сохранив
   остальные правила, выходные метки, типы, порядок и связи.
3. В источнике изменить только Color на blue; повторно выполнить тот же
   узел без перенастройки; получить source_updated.
4. Save после последнего чтения; новый профиль открывает сохранённый пакет,
   заново выполняет его и сверяет весь порт 0 с source_updated; затем штатные
   Close/logout. Формат expected привести к принятому W1 без ослабления проверки.
5. Адресные отказы с неизменённым узлом: дубликат, неверный тип, неизвестное
   имя, regex/смена типа; положительный Boolean и отдельные NULL/empty.

Это проект expected для W1, **не схема cold-check, поддерживаемая на базе**.
Собственный typed cold reader/механизм проверки не создаётся. Регламент этапа 1:
2/3 PASS на одном SHA у исполнителя и отдельно 2/3 независимой приёмки на том
же SHA, cold PASS, проверки затронутых путей. Этап 0 таких PASS не заявляет.

## Что требуется сверх W1

Аддитивная регистрация type/mode и узловых UI readers/procedures; обработка
`ReplaceVariablesWizard`, его Boolean/NULL редакторов, duplicate refusal,
сохранение выходного mapping; собственный reference навыка и сценарий
run-check `variables-replace-exact` с тремя чтениями. Это предложенное имя,
на базе сценарий ещё не зарегистрирован. W1 даёт портовый транспорт/read/cold,
но не таблицы замен и не эту страницу выходного соответствия.

Табличный `replacement-*.mjs` жёстко привязан к `ReplaceColumnsWizard` и
поддерживает другие типы/политики; не расширять его ради нового компонента.
Общий `TBGCustomModelComponentEngine` не является уникальной identity типа:
проверять vendor/иконку и точный GUID узла, а не только fulltype или метку.

Сейчас общие изменения поведения сверх разрешённой аддитивной регистрации
не обоснованы. Узловые процедуры/readback должны подключаться аддитивно,
сохраняя существующие guards/lifecycle. Если для этой страницы mapping
потребуется изменение общего контракта или поведения — `blocked` с вопросом
до правки. В `packages/agent`, бюджеты и deadline не заходить.

Оценка после принятого W1: **2 цикла + 1 резервный**. Первый: правила/редакторы/
mapping, адресные тесты и живой сценарий. Второй: update/source refresh,
persistence/cold и регрессия. Резерв — только под новый наблюдённый отказ.
Цикл включает implementation → проверки → новый бизнес-прогон. W1 и
независимая приёмка в эту оценку не включены.
