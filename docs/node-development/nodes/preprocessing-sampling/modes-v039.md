## Граница предложения

Новые критерии требуют утверждения владельца до этапа 1. Существующий
последовательный контракт не меняется. Новый документ не заменяет историю
v0.3.8 в discovery.md и plan.md.

`fixtures/modes.csv` содержит 20 строк: RowID=1..20, Class=A у первых десяти,
B у остальных, Value=10*RowID. Типы integer/string/integer. Порядок классов
специально сгруппирован: простой последовательный срез не пройдёт проверку
стратификации 4A/4B при размере 8. Отдельные NULL/empty fixtures старого
комплекта остаются обязательными для реализации.

seed введён как 42 и прочитан обратно. Два отдельных обычных Execute,

Стратифицированный S на том же источнике: включён только

ровно A4/B4; схема и порядок исходных полей сохранены. Это одно нативное
выполнение, не 2/3 и не доказательство повторяемости стратификации.

## Случайное Разбиение: нативное наблюдение

На том же источнике и seed42, train_count=8/test_count=4,
приоритет тестового множества выключен. Полные чтения всех трёх портов
одного завершённого Execute:

| Порт | Строки | RowID |
|---|---:|---|
| 0 общий | 12 | 5,7,8,11,13,15,17,20; затем 1,2,4,18 |
| 1 train | 8 | 5,7,8,11,13,15,17,20 |
| 2 test | 4 | 1,2,4,18 |

Train/test не пересекаются, unused отсутствует на общем выходе.
Порты1/2 сохраняют RowID integer/Class string/Value integer;
порт0 добавляет первым IsTestSet boolean: false на train, true на test.
По сравнению с последовательным методом меняется состав строк,
но число/назначение портов и схема остаются прежними. Общий выход
по-прежнему train+test, внутри каждого множества исходный порядок.
Повторный Execute с теми же параметрами дал полное побайтовое равенство
значений всех трёх портов (12/8/4). Журнал: `execution-events.jsonl:1024`–`:1026`
и `:1119`–`:1121`. Это нативная проверка, а не модельная приёмка.
Стратифицированный P по Class, те же размеры/seed, одно полное выполнение:
train RowID=1,3,5,7,15,17,18,20 (A4/B4), test=4,10,14,16 (A2/B2).
Порт0 — эти train+test, всего12 строк A6/B6; IsTestSet и схемы сохранены.
Все значения прочитаны на каждом порте; журнал `execution-events.jsonl:1227`–`:1229`.
Повторяемость stratified отдельно
не проверялась. Для biased/uniform отношения выходов пока предложены
как критерии, а не выданы за измеренные таблицы.

## Приёмочный комплект — предложение

Задания `acceptance/task-random.md`, `task-stratified.md`, `task-biased.md`, `task-uniform.md`
написаны на языке пользователя. Модели передаются только задание и CSV;
`oracle-modes.py`, `modes/expected.json` и этот документ не передаются.
`oracle-modes.py --node sampling|data_partition` строит ожидаемые свойства
из fixture средствами Python stdlib, без Loginom, runtime или actual.

`acceptance/modes/expected.json` — **предложение критериев, не формат stock
cold/run-check**. В нём нет придуманной таблицы случайно выбранных строк.
Никакой новый проверяющий механизм или регистрация runner в PR не добавлены.
Квоты стратификации вычислены независимо: S=8 → A4/B4;
P train=8 → A4/B4, test=4 → A2/B2; округление исключено размером fixture.
Квоты S и P подтверждены одним нативным выполнением каждого узла.
Повторяемость стратификации — обязательство этапа 1,
а не PASS по арифметике oracle.

Предлагаемые критерии случайных методов:

1. Два исполнения при одном seed, неизменном источнике и полной конфигурации
   дают одинаковые полные упорядоченные таблицы на каждом порте.
2. Все строки принадлежат исходному CSV целиком; уникальный RowID не повторён;
   значения, типы, NULL, false и пустые строки не преобразованы.
3. Проверить размеры и квоты, подтверждённые для конкретного метода;
   иной seed **не обязан** давать иной результат на малом входе.
4. У P train/test не пересекаются; общий порт согласован с обоими выходами,
   IsTestSet Boolean и правильные флаги, остаток не включён в общий набор.
5. Создание и update сохраняют GUID, незапрошенные поля/mapping/параметры.
   Done/Close/Execute и несовместимые параметры проверяются отдельно.
6. Сохранение пакета, cold reopen без повторной настройки, точные типы и
   полные таблицы всех портов; штатный cleanup; 2/3 + независимые 2/3
   на одном SHA. Для случайных таблиц критерий cold требует решения владельца
   о сравнении повторных выходов; existing stock exact-rows не умеет это сам.

Таблица параметров здесь отличается от основной SizeGridForm: текущий

## Смещение: препятствие точному oracle

Требование карточки «смещение — точный oracle» нельзя подменять срезом
`source[offset:offset+count]`: такого поля в UI нет. Факторы категорий
и Random seed не определяют независимо воспроизводимую последовательность
генератора. В LAB-648 выбран Class (`BiasedMethodForm;colDisplayName_Class`),
`btnGetUniqueValues` дал A/B по10 строк с исходными факторами1.
После выбора A в `colBiasedValue_0` кнопка `btnBiasedEdit` открыла
`MF;TF-1;WizrdMCF;FactorEditDialog;fldFactor`; значение0.4 применено
через `btnApply`, readback `colBiasedFactor_0`=0.40, B=1.00.
Размер14/seed42, обычный Execute и полный output0 дали **10 строк**:
RowID=1,3,5,11,15,16,17,18,19,20 (A3/B7), схема исходная.
Журнал: `execution-events.jsonl:1331`, sample_complete и cleanup подтверждены.
Это не квота «первые4 A + все B» и не сдвиг по номеру строки.
Результат совпал с историческим LAB-533, но в LAB-648 наблюдение выполнено
заново; конкретный состав actual не превращён в независимый oracle.

В `expected.json` biased явно помечен `exact_oracle_unresolved`;
`rows=null` не выдаётся за успешный oracle. Нужен выбор владельца:
распространить на biased разрешённую случайным методам проверку
детерминизма/инвариантов либо исключить biased из этапа 1.
До решения biased не ready_for_development. Это стоп по новому критерию,
а не из-за бюджета схемы.

## Реализация и размер схемы

Режимы расширяются в существующих `client/lib/sampling-{parameters,context,
procedure,readback,node}.mjs`, `data-partition-{parameters,node}.mjs`.
`sampling-output.mjs` уже читает 1/3 порта и сохраняет значения/типы;
изменять его только при наблюдённом различии выходов. Аддитивные изменения
`node-api.mjs`, `node-contracts.mjs`, `node-contracts.ts`, readback schema,
skill и штатной регистрации acceptance относятся к этапу 1.
Общий `createTabularTransformNodeSupport` уже принимает `implementation.modes`,
поэтому для dispatch нескольких методов общая правка не требуется.
Новый механизм случайной приёмки без решения владельца не реализуется.

Оценка после утверждения: random S/P — 1 цикл реализации + 1 приёмочный;
stratified — 1–2 + 1; biased — 1–2 + 1 после решения по oracle;
uniform — отдельно после подтверждения семантики группы. Не общая смета
переделки UI: новые отказы общего кода требуют отдельного решения.

Полная inputSchema `dock_node_apply` на базе — **43 329 Б** (UTF-8 от
`JSON.stringify`). Добавить значения enum `random`, `random_uniform`,
`stratified`, `biased` один раз для обоих типов: **+48 Б = 43 377 Б**.
Seed, count, train_count/test_count в полной схеме уже есть.
С черновыми полями из `modes-schema.proposal.json` — **+1 229 Б = 44 558 Б**;
это оценка, не утверждённый контракт. Лимит 46 000 Б не блокирует этап 0.
Readback/output schema в эти числа не входят.

Воспроизведение (импортировать node-api.mjs того же чистого базового SHA
с установленными client-зависимостями; сборка CLI не нужна):

```js
const bytes = s => Buffer.byteLength(JSON.stringify(s));
const base = nodeApiTools.find(t => t.name === 'dock_node_apply').inputSchema;
const next = structuredClone(base);
next.properties.mode.enum.push(...proposal.mode_enum_additions);
console.log(bytes(base), bytes(next), bytes(next) - bytes(base));
Object.assign(next.properties.parameters.properties, proposal.parameters_additions);
console.log(bytes(next), bytes(next) - bytes(base));
```
