# 05. Параметры полей: подплан сопровождения и приёмки

[Карточка и принятые границы](README.md) · [реестр](../../registry.json) · [работа с одним узлом](../../workflow/single-node.md).

Обработчик `transform.reform_columns` уже реализован в режиме `scalar`. Этот подплан адаптирует исторический 05 к текущему runtime и standalone CLI: это маршрут адресного исправления, проверки переноса или отдельно назначенного расширения, не повторная разработка с нуля. Историческое принятие сохраняется в своём scope; технические Desktop проверки не являются аналитической CLI-приёмкой. Новых живых наблюдений и прогонов при составлении документа не было, readiness не повышается.

До начала выбрать точное изменение и пройти [подготовку/жизненный цикл](../../workflow/lifecycle.md). Разработчик работает в Astra medium в своей задаче, ветке и worktree. Первичная разработка получает Goal до готовности изменения к первому ревью, без собственного token_budget. Этот документ не назначает следующий узел и не разрешает слияние.

## Узловые требования

Изменять только явно перечисленные свойства полей: имя, метку, scalar-тип, вид, назначение и excluded. Field identity — техническое имя/record identity, не неоднозначная метка. Все незапрошенные поля и свойства сохраняются.

Пять scalar-типов и до 128 изменений; циклический обмен имён не поддержан. Для перевода непрерывного поля в string/boolean необходимо явно выбрать дискретный вид. После исключений должно остаться хотя бы одно поле. Изменение типа является преобразованием значений, поэтому проверка только схемы недостаточна.

## Шаги изменения

1. Сопоставить требуемую конверсию с scalar-matrix и текущим native редактором; отдельно зафиксировать вид, назначение, форматирование и исходный тип.
2. В resolveReformChanges сначала построить полный итоговый набор на одном baseline. Проверить все collisions, исключения и порядок ациклических переименований до открытия первого редактора.
3. Обновить только необходимые свойства, дождаться строки того же record_id и прочитать итоговую схему. После upstream rename заново подтвердить input binding.
4. Развести настройки самого узла и input/output mapping. Возврат из отдельного мастера порта не считать закрытием всей операции; выполнить узел только после фиксации всех настроек.
5. Расширить независимую матрицу конверсий значениями и типами; при потере точности или неподдержанной конверсии явно ограничить scope, а не сравнивать округлённый preview.

## Независимые fixtures и oracle

Ниже — обязательная узловая матрица для объявленного полного scope. При адресном исправлении выбрать затронутые строки и обосновать выбор; расширение режима добавляет новые строки. До автономной попытки сохранить входы и expected отдельно от handler, с версиями и SHA. Ожидания не вычислять импортом реализации и не подгонять по её приёмочному выводу.

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| Сохранение данных | RowID и поля A/B с одинаковыми метками; изменить только метку A, переименовать B, исключить дополнительное поле C. | RowID и все значения A/B сохраняются; конфигурация C исключена только на выходе, неизвестные поля не изменены. |
| Типы | String с корректными числом/датой/boolean и отдельными невалидными значениями; integer, real с дробью 1.234567, отрицательное и NULL. | Использовать независимый expected для каждой разрешённой конверсии из scalar-matrix; семантику невалидного значения/округления закрепить отдельным диагностическим случаем, не угадывать. |
| Вид и назначение | Непрерывный real перевести в string с явно дискретным видом; назначить одному полю «Группа», другому «Показатель». | Проверить native тип, data_kind и usage, а не только строковый заголовок таблицы. |
| Граница схемы | Пустая таблица с типами; широкая схема с изменением последнего поля; повторное открытие сохранённого пакета. | Все неперечисленные поля, порядок, данные и кэширование сохранены; пустота не заменяет доказательство схемы. |

## Негативные случаи

- Циклическое переименование A↔B, коллизия с неизменяемым полем, удаление всех выходных полей: отказ без частичного набора.
- String/boolean с непрерывным видом, variant-конверсия, чужой input binding или отсутствующий source: отсутствие угадывания.
- Смена upstream после baseline, отмена редактора, потерянный ответ сохранения mapping: незапрошенные свойства остаются прежними, неизвестный эффект не сбрасывается.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.

## Автономная проверка и передача

Привести типы, метки и назначения предоставленной таблицы к согласованной схеме, сохранив исходные значения там, где преобразование не запрошено; сохранить и независимо перепроверить результат.

Первичная отладка — штатными скриптами текущего runtime в назначенной изоляции. После неё выполнить адресные source tests и проверить независимый oracle, включая его отказ на подменённых значениях/схеме/идентичности. Только затем подготовить неизменный candidate и получить слот по [CLI-регламенту](../../workflow/acceptance-cli.md): standalone CLI Loginom AI Agent, Sol low, согласованная подписка, бизнес-цель и входные файлы без пошаговых UI-команд.

Критерий аналитического PASS — полный малый output/артефакт, проверенная схема и настройки, новый execution и сохранённый пакет, которые независимо воспроизводятся после отдельного открытия. Configure-only и Close проверяются отдельно; обычный продуктовый путь не переоткрывает мастер ради повторной проверки. Непроверенные платформы, большие наборы и дополнительные режимы остаются явно ограниченными.

Передать checkpoint с точными source/runtime/client/model/platform pins, заявленным scope, результатами и неизменёнными исходными FAIL. Техническое завершение, аналитическая проверка, integration и release — отдельные состояния реестра. Один этап ревью и один раунд исправлений выполняются по общему жизненному циклу; этот подплан не добавляет повторного полного ревью.
