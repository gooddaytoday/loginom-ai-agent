## 1. Цель и проверенная основа

Цель этапа 0 — подтвердить принятый объём текущим standalone CLI и исправить адресные дефекты. Кросс-таблица изменила общую оболочку, `node-read-*`, `workspace-ui.mjs`, `node-procedure.mjs` и `collapse-native-*`; CLI-регрессии прежних обработчиков не было, unit-тесты её не заменяют.

Принятый объём из реестра: Изменение имени/метки/типа/вида/назначения/исключения; явный порядок полей.
Ограничения: Пять scalar-типов; циклические переименования и конверсии из неподдержанных типов не входят в контракт. Для continuous → string/boolean требуется явно задать дискретный вид. Выбор поля по точному имени/identity, не по потенциально одинаковой метке; максимум 128 изменений.

Изменять только явно перечисленные свойства полей: имя, метку, scalar-тип, вид, назначение и excluded. Field identity — техническое имя/record identity, не неоднозначная метка. Все незапрошенные поля и свойства сохраняются.

Пять scalar-типов и до 128 изменений; циклический обмен имён не поддержан. Для перевода непрерывного поля в string/boolean необходимо явно выбрать дискретный вид. После исключений должно остаться хотя бы одно поле. Изменение типа является преобразованием значений, поэтому проверка только схемы недостаточна.

## 2. Этапы

### Этап 0 — перепроверка принятого объёма

Подготовка: проверить SHA, собрать кандидата из закоммиченных исходников, получить `loginom status` = `ready` на назначенном стенде.

1. Собрать `acceptance/` из прежнего контракта (раздел 3): независимые ожидания, значения, freshness и отказы сохранить; адаптировать транспорт, pins и receipts к CLI. Прежний launcher Hermes не запускать.
2. Адресные тесты `client/test/reform-*.test.mjs` (9 файлов), затем весь `client/test`: `bun run test:upstream` в `packages/loginom-runtime`.
3. CLI-сценарий и независимое холодное открытие по RUNBOOK; generic cold-check и адресные дополнения — в разделах 3–4.
4. При расхождении — живая сверка мастера с `?testable=true`; прочитать причину из кнопки ошибки, записать в `discovery.md`; наблюдение не подменять E2E-снимком.
5. Исправить дефект в принятом объёме с адресным тестом; общая оболочка или расширение объёма — стоп-условие.

Выход: PASS исполнителя и независимая приёмка того же SHA; `client_technical_validation` и `analytical_validation` отражаются только по новому результату.

### Адресные действия при FAIL

1. Сопоставить требуемую конверсию с scalar-matrix и текущим native редактором; отдельно зафиксировать вид, назначение, форматирование и исходный тип.
2. В resolveReformChanges сначала построить полный итоговый набор на одном baseline. Проверить все collisions, исключения и порядок ациклических переименований до открытия первого редактора.
3. Обновить только необходимые свойства, дождаться строки того же record_id и прочитать итоговую схему. После upstream rename заново подтвердить input binding.
4. Развести настройки самого узла и input/output mapping. Возврат из отдельного мастера порта не считать закрытием всей операции; выполнить узел только после фиксации всех настроек.
5. Расширить независимую матрицу конверсий значениями и типами; при потере точности или неподдержанной конверсии явно ограничить scope, а не сравнивать округлённый preview.

### Этап 1 и далее — непокрытые режимы Help 7.4 (отдельные карточки владельца)

- Кэш Отключено/При активации/При обращении/Выбранные поля и индивидуальные режимы.
- Преобразования с допустимой потерей информации, локальные string→bool правила и variable values.
- Исключение одного/нескольких полей, обязательность и назначение исключённых; запрет исключить все.

Перечень будущей полноты сохраняет прежний подплан: частично принятые действия перепроверяются на этапе 0, дополнительные controls/типы/режимы назначаются отдельно; совпавшее название режима не расширяет scope.

## 3. Данные и независимые проверки

Комплект `nodes/field-parameters/acceptance/` собирает будущая карточка:

- `task.md` на бизнес-языке с `{{PACKAGE_PATH}}`; без имён инструментов и ожидаемых чисел;
- `data/cleanup.csv` и остальные указанные ниже CSV — точные копии прежних входов; только входы передаются модели;
- `expected.json` из независимого `oracle.py` до прогона; адресные наборы — `fixtures/` с manifest (байты, SHA, формат, типы, порядок).

Прежние входы: `fixtures/field-parameters/cleanup.csv`: 248 байт, 6 записей, колонки `Id, RawAmount, RawFlag, RawWhen, Comment, Unused`, разделитель `;`; кодировка UTF-8, NULL-маркер `NULL`. Размеры и SHA сохранить в manifest до прогона.

Ожидания прежнего контракта: Из `reform_goal_contract.py`: начальный выход `Id, Amount(real), Enabled(boolean), Timestamp(datetime), Comment`; финальный — `Timestamp, Id, NetAmount, Enabled`, `Unused` и `Comment` исключены. Дробь 3.545, неправильные строковые значения → NULL; одинаковые метки не объединяют поля.

Матрица сохранена из прежнего подплана; ожидания и неоднозначные правила переподтвердить до модельного прогона:

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| Сохранение данных | RowID и поля A/B с одинаковыми метками; изменить только метку A, переименовать B, исключить дополнительное поле C. | RowID и все значения A/B сохраняются; конфигурация C исключена только на выходе, неизвестные поля не изменены. |
| Типы | String с корректными числом/датой/boolean и отдельными невалидными значениями; integer, real с дробью 1.234567, отрицательное и NULL. | Использовать независимый expected для каждой разрешённой конверсии из scalar-matrix; семантику невалидного значения/округления закрепить отдельным диагностическим случаем, не угадывать. |
| Вид и назначение | Непрерывный real перевести в string с явно дискретным видом; назначить одному полю «Группа», другому «Показатель». | Проверить native тип, data_kind и usage, а не только строковый заголовок таблицы. |
| Граница схемы | Пустая таблица с типами; широкая схема с изменением последнего поля; повторное открытие сохранённого пакета. | Все неперечисленные поля, порядок, данные и кэширование сохранены; пустота не заменяет доказательство схемы. |

Oracle не импортирует handler/runtime, рассчитывает по исходным байтам, сверяет все ячейки и схему, отличает NULL/пустую строку/0, отвергает чужой узел, старое исполнение, неполное чтение и подмену данных. Freshness, происхождение и настройки доказываются отдельно от правильных значений.

Cold-check: схема проверяется позиционно (имена, метки, типы), строки — как мультимножество, до 100 строк/выход и 32 выходов (`scripts/node-acceptance/expected-outputs.mjs:14,29-39,72-81`). Числа сравниваются точно (`cold-check.mjs:232`); большие Int64 — десятичные строки. Каждый ожидаемый выход однозначно связан с типом и меткой узла. E2E-снимки мастера не являются oracle.

## 5. Ловушки — переподтвердить, не копировать

- Циклическое переименование A↔B, коллизия с неизменяемым полем, удаление всех выходных полей: отказ без частичного набора.
- String/boolean с непрерывным видом, variant-конверсия, чужой input binding или отсутствующий source: отсутствие угадывания.
- Смена upstream после baseline, отмена редактора, потерянный ответ сохранения mapping: незапрошенные свойства остаются прежними, неизвестный эффект не сбрасывается.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.
- Исторический аудит 05: исследовательская scalar-matrix не является заранее предсказанным oracle. Первый frozen FAIL из-за округлённого чтения и повторного назначения после reopen сохранён.
- Приёмки текущего CLI нет; неподтверждено: локальные конверсии и матрица scalar на текущем CLI. Исторические замеры/локаль/платформа не являются гарантией текущего стенда.
