`python3 -B oracle.py --write` регенерирует JSON; `--check` сравнивает его
с независимым расчётом CSV/Decimal. Конверсия около половин, overflow,
string→boolean и другие правила потери информации не включены: поведение
трёх указанных четвертей не доказывает всю матрицу преобразований.

Для обмена имён сначала фиксируется полный итоговый набор на исходных field
identity; временное имя не должно конфликтовать с исходными/конечными именами.
После обмена сохранить input/output mapping, полный порядок, данные,
типы и явно заданные метки A/B; незаданные метки — label_any.

Кэш проверяется отдельно от таблицы: node caching и индивидуальные
`caching_method` уже присутствуют в production readback. В конечном состоянии
узел — «Выбранные поля», A — «При активации», B — «При обращении»,
остальные — «Отключено». CSV сам по себе этого не доказывает.
Пропуск новых параметров на существующем узле должен сохранять кэш.
Число обращений к источнику, производительность и память не являются
критериями; нового измерительного механизма не предлагается.

**`expected-cache-settings.json` — первым шагом цикла, до модельных прогонов**
(решение 7 LAB-1119). Без него `reform-cache` проходит, даже если кэш не менялся:
`expected-cache.json` равен исходной таблице. Сгенерировать его из oracle без
стенда нельзя: readback отдаёт кэш числами — `caching.value` 0..3 у узла и
`fields[].caching_method` 0..2 у полей (`node-result-schema.mjs:118-120`), а
соответствие кодов пунктам «Отключено»/«При активации»/«При обращении»/
«Выбранные поля» не наблюдалось (видна только очередность пунктов списка).
Шаг цикла: на стенде связать коды с пунктами, добавить в `oracle.py` генерацию
`expected-cache-settings.json` (узел — «Выбранные поля», A — «При активации»,
B — «При обращении», RowID/R/S — «Отключено») и аудит readback до и после reopen.
