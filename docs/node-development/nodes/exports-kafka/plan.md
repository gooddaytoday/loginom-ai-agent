## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Checkout/SHA и сборка из закоммиченных исходников, `loginom status` = `ready`; квалифицировать внешнюю среду отдельно. Каждый отказ мастера читать из кнопки ошибки.

1. Палитру «Экспорт > Kafka», edition/license, корень мастера, входные порты; табличного результата Help не задаёт.
2. Topic, client.id, поле ключей и обязательное поле сообщений; поддержанные типы и NULL/empty.
3. Пачку (Help: 2 на локальном broker), timeout и последнюю неполную пачку; момент первой публикации.
4. Реальные настройки Producer и их конфликт с мастером; подтверждение доставки/ошибки, порядок внутри партиции.
5. Смену источника того же узла, пустой набор, недоступный broker/ACL, частичную отправку, отмену и потерю ответа.

Результат — `discovery.md`: observed/hypothesis, exact значения/типы/имена, границы источника и side effects, решения по W. Выход — `ready_for_development` только после снятия блокеров; закреплённые type/mode, `fixtures/` и `acceptance/` до кода обработчика.

## 3. Данные и независимые проверки

Комплект `nodes/exports-kafka/acceptance/` (для следующих этапов `acceptance/stageN/`): `task.md` с `{{PACKAGE_PATH}}`, `data/` только для входов модели, `expected.json` из независимого `oracle.py` до обработчика. Внешние manifests, oracle и ожидания модели не передаются; секреты — только во внешнем окружении.

CSV-спецификации: UTF-8, разделитель `,`, decimal `.`, header, NULL-маркер `\N`; empty string отличается от NULL. `fixtures/manifest.json`: фактические байты/SHA256, типы/метки/порядок и происхождение каждого бинарного файла/внешнего объекта; размер фиксируется при генерации, а не угадывается.

| Набор | Содержание и назначение |
|---|---|
| `messages.csv` | Id,Key,Payload; пять строк, ключи A,B,A,NULL,empty; payload с кириллицей/JSON, уникальный correlation marker для каждого case. |
| `empty.csv / replace.csv` | Пустая схема без строк; другие Id/payload той же схемы. Отдельный topic на каждую роль и попытку. |
| `broker-manifest.json` | Заранее фиксируются topic, partitions, начальные offsets и bytes ожидаемых сообщений; consumer проверяет все сообщения в диапазоне попытки. |

Правило messages.csv: Id=1..5, Key=[A,B,A,NULL,пустая строка], Payload=`<correlation-marker>:<Id>:Привет`; отдельный JSON-case заменяет payload на заранее заданный JSON без преобразования consumer. Marker уникален для попытки, expected bytes вычисляются UTF-8 до отправки.

Oracle не импортирует handler/runtime, считает по входам, сверяет все ячейки/объекты/байты, имена/метки/типы/порядок полей, NULL/empty/0. Отклоняет старое исполнение, чужой destination/узел и подмену данных; E2E preview/обратный импорт не является независимым эталоном.

Нынешний cold-check принимает только таблицы: `expected-outputs.mjs:2-23`, нет файлов, sink или переменных. `expected.json` этого узла — **предлагаемая** схема external_effects[] с объектом/before/after/operation identity, до W она не принимается обвязкой. Нельзя добавлять фиктивный табличный output или объявлять PASS лишь по входной таблице. W приёмки обязателен перед этапом 1; после cold-open сверять настройки/граф и уже произошедший эффект, не повторять внешнюю запись вслепую.

## 4. Проверки, приёмка и завершение

Непроведённая проверка — `not_checked`; ожидания/границы фиксируются до модельного прогона.

| Требование / проверка | Независимое условие успеха |
|---|---|
| `exports-kafka:r01` | Независимый consumer сверяет payload bytes, ключи, количество и принадлежность topic; перестановка колонок не меняет bindings. |
| `exports-kafka:r02` | Пять строк при batch=2 дают все пять сообщений, включая последнюю пачку; медленный брокер проверяет сообщение об ошибке и реально отправленный prefix. |
| `exports-kafka:r03` | Проверить настройки через broker/client trace без секретов; неверное свойство/ACL/топик не дают ложного успешного результата. |
| `exports-kafka:r04` | Пустая таблица не публикует сообщений. После lost reply считывать topic по correlation marker и не делать повторную отправку вслепую. |
| Контракт и отказы | Неверные настройки/типы отклонены до эффекта; исходная ошибка мастера сохранена |
| Изменение существующего | Настройки/связи readback подтверждены; новый источник не даёт старый результат; незапрошенные свойства сохранены |
| Persistence | Сохранить после всех чтений; открыть новым профилем без восстановления настроек; внешние эффекты и происхождение проверить по согласованному W |
| Recovery | Потерянный ответ не повторяет неизвестный эффект; результат сверяется независимо перед продолжением |
| Регрессия | Адресные тесты нового узла и полный `client/test`; прежние контракты не ослаблены |

Задание модели: Отправить сообщения из приложенного файла в выделенную очередь с указанными ключами, проверить доставку и сохранить новый пакет в {{PACKAGE_PATH}}.

PASS исполнителя: CLI и применимый cold-check/согласованный независимый аудит результата, адресная матрица, `package_closed=true`, `logged_out=true`. Файловый/внешний/переменный результат нельзя объявить принятым неподходящим oracle. Публикация и Ловец принимают тот же чистый SHA по RUNBOOK; `integration` и `release` не меняются.

## 5. Ловушки — переподтвердить, не копировать

Ниже документальные ограничения и требования прежнего черновика; точные controls и runtime-семантика для стенда остаются гипотезами до этапа 0.

Подключение Kafka + исходная таблица + необязательные управляющие переменные → публикация сообщений; табличного результата Help не задаёт.

PLAINTEXT, SASL_Plaintext, SSL, SASL_SSL; SASL PLAIN/SCRAM-SHA-256/SCRAM-SHA-512 — отдельные профили подключения. Итоговый порядок проверять внутри партиции; общего порядка между партициями не обещать.

Отдельный topic и независимый consumer. Вход 5 сообщений с ключами A,B,A,NULL,empty и payload с кириллицей/JSON; каждый case имеет уникальный correlation marker. Отдельный producer не используется для ожидаемых экспортированных сообщений.

Публикация может завершиться частично; конфигурация producer не означает exactly-once. Не очищать общий topic и не переиспользовать его для повтора.
