Таким образом, успешное выполнение узла не означает успех каждой строки запроса.
Признак ошибки строки нужно вычислять из ErrorCode, а HTTP-код читать из
HttpStatusCode дополнительного выхода. Пустой выход ответов не отменяет строку
диагностики. Проверка MIME может превратить HTTP 200 в ошибку обработки ответа.
Наблюдённый набор MIME для этой карточки — `application/json` и `text/html`;
поддержку других значений эти наблюдения не доказывают.

Первый бизнес-прогон не принят: дальнейший Калькулятор остановился на
`Input mapping recovery: complete prepared graph required`, итогового экспорта нет;
cold-check — `COLD_EXTRA_OR_MISSING_OUTPUT_NODE`, cleanup true/true.
Общая проверка сопоставления разрешает REST-связи только текущего узла и его
источника; вторая REST-ветвь не проходит это условие. Общая правка в LAB-94
не выполняется. Сырые readback и журналы остаются вложениями карточки.

## Гипотезы и not_checked

Предлагается runtime type **`integration.rest_request`**, mode **`request`**,
component ID `component.integration.RestRequest`. Регистрации в продукте пока нет.

Не проверены: фактические DELETE/POST/PUT/PATCH; две входные строки; ручное и
автоматическое связывание с таблицей; URL encoding/порядок параметров; сегменты и
замена; timezone; отправка пользовательского заголовка; пустая таблица и NULL;
схема до Execute; смена источника; повторное исполнение сохранённого пакета.
Пять методов и три режима URL подтверждены **как варианты UI**, а не как
пройденная матрица. Внутренняя нумерация RequestID для двух строк не проверена и в текущий expected не входит.
Эти допущения нельзя объявлять PASS без нового живого сценария этапа 1.

Auth/TLS, HTTP-ошибки, retry, simulation и интервалы не испытывались; это этапы 2+.
Справка описывает необязательность входной таблицы и семантику bindings:
[REST-запрос](https://help.loginom.ru/userguide/processors/integration/rest-request.html).
Синтаксис замены `:имя` и порядок сегментов документированы в
[REST-подключении](https://help.loginom.ru/userguide/integration/connections/list/rest-service.html),
но на стенде не проверены. Справка не считается живым наблюдением.

## Общие зависимости после решения владельца

| W | Наблюдённое основание | Минимальный требуемый результат |
|---|---|---|
| W1 | Внешнее подключение — отдельный объект модуля и узел-ссылка; мастер запроса получает метод и URL из него | Для этапа 1 только GET и строковые RequestId/Key, привязка подключения и чтение результата. Общие изменения остаются в карточке W; расширенные режимы — этапы 2+ |
| W2 | Response содержит нестабильный JSON; первоначально предлагалась json_projection | Предложение снято владельцем. Разбор в сценарии штатными узлами, expected на конечной таблице; без новых видов проверки в cold-check |
| W3 | Правила волны отменяют ledger | Не требуется; собственный сервис и ledger не создавать |

Допуск `tolerance` уже существует; здесь нет real-колонок, сравнение integer/string
точное. Новый механизм допуска не нужен. Общий код и scripts/node-acceptance
этим PR не меняются. Комплект обновлён по решению владельца; нового согласования JSON-проверки не требуется.
Реестр остаётся `discovery_required`; этот PR не присваивает `ready_for_development`.
