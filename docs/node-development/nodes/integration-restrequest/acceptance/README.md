# Приёмочный комплект: GET и результат после разбора JSON

Решение владельца по ревью PR #95 от 17.10.2026: этап 1 ограничен GET
к https://httpbin.org/anything с RequestId и Key в строке запроса.
Остальные методы, сегменты, замена, тело, заголовки и timezone — этапы 2+;
наблюдения сохранены в discovery.

Модели передаются только `task.md` и `data/requests.csv`. Это одна просьба
пользователя на четырёх строках, без названий компонентов и инструкций построения.
Oracle, expected, manifest и discovery модели не передаются.

`python3 oracle.py --write` создаёт expected и manifest из входного CSV без сети,
runtime и результатов модели; `python3 oracle.py --check` проверяет воспроизводимость.
Две строки требуют двух вернувшихся пар RequestId/Key и фактического HTTP-кода 200.
Ожидания фиксируются до модельного прогона.

## Проверяемый результат

`expected.json` использует существующий табличный формат cold-check:
единственный выход после разбора, `RequestId:string`, `Key:string`,
`HttpStatusCode:integer`. Сравниваются ровно две строки, без требования порядка.
Сырой Response, внутренний RequestID, ErrorCode, ErrorDesc, метод и другие поля
ответа в expected не входят. IP, даты и trace id не проверяются.
Real-колонок нет, поэтому `tolerance` не требуется; существующий допуск не меняется.
Перед cold-check оператор подставляет фактический новый путь .lgp в package_path.

Разбор выполняется в самом сценарии уже поддерживаемыми узлами. В базе есть
`programming.javascript` (один табличный вход и выход) и `transform.join_data`.
Возможный вариант: соединить ответы и дополнительные данные REST по внутреннему
RequestID, затем JavaScript разбирает Response через JSON.parse и выдаёт
вернувшиеся args.RequestId/args.Key вместе с настоящим HttpStatusCode.
RequestId/Key нельзя брать вместо ответа из исходного CSV, а HTTP-код — подставлять
константой. Код разбора и способ построения не включены в задание модели.
Если будет выбран другой поддерживаемый финальный узел, тип цели expected должен
соответствовать ему до прогона; новый обработчик для разбора не предполагается.

Предложение json_projection снято. Новые виды проверки, изменения cold-check,
собственный сервис и ledger не нужны. Бизнес-выгрузка содержит результат после
разбора, и cold-check сравнивает именно эту таблицу по штатному контракту.

## Что подтверждено

Discovery принят владельцем: REST доступен без администратора, сервер Loginom
достаёт httpbin. Наличие обработчиков разбора и соединения проверено в исходниках;
собранный сценарий REST → разбор ещё не выполнялся. Генерация expected и его
проверка штатным matcher не являются native/model/cold PASS.
В этой правке по заданию владельца живые модельные прогоны не выполняются.
