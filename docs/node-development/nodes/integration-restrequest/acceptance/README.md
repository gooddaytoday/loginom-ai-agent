# Комплект этапа 0

Модели передаются только `task.md` и `data/requests.csv`. Oracle, expected,
manifest, discovery и это описание остаются у оператора. Путь нового пакета
подставляется из личной папки аккаунта; общий OAuth не копируется.

`python3 oracle.py --write` детерминированно создаёт `expected.json` и manifest
из входа, без сети, runtime и результатов модели. `python3 oracle.py --check`
проверяет, что они не изменились. Ожидания фиксируются до модельных прогонов.
Два входных ряда дают десять запросов, пять REST-узлов и десять проверяемых выходов.
GET/DELETE/POST проверяют строковые URL bindings, PUT — сегмент, PATCH — замену.
When намеренно строковый: эта бизнес-проверка не доказывает обработку timezone.

## Статус expected.json и W2

Это **предложение формата для W2**, а не готовый вход нынешнего cold-check.
`outputs[*].json_projection` сейчас отклоняется с `EXPECTED_SHAPE_INVALID`.
Так предотвращается ложный PASS только по HTTP 200. До принятия W2 cold PASS
объявлять нельзя. Исполняемый код общей приёмки в карточке REST не добавляется.

Предложенная минимальная семантика `json_projection`:

- `source_columns` — точная native схема порта 0, включая RequestID/Response;
- `source_column` — JSON-строка Response; невалидный JSON/NULL/пропущенный путь — отказ;
- `fields` — отображение имени проверяемой колонки на JSON Pointer RFC 6901;
- RequestID остаётся native integer, остальные колонки получаются только по этим путям;
- `columns`/`rows` содержат ожидаемые стабильные значения после проекции;
- native число строк, полнота чтения, схема и типы проверяются до проекции;
- прочие JSON-поля, включая origin, даты и trace id, не сравниваются.

На порту 1 остаётся существующий точный формат columns/rows. Пять label позволяют
различать узлы одного типа, `output_port` различает их выходы. Это возможность уже
имеющегося формата; переписывать адресацию портов без наблюдённого отказа не нужно.
JSON Pointer используется только как декларативное предложение, своего reader,
verifier или тестового сервера этот комплект не реализует.

Real-колонок нет: `tolerance` не требуется. Если позже появится real-колонка,
использовать существующее `columns[i].tolerance={abs:...,rel:...}`, а не новый допуск.

## Границы доказательства

Oracle ожидает, а не наблюдает RequestID 0/1, успешный status 200 и точные echo-поля.
Непроверенные на стенде допущения перечислены в discovery. PUT/PATCH сравнивают
полный URL с безопасным ASCII RequestId; query-ветки сравнивают декодированные
значения args, поэтому не доказывают конкретную сериализацию percent encoding
или порядок URL-параметров. Это проверяется адресным сценарием этапа 1.
Полная матрица последующих этапов не включена в бизнес-задание.

Ни этот oracle, ни генерация expected не являются живым тестом или cold-check.
После решения владельца по W: чистая сборка → модель gpt-6.1-sol/medium,
1800 с → сохранённый пакет → cold-check обоих портов и echo → 2/3 на одном SHA.
Файлы экспорта — результат бизнес-задания; cold сравнивает выходы самого REST,
а не вычисления вспомогательного узла. Реестр готовности этим комплектом не меняется.
