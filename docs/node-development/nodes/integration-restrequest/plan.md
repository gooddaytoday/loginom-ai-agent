## 0. Как выполняется назначение

Оркестрация — Multica, сквад «Обработчики узлов»: Генератор тасок готовит назначение, Тест-Манки #1 разрабатывает и проходит приёмку, Ловец Галюцинаций независимо принимает опубликованный SHA.

Карточка:

```text
Ветка: <ветка задания>
Узел: integration-restrequest
Обработать узел по его подплану до независимой приёмки. Объём — этап 0 подплана.
```

Первая карточка — этап 0 отдельно; этап 1 — после решения владельца по W, нужным этому этапу (раздел 2). В ветке задания должны быть RUNBOOK, подплан, инструменты приёмки и принятые зависимости, недостающее готовит Генератор.

Разрешено: живое исследование в собственном аккаунте, комплект `acceptance/`, затем назначенный срез и согласованные W, PR и публикация доказательств.
Не разрешено: merge и релиз; следующие этапы; изменение конфигураций обвязки. Общий код правится по правилам сквада: только под наблюдённый отказ бизнес-сценария, минимальным дифом, без новых механизмов верификации.

- неизвестен исход операции с внешним эффектом: не повторять, сначала проверить состояние внешней системы;

## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Подготовка: checkout и сверка SHA, сборка из закоммиченных исходников, `loginom status` = `ready`. Наблюдения — штатными средствами runtime с `?testable=true`, каждый отказ мастера прочитать из кнопки ошибки.

1. Палитра, точный заголовок и корень мастера, страницы, число/тип/необязательность портов; доступность в назначенной редакции.
2. Умолчания, границы, disabled/dependent настройки и точные причины отказов, включая неизвестный параметр.
3. Наблюдать методы GET/DELETE/POST/PUT/PATCH, query/segments/replacement, ручные и автоматические bindings, порядок параметров, headers и timezone.
4. Наблюдать оба выхода, HTTP >=400/code 6, Content-Type, retry count/delay/интервал, connection/total timeout и simulation.
5. Зафиксировать доступность auth/TLS; Windows certificate-store отдельно от файлов сертификата на Linux.
6. Имена, метки, типы и порядок полей каждого выхода, момент появления схемы до/после Execute; NULL, пустой вход и смена источника того же узла.

Результат — `discovery.md`: «наблюдено / гипотеза», конкретные значения и точные схемы, предложение W владельцу. После исследования закрепляются runtime type/режим, fixtures и acceptance до кода; `ready_for_development` не присваивается этим документационным PR.

## 3. Данные и независимые проверки

Комплект `nodes/integration-restrequest/acceptance/` (следующие срезы — `acceptance/stageN/`): `task.md` с `{{PACKAGE_PATH}}` на бизнес-языке, `data/` только с входами модели, `expected.json` из независимого `oracle.py` до кода/прогона. Oracle и expected модели не передаются.

Формат CSV: UTF-8, заголовок, разделитель `,`, десятичный `.`, NULL-маркер `?`, пустая строка в кавычках. `requests.csv`: `RequestId,Key,When,Body`; строки `r-a,"a b&я",2024-02-29T12:00:00.000,"{""amount"":10}"`, `r-b,"x/y?",2024-03-01T12:00:00.000,"{""amount"":20}"`. Service возвращает заранее заданные тела и headers по RequestId, ledger фиксирует метод, URL, байты body и время попытки. При сборке `task.md` этапа 1 явно перечислить методы GET/DELETE/POST/PUT/PATCH и маршруты query/segments/replacement контролируемого сервиса; каждый метод получает собственную настройку подключения и отличимую метку результата. Настройки не выводятся из скрытого expected. `responses.json`/сертификаты находятся у оператора; реальные credentials модели не передаются.
Размеры, число строк, SHA256, кодировка, типы, разделители и NULL фиксируются в `fixtures/manifest.json` до прогона. Доставка — проверенные `artifact_id`/`upload_operation_id`; >1 KiB поддерживается базой, одновременно не более восьми вложений.

| Набор | Содержание и назначение |
|---|---|
| `methods-url` | Пять методов и три схемы URL, UTF-8/reserved characters, body и headers. |
| `errors-retry` | 400/408/429/500/wrong-type/delay, transient fail→success и потерянный ответ POST. |
| `simulation-auth` | Файл ответа при пустом ledger, запись запросов; раздельные тестовые auth/TLS профили. |

Oracle: Ledger и заранее заданные серверные ответы проверяют каждый RequestId, URL encoding, байты, число попыток и интервалы; оба выходных порта сравниваются с ожиданием. HTTP 200 не доказывает правильное тело. Не импортирует runtime.

Ограничения `scripts/node-acceptance/expected-outputs.mjs:7-14,29-39,72-81`: до 32 таблиц, до 100 строк на выход; порядок колонок позиционный, строки сравниваются без порядка. Числа точные (`cold-check.mjs:232`, `requireExactNumbers: true`): в первом комплекте только точно представимые суммы/значения, допуск требует отдельного решения. Адресации порта одного узла, переменных и файлов в expected нет. Для нетабличного результата, внешнего ledger и нескольких портов PASS требует принятых W и дополнительного независимого аудита; подмена результата таблицей не доказывает исходный порт/эффект.

Свежесть результата обеспечивает сам cold-check: он заново выполняет узлы сохранённого пакета в новом профиле. Отдельные доказательства происхождения, квитанции и receipts не требуются. Порядок строк, несколько портов одного узла, допуск для вещественных и выход переменных в cold-check добавляет общая карточка LAB-78 (ветка `acceptance-tools`); в ветке узла эти возможности не реализуются.

## 4. Проверки, приёмка и завершение

Адресная матрица охватывает все этапы; строка вне назначенного среза остаётся `not_checked`. Требования до живого исследования документированы, а не наблюдены.

| Проверка | Условие успеха |
|---|---|
| Контракт | Неизвестные поля/режимы, несогласованный тип/связь и параметры следующего этапа отклонены до мутации; ошибка объясняет исправление |
| `integration-restrequest:r01` | Пять методов × три URL схемы: ledger проверяет метод, кодирование, порядок параметров и точные body bytes. Поле body и URL-параметр не получают один binding. |
| `integration-restrequest:r02` | Сверить header/URL по каждому request ID и typed полям; изменение порядка URL-параметров меняет адрес только в query/segments режимах. |
| `integration-restrequest:r03` | Wrong type и 400 дают явную ошибку в допданных; HTTP200 с неверным телом не принимается за аналитический успех. */* проверяется отдельно. |
| `integration-restrequest:r04` | Ledger считает попытки и интервалы при transient fail→success; 400 не повторяется как transient. Учитывать эффект POST при потерянном ответе. |
| `integration-restrequest:r05` | При simulation ledger пуст, ответ равен fixture; сохранённые request-файлы проверяются отдельно и не содержат реальные секреты. Имитация не заменяет live transport case. |
| `integration-restrequest:r06` | Для каждого разрешённого профиля fixture отвечает только после нужной auth; неверный сертификат/credentials дают отказ. Security override не отключается автоматически. |
| Смена источника/настроек | Тот же узел, новая попытка; незапрошенные настройки сохранены, новый результат не подменён прежним |
| Persistence | Сохранение после всех чтений; новый профиль открывает пакет, настройки/связи и результат проверены без восстановления |
| Recovery | Неизвестный внешний эффект не повторён; причина отказа мастера прочитана; собственные эффекты подтверждены независимо |
| Регрессия | Адресные тесты и весь `client/test`; тесты принятого W |

Задание модели: Отправить запросы по requests.csv в предоставленный тестовый сервис, показать ответы и сведения об ошибках, изменить данные в том же источнике, получить новые ответы и сохранить пакет в {{PACKAGE_PATH}}.

PASS исполнителя: CLI, независимый cold-check в пределах поддержанного табличного среза, обязательный аудит портов/эффектов после согласованных W, вся адресная матрица этапа, `package_closed=true`, `logged_out=true`; частичный вывод/preview не даёт PASS. Ловец принимает тот же чистый опубликованный SHA. Реестр отражается только по доказательствам принятой карточки; `integration` и `release` не трогаются.

## 5. Ловушки — переподтвердить, не копировать

Следующие положения взяты из прежнего черновика и Help, их поведение на стенде остаётся гипотезой до этапа 0:

REST connection + необязательная таблица запроса и управляющие переменные → таблица ответов и дополнительных данных. Без входного набора отправляется один запрос; с набором — запрос на строку.

REST: GET/DELETE/POST/PUT/PATCH; URL query/segments/replacement; HTTP/HTTPS; auth «Не требуется», «Имя пользователя и пароль» (Negotiate/NTLM/Basic/Digest), «Basic», «Токен OAuth» (2.0), «Клиентский сертификат из хранилища», «Файлы сертификата клиента». Certificate-store профиль — Windows. TLS enforcement задаёт администратор, а не обработчик.

Контролируемый HTTP(S) echo-сервис с request ledger и endpoints success/400/408/429/500/wrong-content-type/delay. Входные строки содержат UTF-8, reserved URL characters, дату, JSON body. Серверный ledger и заранее заданные ответы — независимый oracle.

Разрешённые native retry — часть настроек пользователя; recovery handler не добавляет ещё один HTTP retry. После lost reply проверять ledger, особенно POST/PUT/PATCH/DELETE. При отмене сохранить корреляцию завершённых и неизвестных запросов.

Порядок отражает пользу: сначала изменяющие API-запросы и headers, затем доступ
к закрытому API и динамические параметры, типы/URL, устойчивость и отладка.
Зависимость от неутверждённого секретного API не вводится: C3 ограничен сохранёнными
оператором подключениями. Создание/смена credentials, client certificates,
отключение TLS verification и доказательство точного числа попыток не готовы
к реализации в этой аддитивной нарезке; условия продолжения перечислены в discovery.
C9 также требует отдельного решения по файловой приёмке: stock CSV подтверждает
ответ сервиса, а не наличие/содержание native request-файлов. Предложение ожидаемых
UTF-8 тел/длин выведено из fixture, исполняемого нового matcher здесь нет.
Неподтверждённое не становится поддержанным вследствие места в таблице.

Для каждого цикла нужны red→green в его production-ветке, адресные и обязательные
проверки затронутых путей, штатные `run-check start` + `wait` и кворум на одном SHA.
В этапе 0 такого red→green и модельного PASS нет: новые параметры пока отклоняет
текущий валидатор, сборка CLI заданием запрещена. Живое UI-исследование не заменяет
проверку будущего обработчика. Save/cold/cleanup остаются штатными.

Общие изменения допускаются только аддитивно: описание новых параметров типа,
перечисления readback, метаданные Var-порта и регистрация новых сценариев в
существующем каталоге приёмки. `dock_node_apply` уже отдаёт модели открытый
объект type-specific parameters, поэтому его сжатая схема не нуждается в новом
механизме. Новые режимы чтения, secret broker, ledger, matcher или рефакторинг
общего графа не включены. Если конкретный цикл потребует их — stop/blocked.

Особенность C1+C6: текущий `restQueryEncoderRequest` выводит только URL-поля.
При совместном запросе тело и header-поля должны сохраниться неизменёнными;
иначе расширение потеряет Body до REST. Исправление ограничивается REST-веткой,
с отдельным наблюдением и тестом на этот совместный случай. Нельзя кодировать
все строковые поля или требовать, чтобы пользователь заранее кодировал Body.
