Разрешено:

1. Живое исследование штатными средствами runtime в собственном аккаунте.
2. Реализация назначенного этапа и только согласованных общих изменений (W1; W2; W3).
3. Приёмочный комплект, PR в ветку задания, публикация доказательств и независимая приёмка.

Не разрешено: merge/релиз; следующие этапы; новые общие контракты без решения владельца; изменение конфигурации обвязки. Внешние объекты и файлы — только собственные объекты из задания.

## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Checkout/SHA и сборка из закоммиченных исходников, `loginom status` = `ready`; квалифицировать внешнюю среду отдельно. Каждый отказ мастера читать из кнопки ошибки.

1. Палитру «Импорт > XML файл», root мастера, обязательный набор XSD/optional переменные и таблицу.
2. Namespace/root и повторяющийся Item, выбранные поля, составные имя/метку/разделитель и дублирование родителя.
3. Строгую XSD/Schematron валидацию: доступность/умолчания, ошибки типа и бизнес-правила.
4. Имена/метки/типы/порядок результата, nil/empty/absent и timezone default/Z/+03:00; момент появления schema.
5. Смену байтов XML/XSD того же узла; wrong namespace/root, corrupt документ, HTTP 401/404 и потерю ответа.

Результат — `discovery.md`: observed/hypothesis, exact значения/типы/имена, границы источника и side effects, решения по W. Выход — `ready_for_development` только после снятия блокеров; закреплённые type/mode, `fixtures/` и `acceptance/` до кода обработчика.

### Этап 1 — самостоятельный первый срез

Scope: Локальный XML и подключённый XSD, точные namespace/root, выбранные элементы/атрибуты, составные имена и дублирование значений родителя. Создание и настройка существующего узла; readback фактически наблюдённых настроек и свежести результата. Неподдержанные формат/порт/режим/тип/параметр отклоняются до мутации с понятным объяснением исправления.

Требования этапа 1 (частичные режимы явно ограничены разделом 1):

- `imports-xml:r01` — Файл, подключение XSD, namespace/root и выбор импортируемых элементов/атрибутов.
- `imports-xml:r02` — Составные имена/метки и разделитель; дублирование единичных родительских значений.

Для бинарного/XML источника использовать admission вложения: `parameters.source.artifact_id` и `upload_operation_id` из завершённой `artifact.upload`, exact bytes/SHA256/destination из server-copy proof; не брать их из текста модели и не синтезировать старый receipt. Контракт text-import-node.mjs:31-63 — образец проверки, поддержка imports.xml пока отсутствует. После reopen читать persisted source без повторной конфигурации и без receipt прежнего процесса; способ квалифицировать этапом 0 и реализовать W. В XML отдельно подтвердить provenance всех XSD.

Файлы: новые `packages/loginom-runtime/client/lib/imports-xml-{node,parameters,procedure,readback}.mjs`, тесты `client/test/imports-xml-*.test.mjs`; регистрация `node-contracts.mjs`/`.d.ts`, `node-support.mjs`, `node-api.mjs`, `node-result-schema.mjs`, `user-results.mjs`. Образец — [Текстовый импорт](../../../../packages/loginom-runtime/client/lib/text-import-node.mjs), не переносить его семантику/формат. Общие `node-procedure.mjs`/`workspace-ui.mjs` меняются только в согласованных W.

Общие изменения, каждый отдельным коммитом с адресными тестами:

- **W1** — контракт XSD-подключения/порта Подключение, точного набора схем/root/namespace; node-contracts/node-api/node-procedure/workspace-ui.
- **W2** — обобщённый источник XML/XSD с verified artifact_id/upload_operation_id и digest/destination каждого файла, persisted source для cold-open; node-api и scripts/node-acceptance.
- **W3** — этап 2: управляющий путь и bindings, provenance URL/HTTP и Schematron-аудит; node-api/node-procedure/workspace-ui и приёмка.

Видимость для модели: `NODE_TYPES.semantics` объясняет бизнес-результат и побочные эффекты; `description` у каждого параметра, строковые enum, компактный readback. Наблюдённые значения отличать от запроса модели.

Тесты из `packages/loginom-runtime`: `bun run test:upstream`; при изменении приёмки — из того же каталога `node --test ../../scripts/node-acceptance/tests/*.test.mjs`. Команды новых адресных тестов закрепить после появления файлов; сейчас они не существуют.

## 3. Данные и независимые проверки

Комплект `nodes/imports-xml/acceptance/` (для следующих этапов `acceptance/stageN/`): `task.md` с `{{PACKAGE_PATH}}`, `data/` только для входов модели, `expected.json` из независимого `oracle.py` до обработчика. Внешние manifests, oracle и ожидания модели не передаются; секреты — только во внешнем окружении.

CSV-спецификации: UTF-8, разделитель `,`, decimal `.`, header, NULL-маркер `\N`; empty string отличается от NULL. `fixtures/manifest.json`: фактические байты/SHA256, типы/метки/порядок и происхождение каждого бинарного файла/внешнего объекта; размер фиксируется при генерации, а не угадывается.

| Набор | Содержание и назначение |
|---|---|
| `items.csv / orders.xml / schema.xsd` | Order с id/datetime и тремя Item; повторяющиеся записи, две ветви с одинаковым leaf-name, два namespace/root, optional/empty/xsi:nil и спецсимволы. |
| `replace.xml / empty.xml` | Другой digest и другие значения того же root; согласованная XSD пустая таблица с полной схемой. |
| `invalid.xml / rules.sch / timezones.xml` | Неверный XSD type и отдельное нарушение Schematron; Z/+03:00 одного момента, naive с/без default timezone. |

Правило orders.xml: Order id=O1 и datetime=2024-02-29T12:30:00Z, три Item с Id=1..3, Name=[А,пустая строка,NULL], Amount=[10,20,25]; NULL представлен xsi:nil только для nillable. Второй parent/root/namespace — самостоятельный fixture, expected не извлекается из выхода Loginom.

Oracle не импортирует handler/runtime, считает по входам, сверяет все ячейки/объекты/байты, имена/метки/типы/порядок полей, NULL/empty/0. Отклоняет старое исполнение, чужой destination/узел и подмену данных; E2E preview/обратный импорт не является независимым эталоном.

Для табличного выхода cold-check сверяет имена/метки/типы и порядок колонок, строки без учёта порядка (`expected-outputs.mjs:14,29-39`), до 100 строк/выход и 32 выходов. Числа точны (`cold-check.mjs:232`); использовать точно представимые значения или отдельно согласованный допуск до прогона. Метаданные видов/назначений и порядок строк требуют отдельного аудита. Выходы связываются по type/label с уникальным node_id (`expected-outputs.mjs:72-81`), port index отсутствует: переменные статуса не покрыты.

## 4. Проверки, приёмка и завершение

Непроведённая проверка — `not_checked`; ожидания/границы фиксируются до модельного прогона.

| Требование / проверка | Независимое условие успеха |
|---|---|
| `imports-xml:r01` | Проверить три Item и только выбранные поля; другой root/namespace не выбирается по похожей метке. |
| `imports-xml:r02` | Два одинаковых leaf-name разных ветвей остаются различимы; флаг duplication сравнить по каждой строке родителя. |
| `imports-xml:r03` | Невалидный тип и бизнес-правило дают разные ошибки; ускоренный режим не объявлять эквивалентом строгой проверки. |
| `imports-xml:r04` | Z и +03:00 одинакового момента дают одинаковую серверную дату; naive с default-zone преобразуется, без неё сохраняется. NULL не смешивать с empty. |
| `imports-xml:r05` | Новый источник подтверждается digest; 401/404 не создают успешную пустую таблицу. Метки/комментарий и привязки воспроизводятся после reopen. |
| Контракт и отказы | Неверные настройки/типы отклонены до эффекта; исходная ошибка мастера сохранена |
| Изменение существующего | Настройки/связи readback подтверждены; новый источник не даёт старый результат; незапрошенные свойства сохранены |
| Persistence | Сохранить после всех чтений; открыть новым профилем без восстановления настроек; внешние эффекты и происхождение проверить по согласованному W |
| Recovery | Потерянный ответ не повторяет неизвестный эффект; результат сверяется независимо перед продолжением |
| Регрессия | Адресные тесты нового узла и полный `client/test`; прежние контракты не ослаблены |

Задание модели: Загрузить приложенный XML по предоставленной схеме, получить таблицу позиций с данными заказа, сохранить различие пустых значений и пропусков, проверить результат и сохранить пакет в {{PACKAGE_PATH}}.

PASS исполнителя: CLI и применимый cold-check/согласованный независимый аудит результата, адресная матрица, `package_closed=true`, `logged_out=true`. Файловый/внешний/переменный результат нельзя объявить принятым неподходящим oracle. Публикация и Ловец принимают тот же чистый SHA по RUNBOOK; `integration` и `release` не меняются.

## 5. Ловушки — переподтвердить, не копировать

Ниже документальные ограничения и требования прежнего черновика; точные controls и runtime-семантика для стенда остаются гипотезами до этапа 0.

Обязательное подключение набора XSD + необязательные управляющие переменные → таблица. Источник: XML-файл либо HTTP(S)/Basic URL.

Независимо написанные XSD/XML: Order с id, datetime и повторяющимися Item; два namespace/root, отсутствующий необязательный элемент, пустая строка, xsi:nil, спецсимволы. Expected 3 item-строки и точные типы задаются до Loginom; XSD/Schematron проверяет отдельный валидатор.

Повреждённый документ/неверная схема требуют исходной ошибки; не переписывать XSD ради прохождения. Проверять byte lineage XML и всех XSD.
