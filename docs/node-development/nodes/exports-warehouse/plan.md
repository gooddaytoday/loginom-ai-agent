## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Checkout/SHA и сборка из закоммиченных исходников, `loginom status` = `ready`; квалифицировать внешнюю среду отдельно. Каждый отказ мастера читать из кнопки ошибки.

1. Палитру «Экспорт > Deductor Warehouse», root мастера, обязательные подключение/таблицу; Help не заявляет выходную таблицу или порт управляющих переменных.
2. Процесс/измерение, типы элементов и точные bindings; ручное/автоматическое связывание и сортировку списков.
3. Удаление не удалять/в списке, агрегации min/max/first/last у процесса; исходный порядок строк.
4. Когда возникает внешний эффект и как проверить фактическую запись; транзакционность/upsert выяснить, не предполагать.
5. Смену источника того же узла, недоступный DW, NULL/типовые ошибки и прерывание частичной записи.

Результат — `discovery.md`: observed/hypothesis, exact значения/типы/имена, границы источника и side effects, решения по W. Выход — `ready_for_development` только после снятия блокеров; закреплённые type/mode, `fixtures/` и `acceptance/` до кода обработчика.

### Этап 1 — самостоятельный первый срез

Scope: Изолированное DW на Firebird, один выбранный объект и ручные связи; основной case — измерение Product, процесс Sales принимается следующим этапом. Создание и настройка существующего узла; readback фактически наблюдённых настроек и свежести результата. Неподдержанные формат/порт/режим/тип/параметр отклоняются до мутации с понятным объяснением исправления.

Требования этапа 1 (частичные режимы явно ограничены разделом 1):

- `exports-warehouse:r01` — Выбор процесса/измерения, атрибутов/измерений/фактов и ручные/автоматические связи.

Источник и подключение выбираются по наблюдённой identity, не по похожей метке. Для внешней БД/Kafka/DW/1С `artifact_id` и `upload_operation_id` не описывают подключение и не заменяют проверку внешнего объекта. Табличные входы экспорта можно доставить принятым текстовым импортом с проверенным upload receipt; загрузка не подтверждает экспортированный результат.

Файлы: новые `packages/loginom-runtime/client/lib/exports-warehouse-{node,parameters,procedure,readback}.mjs`, тесты `client/test/exports-warehouse-*.test.mjs`; регистрация `node-contracts.mjs`/`.d.ts`, `node-support.mjs`, `node-api.mjs`, `node-result-schema.mjs`, `user-results.mjs`. Образец — [Текстовый экспорт](../../../../packages/loginom-runtime/client/lib/text-export-node.mjs), не переносить его семантику/формат. Общие `node-procedure.mjs`/`workspace-ui.mjs` меняются только в согласованных W.

Общие изменения, каждый отдельным коммитом с адресными тестами:

- **W1** — контракт подключения DW и порта Подключение, identity объекта/элементов и readback; node-contracts/node-api/node-procedure/workspace-ui.
- **W2** — приёмка внешней записи DW: before/after, все факты/атрибуты, частичный эффект и execution receipt, без повторного Execute при cold-open; scripts/node-acceptance и тесты.

Видимость для модели: `NODE_TYPES.semantics` объясняет бизнес-результат и побочные эффекты; `description` у каждого параметра, строковые enum, компактный readback. Наблюдённые значения отличать от запроса модели.

Тесты из `packages/loginom-runtime`: `bun run test:upstream`; при изменении приёмки — из того же каталога `node --test ../../scripts/node-acceptance/tests/*.test.mjs`. Команды новых адресных тестов закрепить после появления файлов; сейчас они не существуют.

## 3. Данные и независимые проверки

Комплект `nodes/exports-warehouse/acceptance/` (для следующих этапов `acceptance/stageN/`): `task.md` с `{{PACKAGE_PATH}}`, `data/` только для входов модели, `expected.json` из независимого `oracle.py` до обработчика. Внешние manifests, oracle и ожидания модели не передаются; секреты — только во внешнем окружении.

CSV-спецификации: UTF-8, разделитель `,`, decimal `.`, header, NULL-маркер `\N`; empty string отличается от NULL. `fixtures/manifest.json`: фактические байты/SHA256, типы/метки/порядок и происхождение каждого бинарного файла/внешнего объекта; размер фиксируется при генерации, а не угадывается.

| Набор | Содержание и назначение |
|---|---|
| `warehouse.csv` | Product,Amount: (A,15),(A,5),(C,7) в этом порядке; независимый fixture создаёт Product и Sales со значениями A=10,B=20. |
| `empty.csv / replace.csv` | Та же схема без строк; другой источник с Product=B и Amount=30. |
| `dw-before.json` | Отдельный объект/снимок для каждого case, manifest структуры измерения/процесса и before/after от SQL/DW-клиента. |

Oracle не импортирует handler/runtime, считает по входам, сверяет все ячейки/объекты/байты, имена/метки/типы/порядок полей, NULL/empty/0. Отклоняет старое исполнение, чужой destination/узел и подмену данных; E2E preview/обратный импорт не является независимым эталоном.

Нынешний cold-check принимает только таблицы: `expected-outputs.mjs:2-23`, нет файлов, sink или переменных. `expected.json` этого узла — **предлагаемая** схема external_effects[] с объектом/before/after/operation identity, до W она не принимается обвязкой. Нельзя добавлять фиктивный табличный output или объявлять PASS лишь по входной таблице. W приёмки обязателен перед этапом 1; после cold-open сверять настройки/граф и уже произошедший эффект, не повторять внешнюю запись вслепую.

## 4. Проверки, приёмка и завершение

Непроведённая проверка — `not_checked`; ожидания/границы фиксируются до модельного прогона.

| Требование / проверка | Независимое условие успеха |
|---|---|
| `exports-warehouse:r01` | Измерение получает заданные атрибуты; процесс — нужные измерения и факты. Перестановка столбцов не подменяет назначения. |
| `exports-warehouse:r02` | Проверить старые A/B и новые C по обоим режимам; удаление ограничено выбранными значениями, B остаётся при filter A. |
| `exports-warehouse:r03` | Для A: min5,max15,first15,last5 при закреплённом порядке; другие ключи не смешиваются. |
| `exports-warehouse:r04` | После reopen сверить bindings, затем внешнее состояние на Firebird/MS SQL/Oracle; успешная активация не заменяет сверку записанных фактов. |
| Контракт и отказы | Неверные настройки/типы отклонены до эффекта; исходная ошибка мастера сохранена |
| Изменение существующего | Настройки/связи readback подтверждены; новый источник не даёт старый результат; незапрошенные свойства сохранены |
| Persistence | Сохранить после всех чтений; открыть новым профилем без восстановления настроек; внешние эффекты и происхождение проверить по согласованному W |
| Recovery | Потерянный ответ не повторяет неизвестный эффект; результат сверяется независимо перед продолжением |
| Регрессия | Адресные тесты нового узла и полный `client/test`; прежние контракты не ослаблены |

Задание модели: Загрузить сведения из приложенного файла в выделенное измерение хранилища, правильно сопоставить атрибуты, проверить сохранённые данные и сохранить пакет в {{PACKAGE_PATH}}.

PASS исполнителя: CLI и применимый cold-check/согласованный независимый аудит результата, адресная матрица, `package_closed=true`, `logged_out=true`. Файловый/внешний/переменный результат нельзя объявить принятым неподходящим oracle. Публикация и Ловец принимают тот же чистый SHA по RUNBOOK; `integration` и `release` не меняются.
