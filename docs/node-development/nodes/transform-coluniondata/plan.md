## Этап 1 по отдельному назначению

Первым шагом дозакрыть not_checked: пустой главный и пустой присоединённый
входы, fulltype, точное полное чтение. При расхождении с утверждёнными
ожиданиями остановиться с вопросом; oracle и критерии молча не менять.
Skill интегрировать по структуре LAB-768: строка маршрутизации и файл узла.

Предложение runtime type: `transform.col_union_data`, mode `positional`.
Не использовать прежнее предложение `transform.column_union`.
Компонент по назначению: `component.transform.ColUnionData`;
живые идентификаторы и неподтверждённый fulltype описаны в discovery.

- Логический вход 0 — главная таблица, 1 — присоединённая; выход 0 — таблица.
- Число строк: минимум, максимум, длина главной или присоединённой.
- Дополнение: NULL, циклический повтор всего набора, последняя запись.
- Полная схема сохраняет обе одноимённые колонки. Явный output mapping
  задаёт согласованный порядок и AttachedCode; автоматический суффикс не угадывать.
- Новые параметры: явные row_count/padding и выбранный вход для правила input.
  Существующие параметры — patch; пустой объект сохраняет настройки.
- Execute пересчитывает входы; обучение и применение обученной модели
  не входят в контракт этапа 1.
- Пустые входы, точность, все сочетания размера/дополнения и сохранение
  требуют живого подтверждения; утверждение ожиданий не заменяет проверку.

Реализация: свои `transform-coluniondata-*.mjs` и адресные тесты;
аддитивная регистрация в существующих dispatch/schema/observe/readback;
своя строка skill и `references/nodes/transform-coluniondata.md`;
аддитивные сценарии run-check. Единственная уже установленная потребность
в общей правке — W0; новые общие изменения требуют нового решения.

Обязательные проверки определяет `required-checks.py list --base origin/v040`
по окончательному diff. Для client — полный pinned-Chromium набор;
для оснастки — полный её набор, для runtime/src — полный host bun test.
Регламент: `openai/gpt-6.1-sol`, medium, 1800 с; только run-check start + wait,
cold со скачанным CSV; ≥2 PASS из 3 на одном SHA у исполнителя и независимого
проверяющего. Критерии и W0 утверждены; текущая карточка runtime-код не меняет.
Оценка: 3–4 цикла разработки с новым бизнес-прогоном между циклами;
первый — W0 и два входа, второй — режимы и mappings,
третий/четвёртый — persistence и устойчивость. Пустые входы и точное чтение
исследуются до реализации первым шагом этапа 1.
