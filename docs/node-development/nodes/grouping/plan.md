# 07. Группировка: подплан сопровождения и приёмки

[Карточка и принятые границы](README.md) · [реестр](../../registry.json) · [работа с одним узлом](../../workflow/single-node.md).

Обработчик `transform.group_data` уже реализован в режиме `aggregate`. Этот подплан адаптирует исторический 07 к текущему runtime и standalone CLI: это маршрут адресного исправления, проверки переноса или отдельно назначенного расширения, не повторная разработка с нуля. Историческое принятие сохраняется в своём scope; технические Desktop проверки не являются аналитической CLI-приёмкой. Новых живых наблюдений и прогонов при составлении документа не было, readiness не повышается.

До начала выбрать точное изменение и пройти [подготовку/жизненный цикл](../../workflow/lifecycle.md). Разработчик работает в Astra medium в своей задаче, ветке и worktree. Первичная разработка получает Goal до готовности изменения к первому ревью, без собственного token_budget. Этот документ не назначает следующий узел и не разрешает слияние.

## Узловые требования

Полные упорядоченные списки group_by и measures заменяют соответствующие роли. Непустые ключи до 128; показатели до 256; sum/count/avg/min/max. Один исходный факт может иметь разные функции, но пара поле/функция и выходное имя должны быть однозначны. Ключ группировки нельзя одновременно назначить показателем.

Count в принятой семантике Loginom считает строки, включая NULL/empty; это не SQL COUNT(field). Avg пропуски не учитывает. Для суммы и среднего требуются integer/real; дополнительные агрегаты и grouping без ключей не входят в контракт. Сортировка групп не доказывает сортировку показателя.

## Шаги изменения

1. Воспроизвести изменяемый переход GroupDataWizard/FactorEditDialog и привязку редактора к точному исходному полю; сверить маску функций с текущим GROUPING_FUNCTIONS.
2. До мутации разрешить все group_by/measures по одной полной схеме, проверить типы, конфликт ключа/показателя, имена и точный состав выходного mapping.
3. Задать полные списки и функции, отключая лишние функции по умолчанию. Сверить каждую функцию каждого факта после Apply, включая несколько функций одного поля.
4. Проверить mapping/inline mapping и источник каждого итогового поля. Не подменять нативные свойства факта порядком строки в UI; сохранять незапрошенное кэширование.
5. Расширить конфигурационный verifier и числовой oracle независимо; проследить от input digest через группировочный ключ до полного результата и сохранённого пакета.

## Независимые fixtures и oracle

Ниже — обязательная узловая матрица для объявленного полного scope. При адресном исправлении выбрать затронутые строки и обосновать выбор; расширение режима добавляет новые строки. До автономной попытки сохранить входы и expected отдельно от handler, с версиями и SHA. Ожидания не вычислять импортом реализации и не подгонять по её приёмочному выводу.

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| Пять агрегатов | Region=A: Amount=10, NULL, 20; Region=B: Amount=-5, 0. Дополнительный RowID. | A: count=3, sum=30, avg=15, min=10, max=20; B: count=2, sum=-5, avg=-2.5, min=-5, max=0. Проверять точные типы и значения без зависимости от порядка групп. |
| Несколько ключей/фактов | Region+Product, Amount и Quantity; Amount для нескольких функций. | Независимый dictionary по составному ключу, отдельное множество полей и функций. Изменение одного факта не должно менять другой. |
| Пропуски | Группа только из NULL, пустая строка в строковом поле для count, header-only вход. | Count фиксируется независимо. Для остальных агрегатов all-null/empty взять подтверждённую семантику в отдельной диагностике до autonomous run; не превращать пустое в 0 молча. |
| Редактирование | Убрать один агрегат, добавить другой, поменять порядок; исключить выходной ключ разрешённым mapping. | Нет оставшейся функции по умолчанию; все ожидаемые поля/значения и сохранённая конфигурация совпадают после reopen. |

## Негативные случаи

- sum строки, отсутствующее поле, повтор пары поле/функция, key-as-measure, коллизия output имени и неполный mapping: отказ без частичной настройки.
- Отмена Factor либо всего мастера, потерянный ответ Apply, смена исходного поля при открытом редакторе: не назначать функцию соседнему факту.
- Старый execution, неполное число групп, правильная общая сумма при неверных группах: независимый аудитор обязан отвергнуть.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.

## Автономная проверка и передача

Построить сводку по регионам и продуктам с количеством, суммой и средним, изменить один показатель, сохранить пакет; сравнить все группы и значения с независимым расчётом.

Первичная отладка — штатными скриптами текущего runtime в назначенной изоляции. После неё выполнить адресные source tests и проверить независимый oracle, включая его отказ на подменённых значениях/схеме/идентичности. Только затем подготовить неизменный candidate и получить слот по [CLI-регламенту](../../workflow/acceptance-cli.md): standalone CLI Loginom AI Agent, Sol low, согласованная подписка, бизнес-цель и входные файлы без пошаговых UI-команд.

Критерий аналитического PASS — полный малый output/артефакт, проверенная схема и настройки, новый execution и сохранённый пакет, которые независимо воспроизводятся после отдельного открытия. Configure-only и Close проверяются отдельно; обычный продуктовый путь не переоткрывает мастер ради повторной проверки. Непроверенные платформы, большие наборы и дополнительные режимы остаются явно ограниченными.

Передать checkpoint с точными source/runtime/client/model/platform pins, заявленным scope, результатами и неизменёнными исходными FAIL. Техническое завершение, аналитическая проверка, integration и release — отдельные состояния реестра. Один этап ревью и один раунд исправлений выполняются по общему жизненному циклу; этот подплан не добавляет повторного полного ревью.
