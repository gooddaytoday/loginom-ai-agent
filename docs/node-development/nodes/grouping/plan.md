## 1. Цель и проверенная основа

Цель этапа 0 — подтвердить принятый объём текущим standalone CLI и исправить адресные дефекты. Кросс-таблица изменила общую оболочку, `node-read-*`, `workspace-ui.mjs`, `node-procedure.mjs` и `collapse-native-*`; CLI-регрессии прежних обработчиков не было, unit-тесты её не заменяют.

Принятый объём из реестра: Упорядоченные ключи и меры sum/count/avg/min/max; согласованная схема результата.
Ограничения: Непустые ключи и меры; не более 128 ключей/256 мер. Одно поле не может быть и ключом, и мерой. Нет медианы, distinct count и произвольных статистических тестов в этом контракте. SUM/AVG только integer/real; аналитически правильный выбор агрегации остаётся ответственностью модели и независимого oracle.

Полные упорядоченные списки group_by и measures заменяют соответствующие роли. Непустые ключи до 128; показатели до 256; sum/count/avg/min/max. Один исходный факт может иметь разные функции, но пара поле/функция и выходное имя должны быть однозначны. Ключ группировки нельзя одновременно назначить показателем.

Count в принятой семантике Loginom считает строки, включая NULL/empty; это не SQL COUNT(field). Avg пропуски не учитывает. Для суммы и среднего требуются integer/real; дополнительные агрегаты и grouping без ключей не входят в контракт. Сортировка групп не доказывает сортировку показателя.

## 2. Этапы

### Этап 0 — перепроверка принятого объёма

Подготовка: проверить SHA, собрать кандидата из закоммиченных исходников, получить `loginom status` = `ready` на назначенном стенде.

1. Собрать `acceptance/` из прежнего контракта (раздел 3): независимые ожидания, значения, freshness и отказы сохранить; адаптировать транспорт, pins и receipts к CLI. Прежний launcher Hermes не запускать.
2. Адресные тесты `client/test/grouping-*.test.mjs` (5 файлов), затем весь `client/test`: `bun run test:upstream` в `packages/loginom-runtime`.
3. CLI-сценарий и независимое холодное открытие по RUNBOOK; generic cold-check и адресные дополнения — в разделах 3–4.
4. При расхождении — живая сверка мастера с `?testable=true`; прочитать причину из кнопки ошибки, записать в `discovery.md`; наблюдение не подменять E2E-снимком.
5. Исправить дефект в принятом объёме с адресным тестом; общая оболочка или расширение объёма — стоп-условие.

Выход: PASS исполнителя и независимая приёмка того же SHA; `client_technical_validation` и `analytical_validation` отражаются только по новому результату.

### Адресные действия при FAIL

1. Воспроизвести изменяемый переход GroupDataWizard/FactorEditDialog и привязку редактора к точному исходному полю; сверить маску функций с текущим GROUPING_FUNCTIONS.
2. До мутации разрешить все group_by/measures по одной полной схеме, проверить типы, конфликт ключа/показателя, имена и точный состав выходного mapping.
3. Задать полные списки и функции, отключая лишние функции по умолчанию. Сверить каждую функцию каждого факта после Apply, включая несколько функций одного поля.
4. Проверить mapping/inline mapping и источник каждого итогового поля. Не подменять нативные свойства факта порядком строки в UI; сохранять незапрошенное кэширование.
5. Расширить конфигурационный verifier и числовой oracle независимо; проследить от input digest через группировочный ключ до полного результата и сохранённого пакета.

### Этап 1 и далее — непокрытые режимы Help 7.4 (отдельные карточки владельца)

- Медиана, мода, стандартное отклонение, distinct/missing count, first/last/single.
- Список: integer/string, разделитель/ограничитель, уникальность и ASC/DESC/без сортировки.
- Кэш значений групп и сортировка результата; редактор всех функций, имён и меток.
- Матрица type×aggregate, включая variable там, где разрешает Help.

Перечень будущей полноты сохраняет прежний подплан: частично принятые действия перепроверяются на этапе 0, дополнительные controls/типы/режимы назначаются отдельно; совпавшее название режима не расширяет scope.

## 3. Данные и независимые проверки

Комплект `nodes/grouping/acceptance/` собирает будущая карточка:

- `task.md` на бизнес-языке с `{{PACKAGE_PATH}}`; без имён инструментов и ожидаемых чисел;
- `data/grouping.csv` и остальные указанные ниже CSV — точные копии прежних входов; только входы передаются модели;
- `expected.json` из независимого `oracle.py` до прогона; адресные наборы — `fixtures/` с manifest (байты, SHA, формат, типы, порядок).

Прежние входы: `fixtures/grouping/grouping.csv`: 150 байт, 8 записей, колонки `Group, Segment, Amount, Other, Text`, разделитель `;`; кодировка UTF-8, NULL-маркер `\N`. Размеры и SHA сохранить в manifest до прогона.

Ожидания прежнего контракта: Из `grouping_goal_contract.py`: начальные ключи Group и меры Amount(sum/count/avg/min/max), Text(count); финальные ключи Segment, Group и меры Other(sum), Amount(avg), Text(count). Финальный выход `Group, OtherTotal, MeanAmount, TextRows`, Segment исключён. Count учитывает все строки; all-null sum/avg/min/max → NULL.

Матрица сохранена из прежнего подплана; ожидания и неоднозначные правила переподтвердить до модельного прогона:

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| Пять агрегатов | Region=A: Amount=10, NULL, 20; Region=B: Amount=-5, 0. Дополнительный RowID. | A: count=3, sum=30, avg=15, min=10, max=20; B: count=2, sum=-5, avg=-2.5, min=-5, max=0. Проверять точные типы и значения без зависимости от порядка групп. |
| Несколько ключей/фактов | Region+Product, Amount и Quantity; Amount для нескольких функций. | Независимый dictionary по составному ключу, отдельное множество полей и функций. Изменение одного факта не должно менять другой. |
| Пропуски | Группа только из NULL, пустая строка в строковом поле для count, header-only вход. | Count фиксируется независимо. Для остальных агрегатов all-null/empty взять подтверждённую семантику в отдельной диагностике до autonomous run; не превращать пустое в 0 молча. |
| Редактирование | Убрать один агрегат, добавить другой, поменять порядок; исключить выходной ключ разрешённым mapping. | Нет оставшейся функции по умолчанию; все ожидаемые поля/значения и сохранённая конфигурация совпадают после reopen. |

Oracle не импортирует handler/runtime, рассчитывает по исходным байтам, сверяет все ячейки и схему, отличает NULL/пустую строку/0, отвергает чужой узел, старое исполнение, неполное чтение и подмену данных. Freshness, происхождение и настройки доказываются отдельно от правильных значений.

Cold-check: схема проверяется позиционно (имена, метки, типы), строки — как мультимножество, до 100 строк/выход и 32 выходов (`scripts/node-acceptance/expected-outputs.mjs:14,29-39,72-81`). Числа сравниваются точно (`cold-check.mjs:232`); большие Int64 — десятичные строки. Каждый ожидаемый выход однозначно связан с типом и меткой узла. E2E-снимки мастера не являются oracle.

## 5. Ловушки — переподтвердить, не копировать

- sum строки, отсутствующее поле, повтор пары поле/функция, key-as-measure, коллизия output имени и неполный mapping: отказ без частичной настройки.
- Отмена Factor либо всего мастера, потерянный ответ Apply, смена исходного поля при открытом редакторе: не назначать функцию соседнему факту.
- Старый execution, неполное число групп, правильная общая сумма при неверных группах: независимый аудитор обязан отвергнуть.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.
- Исторический аудит 07: FactorEditDialog модален и находится вне корня мастера; одной отмеченной функции недостаточно — лишние функции по умолчанию выключаются и сверяются для каждого факта.
- Приёмки текущего CLI нет; неподтверждено: all-null/пустой вход, параметры функций и mapping текущего CLI. Исторические замеры/локаль/платформа не являются гарантией текущего стенда.
