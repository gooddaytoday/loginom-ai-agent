## 0. Как выполняется назначение

Оркестрация — Multica, сквад «Обработчики узлов»: Генератор тасок готовит назначение, Тест-Манки #1 разрабатывает и проходит приёмку, Ловец Галюцинаций независимо принимает опубликованный SHA.

Карточка:

```text
Ветка: <ветка задания>
Узел: datamining-arimax
Обработать узел по его подплану до независимой приёмки. Объём — этап <N> подплана.
```

Первая карточка — этап 0 отдельно: он решает, какие общие изменения нужны этапу 1 (обучение узла, допуск сравнения вещественных чисел). Этап 1 назначается после решения владельца по W1 и W2.

В ветке задания должны быть `docs/node-development/RUNBOOK.md`, этот подплан и инструменты приёмки (`scripts/node-acceptance/cold-check.mjs`, сборка `--no-archive`). Отсутствие — Blocked.

### Объём назначения

Разрешено:

1. Живое исследование стенда (этап 0) штатными средствами runtime в собственном аккаунте.
2. Реализация назначенного этапа и согласованных владельцем общих изменений: W1 (обучение и переобучение узла), W2 (сравнение вещественных выходов с заранее заданным допуском).
3. Приёмочный комплект, PR в ветку задания, публикация доказательств, независимая приёмка.

Не разрешено: merge и релиз; следующие этапы; общие изменения без решения владельца; чтение выходного порта переменных до этапа 2; изменение конфигураций обвязки.

## 1. Цель и проверенная основа

Согласованные решения:

- Узел строит модель временного ряда по одному прогнозируемому вещественному непрерывному полю и добавляет прогноз на горизонт вперёд. Порядок ряда задаётся порядком строк: узел не сортирует.
- Этап 1 — ручная несезонная структура (p, d, q, константа), горизонт, ошибка аппроксимации, доверительный интервал; выходы «Выход модели» и «Коэффициенты модели».
- Обучение — отдельное действие Loginom («Обучить» / «Переобучить», E2E `teach_node.ts`). В runtime его нет ни у одного обработчика: это общее изменение W1.
- Прогноз — вещественные числа, которые oracle не воспроизводит побитно. Cold-check сравнивает числа точно (`cold-check.mjs:232`, `requireExactNumbers: true`): нужен W2 — допуск, объявленный в `expected.json` до прогона, — или узловой аудит поверх readback.

## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Подготовка: checkout и проверка SHA, сборка кандидата из закоммиченных исходников, `loginom status` = `ready` на назначенном стенде.

Наблюдать и закрепить; каждый отказ мастера — с причиной из его кнопки ошибки:

1. Палитру, точный заголовок мастера, порты, страницы мастера.
2. Обучение: что делает Execute необученного узла, когда нужен «Переобучить», что меняет смена параметров или источника; сохраняется ли обученная модель в пакете.
3. Умолчания p, d, q и границы: Help пишет «больше 0», проверить 0 для каждого порядка.
4. Имена, метки и типы полей «Выхода модели» (`<поле>|Прогноз`, `|Ошибка аппроксимации`, `|Нижняя граница`, `|Верхняя граница`) и их порядок относительно входных; число строк при горизонте h.
5. Схема и состав «Коэффициентов модели» для p=1, d=0, q=0 с константой и без.
6. Детерминированность: два обучения на одном входе дают одинаковые коэффициенты и прогноз.
7. Отказы: NULL в ряде, два прогнозируемых поля, целочисленный ряд, слишком короткий ряд.
8. Момент появления выходной схемы — до или после обучения.

Результат — `discovery.md` рядом с подпланом: таблица семантики «наблюдено / гипотеза» с конкретными значениями, решение по W1 и W2 для владельца. Выход этапа 0: статус `ready_for_development`, закреплённые runtime type и режим, `fixtures/` и `acceptance/` — до кода обработчика.

### Этап 1 — ручная несезонная модель

Scope:

- Параметры: прогнозируемое поле, `p`, `d`, `q` (границы — из этапа 0), `constant`, `horizon ≥ 1`, `residuals`, `confidence` (уровень 0..100 или выключен).
- Создание, обучение, перенастройка и переобучение существующего узла; повторное выполнение после смены источника.
- Readback: структура, горизонт, флаги, факт обучения на текущем источнике.
- Отказ до мутации: больше одной цели, нецелые порядки, горизонт < 1, внешние факторы, сезонность, автоподбор, нормализация. Тексты ошибок объясняют исправление: их читает модель.

Файлы: новые `packages/loginom-runtime/client/lib/arimax-{node,parameters,procedure,readback}.mjs` и тесты `client/test/arimax-*.test.mjs`; изменить `node-contracts.mjs` и `.d.ts`, `node-support.mjs`, `node-api.mjs`, `node-procedure.mjs`, `workspace-ui.mjs`, `node-result-schema.mjs`, `user-results.mjs`. Два табличных выхода — по образцу чтения портов Фильтра строк (`read.ports=[0,1]`).

Общие изменения (решение владельца до назначения):

- **W1** — обучение и переобучение узла: действие, readback факта обучения, отказ выполнения необученной модели; отдельным коммитом с тестами.
- **W2** — допуск сравнения вещественных колонок в `expected-outputs.mjs`, объявляемый в `expected.json` по колонке; без допуска поведение прежнее.

Видимость для модели: `semantics` — «прогноз временного ряда; порядок строк задаёт время; требуется обучение»; `description` у каждого параметра; в `user-results.mjs` — модель сортирует вход отдельным узлом.

Тесты из пакетов: `bun run test:upstream` в `packages/loginom-runtime`; `node --test scripts/node-acceptance/tests/*.test.mjs` при W2.

### Этап 2 и далее (отдельные карточки)

- Этап 2 — автоподбор структуры по AIC, сезонность (P, D, Q ≥ 0, период > 0), выход «Сводка» (TotalSamples, RMSE, MAE, MAPE, AIC/AICc/BIC, R², DF). Требует чтения выходного порта переменных — общее изменение.
- Этап 3 — внешние факторы (горизонт 1 и явное игнорирование при горизонте ≥ 2) и нормализация непрерывных и дискретных полей.

## 3. Данные и независимые проверки

Приёмочный комплект `nodes/datamining-arimax/acceptance/`:

- `task.md` на бизнес-языке с `{{PACKAGE_PATH}}`;
- `data/demand.csv` — единственный вход модели;
- `expected.json` — из независимого `oracle.py` до обработчика, допуски — до прогона.

Формат входов: UTF-8, разделитель `,`, десятичный `.`, заголовок в первой строке, без NULL.

`demand.csv`: `Period` (целый номер 1..64) и `Demand` (real) — 64 заранее вычисленные точки `y[t] = 10 + 0.5·(y[t-1] − 10) + e[t]` с фиксированным массивом `e`, записанные с 4 знаками.

Адресные наборы — в `fixtures/` с `manifest.json`:

| Набор | Содержание и назначение |
|---|---|
| `ar1.csv` | Тот же ряд; p=1, d=0, q=0 с константой |
| `ar1-noconst.csv` | Ряд с нулевым средним; константа выключена |
| `trend.csv` | Линейный тренд + шум; d=1 |
| `short.csv` | Ряд короче, чем нужно для p+d+q — ожидаемый отказ |
| `null.csv` | NULL в ряде — ожидаемый отказ |
| `replace.csv` | Тот же состав полей, другой ряд — смена источника и переобучение |

Независимый oracle:

- не импортирует код обработчика и runtime;
- проверяет число строк (исходная длина + горизонт), имена, метки, типы и порядок колонок;
- прогноз пересчитывает рекурсией по коэффициентам, прочитанным из «Коэффициентов модели» того же исполнения, с допуском `atol=1e-6`;
- оценки коэффициентов сравнивает с эталонной реализацией (statsmodels, закреплённая версия) только при совпавшей целевой функции и инициализации, `rtol=1e-4`; иначе — только знак, порядок величины и `|φ| < 1`;
- проверяет `lower ≤ forecast ≤ upper`, остаток = факт − подгонка после установления знака;
- отклоняет старое исполнение, модель, обученную на другом источнике, и чужой узел.

Ограничения источников: cold-check сверяет порядок, имена, метки и типы колонок, строки — без учёта порядка, до 100 строк на выход (`scripts/node-acceptance/expected-outputs.mjs:14,29-39`): горизонт и длина приёмочного ряда выбираются так, чтобы выход был ≤ 100 строк.

## 4. Проверки, приёмка и завершение

Адресная матрица; непроведённая проверка — `not_checked`:

| Проверка | Условие успеха |
|---|---|
| Контракт | Неподдержанные параметры отклонены до мутации; ошибка объясняет исправление |
| Обучение | Выполнение после обучения даёт прогноз; смена параметров требует переобучения по наблюдению этапа 0 |
| Прогноз | Длина = вход + горизонт; прогноз совпадает с рекурсией по коэффициентам в допуске |
| Коэффициенты | Состав строк для p/d/q и константы совпадает с наблюдением этапа 0 |
| Ошибка и интервал | Колонки появляются только при включённых флагах; `lower ≤ forecast ≤ upper` |
| Смена источника | `replace.csv` в том же импорте; переобучение даёт новые коэффициенты, без него — по правилу этапа 0 |
| Persistence | Сохранение после всех чтений; новое открытие и выполнение без восстановления настроек и обучения |
| Recovery | Неизвестный эффект не повторяется; отказ мастера читается из кнопки ошибки |
| Регрессия | Весь `client/test` |

Задание модели (бизнес-язык, без имён инструментов и ожидаемых чисел): по `demand.csv` построить прогноз спроса на 6 периодов вперёд моделью авторегрессии первого порядка с константой, показать прогноз с доверительным интервалом 95 % и коэффициенты модели, затем добавить ошибку аппроксимации на том же узле, выполнить, показать все строки и сохранить пакет в `{{PACKAGE_PATH}}`.

PASS исполнителя: приёмка обвязки (CLI, cold-check с W2, `package_closed=true`, `logged_out=true`) и адресная матрица. Публикация, независимая приёмка и отражение в реестре — по RUNBOOK; слои `integration` и `release` не трогаются.

## 5. Ловушки — переподтвердить, не копировать

- Модель может считать прогноз Калькулятором или Скользящим окном: проверить по протоколу, что создан узел ARIMAX.
- Help: с внешними факторами прогноз только на 1 период, для горизонта ≥ 2 используется ARIMA без факторов — это должно быть видно модели-пользователю, а не скрыто.
- Help требует «больше 0» для p, d, q, но ARIMA допускает 0 — правило берётся только из наблюдения этапа 0.
- Применение не должно скрыто переобучать модель; переобучение не должно молча оставлять старые коэффициенты.
- Не уменьшать горизонт и не отключать флаги молча ради PASS.
