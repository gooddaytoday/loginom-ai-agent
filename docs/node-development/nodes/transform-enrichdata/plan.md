## 1. Подтверждённая основа

На стенде Loginom 7.4.2 есть «Трансформация → Дополнение данных».
Нативный fulltype TBGEnrichDataEngine, VendorGuid
0370e80a-78e1-4ede-b71b-930497994b44; собственный пакет сверён по GUID с UI.
Мастер EnrichDataWizard, два исходных табличных входа и Input_Add,
один табличный выход 0, обычный Execute без обучения.
При двух справочниках логические входы 0/1/2 соответствуют SVG
Input_Data-0/1/3 при создании и Input_Data-0/1/2 после открытия; FPortIndex
третьего табличного входа — 2.

Все связи идут от ключей главной таблицы; right-key поля исключаются.
NULL ключи совпадают, дубликаты порождают все сочетания; unmatched главные
строки сохраняются с NULL справа. Входы main/B-duplicates/C (6/6/5 строк)
дали 13×7 с точным совпадением Python oracle, включая NULL/пустую строку
и двоичные дроби. Смена B на совместимый B без дубликатов дала 8×7 на том же
узле. Полная схема, причина нативного отказа и пределы наблюдения — discovery.md.

Прямые образцы базы: Join — ключи/проверка схем;
Union — динамические входы, field grid, prefixes, полный cached readback.
Обработчика transform.enrich_data в базе нет; реестр готовности не меняется.

## 2. Этапы

### Этап 0 — исследование и приёмочный комплект

Подготовлены discovery.md, fixtures/manifest.json, бизнес-задания,
независимый oracle.py и expected до модельных прогонов.
Предложены NODE_TYPES semantics, parameter_schema с descriptions каждого поля,
компактный readback, файл навыка и строка маршрутизации.
Документы proposal не поставляются runtime и не объявляют доступность handler.

### Этап 1 — основная таблица и до двух справочников

- r01: точные совместимые ключи каждого справочника непосредственно с главной
  таблицей, в том числе составной ключ; полные identities входов и портов.
- r02: выбор свободных/всех совместимых полей, исключение правых ключей,
  буквальные name/label prefixes, уникальные фактические имена результата.
- r03: NULL/unmatched/duplicates, типы/точность/порядок полей, повторное
  выполнение после смены справочника на том же узле, Save/cold и cleanup.

Полный публичный запрос переиспользует имеющиеся inputs/mappings/read/finish.
Новый parameter namespace enrichment описан в parameter-schema.proposal.json;
mode — только left, enum строковый. Новый узел требует полный список таблиц,
ключей и настроек префиксов. При изменённых inputs нужна полная конфигурация;
пустые parameters на существующем узле сохраняют лишь поддержанные настройки
с неизменными источниками. Неподдержанное отклонять до мутации.
Технические имена output сверять с нативным readback, не выводить из меток.

Файлы реализации: собственные enrichdata node/parameters/procedure/context/
readback и адресные тесты client; аддитивные schema/types/dispatch/readback
и stage/observer регистрации, собственный файл references/nodes/transform-enrichdata.md.
Для новых динамических входов зарегистрировать enrichdata в уже существующем
списке типов с ordinal/native-index binding и в type-specific mapping/overflow
ветках. Алгоритм, owner/GUID guards и поведение Union не менять.
Новых общих механизмов не выявлено; если type-only регистрации недостаточно,
остановиться до общей правки. Оценка — 2 цикла с новым бизнес-прогоном в каждом.

Дальнейший объём не назначен: третий и последующие справочники, другие
соединения, произвольные преобразования ключей и переменные не входят в этап 1.

## 3. Предложенные oracle и критерии

Основное task: main + B + C → тот же EnrichData после замены B на duplicates
→ выполнение → Save. Независимые ожидания: single 6×6, initial 8×7,
final 13×7. Отдельный composite/task — один справочник, ключ Code+Zone,
7×4; живой составной результат пока not_checked.
Пустые входы, case/locale строк и удаление динамических портов не выдаются за
наблюдённую работоспособность. Адресная матрица и отрицательные проверки —
acceptance/README.md; новые критерии сверх этого среза согласовываются отдельно.

Выход 0, exact порядок полей через явный выходной mapping с autosync=false;
при autosync=true после открытия наблюдалась перестановка Key перед RowID.
ordered=false для полного мультимножества строк.
Integer/string/NULL точны; real abs=rel=0 для этих двоичных дробей без расчётов.
Незаданные метки label_any=true; заданные LookupName/LookupRate проверяются точно.
Никакого специального reader, receipts или доказательств происхождения не нужно:
существующий cold-check заново выполняет сохранённый граф в новом профиле.

Приёмка одного опубликованного SHA: cold PASS; >=2/3 PASS исполнителя и
отдельные >=2/3 на том же SHA под независимым аккаунтом своей пары;
package_closed=true, logged_out=true. Проверки по изменённым путям:
required-checks.py list --base origin/v040 и verify по итоговому отчёту;
полный client с pinned Chromium, acceptance tests при затронутой оснастке.
Прогоны через run-check; deadline и лимиты не расширяются.
