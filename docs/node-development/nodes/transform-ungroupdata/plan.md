## 0. Назначение и ограничения

Действует регламент сквада из Multica. Описание LAB-771 — отдельный этап 0,
прямое назначение; пара — путь из карточки. Исследуются только собственные
пакеты этой пары на `https://app.loginom.ai/app/?testable=true`, элементы
по `data-tid`. Сборка CLI и код runtime на этапе 0 исключены.

Объём владельца: два входа, распределение групповых итогов по явно заданным
опорным долям. Вычисляемые доли и сезонность не входят в этап 1.

Модель при будущих прогонах — `openai/gpt-6.1-sol`, medium, 1800 с,
существующий `scripts/node-acceptance/run-check.py`, без собственной обвязки.
Источник и target PR — `v040`; короткая ветка без слэшей.

## 1. Подтверждённая семантика

Вход 0 — уникальные итоги групп, вход 1 — опорные позиции с готовыми долями.
Настройки: связи групп, одно разгруппируемое поле, поле наименования,
поле доли, округление и балансировка. Native умолчание вычисляет доли,
поэтому новый shares-handler обязан явно переключить метод.

Основной выход 0 содержит исходные поля итогов, округлённый итог, наименование
позиции и OutputValue. Native выход 1 качества/индексов остаётся вне чтения
этапа 1. Отдельное обучение не потребовалось; Execute считает текущие входы.

Без округления/балансировки — Total × max(Share,0) без нормирования.
NULL Total и NULL Share пропускаются, NULL наименование сохраняется.
NULL-ключи совпадают, пустая строка отдельно; unmatched группы не дают деталей.
Порядок — исходные итоги, затем опорные позиции внутри группы. Пустой вход
даёт активную пустую таблицу с полной схемой. Дубликаты ключей итогов дают
объяснимый native отказ, а не несколько повторённых распределений.

Подробные численные наблюдения, страницы, data-tid, типы и границы уверенности
зафиксированы в discovery. Наблюдение UI не объявляет поддержку runtime.

## 2. Этап 1 — только заданные доли

Собственный handler, чистая проверка параметров, UI writer и компактный
readback. Lifecycle двух входов брать из Слияния; табличные роли/выполнение —
из Группировки. Не переносить семантику чужого узла.

Предлагаемые случаи:

- `ungroup-shares`: основной результат 13 строк, NULL/пустая строка,
  ненормированные/нулевые/отрицательные доли, unmatched;
- `ungroup-rounding`: precision=0, все четыре балансировки и multiple=3;
- `ungroup-null`: NULL доли/наименования и различный порядок групп входов;
- `ungroup-empty`: активный пустой результат с полной схемой.

У нового узла все роли и политики явные. Существующий `parameters:{}`
сохраняет поддержанную конфигурацию. Повторное выполнение с новыми данными
источников той же схемы не требует перенастройки Разгруппировки. Неизвестный
эффект не повторяется; причина отказа читается из native кнопки/статуса.
Вычисляемые веса, сезонный метод, переменные и чтение порта 1 отклоняются
до мутации. Границы первоначально проверенных типов указаны в contract.

Разрешённые точки: собственные `transform-ungroupdata-*.mjs` и тесты,
аддитивная регистрация типа/схемы/диспетчера/readback, собственный файл навыка
с коротким маршрутом, сценарии run-check. Если понадобится общая правка
сверх этого, публичный контракт, бюджет или deadline — stop и вопрос.

## 3. Приёмочный комплект и решение по W

Все входы малы, UTF-8 CSV с запятой, десятичной точкой, кавычкой и NULL `?`.
Manifest задаёт байты, SHA256, типы, порядок и назначение каждого файла.
Task написаны на языке пользователя; oracle и expected в модельный контекст
не передаются. Oracle использует только Python csv/Decimal, без Loginom.

Expected задаёт ordered=true, output_port=0, column_order=exact и допуск
real abs=1e-12 / rel=1e-12. Метки, не заданные task, — label_any.
Проверяются все поля и строки, а не только сумма распределения.
Критерии полной серии, CSV, Save, cold-check, cleanup и независимой проверки
точного SHA — в acceptance/README.md; до утверждения это предложение.

Старый W1 для добавления допуска устарел: текущая база уже имеет числовые
допуски, порядок и identity порта. Новые механизмы проверки не требуются.
W2/W3 сезонного режима к этому этапу не относятся.

Обязательные проверки будущих изменённых путей — required-checks.py list
по базе и verify по отчёту; полный client с pinned Chromium, при правках
оснастки — её набор. Этап 0 меняет только этот узловой каталог.
