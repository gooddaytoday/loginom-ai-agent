## Вычисление долей

Собственная страница `WizrdMCF;UngroupDataWizard`:
`pedUngroupMethod;ValueControl;boundlist;С_расчетом_долей_по_всей_выборке`.
Два входа и два выхода сохраняются. Роли не переименовываются: Weight
назначается как «Поле с долями», Item — «Поле с наименованиями»;
Group слева перетаскивается на Group справа, Total — «Разгруппируемое».
Редакторы ролей — `grdUngroupColumns` / `grdSupportColumns;tbl;celleditor;cbx`.
Без округления и балансировки выбранные параметры сохраняются через Next.
Мастер перешёл к описанию узла; штатный Execute дал активные результаты.

На `fixtures/weights-totals.csv` и `weights-support.csv` повторяющиеся
наименования внутри группы агрегированы: G/a имеет веса 1+2, G/b — 3+6.
Доля равна сумме весов позиции / сумме весов группы. Выход 0 — четыре строки
G/a=25, G/b=75, H/c=20, H/d=60, в порядке групп итогов и первого появления
позиций в опоре. Это отличается от shares: там готовые доли не нормируются.

Чтение: `Graph;<узел>;Output_Data-0` → `mn;mniShowDataPreview` →
`ModelForm;PreviewWindow;PreviewForm;DataSetForm;normalHeaderCt`.
Схема: Group:string, Total:integer, Total_Rounded:integer, Item:string,
OutputValue:integer. CSS заголовков — `dtString-before` / `dtInteger-before`.
Тип результата для произвольного real-входа этим опытом не устанавливается.
Все проверенные значения целые и не требуют вывода о точности дробного preview.

Выход 1 прочитан отдельно тем же способом: ноль строк, поля в порядке
Item:string, Group:string. Это не таблица рассчитанных долей и не второй
распределённый результат. Непустые сезонные показатели требуют своего опыта.

## Приёмочный комплект

`acceptance/task-weights.md`, `acceptance/oracle-weights.py`,
`acceptance/expected-weights.json`: независимый Fraction-oracle по CSV,
без импорта Loginom, runtime или фактического результата. Проверяются оба
порта, все значения, типы, порядок, повторное Execute, CSV/Save/cold/cleanup
и стандартные 2/3 + независимые 2/3 на одном SHA после утверждения владельцем.
Модель получает только task и два CSV; expected и oracle остаются проверяющему.
Предложение ограничено положительными целыми весами с ненулевой суммой
и точно целыми результатами; отрицательные веса, NULL и нулевая сумма
не заимствуют семантику shares без отдельного наблюдения.

## Сезонный срез: состояние исследования

Метод присутствует в списке: «С учётом временных колебаний и сезонности
опорных данных». В DOM создана дополнительная страница `UngroupDataWizard-1`
с `txtUngroupColumn`, `txtSupportColumn`, `pedSeasonalityPeriod`,
`pedSeasonalityMultiplier`, `pedNumSeasonalIndexes`, `pedMaxRareDensity`,
`pedAbsentPeriodFraction`, `pedAbsentDataPoints`, `pedNoveltyPeriodFraction`,
`pedMaxDepthPeriodFraction`, `pedMaxDepthDataPoints`. До перехода на неё
пустые input не являются умолчаниями. Видимость/значения и результат
этой страницы ещё не установлены. Переключение метода само по себе
не доказывает обучение или точность индексов.

Подготовлены `fixtures/seasonal-{totals,support}.csv` (2 и 72 строки):
три года месячной опоры с чередованием a:b=1:3 / 3:1 и два будущих итога.
`acceptance/task-seasonal.md` — черновое бизнес-задание. Числа 25/75
для января и 75/25 для февраля — лишь гипотеза нормированного месячного
профиля; native сезонный estimator может учитывать тренд, глубину и редкость.
Они не записываются как эталон Loginom. Полного expected сезонных портов
пока нет: схема/метрики выхода 1 и соглашение периодов требуют наблюдения.
При настройке уже выполненного узла наблюдалось подтверждение деактивации;
затем в `msgbox;cnt` — «Обнаружен разрыв связи. Восстановить сессию?».
