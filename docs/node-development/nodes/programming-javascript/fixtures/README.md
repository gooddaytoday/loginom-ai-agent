# Данные и спецификация oracle JavaScript

[Подплан](../plan.md). Эти материалы подготовлены до реализации handler.
Они не являются доказательством прохождения Loginom.

## Что уже подготовлено

- `model-input/sales.csv`: 6 строк, 5 колонок, UTF-8, comma, header,
  double-quote qualifier. RowID/Qty/UnitPriceCents/DiscountPct — integer,
  Customer — string. Кодировка, разделитель и типы должны быть подтверждены
  в импортированном источнике, а пробелы Customer — сохранены до JS.
- `model-input/task.md`: бизнес-задача первого автономного прогона.
  Уникальный путь пакета сообщается при запуске. Готового JS, графа, tool calls
  и числовых ответов в задании нет.
- `operator-only/expected.json`: независимый ожидаемый результат 6×4,
  порядок полей/строк и значения каждой ячейки. Все денежные расчёты этого
  случая точные целочисленные, допуск равен нулю.
- `operator-only/sales-changed.csv`: отличается количество в строке RowID=1;
  ожидаемые значения заданы заранее, нужен новый execution без переписывания
  JS под ожидаемый ответ.
- `operator-only/sales-reordered.csv`: те же логические записи с другим
  порядком входных колонок. Проверка обращения по фактическим technical names.
  Подготовить отдельный подтверждённый импорт с теми же именами/типами/значениями;
  простая замена FileName в старом импортере может сохранить индексные mappings
  и исказить вход ещё до JavaScript.
- `operator-only/empty.csv`: header-only, ожидается 0 строк и полная схема.
- `operator-only/typed-cases.json`: спецификация нативных fixtures для
  NULL/empty/Unicode, boolean, real, безопасных и небезопасных int64,
  civil datetime и изменения количества строк. **Это не готовый файл импорта.**
- `manifest.json`: SHA-256 файлов, проверяется до каждой попытки.

## Изоляция модельного задания

Каталог fixtures в репозитории — место разработки доказательств, не workspace
модели приёмки. В отдельную чистую рабочую папку копируются только `sales.csv`
и `task.md`; они передаются CLI отдельными `--file`. Не передавать весь каталог,
manifest с oracle, этот README, `operator-only`, research, план, e2e LGP или
Python-аудитор. В промпте не раскрывать пути к expected.

Для автономного fixed-schema случая создать второе задание из тех же бизнес-
правил, заменив только требование формирования схемы кодом на заранее заданную
структуру выходного набора. Остальные входы/ожидания неизменны. Проверять режим
по конфигурации, а не по совпадению чисел. Оба прогона занимают общий CLI-слот
последовательно; каждый имеет собственные session/attempt/package.

## Независимая проверка

Oracle не импортирует JavaScript handler и не исполняет сгенерированный моделью
код вне Loginom. Бизнес-ожидания рассчитаны отдельно: стоимость количества
уменьшается на заданный процент скидки; нормализация клиента убирает только
краевые пробелы и переводит регистр. Не изменять ожидаемый результат после
просмотра результата модели. Сумма — вспомогательный инвариант, она не заменяет
сравнение всех строк, типов и порядка.

До `ready_for_acceptance` ещё требуется реализовать узловой аудитор,
подготовить typed `.lgp`/входы на живом сервере и подтвердить способ полного
readback. Для дат хранить native serial bytes и civil components, не
приписывать UTC; для int64 брать десятичные строки/байты, не пропускать их
через обычный JSON number в JavaScript. NULL отличать от 0, false, пустой строки
и строк «null»/«NULL». Преобразование обеих входных форм null/undefined в NULL
проверять как отдельный runtime probe.

Отрицательные проверки самого oracle: неверная ячейка при прежней сумме,
потерянная/дублированная строка, перестановка строк/полей, string вместо integer,
другая связь порта, старый execution, другой source SHA, старый код, обрезанное
чтение, неподтверждённый save и пакет, открытый без нового исполнения.
