## Объём

Этап 0 — наблюдение реально добавляемого узла и всех пяти табличных выходов,
схема и смысл метрик, независимый oracle, задания и expected, измерение размеров.
Наличие узла подтверждено; это не одноимённый визуализатор. Сырой пакет,

Этап 1 — реализация **после утверждения этого предложения**. Текущий PR содержит
только документы, входные CSV и независимый oracle. Сборка CLI и модельная
приёмка в этап 0 не входят. Действует актуальный регламент сквада: модель
`openai/gpt-6.1-sol`, medium, 1800 с; живые прогоны только через run-check.

## Предложенный контракт profile

Один табличный вход 0; все его поля используются. Подтверждённые типы/виды:
integer/real — непрерывные, string — дискретный. Иные комбинации до мутации
отклоняются как неподдержанные. `parameters: {}`; отдельного мастера алгоритма
нет. Не вводить несуществующие параметры метода, порога или обучения.

Все пять результатов читаются из одного выполнения:

| Порт | Имя | Наблюдённая штатная конфигурация |
|---:|---|---|
| 0 | OutData — Выходной набор | Исходные поля и строки сохранены |
| 1 | OutDataOut — Выбросы | Пуст, включая набор с положительным Out |
| 2 | OutDataExtr — Экстремальные значения | Пуст, включая набор с положительным Extr |
| 3 | OutDataNull — Пропуски | Все исходные строки; не фильтр строк с NULL |
| 4 | SummaryTable — Итоговая таблица | По одной строке на входное поле |

Порядок полей и строк проверяется точно. NULL не равен нулю или пустой строке.
Метрики и соглашения — в discovery и oracle; особенно: N — номер поля,
Median — верхнее среднее наблюдение, числовая Moda — центр интервала гистограммы,
Moda имеет объявленный тип variant. Не обещать исправление данных по названиям
портов или по скрытым заводским настройкам.

Compact readback: режим; входные имена/метки/типы/виды/роли в их порядке;
привязки пяти выходов и фактически проверенные отображения столбцов.
Не повторять схемы одинаковых выходов в нескольких разделах. Параметры движка,
невидимые в мастере, помечать как недоступные UI-readback. Известное заводское
умолчание не выдавать за наблюдённую настройку существующего узла.
Readback не доказывает выполнение, точность variant или сохранение пакета.

## Разрешённая общая правка и дополнительные решения

В комментарии LAB-774 от 2026-11-04 разрешена адресная правка
`client/lib/workspace-ui.mjs` **на этапе 1**: пять страниц Quality, привязка
к владельцу/выходу, сохранение guards. Распознавание страниц Квантования
`binning_ranges_mapping` не меняется. Обязательны red→green на обоих семействах,
регрессия `preprocessing.binning`: тест и один живой прогон.

Дополнительно обнаружены ограничения базы, которые нельзя скрыть регистрацией:

- `node-api.mjs` допускает в read только порты 0…2, максимум три. Для Quality
  нужны 0…4 и пять; предложить адресный допуск нового типа с сохранением
  ограничений остальных типов, включая `dock_node_read`. До реализации
  подтвердить объём этой адаптации публичного контракта.
- Обычный Table-reader не подтверждает точное значение и subtype Moda/variant.
  Имеющийся private exact variant reader разрешён для Collapse port 0,
  до 50 строк/8 столбцов/400 ячеек; перенос права на Quality port 4 не разрешён
  автоматически. До реализации согласовать адресное использование существующего
  декодера для одной колонки Moda, без расширения общих численных пределов,
  либо другой утверждённый способ точной проверки. Текст Table не заменяет его.
- Штатный helper открытия Table отказал до Add для пятого порта при 1280×800;
  ручное раскрытие через data-tid и больший viewport позволили чтение. На этапе 1
  нужен проверенный способ раскрытия порта при штатной геометрии; новую общую
  правку сверх разрешённой отдельно согласовать по наблюдаемому отказу.

Бюджеты схемы измеряются, а не увеличиваются. Перестройку SKILL.md выполняет
LAB-768; здесь предложены только строка маршрутизации и отдельный файл узла
в новой структуре. Не исправлять общий бюджет, deadlines или packages/agent.

## Этап 1: последовательность

1. Утверждение критериев и перечисленных дополнительных общих адаптаций.
2. Аддитивная регистрация типа/режима/parameter_schema/readback; node-specific
   обработчик по образцу `research.duplicates` и `research.corr_analysis`.
3. Разрешённое распознавание страниц Quality с native owner/port binding.
   Поддержать штатные пропуски пустых страниц, не фабриковать страницу/реф.
4. Пять портов, поля и точные variant-значения; проверка обновления источника
   на том же узле; сохранение без повторной настройки при cold reopen.
5. Строка и файл навыка из model-contract, сценарии run-check из acceptance.
6. Проверки по изменённым путям (`required-checks.py list`/`verify`), полные
   необходимые наборы, один живой binning, затем приёмка двух сценариев Quality.

Минимальный ориентир — 4 цикла: reader/регистрация; пять результатов и точность;
живые сценарии и обновление; save/cold и регрессия. Это оценка, не обещание PASS.

## Приёмка и статусы

| Требование | Проверка |
|---|---|
| research-quality:r01 | Палитра, native TBGQualityEngine, один вход/пять выходов |
| research-quality:r02 | Документированный смысл каждого выхода и каждой метрики |
| research-quality:r03 | Все ячейки/типы/NULL/порядок пяти портов по независимым expected |
| research-quality:r04 | Обновление того же импорта/узла, сохранение и cold без повторной настройки |

Задания на языке пользователя; модели выдаются только task и соответствующие
CSV в data/. Oracle/expected/model-contract ей не передаются. По стандарту
исполнитель получает ≥2 PASS из 3 на одном SHA и cold PASS; независимая приёмка —
отдельно на том же SHA своей разрешённой парой. Никаких численных PASS по
discovery, экранной округлённой Moda или предыдущему SHA.

Завершение этой карточки — docs-PR и предложение критериев. Слияние, релиз,
закрытие карточки и назначение этапа 1 остаются отдельными действиями.
