## 0. Как выполняется назначение

Оркестрация — Multica, сквад «Обработчики узлов»: Генератор тасок готовит назначение, Тест-Манки #1 разрабатывает, Ловец Галюцинаций независимо принимает опубликованный SHA.

```text
Ветка: <ветка задания>
Узел: research-quality
Обработать узел по его подплану до независимой приёмки. Объём — этап <N> подплана.
```

Первая карточка — этап 0 отдельно; этап 1 после решения владельца по W3. В ветке задания обязательны RUNBOOK, подплан и инструменты CLI-приёмки (`scripts/node-acceptance/cold-check.mjs`, сборка `--no-archive`).

### Объём назначения

Не разрешено: merge и релиз, следующие этапы, новые общие контракты без решения владельца, изменение конфигураций обвязки.

### Стоп-условия

Каждое оформляется как Blocked с конкретным вопросом Генератору:

- в ветке задания нет обязательных документов или инструментов;
- аккаунты или CLI не `ready` на назначенном стенде;
- неизвестный исход операции: сохранить попытку, writer marker не удалять;
- в палитре нет «Качество данных» либо native component/fulltype не совпал;
- нет решения владельца по W3, если изменение нужно назначенному этапу;
- внешняя среда недоступна либо открыт одноимённый визуализатор вместо компонента Quality;
- недоступны полные результаты/свежесть/независимый oracle; это не PASS.

## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Подготовка: проверить checkout/SHA, собрать кандидата из закоммиченных исходников, получить `loginom status = ready`. UI только штатными средствами runtime с `?testable=true`; каждый отказ мастера прочитать из его кнопки ошибки.

1. Палитра «Качество данных», точный заголовок и корень мастера, native component/fulltype, входы/выходы и их виды, все страницы.
2. Отдельного узла нет в оглавлении Help; визуализатор имеет другое назначение. Подтвердить компонент Quality и именно пять портов либо historical_only без удаления исторической записи.
3. Умолчания и границы каждого элемента мастера этапов 1+; зависимые/disabled настройки, NULL/пустая строка, пустой вход, неподдержанный тип.
4. Имена, метки, типы и порядок всех выходных полей; момент появления схемы до/после Execute или обучения; все порты одного исполнения.
5. Никакой train/apply семантики не присваивать до подтверждения конкретного компонента.
6. Тот же узел после замены файла существующего импорта: свежие значения и схема, необходимые явные retrain; не пересоздавать узел для обхода.
7. Фиксированный seed (если элемент seed доступен) и два повторных расчёта/обучения на одинаковом входе; при недетерминированности заранее закрепить проверяемые инварианты и допуски. Для random/uniform воспроизводимость состава проверяется в рамках гарантий Help, без копирования чужого PRNG.
8. Ожидаемые отказы из раздела 5; неизвестный эффект сохранить, не повторять автоматически.

Результат — `discovery.md`: конкретные значения с пометками «наблюдено / гипотеза», решения по W3, схема портов/соответствия полей и численный oracle. `ready_for_development` только после закрытия вопросов назначаемого среза и согласования общих изменений; `fixtures/` и `acceptance/` готовятся до кода. Для Quality исследовательский отчёт сам по себе не повышает аналитический статус.

## 3. Данные и независимые проверки

Комплект `nodes/research-quality/acceptance/` (следующие этапы — `acceptance/stageN/`): `task.md` с `{{PACKAGE_PATH}}`, `data/` только с входами модели, `expected.json` из независимого `oracle.py` до обработчика; oracle и ожидания вне workspace модели.
Формат: UTF-8, заголовок в первой строке, разделитель `,`, десятичный `.`, NULL `?`; пустая строка отличается от NULL. `fixtures/manifest.json` фиксирует типы, порядок, байты, SHA256, формат и версии вычислительных зависимостей.

Данные: diagnostic.csv: RowID (integer)=1..8, Value (real)=1,1,2,?,3,4,100,0; Class (string)=A,A,B,B,A,B,пустая строка,?; Note (string) включает Unicode. Fixture только для discovery: никаких ожидаемых чисел неизвестным выходам.

| Набор | Содержание и назначение |
|---|---|
| основной CSV из описания | самостоятельные данные для среза этапа 1; не требует соседнего нового обработчика |
| `empty.csv`, `null.csv`, `invalid.csv` | заголовок без строк; NULL/пустая строка; границы/несовместимые типы и параметры |
| `replace.csv` / `update.csv` | те же имена/типы, заведомо другие значения; переисполнение того же узла |
| `holdout.csv` | для обучаемых: новые RowID вне обучения, применение сохранённой модели без скрытого fit |

Каждое требование сопоставлено независимой проверке; адресные данные создаются по основному правилу с минимальным изменением для указанной границы. Expected и допуски фиксируются до проверяемой попытки.

| Требование | Адресный набор | Независимая проверка и ожидаемый результат | Доказательство |
|---|---|---|---|
| `research-quality:r01` | `stage1-r01.csv` / manifest + oracle | Снимок палитры и native identity показывает именно component.research.Quality; назначение/число/тип всех портов записаны, либо подтверждён historical_only. | Полный readback, expected и квитанция исполнения; до прогона |
| `research-quality:r02` | `stage1-r02.csv` / manifest + oracle | Ни одно поле из статьи визуализатора не переносится без доказательства; открытый пробел имеет owner, вопрос и условие продолжения. | Полный readback, expected и квитанция исполнения; до прогона |
| `research-quality:r03` | `stage2-r03.csv` / manifest + oracle | После discovery дополнить этот же подплан отдельными требованиями: каждый режим, параметр и выход сопоставлен fixture/oracle; до этого этап не ready. | Полный readback, expected и квитанция исполнения; до прогона |
| `research-quality:r04` | `stage2-r04.csv` / manifest + oracle | Независимая проверка всех фактических выходов, а не скриншот визуализатора. Любой недоступный выход сохраняет NOT_RUN. | Полный readback, expected и квитанция исполнения; до прогона |

Независимый oracle не импортирует runtime/handler и не использует фактический результат текущего прогона как expected. Проверяет все ячейки, схему, типы, порядок полей и происхождение; IDs/строки/Boolean/NULL точны. Отрицательные подмены одного значения, типа, связи, источника и модели обязаны нарушить проверку.

`research-quality:s1` принимает только исследовательский результат: идентичность/редакцию компонента, наблюдённые типы портов и источник семантики либо доказанное историческое положение. Oracle вычислений и реализованный handler относятся к `research-quality:s2`. Исследовательское завершение первого этапа не повышает аналитический статус узла; если сведения недоступны, сохраняются вопрос, владелец и условие продолжения.
Подготовить диагностический табличный fixture с RowID, NULL, пустой строкой, дубликатами, двумя значениями категорий и выбросом. Он служит материалом discovery; заранее приписывать пяти выходам числа нельзя. После установления смысла портов отдельный независимый oracle рассчитывает подтверждённые показатели, а отрицательный тест подменяет один выход. Полное содержание оставшегося этапа обусловлено устранением расхождения источников.
Expected, формулы oracle, допуски и отрицательные подмены (значение/тип/порядок/связь/модель/источник) закрепить до модельного прогона. Не вычислять expected импортом handler и не выводить их из фактического результата проверяемой попытки. Непрерывные допуски применяются только к указанным числам; identity, Boolean, NULL, строки, количество и схема сравниваются точно. Раздельно хранить входы для модели и oracle/expected вне её workspace. Для `research-quality:s2` нужны пустой вход, границы типов, Unicode, повторный запуск, смена исходника и save/reopen в релевантном режиме.
`research-quality:s1` завершается проверенным исследовательским отчётом по r01/r02. `research-quality:s2` готов к разработке после закрытия discovery вопросов и фиксации независимых expected; готов к аналитической приёмке после handler, адресных тестов и проверенного oracle; принимается только объявленный stage scope. Полное покрытие узла требует всех строк всех этапов. Исторические результаты другого SHA/режима не переносятся. Checkpoint не длиннее 20 строк: SHA, принятый scope, проверенные результаты, ограничения, следующий stage/trigger. Реализация, интеграция и выпуск остаются отдельными состояниями; слияние и выпуск требуют отдельной команды владельца.

Cold-check базы: до 100 строк/выход и 32 ожидаемых выхода (`expected-outputs.mjs:8,14`), поля позиционно, строки без учёта порядка (`:29-39`); порядок проверяет отдельный ordered oracle. Числа сравниваются точно (`cold-check.mjs:232`, `expected-outputs.mjs:70`): W2 нужен для заранее объявленных допусков, где результат не представим точно.
`matchExpectedOutputs` (`expected-outputs.mjs:72-81`) сопоставляет type/label и уникальный node_id без индекса порта: outputs[] не принимает несколько портов одного узла. Полная приёмка нескольких табличных портов требует W3; для переменных — W4. До их реализации не объявлять такие результаты PASS.

## 4. Проверки, приёмка и завершение

Адресная матрица; непроведённые проверки — `not_checked`:

| Проверка | Условие успеха |
|---|---|
| Контракт/режимы | Все требования назначенного этапа проверены, неподдержанные настройки отклонены до мутации с причиной |
| Полные выходы | Каждая ячейка и все порты из одного свежего исполнения, схема/метки/типы и требуемый порядок совпали |
| NULL/границы | Пустой/ошибочный вход даёт заранее наблюдённый результат/отказ, NULL не заменён нулём |
| Изменение существующего | Readback сохранил незапрошенные настройки, режимы и связи; без подмены другим узлом |
| Lifecycle/источник | Никакой train/apply семантики не присваивать до подтверждения конкретного компонента. После смены данных проверены новый source identity и полный результат |
| Недетерминированность | Seed/повторяемость и объявленные допуски проверены без подгонки после FAIL |
| Persistence | Сохранение после всех чтений; cold reopen и выполнение, модель/настройки не восстанавливаются вручную |
| Recovery | Неизвестный эффект не повторён, причина отказа прочитана, собственный пакет/аккаунт закрыт |
| Регрессия | Адресные тесты и весь `client/test`; тесты изменённых общих контрактов и приёмки |

Задание модели: После подтверждения узла исследуйте качество таблицы diagnostic.csv, покажите все документированные результаты, обновите данные и повторно выполните тот же узел. Сохраните пакет в {{PACKAGE_PATH}}. До установления контракта это задание к приёмке не допускается.

Исследовательское завершение этапа 1 — отчёт по идентичности/семантике с доказательствами, без численного PASS. Для реализованного этапа 2 PASS исполнителя: CLI, независимый cold-check после нового открытия, адресная матрица и oracle; `package_closed=true`, `logged_out=true`. Публикация чистого SHA и независимая приёмка той же головы — по RUNBOOK. Discovery/исторический PASS/skip не заменяют реализацию; `integration`/`release` не повышаются.

## 5. Ловушки — переподтвердить, не копировать

- Отсутствующий компонент/редакция, открытие визуализатора вместо узла, неподтверждённые пять портов. В этих случаях остановить только этот этап как discovery_required; не удалять историческую запись.
- Для обучаемых узлов обучение/применение/выполнение и идентичности источника/модели разделены; старые данные или модель не принимаются как свежие.
- Схема CrossTable sliding разрешена только его режиму: право менять схему автоматически другим узлам не переносится.
- E2E-снимки preview и `:toreview` не являются численным oracle; LGD-тесты адаптируются на самостоятельный CSV.
- Указанные элементы мастера и предлагаемая схема параметров не наблюдались на стенде; значения и ошибки закрепить до кода.
