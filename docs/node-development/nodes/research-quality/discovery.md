# Качество данных: частичное исследование LAB-774

Дата: 2026-11-03 UTC. База: `v040@2910b8782c1ad8c016c6fc478369ddd179457e3e`.
Статус: `discovery_required`, этап 0 заблокирован стоп-условием карточки

## Наблюдено на стенде

Исследование выполнено на `https://app.loginom.ai/app/?testable=true`
под worker назначенной пары LAB-774, в собственном новом несохранённом пакете.
Штатная подготовка runtime подтвердила Loginom **7.4.2**, Linux/Chromium.
Использован имеющийся runtime `caf11bdc7368944bc69007a01d190e16723f4c82`
для входа и подготовки; отдельно UI-reader вызван непосредственно из
исходников назначенной базы `2910b878`. Новая CLI-сборка не создавалась.

Палитра содержит «Исследование → Качество данных»:
`MF;TF-1;ModelForm;colVendors_Компоненты>Исследование>Качество_данных;TreeText`.
Компонент добавлен перетаскиванием; на графе наблюдены
`MF;TF-1;Graph;Качество_данных`, значок `bg-vendor-icon-quality`,
`Input_Data-0` и `Output_Data-0` … `Output_Data-4` под тем же префиксом узла.
Это узел сценария с одним табличным входом и пятью табличными выходами.
У native-графа также есть служебный вход subtype 4; это не второй табличный вход.

Открытие настройки показало информационное сообщение: отдельного мастера
для «Качество данных» нет, доступны страницы настройки полей и описания узла.
Контроллер содержит пять `DerivedDataSourceMappingEngineOutputPortWizard`
и `DoneWizard`. Первая страница соответствия открылась; кнопка «Далее»
перевела на вторую. Отказ мастера не наблюдался: `btnError` скрыта.
Присутствие скрытого элемента `btnError` не принимается за ошибку.

## Блокирующее расхождение reader

После перехода на вторую страницу непосредственно наблюдён:

```text
owner_context.node.label = Качество данных
visible data-tid = MF;TF-1;WizrdMCF;DerivedDataSourceMappingEngineOutputPortWizard-1;btnAddMappingColumn
wizard.stage = binning_ranges_mapping
wizard.stage_status = observed
```

Результат получен штатным `makeWorkspaceUiCode(mode=observe, scope=wizard)`
из production-исходников `2910b878`, после завершения перехода.
Это диагностическое чтение, не модельный прогон и не численный PASS.

Причина: `packages/loginom-runtime/client/lib/workspace-ui.mjs:335`
относит указанный суффикс `-1` к `binning_ranges_mapping` без различения Quality.
Список `output_mapping` на строке 341 допускает только вариант без суффикса.
Выбор mapping form на строке 1403 также использует точное имя без суффикса.
У Quality в native-контроллере присутствуют формы без суффикса и `-1` … `-4`;
последующие страницы через общий reader ещё не проверялись.

Для реализации понадобится адресная правка **общего** reader: различать
владельца Quality и дискретизацию, связывать текущую страницу с её выходом,
распознавать соответствующую форму и читать её столбцы. Существующие guards,
сроки и поведение других узлов должны сохраняться. Это выходит за разрешённые
аддитивную регистрацию типа, свой раздел навыка и сценарий run-check.
Правка не выполнена; исследование остановлено по условию назначения.

## Что ещё не установлено

Native fulltype `component.research.Quality` не прочитан; он остаётся ожидаемой
идентичностью, а `research.quality` — предложением runtime type. Не установлены
имена и смысл пяти выходов, схемы, метрики, порядок, типы, точность, NULL,
train/apply, повторное выполнение и сохранение/повторное открытие.
Отсутствие отдельной страницы настройки не доказывает отсутствие обучения.
Статистики одноимённого визуализатора контрактом компонента не объявляются.

`fixtures/diagnostic.csv` подготовлен как вход исследования: 8 строк,
4 столбца `RowID,Value,Class,Note`, UTF-8, запятая, десятичная точка,
NULL-маркер `?`, кавычки `"`. Предполагаемые типы: integer, real, string, string.
Есть Unicode, повторяющиеся значения, ноль, 100, NULL и отдельно `""`.
Файл доставлен в личный каталог worker; импорт и Quality не выполнялись.

Приёмочные `task.md`, независимый oracle и `expected.json` не сформированы:
без семантики выходов они закрепили бы выдуманный контракт. Модельных прогонов,
Save и cold-check не было. После разрешения общего изменения требуется закончить
discovery, предложить независимую формулу каждой наблюдённой метрики и только
затем зафиксировать все пять `output_port`, `ordered` и допуски до приёмки.
Значения NULL, строки, типы, размеры и целые числа предлагается сверять точно;
вещественные допуски и порядок требуют наблюдения и утверждения.
