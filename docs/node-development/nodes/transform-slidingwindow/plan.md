## 1. Подтверждённый контракт

Один табличный вход 0 и выход 0. Обучения и отдельного apply-состояния нет:
узел копирует значения предыдущих и следующих записей текущего входа.
Время задаёт порядок строк, сортировки и агрегирования нет.
Смена источника и повторная активация работают без перенастройки окна.

Для каждого выбранного поля: history и horizon — целые 0…134217727.
0/0 сохраняет поле без смещённых копий; все нули дают проходной узел.
Граница подтверждена редакторами, огромные окна не выполнялись.
Пустой редактор нормализуется в 0; API принимает только явные целые числа.

H = максимальная история полей, F = максимальный горизонт, N = число входных строк.

| Политика API | UI | Число строк |
|---|---|---:|
| keep_incomplete | Оставлять неполные записи | N + H + F, включая N=0 |
| drop_added | Удалять добавленные неполные записи | N |
| drop_all_incomplete | Удалять все неполные записи | max(0,N-H-F) |

Последняя политика удаляет структурные края, а не настоящие NULL внутри ряда.
Ни исходный NULL, ни NULL в лаговом поле сами по себе строку не удаляют.
В добавленных записях исходные поля пусты; доступные смещённые значения сохранены.
NULL отличен от 0, false и пустой строки.

Типы integer, real, string, boolean, datetime у лагов совпадают с источником.
Имена: Field_H_n / Field_F_n; метки: исходная метка[-n] / [+n].
На свежем узле внутри каждого поля идут история от наиболее далёкой к ближайшей,
исходное поле, затем горизонты по возрастанию. Порядок исходных полей сохраняется.
При уже созданном выходе новые поля могут добавляться в конец; удалённые лаги
исчезают. После открытия пакета автосинхронизация восстанавливает естественный
порядок. Reader обязан брать фактическую схему своего выхода, не угадывать порядок.

## 2. Объём этапа 1

- Новый и существующий узел; один режим lag, несколько полей, три политики.
- windows при наличии заменяет весь список: неуказанные поля получают 0/0.
  Пустой список явно сбрасывает окна. На существующем узле пропуск windows
  сохраняет список; пропуск incomplete_records сохраняет политику.
  Новый узел требует оба параметра явно.
- Перед мутацией: неизвестные/повторные поля, дробные, отрицательные, строковые
  числа, превышение границы, неизвестная политика и привязки переменных отклоняются
  с объяснением исправления. Все нули разрешены.
- Компактный readback: incomplete_records, windows из field/history/horizon,
  output_port=0 и фактические name/label/type/source_field/offset выходных полей.
- Схема доступна через настройку выхода после Done без Execute; значения читаются
  после подтверждённого выполнения. Проверять Save и повторное открытие отдельно.
- Управляющие переменные, Variant, агрегаты, сглаживание, обучение — вне этапа 1.

Образец: createTabularTransformNodeSupport и обработчик «Дата и время».
Свои node/parameters/procedure/readback и читатель собственного мастера;
в общих файлах — аддитивная регистрация типа, режима, стадии/наблюдений и выходов.
Своя секция loginom-automation и сценарий существующего run-check.
Необходимости менять общий reader, порядок alignReadSchema, бюджет, deadline,
packages/agent или публичный общий контракт исследование не показало.
Если реализация выявит такую необходимость — стоп по карточке/регламенту.
