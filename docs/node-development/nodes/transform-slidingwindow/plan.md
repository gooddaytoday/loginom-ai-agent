## 1. Цель и проверенная основа

Согласованные решения:

- Узел добавляет к каждой входной записи значения выбранных полей из предыдущих (глубина истории) и последующих (горизонт прогноза) записей. Время задаёт порядок входных строк, а не поле даты: узел не сортирует.
- Этап 1 — весь мастер без управляющих переменных: несколько полей с собственными глубиной и горизонтом, три способа обработки неполных записей, создание и перенастройка существующего узла, повторное выполнение после смены источника.
- Этап 2 — способ обработки неполных записей через управляющую переменную. Отдельная карточка: runtime пока не настраивает порт управляющих переменных.
- Это не «Сглаживание» и не скользящее среднее: агрегатов нет, выход — смещённые копии значений.

## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Подготовка: checkout и проверка SHA, сборка кандидата из закоммиченных исходников, `loginom status` = `ready` на назначенном стенде.

Ориентиры из E2E — переподтвердить на стенде, не копировать:

- палитра `ModelForm;colVendors_Компоненты>Трансформация>Скользящее_окно`; мастер `WizrdMCF;SlidingWindowWizard`;
- строка поля `colDisplayName_<имя>`, редактор строки `grdColumns;roweditor;colHistory_num` и `colForecast_num`, применение кнопкой Update редактора сетки;
- способ обработки `pedIncompleteRecordsProcessing;ValueControl` со списком «Оставлять неполные записи», «Удалять добавленные неполные записи», «Удалять все неполные записи»; переключатель управляющей переменной `pedIncompleteRecordsProcessing;SwitchButton`;
- без входной связи выполнение даёт ошибку «Скользящее окно: Порт "Входной источник данных" не настроен».

Наблюдать и закрепить; каждый отказ мастера — с причиной из его кнопки ошибки:

1. Палитру, точный заголовок мастера (нужен для `node-target-browser`), порты.
2. Способ обработки по умолчанию. В первом E2E-сценарии способ не выбирался, а 12 строк при окне 6+6 дали пустую таблицу — это указывает на «Удалять все», но остаётся гипотезой.
3. Допустимые глубина и горизонт: 0, верхняя граница, отрицательные и пустые значения; одно поле с горизонтом 0.
4. Имена и метки выходных полей. E2E: `Month_H_<n>` с меткой `Месяц[-n]`, `Month_F_<n>` с меткой `Месяц[+n]`. Порядок полей: в E2E — от `[-n]` до `[+n]` вокруг исходного поля; положение остальных полей входа — наблюдать.
5. Типы смещённых полей для integer, real, string, boolean, datetime: совпадают ли с исходным.
6. Число и состав добавленных записей при «Оставлять»: по Help (глубина 2, горизонт 1) и E2E (6 и 6) в начале добавляется столько записей, каков горизонт, в конце — какова глубина. Значения невыбранных полей в добавленных записях — NULL (в примере Help дата пустая).
7. «Удалять все» при настоящем NULL во входе: удаляется ли запись с исходным NULL в смещённом поле. Help говорит о «пустых значениях в добавленных полях» — неоднозначно.
8. Разные окна у двух полей: какие записи считаются неполными при каждом способе.
9. Момент появления выходной схемы — до или после Execute; смена глубины существующего узла меняет схему.
10. Смену файла в существующем импорте и повторное выполнение того же узла без перенастройки: схема прежняя, значения новые.

Результат — `discovery.md` рядом с подпланом: таблица семантики «наблюдено / гипотеза» с конкретными значениями. Выход этапа 0: статус `ready_for_development`, закреплённые runtime type и режим, `fixtures/` и `acceptance/` — до кода обработчика.

### Этап 1 — окна полей и обработка неполных записей

Scope:

- Один табличный вход и выход. Параметры: список полей с `history` и `horizon` (целые, границы — из этапа 0), способ `keep_incomplete` | `drop_added` | `drop_all_incomplete`.
- Создание узла и перенастройка существующего: список окон заменяется целиком; поля без окна — 0/0.
- Readback: способ, окна по полям, соответствие «исходное поле + смещение → выходное поле».
- Отказ до мутации: неизвестное поле, повтор поля, значение вне наблюдённых границ, все окна нулевые, неподдержанный способ, попытка управляющей переменной. Тексты ошибок объясняют исправление: их читает модель.

Файлы:

- новые `packages/loginom-runtime/client/lib/sliding-window-{node,parameters,procedure,context,readback}.mjs` и тесты `client/test/sliding-window-*.test.mjs`;
- изменить `node-contracts.mjs` и `.d.ts`, `node-support.mjs`, `node-api.mjs` (enum `target.type` и `mode`, schema), `node-procedure.mjs`, `workspace-ui.mjs`, `node-result-schema.mjs`, `user-results.mjs`.

Образец — Дата и время (`date-time-*.mjs`): тоже добавляет вычисляемые поля к входу. Табличная оболочка — `createTabularTransformNodeSupport` (`client/lib/calculator-node.mjs:38`). Схема выхода при неизменных окнах статична, поэтому строгая `alignReadSchema` (`client/lib/node-read-contract.mjs:78`) подходит без изменений; если этап 0 покажет иное — стоп-условие.

Видимость для модели:

- `semantics` в `NODE_TYPES`: «смещённые копии полей из предыдущих и следующих записей; порядок строк задаёт время; не сглаживание и не агрегат». Иначе модель возьмёт Калькулятор или Сглаживание.
- `description` у каждого поля `parameter_schema`, строковые enum способа.
- В `user-results.mjs`: узел не сортирует; при необходимости модель сортирует вход отдельным узлом.

Тесты из пакетов: `bun run test:upstream` в `packages/loginom-runtime` — весь набор как регрессия.

### Этап 2 — управляющая переменная способа обработки (отдельная карточка)

- Порт управляющих переменных (по умолчанию скрыт, см. E2E 3183) и привязка способа к целой переменной: E2E — 0 «Оставлять», 1 «Удалять добавленные», 2 «Удалять все».
- Изменение значения переменной и повторное выполнение того же узла.
- Требует поддержки портов переменных в runtime; объём и владелец общего изменения согласуются с владельцем до назначения.

## 3. Данные и независимые проверки

Приёмочный комплект `nodes/transform-slidingwindow/acceptance/`:

- `task.md` на бизнес-языке с `{{PACKAGE_PATH}}`;
- `data/sales.csv` — единственный вход модели;
- `expected.json` — из независимого `oracle.py` до обработчика.

Формат входов: UTF-8, разделитель `,`, десятичный `.`, NULL-маркер `?`, заголовок в первой строке. Подтверждение размера вложений больше 1 KiB (W2 Кросс-таблицы) входит в базу `dada8010e`; если ветка задания его не содержит — стоп-условие.

`sales.csv`: `Month` (строка `2025-01`…`2026-02`, 14 записей в порядке времени), `Sales` (integer), `Price` (real, значения с шагом 0,25 — точно представимы). Без NULL.

Адресные наборы — в `fixtures/` с `manifest.json` (байты, SHA256, формат, типы, порядок строк):

| Набор | Содержание и назначение |
|---|---|
| `help-example.csv` | Пример из Help: 6 месяцев, продажи 45, 82, 120, 192, 229, 161; глубина 2, горизонт 1 — все три таблицы Help как ожидания |
| `series.csv` | RowID 1..5, X = 10, 20, 30, 40, 50; глубина 1, горизонт 1. «Удалять все» → RowID 2, 3, 4 с окнами (10, 20, 30), (20, 30, 40), (30, 40, 50) |
| `types.csv` | Поля integer, real, string, boolean, datetime с окном 1/1 — типы выходных полей |
| `null-inside.csv` | Настоящий NULL в середине ряда — семантика «Удалять все» (п. 7 этапа 0) |
| `two-windows.csv` | Два поля с разными окнами — неполные записи (п. 8) |
| `short.csv` | Записей меньше суммы окна — пустой результат при «Удалять все» |
| `empty.csv` | Только заголовок |
| `replace.csv` | Тот же состав полей, другие значения — смена источника без перенастройки |

Независимый oracle:

- не импортирует код обработчика и runtime;
- строит окна по порядку строк CSV и способу обработки, отдельно для каждого поля;
- проверяет все ячейки, число строк, имена, метки и типы; NULL не равен 0;
- отклоняет старое исполнение, чужой узел, сдвиг на одну позицию, перепутанные `[-n]`/`[+n]` и потерянные добавленные записи.

Ограничения источников:

- cold-check сверяет порядок, имена, метки и типы колонок, а строки — без учёта порядка; до 100 строк на выход (`scripts/node-acceptance/expected-outputs.mjs:14,29-39`). Значения окна в каждой строке это частично компенсируют; порядок строк проверяется адресной матрицей по readback.
- Каждый ожидаемый выход должен однозначно сопоставиться одному узлу по типу и метке (`COLD_OUTPUT_NOT_UNIQUELY_MATCHED`, `expected-outputs.mjs:72-81`): в приёмочном пакете один узел Скользящего окна или разные метки.
- E2E использует LGD-импорт, который агент не поддерживает; приёмка идёт через текстовый импорт. Ожидания E2E — снимки быстрого просмотра, а не oracle.

Задание модели (бизнес-язык, без имён инструментов, enum и ожидаемых чисел): подготовить из `sales.csv` выборку для модели прогноза продаж — для каждого месяца продажи трёх предыдущих месяцев и следующего месяца и цену предыдущего месяца; сначала показать все записи вместе с неполными, затем на том же узле оставить только полные записи, выполнить, показать все строки и поля и сохранить пакет в `{{PACKAGE_PATH}}`. Ожидаемый финальный результат — 14 − 3 − 1 = 10 записей, если этап 0 подтвердит правило полноты для разных окон; иначе `expected.json` пересчитывается oracle по наблюдённому правилу.

PASS исполнителя: приёмка обвязки (CLI, cold-check, `package_closed=true`, `logged_out=true`) и адресная матрица. Узлового аудита протокола не требуется. Публикация, независимая приёмка и отражение в реестре — по RUNBOOK; слои `integration` и `release` не трогаются.

## 5. Ловушки — переподтвердить, не копировать

- Модель может решить задачу Калькулятором с функциями смещения или Сглаживанием: проверить по протоколу, что создан именно узел Скользящего окна.
- Окно зависит от порядка строк: сортировка входа другим узлом меняет результат; узел сам не сортирует.
- При «Оставлять» строк больше, чем на входе: чтение должно возвращать полный результат, а не первые `sample_rows`.
- Добавленные записи не имеют значений невыбранных полей: oracle и cold-check не должны путать их с исходными записями.
- Числа сравниваются точно (`requireExactNumbers`): в `Price` только точно представимые значения.
