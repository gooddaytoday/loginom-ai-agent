## Входы, выходы и семантика

Выполнение узла применяет настройки базового компонента к новым входным данным. Базовый узел при этом не выполняется. Порты наследуются; собственная конфигурация и переобученная модель должны быть отделены от базовой.

## Реализация и зависимости

`node-contracts.mjs` отклоняет межсценарные связи; `node-workflow-activation.mjs` не реализует вход в Подмодель. Расширять подготовленные refs и навигацию с доказательством владельца; обычный input link не превращать в межсценарный обход. Контекст выбора базового компонента, доступ и сохранённая конфигурация требуют отдельного reader; совпадение меток не является идентичностью.

Подключение реализации включает согласованные изменения `node-contracts.mjs/.d.ts`, `node-support.mjs`, `node-api.mjs`, `user-workflow.mjs` и чтения результата в `user-results.mjs`. Все пути — относительно `packages/loginom-runtime/client/lib/`. Новые UI readers и схемы параметров проектируются после discovery; названия не выдаются за существующие API.

Справочные ссылки на общие работы (обязательны только этапы из hard_requires): [точная приёмка](../../foundations/acceptance/plan.md), [типы портов](../../foundations/typed-ports/plan.md), [вложенные сценарии](../../foundations/nested-workflows/plan.md), [обучение](../../foundations/training/plan.md). ## Ошибки и восстановление

До изменения проверить типы, владельцев портов, существование полей/компонентов и весь запрос. При отказе мастера прочитать причину из кнопки ошибки и закрыть собственный диалог. Неизвестный эффект остаётся `AMBIGUOUS`; повторный жест, продление исходного deadline или создание второго узла не являются восстановлением. Отмена/остановка должны подтвердить фактическое состояние серверного выполнения. Проверить, что сохранённые настройки исходного узла и чужие пакеты не изменены.

## Проверки, задание CLI и приёмка

Для каждой строки матрицы подготовить небольшой самостоятельный fixture и ожидаемый результат до модельного прогона. Указанные числа — спецификация oracle, а не наблюдённый PASS. Для неподтверждённых деталей сначала закрепить независимую семантику по Help и адресному наблюдению, затем ожидание. Пустой вход, NULL, несовместимые типы, повторная настройка и смена источника проверяются отдельно. Не вычислять эталон вызовом разрабатываемого handler.

Комплект следующего этапа: `acceptance/task.md` с бизнес-задачей и уникальным `{{PACKAGE_PATH}}`, `acceptance/data/` только с входами; `acceptance/expected.json` и oracle вне data. Модель и вариант берутся из назначения, предел модельной попытки 7200 секунд. Здесь проектируется комплект, исполняемые acceptance-файлы ещё не созданы.

Адресные Node tests выполнять из `packages/loginom-runtime/client`: `node --test test/<новый-тест>.test.mjs` — имя будет добавлено при реализации, сейчас команды нового теста нет. Существующие проверки контрактов: `node --test test/node-target.test.mjs test/node-apply.test.mjs` из того же каталога. При затрагивании общих контрактов проверить их потребителей. Типы проверять штатной командой пакета, если она объявлена; не вызывать `tsc` вручную.

Приёмка по [CLI-регламенту](../../workflow/acceptance-cli.md) требует чистого опубликованного SHA, отдельного аккаунта проверяющего, сохранения и нового открытия пакета. Проверяются конфигурация, идентичности и связи, все заявленные выходы, значения/типы/порядок, `package_closed=true`, `logged_out=true`. Текущий `cold-check.mjs` ограничен одной таблицей: специфический oracle из общего подплана должен быть готов до объявления PASS.

## Discovery и точка продолжения

Наблюдать создание производного компонента, допустимость конкретного базового типа и обновление/сброс собственных настроек. Подготовленный базовый компонент допускается вместо ожидания полного scope Подмодели.

Первый шаг исполнителя — назначение базового SHA/среды, проверка общих зависимостей и адресное наблюдение мастера. Статус `ready_for_development` допустим только для этапа с закрытыми вопросами. Непроведённые проверки: `not_checked`. Checkpoint — до 20 строк: SHA, результат, ограничения, следующий шаг.
