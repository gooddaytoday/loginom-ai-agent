## 3. Вход и выполнение исходной Подмодели

Первичная настройка Цикла прошла при несвязанном входе Подмодели.
Для построения тела импорт был связан с Подмоделью и отдельно с Циклом:
`G;pages.csv|Output_Data-0|Подмодель|Input_Data-0` и
`G;pages.csv|Output_Data-0|↶Подмодель_(группа)|Input_Data-0`.

Execute Цикла **не активирует исходный экземпляр Подмодели**. После выполнения
в `G;↶Подмодель_(группа);Output_Data-0` наблюдался `output_table_active.svg`,
а в `G;Подмодель;Output_Data-0` — `output_table_warning.svg` с opacity 0.3.

После нового открытия сохранённого REST-пакета связь импорта с Подмоделью удалена
штатно: выбран её точный `data-tid`, Delete, `msgbox;tlb;yes`.
В графе осталась только связь импорта с Циклом. Execute Цикла снова дал три точных
ответа для skip 0, 2, 4. Значит, при выполнении этого уже настроенного тела внешний
вход исходной Подмодели связывать не обязательно. Для получения схемы при настройке
тела комплект сохраняет обе связи. Создание тела с нуля без источника схемы не проверялось.

## 6. Строки, порядок, идентификатор и пустой вход

Прямое тело вход → выход дало исходные строки `pages.csv` в порядке PageNo 1, 2, 3.
После замены тела Калькулятором `Skip + Limit - 1` полный результат дал
LastIndex 1, 3, 5 при тех же трёх строках. Столбцы имели класс
`bg-TBGDataType-dtInteger-before` в `…;DataSetForm;normalHeaderCt;<имя>`.

Native-порядок по умолчанию у этой настройки Калькулятора:
**LastIndex, Limit, Skip, PageNo**. Комплект требует явно настроить
**PageNo, Limit, Skip, LastIndex**; это не гарантия порядка по умолчанию.
Существующий механизм output mappings Калькулятора умеет перестановку полей
(`calculator-node.mjs`, `reorderOutputFields`). Числа oracle сохраняются;
полное совпадение офлайн-схемы с expected этой ручной пробой не заявляется.

При включении идентификаторов в конец добавляется **IterationId**,
метка «Идентификатор итерации», integer, значения 0, 1, 2.
Наблюдение: `…;DataSetForm;normalHeaderCt;IterationId` и `…;IterationId_0/1/2`.

Источник заменён на отдельный header-only CSV с теми же тремя integer-столбцами.
Execute Цикла прошёл без ошибки, output 0 активен, `grdDataTable;grd-1;tbl` пуст.
Это наблюдение пустого результата; отдельного счётчика выполненных итераций в DOM
не получено, «0 итераций» напрямую не измерялось. Cold пустого сценария не принимался.

## 7. REST, точность и ошибки

Внутри Подмодели создано подключение GET `https://httpbin.org/response-headers`,
query string `limit` ← Limit, `skip` ← Skip. Табличный вход REST —
`G;REST-запрос;Input_Data-2`, выход ответа — `…;Output_Data-0`.
Мастер привязок: `W;RESTRequestWizard;ParamLinks;colColumnName_1/2` →
`…;colParam_limit/skip`. Выход 0 REST связан с выходным узлом Подмодели.

На output 0 Цикла — три строки, RequestID integer = 0 в каждой, Response string.
Полный **textContent**, не нормализующий whitespace `innerText`, у
`…;DataSetForm;normalHeaderCt;Response_0/1/2` побайтно совпал с `expected.json`:
по 98 UTF-8 байт, отступ 2, `Content-Length: 98`, LF после закрывающей скобки;
skip 0, 2, 4 в исходном порядке. Postman-echo не требовался и не проверялся.

Отдельная отрицательная проба: URL временно заменён на `https://httpbin.org/status/404`,
дополнительный выход REST 1 выведен через ту же единственную табличную границу.
При **выключенном** `pedIgnoreErrors` Цикл успешно накопил три строки:
`…;normalHeaderCt;RequestID_0/1/2` = 0,
`…;ErrorCode_0/1/2` = 6, `…;HttpStatusCode_0/1/2` = 404,
`…;ErrorDesc_0/1/2` = «СООБЩЕНИЕ: Ошибка при выполнении HTTP запроса.
Status code 404: Not Found». Поэтому утверждение «любая ошибка REST прерывает Цикл»
неверно. HTTP-ошибка превращается в данные самого REST. `btnError` для неё нет;
это не потерянная причина. Настоящее исключение выполнения тела и прерывание
на отдельной итерации не проверялись; не выдавать HTTP 404 за такую проверку.
Настройка REST не меняется: комплект требует точные успешные ответы, а не новый
механизм преобразования HTTP-статуса в исключение.

## 8. Живое тело

Цикл настроен **до** построения тела. После этого в исходной Подмодели выполнены
две замены связей выхода: прямой вход → Калькулятор, затем Калькулятор → REST.
Каждый повторный Execute Цикла дал новый результат без повторного выбора Подмодели
в мастере Цикла. Производный компонент живой, не снимок графа на момент настройки.
Наличие активного прежнего результата не означает автоматический пересчёт:
в пробе Цикл деактивировался и выполнялся заново штатным `G;…;Launch`.

## 9. Сохранение и повторное открытие

Save: `MF;MainMenuForm;btnSavePackage` / `btnSaveAsPackage`,
`SaveDialogForm;edtFileName`, `SaveDialogForm;btnOpen`.
Файл скачан через Files: `FileStorageForm;btnDownload` → `…;mniDownload`.
Использован существующий `browserDownloadScript` перед загрузкой страницы;
внутренние функции Loginom не вызывались и не подменялись.

В `Unit_0/Unit.xml` fulltype находится **на Component самого Цикла**, а не
на Engine Подмодели: `Component/@xsi:type = TBGLoopComponent`.
`ReferencedVendorGuid` указывает на `Vendors/Item/@Guid`; у этого Vendor
`IsAutoGeneratedVendor=true`, `BaseNodeGuid` равен GUID исходной Подмодели,
`BaseComponentVendorGuid` и `OriginalComponentVendorGuid` соответствуют Подмодели.
`LoopKind=lkGroupProcessing`, `GroupDataSourceSocketGuid` равен GUID её input 0.
`InternalComponent` имеет тип `IBGModelComponent.DerivedSchemeType`;
input sockets помечены `__derived=true`. Значения по умолчанию, включая размер 1
и выключенные флаги, могут отсутствовать в XML; отсутствие атрибута не заменяет
UI-readback. Пакет/XML не являются новым oracle и не включены в PR.

`loop-native.lgp` с восстановленным непустым CSV и `loop-rest.lgp` открыты заново
через `OpenDialogForm;edtFileName/btnOpen`; Execute выполнялся без настройки.
Офлайн повторились значения 1, 3, 5; REST повторил все три ответа по 98 байт точно.
Это native-проверка persistence; автоматизированный run-check/cold PASS не заявляется.
После пробы свой пакет закрыт, `MF;AppMenuForm;btnLogOut` выполнен,
возврат `LoginForm;Login;btnLogin` подтверждён, браузер завершён.

## Предложение цикла 2

Одна реализация `control.loop` / `group_rows` в существующем lifecycle.
Новые локальные `loop-parameters/node/procedure/readback.mjs`, адресные тесты;
аддитивная регистрация в `node-contracts.mjs/.d.ts`, `node-support.mjs`,
`node-read-contract.mjs`, `node-result-schema.mjs`, описании типа и skill продукта.
Точный перечень общих точек определяется наблюдением при реализации.

Параметры предложения: scoped ref исходной Подмодели и её табличный input 0;
размер 1 и все четыре выключенных флага зафиксированы срезом.
Проверить допустимый тип, одинаковые document/workflow, наличие ровно одной
табличной границы и отсутствие переменных **до мутации**. Выбор native-строки
связать с identity, не подписью. Readback — исходный ref, производный компонент,
вид/размер/вход/флаги, фактические порты; GUID зеркал не считать глобально уникальными.
FOR, постусловие, параллельность, ключи групп, переменные и прочие тела — отказ.

Объём: один обработчик и его адресные red→green; отдельные последующие циклы —
регистрация `loop-pages-offline/rest` в run-check и бизнес-приёмка.
Риски: адресация дерева по identity, buffered изменения Ext, живое наследование
портов, сохранённые активные результаты, явный порядок output mappings Калькулятора.
Новые схемы/readback — предложение для отдельного допуска, не введённый контракт.
