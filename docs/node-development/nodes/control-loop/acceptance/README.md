# Приёмочный комплект Цикла: этап 1

## Статус комплекта

**Готов к реализации обработчика** после [native-пробы LAB-1669](../discovery.md)
14.11.2026 на Loginom 7.4.2. Срез выполним; исходные задания, CSV и ожидаемые данные
сохранены. Это не PASS обработчика: модельных прогонов и автоматизированного cold
ещё нет. Модели передаются задание и
`../fixtures/pages.csv`; oracle, expected и этот файл остаются вне её контекста.

**Предусловие:** принятый этап 1 Подмодели (NW1 #1078 и обработчик `control.supernode`).
Без него тело цикла не построить.

## Срез

Групповая обработка, группы по одной строке, без параллельности, без идентификаторов
итераций, ошибки не игнорируются. Заключённый узел — Подмодель с одним табличным входом
Page и выходом Answers. Вход Подмодели связан с импортом (схема для настройки тела),
вход Цикла — тоже с импортом.

| Случай | Задание | Тело Подмодели | Ожидание | Сеть |
|---|---|---|---|---|
| rest | `task.md` | REST GET `https://httpbin.org/response-headers`, query limit←Limit, skip←Skip; выход — порт 0 REST | `expected.json` | httpbin.org со стенда |
| offline | `task-offline.md` | Калькулятор `LastIndex = Skip + Limit − 1` | `expected-offline.json` | нет |

1. Execute Цикла и полный выход порта 0: по строке на итерацию, 3 строки в порядке страниц.
   Три разных ответа доказывают три итерации с разными Skip.
2. CSV `pages-result.csv` / `pages-offline.csv`; Save после последнего чтения; cold
   Execute без восстановления настроек, итог совпадает с expected.
3. Readback: заключённый узел (ref), производный компонент, вид цикла и размер группы,
   флаги, фактические порты Цикла.
4. Отрицательные адресные проверки: FOR, постусловие, параллельность, запрещённый тип
   заключённого узла (Условие, Цикл, Выполнение узла, Узел-ссылка), чужой workflow —
   отказ обработчика до мутации. Также отказываются ключи групп, переменные и
   неподдержанные табличные границы. Native причины запрета типов наблюдены в
   `btnError`, но не заменяют preflight обработчика.
5. Исполнитель ≥2/3 PASS на одном SHA; независимая приёмка 2/3 на том же SHA.

## Числа и типы

| Случай | Поля | Строки |
|---|---|---|
| offline | PageNo, Limit, Skip, LastIndex — integer | (1,2,0,1), (2,2,2,3), (3,2,4,5) |
| rest | RequestID integer, Response string | RequestID 0 в каждой итерации; Response — тело httpbin для skip 0, 2, 4 |

Response — точный текст: JSON с отступом 2, ключи по алфавиту, перевод строки в конце,
`Content-Length` = длине тела (98 байт). Oracle вычисляет его тем же правилом, что httpbin;
14.11.2026 три ответа через REST внутри Цикла на самом стенде совпали побайтно;
после Save и повторного открытия совпали снова. Для сравнения DOM использован
`textContent`: отображаемый `innerText` схлопывает whitespace.
RequestID — индекс строки внутри итерации, поэтому 0 у всех трёх строк.

У Калькулятора порядок по умолчанию в пробе оказался LastIndex, Limit, Skip, PageNo.
`task-offline.md` требует явного порядка PageNo, Limit, Skip, LastIndex — его надо
задать output mappings, а не считать свойством Цикла. Арифметика и integer-типы
проверены native; полный точный offline-выход в нужном порядке остаётся проверкой
модельного сценария. Ожидания не подгоняются под порядок по умолчанию.

**Ошибки:** `ignore_errors=false` относится к исключениям выполнения тела.
HTTP 404 сам REST представляет данными: native-проба с дополнительным выходом REST
дала три строки ErrorCode=6 / HttpStatusCode=404, Цикл их не прервал.
Исключение на отдельной итерации этой пробой не проверено. Комплект успешного REST
не требует превращать HTTP-статусы в исключения; точные Response уже исключают
ложный PASS с ошибочным HTTP-ответом. Пустой вход дал пустой активный выход без ошибки;
это дополнительное наблюдение, не отдельный принятый сценарий.

```sh
python3 -I docs/node-development/nodes/control-loop/acceptance/oracle.py --check
```

Сценарии run-check предлагается назвать `loop-pages-offline` и `loop-pages-rest`;
регистрации пока нет. Модель `openai/gpt-6.1-sol`, medium, 1800 с.
