## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Checkout/SHA и сборка из закоммиченных исходников, `loginom status` = `ready`; квалифицировать внешнюю среду отдельно. Каждый отказ мастера читать из кнопки ошибки.

1. Палитру «Импорт > Excel файл», root мастера, только табличный выход, xlsx/xlsm и платформенное ограничение xls.
2. Лист имя/номер, named range, A1/R1C1/до последней строки; допускается только один лист или named range.
3. Пустые строки и header count, анализ 1..200, name/label/type/kind/used, исходный/преобразованный preview.
4. Когда появляется schema и как ведут себя Нет/Только новые/Все; disabled ручные controls при Все.
5. На одном узле A/B→B/C без configure: независимое полное reread, поля/типы/значения и сохранённые пользовательские настройки.
6. Byte lineage новой книги/диапазона, формула с cached результатом без исполнения макросов; неверный диапазон/лист, auth 401/404, пустая/повреждённая книга.

Результат — `discovery.md`: observed/hypothesis, exact значения/типы/имена, границы источника и side effects, решения по W. Выход — `ready_for_development` только после снятия блокеров; закреплённые type/mode, `fixtures/` и `acceptance/` до кода обработчика.

### Этап 1 — самостоятельный первый срез

Scope: Одна xlsx-книга, один лист или named range, A1/R1C1 диапазон, заголовки/пустые строки, вручную закреплённые типы; автоопределение Нет. Создание и настройка существующего узла; readback фактически наблюдённых настроек и свежести результата. Неподдержанные формат/порт/режим/тип/параметр отклоняются до мутации с понятным объяснением исправления.

Требования этапа 1 (частичные режимы явно ограничены разделом 1):

- `imports-excel:r01` — Выбор листа по имени/номеру, именованного диапазона, всего листа; A1/R1C1 и расширение до последней строки.
- `imports-excel:r02` — Пустые строки: импортировать/исключить/до первой; количество строк заголовка.
- `imports-excel:r03` — Ручные имя/метка/тип/вид/использование поля; анализ 1–200 строк и просмотр исходных/преобразованных значений.

Для бинарного/XML источника использовать admission вложения: `parameters.source.artifact_id` и `upload_operation_id` из завершённой `artifact.upload`, exact bytes/SHA256/destination из server-copy proof; не брать их из текста модели и не синтезировать старый receipt. Контракт text-import-node.mjs:31-63 — образец проверки, поддержка imports.excel пока отсутствует. После reopen читать persisted source без повторной конфигурации и без receipt прежнего процесса; способ квалифицировать этапом 0 и реализовать W.

Файлы: новые `packages/loginom-runtime/client/lib/imports-excel-{node,parameters,procedure,readback}.mjs`, тесты `client/test/imports-excel-*.test.mjs`; регистрация `node-contracts.mjs`/`.d.ts`, `node-support.mjs`, `node-api.mjs`, `node-result-schema.mjs`, `user-results.mjs`. Образец — [Текстовый импорт](../../../../packages/loginom-runtime/client/lib/text-import-node.mjs), не переносить его семантику/формат. Общие `node-procedure.mjs`/`workspace-ui.mjs` меняются только в согласованных W.

Общие изменения, каждый отдельным коммитом с адресными тестами:

- **W1** — обобщённый источник бинарного импорта с verified artifact_id/upload_operation_id, bytes/digest/destination и persisted source для cold-open; scripts/node-acceptance (cold reader/source lineage без восстановления прежних настроек); text-import-node как образец, node-api/node-procedure/workspace-ui и тесты.
- **W2** — этап 2: node-specific schema policy Нет/Только новые/Все с readback; node-read-contract/node-read-driver/calculator-node и независимый same-node oracle; прежние узлы остаются строгими.
- **W3** — этап 2: управляющие bindings и аудит HTTP/многих источников с provenance каждого файла; node-api и scripts/node-acceptance.

Видимость для модели: `NODE_TYPES.semantics` объясняет бизнес-результат и побочные эффекты; `description` у каждого параметра, строковые enum, компактный readback. Наблюдённые значения отличать от запроса модели.

Тесты из `packages/loginom-runtime`: `bun run test:upstream`; при изменении приёмки — из того же каталога `node --test ../../scripts/node-acceptance/tests/*.test.mjs`. Команды новых адресных тестов закрепить после появления файлов; сейчас они не существуют.

### Этап 2 и далее — отдельные карточки

Этап 2 — r04, r05, r06, r07: три политики и same-node A/B→B/C, несколько файлов/маски/параллельность, provenance/mtime, URL/Basic, xlsm/xls, метки/clone; допуск W2 до реализации.

## 3. Данные и независимые проверки

Комплект `nodes/imports-excel/acceptance/` (для следующих этапов `acceptance/stageN/`): `task.md` с `{{PACKAGE_PATH}}`, `data/` только для входов модели, `expected.json` из независимого `oracle.py` до обработчика. Внешние manifests, oracle и ожидания модели не передаются; секреты — только во внешнем окружении.

CSV-спецификации: UTF-8, разделитель `,`, decimal `.`, header, NULL-маркер `\N`; empty string отличается от NULL. `fixtures/manifest.json`: фактические байты/SHA256, типы/метки/порядок и происхождение каждого бинарного файла/внешнего объекта; размер фиксируется при генерации, а не угадывается.

| Набор | Содержание и назначение |
|---|---|
| `cells.csv / workbook.xlsx` | Id,Text,Amount,Occurred,Active; независимый writer создаёт два листа, named range B3:D6=R3C2:R6C4, два header ряда, внутреннюю пустую строку, formula cached-result и NULL/empty. |
| `book-a.xlsx / book-b.xlsx` | По три строки и одинаковый manifest; другая версия добавляет C и меняет A, специальная пара A/B→B/C для same-node проверки W2. |
| `late-type.xlsx / empty.xlsx` | Первая строка за sample-limit имеет иной тип; полный oracle проверяет преобразование. Нулевая книга сохраняет заданную схему. |

Правило исходной книги: клетки B3:D3 = Id,Text,Amount; B4:D4=(1,А,10), B5:D5 пустые, B6:D6=(2,Б,20). Второй header и лист задаются отдельным fixture, смешивать ожидаемый count разных header/range нельзя. Для многокнижного case три строки каждой книги: Id=1..3 и Id=4..6, Amount=Id×10. Пара A/B→B/C: первая книга A=1,B=10; вторая B=20,C=2, ожидаемый состав/типы отдельно для каждой политики закрепляет discovery до реализации W2.

Oracle не импортирует handler/runtime, считает по входам, сверяет все ячейки/объекты/байты, имена/метки/типы/порядок полей, NULL/empty/0. Отклоняет старое исполнение, чужой destination/узел и подмену данных; E2E preview/обратный импорт не является независимым эталоном.

Для табличного выхода cold-check сверяет имена/метки/типы и порядок колонок, строки без учёта порядка (`expected-outputs.mjs:14,29-39`), до 100 строк/выход и 32 выходов. Числа точны (`cold-check.mjs:232`); использовать точно представимые значения или отдельно согласованный допуск до прогона. Метаданные видов/назначений и порядок строк требуют отдельного аудита. Выходы связываются по type/label с уникальным node_id (`expected-outputs.mjs:72-81`), port index отсутствует: переменные статуса не покрыты.

## 5. Ловушки — переподтвердить, не копировать

Ниже документальные ограничения и требования прежнего черновика; точные controls и runtime-семантика для стенда остаются гипотезами до этапа 0.

Необязательные управляющие переменные → одна импортированная таблица. .xlsx/.xlsm: Linux и Windows; .xls: Windows. Файл, URL и набор файлов — режимы одного узла.

Независимая библиотека создаёт книгу с двумя листами и именованным диапазоном, двумя заголовочными строками, пустой строкой внутри, формулой с сохранённым результатом, NULL/empty, датой и точным десятичным числом. Отдельные книги той же и изменённой схемы, HTTP fixture с Basic auth; ожидаемые ячейки заданы до Loginom.

После смены файла/диапазона старый preview не доказывает чтение новых байтов; подтвердить digest каждого источника. Не исполнять макросы ради .xlsm. Перезапуск загрузки допускается только после выяснения состояния.
