Статус: `implemented_pending_revalidation` — этап 1 (`xlsx`, один лист) реализован (LAB-96, PR #135), в выпусках с v0.3.2; worker 3/4 на `94ca8b7d7e`, независимая приёмка не зафиксирована. Редакция 2 от 2026-10-07: назначение двух последовательных XLSX-карточек по решению владельца.
Component ID: `component.imports.Excel`, slug `imports-excel`. Runtime type и режим: `imports.excel` / `xlsx` — предложение до конца этапа 0.
База назначения: ветка задания из карточки; исследованы исходники `loginom@dada8010e`. Loginom: ожидается 7.4.2, фактические версию/редакцию и ОС сервера записать на этапе 0; платформа исполнителя — Linux x64.

Шаблон — [node-plan](../../templates/node-plan.md), образец нового узла — [ARIMAX](../datamining-arimax/plan.md). Общий порядок — [RUNBOOK](../../RUNBOOK.md) и [CLI-приёмка](../../workflow/acceptance-cli.md). [Карточка](README.md) · [реестр](../../registry.json).

## 0. Как выполняется назначение

Оркестрация — Multica, сквад «Обработчики узлов»: Генератор тасок готовит назначение, Тест-Манки #1 разрабатывает и проходит приёмку, Ловец Галюцинаций независимо принимает опубликованный SHA.

Карточка:

```text
Ветка: <ветка задания>
Узел: imports-excel
Обработать узел по его подплану до независимой приёмки. Объём — этап <N> подплана.
```

Первая карточка — этап 0 отдельно. Владелец 2026-10-07 согласовал первый XLSX-срез и W1 в границах ниже; повторное разрешение на эти изменения не требуется. Этап 1 запускается только после независимой приёмки discovery/контракта на опубликованном SHA. W2/W3 не согласованы и относятся к следующим карточкам. Подплан и RUNBOOK должны быть в ветке до старта; fixtures/oracle и квалификацию native полного чтения с диагностическим прототипом/спецификацией готовит этап 0, продуктовую интеграцию и итоговый runnable warm/cold reader — этап 1.

Назначение: ветка `excel-import`, один новый PR в `loginom`, исходная база `ef84e68a22bd46f3f24549edd829cfb293836703` (слитый PR #36). При старте сверить текущий удалённый SHA. Обе карточки — скваду «Обработчики узлов»; вторую держать в Backlog до принятого результата первой. Сам текст зависимости не является автоматическим admission gate Multica. Начальный SHA каждой карточки фиксировать отдельно; этап 1 начинается с принятого discovery SHA этой же ветки, не с исходной базы заново. Merge и релиз не назначены.

Первая платформа — Loginom Server Linux и standalone CLI. Desktop, XLSM/XLS, динамическая схема, несколько книг, URL и управляющие переменные отложены. Исследование мастера и подготовку независимых эталонов можно вести параллельно в раздельных рабочих каталогах/аккаунтах; этапы 0 и 1 последовательны.

Разрешено:

1. Живое исследование штатными средствами runtime в собственном аккаунте.
2. Реализация назначенного этапа и только согласованных общих изменений (W1; W2; W3).
3. Приёмочный комплект, PR в ветку задания, публикация доказательств и независимая приёмка.

Не разрешено: merge/релиз; следующие этапы; новые общие контракты без решения владельца; изменение конфигурации обвязки. Внешние объекты и файлы — только собственные объекты из задания.

Каждое — Blocked с конкретным вопросом Генератору:

- нет решения владельца по W, требуемому назначенным этапом;
- неизвестный исход операции/частичный эффект: попытку сохранить, writer marker не удалять, перед повтором независимо сверить фактическое состояние;

## 1. Цель и проверенная основа

Согласованные решения: реестр задаёт первый объём как «Импорт xlsx: один явно выбранный лист и диапазон, заголовки, типы и пропуски; без расширения на xls или макросы.». Предлагаемое разбиение сохраняет полный Help-охват, но не повышает готовность.

Этап 1: Одна xlsx-книга, один лист или named range, A1/R1C1 диапазон, заголовки/пустые строки, вручную закреплённые типы; автоопределение Нет. r01: расширение named range проверяется в фиксированном составе полей. r04: автоматические политики требуют отдельного W2; CrossTable PASS их не разрешает.

Явный выбор пользователя обязателен для обработчика. При отсутствии выбора допустим только однозначный лист и область по наблюдённым данным; несколько подходящих объектов или неоднозначные заголовки требуют списка вариантов и уточнения. Не выбирать молча первый лист. В неинтерактивном CLI завершать с понятным требованием выбора, сохранив точное состояние операции и подтвердив cleanup собственного черновика. Этот выбор источника не означает включение автоопределения столбцов.

Сложные ячейки читаются по фактической семантике Loginom: диагностировать обнаруженные ограничения без пересчёта формул, заполнения объединений или конвертации исходной книги в CSV. Discovery различает наблюдённую диагностику, тихую потерю значения и неизвестное поведение; обязательный native warning не предполагать. Приёмка включает все значения небольших таблиц и книги на 20 789 строк с порядком строк.

## 2. Этапы

### Этап 0 — подготовка, живое исследование, контракт

Checkout/SHA и сборка из закоммиченных исходников, `loginom status` = `ready`; квалифицировать внешнюю среду отдельно. Каждый отказ мастера читать из кнопки ошибки.

1. Палитру «Импорт > Excel файл», root мастера, табличный выход и XLSX на фактическом Linux-сервере. XLSM/XLS остаются документальными границами этапа 2, живые прогоны этих форматов здесь не требуются.
2. Лист имя/номер, named range, A1/R1C1/до последней строки; допускается только один лист или named range.
3. Пустые строки и header count, анализ 1..200, name/label/type/kind/used, исходный/преобразованный preview.
4. Когда появляется schema, ручные настройки и фактическое поведение «Нет»; обнаружение однозначного листа/области и возврат вариантов при неоднозначности. «Только новые/Все» и изменение состава полей не включать в текущие обязательные проверки.
5. Новый и существующий узел: намеренная смена диапазона/пути книги с одной подтверждённой настройкой и readback; отдельно — замена байтов книги по прежнему destination при неизменной схеме и независимое полное reread после свежего исполнения без configure. Сохранить идентичность, связи и незапрошенные свойства. A/B→B/C с динамическими политиками относится к этапу 2.
6. Byte lineage своей XLSX-книги, native upload/download gesture и серверные bytes/SHA/destination. До W1 квалифицировать разрешённый диагностический путь своих fixtures, не обходя продуктовый admission и не объявляя продуктовый CLI XLSX PASS. После открытия новым профилем читать persisted source/область/настройки и независимо скачать текущие серверные байты без replay старого receipt.
7. Формула с cached результатом, без cache/ошибка, дата/время, NULL/empty/0/False, объединённые ячейки; неверный лист/диапазон, пустая/повреждённая/защищённая книга. Сохранить фактическую ошибку мастера и cleanup; HTTP/auth здесь не назначены.
8. Независимый writer/reader, небольшие fixtures и книга на 20 789 строк. До реализации закрепить все ожидаемые значения; наблюдением native возможностей и диагностическим прототипом квалифицировать осуществимость полного warm/cold аудита, включая порядок строк, и записать его спецификацию. Продуктовый интегрированный reader реализуется на этапе 1. Повышение лимитов обычного model preview ради этой проверки не разрешено.

Результат — `discovery.md`: матрица observed/unsupported/unknown с источниками, точные defaults/значения/типы/имена/ошибки, границы источника и side effects, конкретный контракт W1; закреплённые type/mode, `fixtures/manifest.json`, независимый oracle и `acceptance/` до кода обработчика. Worker и reviewer принимают опубликованный SHA исследования. Это PASS этапа 0, не PASS обработчика: продуктовая XLSX CLI-приёмка пока NOT_RUN. Выход — `ready_for_development` только после снятия блокеров; реестр не повышать по одной документации.

### Этап 1 — самостоятельный первый срез

Scope: Одна xlsx-книга, один лист или named range, A1/R1C1 диапазон, заголовки/пустые строки, вручную закреплённые типы; автоопределение Нет. Создание и настройка существующего узла; readback фактически наблюдённых настроек и свежести результата. Неподдержанные формат/порт/режим/тип/параметр отклоняются до мутации с понятным объяснением исправления.

Требования этапа 1 (частичные режимы явно ограничены разделом 1):

- `imports-excel:r01` — Выбор листа по имени/номеру, именованного диапазона, всего листа; A1/R1C1 и расширение до последней строки.
- `imports-excel:r02` — Пустые строки: импортировать/исключить/до первой; количество строк заголовка.
- `imports-excel:r03` — Ручные имя/метка/тип/вид/использование поля; анализ 1–200 строк и просмотр исходных/преобразованных значений.

Для бинарного/XML источника использовать admission вложения: `parameters.source.artifact_id` и `upload_operation_id` из завершённой `artifact.upload`, exact bytes/SHA256/destination из server-copy proof; не брать их из текста модели и не синтезировать старый receipt. Контракт text-import-node.mjs:31-63 — образец проверки, поддержка imports.excel пока отсутствует. После reopen читать persisted source без повторной конфигурации и без receipt прежнего процесса; способ квалифицировать этапом 0 и реализовать W.

Файлы: новые `packages/loginom-runtime/client/lib/imports-excel-{node,parameters,procedure,readback}.mjs`, тесты `client/test/imports-excel-*.test.mjs`; регистрация `node-contracts.mjs`/`.d.ts`, `node-support.mjs`, `node-api.mjs`, `node-result-schema.mjs`, `user-results.mjs`. Образец — [Текстовый импорт](../../../../packages/loginom-runtime/client/lib/text-import-node.mjs), не переносить его семантику/формат. Общие `node-procedure.mjs`/`workspace-ui.mjs` меняются только в согласованных W.

Общие изменения, каждый отдельным коммитом с адресными тестами:

- **W1 (согласован владельцем 2026-10-07)** — источник XLSX с verified artifact_id/upload_operation_id, bytes/digest/destination и persisted source для cold-open; три CSV/TSV/TXT delivery gates в artifact-discovery/executor расширить только после квалификации native XLSX gesture. Admission, artifact identity, delivery journal/deadlines/cleanup переиспользовать; text-import-node — образец integrity, не Excel parser. В Agent разрешено адресное представление оригинального бинарного XLSX описанием для модели по образцу non-UTF8 CSV; исходные bytes/SHA сохраняются, файл не декодируется/не нормализуется. Разрешены непосредственно связанные runtime регистрации, node-api/node-procedure/workspace-ui, scripts/node-acceptance и тесты: полный XLSX warm/cold reader/source lineage для 20 789 строк, привязанный к свежему исполнению узла/порта и серверным байтам, без восстановления настроек/старых receipts. Прежние source guards, схемы остальных узлов и ограничения обычного model preview сохраняются. Desktop/App, конфигурация обвязки и новые форматы вне W1.
- **W2** — этап 2: node-specific schema policy Нет/Только новые/Все с readback; node-read-contract/node-read-driver/calculator-node и независимый same-node oracle; прежние узлы остаются строгими.
- **W3** — этап 2: управляющие bindings и аудит HTTP/многих источников с provenance каждого файла; node-api и scripts/node-acceptance.

Видимость для модели: `NODE_TYPES.semantics` объясняет бизнес-результат и побочные эффекты; `description` у каждого параметра, строковые enum, компактный readback. Наблюдённые значения отличать от запроса модели.

Тесты из `packages/loginom-runtime`: `bun run test:upstream`; при изменении приёмки — из того же каталога `node --test ../../scripts/node-acceptance/tests/*.test.mjs`. Команды новых адресных тестов закрепить после появления файлов; сейчас они не существуют.

## 3. Данные и независимые проверки

Комплект `nodes/imports-excel/acceptance/` (для следующих этапов `acceptance/stageN/`): `task.md` с `{{PACKAGE_PATH}}`, `data/` только для входов модели, `expected.json` из независимого `oracle.py` до обработчика. Внешние manifests, oracle и ожидания модели не передаются; секреты — только во внешнем окружении.

CSV-спецификации: UTF-8, разделитель `,`, decimal `.`, header, NULL-маркер `\N`; empty string отличается от NULL. `fixtures/manifest.json`: фактические байты/SHA256, типы/метки/порядок и происхождение каждого бинарного файла/внешнего объекта; размер фиксируется при генерации, а не угадывается.

| Набор | Содержание и назначение |
|---|---|
| `cells.csv / workbook.xlsx` | Id,Text,Amount,Occurred,Active; независимый writer создаёт два листа, named range B3:D6=R3C2:R6C4, два header ряда, внутреннюю пустую строку, formula cached-result и NULL/empty. |
| `book-a.xlsx / book-b.xlsx` | По три строки и одинаковый manifest; другая версия добавляет C и меняет A, специальная пара A/B→B/C для same-node проверки W2. |
| `late-type.xlsx / empty.xlsx` | Первая строка за sample-limit имеет иной тип; полный oracle проверяет преобразование. Нулевая книга сохраняет заданную схему. |
| `large.xlsx` | 20 789 детерминированных строк, устойчивый Id и независимые ожидания всех ячеек/типов/NULL/порядка; manifest исходных и серверных bytes/SHA. Размер — в существующем admission лимите 16 MiB/файл. |
| `ambiguous.xlsx / irregular.xlsx` | Несколько подходящих листов/областей и отдельные сложные ячейки: выбор требует уточнения; фактические значения/диагностика Loginom закреплены discovery, не исправлены скрытой нормализацией. |

Правило исходной книги: клетки B3:D3 = Id,Text,Amount; B4:D4=(1,А,10), B5:D5 пустые, B6:D6=(2,Б,20). Второй header и лист задаются отдельным fixture, смешивать ожидаемый count разных header/range нельзя. Для многокнижного case три строки каждой книги: Id=1..3 и Id=4..6, Amount=Id×10. Пара A/B→B/C: первая книга A=1,B=10; вторая B=20,C=2, ожидаемый состав/типы отдельно для каждой политики закрепляет discovery до реализации W2.

Oracle не импортирует handler/runtime, считает по входам, сверяет все ячейки/объекты/байты, имена/метки/типы/порядок полей, NULL/empty/0. Отклоняет старое исполнение, чужой destination/узел и подмену данных; E2E preview/обратный импорт не является независимым эталоном.

Для табличного выхода cold-check сверяет имена/метки/типы и порядок колонок, строки без учёта порядка (`expected-outputs.mjs:14,29-39`), до 100 строк/выход и 32 выходов. Числа точны (`cold-check.mjs:232`); использовать точно представимые значения или отдельно согласованный допуск до прогона. Метаданные видов/назначений и порядок строк требуют отдельного аудита. Выходы связываются по type/label с уникальным node_id (`expected-outputs.mjs:72-81`), port index отсутствует: переменные статуса не покрыты.

Этот старый cold-check сам по себе не принимает XLSX: static source proof и native ancestry сейчас текстовые. Этап 0 квалифицирует отдельный Excel reader/audit, этап 1 реализует его в W1. Для малых и большой книги обязательны все ячейки, типы, NULL/empty и порядок строк warm/cold, точный node/port/execution и persisted настройки/серверные байты. Preview, row count, частичный sample, повторный импорт экспортированного результата или PASS старого TXT/CSV SHA не заменяют эту проверку. Oracle не использует handler для вычисления ожиданий.
