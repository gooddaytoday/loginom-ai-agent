# Предлагаемая приёмка столбцов

До реализации и модельных прогонов утвердить [контракт](../contract.md) и W1.
Этот комплект не заявляет model/cold PASS.

## Входы и подготовка

Авторский ввод — `../fixtures/variables.json`. `../fixtures/source.lgp` — малый
пакет Loginom 7.4.2 только с «Калькулятором (переменные)» и служебным блоком
сценария; пользовательских входов пакета, конвертера и готовой таблицы нет.
Выражения константные, поэтому табличный вход источнику не нужен.
Сериализованный XML входного пакета проверяется oracle по именам/типам/меткам,
порядку и формулам. Это проверка fixture, не механизм проверки результата продукта.

Для каждого прогона оператор готовит свежую копию пакета **в каталоге своей пары**.
Заранее выбрать уникальный `--out` для run-check. Для сценария `variables-columns`
путь пакета равен `<package_directory>/<out.name>-variables-columns.lgp`.
Локальную копию `source.lgp` переименовать в это имя, загрузить штатной кнопкой
Files → Upload, только по `data-tid`, без перезаписи предыдущих попыток.
Такой пакет перед модельным чатом ещё не содержит конвертера или результата.
Вторая роль пары готовит свою отдельную копию в своём каталоге.

В этапе 1 добавить только запись `variables-columns` в существующий каталог
`scripts/node-acceptance/run-check.py`: `source` — этот каталог, `prompt=task.md`,
`data=data` (пуст), `base=None`, `input_files=[]`, `expected_name=expected.json`.
Сценарий начинается с открытия подготовленного `{{PACKAGE_PATH}}`.
Новый setup-dispatcher/загрузчик или handler создания калькулятора не требуется.
Если принятый W1 не умеет выполнить/прочитать существующий источник из fixture,
это нужно разрешить до запуска этапа 1, а не заменять исходные переменные таблицей.

`task.md` получает модель; `oracle.py`, expected и внутренние документы — нет.
Все значения в task.md описывают исходные данные, не результат подсчёта oracle.

## Oracle

Из корня репозитория:

```sh
python3 docs/node-development/nodes/variables-vartodata/acceptance/oracle.py --write
python3 docs/node-development/nodes/variables-vartodata/acceptance/oracle.py --check
python3 docs/node-development/nodes/variables-vartodata/acceptance/oracle.py --csv ACTUAL.csv
```

Expected строится из JSON входов: 1 строка, 8 столбцов; `ordered:true`,
`column_order:"exact"`, `output_port:0`. Все типы/имена/метки/значения точные,
для real явно `abs=0,rel=0`. DateTime сравнивается как гражданское время
без timezone, миллисекунды обязательны. Integer — Python int, числа CSV — Decimal.
CSV: UTF-8, запятая, десятичная точка, заголовки имён; NULL `?`, пустая строка `""`,
Boolean True/False, дата `yyyy-mm-dd hh:nn:ss.zzz`. Нуль не считается пропуском.

Run-check использует существующий generic CSV check и expected.json.
`oracle.py --csv` доступен для независимой проверки полного файла; вносить для
него новую ветку общего runner не требуется. Cold должен дополнительно подтвердить
типизированную связь с реальным источником по утверждённому W1.

Ни сохранённый input package, ни таблица с правильными числами без этой связи
не являются доказательством успешной приёмки конвертера.

## Прогоны после утверждения

Использовать штатный start, затем wait одним foreground-вызовом, по регламенту
нагрузки/интервала, модель medium / 1800 с. Сборка здесь не выполнялась.
До start уже должны существовать fixture, oracle, expected и новая входная копия.
На одном SHA — ≥2/3 PASS, cold PASS, затем независимые 2/3 отдельным назначением.
Не продолжать упавший чат и не перезаписывать пакет проваленной попытки.
В ожидаемых метках полей нет свобод, так как они заданы задачей; подпись узла свободна.

Наблюдённые строки/Variant и пустой вход не являются обязательными сценариями
предложенного первого среза столбцов. Для строк есть отдельные
`task-rows.proposal.md` и `expected-rows.proposal.json` (8 × 3 с subtype каждой
непустой Value-ячейки); генерация — `oracle.py --mode rows --write`, сверка —
`oracle.py --mode rows --check`. Это часть предложения по наблюдённому объёму
карточки, но его запуск требует решения о W2/разделении этапов из contract.md.
CSV не способен доказать Variant subtype, поэтому строковый CSV-oracle здесь
намеренно не подменяет типизированную приёмку.
Generic run-check также не сравнивает Variant CSV этого нового сценария:
проект строк не зарегистрирован и не готов к запуску до решения о W2, включая
его адресную приёмку. Столбцовый комплект использует существующий generic путь.
