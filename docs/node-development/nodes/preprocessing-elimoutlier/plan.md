## 1. Подтверждённая основа

В палитре есть «Предобработка / Редактирование выбросов», иконка
`bg-vendor-icon-elimoutlier`, мастер `ElimOutlierWizard`.
Один табличный вход; три табличных выхода: 0 «Выходной набор», 1 «Выбросы»,
2 «Экстремальные значения». Native-обучение существует. Подробные UI-поля,
наблюдённые значения, отказы и пределы проверки находятся в discovery.

При политике «Оставить без изменения» порт 0 сохраняет все строки и значения;
порты 1/2 содержат исходные строки с исходной схемой. Экстремумы на порту 1
не дублируются. Схема наблюдённых трёх портов: RowID integer, X real,
Note string, в исходном порядке. Для основного SD-набора 22/0/1 строк,
для IQR-набора 22/1/1; все выходы сверяются раздельно.

В базе нет обработчика этого типа. Доступность компонента и ручное native
исследование не доказывают модельный PASS или готовность продукта.

## 2. Этапы

### Этап 0 — исследование и предложение критериев (LAB-531)

Результаты: discovery, `fixtures/manifest.json`, независимый
`acceptance/oracle.py`, два задания и два expected, черновая
`parameter-schema.json`, измерение приращения полной схемы. Наблюдение и

Критерии утверждает владелец по отчёту; без утверждения этап 1 не начинается.

### Этап 1 — SD/IQR и три независимых выхода

Требования `preprocessing-elimoutlier:r01/r02`:

- Создать или настроить существующий узел; выбрать непрерывные числовые
  поля по техническим именам. SD и IQR, оба множителя заданы явно.
- Политика обоих классов — «Оставить без изменения»; штатное умолчание
  «Ограничивать» нужно явно заменить. Остальные поля сохранить.
- Расчёт порогов на текущем входе и Execute. Предлагаемый detect всегда
  обучает/переобучает текущий вход перед выполнением через существующее
  `trainConfiguredNode`; применение сохранённой модели на иной вход без fit
  не включать в этот срез без отдельного решения.
- Три табличных порта одного узла: `read.ports:[0,1,2]`. Имена, типы,
  NULL, порядок строк/полей и все ячейки сверяются по expected отдельно
  для каждого `output_port`.
- Частичный запрос к существующему узлу сохраняет неуказанные настройки.
  Для нового узла нужны все параметры черновой схемы; нельзя молча выбирать
  метод, пороги, другой тип поля или способ редактирования.
- Компактный readback: выбранные поля, строковый метод, оба множителя,
  ordered, обе политики keep и актуальные схемы портов; описание каждого
  поля схемы доступно модели. Oracle и ожидаемые числа модели не передаются.
- Неподдержанные методы редактирования, переменные параметров,
  quality-режим, строковые/discrete/Variant-поля — отказ до мутации
  с указанием поддержанного запроса. Наблюдения расширенной применимости
  остаются справочными, а не разрешением расширить срез.

Файлы собственного обработчика: `elim-outlier-{node,parameters,procedure,context,readback}.mjs`
и адресные тесты. Образцы: Кластеризация — native Train и несколько выходов;
«Дата и время» — мастер с выбором поля; Missing Values — список полей;
Фильтр строк — табличное чтение разных портов.

Аддитивная регистрация: NODE_TYPES/NodeType, node-api/support/procedure,
result-schema/user-results, распознавание корня мастера и собственных
селекторов, один раздел `loginom-automation`, сценарии run-check.
Новые ветви не меняют старые guards/параметры или поведение прежних узлов.
Нужда в изменении общего алгоритма — новое согласование, не рефакторинг.

## 3. Контракт и независимый oracle

Предложение параметров — `parameters.outlier` из `parameter-schema.json`:
`fields`, `method:sd|iqr`, `outlier_factor`, `extreme_factor`, `ordered`.
Множители конечные, неотрицательные; extreme ≥ outlier. Глобальные
поля существующих типов (включая прежний `ordered`) не расширяются.
Подробные semantics, cross-field validation и readback — в discovery.

CSV: UTF-8/LF, запятая, десятичная точка, первая строка — заголовок,
`?` — NULL. В основном задании только `acceptance/data/values.csv`,
в IQR — `acceptance/iqr/data/iqr.csv`; дополнительные probes в `fixtures/`.
Oracle использует рациональную арифметику Python stdlib, не импортирует
Loginom/runtime и не читает фактические результаты. Expected создан до
реализации и модельной приёмки; задним числом под FAIL не меняется.

Предлагаемые основные критерии — в `acceptance/README.md` и expected:
`ordered:true`, `column_order:exact`, `output_port:0/1/2`, real tolerance
`abs=0,rel=0` для неизменяемых значений, точные IDs/строки/NULL/типы;
не заданные пользователем метки сверяются через `label_any`.

W2/W3 не являются открытыми общими работами на данной базе:
`expected-outputs.mjs` и cold-check уже поддерживают tolerance, ordered,
точный порядок полей и адресацию пары node_id/output_port. Новый механизм
проверки или доказательства происхождения не нужен. Native cold и
модельная приёмка будущего обработчика остаются задачей этапа 1.

## 4. Проверки и принятие

Обязательства изменённых путей определять штатно:
`python3 scripts/node-acceptance/required-checks.py list --base <база>`;
по отчёту выполнить `verify`. Client — полный pinned Chromium набор под
`nice -n 19`; runtime/src — полный host `bun test`; scripts/node-acceptance —
полный набор его тестов. Команды и exit-коды — в отчёт карточки.

После утверждения критериев: два сценария SD/IQR через run-check, на одном
опубликованном SHA cold PASS и ≥2/3 PASS исполнителя для каждого, затем
2/3 независимой проверки под другим аккаунтом. Save, native закрытие пакета
и logout обязательны; неизвестный/прерванный исход не является PASS.
Не писать свои раннеры и не ждать CI, если результат CI не запрошен отдельно.

## 5. Размер схемы и объём реализации

На базе измерено: полная `dock_node_apply.inputSchema` 45 891 Б;
добавление типа, mode detect и `parameters.outlier` даёт 46 805 Б,
приращение **914 Б** (сама параметрическая схема 865 Б), меньше 1 050 Б.
Тест `node-caption-schema.test.mjs` базы проходит. Общий предел 46 000 Б
обеспечивает F2; это не стоп этапа 0, регистрация делается в этапе 1.

Предварительная оценка этапа 1: 2–3 цикла с новым бизнес-прогоном в каждом:
мастер/схема/readback → обучение и все порты → адресная доводка по отказам,
если понадобится. Сборка, 2/3 каждого сценария и независимая приёмка входят
в следующие назначения; никакой предыдущий native результат не переносится
на новый SHA как PASS обработчика.

## 6. Точка продолжения

Оставшийся различитель — `fixtures/quartile-conventions.csv`: все четыре
числовых поля, IQR 1.5/3, keep/keep, ordered=false. До Train проверить фактический
импорт дробей 12.25/13.25/12.75; после — все три порта. Разные гипотезы дают
разные множества RowID (см. discovery и oracle). Этот probe ещё не выполнен.
Не переносить на него результат другого входа или неподтверждённую конвенцию.

Временная пара `01a124e5-0972-779f-a151-131711f82ee0`, один worker-контекст:
разрыв повторился в 12:27:51.614 UTC. Диагностический замер 12:30:51 —
load1=1.24; нагрузка точно в момент перехода не снята. Старая пара и reviewer
в этом возобновлении не использовались. По условию оркестратора дальнейшие
живые попытки остановлены. Сохранённый диагностический
пакет не является принятым сценарием или доказательством cold persistence.
После завершения исследования владелец утверждает предложенные критерии и
назначает этап 1. Перед реализацией сверить голову назначенной базы и размер
после F2; не превращать not_checked в молчаливое ослабление приёмки.
