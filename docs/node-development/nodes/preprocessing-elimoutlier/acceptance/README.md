# Предложение приёмки этапа 1

Критерии подготовлены в LAB-531 до реализации и модельных прогонов. Их должен
утвердить владелец. Этот комплект не означает PASS обработчика.

Два самостоятельных сценария одного типа узла:

| Сценарий | Задание / вход | Порты 0 / 1 / 2: число строк | RowID аномалий |
|---|---|---|---|
| SD, множители 1 и 3 | `task.md`, `data/values.csv` | 22 / 0 / 1 | экстремум 22 |
| IQR, множители 1.5 и 3 | `iqr/task.md`, `iqr/data/iqr.csv` | 22 / 1 / 1 | выброс 21; экстремум 22 |

Предлагается проверять все ячейки всех трёх портов одного узла, точные типы
`integer, real, string`, имена и порядок `RowID, X, Note`, исходный порядок
строк (`ordered:true`, `column_order:exact`). Метки не заданы пользователем:
`label_any:true`. На этапе detect значения не меняются, поэтому допуск real
нулевой: `abs=0, rel=0`; integer, строки и NULL всегда сравниваются точно.
Порт 0 содержит все исходные строки; порты 1 и 2 содержат исходные поля,
без дополнительных флагов и без дублирования экстремума на порту 1.

Oracle использует только CSV и рациональную арифметику Python stdlib:

```sh
python3 acceptance/oracle.py > acceptance/expected.json
python3 acceptance/oracle.py --case iqr > acceptance/iqr/expected.json
python3 acceptance/oracle.py --case null --package-path /own-account/new.lgp
```

Пути приведены относительно каталога узла. В рабочей копии expected перед cold
заменяется только `{{PACKAGE_PATH}}` на личный путь текущей попытки. Oracle,
expected, discovery и история отказов не передаются модели. Для SD в oracle
задана выборочная дисперсия, для IQR — линейные квартили типа 7 и строгий выход
за границы. Основные два набора имеют одинаковый состав аномалий также при
population SD и альтернативных распространённых квартилях: их PASS отдельно
не доказывает численную конвенцию. Адресные `sd-boundary`, `iqr-boundary` и
`fences` предназначены для её различения; наблюдения и пределы — в discovery.

`fixtures/` содержит дополнительные небольшие входы для NULL, обновления,
сдвига распределения, границ, константы, пустого и строкового входа.
`fixtures/manifest.json` фиксирует формат, типы, порядок, байты и SHA256.
Эти входы не копируются вместе с основным заданием в workspace модели.
`--case` позволяет заранее получить отдельные ожидания адресной проверки;
такие проверки не становятся обязательными модельными сценариями без
утверждения владельца. Пустой/несовместимый вход не объявляется численным PASS.

## Запуск после реализации

Этап 0 не собирает CLI и не запускает модель. В этапе 1 предлагаются два новых
имени каталога run-check: `n21` (SD) и `n22` (IQR), если они ещё свободны на базе
назначения. Нужна обычная аддитивная регистрация source/prompt/data и по трём
CSV чтениям результата, как для существующих многовыходных сценариев; сама
приёмка портов остаётся штатным cold-check с `output_port:0,1,2`.
Пользовательское задание не содержит технических инструкций экспорта;
служебную выгрузку трёх результатов добавляет run-check. Новый verifier,
matcher или механизм происхождения не требуется.

На одном опубликованном SHA для каждого сценария: cold PASS, ≥2 PASS из 3 у
исполнителя и 2/3 у независимого проверяющего под другим аккаунтом. Модель
`openai/gpt-6.1-sol`, medium, 1800 с. Старт — через `run-check start`, затем
foreground `wait` одной shell-командой. Требуются штатные Save, закрытие пакета
и logout; неизвестный исход не засчитывается. Общие лимиты не меняются.
