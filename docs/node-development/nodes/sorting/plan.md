# 08. Сортировка: подплан сопровождения и приёмки

[Карточка и принятые границы](README.md) · [реестр](../../registry.json) · [работа с одним узлом](../../workflow/single-node.md).

Обработчик `transform.sorting` уже реализован в режиме `keys`. Этот подплан адаптирует исторический 08 к текущему runtime и standalone CLI: это маршрут адресного исправления, проверки переноса или отдельно назначенного расширения, не повторная разработка с нуля. Историческое принятие сохраняется в своём scope; технические Desktop проверки не являются аналитической CLI-приёмкой. Новых живых наблюдений и прогонов при составлении документа не было, readiness не повышается.

До начала выбрать точное изменение и пройти [подготовку/жизненный цикл](../../workflow/lifecycle.md). Разработчик работает в Astra medium в своей задаче, ветке и worktree. Первичная разработка получает Goal до готовности изменения к первому ревью, без собственного token_budget. Этот документ не назначает следующий узел и не разрешает слияние.

## Узловые требования

Упорядоченный список keys целиком задаёт приоритет сортировки; ASC/DESC обязательны. Для string/variant — явный case_sensitive у каждого ключа, для числовых/дат — отсутствие этого флага. compare_with_locale относится ко всему узлу. До 128 уникальных ключей.

Сортировка не меняет мультимножество строк. Порядок строк с одинаковыми ключами не обещать как стабильный; если бизнесу нужен детерминированный порядок, добавить явный последний ключ RowID. Не оптимизировать кэширование или количество потоков незапрошенно.

## Шаги изменения

1. Сверить список приоритетов, направление, регистр и locale в текущем мастере; параметры локали закрепить для всех строковых ожиданий.
2. После input mapping разрешать keys по эффективным именам полей; validateSortingInputParameters не должен использовать устаревшие source names.
3. Заменить список ключей и порядок, прочитать флаги; существующий узел без keys сохраняет подтверждённую настройку. Не добавлять поле в ключи по похожей метке.
4. Проверить отдельный/inline output mapping и свежий execution. Выход сохраняет все строки и значения, даже если часть полей не участвует в сравнении.
5. Независимый verifier должен проверять и порядок соседних ключей, и полное мультимножество исходных строк; одно из этих свойств не заменяет другое.

## Независимые fixtures и oracle

Ниже — обязательная узловая матрица для объявленного полного scope. При адресном исправлении выбрать затронутые строки и обосновать выбор; расширение режима добавляет новые строки. До автономной попытки сохранить входы и expected отдельно от handler, с версиями и SHA. Ожидания не вычислять импортом реализации и не подгонять по её приёмочному выводу.

| Случай | Вход/изменение | Независимая проверка |
| --- | --- | --- |
| Числа | RowID 1..5, Value=2,-1,2,0,3. Сортировка Value DESC, затем RowID ASC. | Точный порядок RowID 5, 1, 3, 4, 2; исходное мультимножество полностью сохранено. |
| Составной ключ | Region=A/B, Revenue с дробями/отрицательными, DateTime с разным временем; смешанные ASC/DESC. | Независимый lexicographic comparator для чисел/дат; дробь не округлять до двух знаков до сравнения. |
| Строковая семантика | A,a,B,б,ё,е, пустая строка, NULL; варианты case_sensitive и compare_with_locale. | Закрепить отдельный ожидаемый порядок на объявленной локали по спецификации/диагностике. Не использовать Python locale либо Unicode sort как автоматический эквивалент Loginom. |
| Равные ключи/пустота | Повторяющиеся строки, равные keys без RowID, header-only вход; затем смена приоритета existing узла. | Для равных ключей допускается любая перестановка внутри группы при сохранении кратности. После reopen воспроизводится заданный набор и приоритет ключей. |

## Негативные случаи

- Дубли ключей, неизвестное поле, case_sensitive на real либо его отсутствие на string, некорректное направление: отказ до мутации.
- Upstream rename/reorder и старый mapping, изменение locale во время операции, stale ref: не сортировать по соседнему полю.
- Правильно отсортированная сокращённая выборка, потеря дубля, старый execution: аудитор отвергает независимо от технического завершения.
- Для изменённых фаз отдельно различить отказ до эффекта, известную ошибку с подтверждённым cleanup и неизвестный эффект. Повтор operation_id не создаёт второй узел/запуск; lost reply не оправдывает слепой retry. Чужой пакет и посторонние связи неизменны.

## Автономная проверка и передача

Отсортировать согласованную сводку по нескольким ключам и сохранить пакет. Для сценария продаж сначала независимо проверить расчёт/группировку, затем порядок и сохранность всех строк.

Первичная отладка — штатными скриптами текущего runtime в назначенной изоляции. После неё выполнить адресные source tests и проверить независимый oracle, включая его отказ на подменённых значениях/схеме/идентичности. Только затем подготовить неизменный candidate и получить слот по [CLI-регламенту](../../workflow/acceptance-cli.md): standalone CLI Loginom AI Agent, Sol low, согласованная подписка, бизнес-цель и входные файлы без пошаговых UI-команд.

Критерий аналитического PASS — полный малый output/артефакт, проверенная схема и настройки, новый execution и сохранённый пакет, которые независимо воспроизводятся после отдельного открытия. Configure-only и Close проверяются отдельно; обычный продуктовый путь не переоткрывает мастер ради повторной проверки. Непроверенные платформы, большие наборы и дополнительные режимы остаются явно ограниченными.

Передать checkpoint с точными source/runtime/client/model/platform pins, заявленным scope, результатами и неизменёнными исходными FAIL. Техническое завершение, аналитическая проверка, integration и release — отдельные состояния реестра. Один этап ревью и один раунд исправлений выполняются по общему жизненному циклу; этот подплан не добавляет повторного полного ревью.
