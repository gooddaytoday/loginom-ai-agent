# Приёмка пошагового отбора — предложение LAB-655

Новый режим требует утверждения владельцем до изменения обработчика.
Существующий Enter в базе уже реализован; его старый комплект остаётся
регрессией. Этот каталог не регистрирует новые production-режимы.
Новых механизмов верификации, допусков или общего бюджета не предлагается.

## Данные и независимые ожидания

`../../fixtures/selection.csv` и идентичный `data/selection.csv`: UTF-8,
заголовок, запятая, десятичная точка, NULL `?`.
RowID Integer, X/Noise Real непрерывные, Target/Note String дискретные.
64 строки, 32 yes / 32 no; при каждом X и Noise оба класса присутствуют.
21 пропуск Note не участвуют в обучении и должны сохраниться как NULL.

| X | Строк на каждое Noise=-1 / +1 | yes при Noise=-1 / +1 |
|---:|---:|---:|
| -2 | 10 / 10 | 1 / 2 |
| -1 | 4 / 4 | 1 / 1 |
| 0 | 4 / 4 | 2 / 2 |
| 1 | 4 / 4 | 3 / 3 |
| 2 | 10 / 10 | 8 / 9 |

`oracle.py` не импортирует Loginom/runtime, не читает сохранённые native
результаты и заново вычисляет ожидания из канонического CSV. Newton/IRLS
оценивает MLE всех подмножеств. Для Deviance — LR-тест одной степени свободы,
p=erfc(sqrt(LR/2)). Для информационных критериев, n=64, k включая константу:
AIC=-2LL+2k; AICc=AIC+2k(k+1)/(n-k-1); BIC=-2LL+k ln(n);
HQIC=-2LL+2k ln(ln(n)). Forward начинает с константы, Backward — с X+Noise,
Stepwise после добавления проверяет исключение. Равных кандидатов в fixture нет.

Все 15 комбинаций метода и критерия при основных настройках оставляют X:
beta=(0, 0.898810170457028), p≈0.142140986186215 / 0.289295069068924 /
0.5 / 0.710704930931076 / 0.857859013813785. При cutoff=0.8 — 20 yes / 44 no.
Enter сохраняет слабый ненулевой Noise и отличается по p максимум на 0.0493226.
Проверка чисел поэтому выявляет молчаливую подмену отбора на Enter.

`expected.json` — общий предложенный полный порт 0 для основных задач:
64×9, все строки и поля, типы и NULL. Холодный порядок полей предлагается:
PredictionEvent, PredictionProbability, ActualEvent, Target_predicted,
X, Noise, Target, RowID, Note. Он должен быть подтверждён штатным импортом
и cold на этапе 1; тёплый порядок исследовательского импорта отличается.
Строки упорядочены по исходному RowID; CSV-колонки допускают любой порядок
уникальных технических имён. Только p имеет прежний допуск abs=1e-8 / rel=1e-10.
Служебные метки — `label_any`; метки исходных полей явно заданы задачами.

## Бизнес-задачи

Модели передаются **только одна выбранная task и data/selection.csv**.
Oracle, expected, schema, discovery, выбор факторов и численные ответы
не входят в контекст модели.

| Task относительно acceptance/ | Настройка | Expected |
|---|---|---|
| `task-forward.md` | Forward / Deviance / entry=0.01 | `selection/expected.json` |
| `task-backward.md` | Backward / Deviance / removal=0.2 | тот же |
| `task-stepwise.md` | Stepwise / Deviance / 0.01, 0.2 | тот же |
| `task-stepwise-aic.md` | Stepwise / AIC, без p-порогов | тот же |
| `task-stepwise-aicc.md` | Stepwise / AICc, без p-порогов | тот же |
| `task-stepwise-bic.md` | Stepwise / BIC, без p-порогов | тот же |
| `task-stepwise-hqic.md` | Stepwise / HQIC, без p-порогов | тот же |

Это предложение семи основных сценариев: все методы и все критерии.
Перекрёстные комбинации вне этой матрицы пока проверены только oracle.
Две дополнительные задачи проверяют чувствительность именно к p-порогам:

| Task | Настройка | Expected / независимый результат |
|---|---|---|
| `task-stepwise-strict.md` | Deviance / entry=1e-9, removal=0.2 | `expected-strict.json`, только константа, p=0.5 |
| `task-stepwise-permissive.md` | Deviance / 0.95, 0.99 | `expected-permissive.json`, X+Noise |

Строгий случай отличает слишком высокий/умолчательный entry; мягкий —
слишком низкий/умолчательный removal. Они также не должны передавать модели
ожидаемый состав факторов. Численный oracle поддерживает оба случая явно:

```sh
python3 oracle.py --check
python3 oracle.py --diagnostic
python3 oracle.py actual.csv
python3 oracle.py --entry 0.000000001 --removal 0.2 actual.csv
python3 oracle.py --entry 0.95 --removal 0.99 actual.csv
node schema-size.mjs
```

Регистрация сценариев в `run-check` — только этап 1 после утверждения среза.
Для семи основных можно использовать существующий `source=selection`,
`prompt=acceptance/task-*.md`, `data=selection/data`, `expected_name=expected.json`:
stock CSV oracle вычисляет тот же результат; `--check` подтверждает все 15
математических комбинаций. Для двух адресных случаев нужно зафиксировать
свои настройки вызова oracle в их fixture, без расширения общего runner.
Пока эти команды проверяют документы/CSV и не запускают модель.

## Контракт и стандарт приёмки этапа 1

Предложение: прежний `parameters.logistic` дополняется **selection** из
`selection-schema.json`; mode — отдельное поле `forward|backward|stepwise`.
Прежние четыре обязательных logistic-поля и Enter сохраняют свой смысл.
Для новых режимов criterion обязателен. При Deviance Forward требует только
entry_significance, Backward — только removal_significance, Stepwise — оба,
0 < entry < removal < 1. Для информационных критериев p-поля запрещены.
UI допускает 0..1; сужение до открытого интервала — **предлагаемая** граница
первого среза, не якобы наблюдённый отказ Loginom на 0/1.
Пустые/неприменимые/некорректные параметры должны отклоняться до мутации;
не выбирать вместо неизвестного метода Enter, другой критерий или auto.

Постоянные условия: бинарная строковая цель, явная метка события,
непрерывные числовые кандидаты, intercept=true, epsilon=1e-10, threshold=0.8,
100% обучения, без весов, нормализации факторов, закрепления факторов,
регуляризации, валидации и ручной калибровки. Неприменимые disabled-контролы
не редактируются. Readback содержит наблюдённый mode, criterion и только
применимые пороги, плюс прежние условия/роли/классы/training receipt.
Нельзя выдавать входной список кандидатов за доказанный набор отобранных
факторов. Состав выбранной модели доказывается прогнозами oracle; чтение
коэффициентов и нового переменного выхода в критерии не добавляется.

Для каждого утверждённого сценария: CSV каждой ячейки, Save, новый профиль,
cold Execute сохранённой модели без повторной настройки/Teach, cleanup;
cold PASS и ≥2/3 у исполнителя и ≥2/3 у независимого проверяющего на одном SHA.
Изменение существующего узла должно сохранить node_id, связи и прочие настройки.
Проверки: required-checks list/verify по реальному diff; полный client с pinned
Chromium, acceptance-tests при регистрации runner, прежний logreg-enter.
Ограничение полного пути и стандартные критерии не ослабляются.

Этап 0: сборок и модельных попыток нет. Native-опыт не доказывает ни 2/3,
ни холодное сохранение, ни работу ещё не реализованного обработчика.

## Стоимость схемы и реализации

`schema-size.mjs` импортирует production nodeApiTools, клонирует полную
inputSchema dock_node_apply и считает UTF-8 JSON, включая descriptions:
**43 329 → 44 074 Б, +745 Б**. Из них новые значения mode.enum — **+32 Б**,
вложенный selection с enum пяти критериев и p-полями — **+713 Б**.
До общего предела 46 000 Б остаётся 1 926 Б. Это точный размер данного
предложения на указанной базе; иные тексты/условные схемы изменят результат.
Production schema и её сжатие в этот PR не входят.

Оценка: **3 цикла red→green** после утверждения: (1) новые режимы/контролы,
валидация и честный readback, (2) численные сценарии/пороги/Save/cold,
(3) стабильность и регрессия Enter. Ориентир правки клиента — 100–180 строк
плюс тесты; это оценка, не реализованный diff и не разрешение общего рефакторинга.

| Файлы клиента | Предполагаемая аддитивная правка |
|---|---|
| `log-regression-parameters.mjs` | Проверка mode/criterion/применимых p-полей |
| `log-regression-node.mjs` | Дополнение списка modes и передача mode в настройку |
| `log-regression-procedure.mjs` | Выбор наблюдённого метода, критерий после метода, пороги |
| `log-regression-context.mjs` | Чтение трёх контролов отбора, disabled, importance/irremovable |
| `log-regression-readback.mjs` | Наблюдённые mode/selection вместо константы enter |
| `node-api.mjs`, `node-contracts.mjs`, `node-result-schema.mjs` | Аддитивные enum/selection/readback и описание типа |
| `workspace-ui.mjs` | Три точных data-tid в существующем списке контролов LogRegression |

`log-regression-output.mjs`, общий граф/обучение/чтение/бюджеты не требуют
изменения по наблюдённому. Нужны только собственная ветка навыка
`packages/product/skills/loginom-automation` и аддитивная регистрация принятых
сценариев/required-checks на этапе 1. Потребность в общем алгоритме сверх
этого — стоп с одним вопросом по карточке, не повод расширять текущий PR.
