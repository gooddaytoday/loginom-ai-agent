## 1. Наблюдённая основа

Палитра содержит «Исследование → Факторный анализ»; сохранённый Engine/@xsi:type
— TBGFactorAnalysisEngine. Один табличный вход, два выхода: scores и нагрузки.
Native требует отдельного обучения; обычная активация применяет сохранённую
модель. Образец реализации — текущая Кластеризация и trainConfiguredNode.
Для модели нужна популяционная стандартизация scores; нагрузки — V sqrt(λ)
корреляционной матрицы. Пропуск выбранного фактора даёт NULL scores и 0 нагрузок.

При P признаках native показывает P колонок Factor1..FactorP даже при K<P.
Первый профиль: факторы перед исходными полями; после reopen используемые поля
переместились перед RowID. Строгую приёмку порядка ещё надо обеспечить явным
output mapping с autosync=false; column_order:any не является решением.

Наблюдён NULL в используемом Y: строка и исходный NULL сохранены, её scores NULL,
но точная статистика обучения с пропусками не установлена. В первый срез такой
вход не включается. Константы, пустой вход, коллинеарность и K выше ранга не проверены.
Все DOM-якоря, числа, ограничения и границы наблюдений — в discovery.md.

## 2. Этапы

### Этап 0 — исследование и комплект

Готовы: наличие/версия/engine, роли и параметры мастера, два полных выхода,
независимый oracle, fixture matrix/update/null/constant, пользовательские задания,
expected с утверждёнными портами/порядком/допусками, оценка model-visible размеров.
Модельных прогонов и cold-check.mjs нет. Native reopen повторил scores,
но изменил естественный порядок полей; это не полный PASS.

Решением `v040-scope` блокер общей оснастки снят: минимальная интеграция
единого знака фактора разрешена **на этапе 1**, с явным opt-in в expected.
Открытые живые проверки перенесены первыми шагами этапа 1; этап 0 не заявляет
их успешного прохождения. Первоначальную пару больше не трогать: её сессия
без подтверждённого logout истечёт сама, согласно тому же решению.

### Этап 1 — фиксированный PCA без вращения

Начать с выходных страниц/mapping, закрепления точного порядка после reopen
явным mapping и полного свежего readback после retrain того же узла на update.csv.
Расхождение с утверждённым предложением — стоп с одним вопросом;
ослаблять проверку порядка нельзя. Новую структуру навыка брать по LAB-768;
старые fixtures/skill-*.proposal.md сохраняют только оценку этапа 0.

Требование `research-factoranalysis:r01`: роли признаков, заданное число факторов,
создание и изменение того же узла, train/retrain перед Execute, оба выхода.
Параметры — отдельный объект parameters.factor_analysis: features, factors,
rotation со строковым enum none. Его схема и descriptions всех полей:
fixtures/parameter-schema.proposal.json. Группировка исключает коллизию
с существующим parameters.features Кластеризации.
Semantics и compact readback — в discovery.md и fixtures/type-card.proposal.json.

Файлы будущего обработчика — свои factor-analysis-*.mjs и адресные тесты;
аддитивные регистрации в NODE_TYPES, API, диспетчерах, readback и result schema;
свой node reference, короткая строка навыка и согласованный сценарий run-check.
Разрешённая общая правка оснастки описана в разделе 3; без рефакторинга.
Неподдержанные режимы/типы/настройки отклонять
до мутации с понятной причиной. На существующем узле пропуски сохраняют
поддерживаемые параметры, переданный набор features полностью заменяет роли.

## 3. Общие возможности и стоп

W1: обучение/переобучение уже имеет образец trainConfiguredNode и Кластеризацию.
W2: tolerance, ordered, column_order уже есть в expected-outputs.mjs.
W3: оба output_port одного узла поддержаны базой.
W5 не нужен для фиксированного первого среза.

Разрешённая на этапе 1 общая правка — сравнение одного согласованного знака фактора во всех
нагрузках и scores сразу двух портов. Stock matchesCell не имеет этого правила;
cold-check и CSV-проверка run-check не выполняют адресный oracle.py.
Включать её только явным полем expected, например `factor_sign_groups`:
один знак на фактор для обоих портов, без перестановки факторов.
Без поля сравнение должно остаться прежним. Red→green: новый тест и все
существующие тесты оснастки зелёные. В LAB-776 общая оснастка не меняется.
Глобальные бюджеты,
packages/agent, deadline и публичные контракты не менять.

## 4. Утверждённая независимая приёмка

matrix.csv: 8 комбинаций u/v/w=±1, X=3u+v, Y=3u−v, Z=2w, RowID, Tag.
λ=1.8/1/0.2. K=2; нагрузки X/Y на Factor1=sqrt(0.9), Z на Factor2=1;
scores Factor1=u, Factor2=w; неиспользуемый Factor3 NULL/0 соответственно.
update.csv: X+10, Y−4, Z×3. Новое обучение должно снова дать ±1;
применение прежней модели даёт Factor1=0/2, Factor2=±3 (наблюдено).

Oracle — Python stdlib Jacobi; не использует Loginom/runtime/наблюдённые expected.
Файлы expected.json и expected-update.json получены до модельных прогонов.
ordered=true, column_order=exact, output_port=0/1; типы, исходные значения и NULL
точны; вычисленные Real abs=1e-8, rel=1e-10. Один знак на фактор согласован на
обоих портах, без перестановок при различных λ. Не сравнивать abs ячеек отдельно.
Результат — два полных выхода 8/3 строки, два CSV, Save и cold reopen.
Oracle/expected/историю диагностики модели не отправлять.

Приёмка после отдельного назначения: штатный run-check start и wait одной
командой; ≥2/3 PASS исполнителя и 2/3 независимого проверяющего на одном SHA,
в своей паре; cold-check сохранённого пакета, точные значения/типы/порядок,
package_closed и logged_out; обязательные проверки изменённых путей через
required-checks.py list/verify. Проверки runtime/client сейчас не назначаются:
в LAB-776 меняются только материалы узла.
