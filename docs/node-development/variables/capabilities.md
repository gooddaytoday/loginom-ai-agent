## Три разных способа использовать переменную

1. **Набор переменных**: выход узла соединён с обычным входом переменных
   (native subtype 3). Калькулятор использует его в `Var.Amount`, JavaScript —
   через `InputVariables`, конвертер превращает набор в таблицу.
2. **Управление настройками**: набор соединён с отдельным control-входом
   (subtype 4). В мастере значение переключается с константы на переменную.
   Порт можно показать командой `mn;mniShowControlVariablesPort`; он часто
   скрыт по умолчанию. Его редактор также позволяет задать локальные defaults.
3. **Управление выполнением**: значение участвует в выборе ветви или итерации.
   Это не эквивалент смены параметра табличного узла. Здесь нужны собственные
   обработчики «Условия», «Цикла» и адресация вложенных графов.

Обычный и управляющий входы могут существовать одновременно. В Калькуляторе
подключение только control-входа оставило список переменных выражения пустым;
после связи с обычным `Input_Var-1` появились `Var.Text` и `Var.Amount`.
Индексы табличных входов нельзя сдвигать добавлением переменных.
У файловых компонентов и REST вход с назначением управляющих переменных может
иметь native subtype **3**, а не 4: у нового текстового экспорта наблюдены
`Input_Connection-0`, `Input_Data-1`, `Input_Var-2`. Его переменные переключают
параметры, хотя отдельного `Input_ControlVar` нет. В W1 вид порта определяется
наблюдением; смысл табличного ordinal 0 сохраняется независимо от native суффикса 1.

## Компоненты группы «Переменные»

В живой палитре **ровно пять** элементов этой группы. Встроенный источник
«Переменные сценария» не шестой компонент палитры. Component ID каталога базы,
сериализованный fulltype `Component/Engine/@xsi:type` и предлагаемый runtime
type `variables.*` — разные обозначения. В таблице fulltype прочитан из
собственного штатно сохранённого и скачанного `.lgp`; сопоставление — по GUID
узла и VendorGuid. Строковый getter FullType удалённого объекта не вызывался.
В таблице перечислены порты данных/переменных и замеченный control; общие
служебные порты порядка выполнения, компонента и зависимых узлов не дублируются.

| Имя | Component ID | Сериализованный fulltype | Наблюдённые порты | Объём |
|---|---|---|---|---|
| Замена (переменные) | `component.variables.Replace` | `TBGCustomModelComponentEngine` | `Input_Var-0` → `Output_Var-0`; отдельный скрытый control in | Таблица замен, настройки остальных значений, точность и регистр; `ReplaceVariablesWizard` |
| Калькулятор (переменные) | `component.variables.Calculator` | `TBGCalcVariables` | `Input_Var-0` → `Output_Var-0`; отдельный control in | Выражения; подробности и типы — существующий подплан |
| Переменные в таблицу | `component.variables.VarToData` | `TBGVariablesToDataEngine` | `Input_Var-0` → `Output_Data-0` | Столбцы / строки; существующий discovery и границы Variant reader |
| Соединение (переменные) | `component.variables.ColunionDataVar` | `TBGCustomModelComponentEngine` | `Input_Var-0`, `Input_Var-1`, служебный `Input_Add` → `Output_Var-0` | Mapping выхода; дополнительные входы динамические |
| Таблица в переменные | `component.variables.DataToVar` | `TBGCustomModelComponentEngine` | `Input_Data-0` → `Output_Var-0` | Агрегация таблицы; существующий discovery |

Общий `TBGCustomModelComponentEngine` не различает три компонента. VendorGuid:
Замена `f2c44372-4b7c-41ae-99f5-a3d52d418d90`, Соединение
`b4432322-a745-46b0-93cb-83ac194d8adb`, DataToVar
`c0c06e4e-da43-4f30-b2dd-d95ade0e5970`. В данном пакете Замена и DataToVar
сохранены без завершённой настройки; это инвентаризация, не их бизнес-приёмка.
Для DataToVar такой же общий fulltype после настройки ранее подтверждён
существующим discovery. Не выводить неподтверждённое имя класса из названия узла.

`Input_Add` — команда создания порта, не поток данных. Для соединения нескольких
наборов нужны реальные identities входов, их порядок и разбор коллизий имён;
одна общая W1-связь не заменяет этот обработчик.

ни выход 0, ни переменная пакета. Сессионные/системные значения и административные
настройки нельзя обещать как новый mutable scope без отдельного назначения.

## Управляющие поля реализованных типов

Состав — **32 строки** раздела «Реализованные обработчики»
[inventory.md](../inventory.md) на базовом SHA. Это не утверждение, что каждый
из этих обработчиков уже принимает переменные. Проверяется native UI, а не
текущая публичная схема агента.

Для переключателей использовался непустой источник с integer и string;
для табличных входов — его однострочный результат VarToData. Для каждого типа
выдержки указывают страницы, до которых действительно удалось дойти.
Позже добавлены отдельный integer `Limit`, datetime `When=NULL` и строковые
пути `FileCsv`/`FileXlsx`; это позволило раскрыть условные страницы и проверить
фильтр с независимым порогом. У встроенных редакторов строк TID может быть
коротким (`MethodSettingFrame;…`), поэтому поиск только по префиксу мастера
пропускает часть полей. Нужен DOM-контекст владельца и выбранная строка.
Если обязательные настройки не заданы, отказ Next не подменяется скрытым переходом.
Строки «не обнаружено» ограничены перечисленными страницами, а не всеми
обученными моделями, наборами полей и режимами компонента.

Общий путь: подключить набор к наблюдённому входу → открыть мастер →
переключить `…;SwitchButton` → выбрать совместимую переменную в
`…;VariableControl;trg_picker` → завершить мастер → сохранить пакет →
перечитать binding. Доступность зависит от типа переменных и выбранного режима:
например, наличие boolean-переключателя квантования при integer/string fixture
ещё не означает доступный выбор boolean. Переключатель и совместимость надо
проверять отдельно. Строковые подписи не заменяют TID поля и owner страницы.

### Фильтр строк

У значения сравнения наблюдён
`FilterDataWizard;FilterDataPanel;VariantPropEdit;SwitchButton`.
В режиме переменной появляется `VariableControl;trg_picker`; для целого
параметра список показал `Amount ( 7 )`. Условия `пустой`/`не пустой` не имеют
такого аргумента. Начальная конфигурация `Amount > Amount` проверяла только
привязку. Затем использован независимый порог `Limit`: при `Amount=7, Limit=5`
строка находится на выходе «Соответствуют условию». После изменения только
`Limit` на 9 тот же фильтр даёт пустой соответствующий выход, а строка 7/9
находится на противоположном. Результат прочитан штатным быстрым просмотром
(`ui.jsonl:219–221`), без CSV oracle.

Неправильно заполненная дополнительная
строка получила реальный отказ Next «Поле указано не верно…»; после удаления
пустой строки мастер прошёл на «Описание узла».

Привязка хранится отдельно от постоянного значения `CompareValue`:

```xml
<PropertyBindSavers>
  <Item PropertyPath="CompareValue.[0].Items.Filter.Engine.Root."
        VariableName="Limit" />
</PropertyBindSavers>
```

Это сокращённая выдержка своего сохранённого пакета. Индекс не является
публичным идентификатором условия: после удаления строки наблюдён старый
`Name` с `[1]` при актуальном `PropertyPath` с `[0]`. Writer/readback должен
сопоставлять реальное условие и binding, сохранять связь после Done/Save и
проверять повторное открытие; одной записи константы недостаточно.

Справка дополнительно описывает string-переменную со списком для integer/string
полей, с CSV-подобным экранированием. Это гипотеза отдельного теста, не проверенный
здесь PASS списков: [условия фильтрации](https://help.loginom.ru/userguide/processors/transformation/row-filter/filtering-criteria.html).
Предложение первого расширения — один scalar аргумент; интервалы, списки и NULL
добавлять адресно, не обобщать по наличию одного SwitchButton.

### Калькулятор и JavaScript

В Калькуляторе кнопка `CalcDataWizard;btnVariables` показывает обычный входной
набор: `colFieldName_Var.Amount`, `colFieldValue_Var.Amount`. Двойной щелчок
по имени вставил `Var.Amount` в CodeMirror; выражение прошло Next и «Готово»,
после повторного открытия осталось `Var.Amount`. Сохранённый Engine содержит
`Expression="Var.Amount"`; выражение перечитано также после открытия пакета
в новом документе (`ui.jsonl:205`). `Var.` относится к языку
выражений Loginom. Это не `%Amount%` и не JavaScript-синтаксис.

У JavaScript наблюдён обычный `Input_Var-1`; отдельного subtype 4 на новом
узле не было. Штатный код на странице `JavaScriptCodeWizard;cmpCodeCM`
импортирует `InputVariables` из `builtIn/Data`. Нужна передача входных переменных
через W1 и отдельное расширение разрешённого JS-контракта, если его текущая
схема запрещает этот API. Это не разрешение менять `packages/agent` или
обходить существующие ограничения JavaScript. Исполнение нового JS-скрипта
с переменными данным исследованием не принимается.

### Файлы и REST

Имя файла — полноценное управляющее поле у текстового и Excel импорта/экспорта.
В собственной директории worker выбраны `FileCsv` и `FileXlsx` через
`edtFileName;SwitchButton` и `VariableControl;trg_picker`. Оба экспорта прошли
«Готово» и штатное выполнение; созданные ими CSV и XLSX загружены соответствующими
импортами с теми же переменными пути, после чего импорты также выполнены.
В сохранённом пакете у всех четырёх узлов есть
`PropertyPath="FileName.Engine.Root."`, `VariableName="FileCsv"` или `"FileXlsx"`.
Путь в поле и автоматическая подпись `%FileCsv%` сами по себе не доказывают
текстовую интерполяцию: в этом опыте переключён целый property editor.

Нужно различать выбор всей строки из переменной и текстовую макроподстановку
внутри пути. Справка описывает `%VAR%` для файловых источников/приёмников:
[управляющие переменные](https://help.loginom.ru/userguide/workflow/variables/control-variables.html).
Наличие этого синтаксиса не даёт разрешения менять путь на чужой каталог;
проверки доставки входа и проверенного назначения экспорта остаются обязательны.

Для query REST действует уже исследованный явный мост
`variables → VarToData → строковые поля → REST`. Он не заменяется передачей
того же набора в control-вход. Query bindings и подключение — отдельные настройки;
подробное поведение двух запросов и cold — в [W1 discovery](discovery.md).

## Что нужно агенту и сколько это стоит

Цикл в оценке — реализация → обязательные проверки → живой бизнес-сценарий
на новом SHA; независимая приёмка оценивается отдельно. Это диапазон для
назначения карточек, не обещание принятия после одного прогона.

`W1` здесь означает ровно предложение из [discovery.md](discovery.md):
typed variable/control refs, связи, mapping, пользовательские значения,
VariablesForm reader и cold. Существующие подпланы используют имя `W2`
для **разных** следующих расширений: VarToData — точный Variant/temporal reader;
ColunionDataVar — динамические входы переменных. Это не один уже утверждённый
универсальный W2; в назначении надо назвать конкретную возможность.

## Предложение очередности

После текущих карточек разумный первый срез v0.4.0:

1. Принять точный W1 и текущие три переменных обработчика в их согласованных
   границах; сохранить явный REST-мост как пользовательскую композицию.
2. Добавить scalar-порог Фильтра строк и `Var.*` обычного Калькулятора.
   Это короткие пользовательские сценарии, использующие уже подготовленную
   инфраструктуру и требующие проверяемого результата таблицы.
3. Добавить имя/путь файла через переменную для одного импорта и одного экспорта,
   затем распространить тот же подтверждённый property editor на Excel.
   Отдельно принять правила безопасности пути и сохранение bindings после cold.
4. При оставшемся объёме — Соединение двух наборов и Замена переменных.
   Начать с фиксированных входов и простых типов; динамические порты и новые
   преобразования типов не включать в первый срез неявно.

Позже: пакетный mutable scope, вложенные подмодели, точный Variant/temporal W2,
динамический W2 Соединения, массовое расширение всех scalar настроек,
JavaScript InputVariables за текущими границами, Условие/Выполнение/Ссылка/Цикл.
Системные/сессионные setters — только если найдена доступная штатная операция
и владелец отдельно назначил её исследование.

Наличие элемента UI — основание спроектировать следующий тест, а не принять
сразу весь контракт узла. В частности, один рабочий numeric binding не доказывает
NULL, интервалы, списки, даты, unsafe Int64, типовую конверсию и изменение схемы.
