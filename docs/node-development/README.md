# Разработка узлов Loginom AI Agent

Порядок разработки и приёмки — [RUNBOOK](RUNBOOK.md). Этот каталог содержит подпланы, данные и независимые ожидания, техническую приёмку и подтверждённую историю клиента. Назначения выполняются карточками Multica; настройка обвязки и среды находится в эксплуатационном руководстве.

- [Реестр](registry.json) и [обзор](inventory.md) описывают реализацию и точные пределы готовности.
- У каждого компонента есть карточка `nodes/<slug>/README.md` и подплан `nodes/<slug>/plan.md` по [шаблону](templates/node-plan.md); наличие подплана не назначает работу. Образцы: [Кросс-таблица](nodes/transform-crosstable/plan.md) — после приёмки, [Скользящее окно](nodes/transform-slidingwindow/plan.md) — до этапа 0.
- [Порядок создания подплана](workflow/new-node-plan.md) и [CLI-приёмка](workflow/acceptance-cli.md).
- [История](history/README.md) и [происхождение](provenance.json) — архив прежних подпланов и приёмок до повторной приёмки узлов в новом процессе.

Назначение владельца, текущий код и наблюдаемое состояние имеют приоритет над историей. Нельзя переносить PASS на другой SHA, платформу или режим.

## Обновление реестра

Регистрацию и режимы сверять с `packages/loginom-runtime/client/lib/node-contracts.mjs`, операции и параметры — с исходниками обработчика. В `source_snapshot` указать базовый SHA и хешированные источники текущего снимка. Исторические записи `evidence_catalog` сохраняют свои SHA и область приёмки. Источники текущего кода из `source_snapshot.evidence` обновляются по выбранной голове; независимые результаты добавляются отдельными источниками с фактическим SHA проверки. `acceptance` описывает подтверждённый срез и источник результата: наличие `acceptance/task.md` или oracle само по себе не подтверждает PASS; без независимого подтверждения указывается `not_validated`.

Независимые приёмки v0.3.8–v0.3.9 хранятся также в карточках Multica. Для них в `evidence_catalog` указываются `issue_key`, `issue_id`, `comment_id`, ссылка и точный `source_commit`; `acceptance.scoped_results` сохраняет итог сценариев и оговорки. Статус «независимая приёмка на интеграционной голове» относится к этим карточкам и SHA; для добавок, принятых на собственной ветке и затем включённых в интеграцию, сохраняется фактический SHA проверки. Нового живого PASS текущего статического снимка этот статус не объявляет.

Обзор генерируется штатным инструментом, из корня репозитория:

```sh
python3 docs/node-development/tools/validate.py --registry-only --render
python3 docs/node-development/tools/validate.py --registry-only
python3 -m unittest discover -s docs/node-development/tools -p 'test_*.py'
```

`--registry-only` проверяет полноту типов и режимов, классификацию, существование карточек/подпланов/исходников, ссылки на доказательства, хеши источников текущего снимка и актуальность генерации. Он не проверяет соответствие старых подпланов шаблону или хеши исторической миграции. Полный аудит остаётся отдельной командой `python3 docs/node-development/tools/validate.py` (с исходным ZIP — `--source-archive`). Его прежние ошибки не означают успешную проверку истории после обновления реестра.
