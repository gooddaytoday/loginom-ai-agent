## Файлы

Принимаемый общий минимум `foundation:file-artifacts` — доставка и независимая проверка origin/path/name, точных bytes/SHA, конфликтов назначения и завершения своей операции. Первый владелец — CrossTable W2, включая вложения больше 1 KiB. Этот этап не требует одновременно реализовать parsers всех форматов. XLSX/LGD/XML/Tableau readers и семантика экспорта принимаются в соответствующих узловых этапах до их собственного PASS; наличие общей доставки их не доказывает.

Переиспользовать `client/lib/artifact-delivery.mjs`, `browser-downloads.mjs`, `text-import-node.mjs` и `text-export-node.mjs` там, где такой файл реально существует; точные export/import entrypoints сверить при реализации. Доставка проверяет origin/path/name/байты/SHA, чтение результата — независимый parser формата. XLSX проверяется по структуре workbook и ячейкам; LGD требует отдельного проверенного reader/эталонного файла; XML — по структуре и XSD, текст — по байтам и логическим значениям.

Нельзя доказывать экспорт только повторным импортом через новый handler той же команды. Изменение источника между проверкой и применением, существующий путь и частичный файл — отдельные негативные случаи. W2 Кросс-таблицы сохраняет своего владельца и проверку вложений >1KiB.

| Группа | Провайдеры | Независимая проверка |

Для каждого варианта проверить создание, редактирование, сохранение, выбор узлом, отзыв доступа и удаление тестового подключения. Секреты хранятся в приватном профиле; в плане — только тип и условие среды. Разрешённые параметры, драйверы и редакция берутся из страницы конкретного подключения. Нельзя выводить поддержку одного backend из PASS другого. Первую реализацию допустимо принять на одном провайдере с явным оставшимся объёмом; вся матрица не становится общим блокером простого файлового узла.

## Внешние эффекты

Runtime должен различать отказ до отправки, подтверждённый результат и неизвестный исход. При потере ответа после SQL/HTTP/Kafka/процесса не повторять эффект автоматически. Нужен независимый observer: данные БД, счётчик запросов, сообщения topic, exit/stdout/stderr/выходной файл процесса. Отмена локального ожидания не доказывает остановку внешней операции. Использовать отдельные тестовые объекты, не производственные данные.

Проверки: один успешный эффект, отказ до отправки без эффекта, потеря ответа после отправки с обнаружимым эффектом, частичный результат и штатная очистка. Обязательность connections определяется конкретным узлом; выполнение программы и локальный файл не должны искусственно зависеть от БД.

## Серверный код

JavaScript/Python узлы исполняют код в Loginom, а не в локальном shell агента. Зафиксировать версии, разрешения, внешние модули и ограничения языка; настройка runtime отдельна от handler. Проверять код/модули, входные таблицы/переменные, выходы, console/errors, отмену и save/reopen. Образец — существующий bounded editor lifecycle; нельзя отправлять произвольный browser evaluate в обход UI контракта.

Python, 1С, Выполнение программы, Tableau и лицензируемые сервисы имеют собственные environment gates. Отсутствие стенда даёт `not_checked`/конкретный blocker, а не исключение из полного документационного каталога.

## Приёмка и продолжение

Назначение закрепляет одного владельца общей возможности, базовый SHA и конкретный принимаемый scope. Проверить существующих потребителей и отказ неизвестных/несовместимых запросов до эффекта. Команды Node tests выполнять из `packages/loginom-runtime/client`; новые test filenames и контракт фиксируются в этапе discovery. После реализации — независимые приёмочные доказательства на чистом SHA по RUNBOOK. Непроведённые проверки остаются `not_checked`.

Потребитель не должен ждать всех будущих режимов общей возможности: его обязательное ребро означает только описанный в этом подплане минимальный принимаемый контракт. Не переносить незавершённую ветку соседа; общую работу разрешено выполнить в одном назначении с первым потребителем, отдельно доказав её критерии. Изменения контракта сверх этого подплана требуют решения владельца.

Текущий результат: статическое исследование; реализации и live-проверок здесь не было. Следующий шаг — адресное discovery и фиксация интерфейса/ожиданий. Checkpoint до 20 строк.
