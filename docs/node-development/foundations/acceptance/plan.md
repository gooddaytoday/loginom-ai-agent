## Раздельные принимаемые возможности

`foundation:oracle-crosstable` имеет только критерии W3 действующего подплана Кросс-таблицы: два отчёта, необходимые связи и протокол смены sliding-схемы по заданным fixtures. Владелец — её этап1; новые критерии lossless Int64 и универсальной проверки порядка в это назначение не добавляются. Частичный W3 не завершает `foundation:oracle-tabular`.

`foundation:oracle-tabular` — отдельное расширение со всеми критериями ниже, своим назначением и SHA. Потребитель, которому нужна только W3, ссылается на узкую возможность, остальные — на полный oracle. При необходимости повторно использовать W3-код можно, но приёмка полного этапа самостоятельна.

## Подтверждённая основа и требуемое изменение

`scripts/node-acceptance/cold-check.mjs` сегодня выбирает один узел по типу, читает output 0 и сравнивает мультимножество строк. Он проверяет закрытие пакета/выход, но не весь граф, порядок строк и lossless Int64. `client/lib/table-output-pages.mjs` ограничивает обычный preview; `table-output-values.mjs` и `user-results.mjs` нельзя считать универсальным oracle Variant. Пути client здесь относительны `packages/loginom-runtime`.

Требуемый контракт expected: выбранные узлы и связи с однозначными refs, список проверяемых выходов, схема и типизированные значения, политика порядка и числовые допуски по каждому результату. Форму расширения спроектировать совместимой с существующим одиночным expected. Отдельно от вывода модели читать сохранённые настройки; сравнение только запрошенных параметров не доказывает readback.

- Проверять идентичности, количество узлов каждого заявленного типа, входные/выходные индексы и связи. Отсутствующая, лишняя или переставленная связь должна менять verdict.
- Для Sort/Window/временных рядов сравнивать последовательности. Для Join и неупорядоченных результатов — мультимножество с кратностью; решение задаёт подплан до прогона.
- Integer за пределами 2^53 передавать без округления; Real сравнивать с заранее заданным допуском; NULL, пустую строку, Boolean и datetime не сводить к одинаковому тексту. Базовый этап работает с обычными типизированными колонками; смешанные Variant-ячейки и их subtype принимаются отдельно в `foundation:variant-values`. Ограничение арифметики самого узла не подменять дефектом reader.
- Читать весь маленький acceptance fixture и все выбранные порты. Если бюджет/reader допускает только preview, verdict — неполная проверка, а не PASS.
- Самостоятельное чтение после открытия в новом профиле не должно зависеть от утраченных session receipts. Не синтезировать receipts прежней сессии. Для файлов/переменных/деревьев/моделей — специализированные доказательства из соответствующих общих подпланов.
- Сохранить resource manifest/hash проверки, durable journal, исходный deadline и подтверждения `package_closed`/`logged_out`. Model task/data не получают expected и oracle. Проверку равенства sourceCommit кандидата SHA назначения добавить в явный gate либо подтвердить существующим внешним gate; текущий cold-check сам этого сравнения не делает.

## Независимые проверки общей возможности

Две одноимённые по типу таблицы с разными ID и значениями должны различаться. Перестановка двух выходов фильтра, изменение одной связи, удаление дубликата строки, обмен соседних строк в sorted output, замена NULL на пустую строку и округление 9007199254740993 должны вызвать FAIL. Правильный одиночный legacy expected продолжает проходить.

Оба oracle проверяются на самостоятельно подготовленных штатными средствами Loginom пакетах и закреплённых ожидаемых результатах; разработанный handler потребителя не является условием подготовки fixture. Это позволяет принять общий reader до узлового verdict без круговой зависимости.

Расширения под специальные типы принимаются вместе с их foundation:variant-values / typed-variables / typed-trees / training / nested. Не обещать их реализацию первой табличной версией. Для Кросс-таблицы W3 остаётся первым конкретным потребителем multi-output и протокольной проверки sliding.

## Приёмка и продолжение

Назначение закрепляет одного владельца общей возможности, базовый SHA и конкретный принимаемый scope. Проверить существующих потребителей и отказ неизвестных/несовместимых запросов до эффекта. Команды Node tests выполнять из `packages/loginom-runtime/client`; новые test filenames и контракт фиксируются в этапе discovery. После реализации — независимые приёмочные доказательства на чистом SHA по RUNBOOK. Непроведённые проверки остаются `not_checked`.

Потребитель не должен ждать всех будущих режимов общей возможности: его обязательное ребро означает только описанный в этом подплане минимальный принимаемый контракт. Не переносить незавершённую ветку соседа; общую работу разрешено выполнить в одном назначении с первым потребителем, отдельно доказав её критерии. Изменения контракта сверх этого подплана требуют решения владельца.

Текущий результат: статическое исследование; реализации и live-проверок здесь не было. Следующий шаг — адресное discovery и фиксация интерфейса/ожиданий. Checkpoint до 20 строк.
