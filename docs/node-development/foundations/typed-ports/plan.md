## Текущее ограничение

`node-contracts.d.ts` описывает InputLink через числовые табличные input/output, `node-target-browser.mjs` связывает Input_Data/Output_Data, остальные порты не становятся управляемыми от одного наблюдения. `user-workflow.mjs` содержит табличные defaults выходов. Требуется согласованно расширить refs, validation, graph observation, конфигурацию, execution result, `dock_node_read` и compact user-v1; не добавлять вторую браузерную сессию.

## Контракт Variant-значений таблицы

Этот этап не требует портов переменных. Для каждой ячейки сохранить исходный subtype, значение, NULL/пустую строку и точность integer/datetime; ограниченный native reader Collapse не объявлять универсальным. Расширить table-output-values/user-results и cold oracle для обычных Variant-таблиц. Fixture содержит integer9007199254740993, real1.25, строку"1", false, datetime и NULL в одном столбце; проверяются exact transport и сохранение после reopen. Динамический вывод массива/объекта из JS проверяется только где такой subtype документирован и наблюдён. Неподдержанный subtype — явный отказ.

## Контракт переменных

Явно различать вид порта и владельца. Хранить имя, метку, тип, значение и порядок переменных; область сценария, пользовательские и управляющие переменные не смешивать с входным портом. Связывать только совместимые источники/получатели; динамические/необязательные порты подтверждать фактически. Допуски имён и изменения типа согласовать по мастеру, не по отображаемой метке.

Oracle переменных принимает самостоятельный пакет-источник с integer/string/Boolean/datetime/NULL, включая одинаковые метки и разные имена. Проверяет прямой результат и cold reopen без обратного преобразования в таблицу как единственного доказательства. При смене значения исходная схема остаётся различимой, при смене схемы нужен отказ или разрешённая режимная политика.

## Контракт деревьев

Разделять контейнер, массив, поле, отсутствующий элемент, пустой массив и NULL. Связь и mapping должны адресовать типизированный путь и владельца; индекс элемента не является устойчивой идентичностью схемы. Чтение сохраняет вложенность, порядок массива, типы/метки и кратность. Не превращать всё дерево в строковое JSON-представление с потерями.

Fixture: два контейнера с одноимёнными листьями, массив [1,2,2], пустой массив, отсутствующее поле и поле=null. Прямой oracle различает все случаи, сохраняется после выполнения и открытия в новой сессии. Неподдержанный subtype возвращает ограничение, не нулевой результат. Подготовленный tree-source устраняет зависимость от JSONToTree/TreeToJSON.

Явное редактирование схемы дерева проверяется строгим readback после настройки. Автоматический вывод или синхронизация схемы требуют отдельного discovery соответствующего узла и прямого сравнения всех путей/типов после смены источника. Этап Кросс-таблицы `foundation:dynamic-schema` не разрешает relaxed policy для деревьев. Variant-листья проверяет tree oracle; если узел выводит Variant в обычную таблицу, его этап дополнительно требует `foundation:variant-values`.

## Ошибки

Чужой порт/workflow, неоднозначный путь и несовместимый вид порта отклоняются до drag. После потери ответа не повторять связь; сохранять operation identity и разрешать неопределённость через существующий recovery. Отмена editor возвращает исходные значения и подтверждённый контекст.

## Приёмка и продолжение

Назначение закрепляет одного владельца общей возможности, базовый SHA и конкретный принимаемый scope. Проверить существующих потребителей и отказ неизвестных/несовместимых запросов до эффекта. Команды Node tests выполнять из `packages/loginom-runtime/client`; новые test filenames и контракт фиксируются в этапе discovery. После реализации — независимые приёмочные доказательства на чистом SHA по RUNBOOK. Непроведённые проверки остаются `not_checked`.

Потребитель не должен ждать всех будущих режимов общей возможности: его обязательное ребро означает только описанный в этом подплане минимальный принимаемый контракт. Не переносить незавершённую ветку соседа; общую работу разрешено выполнить в одном назначении с первым потребителем, отдельно доказав её критерии. Изменения контракта сверх этого подплана требуют решения владельца.

Текущий результат: статическое исследование; реализации и live-проверок здесь не было. Следующий шаг — адресное discovery и фиксация интерфейса/ожиданий. Checkpoint до 20 строк.
