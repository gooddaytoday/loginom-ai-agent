## Результат и владелец

Первый владелец — этап1 [Кросс-таблицы](../../nodes/transform-crosstable/plan.md), работа W1; независимое доказательство — W3. Этот общий этап не создаёт вторую конкурирующую реализацию. При совместном назначении общую возможность проверяют перед приёмкой узла; это не циклическая зависимость от полного узла.

В `client/lib/calculator-node.mjs` общая табличная оболочка фиксирует ожидаемый mapping до выполнения, а `node-read-contract.mjs` отвергает смену схемы. Нельзя просто отключить schema equality всем узлам. Добавить явную capability/политику конкретного типа и режима: строгая сохранённая схема для fixed и обнаружение свежей фактической схемы для sliding. Разрешение смены схемы получает только runtime из подтверждённого readback режима sliding. Вызывающий не может включить relaxed policy публичным параметром. Форму внутреннего receipt закрепить в discovery, сохранив запрет из W1.

Старый успешный receipt связывает новый read с тем же узлом/режимом, но не превращает старые имена колонок в вечные ожидания. Подтверждать источник/выполнение/порты и повторно строить mapping только по наблюдённой новой схеме. Новые/исчезнувшие поля, порядок и collisions должны попасть в результат компактного API. Переход режима требует явной перенастройки; простой рост категорий — нет.

## Обязательные случаи

- На одном узле выполнить fixture A/B, затем B/C; повторно читать по исходной completed operation без `dock_node_apply` для «починки». Проверить удаление A и появление C и точные факты.
- Для fixed сохранять declared политику «Прочие»/NULL; не переносить sliding на все режимы.
- Исчезновение NULL-категории, повторное использование технического имени другой категорией, одинаковые метки, empty output и лимит числа колонок.
- В обычном Sort/Join неожиданная смена схемы по-прежнему даёт отказ. В неполном наблюдении/потере идентичности нельзя возвращать старый результат как свежий.

Oracle сравнивает полную схему и факты независимо от runtime mapping. Стандартные схемы других узлов не ослабляются. [Справка Кросс-таблицы](https://help.loginom.ru/userguide/processors/transformation/cross-table.html), Help7.4, прочитано 2026-10-02.

## Приёмка и продолжение

Назначение закрепляет одного владельца общей возможности, базовый SHA и конкретный принимаемый scope. Проверить существующих потребителей и отказ неизвестных/несовместимых запросов до эффекта. Команды Node tests выполнять из `packages/loginom-runtime/client`; новые test filenames и контракт фиксируются в этапе discovery. После реализации — независимые приёмочные доказательства на чистом SHA по RUNBOOK. Непроведённые проверки остаются `not_checked`.

Потребитель не должен ждать всех будущих режимов общей возможности: его обязательное ребро означает только описанный в этом подплане минимальный принимаемый контракт. Не переносить незавершённую ветку соседа; общую работу разрешено выполнить в одном назначении с первым потребителем, отдельно доказав её критерии. Изменения контракта сверх этого подплана требуют решения владельца.

Текущий результат: статическое исследование; реализации и live-проверок здесь не было. Следующий шаг — адресное discovery и фиксация интерфейса/ожиданий. Checkpoint до 20 строк.
