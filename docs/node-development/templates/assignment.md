# Назначение этапа через Multica

Короткий вход: [карточка этапа](multica-stage-card.md). Полный допуск Генератор фиксирует в той же карточке; инструкции ролей загружаются штатной обвязкой. Этот шаблон не создаёт задачи и не является самостоятельным оркестратором.

- Карточка: <issue ID>; узел/общая возможность: <ID>; этап или bundle: <точный ID из карт>.
- Режим: parallel | sequential | single; scope и ссылка на канонический подплан: <...>.
- Ветка задания и цель PR: <из карточки>; чистый исходный SHA: <...>.
- Worker/Reviewer и модель/effort: <из действующей конфигурации, без подмены>.
- Native checkout и рабочая ветка: <пути; имя ветки не более трёх слов через дефис>.
- Каждый hard prerequisite: <принятый scope, dependency SHA, evidence, включение в базу>; внутренние gates bundle: <...>.
- Профиль параллельности: <из parallel-execution.json>; фактические agent/daemon limits: <проверенное чтение>.
- Готовность пары аккаунтов и общий назначенный стенд: <проверено>; секреты только в приватных конфигурациях.
- Собственные candidate/output/run directories, профили, пакеты и внешние test objects: <...>.
- Общие файлы/функции и владелец окна: <ресурс, scope, trigger освобождения>; resource gates модели/oracle: <...>.
- OAuth: <legacy serial либо shared-oauth-v1 с доказательствами допуска>; capability и происхождение кандидата: <...>.
- OpenViking: <actor health/search/read через загруженную инструкцию Multica; blocker при недоступности>. Старый bootstrap CURRENT.md для локальных Dock worktree не назначается автоматически агентам Multica.
- Предел модельного прогона: 7200 секунд; общий бюджет запуска Multica: <с учётом всех фаз и cleanup>.
- Передача Reviewer: <чистый опубликованный candidate SHA, PR, receipt/проверенные вложения, завершённые операции Worker>.
- Checkpoint: <SHA, результат, ограничения, следующий trigger>, не больше 20 строк.

Прочитать [RUNBOOK](../RUNBOOK.md), [параллельный регламент](../workflow/multica-parallel.md), подплан и [возобновление](../workflow/lifecycle.md). Сначала закрыть необходимое discovery, затем реализовать только назначенные режимы. При неизвестном эффекте сохранить попытку; не начинать повторную операцию или чужой этап.

Политика ресурсов задаётся по фазам, а не blanket-слотом всей карточки на хост. Статический `host-resources.json` не предоставляет атомарную блокировку. Ожидание ресурса заканчивает текущий запуск с явным владельцем/trigger; продолжение — адресованный native handoff в той же карточке. Worker не ставит Done, Reviewer не принимает другой SHA. Merge, выпуск, изменение runtime-конфигурации и расширение scope — отдельные поручения владельца.
