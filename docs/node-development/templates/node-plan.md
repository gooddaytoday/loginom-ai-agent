## 0. Как выполняется назначение

Оркестрация — Multica, сквад «Обработчики узлов»: Генератор тасок готовит назначение, Тест-Манки #1 разрабатывает и проходит приёмку, Ловец Галюцинаций независимо принимает опубликованный SHA. Правила ролей задаёт эксплуатационное руководство обвязки.

Карточка:


### Объём назначения

Разрешено:

1. Живое исследование стенда (этап 0) штатными средствами runtime в собственном аккаунте.
2. Реализация этапа <N> и перечисленных общих изменений, владелец которых — эта карточка: <W1…Wn или «нет»>.
3. Приёмочный комплект, PR в ветку задания, публикация доказательств, независимая приёмка.

Не разрешено: merge и релиз; следующие этапы; изменение конфигураций обвязки; другие изменения общих контрактов без решения владельца.

### Стоп-условия

Каждое оформляется как Blocked с конкретным вопросом Генератору:

- в ветке задания нет RUNBOOK, подплана или обязательных общих исправлений;
- пара аккаунтов или CLI не `ready` на назначенном стенде;
- неизвестный исход операции; попытку сохранить, writer marker не удалять;
- в палитре стенда нет компонента «<название>»;
- нужны новые режимы или общие изменения сверх объёма.

## Вариант для реализованного узла

Для узла, у которого уже есть обработчик и прежняя приёмка, подплан пишется по тем же разделам 0–6 с такими отличиями. Этот блок в подплан не копируется.

- Шапка: статус `reverification_required`; runtime type и режимы закреплены — из реестра и `node-contracts.mjs`.
- Раздел 1: принятый объём и прежние доказательства (исторический подплан, completion audit, oracle) — с пометкой, что их PASS не переносится на текущий клиент.
- Этап 0 — перепроверка принятого объёма на вершине ветки задания:
  1. Собрать `acceptance/` (task, data, expected, oracle) из прежнего oracle в `packages/loginom-runtime/tools/loginom-acceptance/<node>_*.py`, адаптировав транспорт и сбор доказательств к standalone CLI; проверки значений, freshness и отказов сохранить. Прежний launcher не запускать.
  2. Адресные тесты узла и весь `client/test`.
  3. CLI-сценарий и cold-check по RUNBOOK; живая сверка мастера только там, где тест или прогон расходится с ожиданием.
  4. При FAIL — исправление в принятом объёме, тем же этапом. Расширение объёма — Blocked с вопросом Генератору.
- Причина перепроверки: после прежней приёмки изменены общие модули оболочки узлов (`calculator-node.mjs`, `node-read-*`, `workspace-ui.mjs`, `node-procedure.mjs`), а CLI-регрессии старых узлов не было.
- Этапы 1 и далее — непокрытые режимы Help 7.4, каждый отдельной карточкой по решению владельца.
- Выход этапа 0: PASS исполнителя и независимая приёмка того же SHA; реестр отражает `client_technical_validation` и `analytical_validation` по результату.
