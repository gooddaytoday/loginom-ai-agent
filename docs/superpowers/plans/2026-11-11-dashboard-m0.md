# Dashboard M0. План реализации срочных мер

> Для исполнителя после отдельного назначения: `executing-plans` или `subagent-driven-development`. Отмечать шаги по мере проверки.

**Результат.** На локальном dev-стенде пользователь открывает свой опубликованный dashboard и получает снимок выбранного узла по ID. Сервис закрывает публичную выдачу двух служебных файлов и последнего снимка. Оба клиента Studio прекращают предлагать «Запомнить».

**Архитектура.** Сохраняется текущий путь Studio → Apache → Node. Ограничение файлов применяется только при выдаче по HTTP. Сервер продолжает использовать файлы публикации для поиска приложения и чтения сохранённого примера.

**Стек.** Текущие JavaScript, Node `node:http` и `node:test`, Apache и Bash. Исходные требования — [M0 в roadmap](../specs/2026-11-11-dashboard-architecture-roadmap.md#m0-срочные-меры-в-текущем-javascript) и [порядок работ по изоляции](../../security/dashboard-isolation.md#порядок-работ).

## Границы и объём

- До M2 открывать только свои доверенные dashboard, в том числе при проверке. M0 ещё не изолирует приложение от Studio.
- Существующие URL приложения, ключ привязки, `POST /dashboard/lookup`, `POST /dashboard/targets` и чтение по ID сохраняют контракт. Пакет `.lgp` не меняется.
- В объёме пять файлов. Служба и её тесты — `dashboard/server.mjs`, `dashboard/server.test.mjs`. Установка и конфигурация dev-стенда — `dashboard/install.sh` (он генерирует файл Apache). Инструкции для агента и пользователя — `dashboard/AGENTS.md`, `dashboard/README.md`. Ориентир для будущего `git diff --stat` — 5 файлов, 100–170 добавленных и удалённых строк суммарно, включая тесты и инструкции.
- Вне M0 — миграция на TypeScript, новый установщик, CI, браузерная песочница, одноразовые снимки, публикация через хранилище и установка на release. На release настройкой входа распоряжается администратор. S1–S8 и замеры лимитов для M0 не нужны.

## Что проверить особенно внимательно

1. Отсутствующая публикация тоже даёт 404. Проверять существующий пример, для которого открываются страница и ресурс сборки (задача 1).
2. Перезапуск Node очищает снимки. Проверять закрытый `current` рядом с успешным чтением **нового** снимка по ID (задача 2).
3. Адрес Apache в Docker-сети отличается от loopback. Отладочный флаг и адрес TCP-соседа проверяются совместно (задача 2).
4. Без передачи исходного `Host` Node видит имя контейнера. Проверить штатный адрес пользователя через оба слоя и отказ каждого слоя отдельно (задача 3).
5. На dev-стенде два файла `client.json`. Новое значение должно дойти до обеих страниц входа с сохранением остальных настроек каждого клиента (задача 4).

Команды для Node ниже выполняются из `dashboard/`. В каждой задаче добавлять по одному тесту, наблюдать соответствующее падение, вносить минимальную правку и запускать тест повторно. Установку выполняет будущий исполнитель на выделенном dev-стенде из [рецепта](../../../dashboard/stand/README.md).

Для корня приложения и его JS-ресурса проверить статус 200 и ожидаемое содержимое. Запустить `node --test --test-name-pattern='metadata private' server.test.mjs`.

### 2. Сохранить чтение по ID, ограничить последний снимок локальной отладкой

- [x] Скорректировать проверки двух существующих тестов, которые сейчас требуют открытого `current`. После создания целей A и B проверить `assert.deepEqual(await request("targets/" + a.id), a)` и `assert.equal((await fetch(base + "/current")).status, 404)`. Сохранить проверку вытеснения старого ID.
- [x] Запустить `node --test server.test.mjs`. В обработчике GET разрешить `current` только при флаге и loopback-адресе `request.socket.remoteAddress`. Использовать фактический адрес TCP-соседа, включая IPv4, IPv6 и отображённый IPv4. Иначе вернуть обычный 404. Повторить тесты.
- [x] В тесте отладки запустить `startDashboard(env)` с флагом, создать снимок и по прямому loopback-соединению сравнить ID из `current` с ID созданной цели. Проверить тот же Node через интерфейс Docker-сети с разрешённым HTTP-заголовком `Host`: чтение созданного снимка по ID даёт 200, а `current` — 404 с тем же адресом и заголовком. Использовать тестовый порт, синтетическую цель и интерфейс, отличный от loopback. Если на машине только loopback, этот сетевой случай выполнить на dev-стенде. Штатный сервис остаётся с выключенным флагом.

После перезапуска создать новый снимок и убедиться, что по его ID ответ 200, а `/dashboard/current` через Apache даёт 404. Зафиксировать как `fix(dashboard): restrict latest snapshot to local debugging`.

### 3. Проверять исходный Host в Apache и Node

**Файлы и интерфейс.** `server.mjs`, `server.test.mjs`, `install.sh`. Адрес привязки сокета `DASHBOARD_HOST=0.0.0.0` нужен Apache для связи с Node внутри Docker. Он не задаёт разрешённые имена HTTP.

- [x] Добавить в `server.test.mjs` тест `dashboard accepts only configured hosts`. Использовать обычный публичный ресурс фикстуры и `node:http` для задания `Host`. Для разрешённого имени с портом ожидать 200, для постороннего имени и того же имени с другим портом — 403. Подтвердить падение командой `node --test --test-name-pattern='configured hosts' server.test.mjs`.
- [x] В `dashboardServer` проверять `request.headers.host` до разбора тела и выбора маршрута. Сравнивать полное имя с портом без учёта регистра. Для автономного Node по умолчанию разрешить только loopback-имена (`localhost`, `127.0.0.1`, `[::1]`) с фактическим портом слушателя. Для dev-прокси `startDashboard` принимает точные публичные значения из `DASHBOARD_PUBLIC_HOSTS` (через запятую) и передаёт их как `allowedHosts` вместо локальных значений. Повторить тест и весь `server.test.mjs`.
- [x] В генерируемой `install.sh` секции Apache для `/dashboard/` разрешить `127.0.0.1:32768` и `localhost:32768`, проверяя HTTP-заголовок, и включить `ProxyPreserveHost On`. Передать ту же пару Node через `DASHBOARD_PUBLIC_HOSTS`. Правило касается маршрута dashboard. Сохранить штатные `ProxyPass`, `apachectl -t`, graceful reload и проверку доступности сервиса.
- [x] Выполнить `bash -n install.sh` и `./install.sh`. На том же публичном ресурсе проверить оба разрешённых адреса через Apache (200) и посторонний `Host` (403 на входе Apache). Различить ответы слоёв по журналу отказа Apache для этой проверки и тесту прямого запроса к Node. Убедиться, что обе страницы Studio открываются.
