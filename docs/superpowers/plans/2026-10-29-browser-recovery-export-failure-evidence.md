**Goal:** В actual `readNativeExportFile` сохранить точное наблюдение отказа поиска, чтобы следующая единственная unchanged BR-S5 либо дала исходный strict PASS, либо доказала конкретную ветвь отказа без нового browser read.

**Architecture:** Существующий конструктор `STORAGE_ENTRY_UNAVAILABLE` удерживает один private error payload с уже прочитанными table/name lookup. Внешний catch actual Export reader перед восстановлением пишет его через существующий `onRecord` и существующую фазу `export_file_observation_unsettled`; алгоритм поиска и публичная квитанция не меняются. Это диагностика следующего решения, не исправление причины и не обещание S5 PASS.

**Tech Stack:** текущие Node ESM, `node:test`, `createExecutionJournal`/redactor, stock `stageResources`, unchanged managed BR-S5.

## Review Focus

1. Пустой table либо первая name row без scroll: нужен именно отказавший table до ready predicate, не прошлый post-action snapshot (Task1 Step1).
2. Accepted table с нулём eligible anchors: сохранить этот table и именно следующий absent exact-name lookup (Task1 Step2).
3. Callback throw/неверный ACK дополнительной записи: прежний отказ, quiet restoration и lease release сохраняются; обязательный journal failure остаётся блокирующим (Task1 Step4).
4. Snapshot/stack содержат недоверенный текст: штатная redaction, отсутствие payload в public failure/receipt; raw snapshot не даёт разрешения на UI действие (Task1 Step3).
5. Success, waiter timeout и другие ошибки: нет новой записи обычных чтений и нет нового поведения; остальные shared-reader callers не получают новый публичный результат (Task1 Step5).

## Почему существующих данных недостаточно

Read-only audit private root, указанного в source report, нашёл633 execution events и10 host diagnostic events. В journal только четыре table post-action snapshots (строки618/620/622/624); последний имеет65 name rows,14 anchors, readinessfalse. Строка627 сохраняет reason, но не failing logical sample/stack. Host diagnostics не содержат table; console log не содержит storage failure evidence. `playwright.json`: saveSessionfalse; trace/zip/har/video отсутствуют, artifacts содержит только console log. Ни эти файлы, ни browser cache не восстанавливают JS-local response, на котором выбросили ошибку. Новых запусков при audit не было.

В `findNativeStorageRow` нужный `s` уже существует в обеих ветвях. Вторая ветвь также имеет `r` от последующего exact-name discovery. Waiter удерживает `exportStorageObservation` только для собственного exhausted timeout; немедленный `unavailable()` его не выставляет. Существующий catch `ready` пишет лишь summary timeout, а второй `no_scroll_owner` возникает вообще после возврата из `ready`. Поэтому переключатель штатных logs не решает задачу; дополнительный внешний driver меняет caller/timing и уже остановлен на UI_EPOCH_CHANGED.

## Минимальное решение и цена

В local `unavailable(s, reason, lookup = null)` добавить одно свойство Error `exportStorageFailure:{table:s,name_lookup:lookup,stack:error.stack}`. Существующие `code`, message и `storage_entry:{name,directory,reason}` оставить неизменными. Table branch передаёт только `s`; branches после exact lookup (`no_scroll_owner` и существующий `folder_end`) передают `r`. Stack снимается с той же исходной Error и позволяет сопоставить throw site со staged source; отдельный branch enum/счётчик/history не нужны. Payload не вкладывать в `storage_entry`: delivery уже публикует это поле.

Отдельный private payload необходим, потому что повторное использование waiter `exportStorageObservation` включит прежний `ready` catch с урезанным summary и обязательной record-ошибкой до cleanup. Переустройство waiter ради диагностики затронуло бы его timeout-контракт. Один payload на существующей Error повторяет уже применённый механизм передачи failure evidence без изменения экспортированных сигнатур. Он существует только до обработки отказа; других накопителей нет.

В outer catch `readNativeExportFile`, после фиксации прежнего `failure` и до восстановления, только при matching `STORAGE_ENTRY_UNAVAILABLE` с этим payload сделать одну awaited diagnostic запись через **исходный `onRecord`**, а не local обязательный `record`: `{phase:'export_file_observation_unsettled',operation_id:operation.id,observation:error.exportStorageFailure}`. Проверить обычное совпадение phase/operation ACK; локальный catch записи поглощает только её ошибку. Не менять `journalFailed`, `uncertain`, `navigationOnly`, исходный `error` или `failure`. Нет retry/fallback/stderr/new receipt field. Отсутствие корректной записи означает diagnostic UNKNOWN и сообщается при разборе evidence; обязательные records восстановления по-прежнему могут блокировать результат.

Данные остаются наблюдениями недоверенного UI: записать исходные JSON snapshot объекты через существующий `createExecutionJournal` с redactor, не выполнять их и не использовать для cleanup/admission. Redaction сохраняет structural evidence и может заменить чувствительные строки; отсутствие нужных bindings после redaction означает UNKNOWN. Не обещать byte-exact raw secrets. Source-managed producer уже возвращает bounded JSON, нового parser/validator/limit нет.

Actual callers: `readNativeExportFile` (единственный новый writer); `artifact-delivery.mjs:readRow` передаёт свои ready/guards и публикует только прежние message/storage_entry; `text-export-observer-native.mjs` использует свои callbacks. Последние два не менять. `text-export-node.mjs`/`node-apply.mjs` сериализуют прежний refusal либо фиксированную message/cause, не произвольные свойства Error. Public schemas/generated contracts не менять.

Оценка всего slice:6 tracked файлов, около+215/−10 строк (production1 около+20/−3, tests2 около+70, план1 около100, append source report1 около20, canonical checkpoint1 около5). `git diff --stat` считать вместе с tests/docs; при>450 changed lines остановиться и упростить. Новые зависимости/подсистемы0; стоимость — одна запись только после отказа. Диагностическая запись до cleanup имеет обычную fsync latency; новой timeout machinery нет.

## Stop / exclusions

STOP после единственного диагностического результата или strict S5 PASS; при недоступном journal, ином error, mismatch source/stage/owner, incomplete evidence, cleanup refusal/unknown — зафиксировать факты без повторов. Само добавление записи может повлиять на время cleanup, но не на уже случившийся отказ; исчезновение отказа не доказывает causal fix. Если минимальный payload требует новый transport, публичный контракт, общий error framework или настройки, остановиться до их создания. Не исправлять storage readiness/scroll/UI_EPOCH_CHANGED, не расширять standalone driver, не добавлять inventory/telemetry/recovery/hardening, не запускать installed/model acceptance, merge/release.
