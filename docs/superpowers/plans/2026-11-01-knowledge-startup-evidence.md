# Knowledge startup: сохранить безопасную причину отказа

> Сведения о локальном окружении обезличены. Приватные подтверждения, упомянутые в документе, не включены в репозиторий.

Результат: один штатный installed/sandbox verify сохраняет безопасную классификацию реального startup отказа и original ACK/exit в private evidence после validation cleanup. Это диагностика, не доказанное исправление сети или повторного post-ACK сбоя; accepted24 и бюджеты не меняются.
Основание: новые проверенные байты теряют connectRemote cause в knowledge-client, IPC и supervisor; validation finally удаляет исходные runtime-close. Прежние Knowledge partial-frame PASS не повторяются ради диагноза.

1. Независимое review этого узкого плана; проверить, что existing key-only Knowledge child не использует cwd как отдельную mutable validation identity. Если отдельная cwd действительно обязательна, сохранить только квитанцию перед rm вместо нового общего logger.
2. Один RED→GREEN regression через реальный Host check: предсказуемый локальный MCP initialize отказ с небезопасными body/key/URL; после check failure и удаления validation остаётся только безопасный private runtime-close с тем же публичным LOGINOM кодом, ACK и actual exit. Затем по одному дополнительному контракту для nested network/AggregateError classification, только если основной тест его не покрывает.
3. Минимальный путь: локальный Error.cause в knowledge-client; attach безопасной startup классификации; private IPC → supervisor whitelist → существующий runtime-close JSON. Разрешены только stage=connect_initialize/catalog, фиксированный error class, numeric HTTP/MCP code, allowlisted network cause codes, abort/timeout boolean и elapsed_ms. Никаких message/stack/endpoint/headers/body/session/key/env. Успешные и обычные call ошибки без startup поля не меняются.
4. Validation Knowledge использует существующий root/knowledge/<generation> для cwd/receipt, так как child не пишет иной cwd state; filenames PID+UUID остаются уникальными. Удаление browser validation и все cleanup guards сохраняются. Это проще нового output option/copy pipeline. Проверить именно достаточность изоляции; новый runtime/API функционал не добавлять.
5. Focused pinned Node Knowledge tests и Host tests/typecheck; один independent combined source review. Ожидается 4code+2test+этот план, примерно130–190 изменённых строк; без новых зависимостей/сервиса/runner/логгера/ретраев.
6. Собрать и штатно установить отдельную диагностическую поставку из существующего isolated knowledge-close-build checkout по knowledge-benchmark-activation.md, только собственные hunks поверх текущего candidate; inventory/manifest/pins честные. Не переносить остальной W diff. Принятый Benchmark executable pin для измерений не переключать на diagnostic: private verify config отличается только EVAL_CLI_BIN.
7. После установления idle/ownership выполнить ровно один существующий parallel-env verify --parallel1 (не prepare/setup, без модели) с принятым slots/config, прокси-клиент/env и приватным out. Сохранить original result/receipts до вспомогательной обработки; existing profile history и root QA сохраняют ровно runtime-close, не считать его частью execution-events archive. Собственные leases/процессы закрыть штатно.
8. По actual safe cause выбрать только доказанное минимальное исправление либо конкретный внешний блокер. Невоспроизведение отказа не считать fix и не повторять неизменный verify. Post-ACK markers/правка — только если этот отдельный сбой воспроизведётся; текущий план их не добавляет. Завершить bounded этап независимым review результата и checkpoint.

Исключены модели/судья/cold rerun, новая авторизация/инфраструктура/бюджеты, повтор завершённых форм, смена pins принятых пар, ослабление TLS/redirect/cleanup/kill guards, commit/push/merge/release и heartbeat. P19/P24 сохраняют свои фактические версии; новая поставка сама не делает их сопоставимыми.

## Проверка потерянного флага proxy в management status

Актуальные W и исполняемый H имеют одинаковые исходники этой границы: agentCommand(binary+slots) фильтрует env через childEnvironment и теряет NODE_USE_ENV_PROXY; ordinary management status получает результат напрямую, а sandbox check заново включает flag при наличии proxy. Успешный SDK явно включал flag. Это подтверждённое расхождение условий; связь с прежним post-ACK SIGKILL остаётся гипотезой.

1. Независимо проверить этот узкий план. В существующем agentCommand сразу после построения isolated env включать NODE_USE_ENV_PROXY=1 только для binary+slots с уже отфильтрованным непустым proxy, по тому же predicate, что в sandboxCommand. Общий childEnvironment/судья, TLS, runtime, exit/cleanup guards не меняются; новых helper/опций/зависимостей нет.
2. RED→GREEN существующего теста credential-free proxy routing: valid proxy включает flag даже без внешнего flag, NO_PROXY сохраняется; отсутствующий/отброшенный секретный или path/query proxy не включает flag и не раскрывает canaries. Focused cli/sandbox tests и typecheck из evals; одна независимая combined source review до live.
3. Адресно применить только собственные hunks cli.ts/cli.test.ts к W и H, чьи исходные bytes совпадают. Исполняется H из принятого HARNESS_ROOT; его изменение зафиксировать в handoff как recovery-исключение владельца. Ожидается 2code/test файла (около10–20 строк) в каждом checkout и существующие документы (ещё15–25 строк); runtime/model/judge pins прежние. Новая функциональность модели и повтор измеренной формы исключены.
4. После проверки владения/idle — один штатный verify на прежней постоянной diagnostic installation без markers, parallel1/model0. Сохранить безопасное фактическое подтверждение flag у status/check только из принадлежащего child, без полного env; original close receipts и cleanup/release. Критерий: status0, реальный sandbox check0, все Knowledge ACK+actual exit0/noSignal и штатный release. SDK PASS не заменяет это.
5. При отказе сохранить конкретный отрицательный результат без неизменного повтора. Native DNS/worker и исторический P19 trigger не объявлять доказанными; новые markers/stack probes или изменения exit не входят в эту правку. Завершить independent actual review и короткий checkpoint.
