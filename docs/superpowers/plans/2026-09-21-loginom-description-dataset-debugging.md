## 1. Цель и договорённости

Выявить и исправить дополнительные проблемы создания сценариев через
установленный Loginom AI Agent, когда начальный пользовательский вход —
неизменённые `description.md` и `data/dataset.csv` выбранной аналитической задачи.
Модель сама строит граф и выбирает способы настройки поддержанных узлов.

Подтверждённые решения:

| Вопрос | Решение |
| --- | --- |
| Успех | Пакет создан, выполнен и сохранён; факт подтверждён наблюдениями и квитанциями |
| Аналитическая оценка | Правильность чисел и полнота соответствия description не входят в приёмку |
| Объём | 10 задач: 02, 19, 23, 24, 27, 36, 45, 47, 48, 65 |
| Порядок исправлений | Сначала все 10 на одной исходной сборке, затем разбор и исправления; исключение — общий блокер, делающий остальные прогоны невозможными |
| Повторы | Одна независимая попытка на задачу в исходной и итоговой сериях; дополнительные — для воспроизведения и проверки исправлений |
| Провокация сбоев | Только естественные прогоны и диагностика возникших проблем; искусственно F03/F07/compaction не вызывать |
| Бизнес-уточнения | Отвечать разрешено; прогон отмечается как выполненный с участием человека |
| Кто отвечает | Агент-исследователь выбирает и записывает разумные бизнес-допущения; при повторах сохраняет их |
| Граница исправлений | Только ошибки уже поддержанных операций текущих 14 типов; новые типы и новые режимы не добавлять |
| Предел попытки | 30 минут от отправки начального сообщения; затем сохранение доказательств и штатная остановка |

Предел одинаков для исходных, целевых и итоговых попыток создания пакета.
Ожидание бизнес-ответов записывается отдельно, но не вычитается из этих 30 минут.
Завершение отмены и подтверждение cleanup могут потребовать дополнительного
времени; это не продление работы модели над задачей. Предел закрепить в manifest серии.

Исходная и итоговая серии содержат минимум **20 зачётных попыток**. Целевые
повторы и диагностические запуски считаются отдельно. Одна попытка на задачу
не позволяет оценить вероятность успеха или доказать отсутствие редких сбоев.

Не входят: сравнение с `result.txt`, эталонным графом или рассчитанными числами;
обязательный аналитический отчёт; холодное открытие сохранённого пакета;
новые данные; расширение до остальных задач; обязательное покрытие 14/14;
автоматическая публикация или замена пользовательской установки.

Прикрепить оба исходных файла через интерфейс установленного Desktop.
При отправке проверить присутствие двух вложений, их имена, байты и SHA-256

Путь формируется в наблюдаемой папке текущего пользователя Loginom, например
`/user/description-debug-<series>-D02-baseline-a01.lgp`. Путь — организационный
параметр, не подсказка о решении. Если он занят, выбрать новый до отправки;
чужие файлы не перезаписывать. Экспорт CSV не добавлять как обязательное
требование: он нужен только при самостоятельном выборе модели.

Не передавать `task.md`, `result.txt`, готовый пакет, ожидаемые результаты,
схему графа, список вызовов, заранее выбранные имена полей или формулы Loginom.
Не исправлять входное описание ради прохождения технического теста.

При вопросе модели:

1. Проверить, относится ли вопрос к бизнес-правилу или данным. Ответ опирается
   только на description, dataset и уже записанные допущения этой задачи.
2. Если правило не задано, исследователь выбирает разумное допущение и явно
   обозначает его как допущение. Отсутствующие факты/данные не выдумывать.
3. Передать через тот же Desktop только ответ на вопрос. Например, допустимо
   определить границы ABC; недопустимо назвать функцию, узел, tool ID или
   действие для выхода из ошибки мастера.
4. Сохранить вопрос, точный ответ, основание, время и ID сообщения; установить
   `assistance=business`. Ответы хранить в реестре бизнес-допущений по задаче.
5. В следующих попытках не добавлять ответы в начальный prompt. На тот же
   вопрос отвечать тем же правилом. Новый вопрос получает новую запись;
   различия фактического диалога сохраняются в отчёте.

Если модель сама выбрала другое бизнес-допущение и не спрашивает, её не
переучивать: аналитическая правильность исключена из этапа. Запрос технической
помощи не разрешает дать такую помощь в зачётном прогоне. Его исход фиксируется,
а дальнейшая ручная диагностика относится к отдельному `DEBUG_ONLY` запуску.

## 5. Доказательства и критерий отдельной попытки

Технический PASS (`CREATED_EXECUTED_SAVED`) требует всех подтверждений:

- Построенный граф существует в пакете, а данные на входе связаны с реально
  доставленным пользовательским CSV. Пустой пакет или одна загрузка файла
  не подтверждают создание и выполнение сценария.
- Подтверждено выполнение итогового рабочего графа: квитанции операций,
  завершённые исполнения и доступный фактический выход. Пустая выборка
  допустима; ошибка чтения или отсутствующее свидетельство выполнения — нет.
- Сохранён именно этот пакет по назначенному уникальному пути:
  `save_completed`, наблюдаемое состояние сохранения и подтверждённый cleanup.
  Нет незавершённого действия с неизвестным исходом, выданного за завершённое.

Не задавать минимальное количество узлов, обязательные типы, число выходных
строк или эталонную структуру. Исправленные моделью ошибки не отменяют PASS.
Если граф перестроен, доказательства должны относиться к его итоговому состоянию,
а не к удалённым узлам. Фраза модели «готово» сама по себе не является доказательством.

Фиксировать независимо:

| Поле | Значения / смысл |
| --- | --- |
| `outcome` | `CREATED_EXECUTED_SAVED`, `FAILED`, `BLOCKED`, `INTERRUPTED`; `NOT_STARTED` только в плане |
| `assistance` | `none` или `business`; оба допустимы для технического PASS |
| `run_kind` | `baseline`, `targeted`, `final` или `DEBUG_ONLY` |
| `failure_kind` | product, model, unsupported, input, environment, provider, observation; nullable для PASS |
| `analytical_correctness` | Всегда `not_checked` |
| `description_completeness` | Всегда `not_checked` |

Наблюдение исследователя без сообщений/изменения Loginom не делает попытку
выполненной с участием человека. Ручная настройка узла, техническая подсказка,
исправление запроса модели или продолжение через прямой runtime исключают
такое продолжение из зачётной серии. Сохранить первоначальный исход отдельно.

различию request ID или появлению очередного сообщения модели.

Если предел достигнут либо подтверждено отсутствие прогресса после штатного
deadline операции: сохранить последнюю историю и состояние, запросить штатную
остановку через Desktop и проверить её результат/cleanup. Подтверждённая отмена

Не удалять её журнал и не повторять действие в другом чате вслепую. Пока остаётся

## 10. Отчётность, ограничения и продолжение

При запуске создать новые файлы рядом с этим исследованием:

- `description-dataset-debugging-results.md` — таблицы baseline/final,
  целевые повторы, ссылки на подтверждения и изменения.
- `description-dataset-debugging-checkpoint.md` — текущая фаза, кандидат,
  законченные/оставшиеся задачи, активные процессы и безопасный следующий шаг.
- `description-dataset-business-assumptions.md` — очищенные бизнес-вопросы,
  ответы и основания; без технических подсказок и ожидаемых результатов.

Вне Git для каждой попытки хранить `prompt.txt`, manifest входов/среды,
`chat.json`, компактные metadata, `final.png`, квитанции и доказательства
сохранения; для проблем — состояние до вмешательства. В Git попадёт компактное
описание и ссылка на приватный каталог, без credentials, auth, сырых журналов
и копий пользовательских профилей.

Запись попытки: ID/phase/attempt, время, version/source/ASAR, Loginom build,
model/variant, skill/catalog revisions, hashes двух файлов, chat/profile,
путь пакета, run kind/outcome/assistance, фактические типы и режимы узлов,
execution/save/cleanup, ошибки и их исходы, ссылки на доказательства.
В отчёте разделить product/model/input/unsupported/provider/environment failures;
не превращать каждую ошибку инструмента в отдельный продуктовый дефект.

F03, F07, compaction и первопричина F12 остаются по
[прежнему аудиту](../../testing/loginom-ai-agent/scenario-debugging-audit.md):

| Ограничение | Что фиксировать, если проявится естественно |
| --- | --- |
| F03: read после execute | Факт завершённого исполнения до ошибки чтения, pending/UI/доступное продолжение; новый Execute не доказывает восстановление прежнего чтения |
| F07: deadline/resume | Исходный срок, число resume, фазы/эффекты и реально заблокированный корректный путь; истёкший бюджет сам по себе не дефект |
| F12: исчезновение порта | Граф, port binding, видимость/координаты и состояние чтения; успешный повтор означает «не воспроизведено», не доказательство устранения причины |
| Compaction | Факт сжатия, история до/после и сохранность operation/node/status/error/next step; просто длинный чат не является такой проверкой |

Специальные аварии, принудительное сжатие и нагрузочные варианты не добавлять.
Если ветка не возникла, её статус — `not_exercised`, а не `fixed`.

При паузе по запросу пользователя сохранить точку продолжения и фактическое
состояние активной работы; не заявлять о завершении незаконченного действия.
В возобновлении сначала сверить файлы, версии, процессы и исход предыдущей
операции. Новая попытка не должна вслепую повторять неопределённую мутацию.
В конце закрыть только собственные тестовые приложения после штатного cleanup.
