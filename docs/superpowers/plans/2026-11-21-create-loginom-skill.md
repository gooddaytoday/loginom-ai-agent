# План реализации create-loginom-skill

> Для исполнителя. Выполнять по этапам через `executing-plans` или `subagent-driven-development`. Отмечать пункт после его проверки. Утверждённый [дизайн](../specs/2026-11-21-create-loginom-skill-design.md) задаёт пользовательский контракт.

**Цель.** По одной просьбе агент создаёт переносимую папку или устанавливает готовый скилл из папки либо GitHub. Установленный скилл работает следующим сообщением в уже открытых Desktop и CLI одного пользователя и канала.

**Архитектура.** Один поставляемый `create-loginom-skill` ведёт диалог. Одна операция backend v1 `skill_install` отвечает за получение и проверенную установку файлов. Она нужна для одинаковой работы в поставляемых Desktop и CLI без зависимости от установленного пользователем shell-инструментария. Узкая доработка существующего каталога даёт обоим процессам увидеть опубликованную папку. Текущий инструмент `skill({name})` загружает её как обычный пользовательский скилл.

**Стек.** TypeScript, Effect, существующий YAML-парсер, файловая система Node, сетевой клиент backend и уже поставляемая `@zip.js/zip.js`. Рабочая ветка `create-loginom-skill`. Оценка всей реализации, включая тесты, инструкции и результаты прогона: 18–24 файла, примерно 650–950 добавленных и 40–90 удалённых строк по `git diff --stat` относительно коммита с утверждённым планом. Если объём превысит верхнюю оценку вдвое, пересмотреть подход.

## Общие условия

- Использовать один каталог `<системный каталог настроек пользователя>/<Product.channels[channel]>/skills`. Для Linux учитывать XDG, для Windows — AppData, для macOS — Application Support. Это сосед каталога `cli`; отдельный CLI-профиль его не перенаправляет. Уважать каналы prod/beta/dev. Внешние каталоги Codex/Cursor и независимые данные приложений сохраняются.
- Резервирование имени и верификация официальной поставки принадлежат Product и Host. Внешняя папка не получает происхождение `bundled`, digest поставки или новый профиль полномочий. Локальный путь установки работает без подключения к GitHub. Разрешения агентского режима, сессии и рабочего каталога действуют на фактические чтения, сеть и запись.
- Не нужны отдельная служба, наблюдатель за файлами, связь Desktop с CLI, постоянный индекс, второй скилл, менеджер обновлений и изменения UI. Публикация релиза, отправка репозитория вовне и изменение реальных пользовательских профилей за рамками плана.
- В каждом этапе сначала воспроизвести одно расхождение, добавить ближайшую к реальному входу проверку, получить ожидаемый RED и исправить его. Следующий тест писать после GREEN. Запускать тесты и `bun typecheck` из затронутых пакетов. До каждого тематического коммита из корня — `bun run secrets staged` и проверка staged diff.

## На чём сосредоточить ревью

| Условие | Наблюдаемый результат | Этап |
| --- | --- | --- |
| Оба процесса уже открыты и читали каталог; CLI использует свой профиль | Оба прежних чата загружают один новый скилл и читают его вложенный ресурс | 1 |
| Имя совпало с проектным или защищённым, установку запросили в ограниченном режиме | Сохраняются приоритеты и разрешения, результат сообщает о конфликте | 1–2 |
| Две установки одного имени, повреждённый источник или недоступная ссылка | Видна одна целая папка либо прежнее состояние, прежние файлы целы | 2–3 |
| GitHub-репозиторий содержит несколько скиллов либо ветку с косой чертой | Выбирается правильный каталог на той ревизии, которую видел пользователь | 3 |
| Автор передаёт готовый скилл коллеге или предлагает в базовую поставку | Работают относительные ресурсы, назначение понятно по описанию, продуктовые проверки выполняются отдельно | 4 |

Загрузчик и установщик добавляют `skills` к результату одной и той же функции. Сохранять существующий способ определения канала при запуске Desktop и standalone CLI. Имя назначения выводится из разобранного `SKILL.md`; пользовательский параметр назначения не нужен. В `src/skill/install.ts` выделить общую для обоих источников публикацию `installSkillDirectory(sourceDirectory, sharedSkillRoot)`. Для тестовой папки проверять новое имя, работу вложенного ресурса и фактический источник через `Skill.require`. Актуализировать ожидания комплектности в `packages/opencode/test/{skill,cli}/bundled-skills.test.ts`, `packages/loginom-host/test/stage-resources.test.ts` и `packages/desktop/test/loginom/product-skills-smoke.mjs`. ## 2. Повторная установка, конфликт и отказ

- [ ] В `packages/opencode/test/tool/skill-install.test.ts` перенести проверки на тот же `skill_install`, которым пользуется модель. Для одинаковых файлов ожидать «уже установлен», для различных под тем же именем — конфликт и побайтно прежний результат. Для двух одновременных установок одного имени проверить фактическое содержимое и ответы обоим вызовам. Сравнивать относительные пути, содержимое и значимые исполняемые права; учесть свойства файловой системы назначения. Постоянный журнал установок не нужен.
- [ ] Довести `src/skill/install.ts` до этих результатов. Читать/копировать только содержимое выбранного скилла; исключать `.git`, не исполнять файлы. Сохранять бинарные ресурсы и работоспособность обычных POSIX-скриптов. Ссылки на ресурсы внутри выбранного дерева должны сохранить назначение; выход из дерева, циклы, коллизии путей, специальные файлы и неполная копия дают отказ до появления установки. Если параллельный вызов успел опубликовать папку, сверить победившую копию. Удалять только собственную временную папку. После успешной публикации отдельно сообщать о возможной ошибке чтения каталога, сохраняя установленные данные.
- [ ] Проверить отказ при запрете чтения источника/записи назначения и отсутствие нового инструмента в ограниченных профилях. Проверить, что внешний `SKILL.md` с защищённым именем не подменяет поставляемый даже при неисправной поставке. Выполнить из `packages/opencode` `bun test test/tool/skill-install.test.ts test/product/tool-policy.test.ts test/skill/bundled-skills.test.ts test/cli/bundled-skills.test.ts`, затем `bun typecheck`. ## 3. Обычный GitHub-репозиторий и ссылка на каталог

- [ ] В новом `packages/opencode/test/skill/github-source.test.ts` на маленьких ZIP-фикстурах и локальном HTTP-ответчике проверить обе формы URL, ветку с `/`, корневой скилл, единственный вложенный, несколько и ни одного. В случае выбора ожидать имена, пути и ссылки с закреплённой ревизией; общий каталог пока пуст. Неверный путь, прерывание скачивания и отказ доступа сохраняют прежнее состояние. Сетевой тест не зависит от доступности GitHub.
- [ ] В `packages/opencode/src/skill/github-source.ts` принимать HTTPS-ссылки github.com на репозиторий и на `tree/<ref>/<path>`. Для репозитория разрешать его ветку по умолчанию; для `tree` находить соответствующую ветку, тег или commit, включая имена из нескольких компонентов. Получить SHA до выбора. Скачивать ZIP GitHub на этой ревизии через существующий транспорт и открывать уже используемой `@zip.js/zip.js`. Не запускать Git, установочные скрипты или системный распаковщик. Учитывать отмену, фактическое место назначения перенаправления и существующую сетевую политику. Существующий токен GitHub, если он доступен, используется только для GitHub API; в чат, URL с учётными данными и логи он не попадает. [API GitHub для архивов](https://docs.github.com/en/rest/repos/contents#download-a-repository-archive-zip)
- [ ] В `skill_install({source})` направить GitHub-ссылку в эту ветвь. Если корневого `SKILL.md` нет, перечислить каталоги с ним. Для нескольких кандидатов вернуть список с именами и ссылками на их пути и SHA; `create-loginom-skill` задаёт штатный вопрос и повторяет вызов с выбранной ссылкой. Для одного — передать файлы общей процедуре этапа 1. Разбирать записи архива как недоверенные, материализовать только выбранное дерево, проверять пути и типы до записи. Потоковую загрузку держать вне памяти модели. Незавершённая загрузка, превышение доступных ресурсов и ошибка архива не дают частичной установки. При отсутствии доступа объяснить возможность установки из локальной папки.
- [ ] Выполнить из `packages/opencode` `bun test test/skill/github-source.test.ts test/tool/skill-install.test.ts` и `bun typecheck`. В уже прогретом CLI дать реальную ссылку на доступный репозиторий с несколькими скиллами, выбрать один с безопасным текстовым результатом и применить его следующим сообщением в Desktop. Для воспроизводимости записать выбранные имя и публичный SHA. Пример подходящего каталога — [открытые скиллы Anthropic](https://github.com/anthropics/skills). Коммит `feat(skills): install skills from GitHub repositories`.
