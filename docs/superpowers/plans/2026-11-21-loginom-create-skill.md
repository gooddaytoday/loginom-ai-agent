# План реализации loginom-create-skill

Дизайн и план приняты владельцем 24 ноября 2026 года. Реализация начнётся по отдельной команде владельца.

> Выполнять через `executing-plans` или `subagent-driven-development`. Отметка означает проверенный результат в указанной среде. Контракт, примеры авторства, правила строгой и мягкой проверки — в [дизайне](../specs/2026-11-21-loginom-create-skill-design.md).

**Цель.** Из обычного чата создать стандартный переносимый скилл, проверить без установки, по просьбе установить из папки или GitHub и подтверждённо обновить его в работающих Desktop и CLI.

**Архитектура.** Один поставляемый `loginom-create-skill`. Один инструмент форка `skill_install` с read-only действием `validate` для папки и действием `install` для локального пути/URL. Запись идёт в существующий `~/.agents/skills`. Общий валидатор принадлежит runtime, подготовка и публикация — Host, связь с OpenCode v1 — существующим адаптерам в `src/product/`. Прямые изменения upstream ограничить местами подключения, безопасным текстом встроенного скилла, получением актуальных команд и интерфейсом согласия. [ADR-0001](../../upstream-sync/adr-0001-modular-integration.md) · [Каталог интеграции](../../upstream-sync/catalog.md) · [Границы переезда на OpenCode 2](../../upstream-sync/opencode-2-migration.md)

**Стек.** Bun/TypeScript, Effect для адаптера v1, уже поставляемые Node FS, YAML и zip.js. Ориентир для реализации с тестами и эксплуатационными документами — **26–38 файлов, около 1 700–2 300 добавленных и 90–170 удалённых строк** по `git diff --stat` относительно принятого плана. Основная цена приходится на согласие в клиентах, безопасную замену, актуальность команд и живые проверки. Оценки этапов ниже включают тесты, это ориентиры для пересмотра объёма, а не бюджет, который требуется израсходовать.

## Условия выполнения и обзор рисков

- Устанавливать пользовательскую папку в `~/.agents/skills`. Для read-only `validate` каталог берётся из запроса, место установки вообще не создаётся. Изолированный eval с `LOGINOM_AI_AGENT_DISABLE_EXTERNAL_SKILLS=1` исключает внешние навыки, их команды и пути разрешений; установщик не должен обходить этот режим. Каналы, CLI-профили и другие агенты читают один общий каталог пользователя по собственным правилам. Не заводить новый источник, каталог каналов или `skills.paths`.
- Сначала реализовать и проверить выход «создай»; для установки первым сквозным путём остаются два прогретых приложения и перемещённый исходник. Отдельный небольшой коммит на проверенный результат. Каждый следующий тест писать после предыдущего RED → GREEN. Не включать массово чужие изменения. Проверять staged diff и запускать `bun run secrets staged` из корня перед каждым коммитом.
- Особые риски для ревью — ложный выбор между создателем и `customize-opencode` (этап 1), разница предупреждения и опасной ошибки (1–2), разрешение «всегда» или подтверждение другой редакции (2 и 4), устаревший список/правила или отмена идущего ответа (3), утрата прежней версии при прерывании либо параллельной замене (4). Проверки должны различать отказ и успешную установку с проектным переопределением.
- Новый сервис, постоянный наблюдатель, опрос бездействующих меню, собственный каталог плагинов, установка в чужие профили, порт v2, выпуск и отдельное исправление общего парсера проектных конфигураций за рамками. На ветке 0.4 проверяется backend v1; пакетная граница нужна для будущего переноса, который сейчас не выполняется.

## 1. Автор создаёт и проверяет скилл без установки (около 250–340 строк)

- [ ] **Проверка формата отдельным коммитом.** В `packages/loginom-runtime/client/lib/bundled-skill-manifest.mjs` выделить из существующих проверок заголовка и ресурсов общую функцию для папки/набора подготовленных файлов. Строгость определяется вызывающим сценарием, а не данными входного скилла. Упаковка передаёт своё дерево и перечень разрешённых генерируемых ресурсов, сохраняет проверки манифеста и хешей. Host использует ту же функцию для `validate` и `install` через Node-совместимый экспорт рядом с `src/bundled-skills.ts`. Пример RED: папка с двумя полями и сломанной локальной ссылкой получает ошибку до установки, после исправления ссылки проходит, рабочий каталог, установленные скиллы и файлы кандидата остаются прежними. Проверить точные границы длины, непустое optional `compatibility`, одно диагностическое предупреждение для безопасного стороннего расширения и отказ небезопасному заголовку на уровне данных. Сверить существующие bundled source/installed тесты. Исправить тест каталога, который сейчас требует `compatibility` безусловно.
- [ ] **Доставить сам скилл.** В `packages/product/skills/loginom-create-skill/SKILL.md` дать три явных примера («создай», «установи», «исправь и переустанови»), процесс выбора входа и результата, правила `description`, структуру, цикл пробы. Указать, как опираться на `loginom-automation`, проверять доступные инструменты и зависимости, сообщать о недоступном Python и неподтверждённой среде. Дать автору короткое руководство по базовой поставке, ссылки на первоисточники и автономные правила для офлайна. Добавлять `references/` только для подробностей, которые действительно мешают читать основной сценарий. Включить имя в `packages/product/src/skills.ts`. В `packages/core/src/plugin/skill.ts`, его `skill/customize-opencode.md` и регистрации `packages/opencode/src/skill/index.ts` **безусловно** исправить оба описания и старые указания о пути. Сохранить маршрутизацию запросов о конфигурации OpenCode. Не учить другой сборке вызывать отсутствующий у неё скилл.
- [ ] **Дать машинную обратную связь автору.** Через `packages/opencode/src/product/tool-contributor.ts::definitions` подключить небольшой адаптер форка: `skill_install({action:"validate", source})` запускает только чтение, возвращает путь, ошибки и предупреждения. Допуск определяется текущим профилем и разрешениями сессии, в docs/dashboard такой инструмент не добавляется. Установка будет вторым действием этого же инструмента. Исполнитель Host и валидатор не импортируют `packages/opencode`. В `packages/opencode/test/{skill,cli}/bundled-skills.test.ts`, `packages/loginom-host/test/stage-resources.test.ts` и `packages/desktop/test/loginom/product-skills-smoke.mjs` сохранить независимую проверку комплекта и добавить четвёртый скилл.
- [ ] **Первый реальный результат.** В обычном чате дать задачу «создай скилл, который перечисляет недостающие обязательные колонки перед импортом». В результате получить папку и успешный запуск `validate`; домашний каталог установки не изменился. Внести ошибку в копию файла, проверить диагностику, исправить и повторить пример. В изолированном тестовом контексте поставить корректную копию штатным файловым способом и проверить выбор на двух запросах: поиск недостающей колонки и обычный подсчёт строк. Отдельно проверить запрос о конфигурации. Отчёт отличает результат модели от проверки формата. `bun test test/skill/bundled-skills.test.ts test/cli/bundled-skills.test.ts test/product/load-order.test.ts` из `packages/opencode`. Источники для авторства: [формат](https://agentskills.io/specification), [практика](https://agentskills.io/skill-creation/best-practices), [руководство клиента](https://agentskills.io/client-implementation/adding-skills-support).

## 2. Локальная папка и одноразовое согласие (около 360–480 строк)

Адаптер передаёт `action:"install"` и разрешённый источник; домашний каталог определяется backend, произвольного назначения нет. Сохранить проверки на чтение/запись, `external_directory`, запрет инструмента и read-only агента. Проверить реальные пути и типы, границы дерева, буквальную пригодность имени для slash-команды и шаблонов прав. При обнаружении второго регистрируемого `SKILL.md` показать оба пути, попросить выбрать самодостаточную подпапку и ничего не публиковать. Проверить также двоичные файлы, относительные ресурсы и исполняемость нужных скриптов. Не исполнять файлы, исключить `.git`. Копию готовить на той же файловой системе, вне всех сканируемых корней. Папку с уже занятым или зарезервированным именем не трогать до этапа замены.
- [ ] Обработать отдельное согласие `skill_install` по образцу одноразового `dashboard_delete` в `packages/opencode/src/permission/index.ts`: учитывать deny, запросить именно `once` с идентификатором операции и точным снимком кандидата; прежний allow/always не подтверждает. Показывать в Desktop и TUI источник, SHA GitHub или локальную ревизию, имя, описание, предупреждения, путь и видимость для других агентов. Использовать `packages/app/src/pages/session/composer/session-permission-dock.tsx`, `context/permission-auto-respond.ts` и `packages/tui/src/routes/session/permission.tsx`. В standalone `run` с терминалом и без него применить существующую одноразовую семантику из `packages/opencode/src/cli/cmd/run.ts`, без обхода через `--auto`. Повторная установка идентичного дерева — «уже установлено», записи и согласия на изменение нет.
- [ ] Тестировать инструмент через обычный вызов агента и настоящую службу разрешений. Отказ в Desktop, TUI либо неинтерактивном запуске сохраняет каталог; согласие публикует полную копию. Проверить, что права доступа к источнику не подменены согласием на установку. Проверить тёплую установку из Desktop и холодную загрузку этой копии в CLI отдельным промежуточным результатом. Из корня пакетов — `bun test` по изменённым файлам тестов Host и клиентов, в `packages/opencode` также `bun test test/product/tool-policy.test.ts test/permission/next.test.ts`. Зафиксировать локальную запись и поддержку одноразового диалога отдельными проверяемыми коммитами.

## 3. Следующее сообщение и повторное открытие меню (около 300–410 строк)

- [ ] Сначала прогреть реальный `Skill.available`, `Command.list`, права агента и меню `/` в двух разных процессах. Смена папки под существующим именем должна стать видна как новый текст и новое описание. Проверять отсутствие старого результата, чтение вложенного ресурса и явный пользовательский запрет. Начинать с тестов `packages/opencode/test/skill/skill.test.ts` и `test/agent/agent.test.ts` в прежнем экземпляре рабочего каталога.
- [ ] В адаптере `src/product/skill-source.ts` использовать одно представление ревизии существующего домашнего `.agents/skills`. Для первого варианта достаточно отсортированных путей обнаруженных `SKILL.md` и отпечатка их содержимого: это обнаружит замену при совпадающих файловых временах. Вложенные файлы для каталога не хешировать. Использовать тот же домашний каталог, правила обхода вложенных скиллов и внешних ссылок, что у обычного discovery. При выключенном внешнем источнике вернуть управление до обхода. Проверять на пользовательском входе и запросе списка команд, без опроса на таймере и повторного полного обхода на каждый инструмент.
- [ ] Перед формированием следующего промпта/получением актуального списка при смене ревизии вызвать штатный `InstanceState.invalidate` адресно для данных `Skill` (обнаружение и загруженное состояние), `Command` и `Agent` в этом рабочем каталоге. Сохранять последнюю успешно применённую ревизию на экземпляр, включая первое открытие в каждом процессе; не отмечать её применённой до сброса всех зависимостей. При обычном обращении без изменений сохраняются кэши и порядок источников. Не вызывать глобальный `InstanceStore.reload/dispose`: финализатор `SessionRunState` отменяет активные ответы. Вызовы швов в upstream оставить короткими; проверить отсутствие циклических импортов `test/product/load-order.test.ts`.
- [ ] При открытии подсказки `/` в Desktop и TUI запрашивать **существующий** список команд из backend. Desktop использует `loadCommands`, TUI v1 — `sdk.client.command.list` и обновление `sync.data.command`. В TUI `packages/tui/src/component/prompt/autocomplete.tsx` сейчас исключает `source === "skill"`: показать эти команды в обычной подсказке с прежним приоритетом локальных команд; сохранить `/skills` и актуальность его запроса. При явном вызове применить права `skill` и передать тело как инструкцию через узкий вызов шва в `session/prompt.ts`, без предварительной подстановки команд из текста скилла. Пользовательские команды с источником `command` сохраняют прежнюю обработку. Тело скилла передать одной текстовой частью, без применения к нему `resolvePromptParts`; отдельно сохранить действительные аргументы и вложения пользователя. В тесте проверить состав частей на безвредных текстовых маркерах и настоящем пользовательском вложении, без запуска команд из примера. При смене ревизии обновить локальную модель списка штатным событием/синхронизацией клиента; у Desktop уже есть обработка `command.updated`, наличие отправителя и доставки в реально используемом v1 проверить. Открытие в другом процессе само вызывает перепроверку. Изменение публичного контракта событий, если понадобится после этой проверки, требует штатной регенерации клиента. Критерий — выбрать команду прямо из подсказки в обоих приложениях, без перезапуска и потери активного ответа.
- [ ] **Первая парная сквозная проверка.** Открыть обычные Desktop и CLI/TUI одного тестового пользователя, разные проекты, заранее отправить сообщение и открыть/закрыть `/` в каждом. Из Desktop установить локальный скилл, подтвердить и переместить исходную папку. В прежних чатах получить уникальное ожидаемое значение из вложенного файла общей копии; выбор через меню и выбор моделью проверить отдельно. Повторить при штатно выключенных внешних скиллах: не появляются имя, slash-команда или неявное разрешение на ресурс. Сохранить в отчёте факт двух живых процессов, источника загрузки и прежних сессий. Не переходить к сетевой установке до успеха этого пути.

## 4. Автор изменяет скилл и устанавливает снова (около 270–370 строк)

- [ ] Изменить исходник, сохранив имя. Сравнить фактическое дерево назначения с подготовленной копией, включая ресурсы и значимые режимы файлов. При различии показать отдельный запрос замены с обеими ревизиями; точное согласие одноразово даже для созданного ранее автором скилла. Одинаковые файлы дают идемпотентный результат. На равноправной папке, установленной другим агентом, действуют те же правила. Для назначения-ссылки и неоднозначной коллизии пути отказать до записи.
- [ ] Сопоставить действующий образец `src/skill/discovery.ts` с новой задачей: staging → резервная копия → публикация → откат при ошибке. Сериализовать **одно имя** между установщиками Loginom с общей межпроцессной блокировкой вне дерева скиллов; использовать существующий `Flock` с явным общим каталогом через адаптер v1 либо эквивалентный механизм Host, без привязки к разным каталогам state профилей. Готовить снимок и спрашивать до короткого участка записи. Под блокировкой повторно сверить прежнее состояние, при изменении запросить новое согласие или сообщить об идентичной победившей установке. Подготовленную и резервную копии держать на том же томе вне всех сканируемых корней. Резерв хранить до подтверждённой публикации; перед следующей операцией восстановить единственный незавершённый перенос этого имени, не уничтожая неизвестную версию. Предусмотреть возврат прежней копии при ошибке второго переименования. Не обещать другим агентам моментальную видимость во время двух переименований.
- [ ] Через обычные вызовы проверить отказ и успешную замену, два параллельных согласия, сбой публикации, прерывание между переносами с последующим восстановлением и смену только вложенного ресурса. В живых чатах выполнить цикл «исправь исходник → переустанови»: после отказа прежний результат, после подтверждения новый результат и описание в `/` под прежним именем. Коммит с проверенным циклом обновления.

## 5. Установка по обычной ссылке GitHub (около 340–450 строк)

- [ ] В Host добавить получение кандидата из HTTPS-ссылки GitHub через действующий сетевой транспорт и `@zip.js/zip.js`, с обычными разрешениями и отменой. Принимаются репозиторий и `tree/<ref>/<path>`, в том числе ветки с `/`. Определить фактическую ветку по умолчанию, разрешить ref в SHA и передавать этот SHA через выбор в диалоге и согласие. При закрытом источнике читать уже заданный `GITHUB_TOKEN` из окружения backend Desktop или CLI. Передавать его только официальному GitHub API, без передачи модели и без переноса заголовка при переходе на другой origin. Не брать секреты из файлов профиля, не раскрывать в UI/логах. Имеющийся `skills.urls` обслуживает другой контракт с `index.json`. [GitHub REST API](https://docs.github.com/en/rest/repos/contents#download-a-repository-archive-zip)
- [ ] Запросить корневой или единственный вложенный скилл; при нескольких отобразить имя и путь и спросить через штатный вопрос. Инструкции кандидатов остаются данными. Записи выбранного дерева проходят те же проверки путей, мягкую валидацию, согласие и публикацию, что и локальная папка. Скачивание выполняется во временную область, без системных Git/unzip и передачи архива в промпт. Отсутствие доступа, ошибка архива и отмена не затрагивают прежнюю установку. На локальном HTTP-ответчике проверить выбор SHA, несколько кандидатов, неоднозначность ref/path и отказ. Отдельно проверить успешный доступ к закрытому кандидату с искусственным тестовым значением авторизации из окружения и отсутствие этого заголовка после перенаправления на другой origin.
