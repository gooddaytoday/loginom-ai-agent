# Browser recovery: план выборочного переноса

> **Для исполнителей:** выполнять по этапам через `subagent-driven-development` или `executing-plans`; изменения кода — по `tdd`. Каждый этап предназначен для отдельной карточки Multica. Текущий результат записан в checkpoint в конце плана.

**Цель:** определить, какие изменения из `recovery-build-flag` спасают пользовательские сценарии или устраняют конкретный риск. Измерить каждое решение при его переносе и проверить принятые решения вместе на обычном корпусе.

**Архитектура:** сохраняем текущие контракты Dock, runtime, Host и агента. Переносим поведение по одному, с проверкой потребителей и независимым ревью. Для анализа используем существующие campaign controller, журналы и архивы.

**Технологии:** TypeScript/Bun, Node.js, Playwright/MCP, установленный standalone CLI, eval harness, systemd, Multica.

**Спецификация:** [согласованные решения и требования](../specs/2026-11-17-recovery-port-design.md). Она определяет объём работы; этот документ — порядок выполнения, карточки и checkpoint.

## Общие ограничения

- База `recovery-port` — `c5e652bfa3da10afbb6850b4adafdbde696a8c5c`. Донор — `1ab348a91d7c8ae180744293ff746f859d49145a`.
- Оцениваемый агент: `openai/gpt-6.1-terra`, reasoning `high`.
- Основное сравнение охватывает **146 кейсов × 3 раунда = 438 измерений** на версию, вместе **876**. Отдельно учитываются пилоты, подтверждающие эксперименты по отдельным решениям и 12 сквозных попыток S7.
- Судья: `gpt-6-sol/xhigh`; порог 70; judge timeout 300000 мс. Узловые code-oracle проверки сохраняются.
- Quality FAIL окончателен. Судейский повтор использует сохранённый артефакт; технический повтор не скрывает исходную попытку и не обнуляет счётчики.
- Реализация, карточки и evals начинаются по отдельному поручению. Слияние и выпуск требуют отдельной команды владельца.
- Реальные credentials, адреса стендов, личные пути и сырые архивы не входят в Git. Временные данные — в закрытом `$HOME/storage/tmp/`.

## Как передавать этапы через Multica

Для каждой строки следующей таблицы создаётся одна карточка. В её описание включаются цель и соответствующий раздел плана, ссылка на спецификацию и следующий паспорт:

| Поле карточки | Как определить |
| --- | --- |
| Вход | Полный SHA принятого результата предыдущей карточки; получить `git rev-parse recovery-port` и сверить с её checkpoint |
| Зависимости | ID предшествующих карточек из таблицы; начать только после их принятого результата |
| Владение | Один исполнитель с правом записи в `recovery-port`; остальные — read-only review |
| Область | Файлы и поведение своего этапа; соседние инструкции `AGENTS.md` обязательны |
| Проверки | Команды этапа, RED/GREEN evidence, соседние регрессии, независимое ревью |
| Выход | Полный SHA, решение по каждой гипотезе, результаты проверок, ссылки и hashes закрытых артефактов. В S1–S6 приложить паспорт эксперимента «до/после» |
| Завершение | Критерий своего этапа; checkpoint до 20 строк: вход/выход, результат, ограничения, следующий этап |

Карточки с кодом выполняются последовательно на одной ветке, без параллельных writers. Перед записью проверять фактический branch/HEAD и незавершённые изменения; чужую работу не сбрасывать. Если другой этап продвинул ветку, сначала принять его результат и обновить входной SHA. Не создавать отдельную систему очередей поверх Multica.

| Этап / тема карточки | Зависит от | Самостоятельный результат |
| --- | --- | --- |
| S0. Общая диагностика и условия контрольной серии | Этот план | Разбор построений, одинаковые средства инъекции сбоев; контрольный SHA B |
| S1. Свежие UI refs экспорта | S0 | Экспорт не использует устаревший ref списка |
| S2. Готовность файлового хранилища | S1 | Ограниченное ожидание/поиск файла и достоверная причина отказа |
| S3. Основания для browser recovery | S2 | Допуск только после подходящего отказа, без устаревших предложений |
| S4. Проверка результата recovery | S3 | Подтверждённый результат или честный неподтверждённый исход, включая NO_BASELINE |
| S5. Metadata и контекст задачи | S4 | Агент получает состояние текущей попытки при успехе и ошибке |
| S6. Освобождение runtime и лимиты | S5 | Корректное завершение, очереди и бюджет без второго владельца состояния |
| S7. Установленные сборки и управляемые сбои | S6 | Проверенные B/C, общий harness H, полные логи предварительной серии |
| S8. Контрольные 438 измерений | S7 | Ledger и архивы `loginom/high` |
| S9. Новые 438 измерений | S8 | Ledger и архивы `recovery-port/high` при тех же условиях |
| S10. Анализ и предложение для loginom | S8, S9 | Разбор 876 ключей, всех recovery-эпизодов и рекомендация по каждому переносу |

Здесь B — контрольная продуктовая ревизия после S0, C — итоговая продуктовая ревизия после S6, H — единый принятый harness/анализатор. Это выходы этапов, а не изменяемые branch aliases. Перед S7 записать их полные SHA и hashes артефактов. Если продуктовая диагностика меняется после фиксации B, сопоставимость пересматривается до кампаний; скрыто включать её только в C нельзя.

## Эксперимент в каждой карточке S1–S6

**У одного переноса три вопроса.** Можно ли на текущей базе воспроизвести ошибку и её последствия? Чаще ли с правкой получаем рабочий сценарий в этих условиях? Как часто такие условия встречаются при обычном построении? На первый вопрос отвечает пилот, на второй — парные испытания на отложенных задачах, на третий — обычная кампания. Затраты для каждой серии учитывать отдельно.

### 1. Найти ошибку на версии «до»

- [ ] До реализации сформулировать один проверяемый тезис. Записать задание пользователя, наблюдаемое условие перед ошибкой, ожидаемый результат и конкретный вред. Из исторических E2–E5 взять след для поиска. Например, E3 уже завершился с правильным артефактом, а в E5 агент создал второй экспорт без вызова recovery. Оба пригодны для проверки регрессий.
- [ ] Начать с доступного поведенческого теста, затем проверить установленный CLI с Terra/high. Рабочий ориентир пилота — три разных задания, подверженных этому сбою, и одно обычное, по две свежие попытки на сборке «до» (8 построений). Записать все исходы, включая успех базы. Второй запуск базы показывает, может ли агент самостоятельно справиться при тех же условиях. Если дефект воспроизводится, повторить весь выбранный пилот на кандидате при тех же условиях, включая успехи базы. Тогда доступны обе доли для расчёта объёма. При исходном ориентире получится ещё 8 построений. Объём пилота можно сократить с указанной причиной, например если версию «до» уже защищает нужный контракт.
- [ ] Для естественного сбоя закрепить предпосылки, например тип мастера или размер каталога. Для редкого события подготовить проверяемое воздействие непосредственно перед развилкой, например задержку строк FileStore после квитанции экспорта. Метка в нативном журнале подтверждает место и факт воздействия. В обеих сборках оно сохраняет возможность обычного обхода. Если ошибку удаётся вызвать только искусственно, так и обозначить область будущего вывода. Если в пилоте дефект не воспроизведён, записать условия, число попыток и причину остановки. Результат ограничен проверенными условиями. Расхода на подтверждение пока нет.

### 2. Сравнить две установленные сборки

- [ ] В S0 подготовить общий harness и приватную диагностику для целевых проб. Для первой проверки каждой правки использовать порядок сборки, изоляции, проверки ресурсов и архивирования из S7, не ожидая завершения S6. Контроль — принятая ревизия непосредственно перед правкой, кандидат — та же ревизия с одной правкой. Сохранить SHA, diff, hashes установленных сборок и общий формат evidence. Несколько самостоятельных решений в одной карточке получают разные сравнения. Если эффекты перекрываются, на итоговой сборке убрать одну спорную правку и повторить нужное сравнение. Если разделение нарушает контракт, проверять сочетание и указать это в выводе.
- [ ] До подбора правки независимый участник резервирует отложенные семейства, их эталоны и правила отбора. Две формулировки business/detailed одной аналитической задачи, перефразировки и родственные входы держать в одной группе. Общеизвестный архив и случаи, разобранные при отладке, годятся для разработки. Для подтверждения использовать закрытые до оценки задания, в том числе свежие варианты на самостоятельных данных. После раскрытия и доработки кандидата следующая проверка требует нового отложенного набора.
- [ ] До подбора правки закрепить первичный показатель, знаменатель, порог практической пользы и недопустимый вред. До подтверждающей серии зафиксировать обе ревизии, допустимую стоимость, объём и правило остановки. В паре совпадают задача, входы, состояние Loginom, модель и вариант, лимиты, версия harness и условие сбоя. Порядок «до/после» или «после/до» случайно и сбалансированно распределить внутри временных блоков. Использовать чистые профили и каталоги результатов, завершать cleanup перед повторным занятием слота. Модель получает обычное задание. Эталон, инъекция, метка сборки и чужие ответы ей недоступны. Оценщик видит обезличенный артефакт, ключ сборок открывается после фиксации оценок.
- [ ] Учесть каждую назначенную пару. Для каждой стороны записать, дошла ли она до нужной операции, произошло ли воздействие, потребовался ли браузер, чем закончился сценарий и сколько он стоил. Сборка, избежавшая ошибки и правильно закончившая работу, получает успех. Сравнение только попыток с `recovery_start` исключило бы именно такие улучшения. Чтобы проверить восстановление после одного и того же уже состоявшегося отказа, выделить отдельную пробу из эквивалентного подтверждённого состояния. Причины недостижения состояния видны в общем реестре.

### 3. Проверить результат пользователя и границы безопасности

| Правка | Что предъявить обеим версиям | Чем проверить результат независимо от ответа агента |
| --- | --- | --- |
| S1. Свежая ссылка экспорта | Обновление DOM нужного открытого списка между наблюдением и выбором | Выбран верный формат, в чистом каталоге один требуемый файл с верными данными. Зафиксировать, понадобился ли обход через браузер |
| S2. Готовность FileStore | Позднее появление строк после подтверждённого экспорта. Отдельно проверить действительно пустую папку | Получен файл именно этой операции, значения верны, граф снова доступен. В пустой папке поиск уложился в deadline |
| S3. Допуск к восстановлению | Повтор одной ошибки после штатного release. Отдельный контрпример с неизвестным эффектом операции | По журналу проверить передачу исходной операции и отсутствие двойного действия. По сохранённому пакету проверить, закончена ли задача |
| S4. Проверка восстановленного узла | Отказ configure/open до baseline, существующий частичный узел. Отдельные испытания для устаревшего выхода и для отказа чтения состояния после подтверждённого Save | Открыть сохранённый пакет в чистой сессии, проверить узел, связи и пересчитанные значения. Для Save проверить исходный пакет и отсутствие второго Save. Отдельно считать ложное объявление успеха |
| S5. Состояние текущей задачи | Ошибка или обрезка ответа, продолжение той же попытки и затем переход к другой задаче либо Dashboard | Сверить следующий реальный ход и ID активной операции. Должная подсказка доходит, чужая отсутствует. Отдельно оценить результат пользовательской задачи |
| S6. Освобождение и лимит | Отмена с ожидающим действием, поздняя команда после release, следующая обычная задача в том же слоте | По журналу и состоянию процесса подтвердить отсутствие позднего действия и cleanup. Следующая задача выполняется в чистом слоте. Для изменения бюджета отдельно проверить расход и завершение |

**Пример задания для разработки.** В [задаче про закупочные корзины](../../../evals/tasks/analytic-business/wholesale-basket-concentration-business/SPEC.md) есть 440 строк и [независимый расчёт](../../../evals/tasks/analytic-business/wholesale-basket-concentration-business/oracle.py). Для S2 задержать отрисовку списка, сохранив факт экспорта. Сначала сверить выданный пользователю CSV с эталоном для всех 440 клиентов, а его происхождение — с квитанцией, путём и чистым каталогом исходной операции. Затем открыть сохранённый `.lgp` в чистой сессии, пересчитать результат в другой пустой каталог и повторить сверку. Корректный пересчёт сам по себе не подтверждает, какой файл агент выдал в исходной попытке. Если обе версии справились, карточка фиксирует два успеха и разницу во времени. Для новой проверки использовать другие семейства. Аналогичный холодный запуск применять там, где контракт сценария допускает повторное исполнение в изоляции.

### 4. Рассчитать объём и принять решение

- [ ] Использовать результаты пилота для расчёта подтверждающей серии. Нужны ожидаемые доли пар «кандидат спас» и «кандидат сломал», число независимых семейств и разброс повторов. Иллюстрация для одного двустороннего сравнения при уровне 5%. Если ожидается 30% спасённых и 10% испорченных пар, 84 независимые пары (168 запусков) дают около 80% мощности точного теста Мак-Немара для обнаружения отличия от нуля. Это пример расчёта, бюджет конкретной гипотезы задаёт её пилот. При неустойчивых оценках рассчитать несколько правдоподобных вариантов. Для нескольких заявленных эффектов заранее учитывать множественные сравнения, например методом Холма. Повторы внутри семьи не увеличивают число независимых семей.
- [ ] До запуска записать стоимость в запусках, токенах и времени. При недоступном объёме заранее сузить проверяемый тезис или зафиксировать, какая точность достижима. Зафиксированную серию завершить независимо от промежуточного преимущества кандидата. Критический вред останавливает допуск кандидата с сохранением результатов. Если требуется доработка, присвоить следующему кандидату новую ревизию.
- [ ] Показать числа «обе справились / только кандидат / только контроль / обе провалились». Каждая заранее назначенная пара имеет одинаковый вес. На полных парах прирост равен разности «спасены − испорчены», делённой на их число. При построении 95% интервала сохранить эти веса и учесть зависимость повторов внутри семейств, например повторной выборкой целых семейств при достаточном их числе. Для пропусков вычислить крайние эффекты по всем назначенным парам, подставляя оба возможных исхода только на неизвестной стороне. Если решение меняется между границами, польза остаётся неподтверждённой. Падение продукта с потерей требуемого артефакта — наблюдаемый неуспех. Потеря журнала может оставить качество известным, а механизм — неизвестным. Повтор инфраструктурной попытки сохраняет исходную запись.
- [ ] **Рекомендовать перенос для качества**, если оценка достигает заранее обоснованного полезного прироста, есть свидетельство положительного эффекта с учётом неопределённости и числа сравнений, критический вред отсутствует в проверенной серии, а цена и регрессии в допустимых пределах. **Рекомендовать защитную правку** можно по воспроизведению и устранению конкретного нарушения, с проверенным штатным путём. Рост качества генерации требует собственного измерения. Если интервал допускает и существенный вред, и пользу, отмечать «недостаточно данных». Если надёжно исключён полезный эффект или выявлен неприемлемый вред, рекомендовать отложить либо переработать. В следующую карточку передавать принятую базу и явно перечислять оставшиеся за её пределами решения.

Из OPS-2291 заимствованы разделение разработки и скрытых случаев, независимый эталон, слепая оценка и проверка общего вердикта. В доступном отчёте OPS-2291 было 0/12 подтверждающих разборов. Завершённый смежный опыт в `testingdocs` (`d7efbda`) показал, зачем нужны свежие задания. Исправление вернуло 60 пропущенных пунктов на архиве. В девяти сопоставимых свежих планах обе версии передали все 185 нумерованных проверок и обе пропустили 15 ненумерованных сценариев.

## Правило для каждого изменения кода

1. Прочитать текущую реализацию и её потребителей. По донору брать идею и поведенческие тесты; не заменять файлы целиком.
2. Записать пробел, ожидаемый результат и сохраняемые гарантии. Если база уже решает задачу, приложить доказательство и завершить перенос без лишнего кода.
3. Выполнять по одному циклу RED → GREEN → REFACTOR: тест наблюдаемого отказа, подтверждённое падение, минимальная адаптация, успешная проверка и упрощение. Не писать весь набор тестов заранее.
4. Проверить перечисленные соседние контракты. Затронутые TypeScript-пакеты проверять через `bun typecheck` из их каталогов; тесты из корня запрещены.
