## Результат

Единый репозиторий содержит приложение Loginom AI Agent, перенесённый клиент
Dock, сервер знаний, сайт и средства сопровождения. Desktop-дистрибутив включает
исполнитель и Chromium; на пользовательской машине не требуется устанавливать
Node, Bun, Python, Chrome или отдельный плагин. Сервер знаний работает отдельно.

Первый запуск и прямой раздел «Loginom» используют одну форму: ключ сервера,
URL `http://logi-test-plan.bg.local/app/`, имя `user`, пустой пароль без placeholder.
Папка определяется как `/<username>` без предварительной проверки доступности.
Настройка LLM остаётся в существующем разделе провайдеров, без шага в мастере.

Linux сохраняет ключ/пароль Loginom открытым текстом в собственном `connection.json`
с `0600`; Windows/macOS используют защиту ОС. Новые параметры применяются после
всех активных Loginom задач и разрешения неопределённых операций. Неверный кандидат
или ошибка подготовки нового runtime сохраняет прежнее работающее подключение.

Продуктовые имена, пакеты, executable, каталоги, database, env, URI и updater
переходят на Loginom AI Agent. Внешние протоколы/provider IDs и атрибуция сохраняются
как явно описанные исключения. Codex/Hermes/Cursor остаются только в архиве переноса.

## Документы и порядок работ

В под-планах 26 задач с файлами, контрактами, командами, проверками и коммитами.
Каждый checkbox выполняется как отдельный наблюдаемый шаг; новый CLI сначала
реализуется и проверяется, затем применяется к реальным данным.

| Этап | Задачи и документ | Зависимость | Результат |
|---|---|---|---|
| Основание | F1–F6: [архив, перенос и ребрендинг](2026-09-16-loginom-foundation.md) | Текущий checkout и снимок Dock | Восстановленный архив, source map, Product, новое пространство имён |
| Desktop | D1–D7: [runtime, настройки и интерфейс](2026-09-16-loginom-desktop.md) | F1–F6 | Встроенный host/runtime, безопасное применение настроек, мастер |
| Выпуск | R1–R7: [сборки и приёмка](2026-09-16-loginom-release.md) | F1–F6, D1–D7 для итоговой приёмки | Пакеты, manifest, Linux Docker/GUI, передача native агентам |
| Сервер | S1–S6: [восстановление и переход](2026-09-16-loginom-server-transition.md) | F3 для подготовки; полный F6 перед переходом | Проверенная сборка сервера, backup/restore, отдельное переключение и retirement |

F4 отключает upstream updates до первого запуска ребрендированного приложения.
F5 переименовывает `packages/opencode` в `packages/agent`; последующие планы
используют новый путь. R1–R2 можно готовить после D1 и стабилизации Product,
параллельно с UI; R3–R6 требуют реализованного desktop flow. S1–S2 независимы
от UI после импорта. S3–S5 не блокируют отладку desktop с действующим сервером.
S6 выполняется последним, после актуального архива и проверки независимости сборок.

В параллельной реализации ownership разделяется по этим пакетам. Изменения
`packages/product`, схем/IPC, workspace lock, `packages/desktop` launcher/build
и общих lifecycle contracts согласуются до редактирования пересекающихся файлов.
Чужая незавершённая работа не откатывается.

## Технические границы

- Production backend первой версии — v1 через Electron utility process.
  Экспериментальный V2 не включается автоматически; его orchestration не переписывается.
- `packages/loginom-runtime` сохраняет проверенные Dock `.mjs` и отдельный процесс.
  `packages/loginom-host` связывает trusted session/run/message IDs, inputs и receipts.
- Desktop main владеет единым connection service/coordinator для всех окон/instances.
  Настройки вызывают `window.api.loginom.{read,check,save,cancelPending,status}`;
  общий `global.config.update` не используется для Loginom.
- Run закрепляет generation до model/tool context и удерживает её до завершения
  всего drain. Промежуток между tool calls не позволяет переключить подключение.
- Под закрытым admission gate новое поколение запускается и подтверждает готовность,
  затем фиксируется active pointer. Crash проверяется по durable state/handshake.
- `packages/schema` содержит только переносимые схемы; зависимости остаются
  Schema → Core/Protocol → Server. Generated SDK меняется штатной генерацией.
- Identity и resource paths задаёт `packages/product`. Поставляемые Node/Playwright/
  Chromium, catalog и source hashes закреплены manifest; first-run downloads нет.

## Локальные входы для будущей отладки

Пользователь указал `/home/kiselev/.loginom-dock/config.json` как источник ключа
Loginom Dock и других параметров. Подтверждено только наличие обычного файла,
владелец `kiselev`, права `0600`; его содержимое в рамках планирования не читалось.
При реализации брать необходимые значения локально, без вывода в терминал/отчёт,
argv, Git или память. Это вход отладки, а не зависимость чистого дистрибутива.
Наличие конкретного поля/его актуальность проверяются при использовании.

Перед разрешённой очисткой прежних OpenCode wrapper/desktop сохранить этот файл
в private backup и не включать его в общий список удаления. Не удалять сам
`~/.loginom-dock` вместе с launcher по совпадению имени. Другие машины получают
credentials отдельным закрытым способом, не вместе с документацией/артефактом.

Действующий URL сервера знаний и Loginom даны в спецификации; работоспособность
на момент будущей приёмки проверяется заново. Реальная задача должна использовать
явно выбранную модель и тестовый пакет, не произвольный production workflow.

## Порядок продолжения и границы готовности

1. Прочитать спецификацию и [инвентаризацию Dock](../../migration/loginom-dock-inventory.md),
   выполнить `git status` обоих checkout и всех указанных worktrees. Снимок может
   измениться из-за параллельной разработки; не считать SHA в документации текущим HEAD.
2. Начать с F1: актуализировать снимок/выбор источников, затем F2 archive/restore.
   Только после этого финализировать импорт. Старая установка не является источником сборки.
3. Выполнять под-планы по зависимостям; фиксировать targeted tests/typecheck,
   фактический SHA и blockers. Тесты не запускать из корня монорепы.
4. Поддерживать `docs/migration/foundation-acceptance.md` и platform reports как
   checkpoints реализации. `NOT_RUN`/`BLOCKED` не заменять историческим PASS Dock.
5. Production cutover, публикация и удаление repo — отдельные завершающие действия
   после готового проверяемого результата и явного разрешения на конкретную операцию.
   Дополнительное разрешение на обычную реализацию/локальные проверки не требуется,
   когда пользователь поручит выполнение этого плана.

На этом этапе созданы только документация и согласованный макет. Spec review:
Approved; планы сверены между собой, Markdown/ссылки проверены. Приложение,
установки, сервер и исходный Dock не изменялись; продуктовые tests/build/native
проверки не запускались. Следующий шаг — реализация F1, а не повторное согласование дизайна.
