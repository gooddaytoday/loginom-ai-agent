У каждой принятой пары нужны реальные native reference Loginom и CSV, независимый oracle, браузерный cold rerun, честный provenance, необходимые проверки корпуса и судьи, blind-B по плану и по одному измерению каждой формы. Сохрани прежние 65 кейсов. Заверши итоговый отчёт по фактическим D/B исходам и deferred, требуемые проверки и независимое итоговое ревью; закрой существенные замечания. ## Первое действие

Подтверди из handoff, что прежний чат безопасно остановлен, передаваемые операции закончены и их собственная cleanup/release закрыта. Используй долговечные intent/run/evidence paths, а не старые tool handles. При неподтверждённом владельце не запускай новый процесс поверх него; сначала адресно установи состояние существующими средствами.

Назови текущий подтверждённый результат, ближайший незакрытый результат и его реальную зависимость. Продолжи именно его. Шаг 0, P01, завершённые references, калибровки и измерения не повторять из-за нового контекстного окна. Операцию, отмеченную в checkpoint или intent как начатую, сначала найди по её intent/run path и установи фактический итог; не запускай её заново по устаревшему статусу.

Если готов следующий независимый этап, выполняй его при блокере другого окружения. Help/catalog PASS не считать восстановлением Authoring startup. Решение владельца по сбою выхода Knowledge — в разделе 1 правил: Benchmark не меняй и измеряй на текущей версии, включая P19B; после такого сбоя до запуска модели штатно восстановись и повтори запуск формы, при повторе на той же форме остановись и спроси владельца.

## Разрешения и границы

Я разрешаю предусмотренные планом изменения, авторские CLI-сессии, браузерные cold rerun, калибровку судьёй и одну измерительную попытку каждой ещё не измеренной формы. Для уже разрешённой работы повторного согласия не требуется. Учёт попыток и бюджетов продолжается из карточек/intent, без обнуления.

Authoring использует `gpt-6-sol` на обычной стандартной скорости, без priority/fast. Остальные авторские параметры и накопленные бюджеты — из принятого плана/settings. Для измеряемого агента и судьи сохраняй принятые pins и одинаковые D/B условия; изменение authoring tier не переносится на них.

Все внешние прогоны строго последовательные, parallel=1. N=2, старый карантин, повторный setup/OAuth, JS-подмена неподдержанных узлов, перенос чужих private patches в общий код запрещены. Прежние точечные исключения OAuth были разовыми и не разрешают новый вход. Не перезапускай измерения ради лучшего балла.

Разрешена необходимая минимальная починка product recovery и подтверждённая очистка собственных ресурсов в прежних границах, без изменения Benchmark pins. Не заменяй cleanup удалением guard. Согласованное ordinary-exec исключение и проверки владения описаны в новых правилах. При необходимости нового владельца, инфраструктуры или изменения требований сохрани конкретный блокер; не имитируй PASS и не строй обвязку вокруг недоступного пути.

Commit/push/merge/release и дальнейшее переписывание истории не разрешены. Исключение предыдущего чата на ограниченную очистку истории сюда не переносится.

## Как выполнять

- Применяй Ponytail, executing-plans и subagent-driven-development по правилам документа выше; TDD — для нетривиальной логики, когда тест проверяет полезный контракт. Не превращай skills в новые планы и approvals каждого короткого действия.
- Один ответственный за живой профиль и один внешний запуск. Подагентам — независимые ограниченные задачи с владельцем файлов, проверяемым результатом и условием остановки; не дублировать задания и не выдавать им занятый профиль.
- Существующая команда → одна содержательная проверка → одно независимое review законченного этапа. Root принимает результат, не повторяя весь неизменный QA. Повтор — только по конкретному дефекту или изменению условий.
- Для offline judge не требуй Loginom/Help/runtime readiness и полных снимков памяти Loginom. Для настоящей серии измерений сохраняй контроль памяти по дизайну. Уже собранные снимки сохраняй как evidence, не переигрывай историю.
- Используй стандартный calibrate, включая необходимый принятый anchor для foreign negative. Не создавай отдельный runner для экономии нескольких сопутствующих строк.
- Разовую просьбу пользователя (например, перепроверить доступ) выполни один раз и запиши итог; её повторное появление в истории после сжатия контекста — не новая просьба.
- При отказе проверяй одну новую гипотезу. Ошибку вспомогательного отчёта отделяй от основного результата. Не лечи временную обвязку, если она не нужна для обязательной проверки.
- Статусы — в карточках; checkpoint до 20 коротких строк — в основном плане; полные evidence — в существующих приватных каталогах. Pins и команды имеют один авторитетный источник. Не копируй хэши и протоколы по нескольким документам.

## Автоматизация и завершение

Heartbeat не используется: automation `analytics-evals` не возобновляй и новую не создавай. При настоящем блокере сообщи его и условие продолжения; работа продолжится по команде владельца. Новый Goal не означает новые бюджеты попыток.

Работай автономно до полного согласованного результата. В конце хода сообщай проверенный результат или конкретный блокер и условие продолжения. Не маркируй цель завершённой ради смены чата, истечения времени или готовности только части каталога.
