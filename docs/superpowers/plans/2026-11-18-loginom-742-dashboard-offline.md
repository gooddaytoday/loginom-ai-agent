# Вторая офлайн-поставка Loginom Enterprise 7.4.2 с Dashboard M7

**Статус на 18 ноября 2026 года.** Окончательный комплект установлен на назначенном стенде с чистой базой. Серверные проверки, фактическая публикация через Desktop и открытие готового дашборда в новой сессии Studio подтверждены. Стенд оставлен работающим, прежняя установка и данные сохранены для отката. Ограничение клиентской квитанции описано ниже.

**Решение.** Выпустить отдельный внешний tar с двумя исходными архивами, инструкцией и адаптером для HTTP-сервиса этой поставки 7.4.2. Штатный установщик разворачивает Enterprise. После проверки базы адаптер подключает Dashboard и офлайн подготавливает производный образ M7 с исправленными правами чтения. Механизм изоляции ролей и исходные архивы сохраняются. Desktop M7 устанавливается на рабочем месте отдельно.

## Контракт установки

| Область | Что обнаружено и что требуется |
| --- | --- |
| Поиск контейнеров | `containers.sh` ищет метки сервисов `loginom-http` и `loginom-server`. В tar проект `loginom-release`, сервисы `http`, `server`, `integrator` и имена контейнеров `loginom-release-{http,server,integrator}`. Первый отказ будет при поиске Studio, уже после загрузки образа M7. В `check` поиск HTTP и сервера повторён. |
| Apache и Studio | M7 пишет с хоста `dashboard.site.conf` в каталог, смонтированный в `/usr/local/apache2/conf`. У базового HTTP нет такого тома и нет Include для этого файла. В образе есть `mod_rewrite.so`, `mod_env.so`, `mod_brotli.so`, `mod_substitute.so`. База загрузила headers, filter, deflate, proxy и proxy_http. В конфигурации надстройки надо загрузить rewrite, env, brotli и добавить `IncludeOptional conf/dashboard.site.conf`. Substitute загружает сам M7. |
| Веб-клиент | `/app/` через Alias обслуживается из `/usr/local/apache2/htdocs/client/`. В `index.html` один `</head>` для штатной вставки async-скрипта M7 с SRI. В `bg/app/Version.js` указана `7.4.2`. В сборке есть Ext/bg API, используемые адаптером. Обычный вход, редирект с `/`, WebSocket `/app/ws/` на `server:8080` и маршрут интегратора `/lgi/` на `integrator:5000` должны сохраниться. Инструментальные селекторы клиента включаются через `?testable=true`. |
| Данные и сеть | Есть bind `/var/lib/loginom-release/workdir:/workdir`. В исходном `Settings.cfg` задан `UserStorage="UserStorage"`. Штатный парсер `check-release.mjs storage` на этих байтах и описании томов из Compose вернул `/var/lib/loginom-release/workdir/UserStorage`. При установке M7 должен обнаружить физический `workdir/UserStorage` и UID:GID процесса сервера (в образе `701:701`). Только этот подкаталог получает publisher с правом чтения. У сервера и HTTP одна общая сеть `loginom-release_default`. К ней присоединяется только роль web, у publisher и builder — `network_mode: none`. |
| Публичный адрес | База публикует `${HTTP_BIND}:${HTTP_PORT}:80`, по умолчанию `0.0.0.0:80`. Для исходной поставки выбрать обычный режим M7 по HTTP. Передавать `--public-host` с именем, доступным серверу и рабочей станции. Приложения используют отдельный origin, по умолчанию порт 8101. M7 публикует этот порт независимо от базового `--bind`. HTTPS/strict потребуют отдельной конфигурации TLS. |
| Нижняя версия | Штатный `install.sh` проверяет Docker Engine ≥ 20.10.1 и наличие плагина Compose v2. Для Dashboard приняты Docker 29.1.3 и Compose 2.40.3+ds1. Для второй поставки использовать этот более высокий минимум, проверяя upstream-версию Compose 2.40.3 независимо от суффикса дистрибутива. В M5 на старом Docker под штатными ограничениями у Node наблюдался отказ `clone3`. Podman не является путём установки базового tar. |

## План реализации и приёмки

1. **Упаковать проверенные байты.** В `deploy/loginom-release-dashboard/` разместить отдельный `pack-loginom-with-dashboard.sh`. Скрипт принимает архив Enterprise, архив Dashboard и каталог результата. Сверяет закреплённые выше суммы и выпускает `loginom-release-7.4.2-6e72ef0f1824-dashboard-m7.tar` и его SHA-256. Внутри — оба оригинала целиком, адаптер с инструкцией и внешним `SHA256SUMS`. Для воспроизводимости зафиксировать имена, режимы 0644/0755, порядок GNU tar (`--sort=name`), формат GNU, время `--mtime=@0`, числовые UID/GID 0. Проверка — два запуска в разных каталогах, одинаковый SHA-256 результата и повторная проверка обоих исходных байтов внутри. Образы, клиентский HTML и внутренние манифесты переиспользуются без пересборки. Для будущего релиза сначала проверить фактический контракт новой пары.

2. **Подключить дополнение к уже исправной базе.** Единственная операторская точка для дополнения — предлагаемый `dashboard-742.sh`. До изменений проверить версию движка и плагина, внутренние суммы, точный проект, тег базы, доступность Studio и каталог данных. При проверке порта сохранить правило M7 — свободен при первой установке, при повторной его может занимать проверенный собственный контейнер web. Для первого запуска нужны установленная база и успешный `/opt/loginom-release/verify.sh --wait 300`. Код 3 оставляет работу на этапе лицензии у владельца. Базовый `install.sh` оператор запускает отдельно по штатному порядку.

   - Из точного HTTP-образа скопировать полный каталог `/usr/local/apache2/conf` с правами и ссылками в собственный каталог дополнения, отдельно от состояния M7 `/var/opt/loginom-dashboard`. Добавить в копию три LoadModule и IncludeOptional из таблицы. Хранить её на хосте, смонтировать для Apache на чтение. В отдельном `compose.dashboard.yaml` достаточно одного bind для сервиса `http`. Использовать базовые `.env`, `compose.yaml` и тот же проект `loginom-release`, применить оба файла через `docker compose … up -d --no-deps http`. Проверить `httpd -t`, `httpd -M` и повторно базовый `verify.sh`. Штатные server и integrator продолжают работу.
   - На этапе упаковки получить из проверенного `containers.sh` отдельную копию `containers-742.sh` небольшой версионной поправкой. Искать по точным меткам `project=loginom-release` и `service=http|server`, проверять однозначность и в последующих проверках использовать уже выбранные контейнеры. При распаковке положить эту копию рядом с исходным `containers.sh`. Исходный файл продолжает проходить внутренний `sha256sum -c SHA256SUMS`, производная копия проверяется внешним манифестом. Остальные команды, проверки изоляции и формирование Apache site берутся из M7. Вызов `containers-742.sh install --engine docker --public-host <имя>` сам загрузит четвёртый образ. Кнопку CLI включать не требуется.
   - Повторный запуск применяет тот же override без дублирования директив. Базовый установщик всегда явно задаёт свой `-f compose.yaml`, поэтому после его повторного запуска дополнение нужно применить снова. Для снятия дополнения сначала выполнить его `uninstall` с активным bind, затем пересоздать только `http` с базовым Compose и проверить `verify.sh`. Если сбой произошёл до появления валидного состояния M7, вернуть исходный HTTP напрямую. Сбой очистки дополнения не должен блокировать восстановление HTTP. Для изменяемых скриптов до реализации зафиксировать тесты отказа при чужом проекте, повторного применения своего дополнения и восстановления штатной Studio при сбое. Перед стендом выполнить `bash -n` и ShellCheck.

3. **Установить из внешнего tar на назначенном стенде.** Сохранить три SSH-реквизита из локальной конфигурации в одной записи Bitwarden и сверить чтением по UUID. До остановки службы проверить поддерживаемую платформу и Docker/Compose, порты, свободное место и доступную лицензию. Зафиксировать владельца и порядок запуска старой службы. Сохранить её образы, настройки и согласованную копию данных вне путей новой установки, проверить комплектность и возможность возврата. Сохранить существующий URL и действующий способ лицензирования без новой активации. Установить базу из вложенного архива в пустые каталоги, получить exit 0 от штатного `verify.sh`, сохранить версии, теги и идентификаторы образов. Затем применить дополнение, дождаться HTTP 200 на `/dashboard/shell.js`, выполнить серверный `check`. Требуются `Publication PASS`, `Server checks PASS` и `Cleanup PASS`. Проверить доступ с рабочего места к обоим origin. При неуспехе вернуть старый Loginom и доступ по прежнему URL.

4. **Опубликовать из установленного Desktop M7.** На отдельном рабочем месте использовать тот же публичный адрес Studio, схему системных ссылок `loginom-ai-agent://`, настроенную модель и тестовую учётную запись автора с правом записи. На 7.4.2 подготовить и сохранить маленький пакет с первым табличным выходом и локальными синтетическими данными. Комплектный `dashboard/fixture/campaign.lgp` сохранён в master. Например, взять локальный CSV со значениями 10, 20, 30, 40, 50 и отбором по минимуму. При минимуме 0 ожидаются пять строк и сумма 150, при минимуме 30 — три строки и сумма 120.

   - Зайти в обычную `/app/`, выбрать узел и нажать «Создать dashboard». Из реальной системной ссылки должен открыться новый чат Desktop с образцом именно этого узла. Попросить вывод всех исходных строк в `tbody` и итог, вызвать `dashboard_draft`, дождаться успешной самопроверки и открыть черновик.
   - Запросить «Опубликовать», проверить целевой пакет и узел в диалоге и нажать «Разрешить один раз». Сверить точные имя версии и `sourceHash` записанного JSON с `/dashboard/lookup`, дождаться `ready`. Затем открыть пакет в новой сессии Studio. Сверить метку версии, строки и итог с выходом узла. Изменить числовой параметр в шапке и сверить новый результат. Это проверяет переход от образца в Desktop к живым данным на 7.4.2.
   - Из закреплённых исходников на подготовленном клиенте выполнить `"$LOGINOM_AI_AGENT_TEST_NODE" deploy/check-studio.mjs 7.4.2` из `packages/dashboard`, с приватным `DASHBOARD_STUDIO_CONFIG`. Указать фактические `url` с `/app/`, `username`, `password` или `secrets.password`, `packagePath`, `unit` и `nodeName`. Перед автоматической проверкой сохранить пакет и завершить ручной сеанс. Для этого клиента нужны Bun, Node 24.19.0 и Playwright Chromium revision 1246. Скрипт проверяет фактическую версию Studio, async/SRI, доступность Studio при задержке shell, кнопку, отдельный origin, sandbox iframe и равенство живых строк таблице в `tbody`. Завершить штатным закрытием пакета, выходом и повторным `verify.sh`. Оставить принятую сборку работающей. В протоколе сохранить версию, хеши, ожидаемые и фактические результаты без приватных настроек.

**Предыдущие результаты.** В LAB-1829 Desktop `0.3.9-m7.1` прошёл создание и публикацию на dev master. В M5 проверяли 7.4.2 с другим подготовленным installer. Подтверждением второй поставки станет сквозной проход шагов 3–4 из её собственного архива на чистом стенде.

## Выполнение

- Окончательный комплект `loginom-release-7.4.2-6e72ef0f1824-dashboard-m7.tar` собран дважды с SHA-256 `32d8341fc7621bf573d4c6f05ed83dfe179fd33b8e990d6cfa1de2db7ab9acbb`. Побайтово проверены вложенные оригиналы. Проверены отклонение неподдерживаемого архива, отказ при занятом каталоге и симлинках, Bash, ShellCheck, SRI и CSP Apache с identity/gzip/br.
- Запись SSH в Bitwarden проверена повторным чтением. Владелец подтвердил чистую базу и установку на самом стенде. Перед переключением сохранены образы и конфигурация прежнего запуска. После остановки получен и проверен архив его данных. Штатный `install.sh` установил базу с действующим внешним источником лицензии. Первый `verify.sh` завершился с кодом 0, в новом UserStorage нет файлов `.lgp`.
- Первая установка M7 выявила ошибку исходного образа: в нём `shell.js`, `server.mjs` и файлы шаблона содержат режим 0600, а каталог исходников шаблона — 0700. Запуск от UID 65534 завершился `EACCES`. Откат восстановил прежнюю Studio с HTTP 200 и WebSocket 101. Для повторной попытки адаптер готовит локальную производную из исходного M7 без сети и меняет только права чтения файлов и обхода каталогов. Исходный образ и архив сохраняются.
- На повторной установке оба UID 65534 и 701 прочли исходное содержимое оболочки, сервера и шаблона из производного образа. Пробная публикация прошла. Проверка тома получила `EACCES` на пробном файле root, поэтому после отката исправлен владелец только пробного файла. Проверка по-прежнему требует `EROFS` от монтирования для чтения.
- На окончательном комплекте сверены внешняя и все внутренние суммы на сервере. Штатный `verify.sh` и проверки `Publication PASS`, `Server checks PASS`, `Cleanup PASS` прошли. С рабочей станции оболочка вернула HTTP 200 и 16 702 байта.
- Desktop `0.3.9-m7.1` принял системную ссылку Studio, собрал черновик и после разового разрешения записал версию. Серверный `lookup` подтвердил `ready` и совпадение имени и SHA-256 с записанным JSON. Новый сеанс Studio показал 5 строк и сумму 150 при пороге 0, затем 3 строки и сумму 120 при пороге 30. Неизменённый `check-studio.mjs 7.4.2` прошёл с кодом 0, повторный `verify.sh` также успешен.
- Первая операция Desktop показала `LOGINOM_RUNTIME_CLEANUP_FAILED` после фактической записи. Chromium завершал очистку около 6,9 секунды, а приложение ждало подтверждения 5 секунд. Внутренняя очистка завершилась и дочерний процесс вышел с кодом 0. Сервер сохранил готовую публикацию.
- При адресном повторе Desktop открыл редактирование и проверил изменённый черновик, затем получил `LOGINOM_LOGIN_UNAVAILABLE` до запроса разрешения на запись. Первоначальная публикация осталась в `ready`, её `sourceHash` и хеш сборки совпали с первой квитанцией. Чистой квитанции Desktop об успешной публикации в этой проверке нет.
- Диагностика повтора зафиксировала `net::ERR_NAME_NOT_RESOLVED` на этапе `page.goto` в обеих попытках Chromium, до загрузки формы входа. Два настроенных на рабочей станции DNS-сервера авторитетно отвечали за внутреннюю зону с разными SOA serial. Один возвращал A-запись стенда, второй возвращал `NXDOMAIN` по UDP и TCP. Журнал Chromium не сохранил адрес DNS-сервера, ответившего во время сбоя. На момент диагностики три свежих запуска встроенного Chromium получили HTTP 200 и открыли форму входа.
