# План реализации открытия черновика Dashboard из снимка

> Для исполнения по шагам подходят `executing-plans` в этой сессии или `subagent-driven-development` с отдельным исполнителем на задачу.

**Цель.** Из Studio открыть в Desktop чат и локальный предпросмотр нового Dashboard. Первый дополнительный вход в Studio происходит по запросу на публикацию.

**Архитектура.** Общая функция `prepareDashboard` уже проверяет одноразовый снимок и сохраняет рабочую папку узла. Только Desktop откладывает чтение публикации для создания. Для согласия используются существующий запрос `dashboard_publish`, окно Desktop и проверка ожидаемой версии непосредственно перед записью.

**Стек.** TypeScript, Electron, Solid, Bun и проектный Node для тестов пакета Dashboard.

**Спецификация.** [Утверждённое поведение и текст предупреждения](../specs/2026-11-19-dashboard-create-from-snapshot-design.md).

## Границы и объём

Режим подготовки определяется по `published` из проверенного снимка. Снимок с настроенного стенда по-прежнему нужен. Признак отсутствия готовой сборки оставляет открытым вопрос о сохранённых исходниках. Источник истины при публикации — актуальная сохранённая версия.

Область изменения — переход Studio → Desktop. Формат снимка, ссылка, поведение CLI, чтение исходников при редактировании, права Studio и механизм записи версий сохраняются. Установка сборки в систему, выпуск и замена пользовательского Dashboard в объём не входят.

Оценка внедрения по `git diff --stat`, включая проверки и актуализацию инструкций, — 9–11 файлов и около 70–125 изменённых строк суммарно. Для новой ветки создания нужен только внутренний выбор в общей функции. Модель, IPC и хранилище дополнительных полей не получают.

## На что обратить внимание при проверке

- Холодный запуск с настроенным стендом — от получения свежего снимка до локального предпросмотра вторая вкладка Studio не появляется.
- Повторное создание — свежий образец доступен, правки и прежняя основа локального черновика сохраняются.
- Редактирование на чистом профиле — загружаются проверенные исходники опубликованной версии.
- На сервере уже сохранили версию, даже если при открытии ещё не было готовой сборки — окно показывает предупреждение до записи.
- Версия меняется после открытия окна — прошлое согласие не разрешает запись поверх следующей версии.

## 2. Показать, какую версию пользователь разрешает заменить

- [ ] В `packages/app/test-browser/dashboard-publication.test.ts` расширить существующую проверку окна. Для `dashboardConflict.base === null` проверить согласованный текст, узел, пакет, видимое имя последней версии и кнопки «Опубликовать мою версию» и «Отмена». До нажатия ответов нет, нажатия в отдельных запросах дают соответственно `once` и `reject`. Для обычной первой публикации и редактирования сохранить действующие варианты окна. Запустить команду теста ниже и убедиться, что проверка нового текста падает.
- [ ] Изменить `packages/app/src/pages/session/composer/session-permission-dock.tsx` и словари `packages/app/src/i18n/{ru,en}.ts`. Использовать существующее поле `dashboardConflict`, в котором сервер уже передаёт `base: null` при неизвестной или отсутствующей основе. Применить согласованные подписи к этому случаю. Повторную проверку версии и передачу подготовленных байтов оставляем текущему инструменту. Дополнить пользовательский шаг публикации в `dashboard/README.md`.
- [ ] Из `packages/app` выполнить `bun test --conditions=browser --preload ../ui/test/solid-jsx.ts --preload ./happydom.ts ./test-browser/dashboard-publication.test.ts` и `bun typecheck`. Из `packages/opencode` выполнить `bun test test/tool/dashboard.test.ts`; из `packages/dashboard` — `"$LOGINOM_AI_AGENT_TEST_NODE" --test --test-name-pattern='changed, cancelled' test/agent/publish.test.mjs`. Проверить результаты отказа, однократного согласия и изменения версии после подтверждения. Коммит — `feat(app): clarify dashboard publication conflicts`.
- [ ] Пересобрать и запустить кандидат Desktop с изменениями окна подтверждения в отдельном обычном профиле. На тестовой копии открыть черновик A, затем в другом профиле опубликовать B для того же узла. При публикации A проверить предупреждение и отменить — в Studio видна B, правки A доступны. Снова запросить публикацию A и подтвердить — после успешной сборки в Studio видна A. Отдельно изменить версию между появлением предупреждения и нажатием кнопки, убедиться, что требуется новое согласие. В свежей локальной папке открыть последнюю версию на редактирование и проверить узнаваемую правку из опубликованных исходников.

Перед каждым коммитом проверить подготовленные файлы через `bun run secrets staged`. В результате приёмки указать сборку кандидата и наблюдения на стенде отдельно от автоматических проверок.
