# Prompt для планирования и реализации облачного входа на loginom.ai

Работай в репозитории сайта `$HOME/storage/git/loginom-ai-site`.
Спланируй и реализуй серверную и браузерную части подключения Loginom AI Agent
к облачным Dock через loginom.ai. Доведи работу до проверенного результата
в доступном изолированном окружении, подготовь развёртывание и точный отчёт
об оставшихся внешних зависимостях. Отвечай по-русски.

## 1. Результат

Пользователь регистрируется или входит на loginom.ai, явно подтверждает код
Desktop/CLI и получает работающий доступ к официальной базе знаний.
Каждая установка получает собственный отзываемый бессрочный ключ сайта.
Установки одного пользователя используют общую персональную пару Dock-ключей.
Новая установка сохраняет действующую пару. После ротации разрешённая установка
получает новые ключи без повторного входа. Отзыв ранее выданного доступа
инвалидирует соответствующие ключи сайта и обоих Dock.

Основа решения согласована — Next.js и Better Auth с Device Authorization,
Bearer и API Key. Выбери минимальную достаточную БД, схему и способ развёртывания
по фактическому устройству проекта. Сохрани рабочую публичную страницу,
скачивание установщиков и существующую доставку заявок. Объём переноса текущей
статики выбирай по необходимости интеграции, переиспользуя существующую сборку
и ассеты там, где они продолжают выполнять свою задачу.

## 4. Регистрация, вход и подтверждение устройства

Реализуй email/password регистрацию и вход с обычной веб-сессией.
Регистрация сразу открывает доступ, подтверждение email и ручное одобрение
администратором в принятом продукте отсутствуют. Пароли обрабатывает Better Auth.

При регистрации один раз заполняется анкета. Обязательны имя, фамилия, email,
пароль, телефон, профессиональный статус и согласие на обработку данных.
Отчество, компания, должность и согласие на новости необязательны.
Храни время и версию принятого текста согласия, отдельно от выбора рассылки.
Страницы регистрации, входа и подтверждения устройства закрой от индексации
(`noindex`) и исключи из публичной sitemap. Если владелец выберет личный
кабинет, примени к нему тот же порядок.
Используй согласованные поля и серверную валидацию. Старые заявки на скачивание
содержат контактные данные, их связь с аккаунтом требует нового входа/регистрации.
Совпадение email в заявке не подтверждает владение аккаунтом.

На странице подтверждения покажи текущий аккаунт, возможность его сменить,
название Loginom AI Agent и пользовательский код. Пользователь явно разрешает
или отклоняет подключение. Действующая веб-сессия сама устройство не подтверждает.
После входа/регистрации сохрани контекст исходного кода и верни пользователя
к подтверждению. Полная ссылка из Agent уже содержит код.
Проверь повторный, неверный, истёкший, уже использованный и отклонённый код,
а также смену аккаунта в ходе подтверждения.

В Better Auth 1.7.18 авторизованный `GET /api/auth/device?user_code=…` закрепляет
свободный код за первым аккаунтом. Решение другого пользователя получает 403.
При показе страницы читай статус кода без cookie и Bearer, текущий аккаунт
определяй отдельно. Одним серверным действием по нажатию «Разрешить» или
«Отклонить» проверь браузерную сессию и Origin, привяжи код к выбранному
пользователю, затем выполни его решение. При занятом или погашенном коде
покажи результат без перепривязки. Закрой прямой обход этого действия через
публичные маршруты проверки и решения Better Auth. Публичная выдача device code
принимает разрешённый client ID и исключает назначение владельца через `user_id`.

Ограничь попытки подбора и проверки кодов в том числе для своих серверных
действий. У плагина лимит пути `/device` — пять запросов с IP за срок кода,
он применяется в HTTP-обработчике. Прямые вызовы `auth.api.*` из приложения
его обходят. Используй проверенный IP из цепочки прокси (§9).

## 5. Точный HTTP-контракт уже реализованного клиента

Production адреса закреплены в Agent — `https://loginom.ai`,
`https://mcp.loginom.ai/mcp` и `https://mcp-reserve.loginom.ai/mcp`.
Сайт возвращает ключи для этих назначений. Настройка admin endpoint Dock
принадлежит серверу сайта, пользовательские параметры его не меняют.
Все HTTP-маршруты Agent, включая первый `POST /api/auth/device/code`, обслуживай
без перенаправлений. Клиент использует `redirect: "error"`.

### Получение device code

`POST /api/auth/device/code`, JSON request

```json
{"client_id":"loginom-ai-agent"}
```

Обязательные поля JSON response

```json
{
  "device_code":"TEST_DEVICE_CODE",
  "user_code":"TEST-CODE",
  "verification_uri_complete":"https://loginom.ai/device?user_code=TEST-CODE",
  "expires_in":600,
  "interval":5
}
```

Строки непустые, `expires_in` и `interval` положительные числа в секундах.
Числа в примере иллюстрируют формат, значения срока выбери в плане.
Полная ссылка абсолютная, с тем же origin сайта и без credentials в URL.
Agent использует `verification_uri_complete`, `verification_uri` ему недостаточно.
Разрешённый публичный client ID — `loginom-ai-agent`.

### Ожидание подтверждения

`POST /api/auth/device/token`, JSON request

```json
{
  "grant_type":"urn:ietf:params:oauth:grant-type:device_code",
  "device_code":"TEST_DEVICE_CODE",
  "client_id":"loginom-ai-agent"
}
```

Успешный response

```json
{"access_token":"TEST_RAW_DEVICE_SESSION_TOKEN","token_type":"Bearer","expires_in":600}
```

`token_type` строго `Bearer`, токен непустой, `expires_in` числовой.
Ошибки polling имеют плоский OAuth-формат `{"error":"authorization_pending"}`,
также поддержаны `slow_down`, `access_denied`, `expired_token`.
Клиент продолжает опрос при `authorization_pending`, увеличивает interval на
пять секунд при `slow_down`, завершает вход при отказе и истечении кода.
HTTP 429, 5xx и сетевой сбой допускают повтор до исходного срока кода.
Для временного отказа сервера верни 429 или 5xx. Прочие 4xx, например
`invalid_grant`, завершают вход сразу. На каждом ответе 429 маршрутов Agent
возвращай стандартный `Retry-After`. Штатный HTTP-ограничитель Better Auth
выдаёт `X-Retry-After` в секундах, Agent читает только `Retry-After`.

### Первичный обмен на подключение установки

`POST /api/agent/connections`, body `{}`, header
`Authorization: Bearer <raw device session token>`.
Успешный JSON response содержит полную действующую пару

```json
{
  "installationKey":"TEST_INSTALLATION_KEY",
  "user":{"email":"user@example.test"},
  "dock":{
    "primary":{"apiKey":"TEST_PRIMARY_USER_KEY"},
    "reserve":{"apiKey":"TEST_RESERVE_USER_KEY"}
  }
}
```

Все показанные строки непустые. Ответ имеет обычное успешное HTTP-состояние
с JSON-телом. Пустой 204 не соответствует этому обмену.
Agent вызывает обмен ровно один раз. Любая ошибка, тайм-аут или потеря ответа
завершают этот вход, даже при 429 или 5xx. Сохрани выдачу до ответа.
Принимай только сырую device-сессию, созданную для этого Agent на `/device/token`,
однократно. Атомарно закрепи право выдачи за одним обменом. При двух запросах
с одним токеном возможна максимум одна установка. Новая попытка входа требует
нового подтверждения. Обычная браузерная сессия, в том числе переданная как
Bearer, и installation key не дают этого права.

Каждый site HTTP request Agent ограничен максимум 15 секундами.
Polling и обмен дополнительно расходуют оставшийся срок исходного device code.
Проверь работу на границе этого срока. `token.expires_in` не продлевает
клиентский deadline обмена. Планирование серверных операций учитывает эти пределы.

### Получение актуальной пары

`GET /api/agent/dock-credentials`, без body,
`X-API-Key: <installationKey>`.

```json
{
  "dock":{
    "primary":{"apiKey":"TEST_PRIMARY_USER_KEY"},
    "reserve":{"apiKey":"TEST_RESERVE_USER_KEY"}
  }
}
```

Возвращай полную достоверную пару. Agent вызывает refresh по необходимости
после ответа 401 от Dock, объединяет параллельные попытки и выдерживает паузу
минимум 30 секунд. Поле `Retry-After` может задавать секунды либо HTTP-date.
Обновление пары сохраняет installation key и аккаунт пользователя.

Только доказанный отзыв binding/key/account возвращает HTTP 403
с точным телом

```json
{"error":{"code":"access_revoked","message":"Access to this installation has been revoked"}}
```

Это сигнал удаления локальных credentials и нового входа.
Временная недоступность БД/Dock/сайта, HTML от proxy, обычные 401/403 и ошибки
проверяющего сервиса сохраняют credentials. Используй для временных отказов
отдельные `credentials_unavailable`/`service_unavailable` и подходящие HTTP-коды.
Agent обрабатывает 429 и 5xx до разбора `access_revoked`.

### Обычное отключение установки

`DELETE /api/agent/connections/current`, без body,
`X-API-Key: <installationKey>`. Подтверждённый успех строго `204`.
Отключи binding и ключ этой установки. Общая Dock-пара и другие установки
сохраняются. Agent выполняет локальный выход даже при сетевом отказе,
удалённому запросу выделяет пять секунд и сообщает неподтверждённый отзыв.
Новым ключом можно вызвать DELETE сразу после получения ответа обмена.
Семантику повторного DELETE уже отключённой установки зафиксируй с владельцем (§8).

### Погашение временной device-сессии

Сайт сам гасит точную bootstrap-сессию при успехе и терминальном отказе обмена.
После успешного локального сохранения клиент дополнительных запросов не делает.
Если полная выдача получена, но ключ не сохранён или вход отменён, Agent
сначала пытается отозвать полученный `installationKey` через DELETE, затем
в оставшееся время погасить bootstrap-сессию. На обе попытки вместе дано
пять секунд. Если запись после ошибки подтверждена чтением и принята клиентом,
он сохраняет этот ключ. При сбое обмена до получения ключа возможен лишь
`POST /api/auth/revoke-session` с JSON `{"token":"TEST_RAW_DEVICE_SESSION_TOKEN"}`
и тем же сырым токеном в `Authorization: Bearer …`.

Для ещё действующей device-сессии проверь равенство токена запроса и токена
отзыва, погаси именно эту сессию и верни `{"status":true}`. Уже погашенный
при обмене Bearer даёт ожидаемый 401, как в fixture Agent. Клиент сохраняет
исходную ошибку обмена или записи. Штатный revoke-session допускает отзыв
соседней сессии того же пользователя, а `status:true` возможен для отсутствующего
токена. Проверь отказ при подстановке токена браузерной сессии того же аккаунта
и её сохранение. Проверяй эффект в БД или последующим запросом в тесте.

В Better Auth 1.7.18 `/device/token` создаёт обычную сессию со стандартным
сроком семь суток. При создании через `databaseHooks.session.create.before`
определи источник по контексту `/device/token` и проверенному `client_id`,
сохрани серверный признак device-сессии и короткий абсолютный срок.
Проверяй этот срок и однократность в хранилище. Обычный `get-session` способен
продлить даже такую сессию до срока веб-сессии. Докажи, что обращения, кеш
и обновление сессии не продлевают доступ, сроки обычного входа сохраняются.

Разреши аутентификацию сырым device Bearer только на обмене и точном
`revoke-session`. Ограничение должно действовать до того, как общий плагин
Bearer преобразует заголовок в cookie. Во всех браузерных auth-ответах
исключи `set-auth-token` и его объявление в CORS, включая ответы входа,
регистрации и обновления сессии. Проверь прямые auth API,
включая `get-session`, подстановку браузерного Bearer или cookie на обмене
и запрос с конфликтующими cookie и Authorization.

## 6. Installation key и границы доступа

Используй отдельную API Key configuration `agent-installation`.
Ключ разрешает получение пары и собственное отключение, остаётся бессрочным
до отзыва и независимым от срока веб-сессии. На каждом запросе проверяй
принадлежность configuration и активное серверное binding ключа к пользователю
и состоянию доступа. Ключ другой configuration или без binding доступа не даёт.

`enableSessionForAPIKeys` должен быть `false`. Явно настрой 60 проверок ключа
в минуту, отключи ограничение общего количества использований `remaining`.
Выполняй одну проверку ключа на HTTP-запрос. При `RATE_LIMITED` результат
`verifyApiKey` содержит `error.details.tryAgainIn` в миллисекундах.
Верни HTTP 429 и стандартный `Retry-After` в секундах с округлением вверх.
Превышение частоты сохраняет binding, общую пару и доступ после окончания окна.
Запись API key может сама служить binding, когда её создаёт только доверенный
серверный путь. Отдельную таблицу добавляй по реальной необходимости.

Закрой общие HTTP endpoints плагина точным `disabledPaths` для выбранной версии
(`/api-key/create`, `/api-key/update`, `/api-key/delete`, `/api-key/get`,
`/api-key/list`). Сверь фактические маршруты, base path и доступность тестами.
Серверные `auth.api.*` используются внутри доверенных обработчиков.
Self-revoke реализуй через подходящий server API с проверенным binding.

Для своих маршрутов явно проверь допустимые методы, аутентификацию, CSRF/origin
границы браузерных действий и частоту публичного flow. Native Agent работает
без браузерного Origin, это отдельный допустимый путь Bearer/API-key запросов.
Защити все серверные операции, изменяющие доступ. Возврат после login принимает
только разрешённые локальные назначения.

ROOT/ADMIN Dock остаются server-only. Пользователь не задаёт account/user/role,
admin endpoint или ключи другого пользователя. Dock URL и ADMIN credentials
берутся из защищённой серверной конфигурации.
Выбери и проверь хранение доступной для повторной выдачи Dock-пары, прав БД,
секретов шифрования, резервных копий и миграций с учётом окружения.
Секреты и session tokens исключи из логов, URL, браузерного bundle, localStorage,
публичных env, диагностических ответов и test evidence. JSON credentials получает
аутентифицированный Agent по защищённому серверному маршруту. Ответы с ключами
и персональными auth-данными исключи из публичного/CDN кеша через подходящие
Cache-Control и настройки Next. Проверь отсутствие ключей в HTML и статике.

## 7. Пользователь на двух Dock и согласованность операций

Сайт связывает стабильный Better Auth user ID с USER в account `loginom-dock`
на каждом сервере. Email используется как профильная информация, идентичность
Dock выводится из серверного стабильного ID. Персональная пара общая для
установок пользователя, installation keys у установок различаются.
Выбирай отдельное пространство имён для персональных ID. Используй допустимые
символы `[a-zA-Z0-9_.@-]`, соблюдай валидатор Dock, исключи коллизии с
`dock-admin`, `loginom-dock` и уже существующими USER.

При создании USER на обоих серверах передай `user_config.memory_policy` с
`self.enabled = false`, `peer.enabled = false` и `working_memory.enabled = false`.
Прочитай эффективные настройки до выдачи ключа. По умолчанию типы памяти
разрешены. Эти настройки задают поведение обычной сессии, Dock допускает
переопределение политики сессии. Прямой USER-ключ позволяет писать в разрешённые
области за пределами официальной KB, инициировать извлечение памяти с LLM и
импортировать ресурсы по URL. До открытия регистрации проверь права, затраты и
доступ к внутренней сети. Ограничения или принятие остаточного риска фиксирует
владелец (§8). Ограничение инструментов Help в Agent действует только внутри Agent.

Два одновременных первых подключения получают одну сохранённую пару.
Повторное создание существующего USER не вызывает произвольную ротацию.
Сериализуй initial provisioning, получение пары, восстановление, ротацию
и отзыв по пользователю. Способ выбирай по БД и реальному числу процессов.
Гарантии должны переживать перезапуск и фактическую конкуренцию deployment.

В каждом пути выдачи, включая GET, перепроверяй active binding после ожидания
сериализации и снимай пару в той же защищённой секции. GET, начатый до отзыва,
не может использовать старую проверку для выдачи новой пары после отзыва.
Запоздалый снимок, снятый раньше отзыва, инвалидируется ротацией Dock-ключей.

Покрой частичное создание/ротацию и потерянный ответ Dock. Сохраняй известный
действующий ключ каждого сервера и состояние незавершённой операции.
При следующей попытке сверяй или восстанавливай её под той же сериализацией.
Возвращай фактическую актуальную пару либо временную ошибку до её установления.

Изучи реальные handlers Dock `routers/admin.py`, `api_keys/new.py`,
`api_keys/legacy.py`. ADMIN создаёт USER и ротирует его ключ через account API.
Для восстановления потерянного ответа можно до вызова Dock сохранить в БД
зашифрованный случайный `seed` — отдельный для каждого Dock и каждой новой
операции выдачи или ротации. Повтор незавершённой операции использует её seed.
Dock вычисляет секрет как hex SHA-256 от UTF-8 `user_id + "\0" + seed`.
В новом формате это лишь секрет третьего сегмента ключа. Тот же seed
восстанавливает тот же ключ, в том числе при хранении хеша в Dock.
Повтор `register` существующего USER возвращает конфликт. До выдачи проверь
владельца операции, роль, доступ с восстановленным ключом и настройки памяти:
реестр записывается раньше пользовательской конфигурации. Не ротируй ключ
посторонней записи при совпавшем ID. При восстановлении повторяй только
текущую незавершённую ротацию, чтобы запоздалый повтор не вернул старый ключ.
ADMIN read-back может дать лишь prefix при Argon2, trusted mode скрывает ключ.
Докажи восстановление тестом с потерянным ответом в выбранном режиме.

Сайт хранит ADMIN всего account, что включает управление KB и пользователями.
Ограничь его доступ серверным контуром. Для обычной выдачи в существующем
account используй эти полномочия без ROOT.

## 8. Отзыв ранее выданного доступа

Обычный DELETE одной установки сохраняет общую пару.
Отдельный отзыв установки отключает её binding/site key и меняет оба Dock key.
Остальные разрешённые установки получают новую пару штатным GET без входа.
Отзыв пользователя отключает все существующие подключения и меняет оба
Dock-ключа пользователя.

Предоставь минимальный защищённый способ инициировать эти административные
операции в имеющемся контуре сайта. HTTP/UX для административного отзыва
спецификацией не зафиксирован, выбери необходимый интерфейс в плане.
USER Dock и его данные сохраняются.

Пока старый ключ хотя бы одного Dock ещё действителен, показывай частичное
завершение и сохраняй возможность продолжить операцию после восстановления
сервера. Успех означает инвалидацию обоих прежних ключей.
Сохрани это состояние через перезапуск, исключи выдачу пары отозванным binding.

Гарантия относится к ранее выданным credentials. Сохранившаяся браузерная сессия
или известный пароль позволяют подтвердить новый device login. Открытая
регистрация позволяет создать другой аккаунт. Обычный logout установки
сохраняет браузерную сессию, история диалогов и данные пользователя сохраняются.

### Решения владельца до включения соответствующих возможностей

Зафиксируй ответы владельца в плане сайта. Независимые части device flow
и анкеты можно реализовать и проверить, пока эти решения открыты.

- **Установки.** Видит ли пользователь список своих установок, может ли сам
  отзывать потерянную установку с ротацией обоих Dock-ключей?
- **Повторный DELETE.** Рекомендуемый ответ для уже отключённой установки —
  204 без побочных эффектов. Agent признаёт подтверждением только 204.
  Согласуй поведение для неизвестного ключа и способ проверки повторного запроса.
  Ни один вариант не должен затронуть чужую установку или общую пару.
- **Пароль и аккаунт.** Требуется ли восстановление пароля и как отправлять
  ссылку пользователю? Сейчас почтовый обработчик доставляет только заявки на
  скачивание на адрес оператора. Для сброса пароля потребуется отдельный сценарий
  отправки и проверки ссылки. Как запросить удаление аккаунта или отзыв согласия,
  какие данные удалить и как завершить отзыв доступа на обоих Dock?
- **Новые регистрации.** Нужны ли уведомления или выгрузка, кому, какие поля и
  по какому каналу? Действующая анкета скачивания и регистрация имеют разные цели.
- **Открытая регистрация.** Какие ограничения нужны для прямого USER-доступа
  к записи, LLM и URL-импорту, какие расходы и риски владелец принимает?

## 9. Существующий сайт и развёртывание

Прочитай `README.md`, `site/download-form.html` и `site/download-form.js`.
В `deploy/local/` сверь `Caddyfile`, `compose.yaml`, `compose.download-form.yaml`,
`download-form.caddy`, `download-form.py` и `download-smtp.env.example`.
При регистрации используй поля актуальной анкеты. Сохрани маршрут заявки
на скачивание через Caddy. Он передаёт `POST /api/download-request` сервису
`download-form` во внутренней сети. Python проверяет Origin, JSON, выбранный установщик и согласие.
Обработчик отправляет письмо на фиксированный `testing@loginom.ru`, адрес из
анкеты ставит в `Reply-To`. HTTP 204 означает, что SMTP-сервер принял письмо.
Поступление письма в ящик проверяется отдельно при разрешённой сквозной проверке.

Проверь в браузере, что до ответа повторная отправка и закрытие диалога
заблокированы. Предел ожидания — 20 секунд. После ошибки отправку можно повторить,
после 204 пользователь скачивает файл по показанной ссылке. Локально проверь
успех и отказ почтового обработчика с тестовой доставкой.

Спланируй добавление Next runtime и durable БД с миграциями,
закрытым хранением секретов, backup/restore и понятным откатом deployment.
Сохрани Caddy CIDR/trusted proxy ограничения, внешнюю Docker-сеть и тома,
маршруты `app.loginom.ai`, `/app/` и WebSocket. Проверь overlay mount
`download-form-site` в режиме с формой. Запросы к главной должны получать
сборку выбранного режима, а запросы к новым auth-маршрутам — попадать в Next.js.
Согласуй новую маршрутизацию loginom.ai и `/api/auth`/`/api/agent`
с существующим `/api/download-request`.

Текущий CSP ограничивает scripts/styles до self, form-action до none,
connect-src до none/self. Настрой необходимую политику Next/auth по реально
используемым ресурсам и проверь её в браузере. Изменения должны сохранять
принятую защиту публичного сайта.

В Compose сервис `download-form` подключается к `smtp.gmail.com:465` по TLS.
Почтовые реквизиты берутся из `.env.download-smtp` рядом с Compose-файлами,
права файла — 0600. Сохрани существующий серверный доступ к SMTP и хранение
реквизитов вне Git. Локальный `local.env` оставь в рабочей копии оператора.
Перед разрешённым развёртыванием сверь конфигурацию и доступность SMTP из
контейнера. В примерах используй только имена переменных и безопасные заглушки.

**Шлюз и IP клиента.** В конфигурации сайта TLS публичного входа завершается
перед Caddy. Публичные домены Caddy принимает по HTTP только от доверенных
CIDR. Задай явный production `baseURL: "https://loginom.ai"`, а на стенде —
полный HTTPS origin его сайта. Проверь сквозной маршрут через шлюз и Caddy
для новых путей, включая DELETE, передачу `Authorization`, `X-API-Key`,
достоверных `X-Forwarded-*` и ответного `Retry-After`. Ответы auth API
приходят без кеширования и редиректов, ссылка подтверждения остаётся HTTPS.

В production Better Auth 1.7.18 по умолчанию принимает один валидный IP
из `X-Forwarded-For`. Без настроенных trusted proxies цепочка из нескольких
адресов оставляет один общий счётчик на путь для запросов без определённого IP.
Для `/sign-in/email` и `/sign-up/email` это три запроса за десять секунд.
Выбери проверяемый вариант: закрытый от прямого доступа Next за доверенным
шлюзом/Caddy и корректные `advanced.ipAddress.trustedProxies` для реальных
proxy hops, либо Caddy перезаписывает выделенный заголовок значением
`{client_ip}` и Better Auth читает только его. Задай доверенные сети у каждого
прокси. Клиентские заголовки не могут быть источником доверия сами по себе.
При стандартно включённых в production лимитах два разных IP имеют независимые
счётчики. Добавление поддельного левого адреса в цепочку не сбрасывает лимит.
Проверяй через реальную цепочку стенда в production-режиме.

**Доступ к двум Dock.** В начале работы проверь из сети контейнера сайта на
разрешённом стенде DNS, TLS и аутентифицированный доступ к admin API каждого
Dock. Выясни фактические upstream и доступные методы, не выводя ключи.
Корпоративное DNS-наблюдение связывало `loginom.ai`, `app.loginom.ai` и
`mcp.loginom.ai` с `<external-gateway>`; резервное имя тогда не разрешалось.
Определи фактический upstream за шлюзом по его конфигурации и проверке маршрута.
Шаблон Dock `Caddyfile.server` проксирует API целиком, включая `/api/v1/admin`.
Согласуй защищённый серверный маршрут к каждому admin API (например, приватная
сеть или ACL на шлюзе). Проверь, что из недоверенной сети доступ к admin API
ограничен и публичный MCP работает. Отсутствующий upstream укажи как внешний блокер
этой проверки. Продолжи работу с двумя изолированными экземплярами.

Два Dock должны иметь независимые volumes, реестры и ключи. Подготовь требования
к обоим admin endpoint, credentials, USER mapping, KB URI и ACL. Публикуется одна
версия источников KB отдельно в оба инстанса. Полный primary backup содержит
ключи и предназначен для восстановления собственного сервера. Для актуализации
KB reserve используй существующий импорт. Restore учитывает последующие отзывы,
чтобы прежние ключи не вернулись в доступ.
Сайт зависит от доступности обоих реестров для первой полной выдачи.
Требования к созданию reserve передай в конкретном эксплуатационном checklist,
реальную доступность проверь на предоставленном стенде.

Предусмотри очистку истёкших `deviceCode`, сессий и старых
счётчиков `rateLimit`, если они хранятся в БД. Учитывай самое длинное окно
лимитера и сохраняй данные действующих установок и сведения, нужные для отзыва.
Проверь отдельно восстановление БД сайта из копии, сделанной до отзыва:
до открытия выдачи повтори последующие отзывы из достоверного источника либо
заблокируй восстанавливаемые ключи, если действительность нельзя установить.
Старый installation key не должен вновь получить пару через GET.

## 10. Проверки результата

Выполняй проверки через реальные HTTP handlers, выбранный Better Auth и БД.
Для гонок и отказов допустимы управляемые локальные границы Dock.
Связку сайта с реальным Dock проверь отдельно. Обязательные сценарии следуют
из контракта, каждый получает собственный проверяемый результат.

1. Регистрация с анкетой, вход/выход веб-сессии, обязательные и необязательные
   поля, повторный вход без повторного заполнения анкеты, отсутствие автоматической
   регистрации по старой download-заявке, версия и время согласия, `noindex`.
2. Device login с разрешением/отказом, сохранённой веб-сессией, сменой аккаунта,
   неверным/истёкшим/повторным кодом, pending/slow_down/expiry и ограничением частоты.
   Открой код под A, переключись на B и только затем подтверди или отклони от B.
   Отдельно проверь `invalid_grant` (один ответ), временные 429/5xx и подбор кода
   через серверное действие. В production-режиме проверь IP и подмену XFF по §9.
3. Успешный и терминально неуспешный обмен гасят точную device-сессию, сохраняя
   сессию браузера. Проверь клиентский revoke-session fallback, отмену,
   два конкурентных обмена одного токена, подстановку токена веб-сессии,
   фиксированный срок и ограничение Bearer по §5. После погашения fallback
   получает 401. При сбое записи клиент вызывает DELETE выданного ключа до
   попытки revoke-session и показывает исходную ошибку. Проверь работоспособность
   соседней установки. Потеря ответа обмена не вызывает повтор этого POST клиентом.
4. Две одновременные первые установки получают разные installation keys
   и одну персональную пару. Повторное подключение сохраняет ключи остальных.
   Первый успех требует действующих ключей обоих серверов.
5. Чужая API Key configuration, ключ без binding, отозванный binding и попытки
   подставить чужой user/account/role не получают чужую пару. Exact disabledPaths,
   server API, лимит 60/мин и одна проверка ключа на запрос проверены по факту.
   Исчерпай лимит, проверь 429 со стандартным `Retry-After` и успешный GET тем же
   ключом после паузы. Проверь тот же заголовок при срабатывании HTTP-ограничителя.
6. Обычный DELETE отвечает 204 и сохраняет пару и остальные установки.
   Отдельный отзыв установки и пользователя инвалидирует оба прежних Dock key.
   Первая операция сохраняет доступ остальных установок через refresh.
7. Гонка GET с отзывом, перезапуск между шагами, частичный отказ primary/reserve,
   потеря ответа register/regenerate и восстановление БД сайта из более ранней
   копии сохраняют согласованность и отзыв ранее отключённых ключей.
8. Временные ошибки и 429 со стандартным `Retry-After` сохраняют клиентские credentials,
   доказанный access_revoked удаляет их. Установка не получает новые ключи
   после отзыва по устаревшей проверке доступа.
9. Два независимых Dock отвергают ключи друг друга. Официальная KB доступна
   USER для чтения, её изменение/удаление/ACL и admin API USER запрещены.
   Повторная публикация KB сохраняет реестры/ключи. Проверь эффективные grants
   потомков, политику памяти нового USER, доступность admin API из контейнера
   сайта и внешний запрет, настройки private-network/URL-import.
10. Полный device flow с собранными Desktop и CLI против изолированного сайта
    и двух Dock, включая две установки, ротацию/refresh, cancel и logout.
    Собери оба клиента из `dock-cloud-auth@b536a2e8cb` или проверенного потомка
    в `LOGINOM_AI_AGENT_CHANNEL=dev`, с отдельными профилями. Во время сборки
    `LOGINOM_AI_AGENT_CLOUD_BUILD` содержит ровно `site`, `primary`, `reserve` —
    три HTTPS URL без логина/пароля. Better Auth `baseURL` совпадает с `site`,
    `verification_uri_complete` ведёт на его origin. Перед запуском передай
    тестовый CA процессам клиентов через `NODE_EXTRA_CA_CERTS`, настрой доверие
    браузера к CA стенда. Пройди разрешение и отказ в реальном браузере.
    Тестовый `/approve`, которым пользуются скрипты Agent, существует только
    у fixture. Для проверки сайта используй его страницу подтверждения.
11. Выполни проверки из раздела [«Сохранение существующей главной страницы»](#сохранение-существующей-главной-страницы)
    для всех трёх режимов сборки. Сверь снимки и публичные URL с исходной версией.
    Проверь также маршруты приложения, авторизацию и подтверждение устройства
    в браузере с реальными CSP, cookies и перенаправлениями.

Сначала выполни `node site/build.mjs`, затем `node --test site/*.test.mjs`.
Эти тесты проверяют выбор ОС, данные релиза и обычную сборку. Для проверки
формы отдельно собери `node site/build.mjs --preview-download-form` и
`node site/build.mjs --download-form`, затем проверь их поведение по §2 и §9.
При добавлении Next обнови документированные команды и выполняй сборку,
проверку типов и обязательные тесты фактического проекта.
Для временных данных задай абсолютный существующий TMPDIR текущей машины.
На этой машине используй `$HOME/storage/tmp/`, на VM установи доступный
путь отдельно. Сохраняй сырые логи и секреты вне Git.

## 11. Условия завершения и отчёт

Передай реализованный код сайта, migrations/lockfile, пример серверной конфигурации,
инструкции сборки/запуска/обновления/отката, согласованный план с результатами
и отчёт приёмки без секретов. Организуй независимое итоговое ревью и устрани
подтверждённые замечания в согласованном объёме.

Технические решения выбирай по текущей задаче. Используй штатные plugins,
существующие deployment/import/backup средства и минимальную достаточную схему.
Оплата, личная память, запись диалогов, универсальный OAuth Provider и новая
репликация KB остаются вне согласованной задачи.
Существующий общий ключ старых клиентов сохраняется до отдельной команды
владельца об отключении. Уведомление пользователей и его production отзыв
не выполняются как побочный эффект регистрации или публикации KB.

Покажи отдельно результаты source tests, настоящей Better Auth/DB интеграции,
двух Dock и Desktop/CLI e2e, затем готовность rollout. Для каждой невыполненной
проверки запиши конкретную причину и необходимые входные данные.
При внешнем блокере заверши всю независимую реализацию и проверки, сохрани
короткую точку продолжения. Успех локальных fixtures не означает production PASS.
Нативные Windows/macOS проверки хранения/proxy Agent сохраняют собственный gate.
