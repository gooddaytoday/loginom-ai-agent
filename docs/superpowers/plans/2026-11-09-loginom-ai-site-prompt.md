# Prompt для планирования и реализации облачного входа на loginom.ai

Работай в репозитории сайта `$HOME/storage/git/loginom-ai-site`.
Спланируй и реализуй серверную и браузерную части подключения Loginom AI Agent
к облачным Dock через loginom.ai. Доведи работу до проверенного результата
в доступном изолированном окружении, подготовь развёртывание и точный отчёт
об оставшихся внешних зависимостях. Отвечай по-русски.

## 1. Результат

Пользователь регистрируется или входит на loginom.ai, явно подтверждает код
Desktop/CLI и получает работающий доступ к официальной базе знаний.
Каждая установка получает собственный отзываемый бессрочный ключ сайта.
Установки одного пользователя используют общую персональную пару Dock-ключей.
Новая установка сохраняет действующую пару. После ротации разрешённая установка
получает новые ключи без повторного входа. Отзыв ранее выданного доступа
инвалидирует соответствующие ключи сайта и обоих Dock.

Основа решения согласована — Next.js и Better Auth с Device Authorization,
Bearer и API Key. Выбери минимальную достаточную БД, схему и способ развёртывания
по фактическому устройству проекта. Сохрани рабочую публичную страницу,
скачивание установщиков и существующую доставку заявок. Объём переноса текущей
статики выбирай по необходимости интеграции, переиспользуя существующую сборку
и ассеты там, где они продолжают выполнять свою задачу.

## 4. Регистрация, вход и подтверждение устройства

Реализуй email/password регистрацию и вход с обычной веб-сессией.
Регистрация сразу открывает доступ, подтверждение email и ручное одобрение
администратором в принятом продукте отсутствуют. Пароли обрабатывает Better Auth.

При регистрации один раз заполняется анкета. Обязательны имя, фамилия, email,
пароль, телефон, профессиональный статус и согласие на обработку данных.
Отчество, компания, должность и согласие на новости необязательны.
Используй согласованные поля и серверную валидацию. Старые заявки на скачивание
содержат контактные данные, их связь с аккаунтом требует нового входа/регистрации.
Совпадение email в заявке не подтверждает владение аккаунтом.

На странице подтверждения покажи текущий аккаунт, возможность его сменить,
название Loginom AI Agent и пользовательский код. Пользователь явно разрешает
или отклоняет подключение. Действующая веб-сессия сама устройство не подтверждает.
После входа/регистрации сохрани контекст исходного кода и верни пользователя
к подтверждению. Полная ссылка из Agent уже содержит код.
Проверь повторный, неверный, истёкший, уже использованный и отклонённый код,
а также смену аккаунта в ходе подтверждения.

Отдели обычную браузерную сессию подтверждения от временной device-сессии,
которую получит Agent. Проверь совместную работу плагинов на выбранной версии,
включая привязку подтверждённого device grant к пользователю и сессии обмена.

## 5. Точный HTTP-контракт уже реализованного клиента

Production адреса закреплены в Agent — `https://loginom.ai`,
`https://mcp.loginom.ai/mcp` и `https://mcp-reserve.loginom.ai/mcp`.
Сайт возвращает ключи для этих назначений. Настройка admin endpoint Dock
принадлежит серверу сайта, пользовательские параметры его не меняют.
Credential-bearing маршруты обслуживай непосредственно, клиент запрещает redirect.

### Получение device code

`POST /api/auth/device/code`, JSON request

```json
{"client_id":"loginom-ai-agent"}
```

Обязательные поля JSON response

```json
{
  "device_code":"TEST_DEVICE_CODE",
  "user_code":"TEST-CODE",
  "verification_uri_complete":"https://loginom.ai/device?user_code=TEST-CODE",
  "expires_in":600,
  "interval":5
}
```

Строки непустые, `expires_in` и `interval` положительные числа в секундах.
Числа в примере иллюстрируют формат, значения срока выбери в плане.
Полная ссылка абсолютная, с тем же origin сайта и без credentials в URL.
Agent использует `verification_uri_complete`, `verification_uri` ему недостаточно.
Разрешённый публичный client ID — `loginom-ai-agent`.

### Ожидание подтверждения

`POST /api/auth/device/token`, JSON request

```json
{
  "grant_type":"urn:ietf:params:oauth:grant-type:device_code",
  "device_code":"TEST_DEVICE_CODE",
  "client_id":"loginom-ai-agent"
}
```

Успешный response

```json
{"access_token":"TEST_RAW_DEVICE_SESSION_TOKEN","token_type":"Bearer","expires_in":600}
```

`token_type` строго `Bearer`, токен непустой, `expires_in` числовой.
Ошибки polling имеют плоский OAuth-формат `{"error":"authorization_pending"}`,
также поддержаны `slow_down`, `access_denied`, `expired_token`.
Клиент соблюдает interval, добавляет пять секунд при `slow_down` и учитывает
`Retry-After` для429. Обеспечь защиту публичной выдачи/проверки кодов и ограничения
частоты на стороне сервера.

### Первичный обмен на подключение установки

`POST /api/agent/connections`, body `{}`, header
`Authorization: Bearer <raw device session token>`.
Успешный JSON response содержит полную действующую пару

```json
{
  "installationKey":"TEST_INSTALLATION_KEY",
  "user":{"email":"user@example.test"},
  "dock":{
    "primary":{"apiKey":"TEST_PRIMARY_USER_KEY"},
    "reserve":{"apiKey":"TEST_RESERVE_USER_KEY"}
  }
}
```

Все показанные строки непустые. Ответ имеет обычное успешное HTTP-состояние
с JSON-телом. Пустой204 не соответствует этому обмену.
Сохрани результат выдачи до отправки успешного ответа.
Потеря первоначального ответа может потребовать нового device-входа.
Повторы выдачи ограничь с учётом этого сценария, исключив бесконечное
автоматическое создание установок после потери ответа.

Каждый site HTTP request Agent ограничен максимум15 секундами.
Polling и обмен дополнительно расходуют оставшийся срок исходного device code.
Проверь работу на границе этого срока. `token.expires_in` не продлевает
клиентский deadline обмена. Планирование серверных операций учитывает эти пределы.

### Получение актуальной пары

`GET /api/agent/dock-credentials`, без body,
`X-API-Key: <installationKey>`.

```json
{
  "dock":{
    "primary":{"apiKey":"TEST_PRIMARY_USER_KEY"},
    "reserve":{"apiKey":"TEST_RESERVE_USER_KEY"}
  }
}
```

Возвращай полную достоверную пару. Agent вызывает refresh по необходимости
после Dock401, имеет общую выполняющуюся попытку и demand-only cooldown
минимум30 секунд. Поле `Retry-After` может задавать секунды либо HTTP-date.
Обновление пары сохраняет installation key и аккаунт пользователя.

Только доказанный отзыв binding/key/account возвращает совместимый403
с точным телом

```json
{"error":{"code":"access_revoked","message":"Access to this installation has been revoked"}}
```

Это сигнал удаления локальных credentials и нового входа.
Временная недоступность БД/Dock/сайта, HTML от proxy, обычные401/403 и ошибки
проверяющего сервиса сохраняют credentials. Используй для временных отказов
отдельные `credentials_unavailable`/`service_unavailable` и подходящие HTTP-коды.
Agent обрабатывает429 и5xx до разбора `access_revoked`.

### Обычное отключение установки

`DELETE /api/agent/connections/current`, без body,
`X-API-Key: <installationKey>`. Подтверждённый успех строго `204`.
Отключи binding и ключ этой установки. Общая Dock-пара и другие установки
сохраняются. Agent выполняет локальный выход даже при сетевом отказе,
удалённому запросу выделяет пять секунд и сообщает неподтверждённый отзыв.

### Погашение временной device-сессии

Сайт сам погашает точную bootstrap-сессию после успешного обмена и его
терминальной ошибки. Успешный клиентский обмен дополнительный revoke не вызывает.
Браузерная сессия подтверждения сохраняется.
Клиентский fallback при отмене или неуспешном обмене использует
`POST /api/auth/revoke-session` с JSON `{"token":"TEST_RAW_DEVICE_SESSION_TOKEN"}`
и тем же raw token в `Authorization: Bearer ...`, ожидает `{"status":true}`
и ограничен пятью секундами.

Докажи привязку удаляемого token к текущей device-сессии. В исследованной
Better Auth v1.7.17 `status:true` встречается и для отсутствующего/чужого token.
Проверь реальное удаление правильной сессии в интеграционном тесте и сохранение
браузерной сессии. Дополнительный production read-after-revoke сам по себе
не является обязательным механизмом.
При обрыве до cleanup остаточный доступ ограничен серверным сроком временной
сессии. У standalone Device Authorization полноценные session-полномочия,
отдельный bootstrap-only TTL и scope требуют фактической проверки возможностей.

## 6. Installation key и границы доступа

Используй отдельную API Key configuration `agent-installation`.
Ключ разрешает получение пары и собственное отключение, остаётся бессрочным
до отзыва и независимым от срока веб-сессии. На каждом запросе проверяй
принадлежность configuration и активное серверное binding ключа к пользователю
и состоянию доступа. Ключ другой configuration или без binding доступа не даёт.

`enableSessionForAPIKeys` должен быть `false`. Явно настрой60 проверок ключа
в минуту, отключи ограничение общего количества использований `remaining`.
Выполняй одну проверку ключа на HTTP-запрос.
Запись API key может сама служить binding, когда её создаёт только доверенный
серверный путь. Отдельную таблицу добавляй по реальной необходимости.

Закрой общие HTTP endpoints плагина точным `disabledPaths` для выбранной версии
(`/api-key/create`, `/api-key/update`, `/api-key/delete`, `/api-key/get`,
`/api-key/list`). Сверь фактические маршруты, base path и доступность тестами.
Серверные `auth.api.*` используются внутри доверенных обработчиков.
Self-revoke реализуй через подходящий server API с проверенным binding.

Для своих маршрутов явно проверь допустимые методы, аутентификацию, CSRF/origin
границы браузерных действий и частоту публичного flow. Native Agent работает
без браузерного Origin, это отдельный допустимый путь Bearer/API-key запросов.
Защити все серверные операции изменяющие доступ. Возврат после login принимает
только разрешённые локальные назначения.

ROOT/ADMIN Dock остаются server-only. Пользователь не задаёт account/user/role,
admin endpoint или ключи другого пользователя. Dock URL и ADMIN credentials
берутся из защищённой серверной конфигурации.
Выбери и проверь хранение доступной для повторной выдачи Dock-пары, прав БД,
секретов шифрования, резервных копий и миграций с учётом окружения.
Секреты и session tokens исключи из логов, URL, браузерного bundle, localStorage,
публичных env, диагностических ответов и test evidence. JSON credentials получает
аутентифицированный Agent по защищённому серверному маршруту. Ответы с ключами
и персональными auth-данными исключи из публичного/CDN кеша через подходящие
Cache-Control и настройки Next. Проверь отсутствие ключей в HTML и статике.

## 7. Пользователь на двух Dock и согласованность операций

Сайт связывает стабильный Better Auth user ID с USER в account `loginom-dock`
на каждом сервере. Email используется как профильная информация, идентичность
Dock выводится из серверного стабильного ID. Персональная пара общая для
установок пользователя, installation keys у установок различаются.

Два одновременных первых подключения получают одну сохранённую пару.
Повторное создание существующего USER не вызывает произвольную ротацию.
Сериализуй initial provisioning, получение пары, восстановление, ротацию
и отзыв по пользователю. Способ выбирай по БД и реальному числу процессов.
Гарантии должны переживать перезапуск и фактическую конкуренцию deployment.

В каждом пути выдачи, включая GET, перепроверяй active binding после ожидания
сериализации и снимай пару в той же защищённой секции. GET, начатый до отзыва,
не может использовать старую проверку для выдачи новой пары после отзыва.
Запоздалый снимок, снятый раньше отзыва, инвалидируется ротацией Dock-ключей.

Покрой частичное создание/ротацию и потерянный ответ Dock. Сохраняй известный
действующий ключ каждого сервера и состояние незавершённой операции.
При следующей попытке сверяй или восстанавливай её под той же сериализацией.
Возвращай фактическую актуальную пару либо временную ошибку до её установления.

Изучи реальные handlers Dock `routers/admin.py`, `api_keys/new.py`,
`api_keys/legacy.py`. ADMIN создаёт USER и ротирует его ключ через account API.
Повтор одинакового seed даёт тот же ключ, поэтому постоянный seed пользователя
не обеспечивает ротацию. ADMIN read-back полного текущего ключа зависит от
режима хранения Dock — при Argon2 может быть доступен только prefix,
trusted mode также ограничивает выдачу ключей. Выбери конкретный рабочий способ
восстановления lost reply для выбранного режима и докажи его тестом.
План должен учитывать отсутствие общей транзакции между БД сайта и двумя Dock.

Сайт хранит ADMIN всего account, что включает управление KB и пользователями.
Ограничь его доступ серверным контуром. Для обычной выдачи в существующем
account используй эти полномочия без ROOT.

## 8. Отзыв ранее выданного доступа

Обычный DELETE одной установки сохраняет общую пару.
Отдельный отзыв установки отключает её binding/site key и меняет оба Dock key.
Остальные разрешённые установки получают новую пару штатным GET без входа.
Отзыв пользователя отключает все существующие подключения и меняет оба
Dock-ключа пользователя.

Предоставь минимальный защищённый способ инициировать эти административные
операции в имеющемся контуре сайта. HTTP/UX для административного отзыва
спецификацией не зафиксирован, выбери необходимый интерфейс в плане.
USER Dock и его данные сохраняются.

Пока старый ключ хотя бы одного Dock ещё действителен, показывай частичное
завершение и сохраняй возможность продолжить операцию после восстановления
сервера. Успех означает инвалидацию обоих прежних ключей.
Сохрани это состояние через перезапуск, исключи выдачу пары отозванным binding.

Гарантия относится к ранее выданным credentials. Сохранившаяся браузерная сессия
или известный пароль позволяют подтвердить новый device login. Открытая
регистрация позволяет создать другой аккаунт. Обычный logout установки
сохраняет браузерную сессию, история диалогов и данные пользователя сохраняются.

## 9. Существующий сайт и развёртывание

Прочитай `docs/download-form.md`, `deploy/local/Caddyfile`, `compose.yaml`,
`compose.download-form.yaml`, исходники формы и её Python-обработчика.
При регистрации используй актуальную анкету. Доставка заявки на скачивание
сохраняет собственный контракт — ссылка появляется сразу после валидной формы,
ошибка API/Telegram/VPN/timeout не блокирует установщик,204 означает подтверждённый
приём внешним сервисом. Закрытие диалога и поздний ответ сохраняют текущую защиту.
Существующий Python/Telegram/Xray путь используй в его назначении.

Спланируй добавление Next runtime и durable БД с миграциями,
закрытым хранением секретов, backup/restore и понятным откатом deployment.
Сохрани Caddy CIDR/trusted proxy ограничения, внешнюю Docker-сеть и тома,
маршруты `app.loginom.ai`, `/app/` и WebSocket. Учитывай текущий overlay mount
`download-form-site`, иначе он может продолжить отдавать прежнюю статику.
Согласуй новую маршрутизацию loginom.ai и `/api/auth`/`/api/agent`
с существующим `/api/download-request`.

Текущий CSP ограничивает scripts/styles до self, form-action до none,
connect-src до none/self. Настрой необходимую политику Next/auth по реально
используемым ресурсам и проверь её в браузере. Изменения должны сохранять
принятую защиту публичного сайта.

`local.env` содержит локальные доступы оператора и отделён от серверных env.
Сохрани0600 и исключение приватных файлов из Git. Существующий Xray proxy
для Telegram остаётся локальной зависимостью обработчика, без глобального
VPN/TUN и новых маршрутов всей VM. Пути и состояние VM устанавливай заново
перед разрешённым обновлением. Подготовь пример конфигурации с именами
необходимых переменных и безопасными заглушками.

Два Dock должны иметь независимые volumes, реестры и ключи. Подготовь требования
к обоим admin endpoint, credentials, USER mapping, KB URI и ACL. Публикуется одна
версия источников KB отдельно в оба инстанса. Полный primary backup содержит
ключи и предназначен для восстановления собственного сервера. Для актуализации
KB reserve используй существующий импорт. Restore учитывает последующие отзывы,
чтобы прежние ключи не вернулись в доступ.
Сайт зависит от доступности обоих реестров для первой полной выдачи.
Требования к созданию reserve передай в конкретном эксплуатационном checklist,
реальную доступность проверь на предоставленном стенде.

## 10. Проверки результата

Выполняй проверки через реальные HTTP handlers, выбранный Better Auth и БД.
Для гонок и отказов допустимы управляемые локальные границы Dock.
Связку сайта с реальным Dock проверь отдельно. Обязательные сценарии следуют
из контракта, каждый получает собственный проверяемый результат.

1. Регистрация с анкетой, вход/выход веб-сессии, обязательные и необязательные
   поля, повторный вход без повторного заполнения анкеты, отсутствие автоматической
   регистрации по старой download-заявке.
2. Device login с разрешением/отказом, сохранённой веб-сессией, сменой аккаунта,
   неверным/истёкшим/повторным кодом, pending/slow_down/expiry и ограничением частоты.
3. Успешный и терминально неуспешный обмен гасят точную device-сессию, сохраняя
   сессию браузера. Проверить клиентский revoke-session fallback, отмену,
   повторный запрос и чужой token. Зафиксировать реальную семантику выбранной версии.
4. Две одновременные первые установки получают разные installation keys
   и одну персональную пару. Повторное подключение сохраняет ключи остальных.
   Первый успех требует действующих ключей обоих серверов.
5. Чужая API Key configuration, ключ без binding, отозванный binding и попытки
   подставить чужой user/account/role не получают чужую пару. Exact disabledPaths,
   server API, rate60/min и одна verification на request проверены по факту.
6. Обычный DELETE отвечает204 и сохраняет пару/остальные установки.
   Отдельный отзыв установки и пользователя инвалидирует оба прежних Dock key.
   Первая операция сохраняет доступ остальных установок через refresh.
7. Гонка GET с отзывом, перезапуск между шагами, частичный отказ primary/reserve,
   потеря ответа после изменения ключа и повтор операции сохраняют согласованность.
8. Временные ошибки и429/Retry-After сохраняют клиентские credentials,
   доказанный access_revoked удаляет их. Установка не получает новые ключи
   после отзыва по устаревшей проверке доступа.
9. Два независимых Dock отвергают ключи друг друга. Официальная KB доступна
   USER для чтения, её изменение/удаление/ACL и admin API USER запрещены.
   Повторная публикация KB сохраняет реестры/ключи. Проверь эффективные grants
   потомков, доступность admin API и настройки private-network/URL-import.
10. Полный device flow с собранными Desktop и CLI против изолированного сайта
    и двух Dock, включая две установки, ротацию/refresh, cancel и logout.
    Для staging используй единый build-time tuple `LOGINOM_AI_AGENT_CLOUD_BUILD`
    в явном dev channel Agent и отдельные профили. Сборки со стандартными
    production адресами к локальному site не перенастраиваются runtime env.
11. Существующие download/tests, release metadata, примеры и маршруты приложения
    работают. Браузерная проверка охватывает широкий/узкий экран, клавиатуру,
    авторизацию, подтверждение устройства, реальные CSP/cookies/redirects
    и сценарии без JavaScript там, где их поддерживает существующая страница.

Начальные проверки текущего сайта — `node site/build.mjs`,
`node --test site/*.test.mjs`, `python3 -B -m unittest discover -s deploy/local -p 'test_*.py' -v`.
При добавлении Next обнови документированные команды и выполняй сборку,
проверку типов и обязательные тесты фактического проекта.
Для временных данных задай абсолютный существующий TMPDIR текущей машины.
На этой машине используй `$HOME/storage/tmp/`, на VM установи доступный
путь отдельно. Сохраняй сырые логи и секреты вне Git.

## 11. Условия завершения и отчёт

Передай реализованный код сайта, migrations/lockfile, пример серверной конфигурации,
инструкции сборки/запуска/обновления/отката, согласованный план с результатами
и отчёт приёмки без секретов. Организуй независимое итоговое ревью и устрани
подтверждённые замечания в согласованном объёме.

Технические решения выбирай по текущей задаче. Используй штатные plugins,
существующие deployment/import/backup средства и минимальную достаточную схему.
Оплата, личная память, запись диалогов, универсальный OAuth Provider и новая
репликация KB остаются вне согласованной задачи.
Существующий общий ключ старых клиентов сохраняется до отдельной команды
владельца об отключении. Уведомление пользователей и его production отзыв
не выполняются как побочный эффект регистрации или публикации KB.

Покажи отдельно результаты source tests, настоящей Better Auth/DB интеграции,
двух Dock и Desktop/CLI e2e, затем готовность rollout. Для каждой невыполненной
проверки запиши конкретную причину и необходимые входные данные.
При внешнем блокере заверши всю независимую реализацию и проверки, сохрани
короткую точку продолжения. Успех локальных fixtures не означает production PASS.
Нативные Windows/macOS проверки хранения/proxy Agent сохраняют собственный gate.
