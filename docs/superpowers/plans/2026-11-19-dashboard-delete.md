# План реализации удаления дашборда из чата

> Для исполнителя. Использовать `executing-plans` для последовательной работы или `subagent-driven-development` для независимых проверок. Каждый следующий тест писать после прохождения предыдущего цикла RED → GREEN.

**Цель.** По разовому запросу из Desktop или CLI удалить все публикации узла и черновик текущего профиля. При неизвестном результате на сервере сохранить черновик.

**Архитектура.** Общий инструмент `dashboard_delete` читает привязку чата и запрашивает согласие. Хост передаёт проверенную операцию в авторизованный FileStorage. Агент убирает локальные файлы и запись предпросмотра только после заключительного чтения. Существующий издатель сам замечает исчезновение публикаций.

**Стек.** Bun/TypeScript, Effect, управляемый Node/Chromium, FileStorage Loginom, интерфейс разрешений Solid и терминал standalone CLI.

**Спецификация.** [Принятый дизайн](../specs/2026-11-19-dashboard-delete-design.md). База `dashboard-app@42d2152bbf`, рабочая ветка `dashboard-delete`.

**Оценка изменений.** Около 30 файлов, 1400 добавлений и 80 удалений по `git diff --stat`, включая тесты и документацию.

## Общие условия

- Работать по доверенной привязке пакета, сценария, узла и подключения. Модель передаёт только `{}`. Удаление ограничено данным узлом, локальная часть — текущим профилем. Историю чата и `.lgp` сохранять.
- Каждое согласие относится к точному набору имён и хешей. Число в интерфейсе служит только для показа. Сервер принимает только `once`, в том числе для пустого набора, и не применяет сохранённый `allow` к этому запросу. Оба клиента должны отказывать по умолчанию до подключения своего явного подтверждения.
- Не создавать сервис, таблицу, очередь, общедоступный файловый API или кнопку Studio. Использовать существующий издатель и приватный канал хоста. Временные данные проверок — в выделенном `$TMPDIR` вне Git. Для пакета dashboard подготовить Node и Chromium по [инструкции модуля](../../../packages/dashboard/AGENTS.md).
- Каждую команду тестов выполнять **из указанного пакета**. В конце каждого зелёного этапа проверить staged diff, выполнить из корня `bun run secrets staged` и сделать тематический коммит.

- [ ] В приватном контракте адаптера добавить `dashboardVersions(input, signal?)` и `dashboardDelete({ ...input, expected }, signal?)`. Здесь `input` — существующий `DashboardOperation`, `expected` — отсортированные `PublicationRef[]`. Возвращать список ссылок без исходников. Минимальная схема результата удаления:

  ```ts
  type DeleteResult =
    | { status: "empty" }
    | { status: "changed"; remaining: readonly PublicationRef[]; confirmedRemoved: number }
    | { status: "failed"; reason: string; confirmedRemoved: number; remaining?: readonly PublicationRef[] }
  ```

  `empty` означает подтверждённое чтением отсутствие публикаций. `changed` означает обнаруженное конкурентное изменение. До первого удаления `confirmedRemoved` равен нулю; затем учитываются только собственные успешные ответы FileStorage. Исчезновение имён при итоговом чтении само по себе счётчик не увеличивает. `failed` передаёт через хост известную причину и подтверждённый прогресс, `remaining` присутствует только при успешном чтении. Для `reason` использовать закрытый перечень кодов хоста (отказ доступа, занятость, недоступность или неизвестный исход) с проверкой на границе IPC. Если весь ответ потерян, хост сообщает неизвестный исход без числа.
