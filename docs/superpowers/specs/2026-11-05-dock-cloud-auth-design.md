# Подключение Loginom AI Agent к облачному и своему Dock

Дата: 2026-11-05. Ветка: `dock-cloud-auth`, база: `loginom` (`dd2f949d11`).
Статус: согласованные продуктовые решения; техническая редакция после проверки
замечаний P1–P3. Повторное независимое ревью Host, Dock и auth — Approved,
2026-11-05; ревью уточнений proxy/диагностики/отзыва — Approved, 2026-11-06.
Это подтверждение документа, не работоспособности ещё не написанного кода.

## 1. Результат и границы

Desktop и самостоятельный CLI получают два режима: облачный вход через loginom.ai
и свой сервер с адресом и ключом администратора. Новые сборки не содержат общего
ключа Dock. Облако использует персональную пару ключей пользователя и резервный
сервер. Повторный вход нужен после выхода или подтверждённого отзыва, а не из-за
простоя, сетевого отказа или окончания обычной веб-сессии.

Это каноническая спецификация Agent/Dock и внешнего контракта сайта. Реализация
и отдельный план сайта относятся к `$HOME/storage/git/loginom-ai-site`.
Здесь сайт не изменяется. Канонические исходники Dock — `services/loginom-ai`.
Личная память, запись диалогов, оплата, универсальный OAuth-сервер, сетевой proxy
и фоновый health-check не добавляются. Существующие данные не удаляются.

Пользователь уточнил 2026-11-05: **mcp-reserve.loginom.ai ещё не существует**;
его создадут отдельным от primary инстансом. Требования к его изоляции и публикации
знаний определены в §9; действующий резерв и его синхронизация не предполагаются.

## 2. Принятые решения

| Вопрос | Решение |
| --- | --- |
| Сайт | Next.js + Better Auth. Сейчас сайт статический, действующих аккаунтов нет. Next.js не предоставляет готовую регистрацию; Auth.js с самостоятельным хранением credentials потребовал бы больше прикладного кода. |
| Первичный вход | Один Device Authorization для Desktop/CLI, без отдельного Desktop callback/deep-link. |
| Долгое подключение | Отзываемый бессрочный ключ loginom.ai на установку, независимый от веб-сессии; не огромный TTL обычного OAuth refresh token. |
| Dock | Одна персональная пара на пользователя, общая для его установок. Два независимых реестра; новая установка не ротирует пару. |
| Обычное отключение | Удаление локальных ключей и отзыв ключа этой установки на сайте без смены общей пары. |
| Отзыв ранее выданного доступа | Дополнительно меняются оба Dock-ключа. Это не блокировка потерянного компьютера и не запрет новой регистрации; границы гарантии — §6. |
| Миграция | Новые версии требуют входа; старый ключ временно работает для 0.3.9. Новых переходных сборок со встроенным ключом нет. |
| Возврат с резерва | После успешного перехода оставаться на резерве до следующего запуска приложения. |

## 3. Интерфейс, сохранение и CLI

Вверху настроек Loginom — «Подключение к Loginom AI», radio «Облачный сервер»
(по умолчанию) / «Свой сервер», переключающие карточки. Ниже остаются URL,
логин и пароль самого Loginom: это отдельное подключение.

Облако: до входа — «Подключиться»; во время — код, ссылка, срок ожидания и отмена;
после — аккаунт, состояние и «Отключиться». Состояние показывает резерв, временную
ошибку либо необходимость входа. Кнопки «Обновить подключение» нет.
Повторный запуск входа при сохранённом облачном подключении отклоняется до
обращения к сайту, в том числе при выбранном своём сервере. Для смены аккаунта
сначала выполняется «Отключиться», затем новый вход; лишний ключ установки
поверх действующего не создаётся. Незавершённую попытку без подключения можно
отменить и начать заново.
Своя карточка: MCP endpoint и скрытое поле ключа администратора. Для своего
сервера нет cloud refresh/failover; его запросы не уходят в облако. Допускаются
поддерживаемые HTTP(S) endpoint без credentials в URL; облачные адреса — HTTPS.

Вход сохраняет cloud credentials сразу, но не применяет черновой выбор режима.
Radio и свои endpoint/key применяются штатным сохранением. Переключение режимов
не стирает credentials другого режима. Закрытие формы отменяет незавершённый вход
и черновик; уже завершённые вход/выход сохраняются. Запоздалый ответ отменённой
попытки не меняет состояние.

**Настройки Loginom можно сохранить до облачного входа.** Для cloud без credentials
проверяются локальная корректность полей и правила сохранения; недоступный Help
не запрещает сохранение. Результат — сохранённые настройки с `connection-required`,
а не ложный `ready` или ошибка сохранения. Browser verification остаётся отдельным
состоянием `unknown/verified/failed`. Сохранение cloud-настроек без входа само
не запускает браузерную проверку. Явная кнопка «Проверить» может проверить Loginom
через браузер независимо от Dock; результат показывается отдельно и не превращает
Help в `ready`. Отсутствие такой проверки не мешает сохранить настройки; правила
подтверждённого cleanup после уже запущенной проверки сохраняются.
Для подключённого cloud и своего сервера
сохраняются существующие проверки кандидата и защита рабочего поколения при их
ошибке. Это узкое исключение, не отказ от проверок всех настроек.

Смена Loginom-настроек создаёт поколение по существующим правилам. Вход и
восстановление Help меняют готовность **того же** поколения (§7); пересохранение
настроек и перезапуск после входа не требуются. Browser-задачи не переигрываются.

CLI использует существующие команды управления Loginom. Операции входа — короткие
`start/status/cancel`: Host опрашивает сайт до срока device code, CLI читает статус,
а не держит один management-запрос дольше нынешних 180 секунд. Ctrl+C отменяет вход;
profile guard удерживается до подтверждённого закрытия Host. Отсутствие браузера
не мешает показать ссылку/код для другого устройства. Профили Desktop/CLI независимы.
Секреты не попадают в argv или обычный вывод; свой ключ поступает через скрытый
prompt либо stdin JSON. Management status и model diagnostics различаются (§5).

При `connection-required` headless run и automation preflight завершаются с
подсказкой выполнить `loginom connect` до запуска модели. TUI на старте предлагает
вход также при уже сохранённом поколении, используя тот же Host и удерживаемый
profile guard. Отказ позволяет продолжить обычный чат; действия Loginom требуют
готового Help. Отдельный connect из другого терминала при открытом TUI заблокирован
эксклюзивным профилем: для позднего входа нужно выйти из TUI, выполнить connect
и открыть TUI снова. Межпроцессное разделение профиля не вводится.

Утверждённый макет: `$HOME/storage/tmp/dock-cloud-auth-preview/`.
Это иллюстрация; воспроизводимые требования заданы этим разделом.

## 4. Первичный вход и регистрация

1. Host получает device code и показывает пользовательский код. Открывает в
   системном браузере полную ссылку loginom.ai; перепечатывать код не требуется.
2. Пользователь входит или регистрируется. Регистрация выдаёт доступ сразу,
   без подтверждения email и ручного одобрения администратора.
3. Страница показывает **текущий аккаунт**, возможность его сменить, приложение
   и код. Пользователь сверяет код и явно разрешает/отклоняет подключение.
   Наличие веб-сессии не означает автоматического подтверждения устройства.
4. Host соблюдает interval, slow_down, expiry и отмену. Device code остаётся
   секретом Host, в интерфейс передаётся только пользовательский код.
5. Standalone Better Auth Device Authorization выдаёт полноценную временную
   сессию. Host держит её только в памяти и использует для обмена на ключ
   установки и Dock-пару. Сайт погашает точную bootstrap-сессию как при успешном
   обмене, так и при его терминальной ошибке; клиент при отмене после получения
   токена также запрашивает её отзыв. Не гасится браузерная сессия подтверждения.
   При сетевом обрыве/падении клиента мгновенный удалённый отзыв не гарантирован:
   остаточный доступ ограничен обычным серверным сроком сессии. Штатный плагин
   не даёт отдельного bootstrap-only срока/полномочий. Для подтверждённого
   погашения через `revokeSession` передаётся сырой token полученной device-сессии;
   запрос аутентифицируется этой же сессией, не браузерной сессией подтверждения.
   В v1.7.17 `{ status: true }` сам по себе не доказывает удаления: такой ответ
   возвращается также для отсутствующего токена или сессии другого пользователя.
   Положительный результат трактуется с указанной привязкой target и текущей
   сессии; ошибка удаления не скрывается. Один `signOut success` также не является
   доказательством погашения. Дополнительное чтение после отзыва не обязательно.
6. Cloud credentials сохраняются отдельной записью (§7). Ошибочный, отменённый
   или устаревший результат не заменяет действующее подключение.

К email/паролю добавляются нынешние обязательные поля анкеты: имя, фамилия,
телефон, профессиональный статус и согласие на обработку данных. Отчество,
компания, должность и согласие на новости необязательны. Пароль обрабатывает
Better Auth. Старая анкета не является аккаунтом и не доказывает владение email;
при регистрации она заполняется один раз, не при каждом подключении установки.

Основа — Better Auth `deviceAuthorization`, `bearer`, API Key plugin. OAuth
Provider/JWT/Electron plugins здесь не требуются. Совместная работа, точный
контроль bootstrap-сессии и серверный отзыв проверяются при отдельной реализации
сайта; одной документации плагинов недостаточно для объявления интеграции готовой.

## 5. Credentials, API и сетевые границы

Веб-сессия живёт по политике сайта. Временная device-сессия нужна только для
обмена. Бессрочный ключ установки разрешает получение Dock credentials и свой
выход. Два Dock-ключа принадлежат пользователю, используются его установками
совместно и меняются при отдельной ротации/отзыве. ROOT/ADMIN ключи в агент не попадают.

Сайт сам связывает стабильный ID Better Auth с USER на каждом Dock. Клиент не
задаёт account/user/role. API Key проверяется **в отдельной конфигурации**
`agent-installation` и только вместе с активной серверной записью подключения,
которая связывает ID ключа, пользователя и состояние доступа. Действующий ключ
другой конфигурации или без такой записи не разрешает получение пары. API keys
не создают обычные веб-сессии (`enableSessionForAPIKeys: false`).
Записью подключения может служить сама запись ключа выделенной конфигурации,
если все такие ключи создаёт только доверенный endpoint; отдельная таблица
соответствий сама по себе не требуется.

Общие HTTP endpoints `/api-key/create`, `/api-key/update`, `/api-key/delete`,
`/api-key/get`, `/api-key/list`
закрываются через **точный список** `disabledPaths`, без неработающего wildcard.
Серверные `auth.api.*` остаются способом внутреннего управления. Список сверяется
с закреплённой версией плагина. Самоотзыв делает наш серверный endpoint по активной
записи подключения, например server-only `updateApiKey(enabled:false, userId)`;
он не предполагает вызов session-only `deleteApiKey` с ключом установки.
Лимит установки задаётся явно: 60 проверок в минуту, не default 10 за 24 часа.
Проверка ключа выполняется один раз на запрос; лимит количества использований
`remaining` отключён. Наши маршруты не наследуют автоматически HTTP/CSRF-защиту
`auth.handler`: границы origin, допустимые методы и ограничение частоты публичного
первичного входа проверяются в отдельной реализации сайта.

Первичная выдача, восстановление, ротация и отключение согласованы на пользователя.
Любой endpoint выдачи, включая GET сохранённой пары, проверяет active binding
и снимает пару в той же сериализованной секции; после ожидания проверка выполняется
заново. GET, начатый до отзыва, не может прочитать новую пару после него по старой
проверке ключа. Уже снятый до отзыва снимок может дойти позднее, но смена пары
инвалидирует его ключи. Вторая одновременная установка получает сохранённую пару;
конфликт «пользователь уже существует» не является причиной новой ротации.
Сайт сохраняет выданный ключ до успешного ответа. При частичной ротации возвращает
для каждого Dock его действующий ключ, а не старый снимок целой пары. Отзыв остаётся
частичным до инвалидации обоих старых ключей. Потеря ответа Dock требует сверки
или восстановления под той же сериализацией, без выдачи заведомо устаревшего ключа.
Не привязываем постоянный deterministic seed к пользователю: повтор с тем же seed
не меняет ключ. Способ восстановления операции — часть отдельного плана сайта.

Минимальный внешний контракт:

| Операция | Доступ и результат |
| --- | --- |
| `POST /api/auth/device/code`, `/api/auth/device/token` | Штатный Better Auth, публичный `client_id: loginom-ai-agent` |
| `POST /api/agent/connections` | Временная сессия в Bearer; `{ installationKey, user: { email }, dock: { primary: { apiKey }, reserve: { apiKey } } }` |
| `GET /api/agent/dock-credentials` | Ключ установки в `X-API-Key`; `{ dock: { primary: { apiKey }, reserve: { apiKey } } }` |
| `DELETE /api/agent/connections/current` | `X-API-Key`; `204` после отключения записи подключения и ключа |

Все значения в успешном ответе — непустые строки. Не нужные клиенту ID остаются
на сервере. Первая выдача успешна только с полной действующей парой. Невалидный
или неполный ответ не заменяет сохранённую пару. Потеря ответа первоначального
обмена может потребовать новой попытки входа, но не автоматического бесконечного
создания установок. Схема БД и код маршрутов здесь не проектируются подробно.

Только корректный `{ error: { code: "access_revoked", message } }` от нашего API
подтверждает отзыв и требует удалить cloud credentials. Сервер выдаёт его при
доказанном отключении записи/ключа/аккаунта, не при любом `verifyApiKey.valid:false`:
плагин может так представить внутреннюю ошибку. `credentials_unavailable` и
`service_unavailable`, HTTP 429/5xx, неструктурированные 401/403 от proxy/CDN,
HTML и невалидный JSON сохраняют credentials и возвращают временную/протокольную
ошибку. `Retry-After` соблюдается. Logout завершается локально и без удалённого успеха.

Release cloud endpoint фиксированы: `https://loginom.ai`,
`https://mcp.loginom.ai/mcp`, `https://mcp-reserve.loginom.ai/mcp`.
`LOGINOM_AI_AGENT_KNOWLEDGE_ENDPOINT` и `manifest.endpoint` не переопределяют
cloud адрес. Для unit fixtures допускается явная инъекция зависимости; для
staging — **один build-time набор site/primary/reserve только в нерелизной сборке**,
с отдельным тестовым профилем. Релиз отказывается от такой подмены; обычный
runtime env её не включает. Ответ сайта не перенастраивает адреса. Каждый секрет
уходит только своему адресату, все credential-bearing запросы используют
`redirect: 'error'`.

Для HTTP-запросов Host к сайту и Help к Dock выбирается вариант А, совместимый
с [system proxy v2](2026-09-23-system-proxy-v2.md): **только явно заданные proxy
переменные окружения и системные CA**. При отсутствии явного proxy запросы идут
напрямую. OS/PAC resolver и автоматически обнаруженные настройки backend сюда
не переносятся, в том числе для CLI management. Системный resolver по-прежнему
обслуживает только области, определённые v2. Chromium Loginom сохраняет
`--no-proxy-server`.

Это целевая единая политика, а не утверждение готовности существующих transports.
Help получает proxy environment, включая уже заданный `NODE_USE_ENV_PROXY`, но
одна передача `HTTP(S)_PROXY` ещё не доказывает применения proxy стандартным MCP
transport. Desktop main имеет собственную инициализацию CA/explicit-env proxy;
Host CLI и Help работают в отдельных Node-процессах с `--use-system-ca`.
При реализации нужно обеспечить применение явного environment выбранным
HTTP-клиентом с учётом `NO_PROXY`, без системного resolver, и подтвердить это
для site и Help короткой проверкой на Windows/macOS. Недоступный явно выбранный
proxy не обходится прямым запросом. Проверку TLS не отключаем; область системного
proxy v2 и браузерный маршрут не расширяем.

Management status для renderer/CLI содержит режим, email, сервер, готовность,
безопасную ошибку и pending login `{ userCode, verificationUrl, expiresAt }`.
В нём нет `device_code`, session/API/Dock ключей. `dock_diagnostics` получает
**отдельную** проекцию: существующие несекретные поля Loginom View (`revision`,
`generation`, `url`, `username`, `folder`, `hasPassword`, `state`, `browser`,
`failure`, `recoveries`) плюс режим, выбранный Dock и готовность Help. Диагностика
подключения Loginom сохраняется; новые cloud email, пользовательский код и ссылка
входа в модель не передаются. Не возвращать модели расширенный management status
целиком: одна и та же безопасная проекция используется в текстовом результате
и `structuredContent`. Секреты не пишутся в URL, transcript и логи. Сохранённые ключи
не возвращаются renderer; вводимый свой ключ временно находится в поле формы.

## 6. Выход и отзыв ранее выданного доступа

«Отключиться» немедленно отменяет ожидающие auth/refresh, удаляет локальные cloud
credentials и закрывает Help-подключение облачного профиля. Host ограниченно
по времени запрашивает отзыв ключа установки, но локальный выход завершается
и без сети с сообщением «удалённый отзыв не подтверждён». Ключ ради фоновой
очереди не сохраняется. Свой сервер, другие установки, данные и браузерная
веб-сессия остаются нетронутыми. Уже отправленный запрос нельзя отозвать задним
числом. Browser runtime не перезапускается; новые Help-вызовы требуют входа.

Отдельный отзыв установки блокирует её серверную запись и ключ сайта, затем
меняет оба Dock-ключа. Остальные установки получают новую пару без повторного
входа. Отзыв пользователя блокирует все его существующие подключения и так же
меняет оба Dock-ключа, чтобы сохранённые ключи установок перестали работать. Удаление
пользователя Dock не используется, поскольку удаляет данные. Если один Dock
недоступен, старый ключ этого сервера ещё может действовать; завершение отзыва
нельзя объявлять до инвалидации обоих ключей.

**Граница гарантии:** отзываются ранее выданные credentials. Оставшаяся на потерянном
компьютере веб-сессия или известный пароль позволяют снова подтвердить новый вход.
Защита от этого требует отдельно завершить веб-сессии и при необходимости сменить
пароль; автоматический logout всех браузеров не добавляется к согласованному
обычному выходу. Термин «полный отзыв» не означает бессрочную блокировку устройства.
Блокировка аккаунта не препятствует регистрации другого аккаунта: открытая
регистрация без подтверждения email принята пользователем и сохраняется.

## 7. Host, готовность и единственный remote клиент

`createLoginomHost` владеет cloud credentials, выбранным endpoint, текущей попыткой
Help, ревизией credentials и общей выполняющейся операцией refresh. **Все семь
удалённых чтений продукта проходят через Help child.** Browser child в managed
`user-v1` имеет bundled action catalog; сейчас он обращается к Dock только при
startup initialize/tools-list, а дальнейший remote маршрут недостижим из HostPort.

Убираем этот ненужный remote startup **только из managed user-v1**: browser child
не получает Dock key, не подключается к Dock и не читает remote tools/diagnostics.
Локальные действия и каталог сохраняются. Остальные classic/standalone/non-bundled
режимы bridge не переделываются. Требования горячей замены remote transport в
browser и нового IPC child → Host удаляются.

Help child возвращает классифицированные ошибки через существующий request/reply.
Host выбирает ключ/endpoint, выполняет refresh и заменяет только Help-подключение
существующими Host → child операциями. Закрытие Help не закрывает browser child,
поколение или его leases. Одновременные отказы ожидают одну попытку восстановления;
уже выполняющиеся чтения получают результат либо отмену/повтор в своём исходном
дедлайне. Локальные изменяющие действия никогда не переигрываются.

**Готовность Help изменяема внутри поколения:**

- `connection-required`: cloud без credentials; Help с пустым ключом не запускается.
- `starting`: одна общая текущая загрузка каталога.
- `ready`: каталог текущей ревизии успешно получен.
- `recoverable-error`: временный отказ последней попытки, а не окончательный rejected promise.

Успешный вход, новые credentials и следующий запрос после временной ошибки могут
запустить одну новую попытку и обновить readiness того же поколения. Это касается
не только `call`, но и `tools`, explicit `ready/check` и допуска lease: retry должен
быть доступен **до** нынешнего `phase === ready` gate. Отсутствие credentials
возвращает `connection-required`. Успех очищает только ошибку Help, не browser
verification и не ошибки cleanup. Результат старой попытки/поколения игнорируется.
Фоновых циклов и сетевых проверок перед каждым успешным запросом нет.

Cloud credentials хранятся отдельной изменяемой записью вне неизменяемых поколений
настроек Loginom; нынешний payload `{apiKey,password}` нельзя просто переиспользовать
как пару Dock + site key. Используется существующая платформенная защита с новым
явным payload. Desktop Linux **сейчас хранит plaintext**, с закрытым каталогом и
ограниченными правами файла; это не fallback. Windows/macOS Desktop — safeStorage,
CLI — существующие DPAPI/Keychain и отдельный Linux формат. Нового шифрования и
синхронизации профилей не добавляем. Выход/отзыв удаляет также запись на диске.

## 8. Отказы, retry и резерв

| Ситуация | Действие |
| --- | --- |
| Новый запуск cloud Host | Сначала primary с его ключом |
| Transport timeout/сеть/502/503/504 primary | Попробовать reserve с его ключом; повторять только Help-чтение |
| Reserve ответил успешно | Зафиксировать reserve до следующего запуска; новое поколение настроек его не сбрасывает |
| Оба Dock недоступны до успешного перехода | Сохранить credentials, не фиксировать неработающий reserve; следующий допустимый запрос восстанавливает Help, начиная с primary |
| Уже выбранный reserve временно недоступен | Сохранить выбор reserve; следующая попытка работает с ним, без автоматического failback |
| Dock 401 | Один общий refresh, затем повтор на том же Dock; 401 не повод для failover |
| После refresh тот же ключ снова отклонён | Ошибка доступа к Dock без logout; подавить повторный refresh этой ревизии на 30 секунд, затем разрешить по новому запросу |
| Dock 403/429/ошибка аргументов/инструмента | Вернуть ошибку, не обходить через резерв |
| Сайт недоступен/невалидный ответ | Сохранить credentials; действующий Dock работает, refresh даёт временную ошибку |
| Подтверждённый `access_revoked` сайта | Удалить локальные cloud credentials, отменить Help/auth/refresh, `connection-required`; перезапуск не возвращает ключи |
| Отказ Loginom/browser-задачи | Существующая обработка, без смены Dock и повтора действий |
| Отказ своего сервера | Без cloud refresh/failover |

После неудачной/неизменившей ключ попытки refresh действует короткий demand-only
cooldown, общий для той же ревизии; новые credentials снимают его сразу. HTTP429
учитывает Retry-After. Запрет refresh навсегда «до изменения локальной ревизии»
не подходит: новые ключи невозможно было бы получить. Таймер фонового refresh
не создаётся; после cooldown запрос пользователя может восстановить подключение.

Все попытки расходуют **один исходный deadline Host-вызова**, включая startup,
refresh, смену Help и retry. Обычная отдельная remote read-попытка ограничена
60 секундами; совокупная работа должна уложиться в исходный IPC budget120с,
а внешний budget180с не даёт каждому retry новые180с. Timeout каждой следующей
операции ограничивается оставшимся временем родительского вызова. Так после
60с primary для восстановления остаётся лишь остаток общего бюджета; после
его исчерпания повтор не начинается. Initial primary connect использует до
15 секунд в пределах общего бюджета. На запрос — максимум один refresh и один переход на резерв,
без умножения вложенными retry. Отмена прекращает ожидания. Недоверенный сертификат
не лечится отключением TLS и не трактуется как разрешение сменить политику доверия.

## 9. Область знаний, серверные права и будущий резерв

Персональные USER создаются в account общей KB (`loginom-dock` в bootstrap).
На официальном дереве `viking://resources/loginom-dock` включаются ACL и read
`user:*`; эффективные grants потомков также проверяются. Без grant resources
сейчас доступны на запись, а общие `agent/skills` вообще не покрыты resource ACL.
Поэтому whitelist имён Help-инструментов и ACL одной папки недостаточны.

**Минимальное решение для продукта:** ограничить все managed Help-вызовы корнем
`viking://resources/loginom-dock` в общем knowledge-клиенте перед отправкой:

- `find/search`: отсутствующий `target_uri` заменяется корнем; разрешены только
  он и потомки. `search` поддерживает только `mode: list`; `context` не допускается,
  поскольку не поддерживает target_uri и собирает дополнительные общие области.
- `read`: проверить каждый элемент `uris` до отправки всего вызова.
- `list/tree/grep/glob`: `uri` только внутри KB; отсутствующий у tree/glob заменяется
  корнем. Glob pattern относительный, без `..`, абсолютного пути и URI.
- Проверять границу сегмента, canonical URI и traversal, не строковый prefix:
  `loginom-dock-evil` не потомок KB. Неоднозначные разделители/алиасы отклоняются.
  Инструментальная схема и описание должны отражать эту область.

Ограничение действует в продуктовых режимах cloud/custom; собственный сервер
должен публиковать совместимую KB по тому же пути. Параметр произвольного корня
не добавляется. Прямое чтение вне KB запрещено, а не только исключено из поиска.
Глобальная модель ACL OpenViking здесь не меняется: USER всё ещё может иметь
права вне KB при прямом обращении к Dock, но такие данные не должны попадать
через Help в другие экземпляры Agent. Официальная KB защищается серверными ACL.
Это не утверждение, что любой текст KB безопасен для модели.

Сайт хранит ADMIN **всего account**, а не узкую capability выдачи ключей. ADMIN
имеет manage на KB; при соответствующем режиме хранения может читать ключи
пользователей. Взлом сайта поэтому угрожает всем пользователям и знаниям account.
ROOT для обычной выдачи в существующем account не нужен. Admin endpoint задаётся
серверной конфигурацией, не клиентом. Доступность admin API извне и настройка
`allow_private_networks` в production не проверены; при разрешённом URL-import
USER это также граница SSRF. Проверка этих настроек относится к развёртыванию,
а ограничение Help само по себе не защищает прямые HTTP API Dock.

Будущий reserve имеет **отдельные volume, реестр аккаунтов/пользователей и ключи**.
Одна и та же версия источников KB публикуется отдельно в оба инстанса через
существующие Assets/catalog/import средства с собственными credentials и Assets
State. URI и ACL должны совпадать. Новая репликация не нужна; текущие скрипты
потребуют привязки к deployment нового инстанса, они ещё не готовая команда резерва.

Штатный backup архивирует весь data volume, включая
`/local/_system/accounts.json` и `/local/{account}/_system/users.json`.
**Полный primary backup нельзя восстанавливать поверх reserve с независимыми
ключами и использовать для синхронизации KB.** Каждый сервер восстанавливается
из собственной копии с учётом последующих отзывов; иначе могут воскреснуть старые
ключи. Раздельность реестров и публикация KB являются исходными условиями плана
создания reserve. Рабочая конфигурация primary, ACL и сам будущий reserve ещё
не проверены вживую; их приёмка обязательна перед выпуском облачного входа.

## 10. Миграция и все потребители встроенного ключа

Новая сборка не читает/упаковывает `knowledge-key`, не подставляет build-time
`LOGINOM_MCP_API_KEY` и не использует его как fallback. При обновлении сохраняются
URL/логин/пароль Loginom, профиль и чаты. Запись без режима трактуется как cloud
без входа (`connection-required`); старые сохранённые `apiKey` не становятся
ключами своего сервера. После входа Help становится ready без пересохранения.

Автоматические evals и node acceptance используют explicit custom setup через
stdin JSON: `mode: custom`, `endpoint`, `apiKey` плюс прежние Loginom-поля.
Отсутствие `mode` означает cloud; отдельно переданный legacy `apiKey` не включает
custom и не даёт cloud доступ. Ключ не попадает в build/env продукта или argv.
Harness может читать свой секрет существующим приватным способом и отправлять
его в stdin; универсальные прямые Dock-клиенты не переписываются механически.

Изменение охватывает Host, `stage-resources.ts`, `build-cli.ts`, Desktop
`bundle-loginom.ts`, release CI, harness `scripts/node-acceptance/run-check.py`,
его tests/run-check.md, `evals/src/profile.ts` и `evals/test/profile.test.ts`,
`shutdown-validation.mjs`, fixtures Host/CLI. Полный список групп — §12.
Обновляются также App/Host/Desktop connection AGENTS и активные runbooks;
исторические отчёты не переписываются как будто новая реализация существовала раньше.

Старый ключ временно остаётся на серверах для 0.3.9. Добавление USER/ACL не должно
его ротировать. Этот ключ фактически публичен из старого дистрибутива; сервер
не отличает 0.3.9 от другого клиента с его копией. Отзыв ключа после уведомления
пользователей — отдельная операция эксплуатации; дата здесь не назначается.
Соответствие настоящего бинарника 0.3.9 текущей базе ещё не проверено.

## 11. Поведенческие проверки и условия готовности

TDD: один failing тест поведения → минимальная реализация → упрощение на зелёном
тесте → следующий сценарий. Документ не означает выполненных тестов. Покрытие:

1. Обновление 0.3.9 сохраняет Loginom-настройки, показывает необходимость входа;
   вход делает прежнее поколение ready без save/restart. Первый запуск позволяет
   сохранить Loginom-настройки до входа без автоматического browser check;
   явная проверка браузера независима от Help и не объявляет его готовым.
2. Оба Dock недоступны на старте → восстановление при следующем запросе без
   перезапуска, в том числе через tools/ready/lease gates. Один concurrent retry;
   старый результат не меняет новую готовность.
3. Managed user-v1 browser запускается без сети Dock и без Dock key, сохраняет
   локальный каталог/действия; remote поддержка других режимов не сломана.
4. Device flow Desktop/CLI: успех, отказ, expiry, slow_down, отмена/закрытие формы,
   CLI ожидание дольше180с, Ctrl+C и profile guard; model diagnostics сохраняют
   существующие несекретные поля View, исключают cloud email/коды/ссылки/секреты.
   Bootstrap-сессия отзывается с raw token той же authenticated session; один
   status:true для отсутствующего/чужого токена не доказывает удаления.
5. Две установки одновременно впервые входят и получают одну пару; обычный
   logout одной не меняет её. Offline logout удаляет локальную запись, сообщает
   о неподтверждённом отзыве; запоздалый refresh не возвращает ключи.
6. Startup/runtime Help failover использует правильный key; резерв закрепляется
   после успеха, переживает смену поколения и сбрасывается новым Host. Обе неудачи
   не закрепляют неработающий резерв. Browser-действия не повторяются.
7. 401 вызывает singleflight refresh; тот же отвергнутый key не создаёт шквал
   запросов, после cooldown восстановление возможно. 403/429/ошибки сайта и
   malformed/HTML не удаляют credentials; explicit access_revoked удаляет и на диске.
   Retry/refresh укладываются в исходный deadline, отмена не теряется.
8. На реальном тестовом Dock два USER: A создаёт agent/skills/x и resources/x,
   managed find/search/read/glob/list/tree/grep B их не возвращают и не читают;
   context mode, traversal, чужой URI и смешанный read-массив отклоняются.
   Официальную KB оба читают, USER не изменяет/удаляет её и не вызывает admin API.
9. Первичная выдача/частичная ротация/потеря ответа сохраняют согласованные ключи;
   старый отозванный key отвергается. Чужая API-key config и ключ без активного
   подключения не дают пару. API key rate limits и exact disabledPaths проверены.
   При отзыве пользователя блокируются все установки и ротируются оба Dock-ключа.
10. Release отвергает cloud endpoint override и не содержит общего ключа;
    staging tuple доступен только нерелизной сборке с отдельным профилем.
    Credentials не следуют redirect. На Windows/macOS site и Help проверяются
    с явным proxy environment, `NO_PROXY` и доверенным системным CA; недоступный
    явный proxy не обходится напрямую. Без явных переменных OS/PAC proxy не
    подхватывается этими клиентами. Проверка не расширяет области system proxy v2
    и не меняет прямой маршрут Chromium Loginom.
11. Evals/node acceptance получают custom endpoint/key через stdin и работают
    без embedded resource. Миграция legacy apiKey не включает custom автоматически.
12. Два независимых Dock получают одну KB, разные keys; повторная публикация KB
    не меняет их реестры. Существующая web session после отзыва может разрешить
    новый вход — это проверенная граница обещания, а не заявленная блокировка устройства.

Локальный HTTP fixture проверяет клиентский контракт, но не Better Auth. Перед
выпуском нужен полный Desktop/CLI вход со staging-сайтом и двумя Dock, включая
одновременные установки. Пока сайт и reserve не реализованы, cloud вход не готов
к выпуску. Продуктовый код на стадии этой спецификации не изменяется.

Тесты запускаются из package dirs, typecheck — `bun typecheck`, не прямой tsc.
Изменение публичного Protocol/HttpApi требует штатной генерации packages/client.
Временные файлы — `$HOME/storage/tmp/`. Fixture Dock с жёстким
`test_data/tmp_server` надо направить туда; одного TMPDIR недостаточно.
