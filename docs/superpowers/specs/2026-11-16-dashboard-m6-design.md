# Dashboard M6: эксплуатация и ревью

Статус: дизайн согласован владельцем 16 ноября 2026 года; независимое ревью — Approved, обязательных замечаний нет. По ревью проверка read-only назначена master, а отказ без доступа — release 7.4.2 с учётом результата S1. Реализация M6 не начата. Основание — [roadmap M6](2026-11-11-dashboard-architecture-roadmap.md#m6-эксплуатация-и-ревью) и [требования изоляции](../../security/dashboard-isolation.md).

## Результат и зависимость от M5

Администратор видит значимые события публикации, сборки и нарушения защиты, может остановить службы dashboard и проверить защиту установленной поставки. M6 завершён, когда обязательные замечания независимого ревью устранены либо явно приняты владельцем, нарушения тестовых приложений видны в журнале, читатель не может заменить чужой dashboard и строгий режим принят на реальном HTTPS-стенде.

Планирование выполняется во время M5. Срез исходников для исследования — `004a74be52`; это **не** база реализации M6. В чате продолжения M5 на момент подготовки подтверждены принятие Task 4 и выполнение Task 5. Локальный checkpoint ещё содержит более раннее состояние. Перед реализацией нужно взять итоговый принятый M5, закрепить его SHA и артефакты в runbook M6 и сверить карту файлов. M6 не продолжает незавершённые задачи M5 и не выбирает заново версии Docker/Podman.

Канонические входы: [дизайн M5](2026-11-15-dashboard-m5-design.md), [план M5](../plans/2026-11-15-dashboard-m5.md), [приёмка M5](../../testing/loginom-ai-agent/dashboard-m5.md). Проверенные результаты переиспользуются, если относятся к той же поставке или к неизменённым компонентам; исходниковая проверка не считается установленной приёмкой.

## Решения владельца и рассмотренные подходы

1. Общий выключатель — `stop/start` служб. Новые загрузки и сборки прекращаются; уже открытые dashboard пользователь закрывает сам. Принудительное закрытие вкладок, heartbeat и новый клиентский протокол не нужны.
2. Журналы оперативные: штатные логи контейнеров и существующая ротация `10m × 3`. Нет гарантии истории за определённое число дней или сохранения после пересоздания контейнера. Нужные журналы администратор выгружает до `stop`, обновления или разбора сбоя.
3. Состав этапа: ограниченные журналы publisher/web/CSP, проверка существующих лимитов, выключатель и целевая установленная приёмка безопасности после M5.

| Подход | Цена и ограничение | Решение |
|---|---|---|
| События в stdout существующих контейнеров, штатный просмотр/выгрузка | Минимальное изменение; глубина истории ограничена ротацией и жизнью контейнера | Выбран |
| Постоянный архив, переживающий пересоздание контейнеров | Дополнительные файлы, права, очистка и политика хранения; нужен для гарантированного срока истории | Не требуется |

## Журналы publisher и web

Одна запись — одна ограниченная JSON-строка с временем, ролью, типом события и разрешёнными полями. Достаточно небольшого общего форматтера/ограничителя для реально общих операций; новый logging framework, БД, служба, UI или внешний сборщик не нужны. События поступают в stdout контейнера, просмотр и экспорт выполняются средствами Docker/Podman.

Publisher пишет переходы состояний: обнаружение/принятие публикации, выдача задачи, отказ проверки или сборки, готовность и удаление. Для версии сохраняются относительный путь файла в UserStorage, ключ привязки, время, sourceHash (SHA-256 точных байтов файла публикации) и хеш результата, версия шаблона и образ builder. Поле появляется только когда оно действительно известно; повреждённый файл не получает вымышленный ключ или хеш результата. Версия шаблона — уже проверенное поле `template: 1`; точные байты определяет неизменяемый ID образа. Установщик получает этот ID штатным inspect и передаёт publisher через существующую конфигурацию compose; Docker socket в контейнеры не передаётся. Сохранённый ready после перезапуска не выдаётся за новую сборку текущим образом.

Повторный обход неизменённого файла не создаёт то же событие каждые 10 секунд. Существующий state publisher остаётся источником состояния; журнал не становится второй очередью, реестром или условием успешной публикации. Известный рабочий результат и прежняя версия сохраняются при отказе новой сборки. Ошибка вывода журнала не должна превращать уже готовую публикацию в failed или откатывать её.

Web пишет значимые отказы проверки Host/Origin, схемы/размера запроса и ошибки обработки; полный access log успешных запросов не нужен. Ошибка обозначается стабильным кодом и безопасными метаданными. Не записываются cookie, Authorization, snapshot ID, содержимое снимка/исходников, query/fragment, произвольные заголовки, полный URL, stack или сырые сообщения исключений. Пути публикаций относительные; диагностические выгрузки остаются вне Git и обезличиваются перед включением в отчёты.

Объём записи и частота событий, вызванных недоверенным вводом, ограничены. Ограничитель имеет конечную память, не создаёт накопление по произвольным IP/URL/ключам и сообщает числом о подавленных событиях. Точные небольшие пределы выбирает исполнитель по тестам и фиксирует рядом с кодом и в runbook; это ограничения журналирования, а не изменение разрешённых размеров публикаций или таблиц. Потеря части диагностических событий при потоке нарушений обозначается явно; полноценный аудит каждого запроса не обещается.

## CSP и отчёты браузера

Существующий `POST /_reports`, предельный размер тела 64 КиБ и блокирующие заголовки сохраняются. Вместо записи сырого тела обработчик разбирает известные формы CSP/Reporting API, выбирает допустимые поля и выдаёт безопасное событие. По document URL собственного app-origin извлекаются только проверенные ключ и хеш сборки; неизвестный или поддельный адрес не становится доверенной привязкой. Директива, тип нарушения и disposition берутся из ограниченного набора значений. Неизвестное/повреждённое сообщение даёт ограниченную запись об отказе без исходного тела.

Не сохраняются URL назначения, referrer, script sample, исходный код, IP или произвольный текст браузера. Транспорт публичный: запись показывает полученное заявление, но не доказывает личность отправителя. Проверка использует настоящий браузерный отчёт и отдельный отрицательный пример с искусственными чувствительными строками.

Принятые ограничения M2 сохраняются: нативная доставка CSP проверяется через `report-uri`; доставка `Connection-Allowlist` reports зависит от конфигурации браузера и не гарантируется. Такие отчёты обрабатываются при поступлении, но блокировку сетевого канала проверяют поведением, а не отсутствием/наличием записи.

## Лимиты и выключатель

M6 проверяет уже существующие ограничения вместо введения общих пользовательских квот:

- одноразовые снимки: 100 записей, 15 минут, запрос до 640 КиБ, образец до 512 КиБ;
- публикация: до 1 МиБ и 200 файлов; результат сборки до 20 МиБ;
- одна серверная задача сборки за раз, 90 секунд, ограниченная диагностика;
- конечные память/PID/tmpfs контейнеров, ротация журналов;
- существующие размеры таблицы, время ready и частота сообщений iframe.

Фактические значения сверяются с принятым M5. Пределы не меняются ради успешного прогона. Проверки должны показывать корректный отказ, сохранение прежней публикации и работоспособность обычного примера после нарушения. Автоматическое удаление пользовательских JSON или живых версий ради дисковой квоты не добавляется.

В release переиспользуются `containers.sh stop/start`: stop удаляет собственные контейнеры без данных, start создаёт их из сохранённой конфигурации. В исследованном M5 Podman cron выполняет `compose start`, поэтому удалённые stop контейнеры при reboot не воссоздаются; это поведение нужно сохранить и проверить на итоговой базе. Для dev-master достаточно остановить/запустить три уже установленных контейнера по проверенным ID/owner-меткам: их конфигурация и `unless-stopped` сохраняются, новый state не нужен. Повторный compose up с начальными настройками dev-скрипта для этого не подходит — он может сбросить strict/CLI-настройки.

Остановка прекращает работу собственных трёх служб и сохраняется при перезагрузке; запуск восстанавливает их с прежними настройками. UserStorage, публикации и `.lgp` сохраняются. Studio остаётся работоспособной при недоступном dashboard. Выключатель не рекламируется как отзыв уже переданных браузеру данных.

## Независимое ревью и установленная приёмка

Ревью охватывает цепочку модель → профиль сессии/подтверждение → закрытый Host → ACL Loginom → publisher/builder → web → sandbox/MessagePort. Проверяются текущие границы, а не весь репозиторий. Ревью проводит отдельный агент, не реализовавший проверяемые изменения; внешний аудит человеком не является новым условием M6. Обязательное замечание содержит нарушенное требование, конкретный риск или воспроизводимый дефект. Опциональные улучшения не становятся условиями приёмки; принятие остаточного риска принадлежит владельцу.

Ручные попытки выполняются на собственном установленном release-стенде и тестовых пользователях/пакетах, с существующими вредоносными примерами и браузерным инструментарием. Проверяются доступ к Studio/credentials, запрещённые сетевые действия и навигация, подмена/повтор сообщений, чужая привязка публикации и результат сборки. Не создаётся отдельный фреймворк атак. Сырые данные и credentials в Git не попадают.

Строгий режим: отдельный регистрируемый домен и TLS из M5, закреплённый Chromium 152+ с положительной пробой, нормальный dashboard с живыми данными и попытки нарушения; браузер без поддержки с включённым WebRTC отвергается до расчёта/передачи данных. Сверяются фактические заголовки и процессная изоляция. Ранее принятые ограничения пробы WebRTC и доказательства DNS/preconnect остаются явно обозначенными; отрицательный тест с исправным каналом наблюдения не подменяется отсутствием ответа неисправной мишени.

Многопользовательская матрица учитывает фактические права Loginom. На master автор публикует, а второй пользователь с read-only доступом к общей папке открывает разрешённый пакет, но получает отказ записи/замены авторского JSON. На release 7.4.2 разделение чтения и записи общей папки недоступно (результат S1 roadmap): здесь второй пользователь без доступа к защищённой папке получает отказ записи. Попытка поместить JSON с чужой binding в свою writable папку проверяется на обоих стендах и отвергается publisher. Новая ACL-система не вводится; успех release с правом записи не выдаётся за проверку read-only. До/после сравниваются байты защищённых публикаций, `.lgp` и текущая сборка. Учётные записи и браузерные сессии действительно разные; изменение одного имени в запросе не считается проверкой прав.

Общая браузерная безопасность принимается на одной release-установке; Docker и rootless Podman отдельно подтверждают новые эксплуатационные свойства (журналы, ротацию, stop/start, сохранность). Полная повторная матрица M5 не нужна без изменений или нового риска. Dev-master проходит описанную проверку read-only/подмены и smoke изменённого выключателя/доставки журналов.

## Проверки, документы и границы

Любые изменения кода выполняются вертикально RED → GREEN → REFACTOR через существующие поведенческие тесты. Сохраняются package-local `bun typecheck`, `bun run test`, `bun run test:browser`, `bun run check:size`, действующие пороги покрытия web и publisher/builder, существующие CI-задания; shell-изменения проверяются `bash -n` и ShellCheck. Тесты документации не создаются.

План реализации хранится отдельно в `docs/superpowers/plans/2026-11-16-dashboard-m6.md`. При реализации создаются runbook M6 и checkpoint не более 20 строк; owning AGENTS, roadmap и разделы isolation обновляются вместе с поведением. Исторические отчёты M2/M4/M5 не переписываются как новая приёмка.

Не входят: постоянный архив, мониторинг/алерты, квоты пользователей, новая аутентификация, изменение протокола приложения, принудительное закрытие вкладок, расширение браузерной матрицы, поддержка native Linux, выпуск или слияние. Дальнейшую реализацию этот документ сам по себе не запускает.
