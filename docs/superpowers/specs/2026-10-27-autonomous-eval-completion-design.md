# Завершение автономной eval-кампании

Согласовано владельцем 27.10.2026: подчистить существующую `autonomus-eval`,
сохранить controller и обязательные гарантии, сократить вызовы EvalOps.
Финальный результат обязательно публикует отдельным ответом EvalRunner.

## Результат

После окончания измерений служба сохраняет и публикует проверенный итог,
выключает периодическое наблюдение за прогоном и адресно поручает исполнителю
дать отдельный итоговый ответ. Доставка архива продолжается независимо.
`published=true` и `in_review` означают подтверждённую доставку архива и
наличие отдельного ответа назначенного исполнителя, а не только наличие
машинного комментария. Полный и частичный результаты различаются явно.

## Существующие границы

- Controller, journal, controller lock, native leases, process/storage cleanup,
  missing-only resume и judge recovery остаются. Новых runtime dependencies,
  scheduler, watchdog и реестра инцидентов нет.
- Исторические результаты, manifest/pins, сроки, verdict и receipts не
  переписываются. Quality FAIL не повторяется ради PASS.
- Изменения касаются кода/тестов `evals/` и необходимой документации. Внедрение
  на runner, изменение живых правил Multica и новые модельные измерения сюда
  не входят.
- База интеграции — `loginom`; текущие изменения upstream сохраняются.

## Завершение и отдельный ответ исполнителя

1. После terminal outcome служба выполняет прежнюю проверку очистки. Полный
   результат не объявляется при неподтверждённой очистке; частичный сообщает
   это ограничение. Сохраняются количество измерений, PASS/FAIL, покрытие,
   причина partial и состояние ресурсов.
2. Итог публикуется до загрузки архива и читается обратно. В нём явно
   разделены итог измерений и состояние доставки. Отсутствие архива не
   скрывает готовый результат.
3. Машинный итог одновременно является единственным адресным поручением.
   `manifest.executor` разрешается через `GET /api/agents` в ровно одного
   агента; его ID сохраняется в `executorAgentId` до POST. Неоднозначность
   блокирует поручение, сохраняя результат. Trigger-preview подавляет всех
   агентов кроме этого исполнителя. Новое поручение помечено отдельным
   `<!-- eval-handoff:CAMPAIGN -->`; `reportCommentId` хранит его ID.
   Исполнитель отвечает отдельным комментарием с точным
   `<!-- eval-executor-final:CAMPAIGN -->`, итоговыми числами, состоянием
   cleanup и архива. Принимается только `author_type=agent`,
   `author_id=executorAgentId`, `parent_id=reportCommentId`; ID сохраняется
   в `executorResponseCommentId`. Машинный отчёт/поручение ответом не считаются.
   Обновление attachment не вызывает новое поручение.
4. Повторный tick/restart находит уже опубликованный итог, поручение и ответ
   по campaign marker/ID. Потеря ответа HTTP не вызывает слепой повтор
   публикации. Во время работы controller lock не позволяет параллельные
   dispatch. Существующая инфраструктура Multica выполняет агентскую задачу;
   controller не изображает ответ EvalRunner.
5. После прочитанного итога выключается периодический wakeup только этой
   кампании. Событийное правило остаётся для технического ремонта доставки
   или порученного финального ответа. После полного read-back архива и ответа
   выключаются остальные собственные правила и выставляется `in_review`.
   Чужие правила не затрагиваются. Неудачный disable повторяется идемпотентно.
6. Архив загружается и проверяется прежним download/hash. Ошибка доставки
   сохраняет результат и точную безопасную категорию ошибки. Наличие
   машинного комментария больше не означает, что архив уже доставлен.

Существующие идентификаторы report/attachment используются повторно;
добавляются только данные, необходимые для идентичности поручения и ответа.
Старый `published=true` принимается без новых полей и повторного запуска.
Исторический внешний partial без нового handoff-маркера сохраняет прежний
терминальный путь: немедленно останавливает admission/наблюдение, не требует
архива с недоступного хоста и не переоткрывает измерения. Это совместимость
уже опубликованного старого протокола, а не ответ EvalRunner. Новые snapshot
partial создают обычный адресный итог по сохранённым данным и локальному
snapshot-архиву и требуют отдельного ответа исполнителя; возврат основного
хоста усваивает этот partial, не начинает измерения и не подтверждает cleanup.

## Реже запускать EvalOps

Штатные batches ведёт служба. EvalOps вызывается существующим событием
блокера/native delegation failure. Периодический fallback при подготовке
новой кампании — раз в 7200 секунд; здоровый прогон не требует комментария
о каждом batch. Standing/wakeup инструкции берутся из одного runbook.
Изменение interval уже действующих правил требует штатной установки,
которая не является частью локального исправления ветки.

## Подчистить ветку

- Один текущий runbook, ссылка из `evals/AGENTS.md`, пометка главного старого
  плана как истории. Датированные evidence и незавершённый LAB-170 сохраняются.
- Вернуть существующее исправление optional import bytes/hash с его
  поведенческими тестами; неверные переданные значения остаются ошибкой.
- Убрать неиспользуемый предварительный inventory, сохранив обязательную
  проверку cleanup receipt и архивирование истории.
- Закрыть ранний `wait` принадлежащего кампании batch, обходящий no-progress
  срок. Никакой новый admission после срока; cleanup не подтверждается
  фиктивно для ещё работающего batch.
- Не переписывать controller и не вырезать специальные recovery proofs.

## Проверки

upload не скрывает итог/поручение и не оставляет periodic включённым;
повтор/restart не дублирует поручение; машинный/чужой ответ не закрывает
кампанию; ответ правильного исполнителя закрывает её только вместе с
проверенным архивом; чужие wakeups сохраняются; HTTP outage не теряет
результаты; partial/старые published сохраняют корректную семантику.
