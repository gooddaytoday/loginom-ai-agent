# Исправления контекста и inline-вложений после PR #32

База: `f9bf332cc491baa784e6e04fdfda7c0f09151cb7`, ветка `loginom`.
Назначение владельца: устранить обе подтверждённые регрессии review в новом worktree.

## Решение

1. Суммаризация пользовательского сообщения разделяет обычный текст и синтетический контекст.
   Обычный текст имеет лимит 2000 символов, каждая synthetic TextPart — отдельный лимит 2000.
   Короткое задание и ссылки на несколько snapshots не вытесняются
   preview, независимо от порядка частей. Ignored-части исключаются; описание файлов сохраняется.
2. Обрезанный inline `data:text/plain` получает bounded preview и абсолютный путь к полному
   декодированному тексту в существующем `tool-output`. Cache имеет детерминированное имя
   `tool_attachment_<sha256>` и пользуется существующими разрешениями Read/Grep.
   Исходные data URL и filename остаются в user file-part для original-user Loginom admission.
3. Стандартная очистка tool-output через семь дней сохраняется. Перед модельным выполнением
   snapshots восстанавливаются из всех original user file-parts сессии, включая сообщения,
   исключённые компактацией. SQL-запрос выбирает только URL текстовых user-вложений, чтобы
   не загружать старые assistant/tool outputs. Данные сессии остаются каноническим источником.
   Маленькие inline-вложения не требуют cache-файла. Существующий cache не перезаписывается,
   но его mtime обновляется при обращении, чтобы cleanup не удалил активный snapshot.
   Новые snapshots публикуются атомарно, включая параллельные обращения к одинаковому тексту.
   Materialization/touch и cleanup stat/remove используют общий process-local semaphore,
   чтобы очистка не удаляла snapshot по устаревшему mtime во время обращения к вложению.
   Схема URL проверяется тем же WHATWG parser, что и первичное разрешение вложений.
4. Путь и подсказка чтения идут перед каждым preview, чтобы независимый лимит синтетического
   контекста сохранял доступ к snapshot при компактации.

## Альтернативы и ограничения

- Возврат полного inline-текста увеличивает модельный контекст и отменяет назначение PR #32.
- Ссылка на случайный `Truncate.write` без восстановления перестаёт работать после cleanup.
- Бессрочный `attachment_` обход cleanup создаёт сироты после удаления сессии.
- Явные пользовательские запреты Read/Grep продолжают действовать.
- Перенос исторической сессии на другой профиль или компьютер не входит в эту правку.
- Новые public Protocol/HttpApi контракты и Loginom-runtime не меняются.

## Приёмка

- Команда после CSV preview >2000 символов видна суммаризатору; лимиты контекста сохраняются.
- Ignored-части исключены, несколько вложений не вытесняют обычный текст.
- Модель получает путь к точному full snapshot, а не полный data URL; хвост читается через Read.
- Cache переживает параллельные обращения; обновление срока хранения согласовано с cleanup.
- Cache восстанавливается после удаления перед resume, в том числе для compacted history.
- Восстановление принимает те же варианты регистра/whitespace схемы URL, что и initial prompt.
- Исходные data URL/filename сохраняются, небольшое вложение остаётся точным.
- Проверки выполняются из packages/agent: focused regressions, затронутые session/util/tool suites,
  bun typecheck и git diff --check. Installed Desktop/Loginom acceptance отдельно не выполняется.
