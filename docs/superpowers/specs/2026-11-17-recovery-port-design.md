# Выборочный перенос browser recovery в loginom

Статус: требования согласованы 17 ноября 2026 года. Сейчас готовится только документация; реализация, создание карточек Multica, запуск evals, публикация и слияние в этот этап не входят.

## Цель и исходные версии

Перенести полезные решения из `recovery-build-flag`, сохранив архитектуру и рабочие гарантии текущего `loginom`. Под browser recovery здесь понимаются браузерные действия самого агента после отказа обычного сценарного инструмента, а не ручное вмешательство человека.

| Назначение | Версия |
| --- | --- |
| База новой ветки `recovery-port` | `loginom` / `origin/loginom`, `ae89c43b57b98decde1ef287e01dc501d0da495f` |
| Источник отдельных решений после rebase | `recovery-build-flag`, `1ab348a91d7c8ae180744293ff746f859d49145a` |
| Исторический прогон для дополнительного сравнения | LAB-1747, продукт и harness `ae149d3f13277c1e3d4c0775e83d8ce2e6fbb13b` |
| Источник зафиксированного корпуса LAB-901 / LAB-1747 | `29ea34e27b8f96ed27b744f639c9f48933f52443` |

Ветка создана после повторного fetch `loginom`. Дальнейшие изменения базы не включаются молча: до сборок пересматриваются затронутые контракты, после начала сравнения версии остаются неизменными.

## Согласованный подход

Выбрана адаптация поведения к существующим контрактам. Полная замена recovery-контроллера несёт обнаруженные регрессии; перенос только мелких исправлений не решает проверку результата и жизненный цикл. Поэтому каждое решение проходит собственный цикл: доказанный пробел → поведенческий тест → минимальное изменение → проверки соседних контрактов → независимое ревью.

Если поведение уже реализовано в базе, этап фиксирует доказательство и не добавляет дубликат. Изменение общего контракта требует доказанной необходимости, проверки всех потребителей и согласования по правилам проекта. Смена формата ради сходства с донором не считается пользой.

### Что переносить и проверять

| Направление | Полезное поведение | Что сохранить или дополнительно проверить |
| --- | --- | --- |
| Экспорт: ссылки UI | Брать ref пункта из свежего наблюдения открытого списка | Не повторять совершённый жест; сохранять владельца и исходный deadline |
| Экспорт: файловое хранилище | Дождаться отрисованного окна FileStore, использовать пригодные anchors, сохранять причину отказа | Привязки к папке, документу, workflow и вкладке; предел прокруток; ошибка диагностики не стирает результат |
| Допуск recovery | Распознавать повторный одинаковый отказ после завершённой обычной попытки и неоднозначное исполнение | Не разрешать replay при неизвестном транспортном исходе, отмене, upload или уже завершённом эффекте |
| Завершение recovery | Подтверждать новое собственное исполнение, выходные схемы и спокойное состояние графа | Собственный operation receipt, исходная цель, точный ACK и неопределённый исход; схема не доказывает правильность значений |
| Контекст агента | Сохранять `_meta` при успехе и ошибке; привязывать напоминание к актуальной задаче | Ограничения вывода, отмену, compaction/revert, поздние ответы предыдущей задачи |
| Жизненный цикл | Освобождение принадлежит runtime; устаревшие queued-вызовы не оживляют попытку; учитывается стоимость finish | Не создавать вторую копию состояния в Host; уведомление не равно cleanup; бюджет и lease остаются ограниченными |

Из `loginom` обязательно сохраняются проверка страницы **до первого браузерного действия**, наличие исходной подготовленной вкладки, тот же авторизованный браузерный контекст, permissions, отмена и владение операцией. В доноре первые две проверки ослаблены, поэтому его controller нельзя копировать целиком.

Отдельно решается `NO_BASELINE`: отказ в configure/open ещё не даёт базы для проверки исполнения. Recovery не должен возвращать агента к тому же сломанному configure и не должен объявлять успех без независимой проверки. Нужен ограниченный путь проверки уже восстановленного узла с привязкой к исходному заданию; если доказательств недостаточно, результат остаётся неподтверждённым.

Другой случай — не подтверждён ранний эффект создания/связывания целевого узла. Тихий граф и доступный UI не заменяют точный ACK в `node-target.mjs`. Проверять владение частичным узлом и receipts; не обходить неопределённость повторным созданием, кликом или ослаблением ACK. Если перенос этого не решает, указать доказанное ограничение. После допустимого продолжения сохранить существующие узлы, связи и единственность выхода, когда её требует задача.

Не переносить автоматически терминальную остановку на любом browser `isError`. Различать подтверждённый отказ без эффекта и неизвестный исход. Сохранять доказанный безопасный путь повторного наблюдения; неизвестное действие не повторять. Один текст `Ref not found` или `page.ok` не является универсальным доказательством отсутствия эффекта.

У `loginom` уже есть feature flag, private capability, allowlist, изображения, основные лимиты, Save/export recovery и ACK. Их наличие не записывать в новые достижения. Изменение boolean-флага на строковый формат само по себе не нужно.

## Диагностика каждого построения

Использовать существующие источники: `events.jsonl`, `stderr.txt`, `run.json`, архив профиля с БД/WAL/SHM и `tool-output`, runtime-журнал, `.lgp`, результирующие файлы, oracle и вывод судьи. Короткие receipts в `run.json` не заменяют полный вывод инструмента. После подтверждённого cleanup история каждой попытки архивируется вне доступных агенту mounts.

Проверить самую раннюю границу потери текста: `browser-recovery.mjs` обрезает суммарный текст ответа до 46000 байт ещё до contributor, а action journal содержит только его тип и размер. Ответ длиннее лимита должен оставаться доступным в существующем закрытом архиве до этой обрезки, с действующим redaction. Сначала проверить другие имеющиеся источники; при их отсутствии добавить сохранение в этой точке одинаково для B/C. Лимит текста, передаваемого модели, не увеличивать.

Основные точки интеграции: `evals/src/process-supervisor.ts`, `profile.ts`, `diagnostics.ts`, `analytics-measurements.ts`; со стороны продукта — CLI events, session history, tool contributor и execution journal. Переиспользовать `recoveryToolsCovered` / `auditMeasurement` там, где их контракт подходит. Специализированный `run-analytics-measurements.ts` целиком не использовать: его judge и параметры серии отличаются от согласованного сравнения.

`recoveryToolsCovered` проверяет допустимость конкретной цепочки, а не полноту любых логов: полностью записанный unknown/transport failure тоже может не пройти эту проверку. Разбор полноты учитывает достигнутую фазу отдельно от исхода. Отсутствующий журнал и журнал с честно зафиксированным неопределённым результатом — разные факты.

Для каждого измерения нужен индекс с ключом `(version, case_id, round)`. Его технические попытки различаются по `attempt_id`; повтор не увеличивает число запланированных измерений. Сохраняются фактические model/variant, source/artifact/harness/catalog hashes, session ID, ссылки на архивы, результат, время, токены/расходы и полнота evidence. Для попыток, не дошедших до сессии или пакета, отсутствие этих объектов отмечается явно.

Для каждого эпизода recovery индекс связывает исходный отказ, обычные попытки восстановления, решение о допуске, `start`, браузерные действия, `finish`/проверку, возврат к Dock или остановку. Ключи связи: session, runtime, operation, recovery attempt и tool call; сохраняются фаза, причина, цель, временные отметки, outcome и ownership/cleanup. Использовать существующие поля, добавлять только отсутствующую связь.

Различать факты:

1. Recovery запрошен или отклонён.
2. `start` завершился и был передан контроль.
3. Выполнено хотя бы одно браузерное действие.
4. Runtime выдал исход проверки: `continuable`, `completed` или `unresolved`; сохранить фактический status.
5. Всё построение прошло oracle/судью.

Успешное построение после `start` не доказывает, что recovery исправил ошибку. Отдельно показывать stop/cancel, исчерпание бюджета, неопределённую операцию и недостаток данных. Построения без recovery также должны иметь прослеживаемую цепочку.

Отдельные оси отчёта: полнота evidence, verification status, состояние исходной операции, качество итогового артефакта, CLI status/exit и cleanup. `continuable` означает возможность продолжения, а не доказанный успех исходной операции. `pass=true` у артефакта и `exit=1` у CLI могут сосуществовать по текущему контракту harness; это само по себе не ошибка судьи или recovery.

Если создан скриншот, сохранять файл и его hash, tool/message ID и факт включения изображения в исходящий запрос модели. Создание файла и передача модели — разные события. Подтверждение отправки не означает доказательство того, как модель интерпретировала изображение. Не делать дополнительных браузерных жестов только ради логирования; не сохранять скрытые рассуждения или секреты провайдера.

При связывании изображений учитывать основу hash: текущий `describeContent.sha256` вычислен от base64-строки, а `bytes` — от декодированного изображения. Не сравнивать этот digest напрямую с SHA256 файла PNG и не менять молча смысл существующего поля.

Одинаковая диагностика применяется к обеим сборкам. Если нужны продуктовые изменения только для наблюдаемости и управляемых тестовых сбоев, они образуют отдельный проверенный слой до функциональных переносов; контрольная версия честно обозначается `loginom + общая диагностика/acceptance`. В обычных evals тестовые инъекции отключены. Harness и анализатор также закрепляются одинаково. Новые наблюдения не меняют prompt, tools, retries или критерии результата.

## Проверка на управляемых сбоях

До основных кампаний провести небольшую отдельную серию на установленных сборках с `gpt-6.1-terra/high`. Она проверяет восстановление и полноту evidence, а её оценки не включаются в 876 обычных измерений.

Покрыть сбой настройки до execution baseline, отказ повторного скриптового шага после обычного восстановления, неоднозначное исполнение, экспорт/файловое хранилище и Save. Отдельно проверить отрицательные переходы: неверная/закрытая исходная вкладка, отмена, неизвестный жест и исчерпание бюджета. Дешёвые отрицательные проверки выполняются существующими runtime/Host тестами; реальные модельные попытки нужны для проверки доступности tools, доставки изображений и продолжения работы агента.

Использовать существующий private acceptance путь и fixtures. В базе нет готовых hooks для всех нужных сбоев: минимальные недостающие точки подготовить одинаково для обеих версий до фиксации контрольного SHA. Новый общий fault framework не нужен. Инъекция ограничена назначенными операцией/фазой, помечена в evidence, не меняет oracle и не попадает в основную кампанию. Отсутствие естественного recovery в обычных evals не заменять скрытой инъекцией.

## Основное сравнение

Общие неизменные условия:

- Оцениваемый агент: `openai/gpt-6.1-terra`, reasoning `high`.
- На каждую версию: **146 кейсов × 3 раунда = 438 измерений**; вместе **876**.
- Один frozen корпус LAB-901 / LAB-1747: одинаковые prompts, inputs, references, rubrics, oracle, индивидуальные timeouts и порядок кейсов.
- Судья: `gpt-6-sol/xhigh`; порог 70; judge timeout 300000 мс. Узловые code-oracle проверки сохраняются.
- Одинаковые CLI mode, provider/service tier, model catalog, настройки tools и browser recovery, environment/runner slots, judge и политика технических повторов.
- Только установленный CLI, изолированные профили и действующая bubblewrap-граница. Harness, корпус, чужие результаты и эталоны агенту недоступны.
- Quality FAIL окончателен. Судейский повтор использует сохранённый артефакт; технический повтор не скрывает исходную попытку и не обнуляет счётчики.

До запуска закрепить хэши обеих сборок, общего harness/анализатора и корпуса, реальное наличие Terra в каталоге, разрешённые слоты, лимиты попыток/времени и план хранения. Возможность выбрать модель в CLI не заменяет фактические model/variant в истории. Использовать существующий campaign controller и его preflight, не писать новый scheduler и не добавлять отдельный прогрев модели.

Полные архивы хранить вне Git с действующим маскированием секретов. По предварительной серии оценить объём для 876 измерений с резервом на допустимые технические попытки и незавершённые архивы. Существующий disk guard должен действовать до нового admission. Сбой вспомогательного анализа не стирает подтверждённый результат; неизвестный cleanup или неархивированная история запрещают следующую попытку в том же слоте.

LAB-1747 использует `xhigh` и другую ревизию продукта/harness, поэтому это дополнительное историческое сравнение. На момент исследования в карточке учтено 390 из 438 измерений: 352 PASS / 38 FAIL; полный архив не проверен. В финальном анализе перечитать фактический завершённый ledger, сопоставлять только валидные совпадающие ключи, явно указывать различия условий. Не выводить эффект переноса из сравнения high с xhigh.

## Отчёт и решение о переносе

Результат анализа: таблица всех 876 запланированных ключей с фактическими статусами и ссылками на доказательства; сравнение 146 кейсов по трём раундам; разбор каждого recovery-эпизода; причины всех ухудшений и технических пропусков. Отдельно показывать качество, время, токены/стоимость, технические отказы, долю пригодных архивов и неизвестные исходы. Неизвестную стоимость не подменять нулём; три раунда не считать строгим доказательством причинности.

По каждому переносу дать рекомендацию: оставить, исправить или исключить — с конкретным поведением, evidence и ограничениями. Не вводить произвольный общий процент улучшения как новый порог приёмки. Слияние в `loginom` остаётся отдельным решением владельца.

## Работа через Multica

Каждый этап плана исполним отдельной карточкой: цель, зависимости, точный входной SHA, область файлов, действия, проверки, независимое ревью, выходной SHA/артефакты и критерий завершения. Карточка содержит ссылки на эту спецификацию и свой раздел плана; переписка не нужна для восстановления контекста.

Карточки с кодом последовательно продвигают одну ветку `recovery-port`. Один назначенный исполнитель владеет записью в ветку; следующему передаётся проверенный SHA. Read-only ревью может идти параллельно. Кампании используют закреплённые артефакты и собственные evidence, не меняют исходники во время измерений. Общие требования живут здесь; порядок, состояние этапов и checkpoint — в [плане](../plans/2026-11-17-recovery-port.md).
