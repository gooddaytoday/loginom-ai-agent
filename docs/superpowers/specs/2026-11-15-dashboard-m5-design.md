Статус: дизайн принят владельцем 15 ноября 2026 года. Независимая проверка завершена: вопросы о клиентской диагностике разрешены, обязательное замечание о порядке обновления закрыто. Подготовлен [пошаговый план](../plans/2026-11-15-dashboard-m5.md); владелец разрешил реализацию, Tasks 0–3 приняты. 16 ноября 2026 года владелец принял проверенные современные контейнерные стеки как нижнюю границу поддержки Dashboard; итоговый scoped gate Task 4 пройден: Spec ✅ / Quality Approved, mandatory 0. Начат только source/CI/build-context срез Task 5a; установленная приёмка Task 5 и весь M5 остаются открытыми.

Основа требований — [roadmap](2026-11-11-dashboard-architecture-roadmap.md), разделы M5 и «Скрипты для стендов». Публикация остаётся по [дизайну M4](2026-11-14-dashboard-m4-design.md). Текущее состояние M4 и границы её доказательств — [checkpoint](../../testing/loginom-ai-agent/dashboard-m4-checkpoint.md) и [runbook](../../testing/loginom-ai-agent/dashboard-m4.md). Исходную точку реализации выбирают после принятия M4; документационная ветка не заменяет её финальную продуктовую основу.

## Результат и границы

Администратор устанавливает dashboard рядом со штатной release-установкой Loginom 7.4.x под Docker или rootless Podman. Установленный Linux Desktop на другой ОС подключается по HTTPS: пользователь создаёт черновик, подтверждает публикацию и открывает dashboard в минифицированной Studio `/app/`. CLI проходит перенесённые release-сценарии M4. Обновление Loginom сохраняет интеграцию; удаление dashboard оставляет Loginom и пользовательские данные работоспособными.

Владелец выбрал:

- отдельный release-установщик поверх компонентов M4;
- CA устанавливает администратор штатными средствами ОС и браузера, без управления сертификатами в интерфейсе агента;
- локальную QEMU/KVM VM с автономной подготовкой; Desktop остаётся на основной системе, Docker и Podman проверяются последовательно на чистых гостевых установках;
- пробную публикацию при **каждом** серверном `check`, с ожиданием результата и удалением своих тестовых данных;
- отдельную обязательную клиентскую проверку Studio и сетевого доступа после установки, обновления и изменения конфигурации Loginom.

Недопустимы изменение пользовательских `.lgp`, доступ web к ключу сертификата Studio, доступ web/builder ко всему серверному каталогу, ослабление изоляции приложения и объявление установленной приёмки по исходниковым тестам. Отказ установки или проверки не оправдывает удаление чужих контейнеров, публикаций либо очереди сборки.

За пределами M5: `native.sh`, переработка dev-установщика, новые функции dashboard, параметры в черновике, Windows/macOS installed-приёмка, новая политика прокси, собственное хранилище CA, автоматическое получение сертификатов, registry/автообновление dashboard, Kubernetes, изменения штатного установщика/compose/образов Loginom. Эксплуатационные функции и полноценная приёмка строгого режима остаются в M6; M5 предоставляет предусмотренные roadmap отдельный домен и TLS для этого режима. Слияние и выпуск не входят в реализацию этапа.

## Рассмотренные подходы

| Подход | Цена и ограничения | Решение |
|---|---|---|
| Отдельный `containers.sh`, готовый образ и release-конфигурация; сервисы M4 общие | Небольшое повторение команд развёртывания, зато не требуется менять действующий dev-стенд | Выбран владельцем |
| Общая система установки dev/release с двумя входными скриптами | Меньше дублирования, но переделка dev-установщика расширяет изменения и повторную приёмку M4 | Не выбран |

Общий helper появляется только для действительно используемой обоими путями операции; каталог `lib.sh` из эскиза roadmap сам по себе не требует извлечения кода. Нового сервиса управления, реестра установок или системы задач нет.

## Что уже есть и что нужно добавить

M4 уже содержит формат публикации, закрытую запись через Host/Studio, publisher, builder, `lookup`, откат и очистку сборок. Один [Dockerfile](../../../packages/dashboard/deploy/Dockerfile) собирает образ для трёх ролей. [Web](../../../packages/dashboard/src/web/server.ts) уже проверяет Host; [app host](../../../packages/dashboard/src/web/apps.ts) применяет заголовки и список origin Studio. Эти механизмы сохраняются.

Нынешний `dev-master.sh` ограничен выделенным Docker-стендом: HTTP/loopback, named volume UserStorage, два клиента и вставка script в `index.html`. Переносить эти предположения в release нельзя. Нужны release-скрипт и compose, сборка переносимого набора, вставка оболочки через Apache, TLS-переадресация, обнаружение фактических mounts/прав и проверка установленного пути.

## Поставка и команды администратора

Один архив Linux x64 содержит `containers.sh`, release-compose, необходимые файлы конфигурации/проверки, архив готового образа и контрольные суммы. Образ включает закреплённые Node, набор шаблона, сервер и оболочку. На целевом сервере не нужны checkout, Bun, npm или загрузка зависимостей; используются установленный движок/compose и обычные системные средства. Сложный разбор данных и проверки используют Node из поставленного образа, если shell/форматов `inspect` недостаточно. Версии берутся из существующих закреплений проекта, отдельный механизм pinning не вводится.

Образ загружается штатным `docker load`/`podman load`. Сборка и экспорт архива выполняются на машине подготовки поставки существующими инструментами. Публикация в registry и сборка образа на сервере не являются дополнительными путями установки M5.

Команды: `install`, `check`, `stop`, `start`, `uninstall`. Имя движка задаётся при неоднозначном выборе; остальные параметры ограничены требуемыми внешними адресами/портом, каталогом состояния и строгим режимом. Пользователю не предлагается вручную описывать обнаруживаемые mounts, UID или сеть. Точные флаги и сообщения выбирает исполнитель, сверяясь с интерфейсом roadmap.

`install`/`check` работают от владельца существующей установки Loginom: root для штатного Docker-варианта, тот же непривилегированный пользователь для rootless Podman. Через `inspect` и фактическую конфигурацию определяются контейнеры, сеть, mounts конфигурации Apache и серверного каталога, UserStorage, UID/GID Loginom, SSL, опубликованные и внутренние порты. Неоднозначное/неподдерживаемое размещение завершается понятным отказом до изменения Loginom. Скрипт не устанавливает и не перенастраивает Docker/Podman; это отдельная подготовка тестовой VM или работа администратора.

Состояние dashboard лежит вне каталогов Loginom, чтобы `setup.sh` не менял его владельцев. Для последующих команд сохраняется только конфигурация собственной установки, без Loginom credentials. Пути и имена проверяются на границе; конфигурация не исполняется как произвольный shell. Существующие данные или объекты, принадлежность которых не установлена, не перезаписываются.

## Apache и HTTPS

В Loginom добавляется один `dashboard.site.conf` в уже подключаемый каталог конфигурации Apache. Script с SRI вставляется в `/app/` посредством `mod_substitute`; исходный `index.html` и `client.json` не меняются, `/app-debug/` не создаётся. Оболочка раздаётся web по `/dashboard/shell.js` из установленного образа. `/dashboard/health` даёт минимальный ответ доступности web без внутренних путей и данных.

Файл конфигурации заменяется атомарно. Перед graceful reload выполняется `httpd -t`; при отказе возвращается прежний файл либо удаляется только что добавленный. Текст CSP, список origin и SRI строятся из проверенных настроек и фактически поставленной оболочки. Проверяются отсутствие двойной вставки, правильная работа gzip/br и отсутствие ответа 304 со старым SRI.

Схема TLS остаётся из roadmap: внешний app-порт принадлежит web; при HTTPS он пересылает зашифрованный TCP-поток в выделенный порт Apache, а Apache направляет HTTP в отдельный внутренний listener app host. Ключ остаётся только у Apache. Для HTTP-only установки app-порт обслуживается непосредственно web. TLS-переадресация ограничена настроенным Apache и не является произвольным proxy; ошибки и закрытие любой стороны освобождают парное соединение.

При включённом HTTPS app-origin всегда HTTPS, даже если Studio открыли по HTTP. Разрешённые `frame-ancestors` перечисляют оба фактически поддерживаемых origin Studio; принудительный `frame-src` допускает только app-origin. API web не становится доступным на app-origin. Сохраняются Host-проверки, sandbox, CSP, Permissions-Policy и отсутствие редиректов. Общий серверный каталог и TLS-ключи не монтируются в web.

В обычном режиме используется сертификат Studio. Для строгого режима администратор предоставляет отдельный домен, сертификат и ключ в каталоге конфигурации Apache; M5 проверяет настройку и доставку заголовков, но не объявляет завершённым ревью безопасности M6. Не получив `ready`, оболочка показывает понятную ошибку и предусмотренную roadmap ссылку на HTTPS Studio; отсутствие `ready` само по себе не доказывает ошибку сертификата.

## Права, сеть и жизненный цикл

Release-compose запускает те же три роли. Web/builder работают не от root, publisher получает права чтения фактического UserStorage без изменения прав пользовательских файлов. Publisher монтирует **только** UserStorage RO; `Users.cfg`, лицензии и каталог серверных ключей недоступны. Сохраняются отсутствие сети у publisher/builder, read-only root, drop capabilities, no-new-privileges и существующие конечные лимиты ресурсов.

Rootless UID mapping учитывается при подготовке собственных каталогов dashboard; контейнерный UID не принимается за UID хоста. На SELinux сохраняется работоспособность Loginom: нельзя наложить частную метку publisher на его хранилище. Используется решение roadmap для фактических меток (`ro,z` либо `label=disable` publisher при частной метке сервера); это проверяется на enforcing-среде, без глобального отключения SELinux.

Нижняя граница поддержки Dashboard — проверенные современные Docker/Compose и rootless Podman/podman-compose по [решению владельца от 16 ноября](../../testing/loginom-ai-agent/dashboard-m5.md#границы-поддержки-dashboard). Её подтверждают записанные реальные create/start/server/client проверки одного общего архива с RO/network/limits, а не только разбор YAML. Общие требования вендора Loginom остаются отдельными; исторические отказы более старых стеков сохранены в runbook. Непроверенные промежуточные и более новые версии не считаются прошедшими installed-приёмку. Это изменение политики поддержки, без нового version guard или compatibility-механизма.

`stop` останавливает собственный compose-проект и освобождает его подключения к внешней сети Loginom, сохраняя состояние и публикации. Простого `compose stop` недостаточно для последующего удаления сети Loginom; используется штатное удаление собственных контейнеров без удаления данных. `start` вновь создаёт их из сохранённой конфигурации. Docker использует restart policy; Podman получает только собственную строку автозапуска, чужой crontab сохраняется.

Порядок обновления Loginom: `stop` dashboard → штатное обновление Loginom → запуск Loginom → `start` dashboard → серверный `check` → отдельная клиентская проверка. После `setup.sh --change` также выполняются обе проверки; при смене обнаруженных параметров или сертификата серверный `check` сообщает о необходимости повторного `install`, а не продолжает считать старую конфигурацию исправной. После повторного `install` вновь нужны обе проверки. Безопасный повторный `install` и возврат прежнего Apache-конфига проверяются отдельно.

`uninstall` удаляет только собственные контейнеры, подключение Apache, запись автозапуска и состояние dashboard. UserStorage, JSON публикаций, `.lgp`, сеть/тома Loginom и его конфигурация не удаляются. Удаление образа — отдельный явно заданный выбор. После удаления проверяется открытие того же пакета без компонентов dashboard.

## Пробная публикация в каждом `check`

Каждый запуск создаёт собственный уникальный каталог вида `<check-name>.lgp.dashboards/<nodeGuid>/` внутри фактического UserStorage. Это синтетическая привязка: реальный `.lgp` не создаётся и не меняется. Текущий publisher проверяет совпадение физического пути с binding и формат JSON, а не наличие пакета. Данные проверки не содержат пользовательских строк; исходники — минимальное заранее известное приложение из комплекта поставки.

Check пишет готовый JSON через временный файл и rename внутри своего нового каталога. Доступ выполняется администратором установки, не процессом publisher; его mount остаётся RO. Уже существующее имя не принимается за собственный результат. Успех проверяется через Apache: `lookup` для точного имени и `sourceHash` возвращает `ready`, app-origin отдаёт именно полученную сборку и её ресурсы с ожидаемыми заголовками.

В обычном завершении, при отказе и при обрабатываемом сигнале удаляются только созданный JSON и собственные пустые каталоги. Затем проверяется отсутствие текущей публикации (`lookup` без поля `publication`) и недоступность старой сборки. Очистку state/builds выполняет существующий publisher; `check` не правит его state, не чистит jobs и не удаляет чужие сборки. Уже оставляемые publisher пустые каталоги ключей не считаются пользовательской публикацией; новый механизм GC ради проверки не вводится.

Ожидание конечно и учитывает существующие очередь, интервал обхода и время сборки. Занятый builder не прерывается ради проверки: при истечении срока результат — «проверка не завершена», а не ложный диагноз поломки. Неподтверждённая очистка возвращает неуспех и точное имя собственного остатка; подтверждённый результат сборки при этом сохраняется в отчёте. После принудительного завершения процесса или выключения машины автоматическая очистка не гарантируется; администратор может удалить только названный тестовый каталог. Постоянный реестр проверок и отдельный восстановитель не добавляются.

Такая проба доказывает цепочку UserStorage → publisher → builder → web и обработку удаления. Она не заменяет проверку прав Loginom, подтверждения пользователя, private Host, Desktop/CLI и живой таблицы узла; эти сценарии остаются обязательной установленной приёмкой.

Остальная диагностика следует roadmap: HTTP/HTTPS, заголовки и SRI, модуль Apache, сертификат и предупреждение о сертификате из поставки, настройки контейнеров/томов/сети, режим, SELinux и автозапуск. Ошибка обязательной проверки или неполный результат не выдаётся за успех. Сертификат проверяется без `-k`, `ignoreHTTPSErrors` или отключения верификации TLS.

### Отдельная клиентская проверка

Решение владельца: авторизованная проверка адаптера Studio и доступности app-порта с клиентской машины выполняется отдельно от серверного `check`. Это явное уточнение roadmap: серверная пробная публикация остаётся обязательной при каждом запуске, а две клиентские проверки обязательны после установки, обновления и изменения конфигурации Loginom, в том числе в приёмке M5.

Серверный успех не выдаётся за подтверждение клиентского пути. Клиентский прогон использует существующий браузерный инструментарий и приватную конфигурацию оператора; `deploy/check-studio.mjs` служит исходной реализацией проверки адаптера. Проверяются настоящая установленная оболочка, объекты адаптера в `/app/` и открытие опубликованного dashboard по HTTPS с клиента. Проверка не подставляет shell через `addScriptTag` и не собирает собственную оболочку вместо установленной. Зависимости браузерной пробы остаются на клиентской машине; на сервер не добавляются Chromium, Loginom credentials или служба координации. Инструкция фиксирует оба отдельных результата; общий SSH-оркестратор не создаётся.

## CA и установленный клиент

Администратор заранее устанавливает тестовый частный CA в штатные хранилища ОС и браузера клиентской машины. Пользовательское приложение не импортирует CA, не хранит его отдельно и не отключает проверку сертификата. Проверяются все реальные пути: браузер Studio и iframe, получение снимка Desktop, запросы backend/CLI и Chromium закрытого Host.

Существующие `--use-system-ca` и загрузка системных CA переиспользуются; исправляется только доказанный отсутствующий путь доверия. Политика сети не меняется: runtime Chromium обращается к Loginom напрямую, Node/Electron сохраняют действующую политику proxy/NO_PROXY. Сертификат, который доверен одному компоненту, не считается автоматически проверенным в остальных. Недоверенный CA, неверное имя и просроченный сертификат должны оставаться отказами; соответствующие проверки выполняются на собственных тестовых сертификатах.

## Приёмка и первый сквозной результат

Для приёмки используется одна работающая VM, около 4 vCPU и 6–8 ГБ памяти, отдельные чистые диски для Docker и rootless Podman. Поддерживаемую гостевую ОС выбирает исполнитель; Podman-проверка должна включить SELinux enforcing. VM получает отдельный сетевой адрес без общих каталогов с клиентом. Это две ОС с реальным HTTPS-доступом, а не проверка конкретного корпоративного прокси/внешнего файрвола. Автономная подготовка VM согласована; текущие M4-стенды и пользовательские профили сохраняются.

Для первого живого прогона получают штатную целевую контейнерную release-поставку; для приёмки обновления также нужна пригодная пара выпущенных версий. Уточнение владельца при возобновлении Task 0: разрешена подготовка комплекта из предоставленного контейнерного release и соответствующего тега штатного установщика с проверкой байтов payload и реальной установкой. Такая сборка имеет собственное происхождение и не выдаётся за готовый архив вендора; предоставленные изменения клиента для `data-tid` фиксируются явно. Порядок подготовки и ограничения — в уточнении Task 0 плана. Тестовые образы M4 и нативный архив Loginom её не заменяют. Точные версии выбирают по доступным поставкам в рамках 7.4.x, закрепляют один раз в приёмке и проверяют совместимость runtime с целевой версией. Текущее состояние целевой поставки и пары обновления хранится в [runbook M5](../../testing/loginom-ai-agent/dashboard-m5.md). Отсутствие целевой поставки блокирует первый живой прогон; отсутствие второй версии блокирует проверку обновления, но не первый путь на уже доступной целевой версии. Переустановка той же версии не считается доказательством обновления.

Порядок:

1. На собственной чистой VM проверить штатную установку Loginom, фактические mounts/права/сеть и release Apache. Подтвердить HTTPS Studio с клиентской машины и доверие частному CA на путях агента. При неудаче работать только к этому результату.
2. Получить первый полный результат: минимальная установка dashboard → установленный Desktop → снимок → черновик → подтверждение → UserStorage → серверная сборка → Dashboard в `/app/` по HTTPS. Включить серверную пробную публикацию `check`; сначала доказать основной путь, затем расширять диагностику и упаковку.
3. Выполнить офлайн-установку из готового архива на чистых Docker и rootless Podman, повторный install/check, автозапуск и отдельную клиентскую проверку. Проверить нижние границы совместимости движков/compose, UserStorage RO и реальные SELinux/UID mapping. Сохранить полный M4 release-цикл для Desktop/CLI, права личной/общей папки и отказ, продолжение исходников, отказ новой сборки, rollback и неизменность `.lgp`.
4. Выполнить реальное обновление Loginom и `--change`, снова пройти check и установленный браузерный путь; затем uninstall и открыть исходный пакет. Проверить негативные случаи TLS, сбой применения Apache-конфига и сохранность пользовательских данных при сбоях диагностики.

Исходниковые проверки, контейнерная проверка, установленный Desktop/CLI и фактическое обновление записываются раздельно. Source gate — package-local typecheck, профильные Node/browser-тесты, сборка, существующие пороги покрытия и `check:size`; для shell — `bash -n` и ShellCheck. Новые нетривиальные ветки получают небольшой поведенческий тест; TLS проверяется настоящим соединением, не моками. Пользовательская приёмка запускается на собранной установленной поставке, а не dev renderer. CI расширяется в существующих заданиях; секреты, VM-диски и сырые логи остаются вне Git.

## Затрагиваемые части и цена

| Часть | Изменение и обоснование |
|---|---|
| `packages/dashboard/deploy/` | Release-скрипт/compose/Apache-конфигурация и проба публикации; нужен безопасный lifecycle рядом со штатным Loginom |
| `packages/dashboard/script/`, Dockerfile | Повторяемая подготовка офлайн-архива и включение shell; установка без исходников и сети |
| `src/web/`, `src/shell/` | Доставка shell/health, TLS-forwarder и сообщение при недоступном HTTPS frame; ключ не покидает Apache |
| Профильные тесты и существующий CI | Проверка контрактов, отказов и артефакта; без новой платформы испытаний |
| Desktop/Host/runtime | Только если настоящий HTTPS-прогон выявит дефект использования штатного доверия; новый CA UI/конфиг не добавляется |
| Документы | Дизайн/план, runbook M5 и короткий checkpoint, ссылки roadmap/README, актуальные инструкции затронутых модулей вместе с кодом |

Карта файлов и актуальная оценка реализации с тестами и документацией находятся в [плане](../plans/2026-11-15-dashboard-m5.md). Это оценка, не квота; создание VM и одноразовые пробы в неё не входят и в продуктовый код не переносятся. Расширение более чем вдвое требует пересмотра конструкции по правилам проекта.

Детали размещения файлов, имена параметров, разумные конечные таймауты, способ подготовки VM, генерация тестового сертификата и выбор тестового приложения оставлены исполнителю. Нельзя самостоятельно менять режимы безопасности, требования к пробной публикации, полноту установленной приёмки или выбранные границы CA.
