# Прокси: отказ запуска Windows и временный возврат к OpenCode

Решение пользователя от 22 сентября 2026: задокументировать проблему и варианты,
пока вернуть поведение оригинального OpenCode, отправить изменения в `loginom`
и выпустить Desktop/CLI для всех поддерживаемых платформ. Версия исправления: 0.1.8.

## Принято сейчас

Desktop и standalone CLI больше не читают системные настройки прокси Windows,
macOS и GNOME перед запуском backend. Удалены собственные native/system proxy
importers и их startup calls. Поддержка явных `HTTP_PROXY`, `HTTPS_PROXY`,
`NO_PROXY` и вариантов имён в нижнем регистре остаётся в существующих транспортах.
Сохраняются служебный loopback bypass Desktop, системные CA, передача разрешённых
переменных исполнителю и защита секретов. Системные параметры пользователя не
меняются. Это не реализация прокси только для моделей.

База сравнения — OpenCode `dev`, commit
`fe3f3a41f79ad292cc3c7c629567385a20ec5130`:
[Desktop startup](https://github.com/anomalyco/opencode/blob/fe3f3a41f79ad292cc3c7c629567385a20ec5130/packages/desktop/src/main/index.ts),
[server environment](https://github.com/anomalyco/opencode/blob/fe3f3a41f79ad292cc3c7c629567385a20ec5130/packages/desktop/src/main/server.ts),
[proxy documentation](https://opencode.ai/docs/network/).
Речь о поведении backend/CLI, а не о буквальном откате всего форка.
Chromium и внешний браузер авторизации сохраняют собственное обнаружение
системных настроек; этот релиз не принуждает весь браузерный трафик к DIRECT.

Последствие: если прокси задан только в настройках ОС, запросы backend к моделям
и OAuth больше не получают его автоматически. Для них нужно передать proxy
environment при запуске приложения. Сетевые ограничения и отсутствие доступа
к провайдеру этим изменением не устраняются. Полная поддержка всех схем прокси,
PAC и способов авторизации не заявляется.

## Почему импорт появился

17 сентября в GNOME был включён ручной прокси, но shell environment не содержал
соответствующих переменных. Backend 0.1.0 выполнял OAuth-запросы напрямую и
получал отказ; через системный прокси запросы доходили до сервиса авторизации.
Коммит `989706951` добавил перенос системной конфигурации в окружение и её
приоритет над shell. Позже shared Host и Windows/Desktop получили native adapters
(`a7d812e4a`, `84056c6e4`). Исторические основания:
[дизайн](2026-09-17-system-proxy-design.md),
[приёмка Linux](../../testing/loginom-ai-agent/reports/2026-09-17-proxy/report.md).
Настоящее решение заменяет ту runtime-политику; старые отчёты остаются историческими.

## Подтверждённые проблемы

- Windows `ProxyOverride` с `*vk.com` и аналогичными суффиксными масками вызывает
  `SYSTEM_PROXY_BYPASS_UNSUPPORTED`. Список хранится в ОС, а ошибка находится
  в нашем преобразовании, не в установщике.
- В Desktop синхронное исключение до `whenReady` завершает корневой Effect fiber,
  но оставляет Electron живым без окна и с single-instance lock.
- Автоопределение/PAC вызывает отдельный `SYSTEM_PROXY_AUTOMATIC_UNSUPPORTED`
  на той же границе, в том числе без заданного ручного прокси.
- Ошибка чтения ОС, неподдерживаемая схема или авторизация также могли оборвать
  этот участок запуска. CLI обрабатывал известные коды выходом 2, но тоже
  блокировал работу из-за системной политики.
- `Effect.tapError` не наблюдает такой defect; для полной диагностики нужен
  Cause/Exit handler. Одно логирование не обеспечивает завершение процесса.
- `*vk.com`, `*.vk.com` и `vk.com;*.vk.com` не эквивалентны. Пропуск неизвестной
  маски или отключение прокси целиком меняют маршрут без сохранения политики.
- Синхронный PowerShell добавлял задержку на startup; timeout не устранял
  проблему обработки ошибок. Системные изменения требовали перезапуска.

[Независимая проверка](../../testing/loginom-ai-agent/reports/2026-09-22-windows-startup-verification.md)
содержит уровни доказательств и ограничения: настоящий исходный parser,
предоставленный WinHTTP result и минимальный Electron 42.3.3 harness;
это не установленная приёмка исправленного полного клиента.

## Рассмотренные варианты (отложены)

| Вариант | Польза | Цена и ограничения |
| --- | --- | --- |
| Независимое открытие окна и обработка Cause/Exit | Сетевая ошибка не оставляет невидимый процесс | Сам маршрут не исправляет; требует отдельного startup/error UI |
| Расширять перевод системных исключений в NO_PROXY | Небольшие исправления для распространённых правил | Разные семантики Windows, Node, Bun, WS; PAC не сводится к одной строке |
| Ручной выбор system/direct/custom в приложении | Даёт пользователю выход при несовместимости | Требует настроек, хранения и единообразного применения во всех процессах |
| Системный прокси без исключений для всех запросов | Устраняет разбор bypass | Может отправить внутренний Loginom/MCP через внешний прокси; loopback всё равно нужно сохранять |
| Chromium system network transport | Готовая обработка system/PAC/WPAD | Интеграция HTTP/SSE/WS, redirects, отмены и отдельных Node-процессов; CLI независим от Desktop |
| Системный прокси только для моделей и их авторизации | Ограниченная область; для ручного HTTP/HTTPS проще общей перестройки | Нужен отдельный transport для всех provider paths и OAuth; PAC/auth остаются отдельными задачами |

Общий resolver `session.resolveProxy(url)` только определяет маршрут: он не
реализует proxy authentication, failover или передачу данных. Собственный
loopback HTTP/CONNECT relay не является автоматически полной заменой Chromium:
CONNECT не передаёт полный URL, а NTLM/Kerberos не переносится вместе с адресом.
[Electron net](https://www.electronjs.org/docs/latest/api/net),
[session](https://www.electronjs.org/docs/latest/api/session#sesresolveproxyurl).

## Будущий вариант: прокси только для моделей/OAuth

Кандидат для следующего дизайна, не включён в 0.1.8:

1. Читать адрес ручного HTTP/HTTPS-прокси без перевода `ProxyOverride`.
2. Применять явно в транспорте облачных моделей, без глобального изменения
   `process.env` и без переноса этой политики на Loginom/MCP.
3. Охватить HTTP/SSE, WebSocket, browser code exchange, device initialization/
   polling и refresh токенов. Служебные callbacks и loopback-модели идут напрямую;
   частные/custom model endpoints требуют явной политики.
4. Учесть provider SDK wrappers, native runtime и plugins. Единственная замена
   `options.fetch` не покрывает все пути: native runtime имеет отдельный override,
   некоторые провайдеры создают собственные транспорты.
5. Страница логина открывается внешним браузером через `shell.openExternal`:
   его маршрут не управляется proxy-настройкой backend. Login/password в агент
   не переносить. PAC и auto-detection обрабатывать отдельным resolver, а не
   угадывать постоянный адрес прокси.
6. Не делать скрытый прямой повтор при отказе заданного прокси. Проверить
   cancellation, streaming и смену конфигурации без потери активных операций.

## Проверки текущего возврата и будущих изменений

Для 0.1.8: package typechecks; сохранение разрешённых proxy environment;
реальные HTTP/fetch/HTTPS CONNECT через локальный тестовый прокси, loopback
bypass и отсутствие прямого fallback; subprocess CLI с враждебным gsettings,
который не должен вызываться; native CI и offline smoke всех трёх платформ.
Проверка полного Windows-клиента на машине первоначального инцидента остаётся
отдельной installed acceptance, которую нельзя заменить исходниками или CI.

Будущая системная поддержка требует отдельной матрицы: no proxy, manual,
суффиксы, IPv4/IPv6, `<local>`, PAC/WPAD, недоступный proxy, auth, HTTP/HTTPS,
SSE/WS, OAuth callback/refresh, локальные модели и независимость Loginom.
