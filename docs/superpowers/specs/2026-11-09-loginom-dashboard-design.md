# Dashboard из чата агента внутри Loginom

Статус: утверждено владельцем для автономного выполнения.

## Результат за восемь часов

Пользователь выбирает узел в Loginom, нажимает «Создать dashboard» и пишет в текущий
чат Codex, какой пульт ему нужен. Агент создаёт приложение, собирает и подключает
к узлу. По кнопке Dashboard оно открывается на весь TabForm, включая строку
навигации сценария. Глобальные вкладки и боковая панель Loginom остаются снаружи.
Пользователь меняет параметры, Loginom выполняет узел и приложение показывает
новые строки. Изменение приложения заказывается в том же чате и видно при повторном открытии.

В восемь часов входят параметр на Loginom master, механизм в клиенте и NodeJS,
первое приложение, его создание **и правка** из чата Codex и повторное открытие.
Desktop на этом этапе не меняется. Обработчик текущего чата Desktop — следующий
этап; он использует тот же снимок цели. Новая skill для написания приложений не нужна.

## Первый сценарий и главный риск

Эталон `campaign-roi-by-channel` содержит импорт, группировку, калькулятор,
сортировку и экспорт; «Переменные сценария» пусты. Он проверялся на 7.4.2,
на master пока не открывался. Первым делом **исполнитель** готовит на master
отдельную копию пакета и данных, с порогом бюджета и фильтром `budget >= MinBudget`
перед группировкой. Пользователь и агент, которому заказывают dashboard, сценарий
не меняют. Допустимы loginom-automation, штатные вызовы клиента или правка копии пакета.

Один скрипт без пользовательских действий в UI записывает порог, выполняет итоговый
узел «По убыванию ROI» с зависимостями и заново читает его первый выход. Это первая
сквозная проверка до разработки пульта. Способ записи не является требованием:

1. Переменная сценария в VariablesNode.
2. Управляющая переменная фильтра (как у проверенного GroupLimit).
3. Любой другой параметр, действительно меняющий выход Loginom.
4. Если ROI не удаётся запустить с параметром, использовать проверенный
   `variable-probe.lgp` с GroupLimit для первого приложения. Записать изменение
   требования и потерю маркетинговой демонстрации; не выдавать его за приёмку ROI.

Ориентиры **из CSV**, ещё не результат Loginom master:

| Порог | Кампании | Общий ROI | Первый канал |
|---:|---:|---:|---|
| 0 | 500 | 110,20 % | Email |
| 50 000 | 245 | 33,36 % | TV |
| 100 000 | 0 | — | нет строк |

Пульт показывает суммарные бюджет и выручку, общий ROI по этим суммам, число
кампаний, сравнение каналов и таблицу. Число каналов берётся из результата:
при 99 000 их четыре, при 100 000 — ни одного. При пустом выходе суммы нулевые,
ROI не определён. Схема различает числа, строки и NULL. Детализация до кампании не нужна.

## Приложение и расчёт

React и TypeScript для форм, Recharts для графика, Vite для статической сборки
с относительными путями. На том же origin NodeJS раздаёт приложение в iframe.
Next.js здесь не нужен. Perspective остаётся вариантом для будущей панели
самостоятельного анализа.

Перед открытием приложения общий bootstrap выполняет неактивный узел, а у активного
без сохранённой ошибки использует готовый результат. Во время ожидания видно
«Идёт расчёт». Iframe загружается после успешной подготовки данных, поэтому
приложению достаточно вызвать `state()`; собственный автозапуск и начальная кнопка
«Выполнить» не нужны. Рассчитанная пустая таблица — успешный результат.

Значение принимает штатное событие change (Enter, потеря фокуса, отпускание
ползунка); порог — конечное число не меньше нуля. Некорректное поле не запускает
расчёт. Кнопки «Применить» нет. Принятые значения выполняются последовательно.
Очередь принадлежит странице Loginom; закрытие iframe её не прерывает. При
повторном открытии во время работы видно «Идёт расчёт». В конце очереди приложение
читает из сессии фактический порог и результат.

Если запись порога удалась, но выполнение упало, видны новый фактический порог,
ошибка и прежние данные с подписью «расчёт при пороге N». При повторном открытии
bootstrap делает одну попытку восстановления, даже если после ошибки статус узла
остался активным. Сохранённая ошибка снимается только после успешного выполнения.
При неудаче виден текст ошибки; следующая попытка начинается новым открытием.
Открытие готового приложения само по себе не меняет параметры. После закрытия
применённый порог остаётся в открытой сессии; сохранять ли изменения в .lgp,
решает пользователь.

## Bootstrap и привязка

Сервис и bootstrap создаются **в репозитории** по образцу временной пробы и один
раз подключаются к стенду. Bootstrap всегда включён в обычном /app/ через
index.html. Для одиночного выделения кнопка в ModelForm показывает «Создать
dashboard» или «Dashboard». И создание, и открытие готового пульта сначала
подготавливают результат узла через общую очередь, иначе у снимка не будет
рассчитанных строк. Пустой рассчитанный выход
допустим. Узел без табличного первого выхода показывает «Dashboard для этого узла недоступен».

Привязка: сервер, полный путь пакета, workflow, GUID узла, первый выход узла.
Одинаковые GUID в разных пакетах — разные приложения. Адаптер каждого iframe
привязан к узлу и сессии при открытии; смена выделения не перенаправляет действия.
Он описывает параметры и первый выход, пишет значение штатной операцией настройки,
ожидает окончания выполнения и заново получает схему и строки. Неподдерживаемые
типы выхода не обещаются. Среда — один доверенный локальный пользователь:
код приложения на том же origin имеет доступ к родителю.

## Как чат получает цель и публикует приложение

При «Создать dashboard» и при открытии готового Dashboard bootstrap публикует
в NodeJS неизменяемый снимок под новым идентификатором. Последний опубликованный
снимок — текущая цель этого стенда. Снимки хранятся в памяти NodeJS.
Снимок самодостаточен: привязка, отображаемое имя узла, каталог исходников на хосте,
схема и примерные строки выхода, параметры и их значения, описание действий адаптера,
команды создания из шаблона, проверки типов, сборки и публикации.

В Codex агент в начале каждой просьбы **один раз** читает текущую цель по HTTP,
называет её в первой строке ответа и до конца просьбы использует только этот
идентификатор. В живую сессию Loginom он не входит. Решение автора: одна строка
в инструкциях проекта сообщает адрес и правило чтения цели; никаких ручных ссылок
и JSON от пользователя. Loginom можно открыть в любом браузере. В этом отладочном
пути цель фиксируется при первом чтении, **не** при отправке сообщения. Изменение
выделения или публикация другой цели после чтения не меняют адресата.

Имя каталога каждого приложения на хосте однозначно выводится из полной привязки.
Реестра и поиска нет. Агент получает путь из снимка; при создании копирует шаблон
React/TS/Vite/Recharts с lockfile и уже установленными зависимостями. Сеть нужна
один раз для шаблона. Исходники остаются для правки из чата. На стенд передаются
dist и привязка только после успешной проверки типов и сборки. Ошибка сборки
сохраняет прежнее рабочее приложение. index.html отдаётся без кеширования.
Открытие dashboard заново фиксирует цель для правки из Codex.

## Приёмка через настоящий запрос

Основной агент выполняет действия пользователя в своей браузерной сессии Loginom.
Он нажимает «Создать dashboard» у «По убыванию ROI». Субагент без истории
(`fork_turns="none"`) получает **только текст**: «Сделай для выбранного узла
маркетинговый пульт: бюджет, выручка, ROI, число кампаний, сравнение каналов и
таблица; порог минимального бюджета пересчитывает данные в Loginom». Он сам
находит цель, создаёт и публикует пульт. По кнопке Dashboard основной агент видит
ориентиры выше и после сброса — снова 500. Все числа на экране берутся из
нового выполнения Loginom; примеры в снимке не служат источником данных.

Затем тот же субагент получает вторую просьбу: «Подпиши ROI на графике и добавь
сортировку таблицы по клику». Повторное открытие показывает правку на живых данных.
Смену выделения после чтения цели и отсутствие подмены проверить вживую.
TDD — два теста NodeJS: разные каталоги A и B при одном GUID; выдача прежнего
снимка по его идентификатору после публикации следующего. HTTP-ввод и пути
проверяются на границе. Сохранить скриншоты и JSON вне Git.

Боковая проба подтвердила, что путь пакета различает A и B при одинаковом GUID;
запрос, зафиксированный кликом до переключения, при активном B изменил только
файлы A, и у каждого узла открылось своё приложение. Поле ввода чата, текст
пользователя, снимок через NodeJS и подпись цели пробой не проверены.
Подробности — [исследование](../../research/2026-11-09-dashboard-live-investigation.md).

## Следующий этап: Desktop (вне восьми часов)

«Создать dashboard» открывает уже текущий чат; над полем ввода — «Создаём dashboard
для узла <имя>». В готовом пульте «Изменить в чате» открывает текущий чат с именем
dashboard над полем. В Desktop цель должна фиксироваться **при отправке** сообщения.
Существующий loginom-ai-agent://new-session создаёт новый чат и не реализует этот путь.

На следующем этапе проверить:
- что считать текущим чатом при главном экране или незапущенном Desktop;
- источник отображаемого имени узла: в боковой пробе get_Name() вернул пустую строку;
- как вложить ID снимка в сообщение: build-request-parts.ts отправляет PromptContextItems,
  но сейчас только для файлов;
- запрос браузера на открытие ссылки loginom-ai-agent:// и условие server.isLocal() в обработчике.

Отсчёт восьми часов от начала задания; вопросы владельцу не задавать.

- Секреты не переносить в Git, аргументы или отчёты. Не показывать числа без нового выполнения Loginom и не заявлять непроверенное.
- Разрешены собственные headless Chromium/Playwright и сессия Loginom; docker exec/cp, перезапуск и пересоздание только dashboard-master-20261109-* по рецепту исследования; пакеты и файлы в своём хранилище стенда.
- Разрешены изменения клиентских файлов стенда, при необходимости самого клиента; npm-зависимости шаблона; субагенты для ревью и приёмки; коммиты в отдельную ветку от dashboard-research до трёх слов, без push/PR.
- Для объектов Loginom допустима глобальная loginom-automation: E2E_TESTS_DIR=/home/george/git/testing/e2e-tests, стенд http://127.0.0.1:32768/app-debug/?testable=true. «Стоп и отчёт» завершает способ, не всё задание.
- Тайм-боксы: дизайн, план, ревью ≤1 ч; параметр и ROI ≤1,5 ч (≤45 мин на ступень); NodeJS, bootstrap, адаптер, шаблон, публикация и два теста ≤2,5 ч; создание из чата ≤1,5 ч; правка и открытие ≤1 ч; отчёт 0,5 ч.
- Сначала риск с параметром по лестнице выше. Сборка: npm → bun → меньше параллельных загрузок и локальный кеш → обычный HTML/JS с записью о смене требования. API: проверенные вызовы → исходники debug-клиента из артефакта → правка клиентского кода стенда.
- При блокере получить воспроизводящую команду, перейти на следующую ступень. При исчерпании лестницы или времени записать симптом, попытки и условие возобновления; делать независимое, к нерешённому вернуться в конце.
- Требование менять только после исчерпания его лестницы; записать что, почему и цену изменения. При нехватке времени сокращать по порядку: оформление ошибок и пустого состояния; разные подписи кнопки; правку агентом без истории заменить правкой в этом чате.
- Не сокращать реальный пересчёт Loginom, весь TabForm из узла, создание по запросу из чата, правку и повторное открытие. После 6,5 часа не начинать новые функции, доводить работающее до проверенного.
- В плане держать точку продолжения до 20 строк; обновлять после каждого проверенного шага. До отчёта закрыть свой пакет и выйти из своей сессии, освободив блокировку.
- В отчёте: что работает и чем проверено, ссылки на скриншоты/JSON вне Git, изменённые требования, отложенные блокеры и условия возобновления, утренний адрес и шаги, затраченное время.
