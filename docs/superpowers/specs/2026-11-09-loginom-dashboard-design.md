# Dashboard из чата агента внутри Loginom

Статус: проект дизайна для согласования. Продуктовая реализация не начата.

## Задача

Пользователь выбирает узел Loginom и описывает в чате нужное dashboard-приложение.
Агент создаёт приложение и подключает его к узлу. Пользователь не вводит адрес
приложения, не выбирает его из каталога и не редактирует конфигурацию.
Кнопка Dashboard открывает приложение на всю область TabForm. Управление в
приложении меняет переменные Loginom, запускает расчёт и показывает новый результат.

Первый полный путь выполняется из текущего Codex. Для Loginom AI Agent Desktop
используются тот же контекст, файлы приложения и способ подключения. Новая skill
для создания dashboard не нужна. Предел работы — восемь часов агентной работы;
приоритет — один работающий путь на текущем локальном master-стенде.

## Подходы и основание выбора

Принятую пользователем пробу развиваем как обычное приложение на NodeJS плюс
тонкий адаптер в существующем клиенте Loginom. Окно полностью занимает TabForm;
общая навигация Loginom остаётся доступной. Такое размещение и управление
расчётом уже проверены на стенде: см. документ живого исследования.

Отдельная BI-платформа добавила бы собственные источники и управление объектами,
а задаче нужны произвольные формы и действия приложения. Встраивание всего
механизма во внутренний протокол Desktop потребовало бы изменений продукта до
первой проверки из Codex. Для первой версии предлагается общий внешний механизм.
Это техническая рекомендация автора; согласование этого документа ещё требуется.

## Выбранный стек первого приложения

Пользователь выбрал React и TypeScript для интерфейса первого приложения.
Vite собирает HTML, JS и CSS в `dist` с путями ресурсов, относительными к каталогу
приложения. Существующий NodeJS-сервис раздаёт эти файлы в iframe текущего TabForm.
Адаптер Loginom работает через обычный JavaScript и остаётся доступен приложениям
на других стеках. Живая HTML/JS-проба подтвердила такую возможность.

В первом ROI-приложении React отвечает за поля ввода, текущий результат и состояние
расчёта. Для сравнения каналов используется Recharts. При каждом корректном
изменении параметра адаптер передаёт его в Loginom, ждёт выполнения узла и получает свежие строки.
Диаграмма и таблица используют один и тот же результат. Для этой страницы отдельные
функции Next.js, включая серверный рендеринг и маршрутизацию страниц, не требуются.

В [исследовании 64 вариантов](https://github.com/gooddaytoday/loginom-ai-agent/blob/8ef28ef58f1d4c6d8d6c422f36106efa5d579f27/docs/research/2026-11-03-dashboard-frameworks-report.md)
Perspective лидирует для интерактивного исследования данных узла. Если аналитику
нужно самому выбирать поля, строить сводные таблицы и сохранять настройки,
первым кандидатом для такой панели будет Perspective внутри того же приложения.
Для маркетингового пульта с пятью уже рассчитанными строками достаточно Recharts.
Совместимость предложенного стека с Loginom ещё предстоит проверить. Первая проверка
сборки должна загрузить `dist` из каталога приложения в TabForm и обновить график
после настоящего пересчёта. Для Perspective дополнительно потребовалась бы проверка
загрузки worker и WASM и сохранения настроек при обновлении данных.

## Первый результат

На копии эталона `campaign-roi-by-channel` выбран итоговый табличный узел
«По убыванию ROI». Агент создаёт маркетинговый пульт: общий бюджет, выручка,
ROI, число кампаний, сравнение пяти каналов и итоговая таблица.

Одна переменная сценария `MinBudget` управляет штатным фильтром `budget >= MinBudget`
перед группировкой. Изменение порога автоматически меняет переменную и выполняет итоговый узел
с его зависимостями. Общий ROI считается из суммарного бюджета и выручки.
Второй источник с деталями 500 кампаний и дополнительные фильтры пока не нужны.

Первый проверяемый сквозной результат: при `MinBudget=0` dashboard показывает
500 кампаний, при `MinBudget=50000` — 245, после сброса — снова 500. Все значения
получены из нового выполнения Loginom, а не из вычислений frontend поверх образца.

## Поведение первого приложения

При открытии форма читает фактический `MinBudget` и доступный результат из
Loginom. Если результат ещё недоступен, пользователь может выполнить узел.
Каждое новое корректное значение параметра запускает пересчёт автоматически.
При быстром вводе принятые изменения выполняются последовательно в порядке ввода.
Интерфейс показывает результат последнего выбранного значения. Загрузка текущих
значений при открытии сама по себе не запускает выполнение.
При успешной записи порога и последующей ошибке выполнения экран показывает
фактически установленный порог и ошибку. Предыдущие данные остаются помечены
как результат последнего успешного расчёта с его порогом, если он известен.
Применённое значение остаётся в открытой сессии при закрытии dashboard.
Принятое до закрытия изменение завершается в этой сессии. Запись пакета `.lgp`
остаётся явным действием пользователя в Loginom.

Для обычного и пустого результата есть независимый ориентир по исходному CSV.
При порогах 0 и 50 000 общий ROI с округлением до двух знаков равен 110,20 %
и 33,36 % соответственно. При пороге 100 000 выборка пуста. Экран показывает
ноль кампаний, нулевые суммы и «—» для ROI. Чтение порта должно сохранять
числовую семантику полей и различать NULL и ноль.

## Части решения

### Адаптер внутри Loginom

Отдельный bootstrap подключается через читаемый index.html готового клиента;
минифицированные bundles не переписываются. Bootstrap всегда включён в обычном
клиенте. При выборе одного узла в ModelForm появляется «Создать dashboard», если
приложение ещё предстоит создать, или «Dashboard», если оно уже существует.
При открытии приложение получает привязку к этому узлу на всё время работы.

Адаптер умеет описать выбранный узел и его выходы, прочитать актуальную таблицу,
прочитать и изменить разрешённые для приложения переменные и выполнить цель.
После выполнения выход и схема получаются заново. Используются штатные операции
редактирования и ожидания завершения, подтверждённые живой пробой.

Привязка содержит сервер, путь пакета, workflow, node GUID и выбранный порт.
Один GUID порта или имя узла недостаточны. Смена выделения после открытия
dashboard не должна незаметно менять источник или цель выполнения.
Каждый iframe обращается к экземпляру адаптера своей вкладки и привязки.
Снимок для агента служит описанию данных, значения на экране приложение
получает из действующей сессии Loginom.

### NodeJS и контекст задания

Существующий NodeJS-сервис раздаёт приложения через тот же origin, что Loginom.
Его небольшое дополнение принимает снимок контекста выбранного узла и выдаёт
этот снимок агенту. Контекст включает точную привязку, схему, явно обозначенные
примерные строки, доступные переменные и описание действий адаптера.

Снимок имеет явный идентификатор и содержит цель создания или изменения приложения.
В момент отправки сообщения цель фиксируется в контексте этого сообщения.
Выполнение, изменение файлов и подключение результата используют эту зафиксированную
привязку. Последующее переключение узла или dashboard влияет на будущий ввод в чат.
Если у двух пакетов одинаковые GUID узлов, пути пакетов различают их приложения.

Для первой отладки через Codex пользователь держит dashboard рядом с этим чатом
и пишет пожелания здесь. Агент получает цель из открытой вкладки и уточняет её при
неоднозначности. Полученная цель фиксируется для отправленного запроса. Постоянные
ручные операции по закреплению цели, перенос URL/JSON и ввод адреса приложения
пользователем в этот путь не входят.

Агент редактирует исходники React/TypeScript и описание привязки. Для следующих
правок из чата сохраняются исходники приложения и зафиксированные версии зависимостей.
После проверки типов и успешной сборки готовый `dist` передаётся на текущий стенд
имеющимися командами копирования файлов. При ошибке сборки по кнопке Dashboard
продолжает открываться предыдущая рабочая версия. Новый upload API, очередь
генерации и собственный agent runtime для этого не нужны. NodeJS находит
приложение по сохранённой привязке; отдельный реестр поверх файлов не создаётся.
Привязка сохраняется вместе с приложением и переживает закрытие dashboard.

### Пользовательский путь и Desktop

Пользователь выбрал вход из Loginom в уже открытый чат Loginom AI Agent Desktop.

1. У узла с ещё не созданным приложением «Создать dashboard» открывает текущий чат.
   Над полем ввода показано «Создаём dashboard для узла <имя>». Пользователь сразу
   пишет пожелания и отправляет сообщение.
2. У узла с готовым приложением «Dashboard» открывает его на всю область TabForm.
   Внутри приложения доступна команда «Изменить в чате». Она переводит в текущий
   чат и показывает над полем ввода имя редактируемого dashboard.
3. Отправленное сообщение сохраняет свою цель. Если во время работы агента
   пользователь открыл другой узел или dashboard, выполняющийся запрос продолжает
   относиться к приложению, указанному при отправке.

В Codex действует описанный выше вход через открытую рядом вкладку. Агент получает
контекст, создаёт или редактирует исходники, собирает приложение и подключает
результат к зафиксированной цели. После изменения приложения достаточно повторно
открыть Dashboard. Браузерная сессия Loginom остаётся владельцем расчётов.

В Desktop предстоит реализовать приём контекста в текущем чате, отображение цели
над полем ввода и её фиксацию при отправке. Существующий
`loginom-ai-agent://new-session` принимает `directory` и `prompt` и создаёт новый чат.
Выбранный пользователем путь требует обработчика существующего чата.

### Что подтверждено боковой пробой

На выделенном стенде `http://127.0.0.1:32769/app/` открыты пакеты A и B с одинаковыми
GUID узлов и разными путями пакетов. Контекст A получен из Loginom, передан через
временный Playwright binding инструменту реального агента Codex и прочитан агентом.
При активном B сохранённый запрос изменил приложение A и его реальный GroupLimit
до 2. У B сохранились прежние данные и побайтно те же файлы приложения. Результат
зафиксирован в [evidence.json]($HOME/Documents/Codex/2026-11-09/loginom-dashboard-chatlink-check/outputs/evidence.json).

Это подтверждает передачу точного контекста через инструменты Codex и сохранение
цели во время выполнения запроса. Встроенное поле ввода текущего чата Desktop и
его обработчик ещё требуют реализации и живой проверки. Отображение имени цели
над полем ввода относится к выбранному UX, а в пробе поле `nodeName` осталось пустым.

Проверки установленного Desktop и дополнительно собранного renderer 0.3.9 показали,
что `new-session` сохраняет JSON внутри `prompt`, игнорирует дополнительный
`sessionId` и ведёт на маршрут нового чата. Результат проверки renderer записан
в [bundle-check.json]($HOME/tmp/dashboard-chatlink-side-20261109-5_z_2l9_/desktop-039/bundle-check.json).
AppImage этой сборки запущен в отдельном профиле под Xvfb. Штатные проверки
инициализации, журналирования и аварийного завершения дали PASS в
[crash-logging.log]($HOME/tmp/dashboard-chatlink-side-20261109-5_z_2l9_/desktop-039/crash-logging.log).
Проверка выбранного входа в текущий чат должна пройти через его поле ввода и
обработчик отправки сообщения.

## Проверки и ограничения

TDD применяется к новому поведению общего механизма по одному сценарию: выдача
контекста правильного узла, нахождение установленного приложения по его привязке,
отсутствие подмены источника после смены выделения. Проверяются публичные операции,
а не приватные имена Ext. Входы HTTP и пути файлов проверяются на границе.

В живом minified Loginom отдельно проверяются полный маркетинговый цикл,
закрытие/повторное открытие, размер TabForm и понятная ошибка выполнения.
Предыдущий результат не выдаётся за новый при ошибке расчёта.

Первая версия предназначена для одного доверенного пользователя на локальном
исследовательском стенде и его тестовых данных. Код приложения в iframe с тем же
origin имеет доступ к родительской странице, поэтому этот режим предполагает
доверенный код. Многопользовательская публикация,
удалённая установка, авторизация сторонних приложений, ручной BI-конструктор,
большие datasets и перенос dashboard внутри файла LGP требуют отдельного решения.
Табличное чтение проверяется на первом приложении; иные виды выходов не обещаются.

Главный оставшийся технический риск — настоящая переменная workflow и её связь
с фильтром на master: существующая проба проверила только локальную ControlVariables.
Этот риск проверяется первым, до разработки передачи контекста и красивого UI.

## Что решает исполнитель

Имена внутренних HTTP-маршрутов и файлов, простой формат снимка и привязки,
размещение отдельного пакета в репозитории и оформление первого приложения.
Выбранный стек первого приложения описан выше. Эти решения
не должны менять пользовательский путь, полномочия приложения и критерии проверки.
После согласования дизайна составляется отдельный план с оценкой файлов/строк,
проверяемыми шагами и независимым review до реализации.
