# Большие датасеты: профиль, выборка и полный расчёт

Статус: проект на согласование владельцу (LAB-363, D87 / #288, этап 1).
База: `large-datasets@c2404624356f0fe8cb2411052ce18eb836acc983`
(`loginom@20222c2b` и инструменты регламента). Код продукта этим документом не меняется.

## Решение и границы

Рабочий цикл: **профиль → выборка → построение и отладка → полный источник → один расчёт → сверка**.
Модель получает метаданные и несколько примеров, а не содержимое большого файла.
Поддерживаем локальные CSV/TSV/TXT и XLSX, а также явную ссылку на файл в хранилище
Loginom. Произвольные пути файловой системы Loginom Server в этап 2 не входят.

До 16 МиБ сохраняем проверку серверной копии по SHA-256. Для больших файлов
применяем принятое владельцем доказательство: точный размер из native FileStore
после завершения загрузки и точное число записей на выходе полного импорта,
равное локальному потоковому подсчёту. Размер и число записей не доказывают
побайтовую идентичность; локальный SHA служит идентичности источника и журналу
повторного использования, не объявляется серверным SHA.

## Профиль файла: `loginom_file_profile(path)`

Инструмент сначала вызывает `authorizeLoginomFile`: проверяются исходный и
канонический пути, тип regular file, доступ и действующие разрешения сессии.
Профиль привязан к canonical path, size, mtime, file identity и выбранному
диалекту. Изменение файла инвалидирует профиль, выборку и точный подсчёт.

Быстрый режим: до 5 с и 8 МиБ чтения, буфер 256 КиБ, ограниченные начало,
конец и детерминированные случайные окна. У каждого окна есть byte offset,
объём и признак подтверждённых границ записей. UTF-8/UTF-16 декодируются с
состоянием между блоками; BOM, CRLF и экранированные кавычки могут пересекать блок.
Перевод строки внутри кавычек не является границей записи.

У произвольного seek нет достоверного начального состояния кавычек. Поэтому
случайное окно или хвост не превращаем в записи по первому LF: подтверждаем
границы по потоковому индексу/контрольной точке парсера. Пока такой точки нет,
окно даёт только помеченную эвристику о байтах; неоднозначные окна исключаются
из профиля типов и выборки. При недостаточном покрытии возвращаем `partial` и
предлагаем полный проход. Не обещаем обнаружить редкую смену типа выборкой.

Детектор выбирает BOM → строгую валидность UTF-8 → UTF-16 LE/BE по BOM и
структуре → cp1251/cp1252 по правдоподобию текста и устойчивости диалекта.
Для ASCII cp1251 и cp1252 неразличимы: сообщаем неоднозначность. Не заменяем
ошибочные байты на U+FFFD незаметно. При близких оценках просим явную кодировку
или диалект перед импортом. Аналогично не угадываем заголовок или неоднозначную
дату `01/02/2026` без указания уверенности.

Детектор сравнивает `;`, табуляцию, `,`, `|`, допустимую кавычку, удвоенную
кавычку, LF/CRLF/CR. Оценивает постоянство числа полей на логических записях,
заголовок, `rows_to_skip`, десятичную точку/запятую и NULL marker. Колонки:
имя источника, ASCII technical name, label, integer/real/string/boolean/datetime,
data_kind, формат даты, доля NULL **на исследованной выборке**, до трёх коротких
примеров, число наблюдений и первое несовпадение типа/числа полей.

Ответ ограничен 8 КиБ: `profile_id`, identity, status/coverage/confidence,
размер, оценка числа записей с интервалом и методом, anomalies, `settings`
с готовыми `source`/`format`/`columns` для `text-import-procedure.mjs:57–93`.
`source_path` заполняется после доставки/выбора серверного источника. Encoding
нормализуется через существующий resolver. При широкой таблице отдаём страницу
колонок и continuation; нельзя называть неполный набор готовыми settings.

Полный режим — отдельная отменяемая операция, не продолжение сверх 5 с внутри
обычного вызова. Один потоковый проход строит SHA-256, точное число записей,
индекс границ и проверяет все типы. Память ограничена буфером, максимальной
записью и схемой; запись > 8 МиБ возвращает отдельный отказ, не растит память.
Сообщаем первое нарушение: логический номер записи, физическая строка начала,
byte offset, колонка, ожидаемый тип и короткий пример. Ошибки структуры не
сводим к пропуску строк. Результат `exact` возможен только после EOF и повторной
проверки identity. Прерванный проход остаётся `partial`, не выдаёт точное N.

Подсчёт единый для профиля, выборки и сверки: парсер учитывает кавычки и их
удвоение; исключает `rows_to_skip` и одну запись заголовка, если он включён;
терминатор последней записи не создаёт дополнительную пустую запись. Отдельную
пустую запись внутри файла учитываем по явно выбранной политике Loginom;
многострочные поля, пропуски и пустые строки проверяем на этапе 2 отдельно.

XLSX определяется по контейнеру и workbook relationships, а не расширению.
Потоково читаем ZIP/XML, листы (видимость, имена), declared dimension и фактически
увиденную размерность, стили дат, первые строки, cached values и наличие формул.
Declared dimension — подсказка, не точный row count. Shared strings индексируем
во временном дисковом хранилище, не в массиве размера всей книги. Ограничиваем
размер распаковки/ячейки и глубину XML; внешние ссылки не загружаем.
Нет cached value формулы — явная неполнота, не вычисление формулы агентом.
Точный подсчёт идёт по выбранному листу и политике пустых строк/заголовков.
Текущий Excel-узел поддерживает 1–8 колонок; профиль более широкой книги возможен,
её сценарий не объявляем поддержанным без отдельного расширения узла.

## Выборка: `loginom_file_sample`

Вход: `profile_id`, способ (по умолчанию начало + детерминированная reservoir
выборка при полном проходе), seed, максимум записей и байт. Итог ≤ 8 МиБ:
помещается и в CLI 10 МиБ, и в нынешний host 16 МиБ. Сохраняем исходные байты,
BOM, кодировку, разделитель, кавычки и окончания строк. Только целые записи с
доказанными границами, один заголовок и согласованный `rows_to_skip`; если
сохраняем preamble, он включается один раз. Получаем локальный обычный artifact
и manifest с profile/identity/seed/offsets/числом записей/SHA, без oracle модели.
Копирование байтов вместо decode/encode сохраняет cp1251 и точность чисел.
Редкие типы из подтверждённых окон включаем, доли NULL профиля не пересчитываем
по намеренно обогащённой выборке. Выборка не доказывает корректность всего файла.

Для XLSX создаём маленькую **XLSX**, не CSV: выбранный лист, те же заголовки,
порядок/типы ячеек, стили чисел и дат, date system 1900/1904. Читаем XML потоком,
переписываем номера строк и shared strings; формулы переносим как их cached
values с явной пометкой в manifest. Это выборка значений для импорта, не книга
для пересчёта Excel. Unsupported/encrypted или отсутствующий cache — отказ с
точной причиной. Размер результата проверяется до admission; большая отдельная
запись/строка не обрезается. Выборка проходит нынешнюю SHA-доставку ≤16 МиБ.

## Доставка по ссылке

Владелец разрешил заменить правило `packages/loginom-host/AGENTS.md:20`
«host получает только bytes/name» узким контрактом: **host принимает bytes либо
ссылку на файл, выданную backend после `authorizeLoginomFile`**. Произвольный
путь, строка модели и имя файла сами по себе прав не дают. Изменение AGENTS и
частного IPC реализуется отдельным PR этапа 2 вместе с отрицательными тестами.

После авторизации backend потоково хеширует исходник и создаёт принадлежащий
операции неизменяемый staging snapshot (потоковая копия, закрытый каталог 0700,
файл 0400). Это расходы диска O(size), памяти O(buffer), без base64. Проверяет
file identity, size и mtime до/после и равенство digest копии SHA точного прохода,
иначе `LOGINOM_FILE_CHANGED`: подсчёт другой версии файла не подходит. Host получает
только canonical staging path, size, mtime, sha256, opaque grant и привязку к
chat/user-message/runtime generation. В IPC байтов файла нет. Host проверяет
grant, ожидаемый каталог и metadata; не принимает новый путь от модели.
На другой машине такой локальный grant неприменим: явный unsupported отказ.

Runtime повторно проверяет identity snapshot, передаёт его путь в
`setInputFiles(path)`, после отправки проверяет stat/hash потоком. До окончания
проверок результат не завершён. Staging защищает от обычного изменения исходника
в процессе загрузки; изменение/замена самого snapshot даёт отказ и уборку,
не удачный импорт смешанных байтов. Не обещаем защиту от процесса того же OS user,
который намеренно меняет закрытое staging-хранилище.

Загрузка — операция `start/status/cancel`, с устойчивым operation_id и частным
журналом. Короткий IPC-вызов возвращает operation_id; фоновой работой владеет
живой host, shutdown дожидается cancel/cleanup. Статусы: authorizing, staging,
uploading, verifying_size, ready, cancelling, cancelled, failed, uncertain.
Status возвращает байты/процент/прошедшее время, не читает файл заново.
Используем штатный sender/DOM, без патча JS Loginom.

Срок операции: `120 с + ceil(size / 5 МиБ/с)`, максимум 2 ч, плюс прежний
отдельный budget cleanup. Общие IPC 105/120/180 с не увеличиваем глобально:
status/cancel короткие; дедлайн хранится у операции. Успех — active loaders=0,
точный destination, запись FileStore `Type=0`, безопасный целый `Size===size`,
нет ошибки загрузки. Для ≤16 МиБ дополнительно нынешняя SHA-проверка скачиванием;
для >16 МиБ скачивания назад нет. Никаких 32-битных bitwise для size/offset/count.

Отмена штатной кнопкой/жестом sender, ожидание active=0, затем refresh и удаление
только собственного нового частичного destination. Доставка идёт под уникальным
именем в разрешённом каталоге; существующий чужой файл не заменяем для уборки.
Отсутствие записи проверяем полным FileStore текущего каталога. Если сервер
не подтвердил остановку/уборку — `uncertain`, блокировка дальнейшей мутации и
сохранённый receipt для inspect/recovery; повторный start не отправляет байты снова.

Повторное использование: тот же аккаунт/stand/directory/name, точный size и
доверенный журнал sha256 этой операции; свежая native metadata должна совпасть
с receipt (включая Time, если доступно). Совпадение одного имени/размера без
истории не даёт локального происхождения. После внешнего изменения или потери
истории используем новый destination либо явный серверный source; не выдумываем
server SHA. Snapshot удаляем после подтверждённого terminal cleanup.

## Файл на сервере

`storage`-источник содержит точный путь в разрешённом хранилище, stand/account,
native size/mtime и opaque server-source ref. Агент выбирает существующий файл
в файловом диалоге мастера, заполняет `source_path`, не вызывает upload и не
требует фиктивные artifact/upload_operation_id. Для этого расширяем проверку
происхождения text/Excel import явным discriminated source: локальная verified
delivery или server storage ref; произвольная строка из модели не заменяет proof.

Структура узнаётся из мастера (кодировка/формат, ограниченные preview,
определения колонок) и ограниченного вывода узла. Это серверный профиль с
`coverage=preview`, без локального SHA, доказанного полного count и утверждений
о редких ошибках типов. Лимит анализа мастера не используем как ограничение
выполнения: это привело бы к раннему полному импорту вместо работы на sample.

Для полного цикла server-only источника принимаем конкретное решение этапа 2:
штатное скачивание выбранного файла браузером **потоком на диск** в закрытый
локальный cache, затем те же profile/exact scan/sample. Не передаём download
в JS Buffer/base64 или через IPC. До/после сверяем native size/mtime серверной
ссылки и размер локальной копии; изменение инвалидирует операцию. Это отдельная
асинхронная операция со сроком от размера, прогрессом, отменой и уборкой, по
образцу upload. Работа на маленькой выборке требует доставки только sample;
в конце source переключается на исходную server storage ref **без повторной
загрузки полного файла**. Цена решения — один полный download и дисковый cache;
большой download в этих замерах не проверялся и входит в приёмку PR 4.

Если cache/скачивание запрещены владельцем, доступны профиль preview и выбор
готового серверного источника, но цикл sample→full не начинается автоматически.
Без полного локального файла точная локальная сверка невозможна: показываем
ограничение, принимаем только предоставленный владельцем trusted count для
отдельного server-source сценария, не называем его приёмкой локального пути.

Для своего Loginom Server пути вне FileStore требуют отдельного исследования
прав, серверного профилирования/выборки и контрактов соединения «Локальная
файловая система». В облаке имитируем server-source уже загруженным файлом,
никаких предположений о доступности `/home/...` на сервере не делаем.

## Переключение на полный файл и сверка

Отлаживаем сценарий на выборке с сохранённой схемой. Перед переключением:
точный полный проход успешен, полный файл доставлен/выбран, профиль совместим
со схемой sample. Сохраняем пакет и readback колонок/выходного mapping.
У существующего text import меняем **только** `settings.source.source_path`;
не вызываем «Определить типы», не пересоздаём узел и колонки. После закрытия и
повторного открытия мастера сравниваем все names/labels/types/used/data_kind,
порядок и output mapping. Если Loginom пересоздал определения — отказ до расчёта;
нужна явная миграция схемы, а не молчаливое исправление модели.

Настройки полной обработки не должны сохранять ограничение sample. Один
explicit execute полного сценария; проверка импортированного N берёт metadata
полного выходного порта, а не видимые строки grid, capped BufferedStore или
число строк агрегации. Наблюдённый предел grid — 1 000 000; полный N читается
отдельным связанным reader (см. замеры).
Отдельно сверяем бизнес-результат «сумма продаж по регионам». N mismatch,
conversion errors и незавершённый расчёт — FAIL. При timeout сначала inspect
исходной операции; повторный execute запрещён, пока исход не установлен.
В receipt: identity профиля/источника, proof size, exact expected/actual N,
schema before/after, execution_id, Save/cold/cleanup. Модель oracle не получает.

## Ошибки без маскировки

| Код | Значение / действие |
|---|---|
| `LOGINOM_FILE_TOO_LARGE` | Превышен лимит конкретного пути; actual/limit bytes, подсказка profile/sample/path |
| `LOGINOM_FILE_NOT_FOUND` | Исходник исчез или не существует |
| `LOGINOM_FILE_NOT_REGULAR` | Каталог, FIFO, устройство или иной специальный файл |
| `LOGINOM_FILE_ACCESS_DENIED` | OS доступ или разрешение сессии; не повторять обходным путём |
| `LOGINOM_FILE_CHANGED` | Identity/size/mtime/hash изменились; старые profile/sample/grant недействительны |
| `LOGINOM_FILE_FORMAT_AMBIGUOUS` | Недостаточно данных для уверенного диалекта/кодировки |
| `LOGINOM_FILE_INVALID_RECORD` | Структура/тип: logical record, physical line, byte offset, column |
| `LOGINOM_UPLOAD_QUOTA_EXCEEDED` | Нативно подтверждённая квота; не классифицировать все ошибки сети как квоту |
| `LOGINOM_UPLOAD_CANCELLED` | Подтверждённые остановка и уборка |
| `LOGINOM_UPLOAD_UNCERTAIN` | Исход/уборка неизвестны, требуется inspect/recovery |
| `LOGINOM_ROW_COUNT_MISMATCH` | Полный импорт не совпал с точным count |

Первый PR вводит эти типизированные причины и сохраняет существующие
`LOGINOM_INPUT_INVALID`/`LOGINOM_INPUT_IDENTITY_CONFLICT`, не ослабляя admission.
Известные коды сохраняются через inputStore/artifacts → runtime entry →
host-port → hostError allowlist → Node IPC/transport → adapter/tool. Сейчас
`hostError` неизвестные коды превращает в `LOGINOM_HOST_REQUEST_FAILED`, а
runtime generic catch — в `LOGINOM_RUNTIME_FAILED`: оба слоя должны сохранять
структурированную известную причину. Непредвиденные исключения остаются generic.
Details ограничены, без credential/байтов файла/stack; путь только уже
авторизованный для этой сессии. Различаем безопасный отказ до browser effect,
подтверждённый FAIL и uncertain после отправки. Тестируем всю цепочку, не только
функцию allowlist.

## Desktop и инструкции модели

Большое вложение данных **обрабатывается**, а не отклоняется из-за размера.
Порог Desktop — **>16 МиБ на файл**, по границе нынешнего byte admission host;
CLI `--file` — **>10 МиБ**, по границе нынешнего snapshot CLI. Ровно 16/10 МиБ
соответственно и меньшие файлы идут нынешним путём с его совокупными лимитами.
Большие ссылки не входят в бюджет байтов inline-вложений; предел SHA-сверки
серверной копии остаётся 16 МиБ независимо от способа приложения файла.

Desktop picker возвращает descriptor `local_reference` с исходным `sourcePath`
и metadata **до** `readPickedFile`/`readAttachment` в `attachment-picker.ts`.
Renderer не создаёт для него `new File([bytes])` или фиктивный пустой File:
ссылка хранит настоящий размер и не маскируется под малое вложение.
Drag-and-drop использует `getPathForFile` в `prompt-input/attachments.ts` и тот
же descriptor; ветка выбирается до чтения содержимого и `draftStore.putBlob` /
`createBlobReference`. Для большого файла без `sourcePath` (например, вставка
из буфера) — понятный отказ: «У вложения нет пути на диске. Сохраните файл и
приложите его через выбор файла либо укажите путь». Blob не сохраняется даже
временно; малые вложения без пути сохраняют нынешнее поведение.

`build-request-parts.ts` формирует обычный `file` part с правильно экранированным
`file://` URL, по образцу ветки `LOGINOM_PACKAGE_MIME` для `.lgp`; сам `.lgp`
сохраняет свою отдельную обработку. В draftStore/IndexedDB допускаются только
descriptor и ссылка, **без большого blob**; `submit.ts` не вызывает для ссылки
`blobDataUrl`, в сессии нет `data:`/base64 и байтов файла. При восстановлении
черновика/сессии ссылка остаётся ссылкой, без обхода через inline-сериализацию.
`attachment-preview.ts` не декодирует её как текст: вместо текстового превью
модель получает ограниченный профиль через `loginom_file_profile` этой ссылки.
Backend разрешает file URL через `fileURLToPath` и receipt перед авторизацией;
query/fragment запрещены, пробелы, кириллица, `%` и `#` остаются частью пути.
`session/tools.ts` исключает ссылки из byte-групп обычных вложений: большой файл
не читается и не пересылается в host на каждом Dock-вызове. Host получает
авторизованный grant/descriptor по описанному выше пути доставки, с повторным
использованием в пределах действующей generation, а не повторной отправкой bytes.

В момент добавления вложения доверенный native/backend слой фиксирует receipt:
исходный и canonical path, file identity (file ID / dev+ino), size, mtime с
доступной точностью, ctime где доступен. Picker делает это при выборе; для
drag-and-drop — до добавления ссылки в draft, сверяя также File size/lastModified
с native stat. Renderer не является авторитетом identity: receipt хранится
доверенно и связывается с attachment и исходным user-message при отправке;
произвольные metadata/URL модели не создают grant. Отпечаток не обновляется
на более новый файл при отправке, восстановлении сессии или вызове инструмента.

При profile, sample, полном проходе и staging сверяем receipt до/после чтения,
включая canonical target: удалённый файл → `LOGINOM_FILE_NOT_FOUND`, замена,
перенаправление symlink или изменение → `LOGINOM_FILE_CHANGED`. Не прикладываем
автоматически новое содержимое по прежнему имени: требуется новое вложение.
SHA в момент добавления ещё не вычислен; он считается потоком позже и привязан
к исходному receipt и SHA точного прохода по уже описанным правилам snapshot.
Так проверка сохранности не требует чтения нескольких ГБ в picker/renderer.
Вложение даёт чтение без повторного ask через `authorizeLoginomFile`, как в
[дизайне #465, п. 4](2026-10-21-local-file-paths-design.md#общая-авторизация-локального-пути);
явный deny по исходному/canonical пути и права ОС сохраняют приоритет.

CLI `--file` фиксирует такой же receipt при обработке аргумента и для файла
>10 МиБ создаёт `file://` part через `pathToFileURL`, без `fileSnapshot`,
base64 или отказа из-за прежнего 10-МиБ лимита. Передача через CLI в локальный
backend сохраняет reference/receipt и авторизацию вложения. Недоступный backend
путь не разрешается чтением одноимённого файла другой машины (граница доставки
по локальной ссылке описана выше). После принятия большого вложения оба входа
выполняют тот же цикл profile → sample → сценарий → полный файл → один execute
→ сверка; oracle модели не передаётся.

Skill `packages/product/skills/loginom-automation`: большие dataset file-ссылки
(включая CLI >10 МиБ), а также пути >16 МиБ → profile, уточнение
неоднозначного диалекта, sample, сценарий на sample, exact full scan, доставка
полного файла, source patch/readback, один execute, N и business сверка, Save.
Не использовать Read для «посмотреть первые строки» большого датасета:
`read.ts` сканирует весь файл ради total N; код OpenCode `read.ts` не меняем.
Не передавать файл модели целиком, не строить полный сценарий наугад по preview,
не считать sample count или число групп полным N. Серверный путь отделён от
локального; уже имеющийся файл не загружаем повторно.

## Приёмка этапа 2 и генератор

Целевой размер CSV — не меньше 2³² + 1 МиБ по нативным замерам выше. Приёмка
проверяет весь путь продукта на этом размере, включая одновременную сохранность
sample и full source, а не только успешный `setInputFiles`.

В `scripts/node-acceptance/` планируется детерминированный потоковый генератор
CSV и XLSX: seed, точный target bytes/minimum boundary, rows, encoding, dialect,
распределение регионов/NULL, multiline/escaped quotes, late type change.
Генератор пишет блоками, oracle формирует из исходных typed records до
сериализации (целые minor units для сумм), затем независимый parser проверяет
выход. Manifest: точные bytes/sha/rows, типы, ожидаемые региональные суммы,
позиция нарушения. Файлы и oracle вне Git; ожидаемые данные недоступны модели.
Реализация генератора — этап 2, одноразовые файлы замеров его не заменяют.

| Проверка | Критерий |
|---|---|
| Большой CSV | Целевой размер; UTF-8 и cp1251; `;` + decimal comma; LF/CRLF; кавычки, escaped quotes и multiline, header + skip, последний LF без фантомной строки |
| Большой CSV в Desktop-чате | Отдельно picker и drag-and-drop с sourcePath, путь renderer → server без подмены server request: file:// part + доверенный receipt; модель получает профиль; sample→full даёт oracle/N. Нет большого readPickedFile/ArrayBuffer, blob в draftStore/IndexedDB, data:/base64 в сессии и bytes на повторных Dock-вызовах; повторное открытие draft/сессии сохраняет ссылку |
| Большой CSV через CLI --file | Продуктовый standalone CLI, тот же целевой файл: >10 МиБ → file:// + receipt без snapshot/base64 и повторного ask; profile→sample→full, точные суммы/N, Save/cold/cleanup |
| Границы вложений и изменение источника | Desktop: ровно 16 МиБ inline, 16 МиБ+1 ссылкой; CLI: ровно 10 МиБ inline, 10 МиБ+1 ссылкой. Большой файл без sourcePath отклонён до blob/чтения с подсказкой; малый без пути работает. Изменение, удаление, замена inode/symlink после вложения, в том числе до отправки и после восстановления сессии → CHANGED/NOT_FOUND без загрузки нового содержимого; explicit deny важнее вложения |
| Тип глубоко в файле | Изменение после всех быстрых окон; exact scan находит первое нарушение с logical record/physical line/offset; sample не объявляет full validation |
| XLSX | Около 500 тыс. строк, 1–8 колонок, SST, даты, NULL; sample XLSX сохраняет семантику; full N и суммы равны oracle |
| Бизнес-сценарий | «Сумма продаж по регионам» построен на sample; после source switch один full execute, точные N и суммы, schema/mapping сохранены |
| Серверный источник | Заранее загруженный synthetic файл в хранилище пары; ссылка/preview без upload; для sample→full потоковый download/cache и доставка только sample; ноль повторных full upload, exact count по скачанной копии |
| Память | Снимаем baseline/peak RSS agent, host, runtime и renderer, staging/upload отдельно от расчёта; для каждого из первых трёх ΔRSS <128 МиБ и отсутствие роста пропорционально 1→2→4 ГиБ; renderer сверяем с нативным baseline |
| Отказы | Нет файла, каталог, no access (под обычным user), смена inode/mtime/size/байтов при staging/upload, слишком большая запись, неоднозначный dialect; исходные коды доходят до инструмента |
| Cancel/retry | Отмена на 10–30%, active=0, только свой частичный файл удалён, quota/inventory возвращены; повтор operation_id не отправляет файл снова |
| Сохранность | Save и cold на точном SHA через run-check; исходный импорт и результаты не подменены export выборки; cleanup пакета/профиля/больших файлов подтверждён |

Для каждого PR выполняются `required-checks.py list --base large-datasets` и
`verify` по отчёту. Для client — полный закреплённый Chromium набор, runtime/src
— полный host bun test, оснастки — acceptance tests, все полные наборы под
`nice -n 19`. Продуктовые сценарии — штатный `run-check start`, затем `wait`
одной командой; одноразовый Playwright этапа 1 в приёмку продукта не засчитываем.
