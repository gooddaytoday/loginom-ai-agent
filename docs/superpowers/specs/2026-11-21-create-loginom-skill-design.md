# Создание и установка скиллов для Loginom AI Agent

## Решение

В Desktop и CLI поставляется один скилл `create-loginom-skill`. По запросу «создай» он превращает описанную пользователем задачу в переносимую папку скилла. По запросу «установи» принимает готовую локальную папку или ссылку на GitHub. Установка выполняется один раз для пользователя. Со следующего сообщения скилл доступен в обычных чатах обоих приложений, в том числе открытых до установки.

Пользователь выбрал общий каталог исключительно для Loginom. Desktop и CLI читают одну установленную копию. У приложений сохраняются собственные профили. Действующее разделение стабильной, тестовой и разрабатываемой сборок распространяется и на каталог скиллов.

## Рассмотренные варианты

Выбран один встроенный скилл с двумя сценариями. Пользователь формулирует задачу своими словами, а установка готового или только что созданного скилла проходит одинаково. Рассматривался и вариант с отдельным `install-loginom-skill`, как в Codex. У него собственное имя для прямого вызова и отдельная инструкция, которую пришлось бы согласовывать с инструкцией создания. Для обоих сценариев достаточно одного скилла в поставке.

## Создание

1. Агент выясняет, на какой пользовательский запрос должен откликаться скилл и какой результат человек сможет проверить. Уже известные из переписки условия переносит в черновик. Если существенная деталь осталась открытой, использует штатный вопрос с вариантами и рекомендацией, когда этот инструмент доступен.
2. Создаёт переносимую папку `<имя>/SKILL.md` в указанном пользователем месте или в текущем рабочем проекте. В заголовке YAML указывает имя и короткое описание задачи и условий применения. В тексте оставляет инструкции, специфичные для этой задачи. Справку, скрипты и шаблоны добавляет только при реальной необходимости и связывает относительными ссылками. Пути на машине автора и инструменты, доступные только при разработке продукта, в инструкции не попадают.
3. Проверяет формат, ссылки и поведение на характерном запросе с заранее понятным результатом. Например, для скилла проверки таблицы проба должна показать, какие обязательные поля отсутствуют в образце. По близкому постороннему запросу оценивает, достаточно ли точно описание ограничивает применение. Использует безопасные данные и действующие разрешения. Если предметная проверка требует недоступной системы или полномочий, называет, что удалось проверить и что осталось.
4. Возвращает путь к готовой папке и результат проверки. Просьба «создай и установи» сразу ведёт к установке. По одной просьбе «создай» пользователь получает переносимую папку и может передать её коллеге.

Созданная папка с первого дня соответствует формату базовой поставки. Имя каталога совпадает с `name`, имя и описание проходят существующие ограничения продукта. Обычному скиллу достаточно `name` и `description`. Источник истины для допустимых дополнительных полей, длины значений и ссылок на ресурсы — [проверка поставляемых скиллов](../../../packages/loginom-runtime/client/lib/bundled-skill-manifest.mjs).

## Установка

| Что дал пользователь | Что делает агент |
| --- | --- |
| Папку с `SKILL.md` | Читает её на этой машине. Установленная копия продолжит работать после перемещения исходной папки. |
| Ссылку на каталог скилла в GitHub | Берёт выбранный каталог по указанной ссылке вместе с ресурсами. |
| Ссылку на репозиторий | Если в корне есть `SKILL.md`, берёт корневой скилл. Иначе ищет папки со `SKILL.md`. При единственном результате устанавливает его. При нескольких показывает имена и пути и просит выбрать. При отсутствии сообщает об этом. |

Оба источника проходят одну процедуру. Она разбирает заголовок, выбирает имя из `SKILL.md` и проверяет, что его можно безопасно использовать как имя каталога. Описание должно позволять показать скилл модели. Выбранное дерево переносится с ресурсами, без служебных данных Git. Установка не исполняет инструкции или скрипты полученного скилла и не позволяет ссылкам либо путям выйти за пределы выбранного дерева и места установки. Для закрытого GitHub-источника используется уже доступная авторизация, если её поддерживает выбранный способ получения. Если доступа нет, агент сообщает причину и принимает локальную копию.

Имена поставляемых скиллов и защищённые исторические имена берутся из [реестра продукта](../../../packages/product/src/skills.ts). Внешняя установка не может занять такое имя. При повторной установке тех же файлов достаточно сообщить, что скилл уже установлен. Если в общем каталоге под этим именем другое содержимое, обычная просьба об установке сохраняет прежнюю копию и объясняет конфликт. Обновление или удаление установленных скиллов отдельными командами в этот дизайн не входят.

В каталог попадает только полностью подготовленная папка. Ошибка получения или проверки, а также одновременная установка из двух приложений не должны оставить неполный скилл или затереть существующий. Успех означает, что агент проверил установленную копию и может назвать её имя. При совпадении с проектным скиллом учитывается существующий приоритет проекта, а о подмене ожидаемого результата в текущем проекте агент сообщает явно.

## Видимость в работающих приложениях

Общий каталог принадлежит текущему пользователю и каналу Loginom. Его расположение одинаково вычисляют Desktop и CLI, включая CLI с собственным профилем. Запись идёт только в каталог Loginom. Остальные источники скиллов сохраняют существующий порядок относительно друг друга. Общий каталог имеет приоритет пользовательского источника, проект может переопределять обычные имена. Правила защищённых имён остаются прежними.

Сейчас [загрузчик](../../../packages/opencode/src/skill/index.ts) и [список команд](../../../packages/opencode/src/command/index.ts) запоминают каталог по рабочей директории. Копирование папки само по себе не обновляет эти данные. К следующему сообщению каждое уже запущенное приложение должно получить актуальный список для модели и суметь загрузить скилл по имени. Обновление касается пользовательских скиллов и не должно прерывать текущий ответ, сбрасывать чат или требовать связи между процессами Desktop и CLI. Конкретный способ перечитывания и точку подключения установки выбирает исполнитель в плане.

Скилл работает с разрешёнными инструментами текущего чата. Операции над сценарием Loginom при необходимости используют существующий `loginom-automation` и его штатную активацию. Текст стороннего скилла и поля его заголовка не выдают прав. Создание и установка происходят в обычном чате. Ограниченные режимы, в частности редактор дашборда, сохраняют свои права.

## Включение в официальную поставку

Автор получает обычный пользовательский скилл. Решение о включении в поставку принимает владелец продукта. Для включения берут ту же папку, проверяют используемые инструменты и наличие ресурсов в установленном приложении, добавляют её в `packages/product/skills`, резервируют имя и проводят штатные проверки исходного каталога и собранного комплекта. Host уже упаковывает дерево и проверяет его целостность для Desktop и CLI. При обновлении приложения официальная версия защищена от одноимённой пользовательской копии. Эти же правила применяются к самому `create-loginom-skill`. [Правила продукта](../../../packages/product/AGENTS.md)

Дополнительные права, выполнение сборочных шагов и публикация в удалённом каталоге не следуют из установки папки. Подключение особого профиля инструментов требует отдельного решения продукта. Каталог расширений, автоматическое обновление из сети и изменения интерфейса настроек остаются за границами задачи.

## Проверка результата

Первый сквозной пример — открыть обычные чаты Desktop и CLI, дать одному из них локальную папку с простым скиллом и на следующем сообщении в обоих чатах получить его проверяемый результат. Проверку проводят на одном канале, в разных проектах и с уже загруженными списками скиллов. Исходную папку можно переместить до вызова.

Для завершённой функции проверяют также создание скилла по описанию и установку из другого приложения по обычной ссылке GitHub. Сравнивают результат на подходящем запросе и поведение на постороннем. Проверки на конфликт имени, повреждённый источник и попытку записи за пределы выбранной папки должны подтвердить сохранность прежних файлов и защиты базовых скиллов. Проверка комплекта подтверждает, что сам создатель доступен в установленном продукте. В отчёте разделяют фактические прогоны приложений и проверки исходников.

## Использованные практики

У Codex заимствуем короткое описание для выбора скилла и загрузку дополнительных материалов по необходимости. У Claude — проверку на запросах с наблюдаемым результатом. У Cursor — явный выбор области установки с учётом того, кто должен видеть скилл. Формат и права определяет архитектура Loginom.
