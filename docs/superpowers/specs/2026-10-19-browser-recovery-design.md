# Самостоятельное восстановление Loginom через Playwright

Дата: 2026-10-19. Статус: продуктовые решения согласованы с пользователем; независимое spec review — Approved. Это дизайн, без детального плана реализации.

## 1. Цель и согласованные решения

В production release сборках Loginom AI Agent после исчерпания штатного восстановления Loginom Dock самостоятельно переходит к прямому управлению текущим браузером через Playwright. Тот же агент восстанавливает проблемный шаг, runtime проверяет результат и возвращает управление Dock. Пользователю не поручается закрывать мастера, исправлять порты или выполнять другие доступные агенту действия интерфейса.

Согласованы следующие правила:

- Сначала используются применимые штатные способы восстановления Dock. Ошибки параметров исправляются через Dock.
- Временный режим получает тот же агент, в той же сессии и авторизованной вкладке.
- Через Playwright можно завершить проблемный шаг целиком, включая настройку узла и портов. Остаток сценария выполняется через Dock.
- Возврат разрешён после проверки фактического результата и согласования незавершённой операции. Подтверждённые действия не повторяются.
- Модель не меняется автоматически. Для модели с поддержкой изображений используются DOM и скриншоты; для текстовой модели — DOM.
- На проблемный шаг выделяется до 30 браузерных вызовов и 10 минут. Смена operation ID не начинает бюджет заново.
- Если продолжение невозможно, агент сам выполняет доступное безопасное завершение и сообщает фактическое состояние. Неизвестный результат не объявляется успехом; исправление UI не перекладывается на пользователя.

В задачу не входят постоянный доступ модели к браузеру, отдельный агент восстановления, модельный цикл внутри Dock, автоматическое переключение модели, восстановление всего сценария через Playwright, исправления отдельных Dock-скриптов и распространение режима на dev/beta. Дизайн не заменяет существующие разрешения на выполнение пользовательской задачи.

## 2. Основание

Исследование release 0.2.2 и закреплённых snapshots `origin/demo-022` / `origin/nodes-wave2` не обнаружило такого перехода. В managed runtime уже существует авторизованный BrowserContext и внутренний Playwright, но raw browser tools скрыты от модели. Инструкции запрещают обходить Dock через Playwright. Незавершённая операция может блокировать новые мутации даже после изменения operation ID.

В изученных эпизодах встречались ошибки выходного mapping, незакрытые мастера и потеря подтверждения уже выполненного действия. Были и успешные исправления неверных параметров без браузерного fallback. Поэтому любой отказ инструмента не является достаточным основанием для перехода.

Текущий `interrupt` отправляет отмену исполнителю, но сам по себе не подтверждает прекращение его действий. Существующее завершение runtime закрывает браузер. Для восстановления требуется передать владение, сохранив контекст.

Backend способен доставлять MCP image модели. Однако prod допускает текстовые модели, поэтому способность анализировать скриншот проверяется отдельно.

Это выводы статического анализа и предыдущего исследования логов. Работоспособность предлагаемого механизма ещё не проверена: реализации пока нет.

## 3. Выбор подхода

| Подход | Преимущество | Дополнительная сложность |
| --- | --- | --- |
| **Тот же агент, временные browser tools — выбран** | Сохраняет задачу и историю; использует текущий цикл модели и браузер | Нужны передача владения и согласование результата |
| Отдельный агент восстановления | Узкий контекст и отдельная инструкция | Передача задачи, состояния и результата между двумя исполнителями |
| Модельный цикл внутри Dock | Основной агент сохраняет прежний интерфейс вызова | Dock получает собственную оркестрацию модели и новые зависимости |

Выбран первый подход. Для него достаточно расширить существующие границы product launch, host/runtime и agent tool loop. Отдельный сервис или второй браузер не требуются. Сессия не переводится целиком в исследовательский режим `research`: восстановление является временной фазой managed runtime.

## 4. Доступность только в production release

Разрешение вычисляет продуктовый launcher из метаданных сборки и упаковки, затем передаёт host/runtime как внутреннюю capability. Модель и параметры её инструментов не могут включить эту capability.

| Запуск | Доступность |
| --- | --- |
| Упакованный prod release CLI со штатным проверенным bundle | Включена |
| Упакованный prod release Desktop со штатными resources | Включена |
| Dev, beta, запуск из исходников | Выключена |
| Подмена канала профиля через `LOGINOM_AI_AGENT_CHANNEL=prod` у другой сборки | Остаётся выключенной |
| Внешний development bundle вместо штатного CLI bundle | Выключена |
| Недостаточно метаданных для определения release | Выключена |

Release-процесс фиксирует признак production release в артефакте; runtime не выводит его из изменяемой переменной рабочего профиля. В CLI учитываются встроенный канал/версия и успешная проверка manifest штатного bundle; в Desktop — встроенные release-метаданные и packaged-запуск. Это ограничение продуктовой функциональности, не новая система криптографического подтверждения официальной публикации.

Host/runtime проверяет capability и при публикации инструментов, и при каждом вызове. Скрытого имени инструмента недостаточно для доступа. Изменение промпта или каталога без проверки на границе исполнения не удовлетворяет этому требованию.

## 5. Условия перехода

Штатное восстановление исчерпано, если runtime не предлагает применимого продолжения либо применимые способы уже использованы и не дали подтверждённого продвижения. Повтор той же операции с новым ID, прежними параметрами или другой оболочкой вызова не является новым способом восстановления.

| Ситуация | Действие |
| --- | --- |
| Проверяемая ошибка параметров до изменений | Исправить параметры и продолжить через Dock |
| Операция ещё выполняется | Ожидать её по существующей идентичности |
| Есть применимый штатный recovery / resume | Использовать его; оценить фактическое продвижение |
| Штатное восстановление недоступно или исчерпано | Подготовить передачу управления Playwright |
| Вызов завершился, но эффект неизвестен | После передачи начать с наблюдения, не повторять действие |
| Вызов потенциально ещё выполняется | Не допускать браузерные действия, пока прекращение исполнения не подтверждено |
| Отказ в разрешении, отмена пользователя, отсутствующие исходные данные | Не обходить ограничение через браузер |

Runtime предоставляет структурированное основание перехода и контекст сбоя; решение не строится только на поиске слов в сообщении об ошибке. Модель оценивает смысл исправления, runtime отвечает за допустимость действий и текущего владельца браузера.

Инструкции агента требуют перейти к recovery при таком основании, а цикл агента обрабатывает его до обычного завершения ответа о технической неудаче: формирует следующий ход с контекстом восстановления. Это продолжение текущей задачи, без нового пользовательского запроса. Если модель не выполняет восстановление, ситуация учитывается как отсутствие продвижения и завершается по правилам ограниченной попытки, а не бесконечным повторением инструкции.

## 6. Владение браузером и состояния

Во всех фазах браузером управляет не более одного исполнителя. Режим принадлежит текущей managed-сессии и конкретному проблемному шагу, а не глобальному процессу модели.

| Состояние | Разрешённые действия | Условие выхода |
| --- | --- | --- |
| `dock` | Штатные инструменты Dock | Исчерпание восстановления → `handoff` |
| `handoff` | Завершение/отмена старого исполнителя и проверка его остановки; новые управляющие действия запрещены | Исполнитель завершён и контекст доступен → `browser`; иначе `stopped` |
| `browser` | Прямые действия Playwright в текущей вкладке; Dock не управляет страницей | Запрос проверки → `verify`; лимит/отмена/невозможность → `stopped` |
| `verify` | Наблюдение и согласование результата runtime; новые действия модели запрещены | Подтверждённое продолжение → `dock`; исправимый пробел и оставшийся бюджет → `browser`; иначе `stopped` |
| `stopped` | Сохранение фактов и доступное безопасное завершение | Нет автоматического повторного запуска той же попытки |

Передача начинается с запрета новых управляющих вызовов Dock и ожидания завершения уже принятого исполнения. Отправленный abort и истёкший transport timeout не равны подтверждённой остановке. Не используются второй браузер, новый login или отдельный CDP endpoint.

Изменение доступных инструментов учитывается на следующем ходе модели. Вызовы из старого каталога, параллельные вызовы и запоздавшие ответы проверяются по текущему состоянию и контексту восстановления; они не могут вернуть прежнему исполнителю право изменять страницу.

Закрытие сессии и отмена пользователем прекращают recovery по существующим правилам отмены. После падения процесса журнал сохраняет неопределённость; открытие нового чата не означает снятия блокировки. Автоматическое возобновление модели после падения процесса не добавляется. При следующем явно запущенном продолжении сначала устанавливаются владелец и фактическое состояние.

## 7. Контракт восстановления

Контракт описывает данные на границах компонентов, а не окончательные имена API.

**Вход в восстановление** содержит исходную операцию и запрос; идентичность сессии, пакета, workflow и узла/портов; проблемную фазу; подтверждённые фазы; возможные неподтверждённые эффекты; уже использованные способы recovery; наблюдаемый результат, необходимый для завершения шага; остаток бюджета. Если выполнение узла, сохранение пакета или получение файла входит в шаг, это явно отражено в цели.

**Работа в браузере** использует существующий внутренний Playwright и инструменты наблюдения/взаимодействия: DOM/snapshot, скриншоты, клики, ввод, выбор, прокрутку, клавиши, диалоги и ожидание. Действия направлены на текущую задачу в существующей вкладке. Вместо заранее определённой процедуры `node_apply` конкретное следующее UI-действие выбирает модель по текущему наблюдению. Запуск и редактирование файлов Dock, shell-команды и прямые серверные API для обхода его состояния не являются этим режимом.

Сначала агент получает свежий DOM; для image-capable модели также скриншот. После изменения экрана обновляет наблюдение, прежде чем использовать устаревшие элементы. Нужен реальный image content в сообщении модели, а не путь к PNG. Доступность image определяется `model.capabilities.input.image`. Для текстовой модели image не передаётся ни в tool result, ни отдельным сообщением; продолжается работа по DOM. Если визуальные сведения оказались необходимы и DOM недостаточен, результат остаётся неподтверждённым — модель не заменяется автоматически.

**Запрос проверки** содержит ссылку на исходный контекст восстановления, выполненные действия и предполагаемый результат. Самоотчёт модели служит объяснением, но не достаточным основанием для закрытия pending.

**Ответ проверки** возвращает один из трёх результатов: `completed`, `continuable` или `unresolved`, подтверждённые факты и конкретное следующее допустимое действие. Это различие сохраняется в журнале и ответе модели.

## 8. Проверка и возврат к Dock

Runtime проверяет постусловия исходного шага доступным чтением фактического состояния. Для настройки это идентичность существующего узла, нужные настройки и mappings/связи портов; для выполнения — наблюдаемое завершение соответствующего выполнения; для сохранения и экспорта — соответствующий сохранённый пакет или требуемый файл. Закрытый диалог и отсутствие ошибки сами по себе не доказывают выполнение шага.

Проверка не вызывает проблемный `node_apply` заново и не требует того же сломанного предиката как единственного доказательства. Например, ошибка проверки полного размещения кнопки внутри панели не должна блокировать признание уже применённого mapping, если его состояние достоверно читается. При этом неподтверждённые настройки не объявляются подтверждёнными только по словам модели или наличию кнопки «Готово» на скриншоте. Если независимое наблюдение требуемого результата недоступно, ответ — `unresolved`.

| Результат | Смысл | Продолжение |
| --- | --- | --- |
| `completed` | Требуемые постусловия проблемного шага подтверждены | Dock выполняет следующий шаг |
| `continuable` | Подтверждено состояние, из которого Dock может закончить оставшуюся часть | Dock продолжает с указанной фазы на существующем объекте |
| `unresolved` | Есть неизвестный эффект или недоказанное постусловие | Дополнительное наблюдение/исправление в пределах бюджета либо остановка |

`continuable` не является разрешением без изменений повторить заведомо сломанную процедуру. Нужны подтверждённое изменение состояния и конкретное основание, почему оставшееся действие теперь допустимо. Если Dock снова сталкивается с той же проблемой, это продолжение прежней попытки с оставшимся бюджетом.

Результат проверки согласует существующие записи host/runtime об операции и блокировке. Исходная ошибка и прежние квитанции сохраняются; результат ручного восстановления записывается отдельно со ссылкой на исходную операцию. Выполненное через Playwright действие не превращается задним числом в успешную квитанцию прежнего Dock-вызова. Точная повторная доставка старого запроса не исполняет его заново; сообщает исходный результат и связанный итог recovery.

Перед возвратом runtime подтверждает пригодное для следующего шага состояние страницы, отсутствие мешающего собственного мастера/диалога и отсутствие другого исполнителя. Снятие блокировки и разрешение следующего шага происходят только после записи результата согласования. Незавершённая запись при сбое не разрешает мутации автоматически. Закрываются только относящиеся к восстановлению блокировки, а не весь журнал профиля.

Для продолжения Dock получает свежие наблюдения состояния и портов, а также актуальные ссылки на элементы UI. Ссылки и наблюдения, полученные до ручных изменений, не используются как действующие.

Потеря подтверждения исполнения или экспорта сначала требует наблюдения результата. Повторное выполнение ради получения новой квитанции запрещено. Если идентичность результата нельзя связать с требуемым действием, старые данные в preview не считаются доказательством его успеха.

## 9. Бюджет и остановка

Бюджет одной попытки — 30 вызовов браузерных инструментов, включая чтение, и 10 минут с начала `handoff`; действует первый достигнутый предел. Бюджет общий для переходов `browser` → `verify` → `browser` и возврата Dock к тому же незавершённому шагу. Новый operation ID, переформулировка ошибки или повторный вход в режим его не сбрасывают. Новый бюджет появляется для следующего самостоятельного шага после подтверждённого завершения прежнего.

Собственные наблюдения runtime при передаче и проверке не являются вызовами модели, но входят во временной предел. На исчерпании лимита не принимаются новые модельные браузерные действия. Уже принятое действие сначала завершается или отменяется с установлением результата; таймер не даёт права запустить второго исполнителя.

Для ранней остановки учитывается повтор одного действия над тем же наблюдаемым состоянием без нового основания. После двух таких безрезультатных повторов дальнейшее повторение запрещено: допустим иной обоснованный способ в остатке бюджета или остановка. Непрерывное выполнение операции с наблюдаемым прогрессом не приравнивается к такому повтору. Сохранение новых ID не считается прогрессом.

Агент объясняет, что проверяет или меняет, и прекращает попытку раньше лимита, если браузер недоступен, прекращение исходного исполнения не установлено или нет следующего обоснованного действия. Общие ограничения и отмена текущей задачи имеют приоритет над бюджетом recovery.

Остановка не означает безусловный rollback. Runtime может отменить принадлежащий попытке неприменённый draft, если это безопасно и исполнитель остановлен. Он не удаляет уже созданные узлы, не повторяет выполнение и не отбрасывает неизвестные эффекты ради очистки журнала. Если безопасная очистка невозможна, сохраняется блокировка с причиной. Состояние `stopped` не переходит в Dock только из-за закрытия диалога или окончания таймера.

Пользователь получает конкретное сообщение: что выполнено, подтверждено ли сохранение, где остановилась задача и что осталось неизвестным. Формулировка «исправьте сценарий вручную» не является штатным выходом. Запрос недостающего файла, доступа или смыслового решения допустим, когда это действительно необходимо; он отличается от поручения чинить интерфейс. При недоступности браузера или истощении бюджета задача может остаться незавершённой — это сообщается честно.

## 10. Ответственность существующих компонентов

| Граница | Ответственность | Основание решения |
| --- | --- | --- |
| Product launcher CLI/Desktop | Разрешает capability только для prod release | Проверяемые метаданные сборки/упаковки |
| Host и managed runtime | Владелец браузера, состояния перехода, бюджет, привязка операции, допуск вызовов | Текущее исполнение и журнал |
| Каталог/bridge и agent tool loop | Публикуют нужные инструменты, доставляют контекст и изображения, продолжают задачу | Разрешение runtime и capability модели |
| Тот же агент | Выбирает UI-действия по наблюдениям, выполняет проблемный шаг, запрашивает проверку | Пользовательская задача, цель шага, DOM и при возможности скриншоты |
| Проверка результата в runtime | Подтверждает постусловия, согласует pending и точку продолжения | Наблюдения реального состояния, а не самоотчёт модели |

Инструкции `loginom-automation` и browser recovery должны описывать согласованный временный режим. Общий запрет произвольного обхода runtime сохраняет смысл вне этого режима; внутри него прямые действия Playwright являются штатной разрешённой работой. Не добавляются вторая оркестрация модели, новый глобальный владелец браузера или отдельная база состояния recovery.

## 11. Наблюдаемость и критерии приёмки

В существующем журнале связываются исходная ошибка, состояние и фаза шага, попытки штатного восстановления, начало и окончание handoff, браузерные действия, остаток бюджета, результат проверки и первое последующее действие Dock. DOM/изображения используются в рамках существующих правил хранения артефактов. Журнал не должен называть успешной попытку, которая только сняла блокировку, но не позволила продолжить задачу.

| Проверяемый случай | Требуемый результат |
| --- | --- |
| Ошибка mapping или настройки узла; native recovery исчерпан | Тот же агент выполняет необходимое действие Playwright в той же вкладке; проверка подтверждает результат; Dock успешно продолжает; итог задачи корректен |
| Сломанный DOM-предикат исходной процедуры | Завершённое вручную действие подтверждается чтением результата без повторного прохождения того же ошибочного условия |
| Потеря ответа после фактического выполнения/экспорта | Выполнение не дублируется; подтверждается соответствующий результат либо сохраняется неопределённость |
| Восстановлена только часть шага | Продолжение с подтверждённой точки на существующем узле; нет повторного создания и повторения подтверждённых действий |
| Неверные параметры до изменений | Обычное исправление через Dock, без входа в browser recovery |
| Потенциально живой старый исполнитель и поздний ответ | Ни одного конкурирующего browser-действия; поздний ответ не меняет текущего владельца |
| Попытка вызвать Dock в browser-фазе или Playwright вне неё | Вызов отклоняется на границе исполнения, даже если имя известно модели |
| Повторная ошибка, смена ID и возврат через `continuable` | Бюджет сохраняется; нет бесконечного цикла режимов |
| Истечение лимита, пользовательская отмена, падение runtime | Нет ложного успеха и автоматической очистки неизвестного эффекта; сохраняется пригодный для диагностики результат |
| Текстовая модель | Восстановление по DOM; image не отправляется; модель не меняется |
| Модель с поддержкой изображений | Скриншот приходит настоящим image content и доступен анализу модели |
| Prod CLI и Desktop | Полный путь восстановления работает на упакованных release-артефактах |
| Dev/beta/source и подмена env-канала | Новый режим отсутствует и не включается прямым вызовом скрытого инструмента |

Проверки переходов, допуска вызовов и согласования результата дополняются сквозными прогонами на реальном Loginom. Как минимум нужны подтверждённые случаи восстановления настройки и портов, продолжения через Dock и сохранения/получения требуемого результата. Искусственно вызванный отказ допустим для воспроизводимости, но успешный unit-тест или вызов Playwright сам по себе не доказывает выполнение задачи. Частота успешного восстановления оценивается отдельно от корректности расчёта и от соблюдения маршрута Dock → Playwright → Dock.
