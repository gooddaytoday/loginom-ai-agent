# Самостоятельное восстановление Loginom через Playwright

Дата: 2026-10-19. Редакция 2: ревью по коду кандидата `demo-022` (`b484b275de`) и решения владельца от 19.10. Это дизайн, без детального плана реализации.

## 1. Цель и согласованные решения

В production release сборках Loginom AI Agent после исчерпания штатного восстановления Loginom Dock самостоятельно переходит к прямому управлению текущим браузером через Playwright. Тот же агент восстанавливает проблемный шаг, runtime выполняет общую проверку результата и возвращает управление Dock. Пользователю не поручается закрывать мастера, исправлять порты или выполнять другие доступные агенту действия интерфейса.

Согласованы следующие правила:

- Сначала используются применимые штатные способы восстановления Dock. Ошибки параметров исправляются через Dock.
- Временный режим получает тот же агент, в той же сессии и авторизованной вкладке.
- Модели выдаётся ограниченный allowlist штатных инструментов Playwright MCP через тот же bridge, что и у Dock (раздел 7).
- Через Playwright можно завершить проблемный шаг целиком, включая настройку узла и портов. Остаток сценария выполняется через Dock.
- Возврат разрешён после общей проверки runtime (раздел 8). Настройки, выполненные в браузере, подтверждаются отчётом модели и помечаются `attested_by_model`; runtime не объявляет их проверенными.
- Подтверждённые действия не повторяются. При потере подтверждения сначала наблюдается результат; повтор через Dock допустим только для идемпотентного эффекта.
- Модель не меняется автоматически. Для модели с поддержкой изображений используются DOM и скриншоты; для текстовой модели — DOM.
- На проблемный шаг выделяется до 30 браузерных вызовов модели и 10 минут с входа в фазу `browser`. Смена operation ID не начинает бюджет заново.
- Режим включается флагом сборки, а не переменной окружения (раздел 4).
- Первая версия охватывает все классы раздела 5, включая потерю подтверждения выполнения, экспорта/скачивания, доставки и сохранения.
- Если продолжение невозможно, агент сам выполняет доступное безопасное завершение и сообщает фактическое состояние. Неизвестный результат не объявляется успехом; исправление UI не перекладывается на пользователя.

В задачу не входят постоянный доступ модели к браузеру, отдельный агент восстановления, модельный цикл внутри Dock, автоматическое переключение модели, восстановление всего сценария через Playwright, исправления отдельных Dock-скриптов, новые читатели настроек отдельных типов узлов и распространение режима на dev/beta. Дизайн не заменяет существующие разрешения на выполнение пользовательской задачи.

## 2. Основание

В release 0.2.2 и в `demo-022` такого перехода нет. Managed runtime уже держит авторизованный BrowserContext и один клиент Playwright MCP 0.0.82: executor выполняет свои процедуры через `browser_run_code_unsafe`, а сырые browser tools в профиле `user-v1` скрыты от модели. Навык запрещает обходить Dock через Playwright. Незавершённая операция блокирует новые мутации даже после смены operation ID.

Тупики, которые режим заменяет, точно известны в коде:

- освобождение остановленной `node.apply` отказывает с `user_action` — «попросите пользователя закрыть мастер или диалог кнопкой Отмена»;
- навык при пустых `recovery_options` без `user_action` велит сообщить operation ID, фазу и причину и остановиться.

Исходное исследование опиралось на release 0.2.2 и серию LAB-77 (более ранняя dev-сборка; 28 из 33 технических отказов — на `output_mapping`). В `demo-022` с тех пор вошли исправления этого класса (загрузка исходных полей Calculator `c3d8296b5f`, допуск правой границы строк mapping), подтверждения скачивания экспорта, DOM-owner при скрытой навигации и перенастройки неактивных существующих узлов. Серия LAB-81 `lab81-7a` на этом кандидате прошла 12 из 12, включая кейсы с 0/3 в LAB-77. Остаточные классы по прогонам 18.10: не наблюдён DOM-owner, `UI_SCAN_LIMIT`, `WIZARD_OPEN_NOT_CONFIRMED`, ожидание готовности, подтверждение журнала JS, скачивание на медленном хосте. Это длинный хвост распознавания UI: именно его закрывает прямое управление, тогда как частые классы продолжают исправляться в обработчиках.

Существующие `*-readback.mjs` — проекции собственных квитанций Dock, а не чтение настроек узла. Независимого читателя нативных настроек для каждого типа узла нет, поэтому строгая проверка настроек после ручных действий в первой версии недоступна (раздел 8).

Текущий `interrupt` отправляет отмену исполнителю, но не подтверждает прекращение его действий. Код executor, запущенный через Playwright MCP, нельзя прервать без закрытия браузера, а существующее завершение runtime закрывает браузер. Для восстановления требуется передать владение, сохранив контекст.

Backend доставляет MCP image модели как вложение. Для модели без поддержки изображений изображение сейчас превращается в текст «ERROR: Cannot read image … Inform the user», который подталкивает к остановке.

Это выводы статического анализа кода и предыдущего исследования журналов. Работоспособность механизма ещё не проверена: реализации нет. Приложения исследования хранятся вне git и не нормативны.

## 3. Выбор подхода

| Подход | Преимущество | Дополнительная сложность |
| --- | --- | --- |
| **Тот же агент, временные browser tools — выбран** | Сохраняет задачу и историю; использует текущий цикл модели и браузер | Нужны передача владения и общая проверка результата |
| Отдельный агент восстановления | Узкий контекст и отдельная инструкция | Передача задачи, состояния и результата между двумя исполнителями |
| Модельный цикл внутри Dock | Основной агент сохраняет прежний интерфейс вызова | Dock получает собственную оркестрацию модели и новые зависимости |

Выбран первый подход. Для него достаточно расширить существующие границы product launch, host/runtime и agent tool loop. Отдельный сервис или второй браузер не требуются. Сессия не переводится целиком в режим `research`: восстановление является временной фазой managed runtime.

Инструменты UI-ремонта диагностического профиля (`dock_workspace_observe`, `dock_ui_action` с `recovery_operation_id`, `dock_operation_recover`) не используются как основа режима. Они работают через то же DOM-распознавание Dock, которое и отказало, а `dock_ui_action` запрещён, пока висит `node.apply`.

## 4. Доступность: флаг сборки

Разрешение задаётся константой, которую вшивает сборка, и записывается в метаданные артефакта для диагностики. Продуктовый launcher передаёт его host, host — runtime через private start input как внутреннюю capability. Модель и параметры её инструментов не могут включить режим.

| Запуск | Доступность |
| --- | --- |
| Упакованный prod release CLI со штатным проверенным bundle | Включена: release-процесс всегда ставит флаг |
| Упакованный prod release Desktop со штатными resources | Включена |
| Приёмочная или eval-сборка, в которой флаг задан явно при сборке | Включена — для проверки режима до выпуска |
| Dev, beta, запуск из исходников без флага | Выключена |
| `LOGINOM_AI_AGENT_CHANNEL=prod` или иная переменная в рантайме | Не влияет |
| Внешний bundle через `LOGINOM_AI_AGENT_CLI_BUNDLE` или непроверенный manifest | Выключена |
| Desktop не в packaged-режиме | Выключена |

Канал сборки уже вшивается при сборке, а `LOGINOM_AI_AGENT_CHANNEL` в рантайме меняет только профиль; новый флаг следует тому же принципу. Это ограничение продуктовой функциональности, а не криптографическое подтверждение публикации.

Host/runtime проверяет capability и при публикации каталога, и при каждом вызове. Скрытого имени инструмента недостаточно для доступа.

## 5. Условия перехода

Runtime выдаёт структурированное основание перехода — `next_step` на `dock_browser_recovery` с кодом причины, идентичностью шага и остатком бюджета. Решение не строится на поиске слов в сообщении об ошибке. Модель оценивает смысл исправления, runtime отвечает за допустимость действий и владельца браузера.

| Триггер | Состояние runtime |
| --- | --- |
| T1 | Освобождение остановленной операции отказало с `NODE_RELEASE_REFUSED` и `user_action` |
| T2 | Inspect не предлагает `recovery_options` и `user_action`, последний вызов браузера завершён |
| T3 | Та же фаза того же узла отказала с тем же кодом после освобождения и новой операции над существующим узлом |
| T4 | Потеряно подтверждение выполнения, экспорта/скачивания, доставки или сохранения, и inspect/release не установили результат |

Не являются триггерами: отказ `NOT_APPLIED` с `effect_possible=false` и `next_step` (исправляется через Dock); операция в состоянии `running` (ожидается по своей идентичности); `LOGIN_REQUIRED`; отказ в разрешении; отмена пользователем; отсутствие исходных данных. Если исход последнего вызова браузера не установлен, режим не начинается: попытка завершается `stopped` с честным отчётом.

Модель управляет попыткой вызовами `dock_browser_recovery` (`start`, `finish`, `stop`). Если при активной попытке модель завершает ход текстом, агентский цикл добавляет одно напоминание на попытку. Повторное завершение хода считается отсутствием продвижения и ведёт к `stopped`, а не к бесконечному повторению инструкции.

## 6. Владение браузером и состояния

Во всех фазах браузером управляет не более одного программного исполнителя. Режим — это аренда браузера в bridge, принадлежащая текущей managed-сессии и конкретному шагу. События записываются в существующий execution journal; отдельной базы состояния нет.

| Состояние | Разрешённые действия | Условие выхода |
| --- | --- | --- |
| `dock` | Штатные инструменты Dock | Триггер раздела 5 и вызов `start` → `handoff` |
| `handoff` | Запрет новых управляющих вызовов Dock; ожидание доказательства остановки executor | Последний вызов завершён, его browser-квитанция `completed` с cleanup → `browser`; иначе `stopped` |
| `browser` | Allowlist Playwright в текущей вкладке; Dock не управляет страницей | `finish` → общая проверка; лимит, отмена, невозможность → `stopped` |
| общая проверка | Только чтения runtime; действия модели запрещены | `completed`/`continuable` → `dock`; `unresolved` при остатке бюджета → `browser`; иначе `stopped` |
| `stopped` | Сохранение фактов и доступное безопасное завершение | Нет автоматического повторного запуска той же попытки |

Ожидание в `handoff` не превышает остатка исходного срока операции. Отправленный abort и истёкший transport timeout не равны подтверждённой остановке. Не используются второй браузер, новый login или отдельный CDP endpoint.

Изменение доступных инструментов учитывается на следующем ходе модели: каталог перечитывается на каждом шаге. Вызовы из старого каталога, параллельные вызовы и запоздавшие ответы проверяются по текущему состоянию аренды и не возвращают прежнему исполнителю право изменять страницу.

В Desktop пользователь видит то же окно и может действовать в нём сам. Эксклюзивность относительно человека не гарантируется, поэтому проверка всегда перечитывает фактическое состояние.

Закрытие сессии и отмена пользователем прекращают recovery по существующим правилам отмены. После падения процесса журнал сохраняет неопределённость; открытие нового чата не снимает блокировку. Автоматическое возобновление после падения не добавляется.

## 7. Контракт восстановления

**Вход в восстановление** содержит исходную операцию и запрос; идентичность сессии, пакета, workflow и узла/портов; проблемную фазу; подтверждённые фазы; возможные неподтверждённые эффекты; уже использованные способы recovery; наблюдаемый результат, нужный для завершения шага; остаток бюджета. Если выполнение узла, сохранение пакета или получение файла входит в шаг, это явно отражено в цели.

**Allowlist инструментов Playwright MCP:** `browser_snapshot` (с `target`, `depth`, `boxes`), `browser_find`, `browser_take_screenshot` (только для image-модели), `browser_click`, `browser_hover`, `browser_type`, `browser_press_sequentially`, `browser_press_key`, `browser_fill_form`, `browser_select_option`, `browser_check`, `browser_uncheck`, `browser_drag`, `browser_mouse_*_xy`, `browser_mouse_wheel`, `browser_handle_dialog`, `browser_wait_for`.

Всё остальное запрещено на границе исполнения, в том числе:

| Инструменты | Причина запрета |
| --- | --- |
| `browser_evaluate`, `browser_run_code_unsafe`, `browser_webmcp_*` | Произвольный код и инструменты страницы |
| `browser_navigate*`, `browser_reload`, `browser_tabs`, `browser_close` | Потеря несохранённого пакета и подготовленного документа |
| cookies, local/session storage, `browser_storage_state`, `browser_set_storage_state` | Доступ к авторизованной сессии |
| `browser_network_*`, `browser_route*` | Сетевой трафик и токены |
| `browser_file_upload`, `browser_drop` | Локальные файлы пользователя |
| `browser_resize`, `browser_emulate_media` | Нарушают инварианты геометрии Dock: DPR 1, null viewport |
| pdf, tracing, video, recording, highlight, annotate, `browser_resume` | Не нужны для восстановления |

После каждого действия runtime проверяет тот же origin Loginom, единственную страницу и наличие подготовленного документа. Иначе попытка переходит в `stopped`.

**Ответы.** По умолчанию Playwright MCP прикладывает к каждому действию полный snapshot (`config.snapshot.mode` = `full`). Для recovery задаётся режим без полного снимка; модель читает поддеревья через `target`/`depth` и `browser_find`. Изображение не входит в текстовый лимит ответа `user-v1` (46 000 байт); в журнал пишутся хэш и размеры, а не само изображение.

**Модели без изображений.** Для них агент не публикует инструмент скриншота: возможность определяется `model.capabilities.input.image`. Работа идёт по DOM. Если визуальные сведения оказались необходимы и DOM недостаточен, результат остаётся неподтверждённым — модель не заменяется автоматически.

Новые инструменты проходят тот же permission-путь, что `loginom_*`: запросов разрешения посреди recovery нет. Ожидаемое ограничение — создание связей перетаскиванием портов: Loginom проверяет совместимость асинхронно, и managed-drag Dock держит мышь до подтверждения цели.

Запуск и редактирование файлов Dock, shell-команды и прямые серверные API для обхода его состояния не являются этим режимом.

**Запрос `finish`** содержит выполненные действия, предполагаемый результат и список настроек, сделанных в браузере. Этот отчёт модели фиксируется как `attested_by_model`, но pending не закрывает.

**Ответ проверки** возвращает `completed`, `continuable` или `unresolved`, проверенные runtime факты, отдельный список `attested_by_model` и конкретное следующее допустимое действие.

## 8. Проверка и возврат к Dock

Общая проверка — композиция существующих читателей runtime по классу шага. Проблемный `node_apply` при этом не вызывается заново, и сломанный предикат исходной процедуры не нужен.

| Что проверяется | Чем |
| --- | --- |
| Рабочее место | Release-proof `releasePendingNode`: тот же разблокированный узел на тихом графе, без мастера, диалога и маски, два одинаковых чтения графа. Для recovery выполняется независимо от того, есть ли у остановленной фазы собственный верификатор |
| Выполнение узла | Новая завершённая группа процессов этого узла относительно базовой линии операции (`identifyNewExecution`) |
| Выход узла | Схема выходного порта (`readNodePreviewSchema`) |
| Экспорт | Строка File Storage (имя, размер) и проверенная по байтам локальная копия через существующий lease |
| Доставка входного файла | `verifyArtifact` |
| Сохранение пакета | Путь и dirty-state сохранённого пакета |
| Настройки узла | Отчёт модели, `attested_by_model` |

| Результат | Смысл | Продолжение |
| --- | --- | --- |
| `completed` | Проверенные факты покрывают наблюдаемый результат шага: выполнение и схему, файл, сохранённый пакет | Dock выполняет следующий шаг |
| `continuable` | Узел освобождён на тихом графе, но результат шага ещё не получен | Dock продолжает новой операцией над `existing`-узлом с полными настройками — существующий `next_step` после освобождения |
| `unresolved` | Рабочее место не тихое или нужного факта нет | Работа в остатке бюджета либо `stopped` |

`continuable` не разрешает повторять заведомо сломанную процедуру: если та же фаза снова отказывает с тем же кодом (T3), это продолжение прежней попытки с оставшимся бюджетом.

Результат проверки записывается отдельной recovery-квитанцией со ссылкой на исходную операцию. Исходная операция остаётся `FAILED`/released, её ошибка и прежние квитанции сохраняются; ручное действие не превращается задним числом в успешную квитанцию Dock. `dock_node_read` принимает recovery-квитанцию как `source_operation_id`, если в ней проверены выполнение и схема выхода; чтение по-прежнему выполняет узел свежо и сравнивает схему. Точная повторная доставка старого запроса не исполняет его заново и сообщает исходный результат и связанный итог recovery.

Снятие блокировки и разрешение следующего шага происходят только после записи квитанции. Незавершённая запись при сбое не разрешает мутации автоматически. Закрываются только относящиеся к восстановлению блокировки, а не весь журнал профиля. Для продолжения Dock получает свежие наблюдения и ссылки на элементы UI; полученные до ручных изменений недействительны.

**Потеря подтверждения.** Сначала наблюдается результат по таблице выше. Если наблюдение не установило результат, повтор через Dock разрешён только для идемпотентного эффекта — выполнения узла или экспорта с заменой файла. Экспорт в режиме дописывания, Save As с конфликтом и запись во внешнюю БД остаются `unresolved`. Старые данные preview, не связанные с требуемым действием, не доказывают его успех.

Итоговый ответ пользователю перечисляет, что сделано через браузер и подтверждено только моделью.

## 9. Бюджет и остановка

Бюджет попытки — 30 вызовов браузерных инструментов модели, включая чтение, и 10 минут с входа в `browser`; действует первый достигнутый предел. Ожидание в `handoff` и проверки runtime ограничены отдельно существующими сроками: остаток исходного срока операции, release-proof до 90 с. Бюджет общий для повторных входов в `browser` и для возврата Dock к тому же незавершённому шагу.

Идентичность шага — документ, workflow, узел и фаза; для сохранения — документ и путь пакета. Новый operation ID, переформулировка ошибки или повторный вход в режим бюджет не сбрасывают. Новый бюджет появляется для следующего шага после `completed` прежнего. Отдельный детектор повторов не вводится: достаточно лимита вызовов и существующего doom-loop детектора агентского цикла.

На исчерпании лимита новые действия модели не принимаются. Уже принятое действие сначала завершается с установленным результатом; таймер не даёт права запустить второго исполнителя.

Агент объясняет, что проверяет или меняет, и прекращает попытку раньше лимита, если браузер недоступен, остановка исходного исполнения не установлена или нет следующего обоснованного действия. Общие ограничения и отмена задачи имеют приоритет над бюджетом recovery.

Остановка не означает безусловный rollback. Runtime может отменить принадлежащий попытке неприменённый draft, если это безопасно. Он не удаляет созданные узлы, не повторяет неидемпотентные эффекты и не отбрасывает неизвестные эффекты ради очистки журнала. Если безопасная очистка невозможна, блокировка сохраняется с причиной. `stopped` не переходит в Dock только из-за закрытия диалога или окончания таймера.

Пользователь получает конкретное сообщение: что выполнено, что подтверждено runtime и что только моделью, сохранён ли пакет, где остановилась задача и что осталось неизвестным. Формулировка «исправьте сценарий вручную» не является штатным выходом. Запрос недостающего файла, доступа или смыслового решения допустим, когда он действительно необходим.

## 10. Ответственность существующих компонентов

| Граница | Ответственность |
| --- | --- |
| Сборка и launcher CLI/Desktop | Вшивают флаг; передают capability только при штатном bundle/packaged-запуске |
| Host | Передаёт capability runtime; публикует каталог и отклоняет вызовы вне каталога (гейт уже есть) |
| Bridge runtime | Аренда браузера, allowlist, проверка origin/документа после действий, бюджет, размеры ответов, журнал |
| Executor и `node-apply` | Триггеры T1–T4; release-proof для recovery; recovery-квитанция; приём её в `dock_node_read` |
| Агент: `session/tools.ts` | Публикация инструментов recovery; скриншот только для image-модели |
| Агент: `session/prompt.ts` | Одно напоминание на попытку при завершении хода во время recovery |
| Навык `loginom-automation` | `references/browser.md`: вместо «попроси закрыть мастер» и «сообщи и остановись» — переход в recovery; описание временного режима |
| Тот же агент | Выбирает UI-действия по наблюдениям, завершает шаг, вызывает `finish` и сообщает, что сделал |

Общий запрет произвольного обхода runtime сохраняет смысл вне режима; внутри него действия из allowlist являются штатной работой. Не добавляются вторая оркестрация модели, новый глобальный владелец браузера, отдельная база состояния recovery и новые читатели настроек отдельных типов узлов.

## 11. Наблюдаемость и критерии приёмки

В существующем журнале связываются исходная ошибка, триггер, начало и окончание handoff, браузерные действия, остаток бюджета, результат проверки с разделением фактов runtime и `attested_by_model`, первое последующее действие Dock. Изображения в журнал не пишутся. Журнал не называет успешной попытку, которая только сняла блокировку, но не позволила продолжить задачу.

В отчётах eval и приёмки исход `recovered_via_browser` учитывается отдельно от чистого PASS: это сигнал дефекта обработчика, который по-прежнему нужно исправить в Dock.

| Проверяемый случай | Требуемый результат |
| --- | --- |
| Ошибка mapping или настройки узла; штатное восстановление исчерпано | Тот же агент выполняет действия Playwright в той же вкладке; общая проверка проходит; Dock успешно продолжает; итог задачи корректен |
| Отказ освобождения с `user_action` (T1) | Пользователя не просят закрыть мастер; агент делает это сам, release-proof проходит |
| Сломанный DOM-предикат исходной процедуры | Шаг, завершённый вручную, принимается общей проверкой без повторного прохождения того же предиката |
| Потеря ответа после фактического выполнения/экспорта | Результат установлен наблюдением; повтор только идемпотентный; иначе сохраняется неопределённость |
| Восстановлена только часть шага | Продолжение новой операцией над тем же узлом, без пересоздания узла |
| Неверные параметры до изменений | Обычное исправление через Dock, без входа в recovery |
| Потенциально живой старый исполнитель и поздний ответ | Ни одного конкурирующего browser-действия; поздний ответ не меняет владельца |
| Вызов Dock в фазе `browser` или Playwright вне неё | Отклоняется на границе исполнения, даже если имя известно модели |
| Запрещённый инструмент, навигация или перезагрузка | Отклоняется; подготовленный документ сохраняется |
| Повторная ошибка, смена ID и возврат через `continuable` | Бюджет сохраняется; нет бесконечного цикла режимов |
| Истечение лимита, отмена, падение runtime | Нет ложного успеха и автоматической очистки неизвестного эффекта |
| Текстовая модель | Скриншот-инструмент не опубликован; восстановление по DOM; модель не меняется |
| Модель с поддержкой изображений | Скриншот приходит настоящим image content |
| Prod CLI и Desktop | Полный путь работает на упакованных release-артефактах |
| Приёмочная сборка с флагом / dev без флага / env-канал | Режим есть / отсутствует / не включается |

Проверки переходов, допуска вызовов и общей проверки дополняются сквозными прогонами на реальном Loginom: восстановление настройки и портов, продолжение через Dock, сохранение и получение требуемого файла. Искусственно вызванный отказ допустим для воспроизводимости, но успешный unit-тест или вызов Playwright сам по себе не доказывает выполнение задачи. Частота успешного восстановления оценивается отдельно от корректности расчёта.
