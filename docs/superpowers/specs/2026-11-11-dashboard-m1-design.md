# Dashboard M1. Перенос на TypeScript и проверка на dev-стенде

**Статус.** Дизайн для согласования. База — принятый `dashboard-m0` на `4e09deeb6d`. Общее устройство платформы задаёт [roadmap](2026-11-11-dashboard-architecture-roadmap.md). Этот документ уточняет границы M1 после [приёмки M0](../plans/2026-11-11-dashboard-m0.md).

## Результат для пользователя

После обновления dev-стенда пользователь открывает уже опубликованный ROI-dashboard в обычном и отладочном клиентах Studio. Изменение `MinBudget` пересчитывает таблицу и график, Esc возвращает к сценарию. Кнопка правки передаёт в Desktop снимок выбранного узла. Перепубликовывать ROI для обновления не требуется.

Для разработчика результатом служат один пакет `@loginom-ai-agent/dashboard`, воспроизводимая сборка и проверки в CI. M1 сохраняет ограничения M0. До изоляции в M2 на стенде открывают только собственные доверенные dashboard. Новый протокол iframe, черновик, сборщик публикаций и установка на release относятся к следующим этапам.

## Принятый способ перехода

Сначала фиксируем поведение исходного JavaScript тестами, затем переносим службу снимков и только после неё браузерную оболочку. Обе части проходят проверки до первого обновления dev-стенда. Первый сквозной результат на стенде — открытие сохранённой публикации и пересчёт в Studio после **одного обновления поверх M0**.

Рассмотрели промежуточную установку новой службы со старой оболочкой. Она дала бы более раннюю проверку связи со Studio, но для проверки полного обновления пришлось бы возвращать службу M0. Владелец выбрал один переход. Перезапуск службы, как и в M0, очищает снимки в памяти. Для проверки Desktop получают свежий ID после установки.

## Код и совместимость

- `packages/dashboard/src/web` содержит HTTP-службу на TypeScript и `node:http`. `src/contract` содержит схемы Effect Schema для данных, которыми уже обмениваются служба и оболочка. Адреса, ответы, ключ привязки из пяти полей, вытеснение снимков и чтение сохранённого примера по своей привязке сохраняют поведение M0. Действуют проверки `Host`, закрытая выдача служебных файлов и доступ к `current` только при отладочном флаге с loopback.
- Для `POST /dashboard/targets` поддерживаются обе формы входа. Старая оболочка присылает `schema` и `rows` на верхнем уровне, оболочка M0 использует поле `sample`. Сохраняются смысл `sample: null`, проверка известных полей и действующая обработка лишних полей. Строгий отказ за лишние поля вводится с новым контрактом снимка в M3.
- `src/shell` объединяет поведение `bootstrap.js` и `parameter.js`. Обращения к объектам клиента Loginom и описание их типов находятся в `src/shell/loginom`. Bun собирает один браузерный `shell.js` в формате IIFE и отдельный модуль `.mjs` для службы под закреплённым Node. Проверка типов охватывает сервер и браузер с их собственными библиотеками. Оболочка сохраняет очередь пересчётов, обработку ошибок, параметры и существующий интерфейс с опубликованными приложениями.
- Шаблон переезжает в `packages/dashboard/template` вместе со своим npm lockfile. Исходники приложений остаются в `dashboard/apps/<ключ>` до M3. По этому пути Desktop определяет каталог проекта. Команды нового снимка указывают на действующий скрипт публикации. Он по-прежнему проверяет типы, собирает Vite-приложение и атомарно переключает каталог публикации. При переносе путей учитываются приложения с ранее созданной скриптом ссылкой на `dashboard/template/node_modules`. Существующие правки приложений и их исходники сохраняются.
- Инструкции разработчика переезжают в `packages/dashboard/AGENTS.md` вместе с кодом. Обновляются ссылка из корневой карты модулей и команды в документации установки и переноса. Инструкции создания dashboard для текущего Desktop должны по-прежнему быть доступны при работе из `dashboard/apps`.

## Проверка до установки

Исходная база — поведение всех **19 проверок M0**, включая вложенные случаи. Сначала переносимые тесты проходят на JavaScript. Затем тот же набор проверяет TypeScript-службу по HTTP на настоящем порту с временными каталогами и собранную оболочку в Chromium 154. Недостающие тесты из таблицы M1 в roadmap добавляются по одному через TDD. В частности, проверяются типы и кеширование выдаваемых ресурсов, завершение и отмена изменения параметра, а также ссылка Desktop и обычное предупреждение Studio о несохранённых изменениях.

В CI задача `unit` запускает тесты пакета через Turbo. Тесты службы используют `node:test`. До переноса проверяется их совместимость с Bun 1.3.14 и закреплённым Node 24.19.0. Если оба рантайма совместимы с тестами службы, весь набор запускается в каждом из них. Если Bun не выполняет его корректно, служба тестируется и измеряется под Node. Отдельная задача `dashboard-browser` запускает браузерные сценарии на Chromium продукта. Пакет проходит `bun typecheck` и `bun run build`. ShellCheck проверяет скрипт стенда.

**Покрытие.** Общий порог — 90% строк и 90% функций. В M1 действие ограничения доказывают на `web`: CI проходит на принятом коде и отклоняет контрольное снижение покрытия. При варианте с Node тот же порог проверяет Node. Браузерные сценарии оцениваются по поведению. На реальном коде `publisher` и `builder` порог проверяется в M4, когда появятся эти службы.

**Размер.** Каждый из двух исходных скриптов M0 минифицируется с теми же настройками, что и новый браузерный файл. Складываются размеры файлов M0 в байтах до gzip. С этой суммой сравнивается размер минифицированного `shell.js` без карты исходников. Значение ограничения для CI фиксируется после первого замера. Если существенный прирост даёт Effect Schema, применяется предусмотренный roadmap вариант с компактными проверками в оболочке и тестами соответствия общим схемам.

## Установка, проверка и снятие

`packages/dashboard/deploy/dev-master.sh` заменяет `dashboard/install.sh` и предоставляет `install`, `check`, `uninstall`. В M1 на dev-стенде используются существующие контейнеры Studio и Loginom Server и прежний путь публикации. Установщик подключает один собранный скрипт в каждом клиенте. При обновлении он убирает свои прежние подключения M0, сохраняет опубликованные каталоги, пакеты и настройки доступа к службе. Обе исходные конфигурации Studio читаются и проверяются перед изменением стенда. Установленные копии отличаются от них только значением `rememberuser: false`.

`check` проверяет подключение к службе через Apache, загрузку оболочки и наличие нужных объектов адаптера в обоих клиентах. Живая проверка использует выделенный лицензированный стенд. `uninstall` снимает подключение оболочки, службу и настройки Apache, принадлежащие dashboard. Вновь действует исходный `client.json` каждого клиента, в том числе выбранное для него значение «Запомнить». Пользовательские пакеты, исходники и опубликованные приложения сохраняются. Чистая установка проверяется отдельно от первого перехода поверх M0, например повторной установкой после проверки удаления.

## Приёмка

1. **Dev master.** После единственного обновления открыть прежний ROI-dashboard в `/app/` и `/app-debug/`, изменить `MinBudget`, увидеть пересчёт и закрыть по Esc. Проверить открытие чата с целью по свежему ID. Исходной публикацией служит версия, существовавшая до M1.
2. **Публикация.** На отдельном доверенном тестовом dashboard опубликовать первую версию. Внести ошибку TypeScript во вторую и убедиться из Studio, что первая по-прежнему открывается. Исправить ошибку, повторить публикацию и открыть вторую версию. Проверка использует существующий dev-стенд. Второй стенд для CI не требуется.
3. **Совместимость S8.** На минифицированном `/app/` проверить фактически используемые объекты адаптера на master и 7.4.2 и записать результат для точной сборки. Если в 7.4.2 отсутствует нужная функция, для M1 допустимо документированное ограничение с указанием этой функции и подтверждением, что оболочка отключилась, а Studio продолжает работу. Адаптация нужна к первому последующему этапу, которому потребуется рабочий dashboard на release. Если лицензированная 7.4.2 недоступна, проверка S8 остаётся открытой до прогона.
4. **Удаление.** После `uninstall` обе Studio открываются без элементов dashboard, а «Запомнить» соответствует собственному исходному файлу каждого клиента. После установки на очищенную от интеграции Studio снова доступна сохранённая публикация.

Расположение отдельных файлов внутри частей пакета, способ проверки объектов Studio в авторизованном сеансе и команды измерения размера определяет исполнитель плана. Технические проверки, для которых нужен стенд, и численное ограничение размера на этапе дизайна ещё не получены.
