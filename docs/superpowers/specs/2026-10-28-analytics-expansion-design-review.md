## A. Обязательные замечания (по убыванию риска)

### A1. Общий контракт пары не отделён от алгоритма D — business-форма будет угадывать

- Где: `pairs.md:5` требует передать B «все определения и правила из карточки», но «алгоритм из D не передавать».
  В карточках определения часто записаны только в тексте D или в блоке риска. Явный общий блок есть лишь у P46/P47
  (`pairs.md:520`, `:532`).
- Сценарий отказа: если в B перенести только «Данные» и «Таблицу», B не знает правила и честно получает другой
  ответ; если перенести фразы D, B получает алгоритм. Оба исхода портят сравнение форм.
- Доказательство:
  - P07: «ожидаемый кредит = принято × цена после скидки» есть только в D (`pairs.md:85`); ловушка «цена до скидки»
    (`:89`) невозможна — в данных нет такой цены (`:84`);
  - P41: формула HHI только в D (`pairs.md:465`), ссылка на «общий договор» (`:467`) никуда не ведёт, шкала 0–1
    или 0–10000 не выбрана;
  - P50: имя рабочего листа только в D (`pairs.md:566`), а без имени импорт берёт первый лист, то есть легенду
    (`lib/imports-excel-parameters.mjs:5`);
  - P28: не заданы точные значения `quality_bucket` (`pairs.md:324`), а текст сравнивается посимвольно;
  - P49: «UTF-16» без LE/BE (`pairs.md:554`), в коде это разные кодировки (`lib/text-import-encoding.mjs:6–7`);
  - всего такие места в 28 карточках: P02, P04, P07, P08, P10–P13, P15, P18–P20, P22, P23, P25, P26, P28–P31,
    P33, P35, P39, P41, P45, P48–P50 (P46/P47 — в A7).
- Минимальное исправление: до сборки каждой пары дописать в карточку блок «Общий контракт» по образцу P46/P47 —
  определения, знаменатели, границы периодов, словарь статусов, состав строк, формат. Блок дословно входит в оба
  prompt; D добавляет только способ расчёта.
- Проверка: `diff` двух prompt пары содержит только предложения о способе расчёта; в каждой группе одну пару
  независимый проверяющий решает по тексту B и данным и получает oracle.

### A2. «Одна результатная rubric» несовместима с текущей калибровкой

- Где: `design.md:146` (четыре общих пункта: полный CSV, связный сценарий, расчёт по данным, честность) против
  `design.md:178` («ошибки отклоняются по ожидаемым пунктам»).
- Сценарий отказа: foreign negative оценивается без пунктов результата и честности (`evals/src/calibrate.ts:48`,
  `:91`). Остаются «связный сценарий» и «расчёт по входным данным»; первый пройдёт любой чужой пакет — 50 баллов
  при пороге 40 (`evals/src/config.ts:80`), калибровка падает. Near-miss может ожидать провал только пункта
  результата — это повтор oracle, а не проверка того, что судья видит содержательную ошибку графа.
- Доказательство: у 65 принятых кейсов по 6–8 предметных пунктов, чужому эталону видны пункты общим весом 4–6;
  контракт skill — 5–8 пунктов и `required` на каждый расчёт (`skill/references/case-contract.md:43–48`); судья не
  видит oracle и сверяет CSV по тексту пункта (`case-contract.md:48`, `evals/src/judge.ts:160–181`).
- Минимальное исправление: шаблон rubric пары — 3–5 предметных пунктов «по смыслу» (зерно, ключи, знаменатели,
  правила, NULL), одинаковых для D и B, без требований к числу или именам узлов; один пункт результата с полным
  oracle; один пункт честности `requires_run`. Near-miss ожидает провал предметного пункта. Правило «сужать задачу
  при >50 строках» убрать (как в `design.md:183`), но компактность результата оставить целью fixture: судья сверяет
  встроенный CSV чтением.
- Проверка: калибровка первой пары — positive ≥90 и oracle=true в обеих формах, near-miss выполняет
  `expected_failed`; после второй пары foreign negative ≤40.

### A3. Для cold rerun нет способа, доступного исполнителю

- Где: `design.md:174` требует «фактически доступный поддерживаемый интерфейс», но не называет его; skill отсылает
  к `$VALIDATION_REPO/.agents/skills/loginom-automation` и браузерному MCP (`skill/SKILL.md:25`, `:58`;
  `skill/references/verification.md:25`, `:29` — «без браузерного MCP кейс не готов»).
- Сценарий отказа: первый сквозной шаг не завершается; rerun либо молча пропускают, либо выдают XML-проверку за
  исполнение.
- Доказательство: такого skill вне продукта нет; в конфигурации Codex исполнителя настроен только MCP `node_repl`;
  у CLI нет команды «открыть и выполнить пакет» (`packages/agent/src/cli/standalone.ts:17`); открыть сохранённый
  пакет может только сессия агента — `loginom_dock_prepare(intent: "open_package", local_package_path)`
  (`packages/agent/src/session/tools.ts:682–711`) с поузловым `execute`.
- Минимальное исправление: выбрать способ (D1) и записать его в `skill/references/verification.md` с критериями
  приёмки: новый файл результата, неизменный пакет, отсутствие изменений настроек в журнале, совпадение с oracle
  через `check_reference.py`.
- Проверка: на первой паре файл после rerun новый (не отложенный `-cli`) и совпадает с oracle.

### A4. Формат значений и порядок строк результата не закреплены

- Где: `pairs.md:5` откладывает имена колонок и сортировку на подготовку кейса; формат пустого значения отмечен
  только у P05 (`pairs.md:68`).
- Сценарий отказа: правильный ответ падает. Oracle сравнивает нечисловые значения посимвольно и строки по позиции
  (`evals/src/oracle.ts:35–47`). Экспорт пишет даты только закрытыми форматами, логические значения — только словами
  True/Истина/Да и False/Ложь/Нет, пустоту — маркером `''`, `?`, `null` или `NULL`
  (`lib/text-export-parameters.mjs:40–43`). У сортировки нет правила для NULL и стабильности, строки по умолчанию
  сравниваются с учётом локали (`lib/sorting-procedure.mjs:65`), а Python-oracle сортирует по кодам символов.
- Затронуты: даты и месяцы P16–P25; флаги P05, P37; пустые значения P05, P13, P19, P23, P29, P30, P32, P35, P37;
  строковые ключи сортировки почти везде.
- Минимальное исправление: одно правило рядом с `design.md:93–95`, входящее в общий контракт (A1):
  - полный уникальный ключ сортировки без NULL, упорядоченный одинаково по локали и по кодам (ID с буквенным
    префиксом и нулями слева);
  - месяц и дата — текст фиксированного вида или целые год и месяц;
  - флаги — целые 0/1; пустота — пустая ячейка;
  - `*_pct` — 0–100, доли — 0–1; отклонение = факт − расчёт.
- Проверка: в первых выпусках с датой, флагом и пустой ячейкой реальный экспорт сверен `check_reference.py`;
  наблюдаемый формат записан в `skill/references`.

### A7. K-means: условие приёмки P46/P47 недостаточно для честной business-формы

- Где: `pairs.md:526`, `:538` — достаточно, чтобы native k-means с seed 42 нашёл оптимум; B seed не получает
  (`pairs.md:522`).
- Сценарий отказа: business-агент выставляет другой seed, алгоритм останавливается в локальном минимуме, и провал
  зависит от случая, а не от умения.
- Доказательство: у нового узла seed по умолчанию 42 (`lib/clustering-procedure.mjs:96`), параметров инициализации
  и перезапусков нет; глобальный оптимум не гарантирован. Пример: для трёх сгустков по три точки случайные стартовые
  точки попадают по одной в каждый сгусток лишь в 27 из 84 вариантов.
- Минимальное исправление: в условие приёмки добавить устойчивость — независимый алгоритм Ллойда из всех стартовых
  наборов точек данных и native-прогоны с несколькими seed (включая пропуск seed) приходят к тому же разбиению;
  центры различаются сильнее допуска (строки сортируются по `center_x`). Иначе карточка уходит в резерв.
- Проверка: таблица «seed → SSE» в provenance кейса.

### A8. Неудача авторской попытки не должна отбирать задачи

- Где: `skill/SKILL.md:56`, `skill/references/environment.md:58` (не больше трёх попыток, подсказка в третьей);
  `design.md:193` откладывает выбор модели авторинга; правило при неудаче не задано.
- Сценарий отказа: карточки, которые авторский агент не собрал, тихо заменяют или упрощают; первая очередь
  смещается к тому, что агент уже умеет, и pass rate обеих форм завышается.
- Минимальное исправление: одно правило в плане — неудача авторинга не причина менять или упрощать задачу.
  Reference собирают другим законным способом: подсказка, сборка автором в Loginom, внешний пакет через
  `check_reference.py` и явный provenance (внешний reference уже согласован, `sources.md:9`). В backlog уходит
  только неподдержанный режим. Способ авторинга фиксируется по каждой паре.
- Проверка: в отчёте каждой группы указаны способ авторинга и число попыток; у каждой замены причина — возможность
  runtime, а не неудача авторинга.

## D. Вопрос владельцу

**D1. Каким способом выполнять cold rerun принятого reference?**

- **Рекомендуется:** отдельная сессия `loginom-ai-agent-cli` в авторском профиле открывает сохранённый пакет
  (`open_package`) и выполняет все узлы без изменений. Результат принимается, если в журнале нет изменений настроек,
  SHA256 пакета не изменился, файл результата новый и совпал с oracle. Автономно, без новых инструментов.
- Владелец вручную в Loginom UI: «Пакеты → Открыть», выполнить, закрыть без сохранения. Самый прямой путь, но около
  50 ручных прогонов.
- Подключить исполнителю браузерный MCP и сохранить прежнюю UI-процедуру skill. Меняет окружение исполнителя.

Остальные решения устанавливаются из согласованного контекста.
