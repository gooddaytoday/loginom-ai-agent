# Расширение аналитических evals: 50 задач, 100 формулировок

> Сведения о локальном окружении обезличены. Приватные подтверждения, упомянутые в документе, не включены в репозиторий.

Статус: дизайн согласован владельцем; исполнение и результаты отражаются в [плане реализации](../plans/2026-10-28-analytics-expansion-implementation.md). Решением владельца от 28.10.2026 кампания может завершиться меньшим проверенным набором с перечнем отложенных пар.

## Назначение и документы

Расширить проверку аналитических возможностей Loginom AI Agent и отдельно измерять, насколько ему необходима подробная инструкция. Единица нового аналитического покрытия — **задача**, единица запуска — **формулировка задачи**. Исходный каталог: 50 задач в двух формулировках, до 100 новых evals. Итог кампании — полностью проверенные K пар и явно отложенные 50−K пар по правилам плана; 2K форм не считаются независимыми аналитическими задачами.

- [Каталог 50 пар](2026-10-28-analytics-expansion-pairs.md): постановки, входы, механизмы, независимые проверки и ловушки.
- [База будущих направлений](2026-10-28-analytics-expansion-backlog.md): методы, недостающие возможности, источники и очередь дальнейшего исследования.
- [Демопримеры, wiki и блог Loginom](2026-10-28-analytics-expansion-loginom-sources.md): прочитанные материалы, статически исследованные пакеты, соответствие текущим задачам и дополнительные кандидаты.
- [Полный архив блога Loginom](../../research/analytics-evals/2026-10-28-loginom-blog-archive.md): проверка всех 635 адресов, решения по публикациям и каталог дополнительных постановок для будущих evals.
- [Исходное исследование пользователя](../../research/analytics-evals/2026-10-28-landscape-report.md): сохранённый первичный материал; служебные ссылки `turn…` не считаются проверяемыми ссылками. Уточнения и прямые URL находятся в базе направлений.

Дизайн является базой для последующего плана исполнения. Он не объявляет будущие данные, пакеты, oracle или live-прогоны уже подготовленными. Решения по внешнему review и границы проверки сохранены в [плане правок](../plans/2026-10-28-analytics-expansion-review-fixes.md).

## Согласованные решения

1. Разобрать **50 задач × 2 формулировки**; принять только проверенные пары целиком D/B, остальные явно отложить. Допустим итог меньше 100 evals без ослабления проверки принятой пары.
2. Различать подробные задания и бизнес-вопросы, где агент самостоятельно выбирает расчёты и способ анализа; хранить их в отдельных коллекциях.
3. В обеих версиях обязательны сценарий Loginom и итоговая таблица. Дополнительное эссе, презентация или dashboard не становятся обязательными.
4. Не заменять JavaScript специальный узел, который агент ещё не умеет настраивать. Такой кейс относится к будущей очереди.
5. Использовать смешанные данные: открытые реальные источники и специально созданные пограничные случаи.
6. Разнообразие считать по аналитическим механизмам, комбинациям операций и существенным ошибкам рассуждения; смена отраслевого сюжета сама по себе не даёт нового покрытия.
7. Удалить из рабочего workflow skill старые зависимости от `agent-validation`; при необходимости использовать общий источник задания. Выявленные адаптации `loginom-eval-case` включить в план до массового создания кейсов.
8. Исследовать официальные демопримеры Loginom с готовыми пакетами, wiki и блог, рассмотреть подходящие аналитические задачи и включить результаты отбора в план.
9. Блог рассмотреть целиком: сверить полный архив с sitemap, учитывать каждый материал и объединять повторяющиеся аналитические задачи. Непросмотренное видео или недоступная историческая статья не засчитываются как полный содержательный разбор.
10. Авторинг выполнять через CLI, cold rerun — через уже проверенный браузерный UI-путь Authoring; если он недоступен, вручную владельцем в Loginom UI. Сохранить критерии нового CSV, неизменного SHA256 пакета, отсутствия изменений настроек и совпадения с oracle. Процедура описана ниже; новых инструментов не добавлять.

Существующие 65 кейсов остаются на месте. Новые пары не являются переписыванием их промптов.

## Рассмотренные подходы

**100 разных задач.** Максимальная широта; обе формы задания присутствуют, но сравнение самостоятельности смешивается с различиями самих задач. Был рекомендован как вариант максимального покрытия.

**50 парных задач — выбран пользователем.** Входные данные и целевой результат внутри пары одинаковы. Меняется степень раскрытия способа решения. Получаем 50 новых аналитических механизмов/комбинаций и контролируемое сравнение двух формулировок. Цена выбора: ширина первой очереди ограничена 50 задачами; ответы двух версий статистически зависимы.

## Что существует сейчас

Инвентаризированы все 65 `task.json`, спецификации и XML эталонов из [текущей коллекции](../../../evals/tasks/analytic). Более ранние локальные коллекции на 35 и 25 кейсов не использованы как актуальная база.

| Наблюдаемое свойство | Покрытие |
|---|---:|
| Один входной CSV и один выходной CSV | 65 из 65 |
| Группировка | 63 |
| Калькулятор | 56 |
| Сортировка | 64 |
| Параметры полей | 24 |
| Фильтрация | 4 |
| Слияние | 3 |
| Свёртка столбцов | 3 |
| Кросс-таблица | 1 |
| Дата и время | 1 |

Входы содержат 36–2000 строк, результаты — 1–35 строк. В эталонах нет обучающих узлов, Excel и JavaScript. 55 задач используют для содержательных вычислений только группировку и калькулятор. При этом отдельные формулы уже проверяют Пирсона, одномерную OLS, z-score, веса и правильные знаменатели: их нельзя объявлять полностью отсутствующими.

Названия источников не равны проверяемым методам: `cluster-label-crosswalk` сравнивает готовые метки; `monthly-demand` агрегирует месяцы; `treatment-followup-profile` не оценивает выживаемость; `monthly-retention-curve` получает готовые флаги месяцев. Новая когортная задача должна строить принадлежность и активность из событий, новая модельная задача — действительно обучать модель.

Отдельные node-evals, smoke, local-path сценарии и черновики text-import не включены в эти 65. Они полезны как доказательства отдельных настроек, но не заменяют аналитические сценарии.

Историческая приёмка и пределы калибровки описаны в [отчёте переноса](../../../evals/docs/2026-10-20-analytic-evals-import.md). Новая работа их не пересчитывала. Наличие positive/foreign-negative калибровки не означает наличие near-miss калибровки или свежего live PASS.

## Граница доступных возможностей

Источники истины: [регистрация обработчиков](../../../packages/loginom-runtime/client/lib/node-support.mjs), [контракты типов](../../../packages/loginom-runtime/client/lib/node-contracts.mjs), [публичная схема](../../../packages/loginom-runtime/client/lib/node-api.mjs) и валидаторы параметров рядом с ними. Зарегистрированы 20 типов; исторический [реестр развития узлов](../../node-development/registry.json) используется как список направлений, а не актуальное доказательство поддержки.

| Возможность | Доступная граница для отбора |
|---|---|
| Текст и Excel | Delimited text; XLSX с явной схемой, 1–8 столбцами, выбранным листом. Не произвольный workbook workflow |
| Группировка | `sum/count/avg/min/max`, составные ключи; `count` включает NULL |
| Кросс-таблица | `sum/count/min/max/avg/stddev/sum_squares/unique_count/null_count/first/last`; `stddev` выборочное; first/last зависят от входного порядка |
| Слияние | Только inner/left equijoin, составные ключи, mappings; many-to-many размножает пары; NULL-семантика не предполагается равной SQL |
| Объединение | Append all, 2–15 входов; удаление дублей — отдельная аналитическая операция |
| Калькулятор и фильтр | Scalar-формулы Loginom, AND/OR-условия; функцию сначала проверять по фактическому контракту/справке |
| Дата и время | Числовые компоненты года/квартала/месяца/дня/часа; начало/конец года, квартала, месяца; `date` — начало дня. Нет начала часа или разности месяцев; композиции с калькулятором требуют проверки |
| Дубликаты | Маркировка всех строк групп дубликатов/противоречий. Не автоматическое сохранение одного победителя |
| Пропуски | Mean для numeric continuous и constant для discrete string; без interpolation/forward fill |
| Замена | Точные внутренние словари; не произвольные regex или внешние lookup-таблицы |
| Переформирование | `reform` меняет свойства полей; scalar unpivot выполняет `collapse_columns`, pivot — `cross_table`. Нет произвольного JSON/XML/tree parsing |
| Линейная регрессия | Задаётся manual Enter для numeric predictors/target; intercept=true, normalization none, train/test/validation=100/0/0 и denormalize=true только проверяются. Иное сохранённое состояние вызывает отказ. Predictions и coefficients текущего входа; не готовый holdout/apply workflow |
| Кластеризация | K-means, явные k/seed, normalization none, assignments и centers; без auto-k и сохранённой модели для новых строк |
| REST | GET без auth/body/custom headers. В первой очереди не нужен новый сетевой fixture-сервис |
| JavaScript | Обработчик существует, но не используется как обход недостающего специального узла |
| Экспорт | Один текстовый CSV; native Excel/DB/XML-экспорт не поддержан этим контрактом |

Наличие handler — статическое доказательство доступного API, а не доказательство работы конкретного установленного CLI и сервера. Перед построением первого эталона с каждой новой комбинацией требуется краткая проверка основного пути. Неудачу запуска сначала разделять на ошибку авторинга, окружения и подтверждённо неподдержанный режим. Только последний является основанием переноса по возможностям в backlog; подмена обучения сводкой или окна ручным JS запрещена.

Обычная композиция доступных узлов допустима: например, предварительно агрегировать платежи и затем соединить их со счетами. Искусственная реализация отсутствующего специального алгоритма громоздким графом не используется для обхода ограничения пользователя.

## Две формулировки одной задачи

### Что одинаково

Данные, словарь полей, единицы, бизнес-правила, период наблюдения, требования к итоговой таблице, критерии корректности и ресурсные условия. Блок «Общий контракт» каждой [карточки пары](2026-10-28-analytics-expansion-pairs.md), её входы, схема результата и общие правила формата дословно входят в оба prompt. Они задают знаменатели, границы, словари категорий, состав и полный порядок строк, даты, NULL, флаги и единицы чисел. Формат результата — часть контракта сдачи, а не подсказка об алгоритме.

Если бизнес-правило необходимо для единственного правильного ответа — например, какие возвраты уменьшают выручку или на какую дату считать долг, — оно доступно обеим версиям. Нельзя скрыть правило только от business-агента, а затем штрафовать за его незнание.

### Что различается

`detailed` раскрывает последовательность вычислений и формулы решения. `business` задаёт цель и нужные бизнес-показатели без последовательности преобразований, названий промежуточных таблиц, рекомендуемых узлов и алгоритмических подсказок. Точное определение показателя, в том числе математическое, доступно обеим формам, если иначе возможны разные правильные ответы. Агент сам выбирает путь к тому же ответу.

Проверяется способность вывести способ расчёта, а не угадать пожелания автора. Если несколько определений показателя разумны, определения надо уточнить в общем бизнес-контексте либо принять все допустимые результаты. Первая очередь использует задачи с однозначной семантикой результата; свободное обнаружение любых интересных закономерностей относится к будущему направлению с другим оценщиком.

Эталонный граф показывает один правильный путь. Rubric принимает эквивалентные native-композиции, не требует совпадения количества узлов, имён узлов или внутренней структуры. Требование конкретного обучающего метода допустимо лишь там, где этот метод входит в общий содержательный контракт задачи; иначе в паре оценивается корректность выбранного анализа.

### Размещение

Согласованное размещение использует действующий выбор коллекции:

```text
evals/tasks/analytic/                                  # существующие 65, без переноса
evals/tasks/analytic-detailed/<pair-slug>-detailed/     # K принятых подробных версий
evals/tasks/analytic-business/<pair-slug>-business/     # K принятых самостоятельных версий
```

В двух коллекциях одинаковые K принятых основ `pair-slug` из исходных 50, а полные task ID различаются суффиксами `-detailed`/`-business`; deferred остаются вне принятого runnable-набора. Это необходимо для существующей [near-miss калибровки](../../../evals/src/calibration-cases.ts): она ищет `calibration/<task.id>/cases.json` и сверяет хэш task.json, который различается у двух формулировок. Для каждой формы создаётся свой manifest с точными хэшами; основу имени используют для сопоставления пары. [Loader](../../../evals/src/task.ts) и [config](../../../evals/src/config.ts) уже принимают `--tasks`: новый registry, поле schema или механизм маршрутизации не нужен. Совместный запуск обеих коллекций как плоского списка не предполагается.

Для каждой версии остаётся существующий формат task/SPEC/reference/oracle/provenance. В первой реализации небольшие исходные файлы и oracle можно копировать между двумя self-contained case directories, проверяя их равенство через `cmp` для всех входов и oracle. Цена — дублирование данных на диске; альтернатива с общим storage и новым loader увеличивает сложность. Общие данные, пути за пределы case и symlinks сейчас не вводятся. Авторитетный смысл и статус пары хранятся в её карточке; реализации двух форм сверяются с ней. Перед выпуском сверить prompt: различаются цель в естественной формулировке и раскрытие способа, но не обязательные определения. Для одной пары каждой группы независимый проверяющий получает ответ по B и входам и сверяет его с oracle.

## Данные и независимое доказательство

Реальные данные показывают правдоподобные распределения, пропуски и неоднородность. Небольшие сконструированные наборы гарантируют наличие ошибки, которую задача должна различать. Жёсткая пропорция не задаётся; до утверждения окончательных fixtures у каждой пары отмечаются источник и происхождение.

- Входы замораживаются локально; eval не скачивает меняющийся сайт во время запуска.
- Для внешнего источника фиксируются URL, разрешение на распространение, дата/версия снимка, отбор строк/полей и преобразования. Лицензия кода benchmark не считается лицензией данных.
- Реальный снимок и добавленные искусственные случаи различаются в provenance. Искусственная таблица оплат не называется реальными платежами только потому, что товары взяты из реального каталога.
- Не передаются готовые ответы, итоговые агрегаты или признаки, которые агент должен вычислить. Для пар одинаково исключены oracle, эталон и полное техническое SPEC из агентского workspace.
- Разные механизмы могут использовать один реальный источник, но не считаются новыми задачами только из-за другого фильтра. Одна строка/единица наблюдения и назначение каждого ключа определены явно.
- Размер ограничивается самым узким используемым действующим контрактом. Для Excel заранее учитывать 8 столбцов; правила доставки локальных файлов брать из продукта, а не вводить новую константу.

Независимый oracle реализуется вне сценария Loginom: точная арифметика/SQL/Python для таблиц, проверенная численная библиотека для моделей, явные ручные сверки малых подмножеств. Нельзя использовать экспорт из единственного reference как единственное доказательство истины.

В каждой карточке указано правдоподобное неверное решение. При подготовке fixture сначала проверить, что оно действительно меняет ответ сильнее допуска, затем строить reference. Это предотвращает задачи, которые номинально проверяют знаменатель или cardinality, но проходят при неверном решении.

### Готовые пакеты Loginom

Демопример может стать источником данных, прототипом алгоритма или принятым reference — это разные степени переиспользования. Решение для каждого выбранного материала и связь с P/B-карточками фиксируются в [обзоре источников](2026-10-28-analytics-expansion-loginom-sources.md). Готовность ZIP к скачиванию не доказывает корректность формул, поддержку всех режимов агентом, наличие всех входов или разрешение распространять изменённый пакет.

До приёмки reference статически прочитать все вложенные Unit.xml и используемые компоненты, сверить фактические узлы/параметры с runtime, установить происхождение данных и условия использования. Затем на выделенной среде проверить открытие, полное выполнение и повторное выполнение с новым CSV, сверить независимый oracle и содержательные near-miss. Путь к файлам и табличный экспорт можно адаптировать; отсутствующий специальный алгоритм нельзя заменить или удалить ради включения исходной задачи в первую сотню.

Оригинал и адаптированный пакет различаются в provenance: URL страницы/архива, дата получения, права, версия, исходные и итоговые хэши, существенные изменения, проверенные данные и результаты. Готовому пакету не приписываются вымышленные model/session/CLI attempts. Даже при общем reference обе формы задачи исполняются независимо. Агент получает исходные данные и свой prompt; готовое решение, ссылка на его скачивание и техническое описание остаются у автора/судьи. Для проверки переноса метода добавляются новые граничные данные, а не только известный публичный пример.

## Оценивание без нового harness

[Текущий oracle](../../../evals/src/oracle.ts) требует ровно один `.result.csv`; сопоставляет колонки по именам, а строки по порядку; использует один абсолютный numeric tolerance на задачу. [Judge](../../../evals/src/judge.ts) отдельно проверяет rubric. Этого достаточно для выбранной формы сдачи.

Для обеих форм пары используется одинаковая rubric: 3–5 обязательных предметных пунктов о зерне, ключах, знаменателях, бизнес-правилах и NULL; один пункт полного правильного CSV с `requires_result_file`; честность утверждений — с `requires_run`. Предметные пункты проверяют смысл расчёта по входам, а не имена или число узлов. Общая «связность сценария» не заменяет эти пункты: foreign negative оценивается без результата и `requires_run`, поэтому общие признаки чужого графа способны дать слишком высокий score. Алгоритмические пояснения detailed-промпта не запрещают эквивалентное решение. Дополнительный текстовый вывод не обязателен.

Содержательный near-miss должен проваливать соответствующий предметный пункт в `expected_failed`, а не только CSV; `expected_oracle_pass` проверяется отдельно. Positive ≥90 и oracle=true проверяются для обеих форм, foreign negative ≤40 — после второй различной задачи. Новые ловушки укладываются в существующие виды `sort/aggregate/threshold/filter/column`. Компактный информативный результат — цель fixture, а не запрет таблиц свыше 50 строк.

Ограничения учитывать при конструировании задач:

- Numeric-looking строки в generic oracle могут сравниваться как числа: он сам не докажет сохранение `00123`. Если это центральный смысл кейса, нужны подходящая существующая проверка типа/графа или идентификаторы с буквенным префиксом, если именно формат не является предметом проверки. Нельзя утверждать строгое посимвольное сравнение numeric ID.
- Кластеры сравниваются без произвольного native cluster ID: сортированные центры и агрегаты. Для P46/P47 обе формы получают критерий минимальной внутрикластерной суммы квадратов и одинаковое техническое правило воспроизводимости seed=42 для стохастических native-шагов, без предписания алгоритма форме B. На маленьком fixture независимый перебор доказывает уникальный optimum с точностью до меток, а native k-means с этим seed должен достигать его и при повторном исполнении. Если это не подтверждается, кандидат не получает произвольный единственный gold и переносится в резерв. Способ связывания outputs также проверяется до включения модели в основной выпуск. Это не утверждение устойчивости для любого seed.
- Обученная регрессия в первой очереди проверяет fit/коэффициенты/остатки на наблюдаемом наборе; качество обобщения и причинное влияние этим не доказаны.
- Один tolerance выбирается после независимого расчёта с учётом масштаба всех числовых колонок. Если он скрывает существенную ошибку, меняются данные/единицы или кейс переносится; допуск не расширяется ради PASS.
- По исходному коду нет автоматического повторного исполнения каждого пакета на новых скрытых данных. Калибровка judge также не заменяет реальное открытие и выполнение пакета.
- Текущее неинтерактивное выполнение не моделирует живое уточнение с пользователем. Business-вопросы первой очереди самодостаточны; dialogue/abstention — отдельный будущий трек.

Один reference пары нельзя использовать как foreign negative для другой её формы: они имеют одинаковую истину. Foreign negative выбирается из другой аналитической задачи внутри своей коллекции; калибровку группы выполнять минимум на двух разных задачах. У первой одиночной пары отсутствие такого negative явно отмечается и закрывается после следующей принятой пары; правильный пакет не объявляется отрицательным примером ради полноты отчёта.

## Сравнение формулировок

Обе формы запускаются в независимых чистых попытках с одинаковыми model/harness/tool/server pins и бюджетами. Порядок форм внутри пары следует чередовать между сериями, чтобы время запуска не совпадало систематически с видом задания. Ответ detailed не передаётся business через историю, память, workspace или примеры.

Авторский стенд и профиль отделены от измерительного. Измерения используют существующую sandbox-границу и архивирование истории после каждой попытки в [profile.ts](../../../evals/src/profile.ts) и [run.ts](../../../evals/src/run.ts); новая система очистки не нужна. Это защита локальной истории, отдельная от серверной памяти.

Пять операций, считаемых `memory_tool_calls` в [cli.ts](../../../evals/src/cli.ts), реализует сервер [OpenViking MCP](../../../services/loginom-ai/openviking/server/mcp_endpoint.py); префикс `loginom_` добавляет [каталог инструментов агента](../../../packages/agent/src/session/tools.ts). Область определяется `account_id/user_id` из [Dock API key](../../../services/loginom-ai/openviking/server/auth/plugins/api_key.py), а не Loginom username или CLI-профилем: User memory — `PRIVATE_MEMORY<user_id>/memories/`, проектная — `PRIVATE_MEMORY<user_id>/peers/<peer_id>/memories/`. [VikingFS](../../../services/loginom-ai/openviking/storage/viking_fs/_access.py) отображает URI в серверную AGFS-область `/local/<account_id>/…`; физический диск работающего сервера этим не установлен. Смена профиля или ключа с той же identity память не изолирует; write/edit/forget/add_resource также способны менять другие разрешённые серверные ресурсы.

В текущих исходниках [managed-entry](../../../packages/loginom-runtime/src/managed-entry.mjs) выбирает `user-v1`, а [bridge](../../../packages/loginom-runtime/client/lib/bridge.mjs) и [knowledge-client](../../../packages/loginom-runtime/client/lib/knowledge-client.mjs) допускают только find/search/read/grep/glob/list/tree. Пять инструментов записи через этот путь не выдаются; существующая память при этом может читаться. [Автоархивирование](../../../packages/loginom-runtime/client/lib/archive.mjs) и [hooks](../../../packages/loginom-runtime/client/lib/hooks.mjs) для Codex/Hermes существуют отдельно; их вызов managed CLI в проверенном пути не найден. Нулевой счётчик не доказывает отсутствия автоматической серверной записи.

Минимальная проверка сопоставимости охватывает **всю серию**, включая интервал D→B:

1. До первой серии сверить каталог инструментов и наличие hooks/capture фактической установленной сборки с исходниками; определить разрешённые области по identity каждого eval-ключа без публикации ключей. Проверить, что доступный исходный контекст не содержит решений пар.
2. Под той же identity получить полный снимок содержимого User/Peer memory существующими MCP `list/read` либо read-only [fs/ls](../../../services/loginom-ai/openviking/server/routers/filesystem.py) и [content/read](../../../services/loginom-ai/openviking/server/routers/content.py). Для включённого writer/capture учесть также его фактические URI назначения. Снимки остаются в закрытых evidence оператора; усечённый листинг или отсутствующее разрешение не считать пустой памятью. Новый сервис или универсальный сборщик не нужен.
3. После каждой завершённой попытки, до следующей формы, проверить её журнал на запись/неожиданные инструменты; обнаруженная запись прерывает сопоставимую серию. После серии получить второй полный снимок, сравнить его с исходным и проверить `memory_tool_calls=0` в обоих `summary.json`. Это контролирует запись detailed во время серии; одной проверки до старта недостаточно. Неизменность содержимого и отсутствие каналов записи нужны вместе: одна финальная сумма вызовов недостаточна.
4. При изменении памяти, обнаруженном writer/capture с неизвестным назначением или невозможности полного read-back сохранить результаты, но не объявлять сравнение D/B свободным от переноса решения. Установить причину и область до следующей сопоставимой серии; не удалять память для исправления отчёта.

Первая серия P01 прошла эту процедуру на фактически установленной сборке; текущие доказательства и ограничения находятся в [карточке P01](2026-10-28-analytics-expansion-pairs.md#p01-дебиторская-задолженность-с-частичными-платежами). Проверенный installed path переиспользуется при неизменных условиях; снимки и журналы каждой следующей серии проверяются по процедуре выше.

Публикуются отдельные completion/oracle/structure результаты для каждой коллекции и таблица по K измеренным ready-парам: обе прошли; только detailed; только business; обе не прошли. Deferred-пары перечисляются отдельно. Парная разница — описательная оценка эффекта формулировки, не 2K независимых наблюдений. Результат detailed-only также требует разбор причин: провал business мог быть инфраструктурным.

Действующий `compare` не следует насильно использовать как готовый межколлекционный статистический тест: отличающиеся промпты меняют входные хэши. В первом выпуске достаточно анализа уже сохранённых результатов вне production runner. Новый парный статистический тест или автоматизация отчёта — только после отдельного обоснования потребности. Не смешивать новые пары со старыми 65 в одном среднем без раздельного представления.

### Cold rerun принятого reference

Выбор владельца: авторинг через CLI, cold rerun через уже проверенный браузерный UI-путь готового Authoring; при его недоступности — вручную владельцем в Loginom UI. Перед повтором завершить авторскую сессию, сохранить точные входы и принятый LGP, зафиксировать SHA256 LGP и убрать прежний результат из места экспорта штатным `collect_artifacts.py --park`. В отдельной браузерной сессии через «Пакеты → Открыть» открыть точный сохранённый пакет и выполнить все узлы с графа без открытия мастеров настройки, изменения связей/путей и сохранения пакета. Независимые ветви также должны исполниться; успешный экспорт сам по себе не подтверждает их выполнение. Если существующий UI-инструмент недоступен, передать владельцу тот же пакет и инструкцию; новый инструмент или execution-only API этим планом не разрабатывается.

Приёмка: в журнале/свидетельстве UI нет изменений настроек; SHA256 LGP до/после совпадает; результат создан заново после парковки прежнего; полный CSV совпадает с независимым oracle через существующий `check_reference.py`. Сохранить отдельные `check.json` и `check-rerun.json` по контракту skill. Закрытый oracle остаётся у проверяющего; в rerun передаются пакет, входы и указание выполнить сохранённый сценарий. Доказательство служебного cold rerun Authoring подтверждает способ работы, но не заменяет проверки нового reference.

Readback не заменяет эту процедуру. [TextExport](../../../packages/loginom-runtime/client/lib/text-export-node.mjs) может синхронизировать input mapping и сообщает `settings_applied:true`; специальные пути исполнения без настройки в [node-read-contract](../../../packages/loginom-runtime/client/lib/node-read-contract.mjs) не охватывают весь граф P01. [Схема квитанций](../../../packages/loginom-runtime/client/lib/node-result-schema.mjs) описывает наблюдаемые UI-значения до завершения, без подтверждения persistence; [node-apply](../../../packages/loginom-runtime/client/lib/node-apply.mjs) не доказывает сохранённый пакет. Mappings не дают полного upstream GUID/port графа, а model readback — полного сохранённого состояния. [Извлечение package docs](../../../packages/loginom-host/src/package-docs/extract.ts) читает ограниченную проекцию Unit.xml, не BIN. Поэтому совпадение readback с XML или SHA неизменного файла не разрешает повторное применение настроек при cold rerun.

### Уже подготовленное окружение

Источник актуальных путей и доказательств — план Authoring (приватный архив; не опубликован) и чат «Подготовить окружение local evals» (приватный архив; не опубликован). Переиспользовать принятую установленную CLI-поставку, профиль, workspace и браузерный cold rerun; не повторять setup, OAuth и инфраструктурный smoke. Авторские сценарии и историю сохранять; не передавать Authoring очищаемому benchmark runner. Перед измерениями перечитать актуальную передачу Benchmark в том же чате: его подготовка — отдельная работа. Исторические абсолютные пути другого компьютера из runbook не копировать в локальный запуск. Модель инфраструктурной приёмки не назначает модель новой кампании.

### Неудача авторского построения

Неудача авторинга не разрешает упрощать задачу, заменять её более лёгкой или ослаблять oracle/rubric. В пределах зафиксированного бюджета допустима помощь автору с конкретным исправлением и честным provenance; reference-build не выдаётся за измерительный запуск. При исчерпании бюджета или отсутствии нового основания пару целиком откладывают по [правилам кампании](../plans/2026-10-28-analytics-expansion-implementation.md#откладывание-пары-и-завершение-кампании). Причина, попытки, сохранённые свидетельства и условие возврата остаются в карточке; deferred не означает неподдержанный режим. Отложенная пара не блокирует независимые задачи после подтверждения пригодности общей среды. Итоговый отчёт раскрывает пропуски покрытия и ограничение выводов измеренным подмножеством.

## Последовательность будущего исполнения

Точные файлы/команды адаптации skill, порядок P01–P50 по группам и результаты каждого шага заданы в [плане реализации](../plans/2026-10-28-analytics-expansion-implementation.md). Использовать существующие инструкции [evals](../../../evals/AGENTS.md) и [runbook](../../testing/loginom-ai-agent/parallel-evals.md). Никакая команда запуска кампании настоящим документом не выполняется.

Существующий [skill создания кейсов](../../../evals/skills/loginom-eval-case/SKILL.md) адаптируется по предыдущему разделу непосредственно перед первым кейсом. Модель/вариант для живого построения определяются по действующим настройкам и согласованию запуска, а не назначаются этим исследованием.

Перед первым reference использовать [отбор из официальных материалов](2026-10-28-analytics-expansion-loginom-sources.md) и [каталог полного блога](2026-10-28-analytics-expansion-blog-candidates.md): определить, где можно принять готовый пакет, где требуется адаптация и где материал даёт только постановку для backlog. Новые кандидаты не увеличивают первую очередь сверх 50 пар: при окончательном отборе они конкурируют с близкими по механизму карточками, а не добавляются как отраслевые дубликаты. Для будущих узлов выбирать задачи с конкретными входами и проверяемой ошибкой из каталога; пример настройки без аналитического результата не завершает такую работу.

1. **Проверить P01 end-to-end.** Подготовить одинаковые inputs, два промпта и общий независимый oracle; построить/открыть/исполнить reference, выполнить выбранный cold rerun и прогнать обе формы. Результат: пакет и полный CSV проверены, разница формулировок не меняет смысл задания. До этого не массово создавать каркасы сотни кейсов.
2. **Проверить рискованные механизмы на реальных парах первых групп.** P50 — Excel, P27 — duplicate contradictions, P42 — выборочное stddev/pivot, P44 — регрессия и её проверяемые defaults, P46 — k-means, P22 — даты и переход года, P05 — NULL в результате. Конкретные операции начала дня/часовых ключей дополнительно проверить при первых P16/P20/P21: успех P22 не подтверждает все операции дат. Результат: принятая пара с reference/rerun либо deferred-пара с конкретной диагностической причиной и условием возврата, зафиксированными в её карточке. Отдельный framework проб не нужен.
3. **Уточнить 50 карточек по данным и источникам Loginom.** Сопоставить дополнительные кандидаты с текущими карточками; при замене явно обновить обе формулировки, источники и отличие от прежнего корпуса, сохранив 50 пар. Выбрать разрешённые реальные снимки, построить пограничные случаи, проверить ключи/единицы/ловушки и одинаковую информационную достаточность пары. Результат: каждая задача имеет однозначную сдачу и независимо вычисляемый ответ; использованный демопакет имеет подтверждённый статус, а неподдерживаемые методы остаются в backlog.
4. **Разбирать небольшими группами по 5 пар.** Для каждой принятой пары reference, полный экспорт, cold rerun и полная калибровка по действующему контракту. Результат: до 10 новых evals с доказательствами и явные deferred; прежние принятые кейсы не ослаблены. Независимая следующая группа не ждёт снятия блокера отложенной пары; размер группы — организационный выбор, не новая система очередей.
5. **Провести итоговое ревью исходных 50 пар.** Проверить повторяемость, неповторяемость механизмов, отсутствие утечки эталона и неподдерживаемых обходов. Результат: K принятых пар/2K runnable случаев, корректно выбираемых существующим `--tasks`, и 50−K deferred с причинами/условиями возврата. Неразобранные задачи не выдаются за отложенные.
6. **Запустить отдельные сопоставимые серии.** По одной уже разрешённой измерительной попытке каждой принятой формы с pins и бюджетом плана, последовательно. Результат: два отчёта и парная таблица исходов, K/50 покрытия, перечень отложенных пар и инфраструктурные ограничения; FAIL агента сохраняется как измеренный результат.
7. **Расширять по зависимостям backlog.** После принятия нового узла/режима возвращать соответствующие карточки в отбор. Результат каждого такого шага — один реальный новый аналитический путь, а не только изменение статуса в каталоге.

## Размер, риски и исключения

Исследование и согласованный дизайн находятся в связанных документах выше; текущая правка ограничена документацией по [плану применения review](../plans/2026-10-28-analytics-expansion-review-fixes.md). Исполняемый код, fixtures и зависимости не меняются. Оценки будущих этапов уточняются отдельно по их фактическому объёму, без переноса устаревшей оценки размера первоначального исследования.

Будущая реализация 100 случаев значительно больше текущей документационной работы: по существующему образцу порядка 8 основных файлов на случай плюс входные файлы/near-miss. Точный объём строк нельзя честно предсказать до выбранных данных и XML reference; первые 5 пар дадут основу отдельной оценки. Общий helper/loader/shared store ради уменьшения числа файлов не вводится заранее.

Основные риски: реальные данные не различают неверные решения; бизнес-запрос допускает несколько определений метрики; модельные outputs неустойчивы; нужный режим существует в UI, но отсутствует в API агента; публичный benchmark не публикует gold или права на данные. Для каждого риска предусмотрена проверка перед массовым построением, а не новый универсальный subsystem.

Исключено из первой очереди: новые node handlers, использование JS вместо специального узла, новый runner/judge framework, live web scraping, сетевой сервис fixtures, большие warehouse/GPU среды, dashboards, многоходовый пользователь, actions с бизнес-последствиями, произвольные исследования с неизвестным заранее набором правильных выводов. Эти направления сохраняются в базе будущих работ.

## Проверка документационного результата

Готовность проекта: 50 неповторяющихся карточек, каждая имеет две формы, данные, доступный путь, проверку и отличие от существующего корпуса; будущая база охватывает полный аналитический цикл и различает виды блокеров; ссылки открываются; независимое ревью не оставляет обязательных замечаний. Это проверка проекта, не приёмка будущих evals.

На момент написания выполнены статическое чтение кода, инвентаризация корпуса, чтение памяти и исследования, выборочная проверка первоисточников. Исторический каталог 200 задач из памяти локально не найден и не засчитывается как прочитанный. Текущее исполнение и результаты реальных fixtures/reference отражаются в [плане реализации](../plans/2026-10-28-analytics-expansion-implementation.md#исполнение-и-checkpoint) и карточках пар; принятие одной пары не подтверждает остальные.
