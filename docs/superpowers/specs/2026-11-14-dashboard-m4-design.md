# Dashboard M4: публикация через хранилище Loginom

Статус: дизайн принят владельцем 14 ноября 2026 года, включая технические уточнения ниже. [План реализации](../plans/2026-11-14-dashboard-m4.md) подготовлен и прошёл независимое ревью. Владелец разрешил автономную реализацию всех задач принятого плана.

Основа — [roadmap](2026-11-11-dashboard-architecture-roadmap.md), [изоляция](../../security/dashboard-isolation.md) и [дизайн M3](2026-11-12-dashboard-m3-design.md). Этот документ уточняет M4 по результатам S1/S2 и завершённого M3. Установленная приёмка M3 PASS; её результаты и ограничения сохранены в runbook M3. Публикация, описанная здесь, пока не реализована.

Независимая проверка полноты дизайна завершена: важных вопросов, мешающих составлению плана, не осталось.

## Результат и границы

Пользователь готовит dashboard локально, подтверждает публикацию, а хост агента передаёт исходники через его сессию Studio. Стенд собирает их в изолированном builder и показывает последнюю успешно собранную версию. Файл `.lgp` остаётся неизменным; пакет открывается и без компонентов dashboard.

M4 охватывает формат публикации, закрытые операции хоста для Desktop и CLI, чтение опубликованных исходников, версию-основу черновика, publisher/builder, статусы web и установку трёх контейнеров на dev-стенд. Существующие снимки, локальная сборка, профиль модели и браузерная изоляция M3 используются повторно.

За пределами M4: автоматический merge исходников, инструмент отката или удаления, совместимость с публикациями M3 без исходников, дополнительные зависимости приложения, общий файловый API хоста, новый браузер для Studio, брокер задач, несколько builder, `containers.sh`, HTTPS/частный CA и нативные установки. Release-установка и Podman/SELinux следуют этапам roadmap. Потеря локальных правок, перезапись чужой версии без предупреждения и сообщение об успехе до подтверждения стенда недопустимы.

## Выбранный подход

| Подход | Что даёт и сколько требует | Решение |
|---|---|---|
| А: через авторизованную Studio на обоих стендах | Loginom сам проверяет права; один путь для Desktop и CLI. Нужна узкая операция в существующем хосте | Выбран владельцем |
| А на release, прямая запись на dev | Упрощает первый вызов на master, но оставляет два способа публикации с разными правами и развёртыванием | Отклонён при выборе А для обеих версий |

Владелец также выбрал:

- сохранять локальные `src/` и версию-основу; при открытии сообщать о новой публикации на стенде, перед заменой запрашивать подтверждение;
- перейти с M3 разовой перепубликацией из локальных черновиков;
- проверять S1/S2 независимо от стенда приёмки M3.

S1/S2 подтвердили операции Studio, права чтения publisher и загрузку с последующим переименованием на master и 7.4.2. Подробные условия и ограничения измерений хранятся только в [разделе spike roadmap](2026-11-11-dashboard-architecture-roadmap.md#открытые-вопросы-и-spike). Сквозной вызов из поставляемого хоста агента ещё требуется проверить.

Технические решения ниже используют существующие механизмы M3 и согласованы вместе с дизайном.

## Продолжение локального черновика

1. Desktop или CLI получает одноразовый снимок обычным путём M3 и определяет рабочую папку по ключу привязки. Хост читает сведения о последнем файле публикации через настроенное подключение Studio.
2. Если локальный `src/` уже есть, его содержимое и основа сохраняются. Снимок и образец обновляются по правилам M3. Различие основы и последней версии показывается пользователю при открытии; оно само по себе не блокирует черновик.
3. Если локальных исходников нет, хост читает последний файл публикации, проверяет формат и привязку и только затем раскладывает его `src/`. Основой становится этот файл. При отсутствии публикации используется шаблон; отсутствие основы хранится явно.
4. Последний файл и текущая работающая версия могут различаться: последний файл мог не собраться. Для правки берутся последние корректно прочитанные исходники, а сообщение называет ошибку сборки и работающую предыдущую версию. Некорректный файл не заменяется молча шаблоном или предыдущими исходниками: пользователь получает причину отказа.

В `control/` к существующей привязке добавляется основа: имя файла и хеш его содержимого либо отсутствие основы. Хеш нужен, чтобы заметить ручное изменение содержимого под прежним именем. Если основа в старой папке M3 неизвестна, появление публикации на стенде считается расхождением. Повторное открытие не назначает последнюю серверную версию основой существующих локальных правок.

При недоступности Studio существующий локальный черновик можно открыть с сообщением, что версию на стенде проверить не удалось. Получить исходники для новой папки или публиковать без этой проверки нельзя. При смене origin подключения старая папка автоматически к новому стенду не привязывается: нужна новая кнопка в Studio и проверка принадлежности папки, как в M3.

## Подготовка и подтверждение публикации

Сохраняется разделение `preparePublish` и `finishPublish` из M3. Первая часть фиксирует проверяемые байты, вторая выполняет подтверждённое действие.

1. Инструмент копирует разрешённый `src/` в служебную папку операции, проверяет данные образца, импорты, типы и сборку. Из **той же копии**, прошедшей проверки, создаётся JSON публикации. M3 пока сохраняет только результат сборки; в M4 нужно сохранить и проверенные исходники до окончания операции.
2. Привязка берётся из `control/`. `title` берётся из имени узла, параметры — из доверенного снимка; их подписи по умолчанию совпадают с именами. Отдельный редактор этих метаданных M4 не требует. Образец строк в JSON не попадает.
3. Хост читает последнюю версию. Окно подтверждения называет узел и пакет. Если основа отличается, то же окно явно сообщает о новой версии и предлагает опубликовать поверх неё локальный черновик. Это одно подтверждение конкретной подготовленной публикации.
4. После ответа хост снова сверяет последнюю версию. Если она изменилась за время ожидания, загрузка не начинается: требуется новое подтверждение с новой версией. После подтверждения исходники повторно из рабочей папки не читаются.
5. Далее выполняются загрузка, ожидание статуса и обновление основы. Отказ пользователя сохраняет черновик и ничего не записывает на стенд. CLI сохраняет поведение M3: без `--auto` разрешение отклоняется, с `--auto` подтверждается разработчиком.

Проверка версии не является блокировкой чужих публикаций. Два одновременно подтверждённых черновика могут стать двумя последовательными версиями; действует выбранное в roadmap правило последней публикации. Уже существующий файл никогда не перезаписывается.

## Закрытая операция хоста

Используются существующие порт Desktop/CLI, lease поколения подключения и авторизованный контекст managed runtime. Расширение касается двух служебных сценариев: прочитать последнюю публикацию и записать подготовленную публикацию. `list/read/mkdir/upload/rename` остаются деталями этих сценариев, недоступными модели как произвольные операции.

Подготовка папки происходит до создания чата и сейчас не имеет model-run lease. Для неё короткой операцией владеет вызывающий Desktop/CLI: хост удерживает поколение подключения до окончания чтения и освобождает его при завершении или отмене. Публикацией владеет builtin `dashboard_publish` в существующем lifecycle. Произвольный переход профиля dashboard в automation не разрешается.

Хост проверяет схему аргументов, origin и допустимый путь внутри `<packagePath>.dashboards/<nodeGuid>/`; путь выводится из служебной привязки. Он проверяет размер содержимого до передачи в браузер. Модель по-прежнему вызывает инструмент без аргументов и не получает пароль, cookie, сессию или возможность выполнять браузерный код.

Нельзя просто снять ограничение версии `7.4.2` у общего storage driver: у него другой контракт, три назначения и подготовленный workspace. Узкий сценарий dashboard использует штатные методы Studio из авторизованного контекста и проверяется на минифицированном `/app/` обеих версий. Существующие ограничения остальных инструментов остаются действующими.

### Завершённая загрузка и имена

S1 показал, что конечное имя видно ещё во время записи. Поэтому хост сначала загружает JSON под уникальным временным именем с суффиксом `.part` в той же папке, ждёт окончания штатной загрузки и переносит в окончательное UTC-имя штатным `MoveFile(part, final, false)` в той же папке. Publisher рассматривает только окончательные имена. На master и 7.4.2 проверены сохранение обоих файлов при занятой цели, полные байты/размер при первом наблюдении свободной цели и сохранённый inode. `RenameFile` не подходит: он перезаписывает занятую цель на обеих версиях.

Имя выбирается по правилу времени из roadmap. Штатный `MoveFile` с `AOverwrite=false` при занятом конечном имени отказывает, сохраняя оба содержимых (проверенный отказ OS Code 17). Предварительная проверка наличия файла сама по себе этой гарантии не даёт. Проверка столкновения и свободного переноса выполнена до реализации остальных слоёв; схема UTC-имён и порядок публикаций сохранены.

При столкновении известный отказ оставляет `.part` и возвращает понятное сообщение; следующая публикация выбирает новое имя. При обрыве связи хост читает окончательное имя и сверяет хеш: совпадение подтверждает передачу, а недоступность проверки оставляет результат неизвестным. Автоматически повторять запись после неизвестного результата нельзя. Неоконченные `.part` не становятся публикациями; пользователь может удалить их в Studio. Нового инструмента удаления нет.

## Формат и проверка файлов

Единственный формат v1 задан в [roadmap](2026-11-11-dashboard-architecture-roadmap.md#формат-файла-публикации-версия-1): `format`, `template`, `binding`, `title`, `parameters`, `files`. Схема строгая; обязательны `src/main.tsx`, разрешённые пути, расширения и кодировки. Повторяющиеся пути отклоняются. Ограничение размера относится ко всему UTF-8 JSON, включая base64 и метаданные; успешная локальная сборка сама по себе не доказывает, что публикация помещается в этот лимит.

Агент проверяет готовый JSON до подтверждения, publisher повторяет проверку на границе недоверенного хранилища. Проверки не пытаются доказать безопасность JavaScript: эту границу обеспечивает существующая изоляция браузера и builder.

Publisher сопоставляет физический путь в `UserStorage` с каноническим путём Studio и проверяет `packagePath` и `nodeGuid` из JSON. Общие и личные папки проверяются отдельно. `workflowGuid` проходит валидацию и участвует в ключе; узнать его из пути файла нельзя. Publisher не читает и не изменяет внутренности `.lgp`. GUID чужого сценария не должен попасть в ключ реального сценария при `lookup`.

## Publisher, builder и web

Три роли одного образа и их права остаются как в roadmap. Web читает только проверенные сборки; publisher имеет `UserStorage` только на чтение и не имеет сети; builder не видит ни сеть, ни `UserStorage`. Параметры контейнеров сохраняют ограничения плана изоляции. UID/GID publisher выбираются по реальному процессу Loginom, а доступ проверяется чтением из контейнера; наличие `group_add` само по себе доказательством не считается.

### Обход и сборка

1. Publisher обходит хранилище с интервалом roadmap и не следует символическим ссылкам. Окончательный JSON копируется с ограничением размера в служебный вход, проверяется, хешируется и становится задачей. Изменение файла во время чтения откладывает его до следующего обхода. Для штатной публикации готовность обеспечивает переименование после завершённой загрузки; неизменные size/mtime за два обхода сами по себе не доказывают её завершение.
2. Обрабатывается одна задача за раз одним builder. Последние известные результаты по имени файла и хешу сохраняются рядом с состоянием публикаций; одинаковый уже обработанный файл не собирается на каждом обходе. Ошибка сборки также считается результатом до изменения исходника или явной новой публикации.
3. Publisher создаёт пустой каталог результата непосредственно перед выдачей задачи. Builder накладывает `src/` на закреплённый шаблон и использует проверки и команды сборки M3. Новых зависимостей и конфигурации сборки от приложения не принимает. После одной задачи процесс завершается, контейнер перезапускается по существующей схеме roadmap.
4. Publisher переносит ограниченную копию результата в собственный временный каталог и проверяет именно её: разрешённые пути и типы, отсутствие ссылок и специальных файлов, общий размер. Из этих же байтов считает хеш и формирует неизменяемый каталог сборки. Builder не может менять принятые файлы через `jobs-out`. После обработки вход и выход задачи удаляются.
5. Активация атомарно обновляет состояние привязки, которое читает web. Активной становится самая новая по имени успешно собранная версия из существующих файлов. Завершение старой задачи не откатывает более новую. Ошибка новой версии сохраняет работающую предыдущую.

Таймаут, память, число процессов и максимальный вывод берутся из roadmap. Начальный предельный размер результата — 20 МиБ суммарно; исполнитель проверяет запас на трёх примерах M3. Лимиты подтверждаются реальными примерами, необходимые корректировки принимаются по замерам и независимому ревью без изменения контракта. Превышение ограничений даёт `failed` и сохраняет прежнюю публикацию.

Вход задачи и проверенные результаты уже являются достаточным состоянием для восстановления. После рестарта publisher сверяет их с существующими файлами публикации, использует готовые проверенные сборки и заново ставит только незавершённую задачу. Общего журнала команд, брокера и повторных сетевых операций нет. Если исходник удалён во время сборки, результат не включается.

### Статус и завершение инструмента

`lookup` сохраняет сведения о текущей работающей сборке и добавляет сведения о последней публикации. Для ожидания конкретной операции запрос может содержать имя её файла; ответ отдельно возвращает статус именно этого файла. Это требуется, чтобы новая чужая публикация не скрыла результат своей. Web читает только состояние publisher и не получает файловый API или доступ к `UserStorage`.

Состояния публикации: `pending`, `building`, `ready`, `failed`. До обнаружения загруженного файла publisher ответ на запрос его статуса — `pending`; он не означает, что web подтвердил наличие файла. При `ready` ответ содержит имя файла и хеш его содержимого, проверенный хеш сборки; они должны совпасть с ожидаемой операцией. При последующем удалении файла ответ не возвращает прежний `ready`.

Инструмент ждёт свой результат в пределах уже заданных интервала и срока. `ready` подтверждает успешную публикацию; если к этому моменту текущей стала более новая версия, инструмент сообщает обе вещи. `failed` возвращает ограниченный текст ошибки. По истечении срока возвращается `pending`: «Файл передан, сборка ещё не подтверждена», без повторной публикации и без сообщения об успехе. Этот исход дополняет ответы инструмента из roadmap.

Основой становится собственный подтверждённо записанный файл с проверенным хешем: повторная правка не требует подтверждать замену своей же публикации, в том числе пока она собирается. Неизвестный результат записи основу не меняет. `sample.json` удаляется только после `ready`, с существующей защитой M3 по ID снимка; ошибка удаления не отменяет успешную публикацию. При позднем `ready` после завершения ожидания образец остаётся до следующего успешного действия; фонового наблюдателя ради очистки не добавляется.

### Откат и отключение

Пользователь удаляет новейший файл в Studio; на следующем обходе выбирается предыдущая успешно собранная версия. Удаление папки узла отключает dashboard. Проверенные старые сборки сохраняются, пока существуют соответствующие исходные файлы. При одинаковом результате нескольких исходников удаление одного не удаляет сборку, пока она нужна другому. Удаление применяется только к ресурсам этого dashboard.

## Разовый переход с M3

Сохраняются локальные папки M3 с `src/` и служебной привязкой. Старые опубликованные бандлы не становятся входом нового publisher. Перед заменой стенда оператор сохраняет прежнюю установку и проверяет наличие нужных локальных черновиков; очистка прежних данных выполняется отдельно после проверки перепубликации.

Для каждого нужного dashboard пользователь снова нажимает кнопку в Studio, получает свежий снимок и открывает сохранённую папку. Это необходимо: M3 удаляет образец после успешной публикации, а повторная проверка исходников требует образца. Если M4 ещё не видит публикацию, используется «Создать dashboard»; существующий локальный `src/` при этом сохраняется.

Пользователь один раз подтверждает обычный `dashboard_publish`, затем открывает результат в Studio. Между переключением стенда на M4 и этой публикацией прежний dashboard недоступен. Если локального черновика нет, восстановить исходники из бандла автоматически нельзя; dashboard нужно создать заново. `.lgp` и его GUID при переходе не меняются.

## Последовательность и доказательства результата

Это порядок проверки дизайна; подробный план реализации составляется после согласования.

1. **Первый сквозной результат.** На изолированных master и 7.4.2 из поставляемого хоста прочитать последнюю публикацию, загрузить небольшой искусственный JSON, переименовать и прочитать те же байты. Подтвердить отказ при занятом имени и без прав. Проверить Desktop и CLI через общий канал, включая владение операцией до создания чата. Это снимает главный риск пути А до разработки publisher.
2. **Минимальная настоящая публикация.** Один пример M3, подтверждение, JSON в личной папке, одна сборка без сети, `ready` своего файла, открытие dashboard в Studio. `.lgp` побайтно прежний. Только после этого добавляются остальные отказы и восстановление.
3. **Полный пользовательский цикл.** Правка из локальных и скачанных исходников, новая версия на стенде, подтверждение замены, отказ, смена поколения подключения, общая папка, ошибка сборки с сохранением прежней версии, ожидание дольше срока и ручной откат. Проверяются необходимые границы формата, путей и результата сборки.
4. **Установка и переход.** Dev-рецепт предоставляет `UserStorage` publisher только на чтение с сохранением существующих данных; проверяются права контейнеров, рестарт, разовая перепубликация M3 и открытие пакета без компонентов dashboard. Установленная проверка release 7.4.x выполняется по условиям M4 в roadmap; её отсутствие обозначается явно.

Тесты проверяют наблюдаемые свойства: чужой файл не перезаписан; проверенные исходники совпадают с переданными; прежняя версия работает после отказа; статус относится к своему файлу; образец другого снимка сохранён. Существующие команды пакетов и браузерные проверки используются повторно. Сценарии, которым нужен Loginom, идут на выделенных стендах; приёмка M3 не переустанавливается и не перезапускается этим этапом.

## Изменяемые части и цена механизмов

| Часть | Изменение и основание |
|---|---|
| `packages/dashboard`: contract, agent, shell, web | Формат/статус, проверенные исходники, основа и сообщение о расхождении; без них нельзя безопасно повторно публиковать |
| `packages/dashboard`: publisher, builder, deploy | Три согласованные роли, обработка файлов и ограниченная сборка; повторное использование шаблона, резолвера и раздачи M3 |
| `packages/loginom-host`, `packages/loginom-runtime` | Два закрытых сценария через существующее поколение подключения; права проверяет Loginom |
| `packages/desktop`, `packages/opencode` | Чтение при подготовке папки, подтверждение и вызов хоста в builtin-инструменте; общий контракт для Desktop/CLI |
| Тесты, bundled skill, профильные AGENTS/runbook | Новый путь публикации, отказы и процедура перехода; инструкции должны соответствовать продукту |

Новые состояния имеют конкретную причину: основа замечает чужие изменения; `.part` отделяет загрузку от готового файла; состояние задачи связывает исходник, результат и статус; `pending` не выдаёт ожидание за успех. Каждый механизм располагается у существующего владельца соответствующей операции.

Предварительный масштаб реализации: 25–40 файлов, 1 500–2 500 добавленных/удалённых строк вместе с тестами и документацией; это оценка, не бюджет для заполнения. План уточнит её после принятия M3. При превышении вдвое требуется пересмотреть подход по правилам инженерной простоты.

Исполнителю оставлены точные имена закрытых запросов и файлов состояния, размещение общих функций существующей сборки и последовательность тестов. Новые пользовательские функции, ослабление изоляции и изменение обязательных гарантий требуют отдельного решения. Установка M3, её текущая приёмка и общие ограничения версии runtime этим документом не изменяются.
