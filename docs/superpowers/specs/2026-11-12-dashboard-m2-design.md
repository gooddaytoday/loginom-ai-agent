# Dashboard M2. Изоляция на dev-стенде

**Статус.** Утверждён владельцем 2026-11-12. База — `dashboard-app`, `22fb4a2558`. Общее устройство задают [roadmap](2026-11-11-dashboard-architecture-roadmap.md) и [план изоляции](../../security/dashboard-isolation.md). Этот документ уточняет границы M2 после [приёмки M1](../../testing/loginom-ai-agent/dashboard-m1-handoff.md) и не пересматривает архитектуру.

## Результат

После обновления dev-стенда ROI-dashboard открывается из Studio в песочнице с отдельного адреса `http://dashboards.localhost:32769`. `MinBudget` меняется в доверенной шапке над dashboard. Приложение не видит Studio, сессию и пароли и не может отправить данные в сеть обычными каналами; остаточные каналы обычного режима описаны в плане изоляции. После приёмки снимается правило «открывать только свои dashboard». До M4 действует другое правило: публиковать через `publish.mjs` только доверенный код, потому что скрипт выполняет `npm run` из `package.json` приложения на машине публикации.

Desktop в M2 не меняется: снимок он по-прежнему читает с `http://127.0.0.1:32768/dashboard/targets/<ID>`, только отвечает теперь контейнер web.

## Решения владельца (2026-11-12)

1. Вся служба (снимки, `lookup` и хост приложений) переезжает в один контейнер web. Node уходит из контейнера сервера Loginom.
2. Строгий режим в M2 — флаг `--strict`, режим в `lookup`, проба и отказ. Роль отдельного сайта на dev-стенде играет `dashboards.localhost`. Отдельный домен с сертификатом и TLS — в M5 вместе с `containers.sh`.
3. Шапка показывает все числовые переменные по имени и проверяет только тип. Подписи и пределы придут в M4 из файла публикации. Заплатка `MinBudget >= 0` в оболочке удаляется.
4. Оболочка подключается как в M1: `sed` в `index.html` и статический `shell.js` у Apache. `mod_substitute` и `integrity` — в M5.
5. Trusted Types не включаются. Если строгий `style-src` ломает график, в `style-src` добавляется `'unsafe-inline'`, и решение записывается в roadmap и в раздел «Заголовки» плана изоляции. Вынести данные через CSS приложение и тогда не сможет: `img-src` и `font-src` ограничены хостом приложений.
6. Публикации M1 не переносятся. Все три примера переписываются на SDK v1 и проверяются сборкой; живая перепубликация и приёмка — на ROI.
7. Порядок работ: короткая разведка `Report-Only` до кода, затем код вертикальными срезами через TDD, затем одно обновление стенда и приёмка.
8. Проба строгого режима отвечает через порт, как в плане изоляции.
9. Studio не встраивают в чужие страницы. На странице Studio остаётся `frame-ancestors 'none'`, как в плане изоляции; вопрос S4 о встроенном режиме закрыт этим решением.

## Порядок работ

1. **Разведка на стенде M1, до кода.** На страницу обоих клиентов Studio добавить `Content-Security-Policy-Report-Only` со строкой CSP страницы Studio (раздел «Стенд»). С открытыми DevTools пройти загрузку и выгрузку файлов, импорт, визуализаторы, отчёты и справку. Записать собственные фреймы Studio в roadmap (S4), затем убрать строку. Каждый найденный источник добавляется в `frame-src` только с согласия владельца: в Firefox `frame-src` — единственная защита от перехода iframe на чужой адрес.
2. **Код вертикальными срезами «тест → код»:** хост приложений и `lookup`, `publish.mjs`, SDK v1 и шаблон, оболочка, набор вредоносных dashboard, строгий режим, примеры, `dev-master.sh`. Поведение M1 не удаляется, пока не закреплено тестом через новый канал (раздел «Проверки»).
3. **Одно обновление стенда поверх M1 и приёмка** по разделу «Приёмка».

## Стенд

**Контейнер web.** `dev-master.sh install` запускает контейнер `dashboard-master-20261109-web` (имя по схеме рецепта стенда, переопределяется флагом) в сети стенда. В нём один процесс Node с двумя портами: 8100 — API `/dashboard/…` для Apache, 8101 — хост приложений, опубликованный как `127.0.0.1:32769`.

- Запуск — `docker run` с `--read-only`, `--cap-drop ALL`, `no-new-privileges`, tmpfs для `/tmp`, пределами памяти и числа процессов, ограничением размера журнала (`--log-opt max-size`) и `--restart unless-stopped`. Значения пределов задаёт план. Процесс работает с UID и GID пользователя, который запускает `install`: так web читает сборки, созданные `publish.mjs` с правами 0700. `install` от root отказывается работать, `check` проверяет, что UID контейнера не 0. Compose появится в M4, когда контейнеров станет три.
- Своего образа в M2 нет. Используется `debian:bookworm-slim`, закреплённый по digest: в нём есть `libstdc++`, нужный закреплённому Node. Node и `server.mjs` монтируются только на чтение. Свой образ нужен в M4, когда builder понадобится набор шаблона.
- Каталог состояния — `~/loginom-dashboard/` того же пользователя. В нём `builds/` (у web — только чтение) и копии Node и `server.mjs`: `install` копирует их туда, и пересборка в checkout не задевает работающий контейнер.
- Переменные окружения web: адрес хоста приложений, адреса Studio для `Host` и `frame-ancestors`, режим, каталог сборок внутри контейнера и корень checkout. Корень checkout нужен только для строк `sourceDir` и `commands` в снимке; сам checkout в контейнер не монтируется.

**Переход с M1.** `install` останавливает службу M1 в контейнере сервера Loginom и удаляет её файлы. Старые публикации в `/workdir/dashboard-app` остаются на месте, но больше не раздаются.

**Apache (`dashboard-app.site.conf`).** `install` пишет файл во временный рядом, переименовывает и проверяет `apachectl -t`. При ошибке возвращается прежний файл, и установка останавливается.

- `/dashboard/` проксируется на web с короткими таймаутами и `disablereuse=On`. Проверка `Host` и `ProxyPreserveHost` — как в M1.
- На ответах `/dashboard/`: `Content-Security-Policy: sandbox; default-src 'none'` и `X-Content-Type-Options: nosniff`.
- На странице `/app/` и `/app-debug/` — принудительный `Content-Security-Policy`, `X-Content-Type-Options: nosniff` и `Referrer-Policy: same-origin`. Шаблон строки CSP — `frame-src <DASH>; object-src 'none'; frame-ancestors 'none'` плюс источники, согласованные по итогам разведки. Он хранится в одном файле `packages/dashboard/deploy/studio.csp`. `install`, `check` и тестовая страница Studio подставляют вместо `<DASH>` адрес хоста приложений — то же значение, которое получает web (на стенде `http://dashboards.localhost:32769`, в тестах — адрес со случайным портом).
- Вставка оболочки через `sed`, статический `shell.js` и `client.json` — без изменений.

**Режимы и удаление.** `install --strict` включает строгий режим, повторный `install` без флага возвращает обычный. `uninstall` снимает контейнер, конфигурацию Apache и оболочку, но до M4 сохраняет `builds/`: пересобрать сборки автоматически пока нечем.

## web

**Каталог сборок.**

```
builds/<ключ>/
  <хеш>/          сборка: index.html и assets/; единственное, что раздаётся
  current         хеш текущей сборки, одна строка
  binding.json    привязка; нужна поведению `sample: null` из M1 и уходит в M3
  sample.json     пример строк; то же
```

**API (порт 8100, за Apache).**

- `POST /dashboard/lookup` отвечает `{key, exists, hash, appOrigin, mode}`. `hash` — содержимое `current` или `null`, если сборки нет; `exists` всегда равно `hash !== null`. Схема `LookupResponse` в `src/contract` расширяется. Ручные проверки оболочки дополнительно требуют, чтобы `hash` был 64 шестнадцатеричными символами или `null`, а `appOrigin` — origin `http` или `https`; тест сверяет их со схемой, как в M1.
- `GET /dashboard/apps/…` удаляется: на origin Studio приложений больше нет.
- Снимки (`targets` и `current`) не меняются до M3. Меняется только текст `adapter`: вместо `window.frameElement.dashboard` в нём описан SDK v1, потому что этот текст получает модель в Desktop.

**Хост приложений (порт 8101).**

- Адреса хоста приложений и Studio берутся из настроек web; ниже даны значения стенда. Принимается только `Host` хоста приложений (`dashboards.localhost:32769`), остальные получают 403.
- `GET /apps/<ключ>/<хеш>/` отдаёт `index.html`, `GET /apps/<ключ>/<хеш>/assets/<имя>` — файл сборки. Ключ и хеш — 64 шестнадцатеричных символа, `realpath` не выходит за `<хеш>/`. Разрешены типы js, css, svg, png, jpg, webp и woff2; остальное — 404.
- `/_probe/` (страница и её скрипт) отвечает только в строгом режиме, в обычном — 404.
- `POST /_reports` принимает тело до 64 КиБ, пишет в журнал контейнера одну строку с телом отчёта и отвечает 204 с `Access-Control-Allow-Origin: *`. Заголовки запроса и cookie в журнал не попадают. `OPTIONS /_reports` отвечает 204 с `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods: POST` и `Access-Control-Allow-Headers: content-type`: документ в песочнице может доставлять отчёты с предварительным запросом CORS (S4).
- Всё прочее — 404. Перенаправлений нет: адрес без косой черты в конце тоже получает 404.
- Каждый ответ, включая 403, 404 и 500, несёт набор заголовков из раздела «Заголовки» плана изоляции. `<DASH>` — `http://dashboards.localhost:32769`, `<CLIENT>` — `http://127.0.0.1:32768 http://localhost:32768`. `Cache-Control`: `no-store` у документов и ошибок, `public, max-age=31536000, immutable` у `assets/`. У `assets/` также `Access-Control-Allow-Origin: *`.
- Отключить `Connection-Allowlist` можно только параметром `dashboardServer()` в тестах. Переменной окружения для этого нет.

## Публикация (`publish.mjs`)

Как и раньше, скрипт читает снимок по ID, поддерживает `--init` и выполняет `npm run typecheck` и `npm run build` в каталоге приложения. Затем:

1. считает хеш сборки: SHA-256 по отсортированным относительным путям файлов `dist` и их байтам;
2. копирует сборку во временный каталог рядом и переименовывает его в `builds/<ключ>/<хеш>/`; если такой каталог уже есть, копия не нужна;
3. записывает `binding.json` и `sample.json` через временный файл и `rename`;
4. последним шагом так же записывает `current`.

Если сборка не удалась, ничего не меняется. Прежние каталоги `<хеш>/` остаются, поэтому уже открытые страницы не ломаются; уборка — в M4. `docker cp` и `docker exec` уходят.

Три переменные окружения нужны тестам, у каждой есть значение по умолчанию для стенда: `DASHBOARD_BASE` — адрес службы снимков (`http://127.0.0.1:32768`), `DASHBOARD_APPS` — каталог исходников приложений (`dashboard/apps` в checkout), `DASHBOARD_BUILDS` — каталог сборок (`~/loginom-dashboard/builds`). `check` вычисляет тот же путь по умолчанию и сверяет его с источником монтирования контейнера web.

## Браузер

### Сообщения

| Сообщение | Откуда и куда | Канал | Формат |
|---|---|---|---|
| `ready` | приложение или проба → оболочка | окно | `{type: "loginom-dashboard/ready", version: 1}` |
| `init` | оболочка → приложение или проба | окно, с одним `MessagePort` | `{type: "loginom-dashboard/init", version: 1}` |
| `state` | оболочка → приложение | порт | `{type: "state", parameters, table, error, busy}` |
| `close` | приложение → оболочка | окно | `{type: "loginom-dashboard/close", version: 1}` |
| `probe` | проба → оболочка | порт пробы | `{type: "probe", ok}` |

`table` — `{schema, rows, truncated, totalRows}` или `null`. Единственное, что оболочка принимает с порта, — ответ `probe` с порта пробы. С порта dashboard она не принимает ничего. Сообщение другого вида или с лишними полями игнорируется.

### SDK v1 и шаблон

SDK — один файл `src/sdk/loginom.ts` без зависимостей. Сборка пакета копирует его в `template/src/loginom.ts`; тест сверяет с ним эту копию и копии в трёх примерах.

- При загрузке SDK подписывается на `message` и отправляет `ready` родителю с адресатом `"*"`.
- `init` с одним портом принимается один раз и только от `parent`. Каждое `state` с порта проверяется вручную: в шаблоне нет `effect`. Неверное `state` игнорируется с записью в консоль. Тест сверяет проверки SDK со схемой `contract`.
- Приложению доступны `onState(listener)` (возвращает отписку; поздний подписчик сразу получает последнее состояние) и `close()`. Esc внутри iframe вызывает `close()`. Функций `change` и `run` и обращения к `window.frameElement` больше нет.

Шаблон показывает пять состояний: «Идёт расчёт», ошибка, пусто, данные и усечение. Если страница открыта не во фрейме (`window.parent === window`), шаблон пишет «Откройте dashboard кнопкой Dashboard в Studio». Полей ввода в шаблоне нет. Три примера переписываются так же: без полей, без кнопки «Выполнить» и без `run`. Значение параметра приложение показывает текстом, например «Расчёт при пороге MinBudget = 10 000».

### Оболочка

Порядок открытия — как в M1: `lookup`, в строгом режиме проба, выполнение неактивного узла, снимок. Если `lookup` вернул `hash: null`, оболочка идёт путём «Создать dashboard».

**Шапка.** Имя узла, путь пакета, поля числовых переменных, «Изменить в чате» и «Вернуться к сценарию». Подпись поля — имя переменной, у переменной без значения поле пустое. Значение принимается по Enter и при уходе из поля. Проверяется, что число конечное, а для целой переменной — целое; для этого `parameters()` возвращает признак целого типа, а в снимок (`targets`) этот признак не отправляется. Во время расчёта поля доступны, принятые значения встают в очередь, как в M1. Текст выводится только через `textContent`.

**Iframe.** `sandbox="allow-scripts"`, `referrerpolicy="no-referrer"`, атрибут `allow` из плана изоляции, адрес `<appOrigin>/apps/<ключ>/<хеш>/`.

**Протокол.**

- Из окна принимаются только сообщения с `event.source === frame.contentWindow`.
- На первый `ready` оболочка создаёт `MessageChannel`, отправляет `init` с портом и сразу первое `state`.
- Второй `ready` или повторный `load` после первого `ready` закрывают dashboard с записью в консоль. `close` закрывает dashboard. Больше 50 сообщений в секунду закрывают dashboard.
- Если `ready` не пришёл за 10 секунд, вместо dashboard показывается «Dashboard не ответил».
- Каждое принятое значение параметра — отдельный расчёт в очереди. Перед расчётом приложение получает `state` с `busy: true` и прежней таблицей, после расчёта — новое `state`. Приложение показывает последнее полученное `state`.
- При ошибке расчёта `state` содержит текст ошибки и `table: null`, как в M1. Показать прежнюю таблицу приложение может само.

**Лимиты таблицы.** Оболочка читает не больше 10 000 строк и обрезает ячейку до 10 000 символов. Объём оценивается по длине JSON прочитанных строк; строка, с которой он превысил бы 5 МБ, в таблицу не входит. Любое сокращение ставит `truncated: true`. `totalRows` берётся из `get_RowCount`. Пределы уточняются на реальных узлах.

**Удаляется:** `frame.dashboard`, `change`, `run`, заплатка `MinBudget` и обращение к `contentDocument`. Предел размера `shell.js` задаётся заново по первому замеру, как в M1.

### Строгий режим

Проба нужна только для открытия опубликованного dashboard: путь «Создать dashboard» чужого кода не выполняет и пробу не проходит, поэтому пользователь любого браузера может передать снимок в Desktop. Если `lookup` вернул `mode: "strict"` и `hash` не `null`, оболочка после `lookup` и до выполнения узла и отправки снимка загружает скрытый iframe `<appOrigin>/_probe/` с той же песочницей. Проба присылает `ready`, получает порт, пытается создать `RTCPeerConnection` и отвечает по порту `probe`. `ok: true` означает, что конструктор бросил исключение, то есть браузер применяет `Connection-Allowlist`.

- `ok: true` — открытие продолжается. `ok: false` — отказ с текстом из roadmap: «Dashboard открывается в Chrome, Edge или Яндекс Браузере на Chromium 152 и новее». Узел не выполняется, снимок не отправляется. Оба результата хранятся до перезагрузки страницы.
- Нет ответа за 5 секунд — отказ с текстом «Хост dashboard недоступен». Такой результат не запоминается, и следующее открытие пробует снова.

## Проверки

**web** (`node:test`, настоящие порты и временные каталоги; порог покрытия 90% сохраняется):

- маршруты хоста приложений и полный набор заголовков на 200, 403, 404 и 500;
- отсутствие перенаправлений, проверка `Host`, выход за каталог, список разрешённых типов;
- 404 на `binding.json`, `sample.json` и `/dashboard/apps/`;
- `/_probe/` в обоих режимах, `POST` и `OPTIONS /_reports`, предел тела, отсутствие заголовков запроса в журнале;
- поля `lookup` и равенство `exists === (hash !== null)`.

**`publish.mjs`** (настоящий HTTP-сервер снимков, временные каталоги через три переменные, приложение с тривиальными скриптами `typecheck` и `build`; задача `dashboard-browser`, где уже есть `npm`): `current` переключается атомарно; неудачная сборка не меняет текущую версию; одинаковая сборка не создаёт нового каталога.

**Браузер** (Chromium 154, настоящий `dist/server.mjs` на случайном порту и тестовая страница Studio с CSP из шаблона `deploy/studio.csp`, в который подставлен адрес этого сервера). Запросы к хосту приложений и к серверу-злоумышленнику Playwright не перехватывает.

- **Перенос проверок M1.** Поведение, которое тесты M1 проверяют через `frame.dashboard` и `contentDocument`, проверяется через поля шапки и тестовое приложение на SDK, которое записывает полученные `state`. Это порядок перекрывающихся изменений, повтор после ошибки, закрытие во время расчёта, автозапуск неактивного узла, `BeginOperationEx` и `EndOperationEx`, проверка целых, отмена и фиксация, пустой результат, ссылка Desktop и предупреждение Studio о несохранённых изменениях. Тест M1 удаляется только после того, как его поведение закреплено так.
- **Позитивные:** `state` доходит; изменение параметра в шапке пересчитывает узел; Esc из iframe и из шапки закрывает dashboard; шаблон показывает все пять состояний.
- **Лимиты:** 10 000 строк, ячейка длиннее 10 000 символов, 5 МБ; `truncated` и `totalRows`.
- **S5:** ROI собирается по шаблону и открывается под настоящими заголовками, график рисуется, нарушений CSP нет.
- **Набор вредоносных dashboard** из раздела «Проверки» плана изоляции — статичные HTML и JS без Vite. Внешний адрес — настоящий сервер `http://attacker.localhost:<порт>`, который считает TCP-соединения (событие `connection`), а не только HTTP-запросы: `preconnect` открывает соединение без запроса. Обращения к origin клиента считает обработчик маршрута тестовой страницы Studio, но только запросы из фрейма dashboard: запросы самой оболочки к `/dashboard/…` не в счёт. Попытка считается проваленной, если оба счётчика остались нулевыми и страница не получила доступа. Набор идёт дважды: с `Connection-Allowlist` и без него. WebRTC и `preconnect` проверяются только в первом прогоне. Во втором прогоне `preconnect` служит положительным контролем: соединение обязано появиться, иначе наблюдение не работает и тест падает. Если Chromium 154 не открывает соединение по `preconnect` из песочницы и без заголовка, проверка `preconnect` выносится из автотестов так же, как `dns-prefetch`, с записью в план изоляции.
- **`dns-prefetch` автотестом не проверяется.** Chromium сам разрешает `*.localhost`, и запрос к DNS снаружи не виден. Этот канал закрывают `Connection-Allowlist` и `X-DNS-Prefetch-Control: off`; исключение из списка «Проверки» записывается в план изоляции.
- **Атаки на протокол:** поддельный `state` из чужого окна, второй `ready`, шквал сообщений, огромное и неклонируемое сообщение. Оболочка не меняет параметры и не запускает узел, самое большее закрывает dashboard.
- **Строгий режим:** Chromium 154 с заголовком проходит пробу; сервер без заголовка даёт отказ без выполнения узла и без снимка; проба без ответа даёт «Хост dashboard недоступен», и следующее открытие пробует снова; путь «Создать dashboard» пробу не запускает.

**Примеры.** Все три собираются по шаблону (`tsc` и `vite build`) в CI-задаче `dashboard-browser`.

**`dev-master.sh`.** `bash -n` и ShellCheck. `check` дополнительно проверяет:

- флаги и UID контейнера web, совпадение каталога сборок с тем, куда пишет `publish.mjs`;
- что `hash` из `lookup` ROI равен `builds/<ключ>/current`, а сборка ROI отдаётся с хоста приложений с полным набором заголовков. Если сборки ROI нет, `check` пишет «Не проверено: опубликуйте ROI» и завершается с ошибкой, как живая проба M1;
- заголовки на 404, отказ на чужой `Host`, отсутствие перенаправлений, 404 на `binding.json`, `sample.json` и прежний `/dashboard/apps/`;
- принудительный CSP страницы Studio — точно строку из `deploy/studio.csp` после подстановки; `Content-Security-Policy-Report-Only` или отсутствие заголовка — ошибка. `appOrigin` из `lookup` совпадает с источником в `frame-src`;
- `sandbox` на ответах `/dashboard/` и режим, совпадающий с настройкой;
- прежнюю живую пробу обоих клиентов.

## Приёмка

На dev-стенде этой машины, по runbook в `docs/testing/loginom-ai-agent/`:

1. Разведка до кода выполнена, её итог записан в roadmap (S4).
2. `install` поверх M1. ROI перепубликован по ID свежего снимка. `check` проходит в обоих клиентах.
3. Studio под принудительным CSP: сценарии разведки повторены в обоих клиентах, нарушений CSP в консоли нет.
4. В `/app/` и `/app-debug/` `MinBudget` в шапке 0 → 10 000 → 0 даёт 500 → 453 → 500 кампаний; таблица и график совпадают с независимым расчётом по `dataset.csv`. Esc закрывает dashboard и из iframe, и из шапки. «Изменить в чате» выдаёт свежий ID снимка.
5. S4: в `chrome://process-internals` записаны процессы iframe и вкладки с адресом приложения. Отчёт из документа в песочнице доходит до `/_reports`; для этого тестовый dashboard-нарушитель публикуется на отдельную копию fixture, как проверка публикации в M1, а после приёмки его сборка удаляется вручную. Во вкладке с адресом приложения `document.cookie` бросает исключение. Встроить dashboard в чужую страницу не даёт `frame-ancestors`.
6. S5: у ROI на стенде нет нарушений CSP.
7. Firefox вручную: в обычном режиме ROI открывается и пересчитывается. После `install --strict` и `check` Firefox получает отказ с объяснением, а Chromium 154 открывает dashboard. Затем стенд возвращается в обычный режим.
8. После `uninstall` Studio работает без элементов dashboard, `builds/` на месте. После повторного `install` `check` проходит, и ROI открывается без перепубликации.

**Известное ограничение до M4.** `publish.mjs` выполняет `npm run` из `package.json` приложения и не мешает вшить файл машины публикации через `?raw`. Это угроза машине публикации, а не зрителям: зрителей защищают песочница и заголовки. Закрывает её builder в M4.
