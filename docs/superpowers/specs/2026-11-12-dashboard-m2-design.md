# Dashboard M2. Изоляция на dev-стенде

**Статус.** Утверждён владельцем 2026-11-12. База — `dashboard-app`, `22fb4a2558`. Общее устройство задают [roadmap](2026-11-11-dashboard-architecture-roadmap.md) и [план изоляции](../../security/dashboard-isolation.md). Этот документ уточняет границы M2 после [приёмки M1](../../testing/loginom-ai-agent/dashboard-m1-handoff.md) и не пересматривает архитектуру.

## Результат

После обновления dev-стенда ROI-dashboard открывается из Studio в песочнице с отдельного адреса `http://dashboards.localhost:32769`. `MinBudget` меняется в доверенной шапке над dashboard. Приложение не видит Studio, сессию и пароли и не может отправить данные в сеть обычными каналами; остаточные каналы обычного режима описаны в плане изоляции. После приёмки снимается правило «открывать только свои dashboard». До M4 действует другое правило: публиковать через `publish.mjs` только доверенный код, потому что скрипт выполняет `npm run` из `package.json` приложения на машине публикации.

Desktop в M2 не меняется: снимок он по-прежнему читает с `http://127.0.0.1:32768/dashboard/targets/<ID>`, только отвечает теперь контейнер web.

## Решения владельца (2026-11-12)

1. Вся служба (снимки, `lookup` и хост приложений) переезжает в один контейнер web. Node уходит из контейнера сервера Loginom.
2. Строгий режим в M2 — флаг `--strict`, режим в `lookup`, проба и отказ. Роль отдельного сайта на dev-стенде играет `dashboards.localhost`. Отдельный домен с сертификатом и TLS — в M5 вместе с `containers.sh`.
3. Шапка показывает все числовые переменные по имени и проверяет только тип. Подписи и пределы придут в M4 из файла публикации. Заплатка `MinBudget >= 0` в оболочке удаляется.
4. Оболочка подключается как в M1: `sed` в `index.html` и статический `shell.js` у Apache. `mod_substitute` и `integrity` — в M5.
5. Trusted Types не включаются. Если строгий `style-src` ломает график, в `style-src` добавляется `'unsafe-inline'`, и решение записывается в roadmap. Вынести данные через CSS приложение и тогда не сможет: `img-src` и `font-src` ограничены хостом приложений.
6. Публикации M1 не переносятся. Все три примера переписываются на SDK v1 и проверяются сборкой; живая перепубликация и приёмка — на ROI.
7. Порядок работ: короткая разведка `Report-Only` до кода, затем код вертикальными срезами через TDD, затем одно обновление стенда и приёмка.
8. Проба строгого режима отвечает через порт, как в плане изоляции.

## Порядок работ

1. **Разведка на стенде M1, до кода.** На страницу обоих клиентов Studio добавить `Content-Security-Policy-Report-Only: frame-src http://dashboards.localhost:32769; object-src 'none'; frame-ancestors 'none'`. С открытыми DevTools пройти загрузку и выгрузку файлов, импорт и встроенный режим (Embedded). Записать собственные фреймы Studio и поведение `frame-ancestors`, затем убрать строку. Найденные источники фреймов входят в принудительный `frame-src`.
2. **Код вертикальными срезами «тест → код»:** хост приложений и `lookup`, `publish.mjs`, SDK v1 и шаблон, оболочка, набор вредоносных dashboard, строгий режим, примеры, `dev-master.sh`.
3. **Одно обновление стенда поверх M1 и приёмка** по разделу «Приёмка».

## Стенд

**Контейнер web.** `dev-master.sh install` запускает контейнер `dashboard-master-20261109-web` (имя по схеме рецепта стенда, переопределяется флагом) в сети стенда. В нём один процесс Node с двумя портами: 8100 — API `/dashboard/…` для Apache, 8101 — хост приложений, опубликованный как `127.0.0.1:32769`.

- Запуск — `docker run` с `--read-only`, `--cap-drop ALL`, `no-new-privileges`, не от root, с пределами памяти и числа процессов, tmpfs для `/tmp` и `--restart unless-stopped`. Значения пределов задаёт план. Compose появится в M4, когда контейнеров станет три.
- Своего образа в M2 нет. Используется `debian:bookworm-slim`, закреплённый по digest: в нём есть `libstdc++`, нужный закреплённому Node. Node и `server.mjs` монтируются только на чтение. Свой образ нужен в M4, когда builder понадобится набор шаблона.
- Каталог состояния — `~/loginom-dashboard/` пользователя, который запускает `install`. В нём `builds/` (у web — только чтение) и копии Node и `server.mjs`: `install` копирует их туда, и пересборка в checkout не задевает работающий контейнер. `publish.mjs` пишет в тот же `builds/`; `check` сверяет его с источником монтирования контейнера.
- Переменные окружения web: адрес хоста приложений, адреса Studio для `Host` и `frame-ancestors`, режим, каталог сборок и корень checkout. Корень checkout нужен только для строк `sourceDir` и `commands` в снимке; сам checkout в контейнер не монтируется.

**Переход с M1.** `install` останавливает службу M1 в контейнере сервера Loginom и удаляет её файлы. Старые публикации в `/workdir/dashboard-app` остаются на месте, но больше не раздаются.

**Apache (`dashboard-app.site.conf`).**

- `/dashboard/` проксируется на web с короткими таймаутами и `disablereuse=On`. Проверка `Host` и `ProxyPreserveHost` — как в M1.
- На ответах `/dashboard/`: `Content-Security-Policy: sandbox; default-src 'none'` и `X-Content-Type-Options: nosniff`.
- На странице `/app/` и `/app-debug/` — принудительный `Content-Security-Policy: frame-src http://dashboards.localhost:32769; object-src 'none'; frame-ancestors 'none'` (плюс источники, найденные разведкой), `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`.
- Вставка оболочки через `sed`, статический `shell.js` и `client.json` — без изменений.

**Режимы и удаление.** `install --strict` включает строгий режим, повторный `install` без флага возвращает обычный. `uninstall` снимает контейнер, конфигурацию Apache и оболочку, но до M4 сохраняет `builds/`: пересобрать сборки автоматически пока нечем.

## web

**Каталог сборок.**

```
builds/<ключ>/
  <хеш>/          сборка: index.html и assets/; единственное, что раздаётся
  current         хеш текущей сборки, одна строка
  binding.json    привязка; нужна поведению `sample: null` из M1 и уходит в M3
  sample.json     пример строк; то же
```

**API (порт 8100, за Apache).**

- `POST /dashboard/lookup` отвечает `{key, exists, hash, appOrigin, mode}`. Если сборки нет, `hash` равен `null`. Схема `LookupResponse` в `src/contract` расширяется; ручные проверки оболочки сверяются с ней тестом, как в M1.
- `GET /dashboard/apps/…` удаляется: на origin Studio приложений больше нет.
- Снимки (`targets` и `current`) не меняются до M3. Меняется только текст `adapter`: вместо `window.frameElement.dashboard` в нём описан SDK v1, потому что этот текст получает модель в Desktop.

**Хост приложений (порт 8101).**

- Принимается только `Host: dashboards.localhost:32769`, остальные получают 403.
- `GET /apps/<ключ>/<хеш>/` отдаёт `index.html`, `GET /apps/<ключ>/<хеш>/assets/<имя>` — файл сборки. Ключ и хеш — 64 шестнадцатеричных символа, `realpath` не выходит за `<хеш>/`. Разрешены типы js, css, svg, png, jpg, webp и woff2; остальное — 404.
- Всё прочее — 404. Перенаправлений нет: адрес без косой черты в конце тоже получает 404.
- `/_probe/` (страница и её скрипт) отвечает только в строгом режиме, в обычном — 404.
- `POST /_reports` принимает тело до 64 КиБ, пишет одну строку в журнал контейнера и отвечает 204.
- Каждый ответ, включая 403, 404 и 500, несёт набор заголовков из раздела «Заголовки» плана изоляции. `<DASH>` — `http://dashboards.localhost:32769`, `<CLIENT>` — `http://127.0.0.1:32768 http://localhost:32768`. `Cache-Control`: `no-store` у документов и ошибок, `public, max-age=31536000, immutable` у `assets/`. У `assets/` также `Access-Control-Allow-Origin: *`.
- Отключить `Connection-Allowlist` можно только параметром `dashboardServer()` в тестах. Переменной окружения для этого нет.

## Публикация (`publish.mjs`)

Как и раньше, скрипт читает снимок по ID, поддерживает `--init` и выполняет `npm run typecheck` и `npm run build` в `dashboard/apps/<ключ>`. Затем:

1. считает хеш содержимого `dist`;
2. копирует сборку во временный каталог рядом и переименовывает его в `builds/<ключ>/<хеш>/`; если такой каталог уже есть, копия не нужна;
3. записывает `binding.json` и `sample.json` через временный файл и `rename`;
4. последним шагом так же записывает `current`.

Если сборка не удалась, ничего не меняется. Прежние каталоги `<хеш>/` остаются, поэтому уже открытые страницы не ломаются; уборка — в M4. `docker cp` и `docker exec` уходят.

## Браузер

### SDK v1 и шаблон

SDK — один файл `src/sdk/loginom.ts` без зависимостей. Сборка пакета копирует его в `template/src/loginom.ts`, тест сверяет копию.

- При загрузке SDK подписывается на `message` и отправляет родителю `{type: "loginom-dashboard/ready", version: 1}` с адресатом `"*"`.
- Сообщение `init` с одним портом принимается один раз и только от `parent`. Каждое `state` с порта проверяется вручную: в шаблоне нет `effect`. Тест сверяет эти проверки со схемой `contract`.
- Приложению доступны `onState(listener)` (возвращает отписку; поздний подписчик сразу получает последнее состояние) и `close()`. Esc внутри iframe вызывает `close()`, а она отправляет родителю `{type: "loginom-dashboard/close", version: 1}`.
- `state` — `{parameters, table, error, busy}`, где `table` — `{schema, rows, truncated, totalRows}` или `null`. Функций `change` и `run` и обращения к `window.frameElement` больше нет.

Шаблон показывает пять состояний: «Идёт расчёт», ошибка, пусто, данные и усечение. Полей ввода в нём нет. Три примера переписываются так же: без полей, без кнопки «Выполнить» и без `run`. Значение параметра приложение показывает текстом, например «Расчёт при пороге MinBudget = 10 000».

### Оболочка и протокол

Порядок открытия — как в M1. Если `lookup` вернул `hash: null`, оболочка идёт путём «Создать dashboard».

**Шапка.** Имя узла, путь пакета, поля числовых переменных, «Изменить в чате» и «Вернуться к сценарию». Подпись поля — имя переменной. Значение принимается по Enter и при уходе из поля. Проверяется, что число конечное, а для целой переменной — целое; для этого `parameters()` возвращает и признак целого типа. Текст выводится только через `textContent`.

**Iframe.** `sandbox="allow-scripts"`, `referrerpolicy="no-referrer"`, атрибут `allow` из плана изоляции, адрес `<appOrigin>/apps/<ключ>/<хеш>/`.

**Протокол.**

- Из окна принимаются только сообщения с `event.source === frame.contentWindow`.
- На первый `ready` оболочка создаёт `MessageChannel`, отправляет `init` с портом и сразу первое `state`. С порта оболочка ничего не принимает.
- Второй `ready` или повторный `load` после первого `ready` закрывают dashboard с записью в консоль. `close` закрывает dashboard. Остальные сообщения игнорируются; больше 50 сообщений в секунду закрывают dashboard.
- Если `ready` не пришёл за 10 секунд, вместо dashboard показывается «Dashboard не ответил».
- После изменения параметра в шапке приложение сначала получает `state` с `busy: true` и прежней таблицей, а после расчёта — новое `state`.

**Лимиты таблицы.** Оболочка читает не больше 10 000 строк, обрезает ячейку до 10 000 символов и останавливается, когда накопленный объём превышает 5 МБ. При усечении в `state` стоят `truncated: true` и `totalRows` из `get_RowCount`. Пределы уточняются на реальных узлах.

**Удаляется:** `frame.dashboard`, `change`, `run`, заплатка `MinBudget` и обращение к `contentDocument`. Предел размера `shell.js` задаётся заново по первому замеру, как в M1.

### Строгий режим

Если `lookup` вернул `mode: "strict"`, перед первым открытием за загрузку страницы оболочка загружает скрытый iframe `<appOrigin>/_probe/` с той же песочницей. Проба, как и SDK, сообщает `ready` и получает порт. Затем она пытается создать `RTCPeerConnection` и отвечает по порту `{type: "probe", ok}`. Результат хранится до перезагрузки страницы. Если ответа нет за 5 секунд, оболочка отказывает. Текст отказа — из roadmap: «Dashboard открывается в Chrome, Edge или Яндекс Браузере на Chromium 152 и новее».

## Проверки

**web** (`node:test`, настоящие порты и временные каталоги; порог покрытия 90% сохраняется):

- маршруты хоста приложений и полный набор заголовков на 200, 403, 404 и 500;
- отсутствие перенаправлений, проверка `Host`, выход за каталог, список разрешённых типов;
- 404 на `binding.json`, `sample.json` и `/dashboard/apps/`;
- `/_probe/` в обоих режимах, пределы `/_reports`, поля `lookup`.

**`publish.mjs`** (настоящий HTTP-сервер снимков, временные каталоги, приложение с тривиальными скриптами `typecheck` и `build`): `current` переключается атомарно; неудачная сборка не меняет текущую версию; одинаковая сборка не создаёт нового каталога.

**Браузер** (Chromium 154, настоящий `dist/server.mjs` и тестовая страница Studio с тем же CSP, что пишет Apache):

- `state` доходит до приложения; изменение параметра в шапке пересчитывает узел; Esc из iframe и из шапки закрывает dashboard; шаблон показывает все пять состояний;
- S5: ROI собирается по шаблону и открывается под настоящими заголовками, график рисуется, нарушений CSP нет;
- набор вредоносных dashboard из раздела «Проверки» плана изоляции — статичные HTML и JS без Vite. Набор идёт дважды: с `Connection-Allowlist` и без него. WebRTC, `dns-prefetch` и `preconnect` проверяются только в первом прогоне;
- атаки на протокол: поддельный `state` из чужого окна, второй `ready`, шквал сообщений, огромное и неклонируемое сообщение. Оболочка не меняет параметры и не запускает узел, самое большее закрывает dashboard;
- строгий режим: Chromium 154 с заголовком проходит пробу; сервер без заголовка и проба без ответа приводят к отказу.

**Примеры.** Все три собираются по шаблону (`tsc` и `vite build`) в CI-задаче `dashboard-browser`.

**`dev-master.sh`.** `bash -n` и ShellCheck. `check` дополнительно проверяет:

- флаги контейнера web и совпадение каталога сборок с тем, куда пишет `publish.mjs`;
- заголовки хоста приложений на 200 и 404, отказ на чужой `Host`, отсутствие перенаправлений, 404 на `binding.json` и `sample.json`;
- 404 на прежний `/dashboard/apps/`;
- принудительный CSP страницы Studio — точно ожидаемую строку; `Content-Security-Policy-Report-Only` или отсутствие заголовка — ошибка;
- `sandbox` на ответах `/dashboard/` и режим, совпадающий с настройкой;
- прежнюю живую пробу обоих клиентов.

## Приёмка

На dev-стенде этой машины, по runbook в `docs/testing/loginom-ai-agent/`:

1. Разведка до кода выполнена, её итог записан (раздел «Порядок работ»).
2. `install` поверх M1, `check` проходит в обоих клиентах.
3. ROI перепубликован по ID свежего снимка. В `/app/` и `/app-debug/` `MinBudget` в шапке 0 → 10 000 → 0 даёт 500 → 453 → 500 кампаний; таблица и график совпадают с независимым расчётом по `dataset.csv`. Esc закрывает dashboard и из iframe, и из шапки. «Изменить в чате» выдаёт свежий ID снимка.
4. S4: в `chrome://process-internals` записаны процессы iframe и вкладки с адресом приложения. Отчёт из документа в песочнице доходит до `/_reports`: для этого на стенд публикуется тестовый dashboard-нарушитель. Во вкладке с адресом приложения `document.cookie` бросает исключение. Встроить dashboard в чужую страницу не даёт `frame-ancestors`.
5. S5: у ROI на стенде нет нарушений CSP.
6. Firefox вручную: в обычном режиме ROI открывается и пересчитывается. После `install --strict` Firefox получает отказ с объяснением, а Chromium 154 открывает dashboard. Затем стенд возвращается в обычный режим.
7. После `uninstall` Studio работает без элементов dashboard, `builds/` на месте. Повторный `install` — ROI открывается без перепубликации.

## Не входит в M2

- `mod_substitute`, `integrity`, TLS, отдельный домен с сертификатом — M5.
- Подписи и пределы параметров, publisher и builder, compose, свой образ — M4.
- Новый контракт снимка, ключ привязки из трёх полей, черновик — M3.
- Журнал отчётов и общий выключатель — M6.
- Trusted Types — не планируются.
- Перенос публикаций M1.

**Известное ограничение до M4.** `publish.mjs` выполняет `npm run` из `package.json` приложения и не мешает вшить файл машины публикации через `?raw`. Это угроза машине публикации, а не зрителям: зрителей защищают песочница и заголовки. Закрывает её builder в M4.
