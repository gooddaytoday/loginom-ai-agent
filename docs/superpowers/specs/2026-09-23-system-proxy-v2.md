# Системный прокси v2

Решение от 23 сентября 2026. Заменяет политику «не читать ОС» из
[2026-09-22-proxy-policy.md](2026-09-22-proxy-policy.md): Desktop и CLI снова
подхватывают системный прокси, но любая ошибка этого кода только отключает
подхват и оставляет приложение запущенным.

## Что уходит через прокси

Уточнение 2026-09-25: браузер Chromium для Loginom всегда запускается с
`--no-proxy-server`: Desktop, CLI, проверка подключения, вход и браузер Playwright
MCP, с окном и headless. Это отключает системные прокси/PAC и proxy-переменные
именно для браузерного трафика, для любого адреса. Ошибка прямого подключения
не разрешает повтор через прокси. Флаг не передаётся Electron: его
`session.resolveProxy` по-прежнему нужен для настройки backend. Окружение
runtime и сетевое поведение серверного MCP не меняются. Подробности и границы:
[приёмка Chromium без прокси](../../testing/loginom-ai-agent/chromium-direct.md).

Запросы к моделям и OAuth (в том числе `auth.openai.com`, device flow, refresh,
ChatGPT, Anthropic, Google, OpenRouter, GitHub). Окружение с прокси получает
только backend: sidecar Desktop или процесс CLI после запуска хоста Loginom.
Main-процесс Electron, runtime Loginom и WSL sidecar переменные прокси не
получают. Явный `HTTP(S)_PROXY` / `ALL_PROXY` по-прежнему сильнее системных
настроек. `LOGINOM_AI_AGENT_SYSTEM_PROXY=off` и переключатель в настройках
отключают подхват.
Desktop сначала загружает login-shell окружение. При непустом `HTTP_PROXY`,
`HTTPS_PROXY`, `ALL_PROXY` или их нижнерегистровых вариантах чтение ОС и ожидание
Chromium пропускаются; возвращается состояние `environment`. Ошибка или зависание
системного читателя не меняет этот результат.

## Перевод

Системные правила переводятся в общий диалект `NO_PROXY`, который одинаково
понимают Bun 1.3.14 и Node 24.15: `имя`, `.имя`, точный IP, `host:port`,
`localhost,127.0.0.1,::1,[::1]`.

| Источник | Результат |
| --- | --- |
| `*` | `*` |
| `vk.com` в Windows/macOS | `vk.com` |
| `*.vk.com`, `.vk.com` | `.vk.com` |
| `*vk.com` и суффикс GNOME/KDE | `vk.com,.vk.com` |
| `<local>`, `ExcludeSimpleHostnames` | имя компьютера, уведомление `approximated` |
| `<-loopback>` | игнорируется, loopback всё равно напрямую, `approximated` |
| IP-маски, CIDR, диапазоны | пропуск, `rules-skipped`, прокси остаётся |

Учётные данные из ОС не копируются. В логе только `host:port`.
Недоступный прокси не обходится напрямую: запрос завершается ошибкой, пользователь
видит `unreachable`.

SOCKS без HTTP на том же порту не применяется (`socks-only`). Если на порту
отвечает HTTP, он используется как HTTP-прокси. PAC в Desktop для списка URL
моделей и OAuth решает Chromium (`session.resolveProxy`). В CLI, если в скрипте
ровно один `PROXY`/`HTTPS`, берётся он, иначе `automatic-unsupported`.
Автоопределение Windows без ручного прокси в CLI — прямой доступ без уведомления.

## Режимы и бюджеты

Ручные адреса читаются только в режиме manual: GNOME `mode=manual`, KDE
`ProxyType=1`. Выключенный режим и устаревший PAC URL не дают уведомления.
`use-same-proxy` не учитывается: HTTPS берётся из своего поля и только при пустом
HTTPS совпадает с HTTP. Пустой host или порт 0 не становятся адресом.

Перед применением каждый URL проходит `URL.canParse` и должен быть `http:` или
`https:` с непустым hostname. Иначе состояние `failed` / `internal`, переменные
не выставляются. `https://` у TLS-прокси сохраняется вместе с портом; запись
`https=host:port` в Windows и macOS остаётся `http://`. SOCKS без порта — 1080.
IPv6 проверяется через `net.isIPv6` и не получает вторую пару скобок.

Chromium: 3 с на все URL, затем маршрут ОС. `stop()` прерывает ожидание. Общий
предел обнаружения Desktop — 10 с. Проба порта — 1 с и входит в `resolveSystemProxy`.
Проверяются оба маршрута, HTTP и HTTPS, параллельно. Для `https://` проверяется
только TCP-соединение: TLS-прокси молчит на открытый `CONNECT`.
Загрузка PAC в CLI — 1,5 с на весь этап, включая чтение `file:`. Для `file:`
принимаются только обычные файлы; каналы и устройства отклоняются до открытия.
Файлы и HTTP-ответы читаются потоком с пределом 1 МиБ в байтах до декодирования
UTF-8. При превышении предела чтение прекращается, HTTP-поток отменяется.
Desktop PAC не скачивает.
PAC разбирается токенизатором Acorn 8.15.0 без выполнения скрипта. Комментарии и
литералы регулярных выражений не участвуют в поиске маршрутов; URL, кавычки и
маркеры комментариев внутри строк сохраняются. Ошибка токенизации оставляет
`automatic-unsupported`. Отдельный ответ `DIRECT` также оставляет
`automatic-unsupported`. Ответ Chromium `DIRECT` для всех URL не добавляет хосты
в `NO_PROXY` и не помечает PAC как неподдерживаемый.

Если sidecar с прокси завершается до готовности, он запускается ещё раз без
proxy-переменных. В журнале строка `system proxy: fallback`, уведомление
`internal`. Разные прокси у провайдеров дают `routes-merged`, включая сочетание
HTTP/SOCKS в любом порядке и разные SOCKS-адреса. Сравнение выполняется после
выбора маршрутов, поэтому предупреждение указывает адреса с заменённым маршрутом.
Предупреждение CLI попадает в TUI как аргумент `warning`, а не как тост главного
потока.

## Проверено в исходниках

- Регрессия `*vk.com` и масок `192.168.*` / `10.200.*` / `10.1.3.*` без исключения.
- Парсеры Windows, scutil, GNOME и KDE, включая враждебный ввод.
- Читатель Linux: код выхода, зависание и `kioslaverc`.
- Контракт `NO_PROXY` на Bun 1.3.14 и Node 24.15 внутри Electron 42.3.3.
- WebSocket OpenAI Responses под Node идёт через `HttpsProxyAgent`.
- CLI: ручной прокси виден следующему `fetch`; сбой `gsettings` пишет
  `SYSTEM_PROXY_NOT_APPLIED` в stderr и не портит JSON stdout.
- Падение main до окна завершается кодом 1.
- Исправления повторного review от 24 сентября покрыты циклами RED → GREEN:
  строка URL и кавычки в PAC не скрывают `DIRECT`; зависший файловый PAC не
  блокирует CLI; превышение лимита отменяет незавершённый HTTP-ответ; файловый
  лимит считает байты UTF-8; конфликты HTTP/SOCKS и SOCKS/SOCKS дают уведомление.
  Проверка зависшего канала выполняется отдельным процессом на Linux.

После этих исправлений на Linux прошли 48 тестов system-proxy в `loginom-host`,
13 тестов Desktop и 4 теста standalone proxy в `agent`; `bun typecheck` всех
трёх пакетов и контракт запуска Electron Node на 11 конфигурациях прокси.

Два замечания следующего review исправлены отдельными циклами RED → GREEN:
регулярное выражение с URL больше не скрывает ветку `DIRECT`, а явные proxy-переменные
Desktop не запускают читатель ОС и не ждут Chromium. Дополнительно проверено, что
комментарии, регулярные выражения и операция деления не добавляют ложные маршруты PAC.
После этих изменений прошли 50 тестов system-proxy в `loginom-host`, 14 тестов
Desktop и 6 тестов standalone proxy / WebSocket transport / proxy errors в `agent`;
`bun typecheck` всех трёх пакетов и контракт Electron Node на 11 конфигурациях.
Собранный для Node модуль с Acorn отдельно выполнил регрессионный сценарий PAC
под Electron Node 24.15.0.
