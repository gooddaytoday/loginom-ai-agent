# Loginom AI Agent: единый репозиторий и готовый desktop-дистрибутив

Дата: 2026-09-16. Статус: пользователь согласовал архитектуру, интерфейс,
ребрендинг, поведение настроек и матрицу платформ. Документ предназначен для
планирования реализации; описанные изменения приложения ещё не реализованы.

Независимое ревью спецификации: Approved, 2026-09-16, после уточнения отказа
при активации нового поколения подключения. Runtime-проверки этим не заявляются.

## 1. Результат и границы

Пользователь устанавливает Loginom AI Agent и при первом запуске вводит ключ
сервера Loginom AI, URL Loginom, имя пользователя и пароль. Дистрибутив уже
содержит локальный исполнитель Loginom, его runtime-зависимости и Chromium.
Внешние Node.js, Bun, Python, Chrome и самостоятельная установка плагина для
начала пользовательской работы не требуются. Системные библиотеки Linux
декларируются зависимостями пакета; это не обещание установки на произвольной
минимальной системе без доступа к пакетному репозиторию.

Подключение языковой модели сохраняет существующий пользовательский сценарий
OpenCode через настройки. В мастер Loginom шаг выбора или авторизации модели
не добавляется. «Loginom настроен» не означает «провайдер модели настроен».

Вся дальнейшая разработка продукта переносится в этот репозиторий: desktop,
клиент Dock, сервер знаний, сайт, тесты, инструкции и средства развёртывания.
Сервер знаний продолжает работать отдельно от пользовательского desktop.
Codex/Hermes-интеграции сохраняются в архиве переноса и не входят в активную
матрицу поддержки. Общие механизмы этих интеграций можно использовать внутри
продукта. Cursor-интеграцию также не превращаем в новую поддерживаемую цель.

Старый репозиторий предполагается удалить после полного переноса. Этот документ
не является командой на его удаление, переключение production или публикацию
релиза. Удаление выполняется последним отдельным этапом после проверки архива.
Пользователь разрешил перед реализацией убрать старые OpenCode desktop и wrapper;
сначала составляется список принадлежащих им установочных файлов и сохраняются
необходимые настройки. Посторонние проекты и пользовательские данные сохраняются.

## 2. Принятые решения

1. Единый мастер при первом запуске, общий для всех платформ; в платформенных
   установщиках не создаются отдельные формы ввода credentials.
2. Четыре поля: API-ключ; URL по умолчанию `http://logi-test-plan.bg.local/app/`;
   имя `user`; пустой пароль. У поля пароля нет placeholder ни в одном состоянии.
3. Прямая кнопка «Loginom» в боковой панели и та же форма в настройках.
4. Корень файлов Loginom всегда `/<имя пользователя>`. Отдельного выбора папки
   и предварительной проверки её существования/доступности нет.
5. На Linux API-ключ и пароль сохраняются открытым текстом в пользовательском
   конфиге с правами `0600`. Это основной согласованный режим, не fallback.
6. На Windows/macOS секреты защищаются средствами ОС. Во всех ОС секреты
   исключаются из истории модели, обычных API-ответов, логов и отчётов.
7. Изменение подключения применяется целиком после завершения активных задач
   Loginom. Ошибочный новый набор параметров не заменяет рабочий.
8. Бренд — `Loginom AI Agent`; техническое имя — `loginom-ai-agent`.
9. Windows/macOS проверяют отдельные агенты на других машинах. Здесь готовится
   полная документация передачи; результаты этих платформ не подменяются Linux.

## 3. Исходное состояние и основания

Снимок приложения: ветка `loginom`, commit
`501ff62cbf40d4ff260b48c9f1fc113e9b9a83e1`, чистый checkout до документационных
изменений этой задачи. Подробный снимок Dock: [инвентаризация](../../migration/loginom-dock-inventory.md).

- Desktop использует Electron 42.3.3 и electron-builder 26.15.2. Текущий
  production-путь собирает сервер v1 под Node и запускает его через Electron
  utility process. Внешний пользовательский Node для этого пути не нужен.
- Экспериментальный `OPENCODE_SIDECAR_V2` выбирает другой серверный путь.
  Наличие схемы MCP в Core V2 не означает готового исполнения MCP-инструментов.
  Первая версия продукта использует проверяемый v1-путь; V2 не включается
  автоматически и не становится зависимостью выпуска.
- В Dock готовые host adapters ориентированы на Codex/Hermes. Требуется
  собственная интеграция с реальными session/message/run identities приложения.
- Dock bundle содержит Node и модули, но текущий installer скачивает Chromium.
  В новой сборке браузер скачивается на этапе сборки и включается в артефакт.
- Обычный Loginom login сейчас ручной; имеющийся passwordless bootstrap
  не реализует полноценную передачу сохранённого непустого пароля.
- Обычный `global.config.update` v1 сохраняет конфигурацию и асинхронно
  уничтожает backend instances. Finalizer отменяет session runners и закрывает
  дочерние MCP-процессы. Для Loginom используется отдельный сервис настроек.
- Текущий updater и publishing workflow привязаны к upstream OpenCode;
  их нельзя включать в Loginom-дистрибутив без изменения адресов и идентичности.

## 4. Границы компонентов

Целевые каталоги ниже создаются при реализации, а не этой документационной задачей.

- `packages/desktop` и `packages/app`: окна, чаты, мастер и настройки. Renderer
  вызывает узкие методы `window.api.loginom`, зарегистрированные в desktop IPC.
- `packages/loginom-host`: адаптер приложения к исполнителю. Принимает доверенные
  session/message/run IDs, пользовательские вложения и события жизненного цикла;
  выдаёт инструменты и инструкции Loginom, маршрутизирует результаты и завершение.
  Подключается как встроенный модуль сервера v1, без npm-установки при запуске.
- `packages/loginom-runtime`: перенесённый клиент Dock, обработчики узлов,
  браузер, receipts/recovery, политика файлов и локальные артефакты. На первом
  этапе сохраняет отдельный управляемый процесс и его проверенные контракты.
  Переписывать все `.mjs` на TypeScript одновременно с переносом не требуется.
- `services/loginom-ai`: сервер знаний и необходимые upstream-компоненты,
  Studio, импорт/публикация каталога, server tests и deployment. Первичный перенос
  сохраняет внутренние относительные пути серверного дерева. Серверный Python/Rust
  стек не включается в пользовательский desktop.
- `apps/loginom-site`: сайт и инструкции загрузки, перенесённые из Dock.
- `docs/migration`, `docs/testing/loginom-ai-agent`: происхождение переноса,
  инструкции воспроизведения и результаты приёмки.

Существующее направление зависимостей Schema → Core/Protocol → Server сохраняется.
Client runtime не импортирует Core/Server. Публичные типы, если они понадобятся
клиенту, проходят Schema/Protocol и штатную генерацию, а не ручную правку generated.
Новый host adapter не меняет admission/execution и сериализацию сессий движка.

## 5. Перенос исходников и знаний

Перенос выполняется из зафиксированного inventory, а не одним копированием `main`.
В нём учитываются refs, tags, stash, все worktrees, untracked и необходимые ignored
материалы. Архив истории и рабочие файлы проверяются восстановлением в отдельную
папку. Секреты и серверные данные не попадают в Git/общедоступный архив.

Базовый кандидат клиента: актуальный `main` с принятыми Linux-изменениями;
`wow-landing` содержит Linux и отдельные исправления упаковки/сайта. Из `cursor`
отдельно оцениваются общие улучшения host/runtime. Старые experimental ветки,
stash и regression harness сохраняются как незавершённые до их проверки.
Исторические PASS не переносятся на новый runtime SHA автоматически.

Источники `ai-skills`, `e2e-tests`, `loginom-help` — самостоятельные внешние
репозитории. Переносятся каталоги источников, правила импорта, закреплённые
ревизии, release manifests и инструкции восстановления базы знаний. Копирование
Dock не копирует автоматически сами внешние репозитории или серверный индекс.
Сохраняются совместимые URI ресурсов и API-контракты работающего сервера.

Серверное переключение — отдельная процедура: inventory реально развёрнутого
commit/images/config/data, защищённая резервная копия, пробное восстановление,
сборка из нового репозитория, проверка совместимости клиента, затем явное
переключение с проверенным откатом. Операции не выполняются в рамках планирования.

Архив содержит прежние host integrations и их историю. Их удаление из активной
сборки не удаляет общие проверки, нужные исполнителю Loginom AI Agent. Лицензии,
атрибуция и происхождение импортируемых компонентов учитываются в manifest;
переименование не заменяет лицензии компонентов механически.

## 6. Настройки и безопасное применение

Единственный источник пользовательского подключения — desktop connection service.
Он хранит URL, точное допустимое имя пользователя, credential references/values,
номер поколения и состояния `draft`, `pending`, `active`. Настройки не зависят
от текущего рабочего каталога проекта и общие для окон этого профиля приложения.
Проектный `.loginom-ai-agent` не переопределяет глобальные секреты Loginom.

Операции сервиса: чтение редактируемых несекретных полей и признаков наличия
секретов; проверка кандидата; сохранение кандидата; получение статуса применения;
отмена ожидающего изменения. UI не получает сохранённые секреты обратно.
Для нового ключа используется явная замена; незаполненное поле при редактировании
сохраняет текущий ключ. Пароль имеет три операции: preserve, replace, empty.
При первоначальной настройке пустая строка означает допустимый пустой пароль.

На Linux `connection.json` находится в собственном config directory приложения,
содержит plaintext API key/password и записывается атомарно с mode `0600`;
каталог принадлежит пользователю. Он отделён от общего `loginom-ai-agent.jsonc`,
который может читаться общим config API. OS keyring на Linux не требуется.
На Windows/macOS конфиг хранит metadata, секреты — в отдельном защищённом
хранилище desktop. Ошибка доступа к нему возвращает явную ошибку сохранения;
автоматического plaintext fallback на этих платформах нет.
Эта политика относится к API-ключу Loginom AI и паролю Loginom; существующие
механизмы авторизации и хранения credentials провайдеров моделей сохраняются.

Проверка кандидата выполняется в отдельной краткоживущей браузерной сессии:
доступ/авторизация сервера знаний и вход в Loginom. Рабочие браузеры задач
не переключаются. Корень `/<username>` вычисляется локально; ни наличие папки,
ни доступ к ней, ни пробная запись не входят в проверку подключения.
Ошибки реальной файловой операции обрабатываются в момент самой операции.

URL принимает HTTP/HTTPS. Пользовательское значение сохраняется без навязывания
служебного query-параметра; runtime добавляет `testable=true`, сохраняя остальные
параметры. Имя пользователя проверяется как один допустимый сегмент пути:
пустое имя, разделители, управляющие символы, `.` и `..` отклоняются. Это
проверка синтаксиса, не существования аккаунта/папки. Регистр имени сохраняется.
При обнаружении в браузере чужой authenticated identity автоматический вход
не считается успешным. Секреты вводятся host-controlled механизмом, а не через
модель, MCP tool arguments или transcript.

Кандидат не становится `active`, пока проверка не успешна. Ошибка оставляет
прежнее активное поколение; при первой настройке сохраняется только draft.
Введённые несекретные значения доступны для исправления. Успех проверки и
успех применения отражаются отдельно; HTTP/IPC-успех записи не выдаётся за
готовое новое подключение.

Каждая активная задача Loginom закрепляется за поколением подключения. При
сохранении нового поколения сервис закрывает допуск новых задач Loginom,
показывает ожидающее изменение и ждёт завершения всех уже начатых задач во
всех окнах. Конец одного tool call не является границей применения. Незавершённая
операция с неопределённым результатом также удерживает старое поколение до
восстановления/явного завершения. Под закрытым допуском сначала запускается новое
поколение Loginom connections/profiles, старое рабочее поколение сохраняется.
После подтверждения готовности нового runtime атомарно фиксируется указатель
active, открывается допуск и завершаются старые idle-процессы. Ошибка запуска
оставляет прежнее поколение активным, помечает pending ошибкой и открывает
допуск со старым подключением. Если прежний runtime тоже утрачен, сервис
переходит в восстанавливаемое blocked-состояние Loginom с явным действием
повторного подключения; остальные чаты/backend не перезапускаются. Сбой между
записью active и завершением старых процессов сверяется по durable указателю и
generation handshake; ни одна новая задача не получает смешанные поколения.
Смена URL или username всегда получает новый браузерный профиль без старых cookies.

После сбоя процесса сервис восстанавливает active/pending состояние; неопределённые
изменяющие операции не повторяются автоматически. Повторная проверка кандидата
допустима; replay бизнес-операции требует исходной receipt/recovery-процедуры.
Отклонение/отмена кандидата открывает допуск с прежним активным поколением.
Перезапуск остальных backend instances и смена модели для применения Loginom
настроек не выполняются.

## 7. Первый запуск и постоянный интерфейс

Форма использует одни и те же поля и validation как при первом запуске, так и
в разделе «Loginom». В первоначальном мастере пароль пуст и без placeholder.
Секретные поля замаскированы. Корень файлов показан read-only, обновляется из
имени пользователя и не является отдельной настройкой.

Кнопки: «Проверить подключение», «Сохранить и продолжить», «Позже»; в настройках
— «Сохранить изменения». Если есть активные задачи, отображается статус
«Изменения ожидают завершения задач Loginom» и действие отмены ожидающего изменения.
Повторное редактирование заменяет pending-кандидат с проверкой его поколения.

Завершение мастера связано с применённой конфигурацией, не со старым upstream
onboarding-флагом или наличием проектов. «Позже» даёт доступ к приложению;
Loginom остаётся ненастроенным и доступен по прямой кнопке. После перезапуска
незавершённая настройка предлагается снова. Модели по-прежнему настраиваются
в существующем разделе; произвольный тестовый prompt провайдеру не отправляется.

Ошибка выводится по этапу: неверный ключ, недоступен сервер знаний, недоступен
Loginom, ошибка входа, недоступно локальное хранилище credentials. Диагностика
маскирует секреты и не включает пароль в URL, сообщения или копируемый отчёт.
UI проходит существующий i18n-путь; русские тексты — основной проверяемый сценарий.

## 8. Runtime и изоляция задач

Host adapter использует реальные доверенные identities приложения и события
завершения/отмены. Подготовка Loginom, инструкции, инструменты, input admission,
output artifacts и очистка входят в один контракт. Одной регистрации MCP мало.
Путь к пользовательскому файлу не принимается от модели как полномочие доступа;
вложение регистрирует host с привязкой к исходному сообщению и задаче.

Разные чаты имеют отдельные браузеры/профили, grants, очереди и артефакты.
Общий server client/cache допускается только без смешивания task identities.
Конфликт загрузки не перезаписывает чужой файл. Receipts, operation IDs,
pending/ambiguous recovery и независимая проверка сохранённого пакета сохраняются.
Изменение общего UI-профиля не отменяет эти ограничения.

Сервер знаний по умолчанию сохраняет текущий endpoint поставки
`https://loginom.duckdns.org/mcp`; дополнительного поля в мастере нет.
Адрес задаётся release configuration и техническим override в app config.
Рабочие server resource URI, protocol headers и чужие provider IDs не получают
механическую замену названия. HTTP-адрес Loginom остаётся разрешённым согласно
согласованному значению по умолчанию.

## 9. Ребрендинг и пользовательские данные

Единый product manifest задаёт display name, технический slug, package namespace,
app IDs/channel IDs, executable, URI scheme, artifact names и update feed.
Для нового runtime namespace используются `loginom-ai-agent`,
`@loginom-ai-agent/*`, `LOGINOM_AI_AGENT_*` и `loginom-ai-agent://`.
App IDs: `com.loginom.aiagent`, `com.loginom.aiagent.beta`,
`com.loginom.aiagent.dev`; channels имеют отдельные user data/locks/update feeds.
Имя базы — `loginom-ai-agent.db`, desktop stores — `loginom-ai-agent.settings`
и `loginom-ai-agent.updater`. Продуктовый исходный каталог `packages/opencode`
переименовывается в `packages/agent` с обновлением workspace/build/test ссылок.
Пути к исходникам в разделе 3 описывают снимок до этого переименования.

Конфиг проекта: `.loginom-ai-agent/`, `loginom-ai-agent.jsonc` (JSON-вариант
поддерживается как `loginom-ai-agent.json`). CLI install fallback —
`~/.loginom-ai-agent/bin`. Linux XDG config/data/cache/state используют slug
`loginom-ai-agent`; Windows/macOS — собственные стандартные app directories.
Desktop store, база, logs, tmp, local storage keys, browser profiles и lock names
получают собственную идентичность. Чистый запуск не создаёт активных `.opencode`
каталогов и не читает прежний OpenCode профиль как свою конфигурацию.

Инвентаризация различает продуктовые имена и внешние контракты: scoped packages,
imports/build scripts, env, config/schema identifiers, database/store names,
IPC/deep links, endpoints, UI/i18n/assets, installer metadata, updater,
provider integration IDs и лицензии. Исключения перечисляются в проверяемом
compatibility manifest с объяснением; слепой глобальной замены строк нет.
Upstream update feed отключается в самом начале ребрендинга. Собственное
автообновление включается только после проверки нашего manifest/feed/artifact.

## 10. Сборки и поддерживаемые платформы

- Windows 11+ x64: NSIS `.exe`.
- Ubuntu 22.04+ / Debian 12+ x64: основной `.deb`, дополнительный AppImage.
- macOS 14+ Apple Silicon arm64: `.dmg`; `.zip` допускается как служебный
  артефакт обновления, если нужен выбранному updater.

Это матрица целевых сборок, не утверждение о выполненной приёмке. Windows/Linux
arm64 и macOS Intel не входят в первую согласованную матрицу.

Сборка закрепляет Electron, runtime Node, Playwright/MCP, Chromium revision,
нативные модули, action catalog и source hashes. Исполнитель получает абсолютные
пути к bundled executable/resources и не ищет Node/Chrome через пользовательский
PATH. Ресурсы доступны при пробелах/Unicode в путях, из read-only install directory
и в упакованном приложении. Локальное изменяемое состояние находится в user data.

Новый CI использует собственные repository conditions, runners, release channels
и signing inputs. Тестовые неподписанные сборки помечаются; подтверждение
подписанного выпуска/нотаризации относится к нативной платформенной приёмке.
Защита Chromium не отключается глобально ради контейнерных тестов.

Release manifest включает commit и dirty-diff identity, dependency/browser pins,
platform/arch, artifact hashes, backend version, schema/config generation,
catalog hash, actual runtime/user paths и updater/signature identity. Приложение
и исполнитель выпускаются совместно; самостоятельного auto-update бывшего
плагина Dock внутри desktop нет.

## 11. Проверка и критерии готовности

Локально при реализации: package tests/typecheck, контракт host/runtime,
пакетирование и установка `.deb`, первый/повторный запуск, onboarding/settings,
runtime/Chromium без системных Node/Bun/Chrome, upgrade и recovery.
Тесты не запускаются из корня; typecheck — `bun typecheck` в package directories.
После изменения публичных Protocol/HttpApi запускается генерация из
`packages/client`; generated вручную не редактируется.

Docker-матрица: Ubuntu 22.04, 24.04, 26.04; Debian 12, 13. Каждый job использует
обычного пользователя, фиксированный image digest, чистый HOME и собственные
volumes. Проверяются системные зависимости, установка пакета, основной процесс,
sidecar, bundled browser и persistence под виртуальным дисплеем. Linux GUI
на текущем Ubuntu 22.04 проверяется отдельно; X11 и Wayland имеют отдельные
строки отчёта. Контейнер делит ядро хоста и не доказывает работу на всех ядрах,
графических драйверах или desktop environments соответствующего дистрибутива.

Windows/macOS: полный handoff находится в
[инструкциях платформенной приёмки](../../testing/loginom-ai-agent/README.md).
Сборку, отладку и нативную приёмку выполняют отдельные агенты на этих машинах.
Отсутствующий артефакт, credentials, сервер или platform signer отмечается
`BLOCKED` для соответствующего теста; `NOT RUN` не превращается в `PASS`.
Готовность документации и Linux не ожидает завершения этих внешних запусков.

Обязательные наблюдаемые результаты:

1. Чистая установка запускается без отдельно установленных Node/Bun/Chrome;
   runtime/browser из manifest присутствуют до первого запуска.
2. Мастер имеет четыре согласованных поля/значения, у пароля нет placeholder.
3. Нет шага настройки LLM; существующий способ подключения провайдера работает.
4. Повторный запуск использует сохранённую конфигурацию; незавершённый мастер
   восстанавливается; «Loginom» доступен напрямую и в настройках.
5. Linux сохраняет plaintext credentials с `0600`; Windows/macOS используют
   защищённое хранилище, в обычном конфиге/API/логах секреты отсутствуют.
6. Проверка подключения проверяет auth сервера и Loginom login, но не листает
   папку пользователя, не делает filesystem probe/тестовую запись в Loginom.
7. Папка `/<username>` вычисляется, пользователь не выбирает её отдельно;
   runtime file errors не маскируются и не используются как onboarding gate.
8. Пустой пароль работает; preserve/replace/empty и замена API-ключа различимы.
9. Изменение во время двух активных задач не прерывает их, не смешивает аккаунты
   и не отменяет другие чаты; новое поколение применяется после общего барьера.
10. Ошибочный кандидат сохраняет рабочий профиль; смена identity не наследует
    cookies/артефакты предыдущего пользователя. Отказ запуска нового runtime
    сохраняет старое поколение и открывает допуск к нему; потеря обоих runtime
    даёт recoverable blocked для Loginom без отмены других чатов.
11. Реальная задача принимает датасет, создаёт согласованный сценарий Loginom,
    исполняет и сохраняет пакет. Отдельное открытие/выполнение подтверждает
    ожидаемые поля, строки и значения; текст ответа агента не является oracle.
12. Два чата изолированы; cancel/network timeout/ambiguous receipt не приводят
    к повторному созданию узлов или потере управляемого процесса.
13. Установка/запуск/обновление используют новую идентичность; собственный
    updater не скачивает OpenCode и сохраняет настройки продукта.
14. Перенос имеет manifest происхождения, восстановленный архив и отдельный
    учёт серверных данных. Старый репозиторий не нужен для чистой сборки.

## 12. Этапы и завершение планирования

Работа делится на самостоятельные проверяемые этапы: inventory/archive;
перенос исходников/серверного дерева; product identity; host/runtime integration;
settings/credentials/onboarding; reproducible bundles; Linux acceptance;
платформенный handoff; server deployment migration; retire старого репозитория.
Серверный перенос данных и retirement не выполняются как побочный эффект
копирования исходников.

В этой задаче готовятся спецификация, подробный implementation plan,
inventory и platform runbooks. Продуктовый код, installed clients, server state
и старый репозиторий не меняются. Документы проходят независимую проверку и
коммитятся. Следующий исполнитель сверяет реальное состояние с этим снимком.

Внешние основания платформенных ограничений:
[Playwright system requirements](https://playwright.dev/docs/intro#system-requirements),
[Node 24 platform list](https://github.com/nodejs/node/blob/v24.x/BUILDING.md#platform-list),
[Electron credential storage](https://www.electronjs.org/docs/latest/api/safe-storage).
Версии фиксируются и проверяются повторно при подготовке release manifest.
