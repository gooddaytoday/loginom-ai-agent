# Устойчивый вход на runner3 после простоя

**Результат:** EvalOps входит на прежний runner3 из своего runtime после простоя, устанавливает уже принятый harness и продолжает LAB-170 штатными командами. Результаты, leases, pins, бюджет и срок сохраняются. Полная автономность исходной LAB-170 этим ремонтом не подтверждается.

**Основание:** native SSH неоднократно отказывает до remote dispatch; проверки через отдельный исходящий SSH с host на runner2 проходят. На host runner3 маршрут к runner2 идёт через `wg0`; единственный существующий peer имеет выключенный persistent keepalive и в live state, и в `/etc/wireguard/wg0.conf`. После простоя handshake старше десяти минут. Потеря NAT mapping — проверяемая гипотеза, не установленная причина. Предыдущий capture не пересёкся с native подключением и ничего о месте потери не доказал. Материалы — private `preparation-accounting/host-wg-*-readonly.json` и `native-ssh-correlated-assessment.json`.

WireGuard [рекомендует keepalive для входящих соединений за NAT после простоя](https://www.wireguard.com/quickstart/#nat-and-firewall-traversal-persistence); штатный интервал — 25 секунд. Это свойство существующего client peer, без нового туннеля, службы или изменения удалённого VPN-сервера. Цена — служебные пакеты во время простоя; расходов измерений нет.

**Область:** client peer на host выделенной runner3 VM, один параметр в существующем config и live state; этот план и краткий owning checkpoint. Оценка: 3 файла, около 45 изменённых строк с документацией. До изменения проверить владельца config и самостоятельность этой настройки. Общие маршруты, ключи, endpoint, allowed IPs, SSH auth/host-key и чужие процессы не меняются; интерфейс не опускается и службы не перезапускаются.
