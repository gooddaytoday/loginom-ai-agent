# Исходный срок новых eval-кампаний

Цель — применять уже принятое исправление срока ко всем новым кампаниям, чтобы отказ первого preflight и последующий ремонт не начинали отсчёт заново.

Существующая CLI поддерживает `reserve --initial-progress-at`: она сверяет ID, created_at и активный статус исходной задачи через API, сохраняет исходный срок в native journal до preflight и не выдаёт owner при отказе. Этот путь проверен в LAB-171. Общая инструкция старта пока описывает обычный reserve; одного наличия опционального флага в коде недостаточно.

Решение — дополнить общий порядок старта в основном плане и одну эксплуатационную инструкцию EvalOps. Новую кампанию создавать с тем же исходным issue ID и неизменным manifest; первый reserve выполнять с authenticated created_at исходной задачи до readiness и ремонта. Ожидание выбора/освобождения сервера также считается от исходной даты. Повторы не создают новую задачу и не переписывают journal. Для существующего journal сохраняется прежнее время; повтор идёт обычным путём. Новый флаг не применяется задним числом к уже начатым кампаниям.

Если принятый source выбранного сервера не поддерживает команду, это технический блокер совместимости; EvalOps устраняет его по действующим полномочиям, проверкам и независимому ревью. Убирать флаг и начинать новый срок ради допуска нельзя. Текущие LAB-170/LAB-171, их сроки, результаты, runtime и работающие службы этим изменением не затрагиваются.

Первый проверяемый результат от входа до выхода уже получен LAB-171: штатный reserve отказал до owner из-за budget scopes, исходное время сохранилось в journal и snapshot. Новая правка распространяет этот порядок на общий вход; дополнительный модельный прогон для изменения текста не нужен.
