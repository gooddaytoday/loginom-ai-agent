Полные исторические входы legacy hash отсутствуют; continuity нельзя объявлять доказанной или исправлять подстановкой текущих данных.

Чтение текущим frozen source подтвердило точное совпадение текущей server identity с retained verification, собственный маркер пустого storage и чистый/незанятый профиль A. Старый storage.device изменился; прежняя физическая identity не подтверждается. Admin receipt именно исходного producer подтверждает dispose, disconnect и cleanup без неизвестных процессов. Это входы для квалификации отмены, ещё не release proof. Private evidence: `/home/george/.codex/tmp/preparation-accounting/runner2-{retained-first-probe,terminal-cleanup-readonly-probe,unused-verify-qualified-inputs}.json`.

Обычный reconciliation требует текущую identity у всех исторических admin/preparation/storage receipts; старый каталог содержит разные эпохи. `cleanupSlotStorage` закономерно отвергает старую preparation и storage proof. `releaseClosedEnvironment` требует уже released profiles; `destroyPair` не принимает retained reservation от verify. Published-ветка controller уже умеет позднее подтвердить очистку и снять matching owner; ей недостаёт допустимого способа закрыть именно этот неиспользованный verify.

## Узкая граница исправления

Использовать существующие controller lock, `reopenEnvironmentLeases`, native admin, profile/storage observations, archive и CAS release. Не вводить scheduler, новую БД, состояние reservation, общий retirement-сервис или повтор измерений. Новый механизм нужен только для терминальной отмены verification, которая не дошла до использования CLI слота; обычное выполнение и cleanup сохраняют прежние проверки.

Квалификация отмены должна подтвердить опубликованный partial, matching campaign owner, inactive batch, завершение владельца именно отменяемого verify и неизменность его command/reservations. Допускается только собственный unactivated verify с доказанным отказом до CLI; неизвестный исход, management/measurement admissions и неподтверждённый admin cleanup не превращаются в «ничего не запускалось». Под настоящими leases повторяются exact server identity, принадлежность и пустота текущего storage, чистота/отсутствие процессов профиля, отсутствие sessions/backup/открытых серверных файлов; новый admin также завершается подтверждённо. Чужие ресурсы не затрагиваются.

Терминальное доказательство отделяет отмену reservation от готовности эксперимента. Оно не разрешает удаление по старому storage proof и не объявляет старую preparation пригодной для следующего измерения. Существующий допуск benchmark через точную preparation остаётся обязательным; для новых кампаний нужна штатная свежая preparation. Расширение release-контракта допускается только для этого проверенного терминального исхода; не записывать прежние `storageDeletionAllowed`/`nextAdmissionAllowed` как true ради прохождения старого guard.

Основание отмены — принадлежность собственных leases, pair и storage по исходной creation→storage цепочке и свежему nonce-bound marker. Текущий exact username/userKind ограничивает запрос inventory; равенство proxy objectId между эпохами не требуется и непрерывность native аккаунта не утверждается. Это устраняет неверное дополнительное условие, выявленное первой live-проверкой. Контракт прямо запрещает account mutation, deletion и admission; прежние проверки подготовки и изменяющих действий сохраняются. Путь квалифицирован после restart собственной временной pair, с отказами для старой preparation, неверного nonce и чужой pair.

Controller учитывает реальный поздний cleanup отдельным подтверждением, сохраняет исходный опубликованный отчёт/архив и снимает только matching owner. Итог LAB-134 остаётся partial, её измерения не возобновляются и срок не меняется. Новая кампания до подтверждённых release и отсутствия прежнего owner не назначается.
