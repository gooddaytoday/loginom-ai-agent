# Продолжение ремонта EvalOps через существующие будильники

**Результат:** после окончания очередной задачи EvalOps сам продолжает разрешённый технический ремонт на следующем штатном пробуждении, без новой подсказки пользователя/Codex. Работающий job или другой исполнитель не дублируется; срок и условия кампании сохраняются.

**Причина:** текущие instructions двух будильников LAB-170 старше действующего правила личного ремонта EvalOps. Event предлагает передавать исправление другому агенту; periodic требует check-in при неизменном состоянии. Задачи подготовки завершились после промежуточных результатов, хотя написание принятого retire-script остаётся доступным действием. Постоянный `repairing=true` не доказывает, что такой исполнитель сейчас работает. Read-only before-state — private `preparation-accounting/turn12-wakeups-before.json`; terminal tasks и оставшиеся действия — `turn12-c3-implementation-progress.json`.

**Минимальное изменение:** уточнить только instruction у существующих event и 15-минутного periodic будильников LAB-170. Использовать прежние IDs, EvalOps, интервал, фильтры и события. Новых будильников, служб, состояния, retry или scheduler нет. Agent instructions/runtime/model/env, кампании и инфраструктура не меняются. Полезная конфигурационная delta — два строковых поля. Установленный CLI update заменяет полную конфигурацию и явно re-enables rule: поэтому передать все прежние настроенные значения; обе rules до изменения должны оставаться enabled. Вычисленные сервисом revision/следующее срабатывание не задавать вручную и не считать изменением срока кампании.

**Объём:** этот план, уточнение раздела7 основного плана и ссылка/checkpoint адресной очистки: **3 файла, около 45–70 строк Git**; production-кода нет. Private before/update/read-back и один точный текст инструкций сохраняются для сверки. Дополнительных измерений или модельной кампании для этой проверки нет.

## Порядок и проверяемый результат

1. [x] **Проверить фактический пробел.** Прочитаны обе действующие rules и terminal tasks. Основной план уже требует личного ремонта и check-in только при отсутствии новых действий; конкретные prompts выражают это недостаточно точно.
2. [x] **Независимо проверить минимальное уточнение до изменения.** План и exact instruction review — PASS, обязательных замечаний нет. Отчёт private `preparation-accounting/evalops-repair-wakeup-plan-instruction-review.json`; сохранены duplicate/review/ownership/cleanup guards, deadline и финализация.
3. [ ] **Адресно обновить и прочитать обратно.** Native EvalOps выполняет штатный CLI update в своей действующей task context: установленный CLI запрещает запуск из daemon workdir без task-scoped token; marker не удалять и доступы не подменять. Сохранить свежий before-state и передать полную прежнюю конфигурацию, меняя instruction двух нужных IDs. Точный кандидат — private `preparation-accounting/evalops-repair-wakeup-candidate.json`. Read-back подтверждает точный текст и прежние agent/kind/condition/interval/filters/max_fires/enabled. Служебные timestamps/revision/last-fire поля могут штатно изменяться. При конфликте перечитать состояние; не заменять неизвестную конфигурацию или выключенную/final rule.
4. [ ] **Проверить продолжение на существующем событии.** После установки не посылать новый prompt для продолжения ремонта. Следующий штатный wakeup должен фактически проверить отсутствие другого active repair/job/retry и продолжить доступный шаг лично — например, подготовить retire-script и направить точные артефакты на независимое ревью. Проверить task attribution с исходным wakeup ID и полученный артефакт/делегированное review. Если найден настоящий внешний блокер, сохранить конкретный факт и условие возобновления; повтор статуса без доступного действия не считать прогрессом. Это проверка данного продолжения, не доказательство автономности всей LAB-170.

## Смысл обеих инструкций

- Сначала сверить journal, deadline/final, фактические процессы, результаты, владение и исход текущей операции. Здоровый batch принять под управление; готовые измерения и неизвестный исход изменяющей команды не повторять.
- Active repair определяется реальной running/queued задачей другого исполнителя, живым owned job или подтверждённым pending retry. Историческая terminal task, checkpoint и один `repairing=true` недостаточны. Своё текущее пробуждение не считать параллельным исполнителем.
- При действующем repair/job/review/retry следить за его исходом, не запускать дубль. Если прежняя задача закончилась и следующий разрешённый шаг доступен, лично продолжить ремонт по принятому плану и checkpoint. Написание кода/скрипта, проверки и подготовка к независимому ревью — работа EvalOps; само ревью выполняет другой агент, поручение исполнителю ограничено штатным продолжением прогона.
- Не заканчивать только перечислением доступных собственных действий. Завершить конкретный шаг до проверяемого результата, ожидаемого независимого review/живого job либо фактического внешнего блокера. Не отменять предварительное ревью и не выполнять ещё не принятый script.
- Check-in periodic без комментария — при здоровой работе, уже реально идущем ремонте или отсутствии безопасного действия до события/исчезновения внешнего блокера. Для event при таком же отсутствии действий — пустой текстовый ответ без вступительного commentary, с учётом fallback Multica v0.6.5.
- Ремонт не меняет repairer, Results, manifest/pins, бюджеты, таймауты и no-progress deadline; исходные ошибки и receipts сохраняются. После deadline — существующий partial/finalization. Если хост недоступен, EvalOps публикует partial по последним известным данным с неподтверждёнными ресурсами и выключает будильники.
- После очистки исполнитель выполняет штатное продолжение; EvalOps проверяет финальный cleanup/release, архив/download/hash/read-back, статус, выключение обоих будильников, выход unit и один post-final no-op без новых admissions/publications.

## Ограничения и остановка

Уточнение prompt не доказывает исправление Multica runtime или устойчивость SSH. Если agent снова завершит задачу без результата при доступном шаге, сначала проверить фактические messages/tool outcomes и причину остановки; не добавлять ещё один таймер, повторные комментарии или новый runner. При активном чужом исполнителе либо неизвестном исходе — сверка и ожидание существующего события. [Адресная очистка c3](2026-10-25-c3-cleanup-plan.md) и её implementation gates сохраняются.

Checkpoint:
- Plan/exact instruction review — PASS. Проверен installed CLI: full-config update re-enables rule; выполняет EvalOps в собственной task context с сохранением прежних настроенных значений. Rules пока не изменены.
- Следующий шаг — адресная штатная установка EvalOps с read-back; затем проверка следующего существующего wakeup без нового nudging Codex.
