# Сравнение stable proof после нормализации пустого Docker DNS

## Результат и границы

Разблокировать штатный `prepare-generation` при единственном различии `HostConfig.Dns: null ↔ []`, сохранив проверку настоящих настроек и исходные receipts. Это адресный дефект, выявленный при выполнении раздела D [плана runner3](2026-10-24-local-eval-runner-plan.md); применяется предусмотренный его разделом 9 порядок: воспроизведение → отдельный план → независимое ревью → TDD → проверенный кандидат.

План подготовлен в `bdd0/runner3-deploy`; разработка передана в канонический чат вместе с остальными открытыми проверками. Здесь код не начат. Активная LAB-170 продолжает использовать прежний frozen checkout. Этот план **не разрешает менять её acceptedHarness, units/config или разворачивать кандидат**. Перед таким действием владелец должен принять конкретный проверенный SHA и изменение прежнего frozen pin. Результаты, manifest, CLI/corpus/model/judge pins, пределы и история сохраняются. Внешнее исправление harness не выдаётся за полностью автономное прохождение кампании без вмешательства.

## Проверенные основания

- LAB-170 пережила настоящий guest reboot. До него batch был unaccounted, все 8 native reservations released; после него сохранены 63 файла, 22 копии исходных proofs и manifest. Два quality FAIL учтены по одному разу, missing=232. Owned container IDs прежние, epoch новая; новая generation ещё не принята.
- На установленном Docker 29.1.3/API 1.52 у обоих контейнеров пустой `HostConfig.Dns` стал `[]`. Текущий stable hash отличается от сохранённых двух preparations. Независимое fenced воспроизведение штатной функцией доказало: замена **только в памяти** этих двух полей на `null` в точности возвращает оба сохранённых hash. Файлы и контейнеры не менялись; private proof — `stable-dns-readonly-reproduction.json` в рабочем каталоге диагностики runner3.
- Установленные `docker update/start` и Moby UpdateConfig не предоставляют изменения DNS на существующем ID; эту проверку EvalRunner выполнил отдельно. Независимый reviewer проверил Moby `docker-v29.1.3`: [buildSandboxOptions](https://github.com/moby/moby/blob/docker-v29.1.3/daemon/container_operations.go#L53) применяет DNS override только при `len(Dns)>0`, поэтому обе пустые формы здесь эквивалентны. [UpdateConfig](https://github.com/moby/moby/blob/docker-v29.1.3/api/types/container/hostconfig.go#L375) не предоставляет изменения DNS.
- `readServerObservation` уже получает полную конфигурацию одним fenced чтением. Его Docker launcher пропускает только заданный набор env и не поддерживает `DOCKER_API_VERSION`; обход через wrapper не нужен. Пересоздание контейнеров нарушило бы требование сохранения IDs.

## Минимальное решение

Сохранить формулу `stablePairConfiguration`, формат `{version:1,hash}` и байтовую совместимость `ServerIdentity.configurationHash`. Изменить только сравнение с новым fenced observation: для полей `serverHost.Dns` и `studioHost.Dns`, если фактическое значение ровно `null` или пустой массив, вычислять допустимые v1 hash для этих двух эквивалентных форм. Максимум четыре значения. Все остальные входы участвуют в каждом hash без изменений.

Новый чистый helper в `parallel-pair.ts` возвращает уникальные hash; `readServerObservation` возвращает их отдельным внутренним полем, не сохраняя в preparation receipt. `prepareGeneration` проверяет вхождение сохранённого stable hash в этот набор. Producer и старые receipts не переписываются. All-legacy branch сохраняет прежнее точное сравнение. Это одна известная семантическая эквивалентность, без версий миграции, таблиц совместимости или произвольных исключений.

Непустой DNS, его порядок, `DnsOptions`, `DnsSearch`, неизвестные поля HostConfig и остальные массивы остаются значимыми. Отсутствующее поле не синтезируется. Нормализация всех пустых массивов или исключение DNS из fingerprint запрещены.

Выбор сравнения вместо смены producer сохраняет действительные v1 receipts с любой из исходных форм, включая смешанную пару `null/[]`. Канонизация только producer под тем же version могла бы отвергнуть ранее сохранённый hash для `[]`; новая версия proof потребовала бы лишнего изменения reader/producer. Текущий путь оставляет оба механизма неизменными.

## Шаги и проверяемые результаты

1. **Независимое ревью до кода.** Проверить первичный Moby source, точное воспроизведение, достаточность существующих средств и необходимость только указанного сравнения. Обязательные замечания требуют ссылки на требование/конкретный риск; предпочтения отдельно. Результат: принятый план без неразрешённых обязательных замечаний.
2. **Один RED → минимальный GREEN.** Через публичный helper проверить допустимость старых v1 hash для `null`, `[]` и смешанных форм без мутации входа. В том же контракте сохранить отказ для непустого/переставленного DNS и изменений других HostConfig полей. Включить helper в единственное fenced observation и continuity guard; не менять legacy hash или native proof schemas. Результат: воспроизводимый regression-тест проходит и фактическая DNS-only разница распознаётся, реальные изменения отвергаются.
3. **Регрессии и ревью кода.** Целевые parallel-pair/campaign-control/user-environment tests, package typecheck с настоящим Node и Bun 1.3.14, затем полная unit-suite без live/process-denial opt-in. Использовать существующие средства для ограничений inotify, не менять глобальные лимиты/чужие процессы. Сверить diff/secrets, независимо проверить композицию чтение → candidates → guard и сохранить чистый commit. Результат: конкретный проверенный frozen кандидат; local tests не объявляются завершённым live reboot E2E.
4. **Решение о поставке — последним.** Предъявить владельцу SHA, diff, проверки и ограничение автономности LAB-170. После отдельного принятия — одно адресное поручение EvalOps/EvalRunner: согласованно поставить единый checkout во все server/unit/preflight/verify paths, сохранив старый checkout и результаты; затем штатные prepare-generation/restart/resume. Без принятия активная среда остаётся прежней. Результат после разрешённой поставки: native generation на тех же IDs, единственный учёт старых FAIL и продолжение только missing; при отсутствии разрешения — конкретный внешний блокер.

## Стоимость и исключения

Ориентир: два source-файла, один-два существующих test-файла и три плана, **6–7 файлов / 100–220 строк** суммарного diff этой адресной задачи. Механизм нужен только потому, что старый receipt хранит hash, а не исходный HostConfig; ограниченный пересчёт проверяет всю конфигурацию целиком и сохраняет оба старых представления без миграции.

Исключения: изменение CLI/корпуса/моделей, пропуск guard, подмена receipts, реальное изменение DNS, пересоздание pair, ручной reset journal/attempt budget, повторы quality FAIL, новый scheduler/runtime/deployer. LAB-134, runner1, текущие окружения и канонический worktree `1c6f` не меняются. Если отличается что-либо кроме доказанной DNS-эквивалентности или растёт необходимый механизм — остановить эту гипотезу и разобрать фактический diff.

Независимое ревью плана — **PASS, обязательных замечаний нет**. Проверены первичный Moby source, private воспроизведение, совместимость v1 и неизменность legacy branch. Необязательная рекомендация: при реализации использовать существующий opt-in native generation-continuity тест на собственной pair; отдельный проверочный механизм не нужен.

Checkpoint: DNS-only причина подтверждена; план рассмотрен, код не изменён, live поставка не разрешена. Реализация и решение о поставке переданы в канонический чат; новых работ по этому плану здесь не начинается.
