# Учёт сохранённой node-попытки

Часть шага 6 [плана автономных eval](2026-10-23-autonomous-evals-plan.md). Цель — учитывать подтверждённые node PASS и FAIL без повторной генерации, даже если общий summary не записан. Критерии эксперимента не меняются.

## Почему существующего пути недостаточно

Node запускается с `--skip-judge`: в `result.json` штатно остаются `pass=null`, `score=null`, `judge_status=skipped`. Качество определяет детерминированный checker. Сейчас controller применяет к нему контракт LLM-судьи и не засчитывает результат; admission guard ошибочно считает три обычных node FAIL техническими ошибками. Чтение общего `code-verdict.json` после batch этого guard не исправляет.

Существующий `validateNodeRun` требует общий summary и закрытие всего слота. Для сохранённой попытки достаточно её собственного подтверждённого cleanup и архива. Общие проверки завершённого run остаются строгими. Сбор native evidence сейчас происходит только после `main()`; его нужно выполнить до проверки содержимого попытки.

## Минимальное изменение и границы

В `evals/src/node-evals.ts` добавить `assessNodeAttempt({runDir, taskId, tasksDir, slot})`. Она читает собственный `<runDir>/<taskId>/1/result.json`, проверяет идентичность, допустимый статус, отсутствие технической ошибки, cleanup и связанный архив. `slot` содержит существующие ID и profile/history paths из `SlotDefinition`; флаг `liveQualified` не выдумывается. Состояние `closed` и live qualification остаются проверками общего завершённого run. Ошибку проверки возвращать в существующей форме code-verdict: `verdict`, `code`, `errors`, `failures`, `attempts`.

Для completed-попытки функция сначала использует существующие `collectNodeNativeEvidence` / `collectTextImportEvidence` там, где они нужны, затем `validateNodeAttempt`. Для штатных failed/timeout/no_artifact возвращает code FAIL при подтверждённых доказательствах. Для provider/harness/infra/interrupted и неподтверждённых доказательств — ERROR. Детерминированная повторная проверка сохранённого артефакта не запускает модель и не создаёт измерение; не доверять непроверенному общему verdict вместо исходных доказательств.

Вызовы:

- `node-runner.ts` передаёт в `main` внутреннюю опцию `{nodeEvaluation:true}`; `run.ts` передаёт её подготовленному runner. Новых env, пользовательских флагов и режимов нет.
- `prepared-run.ts` оценивает node после сохранения result и собственного cleanup, до `campaignAdmission.complete`. PASS и FAIL дают `quality=true`; ERROR сохраняет прежнее правило технических ошибок. Ошибка вспомогательной оценки не переписывает `result.harness_error` и не уничтожает готовую генерацию.
- `validateNodeRun` использует ту же проверку попытки, сохраняя общие проверки run, внешний формат и exit codes. Отдельный after-main сбор evidence в `node-runner.ts` становится не нужен.
- `run-campaign.ts` передаёт в `campaignTick` пятым аргументом узкий контекст уже прочитанного серверного config (`harnessRoot`, `corpora`, `slotsFile`, пути прежних pins) во всех трёх вызовах: repair, resume и основной цикл. Для corpus `node` используется тот же checker с задачами принятого root; slot выбирается по точному `result.slot_id` из проверенного slots-файла. Пути не берутся из summary или текущего окружения, живой preflight при восстановлении не вызывается. PASS/FAIL записываются только в существующий учёт кампании; исходные `Result.pass`, `score`, `judge_status` не меняются. Ошибка общего summary/report не отменяет отдельно подтверждённое качество. Ресурсные проверки и frozen pins применяются как раньше.

Новых ledger, receipts качества, сервисов или зависимостей нет. Исходные result и cleanup receipts не переписываются. Срок прогресса берётся из прежнего native completion, при его отсутствии — из времени исходного result; время восстановления срок не продлевает.

## Порядок и проверяемые результаты

Реализация по `evals/AGENTS.md`: один RED → минимальный GREEN → коммит; независимое ревью до поставки. Все команды из `evals/` на принятом Bun 1.3.14.

- [x] 1. Один тест `assessNodeAttempt` на сохранённую completed node-попытку без summary: собственный архив содержит native observation; collector исполняется до content checker, получается честный FAIL без изменения result. Неподтверждённый архив остаётся ERROR. Результат — локально проверенный путь от сохранённых файлов до оценки.
- [ ] 2. Подключить общую оценку к подготовленному runner и общей проверке run. Тест доказывает: три node quality FAIL не закрывают четвёртый admission; настоящие ERROR по-прежнему закрывают его. Существующие node/text-import тесты сохраняют результаты и строгие проверки.
- [ ] 3. Подключить controller. Локальный сквозной тест через разрешённый fake harness получает code FAIL, удаляет только summary, дважды вызывает `campaignTick`: один учтённый ключ без повторной генерации, без нового времени прогресса и без изменения исходного результата. Отдельно неподтверждённая оценка не считается пригодным качеством.
- [ ] 4. Выполнить целевые node/campaign/admission тесты и `bun typecheck`, провести независимое ревью diff. Результат — проверенная поставка для последующей живой проверки шага 6, без утверждения о доказанном reboot.

Ожидаемая область: пять существующих source-файлов (`node-evals.ts`, `node-runner.ts`, `run.ts`, `prepared-run.ts`, `run-campaign.ts`), три существующих тестовых файла и связанные планы; примерно 350–500 изменённых строк. Если точная передача slot потребует ещё одного механизма, сначала пересмотреть более простой прямой вызов, не добавлять хранилище.

## Что остаётся в основном плане

Ранний долговечный result до судьи, продолжение только незаконченного судейства под прежними pins, запуск выделенных контейнеров после reboot и живая проверка reboot — следующие отдельные части шага 6. Они не считаются реализованными этой правкой. Четыре сочетания исполнитель/сервер и полный manifest на 234 ключа также остаются обязательными.
