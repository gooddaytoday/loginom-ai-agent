# Параллельные попытки evals на изолированных слотах

Дата: 2026-10-11. Статус: **дизайн согласован, реализация не начата**.
Ветка: `evals-parallel`. Исследованный код: `61705f09577234d312c852685153b0c2080b156c`.

## 1. Решение и границы

Один процесс обычного eval harness распределяет пары «задача × номер попытки»
между фиксированными слотами. Каждый слот владеет отдельным профилем CLI,
авторизацией, runtime и архивом истории, а также собственной парой
Studio + Loginom server. Координатор сохраняет один run и один итоговый summary.
Первая живая приёмка — два слота, затем тот же путь с одним слотом.

Пользователь согласовал отдельный Loginom-контейнер на слот, внедрение сначала
в обычный harness и последующее подключение Multica. Код реализации остаётся
в `evals/`; этот документ и ссылка из исходной задачи фиксируют согласованное
проектное решение. Изменения продукта, SDK и протоколов для scheduler не нужны.

Сохраняем существующий цикл `runAttempt` → `afterAttempt` и допустимый infra retry.
Слот занят до окончания всего цикла, включая судью и очистку. Отдельную очередь
судей, динамическое создание стендов, распределённый координатор и автоматическое
перемещение retry между слотами не вводим. Продолжение обычного run после полного
падения harness и слияние runs остаются отдельной задачей №7.

## 2. Основания и рассмотренные варианты

Исходная [задача №6](../testing/loginom-ai-agent/reports/2026-10-01-evals-remaining-work.md)
описывает несколько профилей на одном стенде. После неё появились дополнительные
условия:

- 2–5 октября внедрены подтверждение принадлежности процессов, профильный lease,
  сохранение диагностики до recovery и запрет следующей попытки при неизвестной
  очистке. [Контракт cleanup](../superpowers/specs/2026-09-18-evals-design.md).
- Infra retry сохраняет исходную ошибку и считается одной логической попыткой;
  ошибки качества не становятся основанием для повтора.
  [Решение о retry](../superpowers/plans/2026-10-05-evals-infra-retry.md).
- 7 октября добавлены bubblewrap, закрытое архивирование истории каждой попытки,
  проверка пустого выделенного Loginom и широкая очистка всех `UserStorage` и
  `SessionBackup`. Разделения профилей для параллельности теперь недостаточно.
  [Контракт изоляции](../../evals/docs/2026-10-07-analytic-evals-isolation-plan.md).
- На отдельной Studio уже наблюдалось подключение к общему backend из-за
  `wsproxy=auto`. Разные HTTP-порты не доказывают разделение стендов.
  [Инцидент LAB-31](../../evals/docs/2026-10-09-lab31-blocker-fixes.md).

Read-only API-проверка [LAB-55](https://mas.kartamyshev.dev/lab/issues/LAB-55)
подтвердила 144 измерения, 25 ч 24 мин 48 с работы продукта и 1 ч 8 мин 5 с судьи.
Остановка executor после 43 измерений была восстановлена штатным resume без
повторения измерений; причина остановки не установлена. Линейное ускорение
параллельного режима этим не доказано.

Контроллер серий LAB-55/LAB-75 с журналом и продолжением поставлен отдельно;
его исходников нет в исследованной ветке. Не переносим его механизмы в обычный
harness ради scheduler. [Точки продолжения Multica](../../evals/docs/2026-10-08-evalbaseline-launch-plan.md).
Текущие серии и их закреплённые условия не меняются этим дизайном.

| Подход | Решение |
| --- | --- |
| Общая очередь внутри harness | Выбран: один run/summary, переиспользование нынешнего цикла попытки |
| Несколько harness-процессов с внешним координатором | Отложен: требует координации, объединения результатов и остановки нескольких runs; общий host `/proc` сам по себе не исчезает |
| Несколько профилей на одном Loginom | Отклонён для первой версии: противоречит широкой очистке и admission пустого контейнера |

## 3. Конфигурация

Новый флаг `--parallel N` принимает положительное целое, default — `1`.
`EVAL_SLOTS_FILE` указывает JSON-файл версии 1 со списком подготовленных слотов.
Первые N записей в порядке файла составляют активный набор. Это позволяет
проверить 2 → 1 без изменения файла. Автоматического уменьшения N при занятом
или неисправном окружении до старта нет.

Описание слота содержит:

- уникальный `id` и абсолютный `profileDir`;
- `loginom.url`, `username`, `container`, `storageDir`, ссылку `passwordEnv`;
- `studio.container` и `studio.network` для проверки маршрута к своему серверу.

Модель, variant, установленный CLI, Dock, задачи, rubric, judge и ограничения
времени общие для run. Все активные серверы имеют одинаковый image digest.
Workspace каждой попытки остаётся отдельным каталогом под общим workspace root;
в sandbox монтируется только этот каталог и профиль назначенного слота.

Без файла слотов используется прежний singleton из `EVAL_PROFILE_DIR` и
`LOGINOM_*`. `N > 1` без файла или N больше числа описанных слотов — ошибка
конфигурации до dispatch. При N=1 из файла используется первый слот.

Значения секретов разрешаются из env только для активных слотов. В `results/`,
сообщениях ошибок и логах их нет; сохранённая конфигурация очищается от секретов
всех слотов. Профили подготавливаются заранее и остаются writable для refresh.
Целый профиль с БД, WAL, историей, recovery и browser runtime не клонируется.
Пригодность выбранной авторизации к параллельному refresh — условие live-приёмки;
простое копирование `auth.json` не считается доказательством.

Пример предлагаемого интерфейса (после реализации, из `evals/`):

```bash
EVAL_SLOTS_FILE=/private/eval-slots.json bun run src/run.ts --parallel 2 --repeat 3
```

Fake/dry-run должны позволять проверить очередь без Docker/моделей. Judge-only и
калибровка сохраняют существующий последовательный путь, не требуют файла слотов
и живых credentials; явно заданное `--parallel > 1` в этих режимах отклоняется.
`--keep-storage` несовместим с многослотовым live: его сохранённое хранилище
противоречит admission следующей попытки. Прежняя single-stand конфигурация
`EVAL_NODE_OPS_CONFIG`/`EVAL_NODE_STAND_LEASE` также не допускает N > 1 до отдельной
интеграции Multica. Однослотовое поведение этих интерфейсов сохраняется.

## 4. Admission и изоляция ресурсов

Каждая пара Studio + Loginom находится в отдельной Docker-сети. Штатный backend
alias `loginom-server-7.4.2-test` может сохраняться внутри каждой сети; разные
серверы не делят этот alias в одной сети. Studio публикуются на разных endpoint,
публиковать backend 8080 для работы через Studio не требуется.

До первой модельной попытки все активные слоты проходят проверки:

1. Канонические profile paths уникальны; профили, история и каталоги inputs
   соседних попыток не попадают в mounts друг друга. Ссылки и вложенные пути не
   обходят проверку. Общий закрытый каталог результатов допустим.
2. Фактические server/Studio container ID различаются между слотами. Проверены
   назначенные сети, единственный backend alias, `wsproxy=true` и маршрут Studio
   к своему серверу. HTTP 200 сам по себе недостаточен. Немодельная проверка
   подключения и live smoke подтверждают фактический WS-route и storage.
3. Сохраняются нынешние marker/container-ID/roots/no-bind-mount/Python-disabled
   проверки и требование пустого storage/backups. Перед широкой очисткой marker
   и ID проверяются заново, удаление выполняется по подтверждённому ID.
4. Готовый профиль действительно подключён к endpoint своего слота. Текущее
   `ensureProfile` не перенастраивает уже готовое соединение автоматически;
   изменение URL в конфигурации не означает переключения профиля.
5. Приобретены отдельные leases профилей и контейнеров. Container lease keyed
   по immutable ID расположен в общем стабильном каталоге harness вне профилей,
   а не в произвольном каталоге каждого run. Другой профиль не даёт обхода lease
   того же контейнера. При отказе до использования ресурсов освобождаются только
   собственные пустые reservations. Исчезнувший PID не разрешает stale takeover.

После запуска lease каждого слота освобождается независимо, только после
подтверждённой очистки. Ошибка одного слота не удерживает исправные слоты лишь
из-за общего ненулевого exit code. Неизвестная очистка сохраняет соответствующие
leases и evidence. Старые ручные/Multica исполнители обязаны соблюдать прежнее
эксклюзивное окно: новый lock не координирует автоматически старые версии.

## 5. Очередь и жизненный цикл

Список заданий строится заранее в прежнем порядке: круг 1 по всем задачам,
затем круг 2 и т. д. У каждого задания стабильный индекс и ключ task/attempt.
Свободный слот забирает следующее задание до асинхронного запуска. Порядок
завершения может отличаться от порядка назначения; отдельного барьера между
кругами нет. Повторы одной задачи могут выполняться одновременно на разных
изолированных слотах.

Внутри слота последовательно выполняется существующий путь: agent и его
завершение → извлечение артефакта/оценка → `afterAttempt` с диагностикой, recovery,
архивом профиля и очисткой storage → допустимый retry либо следующее задание.
Фактический порядок защитных действий существующего цикла без необходимости
не переставляется. Между одновременными pipelines не делятся изменяемые command,
config, retry history и состояние остановки слота.

Retry выполняется на том же слоте, с тем же task/attempt, prompt и именем
результата, только после подтверждённой очистки. `infra_retry.initial` сохраняет
первоначальный исход. Результат заменяется по индексу задания, а не через
`attempts[attempts.length - 1]`. Одно измерение не удваивается в качестве.

Каждый pipeline пишет только собственный каталог `<run>/<task>/<attempt>`.
Координатор собирает результаты в устойчивом порядке и один раз пишет итоговые
summary/report после завершения всех pipelines, включая обработку ошибок.
Ранний rejection одного Promise не оставляет другие pipelines без ожидания.
Неназначенные задания не получают выдуманных measured результатов.

## 6. Отказы, отмена и supervisor

| Событие | Решение |
| --- | --- |
| PASS/FAIL/timeout/no_artifact | Сохранить измеренный исход; после cleanup перейти к следующему заданию |
| Infra error | Прежний однократный retry после cleanup; исходная ошибка сохранена |
| Локальный `harness_error` с `stop=true`, включая CLI exit 2/3 | Остановить слот даже при успешном cleanup; не запускать на нём следующие задания |
| Ошибка cleanup/recovery конкретного окружения | Остановить слот, сохранить leases/evidence; остальные продолжают очередь |
| Общая ошибка записи результатов или потеря доказательства изоляции | Запретить новые admissions, завершить/остановить активные pipelines и дождаться их cleanup |
| Ctrl+C | Запретить новые задания/retry, прервать активные agent/judge, дождаться cleanup, сохранить summary |

Карантин слота даёт итоговый exit 1, даже если остальные обработали очередь.
Общая fatal-ошибка отличается от пользовательского прерывания и не записывается
как фиктивный Ctrl+C. Если агент уже завершён, отмена во время judge/cleanup
не стирает его измеренный исход. Повторный Ctrl+C сохраняет нынешний принудительный
выход без гарантии summary. Полное падение процесса также не гарантирует итоговый
summary; доступные файлы попыток и блокировки сохраняются для разбора.

Supervisor остаётся доверенным процессом вне агентского bubblewrap и видит host
`/proc`. Статически найден риск: чужой Chromium grandchild без `user-data-dir`
может попасть в `unknownProcesses`. Воспроизведённым дефектом он пока не считается.
Первый технический риск проверяется двумя одновременными supervisor с одним
browser bundle, потомками, reparent и переписанным process title. Исправление,
если необходимо, опирается на доказанные launcher/birth identities. Исключение
процесса только по argv, PGID или строке чужого пути недопустимо.

Существующий запрет внешнего inspector/CDP сохраняется. Docker-сети серверов
не изолируют host-сеть оцениваемого CLI. Если фактический transport откроет
соседнему агенту CDP, нельзя обходить guard allowlist-ом: live admission запрещён
до устранения доступного канала. Внешний worker namespace не добавляется заранее;
если узкие проверки/исправления не доказывают границу, реализация возвращается
к обсуждению этого конкретного ограничения.

## 7. Summary и потребители

Не меняются смысл статусов, score/pass/oracle, quality denominator и вложенного
infra retry, структура каталогов попыток и статистические алгоритмы compare.
Добавляются необязательные поля:

- `config.parallel`: активный лимит; отсутствие в старом summary означает 1;
- `attempt.slot_id`, в том числе у `infra_retry.initial`;
- `slots`: ID, идентичность Loginom/container, состояние cleanup, причина
  остановки слота и результат листинга storage.

Для одного слота прежние `loginom.container`, `storage_dir`, `image_digest`
сохраняются. Для нескольких `container`/`storage_dir` равны `null`, а
`image_digest` содержит общий проверенный digest; конкретные контейнеры находятся
в `slots`. Старые summary читаются без миграции. Новые поля валидируются: slot ID
уникальны, ссылки попыток разрешаются, initial retry принадлежит тому же слоту.

Общий `storage_leftovers` — `null`, если хотя бы один листинг неизвестен; иначе
объединение остатков текущего run с указанием слота. Прежний листинг ограничен
префиксом `eval-<run-id>-`: пустой массив означает отсутствие этих остатков,
а не доказанную пустоту всего storage/backups. Полная чистота подтверждается
отдельно cleanup и `assertIsolatedStorageEmpty` каждого слота. Результаты
листинга и проверок очистки сохраняются по слотам.

`stopped_reason` сохраняет причину остановки, включая карантин; renderer явно
отличает остановку слота от прекращения всей очереди. Неполный/небезопасный run
не становится молча пригодным для inferential compare. `interrupted_cleanup`
не получает нового смысла: `recovered` означает факт recovery, а подтверждение
очистки берётся из evidence слотов. `total_duration_ms` остаётся суммой времени
исполнений; elapsed run определяется по started/finished.

Compare показывает изменение parallelism среди условий среды; тождество условий
и линейное ускорение не заявляются. Judge-only сохраняет slot metadata через
пересчёт оценок и не читает живые профили/секреты. Node runner выбирает профиль
для native/text-import evidence по `slot_id` из разрешённой конфигурации текущего
run. Неизвестный slot не заменяется первым; проверки принадлежности архива
сохраняются. Legacy попытки используют прежний одиночный профиль.

## 8. Объём изменений и проверки

Основные точки реализации: `evals/src/config.ts`, `run.ts`, `lease.ts`,
`preflight.ts`, `report.ts`; совместимость в `compare.ts`, `compare-analysis.ts`
и `node-runner.ts`. `profile.ts` затрагивается только для проверки привязки
профиля. `process-supervisor.ts` меняется под подтверждённый concurrent сценарий.
Контракты и runbook синхронизируются до изменения поведения; новый дизайн не
объявляет ещё не реализованный режим действующим правилом эксплуатации.

Реализация следует TDD из `evals/AGENTS.md`: поведенческий RED → минимальный GREEN
→ рефакторинг. Внешние процессы проверяются существующими fake CLI/judge и dir
fixtures; настоящие модели в автоматических тестах не вызываются.

Обязательные проверки:

1. Наблюдаемое перекрытие двух fake CLI, максимум N активных попыток; порядок
   назначения и стабильные индексы при обратном порядке завершения.
2. Отказ до dispatch при дубликатах/вложенности ресурсов, одном контейнере под
   разными именами, занятом lease и несовпадении профиля с endpoint.
3. Два concurrent browser дерева: root/helper/grandchild, reparent/title rewrite;
   остановка одного не убивает и не блокирует второго. Неизвестный процесс
   по-прежнему не даёт разрешения на небезопасную очистку.
4. Slot cleanup/recovery failure, продолжение здорового слота, независимый
   release; сохранение initial retry и отсутствие замены соседнего результата.
5. Ctrl+C во время agent, judge, cleanup и между архивированием infra error и
   retry; отсутствие новых admissions, ожидание активных pipelines и сохранение
   измеренных исходов. Ошибка persistence не оставляет забытые workers.
6. Single-slot regression, чтение legacy/new summary, compare/rejudge и выбор
   правильного архива node-evals; отсутствие secrets во всех результатах.
7. Соответствующие package tests, полный `bun test` и `bun typecheck` из `evals/`,
   `git diff --check`. Fixtures с проверкой host-процессов запускаются в чистой
   PID-границе, чтобы чужой Chromium не создавал ложных отказов.

Живая приёмка проводится на двух подготовленных свободных окружениях. Две
разные задачи одновременно доходят до пакетов в своих storage, подтверждены
WS-route, profile/runtime isolation и cleanup. Затем повторяется запуск с одним
слотом. Проверяются доступность лицензий, запас CPU/RAM/диска, лимиты Loginom,
Dock и провайдера, а также выбранная авторизация; отдельный тест supervisor
подтверждает локальность остановки. Полный новый baseline для приёмки scheduler
не требуется. Результаты качества smoke сохраняются без повторов ради PASS.
