## 1. Архитектура и выполнение

Один доверенный harness, один выделенный Loginom Server и общая Studio.
Каждому слоту назначаются отдельный пользователь Loginom, CLI-профиль,
browser runtime, workspace и закрытый архив истории. Сервер эксклюзивно
принадлежит одному run; модель, CLI, задачи, rubric и судья закреплены для run.

Общая очередь выдаёт задания в порядке «все задачи первого круга, затем второго»
без барьера между кругами. Слот занят до завершения агента, судьи и cleanup.
Infra retry выполняется на том же слоте после подтверждённой очистки, сохраняет
исходный результат и остаётся одним логическим измерением. Результаты привязаны
к стабильному индексу задания; coordinator ожидает завершения всех pipelines.

Все выбранные слоты проходят допуск до первой модельной попытки. Неисправность
любого из них даёт exit 2 и preparation evidence без measured summary;
автоматического уменьшения числа слотов нет. После dispatch локальная неисправность
отправляет слот в карантин, здоровые продолжают очередь. Карантин отражается
в `stopped_reason` и даёт exit 1. Чистые user/profile leases освобождаются
независимо; неизвестный результат очистки сохраняет владение и evidence.

## 2. Автоматическая подготовка и права

Harness одной командой готовит и проверяет пользователей, права, личные каталоги,
профили, подключения, credentials и блокировки. Выбранные способы:

| Операции | Интерфейс |
| --- | --- |
| Контейнеры, конфигурация, каталоги, leases, архивы и scoped cleanup | Программные Docker/fs-операции доверенного контроллера |
| CLI-профиль и подключение | Установленный CLI: `loginom setup --stdin-json --format json`, status/check |
| Пользователи, ACL и серверные сессии | Детерминированный Playwright adapter административной Studio; browser RPC через `page.evaluate` |

RPC внутри страницы требует браузера. Один доверенный admin context используется
на run и переиспользуется после проверки состояния; после reconnect proxy handles
перечитываются. Browser берётся из проверенных ресурсов установленного CLI и
запускается через pipe. Полная подготовка выполняется до dispatch и повторяется
при изменении среды или восстановлении. Пользователи и профили переиспользуются;
готовность проверяется по состоянию с ограниченным ожиданием.

Eval-user получает необходимые права проектирования/просмотра без admin,
полного файлового хранилища, scheduler full access и публикации. Эффективные ACL
исключают чужие папки и общие места записи, включая разрешения Everyone и групп.
Сохраняются ограничения небезопасных серверных компонентов и bubblewrap-граница CLI.
Административные credentials, cookies и state доступны только контроллеру,
вне mounts/env агента и судьи; секреты исключаются из результатов и диагностики.

Подготовка идемпотентна: intent и credential сохраняются до мутации, результат
подтверждается чтением состояния. После неопределённого ответа сначала readback,
затем решение о продолжении. Чужой пользователь с совпавшим именем не присваивается.
Новый пользователь явно заблокирован до настройки auth/password/прав и их проверки;
разблокировка выполняется последней. Повторный prepare не сбрасывает пароль и
не переключает уже локальный AuthMode. Приёмка проверяет повторный запуск и
восстановление частично выполненной подготовки.

## 3. Владение, серверные сессии и очистка

Host-global locks хранятся в постоянном `/var/lib/loginom-evals/locks`.
Общий server-run fence дополняется user/profile leases с immutable container ID,
server generation и пользователем. Смена generation аннулирует допуск; исчезновение
PID не разрешает снимать lease. До перехода на marker v2 подтверждается отсутствие
старых исполнителей; старый cleaner обязан отвергать новый marker.

OS guard действует при живом controller, durable reservation сохраняет владение
после аварии. Standalone prepare/verify завершают свои пробы, сохраняют evidence
и released receipt, затем отпускают guards; readiness не резервирует среду.
Run заново получает владение. Только recover под теми же guards может принять
актуальную reservation в recovery-only после проверки owner и цепочки владения
от исходного incident; CAS со старым token отклоняется. Повтор recovery завершает
оставшиеся ресурсы incident, сохраняя уже released слоты. Права на удаление требуют
отдельных proofs. Живой run даёт внешнему recover BUSY.

Admission и cleanup работают с личным root слота. Проверяются все файлы,
включая скрытые, нестандартные имена, `.autosave` и блокировки открытых пакетов.
Принадлежность серверных сессий фиксируется отдельно от агентского `session_id`;
учитываются все соединения пользователя, включая setup/check/recovery и pending
disconnect. Закрытие разрешено только для достоверно собственных свежих session
proxies. Имя сессии и `PendingDisconnect` сами по себе не доказывают принадлежность.

Обязательный порядок cleanup:

1. Сохранить результаты/диагностику, выполнить нужный recovery, после последней
   management-команды подтвердить остановку всех локальных writers. Сохранить
   историю, БД/WAL/SHM и inputs с durable archive receipt до server close.
2. Закрыть все подтверждённые собственные серверные сессии; дождаться их отсутствия
   в свежем списке и прекращения операций/блокировок.
3. Повторно проверить container/generation, marker, lease и user root; удалить
   только собственные данные, затем подтвердить пустоту и отсутствие регенерации.
4. Сохранить receipt и разрешить retry, следующее задание или release.

За эту границу переносятся **все** удаления, включая artifact/orphan cleanup.
После финального закрытия нельзя выполнять management-команду, открывающую новую
сессию пользователя. Неизвестный исход сохраняет файлы/leases/evidence и отправляет
слот в карантин. Общий Server для восстановления одного слота не перезапускается.
Потеря общего административного управления запрещает новые задания до восстановления.
Неопределённое закрытие сохраняет готовый архив. Ошибка архива сохраняет исходники
и частичные копии, запрещает server deletion/release; crash между перемещениями
восстанавливается по manifest. При живом writer история не перемещается.

**SessionBackup:** до live требуется положительная проверка непустого каталога
с доказанной принадлежностью и адресной очисткой либо проверенное безопасное
отключение backups. Пустота каталога такой проверкой не является. Неопознанный
backup сохраняется; если влияние нельзя локализовать, новые задания всего run
останавливаются. Общая очистка UserStorage/SessionBackup запрещена.

## 4. Временно перенести общую OAuth-авторизацию из `shared-oauth`

До включения реализации в `loginom` использовать отдельный установленный CLI
с выбранными коммитами зависимости:

| Порядок | Коммит | Назначение |
| --- | --- | --- |
| 1 | `dfd2b0df2de6b60f529973f35fcccc59feceef5f` | Shared store, межпроцессный lock/refresh, login/logout, capability и тесты |
| 2 | `ba919629f966e23670ff0a02720057067adbb040` | Защита файлов и проверка installed bundle/capability |
| 3 | `bd4951803532db3f51c1b5a66a864038d88865c3` | Изоляция Linux proxy cache/runtime по профилям |

Для выбранного HTTP-only режима dev-кандидата дополнительно применяется
`66f0956bc9f16ee580b20f3cf98e368857048f27` с явным
`LOGINOM_AI_AGENT_EXPERIMENTAL_WEBSOCKETS=false`; transport закрепляется в условиях
приёмки. Перед переносом проверить актуальную `loginom` на эквивалентные изменения.
При разрешении конфликтов сохранить текущий экспорт `./skills` и актуальные
manifest fixtures; продуктовые файлы не заменять целиком версиями старой ветки.

Все возможные адаптации выполняются **поверх продуктового контракта в `evals/`**:
разрешённый env `LOGINOM_AI_AGENT_SHARED_AUTH_DIR` для агента/management,
writable bind всего общего каталога, проверка shared auth в `assertAuth`,
capability/manifest admission и тесты. OAuth store/lock/refresh в harness
не копируются. Каталог canonical, 0700, обычные файлы 0600 без symlink/hardlink;
он находится вне профилей, checkout, workspace, результатов и архивов и сохраняется
при cleanup/reset. Bind всего каталога сохраняет atomic rename и общий lock inode.
Каталог и lock-файл не заменяются во время работы. Shared store ограничивает
ожидание lock 60 секундами, refresh HTTP — 30 секундами; автоматического refresh
после любого HTTP 401 нет. Lock освобождается до модельного запроса.

Используется установленный Linux x64/glibc binary с совпадающей capability
`shared-oauth-v1` в executable и manifest; его SHA и `EVAL_CLI_BIN` закрепляются.
Source-mode с development bundle override для shared-режима не допускается.
Первый вход — штатный `providers login --provider openai --method "ChatGPT Pro/Plus (headless)"`
в отдельном onboarding-профиле с общим store.
Callback создаёт login generation; копирование старого auth.json его не заменяет.
Login/logout/recovery выполняются после остановки потребителей. Неопределённый
refresh блокирует новые запросы до штатного восстановления; pending marker
вручную не удаляется. Общая авторизация сохраняет общие лимиты и отзыв доступа.

Временные cherry-pick выполняются с `-x`, отдельно от собственных evals/docs-коммитов;
фиксируются source/local SHA и разрешения конфликтов. Они не смешиваются через
amend/fixup/squash. Неизбежная продуктовая правка оформляется отдельным небольшим
коммитом с тестом и путём включения в основную ветку.

После слияния эквивалентного OAuth в `loginom` сохранить старый tip и перенести
собственные evals/docs-коммиты по явному списку на чистую новую базу. Временные
копии исключаются из истории будущего PR; необходимая продуктовая правка остаётся,
пока её не поглотил upstream. Проверяются содержание изменений, range-diff,
итоговый diff, новый installed binary и приёмка. OAuth из основной ветки не
откатывается через revert. Подробная процедура —
[задача 7 плана](../superpowers/plans/2026-10-13-evals-parallel-users.md#задача-7-потребить-временный-shared-oauth-сохранив-независимую-авторизацию-судьи).

## 5. Изоляция процессов, судья и совместимость

Принадлежность Chromium проверяется отдельно: два supervisor и trusted admin
launcher, общий browser bundle, helpers, reparent, изменение title и авария A
при работающем B. Ownership опирается на PID/starttime и доказанное происхождение
процессов; argv/PGID не разрешают kill. Неизвестный процесс запрещает неподтверждённый
cleanup. Тест проводится в одной общей чистой PID-границе; доступный TCP CDP запрещён.

Судья `codex exec` использует отдельную авторизацию и CODEX_HOME. Внутри run его
вызовы сериализуются mutex, а host-global lease canonical CODEX_HOME исключает
одновременное использование другим run. Lease освобождается после подтверждённого
завершения судей. Model shared store и Loginom/admin credentials судье не передаются.

Старые summary читаются без миграции. Новые записи содержат `config.parallel`,
`slots` и `attempt.slot_id`, включая initial retry и single-slot режим.
Сохраняются статусы, denominator, provider failure accounting и смысл
`interrupted_cleanup: { recovered: boolean } | null`. Node-evals выбирают профиль
и архив по slot_id; неизвестный ID — ошибка. Compare/rejudge сохраняют metadata,
карантин запрещает inferential compare. Исторические результаты и pins текущих
серий сохраняются.

## 6. Приёмка и оставшиеся проверки

Немодельные evidence Loginom 7.4.2 подтверждают двух пользователей на одном сервере,
продолжение B после аварии браузера A и cleanup A после адресного закрытия сессии
без повреждения B. Источник:
`/home/kiselev/.codex/experiments/loginom-users-20261013-50e5f473/`.
Эксперимент также доказал регенерацию `.autosave` незакрытой сессией; 12 секунд
наблюдения после cleanup не задают универсальный timeout.

Shared-oauth прошёл отдельную приёмку восьми CLI на installed source
`597592f5d53f86beb69ffe318af2d4db52c5f416` с локальным перекрытием 3464 мс.
Это не приёмка нового evals binary, его sandbox или принудительного live refresh;
подробные источники закреплены в плане реализации.

До полного live-допуска остаётся подтвердить:

- устойчивую привязку server sessions к слоту, включая reconnect, reuse имён,
  несколько соединений и неопределённые ответы;
- непустой SessionBackup либо поддержанное безопасное отключение;
- идемпотентную автоматическую подготовку и полную effective-ACL матрицу;
- concurrent supervisor с двумя CLI и административным браузером;
- shared OAuth в sandbox harness, refresh и отдельную авторизацию судьи;
- полноценный LLM-eval двух слотов, затем одного, на закреплённых условиях.

Приёмка включает одинаковые имена файлов A/B, запрет чужого read/write/copy/import/
export и `../`, cleanup A во время B, crash A без повреждения B, отсутствие
регенерации после подтверждённого cleanup, недоступность admin credentials,
отказ допуска до первой попытки, цепочки prepare → prepare → verify → run и
crash → recover → новый run, single-slot, legacy summary и node-evals.
Измеряются ресурсы и совместная нагрузка сервера, проверяются лицензия и лимиты
без 429. Реальные результаты сохраняются без повторов ради PASS.
Run с rate/quota limit, даже скрытым успешным retry, не считается успешной
приёмкой выбранной параллельности. Бюджеты фиксируются до запуска, resource/license
evidence собирается отдельно от оценки качества.

До изменения поведения синхронизируются eval spec, evals/AGENTS.md, README,
isolation, node-evals, orchestration и runtime runbooks. Файлы, TDD-шаги и команды
зафиксированы в плане реализации: нормативные изменения — задача 0, фактические
команды и результаты — задача 11. Реализация начинается по отдельной команде.
