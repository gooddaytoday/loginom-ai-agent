# Ревью дизайна параллельных evals: что доработать в плане

Дата: 2026-10-11. Статус: **рекомендации; сам план не менялся**.
Проверенный документ: [дизайн параллельных попыток](2026-10-11-evals-parallel-design.md),
коммит `98549274bf`, ветка `evals-parallel`. Исходная задача — №6 в
[списке доработок evals](../testing/loginom-ai-agent/reports/2026-10-01-evals-remaining-work.md).
Ссылки вида `путь:строка` указывают на код этого коммита.

## Итог

Архитектура плана верна: один процесс harness, общая очередь, у каждого слота
свой профиль CLI и своя пара Studio + Loginom. Это совпадает с решениями
владельца. Главные ловушки найдены правильно: широкая очистка storage, инцидент
`wsproxy=auto`, замена результата retry через последний элемент массива, снятие
lease только при коде 0.

В нынешнем виде план не готов к составлению плана реализации. Ниже 4 критичных
пробела — каждый может сорвать проект или испортить данные измерений — и 14
важных мест, где план оставляет реализатору решения, которые должен принять сам.

Термины:

- **слот** — одна изолированная связка «профиль CLI + Studio + сервер Loginom»;
- **допуск** — проверки слота перед стартом (в плане — admission);
- **карантин** — слот перестаёт брать задания после сбоя.

## Критично: исправить до начала реализации

### 1. Не проверено, можно ли вообще поднять второй стенд

**Что не так.** Лицензии, сеть и ресурсы план проверяет в самом конце, на живой
приёмке, когда весь код уже написан. На хосте eval-tests лицензионный сервер
Loginom (`10.200.1.87:3186/3187`) открыт в nft только для IP `172.18.0.2` через
один bridge; для остального действует policy DROP
(`evals/docs/2026-10-07-eval-tests-runtime.md:100–102`). Отдельная Docker-сеть
на слот — это новый bridge и новый IP, поэтому без новых правил второй сервер
лицензию не получит. Сколько серверных лицензий доступно, не записано ни в
репозитории, ни в карточках Multica.

**Что дописать.** «Этап 0 — предусловия» перед кодом live-пути: выбрать хост,
вручную поднять вторую пару Studio + Loginom, подтвердить лицензию, правила nft
и запас CPU/RAM/диска, написать runbook подготовки N стендов. Очередь на fake
CLI можно писать параллельно с этим этапом.

### 2. Lease контейнера может не защитить от чужого прогона

**Что не так.** Путь lease в плане не назван: «общий стабильный каталог
harness». Если каталог окажется внутри checkout, другой worktree его не увидит.
Существующий замок общего стенда `R/operations/stand.lease` новый путь не
читает: при N > 1 план запрещает переменные node-ops
(`evals/src/node-eval-ops.ts:41, 72–76`).

**Почему это опасно уже сейчас.** На общем стенде идёт серия LAB-75: на момент
проверки (11.10, 19:38 МСК) — 91/144, контейнер `loginom-evals-server`; за ней в
очереди того же runtime стоит задача LAB-56. Если оператор впишет этот
контейнер слотом, широкая очистка одного прогона сотрёт пакеты другого.
Проверка пустого storage перед попыткой гонку сужает, но не закрывает.

**Что дописать.**

- Фиксированный путь lease на весь хост, вне checkout, профилей и каталога run.
- Перед допуском читать существующий `stand.lease` и отказывать, если container
  ID или endpoint совпадает со слотом.
- Ручную процедуру снятия зависшего lease (исчезнувший PID его не снимает, и
  это правильно).

### 3. Проверки маршрута Studio → свой сервер, на которую опирается план, нет

**Что не так.** План ссылается на «немодельную проверку подключения», которая
подтверждает фактический WebSocket-маршрут. Но `loginom check` возвращает
только `LOGINOM_CONNECTION_VALID`, без адреса WebSocket
(`packages/agent/src/cli/loginom-management.ts:67–76`): тот же пользователь на
чужом сервере даст тот же успех. Preflight проверяет только HTTP 200 и alias в
жёстко заданной сети `loginom-net` (`evals/src/preflight.ts:39–41, 75–78`). Это
ровно класс ошибки [LAB-31](../../evals/docs/2026-10-09-lab31-blocker-fixes.md).

**Что дописать.** Конкретный автоматический критерий допуска:

- Studio и сервер подключены ровно к сети своего слота;
- alias `loginom-server-7.4.2-test` в этой сети есть только у своего сервера;
- из контейнера Studio alias разрешается в IP своего сервера;
- в `server.json` Studio прочитано `wsproxy=true`;
- порт 8080 сервера наружу не опубликован;
- `loginom status --format json` профиля показывает URL и пользователя этого
  слота.

Динамическое доказательство — пакет появился только в storage своего сервера —
остаётся в живой приёмке.

### 4. Авторизацию агента нельзя откладывать до живой приёмки

**Что не так.** При обновлении токена клиент записывает новый refresh token
только в свой профиль, а общей блокировки между процессами нет
(`packages/agent/src/plugin/openai/codex.ts:385–398`). Если у слотов копии
одного `auth.json`, после первого обновления второй слот потеряет авторизацию.

**Почему это хуже, чем кажется.** Такой сбой даёт код выхода 1, то есть статус
`failed` ([спека](../superpowers/specs/2026-09-18-evals-design.md), строка 43;
`evals/src/report.ts:31`). Он попадёт в метрики качества как провал модели —
без retry и без карантина. Короткий smoke может пройти на ещё живом токене и
ничего не доказать.

**Что дописать.** Условие допуска: у каждого слота независимые учётные данные —
отдельный вход или API-ключ. Допуск отказывает, если `auth.json` слотов — один и
тот же файл или в них одинаковый refresh token (сравнивать хэши, не значения).
В живую приёмку добавить принудительное обновление токена у обоих слотов.

Альтернатива — ветка `origin/shared-oauth`: общий каталог токенов
(`LOGINOM_AI_AGENT_SHARED_AUTH_DIR`) и обновление под `flock`. Она не влита в
`evals-parallel`, а её живая приёмка восьми параллельных CLI не пройдена
(`docs/testing/loginom-ai-agent/shared-oauth.md:104, 108` в той ветке). Кроме
того, harness пришлось бы монтировать в sandbox лишний каталог и пробрасывать
переменную. Для v1 вариант не подходит; в плане его стоит упомянуть как
отклонённый.

## Важно: решения, которых не хватает реализатору

5. **Процессы браузера соседа с высокой вероятностью отправят здоровый слот на
   карантин.** Новый процесс того же Chromium без `--user-data-dir` у себя и у
   родителя остаётся «неизвестным», и очистка слота завершается ошибкой
   (`evals/src/process-supervisor.ts:568–573, 601, 731`). Под это правило
   попадают helper-процессы соседа, переподчинённые его launcher.
   - Исправление — обязательная часть v1, а не условная.
   - Механизм: общий для процесса реестр launcher всех слотов (pid +
     starttime); процесс с launcher другого слота среди предков считается
     чужим.
   - Критерий теста №3: пока дерево слота B живо и порождает новые процессы,
     очистка слота A подтверждена, а список неизвестных процессов пуст.
   - Риска взаимного уничтожения нет: у каждой попытки свой subreaper, а
     сигналы шлются поштучно с проверкой identity.

6. **Не сказано, чем кончается отказ допуска одного слота.** В согласованном с
   владельцем тексте было: «если одно окружение не готово, запуск отклоняется до
   первой модельной попытки». В документ эта фраза не попала. Сейчас ошибка
   preflight даёт код 2 без summary, а ошибка подготовки профиля — summary,
   код 1 и неснятый lease (`evals/src/run.ts:28–31, 68`). Дописать: любой слот
   не прошёл допуск → код 2, summary нет, снимаются только собственные пустые
   резервы.

7. **Нет подготовки каждого слота.** `prepareProfile` выполняется один раз на
   run (`evals/src/run.ts:357–364`): снятие `.writer`, `ensureProfile`,
   проверка auth, recovery, начальный архив истории. Проверки preflight
   (`checkSandbox`, контейнер, storage) — тоже (`evals/src/run.ts:40`). Без
   этого первая попытка второго слота упадёт на проверке чистоты профиля.
   Каталог `preparation/` для management тоже нужен свой на слот.

8. **Флаги без многослотовой семантики.**
   - `--reset-profile` удаляет профиль целиком вместе с `auth.json`
     (`evals/src/profile.ts:348–351`); при N > 1 его стоит запретить.
   - `EVAL_HARNESS_LEASE_RECEIPT` — один файл, записываемый с флагом `wx`
     (`evals/src/lease.ts:23–28`). Второй слот упадёт, а его каталог lease уже
     будет создан. Запретить переменную при N > 1 или завести квитанцию на
     слот.
   - Для `--dry-run` нужна своя схема слота: только `id` и `profileDir`.

9. **Теряется свойство round-robin из спеки.** Спека (строка 405) и
   комментарий в `evals/src/run.ts:69` обещают: Ctrl+C после первого круга
   оставляет полное покрытие задач. Без барьера между кругами свободный слот
   возьмёт задание круга 2, пока соседний ещё в круге 1. Нужно явно выбрать:
   принять потерю и поправить спеку — или ввести барьер.

10. **Одновременные судьи делят один `CODEX_HOME`.** Судья наследует общий
    `~/.codex/auth.json`, а `judge.env` в `run.ts` не используется
    (`evals/src/judge.ts:225–231`). Судья занимает около 4,5% времени: в LAB-55
    в среднем 47,5 с против 635 с у агента. Простейшая защита — общий мьютекс
    на вызов судьи (это не отдельная очередь); альтернатива — свой
    `CODEX_HOME` на слот.

11. **Лимиты провайдера смешиваются с качеством.** Ошибки провайдера, включая
    429 и перегрузку, дают код 1 и статус `failed`, который входит в
    знаменатель качества. Параллельность повышает их вероятность. Дописать: N
    выбирается в пределах лимитов учётки, отчёт показывает число сбоев
    провайдера, живая приёмка проходит без 429.

12. **Общий event loop.** Во время запуска браузера supervisor опрашивает
    `/proc` каждые 10 мс (`evals/src/process-supervisor.ts:629–644`).
    Синхронный разбор событий или диагностики в соседнем слоте может сдвинуть
    этот опрос, и очистка не подтвердится. Дописать запрет синхронного I/O на
    пути слота и контроль `observations.max_duration_ms` в тестах и на приёмке.

13. **Общая сеть хоста.** bubblewrap не изолирует сеть
    (`evals/src/sandbox.ts:27`), поэтому агент слота A физически может открыть
    Studio слота B. План закрывает только CDP, хотя повторы одной задачи могут
    идти одновременно. Нужно явно выбрать: принять это как остаточный риск v1 с
    негативной проверкой (действия A не создают файлов в storage B) — или
    требовать сетевую границу между слотами.

14. **Контракт summary и `config.json` не доопределён.**
    - Для N = 1 (с файлом слотов и без него) не сказано, пишутся ли `slot_id`,
      `slots`, `config.parallel`. А исходная приёмка задачи №6 требует «тот же
      контракт summary.json».
    - `config.json` пишется целиком (`evals/src/run.ts:47`). Поля `profileDir`,
      `loginom.url`, `username` в нём станут неоднозначными, а план описывает
      только три поля `summary.loginom`.
    - Любой непустой `stopped_reason` гасит вердикт compare
      (`evals/src/compare-analysis.ts:71`) и роняет node-evals
      (`evals/src/node-evals.ts:46`). Нужно решить, пишется ли он, если слот на
      карантине, а очередь разобрана полностью.
    - `storage_leftovers` оставить списком строк; compare должен считать
      отсутствующий `parallel` равным 1; новые поля проверять, только если они
      есть, иначе старые summary перестанут читаться.

15. **node-evals лучше исключить из v1.** Это отдельный вход
    (`evals/script/run-node-evals.ts`): после `main()` он собирает
    доказательства из внешнего `config.profileDir`
    (`evals/src/node-runner.ts:27–35`). Со слотами, даже при N = 1 из файла, он
    будет смотреть не тот профиль. Запрет слотов в node-evals ещё и сокращает
    объём работ.

16. **Часть обязательных проверок не реализовать в описанном виде.**
    - Задержку fake CLI через `main()` не передать: переменные `EVAL_*`
      срезаются (`evals/src/cli.ts:100`). Нужен канал через `EVAL_TASK_ID` или
      файл сценария.
    - Проверки контейнеров требуют настоящего Docker, а без образа
      пропускаются: на 11.10 было 14 skip
      (`evals/docs/2026-10-11-rebase-checkpoint.md:12–14`). Нужен отдельный
      прогон с Docker.
    - «Чистая PID-граница» должна быть общей для обоих supervisor; граница на
      каждый слот сделает тест №3 бессмысленным.
    - `bun test` нельзя запускать одновременно с живым прогоном
      (`evals/docs/node-evals.md:25`).

17. **Не перечислены документы, которые нужно поправить до кода.** Правило
    «сначала спека» (`evals/AGENTS.md:6`) требует сначала обновить:
    - [спеку evals](../superpowers/specs/2026-09-18-evals-design.md), строки
      около 153, 183, 296, 393, 401–405, 415–417, 423, 474–476, 514;
    - `evals/AGENTS.md`, строки 9 и 21–22;
    - `evals/README.md`;
    - `evals/docs/node-evals.md`;
    - `evals/docs/evaler-orchestration.md`;
    - runtime-документ стенда `evals/docs/2026-10-07-eval-tests-runtime.md`.

18. **Маркер стенда и секреты.**
    - Если `previous_container_id` в маркере одного слота указывает на
      работающий сервер другого слота, допуск падает
      (`evals/src/preflight.ts:62–67`). Правила маркеров нужны в runbook.
    - `redact` и `cleanupSecrets` рассчитаны на один пароль.
    - Переменные `passwordEnv` с именами без префиксов
      `LOGINOM_`/`EVAL_`/`JUDGE_` попадут в окружение судьи и
      management-процессов (`evals/src/cli.ts:100`,
      `evals/src/judge.ts:225–231`, `evals/src/profile.ts:97`). Требовать
      префикс `LOGINOM_` и маскировать пароль каждого слота.

## Желательно

- В схеме файла слотов явно написать: `loginom.url` — это URL Studio,
  `storageDir` — путь внутри контейнера (`/workdir/UserStorage/<user>`). Файл
  проверяется целиком. Если N больше числа заданий, поднимать только нужное
  число слотов.
- Дополнить таблицу отказов:
  - все слоты на карантине → summary и код 1, неначатые пары не пишутся;
  - первый Ctrl+C при успешной очистке → код 0, как сейчас;
  - повторный Ctrl+C → код 130; launcher и lease остаются, нужна ручная
    процедура.
- Добавить правило свёртки `interrupted_cleanup` для нескольких слотов.
  `total_duration_ms` подписать в отчёте как сумму попыток и показывать
  реальное время прогона.
- Добавить префикс слота в строку прогресса (`evals/src/run.ts:93`).
- По CDP явно записать ожидаемое: Playwright запускает Chromium через pipe, без
  TCP-порта. Проверка на отладчик отправляет на карантин слот, который её
  выполняет, а не владельца порта. В живой приёмке снять список listener, пока
  оба браузера живы.
- Вернуть критерий приёмки из задачи №6: «профили не видят чужой `.writer`».
- Для задачи №7 заранее писать `slot_id` в `result.json`, а в lease — run,
  slot, task и attempt.
- Обновить checkpoint плана: `writing-plans` уже установлен
  (`~/.codex/skills/writing-plans/SKILL.md`) — он появился через 8 секунд после
  коммита плана; копии навыка были и раньше.
- Добавить глоссарий и разделы «Предусловия», «Принятые решения», «Открытые
  вопросы»; ссылкам на документы — якоря на конкретные разделы.

## Что в плане верно

Подтверждено по коду, истории и API Multica:

- исторические факты и коммиты 2–7 октября;
- цифры LAB-55: 91 488 296 мс работы продукта и 4 085 291 мс судьи; остановка
  после 43/144 действительно была;
- `ensureProfile` не переключает готовый профиль на новый endpoint;
- дефект с заменой результата retry через последний элемент массива реален;
- `--keep-storage` несовместим с несколькими слотами;
- продукт менять не нужно: на пути `run --headless` нет фиксированных портов,
  кэши и `.writer` лежат внутри профиля;
- compare и rejudge переживут новые поля;
- инструменты знаний Dock только читают, поэтому попытки не пишут друг другу в
  память.

Подход «одна очередь в одном процессе» обоснован, менять его нет причин.

## Как проверялось

Изучена сессия Codex `01a12bba-a4c3-7f71-99b8-a5d6f626d28f`, в которой
создавался план: весь диалог и отчёты трёх её субагентов. План сверен с кодом
на коммите `98549274bf` десятью независимыми проверками по областям: цикл
попытки, допуск и стенды, supervisor процессов, продуктовый CLI, авторизация и
судья, summary, история и контракты, Multica, тесты, критическое чтение.
Multica опрашивалась только GET-запросами. Выводы разделов «Критично» и
«Важно» дополнительно перепроверены по коду. Живые evals и тесты не
запускались, код и стенды не менялись.
