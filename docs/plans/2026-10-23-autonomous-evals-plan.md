# План автономных eval-прогонов

Решения владельца от 23.10.2026 применены. План прошёл независимое ревью без обязательных замечаний. Реализация начата; состояние этапов — в checkpoint.

## Для владельца

### 1. Цель и роли

После постановки кампании система должна выполнить предусмотренные измерения, сохранить и учесть результаты, очистить ресурсы и опубликовать итог без команд пользователя или сопровождающего Codex. Если продолжение объективно невозможно, она завершает работу с честным частичным итогом по правилам раздела 8.

Обычную работу выполняет небольшая служба systemd на сервере: это процесс, который продолжает работу после завершения агентской LLM-сессии. Модель нужна для исключений, а не для выбора каждого следующего измерения.

Операционный squad остаётся группой из трёх агентов:

- **EvalOps — лидер на gpt-6-astra.** Принимает кампанию, выбирает среду и исполнителя, глубоко диагностирует блокеры по логам, процессам и ресурсам. Исправлений не вносит: передаёт исполнителю причину, точное изменение и способ проверки, затем проверяет результат.
- **EvalBaseline** выполняет воспроизводимые baseline-прогоны существующих тестов и сравнение с предыдущим baseline.
- **EvalRunner** выполняет назначенные кампании по закреплённым условиям. Оба исполнителя также вносят порученные технические исправления; их предметная роль не зависит от выбранного сервера.

Evaler и его squad сохраняют создание и приёмку новых тестов; их обязанности и настройки не меняются. Существующие привязки исполнителей к runtime Multica — среде управляющего агента — сохраняются. EvalOps работает в том же runtime, что EvalBaseline. Сервер измерений выбирается отдельно.

**Инструкция постановки: «Кампании назначать на EvalOps; не назначать на squad и не писать @squad».** Это обычная задача агента, без ограничивающего протокола лидера squad. Поручения исполнителю передаются через адресное @упоминание. Собственная сборка, исправления Multica и PR её авторам не предусмотрены.

### 2. Как идёт кампания и что происходит при сбое

EvalOps проверяет доступность, совместимость, активные прогоны и резервирования на eval-runner-1 и eval-runner-2. Статуса idle у агента недостаточно. Он выбирает свободный совместимый сервер и передаёт исполнителю ID кампании и ссылки на её конфигурацию. Сервер закрепляется за кампанией; работающий batch — группа одновременно исполняемых попыток — не переносится.

Служба принимает уже работающий batch либо начинает разрешённый, ждёт его результата, проверяет и учитывает измерения, выбирает только недостающие, затем выполняет очистку и публикацию. Исправно полученный quality FAIL — полноценный результат, его не повторяют ради PASS. Техническую ошибку не выдают за FAIL; готовое качество не теряют из-за позднего сбоя очистки или публикации.

При техническом блокере служба прекращает новые измерения, пишет причину и будит EvalOps. Тот диагностирует и поручает исправление. Исполнитель чинит, проверяет и возобновляет службу; её дальнейшая работа не ждёт освобождения LLM EvalOps. Точные действия и автоматические сигналы описаны в разделе 7.

У владельца один канал состояния: статус карточки и одна запись о блокере. Её ведёт служба и меняет только при смене причины, включая устранение; при недоступности её хоста итог публикует EvalOps по правилам раздела 8. Агенты не дублируют сообщения о состоянии; их адресные поручения и ответы с доказательствами служат передаче работы.

Владелец нужен для решений за пределами выданных полномочий: например, оплаты квоты, выдачи отсутствующего доступа или изменения условий эксперимента. Отдельная ручная операция после потери права вызова агента указана в runbook раздела 7. Когда причина исчезает в пределах допустимого ожидания, система продолжает работу сама.

Не входят в работу: новый scheduler или база инцидентов, перенос batch, миграция runtime, создание eval-тестов, изменение продукта или критериев ради PASS. История LAB-120/LAB-122 не переписывается.

### 3. Порядок реализации

| Шаг | Что сделать | Проверяемый результат |
| --- | --- | --- |
| 1. Цикл на runner2 | Исполнитель реализации пишет TS-команду поверх `origin/evals-parallel`, связывающую существующие запуск, учёт и публикацию, по правилам проекта с независимым ревью. EvalBaseline запускает проверочную кампанию на runner2. | Короткая кампания из двух batch с заранее известным FAIL: LLM прекращена во время первого, итог всё равно опубликован. |

| 3. Правила завершения | Закрепить числа из manifest, частичный финал и единый канал владельца. | Тесты службы подтверждают предел для внешнего и технического блокера, правило последовательных ошибок и корректный итог без живой аварии. |
| 4. EvalOps | Создать группу и агента, настроить доступ, каталог, слоты daemon и штатные пробуждения. Проверить gpt-6-astra минимальным реальным вызовом только на этом этапе. | На одной пробной карточке прямое назначение не добавляет протокол лидера; диагностика → поручение → исправление → финал работают. |
| 5. Второй сервер | После возвращения runner1 подготовить на нём тот же разрешённый путь и дать обоим исполнителям доступ к обоим серверам. | Все четыре сочетания исполнитель/сервер работают; при занятом сервере выбирается другой совместимый. |

| 7. Полная кампания | Выполнить manifest на 234 ключа. | От постановки до опубликованного финала нет вмешательства пользователя или сопровождающего Codex; живые проверки перечислены в разделе 9. |

## Приложение для исполнителя

### 4. Конфигурация и значения по умолчанию

У каждого факта одно место хранения:

- **Manifest кампании:** условия эксперимента, состав измерений и численные ограничения из таблицы ниже. Остальные параметры сохраняются как в действующем manifest.
- **Один конфигурационный файл на сервер:** пути, разрешённые команды, systemd unit и принятая версия harness — кода, который запускает и проверяет eval. Все операционные команды читают этот файл.

Инструкции агентов ссылаются на эти файлы и не копируют SHA, пути и прогресс. Повторная доставка задания использует прежний ID кампании. Каждая попытка сохраняет действовавшие для неё условия и версию harness.

| Параметр manifest | Значение по умолчанию | Как применяется |
| --- | --- | --- |
| Запас попыток | +20% к числу ключей | Всего `K + ceil(0.2 × K)` начатых попыток измерения; для K=234 — 281. Внутренний retry запроса не создаёт новую попытку. |
| Таймаут задачи | 15 / 30 / 60 минут | Базовый — 15 минут; task.json задаёт предусмотренные для конкретного кейса 30 или 60 минут. Не заменять их одним глобальным timeout. |
| Таймаут судьи | 5 минут | Внутренние request/stream retries Codex остаются отключёнными. Существующий второй invoke в harness после неуспешного первого не расширяется. |
| Длительность batch | Не более 8 часов | `RuntimeMaxSec=8h`; это не срок всей кампании. |
| Ожидание любого блокера, включая технический ремонт | 24 часа без прогресса | Повторный просмотр состояния, комментарий, тик будильника, рестарт агента и безуспешная попытка ремонта не продлевают срок. |
| Последовательные инфраструктурные ошибки | 3 → стоп новых измерений и технический блокер | Счётчик ведёт служба по завершившимся попыткам; корректный quality-результат прерывает последовательность. Перезапуск процесса счётчик не обнуляет. |
| Будильник EvalOps | `every=900` секунд | Включён от создания кампании до любого опубликованного финала. |

Параметры переопределяются в manifest до запуска. Дополнительные измерения после исчерпания запаса не разрешаются молча. Источники исходных таймаутов и эксплуатационных ограничений приведены в разделе 12.

### 5. Выбор сервера, владение и доступы

На выбранном сервере хранится **одна запись владения кампанией**: сервер, ID кампании, текущий исполнитель, флаг «идёт ремонт», кто чинит. Запись ведётся под узкой controller-блокировкой `flock`: это новая часть TS-команды, использующая уже применяемый harness механизм ОС; готовой публичной controller-блокировки в исходной базе нет. Проверка актуального назначения и начало изменяющего действия атомарны. Служба также проверяет флаг ремонта перед новыми измерениями. Резервирование по тому же ID кампании идемпотентно — повтор обращения не создаёт второй запуск. Реализацию native leases, то есть штатных резервирований конкретных ресурсов, не изменять.

Выбор делает одна задача EvalOps с использованием штатной сериализации Multica для пары карточка/агент. Перед назначением проверяются реальные ресурсы и активные reservations; локальная проверка и закрепление исключают конфликтующие назначения. Если ответ SSH потерян, опросить **оба** сервера на наличие этого ID кампании и только после выяснения результата выбирать другой. Недоступный сервер означает неизвестный результат, а не доказанное отсутствие кампании. Если оба заняты или недоступны, ждать следующего штатного пробуждения, не создавая новый ID.

Всем трём агентам выдаются одинаковые полные права на оба сервера через текущие учётные записи и sudo по паролю. **Компромисс владельца:** защита от двойного запуска держится на том, что все изменяющие действия проходят через controller; при полных правах ОС не гарантирует соблюдение этого правила. Полные права не разрешают трогать чужую работу или менять условия эксперимента.

Пароли и токены не попадают в аргументы команд, вывод, комментарии, Git или контекст модели. Sudo получает пароль защищённо, например через `SUDO_ASKPASS`, читающий файл с правами 600. Токен Multica для службы хранится в защищённом файле на сервере. При подготовке плана файлы секретов не читались и доступы не распространялись; при реализации их читает только процесс подключения, без вывода значений.

**Совместное размещение — известный риск:** runner2 имеет hostname `swarm`; на нём же работает runtime `Codex (swarm)` и daemon `loginom-evals-runner2-multica.service`. Отказ runner2 одновременно останавливает стенд, EvalBaseline и EvalOps. В шаге 4 включить автоперезапуск daemon вместо текущего `Restart=no`, предусмотреть слоты EvalOps и исполнителя с учётом всех остальных агентов этого daemon; текущий лимит равен 1. Дать EvalOps отдельный управляющий каталог, чтобы он не ждал блокировки каталога исполнителя. Автоматической миграции нет.

### 6. TS-команда кампании и необходимые правки harness

**Исходная база — `origin/evals-parallel`.** Принятый путь: новая небольшая команда `evals/script/run-campaign.ts` и проверка её поведения в `evals/test/campaign.test.ts`. Ориентир — 300–500 строк команды и около 200 строк основного теста. Это целевой объём, а не разрешение создать ещё один слой orchestration.

Ветка реализации начинается от `loginom`; недостающая готовая база переносится отдельным коммитом только из `evals/`, без продуктовых изменений другой ветки. Изменений `loginom` в этом каталоге после общего предка нет. Размер этого переноса учитывается отдельно от нового кода кампании.

Команда связывает существующие `prepared-run.ts`, `scheduler.ts`, `startup-reconciliation.ts`, `lease.ts` и путь незавершённого судейства `rejudge.ts` / `--judge-only`. Она принимает работающий batch → ждёт завершения → проверяет индивидуальные результаты → записывает учёт → выбирает недостающие ключи → запускает следующий batch → финализирует. Сверка состояния выполняется при каждом старте службы. Слепой `Restart=always` для batch-unit запрещён: перезапускается возобновляемый цикл, а не измерение без проверки результатов.

Учёт ведётся в TS-журнале кампании. Сохранённый result без summary принимается по собственному контракту результата и связанным доказательствам; общего summary не требуется создавать задним числом. Завершённое судейство не повторяется. Если артефакт готов, но судейство не завершено, используется только соответствующий этап, без повторной генерации. Существующий rejudge зависит от summary и не обеспечивает выбор только незавершённых результатов: это узкая доработка TS-пути, а не готовая гарантия `--judge-only`.

Готовое качество, освобождение ресурса и доставка отчёта учитываются отдельно. Дополнительное подтверждение позднего cleanup — очистки и освобождения ресурсов — связывается с исходной попыткой; история не переписывается. Новая техническая правка harness не меняет условия измерения сверх принятых решений владельца, а все команды используют принятую версию из серверного файла конфигурации.

| Наблюдавшийся отказ / решение владельца | Минимальное изменение | Проверка рядом с кодом |
| --- | --- | --- |
| Один retry отменял весь batch | В `run-incidents.ts:13–24` не считать голый `session.status: retry` общим инцидентом; в `prepared-run.ts:116` и `:138–139` убрать связанные общую отмену и остановку batch. Новый классификатор ошибок не добавлять. | Retry в одном слоте не отменяет соседей; общие стопы по доказанному нарушению владения или лимита сохраняются. |
| Повтор запроса уже есть в CLI | Переиспользовать до пяти штатных повторов внутри попытки из `packages/agent/src/session/retry.ts`, без сброса общего таймаута. Для auth, quota и неизвестной инфраструктурной ошибки действует последовательность из раздела 4. | Таймер попытки не начинается заново; автоматические повторы судьи не появляются. |
| Пропуски телеметрии отменяли пригодное качество | **Изменение условий эксперимента, принятое владельцем:** если в собранных точках нет превышения лимитов, качество засчитывается; пропуски явно указываются в итоге и не вызывают повтор. В `parallel-acceptance.ts` отделить неполноту наблюдения от наблюдённого превышения. | Пропуск без превышения не отвергает качество; наблюдённое превышение по-прежнему проваливает ресурсную проверку. Отсутствие точек не выдаётся за доказательство непрерывного соблюдения лимита. |
| Смена UID / отказ чтения `/proc` после выхода процесса | Закрепить узкий путь LAB-122: проверить конкретный systemd unit, invocation и boot после выхода процесса, без сигналов и новых логинов. | Подтверждённый выход принимается; живой или неподтверждённый чужой процесс не объявляется очищенным. |
| Первый реальный запрос зависал через proxy при успешных простых пробах | Preflight — предварительная проверка — использует тот же профиль, маршрут и реальный путь запроса. После трёх пустых ответов подряд прекратить новые измерения и установить технический блокер. | Проход простого HTTP-запроса не подменяет реальный ответ; третья пустая проба останавливает попытки, рабочий timeout не увеличивается. |
| Reboot между result и summary; node был исключён из прежнего patch | Учесть regular/analytic/node в TS по собственным контрактам, без переноса Python-реализации. | Сохранённый node-result учитывается после reboot ровно один раз; неподтверждённый результат не засчитывается. |

В шаге 6 служба при сверке запускает выделенные server/studio контейнеры штатной процедурой: их текущая политика `restart=no` сама этого не сделает. Перед продолжением проверяются текущие процессы, резервирования, результаты и готовность ресурсов; работающий batch принимается под наблюдение.

### 7. EvalOps, поручение ремонта и пробуждения

На шаге 4 проверить на живой Multica одной пробной карточкой отсутствие протокола лидера при прямом назначении EvalOps. До этого проверить сборку prompt по локальному source недостаточно, чтобы объявить живой путь подтверждённым.

Порядок ремонта:

1. Служба закрывает новые измерения, записывает блокер и меняет статус по правилам раздела 8. Работающий исправный batch не отменяется только из-за смерти управляющей LLM.
2. EvalOps изучает фактические процессы, результаты и владение; формулирует причину, что исправить и чем подтвердить. Через controller ставит флаг ремонта на конкретного исполнителя и поручает работу адресным @упоминанием.
3. EvalBaseline или EvalRunner вносит исправление, выполняет проверку, снимает флаг ремонта, возобновляет службу с проверкой предела ожидания и опубликованного финала по разделу 8 и @упоминает EvalOps с доказательствами. Незавершённое действие после сбоя сначала сверяется по фактическому результату, а не повторяется вслепую.
4. EvalOps проверяет достигнутый результат. Если он не подтверждается, готовит новый диагноз. Обычный ход службы не ожидает этого LLM-ответа; новый выявленный блокер проходит тот же путь.

Новые многошаговые правки harness проходят существующий независимый review-инструмент до внедрения. Уже проверенные процедуры повторно не ревьюятся. Исполнитель сохраняет условия эксперимента; EvalOps проверяет результат ремонта, не реализует его сам.

EvalOps будят три существующих механизма:

- правило на `status=blocked`;
- встроенный сигнал о падении поручённой задачи: требуется `delegated_from_task_id`, членство в squad для него не обязательно;
- периодический будильник из manifest, зарегистрированный до начала кампании и действующий всё время её жизни. Каждый тик — короткое чтение состояния; при здоровой работе штатный check-in без комментария.

Вся работа исполнителей поручается EvalOps, поэтому достаточно этих трёх механизмов. Сигналы сначала сверяются с живыми задачами, процессами и сохранённой работой; pending native retry или идущий ремонт не дублируются. Периодический вызов покрывает падение самого EvalOps, которое он не успел описать, и проверяет предел ожидания по разделу 8. Зависшую задачу `running` и возвращение offline-runtime обрабатывают существующие механизмы Multica, без нового watchdog и доработки платформы.

Перегрузку управляющей модели переживают служба без LLM, периодический вызов EvalOps и возврат отказа поручённого исполнителя. Нельзя обещать native retry capacity: проверенная Multica его не выполняет; некоторые сообщения с `selected model` попадают в model unavailable. Модели агентов не подменяются, патч классификации не делается. Неподвижное `blocked` само по себе не вызывает повторный запуск, поэтому периодический механизм необходим.

**Runbook:** после возврата потерянного права вызова включить прежнее правило штатно — через UI, CLI или `POST …/wakeups/{id}/enable`; автоматического повторного включения нет.

### 8. Честный финал, публикация и блокеры

**Полный итог** означает: все ключи manifest учтены, артефакты проверены, освобождение ресурсов подтверждено, итог опубликован и прочитан обратно. **Частичный итог** перечисляет сохранённые и недостающие измерения, точную причину остановки и фактическое состояние ресурсов. Оба финала получают `in_review`; заголовок отчёта — «полный» либо «частичный: причина». `blocked` используется только для технического блокера, который будит EvalOps.

Когда исчерпан запас попыток или предел ожидания любого блокера из раздела 4, включая неустранённый технический блокер, служба прекращает новые измерения, выполняет доступную штатную очистку, формирует и публикует частичный итог. Уменьшать объём manifest ради названия «полный» нельзя. Последовательность инфраструктурных ошибок сначала приводит к ремонту, а не немедленному частичному финалу; незавершённый ремонт не продлевает ожидание и не оставляет кампанию в `blocked` бессрочно. В журнале сохраняются срок ожидания и достигнутые результаты; смена процесса или формулировки причины не начинает ожидание заново.

При любом опубликованном финале его автор — служба либо EvalOps — явно выключает будильник: статус `in_review` в Multica не делает этого автоматически. После частичного финала кампания сама не открывается заново.

Если хост службы недоступен дольше предела, EvalOps публикует частичный итог по последним известным данным, ставит `in_review` и выключает будильник, не дожидаясь возвращения хоста. Ресурсы на недоступном хосте помечаются как неподтверждённые; объявлять их освобождёнными или стирать прежние резервирования нельзя. При возвращении служба сначала сверяет опубликованный итог, процессы и результаты: после истечения предела новые измерения не начинаются, опубликованная кампания не открывается заново.

Если одновременно недоступен runtime EvalOps, как при общем отказе swarm, или API Multica, публикация, изменение статуса и отключение правила завершаются при первой доступности. Автоматическая миграция runtime не добавляется. До фактической доставки итог не считается опубликованным.

Сбой доставки не запускает повторные измерения и не удерживает уже очищенные вычислительные ресурсы. Служба сохраняет готовый отчёт, проверяет возможный прежний upload и повторяет только незаконченный шаг. Одна запись о блокере обновляется штатным API комментариев; её ID хранится в журнале службы, без нового канала уведомлений.

| Внешняя причина | Поведение до финала | Что требуется извне |
| --- | --- | --- |
| Оба сервера заняты или временно недоступны | Проверка состояния при очередном пробуждении; чужая работа не останавливается. | Освобождение ресурсов либо возврат сети/сервера. |
| Выбранный сервер или runtime управляющего агента offline | Закрепление сохраняется; живую работу не дублировать; после возврата сначала сверить факты. | Ремонт хоста/питания/сети, если он не выполняется уже разрешённой процедурой. Общий отказ swarm имеет риск из раздела 5. |
| Перегрузка модели, proxy или временная quota | Использовать согласованные внутренние повторы и механизмы раздела 7, затем правила остановки из manifest; дорогие пробы бесконечно не повторять. | Восстановление доступности провайдера/маршрута. |
| Нет credentials, прав или оплаченной квоты | Разрешённое штатное обновление выполняет исполнитель; иначе фиксируется причина ожидания. | Выдача недостающего ресурса/права. Для права вызова Multica действует отдельная строка runbook. |
| Нужна смена модели, корпуса, критериев или бюджета; неизвестно владение ресурсом | Сохранить результаты и не менять условия или чужое владение самостоятельно. | Решение владельца в пределах срока ожидания, иначе честный частичный итог. |
| Multica API недоступен | Сохранить результаты, освободить доказанно очищенные ресурсы, ожидать доставки. | Возврат API; обработка незаконченной публикации не требует команды «повтори измерения». |

### 9. Восемь живых проверок

| № | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| 1 | Оба исполнителя на обоих серверах | Четыре сочетания исполняются через прежние runtime и проходят обычный цикл. |
| 2 | Один сервер занят | Выбран другой совместимый, реальные резервирования соблюдены. |
| 3 | Смерть или перегрузка LLM при живом batch | Ключи учтены один раз, кампания продолжается. |
| 4 | Сбой после итога batch до записи в журнал | Готовое учтено без повторного измерения. |
| 5 | Reboot с сохранённым результатом | Результат, включая node по его контракту, не измеряется повторно. |
| 6 | Технический блокер | EvalOps находит причину и поручает исправление; исполнитель чинит, служба доходит до финала. |
| 7 | Сбой одного слота | Здоровые соседние слоты продолжают работу. |
| 8 | Опубликованный финал | Ключи, артефакты и cleanup отражены честно, статус соответствует итогу, будильник выключен. |

Полный прогон из шага 7 подтверждает автономность только при отсутствии внешних исправлений и команд пользователя/Codex после постановки. Контролируемые отказы проводят в выделенных ресурсах; дополнительные живые аварии ради служебных гонок не нужны.

### 10. Тесты рядом с кодом

Гонки и недоступность проверяются существующими разрешёнными подменами внешних процессов и локальными файлами: потеря SSH-ответа при закреплении; одновременные blocked, delegated failure, periodic и native retry; проверка назначения одновременно с изменяющим действием; мёртвая задача с состоянием `running`; потеря права вызова; неизвестный результат публикации. Для поведения самой Multica проверять реакцию службы/агента на её фактический контракт, а не писать изменения платформы или новые живые квалификации.

Тесты службы также покрывают запас попыток и истечение ожидания без ложного «прогресса» как для внешнего блокера, так и для неустранённого технического блокера: новые измерения прекращаются, публикуется частичный итог, будильник выключается. Проверяются правило последовательных ошибок, полный/частичный итог и отсутствие повторного измерения при сбое очистки или доставки. Локальные проверки пути EvalOps покрывают частичный итог по последним известным данным при недоступном хосте с неподтверждёнными ресурсами; при возвращении служба учитывает опубликованный финал и не возобновляет измерения. Эти тесты подтверждают уже описанные правила и не добавляют условий приёмки.

Из `evals/` выполнять `bun test` для затронутых тестов и `bun typecheck`; соблюдать `evals/AGENTS.md`: один падающий тест поведения → минимальная реализация → проверка. Живую модель и судью в обычных тестах не вызывать, использовать предусмотренные fake-интерфейсы. При новых многошаговых изменениях — отдельный план и независимое ревью до внедрения.
