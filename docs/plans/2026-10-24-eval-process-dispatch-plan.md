# Порядок допуска процесса после spawn

## Результат и основание

Устранить ложный `Process identity changed` при переходе собственного launcher-child из промежуточного Bun в запрошенную программу. Строгие проверки уже принятой identity и право сигналов сохраняются. Это адресная часть устранения management-блокера LAB-170 из [основного плана](2026-10-23-autonomous-evals-plan.md), а не закрытие этапов 5–7.

На runner3 принятая DNS-поставка прошла continuity guard. Следующий `loginom check` сохранил прямого ребёнка launcher как Bun с `via=subreaper`, затем отказал при изменении identity; generation quarantined, три reservations retained. Исторического второго executable-наблюдения нет. Исходный failed receipt сохраняется и не становится успешным из-за последующей правки.

Дешёвая проверка двенадцатью обычными локальными sandbox-процессами не воспроизвела отказ. Адресная проба Bun 1.3.14 через публичные `sandboxCommand` → `superviseProcess` с задержкой `execve(/usr/bin/bwrap)` воспроизвела его 3/3: CLI exit=0, sandboxError=null, cleanup failed. Native hook подтвердил собственный direct child, ещё Bun, с тем же inode, который преждевременно сохранил supervisor. Контроль без задержки прошёл. Отдельная проба показала: обработчик Bun `spawn` получает ребёнка уже после задержанного exec, с executable bwrap. Private evidence: `/tmp/evals-preexec-probe-lUTE8M/`.

Первый проверяемый результат — тот же реальный задержанный fork→exec проходит через публичный supervisor с confirmed cleanup и двумя пустыми финальными проверками. Модель, Loginom и живой браузер для этого не нужны.

## Выбор решения и границы

Выбрана публикация `ready:true` вместе с уже существующим `cli_pid` в обработчике `spawn`. Удаляется прежняя публикация готовности до вызова spawn. Это исправляет producer в месте ошибки без новых состояний, интерфейсов или зависимостей runtime.

Дополнительный admission-протокол в supervisor не нужен: он дублировал бы уже имеющееся подтверждение запуска. Переприсваивание принятой identity, ослабление `sameIdentity`, слепой retry, удаление marker и переписывание failed proof нарушают сохранность владения и не входят в решение.

Область изменений: `evals/src/process-launcher.ts`, один регрессионный тест через публичный API, один Linux C-fixture для управляемой задержки перед exec, этот план и ссылки в двух канонических checkpoint. Ориентир — **6 файлов / 90–160 строк** суммарного diff, включая тест и документацию. Компилятор нужен только для тестовой инъекции; без него такой native-тест явно пропускается. В обязательной квалификации кандидата этот тест выполняется на фактическом Bun 1.3.14 с доступным компилятором. Новой production-настройки LD_PRELOAD нет; тестовый hook удаляет preload перед настоящим exec.

Manifest, corpus/CLI/model/judge pins, результаты, история, лимиты и исходный no-progress deadline LAB-170 не меняются. Новая поставка или смена принятого frozen SHA этим локальным планом не выполняется. Уже оставшийся карантин не снимается этой правкой автоматически.

## Шаги

- [x] **1. Независимое ревью до кода.** Проверены native evidence, достаточность spawn-события на используемом Bun, отсутствие необходимости нового admission-механизма и объём теста. Независимое ревью — PASS, обязательных замечаний нет.
- [x] **2. Один RED через публичную границу.** Небольшой C-fixture задерживает exec собственного launcher-child и сохраняет его parent/device/inode. На старом коде публичный sandbox/supervisor при exit=0 и sandboxError=null отказал именно с `Process identity changed`. Модель и браузер не вызывались.
- [x] **3. Минимальный GREEN.** `ready:true` перенесён в существующий spawn-handler; error/exit handlers и supervisor не изменены. Тот же native-тест подтвердил срабатывание hook, confirmed cleanup, отсутствие unknown processes и две проверки owned_remaining=0. Повтор на окончательном тесте также прошёл.
- [x] **4. Регрессии и commit.** Из `evals/` прошли восемь связанных suite: 156 pass / 13 skip / 0 fail, 616 assertions; package typecheck на Bun 1.3.14 и настоящем Node прошёл. Отрицательные проверки identity и неизвестных процессов сохранены. Независимое ревью кода — PASS, обязательных замечаний нет. Локальная правка сохранена отдельно; production и LAB-170 не переключены. Опциональные proc-denial/live-сценарии не запускались.

## Связанный обязательный recovery

Для LAB-170 отдельно требуется допустимое подтверждение очистки уже failed management и штатное освобождение retained resources перед повторным prepare-generation. Имеющиеся writer settlement и systemd post-exit fallback этот случай не принимают: иной класс ошибки, unknown processes и отсутствие unitBinding у preparation. Обычный повтор упрётся в прежний failed proof.

EvalOps/EvalRunner проверяют эту границу по native receipts. До реализации дополнительного recovery нужен отдельный проверенный способ на фактических данных; нельзя объявлять guard снятым по исчезновению PID или подменять историю. Исправление порядка spawn само по себе не доказывает продолжение missing. Финальный кандидат поставки квалифицируется целиком, включая полную unit-suite, после решения необходимого recovery; затем применяется предусмотренное владельцем принятие конкретного SHA.

Независимая проверка кода подтвердила отсутствие штатного пути для этого карантина. Дополнительный reboot доказывает завершение процессов прежней ОС, но меняет server epoch; нынешние admin/storage API требуют совпадающую текущую identity, а `releaseClosedEnvironment` — уже закрытые слоты. Поэтому reboot сам по себе не разрешает release. Новый способ доказательства очистки между boot/epoch расширяет согласованный контракт и требует решения владельца; failed receipt остаётся неизменным. Без такого расширения сохраняется штатный partial по исходному пределу, а полный результат не объявляется достигнутым.
