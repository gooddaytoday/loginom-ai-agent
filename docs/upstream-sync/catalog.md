# Каталог оставшихся изменений в файлах upstream

Состояние: дерево переноса на OpenCode v2.3.0 (`a6b15d33da`, поле `against` в `catalog.json`; В-83). Каталог описывает файлы, которые существуют в v2.3.0 и в которых форк отличается от него. Новые файлы форка от upstream не зависят и каталогом не описываются: пакеты `loginom-host`, `loginom-runtime`, `product`, `dashboard`, `apps/loginom-site`, `evals`, `services/loginom-ai`, `docs`, `scripts`, workflows форка, корневой `script/` форка, защита от секретов (`.gitleaks.toml`, `.gitleaks-version`, `.gitleaks-upstream`, `.husky/pre-commit`), `.eslintignore` (B1.5), новый файл Desktop `service-identity.ts` (B1.3a). Плагин `loginom.product` (`packages/loginom-agent`, B2.1) — тоже новый пакет форка, как и файл шва U1 `packages/core/src/plugin/product.ts` (CAT-07).

**Записи 0.4 и записи v2.** Записи CAT-01…CAT-12 описывали форк 0.4 на OpenCode v1.19.5 (`810c0eba1a`). Их полный текст с причинами, компонентами и «известным при обновлении» — на точке отсечения: `git show a080f7725c:docs/upstream-sync/catalog.md`. На v2 запись бывает двух видов:

- **с расхождениями** — описывает правку форка в дереве v2;
- **с полем `pending`** — правка 0.4 ещё не перенесена. Поле называет задачу этапа B или этап. Расхождений у такой записи нет. Задача, которая вносит правку, описывает её в записи и снимает `pending`: `catalog-check.py` отклоняет запись с `pending`, у которой появились расхождения.

Новые правки upstream этапа B записывает задача, которая их вносит. Предложение, куда: U1 (B2.1) — CAT-07, U3 (B2.4) — CAT-06, U4 (B2.8) — CAT-08, мягкая остановка службы (B2.3b) — CAT-13.

**Как сохраняется честность каталога.** `catalog.json` относит каждый такой файл к записи по маске пути; побеждает первая подходящая запись. `scripts/upstream-sync/catalog-check.py` завершается ошибкой, если файл не попал ни в одну запись, запись без `pending` осталась без файлов, у записи с `pending` появились файлы или идентификаторы в `catalog.json` и в этом документе разошлись. Проверка входит в процедуру ([procedure.md](procedure.md)), её результат на итоговом SHA — в отчёте. Число файлов в записях меняется с каждой правкой форка, поэтому документ его не хранит: состав по записям и задачи записей с `pending` выдаёт `python3 -I scripts/upstream-sync/catalog-check.py --summary`.

**Имена.** Пакеты upstream носят имена OpenCode 2: область `@opencode/*`, пакет агента — `@opencode/cli` в `packages/cli`. Пакеты только форка сохраняют область `@loginom-ai-agent`. Каталог данных продукта — `loginom-ai-agent` (CAT-13). Внешние имена продукта (`LOGINOM_AI_AGENT_*`, `.loginom-ai-agent`, `loginom-ai-agent.json(c)`, `loginom-ai-agent.db`, `loginom-ai-agent.settings`, `loginom-ai-agent.updater`) применены к дереву v2 командой `apply-identity` (B1.4a). Её правки лежат в записях по маскам путей: CAT-02, CAT-09…CAT-13. Что команда не меняет и что осталось руками — журнал переноса, раздел B1.4a.

## Политики владения

| Политика | Что делать при конфликте |
|---|---|
| `merge` | Объединить обе стороны построчно. Результат проверяется командой из записи и `sync-upstream.sh accepted`. |
| `upstream-first` | Взять файл upstream целиком и повторить описанную в записи правку форка. |
| `fork-owned` | Участок или файл принадлежит форку. Его содержимое сохраняется, изменения upstream в остальных частях переносятся вручную. Выбор файла форка целиком фиксируется как решение владельца (`--allow-ours`). |
| `regenerate` | Не править руками: сгенерировать командой из записи. |

Для всех записей: после слияния выполняются охранные тесты ([guarantees.md](guarantees.md)) и `compat-snapshot` / `compat-compare` ([procedure.md](procedure.md)). Новые `OPENCODE_*`, `.opencode`, `opencode.json(c)` в приходящем коде приводятся к именам продукта командой `scripts/upstream-sync/apply-identity.py` (правило 3 шага 2 процедуры): так записи CAT-02 и CAT-09…CAT-13 получают правку для нового кода.

- **Решение, не процедура: подъём Bun upstream (запись по предложению LAB-306).** Форк на Bun 1.4.4 (В-84, пересмотр решения 2 ADR-0001), а комплект сторонних материалов `packages/loginom-host/licenses/bun` ещё на 1.3.14: генератор — задача B1.6 (её приёмка: CLI собирается без `LOGINOM_BUN_NOTICE_REVISION_MISMATCH`). Требования к генератору и к каждому следующему подъёму Bun не изменились. Версия Bun из корневого `packageManager` связана с точной ревизией в `packages/loginom-host/licenses/bun/source.json`: форк держит Bun на версии своего комплекта сторонних материалов. При переходе на другую версию нужен новый комплект исходников и notices, полученный из её точных upstream pins: Bun LICENSE, native sources и их внутренние инвентари, WebKit commit/tree/archive, locked Rust crates и полный source companion. Значения совместимости из `process.versions` не заменяют проверку build recipes и не являются картой линковки. **Штатного генератора комплекта нет** (проверено по LAB-306 на head `b25776f1`): `build-bun-source-companion.ts` и `build-webkit-source-companion.ts` проверяют и копируют заранее подготовленные архивы по существующим инвентарям, но не получают новые pins и не создают новые инвентари; `collect-build-notices.ts` собирает npm notices фактического bundle, исключая Bun и native dependencies. Генератор нужен воспроизводимый (вход: версия и ревизия Bun, точные upstream sources; выход: неизменённые тексты лицензий, исходные архивы и инвентари с происхождением, размерами, хешами и проверкой состава). Ручная замена version/commit и ослабление guard недопустимы. После генерации — существующие companion builders и независимая проверка SHA256SUMS, CLI build на целевой Bun и отказ на чужой ревизии, release verification и offline smoke Desktop+CLI на Linux/macOS/Windows. Полноту source collection отличайте от оставшегося rebuild/relinking и legal audit; честные `incomplete` и `remaining` сохраняются, пока работы не завершены.
