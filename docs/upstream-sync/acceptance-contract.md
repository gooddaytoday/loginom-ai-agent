# Контракт инструментов приёмки

Что гарантируют шлюз `verify-accepted.py` («слияние — это механическое слияние плюс записанные решения») и `catalog-check.py` («каждое расхождение с upstream описано»). Три проверки подряд (LAB-279, LAB-300, LAB-302) отвергли прежнюю посылку: принятие upstream нельзя вывести эвристикой по содержимому файла, потому что наличие всех строк не доказывает принятия. Шлюз не угадывает: он сравнивает слияние с тем, что делает сам git.

## Как устроен шлюз

1. **Оракул** (`merge_oracle.py`) — механическое слияние двух родителей `git merge-tree --write-tree` с настройками `prepare`: стратегия `ort`, `rerere` выключен, `merge.directoryRenames=conflict`, `merge.renameLimit=30000`, без перенормализации, изолированная конфигурация git. Затем `apply-identity` применяется к каждому обычному текстовому файлу, который слияние изменило относительно форка (тот же набор, что даёт `apply-identity.py --since FORK`). Оракул — функция двух коммитов: те же два коммита дают то же дерево при любой конфигурации git и часовом поясе (тест `OracleIsMechanical`).
2. **Шлюз** смотрит только коммит слияния; его родители обязаны быть ровно форком и upstream (иначе код выхода 2). Он сравнивает дерево коммита с деревом оракула побайтно и требует **запись решения** для путей двух видов:
   - `conflict` — оракул оставил путь конфликтным, значит содержимое выбрал человек;
   - `deviation` — путь не конфликтный, а коммит содержит иные байты, режим, тип или не содержит путь вовсе.
3. **Записи** — файл `docs/upstream-sync/merge-decisions.json` в дереве того же коммита слияния (сам этот файл из сравнения исключён):

   ```json
   {"format": 1, "decisions": [{"path": "<путь>", "rule": "<правило>", "reason": "<что выбрано и почему>"}]}
   ```

   `rule` — ссылка на правило: `CAT-<n>` (запись `docs/upstream-sync/catalog.json` того же коммита), `ADR-<n>`, `STANDING-<n>` или `PROCEDURE-<n>`, при желании с `#якорь`. `reason` не пуст. Формат версионируется полем `format`; шлюз принимает только `1`.
4. **Отказ (`FAIL`)** — путь, которому нужна запись, а её нет; запись, у которой нет такого пути (`stale-record`); запись с неизвестным правилом, пустой причиной или дублем (`bad-record`). Нет записи — `REJECTED`, код выхода 1.
5. **Что остаётся после слияния.** Коммиты поверх слияния (сборка, `upgradeMajor`) шлюз не судит; он перечисляет их в выводе. Отклонение внутри самого коммита слияния судится.
6. **Предупреждения** к путям с записью (не влияют на результат): строки, добавленные upstream и отсутствующие в результате, и строки, удалённые upstream и присутствующие в результате (после замены имён).

## Пределы шлюза

| Чего шлюз не утверждает | Кто и как судит |
|---|---|
| Что конфликт разрешён правильно по смыслу. Запись — это утверждение человека, а не проверка | Проверяющий читает запись и сравнивает результат с обеими сторонами; предупреждения строк помогают, но не заменяют чтение |
| Что в файле нет маркеров конфликта | Сборка и тесты шага `check`; шлюз сравнивает байты, а не смысл |
| Что отклонение от оракула верно по смыслу | То же: проверяющий по записи |
| Что правка после слияния верна | Шлюз её не видит; проверяющий читает перечень коммитов после слияния |
| Что `apply-identity` покрыл видимые строки бренда (CAT-03) | Решение по каждой строке, запись |

## Пространство случаев

Единица — файл. Версия файла — режим и содержимое (текст, двоичный, символьная ссылка, указатель подмодуля) либо «нет».

| Ось | Значения |
|---|---|
| Что сделал upstream (база → upstream) | `A` добавил, `D` удалил, `M` изменил содержимое, `M mode` сменил только режим, `M file to symlink` / `M symlink to file` сменил тип, `R` переименовал (`R+edit` — с правкой) |
| Тип файла | `text`, `bin`, `link`, `sub` |
| Что сделал форк (база → форк) | `none` не менял, `edit` изменил иначе, `same` внёс то же изменение, `delete` удалил, `chmod` сменил режим, `to-symlink` заменил ссылкой, `rename` переместил, `rename+edit`, `different` добавил иное |
| Что оставило слияние | `up` версия upstream, `fork` версия форка, `base` версия базы, `merge` настоящее объединение, `gone` путь удалён, `empty` пустой файл, `lost-line`, `dup-lost`, `removal-kept`, `reorder`, `extra`, `elsewhere`, `old-kept` — искажения результата |

Знак `·` в таблице — сочетание не существует (нечего «объединять» у двоичного файла, нет «версии upstream» у удалённого).

## Вердикты клеток

Вердикт клетки задаёт **модель, независимая от шлюза**: настоящее `git merge --no-commit` в рабочей копии (маршрут индекса, каким пользуется `prepare`, а не `merge-tree`) плюс `apply-identity`. Клетка требует записи, если git оставил её путь конфликтным или коммит отличается от слияния git.

| Код | Смысл |
|---|---|
| `ok` | git сливает без конфликта, коммит равен результату git; записи не нужны, шлюз принимает |
| `C` | git оставил путь конфликтным; без записи `FAIL conflict` |
| `D` | конфликта нет, но коммит отличается от результата git; без записи `FAIL deviation` |

Каждая клетка запускается одна: записаны решения для всех остальных клеток, поэтому код выхода (1) и строка `RESULT: REJECTED` принадлежат только ей; отдельно проверяются запуски «ничего не записано» и «записано всё» (`ACCEPTED`, код 0). Две мутации шлюза — «всегда код выхода 0» и «всегда `ACCEPTED`» — обязаны покраснить все клетки, которым нужна запись (тесты `CellsSeeTheGate`). Маршрут `merge-tree` шлюза и маршрут индекса модели обязаны давать одни конфликты и одно дерево вне конфликтов на всех клетках (тест `TwoRoutesOfGit`).

`catalog-check.py`: охват — файлы, существующие в upstream и отличающиеся в рабочем дереве (изменён, режим, тип, удалён, переименован); добавленные форком файлы вне охвата. Пределы: файлы под `.gitignore` не видны (`git add -A` их не берёт); подмодули учитываются как указатель; проверка считает расхождением любое отличие от `--against`, а не только отличие содержимого.

## Тест процедуры

[`doctest_procedure.py`](../../scripts/upstream-sync/doctest_procedure.py) выполняет блоки с пометкой `doc-test` из [procedure.md](procedure.md) дословно, из корня чистого клона, вплоть до `accepted`: до ручного шага одной оболочкой, после него в новой, где заданы только `OUT` и блок `env` (остальное блоки берут из `pins.env`). Ручной шаг 2 заменяется командой `--resolve`; блок с `<...>` или необязательным `[--флаг]` не проходит. `selftest.sh` запускает его офлайн на синтетическом форке и upstream. Сборка Desktop и шаги, которым нужны bun 1.3.14, Node 24.19 и Chromium, получают `NOT_RUN` с причиной (`CHECK_SKIP`).
