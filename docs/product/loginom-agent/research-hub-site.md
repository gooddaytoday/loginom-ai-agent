# Нужен ли отдельный сайт Loginom Hub

Исследование 18.11.2026 по первичным источникам: документация, спецификации, исходный код, опубликованные правила
операторов. Ничего не запускалось: поведение систем взято из документации и кода. Факты верны на дату исследования.

Вопрос владельца: «нужно разобраться и выяснить нужен ли отдельный сайт для навыков и прочего». Механизм из плана
(отдельный сайт с бэкендом, вход и подпись через GitHub) владелец считает гипотезой, а не требованием.

## Короткий ответ

Сервер нужен — из-за В-34: чтобы аналитик мог опубликовать навык для всех, нужны вход автора, приём навыка,
автоматические проверки, очередь модерации и статусы. Не нужны три вещи из плана: **отдельный публичный сайт**
(витрина, кабинет автора), **GitHub** для входа и подписи, **сервер для самого каталога**. Каталог — подписанные
статические файлы (список, версии, уровни доверия, отозванное); их раздают из интернета, с внутреннего сервера
организации или файлом в закрытый контур. Автор публикует из приложения, модератор работает в служебной консоли.

Ресурсы loginom.ru не используем (В-35): сервис публикации, раздача каталога и, если понадобятся, публичные
страницы — свои, на поддомене loginom.ai.

Что экономит такой вариант по сравнению с планом: не строим и не сопровождаем публичный сайт, кабинет автора и
вход через внешнюю платформу; каталог работает в закрытом контуре без своего экземпляра сервера; нет зависимости
от GitHub.

  библиотеки компонентов. У библиотеки есть страница с установкой, условиями использования и кнопкой «Скачать на

  [github.com/loginom/loginom-silver-kit](https://github.com/loginom/loginom-silver-kit). Все увиденные библиотеки —

- **Аккаунты** на loginom.ru: вход по почте или логину и паролю, регистрация ([вход](https://loginom.ru/u/hi)).
  Можно ли входить этим аккаунтом в другой сервис (OAuth или OIDC), не выяснено.
- **Сообщество** вопросов и ответов [qa.loginom.ru](https://qa.loginom.ru/) с регистрацией.

## Что из этого следует

1. **Каталогу для приложения сервер не нужен.** Homebrew раздаёт каталог как подписанные статические JSON, OpenCode
   берёт навыки из `index.json` по любому адресу. Open VSX документирует перенос зеркала в изолированную сеть
   ([mirror.md](https://github.com/eclipse-openvsx/openvsx/blob/c4849221281440511b16f4bde547c0371f0b7df6/doc/mirror.md?plain=1#L123-L143)).
   Статические файлы одинаково работают из интернета, с внутреннего сервера и с флешки.
2. **Публикация от многих авторов везде приходит к сервису с аккаунтами.** Obsidian ушёл от pull request к своему
   сайту и автоматическому сканеру и так разобрал очередь из 2300 заявок ([блог](https://obsidian.md/blog/future-of-plugins/));
   каталог за полгода вырос с 2750 до 10542 записей ([май](https://github.com/obsidianmd/obsidian-releases/commit/652de396e9),
   [ноябрь](https://github.com/obsidianmd/obsidian-releases/blob/2512b11d937f22a1d98c041d7ff9e35763cf0f3c/community-plugins.json)). Zed и Raycast принимают pull request, но держат свой
   сервер для каталога. Git-публикация — инструмент разработчиков; для аналитиков (В-34) это барьер.
3. **Главная стоимость — модерация, а не сервер.** На ClawHub вредоносные навыки проходили и автоматическую проверку
   ([Unit 42](https://unit42.paloaltonetworks.com/openclaw-ai-supply-chain-risk/)); у Zed проверка занимает недели.
   У Open VSX меньше 50 участников на 100 млн загрузок в месяц и платные тарифы для тяжёлых пользователей
   ([Eclipse](https://eclipse-foundation.blog/2025/09/23/businesses-built-on-open-infrastructure-have-a-responsibility-to-sustain-it/)).
   Если навык — только текст, без программ (предположение, вопрос 2), и навыки сообщества выключены, пока агент
   работает в Loginom (решение 11), проверять проще: нечего запускать, вред ограничен разговором.
4. **Подпись и отзыв почти никто не делает хорошо; образцы — VS Code и Homebrew.** Подписывает каталог (магазин),
   приложение проверяет подпись при установке и регулярно забирает список отозванного.
5. **Стандарт для подписи без привязки к платформе — TUF.** Офлайн-корень, смена ключей, отзыв, зеркала, отдельные
   роли для «Loginom», «Проверено Loginom», «Сообщество». Подвох для закрытого контура: по спецификации клиент
   отказывается работать с просроченной меткой времени
   ([TUF 5.4.4](https://theupdateframework.github.io/specification/v1.0.37/#update-timestamp)), поэтому
   офлайн-набору нужен свой длинный срок и явное, записываемое в журнал решение администратора. Sigstore без своей
   инфраструктуры зависит от внешних сервисов и входа через Google, Microsoft, GitHub
   ([Fulcio](https://github.com/sigstore/fulcio/blob/b01d056a925d1f15d1315676d454adf46b6b6629/config/identity/config.yaml)) —
   для закрытого контура не подходит. Для приложения на TypeScript есть поддерживаемый клиент
   [tuf-js](https://github.com/theupdateframework/tuf-js) (версия 6.0.2 от 04.11.2026 в npm).
6. **GitHub как основа — риск.** Правила GitHub публикацию из России не запрещают
   ([trade controls](https://docs.github.com/en/site-policy/other-site-policies/github-and-trade-controls)), но доля
   сбоев доступа из России выросла с 0,2–1,8% в месяц в 2025 году до 2–5% в 2026-м, с днями до 15–21%
   ([OONI](https://api.ooni.io/api/v1/aggregation?probe_cc=RU&domain=github.com&since=2025-01-01&until=2026-11-18&test_name=web_connectivity&axis_x=measurement_start_day)).
   У GitVerse регистрация только через GigaID ([docs](https://gitverse.ru/docs/gitverse/account-profile/quick-start)).
7. **Реестр отечественного ПО — условие для всего проекта, не для Hub.** С 2023 года у программ в реестре
   хранилище исходников и сборка должны быть в России (постановление 2461,
   [PDF](http://static.government.ru/media/files/c5npn3U2Pz2DiECPIrdUwM9J6emh82R1.pdf)). Правило касается самого
   продукта, о каталогах в нём ничего нет. Репозиторий приложения и сборка выпусков сейчас на GitHub, так что если
   Loginom AI Agent пойдёт в реестр, переносить придётся весь проект, а не только подпись каталога. Требования ГОСТ к
   подписи обновлений в прочитанных актах не найдено; ФСТЭК требует получать обновления из доверенного источника и
   контролировать их целостность ([приказ 239](http://publication.pravo.gov.ru/document/0001201803270041), ОПО.1,
   ОПО.2). Алгоритм подписи стоит сделать заменяемым.

## Рекомендация

Вариант В, в два шага.

- **Свои навыки** живут в приложении: создать, попробовать, включить и выключить, передать файлом коллеге. Ничего
  никуда не отправляется. Механизм — источник навыков плагина продукта и `reload`; в spike на Linux это работало для
  навыка `hub.*` (S9, частично: Windows не проверялся).
- **Каталог** — подписанные статические файлы по схеме TUF: три роли по уровням доверия и список отозванного.
  Одни и те же файлы раздаются из интернета, с внутреннего сервера организации и файлом в закрытый контур.
  Корневой ключ хранится офлайн. Сборка и подпись — на инфраструктуре Loginom, не в GitHub.
- **Публикация, шаг 1 (пока авторов мало).** «Опубликовать» в приложении проверяет навык на месте (формат, нет
  программ, паролей и путей) и отправляет его в Loginom вместе с почтой автора. Сотрудник Loginom проверяет и
  добавляет навык в каталог; ответ приходит автору письмом и виден в приложении после обновления каталога.
- **Публикация, шаг 2 (когда авторов станет много).** Сервис на поддомене loginom.ai со своими аккаунтами (вход по
  почте), статусами
  «Отправлен», «На проверке», «Опубликован», «Отклонён», автоматическим сканером и консолью модерации; отзыв версии.
- **Публичные страницы** навыков — позже, если понадобятся: на поддомене loginom.ai, генерируются из каталога.

## Что меняется в плане

- Этап E: вместо «публичный каталог на hub.kartamyshev.dev → авторы и модерация» —
  1. формат и подпись каталога (TUF);
  2. библиотека своих навыков в приложении;
  3. раздача каталога и отзыва;
  4. сервис публикации и консоль модерации;
  5. внутренний каталог организации;
  6. публичные страницы на поддомене loginom.ai (по желанию).
- Убрать: вход через GitHub OAuth, подпись в GitHub Environments, отдельный сайт на hub.kartamyshev.dev. Где держать
  сервис и ключи — решение владельца.
- Итерация 6 прототипа: «Создать и опубликовать» целиком в приложении. Вместо макета публичного сайта — макет
  консоли модерации.

## Вопросы владельцу

1. **Навыки и работа в Loginom (решение 11).** От ответа зависит, насколько полезен публичный каталог: аналитики
   будут писать навыки в основном для работы в Loginom. Рекомендую:
   - свой навык, написанный в приложении или созданный из своего разговора, работает и в Loginom;
   - навык «Проверено Loginom» тоже работает, ведь Loginom проверил содержимое;
   - навыки «Сообщество» и навыки из файла выключены, пока агент работает в Loginom;
   - администратор может запретить и свои навыки.
2. **Навык — только текст:** инструкции и справочные файлы, без программ и скриптов. Рекомендую так для первой
   версии.
3. **Вариант В.** Без отдельного публичного сайта. Каталог — подписанные файлы. Публикация из приложения: сначала
   отправка на проверку, потом сервис со статусами. Публичные страницы — позже, на поддомене loginom.ai.
4. **Вход автора** — свои аккаунты сервиса с подтверждением по почте, без внешних платформ.
5. **Где всё работает.** Сервис публикации и раздача каталога — на поддомене loginom.ai (например, `hub.loginom.ai`),
   тестовый экземпляр — на вашем сервере. Корневой ключ подписи хранится офлайн у вас, ключи для ежедневной подписи —
   на сервере сборки каталога.

## Что не проверено

- Ничего не запускалось: ни TUF, ни сканеры, ни внутренние зеркала.
- Сколько авторов ожидается: от этого зависит, когда нужен шаг 2 публикации.
- Как приложения отключают уже установленное у Raycast, Claude Code и OpenClaw — источники неполные.
- Акт о требованиях к «доверенному ПО» (возможное место требований к подписи) не найден; сайты ФСТЭК и
  правительства были недоступны, акты читались на publication.pravo.gov.ru.
- Измерения OONI — данные добровольцев, не официальная статистика.
