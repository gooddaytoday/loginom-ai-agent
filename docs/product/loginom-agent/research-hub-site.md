# Нужен ли отдельный сайт Loginom Hub

Исследование 18.11.2026 по первичным источникам: документация, спецификации, исходный код, опубликованные правила
операторов. Ничего не запускалось: поведение систем взято из документации и кода. Факты верны на дату исследования.

Вопрос владельца: «нужно разобраться и выяснить нужен ли отдельный сайт для навыков и прочего». Механизм из плана
(отдельный сайт с бэкендом, вход и подпись через GitHub) владелец считает гипотезой, а не требованием.

## Короткий ответ

Отдельный публичный сайт с бэкендом приложению не нужен. Чтобы каталог работал, хватает **подписанных статических
файлов**: список, версии, уровни доверия, список отозванного. Их можно раздавать откуда угодно: со своего сервера,
с внутреннего зеркала организации или файлом в закрытый контур. Серверная часть нужна только для одного —
**публикации навыков авторами** (В-34): вход автора, загрузка, автоматическая проверка, очередь модерации, статусы.
Это небольшой сервис, а не публичный сайт; автор работает с ним из приложения, модератор — из служебной консоли.
Публичные веб-страницы каталога полезны для поиска и ссылок, но генерируются из тех же файлов и не нужны в первой
версии. Публикацию через git (pull request) для аналитиков не рекомендую, а вход и подпись через GitHub — тем более.

## Что из этого следует

1. **Каталогу для приложения сервер не нужен.** Homebrew раздаёт каталог как подписанные статические JSON, OpenCode
   берёт навыки из `index.json` по любому адресу. Open VSX документирует перенос зеркала в изолированную сеть
   ([mirror.md](https://github.com/eclipse-openvsx/openvsx/blob/c4849221281440511b16f4bde547c0371f0b7df6/doc/mirror.md?plain=1#L123-L143)).
   Статические файлы одинаково работают из интернета, с внутреннего сервера и с флешки.
2. **Публикация от многих авторов везде приходит к сервису с аккаунтами.** Obsidian ушёл от pull request к своему
   сайту и автоматическому сканеру и так разобрал очередь из 2300 заявок ([блог](https://obsidian.md/blog/future-of-plugins/));
   каталог за полгода вырос с 2750 до 10542 записей ([май](https://github.com/obsidianmd/obsidian-releases/commit/652de396e9),
   [ноябрь](https://github.com/obsidianmd/obsidian-releases/blob/2512b11d937f22a1d98c041d7ff9e35763cf0f3c/community-plugins.json)). Zed и Raycast принимают pull request, но держат свой
   сервер для каталога. Git-публикация — инструмент разработчиков; для аналитиков (В-34) это барьер.
3. **Главная стоимость — модерация, а не сервер.** На ClawHub вредоносные навыки проходили и автоматическую проверку
   ([Unit 42](https://unit42.paloaltonetworks.com/openclaw-ai-supply-chain-risk/)); у Zed проверка занимает недели.
   У Open VSX меньше 50 участников на 100 млн загрузок в месяц и платные тарифы для тяжёлых пользователей
   ([Eclipse](https://eclipse-foundation.blog/2025/09/23/businesses-built-on-open-infrastructure-have-a-responsibility-to-sustain-it/)).
   Наш плюс: навык сообщества — только текст, без программ, и он выключен, пока агент работает в Loginom (решение 11).
4. **Подпись и отзыв почти никто не делает хорошо; образцы — VS Code и Homebrew.** Подписывает каталог (магазин),
   приложение проверяет подпись при установке и регулярно забирает список отозванного.
5. **Стандарт для подписи без привязки к платформе — TUF.** Офлайн-корень, смена ключей, отзыв, зеркала, отдельные
   роли для «Loginom», «Проверено Loginom», «Сообщество». Подвох для закрытого контура: по спецификации клиент
   отказывается работать с просроченной меткой времени
   ([TUF 5.4.4](https://theupdateframework.github.io/specification/v1.0.37/#update-timestamp)), поэтому
   офлайн-набору нужен свой длинный срок и явное, записываемое в журнал решение администратора. Sigstore без своей
   инфраструктуры зависит от внешних сервисов и входа через Google, Microsoft, GitHub
   ([Fulcio](https://github.com/sigstore/fulcio/blob/b01d056a925d1f15d1315676d454adf46b6b6629/config/identity/config.yaml)) —
   для закрытого контура не подходит.
6. **GitHub как основа — риск.** Правила GitHub публикацию из России не запрещают
   ([trade controls](https://docs.github.com/en/site-policy/other-site-policies/github-and-trade-controls)), но доля
   сбоев доступа из России выросла с 0,2–1,8% в месяц в 2025 году до 2–5% в 2026-м, с днями до 15–21%
   ([OONI](https://api.ooni.io/api/v1/aggregation?probe_cc=RU&domain=github.com&since=2025-01-01&until=2026-11-18&test_name=web_connectivity&axis_x=measurement_start_day)).
   У GitVerse регистрация только через GigaID ([docs](https://gitverse.ru/docs/gitverse/account-profile/quick-start)).
7. **Реестр отечественного ПО.** С 2023 года у программ в реестре хранилище исходников и сборка должны быть в России
   (постановление 2461, [PDF](http://static.government.ru/media/files/c5npn3U2Pz2DiECPIrdUwM9J6emh82R1.pdf)). Если
   Loginom AI Agent пойдёт в реестр, сборку и подпись нельзя вести в GitHub Actions, как предполагал план.
   Требования ГОСТ к подписи обновлений в прочитанных актах не найдено; ФСТЭК требует получать обновления из
   доверенного источника и контролировать их целостность
   ([приказ 239](http://publication.pravo.gov.ru/document/0001201803270041), ОПО.1, ОПО.2). Алгоритм подписи стоит
   сделать заменяемым.

## Рекомендация

Вариант В.

- **Свои навыки** живут в приложении: создать, попробовать, включить и выключить, передать файлом коллеге. Ничего
  никуда не отправляется. Механизм — источник навыков плагина продукта и `reload` (проверено в spike, S9).
- **Каталог** — набор подписанных статических файлов по схеме TUF с тремя ролями по уровням доверия и списком
  отозванного. Одни и те же файлы раздаются из интернета, с внутреннего сервера организации и файлом в закрытый
  контур. Ключи — у Loginom, корневой ключ хранится офлайн. Сборка и подпись — на инфраструктуре Loginom в России,
  не в GitHub.
- **Публикация** — небольшой сервис: вход автора, приём навыка из приложения, автоматические проверки (формат, нет
  программ, нет паролей и путей, подозрительные инструкции), очередь модерации, статусы «Отправлен», «На проверке»,
  «Опубликован», «Отклонён», отзыв версии. Модератор работает в служебной консоли. После одобрения навык попадает в
  подписанный каталог.
- **Публичные веб-страницы** — позже, если понадобятся поиск и ссылки; генерируются из каталога, без своей базы.

## Что меняется в плане

- Этап E: вместо «публичный каталог на hub.kartamyshev.dev → авторы и модерация» —
  1. формат и подпись каталога (TUF);
  2. библиотека своих навыков в приложении;
  3. раздача каталога и отзыва;
  4. сервис публикации и консоль модерации;
  5. внутренний каталог организации;
  6. публичные страницы (по желанию).
- Убрать: вход через GitHub OAuth и подпись в GitHub Environments. Где держать сервис и ключи — решение владельца.
- Итерация 6 прототипа: «Создать и опубликовать» целиком в приложении. Вместо макета публичного сайта — макет
  консоли модерации.

## Вопросы владельцу

1. Принять вариант В: без отдельного публичного сайта в первой версии; каталог — подписанные файлы; публикация из
   приложения в небольшой сервис; модерация — в служебной консоли.
2. Как автор входит в сервис публикации. Варианты: аккаунт Loginom, если у компании есть общий вход для
   пользователей (не проверено); подтверждение по почте; вход через внешнюю платформу. Рекомендую подтверждение по
   почте сейчас и аккаунт Loginom, когда он будет.
3. Где работают сервис публикации, сборка каталога и ключи: тестовый экземпляр — на вашем сервере, рабочий — на
   инфраструктуре Loginom в России (на случай реестра отечественного ПО).

## Что не проверено

- Ничего не запускалось: ни TUF, ни сканеры, ни внутренние зеркала.
- Есть ли у Loginom общий аккаунт пользователей, которым можно входить в сервис публикации.
- Как приложения отключают уже установленное у Raycast, Claude Code и OpenClaw — источники неполные.
- Акт о требованиях к «доверенному ПО» (возможное место требований к подписи) не найден; сайты ФСТЭК и
  правительства были недоступны, акты читались на publication.pravo.gov.ru.
- Измерения OONI — данные добровольцев, не официальная статистика.
