# Решения владельца по новому приложению

Каждое решение — с датой и источником. Изменённое решение не удаляется, а помечается заменённым.

## 16.11.2026 — постановка

| # | Решение |
|---|---|
| 1 | Новое приложение остаётся форком OpenCode; обновлять форк должно быть как можно проще. |
| 2 | Главный критерий — клиенту всё интуитивно понятно. Прототип — только образец, логику и интерфейс продумываем заново. Технические термины допустимы, если понятно, что они значат. |
| 3 | Каждое UX-решение сначала отражается в прототипе (demo), владелец смотрит, потом реализуем. |
| 4 | Срок не важен: выпускаем, когда сделано хорошо. |
| 5 | Сначала переход форка на OpenCode 2, потом новый интерфейс на нём. |
| 6 | Работаем в форке `loginom-ai-agent-test`; выпуск 0.4.0 доводится отдельно в каноническом репозитории. |
| 7 | Правки в файлах OpenCode держим в форке, в upstream не предлагаем. |
| 8 | Закрытый контур: политика администратора главнее; без неё режим выбирает пользователь. Таких клиентов пока нет, но они важны. |
| 9 | Loginom Hub — отдельный сайт с бэкендом; тестовый экземпляр — Docker на сервере владельца. В закрытый контур — офлайн-пакетом. |

## 17.11.2026 — шлюз этапа A (по итогам spike OpenCode 2)

| # | Решение |
|---|---|
| 10 | Переезжаем на OpenCode **v2.3.0**; более новые версии подтягиваем обычной синхронизацией после переезда. |
| 11 | В обычном разговоре агент **сам** включает доступ к Loginom, как в 0.4. Риск, что чужой текст подтолкнёт агента, принят. Остальные защиты сохраняются: навыки сообщества не загружаются при открытом доступе к Loginom, решения из Hub не дают доступа. |
| 12 | Терминал (shell) агенту по умолчанию **выключен**; пользователь или администратор может включить, каждая команда — с подтверждением. В закрытом контуре выключен политикой. |

## Предложения итерации 1 (исходные формулировки)

| # | Вопрос | Предложение в прототипе |
|---|---|---|
| И1-1 | Название раздела каталога в меню | «Решения» (страница — «Решения · Loginom Hub») |
| И1-2 | Подписи уровней доверия | «Loginom» · «Проверено Loginom» · «Сообщество» |
| И1-3 | Набор действий над пакетом | Документировать · Проверить · Улучшить · Сравнить; «Проверка на эталоне» и «Перенос SQL» — в «Решениях» |
| И1-4 | Где «Создать решение» | Кнопка «Создать своё» в «Решениях», не пункт меню |
| И1-5 | Строка состояния | Убрана; подключение — карточкой внизу боковой панели |
| И1-6 | Решения сообщества без проверки | Ставятся только после явной отметки «Понимаю…»; в закрытом контуре запрещены |
| И1-7 | Как выбирать пакет, когда их десятки | Одно окно: поиск, «Недавние» (история приложения), одна папка Loginom — подпапки, затем пакеты, новые сверху, с датой и размером; поиск по вложенным папкам — отдельной кнопкой; для «Документировать» — ещё файл с компьютера. Альтернатива — общий список всех пакетов: требует обходить всё хранилище при каждом открытии |

## Ждут решения (итерация 1.1, страница «Что решить» на demo)

| # | Вопрос | Предложение в прототипе |
|---|---|---|
| И1.1-1 | Названия (вместо И1-1) | Раздел «Каталог»; типы по тому, что с ними делают: Действие, Навык, Пакет Loginom, Подключение. Альтернативы: «Расширения» / «Возможности»; «Инструмент · Знания · Готовый сценарий · Интеграция» |
| И1.1-2 | Новые действия (вместо И1-3) | Приходят с обновлениями и из каталога; на главной до четырёх по выбору пользователя, остальные в «Все действия»; от сообщества — только «Проверено Loginom» и только как настройка встроенного действия |
| И1.1-3 | Выбор пакета и Loginom (к И1-7) | Работает через внутренний метод веб-клиента Loginom и фоновую сессию приложения. Вопросы: закрепить метод у разработчиков Loginom? занимает ли сессия лицензию? |
| И1.1-4 | Тексты для сообщества (к И1-6) | См. ux-spec, «Каталог»: тексты уровней доверия, отметка «Понимаю, что Loginom это не проверял, и сам проверю результат» |
| И1.1-5 | Состояние (к И1-5) | Строки нет: карточка «Loginom · модель», «Выполняется действие» во время запуска, режим сети вверху |
