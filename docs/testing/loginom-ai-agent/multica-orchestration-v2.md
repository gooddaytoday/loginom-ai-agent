# Оркестрация v2: параллельная обработка узлов

12.10.2026. Владелец разрешил самостоятельные внутренние технические решения и архитектуру в утверждённых критериях, публичных контрактах, правах и безопасности. Изменение этих границ, модели, merge и выпуск остаются отдельными решениями. Приоритет — время до приёмки узлов и сокращение ожидания, а не число запусков. Внедрение всему скваду и LAB-66–73, без пилота.

## Что применено

- [Канонический процесс](multica-mas.md), инструкции сквада и четырёх ролей обновлены через API. Обратное чтение подтвердило точные тексты и сохранность model/thinking/service tier, runtime, лимитов, MCP и лидерства. Центральная секция внутреннего CLI сохранена побайтно.
- У каждого узла выделяются текущая полезная работа, независимая часть и точный результат зависимости. Один автор закрепляется за конкретным исправлением; непересекающиеся компоненты можно выполнять параллельно. Приоритет общего исправления учитывает число получателей и длительность их ожидания.
- Общий PASS связывается с применимыми receiving назначениями и опубликованными кандидатами. Перед дорогим прогоном требуется адресная проверка известных дефектов и уже принятых исправлений; глобального барьера для всех узлов нет.
- Восстановление собственного процесса в разрешённых границах выполняется автономно. Первичный FAIL, UNKNOWN и доказательства сохраняются. Нет разрешения на replay, подмену ACK, обход guards или kill по одному таймеру. Production fix, recovery и приёмка узла различаются.
- AGENTS, RUNBOOK, CLI-регламент, шаблоны и активные подпланы согласованы: внутреннее решение не требует отдельного одобрения только потому, что оно затрагивает общую реализацию. Публичные контракты и критерии не расширялись.
- Во всех восьми карточках записана информационная версия v2 с проверкой отсутствия триггеров. Семь действовавших при доставке запусков получили operator supplement, каждый с exact target, readback и проверенным повтором той же receipt. Дополнительные информационные запуски не создавались.
- Регистратуре назначен один содержательный проход по всем восьми карточкам: сверить текущие состояния и зависимости, обновить checkpoints, снять устаревшие owner-waits, передать только отсутствующую полезную работу. Комментарий `01a12d8e-6400-7836-978a-e39d071289a4`, run `01a12d8e-640c-75df-98d9-8053d2195c47`.

## Ограничение сервера и исправленная доставка

Проверка исходников Multica выявила существенную границу: targeted supplements защищены `RequireHumanActor`; comment steer применяется только к actorType member. Отсутствующий CLI-флаг нельзя считать единственной причиной. Права агентам не расширялись, токен владельца не передавался.

[Обвязка](../../../scripts/multica/README.md) использует два разных пути:

| Отправитель | Доставка | Подтверждение |
|---|---|---|
| Агент | `update.py`: информационный @all через существующие comments API; без agent/squad mentions и нового run | Preview без получателей, точный readback, приватная receipt; получатель читает delta на безопасной границе |
| Оператор | `supplement.py`: существующий endpoint конкретного run | Стабильный client_request_id, exact target, readback; нет fallback на новый run |

Запись сообщения не равна его прочтению. Агентская доставка требует чтения delta после содержательного этапа, перед дорогим прогоном, передачей и завершением. Таймерный polling и новая очередь не вводились. При неизвестном исходе отправки `update.py` сначала сверяет запись и не повторяет POST вслепую; при завершении получателя отправитель пересматривает необходимость следующего поручения.

### Проверка агентской доставки и обнаруженная граница

Ловец передал реальное Import уточнение через agent token: комментарий `01a12d90-e80a-7d17-a296-4d2b0ca48b24`, author_type=agent, @all/Delivery-ID; связанного нового task-run нет. Регистратура аналогично доставила resource delta LAB-72, `01a12d94-2800-7569-9c45-456e19116ddc`, receipt recorded/pull_at_safe_boundary.

Первая доставка Регистратуры в собственную LAB-68 была отклонена: comment-triggered задача должна отвечать под допустимым trigger. Обвязка сохранила непринятую receipt и не повторила POST вслепую. В текущем `cc5cf6fce` parent автоматически берётся из текущего MULTICA_TASK_ID при совпадении карточки; в чужой карточке чужой trigger не заимствуется. Для отсутствующего контекста есть явный --parent. HTTP-статус выводится без тела/секретов. Добавлены два адресных теста; новый pin доставлен всем восьми карточкам и текущей Регистратуре без новых запусков. Первоначальный отказ не скрыт. Проверка нового собственного reply пути на сервере не подменяется успешной межкарточной доставкой.
