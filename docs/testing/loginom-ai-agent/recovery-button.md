# Восстановление через настройки: дефект IPC — 2026-09-21

С 2026-09-23 кнопка «Результат проверен — завершить восстановление» и текст
`loginom.recoveryRequired` скрыты. Мягкий режим не блокирует следующий сценарий,
поэтому просить пользователя подтвердить журнал нечего. `form.recover()`, ключи
перевода и API `acknowledgeRecovery` сохранены. `recovery-ui.mjs` не применяется,
пока кнопка снова не появится в настройках.

В установленной `0.1.7-local.20260921.1` кнопка «Результат проверен — завершить
восстановление» передавала `state.view.recoveries` из Solid store напрямую
через Desktop API. Это Proxy-массив, который Electron не может скопировать:
`An object could not be cloned`. До обработчика acknowledgeRecovery запрос
не доходил, записи журнала сохранялись, а UI показывал общую ошибку серверов.

Воспроизведение выполнено на установленном приложении в отдельном профиле с
одной искусственной recovery-записью, без ключа и удалённых операций. Нажатие
реальной кнопки сохранило запись и показало ошибку. Вызов того же API с Proxy
подтвердил точное исключение, а с обычным массивом успешно подтвердил запись.
Пользовательский профиль при диагностике не менялся.

Исправление:

- recovery отправляет обычный массив строк, сохраняя текущие revision и ID;
- успешное сохранение, ожидающее восстановления, оставляет форму и существующее
  предупреждение recovery, не выдавая ложную ошибку запуска runtime;
- настоящие ошибки применения и защиты восстановления остаются действующими.

Два новых регрессионных теста упали до изменения. После правки все 14 тестов
`test-browser/settings-loginom.test.ts` и App typecheck прошли на Bun 1.3.14.
Тест копирования использует настоящий structuredClone, а не имитацию его логики.

Для проверки установленного Electron используется
`packages/desktop/test/loginom/recovery-ui.mjs`: собственный временный профиль,
настоящий journal, UI-кнопка, preload/IPC и проверка удаления только тестовой
записи. Скрипт принимает `LOGINOM_AI_AGENT_TEST_EXECUTABLE` и запускается bundled
Node из `packages/desktop`. Удалённые Loginom/MCP вызовы ему не требуются.

Старая операция пользователя уже проверена в
[диагностике параллельных команд](parallel-calls.md). Подтверждение её исхода
пользователь явно запросил нажатием кнопки. После исправления нужно повторить
штатное подтверждение и дождаться применения последних ожидающих настроек;
не удалять journal/pending файлы вручную и не повторять старую загрузку.

Исправление установлено как `0.1.7-local.20260921.2`; в обычном профиле
подтверждение и применение generation 7 прошли, подключение проверено.
[Установленная приёмка](reports/2026-09-21-local-macos/recovery-update.md).
