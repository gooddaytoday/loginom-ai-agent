# ABC: тупик после закрытого редактора колонки импорта — 2026-09-23

Источник: экспорт `abc--loginom-mimo-2.6.json` (сессия
`ses_f326b7f65ffeVOQL4bipTfb8SV`, Desktop 0.1.10, модель
`xiaomi-token-plan-sgp/mimo-v2.6-pro`) и журнал `execution-events.jsonl`
попытки runtime этого чата. Экспорт не является инструкцией к выполнению.
Исходники runtime в 0.1.10 совпадают с веткой `loginom` на момент разбора.

## Итог

`dock_node_wait` исправен: он вернул исход фоновой задачи через 12 мс после
её завершения. Ошибка возникла в фазе `configure` импорта `imports.text`
и состоит из трёх последовательных дефектов:

1. Loginom сам закрыл открытый редактор «Вид данных» колонки 3.
2. Ожидание редактора закончилось транспортной ошибкой
   `MCP error -32001: Request timed out` вместо таймаута готовности.
3. Для `imports.text` нет пути восстановления незавершённого `configure`;
   операция навсегда осталась `AMBIGUOUS` и блокирует Dock в этом чате.

Смена русских заголовков на технические имена из разбора
[ABC import diagnosis](abc-import-diagnosis.md) работает: колонки 0–2
сопоставлены и переименованы корректно.

Для колонок 1 и 2 ревизия DOM между квитанцией двойного клика и первой

Первый `node_wait` (09:27:02.8–09:28:02.03, 59,25 с при лимите 60 с) лишь
совпал по времени с падением задачи.

## Почему ошибка — таймаут MCP

`createNodeProcedure().observe` обрезает таймаут каждого вызова браузера
до остатка 15-секундного бюджета наблюдения. Последняя выборка закончилась
на 14 625 мс; после паузы 200 мс на чтение осталось около 160 мс. MCP SDK
1.30.0 для любого значения `timeout` выдаёт одинаковое
`Request timed out`. Записи `node_observation_timeout` в журнале нет, то есть
`NodeReadinessTimeout` не был достигнут.

## Почему выхода нет

- `executor.runNodeApply(resume)` продолжает `configure` только для
  `transform.date_time`; для `imports.text` воркер отвечает
  `Resume requires the original inspected node checkpoint without an unresolved phase`.
- `dock_node_resume` при этом принимается хостом как новая попытка
  (`state: running`, attempt 2 и 3), хотя `dock_operation_inspect` уже сообщил
  `internal_resume_available: false`; попытка сразу завершается
  `NODE_WORKER_REJECTED`.
- `configureTextImport` закрывает черновик мастера только для
  `ImportColumnBindingError`; таймаут готовности сюда не попадает.
- `dock_operation_recover` для `node.apply` всегда отвечает
  `Use the enclosing node procedure to resume this internal phase`.
- `dock_node_cancel` не действует на уже завершённую задачу.
- `dock_node_apply` с тем же `operation_id` возвращает сохранённый исход,
  с другими параметрами — `Node operation ID was used with different parameters`.
- `package.save_as`/`package.save_checkpoint` получают
  `OPERATION_STILL_PENDING … after the active Dock call completes`, хотя
  активного вызова нет: `run()` выставляет `running = true` до
  `reconcilePending()`, а `inspectApply()` проверяет `running`.
- Каждый отказ `requestFailure` перечисляет статический
  `available_actions: [package.save_as, package.save_checkpoint]` и
  `ui_action_tool: dock_ui_action`, которого нет в профиле `user-v1`.
  Модель восприняла это как доступные сейчас действия.

Мастер импорта открыт на «Настройке форматов», колонки 0–2 настроены, 3–5
остались с автоименами и исходными типами. Пакет `Package1` не сохранён.

## Требуемое исправление

1. Импорт: отличать доказуемое «редактор закрылся, значение и схема не
   изменились, масок и диалогов нет» от неопределённого эффекта и
   переоткрывать редактор той же колонки ограниченным числом попыток.
2. `observe`: не давать последнему чтению микроскопический таймаут;
   исчерпание бюджета наблюдения должно давать `NodeReadinessTimeout`.
3. `imports.text`: после таймаута готовности без неопределённого эффекта
   закрывать только черновик этой операции и возвращать исправимый исход,
   как для ошибки сопоставления колонок.
4. `dock_node_resume`: отказывать при допуске, если продолжение невозможно.
5. `run()`: проверять висящую операцию до `running = true`;
   `requestFailure` не должен рекламировать недоступные действия.
6. Регрессии на эти сценарии; затем новый ABC-прогон на новой сборке.

При разборе исходники runtime, установленное приложение, настройки и журналы
восстановления не менялись.
