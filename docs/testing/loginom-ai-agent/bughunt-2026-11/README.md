# Охота на баги 0.4.x: живые сценарии Loginom AI Agent

Свой набор кейсов, отдельный от `evals/`. Каждый кейс проверяет одну
пользовательскую просьбу: построить сценарий с нуля, поправить существующий,
добавить узел, импортировать файл определённого формата и размера, REST,
JavaScript, Python. Вердикт детерминированный: штатные проверки
`run-check` (CSV против oracle, Save, cold, cleanup, refusal/execution_error)
и бюджет действий `bughunt-audit.py` по `case.json → budget`.

## Кейс

`cases/bh-<id>/`:

- `task.md` — просьба пользователя, без названий инструментов и ожидаемых значений;
- `data/` — входы любого формата (все прикладываются на первом ходе); файлы больше 1 МБ не коммитятся, их пишет `gen.py`;
- `gen.py` (необязательно) — `gen.py --out <data>`, детерминированная генерация больших или бинарных входов;
- `expected.json` — `nodes`, `outputs` или `refusal`/`execution_error`, формат `run-check --cases`;
- `oracle.py` — независимый расчёт `expected.json` из входов;
- `case.json` (необязательно) — `base`, `input_files`, `budget`, `notes` (см. `scripts/node-acceptance/run-check.md`).

Имена кейсов — без слов python и javascript (охрана кодовых имён UI).

## Запуск

```sh
python3 docs/testing/loginom-ai-agent/bughunt-2026-11/prepare.py --out ~/bh-cases bh-a01 bh-a02
RUN_CHECK_MODEL=opencode-go/deepseek-v4.1-flash RUN_CHECK_AUTH=~/.config/loginom-run-check/auth-opencode-go.json \
  python3 scripts/node-acceptance/run-check.py start --head <SHA> --cases ~/bh-cases --scenarios bh-a01,bh-a02 --pair <пара> --cold
python3 scripts/node-acceptance/run-check.py wait <каталог> --timeout 5400
```

## Пакет C

`bh-c02`–`bh-c05` независимо продолжают `bh-c01`: раннер сначала выполняет
базу в том же чате, затем один ход изменения. Это не цепочка c01→c02→c03→c04.
Бюджет относится только к ходу изменения, базовые вызовы считаются отдельно.
В c01 контрольный `CheckedRevenue` запрошен специально: c05 должен удалить
реальный существующий узел без изменения смысла суммирования исходного Revenue.

Ожидания вычислены стандартной библиотекой из CSV через `Decimal` и `statistics`,
без Loginom и ответов модели. Для c06/c07 `seed.csv` находится вне `data/`,
поэтому остаётся приватным входом oracle. Приложенные LGP самодостаточны:
не требуют файлов из чужого серверного хранилища. Их детерминированно пересобирает
`python3 cases/generate-c-packages.py` из нативных шаблонов репозитория.
Фикстуры меньше 1 МиБ; все входы передаются на первом ходе.

```sh
python3 prepare.py --out ~/bh-cases-c bh-c01 bh-c02 bh-c03 bh-c04 bh-c05 bh-c06 bh-c07 bh-c08 bh-c09 bh-c10 bh-c11 bh-c12
python3 cases/bh-c12/prepare-upload.py --out ~/bh-c-upload
```

Для c12 нужен штатный `run-check.py start --case-root ~/bh-c-upload --scenarios bh-c12`:
на исходной версии раннера `--cases` допускает только `base/input_files/budget/notes`,
не передаёт `upload_only` и дописывает Save/CSV. Адаптер создаёт локальный
`source_path/attachment/upload_only` без изменения общего раннера. Остальные
флаги запуска и модель те же; ожидаемые CSV/cold для загрузки неприменимы.

Штатные проверки сверяют CSV, типы, Save и cold. Они не доказывают сохранение
GUID/связей, число подмоделей, привязку переменной или доставку дополнительного
Excel. Эти требования необходимо отдельно подтвердить журналом; при отсутствии
доказательства итог не считается полным PASS. `audit-c.py` считает терминальные
`tool_use` в `model.stdout`, ошибки, точные повторы, восстановления, запросы
создания/удаления и прочие инструменты. Он работает только с законченными
прогонами; отчёт с локальными путями хранится вне Git. Идентичный повтор сам
по себе не доказывает лишнее действие: повторные `operation_wait` допустимы.
