# Охота на баги 0.4.x: живые сценарии Loginom AI Agent

Свой набор кейсов, отдельный от `evals/`. Каждый кейс проверяет одну
пользовательскую просьбу: построить сценарий с нуля, поправить существующий,
добавить узел, импортировать файл определённого формата и размера, REST,
JavaScript, Python. Вердикт детерминированный: штатные проверки
`run-check` (CSV против oracle, Save, cold, cleanup, refusal/execution_error)
и бюджет действий `bughunt-audit.py` по `case.json → budget`.

## Кейс

`cases/bh-<id>/`:

- `task.md` — просьба пользователя, без названий инструментов и ожидаемых значений;
- `data/` — входы любого формата (все прикладываются на первом ходе); файлы больше 1 МБ не коммитятся, их пишет `gen.py`;
- `gen.py` (необязательно) — `gen.py --out <data>`, детерминированная генерация больших или бинарных входов;
- `expected.json` — `nodes`, `outputs` или `refusal`/`execution_error`, формат `run-check --cases`;
- `oracle.py` — независимый расчёт `expected.json` из входов;
- `case.json` (необязательно) — `base`, `input_files`, `budget`, `notes` (см. `scripts/node-acceptance/run-check.md`).

Имена кейсов — без слов python и javascript (охрана кодовых имён UI).

## Запуск

```sh
python3 docs/testing/loginom-ai-agent/bughunt-2026-11/prepare.py --out ~/bh-cases bh-a01 bh-a02
RUN_CHECK_MODEL=opencode-go/deepseek-v4.1-flash RUN_CHECK_AUTH=~/.config/loginom-run-check/auth-opencode-go.json \
  python3 scripts/node-acceptance/run-check.py start --head <SHA> --cases ~/bh-cases --scenarios bh-a01,bh-a02 --pair <пара> --cold
python3 scripts/node-acceptance/run-check.py wait <каталог> --timeout 5400
python3 scripts/node-acceptance/bughunt-audit.py <каталог> --cases ~/bh-cases
```

`bughunt-audit.py` (Python 3.9+, стандартная библиотека) выводит Markdown;
`--json` включает машинный отчёт. Код выхода: 0 — бюджет соблюдён (либо
не задан), 1 — `ACTION_BUDGET_EXCEEDED`, 2 — ошибка входа. Каждый этап,
включая `base` продолжения, использует бюджет своего `case.json`.
`max_nodes` ограничивает число созданных узлов, без вычитания удалённых;
отказ без квитанции узла не считается созданием. Повторы — лишние вызовы
с тем же инструментом и каноническим JSON входа; обновления одного call ID
считаются одним вызовом. `forbid` ищется с учётом регистра в полном входе
чужих инструментов и путях из квитанций доставки, до сокращения вывода.
Ошибки сессии приводятся отдельно от ошибок инструментов. Повреждённый или
пустой журнал отклоняется с кодом 2; инструмент не устанавливает итог PASS
самого сценария — это результат `run-check`.

## Пакет C

`bh-c02`–`bh-c05` независимо продолжают `bh-c01`: раннер сначала выполняет
базу в том же чате, затем один ход изменения. Это не цепочка c01→c02→c03→c04.
Бюджет относится только к ходу изменения, базовые вызовы считаются отдельно.
В c01 контрольный `CheckedRevenue` запрошен специально: c05 должен удалить
реальный существующий узел без изменения смысла суммирования исходного Revenue.

Ожидания вычислены стандартной библиотекой из CSV через `Decimal` и `statistics`,
без Loginom и ответов модели. Для c06/c07 `seed.csv` находится вне `data/`,
поэтому остаётся приватным входом oracle. Приложенные LGP самодостаточны:
не требуют файлов из чужого серверного хранилища. Их детерминированно пересобирает
`python3 cases/generate-c-packages.py` из нативных шаблонов репозитория.
Фикстуры меньше 1 МиБ; все входы передаются на первом ходе.

```sh
python3 prepare.py --out ~/bh-cases-c bh-c01 bh-c02 bh-c03 bh-c04 bh-c05 bh-c06 bh-c07 bh-c08 bh-c09 bh-c10 bh-c11 bh-c12
python3 cases/bh-c12/prepare-upload.py --out ~/bh-c-upload
```

Для c12 нужен штатный `run-check.py start --case-root ~/bh-c-upload --scenarios bh-c12`:
на исходной версии раннера `--cases` допускает только `base/input_files/budget/notes`,
не передаёт `upload_only` и дописывает Save/CSV. Адаптер создаёт локальный
`source_path/attachment/upload_only` без изменения общего раннера. Остальные
флаги запуска и модель те же; ожидаемые CSV/cold для загрузки неприменимы.

Штатные проверки сверяют CSV, типы, Save и cold. Они не доказывают сохранение
GUID/связей, число подмоделей, привязку переменной или доставку дополнительного
Excel. Эти требования необходимо отдельно подтвердить журналом; при отсутствии
доказательства итог не считается полным PASS. `audit-c.py` считает терминальные
`tool_use` в `model.stdout`, ошибки, точные повторы, восстановления, запросы
создания/удаления и прочие инструменты. Он работает только с законченными
прогонами; отчёт с локальными путями хранится вне Git. Идентичный повтор сам
по себе не доказывает лишнее действие: повторные `operation_wait` допустимы.

Файл вне workspace модели ещё не означает изоляцию: CLI запускается с доступом
к файловой системе и может прочитать соседний каталог прогона. Аудитор помечает
запросы к `expected*.json`/`oracle.py` как `CONTAMINATED`; полный результат такого
хода нельзя использовать как независимую приёмку. Отказ инструмента, записанный
до первого такого обращения, остаётся отдельным наблюдением с точной строкой.
Обращения к файлам авторизации отмечаются отдельно; сырые журналы и профили
не публикуются в Git или вложениями. Исправление изоляции раннера в пакет C
не входит.

Пакет B воспроизводится `python3 build-b.py` из этого каталога; генератор
пересоздаёт только свои 12 кейсов. Каждый `oracle.py` автономен, использует

`prepare.py` передаёт модели только задание и `data/`, не oracle и ожидания.
Все входы меньше 1 МБ, внешние HTTP-запросы выполняются сервером Loginom.

Если в раннере отсутствует `scripts/node-acceptance/bughunt-audit.py`, для B

проверки нативных receipts/графа; один CSV этого не доказывает.

Ограничения oracle: bh-b03 использует документированный ErrorCode=6 и
описание HTTP из стандартной библиотеки; отличия точного нативного текста
сначала классифицируются как ошибка проверки. В bh-b06 `Timeout` —
предварительная подстрока: REST может вернуть ошибку в строке дополнительного
выхода без ошибки узла; такой результат нельзя автоматически считать дефектом
продукта. В bh-b12 подстрока «огранич» проверяет объяснение; наличие явного
отказа и отсутствие обхода дополнительно проверяются по журналу.

Аудит считает ошибкой только текущий верхний `error`, а не исторический отказ,
вложенный в успешный inspect/recovery. Создания связываются с последующими
settled receipts по operation_id; неуспешный Python с подтверждённым node_id
тоже считается созданным узлом. `max_nodes` по таким receipts — нижняя граница:
ручное создание через браузер требует отдельной сверки графа.

## Пакет A: воспроизведение и границы проверки

Все данные искусственные. Небольшие Excel-книги хранятся готовыми бинарными
фикстурами: изолированный `prepare.py` не требует сторонних библиотек.
Для независимого чтения XLSX в oracle требуется `openpyxl`; остальные oracle
используют стандартную библиотеку. Генераторы больших CSV детерминированы.
Ни один файл больше 1 MiB не хранится в Git. Все входы прикладываются первым ходом.

До первого прогона подготовить входы и пересчитать ожидания из байтов:

```sh
suite=docs/testing/loginom-ai-agent/bughunt-2026-11
python3 "$suite/prepare.py" --out "$HOME/bh-cases-a"
for source in "$suite"/cases/bh-a*; do
  name=${source##*/}
  python3 "$source/oracle.py" --data "$HOME/bh-cases-a/$name/data" > "$source/expected.json"
  cp "$source/expected.json" "$HOME/bh-cases-a/$name/expected.json"
done
```

`expected.json` проверяет имена, native-типы, строки, порядок полей и строк.
`nodes` задаёт обязательные импорты; `case.json` отдельно ограничивает действия.
Число узлов в `notes` — минимальный граф с упорядоченным результатом и CSV-экспортом,
максимум допускает небольшую реализационную вариативность. Для семи файлов
разрешён и один нативный список источников, и семь импортов с объединением;
аудит отдельно проверяет лишние повторные импорты.

Если в раннере отсутствует `bughunt-audit.py`, локальный `audit-a.py` читает
завершённый `model.stdout` и `case.json`: число Loginom/прочих вызовов, коды
отказов, одинаковые повторы, recovery, создание/удаление узлов и нарушения бюджета.
Сырые результаты аудита хранятся только вне репозитория: аргументы инструментов
могут содержать приватные пути. Итоговый граф следует сверять с журналом отдельно.

```sh
python3 "$suite/audit-a.py" <run>/model.stdout "$suite/cases/bh-a01/case.json"
```

LGD использует неизменённый маленький fixture `imports-lgd/fixtures/source.lgd`.
Oracle проверяет его SHA256 и считает по независимому исходному CSV-spec,
который лежит вне `data/` и не попадает модели. Штатный `--cases` проверяет
наличие `exports.lgd` и итоговый CSV; бинарное содержимое дополнительного LGD
требует отдельной проверки. Для отказа a09 подстрока `64` фиксирует объявленный
предел; качество объяснения и запрос области дополнительно проверяются вручную.

Вещественные поля проверяются с abs=1e-8 / rel=1e-10: это допускает погрешность binary64, сохраняя проверку денежных долей. Сортировка ключей может выполняться самой Группировкой (`sort_result`), отдельный узел не обязателен. Простой `bash ls` учитывается как сторонний вызов, но не считается конверсией. Точное совпадение подстроки отказа может дать ложный FAIL при честной формулировке; такой результат классифицируется как ошибка проверки.
