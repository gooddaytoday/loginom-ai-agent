# Приёмка Loginom AI Agent на отдельных машинах

Статус на 2026-09-16: **план проверок, а не отчёт об успешном выполнении**. Нативную отладку Windows и macOS выполняют отдельные агенты на соответствующих машинах. Здесь определены входные материалы, порядок проверки и формат доказательств. Эти документы не разрешают публикацию релиза или изменение рабочего сервера Loginom.

Согласованное поведение описано в [спецификации](../../superpowers/specs/2026-09-16-loginom-ai-agent-desktop-design.md), этапы работ — в [плане реализации](../../superpowers/plans/2026-09-16-loginom-ai-agent.md). Инструкции платформ: [Windows](windows.md), [macOS](macos.md). Результат каждого запуска оформляется по [шаблону отчёта](report-template.md).

## Границы приёмки

| Платформа | Целевой пакет | Где проверяется |
| --- | --- | --- |
| Windows 11+ x64 | EXE, NSIS | Нативная Windows; агент на другой машине |
| macOS 14+ Apple Silicon arm64 | DMG | Нативный Mac; агент на другой машине |
| Ubuntu 22.04+ / Debian 12+ x64 | DEB; дополнительно AppImage | Отдельная Linux-приёмка: контейнеры и текущий desktop |

Нативный тест должен использовать установленный пакет. Запуск renderer в браузере, development mode, Wine, Rosetta или успешная сборка на другой ОС не заменяют этот результат. Linux-контейнеры подтверждают только явно пройденные проверки Linux.

Первая версия использует существующий desktop backend v1. В текущем коде выбор задаётся в `packages/desktop/src/main/index.ts`: v2 включается только переменной `OPENCODE_SIDECAR_V2=1`. Для приёмки этой версии переключение на v2 не допускается; интеграция MCP для v2 не входит в поставку. После ребрендинга проверяется фактический backend и новая карта переменных из manifest, а не сохранение старого имени переменной.

## Что передать агенту до начала

Ответственный за сборку передаёт следующие материалы через согласованный канал. Придумывать недостающие пути, ключи или команды не нужно.

1. Целевой EXE/DMG и release manifest с полями ниже. SHA256 проверяется до установки.
2. Исходники по точному commit и, если сборка не из чистого дерева, patch и перечень untracked build inputs. Для исправлений — рабочая ветка и инструкции проекта из того же commit.
3. Разрешённый тестовый Loginom, API endpoint сервера знаний, действительные учётные данные, права на создание тестового пакета и загрузку файлов. Секреты передаются отдельно, не в manifest или отчёте.
4. Провайдер и модель для сквозного теста; их подключение выполняется через существующие настройки моделей. Отсутствие провайдера не блокирует проверки установки и формы.
5. Два установщика соседних версий и собственный тестовый канал обновлений для проверки обновления. Для одной версии тест обновления имеет статус `BLOCKED`.
6. Для release-приёмки — ожидаемые издатель/Team ID, требования к подписи и доверенный способ получения пакета. Отладочный неподписанный пакет не считается проверкой выпуска.

При отсутствии пакета или manifest вся **нативная приёмка = BLOCKED**. Анализ исходников и подготовку build environment можно продолжить. При недоступном сервере/LLM блокируются только зависимые сценарии; автономные проверки выполняются дальше.

### Release manifest: обязательный контракт передачи

Manifest — JSON с версией схемы и отдельным SHA256, по контракту [плана сборки R2](../../superpowers/plans/2026-09-16-loginom-release.md). Его целевой путь: `artifacts/loginom-ai-agent/<version>/<platform>-<arch>/release-manifest.json`. Это требование к будущему результату сборки; команды его генерации сначала реализуются по плану.

| Поле | Содержание |
| --- | --- |
| Идентичность | Версия, канал, UTC сборки, git commit, чистота дерева, hash patch при изменениях; commit/архив источника перенесённого Dock |
| Цель | ОС, минимальная версия ОС, архитектура, backend `v1`, build host |
| Артефакты | Точное имя, размер, SHA256 EXE/DMG и файлов обновления; ссылка на источник |
| Runtime | Electron и его Node, отдельный Node исполнителя если используется, Playwright, Chromium version/revision; версии нативных модулей |
| Состав | Относительные пути исполнителя, runtime и Chromium внутри установленного приложения; архитектура каждого бинарного файла |
| Имена и пути | Product name, app ID, executable, URI scheme, config/data/cache/state/log/browser-profile paths, имя OS protected secret store; для Linux путь `connection.json` |
| Настройки | Версия схемы, endpoint сервера знаний, значения по умолчанию, способ посмотреть номер активной/ожидающей generation без секретов |
| Обновление | Собственный feed/channel, предыдущая/следующая версия, имя и hash metadata, ожидаемая подпись, политика хранения пользовательских данных при удалении |
| Диагностика | Как экспортировать очищенные логи; где искать operation ID/receipt и chat ID; команды доступных проверок из данного commit |
| Происхождение | Лицензии Electron/Node/Chromium и перенесённого кода, указатель на migration archive; без секретов и серверных данных |

## Сквозной тест и эталон данных

Каждый прогон получает уникальный `run-id`. Используются отдельные тестовые пакеты и файлы; чужие пакеты не изменяются. Корень Loginom вычисляется как `/<username>` без отдельного поля и без предварительной проверки его существования. Дальнейшая фактическая загрузка/сохранение может завершиться ошибкой прав или пути — это ошибка операции с понятной диагностикой.

Создать локальный файл `sales.csv` в UTF-8:

```csv
Product,Quantity,Price
Alpha,2,10
Alpha,1,15
Beta,3,4
Beta,1,8
```

В новом чате попросить загрузить файл в Loginom, импортировать его, вычислить `Revenue = Quantity * Price`, сгруппировать по `Product` с суммой `Revenue`, отсортировать по `Product`, выполнить сценарий и сохранить пакет под уникальным именем. Затем закрыть и открыть сохранённый пакет и проверить результат повторно.

Эталон: импорт содержит 4 строки; рассчитанные значения — `20, 15, 12, 8`; группировка — `Alpha: 35`, `Beta: 20`; итоговая сумма — `55`. Доказательства: receipt/operation ID, структура узлов и связей, фактическая выходная таблица, место сохранения и повторное открытие. Одного ответа модели «готово» недостаточно.

Для второго чата создать другой файл с тем же именем `sales.csv` в другой локальной папке:

```csv
Product,Quantity,Price
Alpha,1,100
Beta,1,1
```

Его результат: `Alpha: 100`, `Beta: 1`, сумма `101`. Выполнить обе задачи параллельно, в отдельных пакетах. Не должно быть подмены вложений, cookie/profile между чатами, результатов или receipt. Пути вложений внутри одного пользовательского корня должны различаться по задаче/чату.

## Обязательные сценарии

Для каждого ID сохранить статус, фактический результат и ссылку на доказательство. `PASS` ставится только после выполнения всех шагов строки.

| ID | Действия | Ожидаемый результат |
| --- | --- | --- |
| PKG-01 | На чистой машине установить пакет без Node, Bun, Python, npm и отдельно установленного Chrome/Chromium; отключить сеть для первого открытия | Открывается мастер. Приложение не требует установки runtime и не скачивает Chromium. Отсутствие связи с сервисом обозначено отдельно |
| PKG-02 | Вернуть доступ к тестовым сервисам; запустить Loginom | Node/исполнитель и Chromium запускаются из путей manifest; системный Edge/Safari не используется вместо комплектного Chromium |
| UI-01 | Первый запуск в чистом профиле | Четыре поля: API-ключ Dock; URL `http://logi-test-plan.bg.local/app/`; имя `user`; пустой пароль **без placeholder**. Нет шага выбора LLM и поля папки |
| UI-02 | Открыть «Loginom» из боковой панели и из настроек; изменить поля | Одна и та же форма, заметный вход, одинаковые сохранённые значения/статусы. Пароль не появляется в форме открытым текстом и не подставляется placeholder |
| CON-01 | Проверить корректные параметры и сохранить | Отдельно подтверждаются доступ к серверу знаний и вход в Loginom; состояние подключения воспроизводится после перезапуска |
| CON-02 | Использовать разрешённую трассировку запросов либо изолированную fixture, где файловый сервис недоступен, а вход работает | Проверка подключения **не вызывает** listing/stat/create/probe папки `/<username>` и не блокируется её состоянием. Рабочий сервер не изменяется; при отсутствии доказательства эта проверка не считается пройденной |
| CON-03 | В работающем подключении по очереди указать неверный ключ, URL, пароль | Ошибка различает сервис знаний, сеть и Loginom auth. Действующая generation, конфигурация и подключение остаются прежними |
| CON-04 | Проверить операции «оставить текущий пароль», «заменить», «вход без пароля» | Повторный запуск сохраняет выбранный вариант; пустое поле редактирования само не стирает сохранённый пароль. Вход без пароля успешен для учётной записи, которой он разрешён |
| CON-05 | Изменить username на вторую разрешённую тестовую учётную запись | Корень для будущих файлов — `/<новое имя>`; создаётся новая browser auth session; старые cookie не используются. Отдельной проверки папки нет |
| CON-06 | Во время двух активных задач Loginom сохранить другой действительный набор параметров | Видно «ожидает применения». Обе задачи завершаются на старой generation, без отмены. Замена атомарна только после всех активных Loginom drains; новая задача не пересекает переключение |
| CON-07 | Оставить неопределённый исход изменяющей операции, затем попытаться сменить настройки; перезапустить приложение | Generation не переключается до разрешения неопределённости. Нет автоматического повтора операции после рестарта; статус позволяет восстановить receipt/фактический результат |
| CON-08 | В изолированном тестовом окружении после завершения drains вызвать отказ запуска нового runtime, затем отдельным прогоном — сбой между readiness и фиксацией active pointer | Старый runtime остаётся доступным до readiness нового. Отказ нового сохраняет прежнюю active generation и допуск задач, pending показывает ошибку. После сбоя восстанавливается одна целостная конфигурация без повторения неопределённых операций. Если старый runtime тоже потерян — восстановимый `BLOCKED` только Loginom, без общего перезапуска backend |
| SEC-01 | Сохранить тестовые секреты Loginom; проверить обычные config, UI API, журналы и экспорт диагностики | На Windows/macOS секреты Loginom защищены средствами ОС, обычные файлы содержат только metadata/flags. В Linux для Loginom применяется исключение: `connection.json` с plaintext и `0600`. Хранение credentials провайдеров моделей не меняется. В UI API, истории и логах секретов нет на любой ОС |
| MODEL-01 | Подключить модель через существующие настройки провайдера | Чат работает; мастер Loginom не меняет настройки провайдера и не просит дополнительный модельный ключ |
| FLOW-01 | Выполнить эталон `sales.csv`, сохранить и переоткрыть | Значения и структура соответствуют эталону выше; импорт загруженного локального файла использует `/<username>` |
| ISO-01 | Два параллельных чата с разными `sales.csv`; закрыть один чат | Результаты 55 и 101 относятся к своим чатам, процессы/браузеры изолированы, второй чат продолжает работу |
| REC-01 | На тестовой операции прервать сеть после отправки изменения; восстановить её | Исход определяется через receipt и наблюдение результата, а не слепой повтор. Нет дублирующих узлов, загрузок или сохранений |
| REC-02 | Завершить собственный процесс Chromium во время тестовой задачи; затем восстановить работу | Понятная ошибка/восстановление; чужие браузеры не затронуты; нет скрытого повтора изменений |
| LIFE-01 | Штатно закрыть и снова открыть приложение | Настройки сохранены, без лишнего мастера; нет оставленных приложением исполнителей или браузеров после штатного закрытия |
| BRAND-01 | Проверить меню, ярлыки, About, команду, config/data/log/profile paths, URI scheme и процессы | Используются имена Loginom AI Agent из manifest; нет записи в старые пространства OpenCode. Сведения об исходных проектах в лицензиях допустимы |
| UPDATE-01 | Из версии N запросить и установить N+1 из собственного тестового feed | Запросы обновления идут только в канал Loginom AI Agent; сохраняются настройки и данные; приложение не заменяется OpenCode; повторно пройти CON-01 и FLOW-01 |
| REMOVE-01 | Удалить тестовую установку и установить заново согласно политике manifest | Удалены зарегистрированные приложением компоненты; пользовательские данные обработаны по явно описанной политике. Чужие OpenCode/Dock/браузеры не удалены |
| LOG-01 | Экспортировать диагностику успеха и ошибок | Есть версии, platform/arch, стадии отказа, chat ID и operation ID; нет ключа, пароля, cookie, auth header и содержимого секретного хранилища |

REC-01/CON-07 выполняются на одноразовом тестовом пакете с управляемой сетевой точкой отказа. В отчёте фиксируется, в какой момент произошёл разрыв. Простой таймаут до отправки запроса не доказывает обработку неопределённого исхода. Для CON-08 передаётся поддерживаемый тестовой сборкой способ инъекции отказа; при его отсутствии сценарий `BLOCKED`. Повреждать рабочие runtime-файлы или отключать общий сервер для проверки не нужно.

## Статусы и классификация отказов

- `PASS`: выполнено на указанном артефакте, доказательства приложены.
- `FAIL`: наблюдаемое поведение противоречит ожиданию; есть воспроизведение и относящиеся к нему логи.
- `BLOCKED`: нет обязательного входа или зависимый сервис/стенд недоступен; указаны точная причина и условие возобновления.
- `NOT_RUN`: тест ещё не выполнялся; причиной нельзя подменять результат.
- `N/A`: только сценарий вне согласованной платформы/поставки с объяснением; не замена `BLOCKED` для отсутствующего обновления или второй учётной записи.

Класс дефекта выбирается отдельно: `packaging/native`, `desktop/UI`, `executor/session`, `knowledge-server`, `Loginom/auth`, `Loginom/data`, `model/provider`, `environment/network`, `test-data`. Сначала установить границу сбоя по стадиям: старт приложения → старт исполнителя → старт Chromium → сервер знаний → вход Loginom → фактическая операция → LLM orchestration. Например, отказ провайдера модели не считается отсутствующей DLL; ошибки DNS не доказывают неверный API-ключ.

В отчёт не включать полный dump окружения, connection config, браузерный профиль или секретное хранилище. Проверку наличия секретов делать локально без вывода значений; фиксировать лишь имя файла/канал и факт утечки. Network trace очищается до передачи. Скриншоты делаются с замаскированными ключами и закрытыми секретными полями.

## Что подтверждено исходниками на момент подготовки

Это проверка существования файлов и объявлений команд; сборки и нативные тесты здесь не запускались.

- [Desktop package](../../../packages/desktop/package.json): `bun run build`, `bun run package:win`, `bun run package:mac`, `bun typecheck`.
- [Текущая конфигурация упаковки](../../../packages/desktop/electron-builder.config.ts): NSIS, DMG/ZIP, DEB/AppImage; пока имена OpenCode и feed `anomalyco`.
- [Prebuild](../../../packages/desktop/scripts/prebuild.ts): сборка Node sidecar; в dev также загрузка существующего CLI. Это не будущая упаковка Loginom runtime.
- [Prepare](../../../packages/desktop/scripts/prepare.ts): меняет `package.json` версии; не запускать автоматически для чтения/проверки.
- [Текущий CI](../../../.github/workflows/publish.yml) и [setup-bun](../../../.github/actions/setup-bun/action.yml): Node 24, Bun из корневого `packageManager`, Windows hoisted linker; upstream release job ограничен чужим репозиторием.
- [Desktop entry](../../../packages/desktop/src/main/index.ts), [sidecar](../../../packages/desktop/src/main/sidecar.ts), [logging](../../../packages/desktop/src/main/logging.ts): точки выбора backend, старые имена путей, экспорт логов.

Все эти ссылки — отправные точки для адаптации. Наличие существующего build script не означает готовность Loginom дистрибутива или правильное включение перенесённого Dock. После реализации backend перемещается из `packages/opencode` в `packages/agent`, namespace пакетов — `@loginom-ai-agent/*`, переменные — `LOGINOM_AI_AGENT_*`. Целевые app ID: `com.loginom.aiagent`, `com.loginom.aiagent.beta`, `com.loginom.aiagent.dev`. Manifest должен отражать итоговые пути и имена проверяемой сборки.
