## 1. Состав комплекта

README каждой задачи объясняет бизнес-условия, данные, ожидаемый результат,

## 3. Oracle и эталоны

Сначала зафиксировать просьбу и CSV, затем независимый oracle, затем получить
из него `expected-demo.json` до любого прогона. Oracle читает только свои CSV,
не expected, результаты модели или Loginom. Использовать стандартную библиотеку
Python, относить пути к `__file__`; без аргумента выводить сохранённый эталон,
аргумент личного пути пакета меняет только `package_path`.

- Кластеризация: размеры групп и центры с явным `tolerance`, независимо от
  номеров кластеров. Пример исходного oracle фиксирует номера — эту особенность
  не переносить. Бизнес-просьба и выбранная форма результата должны позволять
  сравнение существующим проверяющим без новых механизмов верификации.
- Регрессия: независимый расчёт коэффициентов и прогнозов, явно заданные
  абсолютный и относительный допуски и проверка достаточного ранга данных.
- REST: только стабильные поля, не IP, дата, динамические заголовки и не полный
  сырой ответ. `label_any: true` для меток, не заданных бизнес-просьбой.
  Oracle не вызывает сеть: вычисляет ожидания из фиксированного контракта
  запроса и CSV. Доступность httpbin в будущих прогонах здесь не проверяется.

Образцы и правила: [expected](acceptance/v2/expected/README.md),
[oracle](acceptance/v2/oracle/README.md). Исходные примеры не заменяют новые задачи.

## 5. Ловушки и продолжение

Не использовать номера кластеров как идентичность групп; не подгонять oracle
под observed output. Не фиксировать случайные поля HTTP-ответа и не обещать
доступность внешнего сервиса. Не выдавать успешный разбор JSON за PASS исполнения.
Модели будущего прогона передаются только просьба и указанные входы;
README, oracle, expected и технический подплан модели не передаются.
Манки дополняет эту же ветку и PR, обновляет checkpoint карточки и сообщает
результаты статической приёмки. Новых карточек узлов эта поставка не требует.
