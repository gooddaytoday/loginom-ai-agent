### Подключение

Загрузить предоставленное приватное окружение. SSH использует подготовленный конфиг, Chromium — подготовленную клиентскую базу доверия, curl — предоставленный release CA. Для прямого запроса к каждому native Studio взять hostname и порт из URL соответствующего профиля. Достижимый адрес получить из `ssh -F "$DASHBOARD_M6_SSH_CONFIG" -G "$M6_STAND_ALIAS"` (поле `hostname`). Обычный DNS для этих Studio-имён в среде проверки недоступен.

```sh
curl --noproxy '*' --fail --silent -o /dev/null \
  --cacert "$DASHBOARD_M6_RELEASE_CA" \
  --connect-to "$M6_STUDIO_HOST:$M6_STUDIO_PORT:$M6_REACHABLE_HOST:$M6_STUDIO_PORT" \
  "$M6_STUDIO_URL"
```

Для изолированного Chromium передать `--host-resolver-rules="MAP $M6_STUDIO_HOST $M6_REACHABLE_HOST"`. Это сохраняет публичные Host, SNI и порт. Для установленного dashboard учитывать именно authority, которую discovery, оболочка и политика допустимых origin ожидают от Studio. При наличии отличающегося внешнего порта сначала сверить достижимость ожидаемой authority на опубликованном маршруте. Для Docker SSH сервер отклоняет запрос TCP forwarding, используйте существующий опубликованный маршрут.

Оба действующих native HTTPS-сертификата проверены по имени и цепочке. Каждый содержит одно DNS-имя. Для strict требуется отдельный доверенный app-домен с подходящим сертификатом.

Внешний маршрут к app-origin Docker отклоняет TCP-подключение. Внутри VM Studio и app-origin доступны с доверенным TLS, но штатный Chromium с OS sandbox останавливается с `No usable sandbox`. AppArmor ограничивает непривилегированные user namespaces, штатного setuid-помощника нет. Для проверки живых строк нужен доступ к app-origin с браузерного хоста или среда, в которой работает Chromium sandbox.

## Первая установленная CSP-проверка

1. Собрать существующей командой `bun run build:release --out "$M6_RELEASE_OUT"` из `packages/dashboard` с pinned Node и разрешённым Docker engine. Сохранить SHA256 архива вне Git до передачи. Извлечь его в приватный каталог на собственном release-стенде через `tar -xpf "$M6_RELEASE_ARCHIVE" -C "$M6_UNPACK_DIR"`. Проверьте, что у `check-release.mjs` сохранился режим 0644 для непривилегированного вызова в контейнере. Установка — штатный `containers.sh install` с верными параметрами Studio и app-origin из [рецепта M5](dashboard-m5.md). При смене `image.ref` штатный uninstall прежнего комплекта удаляет локальное состояние сборок Dashboard. Выполнять замену только на выделенном стенде, где это состояние можно восстановить из публикаций. Приватно записать исходные параметры install, выгрузить нужный stdout и снять контрольные суммы синтетических `.lgp` и JSON в UserStorage. После uninstall/install сверить сохранность этих файлов и заново дождаться ready.
2. Открыть штатную публикацию синтетического пакета под автором. Проверить trusted TLS, ожидаемые имя и sourceHash публикации, ready, живую таблицу и обычный выход. Если предыдущей публикации нет, сначала провести нормальную подтверждённую публикацию того же синтетического пакета. Для server-only smoke пригоден положительный путь из M5 с `check-release.mjs publication/request/ready` и отдельной синтетической привязкой.
3. После первого GREEN Task 1 добавить обычный inline-стиль в синтетической странице. Chromium должен блокировать стиль и сам отправить CSP POST. Проверить POST и очищенную JSON-строку `csp_violation` в stdout установленного web, а затем штатное открытие той же публикации. В отчёт включить SHA256 установленного архива, статус ответа и разрешённые поля события. Повторить затронутое поведение на финальном артефакте.

В Task 4 использовать обычные сценарии, read-only review исходников и конфигурации, а также применимые доказательства M5. Результаты исторических и текущих проверок привязаны к своим артефактам. Недоступность разрешённых входов указывать по конкретному сценарию.

## Выключатель и журналы

Сохраните журналы в приватный каталог перед остановкой release или обновлением. Команды выполняются с правами оператора соответствующей установки.

```sh
docker logs --since 15m loginom-dashboard-web > "$M6_EXPORT_DIR/web.log" 2>&1
docker logs --since 15m loginom-dashboard-publisher > "$M6_EXPORT_DIR/publisher.log" 2>&1
bash ./containers.sh stop --engine docker
bash ./containers.sh start --engine docker
```

Для rootless Podman выполняйте команды из учётной записи владельца установки. Для ротации нужен conmon с параметрами `--log-rotate` и `--log-max-files` (например, подписанный conmon 2.2.1 из Fedora 43). Установщик ограничивает `k8s-file` для каждой роли до 10 МиБ и включает две копии через launcher только своего проекта. Docker по-прежнему хранит три файла средствами `json-file`. Прежнюю Podman-установку обновите через `install --engine podman` перед проверкой или запуском новым архивом.

При установке launcher получает абсолютный путь к проверенному conmon и использует его для ручного запуска и cron. При повреждённом launcher `stop` остаётся доступен после проверок релиза и принадлежности контейнеров.

`podman logs` показывает активный файл. Чтобы выгрузить всю доступную историю, получите путь через `podman inspect --format '{{.HostConfig.LogConfig.Path}}' loginom-dashboard-web` и скопируйте в приватный каталог существующие сегменты в порядке `.2`, `.1`, активный файл. Повторите для нужных ролей. Удаление контейнеров при release stop удаляет их журналы. После stop откройте Studio штатным способом. Открытый Dashboard пользователь закрывает в браузере.

На dev master выполните `./packages/dashboard/deploy/dev-master.sh stop --config "$DASHBOARD_MASTER_CONFIG"` и `start` с тем же конфигом. Используйте конфиг выделенной установки с подтверждёнными именами и метками владельца. Команды проверяют принадлежность ролей и управляют ими по полным ID. Они сохраняют параметры установленных контейнеров, включая strict и CLI-кнопку.

Одноразовый контейнер с тем же образом и настройками журналирования записал конечный синтетический поток примерно 36 МиБ. Docker `json-file` сохранил три файла суммарным размером 28 390 528 байт. Rootless Podman `k8s-file` сохранил один файл размером 8 174 334 байта. На обоих движках первая запись вытеснена, последняя доступна через `logs`. Это исходный результат до исправления ротации.

Повтор с явными `log-rotate=true` и `max-file=3` на Podman 5.6.2 и conmon 2.1.13 дал тот же один файл. В Podman 5.6.2 эти параметры не передаются conmon. На подписанном conmon 2.2.1 без launcher результат оставался однофайловым. При передаче параметров launcher проба из 46 000 строк оставила активный и два ротированных файла размером 10 485 096, 10 485 510 и 6 425 192 байта. Самая старая сохранившаяся строка имела номер 19948, последняя — 45999. Этот опыт подтвердил механизм ротации, а проверка установленной поставки записывается отдельно.
