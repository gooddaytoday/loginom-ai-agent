# Возврат к приёмке узлов — 15.10.2026

## Решение владельца и границы

Первый рубеж — узел, построенный, настроенный и выполненный в Loginom через Loginom AI Agent по бизнес-заданию и входам, с сохранением и проверкой результата. Полная приёмка по прежнему подплану, включая матрицу, регрессии, cold-check и независимый вердикт точного кандидата, остаётся обязательной. Discovery-only назначения и принятые объёмы не расширяются.

Обычные связанные исправления Манки доводит до цельного результата; раннее независимое ревью необходимо для изменений границ безопасности до соответствующего опасного прогона. Исследование имеет необходимый вопрос и условие окончания; не нужное рабочему пути сохраняется и откладывается. Дополнительные доказательства не становятся критериями автоматически.

Канонический регламент, три роли, RUNBOOK, CLI-приёмка, шаблон и порядок подготовки подпланов согласованы. В восьми активных подпланах изменён только порядок работы, технические разделы с матрицами сохранены побайтно. Модели, лимиты, права, публичные контракты и правила простой уборки не изменяются. Продуктовый код исправляют авторы в собственных ветках; оператор не редактирует их checkout.

Отказ провайдера не объявлен ложным; отклонённые действия не возобновлять, модель не менять и защитный фильтр не обходить.

На безопасной границе завершить текущую проверку сохранённых crash-данных и отложить дальнейшее исследование старого сбоя, если оно не нужно штатному сценарию Sorting. Следующая работа Манки:

1. Проверить реальный штатный путь CLI → Sorting → Execute → Save → завершение → независимое открытие. По исходникам и сохранённым фактам отделить зависимости обычного пути от экспериментального аварийного сохранения старого черновика.
2. Для `terminal-*`, Inspector, witness и receipt определить действующее требование и наблюдаемый дефект, предотвращаемый зависимостью. Не считать имя файла или размер основанием для удаления. Подтверждённо ненужное вывести из активного пути с сохранением истории; полезные исправления оставить.
3. Не отключать проверки владения, идентичности документа, сохранения, исходного deadline, durable journal и UNKNOWN. Изменение этих границ независимо проверить до опасного прогона. Отсутствие обязательного доказательства не подменять разрешающим значением. Экспериментальную схему не достраивать ради неё самой.
4. Для старых собственных неисправных ресурсов использовать постоянное разрешение владельца: подтверждённое освобождение либо доказанная изоляция, сохранение входов/истории, защита уникальных данных. Аварийное сохранение воспроизводимого старого draft не является prerequisite нового сценария; обычное сохранение успешного результата обязательно.
5. После минимального исправления и применимых проверок опубликовать точный кандидат, выполнить первый бизнес-сценарий и вернуться к полной прежней матрице Sorting. Модели — только business task и входы. Старые UNKNOWN не повторять; новый профиль сам по себе не разрешает повтор неизвестного эффекта.

## Проверка внедрения

До публикации: `git diff --check`; технические разделы восьми подпланов и раздел уборки сравнены с исходным commit; противоречащие требования немедленного ревью каждого исправления заменены. Это проверки документации, не runtime/модельная приёмка.

Состав проекта проверяется по API целиком. Исходный снимок: LAB-66/67/69/70/71/72/73 in_progress, LAB-68 in_review; исторические done/cancelled и backlog не запускаются. Активные исправления и модельные операции сохраняются. Перед любым назначением повторно проверяются runs/retry/wakeups; после — точный текст и связь trigger_comment_id. Принятый этап LAB-68 не открывается заново; ограничение публикации его SHA остаётся отдельным фактом.

Публикация, точное чтение инструкций, реальные назначения и наблюдение естественного завершения будут зафиксированы ниже по результату. Полная приёмка Sorting не объявляется по факту обновления инструкций или запуска агента.
