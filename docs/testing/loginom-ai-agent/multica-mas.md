# Независимая обработка узлов в Multica

Процесс `independent-nodes` (14.10.2026). Одна карточка — один узел, собственная ветка и отдельный worktree. Генератор → Манки ↔ Ловец → `in_review` владельцу. Разные узлы работают параллельно; этапы одного узла последовательны. Регистратура в этом процессе не участвует.

## Работа и источники

Перед продолжением прочитать действующие инструкции сквада/роли, короткий checkpoint и подплан узла. Старые инструкции веток и комментарии не возвращают отменённую координацию. Историю читать адресно для незакрытого вопроса. Существующие обработчики, продуктовые исправления, тесты, ветки, PR и результаты сохраняются.

Генератор готовит задание, входы, постоянную пару личных аккаунтов, ветку и ближайший незавершённый этап. Готовую подготовку повторять не надо. Манки самостоятельно доводит узел, включая необходимые изменения общего кода в своей ветке. Одни и те же файлы в разных worktree можно менять параллельно без согласования между карточками. Готовый чужой коммит можно взять добровольно; ожидание чужого исправления не является обязательным этапом. Не писать в чужой checkout и не переносить всю инфраструктурную ветку без необходимости.

Ловец проверяет точный опубликованный кандидат и критерии подплана. Замечания и локальный PASS с остатком передаёт прямо Манки; полный PASS — `in_review` владельцу. Закрытые проверки повторять только при изменении затронутого поведения или новом основании. Частичный SOURCE/OFFLINE PASS не означает native/model/cold или полную приёмку. Исходные FAIL сохраняются. Готовое самостоятельное исправление передавать Ловцу сразу; после его проверки сразу продолжать доступный следующий этап, не ждать всех исправлений или других карточек. Если следующий шаг требует отсутствующего решения владельца, явно назвать это решение и продолжать доступную независимую работу; информационный итог без назначения не заменяет передачу готового этапа.

Цель сквада — принятый узел по подплану, а не отдельный инфраструктурный PASS или отчёт о блокировке. Диагностика, исправление подготовки и кода, выбор поддержанного способа восстановления собственных ресурсов и проверка результата входят в обычную работу агентов. Внутреннюю неисправность не превращать в запрос разрешения владельцу: Манки исправляет, Ловец проверяет и возвращает конкретный следующий этап. Отказ одного способа восстановления не доказывает внешний блокер; выбрать другой поддержанный безопасный путь или исправить причину в своей ветке. Не начинать отдельный инфраструктурный проект: делать минимальное необходимое для своего узла.

К владельцу обращаться только при доказанном внешнем блокере: нет необходимого доступа/права/ресурса, требуется изменение утверждённых критериев или публичного контракта либо конкретное действие за пределами разрешённого. Указать наблюдаемый факт, почему доступные безопасные пути не решают проблему, одно необходимое решение и какую независимую работу можно продолжить. До этого самостоятельно выполнить доступную диагностику и исправления. Если безопасное продолжение найдено, выполнить/назначить его сразу и проверить доставку; не оставлять карточку без следующего шага ради отчёта. Автономность не разрешает повтор UNKNOWN, воздействие на чужие ресурсы или несогласованную потерю сохраняемых результатов.

Внутренние технические решения разрешены в утверждённых критериях, публичных контрактах и правах. Изменение этих границ, моделей, Done, merge, выпуск и удаление аккаунтов — отдельная команда владельца. При последующей интеграции автор разрешает конфликты своей ветки; проверяются затронутое поведение и совместимость объединения. Слияние Git без конфликтов не доказывает совместимость.

## Штатные назначения и checkpoint

Использовать существующий API/CLI Multica с токеном текущего задания. Если установленный CLI не имеет trigger-preview или expected_revision, обращаться напрямую к тому же API через HTTP с MULTICA_SERVER_URL и MULTICA_TOKEN текущего задания; это разрешённый штатный путь, а не восстановление обвязки. Токен владельца не подставлять, секреты не печатать. Собственная обвязка из scripts/multica и её установленные копии выведены из процесса; не восстанавливать их из старых веток. Нового диспетчера, реестра артефактов или протокола квитанций не создавать.

Перед новым поручением проверить актуальный результат и существующие running/queued/wakeups этой карточки. Один следующий этап — один адресный комментарий нужной роли: действие, ветка/полный SHA, результат и необходимые пути. Перед записью штатный trigger-preview должен показать одного адресата; после — прочитать комментарий и связанный task-run. Если ответ потерян, сначала найти фактическую запись/назначение, не повторять POST вслепую. Исторический completed run не является текущей работой.

Передача выполняется через `POST /api/issues/{id}/comments/trigger-preview` с content, затем `POST /api/issues/{id}/comments` с тем же content и type=comment. После записи прочитать комментарий и `GET /api/issues/{id}/task-runs`: нужен queued/running, связанный с этим trigger_comment_id, нужной ролью и предметом. Сам текст «следующий шаг» и ответ trigger-preview не создают назначения. Ответ deferred/coalesced требует найти фактическое продолжение; при неизвестном исходе сначала сверить запись и runs, не повторять POST вслепую. Существующее подходящее назначение использовать без дубля; собственный завершающийся run не считается продолжением. Enabled wakeup допустим только для конкретного ещё не наступившего внешнего события, не вместо готового этапа.

Информационный `[@all](mention://all/all)` не запускает следующего агента. Использовать его для промежуточного сведения либо когда продолжение уже подтверждено; итог с открытой исполнимой работой должен содержать одно адресное agent mention без @all. Агентский parent_id берётся из собственного текущего trigger, не из чужого run. После передачи и штатного завершения собственных операций освободить слот: подтверждённого queued достаточно, ждать начала или результата получателя не нужно. Подтверждённый startup failure без выполнявшейся работы допускает одно адресное восстановление после проверки отсутствия successor/retry/wakeup; UNKNOWN модельной или native операции повторять нельзя.

### Условие завершения запуска

Перед финальным ответом перечитать checkpoint, последний результат, runs и wakeups. Закончить запуск можно в одном из трёх состояний:

- **Передано:** есть конкретный исполнимый остаток и проверенное назначение следующей роли. Генератор передаёт подготовку Манки, Манки готовый результат или конкретный технический вопрос Ловцу, Ловец замечания или частичный PASS с ближайшим открытым этапом Манки. Манки продолжает доступный собственный этап в текущем запуске, а не завершает его отчётом о намерениях.
- **На приёмке:** Ловец подтвердил весь подплан, перевёл карточку в in_review и передал владельцу результат. Done/merge/release отдельно.
- **Внешний блокер:** доступной независимой работы нет; указаны наблюдаемый факт, точное недостающее право/ресурс/решение, адресат и условие возобновления; карточка blocked. Если недоступен только один сценарий, зафиксировать его ограничение и передать другой открытый этап, сохранив in_progress.

В финальном ответе назвать фактическое состояние: получатель/предмет/comment ID/run ID и queued/running; либо in_review; либо конкретный внешний блокер. «PASS», «модель не назначена», «следующий шаг» или in_progress без продолжения не являются завершением работы. Узкий scope текущего ревью ограничивает выполняемые проверки, но не отменяет передачу ближайшего этапа по подплану. Явная пауза или запрет владельца на продолжение сохраняет силу. Не создавать задания ради активности и не передавать один и тот же вывод по кругу: следующее назначение должно производить новый необходимый результат. Если требуется решение владельца по одному критерию, не менять критерий самостоятельно и не останавливать остальные независимые проверки.

Checkpoint — до20 коротких строк: узел, ветка/SHA/PR, последний подтверждённый результат, ограничения и конкретный следующий шаг. Обновлять штатным `PUT /api/issues/{id}` только нужные поля с `expected_revision` свежего GET, затем перечитать. Конфликт — перечитать и согласовать текст; неизвестный ответ — сверить фактическую запись. Устаревшие ожидания общей инфраструктуры заменять самостоятельным следующим шагом, сохраняя технические факты и ограничения ресурсов.

## Проверки и ресурсы

Критерии RUNBOOK и подплана сохраняются: точный чистый кандидат, назначенный модельный сценарий, независимое ревью и cold-check. Собирать существующим build-cli.ts, промежуточную сборку можно делать с --no-archive. Каждая карточка строит свои кандидаты; исходники передаются через Git. Передача бинарных сборок между карточками не обязательна и не создаёт зависимости.

Перед CLI сверить фактическое business task, входы, кандидат, модель/вариант, личный профиль, рабочий каталог и возможность безопасного использования собственных ресурсов. Модели передаются только задание и входы; oracle и служебные доказательства остаются вне её контекста. Существующий CLI вызывается напрямую без admit/artifacts wrappers. Предел модельного прогона7200 секунд сохраняется. Неверная подготовка исправляется до прогона; неизвестный результат операции не разрешает её повтор.

Аккаунты, личные профили, пакеты и доказательства каждого узла изолированы. Генератор использует существующую пару аккаунтов; создаёт только недостающее с прежними правами. Сохранять и закрывать только подтверждённые собственные пакеты/сеансы штатным способом. Перед закрытием браузера/транспорта закончить cleanup. При отказе сохранить состояние и доказательства, затем применить согласованный ниже порядок восстановления; аварийное завершение не выдавать за сохранение/logout. Проблема одного сеанса не запрещает независимую разработку других узлов. После трёх одинаковых попыток без нового результата прекратить этот способ и адресовать конкретный вопрос Ловцу, без общего исследования или ожидания Регистратуры.

Worker сохраняет оригинал .lgp/CSV/экспорт и передаёт точные пути, размеры и SHA256 через существующую общую папку пары. Ловец проверяет оригинал и работает с собственной копией, меняя только пути входов с фиксацией соответствия. Проверенный порядок — [передача файлов](multica-transfer-pilot.md). Не смешивать технический результат с очисткой диска.

## Восстановление собственных тестовых попыток

Владелец 14.10 разрешил постоянный порядок: агент самостоятельно освобождает собственный неисправный тестовый сеанс, включая потерю его воспроизводимого временного черновика, если сохранены исходное задание, входы, исходный пакет при его наличии и достаточная диагностика. Это не касается пользовательских данных, чужих сеансов, неопубликованного кода, единственных экземпляров результатов или данных, воспроизводимость которых не установлена. Доступное штатное сохранение в новый личный путь предпочтительно; доказанная недоступность save не требует повторного разрешения на потерю такого тестового черновика. Решение распространяется на текущие LAB-67 и LAB-73 после проверки принадлежности и воспроизводимости конкретных объектов и заменяет прежний запрет их адресной очистки.

Перед действием установить конкретный собственный аккаунт, серверный сеанс/пакет и локальные процессы; PID сверять с началом и принадлежностью. Использовать штатные средства процесса/ОС и существующий административный доступ в пределах уже выданных прав: разрешены адресное завершение собственных неисправных процессов и закрытие собственного тестового серверного сеанса. Не выполнять массовый kill/закрытие, не менять права аккаунтов и не перезапускать общий daemon/сервер. Отсутствие старого runtime handle не запрещает независимую административную очистку доказанно собственного тестового сеанса и не создаёт права продолжать старую операцию. После действия проверить прекращение собственной активности/освобождение ресурсов и сохранность соседних сеансов. Неизвестный ответ сначала сверить, не повторять действие вслепую.

Старые журналы, pending/UNKNOWN, профили и сохранённые результаты оставить как историю неудачной попытки; не очищать .writer или pending ради обхода блокировки. Зафиксировать фактическую потерю тестового draft и способ освобождения, не объявлять save/logout или отмену подтверждёнными без соответствующей проверки. После подтверждённого освобождения либо доказанной изоляции разрешён новый независимый сценарий в свежем личном профиле; это не replay старой UNKNOWN операции и не её поздний PASS. Модель/лимит/критерии прежние.

Исправление причины входит в ветку узла: отказ cleanup не должен необратимо отрезать поддержанное сохранение/завершение собственного контекста, а удержание незавершённого сеанса не должно зависеть от best-effort фонового процесса, теряемого при завершении задания. Делать минимальное продуктовое исправление с адресными тестами, каждый готовый результат сразу передавать Ловцу и продолжать приёмку. Общую обвязку или новый диспетчер для этого не создавать.

Остановка опасной native операции не равна blocked всей карточки: доступны диагностика, код, тесты и подготовка. Статус blocked допустим только при подтверждённой внешней зависимости, без которой нельзя продолжить ближайшую необходимую работу в имеющихся полномочиях. Указать точное требуемое действие, почему оно недоступно и одно необходимое решение человека. Внутренняя ошибка cleanup, исчезновение процесса или прежний запрет, заменённый этим решением, сами по себе не являются таким основанием. Если продолжение доступно — выполнять его или передать реальное назначение следующей роли, а не только менять статус.

## Простая уборка

После этапа удалять только свои явно ненужные временные файлы и неиспользуемые промежуточные сборки. Сохранять текущий кандидат, последнюю проверенную рабочую сборку, необходимые воспроизводители и итоговые доказательства. Сборки удаляются целиком после окончания использования; чужие каталоги, неопубликованные изменения, личные конфиги, профили, .writer/pending и журналы незавершённых операций не удаляются. Неизвестный объект оставить с короткой причиной.

Нет регистрации, pins/release, отдельного допуска к сборке, таймеров или заданий ради уборки. При нехватке места убрать собственное очевидно ненужное; если этого недостаточно — сообщить конкретный дефицит оператору и продолжить доступную работу. Встроенный GC Multica не менять; до закрытия карточки сохранить исходники в Git, а нужные результаты — вне удаляемого native окружения.

## Переход LAB-66–73

Решение владельца 14.10 для LAB-68: реализовать исходный execution bound нового прямого CLI-вызова внутри штатного CLI в ветке row-filter-sdk. При первоначальном допуске нового вызова фиксировать начало и единственный абсолютный срок с сохранением предела 7200 секунд; передавать тот же origin и исходный сигнал через RunCommand, SDK и фактически приобретённого owner. Дочерние вызовы, ожидания и продолжения не начинают срок заново. Это разрешение заменяет запрет комментариев LAB-68 от15:31–15:33 на создание отсутствующего первичного origin; оно не разрешает подменять старый origin или повторять UNKNOWN. Внешний bootstrap/admission wrapper не возвращается, новый публичный параметр не требуется. Проверить прямой production-маршрут без bootstrap и после адресного ревью продолжить приёмку Фильтра строк; другие карточки этого исправления не ждут.

Существующие ветки, PR и подготовка продолжаются. Устаревшие общие назначения прекращены после сохранения работы; каждому узлу выдан собственный ближайший шаг. LAB-72 возвращён в общий процесс: по отдельному разрешению владельца 14.10 завершены исходные процессы Model86, адресно освобождён его серверный сеанс с потерей несохранённого черновика и назначено самостоятельное продолжение Union. Код, тесты, сохранённые результаты и старый профиль с журналами остаются; старая UNKNOWN операция не повторяется. Доказательства и текущее назначение — [checkpoint recovery](multica-lab72-recovery-plan-2026-10-14.md). Последние два установленных набора старой обвязки удалены; использовать только штатные API/CLI.

Результат перехода и фактические назначения — [отчёт](multica-independent-2026-10-14.md). Полная приёмка восьми узлов, merge и выпуск в переход не входят.
