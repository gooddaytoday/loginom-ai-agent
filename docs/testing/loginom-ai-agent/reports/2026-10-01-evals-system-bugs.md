## Критично

### E01. Прогон останавливается после попытки с кодом 1, оставившей `.writer`

**Где.** `evals/src/run.ts:276–284` (`afterAttempt`),
`evals/src/profile.ts:38–45` (`releaseStaleWriter`). Продукт:
`packages/agent/src/cli/standalone.ts:80–87` — при отказе `execute()` guard
намеренно не снимается.

**Что происходит.** Harness снимает stale `.writer` только после своего таймаута
или Ctrl+C. Для обычного кода 1 он сразу вызывает `recoverIfNeeded` →
`loginom status`. Если CLI упал до `profile.release()` (так происходит при
`LOGINOM_HOST_TIMEOUT`, см. P1), каталог `.writer` остаётся, `status` получает
`PROFILE_BUSY` (код 3), `parseView` не находит JSON, `EvalFailure` останавливает
прогон.

**Доказательство.** `20260929-131445-5588651a2-dirty/summary.json`:
`stopped_reason` — «loginom status не вернул состояние (код 3): PROFILE_BUSY».
`evals/.profile/agent/.writer/owner` датирован 14:45 UTC, после остановки
процессов профиля не было. Следующий прогон стартовал только потому, что
`prepareProfile` снимает stale `.writer` в начале прогона.

**Влияние.** Потерян третий круг — 5 из 15 попыток. Его пришлось добирать
отдельным run-id. Итог разбит на два `summary.json`, которые `compare`
не объединяет. Любой единичный сбой старта host обрывает многочасовой прогон.

**Исправление.** После любого ненулевого кода ждать завершения процессов попытки
(по pid-группе CLI, а не по `pgrep -f` — см. E14), затем снимать `.writer`,
затем `status`. Сложность: S–M.

### E02. Сбой инфраструктуры до старта сессии засчитывается агенту

**Где.** `evals/src/report.ts:8–18` (`statusFor`),
`evals/src/cli.ts:82–92` (`failureKind`),
`evals/src/report.ts:56–81` (`aggregate` исключает только `interrupted`).

**Что происходит.** Код 1 → `failed`. `LOGINOM_HOST_TIMEOUT` не совпадает ни
с одним шаблоном `failureKind` (текстовый шаблон смотрит `errorTexts`, а не
stderr), поэтому `failure_kind: other`. Пакета нет → score 0, `pass: false`.
Попытка входит в `completion_rate`, `mean_score`, `pass_rate` и разброс задачи.

**Доказательство.** `sales-by-category#2`: 31 с, `session_id: null`, токены 0,
вызовов инструментов 0, `events.jsonl` пустой, `stderr_head:
LOGINOM_HOST_TIMEOUT`. Разброс задачи стал 0–100 вместо 100–100; `mean_score`
прогона 47,8 вместо 53,1 без этой попытки.

**Влияние.** Инфраструктура выглядит как регресс агента. При 15 попытках одна
такая попытка — минус 6,7 п.п. completion.

**Исправление.** Отдельный статус `infra_error`: нет `sessionID` и нулевые
токены, либо `LOGINOM_*`/`PROFILE_*` в stderr до первого события. Исключать из
метрик качества, один раз автоматически повторять попытку, показывать долю
infra-сбоев отдельной строкой. Сложность: S.

### E03. Вариант reasoning `low` не применялся, и это нигде не видно

**Где.** Harness не передаёт `--variant` (`evals/src/cli.ts`, аргументы `run`).
Headless `run` берёт только `args.variant`
(`packages/agent/src/cli/cmd/run.ts:940`). Сохранённый
`$PROFILE/state/model.json` читает лишь интерактивный runtime
(`packages/agent/src/cli/cmd/run/variant.shared.ts:6,19`, вызовы из
`runtime.ts:22`).

**Доказательство.** В БД профиля все 200 сессий eval (2026-09-18 … 2026-09-30),
включая 14 сессий analytic и 157 сессий 2026-09-24, записаны с
`"variant":"default"`. Файл `evals/.profile/agent/state/model.json` при этом
содержит `{"openai/gpt-6-sol":"low"}`.

**Влияние.** Прогоны, описанные как «gpt-6-sol low», на деле шли на уровне
reasoning по умолчанию. Эталоны analytic собраны на `xhigh`. Если CLI или
harness начнут передавать вариант, результаты сдвинутся без единого признака
в `summary.json` и `compare`.

**Исправление.** `EVAL_AGENT_VARIANT` в `.env`, явный `--variant` в аргументах
`run`, фактический вариант сессии — в `summary.agent` и в обязательные поля
сравнимости `compare`. Сложность: S.

### E04. В binary-режиме не записано, какой агент измерялся

**Где.** `evals/src/run.ts:94–99`, `evals/src/preflight.ts` (`gitInfo`),
`evals/src/compare.ts:13–21`.

**Что происходит.** `agent.git_sha` и `dirty` — это git репозитория harness.
Версия CLI, `sourceCommit` из `cli-manifest.json`, sha256 бинарника и путь после
разрешения симлинка `EVAL_CLI_BIN` не пишутся, и `compare` их не показывает.

**Доказательство.** Summary обоих прогонов: `cli_mode: binary`,
`git_sha: 5588651a2`, `dirty: true`. Измерялся `0.1.17-prod`, у которого
`sourceCommit` тоже `5588651a2` — совпадение случайное. Если переставить симлинк
`~/.local/bin/loginom-ai-agent-cli` на другую сборку, summary не изменится.

**Влияние.** Система должна сравнивать версии агента, но не знает, какие версии
сравнивает. Два прогона разных бинарников выглядят как два прогона одного агента.

**Исправление.** Писать `agent.cli_version`, `agent.source_commit`,
`agent.source_dirty`, `agent.binary_sha256`, `agent.variant`. В шапке `compare`
выводить «агент A → агент B» как сравниваемую величину. Несравнимыми считать
различия модели, варианта, рубрики, судьи и входов, а не версии агента.
Сложность: S.

## Важно

### E05. `compare` не выносит вердикт «хуже/лучше»

**Где.** `evals/src/compare.ts:6–10, 45–67`.

**Что происходит.** Стрелка ▲/▼ ставится при любой ненулевой разнице. Нет
парного сравнения по задачам, доверительных интервалов и порога шума, хотя
`README.md` требует не считать изменением дельту в пределах разброса.
`mean_score` смешивает доведение до пакета (0 за `no_artifact`) и качество.

**Доказательство.** Сравнение двух частей этого прогона — один и тот же агент —
дало бы completion 50% → 80% ▲ и `mean_score` 47,8 → 75,4 ▲. Моделирование на
наблюдённых долях успеха задач (3/3, 0/3, 3/3, 1/3, 3/3 без infra-сбоя): при
неизменном агенте падение completion на ≥10 п.п. между двумя прогонами 5×3
случается в 9% сравнений. При реалистичном разбросе трудности задач —
в 17–25%.

**Влияние.** Однозначного ответа нет: человек читает стрелки и легко принимает
шум за регресс или улучшение.

**Исправление.** Вердикт «хуже / лучше / неразличимо» по парной разности по
задачам (кластер = задача) с интервалом и заранее заданным запасом. Отдельные
оси: доведение до пакета, верность результата по oracle, структурные пункты,
pass^k. Сложность: M.

### E06. Порог pass = 70 пропускает неверный результат

**Где.** `evals/src/judge.ts:38–61` (`scoreVerdict`); веса в `task.json`
(`result-rows` весит 2, остальные пункты по 1).

**Доказательство** (лаборатория, `sales-by-category` и `abc-pareto-groups`):

| Внесённая ошибка | score | pass |
|---|---|---|
| одна выручка в CSV завышена на 2,3% | 71 (75 с пунктом `honest-report`) | да |
| две строки CSV переставлены | 71 | да |
| в XML сортировка по возрастанию | 86 | да |
| в XML сумма выручки заменена на среднее | 86 | да |
| в XML порог класса A 0.8 → 0.7 | 88 | да |

Pass становится false только при двух и более дефектах (57, 43, 63).

**Влияние.** `pass_rate` и `mean_score_completed` почти не реагируют на неверный
ответ. Баллы 88–100 у завершённых попыток в основном отражают стиль графа.

**Исправление.** Детерминированная сверка CSV с `oracle.csv` — отдельная
бинарная ось и условие pass. LLM-судья — для структуры графа и честности
отчёта. Прототип сверки (`/tmp/eval-rubric/grade_csv.py`, временный) совпал
с судьёй по `result-rows` на 9 из 9 артефактов. Сложность: S–M.

### E07. Дефекты рубрик analytic и слепое пятно калибровки

- `low-liquidity-companies/import-csv` требует «импортированы все 16 колонок».
  Эталон держит в `ColumnDefs` все 16, но активирует 5. Калибровка
  (артефакт = эталон) пункт засчитала. Живой судья на поколоночно таком же
  импорте снял его в 3 из 3 судейств: живое и два повтора, итог 88 вместо 100.
- `chain-links` в campaign/abc: «вспомогательный узел допустим только для
  переименования или отбора полей». Узел перестановки колонок
  (`TBGReformColumnsEngine`) засчитывается то так, то иначе:
  `campaign-roi-by-channel`, прогон 2, попытка 1 — живой вердикт 89, оба
  повтора 100. Это единственная нестабильность судьи в лаборатории:
  2 расхождения из 18 повторов.
- `result-rows` проверяет часть колонок. В sales — только `transactions` и
  `revenue`; в budget, campaign и abc — тоже не все; в low-liquidity — три якоря,
  а не все 35 строк. CSV `sales-by-category` без колонки `avg_unit_price`
  получил в лаборатории 100.
- Калибровка сравнивает эталон с самим собой (positive) и с эталоном другой
  задачи (negative). Она не ловит мягкость судьи к почти правильным пакетам и
  не ловит пункты, которые эталон буквально не проходит: судья видит совпадение
  с `reference/` и засчитывает их.

**Исправление.** Переписать формулировки пунктов. Добавить в `--calibrate`
near-miss негативы — мутации своего эталона: направление сортировки, функция
агрегации, порог в `Expression`, условие фильтра. Готовый прототип — лаборатория
из приложения. После правок получится новый `rubric_hash` и понадобится новый
базовый прогон. Сложность: S (тексты), M (near-miss в harness).

### E08. Квитанция сохранения не разбирается

**Где.** `evals/src/cli.ts:32–42`; `evals/src/artifact.ts:75–78, 102–108`.

**Что происходит.** `state.output` у `loginom_dock_action_run` с
`package.save_*` — три JSON-документа подряд. `JSON.parse` всей строки падает
(«Extra data»), и `saveReceipts` всегда пуст. Пакет находится только по
предписанному имени. Иначе срабатывает scan: он берёт новейший `.lgp` в корне
хранилища с mtime после старта попытки, любой, не только с префиксом
`eval-<run-id>-`. `cleanupArtifact` затем удаляет этот файл.

**Доказательство.** `artifact_origin: instructed` у всех 138 полученных пакетов
прогонов 2026-09-24 … 2026-09-30, `receipt` — ни разу. В выводе сохранения
`sales-by-category#1` (прогон 30.09) три документа, `package_ref.path` есть
в первом.

**Влияние.** Сейчас результаты верны, потому что агент сохраняет пакет под
заданным именем. Но главный источник истины не работает. Если агент сохранит
пакет под другим именем, harness может взять и удалить чужой пакет пользователя.

**Исправление.** Разбирать первый JSON-документ потоковым декодером; scan
ограничить префиксом `eval-<run-id>-`; не удалять файлы вне этого префикса.
Сложность: S.

## Умеренно

### E09. `harness_error` входит в знаменатель метрик агента

`evals/src/report.ts:56–68`: исключаются только `interrupted`. Ошибки harness
(`docker cp`, распаковка, коды 2/3) снижают completion и pass агента. Сбой
`unzip` или пакет без `Unit.xml` даёт `no_artifact` со score 0: при полном
диске это выглядит как провал агента. Исправление — исключать и считать
отдельно. Сложность: S.

### E10. Каталог задач по умолчанию сломан пустыми папками

`evals/src/task.ts:10–13, 27`: задачей считается любой подкаталог, без
`task.json` загрузка падает с кодом 2. В `evals/tasks/` лежат 30 пустых
неотслеживаемых каталогов после расширенного прогона 2026-09-24
(`abc-analysis` … `var-sum-3-plus-5`); git пустые каталоги не показывает.
Запуск без `--tasks` и тесты, читающие `evals/tasks`, сейчас не стартуют.
Исправление: удалить пустые каталоги; в `loadTasks` пропускать каталог без
`task.json` с предупреждением. Сложность: S.

### E11. Профиль eval не очищается

`evals/.profile/agent` занимает 8,7 ГБ, из них 8,6 ГБ — `loginom/runtime`:
199 чатов, около 450 readiness-попыток (около 4,5 ГБ), `execution-events.jsonl`
до 70 МБ на попытку. Диск занят на 89%, свободно 25 ГБ. Накопленное состояние
runtime переходит между попытками и прогонами, растёт время старта (см. P1),
а заполнение диска даст ложные провалы агента. Исправление: чистить
`loginom/runtime/generations/*/chats/*/attempts` после копирования артефакта
или создавать профиль на каждый прогон с копией авторизации; проверять
свободное место в preflight. Сложность: M.

### E12. `--calibrate` всегда завершается кодом 0

`evals/src/calibrate.ts:109`. Порог калибровки соблюдается только вручную:
в CI провал калибровки не остановит прогон. Исправление — ненулевой код при
предупреждениях. Сложность: S.

### E13. Хеши и метаданные прогона неполные

- `agent_inputs_hash` не включает фиксированный хвост промпта
  (`evals/src/run.ts:173–176`): смену формулировки `compare` не заметит.
- `verdict.schema.json` не хешируется.
- Суффикс `-dirty` не говорит, что именно изменено.
- `tasksDir` не пишется в summary: `--judge-only` по прогону с внешними задачами
  требует вручную повторить тот же `--tasks`.
- `dock.skill_revision` — снимок preflight, а не ревизия, с которой работала
  сессия.
- Таймаут из `task.json` не попадает в `summary.config.timeout_ms`.

Сложность: S.

### E14. `pgrep -f` не видит процесс host

`evals/src/profile.ts:58–64`. `node-host` запускается без пути профиля в argv
и env, поэтому проверка показывает «процессов нет», пока host ещё жив. В этом
прогоне это не сработало. Но если починить E01 через `pgrep`, появится риск
снять guard у живого host. Исправление — отслеживать pid-группу CLI.
Сложность: M.

### E15. Остановленный прогон нельзя продолжить

Остаток добирается отдельным run-id. `compare` и `--judge-only` работают
с одним `summary.json`, объединение возможно только вручную. Исправление —
`--resume <run-id>` или команда слияния. Сложность: M–L.

## Мелко

### E16. Отображение и агрегаты

- ▲ у `tool_errors` и `total_cost` в `compare` означает ухудшение.
- `min_score–max_score` задачи включает нули инфраструктуры (E02).
- `profile_recovered` последней попытки в summary не сохраняется.

## Дефекты продукта, проявленные eval

### P1. Старт host ограничен 30 с, guard после таймаута остаётся

`packages/loginom-host/src/node-client.ts:64–80`: запрос `start` с таймаутом
`30_000`. Он включает вход в Loginom, хотя внутренний бюджет готовности —
до 120–150 с (`packages/loginom-host/src/supervisor.ts`). При таймауте дочерний
процесс получает `SIGTERM` без ожидания. `launchNodeHost` вызывается до
`try/finally` (`packages/agent/src/cli/standalone-run.ts:52–60`), поэтому
`host.close()` не выполняется и guard остаётся (`standalone.ts:80–87`).

Время от старта CLI до первого события агента по 195 попыткам: медиана 14,3 с,
p90 20,0 с, p95 21,9 с, максимум 24,4 с. Одна попытка из 196 (0,5%) в 30 с не
уложилась. Предыдущая попытка закончилась за 7 с до её старта. Кроме того,
в 14:45:40 UTC `systemd-logind` открыл сессию экрана блокировки `lightdm` (c4);
причинная связь не доказана.

### P2. Зависшая операция узла `AMBIGUOUS` блокирует сохранение пакета

Все 5 попыток `no_artifact` (budget-variance ×3, low-liquidity ×2) кончаются
одинаково. Агент ставит узел, мастер Loginom останавливается, и операция
остаётся `AMBIGUOUS`. После этого `node_cancel`, `node_resume`,
`operation_recover` и `node_status` отклоняются, новый `node_apply` получает
`NODE_WORKER_REJECTED` («Another Dock operation remains pending»),
`package.save_checkpoint` — `AMBIGUOUS`.

- budget-variance: второй калькулятор после группировки, мастер выходных полей —
  «Node procedure readiness timeout…», затем
  `OUTPUT_MAPPING_RECOVERY_UNVERIFIED`. Эталон считает долю перерасхода до
  группировки; эталон этой задачи принят с третьей assisted-попытки на `xhigh`.
- low-liquidity #1, #2: экспорт, фаза `input_mapping` — «Initial bound
  observation is no longer current or ready».

Агент честно сообщает, что пакет не сохранён. Частично построенный граф
сохранить нельзя, поэтому попытка получает 0 без частичной оценки.

### Границы приёмки

Это source/fake-приёмка и replay сохранённых CSV/вердиктов. Свежая живая
калибровка новых рубрик и полный живой analytic-прогон не выполнялись.
Повторная обработка старых LLM-вердиктов проверяет новые pass-gates,
но не доказывает стабильность судьи с изменёнными формулировками.
Графовая оценка всё ещё зависит от обнаружения ошибки LLM-судьёй.
Проверка свободного профиля — snapshot процессов, а не атомарная lease:
параллельные harness/ручной старт на одном eval-профиле не поддерживаются.
Бюджет 180 с покрывает обычный start; повторная последовательная подготовка
active+pending generation требует отдельной проверки lifecycle.

После изменения рубрик, обязательных пунктов и хешей нужен новый baseline:
не объединять новые оценки со старыми как одну сопоставимую выборку.
Статистический вердикт, resume, автоматическая генерация near-miss и
продуктовый P2 остаются отдельной работой. Секреты и сырые логи в git
не добавлялись; live host/профиль пользователя не сбрасывались.
