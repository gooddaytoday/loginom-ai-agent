# Проверка Windows startup / system proxy — 2026-09-22

## Вывод и границы

Дефект подтверждён независимо: допустимая для Chromium маска `*vk.com`
вызывает `SYSTEM_PROXY_BYPASS_UNSUPPORTED` в парсере приложения. Исключение
прерывает старт до окна; Electron остаётся жив и удерживает single-instance lock.
Это достаточная причина описанного симптома и с высокой уверенностью объясняет
инцидент из приложенного журнала. Это не доказательство общей причины всех
случаев «установилось, но не запускается» на других компьютерах.

Проверен commit `d27338d090cbd83d7f2af85d292745a1f5a60567`, ветка `loginom-work`.
Файлы `desktop/src/main/{index,system-proxy,logging}.ts` и
`loginom-host/src/native-proxy.ts` не отличаются от тега `v0.1.7`.
Исходный код приложения, установленный ASAR, настройки Windows и пользовательский
профиль не менялись. Полная установленная сборка 0.1.7 на проблемной машине здесь
не запускалась; успешный запуск после исправления на ней ещё не проверен.

## Проверенные свидетельства

`LOGINOM-WINDOWS-STARTUP-BUG.md` использован как гипотеза, не как инструкция
применять исправления. `loginom-ai-agent.json` является экспортом исследования
из 47 сообщений, а не конфигурацией приложения.

В JSON есть результаты инструментов, подтверждающие:

- Повторные логи 0.1.7 обрываются после `app starting`.
- Чтение настоящего `WinHttpGetIEProxyConfigForCurrentUser` возвращает
  `autoDetect: false`, пустой `autoConfigUrl`, ручной loopback-прокси и восемь
  исключений с ведущей звёздочкой без точки.
- Извлечённые из ASAR функции отклоняют эти исключения; это соответствует
  текущим исходникам. Успешный A/B-запуск всего приложения после изменения
  настроек в предоставленном исследовании не установлен.

Само отсутствие `tauri migration` не является уникальным доказательством
причины: до этой строки есть другие операции, включая чтение store внутри
`migrate()`. Пустой Crashpad также сам по себе не доказывает отказ Effect.

## Независимое воспроизведение

Исходный `windowsProxyEnvironment` загружен непосредственно из репозитория
через TypeScript transpilation без изменения его логики. На Node 24.19.0:

- Полный WinHTTP JSON из результата инструмента даёт
  `SYSTEM_PROXY_BYPASS_UNSUPPORTED`.
- Поэлементная проверка выявляет ровно восемь проблемных масок.
- Удаление только этих восьми правил из входной fixture позволяет разбору
  завершиться успешно. Системные настройки при этом не изменяются.
- `autoDetect: true` даёт `SYSTEM_PROXY_AUTOMATIC_UNSUPPORTED` даже при пустом
  ручном прокси. Это отдельный триггер того же дефекта старта.

Дополнительно выполнен минимальный Windows Electron harness с настоящими
Electron 42.3.3 / Node 24.15.0, Effect 4.0.0-beta.83 и исходным парсером.
Каждый процесс имеет отдельный временный профиль. Harness воспроизводит
последовательность lock → parser → whenReady → BrowserWindow; это не запуск
полного Desktop/backend. Контрольное окно создаётся скрытым.

| Вход | Electron ready | Достигнут шаг после whenReady | Окон | Lock | Effect |
| --- | --- | --- | --- | --- | --- |
| `*vk.com` | true | false | 0 | удерживается | defect BYPASS_UNSUPPORTED |
| autoDetect | true | false | 0 | удерживается | defect AUTOMATIC_UNSUPPORTED |
| `*.vk.com`, autoDetect=false | true | true | 1 | удерживается | success |

Состояние фиксировалось через 2 секунды; затем harness сам завершал свой
процесс. Бесконечное ожидание не измерялось. По исходникам путь завершения
приложения при этом раннем дефекте отсутствует: quit/window handlers ещё не
зарегистрированы, результат `Effect.runFork(main)` не обработан.

## Что необходимо исправить в предложенном плане

1. **Маски не эквивалентны.** Реальный `session.resolveProxy` в Electron 42.3.3
   с изолированной fixed proxy configuration показал:

   | Исключение | vk.com | sub.vk.com | notvk.com |
   | --- | --- | --- | --- |
   | `*vk.com` | DIRECT | DIRECT | DIRECT |
   | `*.vk.com` | PROXY | DIRECT | PROXY |
   | `vk.com;*.vk.com` | DIRECT | DIRECT | PROXY |

   Следовательно, ни `.vk.com`, ни пара `vk.com,.vk.com` не сохраняют весь
   смысл первоначальной маски. Это соответствует
   [документации Chromium](https://chromium.googlesource.com/chromium/src/+/main/net/docs/proxy.md#proxy-config-url-patterns-hostname).
   Формат Node NO_PROXY имеет собственную семантику:
   [документация Node 24](https://nodejs.org/docs/latest-v24.x/api/http.html#no_proxy-format).
   Совместимость исправления надо проверять на реально используемых HTTP/fetch
   клиентах backend/runtime, а не только по получившейся строке окружения.

2. **`Effect.tapError` не исправляет диагностику этого отказа.** Независимая
   проверка на используемой версии Effect: синхронный throw становится defect,
   callback `tapError` не вызывается; `tapCause` вызывается. Нужен обработчик
   полной Cause/Exit с записью в файл и определённым поведением при отказе.
   Один `tapCause` с логированием сам по себе ещё не завершает зависший процесс.

3. **Отключённый console transport — неполное объяснение тишины.**
   В минимальном harness `runFork` не вывел дефект даже с доступной консолью.
   В приложении нет обработки результата корневого fiber; включение консольного
   транспорта electron-log само по себе не связывает этот результат с файлом.

4. **Продолжение без прокси меняет сетевое поведение.** Тесты native-proxy
   намеренно закрепляют явный отказ для неподдерживаемых политик. Простое
   игнорирование исключения/отдельных bypass-правил не сохраняет эту гарантию.
   Следует обеспечить видимый результат старта и диагностику независимо от
   разбора прокси, а запуск сетевого backend разрешать только при определённом
   корректном маршруте либо после явного выбора пользователя.

## Следующая проверка исправления

Нужны регрессии для wildcard, automatic/PAC и отказа чтения настроек; проверка
Cause/Exit и освобождения lock; затем A/B-приёмка полной новой сборки на
проблемной машине и проверка фактических маршрутов HTTP/HTTPS/fetch.
Правка только ведущей звёздочки не устраняет остальные ранние отказы.

Локальные диагностические скрипты сохранены вне git:
`%TEMP%/loginom-startup-verification-20260922/{verify.cjs,electron-check.cjs,run-electron.cjs}`.
Первый читает предоставленный экспорт, остальные используют минимальные
fixtures. Сырые диагностические логи и экспорт в репозиторий не добавлялись.
