# Dashboard M2 «Изоляция»: приёмка локального dev-стенда

Статус: **приёмочные проверки M2 на локальном dev-стенде пройдены 2026-11-13 с указанными ниже ограничениями**. Проверены установленная интеграция и обычный итоговый режим; результаты исходников и установленного Desktop разделены. Требования: [дизайн M2](../../superpowers/specs/2026-11-12-dashboard-m2-design.md), [план](../../superpowers/plans/2026-11-12-dashboard-m2.md), [изоляция](../../security/dashboard-isolation.md). Рецепт восстановления: [dashboard/stand](../../../dashboard/stand/README.md).

Работать только в worktree `dashboard-m2`, основанном на переписанной `dashboard-app`. Основной checkout и его изменения M3 не трогать. Контейнеры: `dashboard-master-20261109-{server,studio,web}`, сеть `dashboard-master-20261109-net`. Studio: `http://127.0.0.1:32768/app/` и `/app-debug/`; приложения: `http://dashboards.localhost:32769`. Слияние, выпуск, обновление Desktop и перенос на другую машину в эту приёмку не входят.

## Входы и готовность

Задачи 1–11 должны пройти локальные проверки, независимое ревью и CI `unit`/`dashboard-browser` **до обновления стенда**. Решение владельца от 2026-11-13: только при собственной навигации iframe на внешний тестовый сервер без `Connection-Allowlist` разрешён максимум один TCP-контакт. HTTP-запросов должно быть 0; обязательны новое событие `frame-src` для адреса цели, закрытый iframe, неизменный URL Studio и ровно один канал. Для остальных попыток и прогона с заголовком сохраняется TCP=0.

Node закреплён в `packages/product/loginom-release.json` (для этого прогона 24.19.0), Bun — в корневом `package.json` (1.3.14), Playwright/Chromium — в lockfile runtime (Chromium 154.0.8037.0, revision 1246). Используйте `LOGINOM_AI_AGENT_TEST_NODE`, этот же Node первым в `PATH` и `PLAYWRIGHT_BROWSERS_PATH`. Для npm нужен каталог `bin` того же Node в `PATH`. Временные данные и безопасные доказательства — вне Git, в подготовленном `$HOME/storage/tmp/`; задайте `TMPDIR` туда. Учётные данные и реальный путь приватной конфигурации не печатать и не коммитить.

В текущей оболочке подготовьте временный каталог, затем запускайте проверки из `packages/dashboard`:

```sh
mkdir -p "$HOME/storage/tmp"
export TMPDIR="$HOME/storage/tmp"
```

```sh
bun typecheck
bun run test
bun run test:browser
bun run check:size
```

`test:browser` включает публикацию и сборку всех трёх примеров. Из корня дополнительно:

```sh
bash -n packages/dashboard/deploy/dev-master.sh
docker run --rm --network none -v "$PWD:/mnt:ro" -w /mnt \
  koalaman/shellcheck:stable packages/dashboard/deploy/dev-master.sh
```

Сохраните SHA исходников и проверенного CI. Не меняйте `.lgp` репозитория или существующий пакет стенда. Для тестовых копий используйте новый путь; до копирования проверьте, что он свободен. Изменённые параметры сессии не сохраняйте в пакет. В конце закройте свои пакеты и штатно выйдите из Studio до закрытия вкладок, чтобы не оставить блокировку.

## 2. Обновление поверх M1 и свежая публикация ROI

Из корня проверенного worktree с закреплённым Node в `PATH`:


Установщик создаёт `~/loginom-dashboard/{node,server.mjs,builds/}` и отдельный web, останавливает только прежний M1-процесс Node. Существующий fixture не перезаписывается. Обновите Studio, выберите «По убыванию ROI» в `/user/dashboard-roi/campaign.lgp` и нажмите «Создать dashboard»: публикации M1 на новом хосте ещё нет. Получите **свежий ID этого клика** из ссылки Desktop; не используйте `/dashboard/current` или случайный последний снимок.

```sh
node packages/dashboard/script/publish.mjs <ID-свежего-снимка>
export DASHBOARD_STUDIO_CONFIG=/absolute/private/path/to/master.json
./packages/dashboard/deploy/dev-master.sh check
```

Замените placeholder приватной конфигурацией вне Git, не выводя её содержимое. Publisher до M4 выполняет `npm run` на хосте, поэтому публикуйте только подготовленные доверенные исходники ROI. Ожидается успешный `check` для обоих клиентов: текущий хеш, режим, заголовки и ограничения контейнера, API и адаптер. Это не заменяет следующие UI-шаги.

Результат 2026-11-13: обновление поверх M1 и публикация из нового снимка прошли. `check` подтвердил оба клиента, заголовки, ограничения контейнера и настоящий API Studio. Хеш неизменяемой сборки ROI — `9c308a81609cedeb6934675cb86145fbae5dae47379d70bccfb139840a0f1207`.

## 4. ROI, Esc и Desktop

В каждом клиенте поменяйте `MinBudget` **в шапке**: 0 → 10 000 → 0, подтвердите Enter или уходом из поля. Ожидаются 500 → 453 → 500 кампаний. Выход содержит пять строк каналов; не путайте число строк с суммой кампаний. Независимо рассчитайте бюджет, выручку, кампании и ROI по `dashboard/fixture/dataset.csv`, сравните таблицу и график. У приложения нет полей изменения параметра или кнопки выполнения; при расчёте виден статус ожидания.

Проверьте Esc с фокусом внутри iframe и в шапке, повторное открытие с тем же результатом и отсутствие закрытия при фокусе снаружи. После изменения параметра «Изменить в чате» должно передать в неизменённый установленный Desktop новый ID с актуальными параметрами и строками. Проверьте доставку метки узла, не ограничивайтесь наблюдением URL. Не отправляйте новую задачу модели для изменения ROI во время приёмки.

Результат 2026-11-13: в `/app/` и `/app-debug/` подтверждено 500 → 453 → 500 кампаний. Пять строк таблицы, бюджеты, выручка, ROI, названия и проценты обеих осей графика совпали с независимым расчётом по CSV. Esc из iframe и шапки закрывает слой. При пороге 10 000 действие «Изменить в чате» создало новый ID с живыми данными и текущим параметром.

На неизменённом локальном AppImage Desktop 0.3.9 (SHA-256 `e5fc23792dac887ab8e012e6f817761276232222a7489bc3f188016d334b8d2d`) проверены холодный запуск настоящей ссылкой создания и доставка настоящей ссылки изменения в работающий процесс: точные ID сохранены в контексте одного черновика, действие и имя узла показаны правильно, запросы к модели не отправлялись. Использованы действующие backend, IPC и хранилище черновика в отдельном тестовом профиле. Доставка второй ссылки проверена через штатный обработчик `second-instance`; регистрацию системного обработчика URI заново не проверяли.

Ограничение Desktop: проверка подключения Loginom в этом AppImage завершается `LOGINOM_RESOURCES_INVALID`. Шесть абсолютных ссылок `.bin` выходят за каталог bundled runtime и расходятся с manifest. Образ не меняли и не пересобирали; исправление упаковки отложено за пределы M2. Метки dashboard проверены штатным холодным запуском без настроенного подключения (`unconfigured`), без подмены состояния готовности или IPC. Это не подтверждает работу Loginom MCP и генерацию dashboard моделью.

## 5. S4: процессы, самостоятельная вкладка и доставка отчёта

В закреплённом Chromium откройте `chrome://process-internals`; запишите процессы Studio, iframe и отдельной вкладки с адресом опубликованного приложения. В отдельной вкладке `document.cookie` должно бросать исключение из-за sandbox. Запрет встраивания чужой страницей подтверждается браузерным тестом `frame-ancestors` задачи 7; не выдавайте его за проверку HTTPS или OpenID.

Для отчёта скопируйте `dashboard/fixture/{campaign.lgp,dataset.csv}` в **новую** папку хранилища `/user/dashboard-roi-s4/`, не перезаписывая существующие файлы. Откройте её узел, получите свежий ID и создайте отдельные исходники:

```sh
node packages/dashboard/script/publish.mjs <ID-копии> --init
```

В `src/main.tsx` только этой копии добавьте `fetch("http://attacker.localhost:1/").catch(() => {})`, опубликуйте тем же ID и откройте в Studio. В течение минуты ожидается реальный POST в `/_reports` и запись:

```sh
docker logs dashboard-master-20261109-web 2>&1 | rg 'dashboard report'
```

Запишите тип отчёта и привязку к документу копии без строк данных и сырого журнала. Само событие CSP в консоли **не подтверждает доставку** отчёта. После проверки удалите только созданные исходники и `~/loginom-dashboard/builds/<ключ-копии>`; оригинальный ROI не трогать. Закройте тестовую копию без сохранения.

Результат 2026-11-13: `chrome://process-internals` подтвердил разные renderer-процессы Studio, sandbox iframe и отдельной вкладки приложения. У приложения сайт заблокирован по origin; у iframe виден признак sandbox. Отдельная вкладка имеет opaque origin, чтение `document.cookie` бросает исключение. Реальный `csp-report` от документа отдельной копии получен web за 6,54 секунды от начала пробы: директива `connect-src`, ожидаемый адрес блокировки и `disposition: enforce`. Это нативная доставка POST, а не синтетический вызов обработчика отчётов. Исходники, сборка, отдельная копия пакета S4 и искусственные CSV удалены после проверок принадлежности и содержимого; основной ROI сохранён.

HTTP dev-стенда не подтверждает совместимость HTTPS, частного CA или OpenID. Доставка отчётов именно Connection-Allowlist на HTTP/opaque origin этим Chromium не поддержана; проверенная доставка относится к CSP `report-uri`.

## 7. Firefox и строгий режим

В обычном режиме Firefox должен открыть ROI и пересчитать параметр. Затем из корня:

```sh
./packages/dashboard/deploy/dev-master.sh install --strict
./packages/dashboard/deploy/dev-master.sh check
```

Получите свежие снимки после перезапуска web. Firefox должен показать объяснение отказа до расчёта и передачи данных приложению; Chromium 154 — открыть ROI. Проба проверяет административный запрет ICE, а не строку User-Agent. Она не обещает распознавать любой браузер, в котором WebRTC уже отключён настройкой; ограничение записано в дизайне.

Верните обычный режим и повторите проверку:

```sh
./packages/dashboard/deploy/dev-master.sh install
./packages/dashboard/deploy/dev-master.sh check
```

Результат обычного режима 2026-11-13: Firefox 158.0.1, geckodriver 0.37.1, реальные вход и ROI, пересчёт 500 → 453 → 500, пять каналов; пакет закрыт без сохранения, выход подтверждён. После `install --strict` штатный `check` прошёл в обоих клиентах. Firefox получил точное объяснение отказа до создания снимка: iframe ROI не появился, запросов `/dashboard/targets` нет. Chromium 154 открыл ROI и пересчитал его с тем же CSV-oracle. Обычный режим восстановлен командой `install` без флага, повторный `check` прошёл в обоих клиентах.

## 8. Удаление и повторная установка


Обновите Studio: она работает штатно, элементов dashboard нет. `~/loginom-dashboard/builds/` и хеш публикации ROI сохранились; web удалён, исходники и `.lgp` не менялись. Затем:


ROI должен открыться без перепубликации. Итоговый режим — обычный. Для другого имени web передавайте один и тот же `--web NAME` всем командам; не удаляйте чужие контейнеры вручную.

Результат 2026-11-13: `uninstall` прошёл; оба клиента открыли штатный сценарий без script/кнопки/слоя dashboard. `current` и каталог прежнего хеша ROI сохранились. После `install` без флага прошёл `check`, и оба клиента снова открыли ROI с полным CSV-oracle и пересчётом 500 → 453 → 500. Публикация между этими проверками не выполнялась. Итоговый режим — обычный.
