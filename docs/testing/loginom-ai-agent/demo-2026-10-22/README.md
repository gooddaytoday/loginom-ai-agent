# Сценарии живого показа 22 октября 2026

Шесть самостоятельных сценариев и два продолжения первого: s7 (резерв) и s8. Все данные
синтетические, UTF-8 без BOM, разделитель — запятая, первая строка — заголовок,
десятичный разделитель — точка. В файлах 6–20 строк данных, персональных данных нет.
`prompt.md` — проверочная просьба; `prompt-demo.md` в s1–s6 — дословная короткая
формулировка для R1. Oracle и ожидания модели не передаются.

## Независимые ожидания

В каждом каталоге лежат `prompt.md`, `data/*.csv`, `oracle.py`, `expected.json`
и краткий README. Каждый oracle автономен: стандартная библиотека Python,
чтение исходных CSV-байтов, расчёт через `Decimal`, вывод JSON в stdout.
Нет чтения `expected.json`, сохранённого пакета или результатов модели.
В денежной арифметике нет промежуточного округления; в JSON деньги имеют тип
`real`, счётчики — `integer`. Все используемые дроби точно представимы в binary64;
допуск не требуется. Oracle работает из любого текущего каталога.

Из корня репозитория воспроизвести один эталон:

```sh
case=docs/testing/loginom-ai-agent/demo-2026-10-22/s1-revenue
python3 -B "$case/oracle.py" > ./s1-expected-rebuilt.json
cmp "$case/expected.json" ./s1-expected-rebuilt.json
```

Без аргумента oracle воспроизводит сохранённый эталон побайтно. Перед реальным
прогоном подготовить отдельный expected под **новый личный путь пакета**:

```sh
python3 -B "$case/oracle.py" '/<username>/demo-022-s1-<run-id>.lgp' > ./s1-run-expected.json
```

`package_path` должен точно совпасть с фактическим путём сохранённого пакета.
Пути `/demo-2026-10-22/s*.lgp` в эталонах — только воспроизводимые примеры,
не готовые пути тестового аккаунта. Ожидания фиксируют схему и **все** строки
последнего преобразования перед экспортом. Тип `exports.text` проверяется как
часть графа; байты экспортированного файла сам cold-check не сравнивает.

Формат соответствует `scripts/node-acceptance/expected-outputs.mjs` из ветки
`acceptance-tools`: форма `outputs`, `ordered` внутри выхода. Для s1/s2/s3/s4/s7
порядок обязателен, также для s8; для s5/s6 — произвольный, порядок колонок всегда фиксирован.
В `demo-022` этот формат уже поддерживается. В исходном `origin/loginom`
парсер старее; для полной проверки нужен существующий cold-check из `demo-022`
или `acceptance-tools`. Код оснастки в этой карточке не меняется.
`expected-outputs.mjs` экспортирует функции и не имеет собственной CLI-валидации:
простое `node expected-outputs.mjs` ожидания не проверяет. Проверяется вызов
`parseExpectedOutputs(JSON.parse(...))` для каждого файла.

## Демо-формулировки R1

В s1–s6 использовать пару `prompt-demo.md` / `expected-demo.json`.
Проверочные `prompt.md` и `expected.json` сохранены. В демо-ожиданиях все
`outputs` совпадают с проверочными: схема, значения, конечный узел и флаг
порядка. Сокращён только список обязательных типов в `nodes`:

| Сценарий | Помимо импорта и экспорта обязателен |
|---|---|
| s1 | `transform.group_data` |
| s2 | `transform.replace_columns`, `transform.filter_data` |
| s3 | `transform.join_data` |
| s4 | `transform.union_data` |
| s5 | `transform.cross_table` |
| s6 | `transform.group_data` |

Равные ключи проверены расчётами `oracle.py`: у итоговых групп s1 и s4 нет
равной Revenue. В s6 при сортировке товаров Revenue = 0.00 у P-011 и P-012;
оба относятся к C при любом взаимном порядке. Итоговая сводка s6 уже имеет
`ordered: false`: порядок классов не проверяется, их счётчики и суммы сохранены.
Оснастка поддерживает флаг порядка для всего выхода, а не частичный порядок
внутри групп равных ключей; в этих данных такой частичный режим не нужен.

В R1 модели передаются только короткий запрос и исходные CSV, а проверяющему —
`expected-demo.json` с личным путём пакета. Чтобы воспроизвести демо-ожидания,
рассчитать `oracle.py` и заменить `nodes` строго по таблице выше; `outputs`
не менять. Модельных прогонов при подготовке демо-формулировок не было.

## Проведение показа

1. Выбрать s1–s6, новый пакет и отдельный профиль. Рассчитать ожидаемый JSON
   до запуска. Для модели доступны только выбранный `prompt.md` либо
   `prompt-demo.md` и CSV сценария;
   не прикладывать весь каталог с oracle и expected.
2. Отправить просьбу в Desktop/CLI, выполнить построенный сценарий, получить
   CSV и сохранить пакет. Модель/лимит режима показа: `openai/gpt-6.1-sol/medium`,
   1800 с. Эти сценарии в D1 моделью не запускались.
3. Запустить существующий `cold-check.mjs` с `--expected` для этого пути пакета
   и собственными `--config`, `--resources`, `--saved`, `--output`.
   Статическая проверка ниже не заменяет реальный cold-check.
4. s7 отправляется в тот же чат и открытый пакет после успешного s1.
   Это просьба изменить существующий отчёт; новую независимую цепочку не создавать.
   CSV в s7 — копия для автономного oracle, повторно загружать её не требуется.
   После s7 у пакета новый эталон; исходный expected s1 уже неприменим.
5. Для s8 сначала выполнить исходный s1 (проверочный или демо-вариант), затем
   в том же чате и пакете отправить `s8-rename/prompt.md`. Использовать
   `s8-rename/expected-demo.json` с точными `package_path` и `export_destination` из задания
   (для проверочного варианта остаётся `expected.json`): все 6 строк s1 сохранены, имена и подписи полей —
   Регион, Категория, Выручка. CSV из s8 повторно не загружать. s8 начинается
   с исходного s1, до фильтра s7; запуск s1 → s7 → s8 оставил бы только Север.
