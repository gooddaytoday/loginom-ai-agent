# LAB-2037. Контролируемая установленная пара

Контроль и кандидат последовательно выполняют одну и ту же проверку на выделенном слоте из LAB-2037. Комплект проверяет, получает ли агент актуальное напоминание после реального ответа Loginom. Модель-построитель заменена локальным сценарным HTTP-провайдером. Для пилота Terra/high действуют прежние назначения, отдельный профиль и согласованные пределы.

## Где продолжить

- [Каноническая контрольная точка](../../../superpowers/plans/2026-11-17-recovery-port.md#checkpoint-s5-26112026) фиксирует ревизии продукта, результаты, освобождение ресурсов и состояние передачи S6. В LAB-2037 найти указанный там частичный паспорт и сверить SHA-256 с карточкой. В паспорте хранятся хэши поставок, остаток бюджета и шесть оставшихся ключей в `pilot.unexecuted_keys`. Два уже оценённых задания учтены в расходе и не заказываются повторно.
- В квитанции допуска механической пары `01a2149d-49c7-72c9-952b-16853638891d` указаны отпечатки входов и профилей. Семь рабочих входов этого каталога совпадают с комплектом v2, сверенным на стенде. SHA-256 того архива `67cc23770df02cac06346b8a1453277cdb8195957af4682de3697affcbda217b`. Для дерева релевантны отдельные суммы в `SHA256SUMS`, включая обновлённую инструкцию.
- EvalOps возобновляет работу из LAB-2037 после подтверждения системной службы N=1 и права её штатного запуска из текущей служебной учётной записи. Конфигурацию слота, пути, параметры установки и назначенные доступы взять из штатной конфигурации карточки и Kit. Штатно подготовить оба выделенных профиля заново, затем выполнить `parallel-env.ts prepare` и `verify` с фактической проверкой свободы слота и изоляции. Старые временные копии авторизации удалены, потребуется штатная подготовка новых.

## Общие условия

Из каталога комплекта выполнить `sha256sum -c SHA256SUMS`. На обеих сторонах H — `dd9d1e1d561bf65da1d3d2a57a8da3520d424903`. При необходимости локальную HTTP-связность и сценарий можно отдельно проверить командой `PYTHONDONTWRITEBYTECODE=1 python3 check-provider.py`. Она вызывает только искусственного локального поставщика и ничего не говорит об установленном Loginom.

Использовать выделенный чистый checkout H. Хранить дополнительный корпус только в `$harness_root/results/lab-2037-input/tasks/s5-new-package/`, где `harness_root` — абсолютный путь каталога `evals/` этого checkout. Штатный каталог runtime-данных `evals/results/` уже предусмотрен этой версией H. `lab-2037-input` выделяется только для замороженных входов; командные журналы, собранные пакеты и результаты batch размещаются в отдельном рабочем каталоге кампании. Проверить контрольные суммы доставленного комплекта и каталога до обеих сторон. Объявить этот дополнительный корпус явно в server config и отдельном corpus-pins механического опыта. Группа `s5mechanics`, относительные `server.corpora.s5mechanics.tasks` и `groups[].dir` равны `results/lab-2037-input/tasks`, задаче назначен её собственный timeout (например 720000 мс согласно бюджету) и закреплённые хэши ниже.

Для первой поставки выполнить из каталога H, где `fixture` указывает на абсолютный путь проверенного комплекта.

```sh
test "$(git rev-parse HEAD)" = dd9d1e1d561bf65da1d3d2a57a8da3520d424903
test -z "$(git status --porcelain --untracked-files=normal)"
umask 077
mkdir -p results/lab-2037-input/tasks
test ! -e results/lab-2037-input/tasks/s5-new-package
cp -R "$fixture/tasks/s5-new-package" results/lab-2037-input/tasks/
(cd results/lab-2037-input && rg '  tasks/' "$fixture/SHA256SUMS" | sha256sum -c -)
test -z "$(git status --porcelain --untracked-files=normal)"
```

На второй стороне в том же checkout читают уже зафиксированные входы. Закрепить принятую исходную ревизию H и два отдельных хэша входов и рубрики; добавленная задача и место её хранения явно отражены в паспорте. Применяется штатная pre-reservation команда `bun --no-env-file run script/campaign-preflight.ts --manifest "$campaign_manifest" --server "$campaign_server" s5mechanics s5-new-package 1 1`. Полное `ready:true` требуется от реального стенда. В отдельном чистом локальном checkout проверка с точными pins прошла проверки HEAD, дерева, пути корпуса, бинарного файла, задачи, рубрики и лимита до проверки slots; намеренно пустой локальный slots-файл дал `SLOTS_VERSION`. Контрольная подмена каждого хэша обнаружена штатными `TASK_INPUTS_PIN_CHANGED` и `TASK_RUBRIC_PIN_CHANGED`. Эти проверки относятся к входам; допуск стенда оформляет EvalOps. Функции H `loadTasks`, `agentInputsHash` и `rubricHash` для массива из одной этой задачи дают `bc9c15ea01b8216f362bc09ada3131f0abeece61417026734d9d03947527b1f1` и `290cbddf96137ce28485d6a4b981f5bd10aac6761946734477f9a78a577040c5`. Прозрачная поставка содержит искусственный эталон пустого пакета из тестовых данных. Он предназначен только для независимой оценки, никогда не подаётся как вложение CLI или как результат стороны.

Перед допуском выделить два чистых профиля. В каждом заранее подготовить штатный отдельный файл `config/loginom-ai-agent.jsonc` с правами 0600 и точным содержимым из `profile-limit.jsonc`. Обе проверки штатного профиля под H проходят с теми же входами, сначала для исходной конфигурации, затем после подготовки разрешённой накладки и до начала измерения. Записать защищённый снимок хэшей всех документированных входных слоёв в том же окружении обеих CLI (учитывая глобальные `config.json`, основной JSON, JSONC, managed config и доступные env-флаги). Допустимый смысловой delta только `tool_output.max_bytes=256`; `$schema` обозначает формат. Конфигурацию для проекта H отключает. Сверить после закрытия CLI, что файлы в исходном состоянии. При ином составе слоёв/изменениях не выдавать их за одинаковые; прояснить штатной проверкой. У standalone CLI нет отдельной публичной команды печати полной effective config. Проверены могут быть конфигурационные входы с утверждённым порядком merge и фактическое усечение в следующем POST. Значения credentials в отчёт не записывать.

## Запуск

На каждой стороне заранее запустить свежую локальную службу под учётной записью оператора. Каталог для выводов закрытый, вне checkout, installation, workspace и обоих профилей. Пример команды:

```sh
umask 077
python3 "$fixture/provider.py" --port 0 --out "$evidence/requests.jsonl" > "$evidence/provider.port" &
provider_pid=$!
```

Дождаться порта в файле. В утверждённой конфигурации H этого механического профиля задать `EVAL_AGENT_PROVIDER_ID=s5-local`, `EVAL_AGENT_PROVIDER_MODEL_ID=s5-mechanics`, `EVAL_AGENT_PROVIDER_BASE_URL=http://127.0.0.1:<фактический порт>/v1`, `EVAL_AGENT_MODEL=s5-local/s5-mechanics`, `EVAL_AGENT_VARIANT=default`. Тестовое значение `EVAL_AGENT_PROVIDER_API_KEY` — `s5-local-fixture-only`; вводится в штатное окружение подготовки и batch, имя API_KEY запрещено в manifest.pins. Для второй стороны переиспользовать зафиксированный порт первой после её освобождения, чтобы конфигурация поставщика совпадала. При занятом порте продолжать после его штатного освобождения. Никаких внешних запросов модель-построитель не делает. Судью оставить штатным и отдельно учесть его фактические вызовы, время и доступные токены. Native non-node кампания с сохранённым пакетом после `--skip-judge` запланирует offline judge; обычная проверка с судьёй корректно завершает цикл. Перед пилотом Terra/high штатно вернуть модель, сверить базовые настройки и отсутствие JSONC механической пары в отдельном профиле пилота.

В manifest каждой стороны указать `seriesPurpose=controlled`, `parallel=1`, `batchSize=1`, один ключ с `taskId=s5-new-package`, `round=1`, `corpus` из отдельного server config и `experiment={family:"s5-new-package",pair:"s5-installed",arm:"control" или "candidate",order:1 или 2,condition:"P5"}`. Указать уникальные ID кампаний и артефактов, штатные pins и одну и ту же LAB-2037. Для хостового процесса harness первым в PATH идёт назначенный для S5 каталог sandbox launcher из квитанции допуска. Установить абсолютный `EVAL_CLI_BIN` выбранной стороны и сверить его отпечаток с паспортом. Отдельный процесс провайдера не изменяет PATH внутри sandbox. Оператор проверяет фактическую свободу и совместимость слота и выделенную операционную область.

В рабочем каталоге принятого H (`evals/`) использовать отдельные manifest и server config по [регламенту кампаний](../../../../evals/docs/autonomous-campaigns.md). Обе стороны используют одну службу N=1 из LAB-2037, один `batchEnvFile`, одну блокировку контроллера и общий `stateRoot/owner.json`. После свежего допуска EvalOps выполняет резервирование, перечитывает фактического владельца и запускает один проход контроллера.

```sh
bun --no-env-file run script/run-campaign.ts --manifest "$campaign_manifest" --server "$campaign_server" --operation reserve
bun --no-env-file run script/run-campaign.ts --manifest "$campaign_manifest" --server "$campaign_server" --once
```

Дождаться выхода своего системного процесса перед следующим проходом сверки `--once`. Перед передачей слота следующей стороне подтвердить штатный итог и освобождение владельца кампании, сервера, профиля и судьи. После обеих сторон продолжить пилот с первого неисполненного ключа паспорта в пределах остатка бюджета. Полный пилот кандидата и раскрытие отложенных заданий допускаются по условиям плана S5 и карточки.

Системная служба batch должна использовать выделенные настройки этой серии и профиль выбранной стороны. Одна только передача `EVAL_CAMPAIGN_P5_TASKS` не регистрирует назначение. Controller закрепляет owner, manifest и P5, передаёт batch environment, проходит native request-preflight и под настоящей бронью вызывает `runPreparedSlots → runAttempt → runAgent`. Приватный stdin P5 передаёт тот же назначенный package path. Дождаться терминального результата конкретной попытки и cleanup, затем завершить только соответствующий provider_pid. Остальные кампании и ресурсы не затрагивать.

## Доказательства

В `requests.jsonl` сохраняются хэши фактически принятых HTTP POST и текстов результатов, названия объявленных инструментов, ID вызовов и наблюдения. Сырые тела с пользовательскими данными не сохраняются. Разделить title, request-preflight READY, повтор доставки и собственно измерение. Для каждого настоящего POST после `ordinary_stop` проверить только свежие сообщения user после этого assistant stop и сравнить точный текст приглашения с operation ID данной попытки. HTTP-модель видит в тексте только ID операции; native attempt UUID нужно связать отдельно с той же операцией, штатной metadata и записью reminder в историях текущего чата. Отсутствие нового POST устанавливается только вместе с подтверждённым нормальным выходом CLI и её полным интервалом наблюдения. Без доказательств определить исход как неизвестный.

На каждой стороне подтвердить в native evidence единственное срабатывание P5 после фактической записи того же Save, сохранение operation и attempt UUID на start и ошибке второго start, статусы, CLI exit, сработавшее усечение и достижение правильной развилки. Отдельно посчитать подходящие и чужие подсказки. При реально полученном приглашении служба запрашивает read-only снимок и вызывает finish с правдивым описанием попытки просмотра. По нативным данным проверить исход snapshot/finish. Если приглашения нет, новых ходов служба сама не создаёт.

Для проверки пользовательского результата штатный H забирает свежий пакет из серверного хранилища данной попытки. У полной установленной стороны с фактическими `result.json`, `prompt.txt`, `artifact/package.lgp` и `artifact/unpacked` выполнить:

```sh
python3 "$fixture/check-artifact.py" "$attempt_dir"
```

Проверяются назначенный серверный путь, отсутствие неоднозначности, целостность ZIP, совпадение распакованного XML с пакетом, один пустой workflow и ноль аналитических узлов/связей. Сверить хэш пути с `package_sha256` в HTTP-наблюдениях; хэш LGP — с сохранённым артефактом H. Отсутствие или несовпадение пакета остаётся исходом назначенной стороны. Исход корректности пользователя допускает успех контроля независимо от наличия напоминания. Приложить обезличенные итоги и отдельные подтверждения освобождения сервера, профиля и судьи; сырые истории остаются в защищённых каталогах.
