# Общая OAuth-авторизация параллельных CLI

Опциональный режим для standalone CLI на Linux x64. Несколько процессов
используют одну OAuth-сессию OpenAI, сохраняя отдельные профили, базы данных,
историю, Host, браузеры и подключения Loginom. Общей является только
авторизация провайдера модели.

## Контракт

`loginom-ai-agent-cli --capabilities` возвращает JSON без запуска backend,
Host, модели или создания профиля. Поддержка обозначена `shared-oauth-v1`;
она также записывается в `metadata.capabilities` манифеста CLI. Отсутствие
признака означает, что этот режим использовать нельзя.

`LOGINOM_AI_AGENT_SHARED_AUTH_DIR` задаёт абсолютный путь к выделенному
каталогу владельца процесса с правами 0700. В нём находятся `auth.json`
с правами 0600 и постоянный `auth.json.lock`. Каталог должен быть доступен
всем участвующим процессам как один и тот же каталог файловой системы.
В изолированное окружение подключают каталог целиком: замена отдельного
bind-mounted файла не обеспечивает видимость нового inode другим процессам.
Профили и весь каталог настроек при этом не объединяются.

Режим требует standalone CLI; он несовместим с
`LOGINOM_AI_AGENT_AUTH_CONTENT`. Не используйте независимые копии одного
refresh token: все процессы, обновляющие эту OAuth-сессию, должны обращаться
к одному хранилищу и соблюдать его блокировку. Авторизацию Desktop и других
CLI автоматически не импортируем и не изменяем.

## Чтение и обновление

Постоянный файл блокировки использует блокировку ОС `flock`. Его нельзя
удалять или заменять по PID, возрасту или наличию ожидающих процессов.
Закрытие дескриптора и завершение процесса освобождают блокировку в ОС.

Обновление выполняется целиком под этой блокировкой: повторное чтение,
проверка срока, OAuth refresh, запись новых токенов. Если другой процесс
уже обновил токен, повторный refresh не выполняется. Запись использует
временный файл, синхронизацию и атомарную замену. Запрос к модели выполняется
после освобождения блокировки. Вход, выход и изменения авторизации используют
то же хранилище и блокировку, сохраняя записи других провайдеров.

## Неопределённое обновление

Перед refresh сохраняется `refresh-pending.json` без самого токена.
Если процесс оборвался или ответ сервера неоднозначен, повторный запуск
не повторяет обновление прежним refresh token вслепую. Если новая авторизация
уже сохранена, маркер согласуется с ней; иначе требуется новый вход через
штатную команду `providers login` в том же общем хранилище.
Не удаляйте маркер вручную для обхода ошибки.

Удалённый refresh и локальное сохранение не являются одной атомарной
транзакцией: потеря процесса между ними может потребовать повторного входа.
Повреждённый JSON и ошибки прав не считаются пустой авторизацией и не
исправляются перезаписью файла.

## Проверка

Регрессии должны запускать отдельные процессы с временной авторизацией и
локальным тестовым OAuth endpoint: один refresh при одновременном истечении,
параллельные модельные запросы, видимость новой записи, освобождение flock
после SIGKILL, согласованный выход и ошибки записи/обновления. Тестовые
токены не заменяют проверку установленного клиента с настоящим провайдером.

Реальные OAuth-входы, модельные прогоны и приёмка узлов при подготовке этого
изменения не выполняются; это отдельный ручной этап.

Проверено 02.10.2026 на Bun 1.3.14: 80 целевых тестов Agent, Host и Product;
typecheck Core, Agent, Host и Product. На Linux x64/glibc в контейнере без
внешней сети прошли 8 тестов хранилища и 3 проверки настоящего Codex plugin
с локальным фиктивным провайдером. Те же 3 проверки plugin прошли после
компиляции его тестового процесса в Linux executable. Полная поставка CLI
с Host/Chromium и настоящая параллельная приёмка этим не проверены.
