### Что установлено о проблемах

**Нижняя Docker-среда.** Образ успешно загружается, но даже короткий запуск закреплённого Node под обычными ограничениями завершается до полезной работы. В собственной изолированной VM дешёвое воспроизведение из распакованного Dashboard release-каталога:

```sh
sudo docker run --rm --network none --read-only --cap-drop ALL \
  --security-opt no-new-privileges --user 65534:65534 \
  --memory 128m --pids-limit 32 --entrypoint /opt/node/bin/node \
  "$(cat image.ref)" -e 'console.log(process.version)'
```

В проверенной нижней среде получены exit 139 и `uv_thread_create`; обе syscall traces показывают `clone3` → `EPERM`, inspect — `OOMKilled=false`. Это не ошибка загрузки архива или TypeScript. Подписанное обновление только containerd/runc при прежнем Engine уже проверено и не помогло; повторять его как неподтверждённую гипотезу не нужно. Точные старые и обновлённые версии записаны выше. [Docker release notes](https://docs.docker.com/engine/release-notes/20.10/#201010) описывают изменение default seccomp для clone3: это историческое направление для новой проверки, а не доказанный здесь рабочий минимум; поиск более старой границы не входит в принятое продолжение. Отдельный отказ vendor CoreCLR не объяснён этой трассой и не доказан как нехватка памяти. Seccomp unconfined, отключение NNP/cap-drop или собственный профиль не использовались.

**Нижняя Podman-среда.** Stock Compose добавляет worker-контейнерам сеть вопреки `network_mode: none` и не передаёт объявленные PID limits. Важен фактический inspect/процесс, а не успешный `compose config` или install exit 0. Проверка сервера это нарушение отвергает; ошибочные worker-роли остановлены. Более новый изолированный Compose candidate исправил none/PIDs, но не сеть web: native create/init-only probe без запуска Node показал, что старый Podman теряет сеть именно при форме `network:alias`, тогда как простое имя работает. Гипотеза о pod-группировке опровергнута; `--in-pod=false` не применялся. Generic named `network_mode` в translator кандидата отсутствует. Ни этот кандидат, ни промежуточные опыты не подтверждают поддержку нижнего контракта. Точные версии и значения inspect — в предыдущем разделе.

**Отдельный клиентский отказ.** Повторяющийся cleanupFAIL локализован в `deploy/check-studio.mjs`, `closePackage`: исходный `if (!await clean()) throw Error("modified package")` выполняется до ожидания idle, а `clean` требует строгого `IsPackageModified(...) === false`. Наблюдён отказ этой строки; конкретное возвращённое значение и наличие running-состояния в момент отказа не получены. Одна диагностика с записью результата того же единственного RPC прошла, поэтому race/busy/реальное изменение пакета остаются гипотезами. Финальные неизменённые штатные проверки обоих современных стендов прошли по одному запуску; это не исправление нестабильности. Не удалять guard, не закрывать предположительно изменённый пакет принудительно и не добиваться PASS серией повторов. Если отказ повторится, сохранить точное значение и состояние вокруг исходного вызова без extra RPC; менять код только после воспроизводимой причины. Дисковые `.lgp` во время подтверждённых прогонов не менялись.

### Что Git переносит и какие входы нужны отдельно

Git содержит исходники, принятые план/дизайн и это обезличенное описание результатов. `.superpowers/sdd`, `$M5_SCRATCH`, VM-диски, приватные отчёты, сырые журналы и собранные tar-архивы в push не входят. Новую сборку или новый стенд нужно проверять как новые артефакты.

- Получить предоставленный release и соответствующий installer по пинам раздела «Входы и происхождение», либо приватно перенести уже подготовленный `prepared-release-bundle.tar.gz` и сверить его каноническую сумму. Важная поправка installer: первый безусловный overwrite `Integrator.dll.config` заменён copy-if-absent, а ветка явной смены настроек сохранена. Архив/образы в Git не входят; реальные старая установка и переход на целевой подготовленный комплект ещё не проверены.
