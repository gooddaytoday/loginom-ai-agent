# Живая проверка dashboard в Loginom master

## Результат и границы

Установить отдельный локальный стенд из доступной актуальной сборки ветки
Loginom `master` и на нём проверить минимальный путь будущего приложения:
выбор узла → приложение поверх сценария → изменение переменной → выполнение
узла → чтение нового результата. Dashboard впоследствии создаёт агент по
запросу в чате; сначала работа ведётся через Codex, затем через Desktop.

Это исследовательский стенд и временные пробы, не реализация продукта.
Не менять чужие контейнеры, пакеты, рабочие деревья и исходный eval-корпус.
Не создавать dashboard-skill, BI-сервер, новый agent framework или механизм
подключения Desktop к чужой браузерной сессии.

## План

1. Проверить происхождение доступного `build_staging` ветки master через
   существующий GitLab API. Результат: выбран успешный job с артефактом;
   известна его связь с актуальным pipeline ветки. CI не перезапускается.
2. Скачать артефакт в отдельный временный каталог. Использовать Dockerfile
   сборки и библиотеки/config из integration; поднять собственные server/client
   и сеть. HTTP-порт клиента опубликовать только на loopback, без host mounts.
   Результат: minified/debug клиенты доступны, вход и запуск узла работают.
   Это первый сквозной результат.
3. Через реальный клиент проверить toolbar/selection, способ временно открыть
   приложение поверх рабочей области и доступ к идентичности выбранного узла.
   Результат: наблюдаемый mount и точная связь с package/workflow/node/port.
4. На копии тестового пакета изменить одну переменную штатным API, выполнить
   цель и заново прочитать результат. Результат: наблюдаемое изменение данных;
   отдельно отметить, какие части цикла пока не удалось подтвердить.
5. Зафиксировать проверенные точки интеграции и минимальное продолжение для
   создания dashboard агентом. Результат: решения опираются на живую проверку,
   непроверенные свойства явно обозначены. Продуктовый дизайн согласуется далее.

## Средства, риски и объём

Переиспользовать рецепт `loginom-dashboard-evidence/SETUP.md` и подготовку
контекстов `testing/docs/manual-testing/stand.py`; полный installer не запускать:
он останавливает все контейнеры с именем loginom. Новых управляющих слоёв не нужно.

Основные риски: недоступный артефакт текущего pipeline, библиотеки сервера,
изменение клиентского API на master. При блокировке работать только над первым
успешным запуском, не разрабатывать обходные продуктовые механизмы.

Ожидаемый diff: один исследовательский документ, примерно 50–90 строк.
Дистрибутив, временные команды и пробы остаются вне Git; секреты не сохраняются
в отчётах и не передаются в аргументах команд. Проверка плана независимым агентом
обязательна перед установкой. Временные пробы не требуют продуктовых тестов.

## Проверка и точка продолжения

- Стенд: http://127.0.0.1:32768/app/; debug-клиент: `/app-debug/`; параметры — `stand.json` временного каталога.
- Оба HTTP-клиента дали 200, WebSocket — 101; бинарник сервера совпал с артефактом. Вход и выполнение узла проверены через обычный minified-клиент.
- Пакет-проба: `/user/dashboard-probe/variable-probe.lgp`; описание и ожидаемые данные — `fixtures/context.json`.
- Временный bootstrap добавляет кнопку в `ModelForm.Items.tlbModel`; iframe занимает весь `TabForm`, глобальные вкладки и боковая навигация остаются снаружи.
- NodeJS раздаёт приложение через Apache `/dashboard-probe/`, на том же origin. Проверен цикл `GroupLimit`: 1 → 2 → 1 → 2.
- Тип integer сохранился; при значении 2 появились B-колонки: N=7/1, S=2/1. После выполнения заново получены схема и данные. Скриншот: `live-dashboard.jpg`.
- На этом master output читается через `port.get_Socket()` → `get_Output()`.
- Запись требует `node.GetSocketConfigureAssist(socket)` и `BeginOperationEx`/`bg.EndOperationEx`; выполнение ожидается через `bg.AsyncInvoker(node, node.ActivateCancellable, ...)`.
- Проба меняет локальную ControlVariables; полный путь входной переменной workflow ещё не проверен.
- Bootstrap регистрирует обработчик создания ModelForm на обычной странице `/app/`. При выборе одного узла команда Dashboard показывается автоматически.
- Node работает внутри собственного server-контейнера без внешнего порта. После его перезапуска: `docker exec -d dashboard-master-20261109-server /app/dashboard-node /workdir/dashboard-app/dashboard-probe-server.mjs`.
- Закрытие вкладки оставляло серверную сессию и блокировку пакета; новую пишущую пробу начали после перезапуска только собственного server.
- Deep link Desktop открывает чат с черновиком prompt; передачи контекста узла и установки dashboard в продукте пока нет.
- Следующий дизайн: общий способ выдать агенту контекст выбранного узла и установить приложение из Codex/Desktop без ручной настройки пользователем.
- Пробы находятся только вне Git и в собственных контейнерах; не переносить их код в продукт без согласованного дизайна.

## Автоматическое подключение и пересчёт

План пробы прошёл независимую проверку. На обычной странице `/app/` при новом
входе служебная панель отсутствует. Кнопка появляется при выборе узла и скрывается
после снятия выделения. Для CrossTable_bindings открывается NodeJS-приложение.
При первом открытии неактивного узла проба читает настроенный GroupLimit через
штатную операцию настройки сокета и завершает её с отменой. На экране показаны
значение 1 и отсутствие рассчитанных строк. Для активного узла используется
прямое чтение. Изменение на 2 запустило Execute и дало ожидаемые столбцы B.
После быстрых изменений и закрытия во время расчёта приложение при повторном
открытии прочитало выбранное 2 и строки N=15/2/7/1, S=3/1/2/1.
В пробе пакет был открыт только для чтения. Содержимое файла `.lgp` совпало до
и после прогона. Автоматическое сохранение пакета в коде отсутствует.
Скриншот — `automatic-dashboard.jpg` во временном каталоге.
