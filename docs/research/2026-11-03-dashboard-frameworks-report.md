# Выбор OSS BI/dashboard-основы AI Skill для Loginom

Проверено **3 ноября 2026 года**. Назначение: решение для [чата «Спланировать skill для Loginom»](codex://threads/01a1a0cb-4068-7b83-9bc0-c210be182444). Исследование исходников, опубликованных артефактов и официальной документации; совместимость frameworks с Loginom исполнением здесь не проверялась.

## Результат и рекомендуемый выбор

**Основной кандидат для dashboard над результатом узла прямо в браузере — Perspective.** Его опубликованный viewer включает аналитический редактор, многопанельный workspace, общие фильтры и сохранение/восстановление конфигурации. Это уменьшает собственную разработку по сравнению с универсальным UI-стеком. Рекомендация относится к основе первого проверочного прототипа; производственная совместимость, точность типов Loginom, загрузка WASM и сохранение на сервер пока не доказаны. [Опубликованный пакет 5.6.1](https://unpkg.com/@perspective-dev/viewer@5.6.1/dist/esm/ts-rs/WorkspaceConfig.d.ts).

Для **встроенного React-конструктора** отдельно проверить **SQLRooms с Mosaic**: в релизе 0.29.0 уже есть dashboard/chart builder и AI-инструменты. Это более сильный кандидат, чем следует из прежнего описания «только toolkit», но host-приложению всё ещё принадлежат состояние, доступ и persistence. Graphic Walker остаётся альтернативой визуального исследования данных; многопанельный shell и условия LICENSE2 увеличивают объём интеграции. [SQLRooms](https://github.com/sqlrooms/sqlrooms), [Graphic Walker](https://github.com/Kanaries/graphic-walker).

Для **самостоятельной BI-платформы** первый кандидат — **Apache Superset 6.1.0**: полноценные BI/editor/API и Apache-2.0; embedded viewer и редактирование в основном приложении — разные потоки. Стабильный 6.1.0 нельзя заменять на 7.0 release candidate без отдельного решения. **DataLens OSS, Redash, Shaper и Helical Insight 7** заслуживают адресного сравнения по русскому интерфейсу, HTTP JSON, компактному AI/SQL workflow и объёму готового self-service соответственно. **Vizro и Malloy Publisher** особенно интересны для генерации агентом декларативных приложений; они не отбрасываются из-за наличия backend. Обоснования и источники — в карточках.

**Не предлагается одновременно собирать все эти решения.** Для выбора достаточно короткого сравнительного прототипа Perspective/SQLRooms; полный BI-прототип нужен, если самостоятельный доступ пользователей, серверные источники или готовая платформенная работа становятся приоритетом. Наличие собственного AI Skill/MCP — дополнительное преимущество, а не замена сохранения, редактирования и обновления.

## Как читать доказательства

- **Подтверждено** — возможность прямо описана официальной документацией либо найдена в исходнике/API/типах/конфигурации. Если проверен опубликованный tarball или тег, это указано. Это не равнозначно успешному запуску.
- **Предложение/оценка** — конкретная схема Loginom-интеграции и объём нашего кода, выведенные из этих интерфейсов. Все пункты «интеграция» в карточках имеют этот статус, даже если коротко сформулированы без повторения слова.
- **Неизвестно/не проверено** — нет достаточного источника или требуется исполнение. Отсутствие найденного skill не является доказательством отсутствия всех сторонних skills.

Версии фиксируют наблюдённые опубликованные релизы/пакеты на эту дату. `latest` ссылки меняются; номер и дата в тексте — контрольная точка. Тег, версия Python/npm пакета, версия дистрибутива и текущая main могут различаться. Активность релизов/коммитов показывает сопровождение, но не SLA, зрелость или отсутствие дефектов. Границы лицензий изложены по конкретным файлам, без обещания юридической совместимости всех способов распространения.

Оценки **низкий/средний/высокий объём** относительные: низкий — adapter/lifecycle/storage glue при готовом BI, средний — дополнительная оболочка/публикация и заметная продуктовая логика, высокий — собственный BI/editor/query либо перенос платформенного runtime. Они не означают календарные сроки и не включают одинаковую для всех кнопку/toolbar Loginom. «Dashboard есть» и «встроенный пользователь может редактировать его» проверялись раздельно.

## Общая схема интеграции с Loginom

Исходное условие задания — adapter уже может получить schema+rows в браузере. В исходной записке есть предыдущая живая проверка DataSource на minified Loginom7.5.0-alpha+build.4732; здесь она используется как локальная evidence, а не как новая проверка всех типов и объёмов. Reader диагностического инструмента агента не является готовым пассивным адаптером любого узла. [Описание и ограничения исходной проверки](/home/kiselev/.codex/worktrees/2704/loginom-ai-agent/docs/research/2026-11-03-loginom-dashboard.md).

Независимо от выбора нужны:

1. **Привязка и открытие:** обе точки UI передают один binding package/workflow/node/output port. Имена узлов и один port GUID недостаточны; открытие сохранённого dashboard должно находить тот же результат.
2. **Доставка данных:** browser components получают schema+rows/Arrow; серверные платформы — опубликованный snapshot в SQL/Parquet/HTTP API. Браузерный массив не становится серверным datasource без нашего канала доставки.
3. **Сохранение:** config/spec/layout и framework version сохраняются отдельно от результата. `save()` библиотеки обычно возвращает объект, а не пишет файл. Для local PoC допустим browser storage; для переносимого артефакта нужен файл/сервис сохранения. Наличие штатного места внутри LGP для произвольного dashboard здесь не подтверждено. Для BI-сервера сохраняем его ID/UUID и binding.
4. **Обновление:** новый успешный результат заменяет прежний dataset, сохраняя пользовательские edits/filters, если схема совместима. До доказательства устойчивого row key предпочтительна замена snapshot, а не предполагаемый upsert. Для SQL публикация должна не показывать промежуточную половину новой версии; dashboard cache следует обновить/инвалидировать.
5. **Типы и согласованность:** не превращать Int64/UInt64 за 2^53 в JS Number молча; определить NULL, timezone/дату, Variant и длинные строки. Смена node execution/schema во время чтения должна давать согласованную revision или явный повтор/ошибку; silent sample нельзя выдавать за полный результат.
6. **Встраивание и доступ:** mount/iframe/новая вкладка — отдельные варианты. Для iframe проверить CSP, worker/WASM, cookies и фактический доступ пользователя. Платформенные token/signing credentials остаются у доверенного сервера; browser session Loginom не становится автоматически BI-учётной записью. Встраивание viewer не доказывает встраивание authoring UI.

Это необходимая интеграционная работа, которую ни один framework не выполняет за Loginom. Она не требует заранее строить универсальную plugin-платформу, копировать весь runtime агента или вводить дополнительный SQL-сервис в браузерный вариант.

### C01. Perspective

1. **Архитектура, выпуск, поддержка.** Rust/WASM OLAP, worker, Web Component и плагины grid/charts; сервер опционален. Apache-2.0. GitHub Release и npm `@perspective-dev/viewer`/`client` **5.6.1, 23.10.2026**; репозиторий активен. [Релиз](https://github.com/perspective-dev/perspective/releases/tag/v5.6.1), [лицензия релиза](https://github.com/perspective-dev/perspective/blob/v5.6.1/LICENSE.md), [npm](https://registry.npmjs.org/@perspective-dev%2fviewer/5.6.1).
2. **BI / редактор / панели.** Готовы pivot, фильтры, сортировка, агрегации, expressions, таблицы/графики и настройка полей пользователем. Существенное исправление DR: многопанельный workspace уже входит в опубликованный viewer; собственная сетка не обязательна. `WorkspaceConfig` содержит `panels`, `layout`, `global_filters`, `masters`, `derived_tables`. [Опубликованный тип](https://unpkg.com/@perspective-dev/viewer@5.6.1/dist/esm/ts-rs/WorkspaceConfig.d.ts).
3. **Данные / сохранение / обновление.** JSON/CSV/Arrow поступают в Table; `update`/`replace` обновляют данные. `saveWorkspace()`/`restoreWorkspace()` сохраняют всю композицию и фильтры, отдельно от строк. Состояние хранит хост; совпадение схемы важно для восстановления. [API именно 5.6.1](https://unpkg.com/@perspective-dev/viewer@5.6.1/dist/wasm/perspective-viewer.d.ts), [save/restore](https://perspective-dev.github.io/guide/how_to/javascript/save_restore.html).
4. **Embedding / auth / инфраструктура.** Прямой DOM-компонент, можно отдельный origin/iframe. В браузерном режиме нужны статические JS/WASM/worker assets; Loginom владеет правами доступа и доставкой строк. Сервер Perspective нужен при отдельном серверном вычислении, не по умолчанию.
5. **API / AI.** JS/Python API, типизированная JSON-конфигурация. Прикладной официальный Skill/MCP создания dashboard в рассмотренных материалах не подтверждён; агенту достаточно генерировать проверяемый workspace.
6. **Схема Loginom / свой код: low–medium.** Узел → типизированная Table → заранее созданные панели → сохранённый workspace + `{workflow,node,port}`. После повторного выполнения заменить строки, сохранив ручную конфигурацию. Собственные части: адаптер типов, постоянное хранилище/привязка, меню/toolbar и обработка смены схемы.
7. **Неизвестное / минимум проверки.** Нужны реальный cold-open сохранённого workspace, master/detail-фильтр, обновление с тем же числом строк, типы date/decimal/null и измерение памяти/WASM в Loginom. Наличие опубликованных методов не доказывает эту совместимость.

### C03. SQLRooms

1. **Архитектура, выпуск, поддержка.** Модульный React/Zustand framework с DuckDB-WASM и заменяемыми connectors, MIT. GitHub/npm **0.29.0, 09.09.2026**; разработка активна. Важно проверять пакет `@sqlrooms/mosaic`, а не оценивать только общий SQL shell. [Релиз](https://github.com/sqlrooms/sqlrooms/releases/tag/v0.29.0), [LICENSE](https://github.com/sqlrooms/sqlrooms/blob/v0.29.0/LICENSE.md), [npm](https://registry.npmjs.org/@sqlrooms%2fmosaic/0.29.0).

Штатные chart types включают histogram, count, line, scatter, heatmap, box plot и custom spec. Поэтому прежнее утверждение «только toolkit, редактор отсутствует» слишком сильное. [Exports 0.29.0](https://unpkg.com/@sqlrooms/mosaic@0.29.0/dist/index.d.ts), [dashboard types](https://unpkg.com/@sqlrooms/mosaic@0.29.0/dist/dashboard/dashboard-types.d.ts).

Config отделён от runtime; `persistSliceConfigs` сериализует выбранные slices, но не заменяет переносимое хранилище данных/Loginom binding. [Mosaic API](https://sqlrooms.org/api/mosaic/), [persistence](https://sqlrooms.org/persistence).
4. **Embedding / auth / инфраструктура.** Компоненты и room store можно встроить в своё React-приложение без BI-сервера; серверный DuckDB и cloud connectors — дополнительные режимы. Auth/tenant boundaries обеспечивает хост. Для WASM нужны assets, worker и согласованные заголовки выбранного bundle.
5. **API / AI.** Zod-конфиги, SQL/Mosaic specs, команды; **в релизе** доступны `createDashboardAiTools`, `createDashboardAgentTool` и отдельный `./ai`. В актуальных docs также описан skills subsystem/MCP capability runtime CLI, но их наличие в `@sqlrooms/mosaic` не означает готовый внешний Loginom Skill. [AI export релиза](https://unpkg.com/@sqlrooms/mosaic@0.29.0/dist/ai.d.ts), [what’s new](https://sqlrooms.org/whats-new.html).
6. **Схема Loginom / свой код: medium.** Node rows → DuckDB table со stable name → dashboard slice/ChartBuilder → config в хранилище Loginom; обновление заменяет таблицу и инвалидирует queries. Нужна сборка выбранных slices и управление жизненным циклом, но общий editor/layout уже есть.
7. **Неизвестное / минимум проверки.** Запустить именно 0.29.0, собрать две cross-filtered панели, изменить chart вручную, сохранить slices, закрыть и восстановить после новой загрузки rows. Особо проверить invalidation при обновлении таблицы и дрейф Zod-схем; upstream использует Mosaic 0.21, не автоматически latest 0.34.

### C04. Mosaic (UWData)

1. **Архитектура, выпуск, поддержка.** Координатор запросов/selection + SQL AST + Inputs + `vgplot` + декларативные specs. DuckDB серверный или WASM. BSD-3-Clause; фрагменты Plot под ISC. GitHub/npm **0.34.3, 29.10.2026**, активный исследовательский проект UW/CMU. [Релиз](https://github.com/uwdata/mosaic/releases/tag/v0.34.3), [LICENSE](https://github.com/uwdata/mosaic/blob/v0.34.3/LICENSE), [официальный обзор](https://idl.uw.edu/mosaic/).
2. **BI / редактор / панели.** Готова координация многих связанных views, brush/cross-filter и интерактивные inputs; dashboard можно описать композицией `hconcat`/`vconcat`. Универсального self-service BI editor и каталога сохранённых dashboards пакет сам не поставляет. [Spec guide](https://idl.uw.edu/mosaic/spec/), [примеры](https://idl.uw.edu/mosaic/examples/).
3. **Данные / сохранение / обновление.** Данные должны стать таблицей DuckDB; затем выполняются фильтры/группировки/агрегации с pushdown. JSON/YAML spec хранит структуру, а не rows, auth или весь runtime-state. Обновление таблицы и invalidation cached queries нужно связать с жизненным циклом узла. [Core](https://idl.uw.edu/mosaic/core/), [npm зависимости](https://registry.npmjs.org/@uwdata%2fmosaic-core/0.34.3).
4. **Embedding / auth / инфраструктура.** JS/DOM без обязательного BI server; возможен WebSocket/HTTP server connector. Для browser-only нужен WASM engine; для удалённого query endpoint auth/RLS остаются интеграции. `mosaic-core` 0.34.3 закрепляет DuckDB-WASM dev build — не подменять его произвольным stable без проверки.
5. **API / AI.** JS API, SQL builder, JSON/YAML specs и schema удобны агенту; отдельный официальный готовый dashboard Skill/MCP в просмотренных материалах не подтверждён. Есть оптимизированные LLM docs. SQLRooms — независимый способ получить поверх Mosaic редактор, его возможности нельзя приписывать самому Mosaic.
6. **Схема Loginom / свой код: high для редактора, medium для генерации.** Node rows → browser DuckDB → Mosaic spec → несколько linked views; хост хранит spec и node binding. Агент может выдавать декларацию, но ручной authoring, catalog и сохранение selection-state требуют разработки либо SQLRooms.
7. **Неизвестное / минимум проверки.** Две linked views, точные null/date semantics и замена таблицы без stale cache. Отдельно round-trip spec + selections: сериализация структуры не доказывает сохранение пользовательского состояния фильтров.

### C05. DuckDB-WASM

1. **Архитектура, выпуск, поддержка.** Встраиваемый SQL OLAP engine в WASM/worker, MIT; это data engine. GitHub stable Release **1.33.0, 16.12.2025**; npm `latest` указывает **1.33.1-dev57.0, 22.06.2026**. Ветка main активна, но `latest` не равен stable и версия WASM не равна версии native DuckDB. [Release](https://github.com/duckdb/duckdb-wasm/releases/tag/v1.33.0), [npm registry](https://registry.npmjs.org/@duckdb%2fduckdb-wasm), [LICENSE](https://github.com/duckdb/duckdb-wasm/blob/v1.33.0/LICENSE).
2. **BI / редактор / панели.** Есть SQL, joins, window functions, grouping и агрегации. Нет chart renderer, визуального BI editor, dashboard grid, каталога или пользователей. Shell/visualizer не превращают библиотеку в конструктор для продукта. [README релиза](https://github.com/duckdb/duckdb-wasm/blob/v1.33.0/README.md).
3. **Данные / сохранение / обновление.** Arrow/JSON/CSV/Parquet, File/Blob/HTTP и регистрация буферов дают прямой путь от browser rows. SQL управляет фильтрами и пересозданием/изменением таблиц. Export/database/filesystem возможности не заменяют сохранение dashboard specs; OPFS/IndexedDB и lifetime конкретного подключения нужно проектировать отдельно. [Ingestion docs](https://duckdb.org/docs/stable/clients/wasm/data_ingestion), [API](https://shell.duckdb.org/docs/modules/index.html).
4. **Embedding / auth / инфраструктура.** Только frontend assets/WASM/worker, backend необязателен. SQL исполняется на уже доступных пользователю данных; серверные права не появляются внутри WASM. Multi-thread bundles требуют соответствующей browser isolation; default mode single-thread, threading в README stable отмечен experimental. Не переносить требование COOP/COEP каждого bundle на все режимы без проверки.
5. **API / AI.** Типизированный JS API и SQL — сильный агентный контракт. MCP/skills для DuckDB в целом не подтверждают совместимость с конкретным browser WASM instance. Прикладной официальный Loginom/dashboard Skill не найден в проверенных материалах.
6. **Схема Loginom / свой код: high самостоятельно.** Адаптер schema/rows → Arrow/table → SQL results → выбранный renderer/editor. Самостоятельно придётся создать все dashboard/UI/persistence слои; разумнее брать как нижний слой SQLRooms/Mosaic/DuckViz, если их API подходит.
7. **Неизвестное / минимум проверки.** Проверить памяти и время загрузки на типичном/верхнем размере node output, precision decimal/int64, date/timezone/null, CSP/worker, расширения offline. Один SQL group-by над реальным результатом — дешёвый первый тест до выбора UI.

Ручное редактирование — source + live preview с completion, не drag/drop field-based BI authoring. [Dashboard docs](https://docs.duckui.com/docs/dashboards/).
3. **Данные / сохранение / обновление.** Local files/URLs/object stores/remote DuckDB; SQL фильтрует и агрегирует. Dashboards автоматически хранятся в browser storage/profile; код 2.5.1 сохраняет description в IndexedDB, без query results. Есть manual/interval refresh. Локально импортированная таблица в другом viewer не воспроизводится; готовый embed не доказывает private Loginom source bridge или embedded dashboard editor. [Embedding](https://docs.duckui.com/docs/embedding/).
5. **API / AI.** URL `?load=&sql=`, query/share config, SQL+Markdown и Duck Brain; полноценный стабильный library SDK для внешнего CRUD dashboards не подтверждён. AI providers optional, ключи/модель не нужны для обычного rendering. Готовый прикладной AI Skill/MCP не подтверждён.
6. **Схема Loginom / свой код: medium–high.** Либо публиковать versioned Parquet/JSON URL и открывать документ, либо адаптировать внутренний import/store к rows. Хранить канонический source+node binding вне browser profile для переносимости; добавлять обновление источника, а не только refresh SQL.
7. **Неизвестное / минимум проверки.** Private source/auth и передача rows в iframe, external document creation, round-trip между браузерами, schema drift. Проверить именно опубликованный 2.5.1: два charts + input, закрытие/reopen и новый output с прежним количеством строк.

6. **Схема Loginom / свой код: medium для экрана, high для BI.** Собственный Loginom data plugin получает rows и выдаёт widget-ready data; агент генерирует canvas/component settings; хост хранит export, node binding и обновляет data slots. Глобальные filters, grouping и BI authoring — наш слой.
7. **Неизвестное / минимум проверки.** Извлечь designer из v0.0.6, собрать 3 widgets, export→cold-import, проверить динамическое обновление без потери layout. Отдельно выяснить, какие main fixes необходимы: нельзя одновременно обещать стабильность старого релиза и функции новой ветки.

### C15. Freeboard

1. **Архитектура, выпуск, поддержка.** Статический HTML/JS dashboard engine с datasource/widget plugins, MIT. GitHub Releases нет; последний tag **v1.1.0**, package version `1.0.0`; дату tag надёжно не установили. Последний наблюдённый push master **23.09.2023**, поэтому это legacy-кандидат. [Repo](https://github.com/Freeboard/freeboard), [LICENSE tag](https://github.com/Freeboard/freeboard/blob/v1.1.0/LICENSE), [package](https://github.com/Freeboard/freeboard/blob/v1.1.0/package.json).
2. **BI / редактор / панели.** Готовые panes, layout и visual widget/datasource configuration, toggled edit/view mode; ориентирован на IoT/live mashups. Нет штатного generic tabular BI query builder, полноценных aggregation/semantic models и развитого cross-filtering всех панелей.
3. **Данные / сохранение / обновление.** Plugin datasource получает произвольный JSON, отдаёт updates widgets; JS value expressions связывают поля. `serialize()`/`loadDashboard()` позволяют сохранять JSON, UI умеет local file save/load; database persistence, private/public sharing и user management **намеренно не входят** в OSS client. Polling/refresh зависит от datasource plugin. [README/API](https://github.com/Freeboard/freeboard/blob/v1.1.0/README.md), [plugin guide](https://freeboard.github.io/freeboard/docs/plugin_example.html).
4. **Embedding / auth / инфраструктура.** Static app работает без backend. Host сам добавляет auth/storage и private endpoint; старые cross-origin/JSONP варианты README не переносить как рекомендованную защиту. Изолированный iframe проще отделяет устаревшие глобальные JS/CSS зависимости, чем прямое внедрение в Loginom DOM.
5. **API / AI.** Singleton JS API (`initialize`, `setEditing`, datasource/widget plugin registration), serializable dashboard JSON. Готовые актуальные official Skill/MCP не подтверждены; агент может генерировать config, но должен знать plugin-specific settings и не вставлять секреты в browser config.
6. **Схема Loginom / свой код: high для BI.** Написать Loginom datasource plugin и виджеты/aggregations; сериализовать dashboard + node binding в хранилище хоста; повторное выполнение узла отправляет новый JSON update. Экономится базовый pane editor, но большая часть tabular analytics остаётся своей.
7. **Неизвестное / минимум проверки.** Pinned tag в современных браузерах/CSP, JSON save→cold-load, обновление real rows и отсутствие старых внешних сервисов. Наличие рабочего demo не компенсирует длительное отсутствие подтверждённого сопровождения; предпочтение более активной основе — инженерный вывод.

### C16. Apache Superset

1. **Архитектура, лицензия, выпуск.** Python/Flask + React, запросы к внешним SQL-движкам, отдельная metadata DB; Apache-2.0. Стабильный ASF release **6.1.0, 13.05.2026**. GitHub **7.0.0rc2, 16.10.2026 — prerelease**, а не выпущенная стабильная «линия 7» из Deep Research. Проект активно развивается. [ASF releases](https://release-catalog.apache.org/superset/index.html), [GitHub releases](https://github.com/apache/superset/releases), [лицензия 6.1.0](https://github.com/apache/superset/blob/6.1.0/LICENSE.txt).
2. **Готовая аналитика.** Explore с визуальным выбором измерений/метрик, SQL Lab, вычисляемые поля, фильтры, native dashboard filters, сетка нескольких charts, редактор layout. Редактирование предоставляется полноценным приложением. [Документация](https://superset.apache.org/docs/intro).
3. **Данные и жизненный цикл.** Штатный путь — SQL datasource; браузерный массив не является datasource Embedded SDK. Публиковать результат в таблицу/стабильное представление PostgreSQL/ClickHouse, обновлять данные атомарно, сохранять metadata ресурсов в Superset. Фильтры и агрегации выполняет SQL; refresh повторяет запросы с учётом cache. [Источники](https://superset.apache.org/docs/databases/), [API charts релиза](https://github.com/apache/superset/blob/6.1.0/superset/charts/api.py).
4. **Встраивание и инфраструктура.** Официальный Embedded SDK открывает dashboard в iframe через guest JWT, allowed domains и RLS; доверенный backend выдаёт токен. Это **viewer**, не встроенный авторский редактор. Нужны Superset, metadata PostgreSQL/MySQL; Redis/Celery добавляются для cache/async/reporting, не являются доказанным минимумом каждого просмотра. [SDK](https://github.com/apache/superset/tree/6.1.0/superset-embedded-sdk), [guest API](https://github.com/apache/superset/blob/6.1.0/superset/security/api.py), [deployment](https://superset.apache.org/docs/installation/).
5. **Для AI.** REST `/api/v1` создаёт database/dataset/chart/dashboard; есть import/export. `params`/layout — сериализуемый JSON, однако не единая простая высокоуровневая dashboard DSL. Готовый официальный end-user AI Skill не подтверждён; совпадение имени `superset` на skills.sh недостаточно. Независимые `@superset-ui` chart plugins можно извлечь как renderers, но они не поставляют весь Explore/editor без окружения Superset.
6. **Проект интеграции.** Адаптер rows → SQL publisher; skill → dataset → 3 charts → dashboard; в Loginom хранить UUID и ревизию данных; token broker → iframe, ссылка «Редактировать» → Superset UI. **Средний** собственный код, полноценный внешний сервис.
7. **Спорное и PoC.** На 6.1.0 проверить программное создание native filters/layout, восстановление после перезапуска, guest-RLS двух пользователей и сохранность ручной правки при повторной публикации результата. Режим 7 RC не использовать для подтверждения свойств 6.1.0.

### C17. Metabase

1. **Архитектура, лицензия, выпуск.** JVM/Clojure + React; отдельная application DB и SQL/другие источники. OSS **AGPL-3.0**, Enterprise-каталоги под коммерческой лицензией. Высшая проверенная стабильная OSS версия **v0.65.2, 30.10.2026**; одновременно выпускаются maintenance/LTS-патчи (v0.64.4). Проект активен. [Релизы](https://github.com/metabase/metabase/releases/tag/v0.65.2), [LICENSE](https://github.com/metabase/metabase/blob/v0.65.2/LICENSE.txt), [embedding license](https://www.metabase.com/license).

3. **Данные и обновление.** Для произвольного результата узла — публикация SQL-таблицы либо CSV upload в настроенную writable DB; upload не означает отсутствие storage. Сохранённые вопросы/MBQL и dashboard живут в application DB. Стабильная таблица позволяет обновлять данные без пересоздания charts; схема и metadata sync требуют согласования. Refresh dashboard не запускает Loginom. [Uploads](https://www.metabase.com/docs/latest/databases/uploads), [API](https://www.metabase.com/docs/latest/api-documentation).
4. **Embedding/auth/infra.** OSS/Starter имеют guest view-only embeds; authenticated modular embedding/React SDK с SSO и full-app embedding — Pro/Enterprise. Guest-режим не даёт встроенный редактор/drill-through и не наследует пользовательские права как SSO. Нужны JVM-сервис, production application PostgreSQL и источник. [Разграничение режимов](https://www.metabase.com/docs/latest/embedding/modular-embedding), [guest](https://www.metabase.com/docs/latest/embedding/guest-embedding), [overview](https://www.metabase.com/docs/latest/embedding/start).

Headless JWT делегирование агента — Pro/EE. Официальные agent skills касаются embedding setup/upgrades/migrations, а не готового Loginom dashboard workflow. YAML serialization имеет собственные тарифные границы. [MCP](https://www.metabase.com/docs/latest/ai/mcp), [исходник релиза](https://github.com/metabase/metabase/blob/v0.65.2/src/metabase/mcp/README.md), [skills](https://www.metabase.com/docs/latest/embedding/ai-agent-resources).
6. **Проект интеграции.** Rows → Postgres → sync metadata → вопрос/MBQL → dashboard REST/MCP; сохранять ID, guest URL либо лицензированный authenticated embed. Правки в OSS выполнять в отдельном Metabase UI. **Средний** код, компактнее многих BI-стеков.
7. **PoC.** Чистый v0.65.2 без enterprise key: проверить MCP OAuth и dashboard write, необходимые API permissions, view-only guest-фильтры; отдельно показать, какие authoring/SSO операции требуют платной редакции. Проверить decimal/date/null и обновление без потери пользовательских правок.

### C18. Redash

1. **Архитектура, лицензия, выпуск.** Python API/workers + React, PostgreSQL metadata/results и Redis/очереди; **BSD-2-Clause**, стабильный **v26.9.0 от 24.09.2026**, активные релизы 2025–2026. Старые сообщения об остановке Hosted Redash не доказывают остановку OSS. [Релиз](https://github.com/getredash/redash/releases/tag/v26.9.0), [код/лицензия](https://github.com/getredash/redash/tree/v26.9.0), [self-hosting](https://redash.io/help/open-source/setup/).
2. **BI/editor.** Query → visualization → dashboard, несколько перемещаемых/изменяемых панелей, chart/table/pivot, параметры и фильтры, ручная настройка visuals. Основной query editor рассчитан на SQL/YAML, не равен богатому no-code semantic builder. [Начало работы](https://redash.io/help/user-guide/getting-started/), [dashboard editing](https://redash.io/help/user-guide/dashboards/dashboard-editing/).
3. **Loginom без отдельного SQL-хранилища — реальный вариант.** Официальный **JSON datasource** читает HTTP JSON с headers/auth/method/body; Query Results Data Source выполняет SQL над сохранёнными/свежими результатами, давая агрегации. Поэтому внешняя SQL-копия результата **не обязательна**: нужен наш доступный Redash server endpoint со snapshot. Это всё ещё не передача массива напрямую React-компоненту. Scheduled query refresh и `max_age` управляют cache; параметры влияют на допустимость embedding. [JSON](https://redash.io/help/data-sources/querying/json-api/), [query runner 26.9.0](https://github.com/getredash/redash/blob/v26.9.0/redash/query_runner/json_ds.py), [QRDS](https://redash.io/help/user-guide/querying/query-results-data-source/).
4. **Embedding/auth/infra.** Есть iframe/share links; публичный dashboard по ссылке и аутентифицированный просмотр различаются. Редактор открывается как Redash-приложение. PostgreSQL/Redis/server/workers остаются даже при JSON datasource. [Sharing](https://redash.io/help/user-guide/dashboards/sharing-dashboards/), [параметры и embedding](https://redash.io/help/user-guide/querying/query-parameters/).
5. **AI/API.** API keys, API queries/visualizations/dashboards/widgets, polling jobs; Python `redash-toolbelt` — официальный набор автоматизации. YAML JSON-запроса и JSON visualization options подходят агенту. Официальный end-user Skill/MCP в изученных first-party материалах не подтверждён. API-docs сами предупреждают об ограниченной полноте; исходники handlers — важнее догадок. [API](https://redash.io/help/user-guide/integrations-and-api/api/), [handlers](https://github.com/getredash/redash/tree/v26.9.0/redash/handlers), [toolbelt](https://github.com/getredash/redash-toolbelt).
6. **Интеграция.** Snapshot endpoint → JSON query → QRDS aggregates → visuals/widgets/dashboard → ID в Loginom. Обновление заменяет snapshot и принудительно обновляет queries. **Средний** код; этот путь стоит сравнить с Superset как более простую серверную архитектуру.
7. **PoC.** Проверить точные типы JSON, порядок refresh JSON→QRDS, параметры внутри shared iframe, revocation ссылки и ручную правку layout. Отдельно измерить объём результатов/caching: QRDS не обещает масштаб warehouse.

3. **Loginom/refresh.** Собственный endpoint JSON → API connection → reusable dataset → charts. Можно обойтись без внешней SQL-копии; Chartbrew API получает endpoint, headers, pagination и nested fields, группирует/агрегирует данные и сохраняет результаты/cache. Scheduled refresh перечитывает источник; публикация нового результата остаётся у Loginom. [API integration](https://chartbrew.com/integrations/api), [source plugin guide](https://github.com/chartbrew/chartbrew/blob/v6.0.0/source-plugin-guide.md).
4. **Embedding/auth/infra.** Published dashboard/chart iframe предусмотрены; private auth/roles и editor — отдельные пути, не доказанный независимый embedded authoring SDK. Нужны API/frontend, metadata DB, Redis и доступный источник. FSL summary разрешает некоторые embeds, но бесплатный OEM/resale всего BI из этого не следует. [Embedding](https://chartbrew.com/features/embedded-reports).
5. **AI/API.** Реальные `ProjectRoute`/`ChartRoute` дают создание/изменение ресурсов. В 6.0 есть официальный **MCP `/mcp` с OAuth/API keys**, read/refresh, dataset save и filters write. **`create_chart_preview` создаёт временный preview, не размещает постоянную панель dashboard**; source exploration первоначально ограничен Postgres/MySQL/MCP. Подтверждён agent guide, отдельный ready end-user `SKILL.md` не установлен. [Project API](https://github.com/chartbrew/chartbrew/blob/v6.0.0/server/api/ProjectRoute.js), [Chart API](https://github.com/chartbrew/chartbrew/blob/v6.0.0/server/api/ChartRoute.js), [MCP точного релиза](https://github.com/chartbrew/chartbrew/blob/v6.0.0/server/docs/mcp-server.md).
6. **Интеграция.** Snapshot JSON endpoint → connection/dataset REST → dashboard/project + charts REST → saved project ID → iframe; MCP полезен для exploration/filters, полного авторства только им не обещать. **Средний** код, хорошие HTTP capabilities.
7. **PoC.** На 6.0 проверить API datasource, типы/aggregation, private embed и постоянное размещение после MCP preview, re-open после restart и refresh snapshot. До продукта разрешить FSL/OEM вопрос; готовый editor функционально существует, юридическая пригодность пока не подтверждена.

### C29. Blazer

1. **Архитектура/лицензия/выпуск.** Небольшой **Ruby on Rails engine**, Chartkick/JS charts, SQL adapters и ActiveRecord persistence. **MIT**, RubyGems **3.5.2, 25.09.2026**. GitHub Releases пусты: отсутствие release-страницы не означает отсутствие опубликованного gem. Docker wrapper доступен отдельно. [RubyGems metadata](https://rubygems.org/api/v1/gems/blazer.json), [код 3.5.2](https://github.com/ankane/blazer/tree/v3.5.2), [README](https://github.com/ankane/blazer).
2. **BI/editor.** Сохранённые SQL queries автоматически получают chart по типам/порядку колонок; dashboards объединяют несколько queries, показывая chart либо таблицу. Есть variables/smart variables, cohorts, alerts/checks. Это готовый минимальный BI UI, но не универсальный drag/drop chart grammar и не богатый no-code semantic editor.
3. **Данные/persistence/refresh.** Rows→SQL table в Postgres/MySQL/поддерживаемом engine; можно CSV upload в PostgreSQL через встроенный uploads module. Это серверная загрузка в таблицу, не browser-only datasource. Queries/dashboards сохраняются, кэш настраивается и может обновляться принудительно; filter variables подставляются в запрос. Стабильная таблица переживает повторный run Loginom без изменения dashboard IDs. [Uploads/variables/cache](https://github.com/ankane/blazer/blob/v3.5.2/README.md).
4. **Embedding/auth/infra.** Встраивается **в Rails application** через `mount Blazer::Engine`; это действительно независимый от крупной BI платформы компонент, но с Ruby backend. Basic auth, Devise или `before_action` интегрируют существующую Rails auth. Прозрачный Loginom SSO/iframe authoring не входит в готовый контракт; нужны Rails app+metadata/data DB+reverse proxy.
5. **AI/API/конфигурация.** SQL и `blazer.yml` — простая декларативная поверхность. Rails controllers/models для dashboards/queries доступны, но проверенного публичного versioned REST SDK/MCP/готового dashboard Skill нет. Прямое создание `Blazer::Query`/`Dashboard` собственным маленьким серверным endpoint надёжнее притворного внешнего API. [Routes](https://github.com/ankane/blazer/blob/v3.5.2/config/routes.rb), [controller](https://github.com/ankane/blazer/blob/v3.5.2/app/controllers/blazer/dashboards_controller.rb), [model](https://github.com/ankane/blazer/blob/v3.5.2/app/models/blazer/dashboard.rb).
6. **Интеграция.** SQL publisher → наш Rails endpoint создаёт queries/dashboard → URL в Loginom. **Низкий–средний** код для базового SQL dashboard; стоимость выше, если нужен привычный визуальный конструктор, которого Blazer не обещает.
7. **PoC.** Два агрегатных SQL запроса+таблица, общий variable, сохранение/restoration и iframe auth. Пользователю вручную изменить query и состав panels; сравнить UX с требуемым «ручным редактированием». Не добавлять собственный BI builder вокруг Blazer только ради устранения его сознательной простоты.

### C30. Querybook

1. **Архитектура/лицензия/выпуск.** Pinterest SQL/DataDoc workspace: React/TypeScript, Python server/workers/scheduler, MySQL metadata, Redis и search index. **Apache-2.0**, последняя опубликованная GitHub Release **v3.41.4, 22.04.2025**; текущие issue/branch изменения есть, но не равны свежему выпуску. [Release](https://github.com/pinterest/querybook/releases/tag/v3.41.4), [LICENSE](https://github.com/pinterest/querybook/blob/v3.41.4/LICENSE), [Compose](https://github.com/pinterest/querybook/blob/master/docker-compose.yml).
2. **Готовая аналитика.** DataDocs с SQL/text/chart и в release3.41 Python/Pyodide cells, collaborative editing, query review, catalog/lineage, schedules и GitHub versioning. Несколько charts в документе поддерживаются; это **notebook/workspace**, а не доказанный универсальный dashboard grid с BI-wide filters/editor.
3. **Loginom/данные.** Публиковать результат в SQL engine, подключённый к Querybook; queries/parameters и code создают фильтрацию/агрегации. DataDoc сохраняется сервером, schedule/run повторяет запросы. Pyodide cells могут анализировать query DataFrames в браузере, но это не публичный компонент, принимающий живой Loginom rows как источник всей платформы. [Overview](https://www.querybook.org/), [DataDoc operations source](https://github.com/pinterest/querybook/blob/v3.41.4/querybook/server/datasources/datadoc.py).
4. **Embedding/auth/infra.** Есть конкретный **embedded SQL editor iframe** с `SEND_QUERY`/`SET_QUERY`/`SUBMIT_QUERY` postMessage. Это полезный независимый экран редактирования SQL, **не dashboard builder SDK**. Для полного DataDoc просмотра нужна application auth/session и проверка iframe. Типовой Compose — web/worker/scheduler + MySQL + Redis + OpenSearch/search service; не самый лёгкий результатный viewer. [Embedded editor](https://www.querybook.org/docs/integrations/embedded_iframe/).
5. **AI/API/декларации.** First-party API handlers создают/изменяют DataDocs/cells/schedules/access; cell `context/meta` сериализуются, но это внутренний формат документа. Есть text-to-SQL, semantic search/completion; наличие native AI не подтверждает официальный external dashboard-generation Skill/MCP. Независимый поддерживаемый notebook/chart package не установлен.
6. **Интеграция.** SQL publisher → DataDoc с queries/chart meta → authenticated URL; при нужде встроить только SQL editor. **Высокий** код для приведения к привычному dashboard UX; **средний** для аналитического notebook над результатом.
7. **PoC.** На published3.41.4 создать DataDoc API, два charts+table, параметры и schedule; проверить, достаточно ли именно notebook-editing и разрешается ли iframe. Если обязательны global cross-panel filters/drag-resize dashboard, сначала доказать эти функции, а не считать charts в cells их эквивалентом.

### C31. OpenSearch Dashboards

1. **Архитектура/лицензия/выпуск.** Node.js/React frontend server поверх OpenSearch cluster; объекты и данные в индексах. **Apache-2.0**, **3.9.0 опубликован 12.10.2026**; дата commit/tag внутри release раньше даты публикации. Активный проект с matching stack/plugins. [Release](https://github.com/opensearch-project/OpenSearch-Dashboards/releases/tag/3.9.0), [LICENSE](https://github.com/opensearch-project/OpenSearch-Dashboards/blob/3.9.0/LICENSE.txt), [config](https://github.com/opensearch-project/OpenSearch-Dashboards/blob/3.9.0/config/opensearch_dashboards.yml).
2. **BI/editor.** Visualize/Discover, несколько изменяемых panels, query/time/global filters, агрегации, сохранение dashboards. Подходит не только для логов: обычные business records тоже индексируются. Но search/index semantics отличаются от табличного SQL; transforms/joins и точность метрик требуют явного решения. [Dashboard guide](https://docs.opensearch.org/latest/dashboards/dashboard/index/).
3. **Loginom/обновление.** Адаптер bulk-index rows с явным mapping типов, стабильным alias и dataset revision. Browser rows напрямую renderer не подаются; `_refresh` индекса и dashboard auto-refresh — разные стадии. Saved objects (dashboard/visualization/index pattern) сохраняются в системных индексах; exports/imports — NDJSON с references. [Saved objects](https://docs.opensearch.org/latest/dashboards/management/saved-objects/), [bulk API](https://docs.opensearch.org/latest/api-reference/document-apis/bulk/).
4. **Embedding/auth/infra.** Share/embed iframe, Security plugin roles/tenants, поддержка внешней identity на stack уровне. Public/anonymous share не заменяет node ACL. Редактор — приложение Dashboards; standalone authoring SDK без OpenSearch не подтверждён. Минимум cluster+Dashboards+постоянный storage и security/reverse proxy; размер определяется нашими данными, не демонстрационным compose.
5. **AI/API.** OpenSearch REST, dashboards saved-object APIs и plugin APIs, JSON/NDJSON. Есть официальный MCP stack: in-cluster ML Commons MCP c3.3 и standalone варианты; **зарегистрированные data tools не означают полный dashboard CRUD/authoring**. Проверенного готового dashboard-creation Skill для Loginom нет. [MCP](https://docs.opensearch.org/latest/ml-commons-plugin/mcp/in-cluster-mcp-server/), [API source](https://github.com/opensearch-project/OpenSearch-Dashboards/tree/3.9.0/src/plugins/saved_objects_management/server).
6. **Интеграция.** Rows→bulk index→index pattern→visualization/dashboard resources→saved ID→authenticated iframe. **Средний–высокий** код, большой инфраструктурный шаг ради уже табличного результата; разумен при существующем OpenSearch или поисковых требованиях.
7. **PoC.** Проверить decimal/long/date/null mapping, terms cardinality/aggregate accuracy, atomic alias swap, access isolation и сохранность редакторских изменений. Не переносить API/плагины Kibana по историческому родству: современные продукты расходятся.

### C34. Rill

1. **Архитектура, лицензия, версия.** Go runtime, web UI, SQL-модели и YAML-ресурсы поверх OLAP, в локальном Developer обычно DuckDB. Apache-2.0; опубликованный **v0.91.0, 29.10.2026**, репозиторий активно обновляется. Локальный Rill Developer и коммерческий Rill Cloud имеют разное назначение: Developer документирован как среда разработки, Cloud — публикации и коллективного потребления. Метрики и layout описываются в YAML/SQL, локальный UI помогает авторингу и показывает preview. Фильтры и агрегации выполняет Rill; SQL/YAML сохраняются как файлы проекта. Обновление требует перечитывания/refresh source, а не передачи новых rows существующему React-компоненту. Атомарную замену снимка и политику schema change делает адаптер.
4. **Embedding, auth, инфраструктура.** Официальный iframe flow вызывает **api.rilldata.com**, получает URL через сервисный токен и передаёт атрибуты пользователя; это документированный **Cloud** путь. Самостоятельный production embedding только из наличия Apache-кода не следует. Для OSS-пути нужны собственное развёртывание runtime/UI и проверка auth. [Iframe и postMessage](https://docs.rilldata.com/developers/embed/iframe).

6. **Интеграция и свой код: средний/высокий.** Сервис публикации снимков, генератор моделей, deploy/refresh и каталог `node → project/dashboard`; для полностью OSS embedded deployment дополнительный security/hosting-контур. Cloud сокращает его ценой отдельного продукта.
7. **Неизвестное и минимальная проверка.** На v0.91.0 открыть Canvas без Cloud, проверить устойчивое сохранение, защищённый просмотр другим пользователем и refresh того же dashboard ID. Не считать успешный локальный preview доказательством production OSS embedding.

## Дополнительные детали независимого embedded SDK

**Malloy Publisher — сильный претендент на серверное embedded решение, но не готовый browser-only rows widget.** Published0.11.0 SDK экспортирует `ReportEditor`, `ReportBuilder`, `DashboardView`, `/client`, `/builder`, `DocumentStorageProvider`. Его можно вынести без Publisher Console: host реализует storage, router, identity, а query backend остаётся Publisher либо совместимым executor. `DocumentStorage` оперирует текстом отчёта, есть BrowserDocumentStorage и пользовательская authoritative persistence; это подтверждено `.d.ts` опубликованного npm tarball. В контракте нет expectedVersion у saveDocument: защита от параллельного перезаписывания остаётся backend. Builder не является просто layout toy: он управляет фильтрами, chart presentation, tiles и новым report; но arbitrary inline query bodies и inherited views не переписывает. Полноценный выбор dimensions/measures предоставляет отдельный Explorer, который нужно связать с сохранением tile. [Released SDK source](https://github.com/malloydata/publisher/tree/98e2ec5786c8db2b529c75cabbc9ab27fc64fca8/packages/sdk), [reported editor boundaries](https://github.com/malloydata/publisher/blob/98e2ec5786c8db2b529c75cabbc9ab27fc64fca8/docs/reports.md).

**Причины проверять Malloy в финале:** готовые модель, filters, multi-panel, кодовое и ручное создание, persistence contract, Skills/MCP в одном OSS стеке. **Цена:** backend-публикация Loginom snapshots; отдельный auth gateway; достаточно тяжёлые React 19/MUI7 peers и npm Explorer с prerelease-version. Минимальный прототип: host без Console, SDK 0.11.0 и pinned peers, snapshot→Malloy model, Explorer chooses measure/group-by→new tile, manual layout+filter→save our store→restart→refresh new snapshot. Отдельно отказ прямому unauthenticated query и запрет читателю operator write routes. Это проверяет реальное сокращение собственной разработки.

**Sidemantic browser kit — подтверждённая основа агентно созданного explorer, пока менее подтверждённый общий ручной builder.** Tagged0.13 содержит переносимые React components, self-contained static bundle, rows adapters и filter state helpers. Без всей платформы его использовать можно; готовый query runtime можно подключить Python HTTP, либо собирать WASM из source. Python wheel уже включает web UI, но отдельный kit распространяется через source/plugin assets. `sidemantic-wasm` по указанному в Skill имени не опубликован в npm на дату проверки; этот путь не считать готовой зависимостью. Ни schema-import в 15 форматов, ни визуальные controls не доказывают durable dashboard designer. [Canonical components](https://github.com/sidequery/sidemantic/blob/v0.13.0/docs/ui-architecture.md), [copy/scaffold/query workflow](https://github.com/sidequery/sidemantic/blob/v0.13.0/plugins/sidemantic/skills/webapp-builder/SKILL.md).

**Причины сохранить Sidemantic в сравнении:** kit принимает row results, есть готовые leaderboards/time-series/crossfilters, modeler/webapp-builder Skills и несколько transports. **Цена:** собственный authoring/persistence и AGPL композиция; непроверенный browser semantic build. Минимальный прототип: скопировать static bundle из v0.13, подключить 3 Loginom dataset panels к одному query contract, выбрать metric/dimension, crossfilter, заменить данные и восстановить выбранную конфигурацию. Отдельно подтвердить возможность добавить произвольную новую панель без правки кода; если придётся писать builder, измерять это как свою разработку, не готовую функцию Sidemantic.

**Drizzle Cube — сильный альтернативный кандидат для встроенного конструктора с SQL/backend.** По сравнению с двумя предыдущими есть AnalysisBuilder и AnalyticsDashboard в опубликованном 0.12.2, а не только generic chart primitives. Own auth/config CRUD остаются, но выбор полей/мер и multi-panel не нужно писать заново. Сравнивать с Perspective следует по полной цепочке ручной правки/сохранения/обновления, а не только по числу charts; зрелость одного semantic драйвера и dynamic schema bootstrap проверяются адресно. [Published exports](https://github.com/cliftonc/drizzle-cube/blob/v0.12.2/package.json), [dashboard persistence](https://www.drizzle-cube.dev/client/dashboard-persistence/).

## Что изменилось относительно прежних гипотез

1. **React/shadcn — удобная среда создания приложения, но не готовая BI-основа.** Если сохранение аналитической конфигурации, многопанельность и ручная доработка важны, сначала стоит использовать готовые интерфейсы, а не писать их поверх chart library.
2. **Perspective содержит многопанельный workspace уже в опубликованном viewer5.6.1.** Добавлять Gridstack как обязательный слой неверно. Главная оставшаяся работа — Loginom data/lifecycle/persistence.
3. **SQLRooms 0.29.0 содержит Mosaic dashboard/chart builder и AI exports.** Нельзя отсеивать его по старому описанию toolkit. Вместе с тем latest Mosaic и dependency Mosaic внутри SQLRooms — разные версии.
4. **Malloy следует оценивать вместе с Publisher**, который уже имеет опубликованные reports/dashboard authoring возможности. **Sidemantic** также не ограничивается headless API: browser/UI части существуют; степень готовности общего BI authoring нужно проверять отдельно.
5. **Redash не сводится к внешней SQL-таблице:** JSON runner + Query Results Data Source дают другой канал результатов. Наличие отдельного Redash backend всё равно необходимо.
6. **Лицензии проверяются по компонентам.** GoodData MIT core не является свободным dashboard-модулем; Chartbrew FSL не обычный MIT; Graphic Walker LICENSE2 неоднозначен; DataEase и Helical имеют дополнительные условия; Kibana содержит AGPL-вариант части исходников, но это не переносится на весь default distribution.
7. **Качество agent tooling нельзя оценивать только по skills.sh.** Кроме shadcn подтверждены практические официальные материалы Vizro, HoloViz, Gravity UI, Grafana, Lightdash, Rill, DataLens и других кандидатов. У каждого различается предмет: UI code, dashboard resources, платный embedding или работа в live runtime.
8. **Будущая версия не равна опубликованной стабильной.** Superset 7.0 RC, GitHub/main/package versions Graphic Walker/Drizby/Evidence и ранние библиотеки требуют точной фиксации версии. Исходный DR — каталог гипотез, а не реестр доказанных совместимостей.

Источники каждого исправления находятся в соответствующих карточках; локальные записки сохранены как исторические материалы, их выводы не переписаны задним числом.

## Рекомендации по трём архитектурам

### 1. Решение преимущественно в браузере

**Выбрать Perspective как первую основу AI Skill.** Агент формирует сохраняемый workspace над schema+rows, пользователь дорабатывает аналитические поля/фильтры/панели штатными средствами; backend для вычислений не обязателен. Хранение артефакта и его привязку к узлу реализовать узко, отдельно от движка. Первый prototype должен проверять весь путь открытия, сохранения и refresh, а не только render одной таблицы.

Причина выбора — комбинация прямых данных, готовых аналитических операций, редактора и многопанельного round-trip в опубликованном артефакте. Это соответствует заданию ближе, чем изначальный shadcn-stack или chart renderer. **Риск** — WASM/worker/типизация данных и фактическая ergonomics workspace в Loginom, а не отсутствие подходящего API. Если нужен исключительно произвольный авторский дизайн без BI self-service, Observable/Vega/React остаются более свободными способами генерации, но сохраняют больше собственного поведения.

**SQLRooms — полноценный конкурент**, если ценность встроенного SQL/joins/расширяемых аналитических tools оправдывает сборку собственного room. Mosaic отдельно нужен для более специальной связанной аналитики, а DuckDB-WASM отдельно — только когда действительно требуется собственный SQL-слой. Не добавлять их к Perspective автоматически.

### 2. Встроенный визуальный конструктор в своём приложении

**Проверить SQLRooms 0.29.0/Mosaic первым альтернативным прототипом**, если требуется более продуктовый React shell с собственными видами анализа, AI tools и управляемым authoring flow. Из исходного списка он даёт опубликованные dashboard/chart components, а не только сырой renderer. Persistence helpers сокращают работу, но не заменяют серверное сохранение и восстановление данных. Объём собственной сборки выше, чем у Perspective.

**Perspective может закрыть и этот сценарий**, если его штатного authoring достаточно. Не нужно выбирать второй framework ради отдельного названия категории. **Graphic Walker** предпочтителен, когда ключевая функция — знакомый визуальный chart authoring по измерениям/мерам; нужно принять отдельный multipanel shell, общий filter state и выяснить branding/license условия. **DashKit + Gravity Charts** — разумный выбор для тщательно оформленного собственного конструктора, если команда сознательно принимает разработку query/measure editor; наличие layout editMode не заменяет этот editor.

**Drizzle Cube** — сильный вариант встроенного React BI при отдельном SQL backend: готовые AnalysisBuilder/Dashboard экономят собственный editor, но требуют model/API и публикации результата узла. Его преимущество растёт при общей модели метрик и серверном контроле доступа; для прямого browser dataset путь SQLRooms короче. Дополнительный backend разрешён, поэтому Drizzle не исключается по этому признаку. **Malloy Publisher** стоит сравнить, если semantic model и расширяемые отчёты важнее прямого rows-only API. **Supersubset, DuckViz, Analytix, Data Canvas** по доказанным источникам имеют конкретные нерешённые вопросы сопровождения, происхождения/условий или persistence; они не отвергнуты «потому что молодые», но пока несут больше неопределённости именно в обязательных функциях. Подробнее — соответствующие карточки и их дешёвые проверки.

### 3. Самостоятельная BI-платформа

**Выбрать Superset 6.1.0 первым платформенным кандидатом**, если нужно готовое отдельное BI-приложение и результат узла можно публиковать в поддерживаемый datasource. Схема: browser/server delivery → SQL snapshot → dataset/charts/dashboard через REST → сохранённый UUID → Embedded SDK для просмотра; ручная доработка в авторизованном основном UI. Дополнительный backend допустим по заданию, поэтому инфраструктура сама по себе не является основанием исключения.

**DataLens OSS** — близкая альтернатива для русскоязычного self-service и готовых dataset/formula/dashboard средств. Прежде выбора доказать автоматическое создание объектов и приватное встраивание **именно OSS**, не подменяя их Cloud/Enterprise SDK. **Shaper** — особенно подходящий компактный серверный вариант: JSON ingest, SQL-as-dashboard, официальный agent workflow и embed JWT, один binary с постоянным volume. Он требует меньше сервисов, но авторинг основан на SQL; нужно доказать корректную замену snapshot вместо append и постоянный deploy вместо temporary API dashboard. **Redash** — более простой путь, если JSON endpoint результатов предпочтительнее SQL publication и SQL-ориентированный authoring приемлем. **Metabase** особенно удобен для ручных вопросов/дашбордов, но требуемый embedding/auth flow должен помещаться в выбранную редакцию; нельзя брать платный SDK/SSO за OSS default.

**Helical Insight 7** переоценён по новой функциональности, но конфликт/область AGPL и HICL условий требуют прояснения до продуктового embedding. **Frappe Insights** полезен как самостоятельная exploratory BI альтернатива, если его стек уже знаком. **Lightdash, Cube, MetricFlow** больше оправданы общей семантикой/warehouse, чем одним произвольным результатом узла. **Grafana** предпочтительнее для временных operational metrics; **OpenSearch/Kibana** — когда данные уже живут в соответствующем search store, а не ради одной dashboard-интеграции.

Если AI должен выпускать **проверяемый декларативный артефакт**, а full visual editor не обязателен, **Vizro** и **Malloy Publisher** стоит поднять выше стандартных BI-платформ. У Vizro особенно полезны официальный end-to-end skill и MCP; Panel — сильная более общая Python-альтернатива. Rill не исключается, но Cloud embedding нельзя считать доказанным self-hosted OSS решением. Эти варианты сохраняют серверный жизненный цикл приложения, которого у browser components нет.

## Проверочные прототипы финалистов

Это **предложения следующего шага**, не выполненные тесты и не требование установить все платформы. Сначала достаточно P1; P2 позволяет проверить наиболее сильную альтернативу. P3 нужен при выборе платформенной архитектуры. Остальные снимают конкретные условия выбора.

### Общий контрольный набор

Один небольшой dataset с независимо вычисленными count/sum/group totals; NULL, Unicode, дата/timezone, число за 2^53 и длинная строка. Две revisions с одинаковым числом строк, но разными значениями, затем изменение схемы. Положительный результат — правильные показатели и фильтры, сохранённые ручные изменения после закрытия/повторного открытия, refresh той же привязки и явная реакция на несовместимую схему. Принятые пользователем реальные объёмы пока неизвестны: замеры делать на одинаковых размерах и на наблюдённой типичной/максимальной выборке, не обещать performance по чужому benchmark.

Минимально фиксировать framework/build version, тип/размер данных, время загрузки и refresh, память, размер assets и результат cold reopen. Отдельно проверять кнопку в меню и toolbar, потому что работа библиотечного примера не доказывает весь пользовательский путь.

### P1 — Perspective: минимальный полный путь

Закрепить `@perspective-dev/client/viewer`5.6.1 и совместимые плагины. Из реального узла создать Table и workspace из pivot, bar/line и второго аналитического представления; общий/master filter. Агент генерирует config, пользователь меняет группировку и layout. Сохранить `saveWorkspace()` через минимальный host storage, закрыть вкладку, снова открыть из обеих точек Loginom и `restoreWorkspace()`. Выполнить узел заново, заменить dataset без потери edits. Проверить assets/CSP/worker на minified клиенте. **Решающий вопрос:** достаточно ли штатного UI и реально ли сохраняется весь workspace, включая общие filters, при обновлении данных?

### P2 — SQLRooms/Mosaic: сравнение встроенного конструктора

Закрепить SQLRooms 0.29.0 и его dependency graph. Загрузить тот же dataset в browser DuckDB; использовать опубликованные `MosaicDashboard`/`MosaicChartBuilder`, две связанные panels и settings. Сохранить только конфигурационные slices, уничтожить store/DB, заново загрузить rows и восстановить dashboard. Заменить таблицу новой revision и доказать query invalidation. Сравнить с P1 количество своего состояния/кода, функциональность editor и memory/latency на тех же данных. **Решающий вопрос:** оправдывают ли свобода room и AI exports дополнительную собственную сборку и storage?

Для SQL-backend варианта встроенного конструктора альтернативный P2 — **Drizzle Cube**: на поддерживаемой Drizzle БД определить одну cube-модель результата узла, загрузить snapshot, собрать AnalysisBuilder+AnalyticsDashboard, вручную изменить chart/layout, сохранить callbacks config в host storage и восстановить после server/client restart. Проверить refresh той же таблицы, фильтры и серверное ограничение доступа; сравнить объём своего model/auth/persistence с готовым editor. Это альтернатива P2, а не дополнительный обязательный gate.

### P3 — Superset: полноценная BI рядом с Loginom

Поднять закреплённый stable6.1.0, metadata DB и один data source; production Celery/cache добавлять только для реально используемых операций. Доставить результат узла в SQL snapshot с атомарной публикацией. REST создать dataset→charts→dashboard, прочитать обратно и сохранить UUID. Trusted backend выдаёт guest token ограниченного dashboard; Loginom показывает Embedded SDK. Пользователь редактирует в основном Superset UI; повторное открытие/refresh не пересоздаёт и не затирает chart. Проверить expiry token, доступ к данным и обновление cached результатов. **Решающий вопрос:** сколько работы стоят публикация/ACL/lifecycle по сравнению с уже готовым BI authoring?

### P4 — DataLens OSS: спорный API и embedding

На точном Compose v2.9.0, `HC=0`, подключить один результат через поддерживаемый SQL datasource. Найденным OSS API/gateway создать dataset→chart→dashboard и прочитать IDs/config обратно. Отдельно проверить штатный login/iframe/cookies/право пользователя; не использовать Cloud JWT example как замену. Изменить chart вручную, обновить источник и убедиться в сохранности. **Решающий вопрос:** можно ли получить требуемые automation и private embedding без коммерческих компонентов/неподдерживаемого внутреннего API? Если только новая вкладка работает, так и зафиксировать; это другое поведение.

### P5 — Graphic Walker: ценность chart authoring

Оставить branding до выяснения LICENSE2, закрепить 0.5.3. Передать schema+rows, создать canonical `IChart[]`, редактировать chart, round-trip `exportCode/importCode`; показать три сохранённых chart через renderers в минимальной сетке и один общий filter. Не строить полноценную новую оболочку до проверки этих функций. **Решающий вопрос:** достаточно ли лучше его chart editor, чтобы принять shell/filter разработку и условия поставки по сравнению с Perspective/SQLRooms?

### P6 — Vizro / Malloy Publisher: AI-артефакт с backend

Выбрать один по требуемой модели (Vizro YAML/Pydantic либо Malloy model+Publisher report). Проверить два независимо сгенерированных агентом dashboard на одной схеме официальным schema/API и арифметическим oracle. Сохранить артефакт, перезапустить процесс, открыть из Loginom, обновить источник. Для Publisher отдельно проверить ручное добавление/перемещение tiles и save; для Vizro не ожидать WYSIWYG из факта наличия controls. **Решающий вопрос:** меньше ли ошибок/своего кода даёт декларативный skill workflow при допустимом сервере?

### P7 — Redash: JSON без отдельной SQL-публикации

На 26.9.0 дать JSON runner защищённый endpoint snapshot, затем Query Results Data Source для SQL агрегации по тому же результату. Через API создать query/visualization/dashboard; редактировать вручную; повторить refresh при новой revision без изменения dashboard IDs. Не выдавать API key в client config; проверить, какой доступ имеет embedded link. **Решающий вопрос:** покрывает ли этот более простой маршрут задачу отдельной BI-платформы и устроит ли пользователей SQL-ориентированный editor?

### P8 — Shaper: компактная серверная альтернатива

На v0.26.5 отправить rows через JSON ingest API, создать `.dashboard.sql`, выполнить постоянный deploy, а не temporary API creation. Через серверный короткий JWT открыть React/JS embed. В новой revision удалить часть строк и проверить, что refresh не складывает старые и новые snapshots. После рестарта и истечения временных TTL тот же dashboard должен сохраняться; пользователь должен суметь изменить SQL/параметры. **Решающий вопрос:** достаточно ли SQL authoring вместо визуального BI editor, чтобы выиграть в сложности инфраструктуры и agent workflow?
