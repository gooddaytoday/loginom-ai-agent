# Изоляция dashboard от сессии Loginom

Статус: требования безопасности M0–M6; исходная редакция 3 от 2026-11-11 и база `dashboard-app`, `41224d3b77` — исторический срез. Реализация M2 ведётся по [дизайну от 2026-11-12](../superpowers/specs/2026-11-12-dashboard-m2-design.md), итоги установленного стенда — в [runbook M2](../testing/loginom-ai-agent/dashboard-m2.md). Локальные проверки не заменяют живую приёмку. Черновик и профиль M3 реализованы в исходниках по [дизайну M3](../superpowers/specs/2026-11-12-dashboard-m3-design.md); установленная приёмка ещё не выполнена, её порядок — [runbook M3](../testing/loginom-ai-agent/dashboard-m3.md). Builder и publisher остаются целевыми этапами M4–M6.
План меняет предпосылку [дизайна dashboard](../superpowers/specs/2026-11-09-loginom-dashboard-design.md): там среда считалась доверенной и «код приложения на том же origin имеет доступ к родителю».
Общая архитектура, потоки, развёртывание и этапы работ описаны в [roadmap](../superpowers/specs/2026-11-11-dashboard-architecture-roadmap.md). Здесь — только безопасность.

## Цель

Код dashboard считается недоверенным. Его может написать любой пользователь, агент по инструкции, внедрённой в данные, или зависимость шаблона. Открытый dashboard не получает сессию Loginom, сохранённые пароли, другие узлы и обычные сетевые каналы (остаточные описаны в «Принятых рисках») и не запускает расчёт сам. Он получает от оболочки данные своего узла и показывает их.

Доверенный код: клиент Loginom, оболочка (она же bootstrap) и контейнеры платформы web, publisher и builder. Контейнеры обрабатывают недоверенные данные, но написаны платформой. Ориентир — обычная практика изоляции пользовательского кода: отдельный origin для пользовательского контента и iframe в песочнице ([OWASP Micro Frontend Security](https://cheatsheetseries.owasp.org/cheatsheets/Micro_Frontend_Security_Cheat_Sheet.html)).

## Исходные проблемы до M0/M2

Проверено по коду и на стенде 2026-11-11.

1. Iframe открыт с origin клиента и без `sandbox`. Скрипт приложения обращается к `window.parent`: объектам `bg.*`, DOM сценария, хранилищам и любым запросам от имени сессии. Через `navigator.credentials.get` он может получить пароль, сохранённый галочкой «Запомнить».
2. Приложения раздаются по `/dashboard/apps/` с того же origin. Тот же доступ есть и без iframe: достаточно открыть адрес приложения во вкладке.
3. Без входа доступны `GET /dashboard/current` (последний снимок с реальными строками), а также `sample.json` и `binding.json` опубликованного приложения.
4. Адаптер даёт приложению `change` и `run`: оно само записывает переменные и запускает узел. Через переменные данные попадают в сценарий автора; если в сценарии есть узлы с сетевыми запросами, сервер Loginom отправит их наружу.
5. `publish.mjs` выполняет `npm run typecheck` и `npm run build` из `package.json` приложения на машине публикации, то есть автор приложения выполняет там свой код. Строка `import x from "/путь/к/файлу?raw"` вшивает любой файл этой машины в бандл, который раздаётся без входа.
6. Публикация идёт через `docker cp` и `docker exec`, права на пакет не проверяются. Кто может публиковать, тот может заменить и чужой dashboard.
7. Служба снимков запущена внутри контейнера сервера Loginom и видит хранилище пользователей.
8. Страница клиента отдаётся без защитных заголовков. Заголовок `Host` не проверяется, поэтому чужой сайт может обратиться к стенду через DNS rebinding.
9. Bootstrap вставляется в `index.html` клиента командой `sed` на работающем контейнере, и его целостность ничем не проверяется.
10. Desktop берёт каталог проекта из ответа службы (`sourceDir`) и проверяет только суффикс `/dashboard/apps/<ключ>`. Тот, кто отвечает на `127.0.0.1:32768`, может подсунуть другой каталог. Команды `commands` в снимке тоже приходят от службы, а модель их выполняет.

Уже исправлено: служба слушает loopback, если стенд не задал `DASHBOARD_HOST` (`a11153609e`); хранится не больше 100 снимков (`41224d3b77`).

## Решения владельца (2026-11-11)

- Параметры узла меняет только доверенная оболочка. Приложение только показывает данные.
- Агент получает реальные строки, как и раньше. В M3 образец вырастает с 12 до 100 строк (не больше 512 КиБ) и приходит из снимка. В M2 контракт снимка и исходные значения образца из 12 строк не меняются.
- Чужой dashboard открывает любой, у кого есть доступ к пакету, без проверки и подтверждения. Защита — изоляция.
- Неактивный узел по-прежнему выполняется при открытии автоматически.
- Два режима браузера: **обычный** (по умолчанию) и **строгий** (включается настройкой стенда). Строгий пускает только Chromium 152 и новее; обычный браузер не проверяет.
- Права на публикацию — это права записи в папку пакета; проверяет сам Loginom. Если проверка через Loginom окажется невозможной, на dev-стенде файл кладётся в каталог стенда на этой же машине, без ключей ([roadmap](../superpowers/specs/2026-11-11-dashboard-architecture-roadmap.md), путь Б, spike S1).

## Режимы

Режим задаёт администратор стенда одной настройкой и меняет повторным запуском `install`. Основа защиты в обоих режимах одна: песочница, CSP, `frame-src`, лимиты и протокол ниже.

| | Обычный (по умолчанию) | Строгий |
|---|---|---|
| Браузер | любой современный: Chrome, Edge, Яндекс Браузер, Firefox, Safari | только браузеры, которые проходят пробу (Chromium 152 и новее); остальным показывается отказ с объяснением. Проба проверяет признак, а не версию: браузер с отключённым WebRTC она пропустит (см. «Принятые риски») |
| Хост приложений | отдельный порт того же адреса стенда, тот же сертификат. Локально — `http://dashboards.localhost:32769` | отдельный регистрируемый домен со своим сертификатом |
| `Connection-Allowlist` | отправляется всегда: Chromium 152+ его применяет, остальные игнорируют | отправляется и проверяется пробой перед первым открытием |
| Отдельный процесс для документа приложения | в Chromium 124+ (из-за песочницы); в Firefox и Safari документ может делить процесс с клиентом | Chromium 152+: песочница и отдельный сайт; Firefox и Safari не допускаются (кроме браузера с отключённым WebRTC: проба его пропускает) |
| Утечка показанных данных через WebRTC, `dns-prefetch`, `preconnect` | возможна в браузерах без `Connection-Allowlist` | закрыта в браузерах, прошедших пробу |

Если клиент открыт по HTTPS, хост приложений тоже должен быть на HTTPS: иначе браузер заблокирует iframe как смешанное содержимое. Исключение — `*.localhost`.

## Целевая схема

Три роли с разными правами:

- Клиент Loginom и оболочка — origin клиента. Там же, через Apache, остаётся служба web с путями `/dashboard/…`. До этапа M3 пути `/dashboard/lookup` и `/dashboard/targets` не меняются, поэтому Desktop и `publish.mjs` работают как раньше.
- Хост приложений — другой origin, чем у клиента. В обычном режиме это другой порт того же адреса: origin другой, а iframe в песочнице получает непрозрачный origin; в Chromium 124+ он ещё и в отдельном процессе. Локально клиент открывать по `http://127.0.0.1:32768` (на этом адресе опубликован порт стенда), хост приложений — `http://dashboards.localhost:32769`: Chromium сам направляет `*.localhost` на loopback, и это другой сайт. Локально хост приложений ставится на другой сайт, потому что это бесплатно и ближе к строгому режиму. Другой порт того же хоста — тот же сайт: так устроен обычный режим на удалённом стенде, и это допустимо, потому что изоляцию даёт песочница, а риски того же сайта перечислены в «Принятых рисках». В строгом режиме хост приложений стоит на отдельном регистрируемом домене со своим сертификатом.
- Сборка — контейнер builder без сети, без хранилища Loginom и без секретов; результат проверяет publisher (раздел «Сборка и публикация»).

Хост приложений раздаёт только проверенные файлы сборки по неизменяемому адресу `/apps/<ключ>/<хеш сборки>/`, служебную пробу `/_probe/` (только в строгом режиме) и приём отчётов `/_reports`. Адрес всегда точный, перенаправлений нет. На стенде нет ни `sample.json`, ни `binding.json`: образец строк живёт только в снимке (память, 15 минут) и на компьютере пользователя, а привязка лежит в файле публикации в хранилище. `lookup` возвращает текущую версию приложения.

### Iframe

```html
<iframe sandbox="allow-scripts" referrerpolicy="no-referrer"
  allow="camera 'none'; microphone 'none'; geolocation 'none'; clipboard-read 'none'; clipboard-write 'none'; display-capture 'none'; fullscreen 'none'; payment 'none'; publickey-credentials-get 'none'; identity-credentials-get 'none'; usb 'none'; serial 'none'; hid 'none'; bluetooth 'none'"
  src="<DASH>/apps/<ключ>/<хеш>/"></iframe>
```

Других флагов `sandbox` нет, `allow-same-origin` не добавлять. Документ получает непрозрачный origin, не равный ни одному адресу. У него нет доступа к родителю, хранилищам и сохранённым паролям. Формы, всплывающие окна, `alert` и `prompt`, загрузки и переход верхнего окна запрещены. Атрибут `allow` повторяет `Permissions-Policy` из заголовка: заголовок действует при открытии адреса во вкладке, атрибут — если ответ пришёл без заголовка. Значение `'self'` в них не подходит: оно не совпадает с непрозрачным origin.

### Протокол

1. SDK приложения подписывается на `message` сразу при загрузке модуля и сообщает о готовности: `window.parent.postMessage({type: "loginom-dashboard/ready", version: 1}, "*")`.
2. Оболочка проверяет, что `event.source` — это `iframe.contentWindow`, и передаёт приложению `MessagePort`: `frame.contentWindow.postMessage({type: "loginom-dashboard/init", version: 1}, "*", [port])`. Адресат `"*"` неизбежен: у документа в песочнице нет имени origin, а строка `"null"` не разбирается как адрес. Подмену адресата закрывает принудительный `frame-src` на странице клиента (обязателен в обоих режимах, не `Report-Only`) и, в Chromium 152+, `Connection-Allowlist` приложения: iframe не может перейти на чужой адрес.
3. Оболочка → приложение, только через порт: `{type: "state", parameters, table, error, busy}`. Значения параметров передаются только для показа.
4. Приложение → оболочка, только сообщения окна: `{type: "loginom-dashboard/close", version: 1}` по Esc и `ready`. Оболочка принимает их только от `iframe.contentWindow` ожидаемого dashboard; чужой кадр закрыть его не может. Всё остальное игнорируется.
5. Второй `ready` или второй `load` (независимо от порядка `ready`) закрывает dashboard. Порт передаётся ровно один раз; ожидание первого `ready` ограничено 10 секундами.
6. Таблица ограничена: до 10 000 строк, до 10 000 символов в строковой ячейке и 5 000 000 символов суммарного JSON передаваемых строк; сохраняется целый префикс строк. `state.table` содержит `truncated` и исходное `totalRows`. Это предел состояния приложения, не образца Desktop. Более 50 сообщений за секунду суммарно через окно и обратную очередь порта закрывают dashboard; команд этот порт не принимает. Размер входящего клонируемого сообщения браузер ограничивает сам, поэтому это не защита от всех затрат на его создание.

Объекты `bg.*`, функции и окно Loginom в приложение не передаются. Структурное клонирование их и не пропустит; это проверяет тест.

### Параметры в доверенной шапке

Поля параметров рисует оболочка в шапке над iframe. В M2 это все числовые пользовательские переменные сценария, определённые именем и типом: конечное число, для целочисленного типа — целое. Значение принимается по Enter и уходу из поля через прежнюю последовательную очередь. После расчёта оболочка отправляет приложению новый `state`. Метаданные публикации (подписи, min/max, шаг, сужение набора) относятся к M4; в M2 их контракта нет. Имена и значения выводятся как текст. В шапке также видны имя узла и путь пакета, кнопки «Изменить в чате» и «Вернуться к сценарию».

## Заголовки

Каждый ответ хоста приложений, включая страницы ошибок 404 и 500, несёт один и тот же набор; иначе из `index.html` можно перейти на ответ без заголовков в пределах разрешённого хоста. Отличается только `Cache-Control`: `no-store` у документов и страниц ошибок, `public, max-age=31536000, immutable` у файлов `assets/`.

```
Content-Security-Policy: default-src 'none'; script-src <DASH>; style-src <DASH>;
  img-src <DASH> data: blob:; font-src <DASH>; connect-src 'none'; frame-src 'none';
  worker-src 'none'; object-src 'none'; manifest-src 'none'; media-src 'none';
  base-uri 'none'; form-action 'none'; frame-ancestors <CLIENT>; sandbox allow-scripts;
  report-uri <DASH>/_reports
Connection-Allowlist: (response-origin); report-to=dashboard
Permissions-Policy: camera=(), microphone=(), geolocation=(), clipboard-read=(),
  clipboard-write=(), display-capture=(), fullscreen=(), payment=(),
  publickey-credentials-get=(), identity-credentials-get=(), usb=(), serial=(), hid=(), bluetooth=()
X-DNS-Prefetch-Control: off
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Cache-Control: no-store
Reporting-Endpoints: dashboard="<DASH>/_reports"
```

- `<DASH>` и `<CLIENT>` — явные origin хоста приложений и клиента: схема, хост и **порт**. Источник без порта в `http` означает порт 80, и `http://127.0.0.1` не совпадёт с `:32768`. `'self'` не использовать: в документах с непрозрачным origin он не совпадает с адресом хоста.
- `sandbox` в заголовке сохраняет песочницу и тогда, когда адрес приложения открыт во вкладке. Директива работает только в заголовке, который принудительно применяется: в `<meta>` и в `Content-Security-Policy-Report-Only` она игнорируется.
- `Connection-Allowlist` закрывает то, что CSP не покрывает: WebRTC, `dns-prefetch`, `preconnect`, переходы и перенаправления ([руководство Chrome](https://developer.chrome.com/docs/modern-web-guidance/guides/security/restrict-outbound-connections)). `(response-origin)` — это origin ответа вместе с портом, а не origin документа после песочницы: поэтому файлы приложения с того же хоста грузятся. По умолчанию заголовок блокирует **все перенаправления**, даже на тот же адрес, и весь WebRTC. Браузер учитывает его только на ответах-документах. Другие браузеры его игнорируют.
- Директиву `webrtc 'block'` в CSP не писать: Chromium её не реализует, WebRTC закрывает только `Connection-Allowlist`.
- Необязательно, после проверки на странице с реальным графиком: `require-trusted-types-for 'script'; trusted-types 'none'`. Они защищают только от DOM-XSS внутри песочницы и могут сломать React 19 или Recharts.
- Файлы сборки (`.js`, `.css`, шрифты) запрашиваются из непрозрачного origin в режиме CORS (Vite 7 ставит `crossorigin` и на стили). Им нужен `Access-Control-Allow-Origin: *` без credentials: данных в бандлах нет. Не требовать для них `Sec-Fetch-Site: same-origin`. Файлы версии неизменяемы и кешируются как `immutable`.

Страница клиента (через Apache):

```
Content-Security-Policy: frame-src <DASH>; object-src 'none'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: same-origin
```

`frame-src` обязателен в обоих режимах: без него приложение может перейти на чужой адрес, и оболочка передаст порт чужому документу. Заголовок страницы клиента **принудительный** (`Content-Security-Policy`), а не `Content-Security-Policy-Report-Only`: в `Report-Only` браузер лишь сообщает о нарушении и всё равно загружает чужой адрес, а в Firefox, Safari и Chromium до 152 других защит от такого перехода нет. `Report-Only` допустим только как проба внутри M2: на dev-стенде проверить загрузку файлов, импорт и встроенный режим клиента (`Embedded`), затем включить принудительно. В отчётах пробы искать фреймы самой Studio (того же origin, `blob:`, провайдеров входа): в `frame-src` нет `'self'`, и если такие фреймы есть, их источники придётся добавить, иначе принудительный заголовок сломает Studio. Этап M2 с `Report-Only` не принимается, `check` это проверяет, а `containers.sh` на release-стенд пишет только принудительный заголовок. Заголовок `Cross-Origin-Opener-Policy` не добавлять, пока не проверен вход через OpenID: `same-origin` обнуляет `window.opener`, а `same-origin-allow-popups` сохраняет его только для окон без собственной изолирующей политики.

## Проба браузера (только строгий режим)

Перед первым открытием оболочка загружает скрытый iframe `/_probe/` с теми же заголовками и получает от него ответ через свой порт. Проба проверяет административный запрет WebRTC: в закреплённом Chromium 154 конструктор разрешён, а ICE-кандидаты запрещены. Безопасный вызов до установки SDP и совместимость с прежним `NotAllowedError` описаны в [дизайне M2](../superpowers/specs/2026-11-12-dashboard-m2-design.md#строгий-режим). Если запрет не обнаружен, dashboard не открывается: «Dashboard открывается в Chrome, Edge или Яндекс Браузере на Chromium 152 и новее». Результат запоминается до перезагрузки страницы. `/_probe/` — путь платформы, приложения его не перекрывают. Отчёт о нарушении, который вызвала сама проба, ошибкой не считается.

Ограничение пробы: если политика или настройка уже вызывает `NotAllowedError` при создании `RTCPeerConnection` без заголовка, проба пропустит такой браузер. Главный канал утечки в нём закрыт, а подсказки `dns-prefetch` и `preconnect` частично закрывает `X-DNS-Prefetch-Control: off`. Отсутствие API и прочие ошибки дают отказ. Версию браузера по строке User-Agent не проверять: версия Яндекс Браузера не равна версии его Chromium. Это ограничение записано в «Принятых рисках»: строгий режим отказывает не всякому браузеру без `Connection-Allowlist`, а только тому, где WebRTC включён.

## Сервер черновика (M3, реализовано в исходниках)

Черновик выполняет недоверенный код на реальных строках на компьютере пользователя, поэтому защита у него та же, что на стенде.

- Сервер слушает только loopback (`127.0.0.1`) и принимает только `Host` `localhost:<порт>` и `127.0.0.1:<порт>`: другой компьютер и сайт с DNS rebinding до него не достучатся. Другие пользователи этого же компьютера достучаться могут: входа нет (см. «Принятые риски»).
- Шапка и приложение — разные сайты: шапка на `http://localhost:<порт>`, приложение на `http://dashboards.localhost:<порт 2>`. Заголовки приложения, песочница и протокол те же, что на стенде; `<CLIENT>` — адрес шапки.
- `sample.json` читает только страница шапки и передаёт данные приложению через `state`. Само приложение запросить файл не может: у него `connect-src 'none'`.
- Черновик и публикация M3 собираются из копии `src/**` поверх шаблона платформы, а не из рабочей папки целиком. До `tsc` проверяются также импорты типов и reference-директивы, затем резолвер ограничивает Vite; `tsc`/Vite запускаются напрямую встроенным Node, без команд приложения. Сборки лежат в `control/draft/`, вне папки модели; сервер работает в процессе бэкенда. Контейнерная сборка стенда остаётся M4.
- Режим всегда обычный: строгая проба поддержки браузера не проводится. Отдельная headless-самопроверка без сессии Loginom проверяет `ready`, исключения, консоль и CSP.

## Сборка и публикация (M4, целевое состояние)

Пошаговая публикация описана в [roadmap](../superpowers/specs/2026-11-11-dashboard-architecture-roadmap.md). Здесь — требования безопасности.

- Сборка идёт в контейнере builder: без сети, секретов и домашнего каталога, не от root, с `--cap-drop ALL` и файловой системой только для чтения (временные файлы в tmpfs). Builder берёт одну задачу и завершает процесс, compose перезапускает контейнер из образа: взлом сборки не доживает до следующей задачи. Вход задачи builder только читает (`jobs-in`), результат пишет в `jobs-out/<ID>/`. Том `jobs-out` переживает перезапуск builder, и взломанная сборка могла бы оставить в нём файлы для будущей задачи. Поэтому publisher (у него `jobs-out` на запись) создаёт каталог результата пустым прямо перед выдачей задачи и удаляет его после проверки. Время ограничивает builder (дочерний процесс прерывается через 90 секунд), память и число процессов — compose.
- Из публикации берутся только `src/**`. `package.json`, lockfile, `tsconfig`, конфигурация Vite и `index.html` — из шаблона платформы. `tsc` и `vite` запускаются напрямую, не через `npm run`.
- Приложение не добавляет зависимостей; набор расширяется только через шаблон с ревью.
- Импорты за пределами `src/` и пакетов шаблона сборка отклоняет. Резолвер-плагин с `enforce: "pre"` в конфигурации платформы перехватывает `?raw`, `?url`, `import.meta.glob`, `new URL(…, import.meta.url)`, абсолютные пути, а также `url()` и `@import` в CSS. Настройка Vite `server.fs.strict` на `vite build` не действует.
- Результат проверяет publisher: только `index.html` и файлы `assets/` разрешённых типов, без символьных ссылок, в пределах размера. Хеш результата входит в адрес версии.
- Образец строк на стенде не хранится, поэтому поиск его значений длиной от 6 символов в исходниках выполняет `dashboard_publish` на компьютере пользователя до загрузки. Это гигиена, а не граница: кодированием её можно обойти. Граница для зрителей — песочница и заголовки.
- Публикация атомарно переключает указатель текущей версии. Сборка остаётся, пока цел файл публикации в хранилище.
- Привязку файла публикации `dashboard_publish` берёт из служебной папки Desktop (`control/binding.json`), которую модель не видит и не пишет, и называет пользователю узел и путь пакета в окне подтверждения. Без этого обманутая подсказкой в данных модель могла бы переписать привязку и опубликовать dashboard в другой узел, куда у пользователя есть право записи: publisher сверяет привязку с местом файла, а они бы совпали.
- В многопользовательской среде публиковать может тот, кто может записать файл в папку пакета: кто меняет сценарий, тот может изменить и его dashboard. Publisher принимает файл только если привязка внутри него совпадает с местом файла в хранилище, поэтому чужой пакет подменить нельзя.
- Для каждой версии publisher пишет в журнал путь файла, время, хеши файла публикации и результата, версию шаблона и образ сборщика. Отключить dashboard можно удалением файла публикации в Studio и общим выключателем в настройках стенда.

## Служба, хост и клиент

- Раздачу приложений перенести на хост приложений. Описание публикации хранится вне раздаваемого каталога.
- `GET /dashboard/current` по умолчанию выключить; для локальной отладки — только по флагу и только с loopback. В M3 его заменяет одноразовое чтение снимка по ID, Codex получает ID явно, как Desktop.
- Снимок читается один раз и живёт до 15 минут; в памяти не больше 100 снимков. ID — случайный UUID. Снимок не содержит путей и команд: каталог создаёт Desktop, а команд у агента нет, только инструменты `dashboard_draft` и `dashboard_publish`.
- Apache и Node принимают только известные значения `Host`. Apache передаёт web исходный `Host`: в release `ProxyPreserveHost On` уже стоит в виртуальных хостах Loginom, а на dev-стенде виртуальных хостов нет, и `dashboard.site.conf` включает директиву для `/dashboard/` сам; без неё web видел бы `dashboard-web:8100`, и проверка потеряла бы смысл. Список у web включает все публичные имена Studio: `--public-host` задаётся для каждого имени и IP, по которым Studio открывают, а по неперечисленному адресу она получит отказ на `Host` и на `frame-ancestors`. Studio может быть открыта и по HTTP, и по HTTPS, и dashboard работает на обоих адресах (решение владельца, перенаправления нет): `frame-ancestors` хоста приложений перечисляет оба, а при включённом HTTPS iframe всегда идёт по HTTPS.
- Apache ставит на ответы `/dashboard/` заголовки `Content-Security-Policy: sandbox; default-src 'none'` и `X-Content-Type-Options: nosniff`: даже взломанный web не выполнит свой HTML в origin Studio.
- TLS на порту хоста приложений завершает Apache Studio: web лишь пересылает зашифрованный поток, ключ сертификата Studio ему недоступен (схема — в roadmap, «Скрипты для стендов»).
- web, publisher и builder — три контейнера одного образа, не внутри контейнера сервера Loginom; у каждого минимум прав (таблица в roadmap). У всех трёх файловая система только для чтения. web и builder работают не от root, publisher — с UID процесса Loginom: в release в контейнерах Loginom работает от root, значит и publisher. Он разбирает недоверенные файлы, поэтому защищён тем, что у него нет сети и capabilities (`cap_drop: ALL`, `no-new-privileges`), а хранилище он видит только на чтение. У builder нет ни сети, ни хранилища Loginom. У web хранилища нет; запретить ему исходящие соединения средствами compose нельзя, потому что порт хоста приложений требует обычной сети. При необходимости их ограничивает файрвол стенда.
- Оболочка подключается конфигурацией Apache (`mod_substitute`), без правки файлов клиента. Запасной правки `index.html` нет: модуль лежит в образе dev-стенда (httpd 2.4.68 alpine, та же база, что у release). На теге `<script>` есть атрибут `integrity`. Команда `sed` на работающем контейнере уходит. Обязательна оболочка только в минифицированном клиенте `/app/`; отладочный `/app-debug/` есть лишь на dev-стенде master и обязательным на других стендах не считается (правило — в roadmap, «Цели и стенды» и «Скрипты для стендов»).
- CSP-отчёты отправляются нативной директивой `report-uri` в `/_reports` и попадают в журнал web. В закреплённом Chromium 154 `Reporting-Endpoints` не регистрируется для opaque origin и HTTP endpoint; `report-to` создаёт отчёт, но не доставляет его. Поэтому для CSP применяется `report-uri` без `report-to`: иначе Chromium игнорирует запасной транспорт. Это не меняет блокирующие директивы или песочницу. Локальная доставка реального POST и нативная доставка на установленном dev-стенде подтверждены; результат S4 и ограничения записаны в [приёмке M2](../testing/loginom-ai-agent/dashboard-m2.md).
- `Connection-Allowlist` сохраняет `report-to=dashboard` и `Reporting-Endpoints`, но доставка этих отчётов в проверенной HTTP/opaque конфигурации Chromium 154 недоступна. Блокировка проверяется поведением, наличие отчётов не обещается. Нормальный ROI не должен порождать CSP-отчёты; каждый доставленный отчёт разбирается по адресу документа. Общий эксплуатационный журнал — M6.

## Шаблон и инструкции агента

- В M2 `packages/dashboard/template/src/loginom.ts` — копия канонического SDK: `onState` через порт, сообщение `ready`, `close()`. Доступа к `window.frameElement`, `change` и `run` нет.
- В шаблоне нет полей параметров; приложение показывает их значения из `state`.
- В M2 инструкции приложений — в `dashboard/AGENTS.md`, платформы — в `packages/dashboard/AGENTS.md`: приложение не должно использовать сеть, хранилища, формы и всплывающие окна; CSP закрывает обычные сетевые запросы с остаточными рисками обычного режима ниже. Данные образца не вшиваются в код, потому что бандлы раздаются без входа. Навык `loginom-dashboard` и профиль с ограничениями записи появятся в M3.
- Данные снимка — недоверенный текст. Инструкции внутри строк и имён агент не выполняет. Целевое ограничение M3: он правит только `src/` своей рабочей папки и вызывает только инструменты `dashboard_draft` и `dashboard_publish`. Это не пожелание, а ограничение: правила профиля разрешают запись только в `work/src/` и запрещают выход за рабочую папку, а привязка, «основа», сборка черновика и набор шаблона лежат вне папки модели (roadmap, «Черновик — по шагам», шаг 5).
- Перепубликовать существующие приложения. Старые читают `window.frameElement` и в новой схеме покажут ошибку подключения.

## Отдельно для клиента Loginom

- На dev-стенде с M0 для обоих клиентов Studio (`/app/` и `/app-debug/`) задать `"rememberuser": false` в `client.json`. На странице входа исчезнет галочка «Запомнить», и Studio перестанет сохранять новые пароли в браузере. На release-стенде настройку выбирает администратор, установка dashboard сохраняет его выбор.
- Администраторам удалить в браузере уже сохранённые пароли этого адреса. Для административных учётных записей лучше вход через OpenID со вторым фактором: тогда пароля, который можно прочитать, нет.

## Проверки

`dns-prefetch` вне автотестов: Chromium сам разрешает `*.localhost`, поэтому внешний DNS-запрос не виден. Канал закрывают `Connection-Allowlist` и `X-DNS-Prefetch-Control: off`.

`preconnect` также исключён из автоматического набора M2 по правилу положительного контроля: в закреплённом Chromium 154.0.8037.0 попытка без `Connection-Allowlist` не открыла ни одного TCP-соединения за 5 секунд. Поэтому отсутствие соединения с заголовком не подтверждало бы его действие. Этот канал остаётся ограничением проверки; риск браузеров без заголовка сохраняется.

Решение владельца от 2026-11-13: только при собственной навигации iframe на внешний тестовый сервер без `Connection-Allowlist` разрешён максимум один TCP-контакт. HTTP-запросов должно быть 0; обязательны новое событие `frame-src` для адреса цели, закрытый iframe, неизменный URL Studio и ровно один канал. Для остальных попыток и прогона с заголовком сохраняется TCP=0.

Автотесты с намеренно вредоносным тестовым dashboard. Набор идёт дважды: как на стенде и без заголовка `Connection-Allowlist`. В Chromium 154 этот заголовок блокирует переход на чужой адрес сам, и без второго прогона слабый слой CSP (`frame-src`, `connect-src`) остался бы незамеченным, хотя в Firefox, Safari и Chromium до 152 он единственная защита. Пункт про WebRTC, `dns-prefetch` и `preconnect` во втором прогоне не проверяется: без заголовка эти каналы открыты (см. «Принятые риски»). Каждая попытка должна провалиться:

- прочитать `window.parent.document`, `parent.bg`, `window.frameElement`;
- вызвать `navigator.credentials.get({password: true})`, обратиться к `localStorage` и `document.cookie`;
- `fetch`, `sendBeacon`, WebSocket и картинка-маяк на внешний адрес и на origin клиента;
- WebRTC — в закреплённом Chromium проверяется административный запрет ICE, описанный в разделе пробы; успешный конструктор сам по себе не означает обход; `dns-prefetch` и `preconnect` проверяются с указанными выше ограничениями; в остальных браузерах эти каналы остаются открытыми (см. «Принятые риски»);
- `location = "https://…"`, `top.location = …`, `window.open`, отправка формы, `alert`, `prompt`; переход на другой адрес хоста приложений: `frame-src` блокирует, порт чужому документу не передаётся;
- шквал сообщений в окно Loginom, поддельный `state`, повторный `ready`, огромное или неклонируемое сообщение: оболочка не меняет параметры и не запускает узел, самое большее закрывает dashboard;
- открыть адрес приложения во вкладке: песочница сохраняется;
- встроить приложение в чужую страницу: блокирует `frame-ancestors`;
- запросить у хоста приложений `binding.json`, `sample.json`, каталог `/apps/` и несуществующий путь: ответ 404 с теми же заголовками, перенаправлений нет;
- запрос с чужим `Host`: отказ;
- M4, вне приёмки M2: собрать приложение с `import … from "/etc/hostname?raw"`, `import.meta.glob("/**")`, `new URL("/etc/hostname", import.meta.url)`, `url(../../../etc/hostname)` в CSS и обращением в сеть: сборка отказывает или игнорирует;
- M4, вне приёмки M2: publisher — файл публикации с привязкой не по месту, больше 1 МБ, с путём `..` или символьной ссылкой — отказ;
- M4, вне приёмки M2: publisher — каталог результата перед выдачей задачи пуст, файлы, оставленные прежней сборкой, в результат не попадают.

Проверки профиля агента (автотесты на бэкенде):

- записать файл вне `work/src/`: в `control/`, через `..`, по абсолютному пути, через символическую ссылку — отказ;
- открыть путь вне рабочей папки (`external_directory`) — отказ без вопроса пользователю;
- положить в `work/` файлы `postcss.config.js`, `vite.config.ts`, `package.json`, `index.html`: сборка черновика их игнорирует, в неё попадает только `src/**`;
- окно подтверждения публикации называет узел и путь пакета из `control/binding.json`, а не из файлов рабочей папки.

Вручную, не автотест: браузерные автотесты идут только на Chromium 154, поэтому в Firefox dashboard проверяется руками. В обычном режиме он открывается, в строгом — отказ с объяснением.

Положительные проверки: данные приходят; изменение параметра в шапке пересчитывает узел и обновляет экран; Esc и «Вернуться к сценарию» закрывают dashboard; «Изменить в чате» открывает Desktop; пустой результат и ошибка показываются как сейчас. После реализации — независимое ревью безопасности и ручная попытка обхода.

## Принятые риски

- Открытие чужого dashboard выполняет сценарий автора с правами открывшего. Это равносильно нажатию «Выполнить» в его пакете; так решено вместе с сохранением автозапуска.
- Без проверки публикаций чужой dashboard может показать искажённые числа или нарисовать поддельную форму входа в своей области. Обычными каналами отправить введённое он не может: CSP закрывает их во всех браузерах, параметров он не касается. Обходные каналы описаны ниже. Шапка с узлом и пакетом остаётся доверенной.
- Dashboard видит все данные своего узла в пределах лимитов: это его назначение.
- Реальные строки получают агент и внешняя модель (решение владельца).
- **Обычный режим.** В браузерах без `Connection-Allowlist` (Firefox, Safari, Chromium до 152) вредоносный dashboard может вынести показанные ему данные через WebRTC или DNS: имена серверов в запросах `dns-prefetch`, `preconnect` и STUN. Доступа к сессии Loginom, паролям и другим узлам это не даёт. Строгий режим этот канал закрывает.
- **Обычный режим.** В Firefox и Safari документ приложения может делить процесс с клиентом, поэтому остаётся теоретический риск атак класса Spectre. Строгий режим закрывает его отказом: Firefox и Safari в нём обычно не открывают dashboard (исключение — следующий пункт).
- **Строгий режим.** Проба проверяет запрет WebRTC, а не название браузера. Если политика или настройка вызывает `NotAllowedError` при создании `RTCPeerConnection` без заголовка, проба может пропустить такой браузер, в том числе Firefox. В нём остаются оба риска, которые строгий режим должен закрывать: утечка через DNS-подсказки (частично её закрывает `X-DNS-Prefetch-Control: off`) и общий процесс с клиентом. Отсутствие API и прочие ошибки дают отказ. Поэтому строгий режим гарантирует отказ не всякому браузеру без `Connection-Allowlist`, а только тому, где WebRTC включён.
- На том же адресе (обычный режим) хост приложений получает cookie клиента при загрузке документа; приложение их прочитать не может, web их не пишет в журнал.
- Сборка dashboard доступна без входа тому, кто знает адрес. Адрес содержит хеш привязки: чтобы его получить, нужны путь пакета и оба GUID. В сборке нет данных.
- Запасной путь Б не проверяет права Loginom: опубликовать может любой, кто может писать в каталог `UserStorage` dev-стенда на этой машине. Только для dev-стенда.
- Publisher видит всё хранилище, но только на чтение и без сети. В release в контейнерах он работает от root, как и Loginom. Builder, который разбирает недоверенный код, хранилища не видит.
- У web нет запрета исходящих соединений (см. выше).
- Снимок принимается без входа: проверки `Host` и `Origin` не защищают от прямого запроса к порту стенда. Кто до него достучится, может подсунуть пользователю снимок со своими строками и своей привязкой и прислать ссылку `loginom-ai-agent://dashboard?id=…`. Привязка и имя узла в снимке — заявление отправителя. Защита: модель не может изменить привязку (она в служебной папке), пользователь видит узел и путь пакета в окне подтверждения публикации, а запись в хранилище всё равно проверяет Loginom.
- Сервер черновика не требует входа: на компьютере, где работают несколько человек, страницу черновика и образец строк может открыть любой локальный пользователь.
- В CLI публикацию не подтверждает пользователь: команда `run` без `--auto` отклоняет все запросы разрешений, с `--auto` отвечает «да» на все. CLI — инструмент разработки агента.
- За границами плана: ошибки песочницы самого браузера, уязвимости клиента Loginom, сотрудники с доступом к хосту и контейнерам.
