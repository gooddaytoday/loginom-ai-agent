# Защита Git от секретов

Канонические решения, инструкция и итог аудита от 19 октября 2026 года. Интеграционная ветка — `loginom`.

## Как устроена защита

Один Gitleaks **8.30.1**, версия в `.gitleaks-version`, правила в `.gitleaks.toml`. Одинаковые команды используются в Husky и GitHub Actions.

- `pre-commit` проверяет только staged diff. Содержимое рабочей копии вне индекса не участвует.
- `pre-push` читает все обновления refs из stdin Git. Для существующего ref используются полученные `old..new`, включая force push; удаление пропускается. Для нового ref исключаются известные ветки соответствующего именованного remote. Нет базы или объекта — операция блокируется с предложением выполнить `git fetch`; полного сканирования вместо diff нет.
- Каждый коммит диапазона проверяется, включая merge относительно первого родителя. Обход графа остаётся полным: боковые ветки и промежуточное добавление/удаление файла не теряются.
- Только новые версии архивов извлекаются из индекса или Git blobs. Один blob проверяется один раз за запуск. Проверяются `.lgp`/ZIP, TAR, TAR.GZ/TGZ и GZIP; путь находки имеет вид `package.lgp!settings.xml`.
- Глубина архивов и декодирования — два уровня. Повреждение, шифрование, неподдерживаемый формат, неоднозначный путь архива или предупреждение сканера блокируют операцию. Ссылки в TAR проверяются как текстовые имена целей, без перехода по ним.
- Hooks ничего не скачивают и не устанавливают; `bun --no-install` отключает автоматическую загрузку зависимостей рантаймом. Отсутствующая или другая версия Gitleaks блокирует проверку. Установка отдельно проверяет SHA256 официального release asset и версию бинарного файла.
- Вывод содержит только путь, строку, правило, SHA и статистику. Исходные сообщения ошибок остаются в закрытом локальном файле; значения ключей не выводятся.

Принятое уточнение реализации: вместо передачи `.lgp` штатному обходчику Gitleaks содержимое выбранных архивов безопасно распаковывается и передаётся тому же сканеру через отдельный временный Git index. Проверка настоящим сканером показала, что штатный обходчик не распознаёт `.lgp`, может молча пропускать повреждённые ZIP и ошибочно воспринимает `README.br.md`/`gyro.zzz` как сжатые данные. Временный index также отключает пользовательские фильтры и diff drivers, чтобы проверялись исходные байты. Нового сканера и постоянного кэша нет. ZIP читает zip.js; TAR — `tar.Parser`, сохраняющий повторные записи, которые `Bun.Archive.files()` объединяет. Основание: [Gitleaks 8.30.1, обработка файлов](https://github.com/gitleaks/gitleaks/blob/v8.30.1/sources/file.go), воспроизводящие интеграционные тесты проекта.

## Установка и запуск

Из корня проекта после обычной установки зависимостей:

```sh
bun run secrets:install
export PATH="$HOME/.local/bin:$PATH"
bun run prepare
bun run secrets staged
bun run secrets range BASE_SHA HEAD_SHA
```

Установщик поддерживает Linux/macOS/Windows, x64/arm64. Фактически проверена Linux x64. Можно заранее задать `GITLEAKS_INSTALL_DIR`; сканер ищет `gitleaks` в PATH либо по `GITLEAKS_BIN`.

`bun run secrets push origin` предназначена для Git hook и получает стандартные строки pre-push через stdin. Для ручной проверки диапазона удобнее `range`.

Коды выхода: **0** — совпадений нет; **2** — есть находки; **1** — проверка не завершена. Любой ненулевой код блокирует hook/CI. Для исправления случайного добавления убрать значение из индекса и исходника, затем повторить commit. Если секрет уже попал в коммит отправляемого диапазона, простого удаления в следующем коммите недостаточно: исправить локальные коммиты и заменить ключ, если он уже мог раскрыться.

Локальные `.env.*` игнорируются; `.env.example` и `.env.*.example` доступны для безопасных шаблонов и также проверяются сканером. Проверки Husky можно технически обойти, поэтому серверная защита обязательна.

## CI и ветка loginom

Workflow `.github/workflows/secrets.yml` запускает единственный статус **Secret scan**:

- push в рабочую ветку: `before..head`; новая ветка — от merge-base с `origin/loginom`;
- PR в `loginom`: от merge-base base/head до head PR;
- checkout полного графа нужен для выбора диапазона; содержимое всего проекта и полный аудит здесь не сканируются;
- перед проверкой CI устанавливает закреплённый сканер с checksum и запускает его тесты и typecheck только пакета инструментов.

19 октября 2026 года после успешных проверочных [push CI](https://github.com/gooddaytoday/loginom-ai-agent/actions/runs/39263559725) и [PR CI](https://github.com/gooddaytoday/loginom-ai-agent/actions/runs/39263566257) серверное правило для `loginom` включено и повторно прочитано через GitHub API: обязательный `Secret scan` именно от GitHub Actions (`app_id=15368`), слияние через PR, применение к администраторам, **0** обязательных одобрений. Force push и удаление защищённой ветки запрещены. GitHub secret scanning и push protection уже были включены и сохранены.

Изменения опубликованы в [PR #185](https://github.com/gooddaytoday/loginom-ai-agent/pull/185), целевая ветка `loginom`. Слияние PR — отдельное действие; после слияния hooks и workflow станут частью интеграционной ветки. Первая ошибка валидации workflow устранена до включения защиты: `runner.temp` недоступен в job-level env, поэтому `TMPDIR` устанавливается в исполняемом шаге через `$RUNNER_TEMP` и `$GITHUB_ENV`.

## Полный аудит

Для повторения из основного checkout:

```sh
git fetch --prune origin '+refs/heads/*:refs/remotes/origin/*' --tags
umask 077
TMPDIR=/home/kiselev/storage/tmp bun run secrets audit > /home/kiselev/storage/tmp/secret-audit-safe.jsonl
```

На этой машине временные данные размещаются в `/home/kiselev/storage/tmp/`, каталоги имеют режим 700, файлы 600. На CI используется `runner.temp`. Временные копии исходников и отчёты удаляются при завершении. Закрытый файл диагностики при ошибке сохраняется отдельно для локального разбора; его нельзя публиковать.

В начале аудита фиксируются OID локальных веток, удалённых веток, тегов и HEAD; дальнейшая проверка использует именно эти OID, даже если параллельная задача обновит refs. Проверяются все достижимые коммиты, включая удалённые файлы, исторические архивы и отдельно текущие tracked/неигнорируемые untracked файлы основного checkout. Рабочее дерево не изменяется. Локальные `.gitleaksignore`, `.gitleaks.toml` и inline `gitleaks:allow` при аудите не используются: исключения разбираются повторно со стандартными правилами закреплённой версии.

Итог финального запуска исходной команды: **20 799 коммитов**, **111 уникальных blobs архивов**, **14 766 путей текущего checkout**, **175 refs**, **80.412 с**. Из текущих путей 61 — символические ссылки, они явно перечислены как пропуски; содержимое остальных 14 705 файлов проверено. HEAD основного checkout: `775778d38bbb728805fac8af161a7211f03db170`.

Найдено **450 совпадений**: 259 в истории, 175 в текущих файлах и 16 внутри архивов. По разбору контекста: **310 ложных совпадений**, **136 искусственных значений**, **4 подозрительных совпадения**. Совпадения между историей и текущими файлами учитываются отдельно. Код выхода 2 означает наличие находок при завершённой проверке.

Полный снимок refs и безопасные метаданные находятся локально в `/home/kiselev/storage/tmp/secret-audit-20261019/refs-verified-audit.txt` и `verified-audit.jsonl`. SHA256 снимка refs: `e23d42ecf3cee1016f2dfd733be72659963d6ccbd6c07a23b57050943faf3422`. Значения ключей в эти файлы не включены. История ограничена указанным снимком; новые коммиты параллельных задач относятся к последующим проверкам.

Классификация: **3 разных подозрительных значения**, четыре совпадения с учётом повтора одного значения в текущем файле. Их работоспособность через внешние API не проверялась, подтверждённых действующих ключей нет:

1. `daytona.ts:15`, `generic-api-key`, SHA `0bedea52b19515c69057866ec958769004147f66` — исторический literal API key. В текущем checkout файл отсутствует.
2. `opencode.json:6`, `generic-api-key`, SHA `71cd84dbbb59c3655ef9647e9cb1280eb16e73cb` — исторический API key провайдера Cerebras. В текущем checkout этого значения нет.
3. `services/loginom-ai/benchmark/locomo/openclaw/run_full_eval.sh:22`, `generic-api-key`, SHA `26ff8fa7660f470d4973960481b88b88970316c5` — hardcoded ключ benchmark; значение присутствует и в текущем checkout.

Для этих трёх значений владелец соответствующей учётной записи должен проверить происхождение и отзыв. Если они использовались: отозвать у издателя, выдать замену с минимальными правами, обновить локальный secret store/переменную окружения и проверить журналы использования за период раскрытия. Benchmark должен получать замену из окружения без hardcoded default. Удаление строки из Git не отзывает ключ. Внешние обращения с найденными ключами, их отзыв и переписывание истории в этой работе не выполнялись. Переписывание истории рассматривается отдельно после подтверждения конкретных ключей и согласования с владельцами checkout/веток.

Остальные совпадения проверены по контексту: provenance/Git/content hashes, имена полей и путей, выражения кода и UI, документационные переменные/шаблоны, искусственные данные тестов и mock UI. PEM из теста захвата JavaScript не разбираются OpenSSL как private key. В архивах совпали hashes фикстур и идентификаторы BoringSSL/V8/SQLite, подозрительных ключей там не найдено.

Четыре существующих fingerprint-исключения `.gitleaksignore` относятся к искусственным строкам из HTTP recorder redaction tests в коммите `afa57acfda894e0ebf3c637dd710310b705c0a2f`; они повторно проверены и сохранены без расширения. Новых исключений и baseline всех старых совпадений нет. Целые тестовые каталоги не исключаются. Новое исключение допустимо только для установленного искусственного значения и конкретного места; тест проверяет, что другое значение или другой путь по-прежнему блокируются.

## Проверка и время

Разработка выполнена последовательными RED → GREEN → REFACTOR циклами с настоящим Gitleaks и временными Git-репозиториями. Проверены частичный staging, пустой индекс, посторонняя рабочая копия, промежуточные коммиты, merge resolution, боковая merge-история, новый ref без базы, force push, несколько refs, удаление, промежуточный `.lgp`, вложенные архивы, повреждение/шифрование, превышение глубины, повторные/опасные пути, TAR links, безопасный вывод и точность исключений.

Финальный набор: **23 теста**, package-local `bun typecheck`. Независимое ревью не нашло блокирующих замечаний; отдельно в чистом окружении прошли filtered install, тесты, typecheck и установка официального Gitleaks с checksum. Дополнительно существующий общий typecheck завершил **33 задачи успешно**.

Локальные замеры Linux x64, Bun 1.3.14, Gitleaks 8.30.1: медиана трёх запусков, замерена команда `bun run secrets`, время включает запуск Bun и подготовку, существующий typecheck исключён:

- пустой индекс: **34 мс**, 0 архивов;
- один небольшой staged text diff: **623 мс**, 0 архивов;
- тот же diff и один staged `.lgp`: **1014 мс**, 1 архив;
- push **200 коммитов**, **20 уникальных версий `.lgp`**, **9 290 960 байт** новых текстовых файлов: **1242 мс** (запуски 1446/1238/1242 мс).

Это измерения, а не обещание постоянного времени: большой изменённый архив требует чтения всей его новой версии. Гарантия объёма — обычные hooks/CI работают только с выбранными изменениями, полный аудит запускается явно.

## Ограничения

Аудит не охватывает недостижимые Git objects, удалённые на сервере refs, Git LFS payloads, содержимое submodules и игнорируемые локальные файлы. Символические ссылки текущего checkout перечислены как пропуски; внешние цели не читались. Непрозрачные бинарные форматы (изображения, шрифты, базы и т. п.) не имеют гарантированной семантической проверки. Архивы по неподдерживаемым расширениям и вложенность сверх двух уровней не считаются проверенными; распознанные `.7z`/`.xz`/`.bz2`/`.zst` блокируют операцию, а не возвращают clean. В проверенной доступной истории таких архивов, а также `.br`/`.rar`/`.lz`/`.lzma`/`.lz4`/`.tbz`/`.txz`, не обнаружено. Вывод clean означает отсутствие совпадений правил Gitleaks в указанном покрытии, а не доказательство отсутствия любых секретов.
