# Восстановление локального стенда на Linux

Это рецепт **нового стенда на другом компьютере**. Он не останавливает и не заменяет
существующие контейнеры. Имена ниже и порты `127.0.0.1:32768` и `127.0.0.1:32769` должны быть свободны:
они входят в текущий прототип Dashboard и Desktop. Используйте Linux x86_64,
Docker, Git LFS, unzip, curl, ShellCheck и закреплённый Node из инструкции
[переноса](../HANDOFF.md). Node должен находиться в `PATH`: installer копирует
`command -v node` в `~/loginom-dashboard/node` для отдельного Debian web-контейнера `dashboard-master-20261109-web`. Он не запускает Node внутри Loginom Server.

Проверенный ранее путь: master build 5579, библиотечные файлы integration,
обычный/debug веб-клиенты, исполнение ROI-пакета и публикация dashboard. Он использовал
локально доступные базовые образы. Рецепт ниже заменяет эти непереносимые образы
официальными Dockerfile из того же дистрибутива и публичными Debian/Apache base
images. **Чистая сборка по этому рецепту здесь не выполнялась**; проверку на новой
машине начните с HTTP/WebSocket и исполнения fixture, затем переходите к Desktop.

## Внешние входы

Дистрибутив Loginom и integration содержат лицензированные файлы и не входят в
эту ветку. Получите их через обычный разрешённый доступ владельца:

1. Войдите в GitLab и скачайте artifact успешного job
   [build_staging 1367041](http://git.basegroup.ru/dev/deductor/-/jobs/1367041)
   проекта `dev/deductor`, pipeline 205579, commit
   `0dac4766535984c294eed4e42b653a38d397b972`, ветка master.
   Нужен ZIP целиком, содержащий `Dist/Server`, `Dist/Client`, `Dist/ClientDebug`.
   Размер — 217314589 байт, SHA256 —
   `8182dbeec7cb95739f1424bb08367b266b1ab87a8fbc3cd17a3f6ea41195597e`.
   Если job artifact уже истёк, потребуется получить именно эту сборку у владельца
   дистрибутива. Новая сборка master потребует отдельной проверки совместимости.
2. Клонируйте `testing/integration` обычным GitLab clone URL с настроенным SSH
   или credential helper. Для повторения входов текущего стенда используйте commit
   `c81703ad7a5e077e6ec2417a83192753edbe8400` и выполните `git lfs pull`.
   Нужен его каталог `ci/common/install-linux/configs`: `server/libs`,
   `server/ca.bg.local.pem.cer` и `client/config/httpd.conf`.
   Это не только сертификат и конфигурация: без LFS-библиотек сервер не запустится.

Не вставляйте токены в URL/командную строку и не копируйте свой рабочий
`UserStorage`, профили Desktop или настройки авторизации в build context.
`Dist/Server/config` содержит конфигурацию **тестового дистрибутива**, включая его
пользователей и лицензирование. Используйте её только в разрешённом локальном
стенде; собственную лицензию при необходимости подключите приватно.

## Подготовка build context

Все команды выполняются в одной оболочке. Начните из корня checkout этой ветки.
В двух строках с `/absolute/path/...` укажите скачанный ZIP и checkout integration.
Build context создаётся вне Git; исходные файлы integration не меняются.

```sh
repo=$(pwd -P)
mkdir -p "$HOME/storage/tmp"
inputs=$(mktemp -d "$HOME/storage/tmp/dashboard-stand.XXXXXX")
archive=/absolute/path/to/downloaded/artifacts.zip
integration=/absolute/path/to/integration

printf '%s  %s\n' \
  8182dbeec7cb95739f1424bb08367b266b1ab87a8fbc3cd17a3f6ea41195597e \
  "$archive" | sha256sum --check
unzip -q "$archive" -d "$inputs/artifact"
dist="$inputs/artifact/Dist"
configs="$integration/ci/common/install-linux/configs"

cp -a "$configs/server/libs" "$dist/Server/"
cp "$configs/server/ca.bg.local.pem.cer" "$dist/Server/"
cp "$configs/client/config/httpd.conf" "$dist/Client/config/httpd.conf"
cp "$repo/dashboard/stand/loginom.site.conf" "$dist/Client/config/loginom.site.conf"
cp -a "$dist/ClientDebug/client" "$dist/Client/client-debug"
printf '\nCOPY client-debug /usr/local/apache2/htdocs/client-debug\n' \
  >> "$dist/Client/Dockerfile"
printf '{"wsproxy":"true"}\n' > "$dist/Client/server_proxy.json"
```

`libs` дополняют официальный `Dist/Server/Dockerfile`; не заменяйте их системными
библиотеками произвольных версий. Сам Dockerfile устанавливает остальные Debian
зависимости и запускает Loginom от UID/GID 7001. Небольшой wrapper из этой ветки
добавляет `procps`: при обновлении M1 → M2 `dev-master.sh` использует `ps`, чтобы остановить только прежний M1-процесс Node. Новый Node работает в отдельном web-контейнере.
`httpd.conf` загружает `mod_headers`, `mod_proxy_http`, `mod_proxy_wstunnel` и
`conf/*.site.conf`; наш site config направляет оба WebSocket маршрута только в
этот server-контейнер, без Integrator и других стендов.

## Сборка и запуск новой пары

Не запускайте общий `integration/install.sh`: он предназначен для других
окружений и может затронуть их контейнеры. Здесь создаётся только новая пара.
Docker откажется повторно использовать занятое имя или порт; в таком случае
разберитесь с владельцем существующего ресурса, а не удаляйте его автоматически.

```sh
docker build -t dashboard-master-20261109-vendor:5579 "$dist/Server"
docker build -f "$repo/dashboard/stand/Dockerfile.server" \
  -t dashboard-master-20261109-server:5579 "$repo/dashboard/stand"
docker build -t dashboard-master-20261109-client:5579 "$dist/Client"

docker network create dashboard-master-20261109-net
docker run -d --name dashboard-master-20261109-server \
  --network dashboard-master-20261109-net \
  dashboard-master-20261109-server:5579
docker run -d --name dashboard-master-20261109-studio \
  --network dashboard-master-20261109-net \
  -p 127.0.0.1:32768:80 \
  dashboard-master-20261109-client:5579

docker exec dashboard-master-20261109-studio httpd -t
docker exec dashboard-master-20261109-server sh -c 'ldd /app/loginomd'
curl -fI http://127.0.0.1:32768/app/
curl -fI http://127.0.0.1:32768/app-debug/
```

Ожидания: Apache сообщает `Syntax OK`; `ldd` не содержит `not found`; обе страницы
отвечают HTTP 200. Дождитесь готовности сервера по его журналу; при ошибке
`docker logs dashboard-master-20261109-server` покажет причину. Порты server не
публикуются, host mounts отсутствуют, данные новой пары хранятся в контейнерах.

Откройте [обычный клиент](http://127.0.0.1:32768/app/?testable=true), войдите
пользователем тестового дистрибутива и проверьте в Network браузера успешный
WebSocket `/app/ws/` (HTTP 101). Для debug-клиента маршрут — `/app-debug/ws/`.
HTTP 200 страницы сам по себе не доказывает работоспособность Loginom.

## Подключение Dashboard из checkout

После успешного входа вернитесь в ту же оболочку:

```sh
cd "$repo"
(cd packages/dashboard && bun run build)
bash -n packages/dashboard/deploy/dev-master.sh
shellcheck packages/dashboard/deploy/dev-master.sh
./packages/dashboard/deploy/dev-master.sh install
```

Installer подключит оболочку обоих клиентов, принудительный CSP, отдельный web-контейнер (внутренний API `8100`, хост приложений `8101` → `127.0.0.1:32769`) и fixture
`/user/dashboard-roi/campaign.lgp` вместе с `dataset.csv`. Обновите браузер,
откройте пакет, выполните узел «По убыванию ROI»: ожидается 500 кампаний.
Нажатие «Создать dashboard» выдаёт **новый** снимок. Старые ID с прежнего компьютера
не действуют; публикацию и привязку примера выполняйте по [инструкции переноса](../HANDOFF.md).

Порядок обновления с M1: **install → свежий снимок и перепубликация ROI → check**. Автоматического переноса M1-публикаций нет. Состояние M2 находится в `~/loginom-dashboard/` (`node`, `server.mjs`, `builds/`); web читает его без записи и перезапускается самостоятельно. Перезапуск Loginom Server не требует переустановки dashboard. `install --strict` включает строгий режим, повторный `install` без флага возвращает обычный. Перезапуск web удаляет ID из памяти, поэтому получите снимок заново. После проверки
штатно выйдите из своей сессии Loginom и только затем закрывайте вкладку:
простое закрытие браузера может оставить пакет заблокированным.

## Проверка и удаление

Для `check` нужен закреплённый Node в PATH, Bun, Chromium из `PLAYWRIGHT_BROWSERS_PATH` и зависимости `packages/loginom-runtime/client` из [инструкции переноса](../HANDOFF.md). Предоставьте приватный JSON вне Git (доступ только владельцу). Обязательные поля: `url` (URL клиента Studio), `username`, строка `password` или `secrets.password` в конфигурации Desktop. Используйте отдельную тестовую учётную запись и пакет, который можно открыть и выполнить: проба не сохраняет его на диск. По умолчанию это `/user/dashboard-roi/campaign.lgp`, `Unit1`, «По убыванию ROI». Для другого подготовленного сценария задайте `packagePath`, `unit`, `nodeName`; нужен табличный узел с данными и числовой переменной.

Из корня в Bash:

```sh
export DASHBOARD_STUDIO_CONFIG=/absolute/private/path/to/master.json
./packages/dashboard/deploy/dev-master.sh check
```

Проверяются ROI lookup с хешем, origin и режимом, соответствие указателю `current`, заголовки API и appHost на 200/404/403, кеширование assets и отсутствие перенаправлений, ограничения web-контейнера, принудительный CSP обоих клиентов, закрытые `current`, `binding.json` и `sample.json`, запрещённый Host, оба клиентских JSON целиком и точный файл оболочки. Затем проба входит в каждый клиент в отдельном временном профиле, выбирает узел, проверяет кнопку и обращения адаптера к реальной таблице и параметрам. Перед следующим входом закрывает проверочный пакет и выполняет штатный выход. Сбой входа или неподготовленный сценарий даёт «Не проверено» и ненулевой код. Учётные данные не передаются в аргументах процесса. Это проверка адаптера, а не полная UI-приёмка SDK; последняя выполняется по [runbook M2](../../docs/testing/loginom-ai-agent/dashboard-m2.md). Для нестандартного имени web используйте один и тот же `--web NAME` во всех трёх командах; установщик принимает только своё точное имя с меткой принадлежности.

Для лицензированной **7.4.2** укажите отдельную конфигурацию этой машины и URL минифицированного клиента:
`DASHBOARD_STUDIO_CONFIG=/absolute/private/path/to/release.json node packages/dashboard/deploy/check-studio.mjs 7.4.2`. Если интеграции нет, тот же собранный файл загружается только во временную страницу после входа. Нужна работающая Studio; служба dashboard для этой проверки не требуется. Строки результата показывают сборку, наличие кнопки, штатное действие Studio и отсутствующий API, если он обнаружен.

Для снятия интеграции: `./packages/dashboard/deploy/dev-master.sh uninstall`. Оба оригинальных `client.json` остаются на месте, снимаются только их Apache-алиасы и копии. Свой web-контейнер удаляется, `~/loginom-dashboard/builds/`, исходники, пакеты и зависимости сохраняются. После нового `install` запустите `check` и откройте прежнюю публикацию.

## Приёмка M2

13 ноября 2026 приёмочные проверки установленного M2 пройдены на локальном dev-стенде: код `41fcec31af`, Studio `7.5.0-alpha+build.5579`, Node `24.19.0`, Chromium `154.0.8037.0`, Firefox `158.0.1`. Разведка задачи 1 не потребовала новых источников `frame-src`. Обновление поверх M1, публикация ROI по свежему снимку штатной кнопки и первый `check` прошли в обоих клиентах. В обоих клиентах проверены принудительный CSP, штатные действия Studio, ROI 500 → 453 → 500 с CSV-oracle, Esc и свежая метка изменения в Desktop. S4 подтвердил отдельные процессы и нативную доставку CSP-отчёта; S5 прошёл без `unsafe-inline`. Firefox работает в обычном режиме и получает объяснимый отказ в строгом. `uninstall` оставил Studio работоспособной без интеграции; повторная установка сохранила публикацию и открыла ROI без перепубликации. После финального исправления CLI публикация по свежему снимку и открытие ROI повторно прошли с прежним хешем. Стенд оставлен в обычном режиме, исходные `.lgp` и CSV не изменены.

Ограничения: HTTPS/частный CA, OpenID и недоступные на fixture формы визуализаторов/отчётов не проверены; Connection-Allowlist reporting на HTTP/opaque origin не подтверждён. В неизменённом AppImage Desktop 0.3.9 проверены метки и точные ID в черновике, но отдельный дефект bundled runtime мешает проверке подключения Loginom; генерация моделью не запускалась. Полные версии, SHA, результаты восьми шагов и границы проверки — в [runbook M2](../../docs/testing/loginom-ai-agent/dashboard-m2.md). Раздел M1 выше сохраняет результаты той установки.
