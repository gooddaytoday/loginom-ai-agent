The separate fixed installed FP entry is implemented here. Startup control remains a separate receiving boundary; this component does not claim the full assigned startup composition.

`node-client.ts` calls ordinary `client.request("start", ..., 180_000)`. `transport.ts` has a controlled capability only for `readonly.preReady`. `node-entry.ts` constructs `state.port` only in the completion of `createLoginomHost(...).then(...)`; before that, `readonly.preReady.cancel` reaches `!state.host` and returns HOST_NOT_READY. HostPort cancellation additionally requires an acquired run, which startup does not have.

Minimal additional receiver seam proposed for Registry: retain the original FP start request ID/authorization/controller/deadline before the first startup await in node-entry, accept exact-ID FP startup cancellation through the existing private cancellation namespace before HostPort exists, and pass the same startup control through createLoginomHost/connection startup. Preserve ordinary startup and all cleanup/durability predicates. Node-client then snapshots primitive inventory/startup inputs before its first await, rechecks after each inventory await, uses the original signal/deadline for the fixed start request, and refuses late tuple drift. No new namespace or public authority field. No generic request exemption. No direct interruption or process kill as evidence of confirmed cancellation.

These receiver hunks are not written in this component. A caller-only timeout/cancel packet would not prove cancellation of the original startup; the existing controlled read ABI is ineligible until after startup and run acquisition. The separate entry creates no native authority, storage binding, preparation, mutation or release rights.
