# Построение, настройка, выполнение и сохранение

Используй закреплённые описания операций и локальный кеш знаний всю сессию.
Подробности узла читай только в его файле: пути заданы в [таблице маршрутизации](../SKILL.md#выбор-узлов).

Типы полей определяй по значениям источника и задаче, а не по именам полей.
Числовой CSV разбирай при импорте; если формат не поддержан, сначала нормализуй и проверь преобразование значений до построения зависимой цепочки.
Новые NULL после смены типа — провал преобразования, а не успех, даже если выходная схема уже имеет нужный тип.
После смены upstream-схемы получи новую успешную операцию на том же существующем узле и используй её новый source_operation_id для чтения.

Явное бизнес-исключение категории закрепляй условием/Фильтром перед
соответствующей агрегацией, даже если сейчас этой категории в CSV нет.
Совпадение текущего результата не заменяет запрошенное правило сценария.

Если подготовленная таблица — непосредственный выход существующего текстового
Import и нужны только переименования/смена типов её полей, правь этот Import через
`settings.columns`; не добавляй Reform в обход этой правки. Просьбу не перенастраивать
загрузку CSV выполняй сохранением `settings.source` и `settings.format`, остальных
полей и их порядка; запрошенные имена/типы и необходимые output mappings меняй
на том же Import. Получи проверенную доставку исходного вложения текущей сессии
с `overwrite=reject`: повтор по прежнему пути runtime принимает только после
сравнения серверных байтов. При `UPLOAD_PATH_CONFLICT` не меняй путь или политику
перезаписи ради обхода отказа.

Сначала выдели требуемые результаты и преобразования. Сопоставь их стандартным
типам из knowledge.node_types и их композициям, проверь релевантные
parameter_schema и Help. Не требуется перебирать все типы или выполнять
заведомо неподдерживаемые операции. Если стандартная композиция решает задачу,
построй её. Если остаётся конкретная неподдерживаемая операция, назови её,
рассмотренные варианты и подтверждённое ограничение перед запросом схемы JS.
JavaScript используй только для этого остатка или явно указанной пользователем
части. Отсутствующий публичный режим отличается от ошибки его применения;
недоступность терминала и execute_code не означает отсутствие стандартного решения.

При функциональном пробеле перед JS apply проверь весь `source_text`: каждое
преобразование, в том числе внутри циклов и условий, должно относиться к
обоснованной недоступной операции. Например, для списка `Tags` неизвестной
длины JS выдаёт исходные части в `RawTag`: `" red ;;blue"` → `" red "`, `""`, `"blue"`.
Затем стандартный Калькулятор вычисляет `Tag = Trim(RawTag)`, Фильтр исключает
пустые строки и Null, Группировка считает вхождения, Сортировка и Экспорт
завершают сценарий. При таком пробеле `.trim()` и пропуск пустых частей в JS
выходят за разрешённую роль. При отказе следующего стандартного шага исправь
его либо сообщи блокер; не переноси его в JS. Этот пример относится к допуску
по функциональному пробелу; явный запрос JS определяет разрешённую часть сам.

Для каждого поддержанного узла используй loginom_dock_node_apply. Он сам возвращается
из хранилища к нужному сценарию. Перед первым узлом данного типа запроси
loginom_dock_action_describe({node_types:[тип]}) и следуй его parameter_schema.
Не используй node.add для обхода ошибки параметров. Терминал, read_file и
execute_code недоступны; вложение передаётся через input_artifacts.
Координаты, mappings и read можно опустить. По умолчанию выходные поля
сохраняются, Execute читает обычную выборку; это не полный аудит таблицы.
У точных чисел значение может быть только в decimal; отсутствие дублирующего
value не означает NULL. Учитывай type, precision и is_null каждой ячейки.
Для отдельных переименований/исключений используй output mappings.changes;
Dock сохранит остальные поля. mappings.fields — полный список всех полей.
Оба способа одновременно запрещены; обязательные поля узла исключать нельзя.
Построй граф и параметры по заданию. Доступные обработчики и режимы перечислены
в knowledge.node_types; профиль ограничен Loginom 7.4.2.
Все новые числовые показатели отчёта вычисляй в узлах сценария и читай их выход.
Если показателя нет в выходе, добавь вычисление; не досчитывай средние, суммы или
проценты в тексте ответа по просмотренной таблице. Округление лишь оформляет результат.
Сначала выдели каждый требуемый результат из задания. Перед завершением сопоставь
каждый пункт с выполненным узлом и прочитанным результатом. Два разреза в одном
пункте требуют проверки обоих. Если пункт не выполнен, продолжи работу или явно
укажи конкретное ограничение; сохранённый пакет сам по себе не означает полноту анализа.
При LOGIN_REQUIRED войди в открытом браузере и повтори loginom_dock_prepare.
Используй выбранные storage_directories для пакетов, входных файлов и экспорта.
Локальный `.lgp` для правки открывай через `loginom_dock_prepare` с
`intent: open_package` и `local_package_path`; путь собственной открытой копии
бери из `workspace.package_ref.path`. `package_path` относится к серверному пакету.
Для локальных CSV/TSV/TXT >16 МиБ или неизвестного размера после prepare сначала
вызови `loginom_file_profile({path})` вместо Read. Ответ содержит готовые
`source`/`format`/`columns`; пустой `source_path` заполняется только после доставки.
Неоднозначные параметры явно уточни. При continuation собери все страницы колонок:
страница с `settings_complete:false` не является полными настройками импорта.
Точный count, SHA и первое нарушение типа даёт отдельный отменяемый
`loginom_file_scan({profile_id})`; прерванный проход остаётся partial.
Затем `loginom_file_sample({profile_id,seed,max_records,max_bytes})` создаёт
не более 8 МиБ исходных байтов целыми записями с одним заголовком. Зарегистрируй
его возвращённый `path` через `loginom_file_admit`, доставь artifact и построй
сценарий на выборке. Сохрани profile_id и manifest для происхождения результата.
Честно назови результат выборочным: «полный расчёт будет после загрузки полного
файла». До подтверждённой доставки полного источника не обещай полный сценарий
или полные суммы. LOGINOM_FILE_CHANGED требует нового профиля исходника.

Малые файлы данных по локальным путям сначала зарегистрируй после успешного prepare:
`loginom_file_admit({path: "путь из prompt"})`, отдельно для каждого источника.
Не заменяй пути требованием вложить файл. Используй выданные artifact/grant при
доставке, а её подтверждённый destination — при импорте. После повторной
подготовки зарегистрируй локальные файлы заново, получив новые artifact IDs.
Прикреплённые пользователем файлы поступают в input_artifacts через native hook.
Если их нет, сообщи, что передача вложения не подтверждена; не придумывай путь
на сервере и не считай текстовый фрагмент из сообщения полным датасетом.
Если файл уже есть в input_artifacts, ошибка каталога или подготовки не означает
потерю вложения. Актуальный список доступен через loginom_dock_action_describe({}); новый
пакет для этого не требуется. При ARTIFACT_DESTINATION_UNAVAILABLE сопоставь
выбранную папку с вошедшим аккаунтом; повторное вложение не исправит доступ.
Загрузи файлы данных из input_artifacts через loginom_dock_artifact_deliver, сохрани подтверждённую identity
источника для импорта. Каждый node.apply сам проверяет настройки и выполнение.
Для loginom_dock_node_resume передавай только исходный operation_id; запрос хранится в Dock.
Промежуточные выходы читай лишь для следующего решения или диагностики.
Если успешный apply/wait уже вернул нужные строки и схему с sample_complete=true,
используй этот результат; не вызывай node_read повторно без изменения источника.
Для повторного чтения выхода без изменения вычислений используй loginom_dock_node_read
с новым operation_id, source_operation_id успешной локальной операции и read
(например, sample_rows:100, require_exact_numbers:true). Dock выполняет существующий
узел и читает свежий выход без мастера настройки; не передавай формулы, mappings и finish.
Для новых JS-узлов и переноса вычислений в JS действует правило допуска выше.
Чтение и исправление существующего JS-узла, которого касается запрос, разрешены;
это не разрешение переносить в него остальные стандартно решаемые шаги.
При running жди тот же ID через loginom_dock_node_wait.
Для исправления уже завершённого узла используй loginom_dock_node_apply с новым operation_id,
target.kind=existing, выданным target.ref и inputs:[] для сохранения связей.
Новый operation_id с target.kind=new создаёт ещё один узел.
Для узла сохранённого исходного пакета идентификатор ref.node_id — постоянный
GUID, не имя/label узла. Если исходные данные содержат манифест kind=source_only
с package_basename и node_ids, он задаёт только постоянные GUID этого пакета;
бери document_id/workflow_id из свежего loginom_dock_prepare для открытого пакета.
Не угадывай GUID и не подставляй имя вместо него.
В loginom_dock_node_apply передавай workflow_ref только как {workflow_id}, используя
выданные document_id и workflow_id. Длинный путь навигации клиент хранит локально;
не копируй и не восстанавливай tab_tid, prefix, navigation_path в запросе узла.
В компактном ответе configuration.readback содержит наблюдённые настройки и
привязку к узлу и квитанциям; сравни их с задачей. Выборка output.ports сохраняет
запрошенные строки в пределах бюджета операции. Для проверки этих же настроек
не открывай мастер повторно; сохранение подтверждай отдельной квитанцией пакета.
В итоговом отчёте используй только подтверждённые результаты выполненных узлов.
Если sample_complete=false, это часть таблицы: не дополняй её невидимыми строками,
другим концом рейтинга или предположениями из фрагмента CSV. Запрашивай нужный
разрез и объём результата через узлы. Общие суммы и средние тоже вычисляй узлом,
а не вручную из групповых средних; явно называй, по каким строкам рассчитан показатель.
Не выдавай причины отклонений и эффективность подразделений за установленный факт,
если данные показывают только суммы. Отделяй рекомендации от доказанных результатов.
Не повторяй уже подтверждённые проверки. При running жди тот же operation_id;
при неопределённом результате сначала восстанови его, не начинай заменяющую операцию.
Ошибку параметров исправляй по установленной схеме. Дополнительные знания ищи,
если имеющегося описания и наблюдённого состояния недостаточно.
Ошибка параметров, timeout, временный отказ и неполная выборка не разрешают
перейти на JavaScript. При неопределённом результате сначала восстанови исходную
операцию. При подтверждённом отказе исправь запрос по схеме и следуй next_step;
освобождение неопределённой узловой операции описано в browser.md.
При невозможности продолжения сообщи конкретный блокер.
Обычное чтение получает значения напрямую от выходного порта без Table и смены
форматов. Оба значения require_exact_numbers сохраняют точные поддерживаемые
скаляры; true дополнительно отказывает при неподтверждённом Variant, нечисловом
real и неоднозначной дате. При false учитывай явные ограничения precision.
Сохрани готовый пакет в конце через package.save_checkpoint, дождись квитанции.
При правке локального `.lgp` без указанного пути сохранения используй полный
`workspace.package_ref.path` собственной загруженной копии; `conflict_policy: replace`
разрешён только для её перезаписи. Если путь указан, действуют прежние правила.
В ответе назови полный серверный путь и прямо скажи, что локальный файл не изменён.
Если dock_saved_package_state сообщает modified:true, выполни его следующий шаг
сохранения того же собственного пакета с новым ID перед завершением. Не отбрасывай
изменения и не повторяй переоткрытие для устранения dirty-state.
Промежуточное сохранение — по просьбе пользователя или перед риском потери работы.
package.save_as с переоткрытием используй при запросе переоткрытия. package_saved:false
у узла описывает границы node.apply и не требует дополнительного сохранения.
Не приписывай данным валюту, если она не указана. Полные квитанции и диагностика
сохраняются локально; ограничения результата остаются обязательными для вывода.

Технические deadlines задаёт runtime. Не передавай budgets или budget_ms,
не расширяй исходный срок незавершённой операции и не запускай её заново
после неопределённого результата. Полный read-only протокол и ограничения
поддержанных узлов определяются схемами текущего каталога.

## Серверный источник и cache

Для серверного цикла «скачать источник в cache → выборка → полный файл» снова
найди исходный путь через `loginom_dock_storage_source`, затем вызови
`loginom_dock_storage_download_start` с возвращённым `server_source_ref` и новым
`operation_id`. Дождись завершения через status/wait с тем же `operation_id`.
Только успешный download разрешает профиль, точный `loginom_file_scan` и
`loginom_file_sample` по возвращённому локальному `output.path`.
Зарегистрируй и доставь только выборку; полный файл уже есть на сервере.
Построй сценарий на выборке и сохрани checkpoint. Для `source_switch` передай
`profile_id` скачанной копии и исходный серверный источник `kind:"storage"`.
Перед переключением снова открой его каталог через `loginom_dock_storage_source`.
Runtime заново сверяет native size/mtime и связь точного scan с копией в cache.
При `LOGINOM_FILE_CHANGED` останови полный расчёт: найди исходник заново и повтори
скачивание и точную сверку в новой операции. Старый cache не подтверждает подменённый файл.
Проверка источника может оставить навигацию в Files. Перед Save вернись через
`loginom_dock_prepare` с `intent:"existing_workflow"` и последним `workflow_ref`
этого runtime, включив `document_id`; после Save бери ссылку из
`workflow_continuations`. Затем Save с новым `operation_id`. Такой возврат
восстанавливает навигацию, но не разрешает полный расчёт по старому cache.
Не подменяй точную сверку числом видимых строк или preview, не экспортируй и
не загружай полный серверный исходник повторно. После завершения вызови
`loginom_dock_storage_download_cleanup` с operation_id скачивания.
