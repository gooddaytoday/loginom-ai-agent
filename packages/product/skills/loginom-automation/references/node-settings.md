# Настройки штатных узлов

Перед применением узла прочитай соответствующий раздел и его `parameter_schema`.

## Заполнение пропусков

Для замены числовых NULL нулём выбирай `preprocessing.data_recovery`, `mode:"impute"`,
`parameters:{fields:[{field:{kind:"input_field",name:"Amount"},method:"zero"}],max_nulls_percent:100,ordered:false}`.
`zero` — нативный метод для integer/real обоих видов данных; `value` не передавай.
`mean` требует непрерывное числовое поле, `constant` — дискретную строку и строковое
`value`. Переданный `fields` полностью заменяет обработку: неперечисленные поля
выключаются. Для сохранения настроек существующего узла передай `parameters:{}`.
Порог — явное целое 0–100; выше порога и в полностью пустых полях NULL могут
сохраниться. Существующие нули и необрабатываемые поля сохраняются. Используй
`finish:"execute"`, читай порт 0. Median/mode, ordered и интерполяция не поддержаны.

## Корреляция Пирсона

Для корреляции Пирсона числовых полей используй `dock_node_apply` с
`target.type:"research.corr_analysis"`, `mode:"pearson"`,
`parameters.first_set` и `parameters.second_set` — полные массивы технических
имён полей. Подключи таблицу к входу 0, `finish:"execute"`, `read.ports:[0]`.
Каждое поле первого набора сопоставляется с каждым полем второго; native
порядок — второй набор снаружи, первый внутри, по входному порядку полей.
Выход: ColSet1, ColSet1_Label, ColSet2, ColSet2_Label, Pirson. Пропуски
исключаются попарно, при нулевой дисперсии коэффициент NULL. Для этой
корреляции не вычисляй суммы и коэффициент в Калькуляторе или JavaScript.
На существующем узле переданный набор заменяет прежний; пропуск сохраняет его.
В этапе 1 поддержаны непустой источник и минимум два совместных наблюдения
на пару; другие коэффициенты не поддержаны.

## Замена по регулярному выражению

Для замены по регулярному выражению используй `dock_node_apply` с
`target.type="transform.replace_columns"`, `mode="regex"`, а не Калькулятор
или JavaScript. В `parameters.rules` задай `field={kind:"input_field",name:…}`,
`type="string"`, упорядоченные `pairs` с `from={type:"string",value:<шаблон>}`
и `to={type:"string",value:<константа>}`, `other={mode:"keep"}` или `null`.
Первое совпадение подстроки заменяет всю ячейку константой; ссылки на группы (знак доллара с номером) не подставляются и попадают в значение буквально.
Для игнорирования регистра ставь `(?i)` в начале шаблона; `case_sensitive`
и `precision` полностью опускай. Поддержаны ASCII-литералы, группы, `[0-9]`,
положительный `{n}`, `^`/`$`. `output_mode="add"` сохраняет исходное поле,
`replace` заменяет его; обе настройки дают логический `<поле>_Replaced`.
Для изменения текста замены передай тот же existing ref и полное правило
этого поля; незаданные поля и `output_mode` сохраняются. Смешанные exact/regex
таблицы и другие конструкции требуют явного отказа, а не обхода через JS.
## Выбросы и экстремальные значения

Для поиска выбросов и экстремальных значений по SD или IQR выбирай
`dock_node_apply`: `target.type:preprocessing.elim_outlier`, `mode:detect`.
В `parameters.outlier` нового узла задай `fields` (технические имена только
непрерывных числовых полей), `method:sd|iqr`, явные `outlier_factor`,
`extreme_factor` (не меньше первого) и `ordered` (признак уже упорядоченного
входа, без сортировки). Detect сохраняет исходные значения (keep/keep),
обучается на текущем входе перед Execute. Используй `finish:execute` и
`read.ports:[0,1,2]`: все строки, выбросы без экстремумов, экстремумы.
Для patch существующего узла неуказанные параметры сохраняются.
Эту поддержанную операцию выполняй данным узлом; Калькулятор и JavaScript
для её самостоятельного вычисления не нужны. Другие политики редактирования,
quality и применение сохранённой модели к новому входу пока недоступны.

## Скользящее окно

Для копий предыдущих и следующих записей выбирай `dock_node_apply` с
`target.type="transform.sliding_window"`, `mode="lag"` и
`parameters.windows=[{field:"Sales",history:3,horizon:1}]`. Новый узел требует
явный `incomplete_records`: `keep_incomplete` добавляет неполные края,
`drop_added` сохраняет исходные строки, `drop_all_incomplete` обрезает края,
сохраняя настоящие NULL. Порядок входа задаёт время. Для лагов используй этот
узел; Калькулятор и JS для этого шага не нужны. На существующем узле пропуск
параметра сохраняет его, `windows:[]` сбрасывает все окна.

## Слияние

Для сопоставления двух таблиц по ключам используй `loginom_dock_node_apply` с
`target.type:"transform.join_data"`: `mode:"right"` сохраняет все строки правого
входа, `"full"` — обоих входов, `"difference"` — только строки левого входа без
пары справа. Укажи `inputs` с портами `input:0` для левой таблицы и `input:1`
для правой, `parameters.keys:[{left,right}]` для всех частей ключа одновременно,
явные `case_sensitive` и `include_joined_keys`. Повторные ключи сохраняют все
совпавшие пары; отсутствующая сторона заполняется NULL. В `difference` выход
содержит только поля левой таблицы при любом `include_joined_keys`. Для этих
операций выбирай Слияние; Калькулятор предназначен для формул по строкам.
Имена полей ключей должны иметь одинаковые типы; конфликты выходных имён
устрани через входные `mappings`. Существующий узел без перенастройки выполняй
с его фактическим `mode`, `parameters:{}`, `inputs:[]`, `mappings:[]`.

## Выборка и разбиение

Первые/последние N строк выбирай узлом `preprocessing.sampling`, `mode:"sequential"`, `parameters:{count:N,position:"first"}` или `position:"last"`. Последовательное разбиение выполняй `preprocessing.data_partition`, `mode:"sequential"`, `parameters:{train_count:N,test_count:M,allocation_order:"test_train_unused"}`. Размеры — в строках; порядок выделения задаётся `allocation_order`. Обычный `finish:"execute"`, без обучения. Читай порты `[0,1,2]`: общий/train/test; общий содержит сначала train, затем test и первое поле `IsTestSet` boolean (false/train, true/test). Для полного малого результата укажи `sample_rows:100,require_exact_numbers:true` и проверь полноту. Маркер NULL для экспорта выбирай по правилу раздела «Экспорт». Для полей `datetime`, если пользователь не задал формат экспорта, у `exports.text` явно укажи `date_format:"yyyy/mm/dd",date_separator:"-",time_format:"hh:nn:ss.zzz",time_separator:":"`: пустые настройки используют локальный формат даты. Для этих операций выбирай указанные узлы; Калькулятор и JavaScript не нужны. Случайную выборку создавай тем же `preprocessing.sampling`, `mode:"random"`, `parameters:{count:N,seed:42}`. У `preprocessing.data_partition` случайное разбиение задавай `mode:"random"`, `parameters:{train_count:N,test_count:M,seed:42}`; приоритет тестового множества выключен. В random не передавай `position` или `allocation_order`. Новый узел требует явные размеры и seed; существующему передавай только изменения. Для повторного выполнения сохраняй источник и seed, используй существующий узел и `finish:"execute"`, затем сравни полные результаты. На просьбу о стратификации (`stratified`), отборе со смещением (`biased`) или равномерном случайном методе сообщи пользователю: «Этот режим пока не поддерживается». Не подменяй эти режимы другим алгоритмом.

## Логистическая регрессия

Для бинарной строковой цели и вероятности события используй
`loginom_dock_node_apply` с `target.type:"datamining.log_regression"`,
`mode:"enter"`, `parameters:{logistic:{input_fields:[...],target_field:"...",event:"...",threshold:...}}`.
Укажи точную метку события и явный порог: событие при `p >= threshold`.
`finish:"execute"` обучает на всех строках текущего входа и выполняет модель;
`read.ports:[0]` возвращает класс, вероятность и исходные поля.
`input_fields` содержит только числовые факторы; идентификаторы и комментарии
сохраняются без роли. Константа и epsilon 1e-10 фиксированы. Для этого
поддерживаемого обучения выбирай Логистическую регрессию; Калькулятор и
JavaScript не нужны. Для отбора факторов используй тот же узел с `mode:"forward"`, `"backward"` или `"stepwise"`: критерий и пороги отбора — стандартные Loginom. Выбор критерия и пользовательские пороги включения/исключения пока не поддерживаются. Если пользователь просит их изменить, сообщи, что это пока не поддерживается; не передавай такие параметры и не подменяй просьбу стандартным отбором. `input_fields` — кандидаты; исключённые факторы сохраняются в выходной таблице. Для отбора также выбирай Логистическую регрессию. Режим apply, веса, валидация, коэффициенты и
выход переменных пока недоступны. Сначала запроси `parameter_schema` узла.

## Применение линейной регрессии

Для прогноза LinReg на новых данных используй `mode:"apply"` на уже обученном узле с сохранёнными `input_fields`/`target_field`, `inputs:[]`, `finish:"execute"`; `enter` обучает или переобучает модель.

## Дата и время

Для календарных признаков выбирай `loginom_dock_node_apply` с
`target.type:"transform.date_time"`, `mode:"calendar"` и
`parameters.fields:[{field:{kind:"input_field",name:"DateA"},transformations:[{operation:"iso_year",name:"ISOYear",label:"Год ISO"}]}]`.
Входные поля должны уже иметь тип `datetime`. Календарный год — `year`,
ISO-год — `iso_year`, номер ISO-недели — `iso_week`, её понедельник в полночь —
`iso_week_start`, день недели от понедельника 1 до воскресенья 7 — `day_of_week`.
Эти признаки вычисляй данным узлом. Поддержаны также `quarter`, `month`,
`day_of_month`, `hour`, `year_start`, `year_end`, `quarter_start`, `quarter_end`,
`month_start`, `month_end`, `date`. На поле допускается до 12 преобразований.
Каждый элемент `fields` заменяет полный набор преобразований указанного поля;
для удаления одного признака перечисли все сохраняемые преобразования этого
поля. Неуказанное второе поле сохраняется. На existing узле `parameters:{}`
сохраняет настройки, `transformations:[]` очищает только указанное поле.
Порядок выходов задавай через `mappings` output 0 с `autosync:false` и полным
списком `fields`, адресуя конечные имена как `source:{kind:"configured_field",name:"ISOYear"}`.
Используй `finish:"execute"`, `read.ports:[0]`; Save выполняй отдельно.
Конец ISO-недели (`iso_week_end`) недоступен из-за ошибки платформы Loginom:
на такую просьбу сообщи ограничение и не подставляй рассчитанное значение.
Для CSV дат используй формат и разделители из раздела «Экспорт».

## JSON в дерево и дерево в таблицу

Для одного JSON object в одной строке строкового поля сначала выполни и полностью
прочитай источник. Используй `trees.from_json`, `mode:"auto_structure"`,
`parameters:{json_field:"Document",root_mode:"auto"}`, `finish:"execute"` и
`read:{ports:[0],sample_rows:100,require_exact_numbers:true}`. Выход 0 — типизированное
дерево: `tree.schema` хранит порядок, имена, типы, контейнеры и массивы;
`tree.instances` — все экземпляры, их пути, порядок, значения и NULL. Большие
целые передаются десятичными строками. Не восстанавливай дерево из текста задачи.

Подключай этот же порт к `trees.to_table`, `mode:"selected_nodes"`.
На новом узле обязательны `selected_paths` (пути листьев схемы в её порядке,
например `/id`, `/items/sku`, без индексов массива), `repeat_parents`,
`composite_names:false`, `composite_labels:false`, `label_separator:"."`.
`repeat_parents:true` повторяет выбранных родителей для каждой позиции;
`false` оставляет их только в первой строке, далее NULL. Выход 0 — таблица.
Полностью прочитай её, проверь типы и порядок, затем экспортируй и сохрани пакет.
Пустая строка, ноль и false сохраняются; missing scalar и JSON null дают NULL.
Для экспорта таблицы с NULL и пустыми строками явно выбери непустой маркер NULL.

Первый этап поддерживает одну непустую повторяющуюся ветвь объектов с уникальными
именами листьев, до 64 выбранных полей. Нет ручной схемы, XSD, forced root,
дат, Variant, нескольких sibling arrays, индексных и составных колонок.
Дерево ограничено 256 экземплярами, глубиной 16 и 1 MiB; превышение — отказ,
без обрезания. На существующем узле `parameters:{}` сохраняет настройки,
явный `selected_paths` заменяет весь выбор. При отказе области поддержки
сообщи ограничение; не заменяй эти узлы JavaScript или вычислениями по вложению.

## Автокорреляция

Для зависимости числового ряда от предыдущих значений выбирай `dock_node_apply`
с `target.type:"research.auto_correlation"`, `mode:"time_domain"`.
В `parameters.autocorrelation` нового узла передай `field` — одно точное
техническое имя integer/real поля — и `lag_count` — число отсчётов от 1,
включая лаг 0. Используется порядок записей входа; отдельную сортировку добавляй
по просьбе пользователя. Подключи таблицу к входу 0; остальные поля, например
RowID, в расчёт не входят. `finish:"execute"`, `read.ports:[0]`; для полного
результата задай достаточное `sample_rows` (до 100). Временная область и ЧАКФ off
входят в режим. Этот расчёт выполняй узлом Автокорреляция; Калькулятор, JavaScript
и корреляция сдвинутых полей для него не нужны.
Выход содержит Lag и native поля АКФ, ошибки и Boolean значимости в порядке
возрастания лагов. Число строк ограничено длиной входа, исходные поля не проходят.
На существующем узле пропуск `field`/`lag_count` сохраняет поддержанную настройку;
для замены входного файла обнови исходный импорт и выполни тот же existing узел
с прежними параметрами, `inputs:[]`, `mappings:[]`. Новый узел для этого не создавай.
Поддержан ряд из минимум двух конечных непустых значений с положительной
дисперсией. NULL вызывает отказ «Данные содержат пустые значения»: покажи причину,
сохрани NULL; не подставляй ноль и не выдавай прежний результат. Частотная область,
ЧАКФ и несколько серий пока не поддержаны.


## Сглаживание Ходрика–Прескотта

Для сглаживания ряда Ходрика–Прескотта используй `dock_node_apply` с
`target.type="preprocessing.smoothing"`, `mode="hodrick_prescott"` и
`parameters.smoothing:[{field:"X",lambda:1},{field:"R",lambda:1}]`.
Для каждого непрерывного integer/real поля укажи ровно одно из `lambda`
(0.0625…102659800000000) или связанного `period` (2…20000).
Входной порядок строк задаёт последовательность ряда; исходные значения и NULL
сохраняются, добавляются real-поля X_S/R_S. Для этой операции выбирай Сглаживание;
Калькулятор и JavaScript для вычисления тренда не нужны. Новый узел требует полный
список правил; на существующем пропуск `smoothing` сохраняет настройки,
`smoothing:[]` выключает обработку всех полей. Выполняй `finish:"execute"`,
`read.ports:[0]`, без обучения. После замены файла выполни прежний узел;
не пересоздавай его. All-null может дать нативную ошибку алгоритма, её нужно
сообщить пользователю. Для точного порядка полей используй существующий
`mappings:[{direction:"output",port:0,autosync:false,fields:[...]}]`, перечислив
все исходные и сглаженные поля через `source:{kind:"configured_field",name:...}`
в запрошенном порядке. Естественный autosync-порядок может измениться при новом
открытии. Вейвлеты в этом режиме не поддерживаются.
