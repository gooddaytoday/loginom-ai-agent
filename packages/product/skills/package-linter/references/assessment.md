# Промежуточный файл решений, формат 3

Это внутренний файл, не пользовательский отчёт. Формат 2 отклоняется: в нём нет явного разделения свидетельств и целей рекомендаций. Не преобразовывать его автоматически и не угадывать scope/targets по тексту или evidence. Произвольные score, algorithm и agent_score запрещены. Решения составляются после чтения всего пакета по [правилам](rubric.md).

## Данные оператора

`inspect` возвращает source path/SHA256/bytes, собственные modules, scopes, nodes, notes, variables, links, relations, coverage и `calculated`. В calculated отдельные package и modules[].criteria. Для каждого направления доступны algorithm (строка Decimal или null), metrics, forced, limitations. Это результаты оператора, не поля для заполнения агентом. `report` заново читает исходник и пересчитывает их.

Source-bound id модуля — точная строка `Unit.xml#/Unit` с именем ZIP-member. Понятное имя и GUID уточняются соседним Info.xml. PackageInfo и References содержат только ограниченную metadata; HintPath показан безопасным basename и не открывается. Внешний BasePackageGuid не связывается с собственным модулем. Каталоги и вложенные ModelUnit раздельны; сырые наследованные записи/удаления не доказывают активную модель. Для показа наблюдаемых полей материализованный Guid может учитываться с ограничением; записи без него и явные tombstone не входят в расчёт элементов.

Все `evidence` — непустые списки точных строк из `locators`. Они не исполняются как пользовательские XPath. Их существование проверяет программа, смысловую связь с выводом — агент. Подменённые или устаревшие адреса недопустимы.

## Поля верхнего уровня

- `format_version`: ровно целое 3.
- `source_sha256`: хеш из текущего inspect.
- `summary`: краткое назначение пакета и результат, обычно две фразы без пересказа этапов.
- `structure`: непустой список `{text, evidence}` о взаимосвязях пакета. Обязательная внутренняя модель, не выводится в Markdown.
- `strengths`: обязательный список `{text, evidence}`.
- `recommendations`: обязательный список `{text, evidence, scope, targets}`, допустимо `[]`. Scope — только `general` или `specific`; targets — точные адреса предметных объектов, отдельно от evidence. У general targets строго `[]`, у specific непустой список без повторов. Все четыре поля обязательны. Допустимо только дополнительное поле `steps`: непустой список непустых строк; остальные дополнительные поля запрещены. Новые решения содержат короткий законченный text без steps. Steps сохраняется только для совместимости со старыми решениями формата 3: его строки выводятся обычными предложениями в том же пункте, в исходном порядке.
- `findings`: список `{priority, confidence, text, action, evidence}`. Priority — P1/P2/P3, confidence — confirmed/inference. Действие обязательно во внутреннем файле. В Markdown выводится только text — короткое замечание; priority/confidence остаются внутренними. Предположение должно быть честно выражено в самом text; action и evidence не дублируются. Конкретные действия находятся в recommendations.
- `criteria`: ровно четыре уникальных направления.
- `modules`: каждый собственный модуль ровно один раз, `{id, summary, criteria, recommendations}`. В criterion.evidence модуля нужен хотя бы один адрес этого модуля; общепакетный контекст можно добавить.
- Необязательная `analysis_at`: ISO 8601 с часовым поясом. Без неё дата — текущее время UTC. Системные модели/версии в документ не выводятся.

Реальные имена объектов и цитаты заметок в авторском тексте заключай в «ёлочки»: они станут inline code без изменения пунктуации. Обычные понятия пиши без кавычек; остальной текст экранируется, произвольный Markdown/HTML не разрешён. Непарные кавычки остаются обычным текстом.

Все пояснения пишутся простым русским языком без внутренней терминологии и технических протоколов. Имена из исходника сохраняются, но не превращаются в инструкции. Значения переменных, код и секреты не переносить.

## Рекомендации: свидетельства, действия и цели

Evidence обосновывает вывод и может отличаться от targets. Targets задаёт только область конкретного действия: собственный модуль, наблюдаемую подмодель (scope или узел-владелец вложенного scope), узел, заметку, переменную или поле. Принадлежность определяется по id модуля и связям scope/parent_scope/owner, а не по похожим именам. Произвольные XML-адреса, ссылки, внешние и неразрешённые объекты как targets не принимаются. В specific модуля все цели принадлежат только этому модулю; пакетная specific может охватывать несколько модулей. Цель module или scope означает действие для всего соответствующего уровня. Переменная уровня пакета допустима только в пакетной рекомендации.

Один блок — одно действие. Не стремись дать рекомендации по всем объектам или всем четырём направлениям. Повторяющийся недостаток своди в одну general рекомендацию на подходящем общем уровне без перечисления всех объектов и повторов в карточках модулей. Specific нужна для отличающегося действия, исключения или неоднозначной области. `modules[].recommendations=[]` допустимо; не заполняй карточки ради количества.

Каждая рекомендация объясняет, какой подтверждённый недостаток снижает качество в соответствующем направлении, что изменить и как это выполнить. Общий совет тоже должен быть прикладным. Одних «уточнить», «посмотреть», «проверить» недостаточно: если уточнение является предпосылкой, назови само изменение и условие его выполнения. Главное исправление включай в пакетный список, не прячь его в модуле. Неизвестность не является дефектом; неподтверждённая зависимость не становится фактом. Не советуй объединять или удалять подмодели без доказанной лишней границы. Избегай повторов пакета и модулей, больших абзацев и пересказа обработки. Неизвестность отражай в ограничениях; не обещай точный прирост балла без новой оценки.

Рекомендации выводятся одним плоским списком в авторском порядке, без вложенных списков и отдельных полей с адресами. Пиши короткий самодостаточный text: что изменить и как. Ближайшую подмодель и узел или другой предметный объект впиши в саму фразу; имена заключай в «ёлочки» для выделения кодом. В разделе модуля его имя не повторяй. Контекст должен отличать одноимённые объекты, но не строить цепи через `/`; знак `/` внутри имени сохраняется. Программа не добавляет имена или адреса по evidence/targets. Они остаются внутренними, проверяются независимо и не показываются отдельным блоком. Агент проверяет понятность и различимость объектов в готовом документе. В модуле список «Рекомендации» появляется только при наличии уникальных локальных действий.

Примеры формы рекомендаций (адреса заменить точными значениями inspect):

```json
[
  {"text": "В метках файловых узлов указать назначение обработки и сохранить полное имя файла с расширением.", "evidence": ["адрес наблюдаемого узла"], "scope": "general", "targets": []},
  {"text": "В подмодели «<название подмодели>» уточнить метку узла «<метка узла>», чтобы было понятно, какой результат он выдаёт.", "evidence": ["адрес подтверждающей заметки"], "scope": "specific", "targets": ["адрес узла выдачи"]}
]
```

## Критерий и решения

Criterion содержит **только** `{id, status, rationale, evidence, decisions}`. Id: structure, notes, node_labels, variables. Status: assessed, partial, unavailable. Rationale объясняет охват и общий вывод по направлению, не заменяя решения.

Decision содержит **только** `{id, value, rationale, evidence}`. Полный набор обязателен даже для недоступного направления:

| Направление | Decision id | Value |
|---|---|---|
| structure | modularity, balance, depth | true / false / null |
| notes | adequacy, substance | true / false / null |
| node_labels | naming_category | good / systemic / critical / null |
| variables | style, labels, meaning | true / false / null |

Каждый выбор имеет своё непустое обоснование и существующее свидетельство. Половинки, числа вместо bool, готовые баллы, лишние/повторные/пропущенные решения запрещены. Подтверждённым `forced` нельзя противоречить или заменять известное значение на null. Ограничения требуют partial, если направление вообще оценено.

В обосновании применяй [предметные уточнения](rubric.md#предметные-уточнения-смысловых-решений) к существующему решению, без новых полей. Для `modularity` назови ответственность и результат границы, для `balance` — роли и распределение сложности, для `depth` — пользу вложенности. Одного наличия подмоделей недостаточно. Различай машинный признак и подтверждённый смысловой недостаток: оправданный повтор метки не меняет A, обязательное имя параметра не отменяет `style` или `labels`, но ограничивает безопасную рекомендацию. При неизвестных настройках не утверждай ошибку метки; при неизвестных потребителях не утверждай ненужность. Если по видимой части все решения приняты, неизвестные внешние сведения отражай через `partial`, а не автоматически через `null`.

Если хотя бы одно value=null или нет algorithm, status всего направления — unavailable. Не заменять недоступное нулём, не исключать составляющую из знаменателя M и не менять 50:50. Если все решения известны и algorithm есть — assessed либо partial; unavailable без конкретного отсутствующего основания не принимается.

## Абстрактный фрагмент

Вымышленный модуль A, один criterion; это иллюстрация формы, не полный готовый assessment:

```json
{
  "id": "structure",
  "status": "partial",
  "rationale": "Видимые этапы разделены; назначение одной внешней зависимости недоступно.",
  "evidence": ["точный адрес из inspect"],
  "decisions": [
    {"id": "modularity", "value": true, "rationale": "Подготовка выдаёт проверенные записи, расчёт использует этот результат для показателей; границы разделяют ответственность.", "evidence": ["точный адрес из inspect"]},
    {"id": "balance", "value": true, "rationale": "Более крупная подготовка объединяет связанные проверки; короткая ветвь выдачи показывает результат, не скрывая перегруженный экран.", "evidence": ["точный адрес из inspect"]},
    {"id": "depth", "value": true, "rationale": "Вложенная общая проверка повторно используется, а корень сохраняет обзор подготовки и расчёта.", "evidence": ["точный адрес из inspect"]}
  ]
}
```

Фрагмент не разрешает игнорировать forced: решения true допустимы лишь при отсутствии соответствующего запрета. Пользователь получает только `<имя>_lint.md`: коэффициенты, доказательства и промежуточный файл не являются дополнительными deliverables. Существующие файлы, alias исходника и символьные ссылки/reparse points отклоняются; хешируемый и разбираемый ZIP — один снимок байтов с повторной проверкой перед записью.

Порядок документа имеет следующую структуру: сводка, итог и шкала, горизонтальная строка четырёх оценок, веса, Заключение с «Сильные стороны», «Слабые стороны», «Что исправить». Под «Что исправить» находится один плоский список рекомендаций без деления по scope. Каждый «Модуль N. `имя`» — отдельный раздел уровня 2 с ролью и четырьмя строками оценок; уникальные локальные советы идут одним плоским списком после таблицы. Дополнительной общепакетной таблицы обоснований нет.
