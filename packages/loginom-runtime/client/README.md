# Локальный клиент Loginom Dock

Установка, обновление и восстановление для пользователей: [INSTALL.md](INSTALL.md).
Карта кода и ограничения: [памятка агенту](../docs/loginom-dock/agent-handoff.md).
Расположение активной среды, очереди и pins конкретной сессии:
[operations.md](../docs/loginom-dock/operations.md).

Общий MCP-компонент для Windows/macOS/Linux. Он обслуживает initialization,
подключает удалённый Dock и локальный Playwright MCP, объединяет их настоящие
каталоги tools, отвергает коллизии и сохраняет каталог/версии на сессию.
Для каждого запуска создаётся отдельный профиль браузера в каталоге Dock.
`dock_prepare` загружает и проверяет полный серверный skill, возвращает инструкции
в текущий контекст и закрепляет ревизию за сессией. Native-адаптеры и архив подключены к Codex и Hermes. Полная приёмка первого
релиза отражается в журнале реализации.

Зависимости фиксируются `package-lock.json`: MCP SDK 1.30.0, Playwright MCP 0.0.80.
Последний использует Playwright `1.63.0-alpha-2026-08-31` и Chromium revision 1243
(153.0.8010.12). Комплект прошёл сценарии на живом Loginom.
Node.js закреплён в `.node-version` (24.19.0). Системный Node не заменяется.

Используйте закреплённый Node и `npm ci --ignore-scripts`, затем:

```sh
node bin/install-browser.mjs --state-dir /absolute/dock-state
node bin/loginom-dock.mjs --config /absolute/dock-client.json \
  --state-dir /absolute/dock-state --agent codex --adapter-revision 0.1.0-rc.2
```

`client.json` — обычный клиентский ключ сервера с полями `endpoint`, `api_key`,
`account` и `user` (оба `loginom-dock`), права 0600. Путь передаётся явно или через
`LOGINOM_DOCK_CONFIG`; личные `OPENVIKING_*`, `ovcli.conf` и memory provider не читаются.
Endpoint — HTTPS `/mcp`. Если `--state-dir` отсутствует, используется собственный
`~/.loginom-dock`. Для Hermes укажите `--agent hermes` и ревизию его адаптера.

Браузер видимый по умолчанию. `--headless` предназначен для технических проверок;
он не заменяет приёмку видимого Loginom. Закрытие клиентской среды закрывает её
дочерний browser MCP. Профиль и артефакты остаются локально. Сам MCP без native hooks
не активирует архив; фактический статус активации виден в диагностике.
`dock_diagnostics` показывает версии, пути и число инструментов без credentials.

Режим запуска закрепляется на весь процесс. Без параметра используется `classic`,
который сохраняет поведение опубликованного клиента. Для первого E2E-MVP оператор
явно запускает отдельный процесс с `--mode executor-preview`. Он до публикации
tools проверяет серверный `current.json`, manifest, SHA-256 каталогов, E2E commit,
capability ABI, минимальную ревизию executor и attestation для точного runtime.
В проверенном кандидате `rc.3` доступны `dock_action_describe`, `dock_action_run`
и наблюдение графа `dock_workspace_observe`. Доработка от 5 сентября расширяет
наблюдение и добавляет `dock_ui_action`, `dock_operation_inspect`,
`dock_operation_recover` в эту же сессию. Её реализация и приёмка продолжаются;
старый комплект не получает новые tools из обновления skill. Raw browser tools
и `dock_clipboard_transfer` отсутствуют. `--mode research` явно включает прежние
браузерные инструменты для исследования, но не публикует action tools. Модель,
action definition и сервер не могут изменить режим текущей сессии.

До production-активации оператор может запустить `--mode executor-replay` с двумя
обязательными pins: `--action-manifest-uri` указывает ровно на immutable manifest
в каталоге Dock, а `--action-manifest-sha256` фиксирует его содержимое. Replay
принимает `candidate` actions, но отклоняет `stale`; каталог инструментов остаётся
таким же ограниченным, как у `executor-preview`. Эти параметры задаются только при
старте процесса и не публикуются модели как инструменты.
Для native-плагина тот же выбор можно сделать до запуска агента через переменную
`LOGINOM_DOCK_MODE=executor-preview`; отсутствие переменной всегда означает
`classic`. Не разрешайте модели изменять окружение или регистрацию MCP ради смены
режима.

Канонические definitions, selector symbols, schemas и capability ABI находятся в
`executor/`. `deploy/loginom-dock/build-action-catalog.mjs` детерминированно строит
неизменяемый release. При переданном свежем E2E source manifest он по dependency
graph помечает только затронутые действия `stale` и создаёт candidate, который
`executor-preview` не примет. Candidate является режимом сборки по умолчанию, затем
неизменяемые файлы размещаются через `publish-action-catalog.py --stage` без
изменения `current.json`. После review и replay оператор передаёт отчёт через
`--activate --attestation <файл>`: неизменяемые candidate bytes сохраняются, а
production pointer связывает manifest и attestation по SHA-256. Отчёт содержит
точный runtime, проверенную UI-сборку Loginom, Hermes/Xiaomi MiMo 2.5 и обязательные
результаты. Повторная сборка не повышает `stale` до принятого состояния.

`dock_prepare` использует общий lifecycle обычного режима и replay: открывает
Loginom, проверяет frontend build через публичный `bg.app.Version`, определяет
готовый workflow. При `LOGIN_REQUIRED` пользователь входит в окне и повторяет
подготовку. Операторский `--replay-bootstrap --replay-login-user ACCOUNT` разрешает
вход только в явно выбранную учётную запись тестирования без пароля; имени
по умолчанию нет, каталог хранилища определяется отдельно; он не запускает отдельный путь подготовки при старте MCP. Действия запрещены
до `prepared: true`. Node refs включают workflow identity. `operation_id` связывает
повтор запроса с прежним результатом; фазы записываются после redaction в приватный
`execution-events.jsonl` до изменения UI. Неизвестный эффект блокирует новые
изменения до reconciliation. В прежнем `rc.3` отсутствие подтверждения cleanup
после потери связи требует завершить изолированную клиентскую сессию; новое
расширение добавляет проверку фактической браузерной квитанции и восстановление.

В расширенном интерфейсе агент работает по циклу «наблюдать → определить причину →
выбрать действие/исправление → проверить → продолжить». Три готовые операции
`node.add`, `link.create`, `package.save_as` сохраняются. Контракты инструментов:

| Tool | Назначение |
| --- | --- |
| `dock_action_describe` | При `{}` возвращает `available_actions` с тремя точными именами; при `action_key` возвращает definition выбранной операции |
| `dock_workspace_observe` | Читает граф, настройки, диалоги, сообщения, маски и ячейки таблиц; возвращает доступные UI `ref` и `observation_id` |
| `dock_ui_action` | Принимает `observation_id`, `operation_id`, `action` с `verb` из `click`, `double_click`, `fill`, `press`, `drag` и полями по схеме; выполняет один жест по свежим собственным refs |
| `dock_operation_inspect` | По необязательному `operation_id` читает браузерную квитанцию и сверяет заданную либо текущую pending-операцию |
| `dock_operation_recover` | Принимает исходный `operation_id`, отдельный `recovery_operation_id` и `strategy` из `complete_link`, `restore_control`, `accept_observed_state`, `abandon_operation`; для последних двух нужен `observation_id`; проверяет возможность и результат восстановления |

Агент начинает с discovery, не угадывая action keys. Неизвестное действие и
ошибочные аргументы возвращаются обычным MCP-content с `FAILED`; существующая
неопределённая операция сохраняет `AMBIGUOUS`. Эти ошибки запроса не означают
отказ MCP-сервера. `dock_prepare` возвращает capabilities и инструкции текущего
клиента, которые уточняют ограничения более старого полного server skill.
В старом `rc.3` пустой describe может не соответствовать схеме; ориентиром остаются
фактические tools и схемы текущей сессии.

При добавлении узла рядом с другими Loginom может автоматически создать связи.
Обновлённый `node.add` возвращает их в `output.auto_created_links` вместе с
`SUCCEEDED` и `goal_verified: false`, если подтверждены ровно один нужный узел,
его имя и положение, прежние узлы, порты и связи не изменились, а все новые связи
относятся к этому узлу. Одни такие автосвязи не создают pending-блокировку.
Агент проверяет граф по цели: полезные связи оставляет, ненужные удаляет через
обычный `dock_ui_action`. Посторонние изменения графа остаются `AMBIGUOUS`.

`action` использует только соответствующие жесту поля `ref`, `text`, `key`,
`source_ref`, `target_ref`. JavaScript, CSS/XPath, произвольные локаторы и clipboard
не принимаются. После UI-жеста нужно новое наблюдение; успешный жест не доказывает
достижение доменной цели. Настройку или исправление можно выполнить в этой же
сессии, если UI-интерфейс покрывает необходимые действия.

`complete_link` соединяет уже созданный одиночный вход после частичного `Input_Add`,
не создавая следующий. Другое ограниченное исправление через `dock_ui_action`
указывает ID исходной pending-операции в `recovery_operation_id` и использует свежее
наблюдение. После исправления inspect проверяет исходную операцию. Пока браузерный
вызов может выполняться, новые мутации запрещены; другой ID эту проверку не снимает.
Реестр квитанций Playwright для страницы позволяет прочитать фактическое завершение
и cleanup после потери ответа. `restore_control` исправляет только cleanup и
требует подтверждённого окончания вызова, а не простого истечения таймера.

Для pending-жеста `ui.act` с фактически завершённым вызовом и подтверждённым cleanup
доступна `accept_observed_state`. Агент сначала анализирует свежее наблюдение,
затем передаёт его `observation_id` в recover. Runtime повторно читает UI и требует
точного совпадения; сохраняет `resolution: accepted_observed_state`,
`goal_verified: false` и разрешает продолжение. Исходный жест остаётся `AMBIGUOUS`.
Этот checkpoint не доказывает успех жеста или цели; агент проверяет доменный
результат отдельно. Новый ID, незавершённый вызов или неподтверждённый cleanup
не позволяют применить эту стратегию.

Когда агент после анализа меняет цель шага или переделывает ошибочно выбранный
запрос, `abandon_operation` позволяет явно отказаться от исхода pending-операции.
Нужны законченный браузерный вызов, подтверждённый cleanup и свежий
`observation_id`; runtime повторно сверяет тот же UI и идентичность пакета.
Исходный результат остаётся `AMBIGUOUS` с `resolution: abandoned_after_observation`,
`goal_verified: false`. `SUCCEEDED` в квитанции recover подтверждает только отказ:
pending снимается, исходный ID больше не исполняется, автоматического повтора нет.
Агент выбирает новый шаг и отдельно доказывает доменный результат. Пока вызов
может выполняться, отказ запрещён. `accept_observed_state` остаётся только для
завершённого `ui.act`; ни одна стратегия не подменяет неопределённость доменным успехом.

Новые критерии приёмки включают задачу, заданную только целью, и непредупреждённый
частичный эффект в настоящем Loginom. Агент должен сам выбрать исправление и
доказать результат. Исторические **79/79** тестов и replay `rc.3` относятся к
прежним трём операциям; они не закрывают приёмку новых tools.
Для публичного допуска нового runtime к восьми прежним обязательным проверкам
добавлены `agent_partial_link_recovery`, `agent_ui_recovery` и
`transport_receipt_recovery`, подтверждённые для точной выпускаемой ревизии.

`dock_clipboard_transfer` выполняет copy → paste → проверку DOM одним вызовом.
Все сессии Dock на машине используют общую блокировку: эксклюзивно занятый
loopback-порт 46419 без протокола передачи данных. ОС освобождает его при завершении
процесса; живого владельца нельзя вытеснить по таймеру. Ожидание блокировки можно
отменить. После начала copy блокировка удерживается до финального результата
браузера; при потере ответа остаётся до закрытия клиентской среды. Смена браузерных
действий внутри одной сессии также сериализована. Остальные программы не участвуют
в этой блокировке. Прямые copy/paste вне этого инструмента применять нельзя.

Конфигурационный helper `normalizeConfigPath` переиспользован из общей библиотеки
upstream-примеров. Их credential fallback и автоматический memory capture не используются.
Дистрибутив включает эти общие модули вместе с закреплёнными зависимостями.

Native hooks используют собственную SQLite-очередь в `archive/`, читают только
активированную историю Codex/Hermes и очищают события до записи и перед отправкой.
После завершения хода очередь запрашивает штатный commit OpenViking; сервер
выполняет извлечение events/experiences без смешанного персонального профиля.
Доставка повторяется ограниченным фоновым worker и при следующих hooks. Пропавшие
незаписанные streaming fragments не объявляются восстановленными.

`deploy/loginom-dock/build-client-bundle.py` собирает самостоятельный пакет с Node,
лицензиями, зависимостями, native-плагинами и SHA-256 каждого файла. `install.sh`
запускает мастер на macOS/Linux, `install.ps1` — на Windows; ключ вводится скрыто
либо читается из явного приватного файла через
`--config-from`. `--runtime-only` предназначен для приёмки среды до native-установки.
Версии размещаются в `releases/`; `current` переключается атомарно (ссылкой на
macOS/Linux и защищённым pointer-файлом на Windows), `--rollback`
возвращает предыдущую среду в режиме `--runtime-only`. Для штатной установки
`--agent codex --rollback` или `--agent hermes --rollback` восстанавливает также
native-регистрацию выбранного профиля. Мастер сохраняет журнал перед переключением;
после аварийного прерывания та же команда повторяет восстановление. Текущие ключи
при обычном откате сохраняются; при отмене неудачной установки возвращаются её
прежние настройки. При повторной установке того же комплекта цель отката не теряется.

`--agent codex --uninstall` или `--agent hermes --uninstall` удаляет подключение
и native-плагин выбранного агента. Профили, артефакты и очередь остаются в Dock-owned
каталоге. Их удаление — отдельное решение пользователя; серверная история не меняется.
Для native-установки используется `~/.loginom-dock`; нестандартный `--home` предназначен
для изолированных runtime-only проверок. Профиль Hermes задаётся `--hermes-home`.

Обновление Hermes выполняется повторной pinned/subdirectory установкой с `--ref`
полного SHA через его штатный менеджер, с сохранением сканирования плагинов.
MCP-запись меняется штатным `hermes config set mcp_servers.loginom-dock`; результат
читается обратно. Не относящиеся к Dock подключения и memory provider сохраняются.
При работающем gateway после изменения native-пакета его нужно перезапустить.

Диагностика показывает серверную identity, три источника, проверенную ревизию skill,
доступность Loginom, число ожидающих событий этой сессии и всей установки,
возраст самого старого неотправленного события. Отсутствующее время обозначается
как неизвестное. HTTP-доступность страницы не означает успешную авторизацию.
Пакеты с `sourceDirty=true` являются кандидатами и не подходят для закреплённой
публичной установки Hermes.

Проверки: `npm test`; сквозная проверка подключает SDK-клиент к этому stdio-серверу,
читает настоящий каталог и вызывает поиск/чтение Dock и инструменты браузера.

После загрузки Chromium установщик проверяет реальный запуск без окна и прекращает
установку, если браузер не запускается. Для минимального Linux нужны системные
библиотеки Chromium: администратор может установить их командой `install-deps chromium`
через `client/node_modules/playwright-core/cli.js` из того же комплекта. Это отдельные
пакеты ОС; Node/Python пользователя не заменяются. Для обычной работы агента нужен
рабочий стол с `DISPLAY` или `WAYLAND_DISPLAY`; наличие графического окружения
проверяется отдельно и не выдаётся за выполненную авторизацию Loginom.

Целевая Linux-платформа комплекта — x64: Ubuntu 22.04/24.04/26.04 и Debian 12/13
([требования Playwright](https://playwright.dev/docs/intro#system-requirements)).
Для X11 нужен действующий `DISPLAY` и доступ к X-серверу; при нестандартном файле
авторизации — `XAUTHORITY`. Для нативного Wayland нужны socket compositor,
`WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR` и `XDG_SESSION_TYPE=wayland`.
`XDG_CURRENT_DESKTOP` сохраняет определение рабочего стола Chromium, в том числе
выбор нативных настроек прокси. Bridge передаёт эти шесть переменных только на Linux.
XWayland и нативный Wayland проверяются отдельно: успех X11 не подтверждает оба.
Текущие доказательства и ограничения приёмки перечислены в
[плане Linux](../docs/plans/2026-09-15-loginom-dock-linux-maintenance.md).
