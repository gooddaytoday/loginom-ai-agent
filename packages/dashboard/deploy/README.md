# Установка и обслуживание Dashboard для Loginom Studio

Офлайн-комплект рассчитан на одну работающую штатную контейнерную установку Loginom Server и Studio. Нижние поддерживаемые версии для Dashboard:

- Docker Engine 29.1.3 с Compose 2.40.3+ds1.
- Rootless Podman 5.6.2 с podman-compose 1.5.0. Запускайте команды от владельца штатной установки Loginom. Нужны настроенные диапазоны UID/GID для rootless, cgroup v2, пользовательский cron и conmon с параметрами `--log-rotate` и `--log-max-files` (например, conmon 2.2.1).

На сервере нужны Bash, curl и системные утилиты Linux, включая `tar` и `sha256sum`. Серверная проверка использует Node из образа.

## Распаковка и установка

Укажите абсолютный путь к полученному архиву в переменной `archive`. Распакуйте его от имени оператора в новый приватный каталог с сохранением режимов файлов. Помощник `check-release.mjs` поставляется с режимом 0644 для чтения непривилегированным пользователем контейнера. Продолжайте после успешной проверки всех контрольных сумм.

```sh
unpack=$(mktemp -d)
tar -xpf "$archive" -C "$unpack" &&
  cd "$unpack/loginom-dashboard" &&
  sha256sum -c SHA256SUMS
```

Замените `studio.example.org` на имя Studio, доступное серверу и рабочим местам. При нескольких именах повторите `--public-host` для каждого. В обычном режиме первое имя используется для адреса приложений. Порт приложений по умолчанию 8101 должен быть доступен серверу и рабочим местам. Другой порт задаётся через `--app-host-port`. Для HTTPS серверный curl и браузер должны доверять сертификатам Studio и хоста приложений.

Если нужен строгий режим, добавьте к команде `install` параметры `--strict --app-host-domain apps.example.net --app-host-cert /path/in/apache/cert.pem --app-host-key /path/in/apache/key.pem`. Используйте отдельный регистрируемый домен приложений. Пути к сертификату и ключу указываются внутри контейнера Apache. Для проверки пары требуется OpenSSL на сервере. Для работы в строгом режиме используйте браузер на Chromium 152 или новее.

Docker

```sh
sudo docker load -i image.tar &&
  sudo ./containers.sh install --engine docker --public-host studio.example.org
```

Rootless Podman

```sh
podman load -i image.tar &&
  ./containers.sh install --engine podman --public-host studio.example.org
```

## Проверка сервера

После `install` или `start` дождитесь HTTP 200 на `/dashboard/shell.js`. В `studio_origin` укажите фактическую схему HTTP или HTTPS, одно из имён `--public-host` и опубликованный порт Studio, если он отличается от стандартного. Используйте адрес без `/app/`.

```sh
studio_origin=https://studio.example.org
curl --fail --silent --show-error --max-time 10 --output /dev/null \
  --write-out '%{http_code}\n' "$studio_origin/dashboard/shell.js"
```

После ответа 200 выполните `sudo ./containers.sh check --engine docker` для Docker или `./containers.sh check --engine podman` для rootless Podman. Команда проверяет собственную пробную публикацию и её очистку. В конце она просит отдельно проверить доступ с рабочей машины.

## Проверка клиента

На рабочей машине подготовьте исходники той же версии, Bun в `PATH` и установите из `packages/loginom-runtime/client` зависимости runtime и Playwright командой `npm ci --ignore-scripts`. Укажите путь к закреплённому Node 24.19.0 в `LOGINOM_AI_AGENT_TEST_NODE` и каталог браузеров с Chromium revision 1246 в `PLAYWRIGHT_BROWSERS_PATH`. Эти инструменты и `check-studio.mjs` входят в подготовку рабочей машины, серверный комплект содержит только свои средства проверки.

Под тестовой учётной записью откройте небольшую отдельную копию пакета. Выполните узел штатной командой Studio, убедитесь, что первый табличный выход содержит строки, и сохраните пакет. Проверьте, что для узла именно этой копии есть готовая публикация, которая выводит все живые строки первого выхода без преобразований в `tbody`. Проверка закрывает пакет в Studio, поэтому сохраните все изменения до её запуска.

Укажите путь к приватному JSON с правами 0600 вне Git. Поля JSON — `url` (например, `https://studio.example.org/app/`), `username`, `password` или `secrets.password`, `packagePath`, `unit` и `nodeName`. Команда из `packages/dashboard`:

```sh
export DASHBOARD_STUDIO_CONFIG="$HOME/private/studio.json"
"$LOGINOM_AI_AGENT_TEST_NODE" deploy/check-studio.mjs 7.4.2
```

Проверка сравнивает строки в Dashboard с выходом узла, закрывает пакет и выполняет выход из Studio.

## Журналы, остановка и запуск

До остановки или обновления попросите пользователей закрыть Dashboard в браузере. Сохраните журналы ролей `web`, `publisher` и `builder` в приватный каталог. При остановке контейнеры удаляются вместе с журналами.

В Docker для каждой роли хранится до трёх файлов по 10 МиБ. Команда выгружает доступный журнал роли `web`. Повторите для остальных ролей. В примере `log_dir` указывает на подготовленный приватный каталог.

```sh
sudo docker logs loginom-dashboard-web > "$log_dir/web.log" 2>&1
sudo ./containers.sh stop --engine docker
sudo ./containers.sh start --engine docker
```

В Podman для каждой роли хранится активный файл до 10 МиБ и две ротированные копии. `podman logs` показывает текущий файл. Для полной доступной истории узнайте путь командой `podman inspect --format '{{.HostConfig.LogConfig.Path}}' loginom-dashboard-web` и сохраните существующие сегменты `.2`, `.1` и активный файл. Повторите для остальных ролей.

```sh
./containers.sh stop --engine podman
./containers.sh start --engine podman
```

После запуска дождитесь готовности служб и повторите серверную и клиентскую проверки. При сбое проверьте журналы и доступность Studio и хоста приложений с рабочей машины. Если серверная проверка не подтвердила очистку, сохраните напечатанное имя собственной пробы. Удаляйте только её исходный JSON и её пустые каталоги, если они остались после аварийного завершения. Каталоги сборок и очередь очищает publisher.

## Обновление и ручной откат

1. Сохраните прежний комплект, параметры установки, журналы и резервную копию пакетов `.lgp` и JSON публикаций в UserStorage. Зафиксируйте контрольные суммы пакетов и публикаций. Распакуйте новый архив в отдельный каталог и проверьте его суммы до остановки.
2. При смене `image.ref` выполните из **старого** комплекта `sudo ./containers.sh uninstall --engine docker` или `./containers.sh uninstall --engine podman`. Удаляются интеграция и состояние сборок Dashboard. Публикации остаются в UserStorage, прежний образ сохраняется для отката.
3. Из нового комплекта загрузите образ и выполните `install` с прежними параметрами хостов, порта и режима. Сохранённые совместимые публикации будут пересобраны. После готовности сверьте суммы `.lgp` и JSON, повторите серверную и клиентскую проверки.
4. Для отката выгрузите журналы кандидата и выполните `uninstall` из его комплекта той же командой. Загрузите и установите сохранённый предыдущий комплект с прежними параметрами, дождитесь пересборки публикаций, сверьте контрольные суммы пакетов и JSON и повторите обе проверки.
