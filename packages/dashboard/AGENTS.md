# Платформа dashboard

Снимок и папка чата, сборка и публикация — в `src/agent`, loopback-сервер и страница черновика — в `src/draft`, три примера — в `examples`. Службы API и хоста приложений — в `src/web`, схемы обмена — в `src/contract`, доверенная оболочка и адаптер Studio — в `src/shell`, SDK v1 — в `src/sdk/loginom.ts`. Bun собирает `dist/server.mjs` для Node и единый `dist/shell.js` для браузера. Dashboard — недоверенный код: он работает на отдельном origin в `sandbox="allow-scripts"`, получает данные через MessagePort и не меняет параметры. Пакет `.lgp` интеграция не записывает.

Для разработки приложений соблюдайте [инструкции приложений](../../dashboard/AGENTS.md). Desktop/CLI один раз получают снимок с настроенного стенда и создают `<данные бэкенда>/dashboards/*/{work,control}`. Модель читает `work/` и пишет только в `work/src/`; привязка, сборки и набор шаблона ей недоступны. `template/` содержит lockfile и файлы платформы (`index.html`, `tsconfig.json`, `vite.config.mjs`, `resolver.mjs`, `scan.mjs`): сборщик копирует только разрешённые исходники поверх платформы и напрямую запускает `tsc`/Vite встроенным Node, без `npm run` приложения. Исключение границ модулей: `draft` использует `web/apps.ts` и `shell/frame.ts`.

- Публикация M4: `contract/publication.ts` проверяет строгий JSON v1 целиком (UTF-8, до 1 048 576 байт, до 200 файлов, `src/main.tsx`). `preparePublish` сохраняет проверенные `src/` и `dist/` в папке операции, формирует JSON без образца; `finishPublish` передаёт эти байты callback хоста и ждёт свой файл по имени/sourceHash до 2 минут. Подтверждённый `written` с точным хешем обновляет `control.base` под коротким snapshot lock, сохраняя более новую основу и поля свежего снимка. Только `ready` даёт `published` и удаляет прежний образец с проверкой ID снимка. `changed` требует нового подтверждения. Локальная публикация M3 в `builds` и её `publish.sqlite` удалены; `snapshot.sqlite` остаётся.
- `builder/build.ts` содержит общую сборку для agent и серверного builder; локальные `current` и очистка двух сборок остаются только в agent. Publisher обходит UserStorage каждые 10 секунд, проверяет физическую привязку, выдаёт одну задачу и принимает ограниченную собственную копию результата. Один `builds/state.json` хранит статусы по пути файла; web выводит текущую ready по полному ключу и статус своего файла отдельно от последнего. При старте publisher удаляет прежние jobs, перевыдаёт только незавершённое с новым ID и сохраняет проверенные ready/failed. Каждый обход удаляет выходы без входной задачи и сборки без оставшихся ready-ссылок. Builder не воссоздаёт удалённый корень output; права подкаталога выставляет до добавления детей, чтобы publisher с другим UID мог удалить незавершённый результат.
- `dist/server.mjs web|publisher|builder` — три роли одного образа. `dev-master.sh` требует `--config <локальный JSON>` вне Git; существующие Server/Studio/network/UserStorage проверяются по именам и метке, publisher получает UserStorage RO и UID/GID процесса Loginom, web/builder non-root. Схема и минимальный config — [рецепт M4](../../dashboard/stand/README.md#отдельная-dev-пара-m4). Локальные исходники и основа сохраняются при новом снимке; при отсутствии src pre-chat Host скачивает валидную публикацию либо подтверждает отсутствие для шаблона. Отсутствующее поле base старого M3 означает неизвестную основу, null — подтверждённое отсутствие. Конфликт требует нового одноразового согласия. Разовый переход M3 сохраняет полный UserStorage, локальные src/control и origin; после свежего снимка требуется явная перепубликация. Старые bundles не восстанавливают исходники.
- Из `packages/dashboard`: `bun typecheck`, `bun run test` (сборка, отдельное покрытие web и publisher/builder не ниже 90% строк и функций, контракт и SDK), `bun run check:size`, `bun run test:browser` (браузерные проверки, страница, самопроверка, публикация и `test/build` — шаблон, три примера и ограничения сборки). Укажите `LOGINOM_AI_AGENT_TEST_NODE` и `PLAYWRIGHT_BROWSERS_PATH` для закреплённых Node и Chromium из `packages/product/loginom-release.json` и lockfile runtime. Зависимости шаблона: `npm ci --ignore-scripts` из `template`. Для временных файлов используйте подготовленный `$TMPDIR` вне Git.
- Стенд из корня: `./packages/dashboard/deploy/dev-master.sh install --config <файл> [--strict] [--cli-button]`, `check --config <файл>`, `uninstall --config <файл>`. Перед изменением стенда обязательны `bash -n` и ShellCheck. Credentials для браузерного `check` передаются только через `DASHBOARD_STUDIO_CONFIG`. Установленная приёмка M3 остаётся исторической; текущий порядок и приёмка M4 описаны в [runbook M4](../../docs/testing/loginom-ai-agent/dashboard-m4.md).
- Release Task 1: `deploy/containers.sh install --engine docker --public-host <host> [--app-host-port <port>]` обнаруживает одну штатную установку и добавляет только атомарный `dashboard.site.conf`, не изменяя vendor compose/index/client.json. `startDashboard(env, shell)` принимает установленные bytes; web entry читает соседний `shell.js`. HTTPS app-origin требует private `DASHBOARD_TLS_UPSTREAM` до listeners: TCP TLS 8101 → Apache 8444 → private app HTTP 8102; API 8100 остаётся Studio-only. SRI/data-атрибут содержит фактический Studio HTTPS-порт, LookupResponse/MessagePort v1 прежние. Docker install/check используют сохранённую установку, helper из release-каталога и Node образа без сети; отдельный клиентский `check-studio.mjs 7.4.2` требует установленный shell, ready и живую таблицу. Task 2 принят, mandatory 0. Task 3 lifecycle/переносимый архив и fresh offline Docker server/client проверены, независимое ревью ожидается; Task 4–5 не начинались. Фактические source/container/installed проверки и ограничения — [runbook M5](../../docs/testing/loginom-ai-agent/dashboard-m5.md).
- API хранит до 100 одноразовых снимков на 15 минут: `POST /dashboard/snapshots`, затем один `GET /dashboard/snapshots/<ID>`. `targets` и `current` удалены. Образец — до 100 строк и 512 КиБ; ключ привязки содержит путь пакета, GUID сценария и узла, без origin.
- Без решения владельца нельзя добавлять `allow-same-origin`, команды приложения или новые типы сообщений, ослаблять резолвер и проверку импортов до `tsc`, CSP и loopback-границы сервера черновика, одноразовость снимка, заголовки хоста приложений, расширять `frame-src` Studio, менять режимы и лимиты или заменять принудительный CSP на Report-Only. `style-src` остаётся без `unsafe-inline`: реальные React/Recharts проверки прошли без запасного варианта.
