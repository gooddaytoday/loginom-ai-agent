# Артефакты MAS

Инструмент `artifacts.py` обслуживает собственные артефакты агента; Multica продолжает управлять заданиями, очередью, рабочими каталогами и журналами. Linux — проверяемая среда очистки. Все четыре файла `artifacts.py`, `handoff.py`, `update.py`, `supplement.py` устанавливаются рядом из одного проверенного набора. Token берётся только из текущего окружения, операторский token агентам не передаётся.

## Владелец и размещение

Agent mode получает `MULTICA_AGENT_ID`, `MULTICA_TASK_ID`, `MULTICA_WORKSPACE_ID` и `MULTICA_SERVER_URL`. Смена владельца запрещена. Для native пути текущий running run проверяется по списку задач владельца независимо от карточки старого артефакта, а оба native marker подтверждают именно его владельца и карточку. Человеческая разовая миграция использует явные `--owner <UUID> --workspace <UUID>` перед подкомандой; task token не допускается в этот режим даже после удаления task-переменных.

Состояние, блокировки и квитанции находятся в `~/.local/state/loginom-multica/artifacts/<workspace>/<agent>/`. Каталог защищён от полного GC окружений Multica. Блокировки лежат вне удаляемых объектов и сохраняются. Приватные материалы и токены не включать в артефакт или квитанцию.

Перед созданием второй сборки подготовить `expected.json` **вне checkout**, используя фактический `cliSourceSnapshot` выбранных чистых исходников продукта, текущий channel, capabilities и закреплённые зависимости сборщика. Обязательные поля: `sourceCommit`, `sourceTreeSha256`, `sourceDirty=false`, `channel`, `platform`, `arch`, `capabilities`, `dependencies`. Не копировать идентичность старой сборки с заменой одного SHA. При изменении только docs/tests/проверяющего инструмента разрешён прежний exact product: идентичность вычисляется из его исходников, SHA инструмента/проверки фиксируется отдельно. Это не новый runtime PASS; итоговая приёмка по RUNBOOK по-прежнему требует согласованного exact кандидата.

```sh
python3 artifacts.py find --expected /private/expected.json
python3 artifacts.py preflight
python3 artifacts.py allocate --issue <UUID> --name origin-candidate
```

`find` показывает совпадения собственных сборок; наличие совпадения не подтверждает целостность. Перед исполнением обязателен `use`. Новую сборку создавать по возвращённому `destination` штатным build-cli.ts; директория назначения ещё не существует. Сборщик, его проверки и контракт standalone CLI сохраняются. Использовать `--no-archive` для промежуточного кандидата.

```sh
python3 artifacts.py register --issue <UUID> --path /absolute/candidate --kind build
python3 artifacts.py select --current <ID> --previous <ID-previous-working>
```

`select` атомарно сохраняет текущую и предыдущую проверенную рабочую сборки одной карточки. Предыдущую выбирать по результату, не по времени файла. Закрепления, final, unresolved и legacy сохраняются. Дополнительные источники, зависимости и отчёты регистрируются с `--kind source|dependencies|evidence`; evidence требует `--sha <40-hex>`. Основной checkout, профили, credentials и журналы операций не регистрировать как удаляемый мусор. Пересекающиеся каталоги не допускаются.

Для сохраняемой старой сборки внутри native окружения, после подтверждённого окончания использования и снятия всех pins/legacy, выполнить `migrate --id <ID>`. Команда под исключительной блокировкой атомарно переносит целую сборку в постоянное хранилище, повторно проверяет payload и сохраняет карту старого/нового пути. Current/previous/final не снимаются. Неподтверждённые ресурсы и unresolved не переносятся. Исторические отчёты с реально испытанным путём не переписываются. Это нужно до завершения карточки: штатный terminal GC Multica удаляет native окружения целиком.

## Передача и использование

```sh
python3 handoff.py --issue <UUID-получателя> --agent <UUID-роли> \
  --sha <40-hex> --scope <действие> --message /private/next.txt \
  --receipt /private/handoff.json --artifact <ID>
```

`--artifact` повторяется для каждого необходимого объекта. Перед отправкой проверяются и сохраняются закрепления; дескрипторы с путём, source identity и хешем manifest входят в обычное сообщение. Ключ назначения и существующая очередь не меняются. Потерянный ответ, отсутствие проекции, отказ или pending review сохраняют закрепления. Точный повтор не создаёт второе поручение. Для прежнего назначения без дескрипторов использовать обычный read-only `--existing-comment` без `--artifact`; его жизненный цикл разбирается отдельно.

Для docs/tests/checker-only передачи на новом SHA добавить `--product-sha <точный прежний product SHA>`. Source-SHA поручения остаётся SHA изменённого инструмента, Product-SHA и дескриптор идентифицируют реально используемую сборку. Без этого явного разделения несовпадение SHA запрещено. Runtime changes не объявляются проверенными на прежнем продукте.

```sh
python3 artifacts.py use --id <ID> --producer <UUID-владельца> \
  --expected /private/expected.json -- /absolute/run-checks
```

Полная проверка манифеста выполняется перед запуском; переменная `LOGINOM_ARTIFACT_PATH` указывает на проверенную сборку. Чужая сборка доступна только получателю закреплённого поручения. На время команды удерживается shared lock; её дочернему процессу не передаются `MULTICA_*`. Рабочие исходники, браузерные/CLI профили и доказательства каждого участника остаются отдельными. Успешное завершение `use` не является приёмкой.

После окончания всех действий над артефактом получатель добавляет к своему обычному результату две отдельные строки:

```text
Artifact-release: <ID>
Handoff-ID: <ключ-из-передачи>
```

Это сообщение заканчивает существующий этап, без отдельного служебного запуска. До завершения receiving run освобождение запрещено. Владелец при следующей безопасной границе выполняет:

```sh
python3 artifacts.py release --id <ID> --handoff <ключ> --result-comment <UUID>
python3 artifacts.py retire --id <ID> --reason 'Заменён и больше не нужен всем получателям'
python3 artifacts.py cleanup
python3 artifacts.py cleanup --apply
```

`release` сверяет автора результата, исходный completed run, точную receipt и привязку к поручению. Исторический failed run не становится PASS; он сохраняется в Multica. Повтор освобождения идемпотентен. Активный successor, чужой результат и неизвестная доставка запрещают освобождение. Самостоятельные временные объекты без получателей владелец может retire после завершения собственного этапа.

## Хранение и очистка

- Current, previous, final и unresolved сохраняются независимо от возраста. `final` нельзя снять общей командой; unresolved снимать только после доказанного устранения причины.
- Заменённые сборки, источники и зависимости — 24 часа после retire, выполненного после освобождения всех получателей. Новое собственное использование отменяет retire.
- Промежуточные успешные evidence — 7 дней после завершения этапа/retire. Итоговые доказательства и нерешённые ошибки отмечать final/unresolved.
- Cleanup проверяет владение и неизменность пути, native markers, mounts, процессы runtime-пользователя и дочерние процессы, dirty/unpublished Git и operation evidence. Привилегированные штатные systemd/pam/SSH supervisors отделены по argv/cgroup/родителю; их рабочие дочерние процессы не исключаются. Неинспектируемый worker запрещает удаление.
- При занятой блокировке или неизвестном состоянии объект сохраняется с причиной. Сборки удаляются целиком. Git worktree удаляется штатно; checkout с другими worktree, уникальными refs или reflog сохраняется.
- Сетевую сверку старых поручений выполнять вне блокировки каталога владельца, с ограниченным параллелизмом чтений. Затем перечитывать актуальные pins/protections; новые закрепления других карточек не блокируются сетевым ожиданием.
- Dry run не удаляет данные. `--apply` сохраняет intent до удаления и приватную квитанцию после него. Блокировки и catalog не удаляются.
- Ниже 10 ГиБ `preflight` сначала применяет разрешённую очистку, затем запрещает новую тяжёлую сборку при сохраняющемся дефиците. Продолжать безопасный анализ и записать дефицит в текущей карточке; защиту данных не ослаблять.

Очистка выполняется каждым агентом в конце этапа для всех собственных карточек. Таймеров и новых служебных запусков нет: при полном простое срок будет проверен при следующем запуске владельца.

## Накопленные данные и настройки daemon

Ссылки на `parent` в явно указанном Git diff исходного `.mjs/.ts/.py` файла сохраняют исходники, но не требуют хранения всех бинарных копий. Это разрешено только после операторской привязки `source_history: {repo, ref}` в приватном подтверждении: канонический Git repo находится в native области, `refs/cleanup/` указывает на точный sourceCommit, и ссылка повторно проверяется перед очисткой. Без такой привязки, при пропаже истории, для Product-SHA, произвольного SHA, пути/ID/манифеста или упоминания CLI/installed артефакт сохраняется. Ссылки на source артефакты трактуются по прежнему правилу. Pins, возраст, процессы, payload и остальные защиты не ослабляются.

Собственное human-only поручение на очистку не является потребителем перечисленных файлов. Оператор может зарегистрировать его через `maintenance --receipt /private/verified-supplement.json`. Проверяются verified read-back, точный fingerprint содержимого, автор member, исходный task/parent и агент-владелец. Это касается только проверенного control сообщения «Владелец явно возобновил очистку MAS.»; само сообщение и журнал сохраняются. Изменение текста или автора возвращает защиту. Другие поручения, pending/UNKNOWN и pins остаются защищёнными.

Каталоги native происхождения автоматически получают `legacy-unreconciled`; регистрация не доказывает их ненужность. После адресного разбора владелец сохраняет приватное evidence подтверждение с точными owner/workspace/issue/path, `all_consumers_released=true`, `unresolved=false` и ссылками в `evidence`; затем снимает legacy через `protect --remove legacy-unreconciled --confirmation <file>`. Unknown, исходные непринятые FAIL и необходимые воспроизводители не освобождаются.

Разовая операторская миграция чистых вспомогательных source copies и полностью проверенных заменённых сборок может использовать `historical_release` с issue/comment/task IDs и `reviewed_no_consumers=true`. Инструмент повторно проверяет реальный completed review, автора, положительный заголовок и SHA. Для сборки первый SHA положительного заголовка должен совпасть с её sourceCommit; подтверждение дополнительно фиксирует исходный manifest_sha256. Полный payload проверяется при регистрации и перед удалением. Началом хранения становится дата проверенного исторического результата. Такой перенос даты запрещён для evidence, dependencies и для agent mode. До удаления отдельно проверить текущие checkpoint/поручения, current/previous, воспроизводители и всех потребителей. Это освобождение старого завершённого этапа, а не полная приёмка узла.

Для Multica 0.6.1 сохранить GC enabled, interval 2h, terminal TTL 24h, orphan TTL 72h, artifact TTL 12h и остальные текущие сроки. Установить `MULTICA_GC_ARTIFACT_PATTERNS=.next,.turbo`, `MULTICA_GC_COMPLETED_TASK_TTL=0` в окружении запуска daemon. Не добавлять build/dist/resources в generic patterns. `node_modules` внутри сохранённого CLI являются частью продукта; повреждённые старым GC кандидаты помечаются повреждёнными и не используются.

Настройки требуют запуска нового daemon: менять только после подтверждения отсутствия active runs, сохраняя его profile, limits и queue cadence. Перед перезапуском перечитать состояние, после — проверить effective env и runtime identity. Новые инструкции применять на безопасных границах без массового rerun, смены моделей и новых прав.
